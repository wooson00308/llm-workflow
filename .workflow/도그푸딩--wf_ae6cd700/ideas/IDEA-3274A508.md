역할 세션의 동시 실행 제한이 장부 기준이라 실제 프로세스 수를 막지 못한다. 2026-08-19 사용자 발견이다.

문제: 프로젝트당·역할당 동시 세션 제한이 실행 현장에서 지켜지지 않는다. 실측(2026-08-19 밤): 한 프로젝트에서 역할 세션 7개가 동시에 돌았다(개발자·아키텍트·기획자 혼합). 경로는 이렇다.

- 런타임이 감독 프로세스 신원 확인에 실패하면(허위 즉살, heartbeat #38, reason=supervisor_identity_unverified, 당일 44건) 실행 기록을 recovery_required로 내린다. 이때 죽는 것은 장부뿐이고 실제 세션 프로세스는 계속 작업한다.
- 동시 실행 계산은 장부의 활성 상태(reserved·queued·running·paused)만 세므로, recovery_required로 빠진 순간 슬롯이 즉시 빈다. 디스패처가 그 자리에 새 세션을 또 띄운다.
- 장부가 놓은 세션은 남은 정리 절차(process_termination·event_close·lease_release)가 이행되지 않은 채 살아서 일하고, 앱에는 앱 밖 세션으로 보인다. 배정 경로 밖에서 작업이 진행되는 셈이다.
- 이 순환이 반복되며 실프로세스 동시 수가 제한과 무관하게 쌓인다. 허위 즉살이 잦을수록(13분당 1건꼴) 쌓이는 속도가 빨라진다. API 사용량 소진과 병렬 작업 충돌 위험이 있는 상태다.

원하는 것:

- 동시 실행 판정이 장부 상태만이 아니라 실제 살아 있는 프로세스를 함께 세도록 한다. recovery_required라도 프로세스가 생존해 있으면 슬롯 점유로 취급한다.
- recovery_required로 빠진 실행의 남은 정리 절차가 실제로 수행되기 전에는 그 슬롯에 새 세션을 띄우지 않는다.
- 신원 불일치 자체의 수정(#38)과는 별개 과제다. 즉살 오판이 또 나더라도 제한이 뚫리지 않는 구조를 만드는 것이 목적이다.
- 수정 지점은 런타임(claude-heartbeat) 쪽이다. 런타임 이슈는 heartbeat #39로 등록되어 있다. S071·런타임 #37처럼 앱 기획과 런타임 이슈를 짝지어 진행하는 방식과, 구체 판정 방식은 기획에서 확정한다.
