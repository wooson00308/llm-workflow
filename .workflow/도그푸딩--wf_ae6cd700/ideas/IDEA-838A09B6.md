에이전트가 쓰는 문서에 비개발자(결정권자)용 요약 레이어를 계약으로 의무화하자. 기준 은유는 사용자가 직접 정했다 — "회사에서 기획자가 사업부 승인을 받기 위해, 사업부가 보기 편하게 쓰는 문서" 수준. 결정권이 사용자에게 있는 워크플로우인데 결정 재료(기획서·QA 대기 보고서·막힘 사유)가 전부 작업자 언어로 쓰여 있어, 비개발자는 섣불리 선택할 수 없다는 실측 문제 제기에서 출발했다.

사용자가 이미 내린 방향 결정 셋 (기획자는 이걸 되묻지 않아도 된다):

1. **요약은 그 문서를 쓴 세션이 쓴다.** 앱이 LLM을 호출해 요약을 생성하는 방향은 사용자가 명시적으로 기각했다("앱이 LLM을 컨트롤하는 건 별로"). 지금 앱에 LLM 호출이 0건인 구조도 유지된다.
2. **파일은 하나, 양식은 독자별.** 요약 문서를 따로 두지 않는다 — 단일 원천 원칙(file-contract의 "조회 시점 파생, 어디에도 저장하지 않는다")과 드리프트 방지. 문서 안에 사용자용 섹션이 있고, 어떤 독자에게 어떤 양식으로 보이는지는 앱 표시의 몫(IDEA-61927447).
3. **역할별 강도는 다르되 면제는 없다.** 기획자 문서가 가장 엄격하다 — 승인 게이트의 재료라서다. 개발·아키텍트 문서도 배제하지 않는다. 사용자 원문 취지: "그 역할을 받은 세션도 최대한 양식 맞춰줘야지, 일하는 작업자인데 책임을 다하게끔."

기획 재료 (TL 의논에서 나온 구체안, 채택 여부는 기획자 몫):

- 요약 섹션 작성 규칙을 기계 검증 가능하게: 코드 식별자(백틱 토큰·snake_case·camelCase·파일 경로) 0건 같은 조건은 이 저장소가 쓰는 검증 가능한 완료 조건 어법에 맞는다. 가독성·가시성·고유명사 최소화가 사용자가 짚은 세 축이다.
- 드리프트 방지는 기존 어법 재사용: "상태를 전이하는 세션은 같은 편집에서 요약도 갱신한다" — history 규칙(같은 편집에서 append)과 같은 구조.
- QA 동선 절 의무화: 개발 보고서의 "사용자 QA 제안"(REPORT-TASK-096-DEV 선례)은 지금 관례지 계약이 아니다. 클릭 동선("어느 화면 → 어느 버튼 → 무엇이 보이면 정상")을 계약으로 올린다. 화면 없는 작업(TASK-104·106 류)은 "자동 검사로 닫혔고, 확인 도장은 검사 수치를 신뢰한다는 뜻"을 평문으로 말하게 한다.
- 구현 자리는 역할 계약 문언 + 규칙 자산 버전 인상 — TASK-098·102·111이 선례다.
- 소급 기입은 하지 않는다(SPEC-032 소급 제외 선례). 기존 문서 350여 건은 요약이 없고, 표시 폴백은 IDEA-61927447 몫.

경계: 이 아이디어는 문서 계약(무엇을 쓰게 할 것인가) 쪽이다. 앱이 그것을 어떻게 보여주는가(기본 뷰·토글·구조 파생 평문화)는 IDEA-61927447로 갈랐다 — 파일 무리가 완전히 갈린다(계약: project_instructions.rs·역할 계약 / 표시: 프론트엔드).
