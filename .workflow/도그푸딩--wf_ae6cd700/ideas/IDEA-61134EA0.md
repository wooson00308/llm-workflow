개발 작업이 `blocked` 상태일 때 작업 상세의 우측 사이드바에 현재 막힌 이유와 재개 조건을 보여 준다. QA 대기 작업에서 확인 동선과 사용자 조작을 우측 패널에 모아 보여 주는 것처럼, 막힌 작업도 사용자가 원문 전체를 읽거나 개발 보고서를 찾아가지 않아도 "왜 멈췄고 무엇이 해결돼야 다시 시작하는지"를 같은 자리에서 확인할 수 있어야 한다.

현재 실측 사례는 TASK-S051-04다. 작업 문서의 결정권자 요약과 개발 보고서에는 예약 소유권·역할 지시 전달 계약, 실행 PID·이벤트 복구 계약이 없어 구현을 계속할 수 없다는 이유가 적혀 있다. 선언된 선행 TASK-S051-01·02·03도 모두 `qa_waiting`이라 아직 워크플로 기준으로 완료되지 않았다. 그러나 앱의 우측 패널은 `qa_waiting`이 아닌 모든 작업에 상태명과 "QA 대기 상태가 되면 확인 도구가 활성화됩니다"라는 공통 문장만 보여 준다. 사용자가 보고 있는 작업이 `blocked`여도 막힌 이유는 그 패널에 나오지 않는다.

이 문제는 SPEC-039가 의도적으로 남긴 범위와 이어진다. 그 기획은 의존성과 파일 겹침처럼 앱이 이미 계산할 수 있는 구조적 막힘을 평문으로 보여 줬지만, 작성자가 기록한 `blocked` 상태의 사유는 구조화된 필드가 없어서 제외했다. 이번 아이디어는 판정 규칙을 바꾸지 않고, 작성자가 남긴 현재 사유를 계약에 넣어 우측 패널에서 읽히게 한다.

막힘 사유의 문서 계약 후보는 개발 작업 본문의 고정 절이다.

```markdown
## 막힌 사유

- 막힌 지점: 지금 진행할 수 없는 구체적인 이유
- 필요한 해결: 누가 무엇을 제공하거나 바꿔야 하는지
- 재개 조건: 어떤 상태가 되면 다시 개발을 시작할 수 있는지
- 관련 대상: 선행 작업이나 외부 의존이 있으면 그 식별자
```

개발자가 작업을 `blocked`로 전환할 때 상태, 이력, 갱신 시각과 같은 편집에서 이 절을 현재 사실로 작성한다. `blocked`에서 벗어날 때 절을 삭제하지 않고 마지막 막힘 기록으로 보존하되, 우측 패널은 현재 상태가 `blocked`일 때만 이를 현재 사유로 보여 준다. 같은 작업이 다시 막히면 현재 절을 새 사유로 갱신하고 이전 차단의 상세 기록은 당시 개발 보고서와 상태 이력에 남긴다.

우측 사이드바는 작업 상태에 따라 역할을 바꾼다.

- `blocked`: "진행이 막혔습니다" 제목, 막힌 지점, 필요한 해결, 재개 조건, 관련 대상을 보여 준다.
- `qa_waiting`: 지금처럼 확인 동선, 메모, 완료·되돌리기 조작을 보여 준다.
- 그 외 상태: 지금처럼 현재 작업 상태를 보여 준다.

구조화된 `막힌 사유` 절이 없는 기존 blocked 문서는 `결정권자 요약` 절을 폴백으로 보여 준다. 그 절도 없으면 사유를 추측하지 않고 "구조화된 막힘 사유가 없습니다"라고 알린 뒤 원문 위치를 안내한다. 앱이 의존성·겹침에서 이미 아는 구조적 원인이 있으면 같은 패널에서 별도 항목으로 보여 줄 수 있지만, 작성자 사유와 같은 문장을 중복하지 않게 한다.

관련 대상이 실제 작업 문서로 확인되면 제목과 현재 상태를 함께 보여 주고 바로 열 수 있게 한다. 문서가 없거나 외부 저장소 의존이면 값을 지어내지 않고 작성된 식별자와 설명만 표시한다. 사유의 갱신 시점도 보여 주어 오래된 차단 정보인지 판단할 수 있게 한다.

첫 범위는 표시와 문서 계약이다. 우측 패널에서 사용자가 작업 상태를 직접 `todo`로 되돌리거나 lease를 정리하는 기능은 포함하지 않는다. 차단 해제는 역할 계약과 기존 상태 전이 절차를 그대로 따른다. LLM으로 본문을 요약하지 않으며 Markdown의 정확한 절과 라벨만 로컬에서 읽으므로 추가 토큰 비용이 없다.

기획 단계에서 정할 것은 막힘 사유 절의 정확한 형식, 기존 결정권자 요약 폴백, 여러 번 막힌 작업의 기록 보존 방식, 구조적 의존·겹침 정보와 작성자 사유의 중복 제거, 관련 작업 바로가기와 작은 화면 배치다.
