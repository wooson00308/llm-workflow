하트비트 데몬의 설치와 업데이트를 앱이 직접 실행하게 하자 — VSCode 익스텐션처럼. 안내문과 명령 복사가 아니라 버튼 하나로 설치되고 버튼 하나로 업데이트되는 것이 목표다.

현재 상태: SPEC-034(TASK-107~109)가 연동 카드에 갱신 안내를 넣었지만 범위는 표시·안내·복사까지다. 실행형은 당시 신중선으로 남겼다 — SPEC-024 R5("앱이 heartbeat migrate를 대신 실행하지 않는다"), IDEA-FCDDD4DE의 "실행 버튼은 확인 필요로 올리는 편이 맞다". 이 아이디어는 그 선을 옮긴다. 사용자가 2026-08-05에 명시적으로 결정했다: "가이드 제공해주는 게 아니라 설치랑 업데이트 둘 다 VSCode 익스텐션처럼 제공해줬으면 해서". 기획자는 이전 신중 결정과의 관계를 확인 사실로 적되, 실행형 자체를 되묻지 않아도 된다 — 그 결정이 이 아이디어의 존재 이유다.

데몬 쪽 선행(별도 진행 중): 앱이 실행형을 만들려면 데몬 계약에 지금 없는 표면이 필요하다. TL이 claude-heartbeat 저장소에서 병행 개발한다 —
1. 버전 표면: 데몬이 자기 버전을 기계가 읽는 자리(state.json 항목 또는 `heartbeat --version`)에 내놓는다. "업데이트 필요" 판단의 원천. 버전 문자열로 "판정"하지 않는다는 SPEC-024의 결정은 설치 판정에 대한 것이었고, 정보 표시·업데이트 제안은 별개라는 것이 IDEA-FCDDD4DE가 이미 가른 자리다.
2. update 명령: 멱등이고 종료 코드가 신뢰 가능한 `heartbeat update`. 코드 갱신(git pull)·의존성 반영·서비스 재기동까지의 순서와 실패 처리를 데몬이 소유한다. 08-05의 체크아웃-프로세스 불일치 사건(디스크는 main, 메모리는 v0.8.0 — 재시작하면 잡 전체 소실)이 보여줬듯, 갱신과 재기동 사이의 원자성이 이 명령의 존재 이유다.
3. install 명령 정비: 기존 `heartbeat install`(잡 등록)과 서비스 설치(plist·bootstrap)의 경계를 계약 문서에 명시.
앱 기획은 이 표면이 config-contract.md에 착지한 뒤 그 계약을 인용해서 선다. 규격이 먼저, 앱이 그 규격을 따른다.

기획 판단이 필요한 자리:
- 설치 경로. 현재 데몬은 git clone + pip editable 설치가 전제다(사용자 개발 환경). 앱이 실행하는 "설치"가 이 형태의 자동화인지, 배포 채널(pip/brew) 전제인지 — 배포 채널 자체는 claude-heartbeat 프로덕트화 백로그(docs/planning/2026-08-04-productization.md)라 이 기획 범위 밖이지만, 어느 전제 위에 서는지는 명시해야 한다.
- 실행 중 세션 처리. 업데이트의 재기동 단계가 라이브 세션과 만나는 규칙(IDEA-886DAB21의 끄기 고지와 같은 자리).
- 실패의 화면 표기. 업데이트 실패가 전역 에러 문구에 묻히지 않고 어디까지 갔는지(pull까지 됐는지, 재기동만 남았는지) 읽혀야 한다. SPEC-031이 일괄 QA에서 세운 건별 결과 원칙과 같은 계열.
- 기존 안내 UI(TASK-107~109 산출)와의 관계. 실행 버튼이 안내를 대체하는지, 실패 시 폴백으로 남는지.

등록 경위: 2026-08-05(KST) TL 세션에서 사용자 지시로 등록. 데몬 쪽 선행 규격 작업은 TL이 claude-heartbeat 저장소에서 병행 중이며, 이 아이디어의 기획은 그 착지를 기다렸다 계약 인용으로 선다.
