개발 작업이 구현 중 `blocked`가 되는 사례가 반복되고 있다. 현재 확인된 세 사례는 서로 다른 직접
원인을 갖지만, 승인된 기획을 개발 작업으로 분해할 때 구현에 필요한 선행 계약과 검증 영향 범위를
충분히 확인하지 못했다는 공통점이 있다.

- TASK-S051-04는 예약 응답과 provider 실행 수명 계약이 준비되기 전에 dispatcher 구현 작업으로
  분해됐다.
- TASK-S051-06은 기기 단위 서비스·실행 버전·업데이트 영향 조회 계약이 준비되기 전에 앱 설치 작업으로
  분해됐다.
- TASK-S052-01은 규칙 버전을 올리도록 요구하면서 실제로 함께 바뀌어야 하는 두 검사 모듈을
  `scope_files`에서 제외했다. 구현은 가능했지만 범위 밖 파일을 수정할 수 없어 전체 검사를 통과시키지
  못했다.

현재 `blocked`는 안전장치로서 올바르게 동작한다. 개발자가 승인되지 않은 범위까지 확장하거나 실패한
검사를 무시하지 못하게 한다. 문제는 차단 뒤의 복구 경로다. Developer는 blocked 작업을 선택할 수 없고,
Architect는 같은 승인 결정에서 작업이 하나라도 만들어진 뒤에는 다시 자격을 얻지 못한다. 사용자가
단순히 상태만 todo로 되돌려도 잘못된 선행·범위·완료 조건은 그대로여서 같은 차단이 재발한다.

특히 새로 만든 TASK-143은 blocked인 TASK-S052-01을 선행으로 기다리며, 그 작업과 같은 두 파일만
범위로 선언했다. 규칙 버전을 다시 올리면 같은 검사 모듈이 영향을 받으므로 현재 정의를 고치지 않으면
다시 막힐 가능성이 높다.

워크플로에 다음 복구 흐름이 필요하다.

1. 개발자가 차단할 때 원인을 구현 장애, 선행 계약 누락, 작업 정의 오류처럼 구분하고 확인한 근거와
   필요한 변경 후보를 기록한다.
2. 작업 정의 오류에서는 사용자가 앱에서 Architect 수정 요청을 기록한다. 이 결정은 사용자 소유 감사
   기록이며 단순 QA 반려나 기획서 수정 요청과 구분한다.
3. Architect는 그 요청 하나를 선점해 같은 작업 식별자를 보존한 채 범위, 선행, 작업 본문의 구현 범위,
   완료 조건과 검증 절차만 승인된 기획 안에서 수정한다. source specification과 승인 결정, 과거 history,
   막힌 사유와 보고서는 바꾸지 않는다.
4. 수정된 작업은 즉시 자동 재개하지 않는다. 사용자가 변경 내용과 해결 근거를 확인한 뒤 별도의 재개
   조작으로 blocked에서 todo로 돌린다. 이 단계는 SPEC-054의 사용자 전용 재개 흐름과 연결한다.
5. Architect가 새 작업을 만들기 전에 변경 상수·계약을 직접 참조하는 검사와 호출부, 전체 검증 명령이
   수정할 가능성이 있는 파일을 읽기 전용으로 확인한다. 선언 범위가 완료 조건을 충족할 수 없으면 작업을
   만들지 않고 범위를 넓히거나 탐색 작업을 먼저 둔다.
6. Developer도 제품 코드를 바꾸기 전에 짧은 범위 사전 검사를 수행한다. 명백한 범위 누락이면 구현과
   되돌리기를 반복하지 않고 정확한 경로와 근거를 포함한 Architect 수정 요청 후보로 차단한다.

첫 적용은 TASK-S052-01과 TASK-143이다. 두 작업 모두 규칙 버전 단언을 가진
`src-tauri/src/infrastructure/fs_project_repository.rs`와
`src-tauri/src/infrastructure/managed_project_assets.rs`를 범위에 포함하도록 Architect가 수정해야 한다.
TASK-S052-01의 구현 보고서가 남긴 592개 검사 중 11개 실패와 두 파일 근거를 해결 증거로 재사용한다.

자동 범위 확장, Developer의 작업 정의 임의 수정, 테스트 삭제, 사용자 확인 없는 재개와 원래 승인
범위를 넘어서는 요구사항 추가는 포함하지 않는다. `scope_files`는 병렬 충돌 판정과 개발 변경 허용 범위로
계속 엄격하게 사용한다.
