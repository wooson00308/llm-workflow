개발자 하트비트 세션의 동시 실행(병렬화)을 옵트인으로 켠다. 전제는 오늘 다 갖춰졌고, 마지막 안전장치 하나를 함께 만든다.

타이밍 근거 — 갖춰진 전제 (2026-08-04 기준 전부 실증):
- jobs.d 전환(SPEC-024 완주)으로 프로젝트 간 잡 파일 경합이 구조적으로 사라졌다.
- 선점 헬퍼 wf-claim.sh가 앱 관리 자산으로 설치돼 있고(SPEC-013 계열), depends_on이 구조화되어 있다.
- 실증: 2026-08-04 TL 병렬 지휘 세션에서 워커 6기 + 하트비트 세션이 같은 미커밋 트리에서 동시에 작업했고, TASK-073 선점 경합이 lease로 정상 해소됐으며(이중 작업 0), 최종 게이트 풀그린(cargo 401/0, npm 474/0)으로 종결됐다. 병렬 자체는 이미 돌아간다 — 지금 막고 있는 것은 안전 판정의 자동화뿐이다.

빠진 전제 — 같은 날 실측된 결함:
병행 금지 판정이 작업 문서의 산문 선언에 의존한다. 실사례: TASK-073과 TASK-077이 HeartbeatCard.tsx·IntegrationsView.test.tsx에서 충돌하는데, 077 문서의 병행 분석은 작성 시점(TASK-065 미착지) 기준이라 "같은 창에 들어오지 않는다"고 적혀 있었고 073 문서에는 077이 아예 없었다. 문서 작성 이후 상황이 바뀌면 선언이 낡는다. 이날은 TL이 수동 파일 겹침 분석으로 두 작업을 직렬화해 사고를 막았지만, TL 없이 데몬이 개발자 세션을 자동으로 여럿 띄우면 정확히 이 지점에서 같은 파일 동시 편집이 난다.

제안:
1. 작업 문서에 기계가 읽는 충돌 선언을 넣는다 — depends_on처럼 구조화된 필드로. 형태는 아키텍트 판단(예: 범위 파일 목록, 또는 병행 금지 대상 작업 id 목록). 산문 "병행 안전 확인 결과" 절은 근거 서술로 남기되 판정은 구조화 필드가 한다.
2. 자격 판정(조건 스크립트·앱)이 활성 lease가 잡은 작업들의 충돌 선언과 겹치는 작업을 착수 대상에서 제외한다. lease는 이미 task_id를 싣고 있어 원천이 있다.
3. 잡 설정에 동시 세션 수를 옵트인으로 노출한다. 기본값 1(현행 유지) — 켜는 것은 사용자 결정. 쿼터는 잡 단위 recent_runs로 세므로 동시 세션도 같은 쿼터 풀을 소모한다는 사실을 화면이 밝힌다.
4. 동시 세션이 화면에 보인다 — SPEC-011의 활동 뷰/워커 표시 위에 얹는다. 새 원천을 만들지 않고 lease 파일이 근거다.

범위 밖:
- 데몬 스케줄러의 동시 실행 구현 자체 — claude-heartbeat 저장소 별건(2026-08-03 사용자 결정). 데몬 쪽 전제(_inflight 가드, 스케줄러 배리어 제거, max_workers)는 v0.8.0에 이미 있다.
- 기존 작업 문서 수십 건의 충돌 선언 소급 기입 — 새 규칙은 앞으로 분해되는 작업부터. 선언 없는 옛 작업은 보수적으로 "모든 미완료 작업과 충돌"로 취급하면 안전이 유지된다(이 취급 방식 자체도 기획 판단).
- 기획자·아키텍트 잡의 병렬화 — 두 역할은 처리 대상이 문서 한 건이라 병렬 이득이 작고, lease 단위가 이미 그 문서다.

관련: 충돌 선언의 어휘는 "자격 판정이 기계가 읽을 수 있어야 한다"는 SPEC-009 R3·SPEC-010 계열과 같은 지점을 지난다. 분해 시 그 계보 확인이 필요하다.
