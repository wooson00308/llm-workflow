에이전트 개발 세션을 격리된 작업 사본에서 돌려서, 사용자가 LLM과 직접 작업하는 동안에도 자동 파이프라인이 멈추지 않고 함께 돌게 하자.

배경 사실:

- 원천 동기: 사용자는 아이디어, 기획, 승인, 분해 절차를 거치지 않고 LLM에게 바로 시키는 직접 작업을 하고 싶을 때가 있다. 그런데 지금 직접 작업 세션은 선점 체계 밖에 있다. lease의 대상은 문서 id뿐이라 직접 작업이 잡을 대상이 없고, scope_files 선언도 없다.
- 지금 동시 실행 방어는 두 겹이다. 문서 lease가 같은 작업의 중복 착수를 막고, 태스크의 scope_files 겹침 검사가 파일이 겹치는 태스크의 동시 시작을 막는다(공통 규칙 §6, 개발자 역할 계약의 Overlapping work). 두 방어 모두 선언된 태스크 사이에서만 성립한다.
- 개발 세션들은 프로젝트의 단일 작업 트리에서 코드를 고친다. 직접 작업 세션이 같은 트리에 들어오면 서로의 미완성 변경이 상대의 검증 결과에 섞인다. 파일이 겹치지 않아도 함수 시그니처 변경 같은 의미 충돌은 남는다.

제안:

1. 개발 역할 세션이 태스크마다 격리된 작업 사본(git worktree와 태스크 브랜치)에서 구현과 자동검증을 수행하게 한다. 본 판(공유 작업 트리)에는 통합 단계에서만 반영한다.
2. 사용자 직접 작업은 본 판에서 자유롭게 진행한다. 에이전트와의 충돌은 조용한 오염이 아니라 병합 시점의 명시적 충돌로만 나타난다.
3. 통합 단계의 주체, 시점, 충돌 해소 정책을 계약으로 정한다.

기획 시 확인이 필요한 긴장:

1. verified의 의미가 갈라진다. 지금은 한 트리에 변경이 쌓이므로 verified가 곧 본 판 반영인데, 격리 후에는 "사본에서 검증됨"과 "본 판에 병합됨"이 다른 사실이 된다. 그룹 QA는 본 판 기준이어야 하므로 병합이 QA보다 먼저 와야 한다.
2. 병합 주체가 필요하다. 기존 역할(아키텍트)의 확장인지 새 역할인지, 충돌이 났을 때 누가 푸는지 정해야 한다.
3. scope_files 겹침 검사와의 관계. 격리되면 트리 보호로서의 역할은 줄지만, 병합 충돌을 줄이는 스케줄링 힌트로 남길 수 있다.
4. 사본별 빌드 비용. cargo target 저장 공간은 이미 감시 대상이므로(2026-08-13 저장 공간 정리 기록), 사본 수만큼 늘어나는 빌드 산출물의 상한 정책이 필요하다.
5. 세션 기동과의 결합. 하트비트와 예약 핸드오프가 세션을 띄울 때 사본 준비를 누가 하는지(앱, 헬퍼, 세션 자신) 정해야 한다.

범위 밖: 직접 작업이 같은 트리를 써야 할 때의 우선권 게이트(신규 개발 세션 정지와 진행 중 태스크 하나만 완주하는 꼬리 대기)는 별도 아이디어로 미룬다. 이 아이디어가 구현되면 그 게이트는 예외 상황의 안전망으로만 필요하다.
