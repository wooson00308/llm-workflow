SPEC-051 구현 중 드러난 런타임 계약 공백을 보완하고, 실제 방해 요소가 해결된 `blocked` 개발 작업을 감사 기록을 남기며 다시 진행 가능한 상태로 돌리는 정식 경로를 만든다. 현재 TASK-S051-04와 TASK-S051-06에는 활성 lease가 없지만 Developer 계약은 `blocked` 작업을 절대 자격 대상으로 보지 않는다. 현재 규격에는 사용자가 막힘 해소를 확인한 뒤 `blocked`에서 개발 준비 상태로 되돌리는 전이도 없다. 그래서 필요한 계약을 구현하더라도 원래 작업을 다시 claim할 수 없다.

두 작업이 막힌 원인은 서로 다르지만 같은 제품 경계에서 나왔다.

- TASK-S051-04는 provider 프로세스를 시작한 직후 실행 식별자, PID, 시작 시각, 이벤트 읽기 위치와 취소·복구 제어를 dispatcher에 넘기는 계약이 부족하다. 현재 provider 계층은 종료 결과를 만들 수 있지만, 데몬 재시작 뒤 살아 있는 프로세스를 재인식하고 이벤트 읽기를 이어 가는 수명 계약이 없다.
- TASK-S051-06은 앱이 설치와 업데이트를 판단할 때 필요한 설치 버전, 실행 중 버전, 서비스 등록·실행 상태, 복구 가능 여부를 기계가 읽는 계약이 없다. 업데이트 전에 전체 실행 중 작업 수와 영향받는 프로젝트를 계산하고, 서비스 재등록·복구 결과를 구조화해 받는 경로도 없다.
- TASK-S051-01의 예약 도구는 대상, lease, 결과 식별자 접두어와 역할 인계문을 이미 반환하므로 재구현하지 않는다. 후속 dispatcher가 그 응답을 소비하는 연결만 필요하다.

첫 번째 범위는 provider 실행 수명 계약이다. Claude와 Codex 공통 provider가 프로세스를 시작하는 단계와 종료를 기다리는 단계를 분리하고, dispatcher가 실행 중 상태를 영속화하고 복구할 수 있는 안정적인 실행 핸들을 받게 한다. 실행 핸들은 최소한 실행 식별자, PID, 시작 시각 또는 PID 재사용을 판별할 동등한 토큰, 구조화 이벤트의 위치와 현재 읽기 위치, 취소·종료 결과를 연결할 정보를 제공해야 한다. prompt와 인증 정보는 이 핸들·상태·일반 로그에 저장하지 않는다.

dispatcher는 예약 성공 응답과 실행 핸들을 같은 실행 기록으로 묶는다. 예약이 실패하거나 대상·lease가 어긋나면 provider를 시작하지 않는다. 런타임이 재시작되면 PID만 보고 실행 중이라고 추측하지 않고 실행 토큰, 프로세스 생존, lease 소유권과 이벤트 위치를 함께 대조한다. 확정할 수 없는 항목은 중복 실행하지 않고 복구 필요 상태로 남긴다.

두 번째 범위는 설치·서비스·업데이트 조회 계약이다. 앱이 운영체제별 서비스 파일이나 사람이 읽는 CLI 문장을 직접 해석하지 않도록 런타임이 다음 사실을 버전화된 JSON 응답으로 제공한다.

- 설치된 런타임 버전과 실행 중 런타임 버전.
- 계약 API 주 버전과 앱 호환 여부를 판단할 값.
- 서비스 등록 여부, 실행 여부, 서비스 식별자, 마지막 확인 시각.
- 복구 가능 여부와 사용자가 해야 하는 다음 행동.
- 실행 중인 전체 작업 수와 영향받는 프로젝트 식별자.
- 업데이트 계획, 서비스 재기동·재등록·복구의 단계별 결과와 부분 실패.

조회는 상태를 바꾸지 않는다. 업데이트 적용은 사용자가 영향 범위를 확인한 뒤 별도 명시적 요청으로만 실행한다. 새 배포물 검증이나 서비스 전환이 실패하면 현재 동작하는 실행 파일과 서비스가 그대로 유지돼야 한다.

세 번째 범위는 blocked 작업의 재개 전이다. 앱은 blocked 작업의 우측 사유 패널에서 사용자가 방해 요소가 해결됐음을 확인하고 개발 준비 상태로 되돌리는 명시적 조작을 제공한다. 이 조작은 다음을 만족해야 한다.

- 사용자만 실행할 수 있고 에이전트나 Heartbeat가 자동으로 상태를 바꾸지 않는다.
- 현재 막힌 사유와 재개 조건, 관련 보완 작업의 최신 상태를 조작 전에 보여 준다.
- `blocked`에서 `todo`로 상태를 바꾸고, 누가 언제 어떤 근거로 재개했는지 append-only 이력과 감사 기록에 남긴다.
- 기존 `## 막힌 사유` 절은 삭제하지 않고 마지막 차단 기록으로 보존한다.
- 전이 뒤에도 선언된 선행 작업, migration lock, 활성 lease와 파일 겹침을 다시 판정한다. 상태가 `todo`가 됐다는 이유만으로 즉시 실행 가능한 것으로 단정하지 않는다.
- 이미 재개됐거나 문서가 바뀐 경우 오래된 화면 값으로 다시 쓰지 않는다.

현재 작업 이력 계약에는 재개를 표현하는 kind가 없고, 앱이 기록하는 QA 결정에도 blocked 재개가 없다. 기획 단계에서 새 이력 종류와 사용자 감사 기록의 스키마, 앱 소유 결정 문서가 필요한지, 기존 여섯 history kind와 하위 호환하는 방식을 정해야 한다. 에이전트가 Markdown 편집으로 사용자를 사칭하거나 기존 QA 수정 요청을 재개 용도로 오용하지 않는다.

TASK-S051-04와 TASK-S051-06을 첫 적용 대상으로 삼는다. provider 실행 수명 계약의 자동 검증이 통과하면 사용자가 TASK-S051-04의 재개 조건 충족을 확인할 수 있어야 한다. 설치·서비스·업데이트 조회 계약의 자동 검증이 통과하면 TASK-S051-06도 같은 방식으로 재개할 수 있어야 한다. 재개 뒤 각 작업은 원래 문서의 범위와 완료 조건을 그대로 수행하며, 이번 후속 작업이 원래 작업의 제품 구현을 대신하지 않는다.

제외 범위는 Claude Agent SDK와 Codex SDK 도입, Dream 변경, 원격 실행, 기존 blocked 작업을 일괄 재개하는 마이그레이션, 에이전트의 자동 재개, 관련 계약 검증 전에 상태만 강제로 바꾸는 우회다.

기획 단계에서 결정할 사항은 provider 실행 핸들의 최소 필드와 프로세스 재인식 방식, 이벤트 위치 계약, 설치·서비스·업데이트 JSON의 버전 경계, blocked 재개의 사용자 UI와 감사 기록, 관련 보완 작업 완료를 재개 조건으로 연결하는 방식이다. 두 저장소의 변경은 서로 독립 검증할 수 있게 나누되, 종단 검사에서는 계약 버전과 실제 응답이 일치하고 두 blocked 작업이 안전하게 다시 Developer 대상이 되는 것까지 확인한다.
