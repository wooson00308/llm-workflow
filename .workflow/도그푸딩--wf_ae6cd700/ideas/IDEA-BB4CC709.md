LLM Workflow가 외부 자동화 도구의 상태만 보여 주는 수준을 넘어, 프로젝트별로 Claude와 Codex CLI 에이전트를 실행하고 관리할 수 있게 한다. 새 실행기를 처음부터 만드는 대신 기존 claude-heartbeat를 범용 에이전트 런타임으로 고도화하고, workflow-labs가 설치·업데이트·설정·실행 상태를 관리하는 방향을 우선 검토한다.

첫 버전에서 충족해야 할 핵심 조건은 다음과 같다.

- 앱을 종료해도 에이전트 실행과 후속 작업 배정이 계속된다. macOS, Linux, Windows에서는 각 운영체제의 사용자 서비스 방식을 사용한다.
- 프로젝트마다 실행 큐와 상태를 분리한다. 한 프로젝트의 설정·쿼터·오류가 다른 프로젝트의 실행을 막지 않는다.
- 기획자·아키텍트·개발자 역할별로 Claude 또는 Codex CLI를 선택하고, 한 번 실행하거나 반복 실행할 수 있다.
- 역할별 최대 병렬 인원을 사용자가 정할 수 있다. 실제 실행 인원은 사용자가 정한 한도와 워크플로가 현재 배정할 수 있는 작업 수를 함께 반영한다.
- 워크플로 규격으로 정확한 작업 대상을 판정하고 예약할 수 있을 때는 자동 배정한다. 정확한 자동 배정이 어려운 경우에는 사용자가 대상과 병렬 인원을 직접 선택하는 UX를 제공한다.
- 같은 작업을 여러 에이전트가 동시에 가져가거나, 할 일이 없는 에이전트를 조건 확인 전에 실행해 토큰을 낭비하지 않는다.
- Claude Agent SDK는 사용하지 않는다. Claude와 Codex의 비대화형 CLI 실행을 기본 통합 방식으로 삼고, Codex SDK나 App Server는 CLI로 충족하지 못하는 요구가 확인될 때만 재검토한다.

앱과 런타임의 책임은 분리한다. Heartbeat는 운영체제 서비스, 일정 실행, 프로세스 종료와 타임아웃, 프로젝트별 큐, 병렬 제한, 실행 상태와 로그를 맡는다. LLM Workflow는 역할별 자격 판정, 의존성·lease·파일 범위 충돌, 정확한 대상 예약, 역할 프롬프트를 맡는다. 앱은 이 둘을 연결하고 사용자가 provider, 반복 여부, 역할별 최대 인원, 자동·수동 배정을 제어하는 UX를 제공한다.

현재 Heartbeat 연동이 앱 종료 뒤에도 다음 작업을 계속 배정하려면, 워크플로 자격 판정이 GUI 프로세스에만 있어서는 안 된다. Heartbeat가 호출할 수 있는 headless 판정 경로 또는 동등한 런타임 계약을 마련해야 한다. 현재 즉시 실행처럼 데몬을 우회하는 호출은 중복 실행을 만들 수 있으므로, 실행 요청은 데몬의 큐를 통과해야 한다.

claude-heartbeat는 별도 설치 도구로 사용자에게 노출하기보다 앱이 호환 버전을 설치하고 업데이트하는 companion runtime으로 다룬다. 기존 Claude 전용 사용자와 설정은 호환성을 보존하면서 provider 중립적인 이름과 설정 계약으로 단계적으로 이전한다.

Dream 연동은 이 기능의 범위에서 제외한다. 기존 기능을 유지해야 한다면 선택형 또는 legacy 연동으로 분리하고, 새 에이전트 실행 UX와 범용 런타임의 요구사항에는 포함하지 않는다.

기획 단계에서 결정할 사항은 첫 릴리스의 범위, 자동 배정과 수동 배정의 경계, 앱과 Heartbeat 저장소 사이의 버전·배포 계약, 역할별·프로젝트별 병렬 제한의 우선순위, 기존 Heartbeat 설정의 마이그레이션 방식이다.
