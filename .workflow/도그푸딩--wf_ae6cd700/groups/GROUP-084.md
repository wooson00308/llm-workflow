# 워크플로 상태를 명령 한 번으로 조회한다

## 기능 설명

세션과 대화형 작업이 워크플로의 지금 상태를 한 번의 명령으로 확인한다. 프로젝트 루트에서
`sh .workflow/rules/wf-status.sh`를 부르면 진행 집계, 사용자 대기, 활성 선점, 최근 실패가 한 화면에
나오고, `--json`을 붙이면 같은 값이 기계용 JSON 한 문서로 나온다. 아무것도 쓰지 않는 조회 전용
명령이며, 무엇을 집으라는 답은 하지 않는다. 그 답은 지금처럼 `wf-eligible.sh`가 맡는다.

## 판정을 어디서 받아 오는가

기획서 R2의 불변식이 이 그룹의 설계를 정한다. 상태 판정 구현은 지금 셋이고(앱 Rust 판정, 화면 파생
계산, 조건 스크립트) 네 번째 자리를 만들지 않는다. 그래서 조회 명령은 판정을 하지 않는다.

- 문서에 그대로 적힌 값(개발 작업의 status, 그룹의 revision과 qa_mode, lease의 대상과 만료 표기,
  보고 없이 끝난 실행 기록, 마이그레이션 락의 존재)은 조회 명령이 직접 읽는다.
- 판정이 필요한 값(최신 결정을 덮은 기획서의 표시 상태, 앱의 기능 표시 상태, lease의 만료 여부)은
  조건 스크립트가 이미 내부에서 계산하고 있다. 그 계산 결과를 밖으로 내보내는 출력 모드를 조건
  스크립트에 더하고, 조회 명령은 그 출력을 받아 형식만 만든다.

조건 스크립트를 고르고 앱 쪽 통로를 만들지 않은 이유는 둘이다. 첫째, 앱 실행 파일에는 헤드리스
진입점이 없어(`src-tauri/src/main.rs`가 Tauri 창을 여는 것이 전부다) 명령줄에서 앱 판정을 부르려면
새 실행 경로를 통째로 만들어야 한다. 둘째, 조건 스크립트의 기능 판정 훑기는 앱의 표시 상태 사슬을
이미 가지가 다 있는 상태로 이식해 두었고, 지금은 "구성 확인 필요"에 해당하는 가지만 출력하고
나머지 가지에서는 결과를 버린다. 버리던 값을 내보내는 것은 판정 규칙을 새로 적는 일이 아니다.

조건 스크립트와 조회 명령의 판 사이가 어긋날 수 있다. 설치된 조건 스크립트가 상태 투영을 모르는
옛 판이면 조회 명령은 판정이 필요한 값을 빼고, 뺀 항목의 이름을 사람용 출력의 마지막 줄과 기계
출력의 전용 필드에 남긴다. R2가 정한 "값이 조용히 사라지지 않게 한다"가 이 자리에서 실제로 쓰인다.

## 설치 경로를 정한 값

앱이 관리 자산을 동기화하는 경로(`managed_project_assets.rs`)에 얹는다. 예약 헬퍼가 타는 프로젝트
저장소 경로가 아니다. 선점 헬퍼와 조건 스크립트가 이미 그 경로를 타고, 설정 화면의 자산별 설치 상태
목록이 그 경로의 결과를 그대로 그리므로 조회 명령도 같은 자리에서 판 표기와 충돌 처리를 받는다.
화면은 자산 목록을 받은 대로 훑어 그리므로 화면 코드는 손대지 않는다.

## 작업 구성

작업을 셋으로 나눴다.

첫째 작업은 조건 스크립트에 상태 투영 출력을 더한다. 기획서·기능·lease 세 종류의 판정 결과를 탭으로
가른 줄로 내보내고, 역할 판정의 종료 코드 계약은 건드리지 않는다.

둘째 작업은 조회 명령을 앱 관리 자산으로 세운다. 새 자산 모듈과 동기화 배선, 호출 계약(인자 없는
호출과 `--json`은 0, 알 수 없는 인자는 2)까지가 여기다.

셋째 작업은 출력 다섯 묶음과 두 형식을 채운다. 첫째 작업의 투영과 문서 직접 읽기를 합쳐 사람용
출력과 기계용 출력을 만들고, 앱 판정과 대조하는 회귀 검사를 세운다.

첫째와 둘째는 파일이 겹치지 않아 나란히 진행할 수 있다. 셋째는 둘째가 만든 자산 파일을 이어서
채우므로 둘째 다음이고, 첫째의 투영을 소비하므로 첫째 다음이기도 하다. 두 선행 관계를 셋째 작업의
의존 선언에 적었다.

## 이번 그룹이 다루지 않는 것

쓰기 동작을 넣지 않는다. 선점, 상태 전이, 문서 생성은 이 명령이 하지 않는다. 무엇을 집을지 고르는
판단도 넣지 않는다. `wf-eligible.sh`의 역할 판정과 그 종료 코드 계약은 그대로 둔다.

앱 화면은 손대지 않는다. 설정 화면의 자산 목록은 자산 배열을 받은 대로 그리므로 새 자산이 늘어도
화면 코드가 바뀌지 않는다. 하트비트 잡 설정과 조건 문자열도 대상이 아니다.

앱에 헤드리스 명령줄 진입점을 만들지 않는다. 감시 모드, 색 출력, 셸 자동완성, 실패 기록의 확인 처리
상태에 따른 접기도 기획서가 범위 밖으로 정했다.

## 품질 확인 방식

자동 검증으로 둔다. 이 그룹이 만드는 것은 세션이 터미널에서 부르는 조회 명령이고, 사용자가 앱 화면을
열어 확인할 수 있는 결과가 없다. 사용자 확인 절차에는 터미널 명령을 적을 수 없으므로 사용자 확인
방식으로는 이 기능을 확인할 절차 자체를 쓸 수 없다.

기획서가 요구사항마다 붙인 완료 조건이 모두 자동 검사로 표현된다. 앱 판정과의 대조(R2), 묶음 순서와
빈 묶음(R3), 줄 수와 바이트 상한(R4), 표준 출력 JSON 파싱(R5), 실행 전후 해시 동일(R6), 활성 워크플로
둘의 구분(R7)이 세 작업의 완료 조건에 조건 번호로 들어가 있다.
