# 참조 패턴을 적용한 집중형 사용자 QA 작업대

## 기능 설명

기존 개발 작업을 기획서 기준의 작업 그룹으로 전환했습니다.

### QA-01 · 작업마다 확인 완료와 재작업 요청을 나눠 담는 한 번의 품질 확인 제출 통로를 만든다

이 작업에는 눌러 볼 화면이 없다. 통로만 만들었고 이 통로를 부르는 화면은 뒤따르는 작업이 만들기
때문에, 앱을 열어도 달라진 자리가 없다. 확인은 자동 검사가 대신했고, 확인 완료 도장은 아래 수치를
믿는다는 뜻이다.

같은 수치를 직접 확인하려면 저장소 최상위에서 다음을 실행한다.

   메모 분리, 검토 시작 뒤 바뀐 작업의 거절, 대기 상태가 아닌 항목만의 실패, 재작업 요청 메모
   누락 항목만의 실패를 확인한다.
   더한 두 건은 훅이 건별 결과를 그대로 돌려주는지와 호출 자체가 실패할 때 값 없음을 돌려주는지를
   확인한다.

결정 문서 형식이 변하지 않았다는 것은 1번 검사 안에서 확인한다. 새 통로로 만든 결정 문서도 스키마
줄과 작성자 줄이 변경 전과 같은 문자열인지 단언한다.

### QA-02 · 기능별 확인 대상 판정과 기기 내 임시 검토 저장을 화면 밖 모듈로 분리한다

이 작업은 화면을 바꾸지 않는 것이 성공 기준이다. 그래서 확인 동선도 "무엇이 새로 보이는가"가 아니라
"이전과 같은 것이 그대로 보이는가"를 본다.

1. 앱에서 개발 화면을 연다. 상단의 확인할 기능 묶음에서 카드 제목과 오른쪽 위 숫자, 각 카드의 직접
   확인 단계 수와 자동 검증 건수가 변경 전과 같으면 정상이다. 준비 중 예고 카드의 "QA n건 준비 중 ·
   남은 작업 m개" 문구도 같은 수여야 한다.
2. 같은 화면에서 카드의 QA 시작을 누른다. 직접 확인 단계 목록과 접어 둔 자동 확인 항목 수가 이전과
   같고, 확인 완료를 누르면 그 기능의 작업이 함께 기록되면 정상이다.
3. 에이전트 화면을 연다. 내 선택 대기 건수가 개발 화면에서 지금 누를 수 있는 확인 항목 수와 어긋나지
   않으면 정상이다.

제출 전 검토를 담아 두는 자리는 이 작업에서 만들기만 했고 읽는 화면이 아직 없다. 그 부분은 눌러 볼
화면이 없으므로 자동 검사가 대신 확인했고, 확인 완료 도장은 아래 수치를 믿는다는 뜻이다.

저장소 최상위에서 같은 수치를 직접 확인할 수 있다.

   → 131건 통과. 두 검사 파일은 이 작업에서 한 줄도 고치지 않았다.

### QA-03 · 품질 확인 전용 화면에 기능 대기열과 확인 범위 설명을 만든다

1. 앱을 열고 왼쪽 주요 메뉴에서 개발 아래에 있는 품질 확인을 누른다. 화면 위쪽 위치 표시가
   품질 확인으로 바뀌고 품질 확인 화면이 열리면 정상이다.
2. 화면에 지금 확인할 기능과 준비 중인 기능 두 구획이 위아래로 보인다. 지금 확인할 기능 구획에는
   기능 제목, 확인 목표 한 문장, 직접 확인 개수, 자동 근거 개수, 그리고 오른쪽에 시작이라는 글자가
   있다. 작업 번호나 파일 이름이 행에 보이면 잘못된 것이다.
3. 준비 중인 기능 구획의 행에는 품질 확인 대기 건수와 남은 작업 수만 있다. 그 행을 눌러도 아무 화면도
   열리지 않고 시작 버튼도 없으면 정상이다.
4. 지금 확인할 기능 구획에서 행의 아무 곳이나 누른다. 기능 제목이 큰 제목으로 뜨고, 바뀐 점과
   사용자가 확인할 결과가 각각 구획으로 보이며, 오른쪽 위에 전체 항목 수가 보이면 정상이다. 이 수는
   그 기능에서 품질 확인을 기다리는 작업 수와 같아야 한다.
5. 바뀐 점의 문장은 그 기능의 기획서 첫머리에 적힌 문장과 같고, 사용자가 확인할 결과의 문장들은 각
   작업 문서의 확인 동선 첫 문단과 같다. 앱이 지어낸 새 문장이 있으면 잘못된 것이다.
6. 왼쪽 위 대기열로 돌아가기를 누르면 다시 대기열이 보인다.
7. 키보드만 써서 같은 길을 걷는다. 탭 키로 지금 확인할 기능의 행에 초점을 옮기면 초점 테두리가
   보이고, 엔터를 누르면 기능이 열리며, 그때 초점이 대기열로 돌아가기에 있어 엔터를 한 번 더 누르면
   대기열로 돌아오면 정상이다.
8. 창 너비를 좁힌다. 대기열 행과 확인 범위 설명이 세로로 쌓이고 가로 스크롤 막대가 생기지 않으면
   정상이다.
9. 개발 화면과 오늘 화면을 다시 연다. 개발 화면의 확인할 기능 묶음과 QA 시작, 오늘 화면의 내 선택
   대기가 이전과 같이 동작하면 정상이다.

이 작업에서 새 화면은 확인 범위까지만 만든다. 항목을 하나씩 확인하거나 결과를 제출하는 조작은 아직
없으며, 결정을 남기는 길은 개발 화면 하나뿐이다.

저장소 최상위에서 같은 수치를 직접 확인할 수 있다.

### QA-04 · 품질 확인 세션에서 항목을 하나씩 확인하고 중단해도 이어가게 만든다

1. 앱을 열고 왼쪽 주요 메뉴에서 품질 확인을 누른다. 지금 확인할 기능 구획에서 기능 행을 누른다.
2. 확인 범위 설명 아래에 항목 확인 본문이 새로 보인다. 왼쪽에 확인 항목 목록이, 오른쪽에 지금 볼 항목
   하나가 놓이면 정상이다.
3. 본문 맨 위 고정 줄에 기능 이름과 `전체 N개 · 결과를 남긴 M개 · 남은 K개`가 보인다. 이 줄은 아래로
   내려도 화면에 남아야 한다. N은 그 기능에서 품질 확인을 기다리는 작업 수와 같아야 한다.
4. 목록의 자동 근거 묶음을 펼치지 않은 상태에서도 그 항목들의 제목과 상태가 보이고, 자동 근거 개수도
   보인다. 이 항목들이 전체 N에서 빠지면 잘못된 것이다.
5. 오른쪽 현재 항목에서 개발자가 그 작업 문서에 쓴 확인 동선 절이 통째로 보인다. 목록 카드에 실리던
   한 문단 발췌가 아니라 그 절의 모든 줄이어야 하고, 앱이 지어낸 새 문장이 있으면 잘못된 것이다.
6. 화면 조작이 없는 자동 근거 항목을 연다. 직접 조작할 화면이 없다는 안내와 개발자가 남긴 검증 결과가
   같은 자리에 함께 보이면 정상이다.
7. 현재 항목에서 확인함을 누른다. 메모를 적지 않아도 그 항목 상태가 확인함으로 바뀌고 진행률의 남긴
   수가 하나 늘면 정상이다.
8. 다른 항목으로 옮겨 문제 있음을 누른다. 사유가 비어 있는 동안에는 사유를 적어야 결과로 남는다는
   안내가 보이고 그 항목은 확인 전에 머무른다. 메모에 사유를 적으면 그때 문제 있음으로 바뀐다.
9. 작업 원문 보기를 누르면 그 작업 문서 전체가 열리고, 작업 원문 닫기를 누르면 같은 항목과 적고 있던
   메모가 그대로 남는다.
10. 다른 화면으로 갔다가 품질 확인으로 돌아온다. 대기열의 그 기능 행이 시작 대신 계속으로 표시되고,
    열면 남긴 결과와 메모와 보던 항목에서 이어지면 정상이다. 앱을 껐다 켜도 결과와 메모는 남는다.
    이때 보던 자리는 결과가 없는 첫 항목으로 돌아간다.
11. 임시 검토 버리기를 누른다. 기능 이름과 사라질 항목 수를 먼저 보여 주고, 한 번 더 눌러야 지워지면
    정상이다. 첫 누름만으로 지워지면 잘못된 것이다.
12. 확인하는 도중 그 기능의 작업 하나가 개발로 되돌아가면 준비 중이라는 안내와 남은 작업 수가 보인다.
    이때 남긴 임시 검토가 지워지면 잘못된 것이다.
13. 개발자가 그 기능의 작업 문서 하나를 고쳐 갱신 시각이 바뀌면, 그 항목만 다시 확인 필요로 바뀌고
    그 항목의 결과와 메모는 남아 있어야 한다.
14. 키보드만으로 같은 길을 걷는다. 탭과 엔터로 항목을 옮기고 결과를 고르고 메모를 적고 작업 원문을
    열고 닫는다. 항목을 옮길 때 초점이 현재 항목 본문으로 따라오면 정상이다.
15. 창 너비를 좁힌다. 항목 목록과 현재 항목이 세로로 쌓이고 가로 스크롤 막대가 생기지 않으면 정상이다.
16. 개발 화면을 다시 연다. 그 화면의 확인 동선 표시와 QA 조작이 이전과 같이 동작하면 정상이다.

여기서 남긴 결과와 메모는 아직 정식 결정이 아니다. 이 기기에만 남고 작업 문서와 결정 기록에는 아무것도
쓰이지 않으며, 제출 화면은 뒤따르는 작업이 붙인다. 화면 아래 안내가 같은 사실을 말한다.

저장소 최상위에서 같은 수치를 직접 확인할 수 있다.

### QA-05 · 제출 전 검토 화면에서 완료와 재작업 요청을 한 번에 기록하고 실패를 건별로 설명한다

준비물: 같은 기획서에서 나온 품질 확인 대기 작업이 둘 이상인 기능 하나. 없으면 개발 화면에서 그런
기능을 먼저 만들어 둔다.

1. 앱을 열고 왼쪽 주요 메뉴에서 품질 확인을 누른다. 지금 확인할 기능 구획에서 기능 행을 누른다.
2. 항목 확인 본문 아래쪽에 `제출 전 검토로 넘어가기`가 보인다. 결과를 고르지 않은 항목이 남아 있는
   동안에는 이 조작을 쓸 수 없고, 그 아래에 `결과를 고르지 않은 항목이 N개 남았습니다.`가 보인다.
   N은 아직 확인함도 문제 있음도 고르지 않은 항목 수와 같아야 한다.
3. 모든 항목에 결과를 남긴다. 하나는 확인함으로, 하나는 문제 있음으로 하고 문제 있음에는 사유를 적는다.
   마지막 항목에 결과를 남기는 순간 남은 수 안내가 사라지고 조작이 열리면 정상이다.
4. `제출 전 검토로 넘어가기`를 누른다. 재작업 요청으로 기록할 항목 구획이 위에, 확인 완료로 기록할
   항목 구획이 아래에 오고 각 제목에 `재작업 요청 N건`과 `확인 완료 N건`이 붙으면 정상이다. 확인 완료
   구획이 위에 오거나 건수가 없으면 잘못된 것이다.
5. 최종 버튼 문구를 읽는다. 확인함만 있으면 `확인 완료 N건 기록하기`, 섞여 있으면
   `확인 완료 N건과 재작업 요청 M건 기록하기`여야 한다. 건수가 문구에 없으면 잘못된 것이다.
6. 검토 화면에서 한 항목의 메모를 고치고 다른 항목의 결과 단추를 눌러 구획을 옮긴다. 옮긴 뒤에도
   나머지 항목의 결과와 메모가 그대로 남아 있어야 한다.
7. 한 항목에서 `이 항목 다시 보기`를 누른다. 항목 확인 화면이 바로 그 항목에서 열리고 초점이 그 본문에
   있으면 정상이다. 다시 `제출 전 검토로 넘어가기`를 눌러 돌아오면 다른 항목의 결과와 메모가 그대로다.
8. 재작업 요청 항목의 메모를 모두 지운 뒤 최종 버튼을 누른다. 제출되지 않고 사유가 필요하다는 안내가
   뜨며 초점이 그 항목의 메모 입력으로 가야 한다. 사유를 다시 적으면 제출이 열린다.
9. 문제가 없는 기능으로 최종 버튼을 한 번 누른다. 같은 버튼을 시간 안에 다시 누르라고 요구하지 않고
   한 번에 기록되면 정상이다. 기록 뒤에는 대기열로 돌아가고, 그 기능 행이 `계속` 대신 `시작`으로
   바뀌거나 목록에서 사라져야 한다.
10. 확인함과 문제 있음이 섞인 기능을 제출한다. 개발 화면에서 확인함 작업은 완료로, 문제 있음 작업은
    재작업 요청으로 상태와 이력이 바뀌었는지 확인한다.
11. 검토 화면을 연 채로 그 기능의 작업 문서 하나를 편집기에서 고쳐 저장한다. 화면을 새로 고치면 그
    항목에 `다시 확인 필요`가 붙고 최종 제출이 막히며 초점이 그 항목의 `이 항목 다시 보기`로 가야 한다.
12. 일부 실패는 앱을 끄지 않고는 만들기 어렵다. 재현 조건이 갖춰지면 화면이 닫히지 않고 항목마다
    기록됨과 실패 사유가 갈려 보이며, 실패한 항목만 아래 구획에 남고 최종 버튼 건수도 그만큼 줄어야
    한다. 이 상태에서 다시 제출하면 이미 기록된 작업에 결정이 두 번 남지 않아야 한다. 이 갈래는
    `QaWorkbench.test.tsx`의 일부 실패 검사 두 건이 앱 통로를 흉내 내어 자동으로 확인한다.
13. 창 너비를 980픽셀 아래로 줄인다. 검토 화면이 가로 스크롤 없이 읽히고 최종 제출을 그대로 쓸 수
    있어야 한다.
14. 대기열 행부터 최종 제출까지 키보드만으로 같은 길을 걷는다. 탭과 엔터로 기능을 열고 항목 결과를
    고르고 검토로 넘어가고 최종 제출까지 간다. 검토 화면으로 넘어간 직후 초점이 그 화면에 있어야 하고,
    제출이 막히면 초점이 막힌 자리로 가야 한다.

### QA-06 · 오늘 화면과 개발 화면의 품질 확인 입구를 전용 작업대 하나로 모은다

준비물: 사용자 검토 상태의 기획서 하나, 같은 기획서에서 나온 품질 확인 대기 작업이 둘 이상이고 그 기획서의
다른 작업이 모두 끝난 기능 하나, 그리고 아직 진행 중인 작업이 남아 있어 지금은 확인할 수 없는 기능 하나.

1. 앱을 열면 오늘 화면이 나온다. 내 선택 대기 구획을 본다. 기획서 승인 항목과 품질 확인 항목이 같은
   목록에 함께 있고, 오른쪽 위 건수 배지가 두 종류를 합한 수를 말하면 정상이다. 같은 기능의 대기 작업이
   여러 건이어도 목록에는 한 줄로만 나와야 한다.
2. 같은 구획에서 아직 확인할 수 없는 기능이 보이지 않는지 확인한다. 그 기능이 목록에 있거나 건수에
   포함되어 있으면 잘못된 것이다. 품질 확인 줄에 작업 식별자나 개발 상태 수치가 적혀 있어도 잘못된 것이다.
3. 품질 확인 줄을 누른다. 개발 화면이나 중간 상세를 거치지 않고 그 기능의 품질 확인 작업대가 바로 열리고,
   화면 위 이동 경로 끝이 품질 확인이면 정상이다. 제목이 그 기능의 이름이어야 한다.
4. 왼쪽 주요 메뉴에서 품질 확인을 누른다. 특정 기능이 아니라 대기열이 보이면 정상이다.
5. 왼쪽 주요 메뉴에서 개발을 누른다. 확인할 기능 구획의 카드에서 `QA 시작`을 누르면 같은 기능의 작업대가
   열려야 한다. 이 화면 안에서 확인 단계 목록이 열리면 잘못된 것이다.
6. 개발 화면으로 돌아와 `기획서별 묶기`를 켠다. QA 대기만 남은 레인의 헤더에 `이 그룹 N건 품질 확인 열기`가
   있다. 눌렀을 때 대상 선택 목록이나 확인 메모 입력이 뜨는 대화상자가 나오면 잘못된 것이고, 그 기능의
   작업대로 이동하면 정상이다.
7. 개발 화면에서 보기를 리스트로 바꾸고 QA 대기 작업 한 건을 연다. 오른쪽 패널에 상태 표시와
   `품질 확인 작업대 열기`만 있어야 한다. `테스트 플로우와 확인 메모` 입력창이나 `확인 완료`,
   `개발 준비로 되돌리기` 버튼이 남아 있으면 잘못된 것이다. 문서 본문 읽기와 확인 동선 표시는 그대로다.
8. 오늘 화면으로 돌아가 기획서 승인 줄을 누른다. 기획서 검토 화면이 이전과 같이 열리고 승인·수정 요청
   조작이 그대로면 정상이다.
9. 개발 화면에서 검색, 개발 상태 필터, 기획서별 묶기, 보기 전환, 타임라인이 이전과 같이 동작하는지 훑는다.
10. 사용자 검토 기획서도 확인할 수 있는 기능도 없는 워크플로를 고른다. 오늘 화면 내 선택 대기에
    `기다리는 선택이 없습니다`가 보이고 배지가 0이면 정상이다.
11. 품질 확인 작업대에서 기능 하나를 끝까지 확인해 제출한다. 완료와 재작업 요청이 이전과 같은 형식으로
    기록되고 개발 화면의 작업 상태가 그에 맞게 바뀌면 정상이다.
