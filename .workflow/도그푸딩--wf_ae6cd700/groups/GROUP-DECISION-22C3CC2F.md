# 막힌 작업의 정의를 감사 가능하게 수정하고 재개한다

## 기능 설명

기존 개발 작업을 기획서 기준의 작업 그룹으로 전환했습니다.

### QA-01 · 차단 분류와 작업 정의 수정 계약을 관리 규칙에 반영한다

이 작업에는 눈으로 볼 화면이 없다. 바뀐 것은 앱이 설치하는 규칙 문언과 사용자 문서라 자동 검사가 그
문언을 대조하며, 확인 도장은 아래 수치를 신뢰한다는 뜻이다.


문언을 직접 읽고 싶다면 임시 폴더를 프로젝트로 열어 앱이 새로 설치한 규칙에서 네 가지를 확인한다.

1. `.workflow/rules/workflow.md`가 `rules_version: 19`이고, 5절에 `### Naming what kind of block it is`
   절이 있다. 선택 필드 `blocked_kind`와 네 값(`definition_error`, `missing_prerequisite`,
   `implementation_failure`, `external_dependency`)이 각각 한 번씩 정의돼 있고, 값이 없거나 모르는 값인
   문서는 분류되지 않은 것으로 읽으며 원인을 추측하지 않는다고 적혀 있다. 막힘에서 벗어나도 값을
   지우지 않되 현재 방해 요소로는 읽지 않는다는 문장도 같은 절에 있다.
2. 같은 5절의 `### When the task definition itself is wrong`에서, 작업 정의 수정 요청이 앱이
   `decisions/`에 남기는 앱 소유 기록이고 에이전트는 만들 수 없으며, 처리한 요청을 잇는 선택 필드가
   `revision_request_id`라는 것을 읽을 수 있다.
3. `.workflow/rules/roles/architect.md`가 `rules_version: 12`이고 두 절이 새로 있다.
   `## Check the scope before you hand a task over`는 고정 제목 `## 범위 사전 검사`와 그 절이 파일
   목록이 아니라 근거를 담아야 한다는 것을, `## Correcting a task whose definition is wrong`은 고칠 수
   있는 것과 보존할 것과 돌려보낼 조건을 적는다.
4. `.workflow/rules/roles/developer.md`가 `rules_version: 14`이고, 제품 파일을 바꾸기 전에 범위 사전
   검사 절과 저장소를 대조한다는 문장과 `### When the scope declaration is what is wrong` 절이 있다.
   범위 밖 파일이 필요하면 제품 코드를 고치지 않고 `blocked_kind: definition_error`로 막고 보고서에
   누락 경로와 직접 참조와 실패할 검증을 남기며, 이 대조가 검사 삭제나 완화의 근거가 아니라는 문장이
   함께 있다.
5. `.workflow/rules/roles/planner.md`는 `rules_version: 11` 그대로다. 본문이 바뀌지 않은 계약은 버전이
   오르지 않는다.

같은 내용이 `docs/file-contract.md`의 `### 차단 분류`, `### 작업 정의 수정 요청`, `### 범위 사전 검사 절`
세 절에 한국어로 적혀 있다.

기존 문서는 바뀌지 않는다. `blocked_kind`나 `revision_request_id`나 범위 사전 검사 절이 없는 기존 작업
문서를 앱이 고치지 않고, 그 때문에 목록·상세 화면의 표시나 자격 판정이 달라지지도 않는다.

### QA-02 · 사용자가 남긴 작업 정의 수정 요청을 앱 소유 기록으로 저장한다

이 작업에는 눈으로 볼 화면이 없다. 요청을 남기는 화면 조작은 이 승인의 다른 작업이고, 여기서 만든 것은
저장 명령과 기록 형식과 조회 값이라 자동 검사가 그 판정을 대조한다. 확인 도장은 아래 수치를 신뢰한다는
뜻이다.


수치 대신 동작을 직접 보고 싶다면 임시 프로젝트에서 개발용 호출로 재현할 수 있다. 화면이 아직 없으므로
명령을 직접 부른다.

1. `.workflow/<워크플로우>/tasks/`에 `status: blocked`인 작업 문서를 두고, 그 문서의 `updated_at` 값과
   비어 있지 않은 이유, 임의의 요청 식별자로 `record_task_revision_request`를 호출한다.
2. `decisions/REVISION-XXXXXXXX.md`가 한 건 생기고 `task_id`, `request_id`, `previous_updated_at`,
   `created_by: user`, `created_at`이 들어 있으며 본문에 입력한 이유가 그대로 있다. 작업 문서는 한 글자도
   바뀌지 않는다.
3. 같은 요청 식별자로 다시 호출하면 성공을 다시 받지만 요청 문서는 한 건 그대로다. 다른 요청 식별자로
   호출하면 앞 요청이 아직 처리되지 않았으므로 새 문서를 만들지 않고 그 요청을 돌려준다.
4. 작업 상태를 `in_progress`나 `qa_waiting`이나 `completed`로 바꾸거나,
   `.workflow/.runtime/leases/TASK-XXX.yml`에 미만료 lease를 두거나,
   `.workflow/.runtime/migration.lock`을 만들거나, `updated_at`을 다른 값으로 보내면 거절되고 `tasks/`와
   `decisions/`의 파일 내용이 호출 전과 같다.
5. 작업 문서 프론트매터에 `revision_request_id: REVISION-XXXXXXXX`를 넣고 작업을 다시 조회하면 그 요청이
   처리 완료로 읽히고, 미처리 요청이 없어졌으므로 다음 요청을 다시 받을 수 있다.

### QA-03 · 아키텍트 자격 판정이 미처리 수정 요청을 먼저 고른다

이 작업에는 눈으로 볼 화면이 없다. 바뀐 결과는 아키텍트 판정에 수정 요청과 승인을 함께 두었을 때
수정 요청을 먼저 고르고, 요청이 없으면 기존 승인을 고르며, 처리된 요청과 종료 상태의 작업은
후보에서 빠지는 것이다. 확인 도장은 아래 자동 검사 수치와 검사에 포함된 시나리오를 신뢰한다는 뜻이다.

- 변경 범위 다섯 파일의 `rustfmt --check` → 통과

세부 회귀 검사는 요청만 있는 경우, 승인만 있는 경우, 둘 다 있는 경우, 요청이 여럿인 경우를 포함한다.
처리 연결, 품질 확인 대기·완료 상태, 요청·대상 선점, 만료 선점, 마이그레이션 잠금, 판정 전후 문서와
선점 파일 불변까지 각각 대조한다.

### QA-04 · 작업 상세에서 정의 수정을 요청하고 처리 결과를 확인한다

일회용 테스트 프로젝트를 앱으로 열고 왼쪽 메뉴에서 `개발`을 선택한다. 활성 선점이 없는 `막힘` 작업이나
`준비` 작업의 카드를 눌러 상세 화면을 연다.

1. 오른쪽 패널의 `작업 정의 수정 요청`에서 대상 상태, 갱신 시각, 선행 관계, 범위 선언과 기존 요청을
   확인한다. 정상 빈 범위는 `변경 파일 없음 (빈 목록으로 선언됨)`으로 보이고, 선언 없음과 형식 오류는
   각각 다른 문장으로 보여야 한다.
2. `수정이 필요한 이유`를 입력하고 `정의 수정 요청 확인`을 한 번 누른다. 대상과 갱신 시각과 입력 이유가
   확인 상자에 고정되고 아직 저장 결과는 나타나지 않아야 한다.
3. `한 번 더 누르면 수정 요청`을 누른다. 성공하면 입력이 비워지고 기존 요청 목록에 미처리 요청이 나타난다.
   거절 상황에서는 입력이 남고 `최신 작업 다시 읽기`로 같은 상세를 다시 조회할 수 있어야 한다.
4. 왼쪽 메뉴의 `활동`을 열면 요청은 `정의 수정 요청`으로 보인다. 아키텍트가 그 요청을 작업에 연결해
   처리한 테스트 데이터에서는 `아키텍트 수정`이 별도 항목으로 보여야 한다. 기존 `반려`와 `사용자 재개`
   이름은 그대로여야 한다.
5. 실제 창 크기를 좁혔다 넓혀도 정보의 읽기 순서가 바뀌지 않고, 키보드 Tab 이동이 이유 입력, 첫 확인,
   최종 확인, 오류 뒤 재조회 순서를 따라야 한다. 활동 사건과 세 범위 상태의 데이터 조립은 자동 검사 결과를
   품질 확인 근거로 함께 사용한다.
