# 승인된 기획서에도 후속 결정을 보낸다

## 기능 설명

기존 개발 작업을 기획서 기준의 작업 그룹으로 전환했습니다.

### QA-01 · 승인된 기획서에 후속 수정 요청을 기록하는 길이 쓰기 경로에 난다

**볼 화면이 없는 작업이다.** 바뀐 것은 앱 안쪽의 기록 경로 하나이고, 그 경로를 사용자가 누르는
자리는 TASK-128이 만든다. 지금 앱을 띄워도 승인된 기획서 화면은 어제와 같다 — 결정 도구는 여전히
사용자 선택 대기 상태에서만 그려진다. 그 순서는 기획서가 정한 것이다. 화면이 먼저 열리면 버튼을
누르고 오류를 보게 되기 때문에 쓰기 경로가 먼저 선다.

그래서 이 작업은 자동 검사로 닫았고, 확인 도장은 **아래 숫자를 믿는다**는 뜻이 된다.

### 1. 검사 두 개를 다시 돌린다


**정상이면 앞엣것이 504 passed / 0 failed / 0 ignored, 뒤엣것이 22 files / 642 tests passed다.**
이 세션이 넘길 때의 값이고, 다른 세션이 그 사이에 검사를 더했으면 숫자는 늘 수 있다. 늘어도
`failed`가 0이면 정상이다.

### 2. 이 작업이 새로 만든 다섯 건만 돌려 본다


**정상이면 `5 passed; 0 failed`다.** 각각이 확인하는 것은 이렇다.

| 테스트 | 확인하는 것 |
| --- | --- |
| `records_a_follow_up_revision_request_on_an_approved_spec` | 승인된 기획서에 수정 요청이 기록되고 결정 문서가 하나 는다 |
| `a_follow_up_revision_request_writes_the_same_decision_frontmatter` | 그 결정 문서의 프론트매터가 지금과 같은 여섯 값뿐이다 |
| `refuses_every_spec_decision_the_table_blocks` | 표에서 막힌 열한 조합이 전부 거절되고 결정 문서가 늘지 않는다 |
| `a_follow_up_revision_request_moves_the_approval_out_of_architect_work` | 그 수정 요청이 기획자 몫이 되고 승인이 아키텍트 몫에서 빠진다 |
| `a_follow_up_revision_request_leaves_the_derived_task_to_the_developer` | 이미 파생된 작업이 그대로 개발자 몫으로 남는다 |

뒤의 둘은 앱의 판정과 조건 스크립트를 세 역할 모두에서 대조한다. 갈라지면 그 자리에서 실패한다.

### 3. 판정 본문을 건드리지 않았다는 것을 눈으로 본다


**정상이면 이 세션 때문에 새로 뜨는 줄이 없다.** 작업 트리에는 이 세션 전부터 다른 작업들의
미커밋 변경이 섞여 있어 위 명령이 줄을 낼 수는 있다. 이 세션이 만졌는지 아닌지는 아래로 가른다.


**정상이면 목록에 이 작업의 범위 파일과 이 작업 문서, 그 lease, 보고서, 개발 로그, 빌드 산출물
하나만 있다.** 판정 본문 둘도 규칙 자산도 파일 계약 문서도 그 목록에 없다.

### 4. 알아 둘 것

- 이 변경으로 지금 당장 화면에서 달라지는 것은 없다. 사용자가 실제로 누르게 되는 것은 TASK-128
  뒤다.
- 잘못 보낸 후속 수정 요청을 취소하는 길은 여전히 없다. 수정 요청 상태에 결정을 또 얹는 칸은
  이번에도 막혀 있고, 그것이 기획서가 승인한 선택이다.

기획서 완료 조건 5다 — 화면이 여는 조작과 쓰기 경로가 허용하는 조합이 같아야 하고, 그 대조의
기준이 되는 조합 테스트가 이 작업의 산출물이다. 순서가 뒤집히면 사용자는 버튼을 누르고 오류를
본다(확인 사실 2).

### QA-02 · 결정이 끝난 기획서 화면에서 후속 기획 요청을 보내고 도장 이력을 읽는다

**볼 화면이 있는 작업이다.** 앱을 띄우고 기획서 검토 탭에서 아래 넷을 밟으면 된다.

**기록까지 누를 필요는 없다.** 이 저장소의 기획서 결정은 사용자의 도장이고, 양식을 열어 두었다가
"취소"로 빠져나오면 아무것도 기록되지 않는다. 기록되는 것은 "후속 기획 요청 기록"을 누른 순간
하나뿐이다.

### 1. 승인된 기획서에서 조작이 열리는지

기획서 검토 탭 → 필터 "결정됨" → 상태 알약이 "승인됨"인 문서를 아무거나 연다.

**정상이면 오른쪽 사용자 결정 패널이 이렇다.**

- "승인된 기획입니다" 상자 아래에 "후속 기획 요청" 버튼이 **하나만** 있다.
- 승인 도장 버튼도 기획서 폐기 버튼도 **없다**. 이 둘이 보이면 화면이 앱 안쪽보다 넓게 연 것이고,
  눌렀을 때 오류가 난다.
- 그 아래 "결정 이력"이 열려 있고 도장이 시간순으로 한 줄씩 나온다.

### 2. 이력이 읽히는지

같은 자리에서 이력을 읽는다. **정상이면 항목마다 이름과 시각이 있고, 고치거나 지우는 버튼이
하나도 없다.**

- 대부분의 기획서는 도장이 하나라 **한 줄**로 나온다. 그것이 정상이다.
- **두 줄이 나오는 문서는 SPEC-022 하나다.** 승인 도장이 둘 찍혀 있고, 위가 8월 4일 08:52,
  아래가 09:38이어야 한다(기기 시간대에 따라 표기 시각은 달라진다). 이력이 시각순인지 보려면
  이 문서를 열면 된다.
- SPEC-041에는 결정 문서가 둘 있지만 이력은 한 줄이다. 하나가 위임 대리 결정이라 앱이 세지 않는
  것이고, 규칙이 정한 그대로다.

### 3. 실수로 눌리지 않는지

1번에서 연 승인된 기획서에서 "후속 기획 요청"을 누른다.

**정상이면 양식이 열리면서 아래가 순서대로 읽힌다.**

1. 사실 셋 — "기존 승인 결정은 지워지지 않습니다" / "이 기획서에서 나온 개발 작업은 그대로
   진행됩니다" / "대신 이 기획서가 수정을 요청한 기획으로 바뀝니다"
2. 확인 문구 — "이 기획서에 후속 기획 요청을 기록합니다. 결정 기록은 되돌릴 수 없습니다."
3. 코멘트 입력과 "후속 기획 요청 기록" 버튼. **코멘트가 비어 있는 동안 그 버튼은 잠겨 있다.**

여기서 "취소"를 누르고 나온다. 아무것도 기록되지 않는다.

### 4. 지금까지 되던 것이 그대로인지

- 상태 알약이 "내 선택 대기"인 기획서를 연다. **정상이면 승인 도장 찍기 · 수정 요청 · 기획서 폐기
  셋이 어제와 똑같이 있고, "후속 기획 요청"은 없다.**
- 상태 알약이 "수정 요청됨"이거나 "폐기됨"인 문서를 연다. **정상이면 결정 도구가 하나도 없고
  이력만 읽힌다.**

### 5. 자동 검사 두 개


**정상이면 앞엣것이 23 files / 664 tests passed, 뒤엣것이 538 passed / 0 failed / 0 ignored다.**
이 세션이 넘길 때의 값이고, 다른 세션이 그 사이에 검사를 더했으면 숫자는 늘 수 있다. 늘어도
`failed`가 0이면 정상이다.

### 6. 알아 둘 것

- 배치와 여백은 자동 검사가 덮지 못한다. 눈으로 볼 때 그 자리를 함께 봐 주면 된다.
- 활동 뷰는 아직 같은 사건을 "수정 요청"이라고 부른다. 두 화면의 이름을 맞추는 것은 TASK-129의
  몫이라 이 작업에서는 갈려 있는 것이 정상이다.
- 잘못 보낸 후속 기획 요청을 취소하는 길은 없다. 수정 요청 상태에 결정을 또 얹는 칸이 막혀 있고,
  그것이 기획서가 승인한 선택이다.

넷을 가르지 않은 이유는 가른 중간 상태가 뜻을 갖지 않기 때문이다. R1이 여는 조작에는 R3의

두 번째 도장을 읽는 자리다. 셋 중 하나만 선 화면은 QA에서 확인할 것이 없다.

### QA-03 · 기획서 도장과 개발 작업 도장이 누르는 자리에서 갈린다

**볼 화면이 있는 작업이다.** 앱은 이미 떠 있다 — 이 세션이 고친 화면이 개발 서버를 타고 그 창에

**도장은 누르지 않는다.** 아래 1번에서 버튼을 한 번 누르는데 그것은 무장까지고, 3.5초 지나면
저절로 풀린다. 실제로 기록되는 것은 무장된 상태에서 한 번 더 누른 순간뿐이다. 메모 칸에 글자를
넣는 것도 아무것도 기록하지 않는다.

### 1. 개발 작업 반려 버튼이 기획서 쪽과 다른 말을 쓰는지

개발 화면 → "QA 대기" 열에서 작업 카드를 아무거나 연다 → 오른쪽 USER QA 패널.

**정상이면 이렇다.**

- 아래쪽 버튼 둘의 이름이 "개발 준비로 되돌리기"와 "확인 완료"다. "수정 요청"이라는 버튼이
  **없다**. 있으면 이 작업이 값을 내지 못한 것이다.
- "테스트 플로우와 확인 메모" 칸에 아무 글자나 넣으면 왼쪽 버튼이 눌리게 된다. 한 번 누르면
  이름이 "한 번 더 누르면 되돌리기"로 바뀌고, 그 위에 "작업을 개발 준비로 되돌리고 수정 요청을
  기록합니다."가 뜬다.
- **거기서 손을 뗀다.** 3.5초 뒤 이름이 "개발 준비로 되돌리기"로 돌아오면 아무것도 기록되지 않은
  것이다. 넣은 메모는 지워도 되고 그냥 화면을 나가도 된다.

### 2. 기획서 쪽 문면과 나란히 놓아 갈리는지

기획서 검토 탭 → 필터 "결정됨" → 상태가 "승인됨"인 문서를 아무거나 연다 → 오른쪽 사용자 결정
패널.

**정상이면** 거기 버튼 이름이 "후속 기획 요청"이다. 1번에서 본 "개발 준비로 되돌리기"와 나란히
놓았을 때, 무엇이 대상이고(기획서인가 작업인가) 무엇이 일어나는지(후속 기획을 요청하는가 개발
준비로 되돌리는가)가 이름만으로 갈리면 이 작업이 요구한 것이 선 것이다.

여기서도 누르지 않는다. 눌러도 양식이 열릴 뿐이고 "후속 기획 요청 기록"까지 눌러야 기록되지만,
확인에 필요한 것은 버튼 이름을 읽는 것까지다.

### 3. 활동 기록이 그대로인지

활동 탭 → "최근 활동".

**정상이면** 목록이 전과 똑같이 그려지고, 마크 이름이 "생성"·"시작"·"QA 대기"·"반려"·"승인" 등
전과 같다. 이 자리는 회귀만 본다.

**"후속 기획 요청"이라는 마크는 지금 이 프로젝트에서 볼 수 없다.** 그 이름이 뜨려면 승인된
기획서에 수정 요청 도장이 한 번 더 찍혀 있어야 하는데, 이 저장소의 결정 45건 중 그런 것이 아직
없다. 도장을 찍어 만들어 보는 것은 사용자의 결정이라 이 세션이 하지 않았다. 그 갈림은 자동
검사가 닫았고, 그 확인 도장은 아래 두 검사의 수치를 믿는다는 뜻이다.


이름 갈림을 직접 눈으로 보고 싶으면 승인된 기획서에 후속 기획 요청을 한 번 찍으면 된다. 그것은
실제 결정 기록이 남는 조작이라 이 확인 동선이 요구하지 않는다.

않는다"이기 때문이다. 한쪽만 고친 중간 상태에서는 그 요구를 확인할 수 없다.
