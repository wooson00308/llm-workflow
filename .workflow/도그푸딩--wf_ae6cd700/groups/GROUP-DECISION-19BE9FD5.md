# 에이전트가 쓰는 문서의 한국어 문체 규칙을 공통 규칙에 넣는다

## 기능 설명

기존 개발 작업을 기획서 기준의 작업 그룹으로 전환했습니다.

### QA-01 · 공통 규칙에 한국어 문체 절을 넣고 세 역할 계약과 버전 상수를 함께 올린다

`에 적는다. (R7 / 기획서 완료 조건 10)
10. 이 작업이 만든 개발 작업 문서와 개발 보고서가 §9의 문장 원칙을 지킨다. 검증: 보고서를 쓴 뒤
    세션이 스스로 확인하고 그 결과를 보고서에 적는다. (기획서 완료 조건 11)
11. 조건 스크립트(`heartbeat_condition.rs`, `.workflow/rules/wf-eligible.sh`)와 앱 판정 모듈
    (`role_eligibility.rs`)이 이 변경분에서 달라지지 않았다. `.workflow/` 아래 기존 문서의 본문이
    고쳐지지 않았다. 앱 화면 코드가 달라지지 않았다. 문서 본문을 읽거나 검사하는 코드가 추가되지
    않았다. 본문의 권장 분량이 규칙에 들어가지 않았다. 검증: `git diff --stat`으로 변경 파일이
    범위 파일 하나뿐임을 확인하고 결과를 보고서에 적는다. (R8 / 기획서 완료 조건 12)
12. 요약 절(§8)의 금지 조건과 열 줄 상한, 확인 동선 절의 기존 규칙이 달라지지 않았다. 프론트매터
    계약과 스키마 버전도 그대로다. 검증: 기존 대조 검사가 수정 없이 통과한다. (R8)

### QA-02 · 한국어 파일 계약 문서에 확장 대응표와 전후 예문을 넣는다

화면 변경이 없는 문서 작업이다. 다음 내용을 확인하면 된다.

1. `docs/file-contract.md`를 열어 `## 안전 규칙` 바로 앞에 `## 문서 문체` 절이 있는지 본다.
2. `### 표현별 대안` 표의 첫 세 줄이 아래와 같은지 본다.
   - 착지 → 구현, 반영, 병합, 배포
   - 닫다 → 해결, 충족, 완료
   - 원천 → 데이터 출처, 원본 문서, 판단 기준
3. 같은 표에 자리, 몫, 어법, 표면의 대안도 있는지 본다.
4. 표 아래 설명이 어색한 비유를 허용하지 않고, 실제로 통용되는 표준 기술 용어만 예외로 인정하는지
   확인한다.
5. `### 수정 전과 수정 후`에 예문 세 쌍이 있는지 본다. 각 쌍의 "후" 문장에 착지·닫다·원천이 남아
   있지 않아야 한다.
7. 변경 파일은 `git diff --stat -- docs/`로 확인한다. `docs/file-contract.md` 한 줄만 나오면 정상이다.

위 내용이 모두 확인되면 정상이다.
