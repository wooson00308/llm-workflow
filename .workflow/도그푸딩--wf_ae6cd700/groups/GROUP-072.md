# 확인 동선을 평범한 한국어로 써도 기능의 품질 확인이 열리게 하기

## 기능 설명

사용자 확인 모드로 만든 기능은 확인 동선이 사용자 확인 절차로 인정되어야 품질 확인을 열 수 있다.
지금 그 인정 판정은 확인 동선 본문에 화면을 가리키는 낱말, 사용자 행동을 가리키는 낱말, 눈에 보이는
결과를 가리키는 낱말이 각각 하나 이상 있는지를 본다. 문제는 대조 방식이다. 낱말 목록에 활용형이
하나씩만 들어 있고 글자열 포함으로만 맞추기 때문에, 결과 쪽 "보이"는 "보입니다"에는 걸리지만
"보인다"에는 걸리지 않는다.

이 변경은 세 조건의 낱말 대조가 어미 변화로 글자 모양이 바뀐 형태도 같은 낱말로 인식하게 한다.
"보인다", "보이고", "보입니다", "보였다"가 모두 같은 낱말이 되고, 실제 확인 동선이 쓰는 관찰
서술인 나타난다, 표시된다, 적혀 있다, 열린다, 나온다, 바뀐다, 같아진다, 남아 있다, 사라진다도
결과로 인정된다.

실측 사례는 GROUP-070이다. 소속 개발 작업이 검증까지 끝났는데도 확인 동선이 결과 조건 하나를
만족하지 못해 구성 확인 필요 상태에 멈춰 있고, 사용자가 품질 확인을 열 방법이 없다. 이 변경은 그
문서를 한 글자도 고치지 않고 판정만 넓혀서 GROUP-070이 품질 확인 대기로 올라오게 한다.

넓히는 것은 결과와 화면과 행동을 가리키는 낱말을 알아보는 범위 하나뿐이다. 확인 동선에 개발자용
절차가 섞이는 것을 막는 지금의 차단은 그대로 둔다. 터미널 명령, 패키지 실행기 호출, 저장소 조작
지시, 내부 자동 시험 절차, 코드 블록이 들어간 확인 동선은 변경 후에도 인정되지 않고, 본문이 비어
있는 확인 동선도 마찬가지다. 세 조건을 모두 만족해야 한다는 규칙도 그대로여서, 화면도 행동도
말하지 않는 문장은 결과 낱말이 있어도 인정되지 않는다.

기능 상태를 정하는 나머지 판정도 손대지 않는다. 문서 구조 유효성, 작업의 구성 버전 일치, 자동 확인
모드의 규칙, 사용자 확인 흐름과 결정 도장은 지금 그대로다.

## 품질 확인 방식

사용자 확인으로 둔다. 이 변경의 결과는 품질 확인 화면의 목록에서 사용자가 직접 읽을 수 있다.
개발이 끝났는데도 준비 중인 기능 목록에 구성 확인 필요로 서 있던 기능이 지금 확인할 기능 목록으로
올라오는 것이 그것이다.

확인 시점의 판 상태를 전제하지 않도록 절차를 짰다. 실측 사례인 GROUP-070은 이 변경이 반영된 뒤
사용자가 확인을 시작할 수도 있고 이미 마쳤을 수도 있으므로, 확인 항목은 그 기능이 준비 중인 기능
목록의 구성 확인 필요 자리에 더 이상 없다는 사실을 기준으로 삼는다. 어느 쪽이든 이 변경이 의도한
결과이며, 반대로 그 자리에 그대로 남아 있으면 변경이 듣지 않은 것이다.

낱말 인식 범위를 어떤 형태까지 넓혔는지와 개발자용 절차 차단이 약해지지 않았는지는 사용자가 화면
에서 확인할 수 없어 자동 검증이 덮는다. 어느 요구사항을 어느 검사가 덮는지는 작업 문서의 완료
조건에 요구사항 번호로 적었다.

## 작업 구성

작업은 하나다. 고칠 자리가 확인 동선을 사용자 확인 절차로 인정하는 판정 함수 하나이고, 그 함수와
그것을 부르는 자리와 시험이 모두 한 파일 안에 있다. 낱말 목록을 넓히는 일과 어미 변화를 견디게
하는 일은 같은 함수의 같은 대조식에서 만나므로, 둘로 나누면 같은 파일을 두 작업이 차례로 여는 것
말고 얻는 것이 없다.

화면과 프론트 계약은 이 그룹에서 고치지 않는다. 판정이 답을 바꾸면 기능 표시 상태가 사용자 QA
대기로 바뀌고, 그 값을 목록으로 가르는 자리는 지금 화면이 이미 갖고 있다.

## 이번 그룹이 다루지 않는 것

구성 확인 필요 상태의 사유를 화면에 사용자 언어로 설명하는 일과 그 상태를 아키텍트에게 자동으로
넘기는 일은 다루지 않는다. IDEA-FC871690에서 나온 SPEC-073이 그 자리를 맡았고, 이 그룹은 오판을
없애는 데까지만 간다.

GROUP-070의 확인 동선 문장을 판정에 맞추어 손보는 개별 조치도 하지 않는다. 문서를 고쳐서
해결하지 않는 것이 기획서 REQ-05의 요구다.

영어로 쓴 확인 동선의 판정, 확인 동선 작성 규약, 기능 상태를 정하는 나머지 조건도 그대로 둔다.

### QA-01 · 개발이 끝난 기능의 품질 확인이 열리는지 확인하기

1. 앱에서 품질 확인 화면을 엽니다.
   > 지금 확인할 기능 목록과 준비 중인 기능 목록이 함께 보입니다.
2. 준비 중인 기능 목록에서 앱 업데이트 직후 복구와 업데이트 적용을 다루는 기능을 찾습니다. 목록에서 상태가 구성 확인 필요인 항목을 훑으면 됩니다.
   > 그 기능은 구성 확인 필요 자리에 없습니다. 개발이 끝난 뒤에도 구성 확인 필요로 남아 있던 상태가 해소되었다는 뜻입니다.
3. 같은 화면의 지금 확인할 기능 목록을 봅니다.
   > 앞 단계에서 찾던 그 기능이 확인 시작 입구와 함께 서 있습니다. 이미 확인을 마친 뒤라면 완료된 기능으로 남아 있고, 어느 쪽이든 준비 중인 기능 목록으로 되돌아가 있지 않습니다.
4. 지금 확인할 기능 목록에서 그 기능의 확인 시작 입구를 눌러 확인 절차를 엽니다.
   > 확인 절차의 단계와 기대 결과가 문서에 적힌 그대로 열립니다. 문장이 판정에 맞추어 고쳐진 흔적이 없습니다.
5. 확인 절차를 닫고 지금 확인할 기능 목록의 다른 항목을 하나 엽니다.
   > 이 변경 전부터 확인이 열리던 기능들도 그대로 열리고, 확인 시작 입구의 모습과 동작이 달라지지 않았습니다.
6. 준비 중인 기능 목록에 구성 확인 필요로 남은 기능이 있으면 그 항목을 봅니다.
   > 남아 있는 항목은 확인 동선의 문장 표현이 아닌 다른 이유로 그 상태입니다. 사용자 확인 절차가 아예 없거나, 끝나지 않은 작업이 남아 있거나, 개발자용 절차가 섞인 경우입니다.
