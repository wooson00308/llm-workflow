# 사용자 차례가 아닌 기능 상태를 설명하고 구성 오류를 아키텍트가 자동으로 맡게 하기

## 기능 설명

기능 목록에서 사용자가 지금 할 일이 없는 상태의 기능은 상태 이름만 보여주지 않는다. 구성 확인
필요, 구성 중단 의심, 개발 막힘 세 상태의 기능은 무엇이 문제이고 누가 처리하며 지금 사용자가 할
일은 없다는 사실을 상세 화면을 열지 않아도 목록 자리에서 함께 보여준다. 확인 시작 입구와는 다른
모습으로 그려서, 사용자가 목록을 훑을 때 자기 차례인 항목과 아닌 항목이 구분되게 한다.

구성 확인 필요 상태에는 사유가 함께 붙는다. 필수 값이 없거나 형식이 어긋난 경우, 이 구성 버전에
속한 작업이 하나도 없는 경우, 작업이 가리키는 기능과 구성 버전과 출처가 기능 문서와 어긋난 경우,
사용자 확인 절차가 없거나 사용자 행동으로 인정되지 않는 경우, 자동 확인 모드인데 확인 절차가 적혀
있는 경우, 끝나지 않은 작업이 남은 경우를 각각 다른 문장으로 보여준다. 해당하는 조건이 여럿이면
여럿을 보여주고 하나로 합치지 않는다. 사유는 상태를 계산하는 쪽이 상태와 함께 내려주며, 화면이
문서를 다시 읽어 원인을 추측하지 않는다.

구성 확인 필요 기능은 아키텍트가 자동으로 맡는 대상이 된다. 지금은 이 상태의 기능을 어느 역할도
집지 않아 사람이 발견해 물어볼 때까지 그대로 남는다. 대상 순서는 사용자 확인 반려 다음, 작업 정의
오류 수정 앞이며, 선점 규칙은 다른 아키텍트 대상과 같다. 아키텍트는 같은 기능 식별자와 같은 구성
버전을 유지한 채 기능 문서와 그 기능의 작업 문서만 고친다.

원인이 문서 밖에 있으면 몇 번을 다시 잡아도 같은 결과가 나온다. 그래서 아키텍트가 한 번 시도해
문서 쪽에 고칠 곳이 없다고 판단하면, 그 판단을 기능 문서에 남기고 그 구성 버전에서는 자동 대상에서
빠진다. 그때 화면은 그 기능을 사람의 판단이 필요한 상태로 보여주고, 사용자가 무엇을 판단해야
하는지를 함께 보여준다.

기능 상태 계산 결과 자체는 달라지지 않는다. 같은 문서 집합을 넣으면 이 변경 전후로 같은 상태가
나온다. 사용자 확인 흐름, 결정 도장, 기획서 승인 게이트, 기능별 구성 버전도 그대로다.

## 사용자 행동이 늘지 않는다는 뜻

기획서 R-01은 사용자가 지금 할 행동이 있는 상태를 사용자 QA 대기 하나로 유지하라고 요구하고,
R-18은 아키텍트가 풀지 못한 기능이 그때 처음 사용자 차례가 된다고 적었다. 이 그룹은 두 요구를
다음과 같이 함께 지킨다.

사람의 판단이 필요한 상태는 화면에 그 사실과 판단할 내용을 보여주지만, 홈 화면의 내 선택 대기
목록에 들어가지 않고 앱 안에서 누를 입구를 새로 만들지도 않는다. 사용자가 읽고 판단할 거리가
생겼다는 뜻이지, 앱이 사용자에게 처리할 동작을 요구한다는 뜻이 아니다. 확인 시작 입구는 지금과
같이 사용자 QA 대기 기능에만 붙는다.

## 품질 확인 방식

사용자 확인으로 둔다. 이 그룹이 바꾸는 것의 대부분은 사용자가 목록에서 읽는 문장이고, 개발자가
아닌 사람이 화면을 열어 그대로 확인할 수 있다.

확인 시점의 판 상태를 전제하지 않도록 확인 절차를 짰다. 이 그룹의 확인을 시작하는 순간 이 기능
자체가 사용자 QA 대기로 지금 확인할 기능 목록에 서 있으므로, 자기 차례인 항목의 모습은 언제나
그 자리에서 대조할 수 있다. 준비 중인 기능 목록과 개발 보드에는 확인 차례가 아닌 기능이 함께
보이며, 그 항목들이 이번 변경의 대상이다.

아키텍트 대상 판정 순서와 선점 배제, 자동 대상에서 빠지는 조건은 사용자가 화면에서 확인할 수 없어
자동 검증이 덮는다. 어느 인수 조건을 어느 검사가 덮는지는 네 작업 문서의 완료 조건에 조건 번호로
적었다.

## 작업 구성

작업을 넷으로 나눴다.

첫째 작업은 상태를 계산하는 쪽이 사유와 사람 판단 필요 상태를 함께 내려주게 한다. 표시 상태 목록에
사람 판단 필요를 더하고, 구성 확인 필요로 답할 때 어떤 조건이 맞지 않았는지를 값 목록으로 함께
싣고, 기능 문서가 적은 사람 판단 거리를 읽어 싣는다. 나머지 세 작업 가운데 화면과 대상 판정이 이
값을 쓰므로 이 작업이 앞에 온다.

둘째 작업은 아키텍트 역할 계약에 구성 오류 수정 절차를 적는다. 어떤 대상이 오고 무엇을 고칠 수
있고 무엇을 그대로 두어야 하는지, 고치지 못했을 때 무엇을 남기는지가 계약에 있어야 한다.

셋째 작업은 아키텍트 대상 판정에 구성 확인 필요 기능을 넣는다. 앱의 판정과 조건 스크립트가 같은
답을 내야 하므로 두 자리를 한 작업에서 함께 고친다. 계약이 먼저 자리를 잡은 뒤 대상이 나가야
하므로 둘째 작업 뒤에 오고, 판정이 읽는 상태 값이 첫째 작업에서 나오므로 첫째 작업 뒤에도 온다.

넷째 작업은 세 화면이 그 값을 사용자 언어로 보여주게 한다. 개발 보드의 기능 레인, 품질 확인
화면의 준비 중인 기능 목록과 확인 도중 열 수 없게 된 기능 화면, 기획서 화면의 기능 상태가 그
자리다. 첫째 작업이 정한 값을 읽으므로 그 뒤에 오고, 셋째 작업과는 파일이 겹치지 않아 나란히
진행할 수 있다.

그룹 밖 순서는 두 자리에 붙는다. 첫째 작업이 고치는 화면 계약 파일을 지금 TASK-S071-03이 잡고 있어
그 뒤로 두었고, 넷째 작업이 고치는 공용 스타일 파일을 TASK-S068-01과 TASK-S071-03이 함께 잡고 있어
같은 이유로 그 뒤에 두었다. 두 자리 모두 이미 진행 중인 화면 사슬이 먼저 지나가는 자리다.

## 이번 그룹이 다루지 않는 것

어떤 문서가 구성 오류인지 가리는 판정 기준은 고치지 않는다. 자연스러운 한국어 관찰 서술이 사용자
확인 절차로 인정되지 않는 문제도 여기에 속하며, 기획서가 IDEA-85EF9AD9에서 나온 별도 기획서로
넘겼다. GROUP-070의 확인 절차 문장을 지금 판정 규칙에 맞게 고치는 개별 조치도 이 그룹의 일이
아니다.

기능 상태 이름 체계를 전면 개편하는 일, 개발 작업 단위의 상태 표시를 바꾸는 일, 사용자 행동이 없는
상태를 알림이나 메일로 보내는 일, 구성 오류를 앱이 직접 고치는 일도 다루지 않는다. 문서를 고치는
주체는 아키텍트 세션이다.

구성 중단 의심과 개발 막힘의 기존 자동 처리 경로도 바꾸지 않는다. 이 두 상태에는 화면 설명만
더한다.

### QA-01 · 자기 차례가 아닌 기능이 목록에서 구분되는지 확인하기

1. 앱에서 품질 확인 화면을 엽니다.
   > 지금 확인할 기능 목록에 이 기능이 확인 시작 입구와 함께 서 있습니다. 그 항목에는 지금 할 일이 없다는 설명이 붙어 있지 않습니다.
2. 같은 화면의 준비 중인 기능 목록을 봅니다.
   > 구성 확인 필요, 구성 중단 의심, 개발 막힘, 사람 판단 필요 가운데 하나로 표시된 기능마다 상태 이름과 함께 무엇이 문제인지, 누가 처리하는지, 지금 사용자가 할 일은 없다는 문장이 항목 자리에서 바로 보입니다. 그 문장에 내부 상태 이름이나 파일 경로, 코드 이름이 그대로 나오지 않습니다.
3. 준비 중인 기능 목록에서 구성 확인 필요로 표시된 기능이 있으면 그 항목을 봅니다.
   > 어떤 조건이 맞지 않아 그렇게 판정됐는지가 사용자 언어 문장으로 함께 보입니다. 해당하는 조건이 여럿인 기능에서는 문장이 여럿 보이고, 하나로 뭉뚱그려지지 않습니다.
4. 준비 중인 기능 목록에서 사람 판단 필요로 표시된 기능이 있으면 그 항목을 봅니다.
   > 아키텍트가 문서 쪽에서는 고칠 곳을 찾지 못했다는 사실과, 사용자가 무엇을 판단해야 하는지가 함께 보입니다.
5. 개발 보드 화면을 엽니다.
   > 기능 레인에서도 확인 차례가 아닌 기능마다 품질 확인 화면에서 본 것과 같은 세 가지가 보이고, 그 자리가 눌러서 처리하라고 요구하는 모습이 아닙니다.
6. 기획서 화면을 열고 승인된 기획서에서 파생된 기능의 상태 자리를 봅니다.
   > 같은 상태의 기능에서 같은 설명이 보입니다.
7. 다시 품질 확인 화면으로 돌아와 지금 확인할 기능 목록의 항목을 하나 엽니다.
   > 확인 절차가 지금까지와 같이 열리고, 확인 시작 입구의 모습과 동작이 달라지지 않았습니다.
