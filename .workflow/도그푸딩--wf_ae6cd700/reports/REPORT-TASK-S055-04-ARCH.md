# TASK-S055-04 정의 수정 보고서

## 결정권자 요약

TASK-S055-04는 활동 화면에 필요한 사건을 만드는 조회 범위가 빠져 있어 시작할 수 없었다.
새 작업을 만들지 않고 기존 작업에 목록 조회 범위 하나를 추가했다.
요청 기록의 생성 시각과 작업에 연결된 요청과 갱신 시각을 두 활동 사건의 근거로 명시했다.
기존 선행 관계와 이력과 막힌 사유는 그대로 보존했다.
작업은 개발 준비 상태로 돌아갔으며, 사용자 재개 이력은 추가하지 않았다.
제품 코드는 변경하지 않았다.

## 수정 근거

- 작업의 `blocked_kind: definition_error`와 보존된 `## 막힌 사유` 절을 읽었다.
- `REPORT-TASK-S055-04-DEV`가 완료 조건 9와 검증 절차 8을 추진하려면 목록 조회가 활동 사건을 싣는 경로가
  범위에 필요하다고 기록했다. 나머지 조건은 기존 화면 범위로 구현할 수 있다고 판정했다.
- 앱 소유 승인 `DECISION-22C3CC2F`와 `SPEC-055` R2·R6·R9·R12를 다시 대조했다. 요청과 수정을 서로 다른 활동으로
  보이되 앱 소유 기록과 작업 사실에서 로컬로 파생하고, 수정만으로 상태를 자동 전환하지 않는 범위다.
- 사용자 수정 요청 기록은 없었다. 새 공통 규칙이 허용한 정의 오류 작업 자체의 막힌 사유와 개발 보고서를
  근거로 수정했고 `revision_request_id`는 추가하지 않았다.

## 수정 내용

- 상태: `blocked` → `todo`. 아키텍트의 정의 수정 복귀이므로 `history`는 추가하지 않았다.
- 선언 범위: 기존 13개 화면 파일에 `src-tauri/src/infrastructure/fs_project_repository.rs` 하나를 추가했다.
- 선행 관계: `TASK-149`, `TASK-S055-02` 모두 그대로 보존했다.
- 완료 조건 9: 앱 소유 요청 기록을 요청 사건으로, 작업이 연결한 요청과 작업 갱신 시각을 아키텍트 수정
  사건으로 목록 조회에 싣는 조건을 추가했다. 활동 화면의 구분 표시 조건은 보존했다.
- 검증 절차 8: 목록 조회의 두 사건과 활동 화면의 두 이름을 각각 검사하게 나뉈다.
- 나머지 완료 조건과 검증 절차는 제품 요구를 줄이지 않고 보존했다.

## 범위 사전 검사

- 활동 화면은 목록 항목의 `events`만 읽고, 목록 조회는 `read_decision_documents`와
  `merge_qa_decision_events`를 통해 앱 소유 결정과 작업 이력을 사건으로 합친다.
- 정의 수정 요청은 같은 저장소 구현의 `read_revision_request_records`가 이미 읽는다. 작업이 연결한 요청은
  `handled_revision_request_id`로 확인할 수 있다. 따라서 새 조회 명령이나 원격 호출 없이 기존 목록 조회에서 두 사건을 만들 수 있다.
- `TaskEvent`는 이미 임의 종류 문자열과 시각을 담는다. `src-tauri/src/domain/project.rs`는 읽어 확인했지만 새 구조나 필드가
  필요하지 않아 범위에서 제외했다.
- 요청 저장 판정과 이력 종류 제한은 이 작업이 바꾸지 않는다. 목록 조회 조립과 활동 표시만 변경하면 완료 조건 9와
  기존 조건을 충족할 수 있다.

## 검증 결과

- YAML 파서로 작업 문서를 읽어 `status`, `blocked_kind`, 식별자, 승인 참조, 선행 관계, 선언 범위와 이력을 확인했다.
- 상태가 `todo`고 `blocked_kind: definition_error`가 보존됐으며, 기존 이력 3개와 `## 막힌 사유` 절이 그대로임을
  대조했다.
- 완료 조건과 검증 절차의 번호가 각각 1부터 14, 1부터 10까지 중복과 누락 없이 유지됨을 확인했다.
- `git diff --check`가 통과했다.

## 남은 위험과 인계

- 처리 사건의 시각은 작업이 처리한 요청을 연결하며 같이 바꾸는 `updated_at`을 근거로 한다. 후속 전이가 이 값을 다시
  바꾸기 전에 사건을 조립하는 특성을 검사로 고정해야 한다. 요청의 생성 시각과 연결 식별자는 앱 소유 기록이라 그대로 유지된다.
- 요청이 없는 정의 오류 복구는 새 공통 규칙이 에이전트 운영을 위해 허용한 경로다. 다만 `SPEC-055`의 현재 제품 기능은 앱 소유
  요청과 연결된 처리 사건을 보여 주는 범위라, 요청 없는 복구를 별도 활동 사건으로 추측하지 않는다.
