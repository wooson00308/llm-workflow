## 분해 근거

기획자 핸드오프(REPORT-SPEC-002-PLAN)가 "전역 파일 쓰기와 프로젝트 로컬 설치를 같은 작업에 묶지 않는 편이 검증하기 쉽다"고 했다. 그 판단을 받아들이되 축을 하나 더 넣었다.

- **쓰기 대상으로 분리**: 프로젝트 로컬 쓰기(TASK-003)와 전역 파일 쓰기(TASK-004)를 나눴다. 실패 조건과 위험도가 다르다. 전역 파일은 사용자의 다른 프로젝트 잡이 들어 있어 손상 시 피해 범위가 넓다.
- **읽기와 쓰기로 분리**: TASK-005·TASK-006이 읽기, TASK-003·TASK-004·TASK-007이 쓰기다. 기획서 완료 조건 11("앱 시작·프로젝트 열기·자동 새로고침만으로는 파일이 변경되지 않는다")은 읽기 경로에 쓰기가 없다는 것이 코드 구조로 드러나야 검증이 쉽다.
- **UI 슬라이스를 사용자 QA 가능한 단위로**: TASK-006만 완료해도 "연동 카드가 뜨고 상태가 맞다"를 사용자가 확인할 수 있다. 커맨드 배선만 하는 작업은 만들지 않았다. QA 대상이 없는 작업이 되기 때문이다.

기획서 완료 조건 13개는 전부 어느 작업에든 매핑돼 있다. 조건 2~5·8·9는 파일 엔진 수준(TASK-004)과 화면 조작 수준(TASK-007) 양쪽에서 검증하도록 나눠 넣었다.

## 실측으로 확인한 사실

기획서 R2~R5의 전제를 이 세션에서 다시 확인했다. 추정으로 작업에 넣은 항목은 없다.

- 하트비트 파서(`~/Git/claude-heartbeat/src/heartbeat/core.py`)는 줄을 trim한 뒤 `## `로 시작하면 잡 헤더, `- `로 시작하면 필드로 읽는다. 그 외는 전부 무시한다. HTML 주석 마커가 안전하다는 전제가 실제로 성립한다.
- 첫 `## ` 헤더 앞의 `- ` 줄만 전역 설정(`tick`)으로 읽힌다. 관리 블록을 앞에 넣으면 안 되는 이유가 코드로 확인된다.
- 파서는 마지막에 `slug`와 `prompt`가 모두 비어 있지 않은 잡만 남긴다. 두 필드가 빠진 잡은 조용히 사라진다. TASK-004 참고 사실에 넣었다.
- slug 규칙은 "절대 경로의 `/`를 `-`로 치환"이다. `/Users/catze/project/workflow-labs` → `-Users-catze-project-workflow-labs`이고, 실제 `~/.claude/HEARTBEAT.md`의 값과 일치한다.
- 데몬은 기동 시 pid 파일을 쓰고 정상 종료 시 지운다. 상태 조회 경로에서 `os.kill(pid, 0)`으로 생존을 확인해 죽어 있으면 pid 파일을 지운다.
- `state.json`의 `last_result`가 가질 수 있는 값은 `success`, `failure`, `skipped`, `quota_skipped`, `timeout` 다섯이다. `last_run`은 타임존이 없는 로컬 시각 문자열이다. `recent_runs`라는 쿼터용 배열 필드도 있다.
- 조건 검사 실패도 `last_run`을 갱신하고 `last_result`를 `skipped`로 남긴다. 정상 동작 중인 프로젝트의 기록은 대부분 `skipped`다. UI에서 실패로 읽히게 만들면 안 된다는 조건을 TASK-006에 넣었다.

## 아키텍트가 정한 구현 결정

기획서가 제약만 주고 형식을 열어 둔 지점이다. 근거를 남기니 QA에서 다르게 보이면 되돌려도 된다.

1. **잡 이름 = `wf-<역할>` + slug** (예: `wf-planner-Users-catze-project-workflow-labs`). R2가 요구한 세 조건(프로젝트마다 다름·재설치해도 안정·`heartbeat jobs`에서 프로젝트 식별 가능)을 새 의존성 없이 동시에 만족하는 가장 단순한 규칙이다. 대안으로 검토한 경로 해시는 std의 해시가 버전 간 안정성을 보장하지 않고, `project_id` 사용은 같은 저장소를 두 경로에 clone하면 충돌한다. 이름이 길어지는 것이 비용이다.
2. **설치 상태 판정 = 파일 존재 검사만**. `HEARTBEAT.md` 또는 `heartbeat/` 디렉터리가 있으면 설치됨, `heartbeat.pid`가 있으면 실행 중으로 본다. 프로세스 생존은 확인하지 않는다. 확인하려면 플랫폼별 시스템 호출이나 새 의존성이 필요하고, 기획서가 요구한 것은 세 상태의 구분까지다. **한계: 데몬이 정리 없이 죽으면 "실행 중"으로 보인다.** 그래서 UI 문구가 판정 근거를 드러내도록 TASK-005·TASK-006에 조건으로 넣었다.
3. **조건 스크립트 본문은 `const` 리터럴로 복제한다.** `include_str!("../../../scripts/wf-eligible.sh")`로 원본을 참조하면 두 파일이 빌드 의존으로 묶여 나중에 원본을 지울 수 없다. 기획서가 앱 설치본을 단일 원본으로 삼되 이번 범위에서 원본을 정리하지 않기로 했으므로, 지금 묶으면 정리 시점에 되돌려야 한다. 비용은 스크립트 변경 시 두 곳을 맞춰야 한다는 것이며, 정리 작업 전까지만 발생한다.
4. **버전 표기는 셸 주석 두 줄** (`# managed_by: workflow-labs`, `# condition_script_version: 1`). `project_instructions.rs`의 `schema` + `rules_version` 판정과 같은 형태다.
5. **쓰기 순서는 조건 스크립트 먼저, 잡 나중.** 반대로 하면 존재하지 않는 스크립트를 가리키는 잡이 잠깐 활성화되고, 하트비트는 조건 검사 실패를 skip으로 처리하므로 증상이 "아무 일도 안 일어남"이라 원인을 못 찾는다. 잡 쓰기가 실패해도 설치된 스크립트는 되돌리지 않는다. 잡 없는 스크립트는 무해하고 롤백은 실패 경로를 두 배로 만든다.
6. **상태 폴링은 기존 2.5초 인터벌에 얹는다.** 기획서 R5가 새 감시 장치를 만들지 말라고 했다. 설정 화면을 보지 않아도 계속 도는 것이 비용이지만 읽는 파일이 작다.
7. **설치 확인 화면은 프론트가 만든다. 백엔드 dry-run 커맨드를 두지 않는다.** 실패 경로에서 원본이 바뀌지 않는 것이 엔진에서 보장되므로, 확인 단계는 "전역 파일을 건드린다"는 사실과 대상 경로를 알리는 것으로 R6을 만족한다.
8. **모듈은 홈 경로를 스스로 계산하지 않는다.** 경로는 전부 인자로 받고 해석은 커맨드 계층에서 Tauri 경로 API로 한다. 테스트가 사용자의 실제 `~/.claude`를 건드리지 않게 하는 유일한 방법이다. TASK-004·TASK-005의 완료 조건에 `grep`으로 확인하는 절차를 넣었다.

## 핸드오프 노트 (이 세션 범위 밖)

- **도그푸딩 환경에 중복 잡이 생긴다.** 현재 `~/.claude/HEARTBEAT.md`의 `wf-planner`·`wf-architect`·`wf-developer`는 사람이 손으로 적은 잡이다. TASK-007이 끝나면 같은 slug의 관리 잡 3종이 추가되어 역할당 두 세션이 깨어난다. R7 경고가 뜨는 것이 정상 동작이고, 수동 잡 제거는 사용자 몫이다. QA 시 이 상태를 버그로 보지 않아야 한다.
- **TASK-001·TASK-002(SPEC-001)가 아직 `todo`다.** 파일이 겹치지 않아 순서 제약은 없지만, TASK-001이 만드는 `docs/heartbeat.md`는 `scripts/wf-eligible.sh`를 공식 인터페이스로 기술하고 SPEC-002는 `.workflow/rules/` 설치본을 원본으로 삼는다. 두 산출물이 모두 존재하게 된 뒤 문서 경로를 정리하는 별도 아이디어가 필요하다.
- **조건 스크립트의 판정 공백이 그대로 앱 관리 자산이 된다.** lease 만료 미확인, `planner`의 `revision_requested` 미감지, `architect`의 최신 결정 미확인 세 가지다. 기획서가 로직 변경을 제외 범위로 뒀으므로 복제만 한다. 개선하려면 새 아이디어로 올려야 한다.
- **`.gitignore`에 `.workflow/.runtime/` 항목이 여전히 없다.** 이전 두 세션에서 올라온 노트이며 미해결이다.
- **잡 이름에 절대 경로가 들어간다.** `heartbeat jobs` 출력과 `state.json`에 사용자 홈 경로가 남는다. 로컬 도구라 문제로 보지 않았지만, 화면 캡처를 공유할 때 경로가 노출된다는 점은 알아 둘 만하다.
