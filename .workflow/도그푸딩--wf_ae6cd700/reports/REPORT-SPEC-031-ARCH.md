## 분해 판단

**둘로 나눈 이유.** 승인된 확인 필요 1번이 "앱 명령 하나"를 정했으므로 쓰기 경로(Rust + 게이트웨이 +
훅)와 화면(레인 액션 + 확인 화면 + 결과)이 서로 다른 파일 무리로 갈린다. 화면을 더 쪼개는 안 —
"액션과 확인 화면"과 "실행과 결과 보고" — 은 버리기로 했다. 실행이 없는 확인 화면은 눌러도 아무 일이
일어나지 않는 반쪽이고, 두 작업이 같은 두 파일을 다시 직렬로 만지게 되어 이득이 없다.

**TASK-099가 훅까지 가져간 이유.** 훅과 게이트웨이는 명령의 응답 형태(건별 결과 + 요약)를 그대로
따라가는 배선이라, 명령을 만든 세션이 함께 하는 편이 형태가 갈리지 않는다. 대신 컴포넌트 파일
(`WorkspaceShell.tsx`·`App.tsx`)은 TASK-100으로 넘겼다. 프롭 배선은 화면 쪽 결정이고, `App.tsx`를

## 아키텍트가 정한 것 (기획서가 정하지 않은 자리)

기획서가 비워 둔 자리를 이 분해에서 정했다. 근거를 각 작업 문서에 남겼다.

1. **명령 이름을 `confirm_task_qa_batch`로, `outcome` 파라미터는 만들지 않기로.** 일괄 반려가 기획서
   제외 범위이므로 파라미터로 열어 두지 않는다. 이름이 확인 전용이라는 사실을 스스로 말한다.
2. **건 하나를 처리하는 부분을 private 함수로 뽑아 단건·일괄이 함께 쓰기로.** 확인 필요 1번의 비용
   항목("규칙이 지켜지는 자리가 둘이 된다")을 가장 싸게 줄이는 방법이다. 단건 경로의 외부 동작은
   그대로 두는 조건을 달았다.
3. **빈 목록은 에러가 아니라 빈 결과로.** 새 `ProjectError` 변형을 만들지 않는다. 화면이 이미 R2로
   막는다.
4. **훅의 반환은 boolean이 아니라 건별 결과 배열 또는 `null`로.** R4의 건별 보고가 이 값을 타고
   화면으로 간다. 확인 사실 8의 전역 에러 문구에 건별 결과를 얹지 않는다.
5. **결과가 있는 동안 확인 화면을 자동으로 닫지 않기로.** 결과를 읽기 전에 화면이 사라지면 R4가
   무의미해진다.
6. **`WorkspaceShell`의 새 프롭을 필수로.** 선택 필드로 만들면 콜백 없이 도는 화면 상태가 생긴다.
