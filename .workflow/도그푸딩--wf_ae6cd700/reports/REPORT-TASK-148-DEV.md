# TASK-148 개발 보고서

## 결정권자 요약

사용자가 막힌 작업에 해결 근거를 적고 개발 준비 상태로 되돌리는 앱 명령을 구현했다.
상태 전이와 재개 이력, 사용자 감사 기록이 한 요청에서 함께 남고 하나만 남으면 성공을 돌려주지 않는다.
문서가 그사이 바뀌었거나 다른 세션이 선점했거나 마이그레이션 잠금이 있으면 아무 파일도 바뀌지 않는다.
같은 요청을 되풀이하거나 동시에 두 번 보내도 재개 이력과 감사 기록은 각각 한 건이다.
관리 규칙과 파일 계약에는 재개 기록을 앱과 사용자만 만든다는 문언을 넣었다.
집중 검사 15개, 백엔드 전체 609개, 프런트엔드 831개와 배포 빌드가 모두 통과했다.
화면 변경은 없으므로 사용자는 TASK-148 확인 동선의 검사 수치를 확인하고 도장을 찍으면 된다.

## 변경 파일과 모듈

- `src-tauri/src/domain/project.rs`: 재개 요청과 결과 타입을 추가했다. 결과는 성공과 복구 필요 두 상태를
  가지며, 복구 필요일 때만 남은 경로와 사유, 사용자가 할 행동을 함께 싣는다.
- `src-tauri/src/infrastructure/fs_project_repository.rs`: 재개 경로 전체를 구현했다. 관리 자산 설치 뒤
  프로젝트 쓰기 잠금을 잡고 대상 문서를 다시 읽어 요청 식별자 중복, `blocked` 상태, `updated_at` 일치,
  대상 lease를 차례로 판정한다. 감사 문서를 먼저 쓰고 작업 문서를 교체하며, 교체가 실패하면 방금 만든
  감사 문서를 지운다. 지우기까지 실패한 경우에만 복구 결과를 돌려준다. 이력 `kind` 허용 목록에
  `resumed`를 더하고 `workflow-labs/task-resume@1` 기록을 같은 작업 이벤트로 읽게 했다.
- `src-tauri/src/application/project_service.rs`, `src-tauri/src/commands/projects.rs`,
  `src-tauri/src/lib.rs`: 새 명령을 서비스와 명령 계층에 연결하고 실행기에 등록했다.
- `src-tauri/src/infrastructure/project_instructions.rs`: 공통 규칙에 재개 계약을 적고 `rules_version`을
  16으로 올렸다. `kind`는 일곱 값이 되었고, 에이전트는 `resumed` 이력과 재개 감사 기록을 쓰지 않으며
  `resumed`가 `in_progress`를 대신하지 않는다는 문장을 넣었다.
- `docs/file-contract.md`: "막힌 작업 재개" 절에 감사 기록 형식과 판정 규칙, 부분 저장 시 동작을 적고
  이력 값 목록과 상태 설명을 같은 내용으로 맞췄다.
- `src-tauri/src/infrastructure/managed_project_assets.rs`: 규칙 버전 상승에 맞춰 기존 검사의 버전 문자열만
  갱신했다. 판정과 검사 의도는 그대로다. 이 파일은 작업 문서의 `scope_files`에 없다.

## 검증 절차와 결과

- `cargo test --manifest-path src-tauri/Cargo.toml task_resume` 통과: 15 passed, 0 failed.
- `cargo test --manifest-path src-tauri/Cargo.toml` 통과: 609 passed, 0 failed.
- `npm run check` 통과: 타입 검사 성공, 25개 파일 831 tests 통과, 배포 빌드 성공.
- `cargo clippy --all-targets` 경고 없음, `cargo fmt` 적용.
- 새 검사는 완료 조건과 하나씩 대응한다. 정상 재개에서 상태·이력·감사 기록의 시각이 같고 막힌 사유 절과
  알 수 없는 프론트매터 필드가 보존되는지, stale 갱신 시각·이미 재개된 상태·미만료 lease·마이그레이션
  잠금·안전하지 않은 경로·미래 규격에서 작업과 결정 디렉터리 원문이 그대로인지, 같은 요청을 직렬과 동시로
  반복해도 기록이 한 건인지, 감사 저장 실패와 작업 저장 실패와 되돌리기 실패에서 각각 원본 보존 또는 복구
  결과가 남는지, 재개 뒤 선행 미충족이면 개발자 판정이 계속 자격 없음인지, 기존 QA 경로가 재개 이력과
  감사 원문을 지우지 않는지, 재개 기록이 기획서 결정 판정에 들어가지 않는지를 검사한다.

## 남은 리스크

- 되돌리기 실패 분기는 지우기 동작을 인자로 주입해 검사했다. 감사 문서를 쓸 수 있는 디렉터리는 그 문서를
  지울 수도 있어 파일 권한만으로는 이 실패를 만들 수 없기 때문이다. 실제 저장 장치 오류로 인한 지우기
  실패는 재현하지 않았다.
- 권한을 조작하는 두 검사는 유닉스에서만 돈다. 윈도우에서는 저장 실패 경로가 검사되지 않는다.
- 두 저장 사이에서 프로세스가 죽으면 감사 기록만 남거나 작업 문서만 바뀐 상태가 남는다. 앱은 이 상태를
  성공으로 읽지 않고 각각 다른 오류로 거절하지만 자동으로 고치지는 않는다. 사용자가 문서를 보고 정리해야
  한다.
- 규칙 버전이 16이 되어 기존 프로젝트의 규칙 파일은 다음 쓰기 명령에서 새 문언으로 교체된다.

## 후속 작업

- 재개 버튼과 패널, 프런트엔드 호출 배선은 이 작업의 범위가 아니다. 새 명령은 등록됐지만 화면에서 부르는
  곳은 아직 없다.
- 하트비트 조건 스크립트는 이력 값이 아니라 상태로 자격을 판정하므로 이번 변경으로 고칠 곳이 없었다.
  이후 규칙 작업이 `resumed`를 스크립트 쪽에도 설명할지는 그 작업에서 정할 일이다.
- 관리 자산 검사 파일을 범위 밖에서 손댄 것은 규칙 버전 상승이 그 검사의 고정 문자열을 깨뜨렸기 때문이다.
  다음 아키텍트 세션이 규칙 문언을 바꾸는 작업의 `scope_files`에 이 파일을 함께 넣어 주면 좋겠다.
