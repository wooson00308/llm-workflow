# TASK-S051-08 개발 보고서

## 결정권자 요약

실행 계획과 시작, 큐 상태 조회, 일시 정지와 취소와 재시도와 로그 읽기를 앱 백엔드 명령으로 만들었다.
계획은 아무것도 바꾸지 않고 후보와 제외 사유와 적용된 제한을 돌려준다.
확인한 계획만 시작되며 조건이 달라졌으면 성공이 아니라 새 계획 필요로 전달한다.
런타임을 읽지 못하면 상태를 모름으로 두고 마지막에 본 값을 실행 중이라고 말하지 않는다.
프로젝트 신원이 어긋난 응답은 어떤 명령에서도 성공으로 처리하지 않는다.
취소는 미리보기와 적용을 나누고 정리 단계가 남으면 전체 성공으로 표시하지 않는다.
실행은 언제나 런타임 큐를 거치며 앱이 도구를 직접 띄우는 경로를 만들지 않았다.
전용 자동 검사 18건을 더했고 앱 전체 검사 688건을 통과했다.
프런트 검사는 같은 시각 진행 중인 다른 작업 때문에 실패하며 그 사유를 아래에 적었다.

## 변경 파일과 모듈

- `src-tauri/src/domain/agent_runtime.rs`: 실행 상태 여덟 개와 실행 행, 계획, 취소 미리보기, 로그
  묶음, 큐 스냅샷 타입을 더했다. 계약 밖 상태 이름은 값으로 바꾸지 않고 그대로 남긴다.
- `src-tauri/src/infrastructure/agent_runtime_process.rs`: 계획·시작·취소·재시도·일시 정지·로그·상태
  일곱 호출을 더했다. 모두 고정 인자와 표준 입력 JSON만 쓴다.
- `src-tauri/src/application/agent_runtime_run_service.rs`: 새 파일이다. 계획, 시작, 취소, 재시도와
  응답 신원 확인을 담는다.
- `src-tauri/src/application/agent_runtime_status_service.rs`: 새 파일이다. 큐 조회, 일시 정지와 재개,
  로그 읽기를 담는다.
- `src-tauri/src/commands/agent_runtime.rs`와 `src-tauri/src/lib.rs`: 커맨드 여덟 개를 더하고 등록했다.
- `src-tauri/src/application/mod.rs`: 새 서비스 두 개 등록.

## 설계 판단

- 낡은 계획을 실패가 아니라 사실로 다룬다. 런타임이 개정 불일치를 알리면 앱은 그것을 오류 문구로
  뭉개지 않고 새 계획이 필요하다는 값으로 전달한다. 화면이 다음에 할 일이 그 값에서 갈린다.
- 응답의 프로젝트 신원을 모든 명령에서 확인한다. 계획, 시작, 취소, 재시도, 일시 정지, 상태 조회가
  각각 응답의 프로젝트 식별자를 요청과 대조하고, 다르면 성공으로 처리하지 않는다. 상태 조회는 다른
  프로젝트의 행이 하나라도 섞이면 응답 전체를 믿지 않고 모름으로 답한다.
- 조회 실패와 상태 없음을 가른다. 런타임을 부르지 못한 것은 큐가 비었다는 뜻이 아니므로 실행 목록을
  비우고 사유를 함께 싣는다. 화면은 그 사유로 모름을 표시한다.
- 취소는 남은 단계가 하나라도 있으면 부분 결과로 답한다. 프로세스 종료와 lease 정리 중 하나만 실패한
  상태를 성공으로 보이면 사용자가 정리된 줄 알고 넘어간다.
- 재시도가 같은 실행 식별자를 돌려주면 계약 밖으로 다룬다. 같은 식별자를 쓰면 이전 실패 기록이 새
  시도에 덮인다.

## 검증 절차와 결과

- `cargo test --manifest-path src-tauri/Cargo.toml` 통과: 688 passed. 이번에 더한 18건을 포함한다.
- `cargo clippy --all-targets` 경고 0건.
- 앱이 큐 밖에서 프로세스를 띄우지 않는 것을 검사로 고정했다. 이 서비스가 보내는 인자 배열에 `once`도
  provider 이름도 없고 첫 인자는 언제나 `agent`다. 프로세스를 만드는 자리는 설치된 launcher를 부르는
  한 곳뿐이며 그 인자도 고정 배열이다.
- `npm run check`는 실패한다. 아래에 사유를 적었다.

## 프런트 검사 실패의 사유

실패는 이 작업의 변경이 아니다. 같은 시각 프런트 작업 세션이 `src/features/projects/domain/types.ts`의
게이트웨이 타입에 에이전트 런타임 메서드를 더했는데, 그 타입을 구현하는 검사용 대역
`src/features/projects/application/useProjectWorkspace.test.ts`가 아직 갱신되지 않아 타입 검사가 어긋난다.

근거는 셋이다. 첫째, 이 작업은 TypeScript 파일을 하나도 바꾸지 않았고 범위 파일이 모두 `src-tauri`
아래다. 둘째, 오류가 가리키는 메서드 이름은 현재 커밋의 타입 파일에 없고 작업 트리의 그 파일에만 있다.
셋째, 실패한 검사 파일 자체는 수정되지 않은 상태다. 그 세션이 대역을 갱신하면 통과한다.

## 남은 위험

- 검증은 macOS에서만 실행했다.
- 상태 조회는 런타임이 돌려준 실행 행만 읽는다. 런타임이 어떤 행을 빠뜨리면 앱도 그 행을 모른다.
  이 계층에서 보충하지 않는 것이 설계이며, 그 대신 조회 실패와 상태 없음을 갈라 두었다.
- 로그 이벤트의 민감정보 제거는 런타임이 한다. 앱은 받은 이벤트를 다시 해석하지 않고 그대로 전달하므로,
  제거가 런타임 쪽에서 깨지면 앱은 그것을 알지 못한다. 런타임 쪽 검사가 그 자리를 지킨다.
- 화면은 범위 밖이다.

## 후속 작업

- 화면 작업은 계획의 `planId`를 그대로 보관했다가 시작 요청에 실어 보내면 되고, 취소는 미리보기를 먼저
  보여 준 뒤 확인을 받으면 된다.
- 프런트 검사는 프런트 작업이 대역을 갱신한 뒤 다시 실행해야 한다.
