# SPEC-053 아키텍트 인계 보고서

## 결정권자 요약

승인된 SPEC-053을 문서 계약, 로컬 파서와 우측 패널 세 작업으로 나눴다.
문서 계약과 파서는 서로 병렬로 진행할 수 있고, 우측 패널은 파서가 준비된 뒤 구현한다.
기존 결정 보드 작업이 수정할 파일을 피해 별도 막힘 패널과 스타일을 사용하도록 범위를 정했다.
작성된 사유와 시스템이 계산한 의존 정보는 계속 다른 출처로 표시하고 서로의 판정을 바꾸지 않는다.
기존 문서는 결정권자 요약과 원문 안내로 안전하게 폴백하며 일괄 수정하지 않는다.
세 작업 모두 준비 상태이며 제품 코드와 테스트 구현은 아직 시작하지 않았다.
사용자는 각 작업이 품질 확인 대기로 올라오면 문서 계약, 파서와 화면을 차례로 확인하면 된다.

## 대상과 산출물

- 프로젝트: workflow-labs / 활성 워크플로: 도그푸딩
- 역할: 프로젝트 아키텍트
- 대상 승인: DECISION-6723CEE0, SPEC-053
- 산출 작업: TASK-143, TASK-144, TASK-145 세 건
- 제품 코드와 테스트 구현: 수행하지 않음

## 아키텍처 결정

1. 차단 사유의 작성 계약은 앱 관리 공통 규칙과 개발자 역할 계약의 정본에 넣는다. 설치된
   `.workflow/rules/` 사본은 직접 편집하지 않고 관리 자산 동기화가 갱신하게 한다.
2. 파서는 문서 본문 전체에서 코드 펜스 밖의 정확한 `## 막힌 사유` 절이 한 번만 있는지 확인한다.
   네 목록 항목 전체가 유효할 때만 값을 반환하고 부분 성공은 만들지 않는다.
3. 관련 대상 파서는 작성 순서와 원문만 보존한다. 실제 작업 여부는 현재 워크플로 작업 목록과의
   문자 단위 일치로 화면에서 판단한다.
4. 기존 문서 폴백은 정확한 결정권자 요약 절, 무요약 안내와 원문 확인 순서다. LLM 요약, 네트워크와
   저장 변환물은 만들지 않는다.
5. 막힘 패널을 독립 구성 요소와 독립 스타일로 둔다. 결정 보드 작업이 예정한 `App.css`와
   `DevelopmentBoard.test.tsx`를 건드리지 않아 서로 다른 승인 작업의 병렬 공간을 보존한다.
6. 기존 선행·형식·겹침 표시는 현재 왼쪽 구조 정보 영역에 유지한다. 작성된 막힘 사유는 오른쪽 패널에
   두고 같은 공통 문장을 반복하거나 구조 판정을 변경하지 않는다.
7. 상태 재개 조작은 SPEC-053 범위 밖이다. SPEC-054의 후속 Architect 세션이 TASK-145의 패널 경계와
   파일 범위를 보고 별도 작업으로 추가해야 한다.

## 의존 관계

```text
TASK-S052-01 ─ TASK-143

TASK-S052-02 ─ TASK-144 ─ TASK-145
```

- TASK-143과 TASK-144는 서로 파일이 겹치지 않아 두 선행이 충족되면 병렬로 진행할 수 있다.
- TASK-145는 TASK-144의 전체 성공 또는 실패 파서 결과를 사용하므로 기능 의존성을 선언했다.
- TASK-143은 화면의 선행이 아니다. 현재 기존 문서는 폴백으로 표시하고 새 작성 계약은 이후 차단
  전환부터 적용하기 때문이다.
- TASK-S052-01과 TASK-S052-02는 각각 같은 파일의 기존 요약 계약을 먼저 확정하므로 교차 승인
  의존성을 명시했다.

## 병렬 안전과 기존 작업

- 세 작업 모두 한 줄 `scope_files` 선언을 갖고 허용 문자만 사용한다.
- 새 작업끼리 겹치는 파일은 없다. TASK-145의 선행은 파일 겹침이 아니라 파서 API 의존성이다.
- TASK-143의 두 파일은 현재 TASK-S052-01이 선점해 수정 중이므로 그 작업을 선행으로 두었다.
- TASK-144의 두 파일은 TASK-S052-02가 QA 대기 중이다. QA 반려가 일어나도 동시 수정되지 않도록
  그 작업을 선행으로 두었다.
- TASK-145는 새 구성 요소·스타일·검사와 `DevelopmentBoard.tsx`만 수정한다. 예정된 결정 보드 작업의
  전역 스타일과 대형 개발 보드 검사 파일을 피했다.
- 기존 미커밋 제품 변경과 SPEC-051·052 산출물은 읽기만 했고 수정하지 않았다.

## 검증

- `wf-eligible.sh architect`는 승인 뒤 `eligible`, 종료 코드 0이었다.
- `wf-claim.sh acquire SPEC-053 codex-architect 25`는 종료 코드 0으로
  `lease-49857-20260807150401`을 발급했고 작업 중 한 번 갱신했다.
- 승인 결정은 `created_by: user`, `outcome: approved`이며 같은 결정에서 파생된 기존 작업은 없었다.
- TASK-143부터 TASK-145까지 SPEC-053과 DECISION-6723CEE0을 출처로 삼고, todo 상태, created 이력,
  RFC3339 시각, 한 줄 범위 선언과 선행 관계를 갖도록 작성했다.
- 세 작업 문서의 결정권자 요약은 맨 앞 절이며 빈 줄 제외 열 줄 이하로 작성했다.
- 제품 소스, 승인 기획서, 결정 기록, manifest와 migration lock은 수정하지 않았다.
