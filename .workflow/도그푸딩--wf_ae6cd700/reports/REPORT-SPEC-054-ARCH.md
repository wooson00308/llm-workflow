# SPEC-054 아키텍트 인계 보고서

## 결정권자 요약

승인된 SPEC-054를 실행 수명, 기기 상태·업데이트, 사용자 재개 저장과 화면 흐름 네 작업으로 나눴다.
두 런타임 계약과 재개 백엔드는 서로 파일이 겹치지 않아 병렬로 구현할 수 있다.
마지막 화면 작업은 세 보완 작업과 기존 막힘 패널이 검증된 뒤 현재 두 작업의 재개 흐름을 확인한다.
재개 백엔드는 다른 blocked 규칙 작업을 선행으로 삼지 않아 복구 기능이 스스로를 기다리지 않는다.
재개는 사용자 근거와 감사 기록을 요구하며 에이전트나 보완 작업 상태가 자동으로 실행하지 않는다.
네 작업 모두 개발 준비 상태이며 제품 코드와 테스트 구현은 시작하지 않았다.
사용자는 보완 작업의 품질 확인 뒤 패널에서 원래 두 작업의 재개 여부를 직접 결정하면 된다.

## 대상과 산출물

- 프로젝트: workflow-labs / 활성 워크플로: 도그푸딩
- 역할: 프로젝트 아키텍트
- 대상 승인: DECISION-DC3ED4B7, SPEC-054
- 산출 작업: TASK-146, TASK-147, TASK-148, TASK-149 네 건
- 제품 코드와 테스트 구현: 수행하지 않음

## 아키텍처 결정

1. provider 수명 계약은 기존 동기식 실행을 즉시 반환하는 시작, offset 기반 이벤트 감시, 종료 대기,
   취소와 프로세스 신원 복구로 분리한다. 기존 `run`은 이 조합의 호환 경로로 유지한다.
2. 기기 상태·업데이트 계약은 runtime 측 JSON을 정본으로 삼는다. 앱은 SQLite, manifest 내부 파일과
   플랫폼 서비스 출력을 직접 읽지 않는다.
3. 업데이트 계획은 manifest, 설치·실행 버전, 서비스 신원과 실행 영향의 지문을 만든다. 적용 직전에
   같은 사실을 다시 읽어 stale 확인으로 상태를 바꾸지 않는다.
4. blocked 재개는 QA나 specification 결정을 재사용하지 않는다. `workflow-labs/task-resume@1` 감사
   문서와 `resumed` history를 사용자 요청 하나의 결과로 남긴다.
5. 재개 저장은 프로젝트 쓰기 잠금 아래 task와 감사 문서를 함께 준비한다. 부분 저장을 정상으로
   반환하지 않고 rollback 실패는 구조화된 복구 결과로 드러낸다.
6. 재개 뒤 상태는 todo다. developer 자격 판정을 다시 계산하지만 provider 시작과 in_progress 전이는
   별도 claim 세션에 남긴다.
7. TASK-149는 TASK-145의 blocked 패널을 확장한다. 구조화 사유가 없으면 기존 결정권자 요약과 원문
   안내를 보존하고 해결 근거를 앱이 작성하지 않는다.
8. 현재 TASK-S052-01도 blocked다. 재개 백엔드가 그 작업이나 뒤의 TASK-143을 기다리면 순환 대기가
   생기므로 TASK-148은 이미 검증된 TASK-S051-01만 선행으로 삼고 규칙 파일의 최신 변경을 보존한다.

  선언했다.

  조작으로만 todo 전이가 일어난다.

## 병렬 안전과 기존 작업

- 네 작업 모두 한 줄 `scope_files` 선언을 갖고 허용 문자만 사용한다.
- TASK-146과 TASK-147은 별도 계약 문서와 구현·검사 파일을 사용해 서로 겹치지 않는다.
- TASK-148은 앱 backend와 managed 규칙 정본을, TASK-149는 frontend와 blocked 패널을 담당해 새 작업
  사이의 겹침을 만들지 않았다.
- TASK-146은 TASK-S051-03의 provider 파일 변경 뒤에, TASK-147은 TASK-S051-02·05의 runtime 기반 뒤에
  선다.
- TASK-149는 TASK-145의 패널 파일을 확장하므로 명시적으로 뒤에 둔다. TASK-S051-09·10과 일부 frontend
  파일이 겹치지만 두 작업은 현재 blocked 체인 뒤에 있고, TASK-149가 재개 흐름을 먼저 완성한다.
- 기존 미커밋 제품 변경, 승인 기획서, 결정 기록, 기존 task와 migration lock은 수정하지 않았다.

## 검증

- 최초 `wf-eligible.sh architect`는 `eligible`, 종료 코드 0이었다.
- `wf-claim.sh acquire SPEC-054 llm-workflow-a-2 20`은 종료 코드 0으로
  `lease-83207-20260807160336`을 발급했고 작업 중 25분으로 갱신했다.
- 승인 결정은 `created_by: user`, `outcome: approved`이며 같은 결정에서 파생된 기존 작업은 없었다.
- TASK-146부터 TASK-149까지 SPEC-054와 DECISION-DC3ED4B7을 출처로 삼고 todo 상태, created 이력,
  RFC3339 시각, 한 줄 범위 선언과 비순환 선행 관계를 갖도록 작성했다.
- 네 작업 문서의 결정권자 요약은 맨 앞 절이며 빈 줄 제외 열 줄 이하이고 금지된 코드 표기를 넣지 않았다.
- 제품 소스, 기존 task, approval decision, project manifest와 schema version은 변경하지 않았다.
