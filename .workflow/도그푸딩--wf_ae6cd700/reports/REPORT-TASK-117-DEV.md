## 만든 것 1 — 설치 실행 버튼 (R2)

### 버튼이 붙는 자리는 백엔드가 정한다

`HeartbeatSetupStage`에 TASK-114가 실은 `runnable`을 화면 타입에 더하고, 마법사의 각 단계는 그
값**만** 보고 실행 통로를 세운다. 화면에 `step === "init"` 같은 분기가 없다.

검사가 그것을 고정한다 — 픽스처에서 1단계를 `runnable: true`로, 2단계를 `runnable: false`로 뒤집으면
버튼이 1·3단계로 따라간다. 화면이 단계 종류로 다시 가르면 통과할 수 없는 검사다.

### 복사 통로가 그대로 남는다

실행형 단계도 명령 원문과 복사 버튼을 잃지 않는다. 실행 통로는 복사 줄 **아래에** 새 블록으로
서고, 실행 대상이 아닌 1·4단계의 마크업은 한 줄도 바뀌지 않았다.

### 확인 화면

누르는 즉시 실행하지 않는다. 확인 화면에 실행할 명령 원문, 무엇이 만들어지는지, 그리고 판정 근거
경로(`evidence`)가 "만들어지는 자리"로 실린다. 마지막 줄이 **"파일을 만드는 것은 하트비트입니다.
앱은 이 경로에서 어떤 파일도 쓰지 않습니다"**다 — 같은 자리의 "지금 실행" 확인 화면("어떤 파일도
쓰지 않습니다")과 갈리는 지점이라 문구로 구분했다.

무엇이 만들어지는지의 문구는 단계별 표(`setupRunEffects`)에서 온다. **그 표는 버튼이 붙는 자리를
정하지 않는다** — 표에 없는 단계도 명령 원문과 경로만으로 확인 화면이 선다. 갈림이 둘로 늘지 않게
주석에 그 경계를 적었다.

### 실행 중과 결과

단계마다 따로 담기므로 한 단계가 도는 동안 다른 단계의 버튼은 그대로 눌린다. 도는 단계의 버튼만
비활성이고 그 옆에 진행 표시가 뜬다.

결과 셋을 서로 다른 값으로 그린다.

- `ran` — 성공/실패와 **종료 코드 숫자**, stdout·stderr 원문(접힌 `<details>`).
  **앱이 실패 사유를 지어내지 않는다.** 이 두 명령은 원인별 종료 코드가 계약에 없으므로
  (`docs/heartbeat.md` 4·5번 절) 코드마다 다음 행동을 적지 않는다. 업데이트 결과의 `exitNote`를
  빌려 오지 않고 `setupExitNote`를 따로 두었고, 그 이유를 두 함수의 주석에 적었다. 검사가
  업데이트 쪽 문구(예: 코드 11의 "미커밋 변경")가 이 자리에 오지 않는 것을 단언한다.
- `notRun` — 사실, 앱이 본 후보 목록, 사용자가 칠 명령 원문과 복사 버튼(R5).
- `notRunnable` — 앱이 대신 실행하지 않는 단계라는 경고. 정상 경로에서는 나오지 않는 값이고,
  나오면 화면과 백엔드의 답이 갈라진 것이므로 성공처럼 보이지 않게 경고로 그린다.

### 실행 뒤 갱신

실행이 끝나면 훅이 `inspectIntegrations`를 다시 부른다. 커맨드는 스냅샷을 돌려주지 않고 화면도
단계 상태를 스스로 바꾸지 않는다 — 설치 판정의 원천은 조회 하나다.

## 만든 것 2 — 버전 어긋남 표시 (확인 필요 2번)

### 부르는 시점

**카드가 펼쳐지는 순간 한 번, 업데이트가 끝난 뒤 한 번.** 그 둘뿐이다.

- 펼침: 카드의 효과 하나가 부른다. 의존값이 `expanded`와 통로 함수뿐이고 그 함수는 훅에서
  안정적이라, 2.5초 조회 주기가 새 스냅샷을 넣어 다시 렌더돼도 효과가 다시 돌지 않는다.
- 업데이트 뒤: 훅의 `updateHeartbeat`가 끝나는 자리에서 부른다. 방금 바뀐 값이 이 둘이라
  사용자가 결과를 보려고 카드를 접었다 펴게 하지 않는다.
- 겹쳐 부르기는 훅이 ref로 막는다. 카드가 두 번 렌더돼도 프로세스는 하나다.
- **미설치 상태에서는 아예 부르지 않는다.** 두 값이 모두 "확인 불가"일 뿐이라 새 사실이 없고,
  그 상태의 안내는 설치 마법사다. 프로세스를 띄우는 조작이라 부를 이유가 없는 자리에서 부르지
  않는 쪽을 골랐다. 검사가 그것을 고정한다.

완료 조건 10을 검사 둘이 받는다 — 훅 쪽에서 가짜 시간으로 주기를 세 번 돌려도 호출 수가 1에서
늘지 않는 것, 화면 쪽에서 스냅샷을 갈아 끼워 두 번 다시 렌더해도 늘지 않는 것.

### 그리는 값

카드 머리(설치 분기 안, 업데이트 통로 바로 위)에 두 값이 나란히 선다.

- **어긋남** — 두 값과 함께 경고 한 줄. "코드는 갱신됐는데 지금 도는 프로세스는 옛 코드입니다"와
  "위의 하트비트 업데이트가 그 상태를 푸는 다음 행동입니다". 그 버튼이 같은 자리 바로 아래다.
- **같음** — 같은 버전이라는 한 줄.
- **판정 불가** — 아는 값만 싣고 사유가 넷으로 갈린다(실행 파일 없음 / 띄우지 못함 / 출력이 계약
  밖 / 상태 파일에 도는 버전 없음). 백엔드가 사유를 여러 개 실으면 여러 개를 그대로 그린다 —
  하나만 고르면 나머지가 사라진다. 실행 파일을 찾지 못한 경우 본 후보 목록이, 출력이 계약 밖인
  경우 받은 원문이 함께 실린다. **한쪽만 아는 상태를 "같다"로도 "다르다"로도 접지 않는다.**
- 커맨드 자체가 거절한 것은 판정과 다른 값이라 경고로 따로 그린다.

084 경고의 판정은 건드리지 않았다(SPEC-024 R4, 기획서 제외 범위). 검사가 어긋남 표시 옆에서
업데이트 버튼이 그대로 있는 것을 단언한다.

## 하지 못한 검증 — 검증 절차 5

**이 세션에서 앱의 버튼을 실제로 누르지 못했다.** 사유 둘이다.

1. 이 세션은 비대화형이라 GUI 창을 조작할 수단이 없다.
2. `npm run tauri dev`를 두 번 시도했고 둘 다 **포트 1420이 이미 사용 중**이라 vite가 뜨지 못했다.
   그 포트를 잡고 있는 것은 **사용자가 15:28에 띄워 둔 `npm run tauri dev`(pid 79067/79090)와 그
   앱 창(pid 51757, 15:44 기동)**이다. 사용자의 프로세스이므로 죽이지 않았다. 내 시도 둘은 스스로
   끝났고 남은 프로세스는 없다.

대신 이 기기에서 화면이 무엇을 그릴지 정하는 값을 실측했다(2026-08-05T08:2xZ).

| 값 | 실측 |
| --- | --- |
| `~/.claude/heartbeat/state.json`의 `_daemon` | `{"version": "0.8.0", "pid": 875, "started_at": "2026-08-05T10:35:49.785635"}` |
| 이 셸의 `heartbeat --version` | `heartbeat 0.8.0` (`/Users/catze/.pyenv/versions/3.11.9/bin/heartbeat`) |
| 앱의 후보 1 — PATH의 `heartbeat` | GUI 앱이 물려받는 PATH에 pyenv가 없다(`launchctl getenv PATH`가 비어 시스템 기본) |
| 앱의 후보 2 — `~/.local/bin/heartbeat` | **없음** (실측) |

즉 **이 기기의 예상 결말**은 이렇다.

- 버전 표시: 도는 데몬 `0.8.0` / 디스크 `확인 불가` + "실행 파일을 찾지 못해…" + 본 후보 둘.
  두 값을 모두 읽을 수 있었다면 `0.8.0` = `0.8.0`으로 **같음**이었을 것이다. 그 사실이 이번 표시의
  값을 보여준다 — 앱은 자기가 못 읽었다는 것을 "같다"로 접지 않는다.
- 설치 실행 버튼: 확인을 누르면 `notRun`("실행 수단을 찾지 못했다") + 본 후보 둘 + 명령 원문.

기획서 확인 사실 11이 그대로 유효하고 TASK-113·116의 보고서가 적은 같은 표와 일치한다.
**실물 확인은 사용자 QA의 몫으로 남는다.**

QA에 도움이 될 사실: 사용자가 띄워 둔 vite dev 서버가 이 세션의 프론트엔드 변경을 HMR로 서빙하므로
**그 창에서 연동 화면을 열면 새 UI가 이미 보일 가능성이 높다.** 다만 그 앱의 Rust 바이너리는
15:44 빌드다. 디스크의 바이너리에는 `run_heartbeat_setup_step`·`check_heartbeat_versions`가 둘 다
