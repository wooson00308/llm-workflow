## 결과

| TASK-013 | 잡 model 필드를 지원 모델 선택 UI로 전환 (직접 입력 포함) | 선행 필수 없음. SPEC-003 작업과 병행 금지 | 모델 필드 컴포넌트(신규), `SettingsView.tsx`, `SettingsView.test.tsx` |

## 왜 한 건인가

기획서의 요구사항 R1~R5는 화면 한 곳(잡의 `model` 입력)에서만 성립하고, 백엔드 변경이 없다(R4). 나눌 축을
세 가지 검토했고 전부 기각했다.

- **선택 UI 먼저 / 직접 입력 나중.** 기각. 그 사이에 목록 밖 값이 적힌 파일을 앱이 표현하지 못한다. 저장하면
  사용자의 값이 목록 안 값으로 조용히 바뀌는데, 이건 R3가 금지한 동작이라 중간 상태로도 허용되지 않는다.
- **목록·컴포넌트 먼저 / 잡에 적용 나중.** 기각. 소비자가 없는 컴포넌트만 만드는 작업은 화면이 하나도
  바뀌지 않아 사용자가 QA할 것이 없다. SPEC-002·SPEC-003 분해에서 쓴 "QA 대상이 있는 단위로 자른다" 기준과
  어긋난다.
- **역할 잡 적용 / dream 잡 적용.** 기각. dream 잡 UI는 아직 없다(TASK-011·TASK-012 미구현). 지금 만들면
  내용이 비거나 조건부인 작업이 된다. 대신 R5를 "그 시점에 화면에 있는 모든 잡"으로 TASK-013에 넣고,
  순서 문제는 아래 항목으로 넘겼다.

## SPEC-003과의 순서 판단

기획자 핸드오프가 아키텍트 판단 사항으로 남긴 항목이다.

**권장: TASK-012 완료 후 TASK-013 착수.** 근거는 두 가지다.

1. 같은 파일 충돌. TASK-010이 `SettingsView.tsx`의 카드 골격을, TASK-012가 같은 화면의 쓰기 경로를
   재구성한다. TASK-013은 그 화면의 `model` 입력을 갈아 끼운다. 병행하면 세 작업이 같은 컴포넌트를 동시에
   고친다.
2. R5를 한 번에 만족한다. TASK-012가 끝난 시점에는 역할 잡 3종과 dream 잡이 모두 화면에 있으므로,
   "UI에 존재하는 모든 잡"이 한 번의 전환으로 덮인다.

**먼저 착수해도 성립하되 조건이 붙는다.** 그 경우 대상은 역할 잡 3종이고, TASK-012 구현자가 새 모델 필드
컴포넌트를 써야 dream 잡이 자유 입력으로 남지 않는다. TASK-012는 다른 승인 결정에서 파생된 문서라 이
세션에서 고치지 않았고, 대신 TASK-013의 의존성 절과 이 보고서에 적었다. 실제로 그 순서로 간다면 사용자가
TASK-012 착수 세션에 이 사실을 알려야 한다.

## 아키텍트가 정한 구현 결정

기획서가 제약만 주고 형식을 열어 둔 지점이다. 근거를 남기니 QA에서 다르게 보이면 되돌려도 된다.

1. **목록과 필드 UI를 한 컴포넌트 파일에 함께 둔다.** R2의 "한 곳에만 정의"와 R5의 "잡마다 따로 정의하지
   않는다"를 구조로 보장하는 가장 싼 방법이다. 목록만 공유하고 UI를 잡마다 만들면 선택지는 같은데 직접 입력
   동작이 갈라질 여지가 남는다. 비용은 새 파일 하나다.
2. **직접 입력 모드는 값에서 유도하지 않고 별도 상태로 둔다.** 유도하면 사용자가 직접 입력으로 `opusX`를
   적는 도중 `opus`를 지나는 순간 입력 칸이 사라진다. 대신 그 상태가 설치 요청 payload에 섞이면 기존
   `toHaveBeenCalledWith` 단언이 깨지므로, payload는 다섯 키 그대로 유지하라고 못 박았다.
3. **직접 입력 칸의 접근성 이름을 선택 컨트롤과 분리한다**(예: `개발자 모델 직접 입력`). 현행 라벨 규약
   `"<잡 이름> 모델"`은 선택 컨트롤이 그대로 가져간다. 기존 테스트가 그 이름으로 필드를 찾고 있어
   (`SettingsView.test.tsx:148`) 바꾸면 R1과 완료 조건 10이 함께 흔들린다.
4. **`opusplan`은 목록에 넣지 않는다.** CLI 바이너리에 문자열이 있지만 기획서 R2가 목록을 별칭 네 개로
   고정했다. 아키텍트가 임의로 요구사항을 넓히지 않는다. 필요하면 별도 아이디어 사항이다.

## 실측으로 확인한 사실

기획서의 전제를 이 세션에서 다시 확인했다. 추정으로 작업에 넣은 항목은 없다.

- `SettingsView.tsx:62`의 `editableFields` 루프가 `interval`·`maxPer`·`model`을 같은 `<input>`으로 렌더한다
  (`:376`). `model`만 갈라내는 것이 진입점이다.
- 프론트 규칙은 `:91`의 `fieldRules.model`(`/^\S+$/`), 백엔드는 `heartbeat_jobs.rs:323`의 `is_model`이다.
  두 규칙은 같은 값을 통과시킨다. 기획서 기술과 일치한다.
- `claude --help`의 `--model`은 별칭 예시로 `fable`·`opus`·`sonnet`, 정식 모델명 예시로 `claude-fable-5`를
  든다. `/opt/homebrew/bin/claude` 바이너리 문자열에는 `fable`·`haiku`·`opus`·`sonnet`이 모두 있다.
  기획서가 고정한 네 별칭이 지금도 유효하다.
- 같은 바이너리에 `opusplan` 문자열도 있다. 기획서가 다루지 않은 값이다(위 결정 4).
- 설치 요청은 `SettingsView.tsx:339`에서 `{ role, ...form[role] }`로 만들어지고, 테스트가
  `SettingsView.test.tsx:244`에서 다섯 키 객체로 정확히 단언한다. 폼 상태에 필드를 더하면 여기서 깨진다.
- 백엔드 `RoleJobRequest`(`heartbeat_service.rs:53`)와 프론트 `RoleJobRequest`(`types.ts:126`)가 짝이다.
  이번 작업에는 백엔드 변경이 없다.

## 완료 조건 매핑

기획서 완료 조건 11개는 전부 TASK-013 완료 조건 1~11에 1:1로 들어갔다. 나눌 작업이 하나뿐이라 분산이 없다.

## 확인 필요 2건의 반영

기획서 본문이 "승인 시 아래 제안대로 진행한다"고 명시했고 결정이 `approved`이므로 제안대로 반영했다.

1. 목록 구성 범위 → 별칭 네 개만. 정식 모델명은 직접 입력으로 지정한다.
2. 빈 `model`(CLI 기본 모델) 지원 → 이번 범위 밖. 선택지에 "기본값" 항목을 만들지 말라고 TASK-013의 제약에
   명시했다. 만드는 순간 백엔드 검증과 저장 계약까지 번진다.

## 핸드오프 노트 (이 세션 범위 밖)

- **기존 `it.each` 테스트의 `개발자 모델` 행이 그대로 남을 수 없다.** 선택 컨트롤에는 `claude opus` 같은
  문자열을 넣을 수 없다. 커버리지를 직접 입력 경로 테스트로 옮기고 전후 목록을 보고서에 적으라고 TASK-013에
  넣었다. 기획서 완료 조건 10("삭제되거나 비활성화된 테스트가 없다")을 문자 그대로 읽으면 케이스 수가 줄어든
  것처럼 보일 수 있어, QA에서 사용자가 판단할 수 있게 근거를 남기도록 했다.
- **하트비트 실패 사유가 앱에 도달하지 않는 구조적 한계는 그대로다.** 이 기획서는 모델명 오타를 예방으로
  우회했을 뿐이다. 다른 원인으로 잡이 실패하면 여전히 "실패" 배지만 남는다. 별도 아이디어가 필요하다.
- **조건 스크립트 이중화(`scripts/wf-eligible.sh` ↔ `.workflow/rules/wf-eligible.sh`)가 네 번째 보고서째
  미해결이다.** 사용자 아이디어 등록이 필요하다.
- **`wf-eligible.sh`의 `planner` 판정이 `revision_requested` 기획서를 감지하지 못한다.** 기획서 재작업 루프는
  아직 하트비트로 자동 기동되지 않는다.
- **`.gitignore`에 `.workflow/.runtime/` 항목이 없고, 추적되지 않은 `.serena/`가 남아 있다.** 커밋 전 정리
  여부를 정해야 한다.
- SPEC-003 작업 중 TASK-008이 `qa_waiting`이고 TASK-009~012가 `todo`다. 사용자 QA와 개발자 세션이 먼저다.
