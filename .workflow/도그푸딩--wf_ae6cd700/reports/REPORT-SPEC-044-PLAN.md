## 기획 판단

### 아이디어의 실측 주장은 전부 섰고, 값은 아이디어가 아는 것보다 컸다

직전 세션(SPEC-043)이 아이디어의 실측을 뒤집었기 때문에 이번에도 인용된 근거를 먼저 되짚었다. 이쪽은
셋 다 그대로 확인됐다 — PR #19의 검사 실행 세 건에서 윈도우 clippy 4건, 프런트 3건, 대조 헬퍼
하드코딩 2건이 순서대로 났고, 각 실패가 로컬에서 원리상 잡히지 않는 이유도 코드·설정과 일치했다.

확인 과정에서 아이디어가 적지 않은 사실이 나왔고, 그것이 이 기획서의 무게를 바꿨다.

- 아이디어는 "#17이 CI를 안 기다리고 병합 → #18 수습"을 한 번의 전례로 적었다. **같은 일이 v0.1.6
  에서도 있었다** — PR #12가 검사 시작 73초 뒤 병합됐고 병합 커밋의 Rust 세 갈래가 전부 빨갰으며 PR
  #13이 수습했다.
- 더 무거운 쪽: **v0.1.8은 그 빨간 커밋 그대로 태그가 붙어 게시됐다.** 태그 `v0.1.8`이 병합 커밋
  `0899245`를 가리키고 그 커밋의 main 검사는 윈도우 Rust 실패다. 수습 `ead3ea6`에는 태그가 없다.
  v0.1.6은 수습 뒤에 태그가 붙어 이 경로를 통과하지 않았다. 즉 "빨간 커밋에서 산출물이 게시되는 경로"는
  가정이 아니라 이미 한 번 통과한 실물이다.
- 그것이 막히지 않는 구조적 이유도 확인했다. **태그 워크플로는 검사 매트릭스를 돌리지 않는다** —
  버전 대조와 3-OS 번들 빌드만 있고 테스트·서식·정적 검사 명령이 없다. PR 검사가 산출물 앞의 마지막
  검사다.

정확성을 위해 기획서 본문에 함께 적은 것: v0.1.8의 빨강은 정적 검사 한 건이었고 사용자가 받은 앱의
동작을 바꾸지 않았다. 그래서 근거를 피해 크기가 아니라 절차에 뒀다 — 무엇이 빨갰는지는 그날의 운이었다.

### "규범이 앉을 자리" 질문에 결정적인 사실 하나

아이디어의 판정 기준은 "어디에 적어야 다음 컷 세션이 반드시 읽게 되는가"였다. 의미상 가장 맞는 자리인
`docs/releasing.md`를 실제로 누가 읽는지 확인했더니 **개발 로그 여드레치에서 인용 0건**이고 링크는
`README.md:55` 한 곳뿐이었다. 반면 컷 세션이 기준으로 삼는 로컬 게이트는 로그에 51번 나온다. 지금
릴리스 가이드는 "적혀 있지만 아무도 읽지 않는" 문서다.

그래서 후보 넷을 판정 기준으로만 갈라 기획서에 적었고, 선택은 확인 필요 1·2로 남겼다.

- 세션 진입 문서는 관리 블록 밖이 열려 있고(공통 규칙 §2가 금지하는 것은 블록 안 편집), 설치기가 블록
  밖을 보존한다는 것이 `preserves_existing_content_and_is_idempotent` 테스트로 고정돼 있다. 확인하고
  적었다.
- 공통 규칙 자산은 세 역할 세션의 계약이고 컷 세션은 그 역할이 아니다. 게다가 앱 소유라 바꾸려면 앱
  코드와 자산 버전을 함께 올리는 개발 작업이 된다. 자리도 절차도 맞지 않아 후보에서 사실상 뺐다.
- **저장소 설정(필수 상태 검사)이 실질적인 선택지다.** `main`에 브랜치 보호가 없고 규칙 집합도 0건이며
  사용자 계정은 `admin: true`다. 문서 규범과 달리 이쪽은 "읽지 않아서 못 지킨다"를 원천에서 없앤다.
  다만 사용자 계정으로만 켜고 끌 수 있어 에이전트 작업의 완료 조건으로 검증되지 않는다 — 그래서
  이번 범위에서는 빼고 확인 필요 2로 올렸다. 사용자가 켜기를 택하면 나머지는 그대로 두고 R5의 무게만
  줄어든다는 것도 함께 적었다.

### 재실행 기준은 아이디어의 전제를 확인한 뒤 좁게 잡았다

아이디어는 "비결정적 테스트가 남아 있는 동안 그린 확인이 재실행 도박이 되지 않게" 기준이 필요하다고
적었다. 그 전제를 측정했다 — **검사 실행 51건에서 같은 커밋이 두 번 돈 것은 2건이고 둘 다 결론이
같았다. 빨강이 재실행으로 초록이 된 기록은 0건이다.** SPEC-043도 다른 경로로 같은 결론(리눅스 테스트
단계 실패 0건, 뒤집혔다는 실패 둘은 윈도우였고 수정으로 통과)에 닿아 있다.

그래서 허용 범위를 "검사 대상 코드와 무관한 실패(러너 사망·네트워크·취소)에 한해 한 번, 사유를 병합 전에
기록"으로 좁게 제안했다. 근거 없이 폭을 열면 없던 습관이 생긴다는 판단이다.

### 구현 방식은 고르지 않았다

R1~R6은 전부 결과의 성질로 적었다. 문장을 어느 파일 어느 절에 어떤 형태로 쓸지, 정본과 포인터를 어떻게
나눌지는 승인 뒤 아키텍트·개발자 몫이다. 확인 필요 1이 자리만 사용자 결정으로 올린다.

## SPEC-043과의 경계

SPEC-043은 제외 범위에 "커밋·릴리스 절차와 재실행 허용 기준"을 이 건의 몫으로 명시해 뒀다. 이 기획서는
반대 방향으로 같은 선을 그었다 — 비결정적 테스트 자체의 처방은 SPEC-043의 몫으로 제외 범위에 적고,
R4의 마지막 줄에 "그 상황이 실제로 오면 답은 테스트를 고치는 쪽이지 재실행 폭을 넓히는 쪽이 아니다"를
남겼다. 두 문서가 같은 문장을 두고 부딪치는 자리는 없다.

SPEC-043은 아직 사용자 결정 대기다. 그 결과는 이 기획서의 승인 여부에 영향을 주지 않는다.
