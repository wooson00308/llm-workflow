# SPEC-068 기획 보고서

## 결정권자 요약

IDEA-52CC48B0을 실행 환경 계획 적용 결과의 화면 표시 규칙으로 구체화했다.
적용이 끝나면 확인 창이 결과 화면으로 바뀌어 단계별 결과를 순서대로 보여준다.
실패한 단계에는 사유를 사용자 언어로 적고, 부분 실패를 성공과 구분해 표시한다.
마지막 적용 결과는 창을 닫은 뒤에도 실행 환경 상태 자리에서 다시 읽을 수 있다.
런타임이 이미 설치된 기기의 연결 계획은 확인 창이 설치가 아니라 서비스 연결을 말한다.
적용 절차, 계획 확인 순서, 단계 이름과 순서, 배너 판정 규칙은 유지한다.
지금 요청하는 것은 SPEC-068의 승인 여부다.

## 대상과 예약 절차

- 역할은 planner이고 대상은 `IDEA-52CC48B0` 하나다.
- 런타임이 넘긴 lease `lease-10400-20260818075513`을
  `sh .workflow/rules/wf-claim.sh renew IDEA-52CC48B0 lease-10400-20260818075513 30`으로 갱신해 종료
  코드 0을 확인했다. 같은 대상에 `acquire`는 실행하지 않았다.
- 결과 접두어 `RES-20260818T075513Z-10400-20260818075513`은 이 예약을 가리키는 이름으로만 쓰고
  문서 식별자에는 넣지 않았다. 문서 이름은 계보 규칙을 따라 `specs/`에서 쓰이지 않은 가장 낮은
  세 자리 번호인 `SPEC-068`을 골랐다. `SPEC-001`부터 `SPEC-067`까지가 이미 있고 빈 번호는 없다.
- 쓰기 전에 `specs/SPEC-068.md`와 `reports/REPORT-SPEC-068-PLAN.md`가 없음을 확인했다. 기획서는
  덮어쓰기를 막은 셸 리다이렉션으로 만들어 기존 문서를 덮지 않았음을 확인했다.
- `.workflow/.runtime/migration.lock`은 없다. `.workflow/rules/custom.md`도 없으므로 적용한
  프로젝트 커스텀 규칙은 없다.

## 대상 적격성

- `IDEA-52CC48B0`을 `source_idea_id`로 참조하는 기획서는 이 세션 시작 시점에 하나도 없었다.
  미처리 아이디어의 통상적인 경우에 해당한다.
- lease 디렉터리에는 이 예약이 만든 `IDEA-52CC48B0.yml` 외에 `DECISION-5E5DCA0B.yml`,
  `DECISION-82640432.yml`, `TASK-S065-01.yml`이 있었다. 모두 다른 대상의 것이고 이 세션은 건드리지
  않았다.
- 회수할 중단 산출물은 없었다. 이 대상에 대한 중단된 `draft` 기획서가 없으므로 인계 판단이
  필요한 잔여물도 없다.

## 진행 순서

1. lease 갱신으로 소유를 확인했다.
2. 곧바로 `specs/SPEC-068.md`를 `status: draft`와 `source_idea_id`만 담아 만들어, 병렬 세션이 작성
   중임을 보게 했다.
3. 아이디어 원문과 현재 코드를 읽어 사실을 확인한 뒤 본문을 작성했다.
4. 자체 검토 후 `status: user_review`로 옮기고 `updated_at`을 갱신했다.
5. 이 보고서를 쓰고 같은 lease를 반납했다.

## 아이디어와 기획서의 대응

아이디어가 요구한 세 가지를 요구사항으로 옮겼다.

- 첫째, 적용 뒤 단계별 결과와 실패 사유 표시 → REQ-01, REQ-02.
- 둘째, 상태가 그대로인 이유를 화면에서 읽을 수 있게 → REQ-03.
- 셋째, 이미 설치된 기기에서 연결만 필요한 경우의 확인 창 문구 → REQ-04.

아이디어가 후속으로 미룬 "Windows 기기에서 서비스 연결이 실제로 왜 실패하는지"의 원인 수정은
제외 범위에 명시했다. 이 기획서는 사유를 화면에 드러내는 데까지만 책임진다.

## 코드에서 확인한 사실

기획서 본문의 근거다. 기획자 세션이므로 읽기만 했고 코드는 고치지 않았다.

- 적용 결과 값은 단계 목록과 각 단계의 상태, 실패 사유 문장을 싣는다. 설치 계열 적용의 단계는
  버전 설치, 실행기 전환, 서비스 연결 세 개다.
  근거: `src-tauri/src/application/agent_runtime_install_service.rs`의 적용 경로와
  `src-tauri/src/domain/agent_runtime.rs:254`의 단계 결과 구조.
- 파일 설치 뒤 단계가 실패하면 결과는 `partial_success`로 돌아오고 "설치본은 놓였지만 남은 단계가
  있습니다"라는 설명이 함께 온다. 오류가 아니라 정상 응답이다.
  근거: `src-tauri/src/application/agent_runtime_install_service.rs:566`.
- 앱 상태는 마지막 적용 결과를 `application` 필드에 보관하고, 이 값을 그리는 화면은 없다.
  `src/features/projects/components/` 전체에서 이 필드를 읽는 곳은 테스트의 초기값 두 줄뿐이다.
  근거: `src/features/projects/application/useProjectWorkspace.ts:880` 부근의 상태 갱신과
  `src/features/projects/domain/types.ts:1712`의 타입 주석.
- 적용이 예외로 실패하면 계획 창이 다시 열리며 사유가 표시된다. 정상 응답의 부분 실패는 이 경로를
  타지 않으므로 표시가 남지 않는다.
  근거: `src/features/projects/application/useProjectWorkspace.ts:894` 부근의 예외 처리와
  `src/features/projects/components/agents/AgentRuntimeView.tsx:369`의 오류 표시.
- 서비스 연결 단계가 실패하면 서비스는 등록되지 않은 상태로 남고, 배너는 등록 여부만 보므로
  "자동 배정 서비스 연결 필요"를 계속 표시한다.
  근거: `src/features/projects/components/agents/AgentRuntimeView.tsx:82`.
- 확인 창은 네 가지 계획에 하나의 제목("실행 환경 변경")과 하나의 안내 문장을 쓰고, 버전 줄은
  설치 버전과 번들 버전을 화살표 양쪽에 그대로 적는다. 두 값이 같으면 같은 버전이 두 번 보인다.
  근거: `src/features/projects/components/agents/AgentRuntimeView.tsx:345` 이하.

## 기획자가 정한 판단

- 결과 화면은 설치, 업데이트, 복구, 내려받기 네 계획이 함께 쓴다. 네 계획의 적용 결과가 같은 구조로
  돌아오고 표시가 없는 문제도 네 계획에 공통이라, 계획마다 다른 결과 화면을 둘 이유가 없다고 봤다.
  아이디어는 연결 계획 하나를 말했지만, 같은 화면을 나눠 쓰는 쪽이 표시 공백을 한 번에 메운다.
- 마지막 적용 결과를 창을 닫은 뒤에도 다시 읽을 수 있게 했다. 아이디어의 둘째 요구인 "상태가
  그대로인 이유를 화면에서 읽을 수 있다"는 창이 닫힌 뒤에도 성립해야 한다고 판단했다. 상태를
  보관하는 자리는 이미 있으므로 새로 만드는 것은 표시뿐이다.
- 결과를 어느 화면 요소로 그리는지, 다시 여는 입구를 어떤 형태로 두는지는 정하지 않았다. 아키텍트가
  정할 구현 사항이다.

## 인계 노트

- SPEC-067이 같은 에이전트 화면 상단을 다루며 현재 사용자 검토 중이다. 두 기획서가 모두 승인되면
  작업 분해 시 표시 자리가 겹치는지 확인해야 한다. 이 기획서는 배너 판정 규칙과 준비 단계 동선을
  바꾸지 않으므로 내용상 충돌은 없다고 본다.
- 이 표시가 구현되면 Windows 기기의 서비스 연결 실패 사유가 화면에 드러난다. 그 사유가 확인된 뒤
  원인 수정은 새 아이디어로 올려야 한다. 이 세션은 아이디어를 만들지 않았다.

## 자체 검토

- `.workflow/rules/workflow.md` §8의 구조화 요약 형식을 확인했다. `### 제안`, `### 현재`,
  `### 변경 후`, `### 비용과 위험`이 이 순서로 한 번씩만 있고, 요약 안에 역따옴표 토큰, 파일 경로,
  식별자, 함수나 타입 이름을 쓰지 않았다. 문서 id는 예외로 허용된 형태로만 썼다.
- `### 비용과 위험`에 유지 항목과 되돌리기 가능 여부, 미승인 시 남는 상태를 모두 적었다.
- §9의 한국어 규칙을 확인했다. 영어 줄표를 문장 구분으로 쓰지 않았고, 은유 대신 구현, 표시, 등록
  같은 동작 이름을 썼다.
