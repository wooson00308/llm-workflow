# TASK-S076-01 개발 보고서

## 결정권자 요약

공통 규칙의 결정권자 요약 절이 이제 항목별 문장 수 상한을 적는다. 제안은 한 문장이고 현재와 변경
후와 비용과 위험은 각각 세 문장 이하이며, 상한을 문장 수로 정한 이유와 날짜·인용·조사 경위·실측
표는 요약이 아니라 문서 본문에 적는다는 문장을 같은 절에 함께 넣었다. 비용과 위험의 필수 사실 네
가지를 세 문장에 담는 예시도 넣어, 상한이 필수 사실을 밀어내지 않는다는 것이 예시만 읽어도 보이게
했다. 문장 수 상한은 기획서와 개발 작업 문서에 걸리고 구현 보고서는 열 줄 상한을 그대로 쓰며, 이미
쓰인 문서는 한 건도 고치지 않았다. 규칙 번호를 32에서 33으로 올렸으므로 설정 화면의 규칙 항목에
갱신 대기가 뜨고, 사용자가 갱신을 눌러야 설치된 규칙 파일이 새 문구로 바뀐다. 러스트 시험 943건과
프론트 시험 582건, 타입 검사, 생산 빌드가 격리 사본과 통합 커밋에서 모두 통과했다. 이 결과는
GROUP-076 확인 절차의 10번 단계, 규칙 번호를 보는 자리를 뒷받침한다.

## 바꾼 파일과 모듈

선언한 파일 하나 안에서 끝났다. `src-tauri/src/infrastructure/project_instructions.rs`이다.

- 규칙 원본 `WORKFLOW_RULES`의 `### The structured summary` 하위 절. 열 줄 상한과의 관계를 적던
  문단을 문장 수 상한을 적는 문단으로 바꾸고(C1), 그 뒤에 문단 넷을 더했다. 상한을 문장 수로 정한
  이유와 글자 수 상한을 두지 않는다는 문장(C2), 근거 서술이 본문으로 간다는 문장과 그 이유(C3),
  비용과 위험을 세 문장으로 쓰는 방법과 마크다운 코드 울타리 예시(C4), 적용 대상과 소급하지
  않는다는 문장(C5)이다. 제목 넷과 그 순서, 제목별 작성 규칙 목록, 금지 조건, 옛 일곱 제목 규격
  문장은 한 글자도 건드리지 않았다(C7).
- 버전 값 둘. 21행의 `WORKFLOW_RULES_VERSION`과 규칙 본문의 `rules_version`을 33으로 올렸다(C6).
  역할 계약 셋의 버전 상수와 본문 값은 그대로다.
- 같은 파일 시험 모듈. 옛 문구를 확인하던 두 줄을 새 문단의 문구로 바꾸고, 지우려던 문장이 남아
  있지 않다는 확인(`!rules.contains`)을 함께 넣었다. C1부터 C5를 각각 짚는 부분 문자열 확인
  13건을 `records_the_structured_summary_contract_in_the_installed_rules`에 더했다. 숫자 32를
  직접 쓰던 확인 19군데(`rules_version: 32` 17건, `assert_eq!` 2건)를 33으로 맞췄다.

작업 문서 밖에서 읽은 것은 DECISION-290F9E88 머리말과 GROUP-076이다. 작업 문서가 모자라서가 아니라
승인 짝이 SPEC-076의 최신 승인인지 보는 자격 판정과, 이 증거가 뒷받침하는 확인 절차를 보고서에
적기 위해서다. 구현 판단은 모두 작업 문서 안에서 끝났다.

## 검증 절차와 결과

격리 사본에서 먼저 돌리고, 통합한 커밋 위에서 같은 검사를 다시 돌렸다.

- 통합 후보: 기준 커밋 `46d41c4`, 격리 브랜치 커밋 `a1868a9`, 바뀐 파일은 선언한 하나뿐이다.
- 격리 사본 1차: `cargo test` 915건과 28건 통과, `cargo fmt --check` 무출력, `npm run check`의
  타입 검사와 시험 579건과 생산 빌드 통과.
- 통합 직전 공유 기준이 두 번 움직였다. 먼저 `726f86d`으로, 이어 다른 작업이 통합한 `5d4f4ca`로
  옮겨졌다. 두 번 다 격리 브랜치를 그 커밋 위로 옮기고 검사를 다시 돌렸다. 마지막 기준에서
  `cargo test` 915건과 28건, `npm run check`의 시험 582건과 타입 검사와 생산 빌드가 통과했다.
- 통합: 공유 작업 공간에 `1a9b614`로 정방향 병합했다. 통합 시점에 `.workflow` 밖의 추적 파일 중
  수정된 것이 없어 충돌 없이 들어갔다. 통합 커밋과 같은 커밋의 격리 사본에서 검사를 한 번 더 돌려
  `cargo test` 915건과 28건, `npm run check` 시험 582건과 타입 검사와 생산 빌드가 통과했다.
- 검증 절차 3(C7): 제목 넷과 순서, 금지 조건, 옛 일곱 제목 규격, 요약 없는 문서에 관한 기존
  부분 문자열 확인은 한 줄도 고치지 않은 채 통과했다.
- 검증 절차 6(C8): `git status`에서 바뀐 파일은 선언한 하나뿐이었다. 설치된 규칙 파일

  33으로 바뀌는 것은 사용자가 설정 화면에서 갱신을 누를 때 앱이 하는 일이다.
- 검증 절차 7(사람이 읽는 확인): 하위 절을 처음부터 끝까지 읽었다. 상한 문단이 앞의 제목별 작성
  규칙 목록을 이어받아 "제안 한 문장, 나머지 셋은 세 문장 이하"로 수를 매기고, 다음 문단이 왜
  문장 수인지를, 그다음이 그러면 근거는 어디에 쓰는지를 순서대로 답한다. 예시는 그 바로 뒤에서
  세 문장이 비용·유지·되돌리기·미승인 네 가지를 실제로 담아 보이고, 마지막 문단이 누구에게
  걸리는지로 절을 닫는다. C1부터 C5가 각각 한 자리씩 차지해 따로 찾아진다.

## 남은 위험

- 문장 수는 앱이 검사하지 않는다. 지키는 것은 문서를 쓰는 세션의 몫이고, 이번 변경으로 확인
  장치가 생기지는 않았다. 기획서가 그렇게 정했고 이 작업의 범위 밖이다.
- 규칙 문구가 실제로 요약을 짧게 만드는지는 새 규칙이 설치된 뒤 쓰이는 문서에서만 확인된다.
  지금 시험이 보증하는 것은 문구가 규칙 원본에 들어 있다는 사실까지다.
- 코드 울타리 예시를 규칙 본문에 넣었으므로, 나중에 이 절을 옮기거나 다시 쓰는 세션은 울타리가
  닫힌 상태를 유지해야 한다. 닫히지 않으면 설치된 규칙 파일의 뒤쪽 절이 통째로 코드 블록으로
  읽힌다.

## 후속 작업

- 아키텍트 확인 요청: GROUP-076 확인 절차 10번은 설치 번호와 제공 번호가 둘 다 33이고 상태가
  현재라고 적혀 있다. 이 작업 직후 상태는 설치 32 · 제공 33 · 갱신 대기이며, 사용자가 갱신을
  누른 뒤에야 10번이 적은 상태가 된다. 절차에 갱신을 누르는 동작이 빠져 있어 그대로 따르면
  기대와 다른 화면을 보게 된다. 개발자는 작업 그룹 문서를 고치지 않으므로 여기에 남긴다.
- 프로젝트 문서 `docs/file-contract.md`는 요약 절을 한국어로 다시 설명하면서 아직 옛 일곱 제목
  규격을 적고 있다. 작업 문서가 범위 밖으로 뺀 항목이고 이번 변경이 만든 차이도 아니지만, 이제
  문장 수 상한까지 더해져 규칙 원본과의 간격이 벌어졌다.
- 작업 문서 TASK-S076-01의 머리말에서 `created_at` 항목이 이 세션이 상태를 바꾸기 전에 이미
  사라져 있었다. 같은 자리를 지난 두 작업 문서(TASK-S074-01, TASK-S075-01)도 똑같이 비어 있고
  TASK-S076-02에는 남아 있다. 세션이 지운 값이 아니고 앱이 소유한 자리라 되돌리지 않았다.
