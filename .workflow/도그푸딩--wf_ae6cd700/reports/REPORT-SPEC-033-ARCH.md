## 순서를 정한 근거

### 하나로 묶은 것

TASK-104가 셋 중 가장 크고 쪼개지지 않는다. 조건 스크립트는 sh·PowerShell 두 본문이 한 파일에 있고,
`CONDITION_SCRIPT_VERSION`과 두 본문의 버전 줄이 일치 단언 테스트로 묶여 있다(확인 사실 16). 기획자
분기와 아키텍트 분기도 같은 파일·같은 버전 축을 공유한다. 어느 하나만 먼저 착지하면 버전 셋이 어긋나
설치본이 매번 다시 쓰이거나 두 플랫폼의 판정이 갈린다.

### 기획서가 요구한 순서

SPEC-033 R9 마지막 항목과 완료 조건 13이 "TASK-096·TASK-099·TASK-100과 파일이 겹치지 않도록
분해되거나 순서가 지어지고, SPEC-032의 작업과 만나면 나중에 서는 쪽이 선행 선언으로 순서를 적는다"를
요구했다.

- **SPEC-032는 이미 승인·분해됐다**(DECISION-0D79A7F0, TASK-101·102·103 전부 `todo`). 확인 사실 17이

  기획서다.** 세 작업 중 둘이 TASK-101을 직접 선행으로 적었다.

## 아키텍트가 고정한 값

기획서가 방법을 열어 둔 자리가 셋이다. 세 구현(sh·PowerShell·Rust)이 같은 답을 내야 하고, R8은 형태를
아예 아키텍트에게 맡겼으므로 분해에서 정했다. 전문은 각 작업 문서의 "아키텍트가 고정하는 값" 절에 있다.

1. **훑기 예산** (TASK-104): 한 분기가 한 워크플로우에서 각 디렉터리를 한 번만 읽는다. 후보 루프 안에
   디렉터리 훑기가 남지 않는다. 모은 값은 셸 변수에 담고 조회는 셸 내장만 쓴다.
2. **부분 일치 보존 표기** (TASK-104): 참조 판정은 `키: *`를 `키:`로 정규화해 모으고 `case`의 부분
   문자열 검사로 조회한다. 원본 정규식과 정확히 같은 답을 내고, `IDEA-1`이 `IDEA-12`에 걸리는 지금
   성질까지 보존된다.
3. **최신 결정 판정의 동치 변환** (TASK-104): `spec_id`별 `created_at` 최댓값 표로 바꾼다. 자기 자신을
   표에서 빼지 않아도 답이 같다 — 비교가 `>`이므로 자기 값 하나로는 참이 되지 않고, 동률이 최신으로
   남는 규칙이 그대로다.
4. **"이유가 유효한가"의 기준** (TASK-105): "두 번째 훑기가 첫 번째 훑기가 읽은 같은 파일 내용에서
   함께 만들어지는가, 그리고 함께 만들었을 때 payload가 그대로인가". 둘 다 예면 이유가 유효하지 않으니
   합치고, 하나라도 아니오면 합치지 않고 근거를 보고서에 적는다.
5. **회귀 감지 장치의 계량** (TASK-106): 벽시계 시간이 아니라 **조건 스크립트가 띄우는 외부 프로세스
   수**다. `PATH`를 shim 디렉터리 하나로 두고 세며, 1배·3배 픽스처에서 선형 단언과 절대 단언 둘을 건다.
   시간은 러너마다 달라 단언이 될 수 없고, 실제로 비싼 것은 프로세스 수다(확인 사실 5).

## 개발자가 확인할 자리 — 아키텍트가 판단으로 넘긴 것

1. **아키텍트 분기의 곱은 하나가 아니라 둘이다.** 기획서 확인 사실 5는 최신 결정 판정(안쪽
   `decisions/` 122건)만 짚었다. 분해에서 세어 보니 **후보마다 `tasks/*.md` 97건을 다시 읽는 분해 여부
   판정**(`wf-eligible.sh` 아키텍트 분기의 `grep -qs source_decision_id`)도 곱이다 — 파일 읽기가
   31 × 97 = 3,007회이고, 3배 픽스처에서는 후보와 파일이 함께 3배가 되어 9배가 된다. 확인 사실 4에서
   작업 문서를 97→20건으로 줄였을 때 줄어든 0.9초가 이 자리다. **둘 다 없애지 않으면 완료 조건 2의
   3배 픽스처에서 3초를 지키지 못한다.** 기획자 분기에는 같은 모양이 셋 있다(참조 판정·최신 결정
   판정·후속 기획서 판정). TASK-104가 이것을 작업 내용으로 적었다.
2. **앱 판정에는 곱이 없다.** `role_eligibility.rs`는 값만 받고, 최신 판정은
   `latest_approvals`(`fs_project_repository.rs:1754`)가 결정을 한 번 읽어 끝낸다. 그래서 TASK-104의
   `role_eligibility.rs` 범위는 **검사뿐**이고, 판정 함수를 고쳐야 할 상황이 오면 그것은 두 판정이
   갈라졌다는 신호이므로 고치지 말고 보고서에 적으라고 적었다. TASK-106도 앱 쪽 비용 감시를 만들지
   않는다.
3. **줄 번호가 기획서와 다르다.** 확인 사실 12가 적은 번호(`read_spec_decisions:1562` 등)는 기획서
   작성 시점 값이고, 세션 시점 작업 트리에서는 `:1639`다. 미커밋 변경이 크므로 세 작업 문서 모두
   "줄 번호는 작업 트리 기준이고 쓰기 직전에 대상 줄을 다시 읽는다"를 적었다.
4. **설치본과 상수가 어긋나 있다.** `.workflow/rules/wf-eligible.sh`는
   `condition_script_version: 6`, 작업 트리 상수는 7이다. 앱이 다음 설치에서 따라 올리는 종류의
   차이이고, 세 작업 모두 설치본을 손으로 고치지 못하게 했다. **다만 데몬이 실제로 돌리는 것은
   설치본이므로, TASK-104가 착지해도 앱이 재설치하기 전까지는 오늘의 타임아웃이 그대로 남는다.**
   이것은 기획서가 다루지 않은 자리이고, 재설치 시점을 사용자가 알 수 있는지는 별도 판단이 필요하다 —
   아키텍트 후속 아이디어 후보로 남긴다.
