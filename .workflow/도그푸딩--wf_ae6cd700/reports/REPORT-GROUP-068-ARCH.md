# GROUP-068 아키텍처 보고서

## 결정권자 요약

승인된 SPEC-068을 작업 그룹 GROUP-068과 개발 작업 두 건으로 나눴다.
경계는 사용자가 화면을 만나는 시점이며, 적용 뒤 결과 화면과 적용 전 확인 창 문구로 갈랐다.
결과 화면, 실패 사유 표시, 다시 열기 입구가 TASK-S068-01이고, 확인 창 문구가 TASK-S068-02다.
두 작업은 같은 화면 컴포넌트를 고치므로 순서를 두었고, 같은 화면 파일을 고치는 다른 그룹의 작업
두 건 뒤에 놓았다.
품질 확인은 사용자 확인으로 두고 통합 확인 절차 하나를 그룹에 적었다.
그룹은 active로 두었고 두 작업은 todo다.

## 대상과 예약 절차

- 역할은 architect이고 대상은 승인 결정 `DECISION-0202C5DA` 하나다.
- 런타임이 넘긴 lease `lease-30118-20260818080135`을
  `sh .workflow/rules/wf-claim.sh renew DECISION-0202C5DA lease-30118-20260818080135 60`으로 갱신해
  종료 코드 0을 확인했다. 같은 대상에 `acquire`는 실행하지 않았다. 작업 중 한 번 더 갱신했다.
- 결과 접두어 `RES-20260818T080135Z-30118-20260818080135`은 이 예약을 가리키는 이름으로만 쓰고
  문서 식별자에는 넣지 않았다. 문서 이름은 계보 규칙을 따라 기획서 번호에서 `GROUP-068`,
  `TASK-S068-01`, `TASK-S068-02`를 골랐다.
- 쓰기 전에 `groups/GROUP-068.md`, `tasks/TASK-S068-01.md`, `tasks/TASK-S068-02.md`,
  `reports/REPORT-GROUP-068-ARCH.md`가 없음을 확인했다. 작업 문서와 보고서는 덮어쓰기를 막은 셸
  리다이렉션으로 만들어 기존 문서를 덮지 않았음을 확인했다.
- `.workflow/.runtime/migration.lock`은 없다. `.workflow/rules/custom.md`도 없으므로 적용한 프로젝트
  커스텀 규칙은 없다.

## 대상 적격성

- `DECISION-0202C5DA`는 `SPEC-068`에 대한 `approved` 결정이고 `created_by`가 `user`다. 이 기획서에
  더 나중의 결정은 없다.

  전체에서 `SPEC-068`과 `DECISION-0202C5DA`를 참조하는 문서가 없음을 확인했다.

  `DECISION-DFAF80F5.yml`, `TASK-S066-02.yml`이 있었다. 모두 다른 대상의 것이고 이 세션은 건드리지
  않았다.
- 회수할 중단 산출물은 없었다. 이 승인에 대한 중단된 `preparing` 그룹이 없으므로 인계 판단이

## 진행 순서

1. lease 갱신으로 소유를 확인했다.
2. 곧바로 `groups/GROUP-068.md`를 `status: preparing`과 기획서·승인 참조만 담아 만들어, 개발 화면에
   아키텍처 진행이 보이게 했다.
3. 기획서와 그 기획 보고서, 그리고 관련 코드를 읽어 사실을 확인했다.
4. 작업 둘을 만들고 범위와 순서를 정했다.
5. 그룹 본문과 사용자 확인 절차를 채우고 같은 그룹을 `active`로 옮겼다.
6. 이 보고서를 쓰고 같은 lease를 반납했다.

## 작업 분해와 그 근거

기획서의 요구사항 다섯을 작업 둘에 나눴다.

- TASK-S068-01: REQ-01, REQ-02, REQ-03. 적용 뒤 결과 화면, 단계별 표시, 실패 사유의 사용자 언어
  변환, 남은 상태를 설명하는 문장, 창을 닫은 뒤 다시 여는 입구.
- TASK-S068-02: REQ-04. 서비스 연결만 남은 계획의 확인 창 제목과 안내 문장, 버전이 달라지지 않는
  계획의 버전 줄.
- REQ-05는 두 작업 모두의 완료 조건으로 넣었다. 적용이 부르는 명령과 인자, 계획 재생성 동작,
  예외 실패 경로의 지금 표시를 각각 그대로 두게 했다.

경계를 사용자가 화면을 만나는 시점으로 잡았다. 적용 전에 읽는 계획 확인 화면과 적용 후에 읽는 결과
화면은 서로 다른 판단을 돕고, 한쪽만 끝난 상태에서도 화면이 지금보다 나빠지지 않는다. 첫 작업만
끝나면 결과가 처음으로 화면에 남고, 둘째 작업만 끝나면 확인 창이 계획을 정확히 말한다.

요구사항 묶음이 아니라 코드 단위로 자르는 선택도 검토했다. 그러나 REQ-01부터 REQ-03까지가 모두 하나의
결과 화면에서 계산되고 표시되므로, 그것을 더 쪼개면 중간 상태를 설명할 수 없다. 단계 목록만 있고
사유가 없는 화면, 사유는 있는데 남은 상태 설명이 없는 화면은 어느 것도 완결된 사용자 결과가 아니다.

## 병렬 안전 판단

- TASK-S068-02는 TASK-S068-01 뒤에 둔다. 두 작업이 같은 화면 파일의 같은 확인 창 컴포넌트를 고친다.
  첫 작업이 그 컴포넌트에 결과 화면 갈래를 새로 만들고, 둘째 작업은 그 위에 문구 조건을 얹는 작은
  변경이므로 큰 구조 변경을 먼저 두었다.
- TASK-S068-01은 TASK-S067-01과 TASK-S063-02 뒤에 둔다. TASK-S067-01이 같은 화면 파일
  (`src/features/projects/components/agents/AgentRuntimeView.tsx`)의 위쪽을 고쳐 준비 안내를 새로
  세우고, 같은 검사 파일과 `src/App.css`도 함께 고친다. TASK-S063-02는 같은 검사 파일과 `src/App.css`,
  그리고 `src/features/projects/application/useProjectWorkspace.ts`를 고친다. 두 작업이 이미 서로
  순서가 매겨져 있어 뒤의 하나만 적어도 결과는 같지만, 겹치는 상대를 문서에서 바로 읽을 수 있도록
  둘을 모두 적었다.
- 순환은 없다. TASK-S063-02 → TASK-S067-01 → TASK-S068-01 → TASK-S068-02의 한 방향이며, 참조한
  작업 식별자 넷이 모두 실재한다.
- 이 그룹의 두 작업은 서로 겹치므로 동시에 시작할 수 없다. 겹치지 않는데 순서를 매긴 쌍은 없다.

## 표시 자리를 정한 판단

기획서 REQ-03은 마지막 적용 결과를 "실행 환경 상태 자리"에서 다시 열 수 있게 하라고만 정하고, 어느
화면 요소인지는 아키텍트에게 남겼다. 고급 설정의 실행 환경 자리로 정했다. 근거는 둘이다.

- 그 자리는 실행 환경 판정 설명과 계획 버튼과 최신 런타임 조회를 이미 담고 있는 실행 환경 상태의
  집합 자리이고, 실행 환경 판정이 정상이 아닐 때 펼쳐진 채로 열리므로 서비스 연결이 실패한 직후
  사용자가 그 내용을 곧바로 만난다.
- 에이전트 화면 위쪽의 안내는 TASK-S067-01이 준비 안내로 다시 세우는 자리다. 그쪽에 입구를 두면
  아직 구현되지 않은 다른 그룹의 화면 구조에 이번 작업이 매인다. 고급 설정의 실행 환경 자리는
  그 작업이 건드리지 않으므로 두 그룹이 서로를 흔들지 않는다.

## 코드에서 확인한 사실

작업 문서의 범위 사전 검사에 근거를 적었고, 여기에는 판단에 영향을 준 것만 옮긴다. 아키텍트 세션
이므로 읽기만 했고 코드는 고치지 않았다.

- 적용 결과의 단계 이름은 `src-tauri/src/domain/agent_runtime.rs` 240행 `UpdateStage`가
  `snake_case`로 직렬화한 여섯 값이다. 화면이 사용자 언어 이름으로 옮길 대응표를 작업의 완료 조건에
  못 박았다.
- 단계 상태는 설치 계열에서 `ok`, `skipped`, `failed` 셋이 나오고, 업데이트 계열은 실행 환경이 돌려준
  값을 그대로 쓴다. 앱이 전체 목록을 알 수 없으므로 아는 두 값 밖은 실패로 접게 했다.
- 전체 결과 값은 설치 계열에서 `success`와 `partial_success` 둘이다. 업데이트 계열은 실행 환경이
  정하므로, 판정을 결과 값 하나에만 걸지 않고 단계 상태를 먼저 보게 했다.
- 실패 사유의 사용자 언어 변환은 `src/features/projects/components/agents/AgentRunDashboard.tsx`
  715행 `humanRuntimeMessage`가 이미 하고 있고, 대응 규칙이 없으면 민감정보만 지운 원문을 돌려준다.
  기획서 REQ-02의 "변환 규칙이 없는 문장은 원문 그대로"가 이 함수로 이미 성립한다.
- 마지막 적용 결과는 `src/features/projects/application/useProjectWorkspace.ts`의 상태에 남고,
  294행 `readAgentRuntime`이 현재 상태를 펼친 뒤 조회 결과만 덮으므로 조회 주기가 이 값을 지우지
  않는다. 초깃값으로 되돌리는 자리는 프로젝트 전환과 닫기 둘뿐이다.
- 적용이 예외로 실패하는 경로는 결과를 넣지 않고 계획을 다시 만든다. 그러나 이전 적용의 결과는 그대로
  남으므로, 기획서가 정한 "다음 적용이 시작될 때까지 유지한다"를 지키려면 적용이 시작되는 순간
  이전 결과를 지워야 한다. 그 한 줄 때문에 첫 작업의 선언에 앱 상태 파일과 그 검사 파일을 넣었다.

## 품질 확인 방식 판단

사용자 확인으로 두었다. 이 그룹이 바꾸는 것이 전부 화면 표시이고, 확인에 필요한 상태가 이미 사용자의
기기에 있다. 2026-08-18 Windows 새 기기가 런타임은 설치되어 있고 관리형 서비스만 등록되지 않은
상태이며, 그 기기에서 연결 계획을 적용하면 서비스 연결 단계가 실패하는 것이 실측으로 확인되어 있다.

통합 확인 절차는 하나로 썼다. 사용자가 이 기능을 만나는 길이 하나이기 때문이다. 확인 창을 열고,
적용하고, 결과를 읽고, 닫고, 다시 열어 읽는 한 번의 흐름이 네 요구사항을 모두 지난다. 작업별로
절차를 나누지 않았다.

기획서 수용 기준 다섯 중 REQ-05의 것만 화면으로 판단할 수 없어 자동 검증과 완료 조건에 맡겼다.

  확인한 뒤 원인 수정은 새 아이디어로 올려야 한다. 이 세션은 아이디어를 만들지 않았다.
- SPEC-067에서 나온 GROUP-067이 같은 화면의 위쪽을 다시 세운다. 이번 그룹의 작업은 그 그룹의
  TASK-S067-01 뒤에 오도록 순서를 매겼고, 표시 자리도 그 작업이 건드리지 않는 곳으로 골랐다.
  다만 사용자 확인 절차의 1번 단계는 그 안내에서 연결 계획을 시작한다고만 적었으므로, GROUP-067의
  확인 결과에 따라 안내의 모양이 달라져도 이 절차는 그대로 읽힌다.
- 두 작업 모두 검사 파일 `AgentRuntimeView.test.tsx`를 고친다. 이 파일은 지금 네 작업이 차례로
  건드리는 자리이므로, 뒤에 오는 세션은 앞선 작업이 더한 검사를 지우지 말고 이어 붙여야 한다.

## 자체 검토

- `.workflow/rules/workflow.md` §8의 구조화 요약 형식을 두 작업 문서에서 확인했다. `### 제안`,
  `### 현재`, `### 변경 후`, `### 비용과 위험`이 이 순서로 한 번씩만 있고, 요약 안에 역따옴표 토큰,
  파일 경로, 식별자, 함수나 타입 이름을 쓰지 않았다. 문서 id는 예외로 허용된 형태로만 썼다.
- §9의 한국어 규칙을 확인했다. 영어 줄표를 문장 구분으로 쓰지 않았고, 은유 대신 표시, 적용, 판정
  같은 동작 이름을 썼다.
- 그룹의 사용자 확인 절차가 번호 목록 하나이고, 각 항목이 사용자 행동 한 문장과 인용 줄 하나로만
  이루어졌음을 확인했다. 표, 원시 HTML, 중첩 목록, 명령어, 저장소 조작 안내는 넣지 않았다.
- 두 작업 모두 `## 범위 사전 검사` 절을 정확히 그 글자로 두고, 완료 조건이 요구하는 값마다
  `- 값 경로:` 줄을 적었다. 편집이 필요한 hop이 모두 `scope_files`에 들어 있는지 확인했고, 뺀
  파일마다 코드에 근거한 이유를 적었다.
