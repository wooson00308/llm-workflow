# TASK-S073-01 개발 보고서

## 결정권자 요약

기능 상태를 계산하는 쪽이 이제 상태 이름 하나만 내려보내지 않는다. 구성 확인 필요로 판정한 기능은
어떤 조건이 맞지 않아 그렇게 판정됐는지를 여섯 값 가운데 해당하는 것으로 함께 내려보내고, 조건이
여럿이면 여럿을 담는다. 아키텍트가 문서로는 고칠 곳이 없다고 판단해 그 사실을 기능 문서에 적어 둔
기능은 사람 판단 필요라는 별도 상태로 나오며, 사용자에게 무엇을 판단해 달라고 적은 글도 함께 실린다.
판정 규칙 자체는 넓히지도 좁히지도 않았다. 그 표시가 없는 기능은 전부 이전과 같은 상태로 나온다.
품질 확인 제출이 열리는 조건도 그대로라, 사람 판단 필요 기능에 제출하면 지금과 같이 거절된다.
백엔드 시험 901건과 통합 시험 28건, 화면 시험 548건이 통과했고 형식 검사와 생산 빌드도 통과했다.
이 결과는 GROUP-073의 자동 검증 가운데 상태와 사유를 계산해 화면으로 보내는 부분을 뒷받침한다.

## 바꾼 파일과 모듈

- `src-tauri/src/domain/project.rs` — 표시 상태 열거에 `HumanJudgmentRequired`를 더했고, 사유
  열거 `WorkGroupConfigurationIssue`를 여섯 값으로 새로 두었다. 그룹 요약 구조체에는 사유 목록
  `configuration_issues`와 판단 요청 글 `human_judgment_note` 두 필드를 더했다.
- `src-tauri/src/infrastructure/fs_project_repository.rs` — 그룹 판독에서 다섯 갈래를 하나의
  참·거짓으로 합쳐 쓰던 자리를 조건마다 값을 남기는 목록 조립으로 바꾸고, 판정 사슬의 해당 분기를
  그 목록이 비어 있지 않은지로 세웠다. 작업 쪽 한 갈래만 작업 없음과 작업 연결 어긋남으로 나눠
  여섯이며, 나머지 조건식은 글자 그대로 옮겼다. 프론트매터
  `configuration_unresolved_revision`을 읽어 그 값이 그 기능의 구성 버전과 같을 때만 사람 판단
  필요로 답한다. 본문 절 판독 `parse_work_group_section`을 새로 두어 사람 판단 요청 글을 싣고,
  기존 설명 판독과 함께 쓰는 문단 잇기를 `join_paragraphs`로 뽑아 두 자리가 같은 규칙을 쓰게 했다.
- `src/features/projects/domain/types.ts` — 표시 상태 합집합에 새 값을 더하고, 사유 합집합
  `WorkGroupConfigurationIssue`와 요약의 두 필드를 더했다.
- `src/features/projects/components/DevelopmentBoard.tsx`,
  `src/features/projects/components/qa/QaWorkbench.tsx`,
  `src/features/projects/components/SpecWorkspace.tsx` — 상태 이름 표 세 곳에 사람 판단 필요를
  더했다. 개발 보드의 정렬 우선순위 배열에는 맨 앞에 넣었다. 자동 처리가 끝난 뒤에야 나오는
  상태여서 기다린다고 저절로 풀리지 않기 때문이다.

설계 판단 두 가지를 적어 둔다. 첫째, 요약의 새 두 필드를 화면 계약에서 선택 필드로 두었다. 이미
같은 구조체의 기준 커밋 필드가 그 형태이고, 필수로 두면 다섯 개 화면 시험 파일의 기존 조립
도우미가 타입 검사에서 깨지는데 그 파일들은 이 작업이 선언한 범위 밖이다. 둘째, 판정을 사유 목록
위에 세워 목록이 비어 있다는 것과 구성 확인 필요 자리가 아니라는 것이 같은 뜻이 되게 했다. 조건을
두 곳에 나눠 적으면 나중에 한쪽만 고쳐도 아무 시험이 걸리지 않는다.

## 검증 절차와 결과

격리 사본에서 먼저 돌리고, 통합한 커밋에서 같은 검사를 다시 돌렸다. 두 번 모두 같은 결과다.

- `cargo test --manifest-path src-tauri/Cargo.toml fs_project_repository` — 223건 통과.
  이 작업이 더한 시험 9건이 여기에 들어 있고 완료 조건 C1부터 C10까지를 덮는다.
- `cargo test --manifest-path src-tauri/Cargo.toml` — 901건 통과, 통합 시험 28건 통과, 실패 없음.
- `cargo fmt --manifest-path src-tauri/Cargo.toml --check` — 통과.
- `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings` — 경고 없음.
- `npm run check` — 타입 검사 통과, 화면 시험 548건 통과, 생산 빌드 통과. 완료 조건 C11이 여기서
  확인된다. 상태 이름 표에서 새 값을 한 번 빼 보고 타입 검사가 그 자리를 실제로 잡는지 확인한 뒤
  되돌렸다.

통합 후보는 격리 사본의 커밋 `d9a5330`이고 시작한 기반은 `79dd93a`다. 통합 시점의 공유 작업본이
같은 기반이었고 사용자의 미완성 변경이 없어 그대로 반영했으며, 통합 결과는 `1b0501a`다.

## 남은 위험

- 화면 계약의 두 필드가 선택 필드다. 값을 읽는 화면을 만드는 세션은 값이 없을 때를 함께 다뤄야
  한다. 백엔드는 항상 두 값을 실어 보내므로 실제 응답에서 비는 경우는 없다.
- 사람 판단 필요는 기능 문서에 그 표시가 적힌 뒤에야 나온다. 표시를 적는 절차는 아직 없으므로 이
  상태는 지금 어떤 기능에서도 나오지 않는다. 시험이 만든 문서에서만 확인했다.
- 사유 목록의 여섯 값은 지금 어느 화면도 읽지 않는다. 값의 이름이 사용자에게 그대로 보이지는
  않으므로, 문장으로 옮기는 작업이 붙기 전까지는 화면 동작이 이 작업 전과 같다.

## 후속 작업

- 사유와 판단 요청 글을 사용자 문장으로 풀어 화면에 그리는 일은 TASK-S073-04의 몫이다. 읽을 값의
  이름과 형태는 화면 계약 파일에 적어 두었다.
- 아키텍트 대상 판정에 새 상태를 넣는 일은 TASK-S073-03이, 아키텍트가 판단을 남기는 절차를 역할
  계약에 적는 일은 TASK-S073-02가 맡는다.
- 역할 밖 발견을 하나 넘긴다. 기능 문서 프론트매터의 선택 필드를 적은 절이 파일 계약 문서에 아직
  없어서 `configuration_unresolved_revision`을 적을 자리가 없다. 작업 문서가 그 파일을 범위에서
  뺀 판단은 지금도 맞고, 필드를 문서로 남길지는 아키텍트가 정할 일이다.
