# SPEC-079 기획자 핸드오프

## 결정권자 요약

런타임이 예약한 아이디어 IDEA-1892AC97을 처리해 기획서 SPEC-079를 새로 쓰고 사용자 검토 대기로
올렸다. 기획서는 실행 화면 최근 종료 목록의 실패 기록에 확인 처리를 붙이는 기능을 정한다.
아이디어가 기획에 맡긴 선택은 확인 단위와 표시 방식이었다. 단위는 실행 상세에서 하는 개별 확인과
최근 종료 구역에서 하는 일괄 확인 둘을 두고, 표시는 흐리게 남기는 대신 접는 쪽으로 정했다. 최근
종료 목록이 세 줄뿐이라 흐린 줄이 새 실패를 밀어내기 때문이다. 조사 중에 확인 대상이 되는 빨간
표시가 실패와 복구 필요 두 상태이고, 같은 화면에 확인 필요라는 다른 뜻의 구역이 이미 있다는
사실을 확인해 각각 요구사항으로 넣었다. 사용자가 할 일은 이 범위와 표시 방식을 보고 승인하거나
수정 요청을 남기는 것이다.

## 세션 정보

- 역할: 기획자 (planner)
- 대상: IDEA-1892AC97 (최근 종료 목록의 실패 기록 확인 처리 요구)
- 산출 기획서: SPEC-079 (status: user_review, 새로 만든 문서)
- 예약: 런타임 예약 대상 IDEA-1892AC97, lease lease-70146-20260819141418, 결과 prefix
  RES-20260819T141418Z-70146-20260819141418
- 세션: 2026-08-19T14:14Z ~ 14:20Z

## 진행 절차

1. 예약받은 lease로 `wf-claim renew`를 호출해 소유를 확인했다. 종료 코드 0. `acquire`는 부르지
   않았다.
2. `.workflow/.runtime/migration.lock`이 없고 `.workflow/rules/custom.md`도 없음을 확인했다.
   적용할 프로젝트 커스텀 규칙이 없다.
3. `.workflow/.runtime/silent-runs/`에서 이 대상을 가리키는 기록을 찾았고, 하나 있었다. 아래
   "결과 없이 끝난 실행 기록" 절에 그 내용과 인수 판단을 적었다.
4. `specs/`의 번호를 전부 확인했다. SPEC-001부터 SPEC-078까지 빈 번호 없이 차 있어 가장 낮은
   미사용 번호는 SPEC-079였다. 쓰기 직전에 해당 경로가 비어 있음을 확인하고, 덮어쓰기를 막은
   상태로 생성했다.
5. 소유 확인 직후 `status: draft`와 `source_idea_id`만 담은 기획서 골격을 먼저 만들어, 조사하는
   동안 다른 세션이 작업 중임을 볼 수 있게 했다.
6. 조사를 마친 뒤 본문을 채우고 `status: user_review`로 올렸다. lease는 이 보고서를 쓴 뒤 해제했다.

## 결과 없이 끝난 실행 기록

`.workflow/.runtime/silent-runs/`에 이 대상을 가리키는 기록이 하나 있었다.

- 대상: IDEA-1892AC97, 역할: planner
- 시작과 종료가 모두 2026-08-19T14:14:18Z. 실제로 진행한 시간이 없다.
- 사유: supervisor_identity_unverified

인수할 잔여물은 없다고 판단했다. 근거는 두 가지다. 첫째, 그 실행은 시작과 같은 초에 끊겼다.
둘째, 워크플로 디렉터리 전체에서 IDEA-1892AC97을 참조하는 파일을 찾은 결과 아이디어 문서 자신뿐이었고,
그 실행이 만들다 만 기획서 초안은 존재하지 않았다. 그래서 이 세션은 인계가 아니라 새로 시작하는
경우로 처리했고, 버리거나 이어받은 문서는 없다.

## 아이디어가 기획에 맡긴 선택과 결정

아이디어는 확인 단위와 표시 방식을 기획에서 정하라고 남겼다. 정한 내용과 근거는 다음과 같다.

- 확인 대상 상태: 실패와 복구 필요. 지금 빨간 점이 붙는 상태가 이 둘이고, 아이디어가 문제로 지목한
  표시도 그 빨간 점이다. 완료와 취소됨은 새 문제로 읽히지 않아 뺐고, 상태 확인 필요는 결과를 아직
  모르는 기록이라 조치가 끝났다고 적을 근거가 없어 뺐다.
- 복구 필요를 넣은 이유: 그 상태는 사용자에게 남은 정리를 요구하므로, 정리를 마친 기록이야말로
  확인 처리가 필요한 전형이다. 다만 확인 처리가 정리 완료 판정으로 읽히지 않도록, 상세 화면의 남은
  정리 안내는 그대로 둔다는 요구사항(R11, A11)을 함께 넣었다.
- 확인 단위: 개별과 일괄 둘 다. 개별은 상세 화면에 둔다. 사용자가 원인을 보려고 이미 여는 화면이라
  조치가 끝나는 자리와 확인하는 자리가 같아진다. 일괄은 최근 종료 구역 머리에 두고, 대상을 화면에
  보이는 세 건이 아니라 기록 전체의 미확인 실패로 잡았다. 화면 밖 실패를 남기면 다음에 목록이 그
  기록을 다시 끌어올리기 때문이다.
- 일괄의 되돌리기: 개별 해제만 둔다. 일괄 해제는 필요가 확인되지 않았다. 대신 잘못 눌렀을 때의
  비용이 크므로, 실행 전에 건수를 밝히는 확인 창을 한 번 거치게 했다. 앱이 실행 취소와 재시도에서
  이미 쓰는 방식이다.
- 표시 방식: 접기. 아이디어는 접기와 흐리게를 모두 허용했지만, 최근 종료 목록은 세 줄뿐이라 흐린
  줄이 자리를 차지하면 정작 봐야 할 새 실패가 밀려난다. 대신 접힌 건수를 한 줄로 남겨, 접힌 기록이
  있다는 사실 자체는 화면에서 사라지지 않게 했다.
- 감사 용도의 자리: 전체 실행 기록은 접지 않고 끝난 실행 전부를 그대로 보여주며, 확인한 줄에 표시만
  덧붙인다. 아이디어가 우선이라고 말한 감사 성격을 이 화면이 받는다.

## 조사에서 확인한 사실

기획서 본문의 판단이 딛고 있는 사실이다.

1. 최근 종료 구역은 활성 상태가 아닌 실행을 최신순으로 잘라 세 건만 보여준다. 전체 기록 버튼은
   같은 목록을 자르지 않고 보여주는 별도 화면을 연다.
2. 종료 상태는 완료, 실패, 취소됨, 복구 필요, 상태 확인 필요 다섯 가지다. 상태 점에 빨간색이 붙는
   것은 실패와 복구 필요 둘뿐이고, 완료는 파란색, 나머지는 회색이다.
3. 목록의 표시는 실행의 종료 상태만 보고 정해진다. 사용자가 그 기록을 보았는지 조치했는지를 담는
   값은 어디에도 없다. 그래서 조치를 마쳐도 표시가 바뀌지 않는다.
4. 실행 기록은 앱이 만드는 것이 아니라 실행 런타임의 상태에서 읽어 온다. 확인 표시를 그 기록에 쓰면
   앱이 남의 기록을 고치는 일이 되므로, 앱이 따로 보관하고 목록이 함께 읽는 방식으로 요구사항을
   적었다(R9, R10). 보관 위치와 형식은 아키텍트가 정할 몫으로 남겼다.
5. 실행마다 고유한 실행 식별자가 있어 확인 표시를 실행 단위로 구분할 수 있다. 다만 실행 기록의
   보존 기간은 런타임 쪽 사정이므로, 기록에서 사라진 실행의 표시가 계속 쌓이지 않게 정리하라는
   요구사항(R12)을 넣었다.
6. 같은 실행 화면에 확인 필요라는 구역이 이미 있고, 그쪽은 실행 도구 준비 상태나 파일 감시 중단
   같은 앱 쪽 문제를 모으는 자리다. 이 기획서의 확인 처리와 뜻이 다르므로, 화면에 쓰는 말을
   확인함, 확인 해제, 확인한 실패 N건으로 고정하는 요구사항(R13)을 넣었다.

## 아키텍트에게 넘기는 판단

- 확인 표시를 어디에 어떤 형식으로 보관할지는 정하지 않았다. 프로젝트별로 구분되고 앱 재시작 뒤에도
  남으며 실행 기록을 고치지 않는다는 조건만 요구사항으로 적었다.
- R12가 말하는 정리 시점도 정하지 않았다. 화면을 열 때인지 실행 목록을 새로 읽을 때인지는 구현
  구조를 보고 정하는 편이 낫다고 판단했다.
- 접힌 목록을 펼친 상태를 화면을 닫았다 열어도 유지할지는 요구사항에 넣지 않았다. 접기는 그때그때의
  보기 상태이므로 유지하지 않는 쪽이 기본이지만, 구현하며 반대 근거가 나오면 아키텍트가 판단하면 된다.

## 역할 밖에서 확인한 사항

- 기획서 본문에서 최근 종료 목록의 성격이 가장 최근 세 건에서 확인하지 않은 최근 세 건으로 바뀐다고
  밝혔다. 구역 이름은 최근 종료 그대로 두기로 정했으나, 사용자가 승인 단계에서 이름도 바꾸기를
  원하면 수정 요청으로 남기면 된다.
- SPEC-078은 사이드바를 가리키는 데 표준 용어 대신 새로 만든 말을 쓰고 있다. 이 기획서는 그 표현을
  따르지 않았다. 이미 사용자 검토 대기에 올라간 문서라 이 세션은 손대지 않았고, 사실만 적어 둔다.

## 후속과 리스크

- 승인되면 아키텍트가 SPEC-079로 작업 그룹을 만든다. 표시 변경이 대부분이라 되돌리기 비용은 낮다.
- 남는 리스크는 기획서 요약에 적은 그대로다. 확인 여부가 사람의 판단이므로, 조치가 끝나지 않은
  실패를 확인 처리하면 그만큼 늦게 발견한다. 개별 확인 해제를 둔 것이 이 리스크에 대한 답이다.
- 이 세션은 기획서 한 건만 처리했다. 코드는 읽기만 했고 제품 코드와 개발 작업 문서는 만들지도
  고치지도 않았다.
