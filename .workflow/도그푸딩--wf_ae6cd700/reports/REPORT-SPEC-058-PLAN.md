# SPEC-058 기획 보고서

## 결정권자 요약

사용자가 SPEC-057에 남긴 수정 요청 "수준 2 채택"에 답해 SPEC-058을 새로 작성했다.
채택형 관문과 조건부 자동 재개를 하나의 안으로 확정했고 선택지를 다시 묻지 않는다.
자동 재개 조건은 정의 오류 분류와 연결된 수리 처리 기록과 작업당 두 번 한도 셋뿐이다.
실행 주체는 앱으로 한정하고 에이전트의 자동 재개 금지와 사용자 재개 기록의 뜻은 그대로 둔다.
승인된 SPEC-054 R8을 좁히는 개정이라 규칙 문언이 바뀌고 규칙 버전이 오른다.
SPEC-057 원본과 그 결정 기록은 손대지 않았다.
지금 요청하는 것은 SPEC-058의 승인 여부다.

## 대상 선택

- 대상은 DECISION-EDA7E2D0이다. `created_by: user`, `outcome: revision_requested`, 대상 기획서는
  SPEC-057이며 코멘트는 "수준 2 채택" 한 줄이다. 문서를 직접 읽어 확인했다.
- 이 결정이 SPEC-057의 유일한 결정이고, 이 결정 식별자를 `source_decision_id`로 가진 기획서가 없어
  미답변 상태였다. 결정 식별자를 선점하고 작업한 뒤 반납했다.
- 규칙 절차대로 새 식별자 SPEC-058을 만들고 `source_spec_id: SPEC-057`,
  `source_decision_id: DECISION-EDA7E2D0`을 적었다. 계보를 잃지 않도록 `source_idea_id`도 유지했다.
- SPEC-057, SPEC-054, SPEC-055 문서와 결정 기록은 읽기만 했다.

## 이전 문서에서 바뀐 점

- 두 수준을 나란히 제시하고 세 선택지를 묻던 구조를 없애고, 수준 2를 단일안으로 서술했다. 결정
  요청은 이 안의 승인 여부만 묻는다.
- 결정권자 요약은 새로 썼다. 이전 문서의 요약을 옮기지 않았다.
- 채택형 관문은 자동 재개가 다루지 않는 막힘의 경로로 자리를 옮겨 서술했다. 두 부분이 함께 있어야
  성립한다는 관계를 확정안 절에 명시했다.
- 요구사항 번호를 하나의 목록으로 다시 매기고 수준 표기를 없앴다.

## 조사와 실측

SPEC-057에서 확인한 사실을 그대로 근거로 삼았고, 이번 세션에서 다음을 추가로 확인했다.

- 기획 승인 도장에는 코멘트 칸이 없다. 화면이 코멘트 입력을 여는 결정은 수정 요청과 폐기 둘뿐이며,
  승인은 두 번 누르는 도장만 있다(`SpecWorkspace.tsx:25`의 `CommentDecision` 정의와 승인 버튼 경로).
  백엔드 명령 `record_spec_decision`은 결과와 무관하게 코멘트를 받는다(`commands/projects.rs:104`).
  즉 저장 계층은 승인 코멘트를 받을 수 있는데 화면이 그 칸을 열지 않는다.
- 이 사실이 이번 왕복의 직접 원인이다. 사용자는 "수준 2를 고른다"는 말을 승인에 붙일 수 없어 수정
  요청으로 답할 수밖에 없었다. 선택지를 나열하는 기획서는 이 앱에서 반드시 한 번의 수정 요청 왕복을
  만든다.

## 기획 결정

- 자동 재개 조건 셋을 그대로 유지했다. 셋 다 앱이 확인할 수 있는 사실이며 앱이 판단을 창작하지 않는다.
- 한도는 작업당 두 번이다. 관측된 재개는 작업마다 한 번이고 반복 사례가 없다. 한 번이면 수리가 한 번에
  맞지 않는 경우가 곧바로 사람에게 넘어가 효과가 사라지고, 세 번 이상이면 같은 작업에 유료 세션을
  태우는 시간이 길어진다.
- 자동 재개 감사 기록의 작성자 값을 사용자 재개와 구분하도록 요구했다. 사용자가 하지 않은 일을 사용자
  기록으로 남기면 이 기획이 고치려는 문제를 그대로 재생산한다.
- 개정 경계를 문서에 남겼다. SPEC-054 R8은 세 조건 안에서만 좁혀지고 그 밖의 막힘에서는 유지된다.
  에이전트의 자동 재개 금지는 유지된다. 규칙 문언과 사용자 문서 변경, 규칙 버전 상승은 비용으로 적었다.
- SPEC-055 작업과의 순서와 겹침을 그대로 옮겼다. 자동 재개는 TASK-S055-01과 TASK-S055-02 뒤에 오고,
  TASK-S055-04와는 화면 파일이 겹쳐 동시 진행이 불가하다.

## 검증

- 결정 문서의 네 필드와 코멘트를 원문에서 확인했다. 다른 세션이 같은 결정을 선점하지 않았음을 확인한
  뒤 작업했다.
- SPEC-058의 결정권자 요약이 구조화 형식을 지키는지 확인했다. 일곱 하위 제목이 순서대로 한 번씩 있고,
  영향 범위 아래 변경과 유지 표식이 한 번씩 있으며, 요약 안에 역따옴표와 파일 경로와 식별자가 없다.
- 결정 요청이 단일안의 승인 여부만 묻는지 확인했다. 선택지 나열이 없다.
- 사용자 피드백 두 개를 배경 절에 원문으로 인용했다.

## 인계 사항

- 앱 개선 후보: 승인 도장에 코멘트 칸이 없다. 저장 계층은 이미 코멘트를 받으므로 화면만 열면 된다.
  이번처럼 사용자가 승인에 조건이나 선택을 붙이고 싶을 때 수정 요청 왕복이 강제되는 것을 줄인다. 이
  기획서의 범위가 아니므로 별도 아이디어로 남기는 편이 맞다.
- 구현 순서와 파일 겹침은 기획 내용 절에 적었다. 아키텍트가 순서 선언에 반영해야 한다.
- 감사 기록에 인용과 사용자 메모를 구분해 담는 방법과 자동 재개 기록의 스키마 이름은 아키텍트가 정한다.
- 승인 전에는 구현하지 않는다.
