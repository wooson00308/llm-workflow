## 승인 해석

DECISION-D581BB43은 본문이 비어 있다. 사용자 의견 없이 승인만 기록됐다.

SPEC-044의 확인 필요 절은 머리글에 "사용자 결정이 필요한 항목이다. 승인 시 아래 제안대로 진행한다"고
적혀 있다. 그래서 본문이 빈 승인은 세 항목의 제안을 그대로 채택한 것으로 읽었다. 아키텍트가 모호한
요구에 답을 지어내는 것이 아니라, 기획서가 승인의 의미를 미리 정의해 둔 경우다.

채택된 세 항목은 다음과 같고, TASK-138의 "승인이 정한 구현 지침" 절에 그대로 옮겼다.

1. **규범이 앉을 자리.** 릴리스 가이드에 본문을 쓰고 정본으로 삼는다. 세션 진입 문서에는 릴리스
   가이드를 먼저 읽으라는 짧은 절만 둔다.
2. **저장소 설정.** 이번 범위에서 브랜치 보호와 필수 상태 검사를 켜지 않는다.
3. **재실행 허용 기준.** 검사 대상 코드와 무관한 실패에만 허용하고, 재실행 사유를 병합 전에 한 줄
   남긴다.

## 분해 판단

**작업을 하나로 두었다.** 파일별로 둘로 나누지 않은 이유를 적는다.

SPEC-044 R5의 마지막 조항이 "같은 문장이 두 곳에 적히면 어느 쪽이 정본인지 함께 적는다"를 요구한다.
이 조항은 `docs/releasing.md`와 `AGENTS.md` 두 파일에 걸친 하나의 정합성 요구다. 파일별로 작업을
나누면 그 요구가 두 작업으로 쪼개져 어느 쪽도 혼자서는 검증되지 않는다. 진입 문서 쪽 작업이 "규범
본문을 복제하지 않았다"를 확인하려면 가이드 쪽 본문이 이미 있어야 하기 때문이다.

나눴다면 진입 문서 작업이 가이드 작업에 `depends_on`으로 물려 직렬화될 수밖에 없으므로, 병렬 여지도
생기지 않는다. 분해의 이득이 없고 검증만 나빠지는 분할이라 하나로 두었다.

`depends_on`은 쓰지 않았다. 이 작업이 선언한 두 파일을 잡은 다른 작업이 없고, `todo`나 `in_progress`
상태의 작업이 하나도 없어서 순서를 매길 상대가 없다. 근거 없는 직렬화를 만들지 않았다.

`scope_files`는 `[AGENTS.md, docs/releasing.md]`다. 실제로 바뀌는 파일이 이 둘뿐이다. `CLAUDE.md`는
`@AGENTS.md` 한 줄이라 바꿀 것이 없어 선언에서 뺐고, 바꾸지 않는다는 것을 완료 조건 9번으로 고정했다.

## 구현에 앞서 확인한 사실

기획서의 확인 사실을 그대로 믿지 않고, 작업 문서에 옮겨 적는 값만 직접 확인했다.

1. **검사 네 갈래의 실제 이름.** `.github/workflows/ci.yml`에 `frontend` 작업이 `name: Frontend`,
   `rust` 작업이 `name: Rust (${{ matrix.os }})`로 `ubuntu-22.04`·`windows-latest`·`macos-latest`
   3개다. `fail-fast: false`, 동시성 그룹 `cancel-in-progress: true`도 확인했다. 규범 본문이 네 갈래를
   이름으로 지목해야 "어느 갈래가 빨간지는 조건을 바꾸지 않는다"가 검증 가능해진다.
2. **태그 워크플로에 검사가 없다.** `.github/workflows/release.yml`의 단계에 `cargo test`·`cargo
   clippy`·`cargo fmt`·`npm run check`가 없다. PR 검사가 산출물 앞의 마지막 검사라는 근거가 선다.
3. **진입 문서의 관리 블록 구조.** `AGENTS.md`는 1행이 `<!-- workflow-labs:project-instructions:start
   -->`, 15행이 `:end`로 파일 전체를 감싼다. 새 절을 끝 주석 뒤에 두어야 블록 밖이 된다.
4. **설치기의 보존 동작.** `project_instructions.rs`가 관리 블록이 이미 있을 때 블록 앞 내용과 블록 뒤
   내용을 모두 이어 붙이고 블록만 새 본문으로 교체한다. 기획서 확인 사실 10이 인용한
   `preserves_existing_content_and_is_idempotent` 테스트는 기존 본문이 블록 **앞**에 남는 경우만
   고정한다. 이 작업은 블록 **뒤**에 쓰므로 테스트가 직접 덮는 경우가 아니어서, 교체 로직 본문을 열어
   블록 뒤 내용도 보존됨을 확인한 뒤 배치를 정했다. 그 근거를 TASK-138 검증 절차 5번에 남겼다.
5. **릴리스 가이드의 현재 내용.** 브랜치 흐름 네 단계에 검사 통과를 요구하는 줄이 없다. 기존 절을
   지우지 않고 2번과 4번 사이에 병합 조건을 연결하도록 작업에 적었다.
6. **작업 트리의 기준선.** `AGENTS.md`가 이미 커밋되지 않은 수정 상태다. 내용을 열어 보니 앱이 규칙
   버전을 올리면서 관리 블록 안의 절차 목록에 사용자 정의 규칙 단계를 추가한 것이고, 앱이 설치한
   변경이다. `docs/releasing.md`는 수정되지 않았다. 이 사실 때문에 처음에 적었던 검증 절차를 고쳤다.
   `git diff`와 `git diff --stat`은 기준선이 최신 커밋이라 앱이 넣어 둔 이 변경과 다른 작업이 남긴
   수정까지 함께 보여 주므로, 개발자가 "관리 블록을 건드리지 않았다"를 그 명령으로 확인하면 자기
   변경이 아닌 것을 자기 변경으로 읽게 된다. 그래서 기준선을 작업 시작 시점의 작업 트리로 바꾸고,
   편집 전 사본과 대조하는 방식과 `git status --porcelain` 전후 비교로 검증 절차를 다시 적었다.

## 완료 조건 8번을 작업에 넣지 않은 이유

기획서 완료 조건 8번은 "다음 릴리스 컷 한 번에서 이 규범이 실제로 지켜졌는지가 그날 개발 로그에
남는다"이다. 이 조건은 다음 컷 세션이 수행해야 판정되므로 문서 작업의 완료 조건이 될 수 없다. 지금
판정하려 들면 개발자가 일어나지 않은 일을 기록하게 된다.

대신 규범 본문이 그 기록을 요구하도록 TASK-138의 완료 조건 7번에 넣었다. 컷 세션이 확인한 검사 실행과
병합 시각을 개발 로그에 남기게 되면, 8번은 다음 컷 때 사용자가 그 로그로 판정할 수 있다.

기획서 완료 조건 1번부터 7번까지는 TASK-138 완료 조건 1번부터 7번에 순서대로 대응한다. 8번부터 11번은
제외 범위(R6)를 검증 가능한 형태로 옮긴 것이다.
