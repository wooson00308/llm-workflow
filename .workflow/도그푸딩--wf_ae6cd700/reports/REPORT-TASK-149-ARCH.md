# TASK-149 의존성 재판정 보고서

## 결정권자 요약

재개 화면이 자기 재개 대상을 기다리는 원이 있어서 어느 쪽도 시작할 수 없었다.
원인은 화면 작업이 런타임 보완 작업 두 개를 선행으로 갖고 있었던 점이다.
두 보완 작업은 런타임 파일만 바꾸고 화면이 그 기능을 부르지도 않아 실제 선행이 아니었다.
승인된 기획서도 두 작업의 완료를 화면 제작 조건이 아니라 사용자가 재개할 시점의 판단 근거로 둔다.
그래서 선행을 둘로 줄여 원을 끊었고, 화면은 이제 막힌 두 작업과 무관하게 만들 수 있다.
언제 재개할지는 여전히 사용자가 보완 작업의 상태를 보고 직접 정한다.
작업 상태와 이력은 건드리지 않았고 범위 파일과 완료 조건도 그대로다.

- 산출물: 작업 문서의 선행 관계 재판정과 본문 정합 1건, 이 보고서 1건
- 제품 코드, 다른 작업 문서, 상태 전이, git 커밋: 수행하지 않음

## 판정 결과

TASK-146과 TASK-147을 `depends_on`에서 제거했다. 남은 선행은 TASK-145와 TASK-148 두 개다.

### 제거 근거

1. 코드 의존이 없다. TASK-149의 범위 파일은 모두 화면 쪽이고, TASK-146과 TASK-147은 런타임 저장소의
   파일만 바꾼다. 범위 파일 교집합은 각각 0이다. 반면 TASK-145와는 4개가 겹치고 TASK-148은 이 화면이
   부르는 재개 명령을 만든다.
2. 계약 의존도 없다. TASK-149는 provider 수명 호출이나 기기 상태 조회를 호출하지 않는다. 두 작업의
   상태는 패널에 참고 정보로 표시되는 값일 뿐이다.
3. 검사 의존도 아니다. 첫 적용 시나리오의 두 픽스처는 보완 작업이 품질 확인 대기 또는 완료인 상태를
   검사 데이터로 만들어 쓴다. 실제 작업의 진행 상태를 읽지 않으므로 그 작업이 끝나기 전에도 같은
   검사를 만들 수 있다.
4. 승인된 기획서가 그렇게 정한다. SPEC-054 R12는 보완 작업이 품질 확인 대기 또는 완료가 된 뒤 사용자가
   원래 작업을 재개할 수 있다고 말한다. 이것은 사용자의 재개 시점에 대한 조건이지 재개 화면을 만드는
   순서에 대한 조건이 아니다. 같은 R12는 앱이 보완 작업 상태를 참고 정보로만 보여 주고 자동으로 원래
   작업 상태를 바꾸지 않는다고 못 박는다. 완료 조건 10번도 같은 내용을 이미 담고 있다.
5. 아키텍트 계약은 겹치지 않는 작업을 이유 없이 직렬화하지 말라고 요구한다. 이 경우는 병렬 여지를
   잃는 정도가 아니라 아래의 대기 원을 만든다.

### 끊어 낸 원

- TASK-149가 TASK-147을 기다린다.
- TASK-147은 TASK-S051-05를 기다린다.
- TASK-S051-05는 TASK-S051-04를 기다리는데 그 작업은 현재 막힘 상태다.
- 막힌 TASK-S051-04를 사용자가 다시 여는 조작이 바로 TASK-149가 만드는 화면이다. TASK-148이 백엔드
  명령을 만들었지만 그 개발 보고서가 적었듯 화면에서 부르는 곳이 아직 없다.

네 단계가 한 바퀴를 돌아 어느 작업도 시작 조건을 만족하지 못한다. TASK-146 쪽도 같은 모양이며, 그
작업은 지금 진행 중이라 당장은 원이 드러나지 않지만 선행으로 남겨 둘 이유가 없기는 마찬가지다.

## 본문 정합

선행 관계를 바꾼 만큼 본문에서 두 작업을 선행으로 설명하던 부분을 사실에 맞게 고쳤다.

- `현재 상태와 선행 결과`: 두 작업이 막힌 작업들이 기다리는 보완 작업이지 이 작업의 선행은 아니라고
  적고, 화면은 제목과 현재 상태만 참고 정보로 읽는다는 점을 남겼다.
- `첫 적용 시나리오`: 두 픽스처가 보완 작업의 상태를 검사 데이터로 만들어 쓴다는 점을 분명히 했다.
- `목적`과 결정권자 요약: 재개 시점을 화면이 아니라 사용자가 정한다는 사실을 적었다.
- `범위와 선행`: 위 판정 근거와 끊어 낸 원을 기록했다.
- 같은 절의 겹침 목록에서 TASK-S051-06을 뺐다. 범위 파일 교집합이 0이라 사실이 아니었다. TASK-S051-09와
  TASK-S051-10은 각각 7개와 5개가 겹치므로 그대로 두었다.

완료 조건, 검증 절차, 범위 파일, 사용자 흐름은 바꾸지 않았다.

## 남은 위험과 인계 사항

- TASK-149는 TASK-S051-09와 TASK-S051-10과 화면 파일이 겹치지만 세 작업 사이에 순서를 정하는 선언이
  없다. 두 작업은 TASK-S051-06과 TASK-S051-07 뒤에 있어 실제로는 훨씬 나중에 오고, 이번 변경으로
  TASK-149가 더 앞당겨졌으므로 순서가 뒤집힐 가능성은 오히려 줄었다. 그래도 선언으로 고정돼 있지 않고
  현재는 범위 파일 선언이 유일한 안전망이다. 이 두 작업의 문서는 이번 세션의 대상이 아니라 고치지
  않았다.
- 사용자가 원래 작업을 언제 재개할지에 대한 판단 근거는 이제 막힌 작업 문서 각각의 막힌 사유 절에 있다.
  같은 세션에서 TASK-S051-04에는 TASK-146을, TASK-S051-06에는 TASK-147을 재개 조건으로 적어 두었다.
  화면은 그 값을 그대로 보여 주면 되고 스스로 판정하지 않는다.
- TASK-146과 TASK-147이 늦어져도 재개 화면은 만들 수 있지만, 그 화면으로 재개를 실행할지는 여전히
  사용자의 판단이다. 이번 변경은 화면 제작 순서만 풀었고 재개 권한 경계는 건드리지 않았다.
