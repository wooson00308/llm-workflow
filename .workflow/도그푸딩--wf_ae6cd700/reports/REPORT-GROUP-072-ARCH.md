# GROUP-072 아키텍처 보고서

## 요약

승인 결정 DECISION-B4D44EEB를 GROUP-072와 실행 작업 하나로 분해했다. 기능은 확인 동선을 사용자 확인
절차로 인정하는 낱말 대조가 어미 변화를 견디게 해서, 평범한 한국어 관찰 서술로 쓴 기능이 품질 확인
으로 넘어가게 하는 것이다. 그룹은 사용자 확인 모드이며 통합 확인 절차 하나를 담았다. 고칠 자리가 한
파일의 판정 함수 하나여서 작업은 나누지 않았다. 그룹은 active, 작업은 todo다.

## 대상과 선점

- 대상: DECISION-B4D44EEB (SPEC-072의 최신 앱 기록 결정, outcome approved, created_by user)
- 선점: lease-95999-20260818134804 (런타임 예약을 renew로 확인, 종료 코드 0, 재획득 없음)
- 예약 접두사: RES-20260818T134804Z-95999-20260818134804 (보고용 표기이며 문서 식별자에 넣지 않았다)
- 자격 재확인: SPEC-072를 가리키는 결정은 DECISION-B4D44EEB 하나뿐이고 outcome은 approved다. 이
  승인이나 SPEC-072를 출처로 삼은 기능 문서가 없었고, GROUP-072 경로도 비어 있었다.
- 다른 대상 확인: 현재 revision의 사용자 확인 반려 결정은 없었고, definition_error로 막힌 작업도
  없었다. preparing 상태인 GROUP-073에는 만료되지 않은 lease-24641-20260818133642가 붙어 있어 다른
  세션의 대상이다. 이 세션은 예약받은 승인 하나만 처리했다.

## 식별자 판단

기능 문서 이름은 기획서 번호를 따라 GROUP-072로 지었고, 작업은 같은 계보의 두 자리 순번으로
TASK-S072-01로 지었다. 쓰기 전에 두 경로가 모두 비어 있는 것을 확인했다. 예약 접두사는 어느
식별자에도 넣지 않았다.

## 구성 판단

### 확인 방식

사용자 확인으로 두었다. 이 변경의 결과는 품질 확인 화면의 목록에서 사용자가 직접 읽을 수 있다.
개발이 끝났는데도 준비 중인 기능 목록에 구성 확인 필요로 서 있던 기능이 지금 확인할 기능 목록으로
올라오는 것이 그것이다.

확인 절차는 하나로 썼다. 사용자가 이 기능을 만나는 동선이 품질 확인 화면을 한 번 훑는 것이기
때문이다. 확인 시점의 판 상태를 전제하지 않도록, 실측 사례인 GROUP-070이 준비 중인 기능 목록의 구성
확인 필요 자리에 더 이상 없다는 사실을 대조 기준으로 삼았다. 확인 시점에 사용자가 그 기능의 확인을
이미 마쳤을 수도 있어서, 지금 확인할 기능 목록에 서 있는 경우와 완료된 경우를 모두 통과로 적었다.
어느 쪽이든 이 변경이 의도한 결과이고, 구성 확인 필요 자리에 그대로 남아 있으면 변경이 듣지 않은
것이다.

낱말 인식 범위와 개발자용 절차 차단은 사용자가 화면에서 확인할 수 없어 자동 검증이 덮게 했고, 어느
요구사항을 어느 검사가 덮는지를 작업 문서의 완료 조건에 기획서 요구사항 번호로 적었다.

작성한 확인 절차가 지금의 판정 규칙을 통과하는지 미리 대조했다. 본문에 화면 낱말(화면, 목록, 앱),
행동 낱말(열, 확인, 누르), 결과 낱말(보입니다의 보이)이 모두 걸리고 금지 낱말은 하나도 걸리지
않는다. 코드 울타리도 없다. 이 그룹이 고치려는 판정에 이 그룹의 확인 절차가 걸리면 같은 함정에
빠지므로 변경 전 규칙으로 먼저 확인했다.

### 작업을 나누지 않은 이유

고칠 자리가 `src-tauri/src/infrastructure/fs_project_repository.rs` 3399행의 판정 함수 하나이고, 그
함수를 부르는 두 자리와 시험 모듈이 모두 같은 파일 안에 있다. 낱말 목록을 넓히는 일과 어미 변화를
견디게 하는 일은 같은 함수의 같은 대조식에서 만난다. 둘로 나누면 겹침 선언 때문에 두 작업이 차례로
같은 파일을 여는 것 말고 얻는 것이 없어서 하나로 두었다.

화면과 프론트 계약은 이 그룹에서 고치지 않는다. 이 작업이 새 값을 만들지 않고 기존 판정이 답하는
쪽만 바꾸기 때문이다. 사용자 QA 대기 값은 `src-tauri/src/domain/project.rs` 287행과
`src/features/projects/domain/types.ts` 167행에 이미 있고, 그 값으로 두 목록을 가르는 자리도
`src/features/projects/components/qa/QaWorkbench.tsx` 19행과 23행에 이미 있다.

### 구현 방식을 아키텍트가 정한 부분

기획서 REQ-01은 어미가 달라져도 같은 낱말로 인식하라고만 적고 방식은 아키텍트에게 넘겼다. 두 단계로
정했다.

첫째, 지금의 글자열 포함 검사를 그대로 먼저 해 보고 걸리지 않을 때만 넓힌 대조를 한 번 더 돈다.
이렇게 두면 기획서 REQ-03이 요구하는 "지금 통과하던 문장은 계속 통과한다"가 구조로 보장되고, 목록에
섞여 있는 영어 낱말의 판정도 손대지 않게 된다.

둘째, 넓힌 대조는 낱말과 본문을 초성·중성·종성으로 풀어 맞추되 글자 경계를 지킨다. 낱말이 본문의
어느 글자 경계에서 시작해 끝까지 이어지고, 낱말이 끝나는 글자에 남는 것이 종성 하나뿐일 때만 같은
낱말로 인정한다. 초성이나 중성이 남으면 인정하지 않는다.

이 규칙을 자바스크립트로 먼저 구현해 대조해 보고 결정했다. 기획서 REQ-01의 네 형태와 REQ-02의 열
가지 서술이 모두 통과하고, "창"이 "차이"에, "앱"이 "애매"에 걸리지 않는다. 종성만 허용하는 조건이
없으면 이 두 가지가 모두 오탐이 되므로 조건을 넣었다.

"보였다"는 종성 규칙만으로는 "보이"에 걸리지 않는다. 이가 었을 만나 여로 줄어드는 자리여서 중성이
달라지기 때문이다. 다만 결과 목록에 "보여"가 이미 들어 있고, 종성 규칙 아래에서 "보여"가 "보였다"에
걸린다. 그래서 축약을 따로 다루는 규칙은 넣지 않았다.

결과 목록에는 낱말 여섯을 더하기로 했다. 적혀, 열리, 나오, 바뀌, 같아지, 남아다. 기획서 REQ-02가
적은 열 가지 가운데 보인다, 나타난다, 표시된다, 사라진다는 지금 목록으로 덮이고, 나머지 여섯은
낱말 자체가 목록에 없어서 대조 방식만 바꿔서는 덮이지 않는다.

### 실측 사례 대조

GROUP-070의 확인 동선 본문을 결과 낱말 32개와 직접 대조했다. 걸리는 것이 하나도 없어 기획서가 적은
사실과 같았다. 본문이 쓰는 서술은 보인다, 같아진다, 적혀 있고, 남아 있지, 열리고, 바뀐다, 나오는
이며, 위 두 단계를 적용하면 이 가운데 여럿이 결과 조건을 만족한다. 화면 조건과 행동 조건은 지금도
만족한다.

## 겹침과 차례

`src-tauri/src/infrastructure/fs_project_repository.rs`를 선언한 미완료 작업이 하나 더 있다.
GROUP-073의 TASK-S073-01이며 지금 todo다.

`depends_on`은 두지 않았다. 겹침 선언이 두 작업의 동시 시작을 막고, 어느 쪽이 먼저 반영되어도 다른
쪽의 완료 조건이 달라지지 않기 때문이다. TASK-S073-01이 고치는 자리는 3236행의 표시 상태 계산이고
이 작업이 고치는 자리는 3399행의 낱말 대조여서 두 편집이 같은 함수에서 만나지 않는다. 이유 없이
차례를 세우면 병렬 여지만 없어지므로 선언하지 않았다.

TASK-S073-01은 다른 그룹의 작업이므로 이 세션에서 손대지 않았다.

## 범위 사전 검사

작업 문서의 `## 범위 사전 검사` 절에 근거를 적었다. 선언한 파일은 하나이고, 살펴보고 뺀 파일은
`src-tauri/src/domain/project.rs`, `src/features/projects/domain/types.ts`,
`src/features/projects/components/qa/QaWorkbench.tsx`,
`src-tauri/src/infrastructure/heartbeat_condition.rs` 넷이다. 앞의 셋은 이 작업이 새 값을 만들지
않아 지금 코드가 값을 그대로 실어 나르는 것을 행 번호로 확인했고, 넷째는 조건 스크립트가 확인 동선
낱말 대조를 들고 있지 않은 것을 확인했다. 확인 동선 판정은 선언한 파일 하나에만 있다.

값 경로는 여섯 줄로 적었다. 표시 상태, 인정되는 서술, 세 목록 적용, 거절 규칙, 기존 시험, 문서
불변이다.

## 남은 위험과 후속

- 판정이 넓어진 만큼 확인 동선답지 않은 글이 통과할 여지가 생긴다. 기획서가 이 방향을 택한 근거는
  잘못 떨어뜨렸을 때 사용자에게 회복 경로가 없다는 것이고, 통과한 쪽은 확인 화면의 수정 요청으로
  되돌릴 수 있다.
- GROUP-070은 이 작업이 반영되면 사용자 QA 대기로 올라온다. 그 그룹의 확인 절차 문장을 판정에 맞게
  손보는 개별 조치는 기획서가 범위 밖으로 두었고, 이 변경으로 필요가 없어졌다.
- 구성 확인 필요 상태를 사용자 언어로 설명하고 아키텍트에게 자동으로 넘기는 일은 GROUP-073이 맡고
  있다. 두 그룹은 고치는 자리가 겹치지 않는다.
- 역할 밖 발견 하나를 넘긴다. TASK-S073-01이 만들 사유 목록 가운데 "사용자 확인 절차가 사용자
  행동으로 인정되지 않는 경우"는 이 작업이 고치는 판정을 그대로 부른다. 두 작업이 모두 반영된 뒤
  그 사유가 실제 구성 오류에서만 나오는지는 GROUP-073의 확인에서 보게 된다.
