# TASK-129 개발자 핸드오프 (qa_waiting)

## 결정권자 요약

기획서에 찍는 도장과 개발 작업에 찍는 도장이 화면에서 갈렸다. 오늘 사고가 난 그 자리다.

개발 작업 확인 자리의 반려 버튼이 더는 수정 요청이라고 부르지 않는다. 개발 준비로 되돌린다고
말한다. 기획서 쪽은 승인된 기획이면 후속 기획을 요청한다고 말하고, 두 이름이 겹치지 않는다.

활동 기록도 같은 규칙을 따른다. 승인 뒤에 온 기획서 수정 요청은 후속 기획 요청으로 불리고,
아직 결정되지 않은 기획서의 것은 그대로 수정 요청이다. 그 판별을 활동 기록이 따로 하지 않고
기획서 화면이 쓰는 자리에서 그대로 가져다 쓴다.

도장을 누르는 동작 자체는 하나도 건드리지 않았다. 달라진 것은 이름뿐이다.

자동 검사는 전부 통과했다. 남은 것은 화면을 눈으로 보는 QA이고, 어디를 보면 되는지는 작업
문서의 확인 동선에 적어 두었다.

## 바꾼 것

범위 파일 다섯 중 넷을 만졌다. `src/App.css`는 만지지 않았고, 그 이유는 아래 "손대지 않은 것"에
적었다.

### 1. 개발 작업 QA 반려 버튼의 이름 (`DevelopmentBoard.tsx:445` 부근)

바꾼 것은 무장 전후 두 문면뿐이다.

| | 이전 | 이후 |
| --- | --- | --- |
| 무장 전 | `수정 요청` | `개발 준비로 되돌리기` |
| 무장 후 | `한 번 더 누르면 수정 요청` | `한 번 더 누르면 되돌리기` |

확인 문구(`작업을 개발 준비로 되돌리고 수정 요청을 기록합니다.`)는 그대로 두었다. 작업 문서가
"지금 확인 문구는 이미 무엇이 일어나는지를 말하고 있으므로, 남은 것은 버튼 이름"이라고 범위를
직접 좁혀 두었기 때문이다. 그 문장에 `수정 요청`이라는 말이 남아 있는데, 이것은 기록되는 결과
값(`revision_requested`)을 그대로 말하는 자리이고 문장의 주어가 `작업`이라 기획서 쪽 문면과 읽힐
때 갈린다고 판단했다. 이 판단이 마음에 걸리면 QA에서 반려해 주면 그 문장까지 고친다.

무장 후 문면은 오히려 짧아졌다(13자 → 12자). 두 버튼이 한 줄에 서는 자리라 폭이 늘지 않는 것이
확인 사항이었는데, 무장 전이 4자 → 10자로 늘어도 무장 후 조합이 여전히 가장 넓다.

### 2. 검증 절차 1번 — 두 문면을 나란히

| 자리 | 문면 |
| --- | --- |
| 기획서 · 아직 결정되지 않음 | `수정 요청` → `수정 요청 기록` (확인 문구 없음) |
| 기획서 · 승인됨 | `후속 기획 요청` → `후속 기획 요청 기록`, 확인 문구 `이 기획서에 후속 기획 요청을 기록합니다. 결정 기록은 되돌릴 수 없습니다.` |
| 개발 작업 QA | `개발 준비로 되돌리기` → `한 번 더 누르면 되돌리기`, 확인 문구 `작업을 개발 준비로 되돌리고 수정 요청을 기록합니다.` |

세 자리의 버튼 이름이 서로 겹치지 않는다. 대상은 "기획서"·"작업"이라는 말로, 일어나는 일은
"후속 기획을 요청"·"개발 준비로 되돌림"으로 갈린다.

### 3. 활동 뷰의 기획서 결정 이름 (`ActivityView.tsx`)

`specEventLabels` 맵을 지우고 `labelSpecDecisions`를 쓴다. 항목 하나가 늘었다 —
`ActivityEntry`에 `label`을 담아 두고, 표시 클래스는 그대로 `kind`가 만든다. 이름과 표시가
갈릴 수 있는 자리라 필드에 그 사실을 주석으로 적었다.

- **판별을 다시 쓰지 않는다(완료 조건 4).** 승인이 앞에 있었는지를 이 파일이 세지 않는다.
  `labelSpecDecisions`가 문서 하나의 시각 오름차순 목록을 받아 답을 낸다. 항목마다 그 문서의
  `events`를 통째로 넘기므로 앱에서 새 값을 받아 올 필요가 없었다 — 작업 문서가 예상한 그대로다.
- **모르는 종류를 거르는 방법.** 이전에는 맵의 `has`로 걸렀다. 지금은 모듈이 "계약 밖의 종류는
  값을 그대로 돌려준다"고 문서화한 계약을 읽어, `label === kind`인 항목을 버린다. 아는 종류의
  목록을 이 파일에 다시 적지 않기 위해서다.
- **순서.** 이름은 문서 안 시각 오름차순으로 정하고, 화면 정렬은 그 뒤에 전역 내림차순으로
  한다. `types.ts`가 `events`를 "시각 오름차순이다"라고 계약으로 적어 두어 그대로 쓸 수 있었다.
- **시각을 읽지 못하는 항목.** 이전과 순서가 하나 달라졌다. 이름을 먼저 붙이고 그다음 시각을
  판정한다. 그래서 `at`을 읽을 수 없는 `approved` 항목이 있으면, 그 항목 자신은 피드에서
  빠지지만 뒤에 오는 수정 요청의 이름에는 여전히 승인으로 센다. 승인이 있었다는 사실과 그것을
  타임라인에 놓을 수 있느냐는 다른 문제라 이쪽이 맞다고 봤다.

## 손대지 않은 것

- **`src/App.css`.** 범위 파일이지만 바꿀 것이 없었다. 마크 클래스가 `kind`에서 나오므로 색이
  그대로이고, `.activity-mark`가 `white-space: nowrap`인 데다 피드 행이
  `grid-template-columns: auto auto minmax(0, 1fr) auto`라 이름이 길어진 만큼 제목 칸이 줄면서
  흡수한다. QA 버튼 쪽도 위에 적은 대로 가장 넓은 조합이 넓어지지 않는다.
- **`SpecWorkspace.tsx`와 `specDecisionLabels.ts`.** 읽기만 했다. 문면도 규칙도 어긋난 데가 없어
  후속으로 넘길 것이 없다.
- **개발 작업 QA의 동작.** `onTaskQa`에 넘기는 값도 `record_task_qa`도 그대로다. 기존 검사가
  `revision_requested`가 그대로 나가는 것을 이미 단정하고 있고 수정 없이 통과했다.
- **활동 피드의 정렬·상한·스크롤 복원.**

## 못 한 것: 눈으로 보는 확인 (검증 절차 5번)

`npm run tauri dev`가 `Port 1420 is already in use`로 실패했다. 이미 떠 있던 것이 둘 있었다 —
23:19에 시작한 vite 개발 서버와 00:21에 시작한 앱 인스턴스다. 그 둘은 이 세션의 것이 아니라
건드리지 않았다. 실패한 명령이 남긴 프로세스 하나(pid 32479)만 정리했다.

화면을 GUI로 자동 조작하는 것도 안 됐다. 이 세션에 접근성 권한이 없어 AppleEvent가 시간 초과로
끊긴다.

**다만 이 실패가 사용자에게 부담이 되지는 않는다.** 이미 떠 있는 앱이 그 vite 개발 서버에
붙어 있어서, 이 세션이 고친 화면이 HMR로 이미 그 창에 들어가 있다. 새로 빌드하거나 띄울 것 없이
지금 그 창에서 확인 동선을 밟으면 된다.

## 리스크와 후속

- **확인 문구에 남은 `수정 요청`.** 위에 적은 판단이다. 버튼은 갈렸지만 문장 안에는 그 말이
  남아 있다. 이것까지 갈라야 한다고 보면 QA 반려로 돌려주면 된다.
- **`FOLLOW_UP_LABEL`을 검사가 가져다 쓴다.** 그 상수가 바뀌면 두 화면의 검사가 함께 따라간다.
  의도한 결합이다 — 이름이 한 자리에서만 나온다는 것이 완료 조건 4다.
- **후속으로 넘길 것 없음.** `SpecWorkspace.tsx`도 이름 규칙 모듈도 어긋난 데가 없었다.
