## 근거 확인

기획서의 확인 사실은 이 저장소의 앱 코드와 규칙 자산에서 직접 읽은 것이다. 추정으로 쓴 항목은 없다.

- 오늘 화면 배너는 `WorkspaceShell.tsx`에서 `project.activeLeases.length > 0`일 때만 렌더되고, `activeLeases[0]`의 `agent`·`taskId`와 전체 개수만 보여준다. 아이디어가 말한 "대표 1명과 개수뿐"이 그대로 확인된다.
- `AgentLeaseSummary`(`domain/project.rs`·`domain/types.ts`)는 `lease_id`·`agent`·`task_id`·`expires_at` 네 필드다. `AgentLease`는 파일에서 `heartbeat_at`을 읽지만 요약에 싣지 않아 화면까지 도달하지 않는다. R3·완료 조건 8번이 여기서 나왔다.
- lease 스키마에 역할 필드가 없다. 공통 규칙 §4의 예시도 `schema_version`·`lease_id`·`agent`·`task_id`·`heartbeat_at`·`expires_at` 여섯이다. 확인 필요 1번의 근거다.
- `AgentLease`의 `heartbeat_at`은 `Option`이 아니라 필수다. 이 키가 없는 lease 파일은 `serde_yaml` 파싱에 실패해 `read_active_leases`가 그 파일만 건너뛴다. 화면에 아무 흔적도 남지 않는다.
- lease 디렉터리는 `.workflow/.runtime/leases` 하나이고 lease 문서에 워크플로우를 가리키는 필드가 없다. 확인 필요 4번(범위)의 근거다.
- `read_active_leases`는 `expires_at`이 지난 lease를 걸러내기만 하고 파일은 지우지 않는다. 앱에 lease 쓰기 경로가 없다.
- 작업 전이 이력은 이미 동작 중이다. `WorkflowItemSummary.events`(`kind`·`at`)가 있고, `DevelopmentBoard.tsx`가 여섯 종류를 "생성·시작·막힘·QA 대기·완료·반려"로 부른다. R5의 라벨 일치 요구와 완료 조건 18번이 여기서 나왔다.
- `qa_decision_events`와 `merge_qa_decision_events`가 QA 결정 문서를 작업 이벤트로 병합하며 같은 순간·같은 종류를 중복 제거한다. 즉 QA는 이미 원천에 포함되어 있고, 이 기획서가 새로 열어야 하는 통로는 기획서 결정 쪽뿐이다.
- `latest_spec_decisions`는 `decision@1` 문서의 `created_at`을 최신 판정 비교에만 쓰고, `apply_latest_decision`은 `outcome`으로 기획서 `status`를 덮어쓴다. 결정 시각은 화면으로 내려가지 않는다. 완료 조건 19번이 여기서 나왔다.
- `useProjectWorkspace.ts`의 2.5초 `setInterval`이 프로젝트 전체와 연동 스냅샷을 다시 읽는다. 별도 파일 감시 이벤트 경로는 없다. R8·완료 조건 27번의 근거다.
- 프로젝트 검색의 `openSearchResult`는 워크플로우를 전환하고 해당 종류의 뷰를 여는 데까지만 간다. 기획서만 문서를 실제로 열고 아이디어·작업은 목록까지다. R4가 "검색과 같은 경로"로 정하고, 항목 지목·강조를 제외 범위에 둔 이유다.
- SPEC-007의 TASK-025(날짜 선택 상세)와 SPEC-008의 TASK-027(아이디어 전문 미리보기)은 아직 `todo`다. 두 화면이 완성되기 전에도 SPEC-011의 요구가 성립하도록 이동 규칙을 기존 경로에 맞췄다.

## 확인 필요 4건의 배경

1. **역할 표시를 위한 lease 계약 확장**: `agent` 값이 `planner-claude`처럼 보이는 것은 이 저장소의 관행일 뿐 계약이 아니다. 문서 id 접두사로 역할을 되짚는 방법도 규칙을 지킨 세션에서만 맞는 추정인데, 계약을 어긴 세션이야말로 이 화면이 드러내야 할 대상이라 추정에 기대면 안 된다고 봤다. 선택 필드 추가를 제안하고, 역할 표시를 포기하는 무비용 대안도 함께 적었다.
2. **최초 시작 시각**: 아이디어가 "시작·심장박동 시각"을 요구했지만 lease에 시작 시각이 없다. 1번과 같은 기준을 적용하면서 결론은 다르게 냈다 — 만료까지 남은 시간이 같은 질문에 대체로 답하므로 계약 확장 비용을 두 필드로 나누지 말자는 제안이다. 1번이 확장으로 결정되면 같이 얹는 것이 싸다는 반론도 적었다.
3. **최근 활동 피드의 표시 범위**: 작업 31건에 이벤트가 백 건대다. 최근 30건 + 잘림 고지를 제안했다. 기간 기준은 루프가 며칠 쉬면 화면이 통째로 비어 배제했다.
4. **범위 혼합과 메뉴 위치**: lease는 프로젝트 전역이고 최근 활동은 워크플로우별이라 한 화면에 범위가 다른 두 섹션이 놓인다. 파일에 워크플로우 참조가 없으므로 나누려면 유추가 필요하고 유추 실패 워커는 어느 목록에도 못 들어간다. 그대로 두고 워커 카드가 워크플로우 이름을 밝히는 쪽을 제안했다.

## 핸드오프 노트 (이 세션 범위 밖)

- **남은 미처리 아이디어 1건**: IDEA-B91FD491(아이디어 "반영중" 파생 상태). 선점하지 않았고 lease도 없다. 다음 기획자 세션이 가져갈 수 있다.
- **IDEA-B91FD491과의 접점**: 그 아이디어는 "미만료 lease가 선점 중"을 반영중 판정의 원천으로 쓴다. SPEC-011도 같은 lease를 읽는다. 두 기획이 같은 원천을 서로 다른 규칙으로 읽게 되므로, 나중에 구현할 때 lease 해석이 흩어지지 않는지 아키텍트가 볼 필요가 있다. REPORT-SPEC-010-PLAN이 SPEC-010에 대해 같은 지적을 남겼으니, lease를 읽는 곳이 이제 셋이 된다.
- **SPEC-010과의 순서**: SPEC-010(의존 선언 구조화, 아직 미결정)이 승인되면 lease와 문서 상태를 읽는 판정이 또 하나 늘어난다. SPEC-011의 읽기 통로 확장(`heartbeat_at` 노출, 결정 시각 노출)과 같은 파일을 만지므로, 두 기획서가 모두 승인되면 구현 순서를 아키텍트가 정할 필요가 있다.
- **`heartbeat_at` 필수 파싱**: 이 키가 없는 lease 파일은 화면에서 통째로 사라진다. 규칙이 이 키를 요구하므로 현재는 계약 위반 파일만 사라지는 셈이지만, 활동 뷰가 "지금 돌고 있는 것"을 보여주는 화면이 되면 조용히 사라지는 lease의 비용이 지금보다 커진다. 이 기획서는 R3에서 "읽을 수 있는 lease만 그린다"까지만 정했고, 읽지 못한 lease를 사용자에게 알릴지는 다루지 않았다.
- **만료 lease 파일이 계속 쌓인다**: 앱은 lease를 지우지 않고 에이전트가 해제하지 않으면 파일이 남는다. 이 기획서는 만료 lease를 다루지 않는데(제외 범위), 해제하지 않은 세션이 늘면 디렉터리에 파일만 쌓이는 상태는 그대로다.
- **SPEC-011은 프론트엔드와 백엔드를 함께 만진다**: 새 뷰와 배너 변경(프론트엔드), lease 요약 필드 확장과 기획서 결정 시각 노출(백엔드), 그리고 확인 필요 1번이 확장으로 결정되면 규칙 자산까지다. 아키텍트 분해 시 읽기 통로 확장과 화면 신설을 한 작업에 묶으면 검증 범위가 커진다. 판단은 아키텍트 몫이다.
