# TASK-S051-06 개발 보고서

## 결정권자 요약

앱이 런타임을 설치하고 업데이트하는 백엔드 명령 여섯 개를 만들었다.
번들 버전과 설치된 버전과 실행 중 버전을 서로 다른 사실로 구분해 돌려준다.
계획은 아무것도 쓰지 않고, 적용은 직전 계획의 식별자와 사용자 확인이 함께 와야 실행된다.
해시·target·API 주 버전이 어긋나면 launcher를 바꾸기 전에 멈추고 이전 버전이 그대로 남는다.
업데이트가 건드릴 실행 수와 프로젝트 목록은 런타임이 센 값을 그대로 쓰며 앱이 다시 세지 않는다.
확인하지 못한 값과 권한 때문에 확인할 수 없는 값은 실행 중으로 올라가지 않는다.
운영체제 서비스 파일과 런타임 데이터베이스를 앱이 직접 읽는 경로는 없다.
전용 자동 검사 30건을 더했고 앱 전체 검사 659건과 프런트 검사를 통과했다.
사용자의 확인을 요청한다.

## 변경 파일과 모듈

- `src-tauri/src/domain/agent_runtime.rs`: 새 파일이다. 런타임 응답을 앱의 값으로 옮기고 호환을
  판정한다. 지원 API 주 버전과 최소·최대 버전 상수가 이 한 곳에 있다. 서비스 판정 일곱 어휘와 적용
  단계 다섯 이름을 런타임 계약 그대로 값으로 뒀다.
- `src-tauri/src/infrastructure/agent_runtime_process.rs`: 새 파일이다. 고정 인자 배열과 표준 입력
  JSON으로만 런타임을 부른다. 조회, 계획, 적용, launcher 전환, 서비스 등록 다섯 호출이 있다.
- `src-tauri/src/infrastructure/agent_runtime_package.rs`: 새 파일이다. 번들 자산의 manifest를 읽고
  파일마다 해시와 크기를 대조한 뒤 임시 디렉터리를 거쳐 버전 디렉터리로 옮긴다.
- `src-tauri/src/application/agent_runtime_install_service.rs`: 새 파일이다. 여섯 명령의 흐름과 계획
  지문, 확인 검사, 호환 차단을 담는다.
- `src-tauri/src/commands/agent_runtime.rs`: 새 파일이다. 경로 해석은 이 계층에서만 하고 Tauri가 준
  앱 데이터·resource 경로만 쓴다.
- `src-tauri/src/{domain,application,infrastructure,commands}/mod.rs`와 `src-tauri/src/lib.rs`:
  새 모듈 등록과 커맨드 여섯 개 등록.
- `.github/workflows/release.yml`: 이 기기 target의 런타임 배포물 하나를 내려받아 풀고, 번들 자원
  선언을 붙이고, 담긴 target이 맞는지 검사하는 두 단계를 더했다.

## 설계 판단

- 버전을 셋으로 나눴다. 번들이 들고 있는 버전, 디스크에 설치된 버전, 실제로 도는 버전은 서로 다른
  사실이다. 디스크만 새 버전인 상태는 호환이 아니라 재시작 필요로 답한다.
- 처음 설치는 업데이트 경로를 쓸 수 없다. 부를 launcher가 아직 없기 때문이다. 그래서 방금 설치한
  실행 파일 자신에게 launcher 전환을 시키고, 그 뒤에 생긴 launcher로 서비스를 등록한다. 세 단계의
  이름은 런타임 계약의 것을 그대로 쓴다.
- 계획 식별자를 두 곳에서 만들지 않는다. 설치 계획은 번들 자산과 지금 설치 상태를 묶어 앱이 만들고,
  업데이트 계획은 런타임이 만든 값을 그대로 보관했다가 그대로 실어 보낸다.
- 번들 자원 선언을 저장소에 커밋하지 않는다. Tauri가 빌드 시점에 자원 경로의 존재를 검사해서, 배포물이
  없는 개발자 기기에서는 그 선언만으로 `cargo build`가 깨진다. 릴리스 워크플로가 배포물을 놓은 뒤 같은
  단계에서 선언을 붙인다. 저장소에 자리표시 파일을 두는 방법도 있으나 그 파일은 범위 파일이 아니다.
- 번들 자산을 압축물이 아니라 풀린 디렉터리로 다룬다. manifest가 파일마다 해시와 크기를 적고 있어서,
  푸는 단계를 없애면 검증 대상과 설치 대상이 정확히 같아진다. 압축 해제는 릴리스 워크플로가 한다.

## 검증 절차와 결과

- `cargo test --manifest-path src-tauri/Cargo.toml` 통과: 659 passed. 이번에 더한 30건을 포함하며
  기존 629건은 그대로 통과한다.
- `cargo clippy --all-targets` 경고 0건.
- `npm run check` 통과: 타입 검사와 빌드 성공.
- 앱이 플랫폼 파일을 직접 읽지 않는 것을 검색으로 확인했다. 이번 다섯 모듈에서 plist, launchctl,
  systemctl, schtasks, sqlite, LaunchAgents, systemd 중 어느 것도 제품 경로에 없다. 유일한 일치는
  복구 검사가 데이터베이스 파일이 그대로인지 확인하는 한 줄이며, 읽는 것이 아니라 불변을 단언한다.
- 다른 세션이 같은 저장소의 다른 파일을 고치는 중이었으나 전체 검사가 모두 통과했으므로 이번 변경과
  구분해 보고할 실패가 없다.

## 남은 위험

- 검증은 macOS에서만 실행했다. Windows와 Linux의 `cargo test`는 확인하지 못했다. 처음 설치의 launcher
  전환 검사는 실행 권한이 필요해 unix에서만 돌고 Windows에서는 건너뛴다.
- 릴리스 워크플로는 런타임 릴리스 태그를 환경 값으로 고정한다. 그 태그의 산출물이 실제로 존재하는지는
  릴리스를 돌려 봐야 확인된다. 이번 세션에서 워크플로를 실행하지 않았다.
- 서비스 등록은 런타임의 기존 명령을 부르고 그 종료 코드만 본다. 등록물이 이미 다른 이름으로 있는
  기기에서 그 명령이 어떻게 답하는지는 런타임 쪽 동작이며 앱이 해석하지 않는다.
- 화면은 이 작업의 범위가 아니다. 여섯 명령이 돌려주는 값을 사용자에게 어떻게 보일지는 후속 작업이
  정한다.

## 후속 작업

- 화면 작업은 `execution_allowed`와 단계별 결과, 그리고 계획의 실행 영향 수를 그대로 쓰면 된다. 단계
  이름을 합치거나 새로 만들지 않는 것이 완료 조건이다.
- 번들 자원 선언을 저장소에 두는 편이 낫다고 판단되면 자리표시 파일 하나를 범위에 넣는 작업이 필요하다.
- 실제 릴리스 한 번으로 세 target 번들에 배포물이 하나씩 담기는지 확인하는 일이 남았다.
