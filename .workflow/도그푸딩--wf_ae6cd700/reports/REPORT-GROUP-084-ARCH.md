# GROUP-084 아키텍트 핸드오프

## 결정권자 요약

런타임이 예약한 승인 결정 DECISION-ED9827F2을 처리해 SPEC-084의 작업 그룹 GROUP-084을 만들고 개발
작업 셋으로 나눴다. 기획서가 아키텍트에게 맡긴 선택은 둘이었다. 판정이 필요한 값을 어느 통로로
받아 올지, 그리고 두 설치 경로 중 어느 쪽에 명령을 얹을지다. 앞의 것은 자격 확인 도구에 상태 투영
출력을 더하는 쪽으로, 뒤의 것은 앱의 관리 자산 동기화 경로로 정했다. 근거는 아래에 적었다. 확인
방식은 자동 검증으로 두었다. 사용자가 터미널에서 부르는 명령이라 사용자 확인 절차에 적을 수 있는
동작이 없고, 기획서의 요구사항마다 붙은 완료 조건이 모두 자동 검사로 표현되기 때문이다. 사용자가
할 일은 지금 없다. 세 작업이 모두 검증되면 그룹이 자동으로 닫힌다.

## 처리한 대상

- 예약 대상: DECISION-ED9827F2 (SPEC-084 승인, `created_by: user`)
- lease: lease-85690-20260819144359 (renew로 소유 확인, 종료 코드 0)
- 결과 접두사: RES-20260819T144359Z-85690-20260819144359 (보고용 표기이며 문서 id에 쓰지 않았다)
- 만든 문서: GROUP-084, TASK-S084-01, TASK-S084-02, TASK-S084-03

자격 재확인 결과, SPEC-084을 대상으로 한 결정은 DECISION-ED9827F2 하나뿐이고 결과값이 승인이며 그
결정을 참조하는 작업 그룹은 없었다. 문서 이름은 계보 규칙대로 기획서 번호를 따랐고, GROUP-084과
TASK-S084-01~03의 경로가 비어 있는 것을 쓰기 전에 확인했다.

## 보고 없이 끝난 실행 기록 확인

`.workflow/.runtime/silent-runs/`를 읽었다. 이 대상을 짚은 기록이 하나 있다. 실행 id
0bb440a41d624900b3815b3f3c97ed20, 역할 아키텍트, 시작 2026-08-19T14:43:59Z, 종료 14:44:00Z, 사유
`supervisor_identity_unverified`다.

그 실행이 남긴 잔여물은 없었다. 시작과 종료가 1초 차이이고, GROUP-084 경로와 TASK-S084 경로가 모두
비어 있었으며, 작업 트리에 이 기획서와 관련된 변경도 없었다. 그래서 인수한 것도 버린 것도 없고,
이번 세션은 빈 자리에서 시작했다.

## 해석을 정한 자리

### 판정을 어디서 받아 올 것인가

기획서는 통로를 고정하지 않고 불변식만 고정했다. 판정 규칙을 적은 네 번째 자리를 만들지 않는 것이다.
열려 있던 두 방법 가운데 자격 확인 도구의 출력을 넓히는 쪽으로 정했다. 근거는 둘이다.

첫째, 앱 실행 파일에는 명령줄 진입점이 없다. `src-tauri/src/main.rs`가 Tauri 창을 여는 것이 전부이고
인자 파싱이 아예 없어, 앱에게 판정을 물어보는 통로를 만들려면 헤드리스 실행 경로를 통째로 새로 만들어야
한다. 기획서 R1이 산출물을 규칙 디렉터리의 스크립트 하나로 고정했으므로 그 크기의 변경은 이번 승인의
범위 밖이다.

둘째, 자격 확인 도구가 이미 판정을 다 하고 있다. `heartbeat_condition.rs` 620행의 구성 확인 훑기는
앱의 기능 표시 상태 사슬을 같은 순서로 이식해 두었고, 1083행 부근의 최종 판정에서 확정·반려·준비
중·막힘·진행 중에 해당하는 기능을 `continue`로 버린 뒤 구성 확인 필요만 출력한다. 버리는 가지마다
판정 결과는 이미 손에 들려 있다. 509행의 결정 훑기도 기획서별 최신 사용자 결정을 이미 고른다. 그러니
이 통로는 판정 규칙을 새로 적는 일이 아니라 계산해 놓고 버리던 값을 내보내는 일이다.

### 무엇을 판정값으로 받고 무엇을 직접 읽을 것인가

기획서 R2의 두 갈래를 출력 항목마다 갈랐다.

- 판정값으로 받는다: 최신 결정을 덮은 기획서 표시 상태(진행 집계와 도장 대기), 기능의 표시 상태(확인
  대기 목록), lease의 만료 여부(활성 선점).
- 직접 읽는다: 기능 문서에 적힌 준비 중·활성(진행 집계), 개발 작업의 상태(진행 집계와 막힌 작업),
  보고 없이 끝난 실행 기록, 마이그레이션 락, `project.yml`의 프로젝트 이름과 활성 워크플로.

진행 집계의 기능 건수를 표시 상태가 아니라 문서에 적힌 상태로 잡은 것이 이 가름의 핵심이다. 그렇게
두면 판정 통로가 없을 때 빠지는 항목이 넷으로 줄고, 그 넷을 뺀 나머지는 언제나 답할 수 있다. 기획서
확인 사실 3번이 가리킨 문제는 기획서 축에만 있고 기능 축에는 없다. 기능 문서의 `status`는 아키텍트가
직접 쓰는 값이라 결정으로 덮이지 않기 때문이다.

### 설치 경로

관리 자산 동기화 경로(`managed_project_assets.rs`)로 정했다. 선점 헬퍼와 조건 스크립트가 이미 그
경로를 타고, 설정 화면의 자산별 설치 상태 목록이 그 결과를 그대로 그린다. 화면은 자산 배열을 받은
대로 훑어 그리므로(`SettingsView.tsx` 227행) 새 자산이 늘어도 화면 코드가 바뀌지 않는다. 예약 헬퍼가
타는 프로젝트 저장소 경로는 버전 표기와 충돌 처리를 자산 목록에 실어 보내지 않으므로 고르지 않았다.

### 확인 방식

자동 검증이다. 사용자 확인 절차에는 터미널 명령, 패키지 실행기, 저장소 조작, 내부 시험 실행을 적을 수
없다. 이 기능이 사용자에게 드러나는 표면은 터미널 명령 하나뿐이라, 사용자 확인 모드를 고르면 그 절차를
쓸 방법이 없다. 기획서의 R1~R7 완료 조건이 모두 자동 검사로 표현되므로 자동 검증이 유일하게 의미 있는
확인이다.

## 작업 구성과 병렬 안전

- TASK-S084-01 — 조건 스크립트에 상태 투영 출력을 더한다. `heartbeat_condition.rs` 하나만 잡는다.
- TASK-S084-02 — 조회 명령을 관리 자산으로 세우고 호출 계약까지 채운다. 새 모듈과 모듈 나열과 동기화
  배선 셋을 잡는다.
- TASK-S084-03 — 출력 다섯 묶음과 두 형식을 채우고 앱 판정과 대조하는 회귀 검사를 세운다. 새 모듈
  하나만 잡는다.

01과 02는 선언한 파일이 하나도 겹치지 않아 나란히 돈다. 03은 02가 만든 모듈 파일을 이어서 채우므로
겹치고, 01의 투영을 소비하므로 둘 다 선행으로 선언했다. 셋 중 기계 상태를 조건으로 삼는 측정이 없어
단독 실행을 선언한 작업은 없다.

## 아키텍트가 고정한 계약

01과 03이 서로 다른 세션에서 돌므로, 두 작업이 주고받는 값의 모양을 아키텍트가 고정했다. 상태 투영의
호출 형태, 세 레코드의 필드 순서, 기획서 다섯 어휘와 기능 열 어휘, 종료 코드가 그것이며 두 작업
문서에 같은 문장으로 적었다. 03이 그 계약이 부족하다고 판단하면 조건 스크립트를 고치지 말고 막힌
사유로 남기라고 적어 두었다.

판정 통로를 쓸 수 없을 때의 동작도 고정했다. 설치된 조건 스크립트가 옛 판이면 판정에 기대는 네 항목을
빼고, 뺀 항목의 이름을 사람용 마지막 줄과 기계 출력의 배열에 남기며, 종료 코드는 0이다. 기획서 R2의
"값이 조용히 사라지지 않게 한다"가 실제로 쓰이는 자리가 여기다.

## 범위 사전 검사에서 확인한 것

세 작업 문서의 `## 범위 사전 검사`에 값 경로를 적었다. 이번에 실제로 열어 보고 선언에서 뺀 자리 가운데
기록해 둘 만한 것은 셋이다.

- `managed_script.rs` 121행이 설치 계획의 식별자를 `claim_helper`로 박아 둔다. 조건 스크립트는
  `managed_project_assets.rs` 645행에서 그 값을 덮어 쓴다. 새 자산도 같은 길을 쓰게 했다. 공용 규약을
  고쳐 자산마다 식별자를 받게 하는 편이 깨끗하지만 기존 두 자산의 배선이 함께 흔들리고, 이번 승인이
  요구하지 않은 변경이다.
- 설정 화면과 그 시험은 자산 배열을 받은 대로 그리므로 선언 밖이다. TASK-S084-02의 검증 절차에 화면
  시험을 그대로 통과시키는 단계를 넣어 이 판단을 실제로 확인하게 했다.
- 저장소의 `.workflow/rules/*.sh`는 앱이 다시 쓰는 설치본이라 세 작업 모두 선언 밖으로 두었다. 정본은
  Rust 상수다.

## 아키텍트 밖의 발견

세 가지를 남긴다. 이번 승인의 범위가 아니므로 고치지 않았다.

- `managed_script.rs` 117행의 설치 계획이 식별자를 `claim_helper` 한 값으로 박아 두어, 자산이 늘 때마다
  호출처가 경계에서 덮어 써야 한다. 자산이 넷이 되는 이번 변경으로 그 덮어쓰기가 둘이 된다. 정리하려면
  별도의 아이디어가 필요하다.
- 조건 스크립트의 두 구현이 각각 1,800줄과 1,400줄이고 같은 판정을 두 벌 들고 있다. 이번 작업이 그
  쌍을 하나 더 늘린다. 유지 비용을 줄이는 방법은 이 승인의 범위 밖이다.
- 기획서 확인 사실 3번이 가리킨 상황(기획서 문서의 `status`가 결정 이후에도 그대로 남는 것)은 이 조회
  도구가 우회할 뿐 없애지 않는다. 문서 상태를 결정에 맞춰 정리하는 일은 별도 판단이 필요하다.

열린다. 셋이 검증되면 자동 확인 모드라 사용자 도장 없이 그룹이 닫힌다.
