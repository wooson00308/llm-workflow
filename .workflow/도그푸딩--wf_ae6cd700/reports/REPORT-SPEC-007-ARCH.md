# SPEC-007 아키텍트 핸드오프

- 대상 기획서: SPEC-007 (캘린더 뷰를 상태 전이 사실 기반 타임라인으로 전환)
- 근거 결정: DECISION-AA40AF4B (approved, created_by: user, 2026-08-02T16:36:25Z)
- 세션 역할: 프로젝트 아키텍트
- 작성 시각: 2026-08-02T16:58Z
- 파생 작업: TASK-022, TASK-023, TASK-024, TASK-025 (전부 `status: todo`)

## 대상 선정 근거

- `decisions/`의 앱 소유 기획서 결정 7건은 전부 `outcome: approved`다. 그중 파생 작업이 아직 없는
  것은 DECISION-AA40AF4B(SPEC-007) 하나다. 나머지 여섯은 TASK-001·002(SPEC-001),
  TASK-003~007(SPEC-002), TASK-008~012(SPEC-003), TASK-013(SPEC-004), TASK-014~018(SPEC-005),
  TASK-019~021(SPEC-006)이 이미 참조한다.
- 착수 시점에 `.workflow/.runtime/migration.lock` 없음, `leases/` 비어 있음. 배타 생성으로
  `leases/SPEC-007.yml`을 만든 뒤 `tasks/`에 DECISION-AA40AF4B를 참조하는 문서가 없음을 다시
  확인하고 작업했다.
- SPEC-007 본문은 `status: user_review`지만 앱이 기록한 승인 결정이 있으므로 공통 규칙 5절의 차단
  조건에 걸리지 않는다. 결정 본문이 확인 필요 1·2·3번을 "기획서의 제안대로"로 확정했으므로
  종류별 집계 표시, 에이전트가 작업 문서에 기록, 여섯 종류 전부 집계 포함을 확정된 요구사항으로
  다뤘다.

## 분해 방식

계약 → 기록·병합 → 배치 → 상세 순서다. 앞의 둘은 백엔드, 뒤의 둘은 프론트엔드다. 네 작업 모두
병렬로 두지 않았다. 앞의 둘은 같은 Rust 파일을, 뒤의 둘은 같은 컴포넌트와 같은 CSS 블록을 만진다.

| 작업 | 요구사항 | 기획서 완료 조건 |
| --- | --- | --- |
| TASK-022 계약·파서·규칙 자산 | R2(계약), R3 | 4, 6(읽기), 7, 8 |
| TASK-023 앱 기록·QA 결정 병합 | R2(앱 기록), R4, R5(백엔드) | 5, 6(QA 기록), 9, 10, 11, 12, 14 |
| TASK-024 배치 기준·집계 칸·범위 문구 | R1, R6, R8 | 1, 2, 3, 15, 16, 20, 21 |
| TASK-025 날짜 선택 상세·안내·접근성 | R5(화면), R7, R9 | 13, 17, 18, 19, 22 |

완료 조건 23(테스트·타입 검사·포맷)은 네 작업 모두에 걸었다. 완료 조건 6은 읽기 쪽(TASK-022)과
QA 기록 쪽(TASK-023)으로 갈라 각각의 검증 절차에 넣었다.

경계를 이렇게 잡은 이유는 세 가지다.

1. 계약과 규칙 자산을 한 작업에 묶었다. 규칙 문구가 `history` 필드 이름과 여섯 값을 그대로 쓰므로,
   따로 떼면 두 문서가 서로 다른 이름을 가리키는 커밋이 중간에 남는다.
2. 앱의 쓰기와 결정 문서 병합을 한 작업에 묶었다. 앱이 완료 전이를 쓰기 시작하는 순간 같은 사실이
   두 원천에 생기므로, 중복 제거가 같은 커밋에 없으면 화면에 이벤트가 두 번 나오는 구간이 생긴다.
3. 프론트엔드를 배치와 상세로 나눴다. TASK-024까지만 끝난 상태도 말이 되는 화면이다(집계는 보이고
   상세는 못 연다). TASK-025는 그 위에 선택 상태 하나와 패널 하나를 얹는다.

TASK-024를 TASK-023 뒤에 건 것은 파일 충돌 때문이 아니라 확인 가능성 때문이다. TASK-022만 끝난
상태에서는 이 저장소의 작업 21건에 이력이 없어 그리드가 여전히 비어 있고, 개발자가 화면으로
확인할 방법이 없다. TASK-023이 끝나면 기존 QA 결정 13건이 완료·반려 이벤트로 잡혀 실제 데이터가 생긴다.

## 아키텍트가 정한 것

기획서가 아키텍트에게 명시로 위임한 항목과, 구현이 갈릴 수 있어 미리 못박은 항목이다.

1. **이력 필드 구조 (R2가 명시로 위임).** 개발 작업 프론트매터의 선택 필드 `history`, 블록 시퀀스,
   항목은 `{ at: <RFC3339>, kind: <종류> }` 한 줄이다. `kind`는 여섯 값이다:
   `created`·`in_progress`·`blocked`·`qa_waiting`·`completed`·`revision_requested`.
   - 다섯은 진입한 상태 이름과 같고, `created`와 `revision_requested`만 다르다. `created`는 상태가
     아니고, `revision_requested`는 진입 상태가 `todo`지만 작업 생성과 구분해야 한다. 둘 다
     `todo`로 적으면 R6·R7이 요구하는 "무슨 종류의 일"을 화면이 말할 수 없다.
   - 필드 이름을 `status`로 하지 않았다. 프론트매터에 이미 `status:` 키가 있어 들여쓰기 한 칸
     차이로 읽는 사람과 줄 단위 편집기가 헷갈린다.
   - 항목을 한 줄 흐름 표기로 정한 것은 앱의 추가 구현 때문이다. `update_task_frontmatter`가 줄
     단위 편집기라, 항목이 두 줄이면 삽입 로직이 블록 구조를 알아야 한다. 읽기는 블록 표기도
     받아들이게 해서 사람이 손으로 쓴 문서를 깨뜨리지 않는다.
2. **`updated_at`을 건드리지 않는다.** R2가 금지한 것은 `updated_at`을 전이 시각으로 *쓰는* 것이지
   `updated_at` 자체가 아니다. QA 기록이 지금처럼 `updated_at`을 갱신하는 동작은 유지한다.
3. **QA 전이는 두 원천에 남는다.** R3이 앱의 기록 경로에서 남기라고 하고, R4가 결정 문서를 원천으로
   읽으라고 한다. 둘 다 하면 같은 사실이 두 번 생기고, 그래서 완료 조건 12(중복 제거)가 있다.
   이 이중화에는 값이 있다 — 앱이 작업 파일에 이력을 덧붙이지 못하는 경우에도 완료·반려 사실이
   결정 문서에 남아 화면에서 사라지지 않는다. TASK-023의 인라인 표기 실패-무시 처리가 이것에 기댄다.
4. **중복 판정은 파싱한 순간으로 한다.** 문자열 비교로는 안 된다. 이 저장소의 QA 결정은
   `created_at: 2026-08-02T04:37:59.588232+00:00` 형태이고 에이전트는 `Z` 표기를 쓸 가능성이 높다.
   같은 순간이 다른 문자열로 남는다.
5. **`at`은 원문을 그대로 전달한다.** 파싱은 검사·정렬·중복 판정에만 쓰고 정규화한 값으로 바꾸지
   않는다. `HeartbeatJobRun.at`이 이미 원문 전달 선례다.
6. **이벤트는 작업 요약에 실어 보낸다.** `WorkflowItemSummary.events`다. 별도 조회 커맨드를 만들지
   않았다. 이유는 필터다 — R8이 검색어·상태 필터를 타임라인에도 적용하라고 하는데, 이벤트가 작업에
   붙어 있으면 지금 있는 `matchesFilters` 하나로 끝난다. 목록을 따로 두면 필터를 두 번 구현해야 한다.
   TypeScript 쪽은 `dueAt`과 같이 선택 필드로 둬서 기존 테스트 픽스처를 고치지 않게 했다.
7. **가리키는 작업이 없는 QA 결정은 병합 단계에서 사라진다.** 이벤트가 작업에 붙는 구조라, 붙을
   작업이 없으면 자연히 버려진다. R4의 "없는 작업을 가리키는 결정 기록" 요구가 별도 방어 코드 없이
   성립한다.
8. **보기 이름은 "타임라인" (R1이 명시로 위임).** 사용자에게 보이는 말만 바꾼다 — 전환 버튼 라벨,
   상단 안내 문구의 "일정", 섹션 접근성 이름, 헤더 기준 표기. `ViewMode`의 `"calendar"` 값,
   `CalendarView` 컴포넌트 이름, `.task-calendar` 계열 CSS 클래스는 그대로 둔다. "캘린더"도 틀린
   말은 아니지만 상단 문구의 "일정"이 명백히 어긋나고, 한 화면 안에서 "캘린더"와 "타임라인"이
   섞이는 것보다 하나로 맞추는 편이 낫다고 봤다.
9. **하루 칸 칩은 종류당 하나, 순서는 작업 수명 순 고정.** 건수 순 정렬은 날짜를 옮겨 다닐 때 칩
   위치가 흔들려 읽기 어렵다. 종류가 여섯이므로 칩 수의 상한이 여섯이고, 이것이 R6의 "이벤트가
   몰려도 칸이 안 늘어난다"를 구조적으로 보장한다.
10. **이벤트 날짜 키는 로컬 날짜다.** 기존 `calendarDateKey`는 문자열 앞 10자를 떼는 방식이라
    `due_at`(날짜)에는 맞지만 순간에는 UTC 날짜를 집는다. `2026-08-02T23:00:00Z`는 한국에서 8월
    3일이다. 이벤트용 헬퍼를 따로 만들라고 적었고, 기존 헬퍼는 보드·리스트가 계속 쓰므로 남긴다.
11. **이력 없는 작업 안내는 한 줄, 목록 없음.** R5는 "존재를 알린다"까지만 요구한다. 21건을 버튼으로
    늘어놓으면 기획서가 문제 삼은 "아래에 일정 미지정 21만 쌓인다"를 이름만 바꿔 재현하게 된다.
12. **상세 패널은 그리드 아래.** 그리드를 대체하지 않는다. 달 이동 버튼과 필터가 계속 보이므로
    R7의 "상세를 열어도 달 이동·필터가 안 바뀐다"가 구조로 성립한다.
13. **선택 가능한 날은 이벤트가 있는 날뿐.** 42칸을 전부 버튼으로 만들면 탭 정지가 42개가 된다.
    빈 날을 선택해도 보여줄 것이 없다.
14. **규칙 버전 숫자를 상수로 뽑는다.** 지금 네 자리에 리터럴로 흩어져 있어(`:279`, `:284`, `:319`,
    `:329`) 하나만 놓치면 `validate_project_instructions`가 방금 설치한 파일을 미래 버전으로 보고
    `create_workflow`를 막는다. 공통 3→4, 아키텍트·개발자 2→3, 기획자는 2 유지다. 기획자 계약은
    작업 문서를 만들지 않으므로 바뀔 내용이 없다.

## 확인한 사실

추정 없이 파일에서 읽은 값이다. 확인 시점 2026-08-02.

- 이 저장소 개발 작업 21건의 프론트매터 키는 일곱 개뿐이다(`schema`·`id`·`title`·`status`·
  `source_spec_id`·`source_decision_id`·`updated_at`). `due_at` 0건, `created_at` 0건. 기획서의
  전제와 일치한다.
- `CalendarView`는 `DevelopmentBoard.tsx:373`, `item.dueAt` 배치는 `:390`, 헤더 기준 표기는 `:407`,
  일정 미지정 섹션은 `:432`~`:437`이다.
- `tasksForDevelopment`(`:477`)가 완료 작업을 `updated_at` 내림차순 3개로 자르고, 세 보기가 모두
  그 결과(`filteredTasks`, `:50`)를 받는다. 요약줄의 "완료는 최근 3개만 표시"는 `:128`이다.
- `read_markdown_document`(`fs_project_repository.rs:849`)가 요약을 만들고 `due_at`을 `:878`에서
  읽는다. `read_markdown_summaries`(`:822`)는 이 함수가 `Err`이면 파일을 통째로 건너뛴다 — 이력
  파싱 실패를 `Err`로 만들면 작업이 목록에서 사라진다.
- `update_task_frontmatter`(`:688`)는 `status:`·`updated_at:`으로 시작하는 줄만 치환하고 나머지
  줄은 그대로 둔다. 들여쓰기된 줄은 걸리지 않으므로 이력 항목 안의 값이 오인되지 않는다.
  `updated_at`이 없으면 프론트매터 끝에 덧붙인다(`:724`).
- `record_task_qa`(`:314`)가 `created_at`을 `:337`에서 한 번 만들어 결정 문서와 작업 파일 양쪽에
  쓴다. 그래서 앱이 만든 두 기록은 같은 문자열을 갖는다.
- 실제 QA 결정 문서 형태: `schema: workflow-labs/qa-decision@1`, `task_id`, `outcome`,
  `created_by: user`, `created_at: 2026-08-02T04:37:59.588232+00:00`. 본문이 빈 것도 있다.
  `decisions/`에는 기획서 결정 7건과 QA 결정 13건이 함께 있다.
- 프론트엔드는 개별 결정 문서를 받지 않는다. `WorkflowCounts.decisions`(`domain/project.rs:75`)는
  `user_review` 기획서 수를 담은 값이고 결정 문서 수가 아니다.
- 규칙 자산 설치는 `install_project_instructions`(`project_instructions.rs:270`)이고 호출처는
  `create_workflow`·`record_spec_decision`·`record_task_qa` 셋이다. `inspect`는 설치하지 않는다.
  즉 기존 프로젝트는 사용자가 기획서를 승인하거나 QA를 기록할 때 새 규칙을 받는다. 완료 조건 8은
  기존 경로로 충족되고, 버전 상수만 올리면 된다.
- `plan_rules_file`(`:336`)은 `rules_version`이 현재 값보다 클 때만 충돌로 보고, 내용이 같으면
  쓰지 않는다. 그래서 역할 계약 셋의 공통 `current_version`을 3으로 올려도 기획자 계약(2)은 안전하다.
- 검증 명령은 `npm run check`(typecheck + test + build)와 CI의 Rust 3종(`cargo fmt --check`,
  `cargo clippy --all-targets -D warnings`, `cargo test`)이다(`.github/workflows/ci.yml:24`, `:46`~`:48`).
- `chrono`는 `fs_project_repository.rs:6`에서 이미 쓰고 있다. 새 의존성이 필요 없다.
- 캘린더 CSS는 `App.css:438`~`:474`, 칸 `min-height: 102px`는 `:449`다.

## 남은 위험

- **이력 없는 21건.** 소급 추정은 기획서 제외 범위라 하지 않는다. TASK-025의 안내가 이 사실을
  드러내지만, 사용자가 타임라인을 처음 열면 QA 결정이 있는 작업의 완료·반려 이벤트만 보이고
  "표시되지 않는 작업 n건"이 함께 뜬다. 기획서 기준으로는 정상 동작이지만 첫인상이 기대와 다를 수
  있다. 시간이 지나며 자연히 채워진다.
- **에이전트가 규칙을 어기면 구멍이 남는다.** 결정 2번이 받아들인 비용이다. 앱은 이력이 없는 것과
  전이가 없었던 것을 구분하지 못한다. 구멍을 드러내는 수단은 TASK-025의 안내 줄 하나뿐이다.
- **줄 단위 삽입의 취약함.** `update_task_frontmatter`가 YAML 파서가 아니라 줄 편집기다. 계약이
  정한 표기를 벗어난 `history`(인라인 시퀀스 등)에서는 앱이 항목을 덧붙이지 못한다. TASK-023에
  실패-무시로 적었고 결정 문서가 사실을 보전하지만, 그 작업의 작업 문서 이력에는 구멍이 남는다.
  프론트매터를 파싱해 다시 쓰는 방식으로 바꾸면 이 문제가 사라지는 대신 알 수 없는 필드의 원문
  서식 보존이 깨진다. 지금 계약이 더 중요하다고 판단했다.
- **결정 디렉터리 스캔이 2.5초마다 한 번 더 늘어난다.** `latest_spec_decisions`가 이미 같은
