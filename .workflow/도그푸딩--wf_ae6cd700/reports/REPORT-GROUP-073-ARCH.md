# GROUP-073 아키텍처 보고서

## 요약

승인 결정 DECISION-2C016C15를 GROUP-073과 실행 작업 넷으로 분해했다. 기능은 사용자가 지금 할 일이
없는 기능 상태를 목록 자리에서 설명하고, 구성 확인 필요 기능을 아키텍트가 자동으로 맡게 하는 것이다.
그룹은 사용자 확인 모드이며 통합 확인 절차 하나를 담았다. 작업 넷은 상태 계산, 역할 계약, 대상 판정,
화면 순이고 파일 겹침은 모두 선행 선언으로 차례를 정했다. 그룹은 active, 작업 넷은 모두 todo다.

## 대상과 선점

- 대상: DECISION-2C016C15 (SPEC-073의 최신 앱 기록 결정, outcome approved)
- 선점: lease-24641-20260818133642 (런타임이 예약한 것을 renew로 확인, 재획득 없음)
- 예약 접두사: RES-20260818T133642Z-24641-20260818133642 (보고용 표기이며 문서 식별자에 쓰지 않았다)
- 자격 재확인: SPEC-073을 가리키는 결정은 DECISION-2C016C15 하나뿐이고 outcome은 approved다.
  이 승인을 출처로 삼은 기능 문서가 없었고, GROUP-073 경로도 비어 있었다.

## 식별자 판단

기능 문서 이름은 기획서 번호를 따라 GROUP-073으로 지었고, 작업은 같은 계보의 두 자리 순번으로
TASK-S073-01부터 TASK-S073-04까지 지었다. 쓰기 전에 다섯 경로가 모두 비어 있는 것을 확인했다.
예약 접두사는 어느 식별자에도 넣지 않았다.

## 구성 판단

### 확인 방식

사용자 확인으로 두었다. 이 기능이 바꾸는 것의 대부분은 사용자가 목록에서 읽는 문장이고, 개발자가
아닌 사람이 화면 셋을 열어 그대로 확인할 수 있다. 대상 판정 순서와 선점 배제, 자동 대상에서 빠지는
조건은 화면에서 확인할 수 없어 작업별 자동 검증이 덮게 하고, 어느 인수 조건을 어느 검사가 덮는지를
작업 문서의 완료 조건에 조건 번호로 적었다.

확인 절차는 하나로 썼다. 사용자가 이 기능을 만나는 동선이 목록을 훑는 한 번이기 때문이다. 확인
시점의 판 상태를 전제하지 않도록, 이 그룹의 확인을 시작하는 순간 이 기능 자체가 사용자 QA 대기로
지금 확인할 기능 목록에 서 있다는 사실을 대조 기준으로 삼았다.

작성한 절차가 판정 규칙을 통과하는지 미리 확인했다. 확인 절차 인정 판정이 쓰는 세 낱말 목록과 금지
낱말 목록 63개를 소스에서 뽑아 본문과 제목에 대조했고, 화면 낱말·행동 낱말·결과 낱말이 모두 걸리고
금지 낱말은 하나도 걸리지 않았다. 코드 블록도 없다. GROUP-070이 이 판정에 걸려 구성 확인 필요로
남아 있는 상태라 같은 실수를 되풀이하지 않으려고 먼저 확인했다.

### 작업 분할

넷으로 나눈 기준은 계층과 파일이다.

1. TASK-S073-01은 상태를 계산하는 쪽이 사유 목록과 사람 판단 필요 상태와 사람 판단 거리를 함께
   내려주게 한다. 기획서 R-07부터 R-10까지와 R-18의 값 부분, R-19와 R-20의 보호가 여기에 걸린다.
   나머지 셋 가운데 둘이 이 값을 읽으므로 맨 앞에 두었다.
2. TASK-S073-02는 아키텍트 역할 계약과 공통 규칙에 구성 오류 기능을 맡는 절차를 적는다. R-13부터
   R-17까지가 여기에 걸린다.
3. TASK-S073-03은 아키텍트 대상 판정에 그 기능을 넣는다. R-11, R-12와 인수 조건 7·8·9가 여기에
   걸린다.
4. TASK-S073-04는 세 화면이 그 값을 사용자 문장으로 보여주게 한다. R-02부터 R-06까지와 R-18의 화면
   부분이 여기에 걸린다.

### 그룹 안 차례

- TASK-S073-03은 TASK-S073-01과 TASK-S073-02 뒤에 둔다. 앞의 것은 판정이 읽는 상태 값을 만들기
  때문이고, 뒤의 것은 계약이 먼저 자리를 잡은 뒤에 대상이 나가야 하기 때문이다. 계약이 없는 상태에서
  대상이 배정되면 세션이 무엇을 고쳐도 되는지 스스로 정하게 된다. 두 작업은 파일이 겹치지 않지만
  이 통합 차례를 지키려고 선행으로 적었다.
- TASK-S073-04는 TASK-S073-01 뒤에 둔다. 세 화면 파일을 두 작업이 함께 선언하므로 겹침이 실제로
  있다.
- TASK-S073-02는 다른 셋과 파일이 겹치지 않고, TASK-S073-03과 TASK-S073-04도 서로 겹치지 않는다.
  겹치지 않는 쌍에는 차례를 붙이지 않았다.

### 그룹 밖 차례

두 자리에 붙였다.

- TASK-S073-01이 고치는 화면 계약 파일을 TASK-S071-03이 함께 선언하고 있다. GROUP-071의 사슬이 이미
  진행 중이므로 그쪽을 먼저 보내고 TASK-S073-01을 뒤에 두었다.
- TASK-S073-04가 고치는 공용 스타일 파일을 TASK-S068-01과 TASK-S071-03이 함께 선언하고 있다. 같은
  이유로 두 작업 뒤에 두었다.

선언하지 않은 겹침이 없는지 지금 끝나지 않은 작업 여덟의 선언과 대조했고, 위 두 자리 말고는 겹치는
경로가 없었다.

## 설계 판단 두 가지

### 자동 대상에서 빠지는 표시를 어디에 두는가

기획서 R-17은 한 번 시도해 풀리지 않으면 같은 구성 버전에서 자동 대상이 되지 않을 것을 요구한다.
그 사실을 앱이 읽을 자리가 지금 없다. 보고서는 프론트매터가 없어 판정이 읽을 수 없고, 결정 문서는
앱 소유라 에이전트가 쓸 수 없다.

기능 문서의 선택 필드로 정했다. 이름은 `configuration_unresolved_revision`이고 값은 그 기능의 현재
구성 버전이다. 근거는 셋이다. 첫째, 기획서 R-15가 아키텍트가 손대는 범위에 기능 문서를 이미 넣었다.
둘째, 앱의 기능 문서 훑기와 조건 검사 스크립트의 기능 문서 훑기가 둘 다 이미 프론트매터를 읽으므로
새 읽기 경로를 만들지 않는다. 셋째, 값이 구성 버전이라 구성 버전이 올라가면 표시가 저절로 풀린다.
사용자가 무엇을 판단해야 하는지는 본문 절 `## 사람의 판단이 필요한 이유`에 적게 했다. 막힌 작업의
사유 절이 이미 같은 방식을 쓰고 있어 규약이 하나로 이어진다.

### 사용자 차례가 된다는 말과 사용자 행동을 늘리지 않는다는 말

기획서 R-01은 사용자가 지금 할 행동이 있는 상태를 사용자 QA 대기 하나로 유지하라고 하고, R-18은
아키텍트가 풀지 못한 기능이 그때 처음 사용자 차례가 된다고 적었다. 두 문장을 다음과 같이 함께
지키기로 정했다.

사람 판단 필요 상태는 화면에 그 사실과 판단할 내용을 보여주되, 홈 화면의 내 선택 대기 목록에 넣지
않고 앱 안에 누를 입구를 새로 만들지 않는다. 읽고 판단할 거리가 생겼다는 뜻이지 앱이 처리할 동작을
요구한다는 뜻이 아니라고 읽었다. 이 판단을 기능 문서의 별도 절과 TASK-S073-04의 완료 조건에 적어
두었으므로, 다른 판단이 맞다면 확인 결과로 돌려보내면 된다.

## 범위 사전 검사

작업 넷 모두 완료 조건이 요구하는 값을 만드는 자리부터 읽는 자리까지 따라가 `## 범위 사전 검사`
절에 적었다. 이번 검사에서 선언 밖으로 나갈 뻔한 자리를 둘 찾았다.

- 표시 상태 값이 하나 늘면 세 화면의 상태 이름 표가 타입 검사에서 걸린다. 상태 계산만 고치면 화면
  쪽 검사가 통과하지 못한다. 그래서 TASK-S073-01의 선언에 세 화면 파일을 넣고, 그 작업이 하는 일은
  이름 한 줄과 정렬 우선순위까지라고 적었다. 사유를 문장으로 푸는 일은 TASK-S073-04가 맡는다.
- 대상 판정은 앱과 조건 검사 스크립트 두 자리에 있고, 두 자리를 대조하는 시험이 이미 있다. 한쪽만
  고치면 그 시험이 반드시 실패하므로 나누지 않고 TASK-S073-03 하나로 묶었다. 이 그룹에서 가장 큰
  작업이고, 그 이유와 나누지 않은 근거를 작업 문서에 적었다.

살펴보고 선언에서 뺀 파일은 각 작업 문서에 이유와 함께 적었다. 대표적으로 프로젝트 요약을 돌려주는
커맨드 파일과 화면 게이트웨이는 기능 요약의 필드를 하나씩 옮겨 담는 자리가 없어 필드가 늘어도 고칠
것이 없고, 파일 계약 문서에는 작업 그룹 프론트매터를 적은 절이 아직 없어 새 선택 필드를 적을 자리가
없다.

## 남는 위험과 후속

- TASK-S073-03의 조건 검사 스크립트 이식이 크다. 확인 절차 인정 판정이 낱말 목록 셋과 줄 단위 명령
  판별로 이루어져 있어 셸과 PowerShell 두 본문에 같은 규칙을 옮겨야 한다. 판정이 갈라지면 화면이
  보여주는 상태와 실제 배정 대상이 어긋난다. 기존 대조 시험이 그것을 붙들지만, 시험이 덮지 않는
  문서 모양이 남을 수 있다.
- 이 그룹이 모두 반영되면 GROUP-070이 첫 자동 대상이 된다. 기획서가 그 기능의 원인을 판정 규칙 쪽으로
  보고 있으므로, 아키텍트가 문서로는 못 고친다고 판단해 사람 판단 필요로 넘길 가능성이 높다. 그
  경우가 R-17과 R-18이 실제로 도는 첫 사례가 된다.
- 판정 규칙 자체를 고치는 일은 이 기획서의 범위 밖이고 IDEA-85EF9AD9에서 나온 별도 기획서가 다룬다.
  그 기획서가 반영되면 GROUP-070이 다른 경로로 풀릴 수 있다.
- 확인 시점에 세 상태의 기능이 하나도 남아 있지 않으면 확인 절차의 둘째 단계부터 볼 것이 줄어든다.
  지금 판에는 구성 확인 필요 하나와 개발 중 여럿이 있고, 이 그룹의 작업이 도는 동안에도 준비 중인
  기능이 계속 생기므로 가능성은 낮다고 보았다.
