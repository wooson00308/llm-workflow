# TASK-128 개발자 핸드오프 (qa_waiting)

## 결정권자 요약

승인이 끝난 기획서 화면에 후속 기획 요청을 보내는 자리가 섰다. 앞 작업이 앱 안쪽에 낸 길을
이제 사용자가 실제로 밟는다.

실수로 눌리지 않게 두 단계를 지나게 했다. 기획서를 열자마자 보이는 것은 여는 버튼 하나뿐이고,
그것을 누르면 무엇이 일어나고 무엇이 일어나지 않는지가 먼저 읽힌다. 코멘트가 비면 기록되지
않는다.

화면이 여는 칸이 앱 안쪽이 허용하는 칸과 같은지 다섯 상태에서 하나씩 대조했다. 승인된
기획서에서는 후속 기획 요청만 열리고 재승인과 폐기는 열리지 않는다.

그리고 그 기획서에 찍힌 도장이 시간순으로 읽힌다. 도장이 하나뿐인 기획서에서도 한 줄로 나온다.
읽기만 하는 자리라 거기서 결정을 고치거나 지울 수는 없다.

지금 필요한 것은 QA 확인이다. 앱을 띄워 승인된 기획서를 하나 열어 보는 일이고, 무엇을 보면
되는지는 작업 문서의 확인 동선에 적어 두었다. 두 게이트 모두 통과한 상태로 넘긴다.

## 바꾼 것

범위 파일 다섯이고, 그중 둘이 새 파일이다.

### 1. 이름 규칙이 한 모듈에 선다 (R5의 단일 출처)

`src/features/projects/domain/specDecisionLabels.ts`를 새로 만들었다. 답하는 질문은 하나다 — 한
기획서의 시각순 결정 목록에서 어느 항목이 후속 기획 요청이고 어느 항목이 수정 요청인가.

```ts
export function specDecisionLabel(kind: string, afterApproval: boolean): string
export function labelSpecDecisions(events: TaskEvent[]): LabeledSpecDecision[]
```

- 판별 근거는 그 항목보다 **앞에** 승인이 있었는가 하나다. `labelSpecDecisions`가 목록을 훑으며
  승인을 만나면 그때부터 그 사실을 켠다. 승인 자신은 자기 뒤부터 근거가 되므로, 뒤에 온 승인이
  앞 항목의 이름을 바꾸지 않는다. 그 성질을 테스트가 따로 고정한다.
- 계약 밖의 `kind`는 값을 그대로 돌려준다. 활동 뷰가 지금 하는 처리와 같은 어법이다.
- 이 작업에서 이 모듈을 쓰는 것은 기획서 화면뿐이다. 활동 뷰와 개발 작업 화면은 TASK-129의 몫이라
  손대지 않았다.

### 2. 화면이 여는 조작이 표를 따른다 (R1)

`SpecWorkspace.tsx`에 표를 함수 하나로 옮겼다.

```ts
function openDecisions(status: string | undefined): SpecDecisionOutcome[] {
  if (status === "user_review") return ["approved", "revision_requested", "rejected"];
  if (status === "approved") return ["revision_requested"];
  return [];
}
```

TASK-127이 쓰기 경로에 세운 판정은
`("user_review", _) | ("approved", SpecDecisionOutcome::RevisionRequested)`이고, 위 함수가 그
조합과 칸 하나까지 같다. 표에 없는 상태는 아무것도 열지 않는다.

`user_review` 분기의 렌더는 한 줄도 건드리지 않았다. 승인·수정 요청·폐기 묶음과 그 코멘트 양식이
지금 그대로이고, 그래서 기존 테스트 아홉이 수정 없이 통과한다.

### 3. 후속 기획 요청 동선 (R3·R4)

승인된 기획서에서만 그려진다. 여는 버튼 하나가 먼저 있고, 누르면 양식이 열린다.

- 양식 맨 위에 R3의 사실 셋이 선다 — 기존 승인 결정은 지워지지 않는다 / 이 기획서에서 나온 개발
  작업은 그대로 진행된다 / 대신 이 기획서가 수정을 요청한 기획으로 바뀐다.
- 그 아래에 확인 문구가 있다: "이 기획서에 후속 기획 요청을 기록합니다. 결정 기록은 되돌릴 수
  없습니다." 개발 작업 QA의 반려 경고와 같은 `confirm-warning` 자리를 쓴다.
- 코멘트가 비면 기록 버튼이 잠긴다. 지금 규칙 그대로다.
- 기록되는 값은 `revision_requested` 그대로다. 새 결정 종류를 만들지 않았다.
- 문서를 바꿔 열면 기존 `useEffect`가 `commentDecision`과 `comment`를 초기화한다. 새 조작이 그
  상태를 그대로 쓰므로 초기화에 자동으로 들어간다.

무장 확인(`useArmedConfirm`)은 걸지 않았다. R4가 요구하는 것은 (가) 열자마자 눌리지 않을 것
(나) 코멘트 필수 (다) 무엇이 일어나는지 말하는 확인 문구 셋이고, 여는 조작과 코멘트가 이미 두
단계다. 승인 버튼에 무장이 걸린 것은 그쪽이 클릭 한 번으로 끝나기 때문이다.

**아키텍트 대기 물량 관련 문장은 적지 않았다.** 작업 문서가 구현자 판단으로 남긴 자리다. 화면이
아는 것은 "이 기획서를 출처로 적은 작업 건수"이고, 확인 사실 7이 말하는 것은 "이 승인 결정을
출처로 적은 작업이 있는가"다. 둘이 같은 값이 아니라서 적으면 앱이 아는 것 이상을 말하게 된다.

### 4. 도장 이력 (R7)

`SpecDecisionHistory`를 같은 파일에 두고 결정 패널 맨 아래에 놓았다.

- 원천은 목록 항목이다. `read_spec`은 이벤트를 채우지 않으므로, 열린 문서와 같은 파일 이름을 가진
  `workflow.items.specs` 항목에서 찾는다. 새 조회도 새 필드도 만들지 않았다.
- 항목마다 이름과 시각이 나온다. 시각은 날짜만으로는 같은 날 찍힌 두 도장이 갈리지 않아 분까지
  적었고, 원문 값은 `time` 요소의 `dateTime`에 그대로 실린다.
- 결정이 하나뿐인 기획서에서도 한 줄로 편다.
- 읽기 전용이다. 그 안에 버튼도 입력도 없다는 것을 테스트가 고정한다.

### 5. 결과 상자 문구 (R7의 비용)

"결정 기록은 원문과 분리되어 보존됩니다."를 **이력이 실제로 서는 기획서에서만** 뺐다. 이력이
그 말을 실물로 대신하므로 같은 사실을 두 자리에서 두 번 말하지 않게 한 것이다.

읽을 결정 이벤트가 없는 결정 완료 기획서에서는 그 문장이 남는다. 없앤 자리를 대신할 것이 없는데
지우면 화면이 더 적게 말하게 되기 때문이다. 두 갈래 모두 테스트가 고정한다.

기록 직후의 "결정 Markdown을 안전하게 저장했습니다."와 `draft`의 안내 문장은 그대로다.

### 6. 방금 찍은 도장의 이름

문서 위에 뜨는 도장이 `specDecisionLabel`을 쓴다. 승인된 기획서에서 기록하면 "후속 기획 요청",
`user_review`에서 기록한 수정 요청은 "수정 요청"이다. 사용자가 방금 "후속 기획 요청 기록"을
눌렀는데 도장이 "수정 요청"이라고 말하는 자리를 남기지 않았다.

이 변경으로 쓰이지 않게 된 `decisionLabels` 상수를 지웠다.

### 7. `App.css`

새로 붙인 자리만 추가했다 — 이력 목록, 사실 셋 목록, 그리고 긴 이름을 받는 도장 하나. 기존
규칙은 고치지 않았다.

## 하지 않은 것

**작업 문서 검증 절차 6번(앱을 띄워 눈으로 확인)을 이 세션은 하지 않았다.** Tauri 창을 띄워도 이

넘겼고, 사용자가 QA에서 실제로 밟는 것이 바로 그 절차다. 동작은 컴포넌트 테스트가 덮지만
**배치와 여백은 덮지 않으므로**, 눈으로 볼 때 그 자리를 함께 봐 주면 된다.

## 남은 위험

- 결정 이력의 시각 표기는 브라우저 표준 시간대를 따른다. 앱이 쓰는 값에는 오프셋이 붙어 있으므로
  UTC로 적힌 옛 결정과 앱이 쓴 결정이 한 목록에 섞여도 같은 기준으로 늘어선다. 다만 화면에 보이는
  시각은 기기의 시간대라, 문서에 적힌 글자와 다르게 보일 수 있다.
- "후속 기획 요청"이라는 이름을 지금 아는 곳은 기획서 화면뿐이다. 활동 뷰는 아직 같은 사건을
  "수정 요청"이라고 부른다. 그 자리는 TASK-129의 몫이고, 그때까지 두 화면의 이름이 갈려 있다.
- 잘못 보낸 후속 기획 요청을 취소하는 길은 여전히 없다. 수정 요청 상태에 결정을 또 얹는 칸이
  막혀 있고, 그것이 기획서가 승인한 선택이다.
