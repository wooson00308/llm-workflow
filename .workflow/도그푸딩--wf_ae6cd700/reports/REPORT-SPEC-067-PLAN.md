# SPEC-067 기획 보고서

## 결정권자 요약

IDEA-E411CA68을 에이전트 화면의 준비 안내 하나와 동의 상시 진입점으로 구체화했다.
남은 준비 단계를 연결, 동의, 켜기 순서로 담은 안내를 화면 위쪽에 하나만 세운다.
실행 권한 동의는 자동 배정이 꺼져 있어도 열 수 있고 고급 설정에서도 기록할 수 있다.
마친 단계는 완료로 표시하고, 세 단계가 모두 끝나면 안내는 사라진다.
동의를 물어볼 수 없는 실행 환경에서는 사유만 보여주고 완료로 다루지 않는다.
고지 문구, 동의 유효성 판정, 세션 시작 조건, 직접 배정 흐름, 자동 배정 토글 자리는 유지한다.
지금 요청하는 것은 SPEC-067의 승인 여부다.

## 대상과 예약 절차

- 역할은 planner이고 대상은 `IDEA-E411CA68` 하나다.
- 런타임이 넘긴 lease `lease-63049-20260818074815`를
  `sh .workflow/rules/wf-claim.sh renew IDEA-E411CA68 lease-63049-20260818074815 30`으로 갱신해 종료
  코드 0을 확인했다. 같은 대상에 `acquire`는 실행하지 않았다.
- 결과 접두어 `RES-20260818T074815Z-63049-20260818074815`는 이 예약을 가리키는 이름으로만 쓰고
  문서 식별자에는 넣지 않았다. 문서 이름은 계보 규칙을 따라 `specs/`에서 쓰이지 않은 가장 낮은
  세 자리 번호인 `SPEC-067`을 골랐다. `SPEC-001`부터 `SPEC-066`까지가 이미 있고 빈 번호는 없다.
- 쓰기 전에 `specs/SPEC-067.md`와 `reports/REPORT-SPEC-067-PLAN.md`가 없음을 확인했다.
- `.workflow/.runtime/migration.lock`은 없다. `.workflow/rules/custom.md`도 없으므로 적용한
  프로젝트 커스텀 규칙은 없다.

## 대상 적격성

- `IDEA-E411CA68`을 `source_idea_id`로 참조하는 기획서는 이 세션 시작 시점에 하나도 없었다.
  미처리 아이디어의 통상적인 경우에 해당한다.
- 갱신 전 lease 파일은 이 예약이 만든 것 하나뿐이었고, 회수할 중단 산출물은 없었다. 따라서
  이 세션은 인수인계가 아니라 신규 처리다.
- 답변되지 않은 `revision_requested` 결정을 먼저 확인했으나 이 세션은 런타임이 아이디어 하나를
  예약해 넘긴 경우이므로, 예약된 대상 하나만 처리했다.

## 작업 순서

1. lease 갱신으로 소유를 확인했다. → 종료 코드 0.
2. 곧바로 `specs/SPEC-067.md`를 `status: draft`와 `source_idea_id`만 담은 골격으로 만들었다.
   → 병렬 세션이 작성 중임을 볼 수 있게 하는 계약 요구다.
3. 아이디어 본문과 관련 제품 코드, 선행 기획서를 읽어 사실을 확인했다.
4. 본문을 작성하고 결정권자 요약 형식과 한국어 규칙을 자체 점검했다.
5. `status: user_review`로 옮기고 `updated_at`을 갱신했다.

## 확인한 사실

원본 아이디어의 주장을 제품 코드에서 직접 확인했다. 기획서 본문의 현재 상태 서술은 아래 사실에
근거한다.

- 동의 배너는 `automationEnabled && consent.status === "required"`일 때만 나타난다
  (`src/features/projects/components/agents/AgentRuntimeView.tsx:150`).
- 자동 배정 토글은 실행 환경 준비가 끝나지 않으면 눌리지 않는다. 켜지지 않은 상태에서
  `readinessOf`의 결과가 `ready`가 아니면 입력이 비활성화된다(같은 파일 147행).
- 새 기기처럼 관리형 서비스가 등록되지 않은 상태는 `자동 배정 서비스 연결 필요`로 판정되어
  `ready`가 아니다(같은 파일 82행). 그래서 토글을 켤 수 없고, 토글을 켤 수 없으므로 동의 배너의
  표시 조건도 만들 수 없다. 아이디어가 말한 "동의로 가는 상시 진입점 없음"이 코드에서 성립한다.
- 고급 설정의 동의 자리는 동의 여부, 동의 시각, 고지 버전, 고지 전문 다시 읽기, 그리고 동의한
  상태에서의 철회만 제공한다. 동의를 기록하는 버튼이 없다(같은 파일 295~300행).
- 직접 배정 확정 창은 동의가 필요하면 고지를 함께 보여주고 `동의하고 직접 배정 시작`으로 끝낸다
  (`src/features/projects/components/agents/AgentRunDashboard.tsx:325`, 336행). 지금 새 기기에서
  동의에 닿는 유일한 경로다.
- 이어질 행동 없이 동의만 남기는 화면이 이미 있고, 그 화면은 설정을 저장하지 않는다
  (`AgentRuntimeView.tsx:234`~255행). 동의 기록 명령도 프로젝트 단위로 실행 환경에 직접 보낸다
  (`src/features/projects/application/useProjectWorkspace.ts:1078`). 따라서 이 기획서가 요구하는
  것은 새 동의 기능이 아니라 기존 동의 화면의 입구를 자동 배정 상태에서 분리하는 일이다.

## 기획에서 정한 것

아이디어가 "구체 배치는 기획에서 정하면 된다"고 위임했으므로 다음을 정했다.

- 안내는 화면 제목 아래, 자동 배정 토글 위에 하나만 세운다. 지금 그 자리의 서비스 안내 배너와
  동의 배너를 대신한다.
- 단계 순서는 연결, 동의, 켜기로 고정한다. 실제 선행 관계와 같은 순서다.
- 마친 단계는 목록에서 빼지 않고 완료로 표시한다. 사용자가 안내 하나만 보고 진행도를 알 수 있어야
  한다는 판단이다.
- 자동 배정 토글은 지금 자리에 유지한다. 준비가 끝난 뒤에도 쓰는 상시 조작이라 안내와 수명이
  다르다. 안내의 세 번째 단계는 같은 확인 창을 여는 또 하나의 입구로 둔다.
- 실행할 수 없는 단계는 지우지도 않고 버튼만 남기지도 않는다. 사유를 그 자리에 적고 버튼을
  제공하지 않으며, 완료로 표시하지 않는다. 어느 쪽도 동의한 것으로 다루지 않는다는 기존 원칙을
  따랐다.

## 남긴 판단과 위임

- 화면 구현 방식, 컴포넌트 분리, 표시 규칙의 코드 배치는 정하지 않았다. 아키텍트와 개발자의
  판단이다.
- 안내가 대신하는 두 배너를 코드에서 제거할지 재사용할지도 정하지 않았다. 요구사항은 화면에서
  보이는 결과만 규정한다.

## 역할 밖 발견 사항

- `specs/`에 결과 접두어를 그대로 식별자로 쓴 기획서 네 건이 있다
  (`SPEC-RES-20260812T124007Z-...` 외 3건). 계보 규칙과 어긋나지만 이미 사용자 검토 단계에 있고
  식별자 보존이 계약이므로 손대지 않았다. 이번 문서는 계보 규칙대로 `SPEC-067`을 썼다.

## 후속과 위험

- 이 기획서는 `user_review`다. 승인 결정 없이 아키텍트 분해로 넘어가지 않는다.
- 승인되면 아키텍트가 작업 그룹 하나로 분해한다. 화면 표시 규칙 변경이므로 실기 검수 항목이
  들어갈 것으로 본다.
- 위험은 안내가 차지하는 세로 공간이다. 지금도 같은 자리를 배너 두 개가 쓰고 있어 증가분은
  단계 하나 분량으로 본다. 실제 측정은 구현 단계에서 확인할 일이다.
