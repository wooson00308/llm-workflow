# TASK-S071-01 개발 보고서

## 결정권자 요약

실행 도구의 사용 한도에 걸려 끝난 실행이 실행 기록에 실려 오면, 앱이 그 사실을 일반 실패와 구분해
받아 어느 실행 도구가 언제 다시 쓸 수 있는지를 사용자 홈 아래 기기 단위 기록으로 남긴다. 해제 예정
시각이 함께 오면 그 시각을 쓰고, 오지 않으면 종료 시각의 한 시간 뒤를 쓰되 두 경우를 기록에서
구별한다. 한도 판정의 근거는 실행 환경이 실은 종료 사유 값 하나이며 실패 메시지 원문을 훑지 않는다.
지금 보류 중인 실행 도구 목록이 실행 목록 응답에 함께 실려, 뒤이을 배정 보류와 화면 표시가 같은
기록 위에서 이루어진다. 자동 검사는 백엔드 884건과 통합 시험 28건, 화면 시험 505건이 모두
통과했고 형식 검사와 정적 분석도 통과했다. 격리 사본에서 통과한 뒤 공유 기준에 통합했고, 통합한
커밋을 깨끗한 사본에서 다시 검사해 같은 결과를 얻었다. 다만 그 재검사 도중 이 세션의 선점이
만료되어 다른 세션이 같은 작업을 넘겨받았으므로, 이 세션은 작업을 verified로 옮기지 않았다.
이 결과는 GROUP-071의 자동 검증 가운데 기록을 만드는 부분을 뒷받침한다.

  통합 판정 전에 따로 낸 문서 전용 커밋이다. 격리 사본의 원본 커밋은 02f6989이며 내용은 같다.
- 남은 일은 이 보고서의 마무리와 작업 문서를 verified로 옮기는 일뿐이다. 코드를 다시 쓸 필요가 없고,
  버릴 잔여물도 없다. 작업 문서의 본문은 손대지 않았고 상태만 in_progress로 옮겨 두었다.
- 이 세션의 선점 lease-64970-20260818095033은 2026-08-18T10:36:32Z에 만료됐다. 전체 재검사 한 번이
  갱신 주기보다 오래 걸린 것이 원인이다. 만료된 선점 파일은 손대지 않았다.
- 예약 식별자는 RES-20260818T095053Z-64970-20260818095033이다.

## 변경한 파일과 모듈

선언한 다섯 파일만 바꿨다(C19). `.workflow` 아래 문서는 이 커밋에 섞지 않았다(C16).

`src-tauri/src/domain/agent_runtime.rs`

- `RunSummary`에 선택 항목 `usage_limit_resets_at`을 더했다. JSON 이름은 `usageLimitResetsAt`이고
  `#[serde(default)]`를 달아 이 키가 없는 실행 행도 지금과 똑같이 읽힌다(C1).
- 한도 도달 구분값 `USAGE_LIMIT_REACHED`와 판정 `RunSummary::reached_usage_limit`을 이 모듈에 두어,
  뒤이을 화면과 조건 검사가 같은 이름을 쓰게 했다. 대조는 전체 일치이고 대소문자를 구분한다(C2).
- `RunState::is_finished`로 끝난 상태 넷을 한 자리에 적었고, 응답이 실을 `ProviderHold`를 더했다.
- 시험: 해제 예정 시각의 왕복과 구형 행에서의 부재, 구분값이 정확히 같을 때만 참인지, 끝난 상태가
  넷뿐인지를 기존 `run_summary_tests` 옆에 넣었다.

`src-tauri/src/infrastructure/provider_hold.rs`(새 파일), `src-tauri/src/infrastructure/mod.rs`

- 기록 자리는 인자로 받은 루트 아래 `provider-holds/<실행 도구 이름>.yml` 하나다. 이 모듈은 홈을
  해석하지 않고 환경 변수도 읽지 않는다(C3).
- `record`가 기록 여섯 줄을 정해진 순서로 쓴다. 시각은 모두 오프셋 표기와 소수 초가 없는 UTC이며,
  조건 검사 스크립트가 비교할 형식을 흔들지 않으려고 직렬화기에 맡기지 않고 직접 조립한다(C4).
- 재개 시각은 해제 예정 시각이 있으면 그 시각이고 없으면 종료 시각의 한 시간 뒤다. 읽지 못한 해제
  예정 시각은 없는 것과 같이 다뤄, 앱이 추정한 시각이 아는 값으로 올라서지 않는다(C5).
- 실행 도구 이름이 정해진 문자 밖의 값을 담으면 경로 자체를 만들지 않아 디렉터리 밖으로 나가는 길을
  막는다(C6). 같은 실행으로 이미 남긴 기록은 다시 쓰지 않고(C8), 이미 지난 재개 시각은 기록을 만들지
  않는다(C9).
- `hold_for`와 `active_holds`는 파일 이름으로 찾은 실행 도구 이름을 쓴다. 본문이 적은 이름을 믿으면
  한 기록이 다른 실행 도구의 보류를 주장할 수 있기 때문이다(C10). 만료된 기록은 보류로 답하지 않고
  파일을 지우지도 고치지도 않으며(C11), 없거나 깨졌거나 형식이 다른 기록과 읽지 못한 디렉터리는 모두
  보류 없음으로 답한다(C12).
- `infrastructure/mod.rs`에 모듈 한 줄을 등록했다.

`src-tauri/src/application/agent_runtime_status_service.rs`

- `inspect`가 보류 기록 루트를 선택 인자로 받는다. 없으면 보류를 읽지도 남기지도 않고 나머지는 그대로
  답한다. `set_paused`는 같은 값을 그대로 넘기고, 진단 번들은 보류가 항목이 아니므로 넘기지 않는다.
- `usage_limit_ends`가 종료 사유·끝난 상태·종료 시각 셋을 모두 만족하는 행만 고르고, 실행 도구마다
  종료 시각이 가장 늦은 행 하나만 근거로 삼는다(C7).
- `QueueSnapshot`에 `provider_holds`를 채운다. 조회 불가 응답에서는 빈 목록이다(C13).
- 시험: 보류가 응답에 실리는지와 없을 때 빈 목록인지, 한도 종료가 아닌 다섯 가지 행에서 파일이 생기지
  않는지, 실행 도구마다 가장 늦은 행이 근거가 되는지, 쓸 수 없는 루트에서도 조회가 성공하는지를 넣었다.

`src-tauri/src/commands/agent_runtime.rs`

- `provider_hold_root`가 `app.path().home_dir()`로 홈을 얻어 `.workflow-labs`를 붙여 넘긴다. 홈을 얻지
  못하면 보류 기록 없이 지금과 같이 조회한다(C15). 홈 해석은 이 계층에만 있다.

## 남은 위험

- 실행 환경이 아직 구분값과 해제 예정 시각을 싣지 않는다. 그래서 이 코드가 실제 한도 상황에서 기록을
  만드는 장면은 사람이 확인한 적이 없고, 검사에서 만든 실행 행으로만 확인했다.
- 기록 파일은 직접 조립한 여섯 줄이고 읽기는 YAML 해석기가 한다. 두 자리가 갈라지지 않도록 본문 전체를
  글자 그대로 대조하는 검사를 넣어 두었다. 뒤이을 조건 검사 스크립트가 이 형식을 읽으므로, 형식을 바꾸면
  그 검사가 먼저 깨진다.
- 실행 식별자에 줄바꿈이나 콜론이 들어오면 기록이 깨질 수 있다. 그 경우 조회가 보류 없음으로 답하므로
  배정이 멈추는 쪽으로는 틀어지지 않는다.
