- `src/features/projects/domain/types.ts` — `WorkflowItemSummary.status` 주석의 파생값을 셋에서 넷으로 고치고 `closed`의 뜻(참조 기획서가 모두 반려로 끝남)을 적었다. 백엔드 `project.rs:112`의 주석과 같은 문장이다.

- `src/App.css` — 새 규칙 두 줄(`.idea-list-icon.closed`, `.idea-state-tag.closed`)만 더했다. 기존 줄은 건드리지 않았다.

## 핵심 결정과 근거

### 판정하지 않고 읽기만 한다

`ideaState`는 백엔드가 실어 보낸 `item.status`를 좁히기만 한다(SPEC-012 R6). 아는 값 넷이 아니면 `inbox`로 떨어뜨리는 기존 폴백을 그대로 뒀다. 모르는 값을 종결로 읽으면 화면이 없는 사실을 말하게 되는데, 종결은 "남은 길이 없다"는 강한 주장이라 폴백의 기본값이 될 수 없다. 이 성질은 테스트로 고정했다.

### 색을 새로 만들지 않았다

pill은 기존 `.status-rejected`를 그대로 쓴다. 목록 아이콘·태그만 반려 계열 색(`#8a3f38` / `#f3dfdc`)으로 `App.css`에 더했고, 이 값은 `.status-rejected`와 `.idea-state-tag.stalled`가 이미 쓰던 값과 같다. 종결과 반려는 같은 계열의 사실이라 새 색을 만들 근거가 없었다.

### 종결 안내가 `idea-stall-note` 클래스를 나눠 쓴다

작업 문서 §2가 "중단 의심 안내와 같은 자리, 같은 모양, 문구만 다르다"고 정했다. 그래서 새 CSS 블록을 만들지 않고 안내 두 개가 `.idea-stall-note` 한 벌을 공유한다. 근거는 둘이다.

1. 모양을 하나의 출처로 묶으면 나중에 한쪽 여백이 바뀌어도 두 안내가 갈라지지 않는다. 블록을 복제하면 9개 값이 두 곳에 남아 드리프트가 생긴다.
2. `.idea-stall-note`의 선택자를 고쳐 이름을 나누는 방법도 있었지만, 그 규칙은 TASK-036의 산출물이고 이 작업의 범위 밖("중단 의심 표시의 문구와 조건은 그대로 둔다")이라 손대지 않았다. `App.css`를 동시에 만지는 세션(dev-049)이 있어 기존 줄 수정을 피하라는 지시도 같은 방향이었다.

클래스 이름이 "stall"이라 종결 안내에 쓰인 이유가 코드만 봐서는 드러나지 않으므로, 두 안내가 배타적이고 자리·모양을 나눠 쓴다는 사실을 TSX에 주석 한 줄로 남겼다.

### 두 안내의 배타성을 화면이 다시 확인하지 않는다

종결과 중단 의심은 함께 뜨지 않는다. 백엔드에서 `stalled_spec_ids`가 채워지는 가지는 `drafting`뿐이고(`fs_project_repository.rs`의 `drafting` 가지가 `closed` 가지보다 앞선다), `closed` 가지는 그 필드를 비운다. 작업 문서가 정한 대로 화면 코드는 이 전제를 다시 검사하지 않고 두 조건을 각각 그대로 쓴다. 테스트에서 종결 아이디어에 "중단 의심"이 없다는 것으로 확인했다.

### 재큐 버튼을 만들지 않았다

DECISION-1224D86C가 확인 필요 1번을 "구분만 한다"로 확정했다. 안내는 문장으로만 재진입 경로를 알린다 — "위 입력창에서 새 아이디어로 요청해야 합니다". 그 입구는 인박스 상단 작성 칸으로 이미 화면에 있다. 자동으로 다시 잡히지 않는다는 사실도 함께 적어 중단 의심 안내와 결을 맞췄다.

## 검증

전부 프로젝트 루트에서 실행했고 넷 다 통과했다.

| 명령 | 결과 |
| --- | --- |
| `npm run check` | 통과 (typecheck + 14개 파일 319 테스트 + build) |
| `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check` | 통과 |
| `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings` | 통과 (exit 0) |
| `cargo test --manifest-path src-tauri/Cargo.toml` | 통과 (352 passed, 0 failed) |

`IdeaInbox.test.tsx`는 19건에서 23건이 됐다. 늘어난 넷은 다음과 같다.

- `tags a closed idea in the list row` — 종결 아이디어의 목록 행에 "종결" 태그가 뜨고 아이콘이 `closed` 분류를 받는다. (기획서 완료 조건 18)
- `points a closed idea at the new idea path` — 미리보기 pill이 "종결"이고, 안내가 모두 반려로 끝났다는 사실과 새 아이디어 경로를 말한다. 중단 의심은 없다. (완료 조건 4)
- `keeps the closed marking off an adopted idea` — 채택 아이디어에는 종결 태그도 안내도 없다. (기획서 완료 조건 19)
- `reads an unknown state as the inbox state` — 모르는 상태 문자열은 수집됨으로 읽히고 목록 태그가 붙지 않는다. (완료 조건 3)

반영중·수집됨·중단 의심의 기존 표시는 기존 테스트 다섯 건이 수정 없이 통과하는 것으로 확인했다. (기획서 완료 조건 22)

## 리스크

- 동시 세션의 일시적 빨간불 하나를 관측했다. 첫 clippy 실행에서 `dead-code`(`-D warnings`)로 lib test 컴파일이 한 번 실패했는데, 재실행에서 exit 0으로 돌아왔다. 백엔드를 만지는 다른 세션의 편집 도중 상태를 스냅샷한 것으로 보인다. 이 작업은 Rust 파일을 하나도 바꾸지 않았고 최종 실행 넷은 모두 통과했다. 기록만 남긴다.
- `App.css`를 dev-049가 동시에 편집한다. 이 작업은 새 규칙 두 줄만 더했고 기존 줄을 고치지 않았으므로 충돌 면이 없다. 다만 최종 시각 확인은 두 변경이 함께 있는 트리에서 해야 한다.
- 종결 안내가 `.idea-stall-note` 클래스를 공유한다. 나중에 두 안내의 모양을 다르게 하고 싶어지면 그때 클래스를 나눠야 하고, 그 편집은 TASK-036 산출물을 건드리므로 별도 범위가 필요하다.
- 이 저장소에 반려 결정은 아직 하나도 없다(SPEC-018 확인 사실 21번). 실물 종결 아이디어가 없으므로 사용자 QA는 픽스처나 손으로 만든 반려 상태에서 해야 한다.

## 사용자 QA 제안

1. 반려로 끝난 아이디어를 하나 만든다. 아이디어 하나를 참조하는 기획서를 두고, 그 기획서의 최신 결정이 반려가 되게 한 뒤(그 아이디어를 참조하는 다른 살아 있는 기획서가 없어야 한다) 인박스를 연다. 목록 행에 붉은 계열 "종결" 태그와 서류함(archive) 아이콘이 붙는지 본다.
2. 그 아이디어를 선택한다. 미리보기 오른쪽 위 배지가 "종결"(반려 계열 색)이고, 제목 아래 안내가 "기획서가 모두 반려로 끝났습니다 / 자동으로 다시 잡히지 않는다 / 새 아이디어로 요청" 셋을 말하는지 본다. 재큐 버튼이 없는 것이 정상이다.
3. 안내가 시키는 대로 인박스 상단 작성 칸에서 새 아이디어를 넣어 본다. 새 항목이 "수집됨"으로 들어오고, 종결 아이디어는 종결 그대로 남는지 본다.
4. 승인까지 간 아이디어("채택")와 기획서를 쓰는 중인 아이디어("반영중")를 나란히 놓고 셋이 색·라벨·아이콘으로 구분되는지 본다. 채택 아이디어에 종결 안내가 뜨면 안 된다.
5. 중단 의심 아이디어를 열어 기존 안내가 그대로인지 본다. 한 아이디어에 두 안내가 동시에 뜨면 안 된다.
6. 종결 표시가 파이프라인을 되돌리지 않는지 본다. 종결 아이디어만 남은 상태에서 기획자 잡이 그 아이디어를 다시 집지 않아야 한다(기획서 완료 조건 20의 화면 쪽 확인).
