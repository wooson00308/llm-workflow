# TASK-S056-01 개발 보고서

## 결정권자 요약

품질 확인 대기 카드의 미리보기를 그 문서의 확인 동선 첫 문단으로 바꿨다.
확인 동선 절이 없거나 첫 문단이 비어 있으면 지금까지의 발췌를 그대로 보여주고 앱이 대신 문장을 만들지 않는다.
제목이 계약의 문자열과 문자 단위로 같을 때만 절로 인정하며 코드 울타리 안의 같은 줄은 제목으로 세지 않는다.
대기가 아닌 카드와 아이디어·기획서 카드의 표시는 변경 전과 같고 분류 딱지나 색 구분도 생기지 않는다.
요약 구조의 필드를 그대로 써서 도메인과 명령 계층과 프런트엔드는 한 줄도 바뀌지 않았다.
목록 조회는 이미 읽은 본문에서 값을 하나 더 뽑을 뿐이라 파일을 더 열지 않는다.
검사 617개와 프런트엔드 851개가 통과했고 사용자는 TASK-S056-01 확인 동선대로 목록에서 세 경우를 보면 된다.

## 변경 파일과 모듈

- `src-tauri/src/infrastructure/fs_project_repository.rs`: 목록 요약을 만드는 자리에서 문서 상태가 품질
  확인 대기일 때만 확인 동선 첫 문단을 미리보기 값으로 쓰고, 그 밖의 모든 경우는 기존 발췌를 그대로
  쓴다. 절과 문단을 판정하는 함수를 더했고, 발췌와 미리보기가 같은 길이 한도를 쓰도록 자르기 규칙을
  한 곳으로 모았다. 확인 동선 제목은 개발자 계약이 고정한 문자열을 상수로 읽기만 한다.
- 다른 파일은 바꾸지 않았다. 요약 구조의 필드 구성이 그대로라 명령 계층과 프런트엔드가 수정 없이 그대로
  동작한다.

## 검증 절차와 결과

- `cargo test --manifest-path src-tauri/Cargo.toml` 통과: 617 passed, 0 failed. 직전 611개에 이 작업의
  검사 여섯 개가 늘었다.
- `npm run check` 통과: 타입 검사 성공, 25개 파일 851 tests 통과, 배포 빌드 성공. 프런트엔드는 한 줄도
  바꾸지 않았고 그대로 통과한다.
- `cargo clippy --all-targets` 경고 없음, `cargo fmt` 적용.
- 한 픽스처에 확인 동선이 있는 대기 문서 둘, 없는 대기 문서, 대기가 아닌 문서를 함께 두고 미리보기 네
  값을 표로 대조했다. 화면이 있는 작업은 어디에서 무엇을 보는지가, 화면이 없다고 적은 작업은 그 문장이
  카드 값으로 나온다. 아이디어와 기획서는 확인 동선 절을 넣어도 발췌 그대로다.
- 제목 철자 변경, 제목 깊이 변경, 제목 안팎의 공백 변경, 제목 뒤 덧말, 코드 울타리 안의 같은 제목을
  각각 넣어 모두 절로 인정되지 않는 것을 확인했다.
- 첫 문단이 한 줄인 경우와 여러 줄인 경우, 절이 비어 있고 곧바로 다음 제목이나 코드 울타리가 오는 경우,
  절 아래에 아무것도 없는 경우를 확인했다. 여러 줄은 한 줄로 이어지고, 비어 있으면 발췌로 되돌아간다.
- 200자 문단으로 자르기를 확인했다. 161자에서 말줄임표로 끝나며 기존 발췌의 한도와 같다.
- 미리보기를 만드는 함수는 본문 문자열 하나만 받는다. 부르는 자리도 이미 읽어 둔 같은 본문을 넘기므로
  조회가 파일을 더 열지 않는다. 조회가 워크플로 파일을 건드리지 않는 기존 검사도 함께 통과한다.
- `git diff --stat`으로 제품 변경이 범위 파일 하나뿐임을 확인했다. 규칙 문언 파일에는 변경이 없고 네
  버전 상수도 18과 11과 11과 13 그대로다.
- 이 작업 문서의 확인 동선 절에 같은 판정 규칙을 적용해 카드에 실릴 문장을 미리 확인했다. 81자이므로
  잘리지 않고 그대로 나온다.

## 남은 리스크

- 앱은 확인 동선 문장을 검사하지도 보완하지도 않는다. 절을 부실하게 적은 작업은 카드도 그만큼 부실하게
  보이며, 그것은 문서의 상태이지 표시의 결함이 아니다.
- 첫 문단이 코드 울타리로 시작하는 확인 동선은 미리보기를 만들지 않고 기존 발췌로 되돌아간다. 명령 줄을
  카드 문구로 싣지 않으려는 선택이며, 그런 작업의 카드는 지금과 같은 발췌를 보여준다.
- 문서 상세를 여는 경로도 같은 요약을 만들므로 그 값의 미리보기 필드도 함께 바뀐다. 상세 화면은 이 필드를
  그리지 않아 보이는 변화는 없지만, 나중에 상세에서 이 필드를 쓰면 같은 값이 실린다는 뜻이다.

## 후속 작업

- 확인 방식을 화면 확인형과 수치 신뢰형으로 가르는 표시는 만들지 않았다. 승인 범위 밖이며, 필요해지면
  분류의 근거를 누가 정할지부터 정해야 한다.
- 프런트엔드는 이 변경으로 손댈 곳이 없었다. 카드가 받는 값이 달라졌을 뿐 그리는 방식은 그대로다.
