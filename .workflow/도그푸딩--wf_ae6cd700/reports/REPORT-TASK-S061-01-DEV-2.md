# TASK-S061-01 개발 보고서 2

## 결정권자 요약

사이드 메뉴의 기획서 메뉴와 품질 확인 메뉴에 지금 사용자의 결정을 기다리는 건수가 숫자로 붙었고,
지금 보고 있지 않은 워크플로우에 기다리는 결정이 있으면 그 이름 옆에 점이 붙는다. 기다리는 일이
없으면 숫자도 점도 그려지지 않아 사이드 메뉴는 이전과 같은 모습이다. 화면 읽기 도구를 쓰는 사용자도
버튼 이름만 듣고 어떤 메뉴에 몇 건이 밀려 있는지 알 수 있다. 앞선 세션을 막았던 지시서 모순은
아키텍트가 해소했고, 이번 세션은 그 세션이 격리 사본에 남긴 구현을 이어받아 다시 쓰인 조건에 맞춘 뒤
공유 작업 공간에 반영했다. 자동 검사는 격리 사본과 통합 후 양쪽에서 모두 통과했다. 사용자가 지금
확인할 것은 없다. GROUP-061은 남은 작업 하나가 끝나야 사용자 품질 확인 단계로 넘어간다.

## C11 적용 결과

전체 검사를 돌려 실제로 깨진 줄을 먼저 확인했다. 깨진 줄은 체리픽 후 파일 기준 228, 293, 529, 609행
네 개이고, 작업 문서가 예고한 네 자리와 같다(체리픽이 앞에 import 한 줄을 더해 번호가 1씩 밀렸다).
목록 밖에서 깨진 줄은 없었다. 네 줄 모두 아래 한 형태로 바꿨다.

`within(screen.getByRole("navigation", { name: "주요 메뉴" })).getByRole("button", { name: /^품질 확인/ })`

접근 이름이 `주요 메뉴`인 영역으로 범위를 좁힌 뒤 그 안에서 접근 이름이 `품질 확인`으로 시작하는 버튼
하나를 고른다. 조회 문자열에 건수 값이 들어가지 않으므로 검사 자료가 바뀌어 건수가 달라져도 같은 줄이
계속 그 버튼을 가리킨다. 단언, 기대값, 검사 자료, 검사 이름, 검사 순서는 하나도 바꾸지 않았다.

## 남은 위험

- 실제 앱을 띄워 눈으로 본 것은 아니다. 배지가 붙은 상태의 메뉴 폭과 긴 워크플로우 이름의 말줄임
  동작은 검사 환경에서만 확인했다. 사람이 보는 확인은 GROUP-061의 사용자 품질 확인이 맡는다.
- 접근 이름을 형제 노드 이어붙이기로 만들었으므로 쉼표를 뺀 채 문구를 고치면 "기획서승인 대기"처럼
  붙어 읽힌다. 코드에 그 이유를 주석으로 남겼다.
- `pendingDecisions`는 사이드 메뉴 화면 안의 판정만 모은다. 같은 조건식이 품질 확인 작업대와 개발
  화면에도 각각 남아 있고, 그 정리는 이 작업의 범위가 아니다.
