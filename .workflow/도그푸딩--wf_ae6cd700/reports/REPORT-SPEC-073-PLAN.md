# SPEC-073 기획자 핸드오프

## 결정권자 요약

런타임이 예약한 아이디어 하나를 이어받아, 앞선 세션이 뼈대만 남기고 멈춘 기획서 SPEC-073을 같은
식별자로 완성해 사용자 검토 대기로 올렸다. 기획서는 사용자가 손댈 수 없는 기능 문제 상태를 상태
이름만으로 보여주지 않고 문제와 처리 주체와 사용자 몫 없음을 함께 밝히는 범위, 그리고 처리 주체가
없던 구성 확인 필요 상태에 아키텍트 자동 처리 경로를 만드는 범위를 정한다. 판정 기준 자체를 고치는
일은 IDEA-85EF9AD9 계열의 몫이라 경계로 명시했다. 사용자가 할 일은 이 방향과 범위, 그리고 이 문서가
정한 기본값 넷을 보고 승인하거나 수정 요청을 남기는 것이다.

- 역할: 기획자 (planner)
- 대상: IDEA-FC871690 (사용자 행동이 없는 문제 상태를 과제처럼 보여주지 않으려는 요구)
- 산출 기획서: SPEC-073 (status: user_review, 인계받은 기존 초안)
- 예약: 런타임 예약 대상 IDEA-FC871690, lease `lease-22680-20260818131019`, 결과 prefix
  `RES-20260818T131019Z-22680-20260818131019`
- 세션: 2026-08-18T13:20Z ~ 13:29Z

## 무엇을 했나

런타임이 예약한 대상 하나만 처리했다. `sh .workflow/rules/wf-claim.sh renew IDEA-FC871690
lease-22680-20260818131019 60`으로 소유를 먼저 확인했고(exit 0), `acquire`는 부르지 않았다. 본문을
쓰기 전 조사 구간 중간에 한 번 더 갱신했다(exit 0). 작업 시작 시점에 `.workflow/.runtime/migration.lock`
은 없었고, `.workflow/rules/custom.md`도 없어 적용할 프로젝트 커스텀 규칙이 없었다.

소유 확인 직후 대상 상태를 눈에 보이게 만들었다. 이 대상은 새 기획서를 여는 경우가 아니라 인계였으므로,
역할 계약의 인계 절차대로 기존 `specs/SPEC-073.md`의 `updated_at`만 갱신해 작성 재개를 표시한 뒤 본문을
작성했고, 완성 후 `user_review`로 올렸다.

## 인계 판단

`specs/`에서 `source_idea_id: IDEA-FC871690`을 참조하는 문서는 SPEC-073 하나였고 `status: draft`였다.
문서는 frontmatter와 H1 제목, 그리고 "작성 중입니다." 한 줄이 전부였다. 만들어진 시각은
2026-08-18T11:21:19Z로 아이디어가 등록된 11:20:13Z 직후이며, 그 세션의 lease는 이미 만료돼 대상이 다시
예약 가능해진 상태였다. 즉 앞 세션이 뼈대를 만든 직후 멈춘 잔여물이다.

인계 판단은 다음과 같이 갈랐다.

- 유지: 문서 식별자 SPEC-073, `source_idea_id`, `created_at`. 역할 계약은 버려진 초안을 같은 문서에서
  이어 쓰라고 정하고 있고, 새 식별자는 사용자가 읽고 돌려보낸 개정에만 쓴다. 이 초안은 아무도 읽지
  않았고 붙은 결정도 없다.
- 다시 씀: 본문 전체. 남아 있던 것은 "작성 중입니다." 한 줄뿐이어서 이어 쓸 판단이나 사실이 없었다.
- 버림: 없음. 코드 작업 트리에 남은 변경도 없었다. 기획자 세션이라 격리 사본을 쓰지 않았고 제품 코드를
  건드리지 않았다.

버린 시험은 없다. 이 세션은 시험 파일을 만들지도 지우지도 않았다.

## 대상 선택

인계 대상이 이미 예약돼 있었으므로 선택 여지는 없었다. 참고로 같은 시점에 SPEC-072가 IDEA-85EF9AD9를
참조하는 초안으로 존재하고 그 아이디어의 lease는 유효했다. 다른 세션이 진행 중인 대상이라 손대지
않았다.

## 기획서가 정한 것

- 사용자 행동이 없는 문제 상태 셋(구성 확인 필요, 구성 중단 의심, 개발 막힘)은 상태 이름과 함께 문제,
  처리 주체, 사용자 몫 없음을 목록 자리에서 보여준다.
- 구성 확인 필요는 판정 조건 다섯 갈래를 한 이름으로 합쳐 보여주고 있으므로, 어떤 조건에 걸렸는지를
  사유로 함께 내려주고 화면은 그것을 옮기기만 한다.
- 구성 확인 필요 기능은 아키텍트 자동 대상이 된다. 같은 기능 식별자와 구성 버전을 유지하며, 한 번
  시도해 풀리지 않으면 자동 대상에서 빠지고 사용자 판단으로 올라온다.
- 기본값 넷: 설명을 붙이는 대상 상태 셋, 사유의 목록·상세 배치, 아키텍트 대상 순서(사용자 확인 반려
  다음, 작업 정의 오류 수정 앞), 재시도 없이 한 번 시도 후 사용자 판단으로 넘김.

## 조사에서 확인한 사실

기획서의 현황 서술은 다음을 읽고 썼다.

- 기능 표시 상태를 계산하는 자리는 `src-tauri/src/infrastructure/fs_project_repository.rs`의 3200번대
  분기다. 구성 확인 필요로 답하는 조건은 문서 필수 값 결함, 구성 버전에 속한 작업 없음 또는 작업의 출처
  불일치, 사용자 확인 모드인데 절차가 없거나 절차가 사용자 행동으로 인정되지 않음, 자동 확인 모드인데
  절차가 있음, 끝나지 않은 작업 잔존의 다섯 갈래다.
- 상태 이름을 화면에 올리는 자리는 셋이다. `src/features/projects/components/DevelopmentBoard.tsx`,
  `src/features/projects/components/qa/QaWorkbench.tsx`,
  `src/features/projects/components/SpecWorkspace.tsx`. 세 곳 모두 상태 이름 한 낱말만 보여주고 사유를
  담는 자리가 없다.
- 사용자 행동 입구는 사용자 QA 대기 상태에만 붙는다. 홈 화면의 내 선택 대기 목록도 기획서 승인과 이
  상태만 담는다.
- 아키텍트 대상 판정은 `src-tauri/src/infrastructure/role_eligibility.rs`에 있고, 사용자 확인 반려,
  작업 정의 오류, 준비 중 중단, 승인된 새 기획서 넷을 본다. 구성 확인 필요는 어느 조건에도 들어가지
  않는다. 구성 중단 의심은 준비 중 중단 조건으로, 개발 막힘은 개발자의 막힌 작업 복구로 이미 처리
  주체가 있다.

## 경계와 후속

- 판정 기준 자체를 고치는 일은 이 기획서 범위 밖이다. 자연스러운 한국어 관찰 서술이 사용자 확인 절차로
  인정되지 않는 문제는 IDEA-85EF9AD9에서 나온 별도 기획서(작성 시점 SPEC-072 초안)가 다룬다. 두 기획서가
  모두 승인되면 사용자 확인 절차 판정과 그 판정 결과의 표시가 같은 코드 근처를 건드릴 수 있다. 작업
  분해 시점에 범위 겹침을 확인해야 한다.
- GROUP-070의 확인 절차 문장을 지금 판정 규칙에 맞게 고치는 개별 조치는 아키텍트 몫으로 남아 있다.
  이 기획서는 그 개별 조치를 대체하지 않는다.
- 기획서 요구 R-18은 아키텍트가 문서 쪽에서 고칠 수 없다고 판단한 사실이 화면까지 닿아야 한다고 정한다.
  앱은 이미 `reports/`의 보고서를 읽어 실행과 연결하고 있으므로 닿을 길은 있으나, 어떤 값으로 그 사실을
  전달할지는 아키텍트가 정한다.

## 역할 경계

- 작업 그룹, 개발 작업, 제품 코드는 만들지도 고치지도 않았다.
- 결정 문서를 만들거나 고치지 않았고, 승인·반려·폐기를 대신 기록하지 않았다.
- 앱 소유 상태 파일(`project.yml`, `workflow.yml`, `.workflow/.runtime/`)을 직접 쓰지 않았다. lease는
  관리 헬퍼로만 다뤘다.
- 구현 방식은 정하지 않았다. 어떤 값으로 사유를 내려보낼지, 화면 어느 요소에 붙일지, 대상 판정을 어디에
  더할지는 아키텍트 몫이다.

## 마무리

기획서는 `user_review`다. 사용자 승인이 기록되기 전에는 이 범위로 작업을 분해하지 않는다. 이 보고서를
쓴 뒤 같은 lease를 반납한다.
