- 산출: GROUP-066 (`status: active`, `qa_mode: user`, `revision: 1`), TASK-S066-01, TASK-S066-02

## 요약

승인된 기획서 하나를 작업 그룹 하나와 개발 작업 둘로 나눴다. 경계는 기획서의 요구 묶음이 아니라
저장소에서 함께 움직여야 하는 코드 단위로 잡았다. 첫 작업이 앱이 읽어 오는 기능 설명 값을 만드는
규칙을, 둘째 작업이 그 값을 화면에 그리는 규칙을 맡는다.

두 작업 사이에는 순서를 두지 않았다. 파일이 겹치지 않고, 어느 쪽이 먼저 끝나도 화면이 지금보다
나빠지지 않는다. 대신 첫 작업에는 그룹 밖 순서가 셋 붙는다. 같은 저장소 읽기 파일을 고치는
TASK-S065-01, TASK-S065-02, TASK-S063-01이다.

확인 방식은 사용자 확인으로 정했다. 이 그룹이 바꾸는 결과가 전부 앱 화면에서 눈으로 판별되고,
확인에 필요한 두 가지 문서 형태가 이미 저장소에 함께 있어 사용자가 상태를 만들 필요가 없다.

## 대상 선택과 소유 확인

런타임이 예약한 대상 하나만 처리했다. `wf-claim.sh renew DECISION-82640432
lease-42305-20260818074719 30`으로 소유를 먼저 확인했고(exit 0), `acquire`는 부르지 않았다. 첫
호출에서 셸 실행 권한이 없어 스크립트를 직접 실행하지 못했고, 인자를 플래그 형태로 준 두 번째
호출은 사용법 오류로 돌아왔다. 도우미가 요구하는 위치 인자 형태로 고쳐 확인을 마쳤다. 작업 도중
두 번 더 renew했고 모두 exit 0이었다.

대상 적격성을 claim 뒤에 다시 확인했다. DECISION-82640432은 SPEC-066에 대한 앱 기록 승인이고,
`decisions/`에서 SPEC-066을 대상으로 하는 결정은 이 하나뿐이므로 최신 승인이 맞다. `groups/`
전수 확인 결과 SPEC-066이나 이 결정을 참조하는 작업 그룹은 없었다. 우선순위가 더 높은 대상도
없었다. 현재 구성 버전이 반려된 그룹, 정의 오류로 막힌 작업, 중단된 준비 중 그룹 중 어느 것도
확인되지 않았다. 인계받을 중단 잔여물은 없었고, `.workflow/rules/custom.md`는 존재하지 않아
프로젝트 커스텀 규칙은 적용하지 않았다. `.workflow/.runtime/migration.lock`도 없었다.

claim 확인 직후 GROUP-066을 `status: preparing`으로 만들어 아키텍처 진행이 화면에 보이게 했고,
작업 문서를 모두 쓴 뒤에 `active`로 올렸다.

식별자는 계보 규칙대로 잡았다. 기획서 번호를 따 GROUP-066과 TASK-S066-01, TASK-S066-02로 했다.
세 경로 모두 쓰기 전에 비어 있는지 확인했고 덮어쓰기 금지 상태로 만들었다. 보고서 경로도 같은
방식으로 확인했다. 결과 prefix는 이 보고서에만 적었고 문서 식별자에는 넣지 않았다.

## 코드에서 확인한 것

기획자 보고서가 적어 둔 사실을 그대로 받지 않고 저장소에서 다시 확인했다. 결과가 작업 경계를
정했다.

- 값을 만드는 자리는 하나다. `src-tauri/src/infrastructure/fs_project_repository.rs` 3226행의
  `parse_work_group_body`가 기능 설명 문자열과 확인 플로우 시나리오와 시나리오 구조 유효성을 한
  반복문에서 함께 만든다. 기능 설명을 모으는 조건은 3260행 한 줄이며, 문서 제목과 `## 기능 설명`
  제목 줄만 거르고 나머지를 전부 넣는다.

- 값이 지나는 길은 네 hop이고 전부 무변경이다. 3114행 호출부, 3208행 구조체 조립,
  `src-tauri/src/domain/project.rs` 307행의 `description: String`,
  `src/features/projects/domain/types.ts` 195행의 `description: string`이다. 타입이 문자열로
  유지되므로 값의 내용을 바꾸는 변경은 이 hop들을 건드리지 않는다. 그래서 첫 작업의 선언이
  파일 하나로 닫혔다.

- 값을 읽는 자리는 셋이다. `QaWorkbench.tsx` 83행의 목록 카드, 같은 파일 130행의 확인 화면
  머리말, `WorkspaceShell.tsx` 854행의 완료 기록 화면 기능 상세다. 기획자가 확인한 세 자리와
  같다. 셋 다 값이 비었을 때 요소를 그리지 않는 조건을 이미 달고 있어서, 기획서 R5는 새로
  구현할 것이 없고 값이 빈 문자열이 되게 하는 것으로 충족된다.

- 셋이 쓰는 스타일 클래스는 둘뿐이고 같은 파일에 있다. `QaWorkbench.css` 16행의
  `.qa-queue-goal`과 31행의 `.qa-feature-goal`이다. 저장소 전체에서 이 두 이름을 쓰는 자리가
  그 셋뿐임을 확인했다. 그래서 둘째 작업은 화면 구성 파일을 고치지 않고 스타일 선언 둘만
  고치면 된다. 이 확인이 둘째 작업의 선언을 두 파일로 줄였다.

- 줄 수 상한 어법의 선례가 저장소에 이미 있다. `src/App.css` 412행과 640행이 `-webkit-box`와
  `-webkit-line-clamp` 조합을 쓴다. 새 어법을 들이지 않고 그 형태를 그대로 쓰도록 완료 조건에
  적었다.

- 스타일 선언을 확인할 수 있는 시험 자리도 하나뿐이다.
  `src/features/projects/components/qa/qaWorkbenchAlignment.test.ts`가 CSS 원문을 읽어 선택자별
  선언을 확인한다. 화면 시험은 스타일 시트를 적용하지 않으므로 줄 수 상한과 줄바꿈 처리를
  확인하지 못한다. 그래서 둘째 작업의 검증을 이 파일에 걸었다.

- 기능 설명 값을 읽는 다른 판정은 없다. `role_eligibility.rs`와 `heartbeat_condition.rs`는 기능
  문서에서 상태와 확인 방식과 구성 버전만 본다. 셸 본문과 앱 판정이 같은 답을 내야 하는 종류의
  변경이 아니다.

- 새 규칙을 저장소의 기능 문서 62건에 직접 적용해 봤다. 소개가 비는 문서 0건, 소개 길이 최소
  33자 최대 350자, 소개가 두 문단 이상인 문서 3건, 소개 안에 목록이나 인용이나 표를 쓴 문서
  0건이다. 기획자가 59건으로 잰 값과 어긋나지 않으며, 그 뒤에 늘어난 3건도 같은 결과였다.

## 판단한 것

기획자가 아키텍트 몫으로 넘긴 선택이 둘 있었다. 둘 다 정했고 근거를 작업 문서에 적었다.

- 소개를 어느 단계에서 잘라 낼지는 값을 만드는 단계로 정했다. 화면 단계에서 자르면 같은 규칙을
  세 자리가 각각 갖거나 공용 함수를 새로 만들어야 하고, 무엇보다 문서 본문의 뜻을 해석하는 지식이
  두 층으로 갈린다. 값을 만드는 함수가 이미 확인 플로우 절을 갈라내고 있으므로, 내부 절을
  갈라내는 일도 같은 자리에 두는 것이 맞다.

- 세 줄 상한을 문자열 자르기가 아니라 스타일 선언으로 처리하기로 했다. 문자열로 자르면 몇 글자가
  한 줄인지 화면 폭에 따라 달라지는 것을 코드가 알 수 없고, 상세 화면이 쓸 전체 값과 카드가 쓸
  잘린 값이 갈라진다. 스타일 선언으로 처리하면 값 하나를 세 자리가 그대로 쓰고 카드에서만 상한이
  걸린다.

이 두 판단에 따라 문단 구분을 값에 실어 나르기로 했다. 첫 작업이 소개를 문단 단위로 정리해서
한 문단 안의 줄은 공백으로 잇고 문단 사이는 빈 줄로 남긴다. 둘째 작업이 상세 자리에 빈 줄을
살리는 선언을 건다. 정리 없이 원문 줄바꿈을 그대로 살리면 문서가 100자 안팎에서 손으로 줄을
바꿔 둔 자리마다 화면에서도 줄이 끊겨 들쭉날쭉해진다. 정리 결과를 카드가 쓰면 줄바꿈이 공백으로
접혀 한 줄기로 이어지므로, 카드가 문단 구분을 살리지 않는다는 기획서 요구도 같은 값으로 함께
충족된다.

## 순서 판단

첫 작업이 고치는 저장소 읽기 파일을 지금 열려 있는 작업 셋이 함께 고친다. TASK-S065-01(진행 중),
TASK-S065-02, TASK-S063-01이다. 셋 다 첫 작업의 선행으로 적었다. 셋이 이미 서로 순서가 매겨져
있어 마지막 하나만 적어도 결과는 같지만, 겹치는 상대를 문서에서 바로 읽을 수 있도록 셋을 모두
적었다. TASK-S063-01이 같은 이유로 선행 둘을 모두 적은 것과 같은 방식이다.

둘째 작업은 어떤 열린 작업과도 파일이 겹치지 않아 선행을 두지 않았다. 첫 작업과도 두지 않았다.
둘째 작업만 끝난 상태에서는 카드가 지금 값 그대로 세 줄에서 끊겨 지금보다 짧아지고, 상세 자리는
문서의 원래 줄바꿈이 보이게 된다. 둘 다 지금 상태보다 나쁘지 않다. 순서를 둘 이유가 없어서
두지 않았고, 그 대신 둘째 작업의 완료 조건을 값의 내용에 기대지 않는 것들로만 적었다.

## 범위 사전 검사에서 뺀 것

두 작업 모두 값 경로를 끝까지 따라간 뒤 선언에서 뺀 파일과 그 근거를 작업 문서에 적었다. 요지는
둘이다.

- 첫 작업: 도메인 구조체와 화면 타입과 세 화면 파일을 뺐다. 필드 이름과 타입이 그대로이므로 값을
  무변경으로 나르는 hop이다. 판정 파일 둘은 이 값을 읽지 않는다.
- 둘째 작업: 화면 구성 파일 둘을 뺐다. 필요한 클래스 이름과 빈 값 처리를 이미 갖추고 있어 고칠
  것이 없다. 화면 시험 파일 둘도 뺐다. 스타일 시트를 적용하지 않아 이 변경을 확인하지 못한다.

## 후속과 리스크

- 세 줄이라는 상한은 기획서가 정한 값이고 사용자가 확인에서 다르게 판단할 수 있다. 그 경우 반려로
  돌아오며, 고칠 자리는 스타일 선언 하나라 다음 구성 버전의 수정 작업이 작다.
- 카드에서 잘린 뒷부분을 읽는 길은 시작을 눌러 들어가는 것 하나다. 확인 플로우에 그 동선을 5단계로
  넣어 사용자가 잘림을 확인한 직후에 전체를 보게 했다.
- 첫 작업은 선행 셋이 끝나야 시작된다. 그중 하나가 지금 진행 중이므로 이 그룹의 완료 시점은 그
  줄의 진행에 달려 있다. 둘째 작업은 그와 무관하게 지금 시작할 수 있다.
- 아키텍트 작성 지침을 한 형태로 모으는 일은 기획서가 제외 범위로 적었고 이 그룹도 다루지 않는다.
  새 아이디어가 필요한 사안이며, 아이디어를 만드는 것은 사용자의 자리다.
- 역할 경계에서 넘기지 않은 것: 기획서와 결정 문서는 읽기만 했고 고치지 않았다. 제품 코드는 한
  줄도 건드리지 않았다. 작업은 둘 다 `status: todo`로 두었다.
