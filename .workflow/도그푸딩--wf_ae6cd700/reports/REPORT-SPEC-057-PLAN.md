# SPEC-057 기획 보고서

## 결정권자 요약

막힌 작업 재개가 비개발자에게 요구하는 작문을 없애는 기획을 해결 수준 두 가지로 정리했다.
수준 1은 재개 관문을 유지하되 근거 입력을 작문에서 채택으로 바꾼다.
수준 2는 수준 1을 포함하며, 정의 오류로 분류되고 수리 기록이 있고 한도 안일 때 앱이 자동 재개한다.
수준 2는 SPEC-054와 SPEC-055가 명시적으로 금지한 자동 재개를 여는 개정이라 규칙 버전 상승이 따른다.
사용자가 못 보는 것을 묻지 않는다는 점에서 두 피드백은 같은 방향이며 그 논거를 코드로 확인했다.
막히지 않은 작업은 이미 사용자 조작 없이 자동 배정되므로 재개 버튼이 비용 동의 지점은 아니다.
지금 요청하는 것은 현행 유지와 수준 1과 수준 2 중 하나를 고르는 결정이다.

## 대상 선택과 절차

- IDEA-71859B73을 처리했고, TL이 전달한 같은 날 후속 피드백을 같은 기획서에 반영했다.
- 첫 합성으로 SPEC-057을 `user_review`에 올린 뒤 확장 브리프를 받아 같은 문서를 고쳐 썼다. 문서에
  기록된 사용자 결정이 없음을 먼저 확인했고(SPEC-057을 가리키는 결정 문서 없음), 선점을 다시 잡고
  작업했다. 새 식별자를 만들지 않은 이유는 이 문서가 아직 사용자에게 판단받지 않았기 때문이다.
  새 식별자는 수정 요청 결정에 답할 때 쓰는 것이고 여기에는 그 결정이 없다.
- SPEC-054와 SPEC-055 문서는 수정하지 않았다. 무엇이 대체되는지는 SPEC-057 안에 적었다.

## 실측 (2026-08-08, 메인 체크아웃 직접 확인)

- 해결 근거는 쓰기 전용이다. `task_resume_event`는 감사 문서 frontmatter의 `task_id`, `created_at`,
  `outcome`만 읽어 타임라인 항목을 만든다(`fs_project_repository.rs:2428`). 본문에 저장된 사용자
  문장을 다시 읽는 경로가 없다. 사용자가 강제로 쓴 문장이 앱 안에서 다시 보이지 않는다.
- 그런데 화면 안내는 "적은 문장이 그대로 기록에 남고 앱이 대신 만들지 않습니다"이다
  (`BlockedTaskPanel.tsx:209`). 남는다는 말은 맞지만 다시 읽히지 않는다는 사실은 안내에 없다.
- 검증은 세 가지뿐이다. `fs_project_repository.rs:1200` 부근에서 공백 제거 후 빈 값과 2,000자 초과를
  거절하고 요청 식별자를 확인한다. 본문은 별도 처리 없이 문서에 삽입된다.
- 재개 전 판정과 원자성은 이미 있다. 막힘 상태 확인, 갱신 시각 문자 단위 대조, 미만료 lease 거절,
  요청 식별자 멱등, 부분 실패 시 되돌리기와 복구 필요 결과가 모두 구현돼 있다. 자동 재개는 이 계약을
  그대로 소비할 수 있다.
- 비대칭이 코드로 확인된다. 앱이 관리하는 개발자 역할 작업은 실행 조건이
  `sh .workflow/rules/wf-eligible.sh developer`이고(`heartbeat_status.rs:647`), 그 스크립트는 개발
  준비 또는 진행 중 상태의 작업이 있으면 자격 있음을 돌려준다(`heartbeat_condition.rs:498`, `593`).
  막힌 작업은 후보가 아니다. 즉 개발 준비가 되면 사용자 조작 없이 세션이 시작되므로, 유료 세션 동의는
  이미 배정 루프에 있고 재개 버튼이 그 동의를 대신하고 있지 않다. 이것이 수준 2의 정합성 논거다.
- 앱은 보고서 디렉터리의 파일 개수만 세고(`fs_project_repository.rs:2452` 부근) 본문을 읽는 명령이
  없다. 그래서 아키텍트 보고서 인용은 후보에서 뺐고, 인용 원천은 앱 소유 기록과 작업 문서로 한정했다.
- SPEC-055 R1의 차단 원인 분류는 네 값(작업 정의 오류, 선행 계약 누락, 구현 실패, 외부 의존)이며 값이
  없는 문서는 분류되지 않음으로 읽는다. 수준 2의 첫 조건이 이 값이다.
- 금지 문언 위치를 확인했다. SPEC-054 R8 "blocked 재개는 사용자만 실행한다", SPEC-054 범위 밖
  "에이전트나 Heartbeat가 blocked 작업을 자동 재개하는 기능", SPEC-055의 자동 재개 불허 문장 네 곳,
  사용자 문서 `docs/file-contract.md:243` "blocked에서 나오는 경로는 사용자 재개 하나뿐이다".

## 기획 결정

- 두 수준을 한 문서에 담고 결정 요청에서 현행 유지까지 세 선택지로 제시했다. 수준 2는 수준 1을
  포함한다. 자동 재개 조건에 맞지 않는 막힘이 모두 수준 1의 채택 경로로 가기 때문이다.
- 자동 재개 조건을 세 개로 좁혔다. 분류가 작업 정의 오류일 것, 연결된 정의 수정 처리 기록이 있을 것,
  자동 재개 횟수가 한도 안일 것. 셋 다 앱이 확인할 수 있는 사실이며 앱이 판단을 창작하지 않는다.
- 핑퐁 방지 한도를 작업당 두 번으로 정했다. 관측된 재개는 작업마다 한 번이고 반복 사례가 아직 없다.
  한 번이면 아키텍트 수리가 한 번에 맞지 않는 경우가 곧바로 사람에게 넘어가 효과가 사라지고, 세 번
  이상이면 같은 작업에 유료 세션을 태우는 시간이 길어진다. 관측값보다 한 번 여유를 둔 값이다.
- 자동 재개 기록의 작성자 값을 사용자 재개와 구분하도록 요구했다. 사용자가 하지 않은 일을 사용자
  기록으로 남기면 이 기획서가 고치려는 문제를 다시 만드는 것이기 때문이다.
- 수준 1에 "재개 근거를 앱 안에서 다시 읽을 수 있어야 한다"를 요구사항으로 넣었다. 쓰기 전용 필드는
  현행 유지 선택지의 비용이기도 해서 결정 요청과 현재 절에 함께 적었다.
- 규칙 문언 변경은 수준 2에만 붙는다. 수준 1은 관리 자산을 건드리지 않으므로 규칙 버전 상승이 없다.

## 검증

- 위 실측을 모두 원문에서 직접 읽었다. TL이 전달한 측정 결과 가운데 줄 번호는 작업 트리 상태에 따라
  달라서, 함수와 문자열로 다시 찾아 확인한 값을 보고서에 적었다.
- SPEC-057의 결정권자 요약이 구조화 형식을 지키는지 확인했다. 일곱 하위 제목이 순서대로 한 번씩 있고,
  영향 범위 아래 두 표식이 한 번씩 있으며, 요약 안에 역따옴표와 파일 경로와 식별자가 없다.
- 사용자 피드백 두 개를 배경 절에 원문으로 인용했다.
- 앱 소유 상태와 결정 기록은 읽기만 했다. 기존 기획서 문서는 수정하지 않았다.

## 인계 사항

- 구현 순서: 수준 2는 SPEC-055의 분류와 정의 수정 처리 기록에 의존하므로 TASK-S055-01과 02 뒤에 온다.
  TASK-S055-04와는 화면 파일이 겹쳐 동시 진행이 불가하다.
- 감사 기록에 인용과 사용자 메모를 구분해 담는 방법, 자동 재개 기록의 스키마 이름은 아키텍트가 정한다.
  기획서는 사용자 재개 기록의 뜻을 바꾸지 않는다는 경계만 고정했다.
- 승인 전에는 구현하지 않는다.
