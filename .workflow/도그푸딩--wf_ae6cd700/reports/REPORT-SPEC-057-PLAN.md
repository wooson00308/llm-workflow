# SPEC-057 기획 보고서

## 결정권자 요약

막힌 작업 재개에서 사용자가 해결 근거를 직접 쓰는 방식을 채택 방식으로 바꾸자고 기획했다.
앱이 이미 가진 사실만 근거 후보로 모아 보여 주고, 사용자는 확인한 항목을 골라 재개를 승인한다.
감사 기록에는 고른 항목의 출처와 원문이 남고, 자유 입력은 선택 메모로만 남는다.
앱은 재개 조건의 충족 여부를 판정하지 않는다. 그 판정까지 하면 자동 재개가 되기 때문이다.
근거 후보가 없는 막힘에서는 지금처럼 사용자 입력을 필수로 남긴다.
관리 규칙과 역할 계약은 바뀌지 않으므로 규칙 버전 상승 연쇄는 없다.
지금 요청하는 것은 SPEC-057의 승인 여부다.

## 대상 선택

- 사용자 피드백에서 나온 IDEA-71859B73을 처리했다. 이 아이디어를 참조하는 기획서는 없었다.
- 아이디어 하나만 선점해 작업하고 반납했다. 앱 코드와 다른 문서는 변경하지 않았다.
- 이 세션은 앞서 SPEC-056을 만든 planner 세션이며, 첫 선점을 반납한 뒤 두 번째 대상을 새로 선점했다.
  기획자 계약은 한 세션이 대상 하나를 처리한다고 적고 있고 공통 규칙은 선점마다 하나로 적고 있어,
  둘이 어긋나는 자리다. 동시에 두 대상을 잡지 않는다는 성질은 지켰으나 판단 근거를 남겨 둔다.

## 조사와 실측 (2026-08-08)

- 앱이 기록한 재개는 두 건이다. RESUME-546E6381(TASK-S052-01), RESUME-68EA1C33(TASK-S051-04).
  TASK-S051-06은 아직 `blocked`이고 `resumed` 이력이 없다. 아이디어가 적은 "재개 3건"은 실제로는
  두 건이며 기획서에는 실측값을 적었다.
- 두 기록의 본문은 개발 용어로 된 여러 문장이고 아키텍트 보고서 식별자와 QA 반려 식별자를 인용한다.
  비개발자가 그 자리에서 쓸 수 있는 문장이 아니라는 아이디어의 전제는 문서로 확인된다.
- `fs_project_repository.rs:1200` 부근에서 해결 근거를 앞뒤 공백 제거 후 검사한다. 비어 있으면
  거절하고 2,000자를 넘으면 거절한다. 검사 이름은 `task_resume_requires_a_resolution_and_a_request_id`
  이며 공백만 있는 값과 2,001자를 모두 거절한다.
- `fs_project_repository.rs:1244` 부근에서 감사 기록을 만든다. 본문은 `request.resolution.trim()`
  그대로이고 frontmatter는 작업 식별자, 결과, 요청 식별자, 재개 직전 갱신 시각, `created_by: user`,
  생성 시각이다. 즉 본문 저자와 제출자가 같다고 기록되는 구조다.
- 같은 함수가 상태 확인, 갱신 시각 문자 단위 대조, 미만료 lease 거절, 같은 요청 식별자 재호출의
  멱등 처리를 이미 수행한다. 이 안전장치들은 기획서에서 유지 대상으로 못박았다.
- 앱은 `reports/` 디렉터리의 파일 개수만 센다(`fs_project_repository.rs:2452`). 보고서 본문을 읽어
  화면에 보여 주는 경로는 없다. 그래서 아키텍트 보고서 인용은 근거 후보에서 제외했다.
- 관리 규칙(`project_instructions.rs:229`)은 재개 기록의 스키마와 작성자 값만 정하고 본문을 사용자가
  직접 써야 한다고 요구하지 않는다. 본문을 입력 원문으로 한정한 문장은 `docs/file-contract.md:326`에
  있고 그 파일은 관리 자산이 아니다. 따라서 규칙 버전 상승 연쇄가 없다.
- SPEC-055는 DECISION-22C3CC2F로 승인됐고 네 작업으로 분해돼 있다. TASK-S055-01은 `in_progress`,
  나머지 셋은 `todo`다. TASK-S055-04는 "재개 조작의 동작"과 "막힌 사유 절의 표시 규칙"을 손대지
  않는다고 명시하므로, 이 기획서가 다루는 구간과 겹치지 않는다.
- 다만 TASK-S055-04의 `scope_files`가 재개 화면 파일(`BlockedTaskPanel.tsx`, `DevelopmentBoard.tsx`,
  `useProjectWorkspace.ts`, `types.ts`, `tauriProjectGateway.ts`)을 포함한다. 구현은 동시에 진행할 수
  없다는 사실을 기획서에 적었고 순서 결정은 아키텍트에게 넘긴다.

## 감사 관점의 검증 결과

아이디어의 "출처 명시형 인용이 가장된 사용자 작성보다 감사 충실도가 높다"는 주장을 두 축으로 나눠
검증했고, 조건부로 성립한다고 판단했다.

- 출처 추적 축에서는 성립한다. 지금 기록은 본문의 저자를 말하지 않고, 본문 안의 보고서 식별자조차
  에이전트가 적어 넣은 것이다. 채택 방식은 무엇을 근거로 삼았는지를 기록의 구조로 남긴다.
- 사용자 이해 증명 축에서는 두 방식이 같다. 어느 쪽도 이해를 증명하지 못한다. 다만 지금 방식은
  이해했다는 인상을 만들고 채택 방식은 사용자가 실제로 한 일을 그대로 적는다.
- 그래서 기획서는 "감사 충실도가 올라간다"를 출처 추적 축으로 한정해 적었고, 재개 관문이 사용자
  이해를 보증한다고 주장하지 않는다.

## SPEC-054 문언과의 관계

- "해결 근거는 비어 있을 수 없다"는 유지된다. 검사 대상이 입력 문자열에서 고른 항목의 존재로 바뀔
  뿐이고, 근거 없이 재개할 수 없다는 성질은 같다.
- "앱이 사실 여부를 지어내지 않는다"도 유지된다. 앱은 이미 있는 문서와 자기 소유 기록의 값을 옮기고
  출처를 적을 뿐이며, 주장하는 범위는 "이 기록이 존재하고 이렇게 적혀 있다"까지다.
- 바뀌는 것은 SPEC-054 R8과 R9가 전제한 근거의 형태다. 그 두 요구는 근거를 사용자가 입력하는 값으로
  적었고 이번 기획서는 사용자가 채택하는 값으로 바꾼다. 이 변경을 결정 요청에 포함했다.

## 검증

- IDEA-71859B73을 참조하는 기획서가 없음을 확인한 뒤 선점하고 SPEC-057을 만들었다.
- 위 실측을 모두 코드와 문서 원문에서 직접 읽었다. 아이디어에 적힌 재개 건수는 실측과 달라 기획서에
  실측값을 적었다.
- SPEC-057의 결정권자 요약이 구조화 형식을 지키는지 확인했다. 일곱 하위 제목이 순서대로 한 번씩
  있고, 영향 범위 아래 변경과 유지 표식이 한 번씩 있으며, 요약 안에 역따옴표, 파일 경로, 식별자가
  없다.
- 앱 소유 상태와 결정 기록은 읽기만 했다.

## 인계 사항

- 구현 순서: TASK-S055-04와 화면 파일이 겹치므로 동시 진행 금지다. SPEC-055의 정의 수정 요청 기록이
  구현되면 같은 규칙으로 근거 후보에 들어오지만, 이 기획서는 그 기록이 없어도 동작하도록 썼다.
- 감사 기록에 인용과 사용자 메모를 구분해 담는 방법은 아키텍트가 정한다. 기획서는 스키마 이름과
  작성자 값을 바꾸지 않는다는 경계만 고정했다.
- 승인 전에는 구현하지 않는다.
