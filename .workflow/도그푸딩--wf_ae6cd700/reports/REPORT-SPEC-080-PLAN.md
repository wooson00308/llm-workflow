# SPEC-080 기획자 핸드오프

## 결정권자 요약

런타임이 예약한 수정 요청 DECISION-35B8F64E를 처리해 기획서 SPEC-080을 새로 쓰고 사용자 검토
대기로 올렸다. 수정 요청은 SPEC-078에 "어휘가 맘에 안들어유" 한 줄이었고, 지적 대상은 용어이지
기능이 아니었다. 그래서 SPEC-078의 요구사항 R1~R13, 제외 범위, 완료 판정 기준 A1~A13을 그대로
유지하고 표기만 바꿨다. 곁 영역은 사이드바와 패널로, 글줄 폭은 읽기 폭으로, 화면 낭독기는 스크린
리더로 바꾸는 등 11개 항목의 용어 대응표를 문서 안에 남겨 사용자가 바뀐 자리를 바로 확인할 수 있게
했다. 사용자가 할 일은 용어가 이제 맞는지 보고 승인하거나 다시 수정 요청을 남기는 것이다.

## 세션 정보

- 역할: 기획자 (planner)
- 대상: DECISION-35B8F64E (SPEC-078 수정 요청, outcome revision_requested, created_by user)
- 산출 기획서: SPEC-080 (status: user_review, 새로 만든 문서)
- 예약: 런타임 예약 대상 DECISION-35B8F64E, lease lease-78100-20260819141521, 결과 prefix
  RES-20260819T141521Z-78100-20260819141521
- 세션: 2026-08-19T14:15Z ~ 14:21Z

## 진행 절차

1. 예약받은 lease로 `wf-claim renew DECISION-35B8F64E lease-78100-20260819141521 30`을 호출해
   소유를 확인했다. 종료 코드 0. `acquire`는 부르지 않았다.
2. `.workflow/.runtime/migration.lock`이 없고 `.workflow/rules/custom.md`도 없음을 확인했다.
   적용할 프로젝트 커스텀 규칙이 없다.
3. 적격성을 확인했다. `spec_id: SPEC-078`을 가진 결정 문서는 DECISION-35B8F64E 하나뿐이므로 이
   결정이 최신이다. `source_decision_id: DECISION-35B8F64E`를 참조하는 기획서는 없었다.
4. `.workflow/.runtime/silent-runs/`를 확인했고 이 대상을 가리키는 기록이 없었다. 인계할 잔여물이
   없어 인수 판단은 필요하지 않았다.
5. 계보 규칙에 따라 쓰이지 않은 가장 낮은 세 자리 번호가 080임을 확인하고(specs에 001~079 존재),
   경로가 비어 있는 것을 확인한 뒤 `status: draft`와 세 source 참조만 담은 뼈대를 먼저 만들었다.
6. 본문을 작성한 뒤 `status: user_review`로 올리고 `updated_at`을 갱신했다.

## 수정 요청을 어떻게 읽었는가

수정 요청 본문은 "어휘가 맘에 안들어유" 한 줄이다. 기능 범위, 너비 값, 요구사항 항목에 대한
언급이 없다. 그래서 이 세션은 SPEC-078의 기획 판단은 사용자가 문제 삼지 않은 것으로 읽고, 표기만
고쳤다.

지적의 근거는 문서 밖에도 있다. 공통 규칙 v35 9절이 "통용 외래어는 한국어"라고 정하고 사이드바,
패널, 드래그, 토글, 스크린 리더를 그 예로 든다. SPEC-078은 그 통용어 자리에 새로 만든 표현을 썼고,
곁 영역 하나만 24곳에 나온다. 규칙이 금지하는 대체가 문서 전체에 걸쳐 있었다.

## 용어 대응

기획서 본문에 대응표로 남겼다. 11개 항목이며 각 항목마다 근거를 붙였다.

- 곁 영역 → 패널 (공통 규칙 9절, SPEC-006·SPEC-008·SPEC-053이 이미 쓰는 이름)
- 왼쪽 주 메뉴 → 사이드바 (SPEC-006·SPEC-011)
- 경계를 끌다 → 드래그 (공통 규칙 9절, IDEA-1D88D8F8이 쓴 조작 개념)
- 조절 경계 → 리사이즈 핸들
- 두 번 연속 클릭 → 더블클릭
- 글줄 폭 → 읽기 폭 (SPEC-076)
- 화면 낭독기 → 스크린 리더 (공통 규칙 9절, SPEC-052)
- 마우스를 올렸을 때의 안내 → 툴팁
- 머리글 → 헤더
- 픽셀 → px (SPEC-076 표기)
- 저장소 → 브라우저 저장소 (SPEC-006·SPEC-019·SPEC-061 표기)

새 용어를 고를 때 이 워크플로우의 기존 기획서를 먼저 뒤졌다. 사이드바, 패널, 읽기 폭, 스크린 리더,
브라우저 저장소는 전부 다른 기획서가 이미 쓰고 있는 이름이라 새로 정한 값이 아니다. 리사이즈 핸들,
더블클릭, 툴팁, 헤더는 기존 기획서에 용례가 없었고, 공통 규칙 9절이 말하는 통용 외래어로 골랐다.

## 용어 밖에서 손댄 두 곳

둘 다 SPEC-078이 정한 범위를 넓히지 않으며, 기획서 본문에도 같은 내용을 적어 두었다.

1. SPEC-078 R3은 더블클릭으로 "기본 너비"에 돌아간다고 정했는데 기본 너비 값은 사이드바(250px)에만
   적혀 있었다. 나머지 세 패널의 기본 너비는 R11이 말하는 비율 배치 너비라는 문장을 R3과 적용 범위
   표에 명시했다. 새 값을 만들지 않았다.
2. SPEC-078의 저장 실패 처리 근거에 "그 실패로 화면이 뜨지 않는 쪽이 훨씬 나쁘다"가 있었다. 공통
   규칙 9절이 이 형태의 극적 비교를 그대로 예시로 들어 금지하므로, "저장 실패가 화면 렌더링을 막는
   것을 방지한다"는 사실 진술로 바꿨다.

## 검증

- 문서 전체에 em dash가 없다. 해당 문자로 grep한 결과 0건.
- 결정권자 요약에 backtick 토큰, 파일 경로, 식별자가 없다. 문서 전체에 backtick 0건.
- 결정권자 요약은 빈 줄을 뺀 9줄이다. 상한 10줄 안이다. 소제목은 제안, 바뀌는 것, 비용과 위험
  순서로 각각 한 번씩이고, 바뀌는 것은 불릿 3개, 비용과 위험은 불릿 2개다.
- 대응표에 옛 용어를 인용한 자리를 빼면 본문에 곁 영역, 화면 낭독기, 글줄 폭, 픽셀, 주 메뉴가
  남아 있지 않다.
- 요구사항 개수 13개, 완료 판정 기준 개수 13개로 SPEC-078과 같다.

## 사용자가 결정할 것

- 바뀐 용어가 이제 맞는지. 이 문서가 답한 것은 그 지적 하나다.
- SPEC-078에서 판단을 보류했던 항목이 있다면 지금도 유효하다. 적용 대상 네 영역과 품질 확인 화면
  제외, 읽기 폭 상한을 620px에서 최대 860px까지 올리는 R8, 접힘 표시를 폭 28px 세로 바로 정한 것이
  그 셋이다. 이 세션은 이 판단들을 바꾸지 않았다.

## 다음 역할에 넘기는 사항

- SPEC-078 핸드오프가 아키텍트에게 넘긴 사항은 그대로 유효하다. 저장 실패를 삼키고 기본값으로
  그리는 R7은 기획서 레인 접힘 상태 저장소가 이미 쓰는 처리 방식과 같고, 저장 단위만 다르다. 그
  저장소는 워크플로 디렉터리별로 나누지만 R6은 컴퓨터 하나에 하나로 저장하라고 정한다.
- R13이 말하는 980px 배치 전환 규칙은 지금 화면이 이미 갖고 있다. 리사이즈 핸들을 그 폭 이하에서
  숨기는 처리만 새로 필요하다.
- 구현 단계에서 쓸 UI 용어는 이 기획서의 대응표를 따른다. 작업 문서와 구현 보고서가 곁 영역 계열
  표현으로 되돌아가면 같은 지적이 다시 나온다.

## 역할 밖 발견 사항

- SPEC-078은 status가 `user_review`인 채로 남는다. 이 문서를 대체하는 것은 SPEC-080이지만, 기획자
  계약은 기존 기획서를 보존하라고 정하므로 손대지 않았다. SPEC-078을 정리할지는 사용자의 판단이다.
- 소스 아이디어 IDEA-1D88D8F8 본문에도 "곁 영역" 표현이 두 곳 있다. 아이디어 문서는 사용자가 직접
  쓰는 문서 종류이고 공통 규칙 9절의 적용 대상이 아니므로 고치지 않았다.

## 남는 위험

- SPEC-078과 SPEC-080이 같은 아이디어를 참조하는 기획서로 둘 다 남는다. 아키텍트가 어느 쪽으로
  작업 그룹을 만드는지는 사용자의 승인 도장이 결정한다. 승인이 SPEC-080에 찍히지 않은 상태에서
  구현이 시작되면 옛 용어 기준으로 작업이 만들어진다.
- 용어만 바꿨다는 판단 자체가 이 세션의 해석이다. 사용자의 수정 요청이 용어 밖의 무언가를 함께
  가리킨 것이었다면 이 문서는 그 부분을 답하지 못한다. 그 경우 다시 수정 요청으로 돌아온다.
