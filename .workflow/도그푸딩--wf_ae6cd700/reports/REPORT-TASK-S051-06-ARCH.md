# TASK-S051-06 아키텍트 수리 보고서

## 결정권자 요약

앱이 설치를 판단하려면 알아야 하는 사실을 기계가 읽을 방법이 없어 개발이 멈춰 있었다.
그 사실이 어디에서 어떤 모양으로 오는지를 작업 문서에 확정했다.
제공하는 쪽은 TASK-147이며 선행 작업으로 추가했다.
운영체제 서비스 파일과 런타임 데이터베이스를 앱이 직접 읽지 않는다는 경계를 완료 조건으로 세웠다.
설치·실행 버전 구분, 확인 불가와 권한 부족 구분, 업데이트 영향 수치의 출처도 조건으로 못 박았다.
사용자가 품질 확인에서 요구한 조회 명령과 TASK-147의 계약이 갈라지지 않아야 한다는 점을 적었다.
상태는 막힘 그대로 두었고 이력에도 아무 항목을 넣지 않았다.
재개 시점은 사용자가 앱에서 직접 결정한다.

## 차단 사유와 수리 대응

REPORT-TASK-S051-06-DEV가 적은 차단 사유는 하나다. 현재 런타임 계약은 프로젝트 하나의 설정과 상태만
읽을 수 있어서, 설치된 버전, 실제 실행 중 버전, 서비스 등록·실행 상태, 복구 가능 여부, 업데이트가
영향을 줄 실행을 기계가 읽는 방법이 없었다. 그 세션은 계약 밖 상태 파일이나 운영체제 서비스 파일을
직접 읽으면 소유 경계가 깨지고, 사람이 읽는 출력 문장을 해석하면 플랫폼과 버전 변화에 판단이 흔들린다는
위험도 함께 남겼다.

### 문서 수리

`## 런타임에서 받는 사실` 절을 새로 넣어 앱이 받는 값을 네 묶음으로 확정했다. 근거는 TASK-147 문서의
기계 계약 절과 그 완료 조건이다.

- 기기 조회에서 받는 값: 설치 버전, 실행 중 버전, API 주 버전, target과 서비스의 등록·실행 여부,
  식별자, 실행 경로, 마지막 확인 시각, 복구 가능 여부, 확인 출처. 확인한 값과 확인하지 못한 값과 권한
  때문에 확인할 수 없는 값이 구분돼 온다는 점, 오래된 PID로 실행 중 판정이 오지 않는다는 점을 적었다.
- 업데이트 계획에서 받는 값: 대상 버전과 검증 결과, launcher·서비스 전환 필요 여부, 실행 중 작업 수와
  프로젝트 목록, 그리고 계획 식별자가 지문이라는 사실.
- 적용 결과에서 받는 값: 다섯 단계의 단계별 결과, 지문 불일치 시 0단계 중단, 부분 실패의 현재 실행
  가능 버전과 복구 행동, 세 운영체제 공통 코드.
- 앱이 스스로 가지는 것: 번들 resource와 해시 검증, 지원 API major와 버전 범위 상수, 사용자 확인 절차와
  계획 식별자 보관. 런타임이 주지 않는 부분을 분명히 갈라 두어야 개발 세션이 경계를 헷갈리지 않는다.

바꾼 것이며 새 요구가 아니다.

검증 절차에도 두 단계를 더했다. 가짜 런타임 응답으로 등록 없음, 정상 실행, 확인 불가, 권한 부족, 중복

## 판단 근거

### TASK-147을 선행으로 추가한 이유

차단 사유가 요구하는 사실 전부를 한 곳에서 제공하는 작업이 TASK-147이다. 그 문서의 기계 계약은 기기
조회, 업데이트 계획, 단계별 적용과 복구를 모두 정의하고, 완료 조건 10번은 앱이 SQLite와 plist와 unit
파일과 Task Scheduler 출력을 직접 파싱할 필요가 없어야 한다고 못 박는다. 이 작업의 백엔드 계약 여섯
항목이 그 응답 위에서만 성립한다.

사용자 품질 확인 기록 QA-7C6AA0E3도 같은 요구를 남겼다. TASK-S051-05에 설치 버전, 실행 중 버전, 서비스
등록 상태, 복구 가능 여부를 한 번에 돌려주는 기계 판독용 조회 명령을 추가하라는 수정 요청이며, 목적을
"TASK-S051-06 차단 사유 해소"라고 명시했다. 다만 그 요청은 조회 부분만 덮고, 업데이트 계획의 전체 실행
영향과 단계별 적용·복구는 TASK-147의 범위다. 그래서 조회만으로는 이 작업의 백엔드 계약 2번부터 6번까지를
채울 수 없다고 판단해 TASK-147을 선행으로 넣었다.

순환은 없다. TASK-147의 선행은 TASK-S051-02와 TASK-S051-05이고, 이 작업은 이미 TASK-S051-05를 선행으로
갖고 있었으므로 대기 구조가 새로 깊어지지도 않는다.

### 두 조회가 갈라질 위험

QA-7C6AA0E3의 재작업과 TASK-147이 각각 조회 명령을 만들면 같은 사실을 말하는 명령이 두 개가 된다. 그
경우 이 작업이 어느 쪽을 읽어야 할지 문서만으로 정할 수 없다. 그래서 `범위와 선행`에 앱은 TASK-147이
확정한 계약 하나만 사용한다고 적었다. TASK-S051-05를 재작업할 개발 세션이 조회를 먼저 만들면 TASK-147은
그 명령을 확장하는 편이 맞고, 두 번째 명령을 새로 만드는 것은 피해야 한다. 다만 TASK-S051-05와 TASK-147
문서는 이 세션의 대상이 아니므로 고치지 않았다. 인계 사항으로 남긴다.
