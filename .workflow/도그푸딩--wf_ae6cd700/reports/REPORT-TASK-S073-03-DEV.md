# TASK-S073-03 개발 보고서

## 결정권자 요약

구성 확인 필요로 판정된 기능이 이제 아키텍트가 자동으로 맡는 대상 목록에 들어간다. 자리는 사용자
확인 반려 다음이자 작업 정의 오류 수정 앞이며, 이미 잡혀 있는 기능은 선점 규칙에 걸려 두 세션이
같은 기능을 잡지 않는다. 아키텍트가 문서로는 못 고친다고 남긴 기능은 사람 판단 필요로 갈라져 다시
나가지 않는다. 판정 조건 자체는 넓히지도 좁히지도 않았고, 화면이 쓰는 상태 계산을 그대로 읽는다.
앱과 조건 검사 스크립트 두 자리가 같은 답을 내야 해서 한 작업에서 함께 고쳤고, 두 자리를 함께
돌려 대조하는 기존 시험이 이 작업이 더한 상황에서도 통과한다. 백엔드 시험 911건과 통합 시험
28건, 화면 시험 566건이 통과했고 형식 검사와 생산 빌드도 통과했다. 이 결과는 GROUP-073의 자동
검증 가운데 구성 오류를 아키텍트가 자동으로 맡게 하는 부분을 뒷받침한다.

## 바꾼 파일과 모듈

- `src-tauri/src/infrastructure/role_eligibility.rs` — `architect_workflows_verdict`에 단계를
  하나 더했다. 표시 상태가 `ConfigurationError`인 기능을 파일 이름 차례로 보고, 기능 식별자·출처
  승인 식별자·출처 확인 결정 식별자 셋 가운데 하나라도 미만료 선점에 걸리면 후보로만 적는다.
  대상 종류 상수 `CONFIGURATION_ERROR_KIND`를 더했다. 표시 상태는 `WorkflowInput`의
  `items.work_groups`에 이미 실려 오므로 경유 자리는 손대지 않았다.
- `src-tauri/src/infrastructure/heartbeat_condition.rs` — 셸 본문에 `scan_configuration_errors`,
  PowerShell 본문에 `Get-ConfigurationErrorGroups`와 그 딸림 함수들을 더하고, 두 본문의
  `architect` 절 같은 자리에 같은 단계를 넣었다. 판 번호를 24로 올리고 두 본문의 주석 줄도 함께
  올렸다.

스크립트 두 본문은 앱이 이미 계산해 둔 표시 상태를 받을 수 없어 그 사슬 자체를 옮겨 담았다. 그래서
새 훑기가 기능·작업·결정 세 디렉터리를 한 번에 읽고, 기능 문서에서 확인 모드·최종 변경 시각·확인
절차 본문·구성 미해결 표시를 함께 내며, 그 기능에 속한 작업의 상태와 세 연결 값을 대조하고, 그룹
확인 결정과 과거 작업 확인 결정의 최신 판정까지 같은 훑기에서 고른다. 확인 절차가 사용자 행동으로
인정되는지 보는 판정도 낱말 목록 셋과 명령 줄 판독을 그대로 옮겼다.

설계 판단 두 가지를 적어 둔다. 첫째, 한글 어미 변화를 견디는 낱말 대조를 앱처럼 음절을
초성·중성·종성으로 풀어 비교하는 대신, 그 비교와 결과가 같은 형태로 옮겼다 — 앞 음절은 정확히
같아야 하고 마지막 음절은 낱말에 종성이 없을 때만 종성이 다른 음절까지 인정한다. 두 규칙이 같은
답을 낸다는 것은 문서로 확인했고, 시험은 "보인다"가 "보이"에 걸리고 "차이"가 "창"에 걸리지 않는
것으로 붙든다. 둘째, 셸 본문의 새 훑기는 파일 종류를 경로 앞자리로 가른다. 파일 번호로 세면 빈
문서 하나가 레코드를 내지 않아 자리가 통째로 밀린다.

## 검증 절차와 결과

격리 사본에서 먼저 돌리고, 통합한 커밋에서 같은 검사를 다시 돌렸다. 두 번 모두 같은 결과다.

- `cargo test --manifest-path src-tauri/Cargo.toml role_eligibility` — 108건 통과. 이 작업이 더한
  시험 9건이 여기에 들어 있고 완료 조건 C1부터 C8까지와 C10을 덮는다. 대상 판정 시험은 모두
  `assert_matches_condition_script`를 거쳐 앱과 셸 본문을 함께 돌려 대조한다.
- `cargo test --manifest-path src-tauri/Cargo.toml heartbeat_condition` — 55건 통과. 두 본문의
  사유 코드 목록 대조와 시나리오 표가 여기서 돌아 C9와 C11이 확인된다.
- `cargo test --manifest-path src-tauri/Cargo.toml` — 911건 통과, 통합 시험 28건 통과, 실패 없음.
- `cargo fmt --manifest-path src-tauri/Cargo.toml --check` — 통과.
- `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings` — 경고 없음.
- `npm run check` — 타입 검사 통과, 화면 시험 566건 통과, 생산 빌드 통과.

PowerShell 본문은 이 기기에서 한 번도 실행되지 않았다. 시험 러너가 현재 플랫폼의 본문만 돌리는데
이 기기는 macOS이고 `pwsh`도 `powershell`도 설치되어 있지 않다. 그래서 그 본문에 대해 확인된 것은
판 번호 줄, 사유 코드 어휘, 비ASCII 글자 제약 같은 정적 검사뿐이며, 판정이 셸 본문과 같은 답을
내는지는 Windows에서 시나리오 표를 돌려야 확인된다.

통합 후보는 격리 사본의 커밋 `4420a9b`이고 시작한 기반은 `1b0501a`다. 통합 직전에 공유 작업본이
`8b0159e`로 앞서 있어 그 커밋 위로 옮긴 뒤 격리 검사를 다시 돌렸고, 그 결과가 `9c59863`이다.
공유 작업본에 컨트롤 문서 밖의 미완성 변경은 없었다.

## 남은 위험

- PowerShell 본문의 판정이 실측되지 않았다. 옮긴 양이 커서(확인 절차 판독, 명령 줄 판독, 낱말
  대조, 최신 결정 선택) Windows에서 처음 도는 시나리오 표가 두 본문의 차이를 잡을 가능성이 있다.
- 조건 검사 스크립트가 기능 문서를 읽는 방식은 앱과 정확히 같지 않다. 앱은 프론트매터만 보고
  스크립트는 파일 아무 줄이나 첫 일치를 쓴다. 이 차이는 이 작업 전부터 있던 것이고 새 훑기도 같은
  규약을 따랐지만, 확인 절차 본문 안에 프론트매터처럼 생긴 줄이 들어오면 두 답이 갈릴 수 있다.
- PowerShell 본문의 ASCII 전용 제약을 판정 낱말(한글 음절과 절 제목의 가운뎃점)까지로 좁혀 다시
  세웠다. 인코딩은 본문 앞의 BOM이 고정하고 그 BOM은 기존 시험이 붙들지만, ASCII만 쓰던 때보다
  인코딩 사고에 노출되는 면이 넓어진 것은 사실이다.

## 후속 작업

- 역할 밖 발견을 하나 넘긴다. 판정 비용 시험의 픽스처에 있던 승인용 기능 문서들은 속한 작업이 없어
  이 작업이 더한 판정에서 구성 확인 필요가 된다. 문서 수를 늘리지 않으려고 그 문서들에 구성 미해결
  표시를 넣어 사람 판단 필요로 갈라지게 두었다. 최악 경로라는 성질은 유지되지만, 그 픽스처가 이제
  "성립하는 기능이 많은 저장소"가 아니라 "사람 판단을 기다리는 기능이 많은 저장소"라는 점은
  아키텍트가 알아 둘 만하다.
- 기능 문서 프론트매터의 `configuration_unresolved_revision`을 파일 계약 문서에 적는 일은
  TASK-S073-01 보고서가 이미 넘긴 그대로 남아 있다. 이 작업의 스크립트 쪽도 같은 필드를 읽는다.
