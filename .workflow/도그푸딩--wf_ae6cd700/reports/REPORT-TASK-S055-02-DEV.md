# TASK-S055-02 개발 보고서

## 결정권자 요약

사용자가 잘못 분해된 작업에 이유를 적어 남기는 수정 요청을 앱 소유 기록으로 저장하는 명령을 만들었다.
이 명령은 작업 문서를 쓰지 않는다. 요청 문서 한 건이 남거나 아무것도 남지 않으므로 반쯤 남는 결과가 생기지 않는다.
막힘과 선점 없는 개발 준비 두 상태에서만 받고, 진행 중과 품질 확인 대기와 완료는 거절한다.
오래된 갱신 시각과 선점과 마이그레이션 잠금에서도 아무 파일이 바뀌지 않는다.
같은 요청 식별자를 되풀이하거나 동시에 두 번 보내도 기록은 한 건이고, 미처리 요청이 있으면 두 번째 요청을 만들지 않는다.
작업 조회는 요청 목록을 생성 순서로 함께 돌려주며 처리 여부는 작업이 연결한 요청 식별자 하나로만 갈린다.
검사 629개가 통과했고 사용자는 TASK-S055-02 확인 동선의 수치를 확인하면 된다.

## 변경 파일과 모듈

- `src-tauri/src/domain/project.rs`: 요청 입력과 결과, 조회에 실리는 요청 항목 타입을 더했다. 결과는
  기록됨과 미처리 요청 대기 두 상태를 값으로 가른다. 작업 조회 구조에 요청 목록 필드를 더했다.
- `src-tauri/src/infrastructure/fs_project_repository.rs`: 저장 명령과 판정, 기록 읽기를 구현했다. 관리
  자산 설치 뒤 프로젝트 쓰기 잠금을 잡고 대상 문서를 다시 읽어 같은 요청 식별자의 기록, 상태, 선점,
  갱신 시각, 미처리 요청을 차례로 판정한다. 결정 디렉터리를 한 번 훑어 요청을 생성 시각 순서로 읽고,
  스키마와 작성자와 대상 작업이 맞지 않거나 시각을 읽을 수 없는 문서는 그 파일만 건너뛴다.
- `src-tauri/src/application/project_service.rs`, `src-tauri/src/commands/projects.rs`,
  `src-tauri/src/lib.rs`: 새 명령을 서비스와 명령 계층에 연결하고 실행기에 등록했다.
- `docs/file-contract.md`: 기록 형식과 저장 판정과 처리 완료 판정을 기존 결정 기록 설명 옆에 적었다.

## 검증 절차와 결과

- `cargo test --manifest-path src-tauri/Cargo.toml` 통과: 629 passed, 0 failed. 직전 618개에 이 작업의
  검사 열한 개가 늘었다.
- `npm run check` 통과: 타입 검사 성공, 25개 파일 851 tests 통과, 배포 빌드 성공. 프런트엔드는 바꾸지
  않았고 조회 구조에 필드가 하나 늘어도 그대로 통과한다.
- `cargo clippy --all-targets` 경고 없음, `cargo fmt` 적용.
- 다섯 상태와 선점과 마이그레이션 잠금과 오래된 갱신 시각을 각각 검사했다. 거절된 경우 작업 디렉터리와
  결정 디렉터리의 원문이 호출 전과 같다.
- 같은 요청을 직렬로 두 번, 그리고 스레드 둘로 동시에 보내 각각 기록이 한 건인지 확인했다. 미처리 요청이
  있는 대상에 다른 식별자로 요청하면 문서를 만들지 않고 그 요청을 돌려준다.
- 연결 필드가 없는 작업과 있는 작업으로 처리 완료 판정을 대조했다. 연결한 뒤에는 미처리 요청이 없으므로
  다음 요청을 다시 받는다.
- 시각을 읽을 수 없는 요청 문서와 작성자가 앱이 아닌 문서를 섞어, 조회가 그 둘만 건너뛰고 정상 요청
  하나를 돌려주는지 확인했다.
- 요청 기록이 없는 프로젝트에서 조회 결과의 요청 목록이 비어 있고 기존 기획 결정 판정이 그대로인지
  확인했다. 성공 경로에서 작업 문서가 바이트 단위로 그대로인 것도 함께 검사한다.

## 남은 리스크

- 처리 완료 판정의 근거는 작업이 연결한 요청 식별자 하나다. 한 작업이 두 번 고쳐지면 그 필드는 마지막
  요청만 가리키므로 먼저 처리된 요청이 다시 미처리로 읽힌다. 승인 범위가 정한 판정 그대로이지만, 요청을
  두 번 이상 받는 흐름이 실제로 생기면 그 자리에서 다시 판단해야 한다.
- 요청을 남기는 화면이 아직 없다. 명령은 등록됐지만 프런트엔드에서 부르는 곳이 없으므로 사용자 QA는
  자동 검사 수치로 이루어진다.
- 저장 판정에서 미만료 lease는 상태와 무관하게 거절 사유로 삼았다. 완료 조건 2가 선점을 상태와 나누어
  적지 않았기 때문이며, 막힘 상태에 lease가 남아 있는 경우에도 요청이 거절된다.

## 후속 작업

- 앞 작업(TASK-S055-01)의 보고서가 남긴 인계를 이 작업에서 절반만 처리했다. 기록의 스키마 이름을
  `workflow-labs/task-revision-request@1`로, 문서 식별자 접두사를 `REVISION-`으로 정했고 사용자 문서에
  적었다. 규칙 본문에 이 이름을 적는 일은 하지 않았다. 규칙 파일이 이 작업의 범위에 없고, 규칙은 기록의
  소유권과 연결 필드만 정의하면 충분하다고 판단했다. 규칙에 이름까지 적을지는 규칙 파일을 범위로 가진
  다음 작업이 정하면 된다.
- 요청을 아키텍트 자격 대상으로 삼는 판정과 요청을 남기는 화면은 이 승인의 다른 두 작업이다.
- 작업 조회 결과에 요청 목록 필드가 늘었지만 프런트엔드 타입에는 아직 없다. 화면 작업이 그 타입을 더할 때
  같은 이름으로 맞추면 된다.
