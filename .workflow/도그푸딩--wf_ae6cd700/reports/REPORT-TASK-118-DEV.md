# TASK-118 개발자 핸드오프 (qa_waiting)

## 결정권자 요약

앞으로 에이전트가 쓰는 기획서·개발 작업·개발 보고서는 맨 앞에 결정권자 요약 절을 갖는다. 승인 도장과
QA 도장을 찍기 전에 읽을 문단이 문서마다 생긴다는 뜻이고, 목록 카드와 검색 결과의 미리보기도 그날부터
그 문단을 싣는다. 개발 작업에는 확인 동선 절이 하나 더 붙어서, 어느 화면에서 무엇을 누르면 무엇이
보여야 정상인지를 개발자가 평문으로 적는다.

바꾼 것은 규칙 문언뿐이다. 화면도 판정도 한 줄 손대지 않았고, 이미 쓰인 문서는 그대로 읽히고 그대로
보인다. 요약이 없다는 이유로 세션이 멈추거나 작업이 닫히는 일은 없다.

지금 할 일은 하나다. 이 작업에 QA 확인 도장을 찍으면 이 프로젝트의 규칙 자산이 새 버전으로 갱신되고,
그 파일 안에 새 절이 들어 있으면 정상이다. 순서는 아래 확인 동선 절에 있다.

### 1. 공통 규칙 §8 — 맨 뒤에 덧붙였다

`## 8. Open the document with a summary for the decision-maker`를 §7 뒤에 붙였다. 중간에 끼우지
않았으므로 §1~§7의 번호가 한 건도 움직이지 않는다. 아래 "§ 참조 개수"가 그 실측이다.

§8이 한 번씩 정의하는 것: 요약 절의 이름(`## 결정권자 요약`, 한국어 문자열 그대로)·자리(H1 제목 바로
다음, 다른 어떤 절보다 앞)·최소 내용(본문의 축약이 아니라 다른 층의 독자를 전제로 다시 쓴 문단,
본문에 없는 사실을 만들지 않음, 면제 없음)·금지 조건 다섯과 문서 id 예외·분량 상한(빈 줄 제외 10줄)·
갱신 의무·요약 없는 문서의 유효성. 아이디어 문서가 대상이 아니라는 것도 여기 적었다.

확인 동선 절은 §8이 이름만 부르고(`## 확인 동선`) 내용 정의는 개발자 계약으로 넘긴다. 세 역할에
공통인 정의가 아니라 개발자 혼자 쓰는 절이라, §4가 공통 절차를 들고 역할 계약이 참조하는 구조를 이
절에서는 뒤집는 편이 정의를 한 곳에 두는 방법이었다. 완료 조건 4("어느 계약도 §8의 정의를 자기 안에
다시 쓰지 않는다")와 완료 조건 5("`developer.md`가 최소 형태와 화면 없는 작업의 표현을 함께 적는다")를
동시에 만족시키는 배치가 이것뿐이다.

### 4. `docs/file-contract.md` 네 자리

1. **기획서 절** — 본문 예시 맨 앞에 `## 결정권자 요약`을 넣고, 이어서 `### 결정권자 요약 절`
   소절에서 이름·자리·상한·금지 조건·갱신 의무·요약 없는 문서의 유효성을 §8과 같은 값으로 서술했다.
2. **에이전트 역할 계약 절** — 세 역할이 자기 문서에 지는 요약 의무를 한 줄씩 이었다.
3. **개발 작업 절** — 본문 예시에 두 절을 넣고, 예시 뒤 문장을 "본문에는 결정권자 요약 절을 맨 앞에
   두고, 이어서 작업 범위와 완료 조건을 작성한다"로 고쳤다. 두 절의 저자가 다르다는 것(요약은
   아키텍트, 확인 동선은 개발자)도 같은 자리에 적었다.
4. **개발 작업의 QA 절** — 사용자가 QA 화면에서 읽을 확인 동선이 작업 문서 본문에 있다는 것, 최소
   형태와 화면 없는 작업의 표현, 요약의 금지 조건이 이 절에 걸리지 않는다는 것, 그리고 보고서 쪽은
   계약 대상이 아니라는 것을 적었다.

- 프론트매터 계약·스키마 버전·조건 스크립트·앱의 세 역할 판정·미리보기·검색·문서 읽기·QA 기록을
  손대지 않았다.
- 설치된 `.workflow/rules/` 아래 파일을 손으로 고치지 않았다. 앱이 갱신한다.
- `.workflow/` 아래 기존 문서의 본문을 고치지 않았다. 소급 기입 0건.

**그래서 이 보고서의 확인 동선이 TASK-118 문서가 아니라 여기에 있다.** 새 계약은 확인 동선을 작업
문서 본문에 쓰라고 하지만, 이 작업의 완료 조건 12가 "`.workflow/` 아래 기존 문서의 본문 수정이
변경분에 없다"를 요구한다. TASK-118은 이 변경 전에 쓰인 문서이므로 그 본문에 절을 더하면 자기 완료
조건을 깬다. 계약이 "앞으로 쓰는 문서에 걸린다"고 적은 그대로, 이 절은 이번만 보고서에 둔다. 다음
개발 작업부터는 작업 문서 본문에 선다.

## 확인 동선

### 1. 옛 문서가 그대로 열린다 (도장 전에 확인)

앱 → 기획서 화면에서 요약 절이 없는 옛 기획서 아무거나 선택 → 본문이 지금까지와 똑같이 처음부터
끝까지 열리면 정상이다. 개발 작업 화면에서도 옛 작업 아무거나 열어 같은 것을 본다. 목록 카드의
미리보기 문구도 지금과 같아야 한다 — 이번 변경은 옛 문서를 한 글자도 고치지 않았다.

무엇이 정상이 아닌가: 본문이 빈 채로 열리거나, 카드 미리보기가 사라지거나, 문서를 여는 도중 오류가
나면 그것은 이 변경의 실패다. (예상: 문서를 읽는 코드가 이번 변경분에 없으므로 아무 변화가 없다.)

### 2. QA 확인 도장이 규칙 자산을 새 버전으로 갱신한다 (도장 직후 확인)

이 작업에 QA 확인 도장을 찍으면 앱이 그 자리에서 규칙 자산을 다시 설치한다. 도장 뒤에 프로젝트의
`.workflow/rules/workflow.md`를 열어 다음을 본다.

- 머리말의 `rules_version`이 `12`
- 문서 맨 뒤에 `## 8. Open the document with a summary for the decision-maker` 절이 있고, 그 안에
  `## 결정권자 요약`과 `## 확인 동선` 두 이름이 보인다
- `## 1.`부터 `## 7.`까지의 제목과 번호가 전과 같다

이어서 `.workflow/rules/roles/` 아래 셋을 본다.

- `planner.md`의 `rules_version`이 `7`, 완료 절에 기획서 요약 의무 한 줄
- `developer.md`의 `rules_version`이 `7`, `## The confirmation walkthrough` 절
- `architect.md`의 `rules_version`이 `6`, 완료 절에 작업 요약 의무 한 줄

명령으로 한 번에 보려면 프로젝트 루트에서:

```sh
grep -n "rules_version" .workflow/rules/workflow.md .workflow/rules/roles/*.md
grep -n "^## " .workflow/rules/workflow.md
```

무엇이 정상이 아닌가: 도장 뒤에도 네 값이 옛 값(공통 11 / planner 6 / architect 5 / developer 6)으로
남아 있으면 설치가 일어나지 않은 것이다. 그때는 앱을 새 빌드로 띄웠는지부터 본다 — 계약 본문은 앱 실행 파일 안에 있고, 이 변경은
빌드에 들어가야 디스크로 나간다.

## 하지 못한 검증
