## 분해 근거

**왜 둘인가.** 기획서가 요구하는 세 상태와 중단 의심 근거가 지금 화면까지 오지 않는다. 화면은 두 갈래
`status` 문자열 하나만 받는다. 판정을 만드는 쪽(Rust·판정 배선·파일 계약 문서)과 그리는 쪽(TSX·CSS·화면
테스트)은 검증 방법이 다르다 — 앞은 "픽스처를 놓고 payload가 무엇이 되는가", 뒤는 "그 payload로 무엇이
보이는가"다. 한 작업으로 묶으면 완료 조건이 20개를 넘고 리뷰가 한 번에 두 종류의 판단을 요구한다.
SPEC-011 분해(TASK-032 → TASK-033·034)와 같은 경계다.

**왜 셋으로 더 쪼개지 않았나.** 화면 변경이 `IdeaInbox.tsx` 한 파일이고, 세 상태 표시와 중단 의심 표시가
같은 두 지점(목록 행, 미리보기 헤더)을 만진다. 나누면 같은 파일을 두 작업이 연달아 열고 순서 제약만
늘어난다. 백엔드도 마찬가지다 — 판정 함수와 두 경로 배선을 나누면 첫 작업이 아무도 부르지 않는 함수를
남기고 끝난다.

**왜 화면 작업에 CSS를 넣었나.** "구분된다"(R4)가 색과 아이콘으로 이뤄지므로 TSX와 CSS를 나눌 수 없다.
같은 이유로 CSS 충돌(TASK-030·033·034)은 병행 금지로만 막았다.

## 아키텍트가 정한 것

기획서가 구현·표현 판단으로 남겨 둔 항목 중 이번에 확정한 것들이다. 기획서의 요구를 넘지 않는 선에서만
정했다.

1. **파생 상태를 어디에 싣는가.** 새 상태 필드를 만들지 않고 기존 `status`에 세 값
   (`inbox`·`drafting`·`adopted`)을 싣는다. 앱은 이미 아이디어의 `status`를 `adopted`로 덮어쓰고 있고,
   화면 소비처도 그 한 필드다. 별도 필드를 만들면 `status`가 아이디어에서 죽은 값이 되고, 화면이 어느
   쪽을 믿을지 정해야 한다. 값 이름은 `drafting`이다 — 개발 작업의 `in_progress`를 재사용하면 같은
   필드에 뜻이 다른 같은 글자가 들어간다.
2. **파일에 적힌 아이디어 `status`를 payload로 흘려보내지 않는다.** 세 상태가 배타적이려면(R1) 판정이 세
   경우 모두에 값을 써야 한다. 지금 코드는 채택일 때만 덮어쓰므로 `status: adopted`라고 적힌 아이디어
   파일이 참조 없이도 채택으로 보인다. 파일은 여전히 쓰지 않는다(R6) — 읽은 값을 화면에 흘리지 않을
   뿐이다.
3. **중단 의심을 값 하나로 표현한다.** `stalled` 불리언과 걸린 기획서 목록을 따로 싣지 않고
   `stalledSpecIds` 하나만 싣는다. 반영중인데 선점 lease가 없다는 것은 곧 draft 참조가 있다는 뜻이라
   (lease도 draft도 없으면 반영중이 아니다) 두 값이 항상 같이 움직인다. 따로 두면 서로 어긋난 조합이
   표현 가능해지고, 화면이 어느 쪽을 믿을지 정해야 한다.
4. **판정 본체를 함수 하나로 모은다.** `workflow_items`와 `read_idea`가 각자 `adopted_idea_ids`를 부르는
   현행 구조를 유지하지 않고, 두 경로가 같은 판정 함수를 부르게 한다. 기획자 핸드오프가 "규칙이 한 줄일
   때는 중복이 싸지만 세 갈래가 되면 어긋날 여지가 생긴다"고 지적한 지점이다. 완료 조건 19는 결과의
   일치만 요구하지만, 규칙을 복제해 두고 테스트로 대조하는 방법은 갈라진 뒤에야 실패한다.
5. **기획서의 `draft` 판정 기준.** "화면 기준 상태가 `draft`"는 결정 문서가 없고 파일 `status`가
   `user_review`가 아닌 경우다. `normalize_spec_status`가 알 수 없는 값을 `draft`로 떨어뜨리고
   `latest_spec_decisions`가 결정으로 덮어쓰는 현행 두 단계를 그대로 반영한 표현이며, 새 판정을 만들지
   않는다. 기획서 확인 사실 33번째 줄이 이 성질을 이미 명시했다.
6. **`create_workflow`가 넘기던 빈 lease 목록을 고친다.** 그 호출은 기존 워크플로우의 아이디어까지 다시
   실어 보낸다. 지금은 배너가 잠깐 비는 정도지만, 이 변경 뒤에는 살아 있는 lease가 무시되어 정상
   반영중인 아이디어가 한 조회 동안 중단 의심으로 보인다. 거짓 경고는 그 경고를 못 믿게 만든다.
   `migrate`의 빈 목록은 그대로 둔다 — 그 경로는 활성 lease가 있으면 이미 실패한다.
7. **`read_active_leases`의 오류 처리는 그대로 둔다.** `migrate`가 이 함수의 `Err`를 마이그레이션 차단
   근거로 쓰기 때문이다. R6의 "lease를 못 읽어도 화면이 산다"는 전문 읽기 경로에서만
   `unwrap_or_default()`로 받는다. 완료 조건 18(디렉터리 없음)은 현행 코드가 이미 빈 목록을 돌려주므로
   목록 경로에서도 성립한다.
8. **반영중 아이콘은 기존 `refresh`를 쓴다.** `Icon.tsx`에 새 아이콘을 더하지 않는다. TASK-033(SPEC-011,
   `todo`)이 그 파일에 `activity`를 더할 예정이라 겹치는 것을 피했고, 원형 화살표가 진행 중을 뜻하는
   데 부족하지 않다.
9. **중단 의심 문구가 자동 처리를 약속하지 않는다.** 안내 문장에 "자동 처리로 다시 잡히지 않으므로 직접
   확인해야 합니다"를 넣었다. 조건 스크립트는 참조가 있는 아이디어를 건너뛰므로(기획서 제외 범위) 이
   아이디어는 하트비트가 다시 집지 않는다. 이 문장이 없으면 사용자가 "곧 자동으로 처리되겠지"라고
   읽는다. R5가 요구한 "무엇을 하면 되는지"의 실체다.
10. **상태 태그를 두 상태에 붙인다.** 목록 행의 태그는 반영중(`반영중`)과 채택(`채택`)에 붙고 수집됨에는
    붙지 않는다. 태그 없음이 곧 수집됨이라는 현행 성질을 유지하면서 `기획 반영` 문구를 없앤다
    (완료 조건 13). 클래스 이름도 `idea-adopted-tag` → `idea-state-tag`로 바꾼다 — 태그가 두 상태에
    붙게 되므로 옛 이름은 사실이 아니다.

## 확인 필요 3건의 반영

DECISION-9B93CEA0이 셋 모두 기획서 제안대로 확정했다.

1. **중단 의심은 반영중의 부가 표시** → TASK-036. 상태 축은 셋 그대로이고 반영중 아이디어에 `중단 의심`
   태그와 안내 블록이 더 붙는다. payload에도 네 번째 상태값을 만들지 않았다.
2. **재작업 중 아이디어는 반영중으로 되돌림** → TASK-035의 판정 규칙 그대로다. `draft` 참조가 하나라도
   있으면 다른 참조가 승인됐어도 반영중이다. 테스트로 고정했다(`draft` + `user_review` 조합).
3. **걸린 draft 기획서의 문서 id 표시** → `stalledSpecIds`(TASK-035)와 미리보기 안내 블록(TASK-036).
   기획서로 이동하는 동작은 양쪽 "범위 밖"에 명시했다.

## 핸드오프 노트 (이 세션 범위 밖)

- **lease 해석이 세 곳으로 늘어난다.** REPORT-SPEC-011-ARCH가 "SPEC-012가 승인되면 판정 자리를 한 곳으로
  모으는 것을 그 분해에서 다뤄야 한다"고 남겼다. 확인해 보니 이 기획서가 만드는 것은 새 lease 읽기 경로가
  아니라 `read_active_leases` 결과의 **소비 규칙** 하나다(`task_id == 아이디어 id`). 읽기는 여전히
  `read_active_leases` 한 곳이고, TASK-035는 판정을 `derive_idea_states` 하나에 모은다. 그래서 이번에는
  통합 리팩터링을 만들지 않았다. 다만 SPEC-010 개정판(의존 판정)이 승인되면 소비 규칙이 셋이 되므로,
