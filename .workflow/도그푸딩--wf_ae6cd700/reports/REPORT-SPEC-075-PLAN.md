# SPEC-075 기획자 핸드오프

## 결정권자 요약

런타임이 예약한 아이디어 IDEA-487F3ACF를 처리해 기획서 SPEC-075를 새로 쓰고 사용자 검토 대기로
올렸다. 기획서는 품질 확인 목록의 기능 카드에 기능 소개의 첫 문장 하나만 최대 두 줄로 보여주고,
나머지 설명은 시작을 눌러 들어간 확인 화면에서만 보이게 하는 범위를 정한다. 아이디어가 기획에
맡긴 두 선택(요약의 상한, 요약으로 삼을 부분)은 실측 70건을 근거로 첫 문장 하나와 두 줄 상한으로
정했고, 나머지를 어디서 보여줄지는 카드에 펼치기 조작을 만들지 않고 확인 화면에 맡기는 쪽으로
정했다. 사용자가 할 일은 이 범위와 세 기본값을 보고 승인하거나 수정 요청을 남기는 것이다.

- 역할: 기획자 (planner)
- 대상: IDEA-487F3ACF (품질 확인 카드의 설명을 한두 문장으로 줄이려는 요구)
- 산출 기획서: SPEC-075 (status: user_review, 새로 만든 문서)
- 예약: 런타임 예약 대상 IDEA-487F3ACF, lease `lease-12839-20260819063052`, 결과 prefix
  `RES-20260819T063052Z-12839-20260819063052`
- 세션: 2026-08-19T06:31Z ~ 06:45Z

## 무엇을 했나

런타임이 예약한 대상 하나만 처리했다. `sh .workflow/rules/wf-claim.sh renew IDEA-487F3ACF
lease-12839-20260819063052 30`으로 소유를 먼저 확인했고(exit 0), `acquire`는 부르지 않았다. 조사와
작성 중에 두 번 더 갱신했다(둘 다 exit 0). 시작 시점에 `.workflow/.runtime/migration.lock`은 없었고,
`.workflow/rules/custom.md`도 없어 적용할 프로젝트 커스텀 규칙이 없었다.

소유 확인 직후 뼈대를 만들려 했으나 식별자 충돌이 있었다. 아래에 따로 적는다. 뼈대를 만든 뒤
조사하고, 본문을 쓰고, `user_review`로 올렸다.

## 식별자 결정

`specs/`의 번호는 001부터 073까지 빈 자리 없이 차 있었으므로 처음에는 SPEC-074를 쓰려 했다. 파일을
만들기 직전에 `specs/SPEC-074.md`가 이미 있었다. 다른 기획자 세션이 2026-08-19T06:31:51Z에
IDEA-49AB3D06으로 그 번호를 먼저 가져갔고, 그 아이디어의 lease도 유효했다. `workflow.md`의 계보
규칙이 정한 대로 다음 빈 번호인 SPEC-075로 옮겨 만들었다. 남의 문서는 열어 읽기만 했고 손대지
않았다. 결과 prefix는 문서 식별자에 넣지 않았다.

## 중단 기록 확인과 인계 판단

`.workflow/.runtime/silent-runs/`를 읽었고, 이 대상을 가리키는 기록이 하나 있었다. 기획자 역할로
2026-08-19T06:30:52Z에 시작해 06:30:54Z에 끝났고, 사유는 `supervisor_identity_unverified`다. 시작
시각이 이 세션에 넘어온 예약의 시각과 같으므로, 같은 예약으로 먼저 뜬 실행이 2초 만에 끊긴 뒤 이
세션으로 다시 뜬 것으로 읽었다.

그 실행은 잔여물을 남기지 않았다. `specs/`에서 `source_idea_id: IDEA-487F3ACF`를 참조하는 문서는
하나도 없었고, 대상 아이디어 문서도 등록 당시 그대로였다. 기획자 세션이라 격리 사본을 쓰지 않았고
코드 작업 트리에 남은 변경도 없었다. 그래서 이어받을 것도 버릴 것도 없었고, 뼈대부터 새로 만들었다.
시험 파일은 만들지도 지우지도 않았다.

같은 디렉터리에 IDEA-49AB3D06을 가리키는 같은 사유의 기록이 하나 더 있으나, 그 대상은 다른 세션이
유효한 lease로 잡고 있어 손대지 않았다.

기록 파일 셋은 앱 소유이므로 읽기만 했다.

## 기획서가 정한 것

- 카드에 쓰는 값을 기능 소개의 첫 문장 하나로 좁힌다. 첫 문장은 마침표·물음표·느낌표 뒤가 공백이거나
  소개의 끝인 자리까지로 보고, 그런 자리가 없으면 소개 전체를 첫 문장으로 본다.
- 카드의 표시 상한은 두 줄이다. 실측상 지금 어떤 기능도 두 줄을 넘지 않으므로, 이 상한은 앞으로 더
  긴 첫 문장이 들어올 때만 작동하는 안전장치다.
- 나머지 설명은 시작을 눌러 들어간 확인 화면과 완료 기록 화면에서만 보인다. 카드에 펼치기 조작을
  새로 만들지 않는다.
- 확인 화면과 완료 기록 화면의 표시 기준, 소개 문단을 뽑는 기준, 기능 문서 자체는 바꾸지 않는다.

기본값 셋: 요약 단위(첫 문장 하나), 카드 상한(두 줄), 나머지를 여는 방식(펼치기 조작 없이 시작으로).
셋 다 기획서 본문에 근거와 함께 적었고, 사용자가 다르게 원하면 수정 요청으로 돌려보낼 수 있다.

## 조사에서 확인한 사실

기획서의 현황 서술과 수치는 다음을 읽고 썼다.

- 카드가 쓰는 값은 `src-tauri/src/infrastructure/fs_project_repository.rs`의
  `parse_work_group_description`이 만든다. 문서 본문에서 소개 문단을 뽑아 문단 구분을 유지한 채
  통째로 넘긴다. SPEC-066이 정한 두 단계 기준이 여기에 반영돼 있다.
- 카드는 `src/features/projects/components/qa/QaWorkbench.tsx`의 확인 대기 목록 행이고, 설명은
  `QaWorkbench.css`의 `.qa-queue-goal`에서 3줄로 잘린다(글자 12px, 색 #777a70). 잘림은 CSS 줄 수
  제한이라 문장 경계와 무관하게 끊긴다.
- 소개 전체를 보여주는 자리는 둘이다. 같은 파일의 열린 기능 머리말과
  `src/features/projects/components/WorkspaceShell.tsx` 854번 줄의 완료 기록 상세이며, 둘 다
  `.qa-feature-goal`을 쓰고 줄 수 제한이 없다.
- 준비 중인 기능 목록의 행은 제목과 상태만 그리고 설명을 붙이지 않는다. 이 변경의 대상이 아니다.
- `groups/`의 기능 문서 70건을 SPEC-066의 소개 추출 기준으로 실측했다. 소개 전체는 33자에서 1024자,
  문장 수는 1에서 17이다. 55건은 소개가 1문장이고, 15건이 4문장 이상(203자에서 1024자)이다. 첫
  문장만 뽑으면 70건 모두 27자에서 75자, 중앙값 33자, 상위 10%가 54자이며 100자를 넘는 건은 없다.
  소개가 비는 문서도 없다.
- 첫 문장이 기능의 변화가 아니라 상황 설명으로 시작하는 문서가 15건 중 1건 있었다(GROUP-072). 둘째
  문장을 붙여도 나아지지 않는 구성이라, 첫 문장 하나라는 기준을 그 1건 때문에 바꾸지는 않고 위험으로
  적었다.

## 경계와 후속

- 아키텍트가 기능 문서의 소개 첫 문장에 무엇을 쓸지 정하는 작성 지침은 이 기획서 범위 밖이다.
  SPEC-066도 같은 이유로 지침을 건드리지 않았고, 위에 적은 1건은 그 지침이 없어서 생긴 결과다.
  지침을 정하는 일은 별도 아이디어가 필요하다.
- SPEC-066은 아직 `user_review`이고 GROUP-066은 `active`다. 즉 카드의 3줄 상한과 소개 추출은 이미
  코드에 들어가 있다. SPEC-075는 그 결과 위에 얹히는 변경이며, 소개를 뽑는 기준은 그대로 쓰고 카드에
  무엇을 실을지만 바꾼다. 작업 분해 시점에 두 계보가 같은 표시 규칙을 건드린다는 점을 확인해야 한다.
- 첫 문장을 잘라내는 처리를 앱의 값 만드는 자리에서 할지 화면에서 할지는 정하지 않았다. 아키텍트
  몫이다. 다만 확인 화면과 완료 기록 화면은 소개 전체를 계속 받아야 하므로, 두 자리가 같은 값을
  나눠 쓰는 지금 구조를 어떻게 다룰지가 판단 지점이다.

## 역할 경계

- 작업 그룹, 개발 작업, 제품 코드는 만들지도 고치지도 않았다. 저장소 코드는 읽기만 했다.
- 결정 문서를 만들거나 고치지 않았고, 승인·반려·폐기를 대신 기록하지 않았다.
- 앱 소유 상태 파일(`project.yml`, `workflow.yml`, `.workflow/.runtime/`)을 직접 쓰지 않았다. lease는
  관리 헬퍼로만 다뤘다.
- 다른 세션이 쓰고 있는 SPEC-074와 IDEA-49AB3D06에는 손대지 않았다.

## 마무리

기획서는 `user_review`다. 사용자 승인이 기록되기 전에는 이 범위로 작업을 분해하지 않는다. 이 보고서를
쓴 뒤 같은 lease를 반납한다.
