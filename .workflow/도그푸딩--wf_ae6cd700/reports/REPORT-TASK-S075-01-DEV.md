# TASK-S075-01 개발 보고서

## 결정권자 요약

품질 확인 대기열의 기능 카드는 이제 기능 소개의 첫 문장 하나만 보여주고, 그 문장을 그리는 줄 수
상한이 세 줄에서 두 줄로 내려갔다. 소개가 실려 있는 기능 문서 64건을 다시 재니 첫 문장은 33자
에서 69자 사이이고, 실제 대기열 폭에서는 그중 가장 긴 문장도 한 줄에 들어와 말줄임이 걸리는
문서가 하나도 없다. 소개가 긴 기능과 짧은 기능의 카드 높이를 재니 모두 71픽셀로 같았고, 소개가 없는 기능의
카드는 제목만 실린 63픽셀이었다. 첫 문장 뒤의 설명은 시작을 눌러 들어간 확인 화면 머리말과 완료
기록 화면에서 전과 똑같이 전부 보인다. 카드에는 소개를 펼치는 조작을 만들지 않았고 기능 문서는
한 건도 고치지 않았다. 시험 579건과 타입 검사, 생산 빌드가 격리 사본과 통합 커밋에서 모두
통과했다. 이 결과는 GROUP-075의 사용자 확인 절차 전체를 뒷받침한다.

## 바꾼 파일과 모듈

- `src/features/projects/domain/featureIntro.ts` — 새 모듈. 소개 문자열에서 첫 문장을 잘라 내는
  `featureIntroLead` 하나만 내보낸다. 마침표·물음표·느낌표 뒤에 공백류나 문자열 끝이 오는 첫
  자리에서 끊고, 그런 자리가 없으면 소개 전체를 돌려준다. 부호 뒤가 공백이 아니면 문장 끝으로
  보지 않으므로 소수점은 문장을 끊지 않고, 부호가 잇달아 붙은 자리는 공백이 따라오는 마지막
  부호에서 끊긴다.
- `src/features/projects/components/qa/QaWorkbench.tsx` — 대기열 카드가 `group.description`
  대신 그 함수의 결과를 그린다. 결과가 빈 문자열이면 소개 자리를 만들지 않아, 빈 소개를 다루던
  기존 방식이 그대로 유지된다. 확인 화면 머리말(132행 부근)은 손대지 않았다.
- `src/features/projects/components/qa/QaWorkbench.css` — `.qa-queue-goal`의 줄 수 상한만 3에서
  2로 내렸다. 넘침 감추기와 여러 줄 상자 선언, `.qa-feature-goal`은 그대로다.
- 시험 셋: `domain/featureIntro.test.ts`(새 파일, 9건), `qa/QaWorkbench.test.tsx`(4건 추가),
  `qa/qaWorkbenchAlignment.test.ts`(대기열 기대값을 2로, 시험 이름과 근거 주석을 함께 고침).

판정을 프론트에 둔 이유는 작업 문서가 정한 그대로다. 확인 화면 머리말과 완료 기록 화면이 같은
소개 값을 계속 써야 해서, 앱이 내려 주는 값을 좁히면 그 두 자리가 함께 좁아진다. 값은 지금대로
전부 내려보내고 카드가 그릴 때만 좁혔으므로 저장소 읽기 코드와 프론트 계약 타입은 손대지 않았다.

작업 문서 밖에서 읽은 것은 SPEC-075와 DECISION-52462782 둘이다. 작업 문서가 모자라서가 아니라,
승인 짝이 이 기획서의 최신 승인인지 확인하는 자격 판정이 요구해서 열었다.

## 검증 절차와 결과

격리 사본에서 먼저 돌리고, 통합한 커밋을 격리 사본에 옮겨 같은 검사를 다시 돌렸다.

- 통합 후보: 기준 커밋 `0265e73`, 격리 브랜치 커밋 `aad5abf`, 바뀐 파일은 선언한 여섯뿐이다.
- 격리 사본 `npm run check`: 통과. 시험 파일 30개, 579건 통과·42건 건너뜀, 타입 검사와 생산
  빌드 모두 통과.
- 통합 커밋 `1b50c74`에서 `npm run check`: 통과. 같은 수치(30개 파일, 579건 통과·42건 건너뜀).
- C1·C2·C4·C5는 새 단위 시험 9건이 규칙별로 확인한다. 4문장 소개에서 결과에 둘째 문장의 첫
  낱말이 없다는 것, 1문장 소개가 입력과 같다는 것, 빈 문자열과 공백만 있는 문자열이 빈 결과를
  낸다는 것을 각각 따로 본다.
- C1·C4·C5·C6은 화면 시험 4건이 확인한다. 문단이 여럿인 4문장 소개를 대기열에 올려 카드에 첫
  문장만 실리는 것, 1문장 소개의 카드 값이 그대로인 것, 빈 소개의 카드에 소개 자리 자체가 없는
  것, 기능을 열면 머리말에 소개 전체가 문단 구분까지 그대로 있는 것을 본다.
- C3·C6은 스타일 시험이 확인한다. 대기열 쪽 상한이 2이고 넘침 감추기와 여러 줄 상자가 그대로이며,
  열린 화면 쪽에는 상한이 없고 문단 구분이 살아 있다.
- C7은 이 작업이 카드 안의 소개 자리 하나만 바꿨고 조작을 더하지 않았다는 사실과, 카드를 눌러
  확인 화면이 열리는 기존 시험이 그대로 통과한다는 사실로 확인했다.
- C8은 `git status`로 확인했다. 통합 커밋의 변경 파일이 선언한 여섯과 정확히 같다.
- 눈으로 보는 확인은 실제 스타일 파일과 저장소의 실제 기능 소개로 카드 목록을 그려서 했다.
  대기열 폭을 앱과 같은 760픽셀로 두고 재니 소개가 있는 카드는 첫 문장이 69자든 33자든 모두
  71픽셀이었고, 소개가 없는 카드만 63픽셀이었다. 웹킷 렌더링으로도 같은 결과를 확인했다.
  이때 다시 잰 대상은 소개 절이 실려 있는 기능 문서 64건이다. 기획서가 적은 70건·27자에서
  75자와 표본이 달라 수치가 조금 다르지만, 첫 문장이 100자를 넘지 않는다는 결론은 같다.

통합 커밋의 첫 검사에서 이 작업과 무관한 화면 시험 하나가 5초 제한에 걸려 떨어졌다. 같은 파일을
따로 돌리니 그 시험의 실제 소요는 248밀리초였고, 떨어진 검사는 다른 개발 세션이 같은 기계에서
돌던 시간대에 전체 소요가 평소의 두 배(18초→35초)로 늘어난 회차였다. 부하로 인한 시간 초과로
판단하고 다시 돌려 통과를 확인했다. 이 작업의 변경과는 무관하다.

## 남은 위험

- 첫 문장 판정은 마침표·물음표·느낌표 세 부호에만 기댄다. 이 부호를 하나도 쓰지 않는 소개는
  통째로 카드에 실리고 두 줄에서 끊긴다. 지금 저장소의 64건에는 그런 문서가 없다.
- 카드 높이는 소개뿐 아니라 제목 줄 수에도 달려 있다. 제목이 두 줄로 감기는 기능의 카드는 여전히
  한 줄 더 높다. 제목은 기획서가 제외 범위로 둔 자리라 이 작업이 다루지 않았다.
- 데스크톱 앱을 실제로 띄운 눈 확인은 이 세션이 하지 못했다. 아래 후속 작업에 적었다.

## 후속 작업

- 아키텍트 인계. 작업 문서의 검증 절차 6번은 앱을 띄워 화면을 눈으로 확인하라고 적혀 있는데, 이
  세션의 실행 환경에서는 할 수 없다. 앱은 네이티브 창을 여는 데스크톱 앱이고 화면 데이터가
  백엔드를 거쳐 오므로, 브라우저만으로는 대기열에 기능이 실리지 않는다. 대신 실제 스타일과 실제
  소개로 카드를 그려 확인했고, 같은 확인이 GROUP-075의 사용자 확인 첫 항목에 이미 들어 있다.
  앞으로 작업 문서의 검증 절차에는 개발 세션이 실행할 수 있는 단계만 두고, 화면을 눈으로 보는
  확인은 작업 그룹의 사용자 확인 동선에 맡기는 편이 낫다.
