# TASK-S073-04 개발 보고서

## 결정권자 요약

사용자가 지금 할 일이 없는 기능은 이제 상태 이름 하나만 보여주지 않는다. 무엇이 문제이고 누가
처리하며 사용자가 지금 무엇을 하면 되는지가 상세를 열지 않아도 목록 자리에서 함께 보인다. 구성
확인 필요와 사람 판단 필요 기능에는 어떤 조건이 맞지 않았는지가 조건마다 한 줄씩 붙고, 아키텍트가
사람의 판단이 필요하다고 남긴 기능에는 무엇을 판단해야 하는지가 함께 나온다. 사유를 만들지 못한
기능도 상태와 처리 주체만으로 그대로 서고 목록에서 사라지지 않는다. 사용자 QA 대기 기능의 확인
시작 입구는 손대지 않았고, 새 설명 자리는 읽는 자리라서 눌러도 아무 일이 일어나지 않는다. 사람
판단 필요 기능이 홈 화면의 내 선택 대기 목록에 들어가지 않는 것도 함께 붙들어 두었다. 화면 시험
566건과 타입 검사, 생산 빌드가 격리 사본과 통합 커밋에서 모두 통과했다. 이 결과는 GROUP-073의
자동 검증 가운데 네 상태를 사용자 문장으로 옮겨 네 자리에 보여주는 부분을 뒷받침한다.

## 바꾼 파일과 모듈

- `src/features/projects/components/DevelopmentBoard.tsx` — 네 상태의 설명 표, 여섯 사유의 문장
  표, 설명 자리를 그리는 `GroupAttentionNote`를 두고 내보낸다. 기능 레인의 머리글 아래에 그
  자리를 붙였고, 레인을 접어도 남게 두어 목록만 훑어도 갈리게 했다. 확인 시작 입구를 그리는
  분기는 손대지 않았다.
- `src/features/projects/components/qa/QaWorkbench.tsx` — 준비 중인 기능 목록의 항목과, 확인
  도중 열 수 없게 된 기능 화면에서 같은 설명 자리를 부른다.
- `src/features/projects/components/SpecWorkspace.tsx` — 기능 상태와 작업 수를 보여주는 자리
  아래에 같은 설명 자리를 부른다.
- `src/App.css` — 상태 알약 규칙과 나란히 설명 자리의 공통 모양을 두었다. 알약도 버튼도 아닌
  왼쪽 선 하나짜리 글 덩이이고, 줄바꿈만 하고 줄 수를 자르지 않는다.
- `src/features/projects/components/qa/QaWorkbench.css` — 준비 중인 기능 한 줄을 두 칸 격자로
  바꿔, 제목과 상태는 한 줄에 두고 설명이 그 아래를 가로지르게 했다.
- 시험 넷: `DevelopmentBoard.test.tsx`, `qa/QaWorkbench.test.tsx`, `SpecWorkspace.test.tsx`,
  `WorkspaceShell.test.tsx`.

설계 판단 하나를 적어 둔다. 설명 한 벌은 세 화면이 함께 써야 하는데 선언한 범위 안에 공용 모듈이
없어, 이미 `taskColumns`를 같은 방향으로 나눠 쓰던 개발 보드 파일에 두고 나머지 두 화면이 가져다
쓰게 했다. 표를 세 번 적으면 세 화면의 문장이 갈라지고, 그때 어느 화면이 옳은지 판정할 자리가
없어진다.

## 검증 절차와 결과

격리 사본에서 먼저 돌리고, 통합한 커밋을 격리 사본에 옮겨 같은 검사를 다시 돌렸다. 두 번 모두
같은 결과다.

- `npm run test` — 화면 시험 566건 통과, 42건 건너뜀, 실패 없음. 이 작업이 더한 시험 18건이
  여기에 들어 있고 완료 조건 C1부터 C12까지를 덮는다. C12는 홈 화면 시험에서 확인했고, 내 선택
  대기 목록에 실제로 두 줄만 서는 것까지 함께 붙들어 두었다.
- `npm run check` — 타입 검사, 화면 시험, 생산 빌드가 모두 통과했다. 통합 뒤 종료 코드 0이다.
- 눈으로 본 화면 — 개발 보드의 기능 레인, 품질 확인 화면의 준비 중인 기능 목록, 확인 도중 열 수
  없게 된 기능 화면, 기획서 화면의 기능 상태 넷을 네 상태 모두에서 보았다. 설명 자리가 확인 시작
  입구와 다른 결로 서고, 폭을 980에서 400으로 줄여도 문장이 잘리지 않고 줄만 바뀌는 것을 확인했다.
  웹킷과 블링크 두 엔진에서 같은 모습이다.

통합 후보는 격리 사본의 커밋 `60242a9`이고 시작한 기반은 `bceb51f`다. 통합 시점의 공유 작업본이
같은 기반이었고 통제 문서 밖에 사용자의 미완성 변경이 없어 그대로 반영했으며, 통합 결과는
`c6c0152`다.

## 남은 위험

- 눈으로 본 화면은 앱 창이 아니라, 화면이 실제로 그린 마크업을 생산 빌드의 스타일과 함께 브라우저
  두 곳에서 렌더링해 본 것이다. 앱 창에서만 드러나는 스케일이나 폰트 차이는 이 확인이 잡지 못한다.
- 사람 판단 필요는 기능 문서에 그 표시가 적힌 뒤에야 나오고 그 표시를 적는 절차는 아직 없으므로,
  이 상태의 설명은 지금 어떤 실제 기능에서도 나타나지 않는다. 시험이 만든 값에서만 확인했다.
- 아키텍트가 남긴 판단 요청 글은 그대로 화면에 실린다. 그 글에 내부 이름이나 경로가 적혀 있으면
  화면에도 그대로 나온다. 이 작업이 만드는 문장에는 그런 이름이 없다는 것만 시험이 붙든다.

## 후속 작업

- 역할 밖 발견 하나를 아키텍트에게 넘긴다. 작업 상세 화면 안에도 소속 기능의 상태 알약이 하나 더
  있는데, 이 작업의 변경 범위가 자리를 넷으로 한정해서 그대로 두었다. 같은 설명을 그 자리에도
  붙일지는 아키텍트가 정할 일이다.
- 역할 밖 발견 하나를 더 넘긴다. 이 작업의 검증 절차 3번은 앱을 띄워 눈으로 확인하라고 적혀
  있는데, 에이전트 세션은 창을 띄우고 그 창을 보는 일을 할 수 없고 네 상태를 실제로 띄우려면
  구성이 깨진 프로젝트도 필요하다. 위에 적은 방식으로 대신했고 완료 조건은 모두 충족했으나,
  절차 문구를 에이전트가 실행할 수 있는 형태로 다시 쓸지는 아키텍트가 정할 일이다.
