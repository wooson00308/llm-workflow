# SPEC-059 아키텍트 보고서

## 결정권자 요약

승인된 SPEC-059를 작업 그룹 GROUP-059와 개발 작업 TASK-S059-01 하나로 구성했다.
개발 작업 화면의 목록·수치·안내가 모두 한 화면 컴포넌트 안에서 만들어지고 소비되어 작업을 하나로 뒀다.
품질 확인 방식은 사용자 확인으로 정했다. 바뀌는 것이 사용자가 직접 보는 목록과 수치이기 때문이다.
사용자 확인 플로우는 보기를 바꿔 가며 같은 작업만 나오는지 확인하는 통합 동선 하나로 썼다.
지금 사용자에게 요청하는 결정은 없다. 개발이 끝나면 GROUP-059의 품질 확인이 열린다.

## 대상과 예약 절차

- 역할은 architect이고 대상은 DECISION-D01A8B62 하나다.
- 런타임이 넘긴 lease-27655-20260817141827을 wf-claim renew로 갱신해 종료 코드 0을 확인했다. 같은
  대상에 acquire는 실행하지 않았다.
- 결과 접두어 RES-20260817T141827Z-27655-20260817141827은 이 보고서에서만 인용하고 문서 식별자에는
  넣지 않았다. 그룹과 작업 식별자는 계보 규칙대로 승인된 기획서 번호에서 정했다.
- 소유 확인 직후 GROUP-059를 status preparing으로 먼저 만들고, 작업 문서를 쓴 뒤 같은 그룹을 status
  active로 전환했다.
- 마이그레이션 잠금은 없었다. 사용자 정의 규칙 파일도 없어서 공통 규칙과 architect 역할 계약만
  적용했다.
- 인수한 잔여물은 없다. lease 디렉터리에는 이 세션의 lease 하나만 있었고, 쓰기 직전 GROUP-059와
  TASK-S059-01 경로가 모두 비어 있음을 확인했다.

## 자격 판정

- DECISION-D01A8B62는 SPEC-059를 가리키는 유일한 결정이며 outcome은 approved, created_by는 user다.
  이 기획서에 다른 결정은 없어 이것이 최신 승인 결정이다.
- 이 승인을 source_decision_id로 참조하는 작업 그룹이 하나도 없음을 groups 전체 검색으로 확인했다.
  SPEC-059를 참조하는 작업 문서도 없었다.
- 이 대상에 다른 lease는 없었다. 그룹 QA 반려, 정의 오류로 막힌 작업, 중단된 preparing 그룹은 이
  세션의 대상이 아니었고 런타임이 예약한 승인 대상 하나만 처리했다.

## 코드에서 확인한 사실

개발 작업 화면은 `src/features/projects/components/DevelopmentBoard.tsx` 한 컴포넌트다.

- `tasksForDevelopment`가 지금 항등 함수이고, 보드·리스트·작업 그룹별 보기가 모두 그 결과에서 파생된
  `filteredTasks`를 쓴다. 감춤 판단을 넣을 자리가 이미 한 곳으로 모여 있다.
- 끝난 그룹을 빼는 처리는 `WorkGroupLaneBoard`의 `activeGroups` 안에만 있고, 화면 머리 수치와 요약
  띠 세 수치는 `workflow.items.tasks`를 그대로 센다. 기획서가 말한 "보기마다 목록이 달라진다"는
  현상의 원인이 이 두 갈래다.
- 타임라인은 `timelineTasks`라는 별도 파생을 쓴다. 그래서 R7이 요구하는 타임라인 불변은 좁혀진
  집합을 다른 곳에만 적용하면 코드 구조로 성립한다.
- 소속 그룹 확정 판정은 `matchingWorkGroup`에 이미 있다. 그룹 존재, revision 범위, 기획서와 결정
  출처 일치를 함께 본다. 기획서 R5가 요구하는 "소속을 확정할 수 없는 작업은 감추지 않는다"가 이
  함수의 실패 조건과 정확히 같아서 새 판정을 만들지 않고 이것을 재사용하도록 작업에 적었다.
- 작업 그룹의 `displayStatus`는 백엔드 `fs_project_repository.rs`가 파생해 넘기며 completed와
  automatic_completed가 이미 타입에 있다. 감춤 기준으로 새 값을 만들 필요가 없다.
- 안내 문구가 쓰는 클래스 중 `.task-lane-completed-note`에는 스타일 규칙이 없고 `.task-lane-note`만
  규칙을 가진다. 안내를 다른 위치에서 같은 클래스로 그려도 스타일 파일을 바꿀 일이 없다.
- `WorkspaceShell.test.tsx`가 개발 화면에서 같은 안내 문구와 개수를 찾는다. 문구와 개수 정의를
  유지하면 수정 없이 통과하므로, 이 검사를 C8의 회귀 감시로 쓰도록 검증 절차에 넣었다.

## 구성에서 내린 판단

- 작업을 하나로 뒀다. 감춤 판단, 목록과 수치의 범위, 감춘 그룹 수 안내가 모두 같은 파일 안에 있어
  나눠도 병렬로 진행할 수 없다. 게다가 감춘 그룹 수는 감춤 판단이 만드는 값과 같은 계산에서 나오므로,
  나누면 한 값을 두 세션이 각각 다시 유도하게 된다. 순서만 강제되고 얻는 것이 없어 하나로 묶었다.
- 품질 확인 방식은 user로 정했다. 바뀌는 결과가 사용자가 개발 작업 화면에서 직접 보는 목록과 수치라
  비개발자가 화면을 열어 확인할 수 있다.
- 사용자 확인 플로우는 QA-01 하나로 썼다. 기능의 진입점이 개발 작업 화면 하나여서 보기를 차례로
  바꿔 보는 동선 한 번이면 전체를 덮는다. 작업이 하나뿐이지만 그와 무관하게, 플로우는 사용자가
  기능을 만나는 순서를 따랐고 작업 제목을 옮기지 않았다.
- 확인 단계에 타임라인과 기록 화면을 함께 넣었다. R7과 R9가 요구하는 것은 "바뀌지 않음"이고, 그
  불변은 사용자가 직접 열어 봐야 확인된다.
- `depends_on`은 쓰지 않았다. 이 승인에서 나온 작업이 하나뿐이라 순서를 매길 상대가 없다.
- `scope_files`에는 화면 컴포넌트와 그 검사 파일 두 개만 넣었다. 백엔드 파생, 타입 정의, 스타일
  파일, 기록 화면은 값을 무변경으로 통과시킨다는 것을 코드에서 확인하고 근거와 함께 선언 밖에 뒀다.
  근거는 작업 문서의 범위 사전 검사에 값 경로 네 줄로 적었다.

## 자기 검토

- 완료 조건 C1~C10이 기획서 요구사항 R1~R10과 하나씩 대응하는지 확인했다. R7·R8·R9·R10처럼 "바뀌지
  않는다"는 요구도 완료 조건으로 명시해 구현자가 판단할 대상으로 남겼다.
- 기획서의 검수 기준 10개가 GROUP-059의 QA-01 여덟 단계와 작업의 검증 절차로 모두 덮이는지 확인했다.
  검수 기준 3번의 실측 수치는 자동 검사로 판정할 값이 아니어서 사용자 동선에는 "누적 총계가 아니다"
  라는 읽기 판정으로, 작업 쪽에는 검사 항목으로 나눠 넣었다.
- 작업의 결정권자 요약을 구조화 형식으로 썼다. 제안, 현재, 변경 후, 비용과 위험을 순서대로 한 번씩
  두었고 요약 안에 파일 경로, 코드 이름, 백틱 토큰을 넣지 않았다.
- 그룹의 사용자 확인 플로우에 터미널 명령, 패키지 실행 명령, 저장소 조작, 내부 자동 검사 절차가
  들어가지 않았음을 확인했다. 각 단계는 사용자 행동 한 문장이고 기대 결과는 같은 항목 안 인용
  줄이며, 표나 중첩 목록을 쓰지 않았다.
- 한국어 문체 규칙에 따라 영어 대시를 문장 구분으로 쓰지 않았고, 은유 대신 실제 동작을 가리키는 말로
  썼다.
