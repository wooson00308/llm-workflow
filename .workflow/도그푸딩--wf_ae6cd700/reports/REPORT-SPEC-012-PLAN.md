# SPEC-012 기획자 핸드오프

- 대상 아이디어: IDEA-B91FD491 (아이디어 "반영중" 파생 상태 도입)
- 산출 기획서: SPEC-012 (`status: user_review`)
- 세션 역할: 기획자
- 작성 시각: 2026-08-03T01:58:00Z

## 결과

미처리 아이디어 3건(IDEA-B91FD491·IDEA-54B29779·IDEA-48EDAF2B) 중 가장 오래된 IDEA-B91FD491을 선점해 SPEC-012를 작성하고 `user_review`로 올렸다. 요구사항 R1~R8, 확인 필요 3건, 완료 조건 23개다. 작업 분해도 구현도 하지 않았다.

착수 판단 시점(01:41Z)에 `revision_requested` 결정은 없었다. 기획서 결정 문서 9건이 모두 `approved`였고 SPEC-010·SPEC-011은 결정 없이 `user_review` 상태였다. 그래서 미처리 아이디어 쪽을 대상으로 골랐다.

세션 진행 중(01:44Z) 앱이 결정 문서 두 건을 새로 기록했다. DECISION-FE4BCCC7(SPEC-011 승인)과 DECISION-FEB99DAB(SPEC-010 수정 요청)이다. 후자는 기획자 재작업 대상이지만, 공통 규칙 §3의 "한 클레임당 한 건"에 따라 이 세션에서 이어서 처리하지 않고 아래 핸드오프에 남긴다.

## 근거 확인

기획서의 확인 사실은 이 저장소의 앱 코드와 규칙 자산에서 직접 읽은 것이다. 추정으로 쓴 항목은 없다.

- `adopted_idea_ids`(`fs_project_repository.rs`)는 `specs/`의 모든 `.md`에서 `source_idea_id`만 뽑아 `HashSet`으로 만든다. 기획서 `status`도 결정 문서도 읽지 않는다. 아이디어가 지적한 "스펙 상태와 무관하게 참조만 본다"가 코드 그대로 확인된다.
- `workflow_items`는 그 집합에 든 아이디어의 `status`를 `adopted`로 덮어쓴다. `read_idea`도 같은 함수를 호출해 같은 판정을 따로 한 번 더 한다. 규칙이 두 곳에 있다는 사실이 R7과 완료 조건 19번의 근거다.
- 같은 함수에서 기획서 상태는 `normalize_spec_status`로 `draft`·`user_review`로 정규화된 뒤 `latest_spec_decisions`의 `outcome`으로 덮어쓰인다. 그래서 화면 기준 기획서 상태는 다섯 가지이고, "draft가 아니다"가 곧 "사용자 검토에 도달했다"가 된다. R1의 경계를 여기에 맞췄다.
- 정규화가 알 수 없는 상태를 `draft`로 떨어뜨린다는 점도 확인했다. 상태 오타가 난 기획서는 영원히 반영중으로 보인다는 뜻이라 확인 사실에 명시했다.
- `read_active_leases`는 `expires_at`이 현재보다 뒤인 lease만 담고 `AgentLeaseSummary`(`lease_id`·`agent`·`task_id`·`expires_at`)로 내려보낸다. `task_id`는 `Option`이다. R3의 세 조항이 여기서 나왔다.
- `activeLeases`는 `ProjectSummary` 수준(프로젝트 전역)이고 아이디어는 워크플로우 디렉터리 안에 있다. lease 문서에 워크플로우 참조 필드가 없어서 문서 id 충돌 시 판정이 겹칠 수 있다. 새로 해결하지 않고 R3에 전제로 적었다.
- 화면 표시 지점은 `IdeaInbox.tsx` 두 곳뿐이다. 목록 행의 아이콘(`stamp`/`idea`)과 `기획 반영` 태그, 미리보기의 상태 배지(`수집됨`/`기획서 채택`). 상태 소비처가 이 파일 하나라 R4의 범위가 좁게 유지된다.
- 목록 태그 문구가 `기획 반영`이라는 것을 이 파일에서 확인했다. 새 상태 이름 "반영중"과 글자가 겹쳐서 같은 화면에 둘 다 나오면 뜻이 섞인다. 완료 조건 13번을 따로 둔 이유다.
- `wf-eligible.sh`(`heartbeat_condition.rs`)의 기획자 판정은 `grep -qs "source_idea_id: *$id" "${wf}"specs/*.md` 한 줄이다. 화면 표시와 자격 판정이 애초에 다른 코드라, 화면만 바꾸는 이 기획서가 자격 판정을 건드리지 않는다는 사실이 확인된다. 완료 조건 22번이 이걸 고정한다.
- 기획자 계약(`rules/roles/planner.md`)의 "claim 직후 draft 스켈레톤, 마지막에 user_review + lease 해제" 순서를 확인했다. 정상 종료 세션은 "user_review + lease 없음", 죽은 세션은 "draft + lease 없음"을 남긴다. R5의 중단 의심 판정이 이 비대칭에 기댄다.
- `useProjectWorkspace.ts`의 2.5초 폴링이 유일한 갱신 경로다. R8이 "다음 조회에서 바뀐다"로 쓰인 근거다.

## 확인 필요 3건의 배경

1. **중단 의심을 네 번째 상태로 둘지**: 아이디어가 명시적으로 기획에 맡긴 항목이다. 상태 축(파이프라인 단계)과 건강 축(고장 신호)을 섞지 않는 쪽을 제안했지만, 자동 루프의 고장 감지를 더 중시한다면 네 번째 상태가 세기 쉽다는 반론을 함께 적었다. 이 결정이 R4·R5의 표현과 완료 조건 11·14번의 형태를 바꾼다.
2. **수정 요청 재작업 중인 아이디어**: 계약상 수정 요청 재작업은 새 ID의 기획서를 만들므로 한 아이디어를 여러 기획서가 참조하는 상태가 실제로 생긴다. 아이디어 원문은 이 경우를 다루지 않아서 기획에서 규칙을 정했다(R2). "draft 하나라도 있으면 반영중"이 되어 채택에서 뒤로 돌아가 보이는 점이 트레이드오프다.
3. **걸려 있는 기획서 짚어 주기**: R5가 행동 가능한 경고를 요구하는데, 문서 id 없이는 사용자가 `specs/`를 뒤져야 한다. 표시까지만 제안하고 기획서로 이동하는 동작은 제외 범위에 뒀다.

## 핸드오프 노트 (이 세션 범위 밖)

- **SPEC-010 수정 요청이 대기 중이다 (우선순위 높음)**: DECISION-FEB99DAB(01:44:10Z, `revision_requested`)가 이 세션 진행 중에 기록됐다. 기획자 계약에 따라 새 ID의 기획서를 만들고 SPEC-010과 이 결정 id를 참조해야 하며, SPEC-010은 보존한다. 추가 요구는 선점(claim) 헬퍼를 조건 스크립트와 같은 방식으로 `.workflow/rules/`에 앱 관리 자산으로 설치하고, 공통 규칙의 선점 절차를 헬퍼 기준으로 갱신하는 것이다. 이 아이디어(SPEC-012)와 원천이 겹친다 — 양쪽 다 lease를 판정 근거로 쓰므로, 개선 기획서를 쓰는 세션이 SPEC-012의 R3을 함께 읽는 것이 좋다.
- **남은 미처리 아이디어 2건**: IDEA-54B29779(연동 Windows 지원, 조건 스크립트 플랫폼별 설치)와 IDEA-48EDAF2B(하트비트 설치 안내 마법사). 둘 다 2026-08-03T01:33Z 생성이고 lease가 없다. 다음 기획자 세션이 가져갈 수 있다. 위의 SPEC-010 재작업이 먼저다.
- **TASK-027과 같은 파일을 만진다**: SPEC-008의 TASK-027(아이디어 미리보기를 문서 뷰어로 전환)이 아직 `todo`이고, 이 기획서의 R4도 같은 `IdeaInbox.tsx`의 미리보기 패널을 만진다. 둘이 병렬로 진행되면 충돌한다. SPEC-012가 승인되면 아키텍트가 TASK-027 뒤로 순서를 잡는 편이 안전하다. 판단은 아키텍트 몫이다.
- **lease를 읽는 곳이 넷째로 늘어난다**: REPORT-SPEC-010-PLAN과 REPORT-SPEC-011-PLAN이 각각 같은 지적을 남겼다. SPEC-010(의존 판정), SPEC-011(활동 뷰), 그리고 이 기획서(아이디어 반영중 판정)가 모두 `activeLeases`를 서로 다른 규칙으로 읽는다. 이 기획서는 새 필드를 요구하지 않아 읽기 통로 확장은 없지만, 해석이 세 곳에 흩어지는 문제는 그대로다. 아키텍트가 볼 필요가 있다.
- **판정 규칙이 두 곳에 있다**: `workflow_items`와 `read_idea`가 각자 `adopted_idea_ids`를 호출한다. 지금은 규칙이 한 줄이라 중복이 싸지만 세 갈래 판정으로 바뀌면 두 곳이 어긋날 여지가 생긴다. 완료 조건 19번이 결과의 일치만 요구하고 구현 방식은 정하지 않았다.
- **조건 스크립트와 화면의 결론이 갈린다**: 이 변경 후 화면은 "반영중(중단 의심)"이라고 말하는데 조건 스크립트는 그 아이디어를 자격 없음으로 계속 건너뛴다. 의도한 것이고(제외 범위에 근거를 적었다) 완료 조건 22번이 현행 동작을 고정하지만, 사용자가 "고장이 보이는데 앱이 아무것도 안 한다"고 느낄 수 있다. 죽은 세션의 회수 정책은 별도 아이디어로 다룰 문제다.
- **만료 lease 파일 누적**: 이 기획서는 만료 lease를 판정에서 제외하기만 하고 정리하지 않는다. REPORT-SPEC-011-PLAN이 같은 지적을 남겼고 상태는 그대로다. 실제로 이 세션 시작 시점에 `SPEC-009.yml`이 2026-08-03T01:20:00Z에 만료된 채 남아 있었다.
