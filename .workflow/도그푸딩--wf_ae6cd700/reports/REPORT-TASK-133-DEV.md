# TASK-133 개발 보고서

## 결정권자 요약

프로젝트 열기와 수동 새로 고침에서만 관리 규칙 동기화를 실행하도록 연결했다.
프로젝트 조회 결과는 동기화보다 먼저 화면 상태와 최근 프로젝트 기록에 보존된다.
동기화 충돌이나 명령 오류가 생겨도 읽은 프로젝트와 일반 오류 상태는 유지된다.
자동 조회는 관리 규칙을 쓰지 않으며 마지막 동기화 결과와 오류도 지우지 않는다.
네 가지 결과와 자산별 버전, 실패 사유, 복구 위치를 손실 없이 화면 계층에 제공한다.
프런트엔드 검사 710개와 타입 검사, 배포 빌드가 모두 통과했다.
화면 표시는 다음 작업에서 추가하며 현재 작업은 사용자 확인을 기다린다.

## 구현 내용

### 결과와 상태 계약

- `types.ts`에 관리 자산 전체 결과, 자산별 상태, 롤백 실패와 복구 위치 타입을 백엔드 응답과 같은
  모양으로 추가했다.
- 작업 공간 상태는 진행 여부, 마지막 구조화 결과, 명령 오류, 실행 계기를 서로 분리한다.
- 프로젝트 게이트웨이는 `synchronize_managed_project_assets` 명령을 별도 메서드로 호출한다.

### 호출 시점과 오류 격리

- 폴더 선택과 최근 프로젝트 열기는 프로젝트 조회가 성공한 뒤 현재 문서 규격일 때만 동기화한다.
- 수동 새로 고침도 조회 뒤 동기화하며 두 단계가 끝날 때까지 기존 진행 상태를 유지한다.
- 초기화되지 않았거나 마이그레이션이 필요하거나 더 새로운 문서 규격이면 동기화하지 않는다.
- 2.5초 자동 조회는 기존 프로젝트와 연동 조회만 호출하고 관리 자산 동기화를 호출하지 않는다.
- 동기화 명령 오류는 일반 프로젝트 오류와 별도로 저장한다. 읽은 프로젝트와 최근 프로젝트 기록은
  그대로 유지한다.
- 프로젝트를 닫으면 해당 프로젝트의 관리 자산 상태도 함께 비운다.

## 검증 결과

- 명시적 폴더 열기, 최근 프로젝트 열기, 수동 새로 고침의 조회 후 동기화 순서를 확인했다.
- 비호환 프로젝트와 조회 실패에서는 동기화가 호출되지 않는지 확인했다.
- 동기화 명령 실패 뒤에도 프로젝트와 최근 기록이 유지되는지 확인했다.
- 가짜 시간을 7.5초 진행해 자동 조회가 세 번 늘어도 동기화 호출과 마지막 상태가 바뀌지 않는지 확인했다.
- `npm test -- src/features/projects/application/useProjectWorkspace.test.ts --maxWorkers=1`: 48개 통과.
- `npm run check`: 프런트엔드 710개 검사, 타입 검사, 배포 빌드 통과.
- `git diff --check`: 통과.

## 남은 위험과 후속

- 번들 크기 경고는 기존 빌드 경고로 남아 있으며 이번 호출 시점 변경과 무관하다.
- TASK-134가 이 상태를 설정 카드와 공통 알림에 표시한다.
- TASK-136은 사용자 정의 규칙 조회와 저장 상태를 같은 작업 공간 수명에 추가한다.
