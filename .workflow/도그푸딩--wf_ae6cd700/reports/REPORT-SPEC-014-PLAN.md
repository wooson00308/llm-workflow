# SPEC-014 기획자 핸드오프

- 역할: 기획자 (planner)
- 대상: IDEA-54B29779 (연동의 Windows 지원 해제, 플랫폼별 조건 스크립트 설치)
- 산출 기획서: SPEC-014 (`status: user_review`)
- 세션: 2026-08-03T04:21Z ~ 04:33Z

## 무엇을 했나

선점 시점(04:22Z)에 기획자 대상은 미처리 아이디어 4건이었다. IDEA-54B29779와 IDEA-48EDAF2B(둘 다 01:33Z), IDEA-08303478(02:05Z), IDEA-C95EABD2(02:26Z). `revision_requested` 결정은 DECISION-FEB99DAB 하나뿐인데 SPEC-013이 이미 후속 기획서로 처리했으므로 대상이 아니다.

그중 IDEA-54B29779를 골랐다. 근거는 `created_at` 최선착이다. 계약에 우선순위 규칙이 없어서 판단 근거를 하나 정해야 했고, 네 아이디어 사이에 긴급도 차이를 주장할 재료가 없었다. IDEA-C95EABD2가 바로 이 공백(재작업과 새 아이디어의 우선순위를 계약에 명시)을 다루고 있으니, 규칙이 생기면 이 판단을 대체하면 된다.

`.workflow/.runtime/leases/IDEA-54B29779.yml`을 배타적 생성(`set -o noclobber`)으로 선점하고, 즉시 SPEC-014 스켈레톤(`status: draft`)을 만든 뒤 본문을 작성했다. 완료 후 `user_review`로 올리고 lease를 해제했다.

작성 근거는 앱 코드(`heartbeat_condition.rs`·`heartbeat_roles.rs`·`heartbeat_status.rs`·`heartbeat_service.rs`, 연동 화면 세 파일)와 현재 설치된 하트비트 소스(`~/Git/claude-heartbeat`, 편집 가능 설치라 이 소스가 실행본이다)에서 직접 확인했다.

## 결정 사항

- **판정 로직 변경을 제외 범위로 뺐다.** 두 구현 모두 현행 `sh`의 판정을 그대로 옮긴다. 조건 스크립트의 판정 기준을 손보자는 IDEA-C95EABD2가 인박스에 있는데, 그것과 섞으면 "옮겼는데 결과가 달라졌다"와 "일부러 바꿨다"가 한 diff에서 구분되지 않는다. 옮기기와 고치기를 분리했다.
- **`skipped` 오표시 수정을 범위에 넣었다(R8, 확인 필요 4번).** 하트비트는 조건 불충족과 조건 실행 실패를 모두 `last_result: "skipped"`로 적고, 앱 카드는 그것을 "건너뜀 · 처리할 대상 없음"으로 번역한다. 즉 스크립트가 아예 실행되지 못해도 화면은 "대상 없음"이라고 단정한다. Windows 차단을 푸는 순간 이게 Windows 사용자가 가장 먼저 만날 화면이라, 차단 해제와 같은 범위에 두는 것이 맞다고 봤다. 범위 확대라는 반론이 있어 확인 필요로 올렸다.
- **slug 문제를 범위에 넣었다(R7).** 앱의 slug 생성은 경로 문자열의 `/`를 `-`로 바꾸는 규칙이라 구분자가 `\`인 Windows 경로에서 무엇이 나오는지, 하트비트의 역변환(`/`부터 최장 일치로 내려가는 추정)이 그것을 되돌릴 수 있는지 확인되지 않았다. 이게 깨지면 조건 검사의 cwd가 프로젝트 루트가 아니게 되고 상대 경로 조건이 전부 실패한다. 즉 스크립트를 아무리 잘 만들어도 안 돈다. 아이디어가 명시하지 않은 항목이지만 같은 실패(침묵 skip)를 만드는 원인이라 넣었다.
- **dream을 함께 여는 쪽을 제안했다(확인 필요 3번).** "플랫폼 지원 여부는 섹션 공통 정책"이 SPEC-003의 승인된 결정이고, dream만 막으려면 연동별 지원 판정이라는 축을 새로 만들어야 한다. 대신 dream 잡의 조건이 외부 명령(`dream-prep`)이라 앱이 보증하지 않는다는 사실을 카드에 밝히는 것을 R11로 요구했다.
- **선점 헬퍼의 플랫폼 대응을 범위에 넣었다(R10).** 작성 중에 SPEC-013이 DECISION-73D4BC1B(04:18:48Z, `created_by: user`)로 승인된 것을 확인했다. 그 결정문이 확인 필요 2번을 "이번에는 POSIX sh만, Windows 대응 시 헬퍼 포함 의무를 IDEA-54B29779 범위에 부채로 명시"로 확정했으므로, 헬퍼를 여기서 맡는 것은 이미 내려진 사용자 결정이다. 물어볼 항목이 아니라 받아야 할 부채로 다뤘다.
  - 초안에서는 SPEC-013 파일의 `status: user_review`만 보고 미결정으로 판단해 헬퍼를 제외 범위에 뒀다가, 결정 문서를 확인하고 되돌렸다. 기획서 상태는 파일 값이 아니라 최신 결정이 결정한다(SPEC-012 확인 사실).
  - 다만 헬퍼의 `sh` 구현은 아직 파일로 없다. `source_decision_id: DECISION-73D4BC1B`를 참조하는 작업 문서가 하나도 없다. 그래서 "조건 스크립트만으로 먼저 열지, 헬퍼까지 갖춘 뒤 한꺼번에 열지"를 확인 필요 5번으로 올렸다.
- **PowerShell 실행 정책을 확인 필요 1번으로 올렸다.** Windows 클라이언트의 기본 실행 정책은 `.ps1` 실행을 막고, 그 상태에서 조건 검사는 실패한 뒤 skip으로 끝난다. 앱이 우회 형태를 파일에 박는 것이 맞는지는 보안 정책 판단이라 사용자 결정으로 올렸다. 호출 형태의 구체적 인자 조합은 아키텍트 몫으로 남겼다.
- **파일 이름을 확정하지 않았다.** 아이디어가 제안한 `wf-eligible.ps1`을 그대로 적되, 최종 이름은 R6(중복 감지 규칙)과 같은 근거를 쓰라는 조건만 걸고 아키텍트에게 남겼다.

## 아키텍트에게 넘기는 사실

- **Windows 차단 지점은 상수 하나와 그 파생 셋이다.** `heartbeat_service.rs`의 `PLATFORM_SUPPORTED = !cfg!(windows)`가 스냅샷의 `supported`로 나가고, 화면 세 곳(연동 뷰 배너, 하트비트 카드 버튼 둘, dream 카드 버튼)이 그것을 읽는다. 잡 설치 경로 둘(`install`·`install_dream`)은 진입 즉시 `UnsupportedPlatform`으로 거부한다. 차단 해제는 이 다섯 자리의 문제다.
- **중복 감지 규칙이 확장자에 묶여 있다.** `is_role_condition`은 조건 문자열에 `wf-eligible.sh`가 들어 있는지로 역할 잡을 식별한다. PowerShell 조건은 이 규칙을 통과하므로 중복이 감지되지 않는다. 감지 규칙과 파일 이름 결정이 서로 물려 있다(R1·R6).
- **조건 스크립트 실행 테스트가 전부 `#[cfg(unix)]`다.** `sh`를 실제로 실행하기 때문이다. R3의 판정 일치 테스트는 이 구조를 뒤집어야 하고, 그 방법이 확인 필요 2번의 결정에 달려 있다. 사용자 결정 없이 분해하면 테스트가 어디서 도는지 정해지지 않은 작업이 나온다.
- **Windows 실환경 검증이 필요한 완료 조건이 여섯이다(1·9·10·11·16, 그리고 4의 절반).** 이 저장소에는 지금 Windows 검증 경로가 없다. 분해할 때 "Windows에서 확인" 단계를 누가 어떻게 수행하는지가 작업의 완료 조건 안에 들어가야 하고, 그것이 확인 필요 2번의 러너 결정과 같은 결정에 묶인다.
- **조건 스크립트가 이제 세 벌이 될 수 있다.** 앱 설치본(`.workflow/rules/`) 외에 저장소의 `scripts/wf-eligible.sh`가 있고 `docs/heartbeat.md`가 그 경로를 공식 인터페이스로 안내한다. 두 벌 정리는 SPEC-002 확인 필요 1번에서 별도 아이디어로 미뤄져 있어 이 기획서도 손대지 않았다. PowerShell 구현이 들어오면 "설치본 2 + 저장소 1"이 되고, 저장소 쪽은 여전히 sh 하나다. R3의 일치 테스트가 무엇과 무엇을 대조하는지 분해 시점에 분명히 해야 한다.
- **조건 검사 실패는 fail-closed다.** 현재 하트비트 소스는 타임아웃(10초)과 예외에서 잡을 깨우지 않는다. PowerShell 기동 시간이 이 10초 안에 들어오는지는 확인하지 않았다. Windows 실환경 검증 항목에 함께 넣을 만하다.
- **`.workflow/`가 커밋되는 저장소라 두 플랫폼 자산이 공존한다.** R9가 이것을 정상 상태로 못박았다. 설치 액션이 현재 플랫폼 자산만 건드린다는 R2 조항과 짝이다.
- **DECISION-73D4BC1B에서 파생된 작업이 아직 없다.** SPEC-013은 승인됐는데 분해되지 않았다. 지금 아키텍트 대상 중 하나이고, 이 기획서가 승인되면 두 기획서의 작업이 같은 자산(`.workflow/rules/`의 실행 자산, 조건 스크립트 설치 모듈)을 건드린다. 확인 필요 5번의 결정에 따라 `depends_on`으로 순서를 걸어야 하는 구간이다.

## 역할 밖 발견

- **`skipped` 오표시는 지금도 틀릴 수 있다.** Windows와 무관하게, 조건 스크립트 파일이 없거나 `sh` 실행이 실패해도 카드는 "처리할 대상 없음"이라고 말한다. SPEC-014가 승인되면 그 안에서 고쳐지지만, 반려되면 이 오표시는 남는다. 별도 아이디어 후보다.
- **`.workflow/.runtime/leases/SPEC-009.yml`이 여전히 만료된 채 남아 있다.** `agent: architect-claude`, `expires_at: 2026-08-03T01:20:00Z`. REPORT-SPEC-013-PLAN이 같은 지적을 남겼고 그 뒤로도 정리되지 않았다. 남의 lease라 이 세션은 건드리지 않았다.
- **`docs/heartbeat.md`가 sh 경로만 안내한다.** Windows를 열면 이 문서는 Windows 사용자에게 반쪽이 된다. SPEC-002 확인 필요 1번의 결정 때문에 이 기획서의 제외 범위로 뒀지만, 두 벌 정리 아이디어가 나올 때 Windows 안내도 같이 다뤄야 한다.
- **조건 스크립트의 `planner` 분기는 여전히 `revision_requested`를 보지 못한다.** 이번 세션도 인박스에 아이디어가 있어서 깨어났다. IDEA-C95EABD2의 범위이고 이 기획서는 판정 로직을 옮기기만 하므로 공백은 그대로다.
- **남은 미처리 아이디어 3건.** IDEA-48EDAF2B(하트비트 설치 마법사), IDEA-08303478(실행 한도 "제한 없음"), IDEA-C95EABD2(수정요청·반려 회수 정책). 모두 lease가 없다.
  - IDEA-48EDAF2B의 설치 마법사는 단계별 감지 기준을 정의하는 것이 핵심인데, 이 기획서가 Windows를 열면 그 감지 기준도 플랫폼별로 갈린다. SPEC-014의 결정 이후에 기획하는 편이 낫다.
  - IDEA-08303478은 SPEC-009에서 나온 TASK-028~031과 같은 화면·같은 payload를 건드린다고 스스로 적고 있다.

## 세션 종료 시점에 도착한 결정 — 반드시 읽을 것

세션이 끝나기 직전 DECISION-2F71D20D(04:35:08Z, `created_by: user`, `outcome: revision_requested`)가 SPEC-014에 기록됐다. 방향과 확인 필요 1~4번은 모두 동의이고, 사유는 확인 필요 5번 하나다. 다음 기획자 세션이 이 결정으로 개선판(새 ID)을 만들 때 알아야 할 것을 남긴다.

- **결정이 본 SPEC-014와 지금 파일의 SPEC-014가 다르다.** 결정이 지적한 것은 "선점 헬퍼를 범위에서 뺐다"인데, 이 세션이 같은 분(04:32~04:35Z)에 SPEC-013 승인(DECISION-73D4BC1B)을 발견하고 이미 되돌렸다. 지금 파일의 R10은 헬퍼를 포함하고, 확인 필요 5번은 "포함하되 무엇을 먼저 열지"를 묻는 항목으로 바뀌어 있다. 결정문의 첫 두 요청은 현재 파일에서 이미 대부분 충족돼 있다.
- **결정이 요구한 사실 갱신은 아직 반영되지 않았다.** 확인 필요 2번의 반대 근거가 "이 저장소는 단일 플랫폼 검증으로 굴러 왔다"고 전제하는데, 결정문에 따르면 CI는 이미 ubuntu·windows·macos 3 러너 매트릭스를 돌린다(v0.1.6 핫픽스 2건이 Windows 러너 실패 수습이었다). 즉 확인 필요 2번의 "러너 추가 비용"이라는 반대 근거 자체가 성립하지 않는다. 개선판은 이 전제를 현행 사실로 바로잡고, 그렇게 되면 2번은 사실상 결정이 필요 없는 항목이 될 수 있다. 개선판 작성 전에 CI 워크플로우 파일에서 직접 확인할 것.
- **개선판은 새 ID로 만들고 SPEC-014를 보존한다**(공통 규칙 §5). 프론트매터에 `source_spec_id: SPEC-014`·`source_decision_id: DECISION-2F71D20D`를 두고 원 아이디어 `source_idea_id: IDEA-54B29779`도 유지한다. SPEC-013이 같은 상황에서 쓴 형식이다.
- **확인 필요 5번의 남은 질문은 유효하다.** 결정문도 "실행 순서는 SPEC-013의 헬퍼(sh)가 존재한 뒤가 되도록 `depends_on` 또는 실행 순서 명시로 아키텍트가 걸게 한다"로 답을 줬다. 개선판에서는 이것을 질문이 아니라 확정된 결정으로 본문에 반영하면 된다.

## 상태

SPEC-014는 `user_review`로 올렸고, 그 직후 DECISION-2F71D20D로 `revision_requested`를 받았다. 확인 필요 1·3·4번은 결정문이 이미 동의했고, 2번은 사실 갱신 뒤 다시 볼 항목이며, 5번은 결정문이 실행 순서 지침으로 답을 줬다. IDEA-54B29779 lease는 해제했다.

이 세션은 여기서 멈춘다. 개선판 작성은 DECISION-2F71D20D를 선점하는 다음 기획자 세션의 몫이다(공통 규칙 §3, 한 세션 한 대상). 작업 분해나 구현으로 넘어가지 않는다.
