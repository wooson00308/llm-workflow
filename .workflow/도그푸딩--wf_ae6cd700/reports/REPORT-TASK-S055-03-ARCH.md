# TASK-S055-03 작업 정의 수정 보고서

## 결정권자 요약

판정 결과가 대상 종류를 담을 수 없었던 작업 정의 오류를 바로잡았다.
결과 구조와 요청 기록을 판정 입력으로 넘기는 조회 경로를 작업 범위에 추가했다.
두 대상 종류의 값을 승인 분해와 작업 정의 수정 요청으로 각각 고정했다.
기존 막힌 사유와 개발 보고서와 이력은 그대로 보존했다.
현재 규칙에 따라 작업을 개발 준비 상태로 돌렸고 사용자 재개 이력은 만들지 않았다.
제품 코드는 바꾸지 않았으며 개발자는 수정된 범위와 완료 조건으로 다시 착수할 수 있다.

## 수정 근거

- TASK-S055-03의 `blocked_kind: definition_error`와 `## 막힌 사유` 절을 근거로 삼았다.
- REPORT-TASK-S055-03-DEV가 완료 조건 8과 9를 만족하려면 앱 판정 결과에 대상 종류를 담을 별도 자리가
  필요하다고 기록했다. 기존 후보 판정 코드는 제외 사유와 같은 어휘를 쓰므로 종류를 섞을 수 없다는 판단도
  그대로 채택했다.
- 앱 소유 작업 정의 수정 요청 기록은 없었다. 따라서 `revision_request_id`를 추가하지 않았다.
- SPEC-055와 앱 소유 승인 DECISION-22C3CC2F를 다시 읽어, 미처리 수정 요청을 승인 분해보다 먼저 고르고
  두 판정이 같은 답을 내게 하는 승인 범위 안의 수정임을 확인했다.

## 수정 전후

- 상태: `blocked`에서 `todo`로 돌렸다. 현재 공통 규칙 20과 아키텍트 계약 13이 정의 오류 수정 뒤 이
  상태 전환을 요구한다. 기존 이력은 세 항목을 그대로 보존했고 `resumed` 항목을 추가하지 않았다.
- 선언 범위: 기존 세 파일에 `src-tauri/src/domain/project.rs`와
  `src-tauri/src/infrastructure/fs_project_repository.rs`를 추가했다. 앞 파일은 판정 결과 구조를, 뒤 파일은
  요청 기록 읽기와 앱 판정 입력 조립을 맡는다.
- 선행 관계: TASK-S055-01과 TASK-S055-02를 그대로 보존했다. 새로 추가한 조회 파일은 TASK-S055-02와
  겹치지만 그 작업이 이미 선행이다.
- 대상 종류: 승인 결정은 `spec_approval`, 작업 정의 수정 요청은 `task_revision_request`로 고정했다.
  대상이 없으면 종류도 비어 있게 했다. 설치되는 판정 도구의 기계 출력은 같은 값을 `targetKind`에 싣고,
  기존 호출의 표준 출력과 종료 코드와 기계 출력 스키마 버전은 유지하게 했다.
- 본문: 범위 사전 검사, 우선순위, 두 판정의 일치, 완료 조건 8, 검증 절차 4와 범위·선행 설명을 위 결정에
  맞게 고쳤다. 기존 막힌 사유 절은 한 글자도 바꾸지 않았다.

## 범위 사전 검사 근거

- `src-tauri/src/domain/project.rs`의 `RoleWorkVerdict`는 현재 `target`과 `candidates`만 가진다. 별도 대상
  종류가 없다는 개발 보고서의 차단 근거를 확인했다.
- `src-tauri/src/infrastructure/fs_project_repository.rs`의 `PreparedWorkflow`가 앱 판정용
  `WorkflowInput`을 조립한다. 같은 파일의 `read_revision_request_records`가 작업 정의 수정 요청 문서를
  읽고 `handled_revision_request_id`가 처리 여부의 근거를 제공한다. 이 값을 판정 입력으로 넘기지 않으면
  앱 판정은 요청 후보 자체를 알 수 없으므로 결과 구조 파일만 추가해서는 범위가 충분하지 않다고 판단했다.
- `src-tauri/src/infrastructure/role_eligibility.rs`는 파일 시스템을 직접 읽지 않는 순수 판정 모듈이다.
  저장소 조회가 준비한 요청 후보를 받아 우선순위와 종류를 정하는 현재 구조를 유지한다.
- `src-tauri/src/infrastructure/heartbeat_condition.rs`는 셸과 PowerShell 판정 본문, 기계 출력과 두 구현의
  버전 축을 함께 가진다. `src-tauri/src/infrastructure/managed_project_assets.rs`는 새 관리 자산 본문 설치와
  미래 버전 보존 검사를 고정하므로 둘 다 기존 범위에 남겼다.
- `src-tauri/src/infrastructure/reservation_helper.rs`도 검토했지만 제외했다. 이 작업은 대상 식별자를 그대로
  선점하는 기존 계약을 바꾸지 않고, 대상 종류는 판정 도구의 기계 출력과 앱 판정의 동치를 확인하는 범위다.

## 검증

- 작업 문서의 id, 기획서·승인 참조, 선행 관계와 기존 이력 세 항목이 수정 전과 같은지 대조했다.
- `status: todo`, `blocked_kind: definition_error`, 막힌 사유 절의 네 표식이 각각 한 번 있는지 확인했다.
- `scope_files`가 한 줄 흐름 시퀀스이며 다섯 경로가 실제 파일로 존재하는지 확인했다.
- 구조화 결정권자 요약의 필수 제목과 영향 범위 표식 순서를 확인했다.
- 제품 코드와 결정 문서는 수정하지 않았다.

## 남은 위험

- 저장소 조회 파일 추가는 최초 개발 보고서가 제시한 두 대안 중 하나보다 범위가 한 파일 넓다. 실제 코드
  대조에서 요청 후보를 앱 판정 입력으로 넘기는 유일한 배선이 그 파일에 있음을 확인해 추가했다. 이를 빼면
  대상 종류 자리는 생겨도 앱 판정이 미처리 요청을 선택할 수 없다.
- 같은 작업에 여러 수정 요청이 생길 때 작업 문서의 연결 필드 하나가 마지막 요청만 가리키는 한계는
  TASK-S055-02 개발 보고서에 남아 있다. 이번 수정은 그 승인된 판정 근거를 바꾸지 않는다.
