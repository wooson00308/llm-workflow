# TASK-S052-01 아키텍트 수리 보고서

## 결정권자 요약

규칙 버전을 올리면 다른 파일 두 개에 박혀 있는 이전 버전 문자열이 반드시 함께 깨진다.
그 두 파일이 작업 범위 밖이어서 개발 세션이 범위 조건과 전체 검사 통과 조건을 같이 지킬 수 없었다.
두 파일을 범위에 넣고 완료 조건을 네 파일 기준으로 다시 써서 그 충돌을 없앴다.
두 파일에서는 버전 문자열만 고치고 검사를 지우거나 약하게 만들지 못하도록 조건을 하나 더 세웠다.
그사이 다른 작업이 규칙 버전을 16으로 올렸으므로 이 작업의 목표 버전도 현재 사실에 맞춰 갱신했다.
범위가 겹치는 그 작업을 선행으로 적어 두 작업이 같은 시각에 같은 파일을 고치지 않게 했다.
구현 대상인 구조화 요약 계약 자체는 승인된 범위 그대로다.
상태는 막힘 그대로 두었고 이력에도 아무 항목을 넣지 않았다.

## 판단 근거

### TASK-148을 선행으로 추가한 이유

범위를 넓힌 결과 이 작업과 TASK-148의 파일이 세 개 겹친다. `docs/file-contract.md`,
`project_instructions.rs`, `fs_project_repository.rs`다. 아키텍트 계약은 겹치는 쌍을 `depends_on`으로
순서를 정하고 뒤에 오는 쪽에 그 필드를 쓰라고 요구한다. 이 작업이 TASK-148이 만든 버전 16과 재개 계약
문언 위에 17을 올리므로 뒤에 오는 쪽은 이 작업이다.

TASK-148은 현재 `qa_waiting`이다. 자격 판정은 선행이 `qa_waiting` 또는 `completed`이면 충족으로 보므로
이 의존은 재개를 지연시키지 않는다. 대신 TASK-148이 QA에서 수정 요청을 받아 다시 열릴 경우 두 작업이
같은 파일을 동시에 고치는 상황을 막는다.

### 범위를 넓히는 것과 작업을 쪼개는 것 중 넓히기를 택한 이유

개발 보고서는 두 방법을 제시했다. 두 파일을 범위에 넣거나, 단언 갱신을 별도 선행 작업으로 분리하는
것이다. 분리를 택하지 않았다. 갱신할 문자열의 값이 이 작업이 정하는 새 버전 번호에 달려 있어서, 선행
작업이 혼자서는 무엇으로 바꿀지 결정할 수 없다. 두 작업으로 나누면 그사이 전체 검사가 실패하는 구간이
생기고, 어느 쪽도 단독으로 통과 상태를 만들지 못한다. 한 작업 안에서 버전 상승과 문자열 갱신을 함께
하는 편이 검증 가능한 단위다.

대신 넓힌 범위가 다른 변경의 통로가 되지 않도록 완료 조건 11과 검증 절차 5로 변경 성격을 버전 문자열로
한정했다.
