# GROUP-061 승인 분해 아키텍트 핸드오프

- 역할: 아키텍트 (architect)
- 대상: DECISION-85309F56 (SPEC-061 승인, `outcome: approved`, `created_by: user`)
- 산출물: GROUP-061 (`status: active`, `revision: 1`, `qa_mode: user`), TASK-S061-01, TASK-S061-02
- 예약: 런타임 예약 대상 DECISION-85309F56, lease `lease-15035-20260818043402`, 결과 prefix
  `RES-20260818T043402Z-15035-20260818043402`
- 세션: 2026-08-18T04:34Z ~ 04:50Z

## 결정권자 요약

승인된 SPEC-061을 개발 작업 둘로 나눴다. 첫 작업은 기획서·품질 확인 메뉴의 결정 대기 숫자와
워크플로우 목록의 대기 점을, 둘째 작업은 아이디어·개발 메뉴의 변경 점과 마지막 확인 시점 기록을
맡는다. 두 작업 모두 화면 쪽 변경만으로 끝나며, 백엔드에 새로 요청할 값이 없다는 것을 코드에서
확인했다.

품질 확인은 사용자 확인 방식으로 정했다. 바뀌는 결과가 사이드 메뉴에서 사용자가 직접 보는 숫자와
점이고, 메뉴를 열었을 때 점이 꺼지는지와 워크플로우를 오갈 때 판단이 유지되는지는 화면을 실제로
조작해야만 확인할 수 있다.

## 무엇을 했나

런타임이 예약한 대상 하나만 처리했다. `sh .workflow/rules/wf-claim.sh renew DECISION-85309F56
lease-15035-20260818043402 30`으로 소유를 먼저 확인했고(exit 0), `acquire`는 부르지 않았다.
`.workflow/.runtime/migration.lock`은 없었고, `.workflow/rules/custom.md`도 없어 프로젝트 커스텀
규칙은 적용하지 않았다.

claim 뒤 자격을 다시 확인했다. SPEC-061을 가리키는 결정은 `decisions/`에 DECISION-85309F56
하나뿐이고 `outcome: approved`에 `created_by: user`다. SPEC-061 또는 그 결정을 참조하는 작업
그룹은 `groups/` 어디에도 없었다. 다른 세션이 먼저 처리한 흔적은 없었다.

claim 직후 GROUP-061을 `status: preparing`으로 먼저 만들어 근거 문서 참조와 사용자 품질 확인 동선을
적었다. 그 뒤 코드를 읽고 작업 둘을 만들었으며, 두 작업 문서와 범위 사전 검사를 마친 다음 그룹을
`active`로 올렸다.

### 문서 이름

계보 규칙대로 붙였다. 기획서 번호가 061이므로 그룹은 GROUP-061, 작업은 TASK-S061-01과
TASK-S061-02다. 결과 prefix는 이 보고서에만 적었고 문서 식별자에는 넣지 않았다. 세 경로 모두 쓰기
전에 존재 여부를 확인했고 셋 다 비어 있었다.

## 작업을 둘로 나눈 근거

기획서가 "두 가지 표시를 구분하는 이유" 절에서 스스로 그은 경계를 그대로 썼다.

- TASK-S061-01: R1, R2, R4, R7, R8, R9. 결정 대기를 세어 숫자와 점으로 알린다. 세 표시 자리가 모두
  같은 판정 하나에서 나오므로 한 작업으로 묶었다. 판정을 만드는 작업과 그것을 쓰는 작업을 나누면
  경계가 판정 한가운데를 지나가고, A1이 요구하는 "오늘 화면과 같은 수"를 어느 쪽도 혼자 보증하지
  못한다.
- TASK-S061-02: R3, R5, R6. 마지막 확인 시점을 새로 기록하고 그것으로 변경 점을 판단한다. 이 작업만
  화면에 없던 값을 새로 만들고 브라우저 저장소 모듈을 새로 세운다.

순서는 TASK-S061-01 → TASK-S061-02다. 둘 다 `src/features/projects/components/WorkspaceShell.tsx`,
그 시험 파일, `src/App.css`를 편집하므로 동시에 진행할 수 없다. `depends_on: [TASK-S061-01]`을
둘째 작업에 적었다. 첫 작업을 앞에 둔 이유는 새 저장소 없이 완결되고, 배지와 접근 이름의 표현
방식을 먼저 세워 두면 둘째 작업이 거기에 맞추기만 하면 되기 때문이다.

병렬 여지를 일부러 버린 것이 아니다. 이 기획의 변경 지점이 사이드 메뉴 화면 파일 하나에 모여 있어
실제로 겹친다. 겹치지 않는 작업을 줄 세우지 않았다.

## 코드에서 확인한 사실

- 결정 대기 판정이 이미 `WorkspaceShell.tsx`에 있다. `readyQaFeatures`(186~189행),
  `pendingSpecs`(190~193행), `decisionCount`(195행)이며 472행 오늘 화면 배지가 그 값을 쓴다. 세
  화면이 같은 수를 말하게 하려면 사이드 메뉴가 이 판정을 그대로 써야 한다. TASK-S061-01의 C3이 그
  조건이다.
- 모든 워크플로우의 판정 재료가 이미 화면까지 온다.
  `src-tauri/src/infrastructure/fs_project_repository.rs` 1842~1853행이 워크플로우마다
  `PreparedWorkflow::read`를 돌리고 1891~1901행이 그 결과를 그대로 요약에 싣는다. R7의 다른
  워크플로우 판정에 백엔드 변경이 필요 없다는 근거다.
- 변경 판정에 쓸 마지막 변경 시각도 이미 온다. `read_markdown_summaries`(3890~3897행)가 문서의
  `updated_at`, 없으면 `created_at`, 그것도 없으면 파일 수정 시각 순으로 채운다. 다만 화면 타입
  `WorkflowItemSummary.updatedAt`(`types.ts` 48행)은 `string | null`이라 화면이 `null`을 다뤄야
  한다. TASK-S061-02의 C3에 그 처리를 적었다.
- 화면 진입 경로가 메뉴 버튼만이 아니다. `openSearchResult`(258~283행)가 269행과 273행에서
  아이디어 화면과 개발 화면을 직접 연다. 확인 시점 갱신을 버튼 클릭 처리에만 붙이면 이 경로에서
  새어 나간다. TASK-S061-02의 C4에 두 경로를 모두 적었다.
- 브라우저 저장소 열쇠가 지금 여덟 개 쓰이고 있다. 한 저장소를 여럿이 나눠 쓰므로 새 모듈이 전체를
  덮어쓰면 다른 기억이 지워진다. 여덟 열쇠를 소스에서 직접 뽑아 TASK-S061-02 본문에 적었고, 남의
  열쇠를 건드리지 않는 조건을 C2와 C11에 넣었다.
- 기존 `.count-badge`(`src/App.css` 181행)는 최소 너비와 높이가 28픽셀이라 메뉴 버튼 줄에 그대로 쓸
  수 없다. 두 작업 모두 새 선택자만 더하도록 못 박았다.

## 품질 확인 동선

사용자 확인 방식으로 정하고 QA-01 한 절에 전체 동선을 담았다. 작업별로 나누지 않았다. 사용자가
이 기능을 만나는 순서가 "사이드 메뉴를 한 번 훑고 → 숫자를 확인하고 → 메뉴를 열었다 나오며 점이
꺼지는지 보고 → 워크플로우를 오간다"이지 작업 경계를 따라가지 않기 때문이다. 수용 기준 A1부터
A9까지가 이 여덟 단계 안에 모두 들어간다. 터미널 명령, 패키지 실행기, 저장소 조작, 내부 자동 시험
절차는 넣지 않았다.

## 검증

- 문서 규격: 두 작업 모두 `scope_files`를 열 0의 한 줄 흐름 시퀀스로 적었고, `depends_on`도 같은
  어법을 썼다. 저장소 시험 8807~8828행이 블록 형식과 따옴표 형식을 형식 오류로 잡고 있어 그 형식을
  피했다.
- 그룹 본문 구조: `parse_work_group_body`(3226~3282행)가 `### QA-<두 자리> · 제목` 형태를 연속
  번호로 읽는다. QA-01 하나이므로 기대 식별자와 일치한다.
- 동선 안전성: `scenario_is_user_safe`(3284~3291행)와 `contains_internal_qa_instruction`
  (3412~3481행)이 막는 토큰 목록을 읽고 대조했다. 코드 울타리도 명령어 토큰도 넣지 않았고,
  화면·메뉴 같은 표면 낱말과 열다·확인하다 같은 동작 낱말이 본문에 들어 있어
  `scenario_describes_user_observable_flow`(3293~3410행)의 조건을 만족한다.
- 인용한 행 번호는 모두 이 세션에서 파일을 직접 열어 확인했다. 이전 작업 문서가 적어 둔 행 번호를
  그대로 옮기지 않았다.
- 코드는 실행하지 않았다. 아키텍트 세션이라 제품 소스와 시험을 건드리지 않는다.
- 세션 도중 다른 개발 세션이 `da76399`를 커밋해
  `src-tauri/src/infrastructure/fs_project_repository.rs`의 행 번호가 한 차례 밀렸다. 이 보고서와 두
  작업 문서에 적힌 그 파일의 행 번호는 모두 `da76399` 기준으로 다시 확인해 고쳤다. 프론트엔드 파일의
  행 번호는 그 커밋에 포함되지 않아 변동이 없었고, 이 역시 다시 확인했다. 두 작업 모두 그 저장소
  파일을 편집 대상으로 삼지 않으므로 번호가 다시 밀려도 작업 수행에는 영향이 없다.

## 후속과 리스크

- 그룹을 `active`로 올린 직후 개발 세션 하나가 TASK-S061-01을 선점해 `in_progress`로 옮겼다. 이
  보고서를 쓰는 시점의 상태이며, 이 세션이 옮긴 것이 아니다.
- 개발 세션은 TASK-S061-01을 먼저 가져가야 한다. TASK-S061-02는 첫 작업이 `verified`가 되기 전에는
  선언한 의존 때문에 시작할 수 없다.
- 두 작업 모두 `WorkspaceShell.tsx`의 같은 구역을 편집한다. TASK-S061-02의 본문에 적은 행 번호는
  첫 작업 이전 기준이므로, 둘째 작업 세션은 편집 전에 현재 파일을 다시 읽어 자리를 확인해야 한다.
  이 지시는 작업 문서 안에도 적어 두었다.
- 범위 밖 발견 하나를 핸드오프로 남긴다. 품질 확인 준비 완료 판정
  (`qaMode === "user" && displayStatus === "qa_ready"`)이 `WorkspaceShell.tsx` 186~189행과
  `src/features/projects/components/qa/QaWorkbench.tsx` 19행에 각각 따로 적혀 있다. 지금은 두 벌이
  같은 조건이지만 한쪽만 바뀌면 화면들이 다른 수를 말하게 된다. SPEC-061은 사이드 메뉴만 다루므로
  이번 두 작업의 범위에 넣지 않았다. 화면 사이의 중복을 정리하려면 새 아이디어가 필요하다.
- 확인 시점이 사용하는 컴퓨터에만 남는 것과, 새로 생긴 문서와 고쳐진 문서를 구분하지 않는 것은
  SPEC-061이 밝히고 사용자가 승인한 선택이다. 이번 작업으로 바꾸지 않는다.
