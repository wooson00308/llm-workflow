# 아키텍처 보고: 격리 작업 사본 기반 개발 세션과 통합 절차

## 결정권자 요약

승인된 기획서 SPEC-RES-20260815T030040Z-31959-20260815030040을 작업 그룹 GROUP-RES-20260815T032125Z-60360-20260815032125과 개발 작업 여섯 개로 나눴다.
확인해 보니 이 기획서는 두 저장소에 걸쳐 있다. 세션을 실제로 시작하고 감시하는 실행 환경은 별도로 배포되는 다른 저장소에 있고, 이 워크플로우는 앱 저장소에만 작업을 만들 수 있다.
그래서 앱 저장소가 소유한 부분만 이 그룹에 담았다. 규칙 본문, 예약 단계의 사본 준비와 실패 정리, 준비 기록, 통합 대기 판정, 저장 공간 상한, 품질 확인의 기준 고정, 그리고 격리를 지원하지 않는 실행 환경에서 개발 실행을 열지 않는 관문이다.
남긴 것은 준비된 사본을 세션의 작업 위치로 쓰는 일, 대기 해소를 감지해 다시 올리는 일, 실행 상태 단계를 앱에 전달하는 일이다. 이 셋은 실행 환경이 제공해야 하므로 별도 아이디어가 필요하다.
그 결과 이 그룹이 모두 끝나도 격리는 아직 실제 실행에 적용되지 않고, 자동 개발 실행은 지원 판이 나올 때까지 갱신 안내와 함께 멈춘다. 이는 예전 방식으로 조용히 되돌아가지 않기 위해 기획서가 요구한 동작이다.
품질 확인 방식은 자동 검증으로 정했다. 여섯 작업의 결과가 모두 내부 판정과 규칙 본문이라 비개발자가 화면에서 확인할 기능이 없기 때문이다.

## 대상과 자격 확인

- 대상은 런타임이 미리 예약한 승인 결정 DECISION-82CD54F4이며, 인계받은 lease를 갱신해 소유를 먼저 확인했다. 새로 acquire 하지 않았다.
- 마이그레이션 잠금은 없었고, 겹치는 lease도 없었다. 예약 시점에 존재한 lease는 이 대상의 것과 무관한 SPEC-009의 것 하나였다.
- 자격 재확인: DECISION-82CD54F4은 SPEC-RES-20260815T030040Z-31959-20260815030040에 대한 최신 앱 소유 승인이고, 이 결정이나 기획서를 참조하는 작업 그룹은 없었다. 결과 접두사가 가리키는 그룹·작업·보고서 경로도 모두 비어 있었다.
- 프로젝트 사용자 규칙 문서는 없으므로 공통 규칙과 아키텍트 역할 계약만 적용했다.

## 핵심 판단과 근거

### 저장소 경계

기획서의 요구사항 R2, R3, R7, R10, R11은 "런타임"이 사본을 준비하고 상태를 구분해 보여 준다고 적는다. 실행 환경의 소스가 이 저장소에 있는지 확인했다. `docs/agent-runtime.md` 3~5행이 실행 환경을 별도 배포물로 규정하고, `scripts/verify-agent-runtime-contract.mjs` 216행이 그 저장소를 이 저장소 밖 경로에서 찾는다. 저장소에 담긴 실행 환경은 빌드된 실행 파일과 manifest뿐이다.

따라서 실행 환경 쪽 변경은 이 워크플로우의 작업으로 만들 수 없다. `scope_files`는 프로젝트 루트 기준 상대 경로만 담을 수 있고, 개발자 세션도 이 프로젝트 안에서 작업한다.

### 예약 헬퍼를 격리 준비 자리로 선택한 근거

기획서 R2는 "예약 성공 뒤, provider 시작 전"을 준비 시점으로 못박는다. 그 시점에 실행되는 것 중 이 저장소가 소유한 것은 예약 헬퍼다. `src-tauri/src/infrastructure/reservation_helper.rs`가 그 본문을 관리 자산으로 들고 있고, 실행 환경은 그 헬퍼를 호출해 JSON을 받은 뒤에야 세션을 시작한다. 헬퍼가 0이 아닌 코드로 끝나면 세션은 시작되지 않으므로 "준비 실패 시 provider 미시작"이 그 자리에서 성립한다. 헬퍼에는 이미 실패 시 lease를 반납하는 경로가 있어(POSIX 95~98행) 정리 계약도 같은 모양으로 확장된다.

### 예약 결과 계약 판을 2로 올린 근거

필드만 늘리고 판을 그대로 두면, 새 필드를 모르는 실행 환경이 사본 경로를 무시한 채 공유 작업 공간에서 세션을 시작한다. 그것이 R13이 금지한 부분 실행이다. 판을 올리면 그 실행 환경은 예약 결과를 해석하지 못해 세션을 시작하지 않는다.

### 실행 환경 최소 판을 따로 둔 근거

처음에는 기존 최소 지원 판을 올리는 방법을 검토했다. 확인해 보니 `scripts/verify-agent-runtime-contract.mjs` 53~56행이 그 상수를 정규식으로 읽어 함께 배포되는 실행 환경 manifest와 대조한다. 지금 담긴 실행 환경은 0.9 계열이므로, 그 상수를 올리면 릴리스 검사가 실패하고 앱 설치 자체가 막힌다.

그래서 개발 실행에만 적용되는 별도 상수를 두기로 했다. 설치·갱신·진단과 다른 두 역할의 실행은 그대로 두고, 개발 역할 슬롯이 있는 실행만 막는다. 값은 0.10.0을 기본값으로 정했다. 예약 계약 판 2는 계약 주 버전 1 안에서 일어난 호환되지 않는 변화이므로 현재 0.9 계열의 다음 소수 판을 경계로 삼았다. 이 값은 실행 환경 저장소가 실제 판을 정하면 달라질 수 있으며, 이견이 있으면 새 아이디어로 되돌릴 수 있게 작업 문서에 근거를 남겼다.

### 품질 확인 방식

여섯 작업의 결과는 규칙 문서 본문, 관리 헬퍼의 종료 코드와 판정, 자격 판정 결과, 품질 확인 관문의 거절 조건이다. 비개발자가 화면을 열어 확인할 수 있는 기능이 없고, 격리가 실제로 동작하는 모습은 실행 환경이 나온 뒤에야 볼 수 있다. 그래서 `qa_mode: automatic`으로 정했다.

## 병렬 안전 판정

선언한 범위가 겹치는 쌍은 하나뿐이다. 02번과 04번이 예약 헬퍼 파일을 함께 고치므로 04번에 `depends_on`으로 02번을 적었다. 나머지 다섯 조합은 파일이 겹치지 않는다.

의미상의 선후로 더 적은 것은 세 가지다. 02번과 03번과 05번은 규칙 본문이 정한 절차를 구현하므로 01번을 선행으로 둔다. 03번은 02번이 만드는 준비 기록을 읽으므로 02번도 선행으로 둔다. 06번은 어느 것과도 겹치지 않아 선행을 두지 않았다.

그 결과 01번과 06번이 먼저 함께 진행되고, 그다음 02번, 이어서 03번과 04번과 05번이 함께 진행될 수 있다. 겹치지 않는 작업을 이유 없이 줄 세우지 않았다.

## 확인한 코드와 범위 사전 검사

각 작업의 `## 범위 사전 검사`에 값 경로를 적었다. 이번 세션에서 실제로 열어 확인한 자리는 다음과 같다.

- 규칙 본문과 판 번호가 한 파일에 함께 있고 판 번호 고정 검사도 같은 파일에 있음(`project_instructions.rs` 21~24·46·667·831·1646~1649행).
- 관리 자산 동기화와 저장소 계층이 판 번호를 리터럴이 아니라 상수 이름으로 참조하고 기대값도 그 상수로 조립함(`managed_project_assets.rs` 865~897행, `fs_project_repository.rs` 1601·1615·4835·8416·8428행). 그래서 판 번호 상향에 이 두 파일의 편집이 필요 없다.
- 예약 헬퍼의 JSON 조립 자리와 실패 시 반납 경로(`reservation_helper.rs` 95~105·173~193행).
- 개발자 자격 판정이 스크립트 본문과 앱 코드 두 벌로 있고 둘의 일치를 대조하는 검사가 있음(`heartbeat_condition.rs` 950·1842행, `role_eligibility.rs` 378·504행).
- 품질 확인 제출의 최신성 거절 자리와 그룹 상태 계산(`fs_project_repository.rs` 681·738·2865행, `domain/project.rs` 290·434행).
- 실행 환경 호환 판정과 실행을 여는 두 자리(`domain/agent_runtime.rs` 24·112·121·156행, `agent_runtime_run_service.rs` 23·97·118·213행).
- 실행 상태 표시의 소비자 화면(`AgentRuntimeView.tsx`)과 그룹 요약의 화면 타입(`types.ts` 183행). 두 파일은 이번 작업에서 고치지 않아도 되는 이유를 각 작업 문서에 적었다.
- `.workflow/.runtime/`가 저장소의 `.gitignore` 33행에 통째로 들어 있어, 그 아래에 사본과 기록을 두면 공유 작업 공간의 변경 목록이 더러워지지 않음.

## 위험과 후속

- 이 그룹이 끝나도 격리는 실제 실행에 적용되지 않는다. 실행 환경 저장소에서 준비된 사본을 세션의 작업 위치로 쓰고, 대기 해소를 감지해 다시 올리고, 실행 상태 단계를 앱에 전달하는 작업이 필요하다. 사용자가 새 아이디어로 올려야 그 저장소의 계획이 시작된다.
- 마지막 작업이 반영되면 자동 개발 실행이 지원 판이 나올 때까지 멈춘다. 이 정지는 기획서가 요구한 것이지만, 도그푸딩 중인 이 저장소의 자동 개발도 같이 멈추므로 반영 시점을 사용자가 정하는 편이 좋다. 06번을 마지막에 두는 것으로 그 시점을 늦출 수 있다.
- 실행 환경 최소 판 0.10.0은 아키텍트가 정한 기본값이다. 실행 환경 저장소가 다른 판으로 내면 06번의 값을 그때 맞춰야 한다.
- 저장 공간 상한 20 GiB는 사본 하나에 빌드 산출물이 쌓이는 이 저장소에서는 사본 두세 개 분량이다. 개발자 병렬 상한을 높게 잡으면 상한 대기가 잦아질 수 있다.
- PowerShell 본문은 현재 기기에서 실행할 수 없다. 02번과 04번과 03번의 PowerShell 쪽은 정적 대조까지만 확인하고 실제 실행은 Windows 환경이 필요하다는 사실을 각 작업의 검증 절차에 적었다.
- 기획서 본문, 기존 결정 문서, 이미 완료된 작업과 다른 작업 그룹은 이 세션에서 건드리지 않았다.
