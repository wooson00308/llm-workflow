## 현재 코드에서 확인한 사실

기획서의 근거로 실제 코드와 파일을 읽어 확인했다. 추정으로 쓴 항목은 없다.

- **보존이 저장 계약이 아니라 화면 시딩에 있다.** `RoleJobRequest`·`DreamJobRequest`는 편집 가능 값을 문자열로 그대로 받고, 백엔드는 그것을 그 연동의 desired state로 신뢰한다. 요청 값과 파일 값을 비교하는 지점이 없다. 파일 값이 살아남는 유일한 이유는 `HeartbeatCard`의 `roleFormFrom`(과 `DreamCard`의 `formFrom`)이 파일 값을 폼에 채워 넣기 때문이다. 이 기획서의 핵심 판단이 여기서 나왔다.
- **조회 경로가 읽기 실패를 빈 문서로 접는다.** `HeartbeatService::inspect`의 `fs::read_to_string(...).unwrap_or_default()`가 그것이다. 그러면 `managedJobs`가 빈 목록이 되고, 화면은 `managedJobs.length === 0`을 첫 설치로 읽어 역할 3종을 켠 채 기본값을 채운다. 그 상태에서 저장하면 기본값이 파일에 기록된다.
- 같은 파일의 설치 경로 `read_document`는 반대로 동작한다. `NotFound`만 빈 문서로 보고 다른 읽기 실패는 오류로 올리며, "못 읽은 문서를 빈 문서로 보면 다른 연동의 잡을 지우는 병합이 만들어진다"는 근거가 주석에 적혀 있다. 두 경로의 판단이 갈라져 있다.
- **연동 사이에서는 파일 기준 보존이 이미 성립한다.** `preserved_role_jobs`·`preserved_dream_job`이 블록의 편집 가능 값을 그대로 다시 만들고, 값이 검증을 통과하지 못하면 `PreservedJob`으로 실패하며 아무 파일도 쓰지 않는다(TASK-012). 즉 이 기획서가 요구하는 규칙은 새 원칙이 아니라, 이미 연동 축에 적용된 규칙을 자기 연동 안으로 넓히는 것이다. 요구사항을 그 표현으로 썼다.
- 편집 가능 값은 `interval`·`max_per`·`model` 셋뿐이다. `slug`·`prompt`·`timeout`·`condition`·`notify`는 `role_managed_jobs`가 매번 앱 값으로 다시 만든다. 그래서 앱 소유 필드의 사용자 편집 보존은 제외 범위로 두고, 되돌아간다는 사실의 고지만 R4에 넣었다.
- 화면은 `JSON.stringify(managedJobs)` 변화로 재시딩을 판정하고, 사용자가 편집 중이던 값을 알림 없이 파일 값으로 대체한다. R3의 두 번째 항목이 이것을 다룬다.
- 확인 화면은 쓰게 될 값만 나열한다(`기록: wf-developer-... — 20m · 6/24h · opus`). 파일의 현재 값과의 차이는 표시하지 않는다. 사고가 확인 단계에서도 눈에 띄지 않은 이유다.
- 저장 버튼 문구는 이미 상태에 따라 갈린다("이 프로젝트에 역할 잡 설치" / "역할 잡 변경 사항 저장"). 그러나 두 문구가 부르는 것은 같은 커맨드이고 payload 형태도 같다. 즉 아이디어가 지적한 "설치와 저장의 의미 분리"는 문구에만 있고 계약에는 없다.
- 기본값으로 되돌리는 명시적 액션은 없다. 현재 그 결과를 얻는 유일한 경로는 잡을 껐다 켜는 것이다.
- 실제 `~/.claude/HEARTBEAT.md`의 관리 블록은 `max_per`가 `8/24h`·`8/24h`·`16/24h`로 세 값 모두 앱 기본값과 다르다. 이 저장소의 실사용 구성 자체가 편집값에 의존하고 있다.
- 사고의 기록은 `docs/development-logs/2026-08-02.md`의 "SPEC-003·004 구현 사이클과 QA 일괄 확인" 절에 있다. 개발자 잡 `max_per`가 `8/24h`에서 `6/24h`로 리셋되어 쿼터가 조기 소진됐고, 값은 손으로 복구했다.

## 설계 판단의 근거

- **왜 보장의 위치를 옮기는가.** 값 하나를 고치는 것으로는 같은 사고가 다시 난다. 지금 구조에서 보존은 화면이 파일을 정확히 읽었다는 조건 하나에 전부 걸려 있고, 그 조건이 깨지는 지점이 코드에 실재한다(위 `inspect`). 저장 계약에 규칙을 두면 카드가 늘어나거나 저장 경로가 추가되어도 같은 보장이 따라온다.
- **왜 읽기 실패에서 쓰기를 막는가.** 앱이 모르는 값을 덮어쓰지 않는다는 것이 이 기획서의 규칙을 상태 축으로 옮긴 것이다. 읽기 실패가 `readFailures`로 이미 표시된다는 사실만으로는 부족하다. 경고가 떠 있어도 폼에 기본값이 차 있고 저장 버튼이 살아 있으면 사고는 그대로 일어난다.
- **왜 확인 화면을 차이 표시로 바꾸는가.** 아이디어가 "실행 전 무엇이 바뀌는지 보여준다"를 명시적으로 요구했다. 나열은 사용자가 파일의 현재 값을 외우고 있을 때만 검증 수단이 된다. 관측된 사고에서는 확인 화면을 지나갔는데도 아무도 알아채지 못했다.
- **왜 기본값 재설정을 분리하는가.** 되돌리는 것이 정당한 경우가 있다. 그것을 저장의 부작용으로 두면 정당한 요구와 사고를 구별할 수 없다. 명시적 액션으로 두면 둘 다 표현할 수 있다.
- **왜 앱 소유 필드를 제외 범위로 두는가.** SPEC-002 R2가 정한 계약이다. 기획서 하나가 그 계약을 조용히 바꾸는 것은 옳지 않고, 아이디어도 주기·쿼터·모델을 지목했다. 다만 되돌아간다는 사실 자체는 숨길 이유가 없어 R4에 고지 요구로 넣었다.

## 확인 필요 2건의 배경

1. **토글 왕복 시 편집값 복원.** 넓게 보면 이것도 편집값이 사라지는 경로라서 조용히 결정하지 않고 올렸다. 제안은 이번 범위 제외이고 근거는 비용이다. 꺼진 잡의 값을 기억하려면 관리 블록 밖에 앱 소유 저장소가 새로 필요하고, 그것은 "한 파일 안에서 누구의 값이 이기는가"와 다른 종류의 변경이다. 관측된 사고도 켜져 있는 잡의 값이었다.
2. **기본값 재설정의 단위(잡 단위 vs 연동 단위).** 제안은 잡 단위다. 전체 단위만 제공하면 잡 하나를 되돌리려는 사용자가 나머지 잡의 편집값을 잃는다. 되돌리기 액션이 값을 잃게 만드는 것은 이 기획서의 취지와 정반대다.
