# TASK-S051-09 개발 보고서

## 결정권자 요약

프로젝트마다 역할 정책과 실행 환경 준비 상태를 다루는 에이전트 화면을 만들었다.
준비 상태 여섯 가지와 실행 도구 진단 여섯 가지가 각각 다른 문장과 다음 행동을 갖는다.
설치와 업데이트와 복구는 계획을 먼저 보여 주고 사용자가 확인한 뒤에만 적용된다.
역할 표는 세 역할 고정 순서로 도구와 모델과 실행 방식과 한도를 편집하고 저장은 두 번 확인해야 나간다.
역할 끄기는 런타임 계약에 자리가 없어 저장되지 않으므로 조작을 열지 않고 그 사실을 적었다.
새 화면에는 Dream이 없고 기존 연동 화면의 Dream 카드와 역할 잡 자리는 그대로 두되 새 화면을 가리킨다.
화면 검사 30개와 전체 884개, 백엔드 688개가 통과했다. 다만 최상위 조립 파일이 범위 밖이라 메뉴는 아직 뜨지 않는다.

## 변경 파일과 모듈

- `src/features/projects/domain/types.ts`: 런타임 계약의 값들을 화면 타입으로 옮겼다. 기기 상태와 호환
  판정, 설치·업데이트 계획과 적용 결과, 역할 정책과 provider 진단, 마이그레이션 미리보기, 그리고 화면
  수명을 담는 상태와 조작 묶음이다. 값 어휘는 백엔드가 런타임에서 그대로 옮긴 것을 다시 옮겼다.
- `src/features/projects/infrastructure/tauriProjectGateway.ts`: 에이전트 명령 열 개를 이었다.
- `src/features/projects/application/useProjectWorkspace.ts`: 조회와 계획과 적용과 마이그레이션과 저장을
  훅이 소유한다. 화면을 옮겨 다녀도 진행 표시가 남고, 프로젝트가 바뀌면 상태를 통째로 갈아 끼운다.
  저장이 경합으로 거절되면 사유를 남긴 뒤 최신 값을 다시 읽어 폼을 조용히 덮지 않는다. 적용이 오래된
  계획으로 거절되면 같은 조작의 계획을 다시 만든다.
- `src/features/projects/components/agents/AgentRuntimeView.tsx`: 준비 영역과 계획·적용, 실행 도구 진단,
  마이그레이션 미리보기를 그린다. 상태 판정은 앞의 사유가 뒤의 사유를 가리는 순서를 지킨다.
- `src/features/projects/components/agents/AgentRoleSettings.tsx`: 역할 표와 상한 편집과 두 단계 저장.
- `src/features/projects/components/WorkspaceShell.tsx`: 메뉴 진입점과 화면 배선. 통로가 없으면 진입점을
  세우지 않는다.
- `src/App.css`: 새 화면의 배치와 980픽셀 이하 한 열 규칙.
- `src/features/projects/components/integrations/HeartbeatCard.tsx`: 역할 잡 자리 맨 위에 역할 설정의
  정본이 에이전트 화면이라는 안내를 넣었다.
- 검사: `agents/AgentRuntimeView.test.tsx`(30건 신규), `WorkspaceShell.test.tsx`(진입점 2건),
  `IntegrationsView.test.tsx`(안내와 Dream 카드 1건), `useProjectWorkspace.test.ts`(게이트웨이 픽스처).

- `npm run check` 통과: 타입 검사 성공, 26개 파일 884 tests 통과, 배포 빌드 성공. 변경 전 851개였다.
- `cargo test --manifest-path src-tauri/Cargo.toml` 통과: 688 passed, 0 failed.
- 준비 상태 여섯과 진단 여섯을 표로 검사했다. 진단 값 목록은 런타임 구현의 `DiagnosticStatus` 여섯 값을
  그대로 대응시켰고, 그 밖의 값은 문자열을 그대로 보여주는 것까지 검사한다.
- 계획 전 적용 버튼 부재, 실행 중 작업이 있는 계획의 영향 표시, 화면 진입과 다시 읽기에서 쓰기 명령
  비호출, 마이그레이션 확인 게이트, 저장의 두 단계 확인과 요약 내용, 호환 불가에서의 저장 차단, 스냅샷
  교체 시 폼 재설정, 새 화면의 Dream 부재를 각각 검사한다.
- 연동 화면 검사로 역할 잡 자리의 안내 문구와 Dream 카드 잔존을 확인했다.

## 남은 리스크

- 최상위 조립 파일이 이 작업의 선언 범위에 없어 작업 공간의 값을 화면 껍데기로 넘기는 두 줄을 넣지
  않았다. 그래서 실제 앱 메뉴에는 아직 에이전트 항목이 뜨지 않는다. 빈 화면을 여는 진입점이 생기지
  않도록 통로가 있을 때만 메뉴를 세우게 했으므로, 지금 상태에서 사용자가 깨진 화면을 만나지는 않는다.
- 조회를 2.5초 자동 주기에 넣지 않았다. 이 조회는 런타임 프로세스를 부르므로 주기마다 띄우면 비용이
  크다. 화면을 열 때와 프로젝트를 열 때와 다시 읽기에서만 부른다.
- provider 진단 값의 뜻은 런타임 구현에서 읽어 맞췄고 계약 문서에는 그 목록이 없다. 런타임이 값을 늘리면
  화면은 그 문자열을 그대로 보여주지만 안내 문장은 없다.
- 실제 런타임과 이어 붙인 손 검사는 하지 않았다. 검사에서는 게이트웨이 대역을 쓴다.

## 후속 작업

- `src/App.tsx`에 두 줄을 더하면 메뉴가 열린다. 작업 공간의 에이전트 상태와 조작을 껍데기로 넘기는
  값이며, 그 파일을 범위로 가진 작업이나 이 작업의 범위 확대로 처리하면 된다.
- 연동 화면의 역할 잡 폼과 역할별 지금 실행은 남겨 두고 안내만 얹었다. 완료 조건이 제거와 안내 둘 중
  하나를 허용하므로 안내를 택했고, 옛 잡을 정리하는 고급 관리 자리로 남는다. 완전히 걷어내는 편이
  낫다고 판단되면 그 파일과 5,300줄짜리 검사 파일을 함께 범위로 가진 작업이 필요하다.
- 실행 큐와 제어와 취소·재시도 화면은 이 작업의 범위가 아니며 후속 대시보드 작업이 같은 파일들을 쓴다.
