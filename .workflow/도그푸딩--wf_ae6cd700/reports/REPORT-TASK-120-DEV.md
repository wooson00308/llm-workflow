# TASK-120 개발자 핸드오프 (qa_waiting)

## 결정권자 요약

이제 기획서와 개발 작업을 열면 먼저 보이는 것이 결정권자에게 쓴 요약이다. 지금까지는 작업자가
작업자에게 쓴 본문이 통째로 열렸고, 도장을 찍기 전에 문서를 처음부터 읽어야 했다.

원문은 사라지지 않는다. 토글을 한 번 누르면 전문이 그대로 펴진다. 문서를 닫았다 다시 열면 언제나
평문에서 시작한다 — 토글 상태를 저장하지 않기로 한 결정 그대로다.

요약이 없는 옛 문서는 지금과 똑같이 열린다. 원문이 그대로 나오고 어떤 문구도 붙지 않으며, 그 문서에는
토글도 서지 않는다. 눌러도 같은 것이 다시 나오는 토글은 감춰 둔 것이 있다고 거짓말을 하기 때문이다.

기획서 화면에는 그 기획서에서 나온 개발 작업의 상태별 건수가 붙었고, 무엇을 센 값인지 화면이 한 줄로
밝힌다. 개발 작업 상세에서는 시작 가능 여부가 상태 배지 옆으로 옮겨 왔다.

앱은 문서 파일을 고치지 않고 요약을 지어내지도 않는다. Rust는 한 줄도 손대지 않았다. 지금 필요한 것은
사용자 QA다.

### 1. 절 찾기는 화면 밖의 순수 함수다 (고정값 2)

`splitSection(body, heading)`이 본문과 절 제목 하나를 받아 `{ section, rest }`를 돌려준다. 판정은
원문 문자열 위에서 하고 Markdown을 파싱해 트리로 만들지 않는다 — 잘라 낸 조각도 지금과 같은
`react-markdown` 경로로 그린다.

- 절의 경계는 같은 깊이의 다음 제목이다. `## 결정권자 요약` 다음의 `###`는 절 안이고, 다음 `##`도
  `#`도 절 밖이다.
- 코드 펜스(``` 와 ~~~) 안의 `#`은 제목이 아니다. 여는 펜스와 같은 문자로 그 길이 이상이고 뒤에
  아무것도 오지 않는 줄만 닫는 펜스로 본다. 그래서 ```` ```md ````처럼 정보 문자열이 붙은 줄은
  블록 안쪽에서 닫는 줄로 오인되지 않는다.
- 찾는 문자열은 하나다. 줄 끝 공백만 무시하고, 대소문자·공백·깊이 변형을 만들지 않는다(R2).
- 같은 제목이 두 번 나오면 첫 번째를 쓴다. 같은 절을 두 벌 가진 것은 문서 쪽 문제이고 화면이 고를
  근거가 없다.

`rest`는 이 작업에서 쓰지 않는다. 고정값 2가 정한 출력 모양이고, TASK-121이 `## 확인 동선`을 본문에서
빼내 도장 옆으로 옮길 때 "같은 사실을 두 자리에서 말하지 않는다"를 지키는 데 쓸 값이다.

### 2. 두 양식은 공용 컴포넌트 하나가 그린다 (고정값 3)

`DocumentReader`가 기본 뷰와 원문 토글을 갖고, 두 화면이 그것을 쓴다. `MarkdownBody`는 고치지 않았다 —
그리는 방법이 아니라 무엇을 넘길지가 바뀌었을 뿐이고, 아이디어 미리보기가 같은 컴포넌트를 쓴다.

토글 상태는 저장하지 않는다. 새 저장소 파일을 만들지 않았고 `browserSpecLaneCollapseStore` 계열에
다섯 번째를 더하지도 않았다. 문서가 바뀌었을 때 다시 접히는 것은 부르는 쪽이 `key={fileName}`으로
보장한다. 기획서 화면은 같은 자리에서 문서만 갈아 끼우므로 이 한 줄이 없으면 앞 문서에서 연 토글이
다음 문서까지 따라간다.

토글은 한 번의 조작으로 전문에 닿고, 원문은 자르지 않은 본문 그대로라 기본 뷰에서 감춰졌던 절이 전부
보인다.

### 3. 폴백에서 토글을 두지 않기로 했다 (고정값 4, 개발자 판단)

요약 절이 없으면 기본 뷰가 원문 전문을 그리고 **아무 문구도 붙지 않는다**. 여기까지는 고정값이다.

고정값 4가 개발자에게 남긴 선택은 그때 토글을 어떻게 할지였고, **숨기는 쪽**을 골랐다. 근거는 승인된
확인 필요 2번과 같다 — 눌러도 같은 것이 다시 나오는 토글은 "감춰 둔 것이 있다"는 말을 조작 가능한
컨트롤로 하는 셈이고, 문구를 붙이지 않기로 한 결정이 막으려던 것이 바로 그 말이다. 이 저장소의 문서
167건 중 요약 절을 가진 것이 15건뿐이라, 남기는 쪽을 고르면 거의 모든 문서 화면에 아무 일도 하지 않는
버튼이 하나씩 선다. 기획서 완료 조건 4는 어느 쪽으로도 깨지지 않는다.

### 4. 파생 작업 배지와 셈 대상 (고정값 5)

`SpecWorkspace`가 이미 받는 `workflow.items.tasks`에서 센다. 새 payload도 새 조회도 없다.

- 묶는 열쇠는 `sourceSpecId`를 `trim()`한 값이고, 보드 레인의 `laneKeyOf`와 같은 식이다.
- 다섯 상태의 목록과 이름은 `DevelopmentBoard`의 `taskColumns`·`statusLabels`를 그대로 가져다 쓴다.
  두 자리가 각자 상수를 갖는 것이 고정값 5가 비용으로 적은 어긋남의 경로라, 목록 자체를 나눠 쓰는
  쪽으로 막았다. 두 상수에 `export`를 붙인 것이 `DevelopmentBoard.tsx` 변경의 절반이다.
- 무엇을 센 값인지 화면이 밝힌다: "이 기획서를 출처로 적은 개발 작업 전체를 셉니다". 레인의
  `LANE_BASIS_NOTE`와 같은 어법이다.
- 다섯 상태 밖의 값은 "규격 밖 N"으로 따로 보인다. 레인의 `unknownCount`와 같은 이유다.

**셈 대상 대조 (검증 절차 6).** 두 자리를 나란히 두고 읽었다.

| | 보드 레인 (`buildSpecLanes`) | 기획서 배지 (`countTasksOfSpec`) |
| --- | --- | --- |
| 세는 집합 | `allTasks` = `workflow.items.tasks` | `workflow.items.tasks` |
| 필터·완료 절단 | 적용 안 함 | 적용 안 함 |
| 묶는 열쇠 | `item.sourceSpecId?.trim()` | `task.sourceSpecId?.trim()` |
| 상태 목록 | `taskColumns` | 같은 `taskColumns` (import) |
| 규격 밖 | `unknownCount`로 따로 | `unknown`으로 따로 |

어긋나는 지점은 없다. 유일한 차이는 출처가 없는 작업의 처리인데, 레인은 그것을 "미분류" 레인으로
모으고 배지는 어느 기획서와도 일치하지 않아 세지 않는다. 같은 값을 다르게 부르는 것이 아니라 배지의
질문("이 기획서에서 나온 작업")에 애초에 포함되지 않는 집합이다.

**파생 작업이 0건일 때 (고정값 5, 개발자 판단).** 빈 배지 줄 대신 "이 기획서에서 나온 개발 작업이 아직
없습니다."라는 한 줄을 두고, 셈 대상 문장은 그대로 남긴다. 근거는 배지가 답하려는 질문이 "이거 어디까지
됐나"이고 "아직 아무것도 없다"가 그 질문의 정당한 답이라는 것이다. 줄이 통째로 사라지면 "파생 작업이
없다"와 "이 화면이 그것을 말하지 않는다"가 사용자에게 같아 보인다.

### 5. 시작 가능 여부가 상태 배지 옆으로 옮겨 왔다 (고정값 6)

TASK-119가 선행 상자 헤더에 남겨 둔 "시작 가능"/"시작할 수 없음"이 작업 상세 머리의 상태 배지 옆으로
갔다. 옮긴 것이지 복제한 것이 아니라, 선행 상자 헤더에는 남지 않는다. `.task-dependencies`의
`startable`/`waiting` 클래스와 그 클래스에 걸려 있던 CSS 규칙 셋도 함께 새 자리로 옮겼다.

말하는 조건은 그대로다. 선행·겹침·형식 오류 중 하나라도 선언된 작업에서만 이 한 줄이 뜬다. 아무것도
선언하지 않은 작업을 "시작 가능"이라고 부르면 자리를 옮기는 대신 새 사실을 만드는 것이고, 고정값 6이
요구한 것은 이동이다.

## 사용자 QA 제안
