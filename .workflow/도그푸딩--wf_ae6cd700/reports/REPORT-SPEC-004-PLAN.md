## 대상 도구 실측 확인

기획서의 근거로 실제 설치본을 읽고 실행해 확인한 사실이다. 추정으로 쓴 항목은 없다.

- 하트비트(`claude-heartbeat` 0.5.1, 편집 가능 설치본 `~/Git/claude-heartbeat`)의 `core.py`는 잡의 `model`을 `claude --model <값>`으로 그대로 넘긴다. 값이 비면 `--model`을 붙이지 않는다(주석: "비어 있으면 CLI 기본 모델").
- **쿼터는 종료 코드 확인 전에 차감된다.** `_record_quota_run`이 `subprocess.Popen` 직후, `communicate` 이전에 호출된다. 소스 주석이 의도를 밝히고 있다. 즉 모델명이 틀리면 매 주기 쿼터만 소모하면서 아무 일도 하지 않는다. 아이디어가 말한 "조용한 실패"의 실제 비용이 이것이고, 기획 내용의 핵심 근거다.
- `claude --model definitely-not-a-model -p "1"`을 실제로 실행해 종료 코드 1과 `There's an issue with the selected model (...)`을 확인했다. 요청은 나가지 않는다.
- 하트비트는 비정상 종료를 상태 파일에 `failure`로 기록하고, 앱(`SettingsView.tsx`의 `runResultLabels`)은 그것을 "실패" 배지로만 표시한다. 사유가 화면에 도달하는 경로는 없다. 사후 표시 개선은 SPEC-002가 제외한 관측 기능 확장이라 예방 쪽으로 방향을 잡았다.
- `claude --help`의 `--model`은 별칭 또는 정식 모델명을 받는다고 기술한다. 설치된 CLI 바이너리에서 확인되는 별칭은 `fable`, `haiku`, `opus`, `sonnet` 네 개다.
- **CLI에 모델 목록 조회 명령이 없다.** 하위 명령 목록을 확인했고, `--model`에 잘못된 값을 주면 대화형 선택기를 안내할 뿐 기계가 읽을 목록을 내보내지 않는다. 목록을 앱 소유 값으로 둔 결정의 직접적 근거다.
- 현재 검증 규칙은 프론트 `/^\S+$/`(`SettingsView.tsx`), 백엔드 `is_model`(`heartbeat_jobs.rs`)이며 두 규칙은 같은 값을 통과시킨다. `opuss` 같은 오타는 양쪽 모두 통과한다.
- 관리 UI에 존재하는 잡은 현재 역할 잡 3종뿐이다. dream 잡 UI는 SPEC-003의 산출물이고 아직 구현 전이다(SPEC-003 대응 태스크가 없다).

## 설계 판단의 근거

- **왜 목록을 앱이 소유하는가.** 외부 조회 경로가 실질적으로 없다. 그리고 앱이 외부 명령을 실행하는 방식은 SPEC-003 확인 필요 1번이 `dream-prep`에 대해 이미 기각한 방향이다. 같은 이유(GUI 앱의 PATH, 기존에 외부 명령을 실행한 적 없음)가 그대로 적용된다.
- **왜 별칭 중심인가.** 앱 소유 목록은 앱 릴리스로만 갱신된다. 정식 모델명을 넣으면 모델 출시마다 목록이 낡지만, 별칭은 세대가 바뀌어도 유효하다. 갱신 압력을 설계로 낮추는 쪽을 택했다.
- **왜 직접 입력을 남기는가.** 목록이 낡는 것을 전제로 설계했으므로, 목록이 낡았을 때 사용자가 막히면 안 된다. R3에 "목록의 정확성은 편의의 문제이지 가용성의 문제가 아니어야 한다"를 명시했다.
- **왜 백엔드 검증을 그대로 두는가.** 선택 UI는 예방이고 백엔드는 방어선이다. 백엔드를 목록으로 좁히면 손으로 정식 모델명을 적어 둔 파일을 앱이 저장하지 못하는 회귀가 생긴다. 앱이 목록을 갱신하기 전까지 유효한 값이 거부되는 상태도 함께 생긴다.

## 확인 필요 2건의 배경

1. **목록의 구성 범위(별칭만 vs 정식 모델명 포함).** 아이디어가 "목록의 출처와 갱신 방법"을 기획에서 다루라고 명시적으로 지시한 항목이다. 제안은 별칭 네 개만 넣는 것이고, 근거는 비용의 분포다. 세대 고정은 소수의 요구이고 그 소수는 모델명을 이미 알고 있다. 목록이 낡는 비용은 모든 사용자가 지불한다.
2. **빈 `model`(CLI 기본 모델) 지원.** 하트비트는 빈 값을 지원하는데 앱은 거부한다. 즉 앱으로는 표현할 수 없는 유효한 상태가 하나 있다. 선택 UI를 만드는 김에 넣고 싶어지는 항목이라 조용히 결정하지 않고 올렸다. 제안은 제외이며, 근거는 이 변경이 백엔드 검증 규칙과 저장 계약까지 건드려 기획서의 성격이 "입력 방식 전환"에서 "값의 의미 확장"으로 바뀐다는 것이다.

## 순서 의존성 (아키텍트가 판단할 사항)

아이디어의 대상에는 dream 잡의 `model` 필드가 포함되지만, dream 잡 UI는 SPEC-003의 산출물이고 아직 없다. SPEC-003은 승인(DECISION-5276FDBF)되었으나 대응 태스크가 만들어지지 않은 상태다.

이 기획서는 두 기획서의 구현 순서 중 어느 쪽이 먼저여도 성립하도록 썼다. 요구사항과 완료 조건의 대상을 "연동 관리 UI에 존재하는 모든 잡의 `model` 필드"로 표현했고, 특정 잡 목록을 고정하지 않았다(R5). 순서 자체는 작업 분해 시점의 판단이므로 기획서에서 정하지 않았다.
