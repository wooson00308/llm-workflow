# TASK-S074-01 개발 보고서

## 결정권자 요약

사용 한도 보류가 더 이른 해제 시각으로 줄어들지 않는다. 실제 해제 시각으로 보류가 걸린 뒤에 같은
실행 도구에서 해제 시각을 싣지 못한 한도 종료가 다시 확인되어도, 앞서 적힌 늦은 해제 시각이 그대로
남는다. 새 한도 종료가 더 늦은 해제 시각을 말하면 그 시각까지 보류가 연장되고, 해제 시각이 이미 지난
기록은 새 한도 종료가 대신한다. 한 번의 실행 목록 확인에서 같은 도구의 한도 종료가 여럿 보일 때도
그중 가장 늦은 해제 시각이 보류가 된다. 기존 시각을 유지할 때는 파일을 다시 쓰지 않으므로, 실제
값인지 추정값인지의 구분과 기록에 남은 실행 식별자도 지금 보류를 만든 실행의 값으로 남는다. 기록
형식과 놓이는 자리, 보류 판정, 화면 표시, 역할·실행 도구 대응표는 그대로다. 백엔드 시험 943건과
화면 시험 579건, 형식 검사와 정적 분석, 생산 빌드가 격리 사본과 통합 커밋에서 모두 통과했다. 이
결과는 GROUP-074의 자동 검증 전체를 뒷받침한다.

## 바꾼 파일과 모듈

- `src-tauri/src/infrastructure/provider_hold.rs` — `record`가 파일을 쓰기 전에 이미 있는 기록을
  한 번만 읽는다. 실행 식별자가 같으면 지금처럼 쓰지 않고, 기록의 해제 시각을 읽을 수 있고 그
  시각이 지금 시각보다 뒤에 있으며 새로 정한 재개 시각보다 늦거나 같으면 역시 쓰지 않는다. 그 밖의
  경우는 지금과 같이 새 값으로 쓴다. 비교에는 이미 있던 `read_record`와 `parse_stamp`를 그대로
  쓴다. 시험 넷을 더했다. 실제 해제 시각을 유지하는 시험, 추정값을 유지하며 그 구분이 남는 시험,
  더 늦은 시각으로 연장하는 시험, 만료된 기록을 새 한도 종료가 대신하는 시험이다. 실행 식별자만
  다른 행을 만드는 시험 도우미 `run_as`도 함께 두었다.
- `src-tauri/src/application/agent_runtime_status_service.rs` — `usage_limit_ends`가 실행 도구마다
  한 행으로 줄이지 않고, 종료 사유·상태·종료 시각 세 조건을 만족하는 행을 모두 돌려준다. 고르기에
  쓰던 `BTreeMap`이 없어져 그 import와 `DateTime` import를 함께 뺐다. 부르는 자리의 반복문은
  그대로다. 지금 고르기 규칙을 못 박고 있던 시험을
  `the_latest_resume_time_of_each_provider_becomes_the_provider_hold`로 고쳤다. 늦게 끝난 행이 해제
  시각을 싣지 않은 경우와 반대 순서인 경우를 두 실행 도구로 함께 확인한다.

## 검증 절차와 결과

격리 사본(base 0265e73, 커밋 f5e449a)에서 먼저 돌렸다.

1. `cargo test --manifest-path src-tauri/Cargo.toml provider_hold` — 21건 통과. C1, C3, C4, C6, C7,
   C11, C12를 덮는다.
2. `cargo test --manifest-path src-tauri/Cargo.toml agent_runtime_status_service` — 위 실행에 함께
   포함되어 통과. C5, C8, C9를 덮는다.
3. `cargo test --manifest-path src-tauri/Cargo.toml heartbeat_condition` — 55건 통과, 건너뛴 시험
   없음. C2에 회귀가 없다. 작업 문서가 언급한 PowerShell 본문 시나리오는 이 기기에서 건너뛰지 않고
   그대로 돌았다.
4. `cargo test --manifest-path src-tauri/Cargo.toml` — 915건 + 28건 통과. 대응표 시험 둘이 여기
   포함되어 C10을 덮는다.
5. `cargo fmt --check`와 `cargo clippy --all-targets -- -D warnings` — 둘 다 통과.
6. `npm run check` — 화면 시험 579건 통과, 42건 건너뜀(변경 전과 같은 값), 타입 검사와 생산 빌드
   통과.

통합 직전에 공유 작업본을 다시 읽었더니 기준 커밋이 0265e73에서 1b50c74로 앞서 있었다. 다른 세션이
그사이에 화면 쪽 변경을 반영했고, 겹치는 파일이 없어 그 커밋 위로 그대로 얹혔다(통합 커밋 3e0142d).
격리 사본을 그 커밋으로 옮겨 위 검사를 모두 다시 돌렸고, 백엔드 943건과 화면 579건, 형식 검사와
정적 분석, 생산 빌드가 같은 결과로 통과했다. `.workflow` 밖에 사용자의 미완료 변경은 없었고, 추적
대상이 아닌 스크린샷 디렉터리 하나만 남아 있어 충돌하지 않았다.

## 남은 위험

- 앞 기록이 추정값이고 나중 실행이 그보다 이른 실제 해제 시각을 실어 오면 최대 한 시간을 필요
  이상으로 기다린다. 기획서가 고른 기본값이며 시험
  `an_estimated_hold_that_is_kept_stays_marked_as_an_estimate`가 그 동작을 그대로 못 박고 있다.
- 실행 목록 확인 한 번에 같은 도구의 한도 종료 행이 많아지면 `record` 호출 수가 그만큼 늘어난다.
  호출마다 기록 파일을 한 번 읽지만 행 수가 화면 폴링이 다루는 규모라 실측이 필요할 만큼은 아니다.
- 실행 환경이 해제 예정 시각을 실제보다 늦게 실어 보내는 경우는 이 변경이 걸러 내지 못한다. 실어
  오는 값 자체는 범위 밖이다.
