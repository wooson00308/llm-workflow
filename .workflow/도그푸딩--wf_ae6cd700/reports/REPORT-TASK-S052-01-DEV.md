# TASK-S052-01 개발 보고서

## 결정권자 요약

앱이 설치하는 공통 규칙과 세 역할 계약에 구조화된 결정권자 요약 문법을 추가했다.
새 기획서와 새 개발 작업은 일곱 하위 제목과 두 영향 표식을 정해진 순서로 쓰고, 개발 보고서는 기존 평문 요약을 그대로 지킨다.
구조화 요약에는 열 줄 상한 대신 항목별 간결성이 걸리며, 평문 요약과 보고서의 열 줄 상한은 바뀌지 않는다.
기존 평문·무요약·불완전 구조 문서는 그대로 유효하고 소급 변환도 자동 보정도 하지 않는다.
공통 규칙 17, planner 11, architect 11, developer 12로 버전을 올리고 같은 문언을 사용자 문서에도 적었다.
이전에 이 작업을 막았던 범위 충돌은 아키텍트가 범위를 네 파일로 넓혀 해소했고, 새로 들어온 두 파일에서는 버전 문자열만 고쳤다.
자동 검사 610개가 통과했고 사용자는 TASK-S052-01 확인 동선의 수치를 확인하면 된다.

## 이전 차단과 이번 재개

이 보고서는 이전 차단 보고를 대체한다. 그때 막힌 것은 구현이 아니라 범위였다. 규칙 버전을 올리면
범위 밖 두 파일에 박힌 이전 버전 문자열이 함께 깨져서, "범위 파일만 바꾼다"와 "전체 검사가 통과한다"를
동시에 지킬 수 없었다. 아키텍트가 두 파일을 범위에 넣고 완료 조건 10을 네 파일 기준으로 다시 썼으며
조건 11로 그 두 파일의 변경 한도를 정했다. 사용자가 앱에서 재개해 이번 세션이 이어받았고, 이전 세션의
제품 변경은 남아 있지 않아 신규 구현으로 진행했다.

## 변경 파일과 모듈

- `src-tauri/src/infrastructure/project_instructions.rs`: 공통 규칙 §8에 `### The structured summary`
  절을 더했다. 일곱 하위 제목과 순서, 두 영향 표식, 선택 항목 규칙, 구조 불인정 조건, 보고서 제외,
  열 줄 상한과의 관계, 금지 조건과 표시 경계를 한 번씩 정의한다. 호환성 문단에는 평문 요약과 불완전
  구조가 그대로 유효하고 프론트매터·스키마·자격 판정에 영향이 없다는 문장을 더했다. 세 역할 계약에는
  자기 의무만 적고 공통 정의는 `§8`을 가리킨다. 버전 상수와 규칙 본문 frontmatter를 17·11·11·12로
  함께 올렸고, 새 검사 하나로 제목 순서·표식·경계·호환성·역할별 의무를 대조한다.
- `docs/file-contract.md`: `#### 구조화된 요약` 절을 더해 같은 계약을 한국어로 적고, 기획서와 개발
  작업 예시를 구조화 형태로 바꿨다. 역할별 설명 세 줄에 각 역할의 의무를 더했으며 개발 보고서는 평문
  요약과 열 줄 상한을 유지한다고 명시했다.
- `src-tauri/src/infrastructure/fs_project_repository.rs`: 규칙 설치·갱신 검사가 직접 비교하는 이전
  버전 문자열만 새 버전으로 바꿨다. 검사 140개, 단언 401개, 파일 줄 수 7,638줄이 변경 전과 같다.
- `src-tauri/src/infrastructure/managed_project_assets.rs`: 관리 자산 동기화 검사의 버전 표와 픽스처
  문자열만 바꿨다. 검사 16개, 단언 72개, 파일 줄 수 1,558줄이 변경 전과 같다.

## 검증 절차와 결과

- `cargo test --manifest-path src-tauri/Cargo.toml` 통과: 610 passed, 0 failed. 변경 전 609개에 새 계약
  검사 하나가 늘었다.
- `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets` 경고 없음, `cargo fmt` 적용.
- 설치된 규칙을 임시 프로젝트에 풀어 제목 일곱 개의 등장 순서, 표식 두 개, 선택 항목과 불인정 조건,
  보고서 제외, 열 줄 상한 해소, 표시 경계, 호환성 문언, 역할별 의무와 네 버전 값을 단언과 대조했다.
- `docs/file-contract.md`와 규칙 본문을 같은 항목표로 대조했다. 일곱 제목과 두 표식이 양쪽에 모두 있고,
  보고서 제외·열 줄 상한·표시 경계·호환성·스키마 무변경·결정 요청의 이중 의미가 짝을 이룬다.
- `git diff --stat -- . ':!.workflow'` 결과 제품 변경은 범위 파일 네 개뿐이다. 같이 나오는
  `docs/handoff.md`는 이 세션 착수 전에 이미 변경돼 있던 파일이고 이번 세션이 손대지 않았다.
- 새로 들어온 두 파일의 `git diff`를 줄 단위로 읽었다. 바뀐 줄은 전부 버전 숫자와 버전 문자열이며
  검사 이름, 시나리오, 단언 줄은 그대로다. 위에 적은 세 수치가 그 대조 결과다.

## 남은 리스크

- 두 파일의 픽스처 가운데 두 개는 변경 전 상태에서 이미 무의미해져 있었다. 아키텍트 계약 픽스처는
  존재하지 않는 문자열을 바꾸려 했고, 개발자 계약 픽스처도 같은 상태였다. 버전을 올리면서 두 픽스처가
  다시 실제로 낮은 버전을 설치하도록 숫자를 맞췄다. 검사 개수와 시나리오는 그대로이지만, 두 검사는
  이번 변경으로 판정력이 되살아났으므로 다음 회귀에서 처음으로 실패할 수 있는 자리다.
- 규칙 문언은 사람이 읽는 계약이라 자동 검사가 문자열 존재와 순서까지만 확인한다. 문장이 실제로 세
  역할에게 같은 뜻으로 읽히는지는 다음 기획·아키텍트 세션이 그 구조로 문서를 쓸 때 처음 드러난다.
- 버전이 17이 되어 기존 프로젝트의 `.workflow/rules/` 네 파일은 다음 쓰기 명령에서 새 문언으로 교체된다.
  교체 자체는 기존 동기화 경로가 하며 이 작업이 새로 만든 경로는 없다.

## 후속 작업

- 구조화 요약을 실제로 쓰는 첫 문서는 다음 기획서와 다음 개발 작업이다. 이 작업은 계약만 정했고 기존
  문서를 바꾸지 않았다.
- 앱 화면이 구조화 요약을 항목별로 보여 주는 일은 SPEC-052의 다른 작업 몫이다. 이번 변경은 본문 계약
  까지이며 표시 경로와 파서를 만들지 않았다.
- 이 세션은 `.workflow/rules/`를 편집하지 않았다. 착수 시점에 그 네 파일이 이미 변경 상태였는데, 앱이
  이전 버전으로 동기화한 결과이고 이번 변경 집합에 들어가지 않는다.
