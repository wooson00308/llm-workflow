# SPEC-083 기획자 핸드오프

## 결정권자 요약

런타임이 예약한 수정 요청 DECISION-00AF7157을 처리해 기획서 SPEC-083을 새로 쓰고 사용자 검토
대기로 올렸다. 사용자는 SPEC-079를 읽고 "접히면 최근 종료 항목에서 안보이는게 나을듯"이라고
돌려보냈으므로, 접었다 펼치는 방식과 "확인한 실패 N건" 건수 줄을 통째로 뺐다. 확인한 기록은 최근
종료 구역에서 어떤 형태로도 그리지 않고, 전체 실행 기록에만 회색 점과 확인함 표시를 달고 남는다.
그 결과 확인한 기록을 다시 여는 경로가 전체 실행 기록 하나로 줄어드는데, 새 진입점을 만들지 않고
기존 전체 기록 버튼을 그대로 쓰기로 정했다. 화면에 흔적을 남기는 방식은 사용자가 지목해 뺀 그
줄을 되살리는 셈이기 때문이다. 조사 중에 이 화면의 각 구역이 그릴 항목이 있을 때만 그려진다는
사실을 확인해, 최근 종료가 비는 경우의 요구사항을 그 동작에 맞춰 고쳐 썼다. 사용자가 할 일은 이
감추기 방식과 되돌리기 경로를 보고 승인하거나 수정 요청을 남기는 것이다.

## 세션 정보

- 역할: 기획자 (planner)
- 대상: DECISION-00AF7157 (SPEC-079에 대한 revision_requested)
- 산출 기획서: SPEC-083 (status: user_review, 새로 만든 문서)
- 예약: 런타임 예약 대상 DECISION-00AF7157, lease lease-25362-20260819142659, 결과 prefix
  RES-20260819T142659Z-25362-20260819142659
- 문서 식별자는 계보 규칙으로 정했다. specs/에 001부터 082까지가 차 있어 가장 낮은 미사용 번호인
  083을 썼고, 쓰기 전에 해당 경로가 비어 있음을 확인했다. 결과 prefix는 이 보고서에만 적었다.

## 소유권과 자격 판정

- 재예약 없이 `wf-claim.sh renew DECISION-00AF7157 lease-25362-20260819142659`로 소유권을 확인했다
  (종료 코드 0). 작업 도중 한 번 더 갱신했다. 중간에 종료 코드 5가 한 번 나왔는데, 헬퍼를 프로젝트
  루트가 아닌 워크플로 디렉터리에서 호출한 탓이었다. 루트에서 다시 부르니 0이었고 lease 파일의
  소유자 값도 그대로였다.
- 자격: DECISION-00AF7157은 SPEC-079에 달린 유일한 결정이므로 최신 결정이다. specs/ 전체를 훑어
  이 결정 id를 `source_decision_id`로 가진 문서가 하나도 없음을 확인했다. 수정 요청이 아직
  답해지지 않은 상태였다.
- `.workflow/.runtime/silent-runs/`에서 이 대상이나 SPEC-083을 언급하는 기록을 찾지 못했다. 이어받을
  잔여물이 없는 새 작업이며, 인수 판단이 필요한 대목도 없었다.

## 수정 요청이 요구한 변경

사용자 코멘트 전문은 다음과 같다.

> 접힌 건수만 한줄로 남는다. 이건 별론데? 접히면 최근 종료 항목에서 안보이는게 나을듯.

SPEC-079는 확인한 실패를 접고 목록 아래에 건수 줄을 남겨 펼칠 수 있게 하는 안이었다. 요구는 그
중간 단계를 없애고 아예 보이지 않게 하라는 것이다. SPEC-083에서 다음을 바꿨다.

- SPEC-079 R6(건수 줄과 펼치기)을 삭제했다. 그 자리를 새 R6이 대신하는데, 확인한 기록을 최근 종료
  구역에 어떤 형태로도 그리지 않는다는 금지 조항이다. 건수 줄, 접힌 행, 자리를 지키는 표시를 함께
  막아 두어 같은 것이 다른 모양으로 돌아오지 않게 했다.
- SPEC-079 R7은 확인한 줄의 회색 점과 확인함 표시를 최근 종료와 전체 실행 기록 양쪽에 걸었다.
  확인한 줄이 최근 종료에 더는 나오지 않으므로 이 표시를 전체 실행 기록 조항인 R8로 합쳤다.
- 되돌리기 경로를 R9로 새로 명시했다. SPEC-079에서는 확인 해제를 최근 종료에서 펼친 줄로도 할 수
  있었지만, 이제 전체 실행 기록을 거쳐야 한다.
- 최근 종료가 비는 경우를 R7로 새로 넣었다. SPEC-079는 이 경우를 다루지 않았고, 확인한 기록이
  화면에서 완전히 빠지면서 발생 확률이 올라갔다.
- 판정 기준을 다시 썼다. 펼치고 접는 동작을 검사하던 A2와 A3을 흔적이 없음을 검사하는 A2와 전체
  실행 기록을 검사하는 A3으로 바꾸고, 빈 구역을 검사하는 A7을 새로 넣었다.
- 화면 용어에서 "확인한 실패 N건"을 뺐다. R14는 확인함, 확인 해제, 일괄 확인 셋만 고정한다.
- 제외 범위에 두 줄을 넣었다. 접었다 펼치는 방식을 다루지 않는다는 것과, 최근 종료 구역 안에 필터나
  전환 스위치를 두지 않는다는 것이다. 뒤쪽은 구역 안에서 확인한 기록을 되살릴 방법이 생기면 R6이
  무력해지기 때문에 막았다.

SPEC-079에서 사용자가 문제 삼지 않은 부분은 그대로 옮겼다. 확인 대상 상태 둘, 개별과 일괄 두 가지
확인 방법, 일괄 확인의 건수 확인 창, 앱이 표시를 따로 보관한다는 점, 표시가 재시도나 자격 판정에
관여하지 않는다는 점이 그렇다.

## 기획자가 판단해 정한 것

수정 요청은 감추라는 결론만 주었고, 그에 딸린 선택은 이 기획서에서 정했다.

- 되돌리기 경로에 새 진입점을 만들지 않기로 했다. 최근 종료 구역의 전체 기록 버튼이 이미 그 목록을
  여는 자리다. 확인 해제가 한 단계 멀어지지만, 되돌리기 편하라고 최근 종료에 흔적을 남기면 사용자가
  지목해 뺀 그 줄을 다시 만드는 셈이 된다. 확인 처리 자체가 조치를 끝낸 뒤에 누르는 동작이라 되돌릴
  일이 드물다고 보았다.
- 최근 종료가 비었을 때 안내 문구를 두지 않기로 했다. "확인한 기록이 있습니다" 같은 문장은 건수 줄과
  기능이 같다.
- 일괄 확인은 최근 종료 구역 머리에 그대로 두었다. R4가 미확인 대상이 없으면 그리지 않게 하므로,
  구역이 사라지는 경우와 충돌하지 않는다.

## 조사해서 확인한 사실

- 에이전트 화면의 각 구역은 그릴 항목이 있을 때만 그려진다. 처음에는 최근 종료가 비었을 때 "지금의
  빈 상태 표시를 그대로 쓴다"고 적었으나, TASK-S065-03이 기록해 둔 화면 구조를 읽고 그런 구역별 빈
  상태 표시가 없다는 것을 확인했다. R7과 A7을 구역 자체가 사라지는 동작으로 고쳐 썼다.
- 주의할 것, 사용자 결정, 진행 중, 배정 대기, 최근 종료가 모두 비면 화면 전체에 조용한 한 줄이
  나온다. 확인 처리로 최근 종료가 비는 경우도 그 조건에 들어가므로, 그 줄의 문구와 조건은 건드리지
  않는다고 R7에 못 박았다.

## 아키텍트에게 넘기는 참고

- 구현 대상은 SPEC-083 하나다. SPEC-079는 수정 요청을 받은 이전 판이며 되살리지 않는다.
- R6과 R9는 짝이다. 최근 종료에서 완전히 감추는 대신 전체 실행 기록이 유일한 복귀 경로가 되므로,
  그 목록에서 상세 화면으로 들어가는 동선이 실제로 동작하는지 확인이 필요하다.
- R13의 정리 대상은 화면에서 사라진 실행에 딸린 확인 표시뿐이다. 실행 기록 자체를 지우는 기능으로
  넓히지 않는다.
- 역할 밖이라 손대지 않은 것: specs/에 결과 prefix를 식별자로 쓴 문서 넷(SPEC-RES-로 시작하는
  파일)이 남아 있다. 계보 규칙에 어긋나는 이름이지만 이번 대상이 아니어서 그대로 두었다.
