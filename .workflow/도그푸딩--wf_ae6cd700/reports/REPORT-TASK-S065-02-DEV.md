# TASK-S065-02 구현 보고서

## 결정권자 요약

단독 수행 표시를 AI 세션이 읽는 규약 문서 셋에 적었다. 공통 규약에는 값의 모양과, 읽을 수 없는 값을
단독으로 다룬다는 것과, 값을 보존해야 한다는 것을 적었다. 작업을 만드는 세션이 읽는 문서에는 이 표시를
언제 붙이는지를 적었고, 작업을 받는 세션이 읽는 문서에는 이 표시를 자기가 바꾸지 못한다는 것과 틀렸다고
판단했을 때 넘기는 경로를 적었다. 워크플로우를 새로 만들 때 쓰는 안내 문서의 작업 예시에도 선택 항목으로
더했다. 본문을 고친 문서 셋의 버전을 함께 올렸고, 이번에 손대지 않은 기획자 문서의 버전은 그대로 두었다.
배정 판정은 한 줄도 바꾸지 않았다. 격리 사본과 통합 뒤 공유 기준 양쪽에서 시험이 전부 통과했다. 이
증거는 GROUP-065의 자동 검증 결과를 뒷받침한다.

## 변경한 파일과 모듈

- `src-tauri/src/infrastructure/project_instructions.rs`
  - 공통 규약 본문의 `## 6. Preserve the file contract` 절에 `solo_run` 선택 필드 항목 셋을 더했다(C1).
    값의 모양, 읽을 수 없는 값을 단독 선언으로 다룬다는 것, 상태 전이와 막힘 기록과 정의 오류 수정에서
    값을 보존한다는 것이다.
  - 아키텍트 계약 본문의 `## Split for parallel safety` 절에 이 선언을 언제 쓰는지 항목 둘을 더했다(C2).
    판단 기준은 기획서의 요구가 코드가 아니라 기기의 조건을 묻는 경우이고, 무부하 성능 측정과 타이밍에
    민감한 재현 시험을 그 예로 적었다.
  - 개발자 계약 본문에 `### When the solo-run declaration is what is wrong` 절을 더했다(C3). 구현 세션이
    이 선언을 쓰거나 넓히거나 지우지 않는다는 것과, 선언이 틀렸을 때 기존 정의 오류 경로를 그대로 탄다는
    것이다.
  - 본문을 고친 문서 셋의 버전을 상수와 본문 머리에서 함께 올렸다(C5). 공통 규약은 28에서 29, 아키텍트는
    19에서 20, 개발자는 21에서 22다. 본문을 고치지 않은 기획자 계약은 12 그대로다.
  - 같은 파일 시험의 버전 기대값 43줄과 상수 단언 3줄을 새 값으로 맞췄다.
- `src-tauri/src/infrastructure/fs_project_repository.rs`
  - `workflow_readme`가 만드는 안내 문서의 개발 작업 frontmatter 예시에 선택 항목 한 줄을 더했다(C4).
    기존 `due_at` 줄과 같은 어법이다.

## 검증 단계와 결과

격리 사본에서 먼저 돌리고, 통합한 뒤 통합 커밋에서 같은 검사를 다시 돌렸다. 두 결과가 같다.

- `cargo test --manifest-path src-tauri/Cargo.toml project_instructions`: 25건 통과, 실패 0.
- `cargo test --manifest-path src-tauri/Cargo.toml`: 868건 통과, 실패 0(라이브러리 843, 통합 시험 25).
- `cargo fmt --manifest-path src-tauri/Cargo.toml --check`: 통과.
- `npm run test`: 파일 29개, 505건 통과, 42건 건너뜀, 실패 0.
- `git diff`로 확인했다(검증 5). 바뀐 단언 줄은 전부 버전 기대값이고, 지워지거나 느슨해진 단언은 없다.
- `git status`로 확인했다(검증 6, C9). 바뀐 파일은 선언한 둘뿐이고 `.workflow` 아래 문서는 그대로다.
- C6 대조. TASK-S065-01이 구현한 `parse_solo_run_declaration`과 `SoloRunDeclaration::reads_as_solo`,
  `role_eligibility.rs`의 `SoloGate`와 `solo_representative`를 읽고 문서 서술을 그 판정에 맞췄다. 읽을
  수 없는 값을 단독으로 다룬다는 서술은 `reads_as_solo`가 `Malformed`를 참으로 읽는 것과 같은 뜻이고,
  선언이 있는 작업이 다른 세션이 도는 동안 후보에서 빠진다는 서술은 대표 작업을 `solo-run-wait`로,
  나머지 후보를 `solo-run-active`로 제외하는 게이트와 같은 뜻이다. 어긋나는 곳은 없어 판정은 읽기만 했다.
- C8 확인. 조건 스크립트와 앱 판정과 도메인 상수는 이번 변경의 대상 밖이고 실제로 바뀌지 않았다.

통합 후보의 사실은 다음과 같다. 격리 커밋 `dfd71ff`, 시작 기준 `2730117`이다. 통합 직전에 공유 기준이
`a623ed8`로 옮겨 간 것을 확인하고 그 커밋 위로 다시 얹은 뒤 격리 검사를 처음부터 다시 돌렸다. 화면 시험
건수가 504에서 505로 는 것은 그 사이 통합된 다른 작업의 시험이 들어왔기 때문이다. 공유 작업 공간에서
`.workflow` 밖에 추적 중인 변경이 하나도 없어 충돌 없이 `50e930f`로 통합했고, 통합 커밋을 격리 사본에
옮겨 위 검사를 다시 돌렸다.

## 남은 위험

- 규약 문서는 앱이 프로젝트를 열 때 동기화되므로, 자동 실행만 도는 프로젝트에는 앱을 한 번 열기 전까지
  새 문서가 닿지 않는다. 이번 변경이 만든 문제가 아니고 별도 기획서가 다루고 있다.
- 문서 서술과 판정의 일치는 지금의 구현을 읽어 확인한 것이다. 판정이 나중에 바뀌면 문서가 먼저 낡는데,
  그 어긋남을 자동으로 잡아 주는 검사는 없다.
- 세 문서의 버전이 올라갔으므로 이미 설치된 프로젝트의 해당 문서는 다음 동기화에서 다시 쓰인다. 관리
  블록 규칙 자체는 이번 변경의 대상이 아니어서 그대로다.
