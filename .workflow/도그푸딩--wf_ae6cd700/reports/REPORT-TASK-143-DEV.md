# TASK-143 개발 보고서

## 결정권자 요약

작업이 막힐 때 현재 사유를 작업 문서에 남기는 고정 절을 관리 규칙과 개발자 계약에 넣었다.
제목과 네 라벨을 각각 한 번씩 쓰고 값을 비우지 않으며, 관련 대상이 없으면 없음이라고 적는다.
사유만 고치는 편집은 상태 전이가 아니므로 이력을 늘리지 않고, 차단이 풀려도 마지막 사유는 지우지 않는다.
같은 작업이 다시 막히면 절을 현재 사유로 교체하고 이전 상세는 보고서와 추가 전용 이력에 남는다.
기존 작업은 일괄 변환하지 않으며 절이 없거나 불완전한 문서도 계속 유효하다.
본문이 바뀐 두 계약만 버전을 올려 공통 규칙 18, 개발자 13이 되고 기획자와 아키텍트는 11에 머문다.
자동 검사 611개가 통과했고 사용자는 TASK-143 확인 동선의 수치와 설치본 문언을 확인하면 된다.

## 변경 파일과 모듈

- `src-tauri/src/infrastructure/project_instructions.rs`: 공통 규칙 5절에
  `### Recording why a task is blocked` 절을 더했다. 전이와 같은 편집에서 상태·이력·갱신 시각과 함께
  쓸 것, 제목과 네 라벨을 한 번씩 쓰고 값을 비우지 않을 것, 관련 대상의 없음 표기와 여러 값 나열법,
  사유 갱신이 전이가 아니라는 경계, 해제 뒤 보존과 재차단 시 교체, 기존 문서 호환성을 정의한다.
  개발자 계약에는 `## Blocking a task` 절을 더해 자기 의무만 적고 라벨 목록은 공통 규칙 `§5`를
  가리킨다. 현재 사유의 정본이 작업 문서이고 보고서가 그 자리를 대신하지 않는다는 문장을 넣었다.
  버전 상수와 규칙 본문 frontmatter를 공통 규칙 18, 개발자 13으로 올렸고 기획자·아키텍트는 11 그대로다.
  새 검사 하나가 제목·네 라벨·네 규칙·호환성·역할 분담과 네 버전 값을 대조한다.
- `docs/file-contract.md`: 개발 작업 절에 `### 막힌 사유 절`을 더해 같은 계약을 한국어로 적었다.
  형식 예시, 라벨 규칙, 전이·보존·재차단 규칙, 기존 문서 호환성, 현재 사유의 정본이 작업 문서라는
  점을 담았다.
- `src-tauri/src/infrastructure/fs_project_repository.rs`: 규칙 설치·갱신 검사가 직접 비교하는 버전
  문자열만 계약별로 골라 바꿨다. 공통 규칙 자리 여섯 곳과 개발자 계약 자리 두 곳이 대상이고 아키텍트
  계약 자리 두 곳은 그대로 두었다.
- `src-tauri/src/infrastructure/managed_project_assets.rs`: 같은 방식으로 버전 표와 픽스처 문자열을
  바꿨다. 공통 규칙과 개발자 계약만 올리고 기획자·아키텍트 문자열은 손대지 않았다.

## 검증 절차와 결과

- `cargo test --manifest-path src-tauri/Cargo.toml project_instructions` 통과: 22 passed, 0 failed.
- `cargo test --manifest-path src-tauri/Cargo.toml` 통과: 611 passed, 0 failed. 직전 610개에 새 계약
  검사 하나가 늘었다.
- `npm run check` 통과: 타입 검사 성공, 25개 파일 851 tests 통과, 배포 빌드 성공.
- `cargo clippy --all-targets` 경고 없음, `cargo fmt` 적용.
- 두 검사 파일의 치환 열여섯 곳을 각각 어느 계약 파일을 대상으로 하는지 판별해 대조했다. 모든 치환의
  대상 문자열이 그 계약의 현재 제공 버전과 일치하므로 아무것도 바꾸지 못하는 치환이 없다. 위쪽 방향
  픽스처 한 곳(아키텍트 계약을 11에서 12로 올려 덮어쓰지 않는지 보는 자리)은 방향을 그대로 두었다.
- 두 파일의 검사 개수, 단언 개수, 파일 줄 수가 변경 전과 같다. `fs_project_repository.rs`는 140개와
  401개와 7,638줄, `managed_project_assets.rs`는 16개와 72개와 1,558줄이다.
- 공통 규칙, 개발자 계약, 파일 안내 셋을 같은 항목표로 대조했다. 제목과 네 라벨이 공통 규칙과 파일
  안내에 한 번씩 있고 개발자 계약은 라벨을 복제하지 않으며, 전이·중복 금지·여러 값 표기·가짜 전이
  금지·해제 뒤 보존·재차단 교체·기존 문서 호환이 두 문서에서 같은 뜻으로 읽힌다.
- 개발 중인 앱이 세션 도중 관리 자산을 동기화해 이 저장소의 설치본이 실제로 갱신됐다. 결과는
  `.workflow/rules/workflow.md` 18, `developer.md` 13, `planner.md`와 `architect.md` 11로 의도한 값과
  같다. 실제 동기화 경로가 같은 결론을 낸다는 확인이다.

## 남은 리스크

- 규칙 문언은 사람이 읽는 계약이라 자동 검사는 문자열의 존재와 개수까지만 본다. 네 라벨이 실제로
  개발 세션에서 같은 뜻으로 채워지는지는 다음 차단이 일어날 때 처음 드러난다.
- 앱은 이 절을 요구하거나 검사하지 않는다. 작성 계약만 정했고 파서와 화면은 이 작업의 범위가 아니다.
  형식이 어긋난 절을 쓴 문서가 있어도 앱은 지금처럼 읽고 표시한다.
- 버전이 18과 13이 되어 기존 프로젝트의 두 파일은 다음 쓰기 명령에서 새 문언으로 교체된다. 교체는
  기존 동기화 경로가 하며 이 작업이 새 경로를 만들지 않았다.

## 후속 작업

- 이 절을 실제로 쓰는 첫 문서는 다음에 차단되는 개발 작업이다. 기존 작업 문서는 하나도 바꾸지 않았다.
- 절을 읽어 화면에 구조화해 보여 주는 일은 TASK-144와 TASK-145가 이미 맡았다. 이 작업은 작성 계약까지다.
- 이 세션은 `.workflow/rules/`를 편집하지 않았다. 설치본이 갱신된 것은 개발 중인 앱이 관리 자산을
  동기화한 결과이고, 검토 대상 변경 집합은 범위 파일 네 개뿐이다. 같이 나오는 `docs/handoff.md`도
  이 세션 착수 전에 이미 변경돼 있던 파일이다.
