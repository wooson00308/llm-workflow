# TASK-S080-04 개발 보고서

## 결정권자 요약

기획서 화면의 문서 목록 패널과 결정 패널, 아이디어 화면의 목록 패널에 리사이즈 핸들과 접기 버튼을
붙였다. 경계를 끌면 기획서 화면의 두 패널은 190px에서 420px, 아이디어 목록은 300px에서 520px 사이에서
움직이고, 더블클릭하면 정해 둔 너비가 지워져 지금과 같은 비율 배치로 돌아간다. 헤더 오른쪽 끝의 접기
버튼을 누르면 폭 28px 세로 바만 남고, 다시 누르면 접기 직전 너비로 돌아온다. 세 패널과 사이드바에서
되찾은 폭만큼 문서 본문의 읽기 폭 상한이 620px에서 오르고 860px에서 멈춘다. 한 번도 조절하지 않은
화면은 지금과 같은 배치와 620px 읽기 폭으로 그려지며, 개발 화면과 품질 확인 화면의 본문 폭도 그대로다.
자동 검증은 격리 사본과 통합 후 모두 통과했고(시험 719개), 실렌더로 최소 너비·접힘·좁은 창 배치를 눈으로
확인했다. 창 폭 980px 이하에서 접힌 문서 목록 칸이 190px 자리를 그대로 차지하는 한 가지는 아키텍트에게
넘긴다. 이 결과는 GROUP-080의 사용자 확인을 뒷받침한다.

## 검증 단계와 결과

- 격리 사본 `npm run check`: 통과. 시험 719개(36파일), 타입체크와 빌드 포함.

  두 커밋 사이 변경은 문서뿐이고 `src/`는 손대지 않았다. 리베이스 후 같은 719개 통과.

- 통합 후 검사: 통합 커밋으로 옮긴 격리 사본에서 `npm run check` 통과. 같은 719개.
- C1·C2·C3: 화면 시험에서 포인터 사건으로 끌어 최소·최대에서 잘리는 것과 저장값을 확인했다.
- C4·C5: 더블클릭이 저장한 너비만 지우고 기준 너비는 남기는 것, 방향키가 16px씩 움직이고 양 끝에서
  멈추는 것을 확인했다. 결정 패널은 왼쪽 경계를 잡아 방향키 부호가 반대인 것도 함께 봤다.
- C6·C7: 두 패널을 모두 접으면 격자 변수가 28px 둘이 되고, 세로 바의 툴팁과 접근 이름에만 패널
  이름이 들어가는 것을 확인했다. 조절한 적 없던 패널은 펼칠 때 변수가 다시 비었다.
- C8: 되찾은 폭이 없을 때 변수를 싣지 않고, 목록을 최소로 줄이면 670px, 두 패널을 접으면 860px에서
  멈추는 세 지점을 확인했다. 아이디어 화면도 같은 방식으로 확인했다.
- C10·C11: 대체 저장소로 확인했다. C11은 읽기와 쓰기가 모두 던지는 저장소에서 두 화면이 그려지고
  드래그와 접기가 그대로 도는 것까지 봤다.
- C12: 창 폭 600px에서 저장한 300px 둘이 190px로 줄어 그려지고 저장값은 300px로 남았다. 1024px로
  넓히자 300px이 다시 나왔다.
- C13·C14·C15: `documentPanelLayout.test.ts`가 세 격자 규칙의 되돌림 값과 영역 표의 최소값,
  좁은 창의 배치 전환과 핸들 비표시, 결정 보드와 작업 요약 상자와 품질 확인 화면의 폭을 맞대어
  확인한다. 막힌 작업 상자가 최대 폭을 정하지 않는다는 사실도 함께 확인한다.
- C16: `git status`에 선언한 파일 일곱 밖의 변경이 없다.
- 실렌더 확인(검증 절차 10): 두 화면을 픽스처로 띄우는 임시 진입점 둘을 만들어 크로미움 141로

## 남은 위험

- 헤더의 부가 정보가 자리를 옮겼다. 기획서 목록의 "5개 문서"와 아이디어 목록의 개수 배지가 오른쪽
  끝에서 제목 옆으로 붙는다. 접기 버튼이 오른쪽 끝을 쓰기 때문이며, 실렌더에서 읽기에 지장은 없었다.
- 드래그는 포인터가 움직일 때마다 저장소에 쓴다. TASK-S080-03이 남긴 위험과 같은 것이고, 패널이
  셋 늘어 쓰기가 일어나는 자리도 늘었다.
- 시험은 jsdom이라 격자 변수의 값까지만 확인한다. 실제 배치는 위 실렌더가 근거다.

  그대로 차지해 본문이 넓어지지 않는다. 그 시험과 미디어 규칙을 함께 선언한 작업이 필요하다.
