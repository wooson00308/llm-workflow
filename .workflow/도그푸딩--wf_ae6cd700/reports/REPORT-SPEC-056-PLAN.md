# SPEC-056 기획 보고서

## 결정권자 요약

QA 대기 큐의 정보 과부하 피드백을 표시 계층 변경 하나로 좁혀 기획했다.
QA 대기 카드의 미리보기를 요약 발췌에서 개발자가 쓴 확인 동선 첫 문단으로 바꾼다.
그러면 눈으로 볼 화면이 있는 작업과 자동 검사 수치를 신뢰하는 작업이 카드에서 바로 갈린다.
앱이 두 유형을 자동 분류하는 방향은 넣지 않았다. 문서에 고정 표식이 없어 추측이 되고,
표식을 만들려면 역할 계약과 규칙 문언을 고쳐 규칙 버전 상승 연쇄가 따라온다.
사용자 QA 도장은 작업별 사용자 전용 그대로이고 상태 기계와 결정 기록은 건드리지 않는다.
지금 요청하는 것은 SPEC-056의 승인 여부다.

## 대상 선택

- 사용자 피드백에서 나온 IDEA-C0BBA9A3을 처리했다. 이 아이디어를 참조하는 기획서는 없었다.
- 선점 대상은 아이디어 하나이며 lease를 받아 작업하고 반납했다.
- 앱 코드, 다른 기획서, 개발 작업, 결정 기록은 변경하지 않았다.

## 조사와 실측 (2026-08-08)

기획서의 근거로 다음을 코드와 문서에서 직접 확인했다.

- 개발자 계약 `.workflow/rules/roles/developer.md`는 화면이 없는 작업의 확인 동선에 "자동 검사로
  닫혔고 확인 도장은 그 수치를 신뢰한다는 뜻"임을 평문으로 적도록 이미 요구한다. 다만 고정 문구는
  없다. 현재 QA 대기 네 건에도 "이 작업에는 눈으로 볼 화면이 없다"와 "화면 확인 대상은 없다" 두
  표현이 섞여 있다. 앱이 문구로 유형을 판정할 근거가 없다는 뜻이다.
- 일괄 확인 경로는 이미 있다. `confirm_task_qa_batch`가 건별로 QA 결정 문서를 남기고, 화면에서는
  레인 헤더의 일괄 확인 화면이 그 경로를 부른다(SPEC-031). 도장이 작업별로 남는 성질은 유지된다.
- 확인 동선은 이미 단건 QA 패널에서 도장 옆에 표시된다(SPEC-039 R7,
  `src/features/projects/components/DevelopmentBoard.tsx`의 확인 동선 영역). 목록 카드에는 없다.
- QA 대기 카드는 상태 배지, 문서 id, 제목, 요약 발췌, 날짜만 보여준다. 발췌는 백엔드
  `markdown_excerpt`가 본문에서 제목 줄과 빈 줄을 뺀 앞 세 줄로 만든다. 그래서 카드에는 결정권자
  요약의 앞부분이 실리고 확인 방법은 실리지 않는다.
- 목록 조회는 이미 문서마다 본문 전체를 읽어 그 발췌를 만든다(`fs_project_repository.rs`의 목록
  구성 경로). 같은 본문에서 값을 하나 더 뽑아도 파일 읽기는 늘지 않는다.
- 절 분리 도구는 이미 있다. `src/features/projects/domain/documentSections.ts`의 `splitSection`이
  코드 펜스를 인식하고 같은 깊이의 다음 제목까지를 절로 자른다.
- 현재 QA 대기는 TASK-143, TASK-S051-03, TASK-S051-04, TASK-S052-01 네 건이고 SPEC-051, SPEC-052,
  SPEC-053 세 레인에 흩어져 있다. 네 건 모두 화면이 없는 작업이다.

## 기획 결정과 범위

- 표시 계층만 바꾼다. 규칙 문언(`project_instructions.rs`)과 역할 계약을 바꾸지 않으므로
  `fs_project_repository.rs`와 `managed_project_assets.rs`의 규칙 버전 단언 연쇄가 발생하지 않는다.
- 앱은 유형을 분류하지 않는다. 개발자가 쓴 문장을 그대로 옮기고, 사람이 읽어 판단한다. 문서 화면이
  이미 따르는 "추측하지 않고 구조가 어긋나면 원문에 맡긴다"(SPEC-039 R2)와 같은 원칙이다.
- 사용자가 참고 방향으로 말한 두 가지는 각각 근거를 적어 채택하지 않았다. "정말 필요한 것만
  보여주기"는 앱이 확인 필요 여부를 판정한다는 뜻이라 도장의 의미를 약화한다. "선행 관계 묶음"은
  레인 단위 묶음이 이미 있고, 실측에서 네 건이 세 레인에 흩어져 있어 카드 수가 크게 줄지 않는다.
- 계약 이전에 쓰인 작업 문서는 고치지 않는다. 확인 동선 절이 없으면 지금 발췌를 그대로 쓴다.

## 검증

- IDEA-C0BBA9A3을 참조하는 기획서가 없음을 확인한 뒤 lease를 받고 SPEC-056을 만들었다.
- 위 실측 항목을 모두 코드와 문서 원문에서 직접 읽어 확인했다. 추정으로 적은 사실은 없다.
- SPEC-056의 결정권자 요약이 구조화 형식을 지키는지 확인했다. 일곱 하위 제목이 계약 순서대로 한
  번씩 있고, 영향 범위 아래에 변경과 유지 두 표식이 한 번씩 있으며, 요약 안에 역따옴표, 파일 경로,
  식별자가 없다.
- 기획서와 이 보고서에 영문식 긴 대시가 없는지 확인했다.
- 앱 소유 상태와 결정 기록은 읽기만 했다.

## 인계 사항

- 승인 뒤 아키텍트가 정할 사항: 카드에 실을 값을 목록 조회에서 만들지, 화면에서 본문을 받아 만들지.
  목록이 2.5초마다 다시 읽히는 자리라 두 선택의 비용이 다르다. 파일 읽기 횟수는 어느 쪽이든 늘지
  않는다.
- 앱이 화면 확인형과 수치 신뢰형을 자동 분류하려면 확인 동선에 고정 표식이 필요하고, 그것은 개발자
  계약과 규칙 문언 변경 및 규칙 버전 상승 연쇄를 부른다. 사용자가 그 분류까지 원하면 별도 아이디어로
  다시 여는 편이 맞다.
- 승인 전에는 구현하지 않는다.
