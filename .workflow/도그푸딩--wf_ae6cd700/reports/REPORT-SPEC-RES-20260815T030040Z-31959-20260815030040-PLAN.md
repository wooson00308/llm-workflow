## 기획 판단

### 완료 의미를 둘로 나누지 않았다

격리 검사 완료와 공유 기준 통합 완료는 실행 단계로 구분하되 태스크 상태를 새 완료 상태로 나누지 않았다.
`verified`는 격리 검사, 통합, 공유 기준 재검사와 보고서가 모두 끝난 상태로 유지했다. 이 선택으로 그룹 QA와
자동 그룹 완료가 격리 사본만 보고 열리는 일을 막고 기존 사용자 관문을 그대로 보존한다.

### 통합은 개발자 역할의 마지막 책임으로 정했다

아키텍트는 작업 정의와 범위를 책임지며 제품 코드를 고치지 않는다. 통합 충돌은 구현 변경을 가장 잘 아는
역할이 해결해야 한다. 따라서 새 역할이나 아키텍트 권한 확장 대신 같은 태스크의 개발자 역할이 통합을
수행하도록 정했다. 최초 세션이 끝났으면 같은 태스크를 다시 선점한 개발자 세션이 저장된 통합 후보를
인수한다.

### 제어 문서와 제품 코드를 서로 다른 면으로 분리했다

개발 세션 전체를 worktree 안에만 두면 태스크 상태와 보고서도 격리 브랜치에 갇혀 앱이 진행 상황을 읽지
못한다. lease, 태스크 상태와 역할 보고서는 공유 프로젝트 정본에 즉시 쓰고, 제품 코드·빌드·검사만 격리
사본에서 수행하도록 요구했다. 제품 변경 커밋에는 워크플로우 상태를 섞지 않아 통합 때 오래된 문서가 정본을
덮어쓰지 않게 했다.

### 런타임이 사본을 준비하도록 정했다

런타임은 이미 예약 성공과 provider 시작 사이를 소유하고 실행을 복구한다. 그 사이에 사본을 준비하면 사본
실패 때 유료 세션을 시작하지 않고 자신의 lease를 정리할 수 있다. 세션이 임의 경로와 브랜치를 만들게 하면
자동·수동 배정과 재시작 복구가 서로 다른 답을 가질 수 있으므로 허용하지 않았다.

### 직접 작업은 통합 때도 자동 조작하지 않는다

공유 작업 공간이 깨끗하지 않으면 통합만 기다린다. 사용자 변경을 자동 stash, commit, reset, checkout 또는
삭제하지 않는다. 다른 비겹침 태스크는 격리 환경에서 계속 구현할 수 있어 원본 아이디어의 병행 목표를
지키고, 충돌은 기준이 확정된 뒤 명시적으로 해결한다.

### 범위 판정은 계속 시작 조건으로 남겼다

worktree가 파일의 물리 충돌은 막아도 공개 계약과 함수 시그니처 같은 의미 충돌은 막지 못한다. 따라서
`scope_files`와 `depends_on`을 자동 태스크의 시작 조건으로 유지했다. 직접 작업은 이 선언 밖에 있으므로
그 빈칸은 격리와 통합 비교가 담당한다. 개발자에게 누락 범위를 자동 확장할 권한은 추가하지 않았다.

### 저장 공간 상한을 수치로 정했다

런타임 관리 사본과 빌드 자료의 기본 기기 상한을 20GiB, 새 실행을 막는 데이터 볼륨 여유 하한을 10GiB로
정했다. 성공·취소 사본과 재생성 가능한 산출물을 먼저 회수하고 통합되지 않은 변경 커밋과 사용자 작업은
보존한다. 2026-08-13의 106GB 실측을 다시 허용하지 않으면서 현재 10GB 빌드 자료를 바로 불가능하게 만들지
않는 보수적 기본값이다.
