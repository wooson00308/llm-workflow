# TASK-S071-03 개발 보고서

## 결정권자 요약

실행 화면에 사용 한도 대기를 알리는 자리를 세웠다. 어느 실행 도구가 쉬고 있고 언제 다시 시작하는지가
화면 맨 위 한 문장으로 보이고, 다시 시작할 시각을 실행 환경에서 받지 못했으면 시각을 지어내지 않고
남은 대기만 보여 준다. 보류 중인 실행 도구가 둘이면 둘 다 보인다. 보류가 없으면 안내를 그리지 않아
화면은 지금과 같다. 한도로 끝난 실행은 목록과 상세 모두에서 사용 한도에 도달했다고 적히고, 자리 소진과
대상 없음과 로그인 필요는 각각 자기 문장을 지켰다. 직접 배정은 한도 대기 사실을 알리되 시작을 막지
않는다. 화면 시험 548건과 백엔드 892건, 통합 시험 28건이 통과했고 형식 검사와 생산 빌드도 통과했다.
이 결과는 GROUP-071의 자동 검증 가운데 대기 상태를 사용자에게 보여 주는 부분을 뒷받침한다.

## 바꾼 파일과 모듈

- `src/features/projects/domain/types.ts` — 실행 목록 응답 타입에 실행 도구별 보류 항목
  `providerHolds`와 그 항목 타입 `AgentProviderHold`를 더했다. 선택 항목이라 값을 싣지 않는 응답도
  지금과 같이 읽힌다. 이름과 형태는 백엔드가 내보내는 값에 맞췄다.
- `src/features/projects/components/agents/AgentRunDashboard.tsx` — 화면 본문 첫 자리에 한도 대기
  구역을 세웠다. 문장을 만드는 `holdNotice`와 남은 대기를 세는 `holdWaitLabel`을 더했고, 남은 대기가
  낡지 않도록 이미 있던 30초 갱신에 보류를 조건으로 함께 넣었다. 사유를 문장으로 옮기는
  `exclusionLabel`·`reasonLabel`·`humanRuntimeMessage` 세 자리가 판정 함수 `reachedUsageLimit`
  하나를 함께 쓴다. 직접 배정 창에는 고른 역할의 실행 도구가 대기 중이라는 안내 한 줄을 더했고,
  단추의 활성 조건은 손대지 않았다.
- `src/features/projects/components/agents/AgentRuntimeView.test.tsx` — 한도 대기 표시 검사 일곱
  건을 더했다. 응답 조립 도우미가 보류 목록을 받도록 인자를 하나 늘렸다.
- `src/App.css` — 안내가 여러 줄일 때 실행 도구별 문장이 한 문단으로 읽히지 않도록, 기존 안내 문장
  스타일 옆에 인접 규칙 한 줄을 더했다.

설계 판단 두 가지를 적어 둔다. 첫째, 한도 도달 구분값은 화면 쪽 상수 하나로 두고 세 함수가 함께
쓰게 했다. 판정은 문자열이 정확히 같을 때만 참이다 — 실행 환경이 쓰는 값이 자리 소진 값을 부분
문자열로 품고 있어, 판정 차례를 자리 소진보다 앞에 두지 않으면 계정 사용 한도가 자리 소진 문장에
먼저 삼켜진다. 값의 정본은 백엔드 상수이고, 그 자리를 상수 옆 주석에 적었다. 둘째, 안내는 배정 대기
구역 밖에 세웠다. 그 구역은 대기 후보가 없으면 통째로 사라져, 안에 넣으면 보류만 있는 순간에 안내가
함께 사라진다.

## 검증 절차와 결과

격리 사본과 통합 후 결과를 함께 적는다. 통합 직전에 공유 기준이 후보의 기준 커밋 06b91f5와 같았고,
옮길 변경이 없어 그대로 통합했다. 두 자리의 결과는 아래와 같이 모두 같다.

1. `npx vitest run src/features/projects/components/agents/AgentRuntimeView.test.tsx` — 96건 통과.
   완료 조건 C15가 요구한 검사 일곱 건이 모두 들어 있다.
2. `npm run test` — 시험 파일 29개, 548건 통과(42건 건너뜀), 실패 0.
3. `npm run typecheck` — 통과.
4. `npm run check` — 형식 검사와 생산 빌드 통과.
5. `cargo test --manifest-path src-tauri/Cargo.toml` — 892건 + 통합 28건 통과, 실패 0. 백엔드를
   고치지 않았고 값도 달라지지 않았다.
6. `git status` — 격리 사본의 변경 파일이 선언한 네 개뿐이다. `.workflow` 아래 변경은 없다.

새 검사가 실제로 판정을 잡는지 한 번 확인했다. 사유 판정에서 한도 도달 분기를 지우고 돌리자 목록과
상세 검사가 실패했고, 되돌린 뒤 다시 통과했다.

통합은 fc6dcec로 이뤄졌다. 통합 직전에 공유 저장소에서 확인한 미커밋 변경은 이 작업의 상태 전이
문서 하나뿐이었고, 그것은 6f9feb4로 먼저 따로 실었다. 사용자의 미커밋 변경과 겹치는 파일은 없었다.
통합 후 검사는 작업 트리가 깨끗한 그 커밋 자리에서 위 1번부터 5번까지를 다시 돌린 결과다.

## 남은 위험

- 한도 도달 구분값이 백엔드와 화면 두 곳에 적혀 있다. 값이 갈라지면 화면이 한도를 알아보지 못하고
  지금의 자리 소진 문장으로 되돌아간다. 상수 옆 주석에 정본의 자리를 적어 두었다.
- 실행 도구 이름은 화면 문장에 그대로 쓴다. 실행 환경이 사용자가 설정 화면에서 만나지 않는 이름을
  보류에 실으면 사용자가 모르는 낱말이 문장에 나올 수 있다.
- 남은 대기는 30초마다 다시 계산한다. 직접 배정 창의 안내는 창을 열어 둔 동안 다시 그릴 때마다
  계산하므로, 창을 오래 열어 둔 채 아무것도 누르지 않으면 그 자리의 값만 낡을 수 있다.
- 보류가 실제로 실려 오는지는 실행 목록 응답을 만드는 TASK-S071-01의 몫이고, 이 작업의 검사는 그
  값이 실려 온 응답을 직접 주어 화면만 확인했다.
