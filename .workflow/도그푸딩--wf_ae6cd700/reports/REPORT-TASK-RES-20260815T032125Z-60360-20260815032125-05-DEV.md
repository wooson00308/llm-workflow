## 결정권자 요약

작업 그룹이 품질 확인을 열 수 있는 상태가 되는 시점에 확인 대상 코드 상태를 고정하고, 사용자가
결과를 제출할 때 그 상태가 그대로인지 다시 확인하도록 구현했다. 고정 값은 앱이 소유하는 실행
상태로 저장하며, 한 번 정해지면 같은 구성 버전에서는 다시 바뀌지 않는다. 확인 도중 코드가 바뀐
채로 제출하면 완료 기록을 만들지 않고, 문서가 바뀌었을 때와 구분되는 안내가 돌아간다. 같은 요청
식별자로 이미 남은 제출은 지금처럼 그대로 돌려준다. 자동 확인 그룹은 코드가 어긋나면 완료로
넘어가지 않고 개발 단계에 남는다. Git으로 관리하지 않는 프로젝트에서는 고정 값이 생기지 않고 모든
판정이 이전과 같다. 완료 조건 아홉 가지를 재현하는 자동 검사 일곱 개를 새로 넣었고, 격리 사본과
공유 기준 양쪽에서 전체 자동 검사가 통과했다. 이 결과는 이 작업이 속한 작업 그룹의 자동 검증에
완료된 항목으로 들어간다.

## 판단이 필요했던 지점

자동 모드 그룹이 완료로 넘어가지 못할 때 쓸 화면 상태를 새로 만들지 않고 기존 `Developing`을
재사용했다. 상태 값을 늘리면 화면 쪽 타입 선언과 표시 문구 표를 함께 고쳐야 하는데, 이 태스크는
그 파일을 범위 밖으로 명시했다. 태스크 문서만으로 구현이 가능했고 기획서는 열지 않았다. 그룹
문서와 결정 문서는 자격 판정에 필요한 범위에서만 읽었다.

## 남은 위험

- 고정 값은 같은 구성 버전에서 다시 만들어지지 않는다. 그래서 확인이 열린 뒤 공유 기준이 한 번이라도
  앞으로 나가면, 그 구성 버전의 그룹은 사용자가 다시 확인하더라도 제출이 계속 거절된다. 자동 모드
  그룹도 같은 이유로 완료 상태에서 개발 단계로 내려온 뒤 돌아오지 못한다. 완료 조건이 요구한 동작을
  그대로 구현한 결과이며, 판정을 완화하지 않았다. 아래 후속 항목으로 넘긴다.
- 자동 모드 그룹이 기준 어긋남으로 내려올 때 화면에는 "개발 중"으로 보인다. 소속 작업이 모두 끝난
  상태이므로 표시 문구가 실제 사정을 설명하지 못한다.
- 기준 커밋은 상태 조회마다 최대 한 번 `git rev-parse HEAD`를 실행해 읽는다. 품질 확인을 열 수 있는
  그룹이 하나도 없으면 실행하지 않지만, 그런 그룹이 있으면 조회 때마다 프로세스가 하나 뜬다.
- 반영 도중 공유 작업 공간에 `src-tauri/src/infrastructure/reservation_helper.rs`의 미커밋 변경이
  나타났다. 이 세션이 만든 것이 아니어서 손대지 않았고, 8번의 공유 기준 검사는 그 변경이 함께 있는
  작업 트리에서 돌았다. 이 태스크의 범위 파일과 겹치지 않으며 체리픽에서 충돌도 없었다. 그 변경은
  이후 그 주체가 `372f7b1`로 직접 커밋했다.
