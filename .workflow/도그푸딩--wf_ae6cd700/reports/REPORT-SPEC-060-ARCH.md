## 결정 사항

### 그룹 확인 방식은 사용자 품질 확인으로 정했다

바뀌는 결과가 개발 작업 화면과 기록 화면에서 사용자가 직접 보는 작업 그룹의 상태다. 갇혀 있던 그룹이
실제로 완료로 정리되었는지는 화면을 열어 목록과 진행 중 수치를 보는 것으로만 확인된다. 수용 기준 3이
요구하는 확인도 사람이 화면에서 보는 확인이다. 그래서 자동 확인이 아니라 사용자 확인으로 두었다.

### 자동 확인 모드는 판정 시점의 기준 커밋에서 판정하고 그 값을 다시 기록한다

`parse_work_group`의 되돌림 분기(3184~3190행)를 없애고, 자동 확인 판정이 쓰는 기준 기록을 판정
시점 값으로 갱신하게 했다. R1이 요구하는 두 문장을 그대로 옮긴 것이며, 완료 판정 조건 자체
(3127~3172행 분기)는 건드리지 않는다. 판정은 프로젝트를 읽을 때마다 다시 계산되므로 갇힌 그룹은
다음 읽기에서 스스로 회복된다. 이전 절차나 파일 수동 삭제를 요구하지 않는다는 R2가 이 구조로 성립한다.

기록 파일을 읽기 경로에서 쓰는 것이 새로 생기는 부작용은 아니다. 지금도 `pin()`이 조회 경로에서 첫
고정을 쓴다. 값이 같으면 쓰지 않으므로 정상 상태에서는 쓰기가 늘지 않는다.

### 사용자 확인 모드는 확인 시점의 코드 상태를 제출에 실어 R3을 지키면서 R4를 연다

R3과 R4를 동시에 만족시키려면 서버가 "사용자가 무엇을 보고 확인했는지"를 알아야 한다. 서버가 보는
것은 제출 한 번뿐이고, 확인을 시작한 시점은 화면에만 있다. 그래서 화면이 확인할 때 읽고 있던 기준
커밋을 제출에 실어 보내고, 서버가 그 값과 현재 값을 비교하게 했다. 이미 `expected_revision`과
`expected_updated_at`이 같은 방식으로 쓰이고 있어 새 방식을 도입하는 것이 아니다.

실을 값은 확인 결과를 고른 시점의 값이며, 임시 결정에 함께 저장한다. 제출 시점의 최신 요약을 다시
읽어 실으면 안 된다. 제출이 거절되면 화면이 곧바로 프로젝트를 다시 읽기 때문에
(`useProjectWorkspace.ts` 1644~1655행), 최신 값을 싣는 구현에서는 사용자가 다시 확인하지 않고
제출을 한 번 더 누르는 것만으로 확인하지 않은 코드에 결과가 붙는다.

기각한 대안을 적어 둔다. 거절할 때 서버가 기준을 새 값으로 다시 잡아 두는 방식은 화면을 손대지 않고
R4를 만족시킬 수 있다. 그러나 위와 같은 이유로 두 번째 제출이 그대로 기록되어, R3은 "코드가 바뀐 뒤
첫 제출 한 번은 거절된다"는 뜻으로 약해진다. 확인한 대상과 기록되는 대상이 어긋나지 않게 하는 것이
이 보호의 목적이므로 이 대안을 택하지 않았다.

### 작업을 둘로 나눈 이유는 보호가 끊기는 구간을 만들지 않기 위해서다

한 작업으로 묶으면 다섯 파일 이상을 한 번에 바꾸게 되고, 반대로 계층으로 나누면 백엔드가 새 필드를
받기 시작한 뒤 화면이 그 값을 실을 때까지 사용자 확인 모드의 보호가 비는 구간이 생긴다. 그래서
경계를 계층이 아니라 확인 방식으로 그었다.

- TASK-S060-01은 자동 확인 경로만 바꾸고 사용자 확인 경로를 그대로 둔다. 이 작업만 끝난 상태에서도
  R3은 지금 그대로 작동하고, R1·R2는 이미 확인할 수 있다.
- TASK-S060-02가 사용자 확인 경로를 한 번에 바꾼다. 제출 요청 필드 추가, 판정 전환, 화면의 값 저장과
  임시 결정 처리가 한 작업 안에서 함께 끝난다.

두 작업은 같은 파일(`fs_project_repository.rs`)의 같은 판정 자리를 손대고 02가 01이 만드는 갱신
동작을 재사용하므로, 02에 `depends_on: [TASK-S060-01]`을 적어 순서를 고정했다. 겹치는 쌍은 이 하나뿐이고
순환은 없다.

### 화면 초기화 자리를 02의 완료 조건에 넣었다

`QaWorkbench.tsx` 53행의 `key`는 워크플로 디렉터리·그룹 식별자·구성 버전이 바뀌면 확인 화면을 처음
상태로 돌린다. 확인 대상 기준이 이 값에 들어가지 않으면, 거절 뒤 요약이 갱신되어도 사용자가 고른
결과가 화면에 남아 제출을 다시 눌러도 같은 거절만 반복된다. R4가 요구하는 "같은 거절이 무한히 반복되는
상태가 남지 않는다"를 화면 쪽에서 닫는 자리라서 완료 조건 C6에 함께 적었다.

기존 시험 셋은 이 변경이 바꾸는 규칙을 고정하고 있다. 지우고 지나갈 시험이 아니라 기대값을 고쳐 쓸

## 검증

- 문서 형식을 자기 점검했다. 작업 둘의 `## 결정권자 요약`은 `.workflow/rules/workflow.md` §8의

  따라 한국어로 썼고 영어 em dash를 문장 구분자로 쓰지 않았다.
- `scope_files`는 두 작업 모두 0열에서 시작하는 한 줄 flow 시퀀스이고, 경로는 저장소 루트 기준이며
  허용 문자만 쓴다. `depends_on`은 02에만 있고 존재하는 작업 하나를 가리킨다.
- 그룹의 사용자 확인 플로우는 `### QA-01 · 제목` 한 절이고, 번호 목록과 각 항목 안의 인용 한 줄
  형식을 GROUP-059와 같게 맞췄다. 터미널 명령, 패키지 실행 명령, 저장소 조작, 내부 시험 절차를 넣지
  않았다.
- 앱 소유 상태는 건드리지 않았다. 결정 문서, `project.yml`, `workflow.yml`, `.workflow/.runtime/`
  아래 파일을 만들거나 수정하지 않았고 lease는 헬퍼로만 다뤘다. 기획서 파일도 열어 읽기만 했다.
- 기존 문서 경로를 덮어쓰지 않았다. GROUP-060, TASK-S060-01, TASK-S060-02, 이 보고서 모두 쓰기
  직전에 경로가 비어 있음을 확인한 새 파일이다.
- 제품 소스 코드는 한 줄도 바꾸지 않았다.
