## 대상 선정 근거

- `decisions/`의 앱 소유 기획서 결정 8건은 전부 `outcome: approved`다. 그중 파생 작업이 없는 것은
  DECISION-E03D1301(SPEC-008) 하나다. 나머지 일곱은 TASK-001·002(SPEC-001), TASK-003~007(SPEC-002),
  TASK-008~012(SPEC-003), TASK-013(SPEC-004), TASK-014~018(SPEC-005), TASK-019~021(SPEC-006),
  TASK-022~025(SPEC-007)이 이미 참조한다.
- 착수 시점에 `.workflow/.runtime/migration.lock` 없음, `leases/` 비어 있음. 배타 생성으로
  `leases/SPEC-008.yml`을 만든 뒤 `tasks/`·`reports/`에 SPEC-008이나 DECISION-E03D1301을 참조하는
  문서가 없음을 다시 확인하고 작업했다.
- SPEC-008 본문은 `status: user_review`지만 앱이 기록한 승인 결정이 있으므로 공통 규칙 5절의 차단
  조건에 걸리지 않는다. SPEC-006·SPEC-007도 같은 상태다. 결정 본문이 확인 필요 1·2번을 "기획서의
  제안대로"로 확정했으므로, 패널 안 스크롤과 실패 노출을 확정된 요구사항으로 다뤘다.

읽기 경로 → 화면, 둘이다.

| 작업 | 요구사항 | 기획서 완료 조건 |

| TASK-026 읽기 경로 (Rust ~ 훅) | R7, R1의 전제 | 5(백엔드), 7(백엔드), 14, 15, 16 |
| TASK-027 미리보기 화면 | R1, R2, R4, R5, R6, R3 보존 | 1~13, 16 |

세 번째 작업으로 쪼개지 않았다. 화면 쪽을 "본문 렌더"와 "레이아웃·스크롤"로 나누는 안을 검토했지만,
둘은 같은 컴포넌트의 같은 블록과 같은 CSS 규칙을 만지고, 레이아웃만 끝난 상태는 확인할 것이 없다.
TASK-027 하나가 크지만 파일 다섯 개에 걸친 한 덩어리의 변경이다.

경계를 읽기 경로에서 끊은 이유는 두 가지다.

1. TASK-026만 끝난 상태가 독립적으로 검증된다. Rust 테스트로 "본문이 온다 / frontmatter가 없다 /

   그대로 덮는다. 화면 없이도 완결된다.
2. 두 작업의 파일이 겹치지 않는다. TASK-026은 Rust 4개 + `types.ts`·`tauriProjectGateway.ts`·
   `useProjectWorkspace.ts`, TASK-027은 `IdeaInbox.tsx`·`WorkspaceShell.tsx`·`App.tsx`·`App.css`와

TASK-026이 끝난 시점에 훅의 `readIdea`를 부르는 곳이 없다. 한 커밋 동안 쓰이지 않는 반환값이
생기는 것은 의도한 상태이고 타입 검사는 통과한다. 이것을 피하려고 화면까지 한 작업에 묶으면
리뷰 단위가 Rust와 React를 한꺼번에 안게 된다.

## 아키텍트가 정한 것

기획서가 아키텍트에게 명시로 위임한 항목과, 구현이 갈릴 수 있어 미리 못박은 항목이다.

1. **조회는 문서 하나 단위. 목록에 본문을 싣지 않는다.** `inspect`는 2.5초마다 돈다
   (`useProjectWorkspace.ts:305`~`:308`). 목록 요약에 본문을 얹으면 폴링마다 모든 아이디어 파일을
   통째로 읽어 IPC로 넘기게 된다. 기획서·개발 작업이 이미 문서 단위 읽기 경로를 쓰는 이유와 같다.
2. **`IdeaDocument { summary, body }` 모양을 유지하고, 요약 상태에 `adopted`를 반영한다.** 화면은
   R4에 따라 목록 요약으로 머리·바닥을 그리므로 `summary`를 쓰지 않는다. 그래도 `SpecDocument`·
   `TaskDocument`와 모양을 맞췄고, `read_spec`이 반환 전에 상태를 정규화하는 것과 같은 규칙으로
   채택 여부를 반영하게 했다. 목록은 `adopted`를 보여주는데 문서 읽기는 `inbox`를 돌려주는 어긋남을
   남기지 않기 위해서다. 비용은 사용자가 아이디어를 고를 때 `specs/` 한 번 훑기이고, `workflow_items`가
   이미 폴링마다 하는 일과 같은 성격이다.
3. **실패 표시는 컴포넌트 안에 둔다. 전역 오류 배너에 기대지 않는다 (R5가 세부를 위임).**
   `inspect`가 폴링 경로에서도 `setError(null)`을 실행한다(`useProjectWorkspace.ts:50`). 즉 전역
   배너에 띄운 조회 실패 문구는 2.5초 안에 지워진다. R5가 요구하는 "실패했다는 사실이 보인다"를
   전역 배너로 만족시킬 수 없다. `readIdea` 자체는 `readTask`와 동일하게(실패 시 `setError` +
   `null` 반환) 두고, 화면은 `null`을 실패 상태로 받아 자기 안에 보존한다.
4. **화면 아래 로딩 토스트는 만들지 않는다 (R5가 세부를 위임).** 기획서 화면에 토스트가 있는 것은
   그 로딩 상태를 셸이 들고 있기 때문이다(`WorkspaceShell.tsx:101`, `:385`). 아이디어 조회 상태는
   `IdeaInbox` 안에 있고, 토스트 하나를 위해 상태를 셸로 끌어올리면 컴포넌트 경계가 흐려진다.
   사용자가 보고 있는 곳은 미리보기 패널이므로 패널 안 표시로 충분하다.
5. **조회는 클릭이 아니라 선택된 파일명을 보는 효과로 건다.** R1이 자동 선택된 첫 항목도 전문이
   보여야 한다고 요구한다. `IdeaInbox`에는 클릭을 거치지 않는 선택 경로가 둘 있다 — 초기값(`:14`)과
   목록에서 사라졌을 때의 재선택(`:18`~`:22`). 클릭 핸들러에 조회를 걸면 둘 다 빠진다.
6. **효과 의존성은 파일명 문자열 하나뿐이고, 조회 함수는 ref로 넘긴다.** 폴링이 `project` 객체를
   2.5초마다 새로 만들고, `readIdea`의 `useCallback` 의존성에 `project`가 있어 함수 정체성이 같이
   바뀐다. 그 함수를 효과 의존성에 넣으면 2.5초마다 재조회가 돌아 로딩 깜빡임과 스크롤 초기화가
   반복된다. 이 저장소에는 eslint가 없어 의존성 누락을 잡아 주는 장치도 없으므로 작업 문서에 이유를
   적어 뒀다.
7. **늦게 온 응답을 버린다.** 목록을 빠르게 오가면 이전 문서의 응답이 나중에 도착할 수 있다.
   R1의 "이전 문서의 본문이 남아 있어서는 안 된다"가 여기서 깨진다. `DevelopmentBoard`의
   `openTask`(`:56`)에는 이 처리가 없지만, 그쪽은 클릭으로 여는 전체 화면 전환이라 선택이 연속으로
   바뀌지 않는다.
8. **스크롤 초기화는 `key`로 한다.** 스크롤 컨테이너에 `key={item.fileName}`을 주면 문서가 바뀔 때
   다시 마운트되어 위치가 0이 된다(R6). `scrollTop`을 직접 되감는 것보다 짧고, 로딩·실패 상태를
   오갈 때도 결과가 같다.
9. **높이 상한은 본문 영역에 건다.** 왼쪽 `.idea-list`가 `max-height: 430px; overflow: auto`
   (`App.css:242`)로 이미 자기 안에서 스크롤한다. 오른쪽도 같은 위치 — 머리와 바닥 사이의 본문
   영역 — 에 상한을 걸면 2단 구조가 유지되고(R6), 제목·상태·문서 정보가 스크롤 밖에 남아 R4가
   구조로 성립한다. `.spec-paper.embedded`(`:296`)가 같은 방식의 선례다.
10. **문구는 기획서 화면의 어법을 그대로 옮긴다.** 로딩은 `아이디어를 불러오는 중…`
    (`기획서를 불러오는 중…`, `SpecWorkspace.tsx:131`과 같은 꼴), 실패는 실패 사실을 남기는 한 줄이다.
    새 어투를 만들지 않는다.

## 확인한 사실

추정 없이 파일에서 읽은 값이다. 확인 시점 2026-08-02.

- 목록 행(`IdeaInbox.tsx:58`)과 미리보기(`:104`)가 같은 `item.excerpt`를 쓴다. 미리보기는 `<p>`
  하나로 그린다. 기획서의 전제와 일치한다.
- `markdown_excerpt`(`fs_project_repository.rs:935`)는 빈 줄과 `#`으로 시작하는 줄을 뺀 뒤 앞 세
  줄을 이어 붙이고 160자에서 자른다. 불릿 기호(`-`, `*`)는 `trim_start_matches`로 떨어져 나가므로,
  불릿 목록 아이디어는 목록 구조를 잃은 채 한 문단으로 붙는다.
- `read_markdown_document`(`:849`)가 `split_frontmatter`(`:894`)로 frontmatter를 떼고 `body.trim()`을
  돌려준다(`:890`). 기획서 완료 조건 5는 백엔드에서 이미 성립하고, 화면이 그 값을 그대로 그리면 된다.
- `safe_markdown_file`(`:758`)은 단일 경로 성분·`.md` 확장자·심볼릭 링크 아님을 검사한다.
  `read_spec`(`:240`)과 `read_task`(`:258`)가 각각 자기 디렉터리를 넘겨 부른다. 아이디어도 같은
  함수에 `ideas/`를 넘기면 기획서 완료 조건 15가 성립한다.
- 아이디어 목록의 기본 상태는 `"inbox"`이고 채택 판정은 `adopted_idea_ids`(`:799`)가 `specs/`의
  `source_idea_id`를 모아서 한다(`workflow_items`, `:786`~`:791`).
- `lib.rs` 핸들러 목록에 `read_spec`·`read_task`가 `:17`~`:18`에 등록되어 있다. 커맨드는 등록하지
  않아도 Rust 테스트가 전부 통과하므로 이 단계가 조용한 실패 지점이다.
- 훅의 `readSpec`(`useProjectWorkspace.ts:125`)·`readTask`(`:143`)는 실패를 `setError`로 올리고
  `null`을 돌려준다. 반면 `inspect`(`:47`)는 `silent`일 때도 `setError(null)`을 실행하고(`:50`),
  2.5초 인터벌이 그 `inspect`를 부른다(`:306`). 그래서 전역 배너는 조회 실패 표시로 쓸 수 없다.
  연동 조회가 같은 이유로 실패를 전역에 올리지 않는다는 주석이 `:237`~`:238`에 이미 있다.
- 문서를 읽어 화면에 그리는 컴포넌트 선례는 `DevelopmentBoard`다. `onReadTask` prop(`:33`), 자체
  로딩 상태(`:43`~`:44`), `MarkdownBody` 사용(`:239`)이다.
- `MarkdownBody`는 `remark-gfm`을 쓰고 링크에 `target="_blank"`·`rel="noopener noreferrer"`를 붙인다.
  기획서·개발 작업 두 화면이 이 컴포넌트를 쓴다(`SpecWorkspace.tsx:144`, `DevelopmentBoard.tsx:239`).
- `IdeaInbox`는 `key={workflow.directory}`로 렌더된다(`WorkspaceShell.tsx:360`). 워크플로우 전환 시
  다시 마운트되므로 조회 상태 초기화를 따로 만들 필요가 없다.
- `IdeaInbox.test.tsx:25`의 `getAllByText(...).toHaveLength(2)`는 목록과 미리보기가 같은 요약을
  쓴다는 사실에 기댄 단정이다. 이 기획서를 구현하면 반드시 깨지고, 깨지는 것이 맞다.
- `WorkspaceShell.test.tsx`에는 렌더 지점이 여섯 곳 있고 모두 `onReadSpec`·`onReadTask` 스텁을
  넘긴다. 필수 prop을 더하면 여섯 곳을 함께 고쳐야 한다.
- 이 저장소에 eslint·biome 설정이 없다. `npm run check`는 `tsc -b` + `vitest run` + `vite build`다.
  React hook 의존성 규칙을 자동으로 잡아 주는 장치가 없다.
- CSS 기준값: `.idea-inbox-layout`은 2단 그리드(`App.css:235`), `.idea-list-panel, .idea-preview`는
  `min-height: 360px`(`:236`), `.idea-list`는 `max-height: 430px; overflow: auto`(`:242`),
  `.idea-preview-body`는 `flex: 1; padding: 28px 5px`(`:259`)로 상한도 스크롤도 없다.

## 남은 위험

- **본문이 자동으로 갱신되지 않는다.** 조회를 파일명으로만 걸므로, 보고 있는 아이디어 파일을
  에이전트나 사용자가 밖에서 고쳐도 다시 고르기 전까지 화면은 옛 본문이다. 목록 요약과 문서 정보는
  2.5초 폴링으로 갱신되므로 이론상 어긋남이 생긴다. 갱신 조건에 `updatedAt`을 넣으면 해소되지만,
  파일이 건드려질 때마다 읽던 위치가 초기화된다. 아이디어는 만든 뒤 거의 바뀌지 않는 문서라 지금
  방식을 택했다. 기획서 요구가 아니므로 두 작업 범위 밖으로 뒀다.
- **긴 본문 확인이 수동이다.** 기획서 완료 조건 12(2단 구조 유지·끝까지 읽기)는 실제 렌더링 높이에
  달린 것이라 jsdom 테스트로 단정할 수 없다. TASK-027의 검증 절차에 화면 확인으로 적었다. 이
  저장소의 아이디어 문서 중 긴 것을 그대로 쓰면 된다.
- **`WorkspaceShell.tsx`·`types.ts`·`useProjectWorkspace.ts`·`App.tsx`가 지금 더러운 상태다.**
  `git status` 기준으로 SPEC-003·005 계열 연동 작업의 커밋되지 않은 변경이 넓게 올라와 있다.
  TASK-026·027 모두 그 파일들을 만지므로, 착수하는 개발자는 작업 트리 상태를 먼저 확인하는 편이 좋다.
- **TASK-019와 파일이 겹친다.** SPEC-006의 TASK-019가 `WorkspaceShell.tsx`와 `App.css`를 크게 고친다
  (연동을 사이드바 독립 메뉴로 이동). TASK-027과 같은 시각에 돌리면 충돌한다. TASK-020·021도
  `App.css`를 만진다. 순서는 어느 쪽이 먼저여도 되지만 병행은 안 된다.
- **`.idea-preview-body p` 규칙이 쓰이지 않게 된다.** 미리보기 본문이 `.markdown-body` 규칙을 타므로
  기존 문단 서식(서체·`pre-wrap`)은 대상이 사라진다. TASK-027에 "이 작업 때문에 쓰이지 않게 된
  규칙만 정리"로 적었다. 주변 규칙까지 손대지 않도록 리뷰에서 확인할 부분이다.

## 핸드오프 노트 (역할 밖 발견)

이 세션의 역할로는 손대지 않았다.

- `tasks/TASK-022.md` 본문에 개발 작업 프론트매터 예시가 코드 블록이 아닌 형태로 들어 있어,
  프론트매터 키를 줄 단위로 훑는 도구(`grep -H "^id:"` 등)에 `id: TASK-001`,
  `source_decision_id: DECISION-001`이 실제 값처럼 잡힌다. 문서 파싱은 첫 frontmatter 블록만 보므로
  앱 동작에는 영향이 없지만, 규칙 자산이나 조건 스크립트가 grep으로 판정하면 오탐 소지가 있다.
