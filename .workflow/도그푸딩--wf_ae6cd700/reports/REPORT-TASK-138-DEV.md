# TASK-138 개발 보고서

## 결정권자 요약

릴리스 컷의 병합 조건을 릴리스 가이드에 규범으로 적고, 모든 세션이 읽는 진입 문서에서 그 자리를 가리켰다.
병합은 원격 검사 네 갈래가 모두 끝나고 통과한 것을 확인한 뒤에만 한다는 문장이 정본 자리에 생겼다.
로컬 검사는 사전 신호로 위상이 갈렸고, 로컬에서 원리상 잡히지 않는 실패 세 가지를 이유와 함께 남겼다.
확인 대상은 실제로 병합할 커밋이며 새 커밋을 올리면 다시 확인한다는 조항도 함께 적었다.
재실행은 검사 대상 코드와 무관한 실패에만 허용하고 그 사유를 병합 전에 남기도록 했다.
컷 세션이 확인한 검사 실행과 병합 시각을 그날 개발 로그에 남기라는 요구도 규범에 포함했다.
바뀐 파일은 릴리스 가이드와 진입 문서 두 개뿐이고, 실행되는 코드와 워크플로 설정은 그대로다.
진입 문서의 앱 관리 블록은 한 글자도 바뀌지 않았음을 사본 대조로 확인했다.
설치기의 블록 밖 내용 보존 테스트가 통과했고, 검사 워크플로 이름과 규범의 이름이 일치함을 대조했다.
사용자는 TASK-138 확인 동선의 문서 읽기 절차로 규범 일곱 항목이 제자리에 있는지 확인하면 된다.

## 구현 내용

### 릴리스 가이드에 적은 규범

`docs/releasing.md`의 브랜치 흐름 절에 `### 병합 조건` 하위 절을 추가했다. 기존 네 단계 목록은 문장을
그대로 두고, PR을 여는 2번 단계와 태그를 만드는 기존 4번 단계 사이에 병합 조건을 확인하라는 단계를
새로 넣었다. 그 결과 목록은 다섯 단계가 되었고 기존 4번은 5번으로 번호만 밀렸다.

규범 본문은 번호 매긴 일곱 항목이다.

1. 검사 네 갈래가 모두 끝나고 통과한 것을 확인한 뒤에 병합한다. 네 갈래의 이름을 그대로 적었고,
   "돌고 있다"는 확인이 아니라는 것과 실패의 성격 판단이 병합 전이라는 것을 함께 적었다.
2. 로컬 게이트 네 명령은 사전 신호이고 병합 근거가 아니다. 게이트를 없애거나 줄이지 않는다는 문장을
   같은 항목에 두었다.
3. 로컬에서 원리상 잡히지 않는 세 계열을 각각 한 줄로 적고, 왜 로컬 반복 실행으로 재현되지 않는지를
   항목마다 덧붙였다.
4. 통과 확인은 병합할 커밋의 실행 결과여야 하며 새 커밋을 올리면 다시 확인한다. 동시성 설정 때문에
   이전 실행이 취소되기도 한다는 근거를 함께 적었다.
5. 재실행 허용 범위를 세 가지 경우로 한정하고, 사유를 병합 전에 한 줄 남기도록 했다. 범위 밖의
   재실행으로 얻은 통과는 병합 근거가 아니라는 문장을 같은 항목에 두었다.
6. 이 절이 정본이고 진입 문서의 절은 포인터라는 것, 두 문서가 어긋나면 이 절을 따른다는 것을 적었다.
7. 컷 세션이 그날 개발 로그에 확인한 검사 실행과 병합 시각을 남기도록 적었다.

규범 앞에는 왜 기다려야 하는지의 근거 두 가지를 두었다. 태그 워크플로에 테스트와 서식, 정적 검사 명령이
없어서 PR 검사가 산출물 앞의 마지막 검사라는 것과, 릴리스 두 번이 검사 실패 상태에서 병합됐고 그중
v0.1.8은 그 커밋에 태그가 붙어 게시됐다는 것이다.

`## GitHub 설정`과 `## 배포 방식` 절은 손대지 않았다.

### 진입 문서에 둔 포인터

`AGENTS.md`의 관리 블록 끝 주석 뒤에 `## 릴리스 컷` 절 네 줄을 추가했다. 내용은 릴리스 컷 세션이
릴리스 가이드를 먼저 읽으라는 지시와, 병합 조건의 정본이 그 문서의 병합 조건 절이라는 안내까지다.
규범 본문은 옮겨 적지 않았다. 관리 블록 안쪽은 시작 주석과 끝 주석을 포함해 편집하지 않았고,
`CLAUDE.md`는 열지도 바꾸지도 않았다.

## 검증 결과

작업 시작 시점에 `AGENTS.md`를 `/tmp/wf138-agents-baseline.md`로 복사해 두고, `git status --porcelain`의
출력을 `/tmp/wf138-status-before.txt`에 저장한 뒤 편집했다.

1. **완료 조건 1번부터 7번까지의 자리 확인.** `docs/releasing.md`를 처음부터 읽어 대응을 확인했다.
   조건 1번은 26번째 줄부터의 1번 항목, 조건 2번은 31번째 줄부터의 2번 항목, 조건 3번은 35번째 줄부터의
   3번 항목과 그 아래 세 줄, 조건 4번은 45번째 줄부터의 4번 항목, 조건 5번은 48번째 줄부터의 5번 항목,
   조건 6번은 52번째 줄부터의 6번 항목과 18번째 줄의 정본 문장, 조건 7번은 54번째 줄부터의 7번 항목이다.
   기존 브랜치 흐름 네 단계의 문장과 `## GitHub 설정`, `## 배포 방식` 절이 그대로 남아 있음을 함께
   확인했다.
2. **관리 블록 무변경 대조.** `diff /tmp/wf138-agents-baseline.md AGENTS.md`의 출력이 `15a16,20`
   하나뿐이다. 사본의 15번째 줄이 관리 블록 끝 주석이므로 추가된 다섯 줄이 전부 끝 주석 뒤에 있고,
   블록 범위에는 변경 줄이 없다.
3. **관리 블록 개수.** `grep -c`로 시작 주석 1개, 끝 주석 1개를 확인했다.
4. **변경 파일 범위.** 편집 뒤 `git status --porcelain`을 다시 받아 시작 시점 출력과 대조했더니 차이가
   `docs/releasing.md` 한 줄 추가뿐이다. `AGENTS.md`는 시작 시점에 이미 수정 상태였으므로 두 출력에
   같은 형태로 나타난다. `CLAUDE.md`는 어느 출력에도 없다. 시작 시점에 수정 상태였던 제품 코드와 규칙
   자산 파일들은 이 작업에서 건드리지 않았다.
5. **설치기 보존 테스트.**
   `cargo test --manifest-path src-tauri/Cargo.toml preserves_existing_content_and_is_idempotent`가
   1 passed, 0 failed로 통과했다.
6. **검사 워크플로 이름 대조.** `.github/workflows/ci.yml`의 `frontend` 작업 이름이 `Frontend`이고
   `rust` 작업 이름이 `Rust (${{ matrix.os }})`이며 matrix가 `ubuntu-22.04`, `windows-latest`,
   `macos-latest`이므로, 규범에 적은 네 이름이 실제 표시 이름과 일치한다.
   `.github/workflows/release.yml`의 실행 단계는 `npm ci`, `npm run release:verify`,
   `npm run release:config`, `tauri-action` 넷이고 테스트와 서식, 정적 검사 명령이 없다. 근거 문장이
   사실과 맞는다.
7. **두 문서 정합성.** 릴리스 가이드는 6번 항목에서 자신이 정본이고 진입 문서가 포인터라고 적고,
   진입 문서는 정본이 릴리스 가이드의 병합 조건 절이라고 적는다. 서로 어긋나는 문장이 없고 진입 문서
   쪽에 규범 본문이 복제돼 있지 않다.
8. **추가 검사 없음.** 산출물이 문서뿐이므로 5번 외에 코드 검사를 새로 추가하지 않았고 기존 검사를
   지우지 않았다.

저장소 설정은 조회도 변경도 하지 않았다. 브랜치 보호와 필수 상태 검사는 이 작업의 범위 밖이며
SPEC-044의 확인 필요 2번이 사용자 결정으로 남긴 사항이다.

## 남은 위험과 후속

- 이 규범은 문서이므로 다음 컷 세션이 읽지 않으면 지켜지지 않는다. 저장소 설정으로 병합 자체를 막는
  길은 SPEC-044의 확인 필요 2번이 다음 컷 한 번을 지켜본 뒤 다시 보기로 남긴 사항이다.
- SPEC-044의 완료 조건 8번은 다음 릴리스 컷 세션이 개발 로그에 남기는 기록이라 이 작업에서 판정할 수
  없다. 규범 본문이 그 기록을 요구하도록 적는 데까지 수행했다.
- 병합 조건이 두 문서에 나뉘어 있어 한쪽만 고치면 어긋날 수 있다. 정본 표시가 그 경우의 해석 기준이다.
- 비결정적 테스트가 실제로 나오면 재실행 기준을 다시 볼 자리가 생긴다. SPEC-043이 그 주제를 다루며
  아직 사용자 결정 대기 상태다.

## 사용자 확인 요청

TASK-138의 확인 동선을 따라 두 문서를 읽고, 병합 조건 일곱 항목이 릴리스 가이드에 있고 진입 문서에는
포인터만 있는지 확인해 주기 바란다. 이 작업은 화면 동작이 없는 문서 변경이라 확인은 문서 읽기와
자동 검사 결과로 이루어진다.
