# SPEC-081 아키텍트 핸드오프

## 결정권자 요약

런타임이 예약한 승인 DECISION-99108E8E를 처리해 작업 그룹 GROUP-081과 개발 작업 두 건을 만들었다.
그룹은 사용자 QA 모드이고 지금 active다. 기획서가 아키텍트에게 남긴 두 판단을 코드를 읽어 정했다.
하나는 "앱 쪽 운영 사유로 종료 처리됨"을 앱의 어떤 값으로 알아보는지이고, 다른 하나는 목록이 실행
활동 기록을 어느 단위로 함께 읽는지다. 사용자가 할 일은 두 작업이 verified가 된 뒤 그룹 QA 한 번뿐이다.

## 세션 정보

- 역할: 아키텍트 (architect)
- 대상: DECISION-99108E8E (SPEC-081 승인 결정)
- 산출물: GROUP-081 (revision 1, qa_mode user, status active), TASK-S081-01, TASK-S081-02
- 예약: 런타임 예약 대상 DECISION-99108E8E, lease lease-44222-20260819142906, 결과 prefix
  RES-20260819T142906Z-44222-20260819142906
- 세션: 2026-08-19T14:33Z ~ 14:46Z

## 진행 절차

1. 예약받은 lease로 `wf-claim renew`를 호출해 소유를 확인했다. 종료 코드 0이었고 lease 파일의
   `lease_id`도 예약값과 같았다. `acquire`는 부르지 않았다.
2. `.workflow/.runtime/migration.lock`이 없고 `.workflow/rules/custom.md`도 없음을 확인했다. 적용할
   프로젝트 커스텀 규칙이 없다.
3. `groups/` 전체에서 SPEC-081이나 DECISION-99108E8E를 참조하는 문서가 없음을 확인했다. 이 승인에서
   파생된 그룹이 아직 없다는 뜻이므로 자격이 유효했다.
4. 계보 규칙에 따라 GROUP-081과 TASK-S081-01, TASK-S081-02로 이름을 정했다. 세 경로 모두 비어 있는
   것을 쓰기 전에 확인했다. `tasks/TASK-081.md`가 이미 있으나 이는 번호만 쓰던 시절의 다른 문서이고
   식별자가 겹치지 않는다. 결과 prefix는 이 보고서에만 적고 문서 식별자에 넣지 않았다.
5. 청구 직후 GROUP-081을 `status: preparing`과 승인 참조만 담아 먼저 만들었다. 두 작업을 다 쓴 뒤
   기능 설명과 QA 흐름을 채우고 `active`로 올렸다.

## 결과 없이 끝난 실행 기록 확인

`.workflow/.runtime/silent-runs/`를 읽었고, 이 대상을 가리키는 기록이 하나 있었다.

- 파일: `be72e69b0e964dcea40b18e3d83342eb.json`
- 내용: 대상 DECISION-99108E8E, 역할 architect, 시작과 종료가 모두 2026-08-19T14:29:07Z, 사유
  `supervisor_identity_unverified`

기록이 말하는 대로 그 실행은 결과를 남기지 않았다. 잔여물을 찾아 확인한 결과 남긴 것이 하나도 없었다.
`groups/GROUP-081.md`가 없었고, `tasks/`에 `TASK-S081-*`가 하나도 없었으며, `reports/`에 이 대상의
아키텍트 보고서가 없었다. 시작과 종료 시각이 같아 실제로 작업이 시작되지 않은 실행이다. 그래서 버릴
것도 다시 쓸 것도 없었고, 이 세션은 빈 상태에서 시작했다. 시험을 지운 일도 없다.

같은 사유 `supervisor_identity_unverified`가 이 프로젝트의 결과 없이 끝난 실행 기록 21건 전부에
붙어 있다. 이 사실은 아래 판단 하나의 근거로도 썼다.

## 아키텍트가 정한 것 하나: 운영 사유 종료의 판별 기준

기획서 R4는 "실행이 세션 자신의 결과가 아니라 앱 쪽 운영 사유로 종료 처리된 경우"를 정의만 하고,
앱의 어떤 값이 거기 해당하는지는 정하지 않았다. 기획자 보고서도 이 판단을 구현 단계로 넘겼다.
코드를 읽어 다음 셋으로 정했고 TASK-S081-01의 완료 조건 C6에 적었다.

- 실행 상태 `recovery_required`(복구 필요). `docs/agent-runtime.md`가 이 상태를 앱이 실행을 취소하다가
  프로세스 종료나 선점 반납에 실패했을 때 남는 상태로 정의한다. 세션이 결과를 보고한 것이 아니다.
- 실행 상태 `unrecognized`(상태 확인 필요). `src-tauri/src/domain/agent_runtime.rs`의 `RunState`가
  `#[serde(other)]`로 붙이는 값이며, 계약 밖 상태값이 왔을 때 앱이 읽지 못했다는 표시다.
- 실행 사유 `supervisor_identity_unverified`와 `handle_mismatch`. 상태값과 무관하게 이 사유가 붙어
  있으면 앱이 세션 정리를 안전하게 미룬 것이다. 화면이 이미 이 두 값을 같은 뜻으로 묶어
  "세션 정리를 안전하게 미뤘습니다"로 옮기고 있다(`AgentRunDashboard.tsx` 825행). 기획서가 근거로 든
  2026-08-18 사고의 실제 값이 이것이며, 위에서 적은 21건이 모두 이 사유다.

세션 자신의 결과로 끝난 상태는 `succeeded`, `failed`, `cancelled` 셋이다. 기획서가 종료에 함께 적은
"시간 초과"는 실행 상태가 아니라 실행 기록의 신호 종류이고, 시간 초과로 끝난 실행은 상태값으로는
`failed`로 온다. 새 상태값을 만들지 않는다는 것을 작업 문서에 적어, 개발자가 없는 값을 지어내지 않게 했다.

## 아키텍트가 정한 것 둘: 활동 기록을 읽는 단위

기획자 보고서가 "목록을 그릴 때 활동 기록을 어느 단위로 함께 가져올지"를 아키텍트에게 넘겼다.
읽어 본 사실은 다음과 같다.

- 마지막 활동 시각은 실행 이벤트에서만 나온다. 이벤트를 주는 경로는 `read_agent_run_log` 하나뿐이고
  cursor 단위로 한 묶음씩 준다. 마지막 값을 얻으려면 끝까지 이어 읽어야 한다.
- 실행 목록 조회는 에이전트 화면이 열려 있는 동안 2.5초마다 돈다. 여기에 활동 조회를 붙이면 2.5초마다
  전체 이벤트를 다시 읽는다.
- 앱 밖 세션 목록에 남는 선점은 SPEC-069의 제외 기준 때문에 대체로 활성 실행이 없는 것들이다. 즉
  활동 시각이 필요한 실행은 이미 끝난 실행이고, 끝난 실행의 이벤트는 더 늘지 않는다.

그래서 조회 단위를 이렇게 정했다. 갱신이 10분을 넘은 선점 중 대상을 맡은 실행 행이 있고 그 실행이
진행 중 넷에 들지 않는 것만 읽는다. 실행 하나당 한 번만 읽고 결과를 실행 식별자별로 담아 두며, 그 실행의
상태가 달라진 경우에만 다시 읽는다. 조회 실패도 결과로 남겨 같은 실행을 반복해서 다시 부르지 않게 했다.

실행별 활동 시각만 한 번에 돌려주는 백엔드 명령을 새로 만드는 길도 검토했다. `audit_run_reports`가
같은 모양의 선례이고 오가는 값도 훨씬 작다. 그러나 이벤트 시각을 계산하는 규칙이
`runActivity.ts`의 `eventOccurredAt` 한 자리에만 있어서, 백엔드에서 계산하면 같은 규칙이 두 언어에
생긴다. 읽는 실행이 카드 후보로 좁혀져 있고 한 번만 읽으면 되므로 규칙이 한 자리에 남는 쪽을 골랐다.
이 판단과 그 대가를 TASK-S081-02의 범위 사전 검사에 적어 두었다.

## 기획서에서 해석이 갈릴 수 있어 정한 것

기획서의 "생존" 정의가 "실행이 아직 끝나지 않은 상태로 남아 있거나, 마지막 활동이 10분 이내다"이고,
"종료" 정의는 조건 없이 "실행이 세션 자신의 결과로 끝났다"다. 두 정의를 그대로 겹치면 세션 자신의
결과로 끝난 실행이면서 마지막 활동이 10분 이내인 경우가 양쪽에 걸린다.

R4가 "이때는 최근 활동이 있는지로 가른다"라고 활동 판정의 적용 범위를 운영 사유 종료로 한정하고 있고,
완료 판정 A4와 A5도 활동 시각으로 갈리는 경우를 운영 사유 종료에서만 든다. 그래서 판정 순서를 이렇게
정했다. 미종료 상태면 생존, 세션 자신의 결과로 종료했으면 종료, 운영 사유로 종료 처리됐으면 최근 활동으로
생존과 확인 불가를 가르고, 실행 기록이 없으면 확인 불가다. 이 순서를 TASK-S081-01의 C4부터 C9에 적었다.

## 작업 분해와 병행 판단

두 작업의 선언 파일이 하나도 겹치지 않는다.

- TASK-S081-01은 새로 만드는 판정 파일과 그 시험 둘만 선언한다.
- TASK-S081-02는 화면 계약, 훅, 화면, 스타일과 그 시험 넷을 선언한다.

겹침이 없는데도 `depends_on`을 둔 이유는 파일 충돌이 아니라 값의 순서다. 두 번째 작업이 첫 번째 작업이
만드는 판정을 가져다 쓰므로, 첫 번째가 verified가 되기 전에 두 번째를 시작하면 없는 파일을 참조한다.

기계 상태를 조건으로 삼는 측정이 없어 `solo_run`은 두 작업 다 선언하지 않았다.

분해에서 한 번 되짚은 지점이 있다. 조회 경로와 표시 경로를 세 번째 작업으로 더 쪼갤 수도 있었으나,
둘 다 화면 계약 파일을 함께 고쳐야 해서 선언이 겹치고 결국 순서가 생긴다. 그리고 조회만 끝난 상태는
사용자가 만날 변화가 하나도 없어 작업 요약이 사용자 층위에서 할 말을 갖지 못한다. 그래서 둘로 두었다.

## 확인한 코드 사실

작업 문서에 적은 판단의 근거로 다음을 직접 열어 읽었다.

- `src/features/projects/components/agents/AgentRunDashboard.tsx`: 앱 밖 세션 절 전체와 지금의
  판정 함수, 역할을 채우는 지도, 상태 이름표와 시각 표기 함수.
- `src/features/projects/domain/runActivity.ts`: 마지막 활동 시각을 만드는 두 함수와 실행 상세 화면의
  5분 기준 상수.
- `src/features/projects/application/useProjectWorkspace.ts`: 실행 목록 조회 주기, 실행 기록 조회 함수와
  그것이 쓰는 상태 넷, 보고서 판정을 한 번에 받아 두는 선례.
- `src/features/projects/domain/types.ts`: 실행 행과 선점 요약의 형태, 화면 상태와 동작 묶음의 자리.
- `src-tauri/src/commands/agent_runtime.rs`와 `src-tauri/src/domain/agent_runtime.rs`: 실행 기록 조회
  명령의 계약과 실행 상태값 아홉 개, 실행 행에 선점 식별자가 없다는 사실.
- `src-tauri/src/application/agent_runtime_status_service.rs`: 이벤트를 끝까지 이어 읽는 기존 반복.
- `src/features/projects/components/agents/AgentRuntimeView.test.tsx`: 앱 밖 세션 절의 기존 시험 아홉 건.
  그중 한 건이 "신호 지연" 문구를 확인하고 있어, 그 줄을 함께 고치지 않으면 완료 판정 A7이 통과한 것처럼
  읽힌다는 사실을 작업 문서의 검증 절차에 적었다.
- `docs/agent-runtime.md`: 복구 필요 상태의 정의.

## 사용자 QA

그룹을 `qa_mode: user`로 정했다. 바뀌는 것이 목록의 줄 나눔과 문구와 근거 줄이라 비개발자가 화면에서
바로 확인할 수 있다. QA 흐름은 한 절(QA-01)로 썼고, 사용자가 에이전트 화면에서 앱 밖 세션 절을 한 번
훑는 순서를 따른다. 작업 단위를 반영하지 않았고 단말 명령이나 저장소 조작을 넣지 않았다.

## 남는 위험

- 완료 판정 A1이 상정하는 상태, 곧 실행이 진행 중인데 그 선점이 앱 밖 세션 목록에 남아 있는 상태는
  화면의 제외 기준 때문에 실제 화면에서는 드물다. 앱이 돌린 실행이 잡은 대상은 진행 중 목록이 가져가기
  때문이다. 선점 목록과 실행 목록이 서로 다른 시점의 값일 때 잠깐 생길 수 있고, 판정 자체는 그 경우를
  다뤄야 하므로 A1은 판정 단위의 시험으로 확인하도록 작업 문서에 적었다. 화면 시험에서도 같은 입력을
  직접 만들어 확인한다.
- 새로 정상 줄로 내려간 세션은 갱신 시각이 가장 오래됐으므로 정렬에서 아래쪽에 서고, 정상 세션이 여덟을
  넘으면 접힌 쪽으로 들어갈 수 있다. 기존 정렬과 접힘 규칙이 낸 결과이고 기획서 R10이 그 둘을 바꾸지
  말라고 정했으므로 이번에 고치지 않았다. 사용자가 이 동작을 문제로 본다면 새 아이디어가 필요하다.
- 운영 사유 판별에 쓴 두 사유 문자열은 실행 환경이 싣는 값이고 이 저장소가 정본을 갖고 있지 않다. 실행
  환경이 값을 바꾸면 판정이 조용히 빗나간다. 화면이 이미 같은 문자열을 문장으로 옮기고 있어 두 자리가
  함께 어긋나므로 발견은 되지만, 값의 정본이 밖에 있다는 사실은 남는다.

## 역할 밖 발견 사항

- `src/features/projects/components/agents/AgentRunDashboard.tsx`의 `runRoleByTarget`은 역할이 없는
  실행을 근거에서 빼기 때문에 "최신 실행"이 아니라 "역할이 있는 실행 중 최신"을 돌려준다. 역할 표시에는
  맞는 동작이지만 이름만 보면 오해할 수 있다. 이번 작업은 새 지도를 따로 두는 쪽으로 피했고 이 함수는
  고치지 않았다. 이름이나 주석 정리는 이 기획서의 범위 밖이라 손대지 않았다.
- 실행 기록 조회가 실행 환경 프로세스를 부르는 비용이 큰 데 비해, 계약에 마지막 이벤트만 묻는 길이 없다.
  이벤트를 끝까지 이어 읽는 것 말고는 방법이 없어 앱과 백엔드 양쪽에 같은 반복이 생긴다. 실행 환경 쪽
  계약 문제라 이 저장소에서 정할 수 없고, 이번 작업은 읽는 실행을 좁히고 한 번만 읽는 것으로 대응했다.

## 다음 역할에 넘기는 사항
