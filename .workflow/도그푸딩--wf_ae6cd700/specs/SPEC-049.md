# 자격 판정과 작업 문서 구조를 개선해 세션의 규격 준수 비용을 낮춘다

## 결정권자 요약

역할 세션 하나가 실제 구현보다 절차를 지키는 데 쓰는 토큰이 상당하다. 실측에 따르면 세션 하나가
규격을 지키는 데만 3만에서 4만 토큰을 쓰고, 이 비용은 쌓인 문서 수에 비례해 계속 늘어난다. 원인은
셋이다. 자격 확인 도구가 일감의 유무만 답해 실제 대상은 세션이 전체 문서를 대조해 직접 찾아야 하고,
작업 문서와 기획서가 같은 내용을 겹쳐 담아 세션이 둘 다 읽어야 하며, 보고서 분량과 구성에 제약이
없어 뒤이은 세션이 매번 전체를 읽는다.
이 기획은 세 가지를 함께 고친다. 자격 확인 도구가 대상 문서와 제외 사유까지 답하게 하고, 작업 문서
하나만으로 착수할 수 있게 기획서와의 역할을 나누고, 보고서에 필수 항목과 분량 상한을 둔다. 안전
계약 본문 자체를 줄이는 일은 이번 범위에 넣지 않는다.
인용한 수치는 세션 하나의 추정이라 재검증이 필요하다. 세 제안을 하나로 묶어 진행할지, 이미 진행
중인 기획서와 작업에도 새 규칙을 적용할지는 사용자가 정할 부분이다.

## 기획 내용

### 배경

이 저장소는 역할 세션마다 공통 규칙, 배정된 역할 계약, 관련 문서를 읽고 나서야 실제 작업을
시작한다. 문서와 결정이 쌓일수록 세션이 절차를 지키는 데 쓰는 토큰도 함께 늘어난다는 문제 제기가
있었다. 2026-08-06에 병렬로 실행한 여러 개발 세션을 관찰한 결과, 세션 하나가 규격을 지키는 데만
3만에서 4만 토큰을 쓴다는 추정이 나왔다(문서 바이트 수를 한국어 기준 약 2바이트당 1토큰으로 환산한
값이며, 개발 로그 240킬로바이트가 약 11만 7천 토큰으로 측정된 값을 근거로 삼는다).

### 확인 사실

이 기획서를 쓰며 저장소에서 직접 확인한 값이다. 추정으로 적은 항목은 없다.

1. 2026-08-06 기준 이 워크플로우에는 아이디어 45건, 기획서 48건, 결정 문서 184건(그중 사용자 확인
   결정 134건), 작업 문서 133건이 있다. 작업 문서 133건은 원 아이디어가 든 대조 건수와 정확히
   일치한다. 결정 문서는 원 아이디어가 든 175건에서 184건으로 늘어 있어, 문서 수가 계속 늘어난다는
   지적이 실제로 진행 중임을 보여준다.
2. 자격 확인 도구는 기획자·아키텍트·개발자 세 분기 모두 판정 사유 코드 한 줄만 표준 출력에 낸다.
   일감이 있다는 뜻의 코드와 없다는 뜻의 코드만 있을 뿐, 어느 문서가 대상인지나 다른 후보가 왜
   제외됐는지는 이 출력에 없다.
3. 앱이 내부에서 쓰는 대기 물량 판정 함수도 세 역할 각각 참과 거짓 하나만 반환한다. 대상 문서의
   식별자나 후보 목록은 반환값에 없다.
4. 개발자 역할 계약의 허용 범위는 배정된 작업, 연결된 기획서와 결정, 관련 코드와 테스트를 읽는
   것으로 적혀 있다. 작업 문서만으로 착수하고 기획서는 모호할 때만 여는 경로를 계약이 아직 구분해
   인정하지 않는다.
5. 아키텍트 역할 계약의 완료 조건은 작업 문서에 완료 조건과 검증 절차를 갖추라고 요구하지만,
   기획서의 요구사항 명세를 작업 문서 안에 전부 옮겨 담으라는 문장은 없다. 지금은 두 문서가 같은
   내용을 각자의 표현으로 다시 적는 경우가 흔하다.
6. 보고서의 절 이름과 분량에는 지금 제약이 없다. 유일한 선례는 결정권자 요약 절에 이미 있는 열 줄
   상한이다.
7. 실측 기준 문서 크기 분포는 기획서 평균 24229바이트(8053~43016바이트, 48건), 작업 문서 평균
   11914바이트(4097~23701바이트, 133건), 보고서 평균 10487바이트(2418~26321바이트, 213건)다. 작업
   문서와 보고서는 원 아이디어가 든 구간(각각 9~13킬로바이트, 약 10킬로바이트)과 비슷하지만, 기획서는
   원 아이디어가 든 구간(10~16킬로바이트)보다 실제 평균이 상당히 높다. 세 항목 중 기획서 추정치의
   오차가 가장 크므로, 재검증이 먼저 필요한 자리도 여기다.

### 제안 1. 자격 확인 도구가 대상과 제외 사유를 함께 답한다

지금은 자격 확인 도구가 일감의 유무만 답해, 실제로 어느 문서를 집어야 하는지는 세션이 아이디어·
결정·작업 문서 전체를 스스로 대조해서 찾는다. 문서 수가 늘수록 이 대조 비용도 함께 늘어난다.

자격 확인 도구가 대상 문서 식별자, 후보 목록, 후보마다 제외된 사유까지 답하게 한다. 세션은 전체
대조를 반복하는 대신 도구의 답을 검증만 하면 된다. 지금 이 저장소가 이미 지키는 원칙 — 조건
스크립트와 앱 내부 판정이 같은 답을 내야 한다 — 을 대상 선택에도 그대로 넓히는 것이므로, 조건
스크립트와 앱 코드 양쪽을 함께 고쳐야 한다.

### 제안 2. 작업 문서 하나만으로 착수할 수 있게 한다

지금은 기획서와 작업 문서가 요구사항과 완료 조건을 겹쳐 담고, 개발자 역할 계약은 세션이 배정된
작업과 연결된 기획서를 함께 읽게 한다. 두 문서가 사실상 같은 내용을 담고 있는데도 계약이 이중 독해를
기본값으로 만든다.

개발자 역할 계약에 개발자는 작업 문서만으로 착수하고, 기획서는 작업 문서의 내용이 모호할 때만 연다는
문장을 넣는다. 그 전제로 아키텍트 역할 계약에는 작업 문서가 완결된 지시서가 되도록, 그 작업에 필요한
완료 조건과 검증 절차를 작업 문서 안에 전부 갖추라고 요구한다.

### 제안 3. 보고서에 필수 항목과 분량 상한을 둔다

지금은 보고서의 절 이름과 분량에 제약이 없어, 세션마다 다른 형식으로 쓰고 뒤이은 세션은 필요한
사실을 찾기 위해 보고서 전체를 읽는다.

보고서에 반드시 담을 절 목록과 분량 상한을 정한다. 결정권자 요약 절에 이미 있는 열 줄 상한이라는
전례를 그대로 따른다. 핸드오프로 보고서를 읽는 후속 세션의 비용이 함께 줄어든다.

### 세 제안을 하나로 묶는 이유

세 제안은 서로 다른 문서와 도구를 고치지만 겨냥하는 문제는 하나다 — 세션이 실제 작업과 무관하게
반복해서 읽고 대조하는 고정 비용이다. 하나만 고치면 나머지 둘이 그대로 비용을 남긴다. 예를 들어
자격 확인 도구가 대상을 알려줘도 개발자가 여전히 기획서와 작업 문서를 모두 읽어야 한다면 절감 폭이
크게 줄어든다.

### 경계

공통 규칙과 역할 계약 본문 자체를 줄이는 일은 이번 범위에 넣지 않는다. 이 두 문서는 앱의 안전 계약을
담고 있어 줄이는 데 별도의 신중한 판단이 필요하고, 세션이 이미 읽은 내용을 다시 안 읽는 요령으로
계약 자체를 우회할 위험이 있다.

이 기획서가 인용한 절감 수치는 세션 하나의 관찰에서 나온 추정이다. 확인 사실 7번이 보여주듯 항목별
오차가 있으므로, 계획 단계에서 측정 방법과 함께 다시 검증해야 한다.

### 포함 범위

- 자격 확인 도구(조건 스크립트와 앱 내부 판정)가 대상 문서 식별자, 후보 목록, 후보별 제외 사유를
  답하도록 넓힌다.
- 조건 스크립트와 앱 내부 판정이 넓어진 뒤에도 같은 결론을 내는지 검증하는 절차를 함께 마련한다.
- 개발자 역할 계약에 작업 문서 우선 착수와 기획서를 여는 조건을 명시한다.
- 아키텍트 역할 계약에 작업 문서가 갖춰야 할 완료 조건·검증 절차의 최소 범위를 명시한다.
- 보고서에 적용할 필수 절 목록과 분량 상한을 정하고 개발자 역할 계약에 반영한다.
- 위 변경에 맞춰 공통 규칙, 역할 계약, 관련 관리 자산의 버전을 올린다.
- 절감 효과를 다시 잴 수 있는 측정 방법을 정하고, 이번 변경 전후 값을 비교할 수 있게 한다.

### 제외 범위

- 공통 규칙과 세 역할 계약 본문 자체의 분량 축소.
- 아이디어 문서의 형식이나 분량 변경.
- 기획서 자체의 분량 상한 도입. 확인 사실 7번이 보여주듯 기획서는 세 문서 중 실측과 추정의 차이가
  가장 커서, 이번 기획만으로 상한을 정하면 근거가 약하다.
- 자격 확인 도구나 앱 판정의 성능 최적화. 이미 다른 기획서가 다룬 영역이며 이번 기획은 출력 내용을
  넓히는 것만 다룬다.
- 결정, lease, 선점 절차의 판정 규칙 변경.
- 문서 저장 형식이나 스키마 식별자의 변경.
- 이미 존재하는 기획서·작업 문서를 이번 기획에 맞춰 일괄 재작성하는 일. 소급 적용 범위는 확인 필요
  2번에서 사용자가 정한다.

## 요구사항 명세

### R1. 자격 확인 도구가 대상과 후보별 제외 사유를 답한다

- 조건 스크립트의 기획자·아키텍트·개발자 세 분기가 일감이 있을 때 대상 문서 식별자를 함께 낸다.
- 세 분기 모두 후보 목록과, 후보가 대상에서 제외됐다면 그 사유를 답에 담는다. 사유는 지금 각 분기가
  이미 적용하는 조건(선점 여부, 상태값, 선행·겹침 충족 여부 등)을 사람이 읽을 수 있는 형태로 옮긴
  것이어야 하며, 새로운 판정 기준을 만들지 않는다.
- 지금의 판정 결과(일감이 있다/없다)는 이 변경으로 달라지지 않는다. 넓어지는 것은 답의 내용이지
  판정 자체가 아니다.
- 앱 내부의 대기 물량 판정도 같은 정보를 반환하도록 넓힌다. 조건 스크립트와 앱 내부 판정은 같은
  대상, 같은 후보 목록, 같은 제외 사유를 답해야 한다.
- 이 변경으로 조건 스크립트의 기존 성능 특성(문서 수가 늘어도 대상 문서마다 상수 비용으로 판정하는
  성질)을 되돌리지 않는다.

### R2. 개발자는 작업 문서만으로 착수하고, 모호할 때만 기획서를 연다

- 개발자 역할 계약에 개발자는 배정된 작업 문서를 먼저 읽고 그것만으로 착수하며, 작업 문서의 내용이
  모호하거나 판단 근거가 부족할 때만 연결된 기획서와 결정을 연다는 문장을 넣는다.
- 기획서를 열 수 있는 권한 자체는 없애지 않는다. 이번 요구가 정하는 것은 기본 경로이지, 접근을 막는
  것이 아니다.
- 개발자가 기획서를 열어야 했다면, 그것이 작업 문서의 어떤 부분이 부족했기 때문인지 보고서에 남긴다.
  이 기록이 R3의 필수 절 목록에 반영해야 할 근거가 된다.

### R3. 작업 문서는 완결된 지시서다

- 아키텍트 역할 계약에 작업 문서가 그 작업에 필요한 완료 조건과 검증 절차를 모두 담아야 한다고
  명시한다. 기획서의 요구사항 명세를 참조만 하고 작업 문서에는 요약만 남기는 방식을 금지한다.
- 이 요구는 아키텍트가 작업을 분해하는 방식을 바꾸는 것이지, 기존에 이미 승인된 기획서의 요구사항
  명세 자체를 줄이거나 없애는 것이 아니다.
- 작업 문서가 완결됐는지는 R2가 요구하는 절차 — 개발자가 실제로 기획서를 열어야 했는지 여부 — 로
  사후에 확인할 수 있어야 한다.

### R4. 보고서에 필수 절 목록과 분량 상한을 둔다

- 개발 보고서가 반드시 담아야 할 절 목록을 정한다. 최소한 변경한 파일과 모듈, 검증 절차와 결과,
  남은 위험, 후속 작업을 각각 확인할 수 있는 자리를 포함한다. 결정권자 요약 절과 확인 동선 절은 이미
  정해진 자리를 그대로 유지한다.
- 결정권자 요약 절의 열 줄 상한과 같은 방식으로, 보고서 본문에도 분량 상한을 정한다. 상한을 넘는
  세부 내용은 보고서 대신 코드 주석이나 커밋 메시지처럼 이미 있는 다른 자리로 옮긴다.
- 이 요구는 새로운 문서 종류나 스키마를 만들지 않는다. 지금의 보고서 문서 하나에 적용되는 구성
  규칙이다.

### R5. 안전 경계와 기존 계약은 그대로 유지된다

- 앱 소유 상태, 사용자 결정, 선점, 역할 분리, 세션당 한 대상 처리라는 기존 원칙은 이번 변경으로
  느슨해지지 않는다.
- 공통 규칙과 세 역할 계약 본문 자체의 분량은 이번 기획의 대상이 아니다. R1~R4가 요구하는 새 문장만
  각 계약에 추가한다.
- 조건 스크립트는 앱 관리 자산이므로 버전을 올리고, 관리 마커가 없는 파일을 덮어쓰지 않으며 설치본이
  앱보다 새 버전이면 멈추는 기존 안전 절차를 그대로 따른다.
- 이번 변경으로 기존 자동화 검사를 삭제하거나 비활성화하지 않는다.

## 확인 필요

사용자 결정이 필요한 항목이다. 승인 시 아래 제안대로 진행한다.

1. **세 제안을 하나의 기획으로 계속 묶어 진행할지, 별도 기획으로 쪼갤지.**

   제안: 하나로 묶어 진행한다. 근거는 원 아이디어가 이미 셋을 하나로 제시했고, 세 제안이 겨냥하는
   문제(세션의 반복 고정 비용)가 하나로 같기 때문이다. 다만 아키텍트 단계에서 세 제안을 서로 겹치지
   않는 작업으로 나눠 병렬로 진행할 수 있게 분해할 것을 권장한다.

   반대 근거: 세 제안은 건드리는 자산이 서로 다르다(도구·코드, 역할 계약, 보고서 관례). 하나로
   묶으면 셋 중 하나에 대한 이견 때문에 나머지 둘의 승인도 함께 미뤄질 수 있다. 쪼개면 승인과 적용을
   독립적으로 진행할 수 있다.

2. **이번에 바뀌는 규칙을 이미 진행 중인 기획서와 작업 문서에도 적용할지, 이번 기획이 승인된 뒤에
   새로 만드는 문서부터 적용할지.**

   제안: 새로 만드는 문서부터 적용한다. 이미 `user_review`나 그 이후 상태인 기획서, 이미 만들어진
   작업 문서를 이번 규칙에 맞춰 다시 쓰는 일은 별도의 비용이며 이번 기획의 목적(앞으로의 고정 비용
   절감)과 다른 문제다.

   반대 근거: 새 규칙이 새 문서에만 적용되면 한동안 두 형식이 섞여 있어 세션이 어느 문서가 어떤
   규칙을 따르는지 매번 판단해야 하는 과도기 비용이 생긴다.

3. **인용된 절감 수치를 이번 변경의 완료 조건으로 삼을지, 아니면 이번 변경은 구조만 만들고 수치
   재검증은 별도로 진행할지.**

   제안: 이번 기획은 구조(자격 확인 도구의 응답 범위, 역할 계약 문장, 보고서 구성)를 완료 조건으로
   삼고, 실제 절감 폭 측정은 이번 변경이 적용된 뒤 별도로 관찰해 보고한다. 확인 사실 7번이 보여주듯
   지금 인용된 수치 자체가 재검증 대상이라, 이번 기획의 완료 조건으로 못박기에는 근거가 아직 약하다.

   반대 근거: 측정을 나중으로 미루면 이번 변경이 실제로 효과가 있었는지 확인할 시점이 불명확해질 수
   있다.

## 기대효과

- 세션이 대상을 찾기 위해 아이디어·결정·작업 문서 전체를 대조하는 대신 자격 확인 도구의 답을 검증만
  하면 되어, 문서 수가 늘어도 이 부분의 비용이 늘지 않는다.
- 개발자가 작업 문서 하나만으로 착수할 수 있어, 기획서와 작업 문서를 겹쳐 읽는 비용이 줄어든다.
- 보고서의 형식이 일정해져 뒤이은 세션이 필요한 사실을 더 빠르게 찾는다.
- 절감 폭을 실제로 측정할 수 있는 방법이 마련되어, 이후 비슷한 개선을 제안할 때도 같은 방식으로
  근거를 검증할 수 있다.
- 안전 계약과 승인 절차, 역할 분리는 그대로 유지되어 비용 절감이 기존 보호 장치를 약화하지 않는다.

## 완료 조건

1. 일감이 있는 상태에서 조건 스크립트의 세 분기 모두 대상 문서 식별자를 답에 포함한다. 검증: 각
   역할의 자격이 있는 임시 프로젝트에서 조건 스크립트를 실행해 출력에 대상 식별자가 있는지 확인한다.
2. 후보가 여럿이고 그중 일부가 제외되는 상태에서, 답에 후보 목록과 제외된 후보별 사유가 담긴다.
   검증: 여러 후보 중 일부는 선점되고 일부는 상태 조건을 만족하지 않는 픽스처로 확인한다.
3. 일감이 없는 상태에서 지금과 같은 결과(대상 없음)를 낸다. 검증: 기존 조건 스크립트 검사가 수정
   없이 통과하는지 확인한다.
4. 앱 내부 대기 물량 판정이 1~3과 같은 대상, 같은 후보 목록, 같은 제외 사유를 반환한다. 검증: 조건
   스크립트와 앱 내부 판정의 일치를 고정한 기존 검사에 새 시나리오를 더해 통과시킨다.
5. 개발자 역할 계약에 작업 문서를 먼저 읽고 그것만으로 착수하며, 모호할 때만 기획서를 연다는 문장이
   있다. 검증: 설치된 역할 계약과 앱 내장 본문을 대조한다.
6. 아키텍트 역할 계약에 작업 문서가 완료 조건과 검증 절차를 모두 갖춰야 한다는 문장이 있다. 검증:
   같은 방식으로 설치본과 앱 내장 본문을 대조한다.
7. 이번 기획이 승인된 뒤 새로 분해되는 작업 문서가 요구사항 명세를 참조만 하지 않고 완료 조건과
   검증 절차를 직접 담고 있다. 검증: 이번 변경 이후 만들어진 작업 문서 표본을 확인한다.
8. 개발 보고서에 필수 절 목록이 모두 있고 정한 분량 상한을 넘지 않는다. 검증: 이번 변경 이후 작성된
   보고서 표본이 절 목록과 분량 조건을 만족하는지 확인한다.
9. 공통 규칙과 관련 역할 계약, 조건 스크립트의 버전이 이번 변경만큼 올라가 있다. 검증: 각 문서의
   버전 값과 앱 내부 상수를 대조한다.
10. 기존 자동화 검사가 삭제되거나 비활성화되지 않는다. 검증: 검사 목록의 변경분을 확인한다.
11. 확인 필요 3번에서 정한 측정 방법으로, 이번 변경 전후의 세션당 규격 준수 토큰 비용을 비교할 수
    있다. 검증: 정해진 측정 방법을 실제로 한 차례 실행해 비교 가능한 값이 나오는지 확인한다.
