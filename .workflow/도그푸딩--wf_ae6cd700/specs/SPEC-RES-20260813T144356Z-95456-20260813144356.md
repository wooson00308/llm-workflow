# 참조 패턴을 적용한 집중형 사용자 QA 작업대

## 결정권자 요약

### 제안

개발 현황 안에 흩어진 사용자 QA를 독립된 품질 확인 작업대로 모은다. 기능별로 무엇이 바뀌었고 무엇을
확인할지 먼저 보여 준 뒤, 항목별 확인과 문제 기록과 최종 제출을 한 흐름으로 잇는다.

### 현재

오늘 화면은 기획서 결정만 보여 주고 사용자 QA는 개발 화면 안에서 찾아야 한다. 기능 카드, 단계 목록,
작업 원문, 입력 패널과 시간 제한 이중 클릭을 오가야 하므로 대상과 진행 상황과 최종 결과를 한눈에 보기 어렵다.

### 변경 후

오늘 화면과 전용 메뉴가 기능 단위 QA 대기열로 바로 이어진다. 작업대는 짧은 항목 목록과 현재 단계 하나에
집중하고, 확인한 내용과 문제를 임시로 모아 마지막 검토 화면에서 한 번 제출한다.

### 사용자 결과

사용자는 앱을 열자마자 확인할 기능과 남은 항목을 알고, 화면을 잃지 않은 채 순서대로 검사한다. 문제가
있으면 해당 항목에 사유를 남기고, 마지막에는 완료와 재작업 요청 범위를 확인한 뒤 결정한다.

### 영향 범위

- 변경: 오늘 화면의 선택 대기, 품질 확인 진입점과 대기열, 기능별 확인 진행, 문제 기록과 최종 제출
- 유지: 기능별 QA 묶음 기준, 작업별 결정 기록과 상태 전이, 사용자만 품질 결정을 남기는 권한, 제품의 종이 질감과 차분한 시각 언어

### 비용과 위험

제출 전 진행 내용은 정식 결정이 아니므로 별도 임시 상태로 다뤄야 한다. 확인 도중 작업이 바뀌거나 여러
건 중 일부 기록만 실패할 수 있으므로 오래된 항목과 부분 실패를 감추지 않는 복구 흐름이 필요하다.

### 결정 요청

기능별 QA를 독립 작업대로 모으고 항목별 임시 검토 뒤 마지막 화면에서 완료와 재작업 요청을 함께 제출하는
방향을 승인할지 결정한다. 승인하지 않으면 현재의 개발 화면 중심 QA 진입과 건별 즉시 결정 방식을 유지한다.

## 기획 내용

### 문제와 목표

IDEA-F46517EC은 이전 개선으로 QA 카드 미리보기와 기능별 묶음이 생겼지만, 실제 사용자가 한눈에 대상을
파악하고 확인을 끝내는 경험은 여전히 번거롭다고 지적한다. 목표는 새 장식이나 개발자용 관제 화면을 더하는
것이 아니다. 사용자가 앱에 들어온 순간부터 정식 QA 결정을 제출할 때까지 하나의 짧고 분명한 흐름을 만드는
것이다.

현재 제품의 핵심 사용자는 LLM에 실무를 맡기고 자신은 결정권자로 일하는 사람이다. PRODUCT.md는 앱을 연
순간의 핵심 질문을 “지금 내가 결정할 게 뭐지?”로 정의하고, 화면당 사용자 결정 하나와 단계적 공개를 원칙으로
둔다. 사용자 QA는 이 원칙을 가장 강하게 적용해야 하는 관문이다.

### 현재 경험에서 확인한 사실

2026-08-13 작업 트리와 도그푸딩 워크플로 문서를 기준으로 확인했다.

- 오늘 화면의 `내 선택 대기`는 `user_review` 기획서만 나열한다. QA 대기 작업은 개발 화면이나 에이전트
  화면으로 이동해야 찾을 수 있다. 제품의 첫 질문과 실제 진입점이 어긋난다.
- 개발 화면에는 기능별 `확인할 기능` 묶음, 기획서별 일괄 QA, 작업 상세의 단건 QA라는 세 입구가 함께
  있다. 같은 결정을 서로 다른 정보량과 조작으로 수행할 수 있어 사용자가 어느 길이 기본인지 판단해야 한다.
- 기능별 QA 화면은 작업 제목과 짧은 발췌를 단계로 보여 주지만, 자세히 보거나 문제를 남기려면 작업 상세로
  이동한다. 돌아오면 읽던 단계와 작성 중인 판단을 이어 간다는 표시가 없다.
- 단건 QA는 왼쪽 작업 원문과 오른쪽 입력 패널을 동시에 보여 준다. 확인 완료와 되돌리기는 첫 클릭 뒤
  3.5초 안에 같은 버튼을 다시 누르는 방식이어서, 사용자는 내용 검토와 별개로 시간 제한 조작을 익혀야 한다.
- 자동 검사만 신뢰하는 작업은 확인 동선 미리보기 안의 특정 한국어 문구를 기준으로 접힌 근거로 분류한다.
  분류된 항목도 최종 결정 대상이지만 기본 단계 목록에서는 빠지므로, 사용자가 전체 범위를 이해하려면 별도
  펼침을 열어야 한다.
- 현재 실제 QA 대기는 17건이며 세 기획서에 묶인다. 작업 문서를 한 장씩 처리하는 양보다 기능 세 묶음을
  검토하는 경험이 먼저 보여야 한다는 사례다.
- 상태 기계와 감사 로그는 이미 작업별 결정을 요구한다. 화면에서 기능 단위로 검토해도 최종 기록은 각
  작업의 확인 완료 또는 수정 요청으로 남겨야 한다.

### 조사한 참조와 적용 판단

UI 모양을 그대로 복제하지 않고, 검토 과업을 단순하게 만드는 상호작용 원칙만 가져온다.

| 참조 | 확인한 패턴 | 이 제품에 적용할 부분 | 적용하지 않을 부분 |
| --- | --- | --- | --- |
| [Apple TestFlight](https://developer.apple.com/testflight/) | 테스터가 시작하기 전에 무엇을 시험할지와 관련 정보를 먼저 제공하고, 사용 중 발견한 문제에 맥락을 붙여 피드백한다. | 기능 제목 아래에 바뀐 점과 확인 목표를 먼저 두고, 문제를 발견한 바로 그 항목에 메모를 붙인다. | 빌드 배포, 테스터 그룹, 화면 캡처 첨부와 외부 사용자 관리는 넣지 않는다. |
| [GOV.UK 작업 목록](https://design-system.service.gov.uk/components/task-list/) | 짧은 작업명과 상태로 남은 일을 훑고, 행 전체를 눌러 시작하며, 완료 항목보다 행동이 필요한 항목을 강조한다. | 기능 대기열과 세션 항목을 짧은 행과 평문 상태로 구성하고, 행 전체를 진입점으로 삼는다. | 정부 서비스의 색상과 구성요소 외형은 복제하지 않고 제품의 종이 질감과 딥그린 강조를 유지한다. |
| [GitHub 변경 검토](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request) | 검토 단위를 하나씩 확인하고 진행률을 보며, 피드백을 보류 상태로 모은 뒤 마지막에 승인 또는 변경 요청으로 제출한다. | 항목별 확인 상태와 진행률, 제출 전 문제 메모, 한 번의 최종 검토와 제출을 적용한다. | 코드 차이, 줄 단위 댓글, 토론과 병합 권한은 범위에 넣지 않는다. |
| [GOV.UK 제출 전 답변 확인](https://design-system.service.gov.uk/patterns/check-answers/) | 제출 직전에 내용을 구획별로 다시 보여 주고, 각 항목을 고친 뒤 검토 화면으로 돌아오며, 제출 동작의 결과를 버튼 이름에 명시한다. | 완료와 재작업 요청 대상을 제출 전에 요약하고, 항목을 고쳐도 앞선 입력을 보존하며, 버튼에 기록 결과와 건수를 쓴다. | 별도 신청서나 완료 영수증 화면은 만들지 않는다. |

네 참조의 공통점은 정보량을 늘리지 않고 검토의 상태를 보이게 한다는 것이다. TestFlight의 “무엇을
시험할지”, GOV.UK의 짧은 작업 목록, GitHub의 보류 중 검토, 제출 전 확인 화면을 하나의 QA 여정으로
결합한다.

### 제품 판단

#### 품질 확인을 독립된 사용자 과업으로 둔다

주요 메뉴에 `품질 확인`을 추가한다. 이 화면은 개발 보드의 새 보기 모드가 아니라 결정권자를 위한 전용
작업대다. 개발 보드는 작업 상태와 진행을 보는 장소로 남고, 사용자 QA 결정은 품질 확인 작업대에서 수행한다.

오늘 화면의 `내 선택 대기`는 기획서 승인과 지금 시작할 수 있는 기능별 QA를 함께 보여 준다. 건수는 문서
수가 아니라 사용자가 지금 처리할 결정 단위를 센다. 같은 기획서에서 QA 대기 작업이 일곱 건이어도 하나의
기능 QA로 표시한다. 항목을 누르면 개발 보드를 거치지 않고 해당 QA 세션으로 바로 이동한다.

개발 보드에는 QA 상태와 대기 건수를 계속 보여 주되, 결정 입력 양식은 중복하지 않는다. QA 대기 카드나 기능
요약에서 `품질 확인 열기`를 누르면 같은 전용 작업대로 이동한다. 서로 다른 세 입구가 서로 다른 행동을
제공하지 않게 한다.

#### 대기열은 기능을 먼저 보여 준다

대기열은 `지금 확인할 기능`과 `준비 중인 기능` 두 구획만 둔다. 지금 확인할 기능은 파생 작업이 모두 완료
또는 QA 대기여서 기능 전체를 검토할 수 있는 기존 묶음 기준을 따른다. 준비 중인 기능은 QA 대기 작업이
있지만 아직 끝나지 않은 작업이 있는 경우이며, 남은 작업 수만 보여 주고 시작 조작을 제공하지 않는다.

준비된 기능 행에는 기능 제목, 확인 목표 한 문장, 직접 확인 항목 수, 자동 근거 항목 수와 `시작` 또는
`계속` 상태만 둔다. 작업 식별자 목록, 구현 파일, 상태별 개발 수치와 긴 원문은 기본 대기열에서 숨기고
필요할 때만 상세로 연다. 행 전체를 눌러 세션을 시작한다.

#### 세션은 한 번에 한 항목에 집중한다

세션 상단에는 기능 이름, 바뀐 점 한 문장, 전체 항목 수와 진행률을 고정해 보여 준다. 본문은 왼쪽의 짧은
항목 목록과 오른쪽의 현재 항목 한 개로 구성한다. 넓이가 부족하면 항목 목록을 접을 수 있는 한 열 흐름으로
바꾼다.

모든 QA 대기 작업은 항목 목록에 남는다. 앱이 평문 표현을 추측해 항목 자체를 숨기지 않는다. 화면 조작이
필요한 작업은 개발자가 적은 확인 동선을 그대로 보여 주고, 자동 검사 결과를 신뢰하는 작업도 그 설명과
검사 결과를 같은 목록의 항목으로 보여 준다. 자동 근거는 시각적 무게를 낮출 수 있지만 기본 범위에서
사라지거나 건수에서 빠지지 않는다.

현재 항목에서는 먼저 `확인할 것`, 다음으로 개발자가 남긴 동선과 기대 결과, 마지막으로 보조 정보 순서로
보여 준다. 작업 원문과 구현 상세는 `작업 문서 보기`로 필요할 때만 연다. 사용자가 확인을 마치면 `확인함`
또는 `문제 있음` 중 하나를 고른다. 확인함에는 메모를 요구하지 않고, 문제 있음에는 재현한 동작과 기대와
다른 점을 적어야 한다.

#### 결정은 검토가 끝난 뒤 한 번 제출한다

항목에서 고른 결과는 즉시 작업 문서나 결정 로그를 바꾸지 않는다. 세션 안의 보류 중 검토로 모으고, 모든
항목에 결과가 있으면 `결과 검토`로 이동한다. 검토 화면은 확인 완료 대상과 재작업 요청 대상을 구획으로
나누며 각 항목 옆에서 결과와 메모를 바꿀 수 있다. 변경 뒤에는 검토 화면으로 돌아오고 다른 입력은 유지한다.

최종 버튼은 결과를 모호하게 쓰지 않는다. 문제가 없으면 `17건 확인 완료 기록`, 문제가 섞이면
`12건 완료·5건 재작업 요청`처럼 실제 기록 범위를 표시한다. 이 검토 화면 자체가 오클릭 방지 단계이므로
시간 안에 같은 버튼을 다시 누르게 하는 방식은 쓰지 않는다.

제출하면 확인한 작업에는 기존 `confirmed`, 문제가 있는 작업에는 기존 `revision_requested` 결정을 각각
기록한다. 기능 단위 입력이 작업별 감사 기록을 합치거나 새 상태를 만들지는 않는다. 일부 기록만 실패하면
성공한 항목과 실패한 항목을 구분해 보여 주고, 실패한 항목의 보류 중 결과와 메모를 보존해 다시 제출할 수
있게 한다.

#### 중단과 동시 변경을 안전하게 다룬다

제출 전 결과는 프로젝트 문서의 정식 상태가 아니다. 사용자가 나중에 확인을 눌러 다른 화면으로 이동하거나
앱을 다시 열어도 이어갈 수 있도록 기기에 임시 저장하되, 결정 로그나 작업 문서에는 쓰지 않는다.

임시 검토가 시작된 뒤 대상 작업의 상태나 갱신 시각이 바뀌면 그 항목을 `다시 확인 필요`로 표시한다. 오래된
결과를 자동 제출하지 않고 현재 확인 동선과 상태를 다시 읽게 한다. 기능 묶음이 더 이상 전체 QA 가능 조건을
충족하지 않으면 제출을 막고 대기열의 준비 중 상태로 돌려보낸다.

### 정보 구조와 시각 원칙

- 대기열은 카드 격자보다 한 열 목록을 우선한다. 제목, 짧은 힌트와 상태가 같은 축에 있어 여러 기능을
  빠르게 비교할 수 있어야 한다.
- 세션 본문은 읽기 폭을 제한하고 현재 항목 한 개를 주인공으로 둔다. 긴 원문, 자동 검사 명령과 구현
  세부사항은 단계적으로 펼친다.
- 진행 상태는 색만으로 구분하지 않는다. `확인 전`, `확인함`, `문제 있음`, `다시 확인 필요`를 평문으로
  함께 표시한다.
- 완료 항목은 장식적 성공색을 크게 쓰지 않고 물러나게 한다. 확인 전과 문제 있음처럼 행동이 필요한 항목이
  먼저 눈에 들어와야 한다.
- 제품의 낮은 채도 종이 배경, 딥그린 주요 행동, 절제된 모션을 유지한다. 참조 제품의 파란색, 회색 표,
  코드 검토 외형을 복제하지 않는다.
- 본문과 조작 글자는 제품의 최소 11픽셀 정책과 명암비 기준을 지킨다. 전체 행 진입, 단계 이동, 결과 선택,
  최종 제출을 키보드로 수행할 수 있고 현재 초점이 분명해야 한다.

## 요구사항 명세

### R1. 오늘 화면에서 사용자 QA가 바로 보인다

- `내 선택 대기`에 지금 시작할 수 있는 기능별 QA와 기획서 결정을 함께 표시한다.
- 같은 기능의 QA 대기 작업 여러 건은 한 결정 단위로 센다.
- QA 항목은 기능 제목, 확인 항목 수와 `품질 확인 시작` 조작을 보여 준다.
- 항목을 선택하면 개발 보드나 중간 상세를 거치지 않고 해당 QA 세션으로 이동한다.
- QA와 기획 결정이 모두 없을 때만 기다리는 선택이 없다고 표시한다.

### R2. 품질 확인 전용 대기열을 제공한다

- 주요 메뉴에서 `품질 확인` 화면으로 바로 이동할 수 있다.
- 대기열은 `지금 확인할 기능`을 먼저, `준비 중인 기능`을 그다음에 보여 준다.
- 준비된 기능은 기존 기능별 QA 가능 판정과 같은 집합을 사용한다.
- 준비 중 기능은 QA 대기 건수와 남은 작업 수를 보여 주되 시작할 수 있는 것처럼 보이지 않는다.
- 준비된 기능 행 전체가 진입점이며, 상태 표시는 버튼처럼 보이지 않는다.
- 검색이나 정렬이 없어도 현재 기능 목록을 훑을 수 있는 밀도를 기본으로 한다. 목록이 길어져 보조 탐색이
  필요해질 때도 기본 정보량은 늘리지 않는다.

### R3. 시작 전에 기능의 목적과 확인 범위를 설명한다

- 세션 첫 화면과 고정 머리말에 기능 제목, 바뀐 점, 사용자가 확인할 결과와 전체 항목 수를 보여 준다.
- 설명은 기획서와 작업 문서에 이미 있는 사용자 관점 내용을 근거로 하며, 앱이 구현 세부사항을 새 사실처럼
  만들어 내지 않는다.
- 작업 식별자, 파일 범위와 자동 검사 명령은 첫 화면의 필수 정보가 아니다.

### R4. 모든 QA 대기 작업을 추적 가능한 확인 항목으로 보여 준다

- 기능에 포함된 모든 QA 대기 작업이 항목 목록과 전체 건수에 나타난다.
- 앱이 확인 동선의 평문 표현을 추측해 항목을 목록에서 제거하지 않는다.
- 화면 조작형 항목은 확인 동선과 기대 결과를, 자동 근거형 항목은 화면이 없다는 설명과 검증 결과를 보여 준다.
- 자동 근거형은 접어 둘 수 있지만 제목, 상태와 건수는 접힌 상태에서도 보인다.
- 각 항목의 상태는 `확인 전`, `확인함`, `문제 있음`, `다시 확인 필요` 중 하나로 평문 표시한다.

### R5. 한 번에 한 항목을 확인하고 진행 상황을 유지한다

- 현재 항목만 본문에서 강조하고 이전과 다음 항목으로 이동할 수 있다.
- 전체 수, 결과를 남긴 수와 남은 수를 항상 확인할 수 있다.
- 사용자가 순서와 무관하게 항목을 열 수 있지만, 결과가 없는 항목이 있으면 최종 제출할 수 없다.
- `확인함`은 메모 없이 선택할 수 있다.
- `문제 있음`은 해당 작업과 연결된 구체적인 설명을 필수로 받는다.
- 작업 원문은 보조 상세로 열며, 닫으면 같은 항목과 작성 중인 내용으로 돌아온다.

### R6. 제출 전 검토 화면에서 결과를 수정할 수 있다

- 모든 항목에 결과가 생기면 제출 전 검토 화면을 연다.
- 검토 화면은 확인 완료 대상과 재작업 요청 대상을 분리하고 각각의 건수를 보여 준다.
- 각 항목에서 결과와 메모를 다시 고칠 수 있으며, 돌아왔을 때 다른 항목의 입력이 보존된다.
- 최종 버튼은 완료와 재작업 요청 건수를 문구에 포함한다.
- 검토 화면 뒤의 최종 제출에는 시간 제한 이중 클릭을 추가하지 않는다.

### R7. 기능 단위 검토와 작업별 감사 기록을 함께 지킨다

- 한 번의 제출이더라도 대상 작업마다 기존 QA 결정 문서 하나와 해당 상태 전이 하나를 남긴다.
- `확인함`은 기존 확인 완료 결과로, `문제 있음`은 기존 수정 요청 결과로 기록한다.
- 기능 단위 결정을 위한 새 작업 상태나 합쳐진 결정 문서 형식을 만들지 않는다.
- QA 결정은 계속 사용자 조작으로만 기록되며 에이전트가 대신 제출할 수 없다.

### R8. 중단한 검토를 안전하게 이어 간다

- 제출 전 결과와 메모는 정식 프로젝트 문서가 아닌 기기 내 임시 검토로 저장한다.
- 다른 화면으로 이동하거나 앱을 다시 열어도 `계속`으로 돌아갈 수 있다.
- 임시 검토를 버리는 조작은 대상 기능과 사라질 항목 수를 보여 준 뒤 실행한다.
- 대상 작업의 상태나 갱신 시각이 바뀌면 해당 항목을 다시 확인하기 전까지 제출하지 못한다.
- 기능 묶음이 준비 조건을 잃으면 임시 검토를 보존한 채 준비 중으로 표시하고 원인을 알린다.

### R9. 실패와 동시 변경을 건별로 설명한다

- 제출 직전에 대상 작업의 현재 상태와 검토 시작 시점의 근거를 다시 확인한다.
- 일부 기록만 실패해도 성공한 결과를 실패로 보이게 하거나 실패한 결과를 성공으로 보이게 하지 않는다.
- 결과 화면은 성공한 완료 건, 성공한 재작업 요청 건과 실패한 항목의 제목과 사유를 구분한다.
- 실패한 항목의 결과와 메모는 보존하고 성공한 항목은 다시 제출 대상에 넣지 않는다.
- 입력이 너무 길거나 수정 요청 사유가 비어 있는 경우에는 제출 전에 해당 항목에서 바로 고칠 수 있게 한다.

### R10. QA 결정 입구를 한 작업대로 연결한다

- 개발 보드의 QA 상태, 카드와 기능 요약은 유지한다.
- 개발 보드에서 QA 조작을 선택하면 전용 작업대의 같은 기능과 항목으로 이동한다.
- 작업 상세와 기획서별 일괄 화면에 서로 다른 독립 결정 양식을 남겨 두지 않는다.
- 검색, 개발 상태 필터, 기획서별 묶기와 기존 작업 상세의 읽기 기능은 그대로 동작한다.

### R11. 접근성과 화면 크기 변화에 대응한다

- 항목 행 전체 진입, 이전과 다음 이동, 결과 선택, 검토와 제출을 키보드만으로 수행할 수 있다.
- 초점 이동은 현재 항목과 오류 위치를 따라가며, 화면 읽기 도구가 진행률과 각 항목 상태를 읽을 수 있다.
- 상태는 색, 아이콘이나 위치 하나에만 의존하지 않는다.
- 좁은 창에서는 목록과 현재 항목을 세로로 배치하고, 가로 스크롤 없이 주요 행동을 사용할 수 있다.
- 모션 감소 설정에서 진행 전환과 상태 변화가 움직임 없이도 이해된다.

### R12. 제품 시각 언어와 정보 절제를 유지한다

- 참조 서비스의 구조 원칙만 적용하고 색상, 타이포그래피와 브랜드 외형은 복제하지 않는다.
- 대기열 한 행의 보조 설명은 한 문장으로 제한하고 긴 문서는 필요할 때 펼친다.
- 주요 행동은 화면마다 하나만 가장 강하게 표시한다. 세션에서는 현재 항목 결과, 검토 화면에서는 최종 제출이
  그 행동이다.
- 장식 목적의 그래프, 점수, 축하 애니메이션과 개발 생산성 지표를 추가하지 않는다.

## 완료 조건

1. QA 가능한 기능과 기획서 검토가 함께 있는 프로젝트를 열면 오늘 화면의 `내 선택 대기`가 둘을 모두
   보여 주고, 기능 QA 여러 작업은 한 항목과 한 건수로 센다.
2. 오늘 화면의 QA 항목이나 주요 메뉴의 `품질 확인`을 선택하면 개발 보드를 거치지 않고 같은 기능의 QA
   작업대로 이동한다.
3. 대기열은 지금 확인할 기능과 준비 중인 기능을 구분하고, 준비 중 기능은 남은 작업 수만 보여 주며 시작
   조작을 제공하지 않는다.
4. 실제 17개 QA 대기 작업을 가진 현재 문서 집합에서 세 기능이 먼저 보이고, 각 기능을 열면 그 기능의
   모든 QA 대기 작업이 항목 목록과 전체 건수에 포함된다.
5. 세션을 시작하면 기능의 바뀐 점과 확인 목표를 먼저 읽고, 현재 항목 하나와 전체 진행률을 같은 화면에서
   확인할 수 있다.
6. 화면 조작형과 자동 근거형 항목이 모두 목록에 남고, 자동 근거를 접어도 제목과 상태와 건수는 보인다.
7. 확인함을 메모 없이 기록할 수 있고, 문제 있음은 사유가 없으면 결과로 확정되지 않는다.
8. 일부 항목을 확인하고 다른 화면으로 이동하거나 앱을 다시 연 뒤 같은 항목과 입력 내용에서 계속할 수 있다.
9. 모든 항목에 결과를 남기면 검토 화면이 완료와 재작업 요청 대상을 분리해 보여 주고, 항목을 고친 뒤에도
   다른 입력이 유지된다.
10. 문제가 없는 기능은 최종 버튼 한 번으로 대상 전 건의 확인 완료를 기록한다. 버튼은 기록할 건수를 말하고
    시간 제한 이중 클릭을 요구하지 않는다.
11. 확인함과 문제 있음이 섞인 기능은 한 번 제출해 각 작업에 기존 확인 완료 또는 수정 요청 결정을 남기고,
    작업 상태와 이력이 각 결과에 맞게 바뀐다.
12. 제출 중 일부 작업만 실패하는 시나리오에서 성공과 실패가 항목별로 보이고, 실패 항목의 메모는 남으며,
    성공 항목은 재시도 때 중복 기록되지 않는다.
13. 검토 도중 작업의 상태나 갱신 시각을 바꾸면 그 항목이 다시 확인 필요로 바뀌고, 현재 내용을 다시 보기
    전에는 제출할 수 없다.
14. 개발 보드의 QA 카드에서 품질 확인을 열면 같은 작업대로 이동하며, 별도의 이전 방식 결정 양식과 결과가
    충돌하지 않는다.
15. 키보드만으로 대기열 진입부터 항목 결과 선택과 최종 제출까지 완료할 수 있고, 좁은 창에서도 가로 스크롤
    없이 같은 흐름을 수행한다.
16. 기획서 승인, 개발 작업 상태 표시, 작업별 QA 결정 스키마와 사용자 전용 결정 권한이 변경 전과 같다.
17. 기존 자동 검사를 삭제하거나 비활성화하지 않고, 사용자 QA 진입, 임시 검토, 혼합 결과 제출, 부분 실패,
    동시 변경과 접근성 시나리오를 자동 검사로 추가한다.

## 제외 범위

- TestFlight처럼 앱 빌드를 배포하거나 외부 테스터와 테스터 그룹을 관리하는 기능
- 화면 캡처, 이미지 표시, 주석 첨부와 파일 업로드를 QA 피드백에 추가하는 기능
- 앱이 테스트 명령이나 제품 화면 조작을 자동 실행하는 기능
- LLM이 사용자 대신 QA 결정을 만들거나 최종 제출하는 기능
- 작업별 QA 결정 문서 형식, 작업 상태 기계와 기존 사용자 결정 권한의 변경
- 개발자 계약에 새 QA 분류 필드를 추가하거나 기존 작업 문서를 소급 변환하는 일
- 기획서 승인과 수정 요청 화면, 작업 정의 수정 요청과 막힘 복구 흐름의 재설계
- 원격 알림, 계정별 동기화와 여러 기기 사이의 임시 검토 공유
- 제품의 브랜드, 전체 내비게이션 체계와 개발 보드 자체를 전면 교체하는 일

## 기대효과

- 사용자는 개발 문서와 보드를 탐색하기 전에 지금 확인할 기능을 발견한다.
- 기능 하나의 목적, 확인 항목, 진행률과 최종 결과가 한 흐름에 있어 QA를 중단하거나 빠뜨릴 가능성이 줄어든다.
- 문제 메모가 해당 작업에 연결된 상태로 마지막 제출까지 보존돼 개발자가 재현할 근거가 분명해진다.
- 기능 단위의 간결한 화면과 작업별 감사 기록을 함께 유지해 사용자 경험을 단순화하면서 파일 계약을 약화하지 않는다.
- 외부 참조의 검증된 검토 패턴을 제품의 차분한 문서형 시각 언어에 맞게 적용해 새 UI를 임의로 창작하는 위험을 줄인다.
