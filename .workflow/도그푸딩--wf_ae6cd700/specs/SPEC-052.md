# 구조화된 결정권자 요약 보드

## 결정권자 요약

짧은 요약을 고정된 정보 구조와 읽기 쉬운 결정 보드로 바꿔, 검토자가 긴 원문 전에 변화와 판단을 파악하게 한다.
사용자가 결정할 것은 첫 적용 대상을 기획서와 개발 작업으로 한정하는 제안과 그 표준 항목이다.
승인하면 새 문서는 현재, 변경 후, 사용자 결과, 영향과 위험, 결정 요청을 같은 순서로 보여 준다.
기존 문서와 형식이 불완전한 문서는 지금의 평문 요약과 원문 보기 방식을 그대로 유지한다.
원문은 계속 유일한 정본이며, 자동 요약, 저장용 변환물, 임의의 차트와 외부 공유 기능은 추가하지 않는다.
승인하지 않으면 현재의 일반 Markdown 요약 화면과 문서 작성 방식이 유지된다.

## 기획 내용

결정권자 요약과 원문 전문 토글은 이미 사용자가 기획서와 개발 작업을 검토할 때 긴 작업자용 본문을
먼저 읽지 않게 한다. 그러나 요약 자체는 일반 Markdown 본문으로만 표시된다. 무엇을 바꾸는지, 현재
제약이 무엇인지, 승인 후의 결과와 지금 내려야 할 판단이 한 문단에 섞이면 짧은 요약도 빠르게 비교하기
어렵다.

이 기획서는 Markdown을 계속 유일한 정본으로 두고, 결정권자 요약 안에 기계가 추측하지 않아도 되는
고정 구조를 추가한다. 앱은 구조를 갖춘 새 문서만 전용 결정 보드로 표시한다. 형식이 없거나 일부만
있는 문서는 오류로 취급하거나 내용을 보완하지 않고, 현재의 Markdown 요약 표시로 돌아간다. 따라서
기존 문서와 사용자 작성 문서는 소급 수정 없이 안전하게 읽을 수 있다.

첫 범위는 사용자가 실제로 결정 또는 QA 확인을 하는 기획서와 개발 작업이다. 개발 보고서는 현재
전용 검토 화면이 없으므로 기존의 결정권자 요약 계약을 유지하되, 이 기획서의 구조화 표시 대상에서는
제외한다. 보고서를 읽고 결정하는 화면이 필요해질 때 문서 종류와 표시 맥락을 함께 정하는 후속
기획으로 다룬다.

### 구조화된 요약의 문서 계약

구조화된 요약은 기존 `## 결정권자 요약` 절 안에 아래 순서와 제목으로 작성한다. 모든 필수 항목은
문서마다 한 번만 쓴다. 앱은 제목이나 순서를 유사한 표현으로 해석하지 않는다.

```markdown
## 결정권자 요약

### 제안
한 문장으로 이번 변경의 정체성을 말한다.

### 현재
사용자가 겪는 문제나 현재 제약을 말한다.

### 변경 후
승인 또는 완료 뒤 제품과 운영이 어떻게 달라지는지 말한다.

### 사용자 결과
사용자가 직접 얻는 결과를 말한다.

### 영향 범위
- 변경: 바뀌는 영역을 짧게 적는다.
- 유지: 바뀌지 않는 영역을 짧게 적는다.

### 비용과 위험
결정 전에 알아야 할 비용, 호환성, 마이그레이션 또는 운영 위험을 적는다.

### 결정 요청
지금 승인, 수정 요청 또는 QA 확인으로 판단할 내용을 적는다.
```

`비용과 위험`은 해당 값이 있을 때만 쓴다. 나머지 여섯 항목과 영향 범위 안의 `변경`·`유지` 표식은
필수다. 빈 항목, 같은 제목의 반복, 다른 깊이의 제목, 항목 순서 변경, `영향 범위`의 한쪽 표식 누락은
구조화 형식으로 인정하지 않는다. 이 경우 원문을 바꾸지 않고 평문 요약으로 표시한다.

기획서와 개발 작업을 새로 작성하거나 수정 요청에 따라 다시 작성하는 역할은 이 구조를 작성한다.
개발 작업의 `결정 요청`은 사용자가 QA에서 확인할 결과를 말하고, 기획서의 `결정 요청`은 승인 또는
수정 요청으로 판단할 범위를 말한다. 개발자가 작업 상태를 바꾸면서 요약을 갱신할 때도 구조와 문서의
사실이 어긋나지 않게 유지한다.

### 결정 보드의 사용자 경험

구조화된 요약을 읽을 때 첫 화면은 일반 본문을 세로로 반복하지 않는다. 상단에는 `제안`과 `현재`를
보이고, 다음에는 `현재 → 변경 후 → 사용자 결과`를 같은 읽기 순서의 흐름으로 보여 준다. 그 아래에는
변경·유지 영역을 구분하고, 값이 있을 때만 비용과 위험을 경고 영역으로 보인다. 마지막에는 `결정 요청`과
기존 승인·수정 요청·폐기 또는 QA 조작을 같은 시야에 둔다.

표현은 문서마다 임의의 삽화나 차트를 만들지 않는다. 각 항목은 같은 위치와 제목을 유지해 여러 문서를
비교할 수 있어야 한다. 상태, 파생 작업 수, 결정 이력처럼 이미 별도 화면 요소가 말하는 사실을 요약
보드가 다시 장황하게 반복하지 않는다. 아이콘과 색상은 보조 수단이며, 텍스트 제목과 읽기 순서만으로도
정보와 위험의 의미를 이해할 수 있어야 한다.

원문 전문 토글은 유지한다. 구조화된 보드는 문서의 정본을 대체하거나 편집하지 않으며, 원문을 열면
구조화된 요약을 포함한 문서 전체가 현재처럼 그대로 보여야 한다.

## 요구사항 명세

### R1. 결정권자 요약에 결정적인 구조를 추가한다

- 새 기획서와 새 개발 작업의 결정권자 요약은 정해진 제목, 순서, 필수 항목을 사용한다.
- 앱은 문장 내용이나 비슷한 제목을 추측하지 않고 정확한 구조만 읽는다.
- 구조를 모두 충족한 문서만 전용 결정 보드로 표시한다.
- 선택 항목인 비용과 위험이 없으면 빈 카드, 빈 제목, 빈 공간을 만들지 않는다.

### R2. 기획서와 개발 작업에 맞는 판단을 구분한다

- 기획서 보드는 무엇을 승인하거나 수정할지와 승인 후 변화, 미승인 시 유지되는 상태를 분명히 보인다.
- 개발 작업 보드는 QA에서 무엇을 확인할지와 완료 뒤 사용자가 얻는 결과를 분명히 보인다.
- 영향 범위는 바뀌는 영역과 유지되는 영역을 각각 보여 주어, 변화의 크기를 추측하게 만들지 않는다.
- 이미 독립적으로 표시하는 상태와 결정 이력은 원래 표시를 유지하고, 요약 보드는 판단에 필요한
  설명만 제공한다.

### R3. 기존 문서와 불완전한 문서를 안전하게 읽는다

- 기존 평문 요약을 가진 문서는 현재의 요약 표시와 원문 전문 토글을 그대로 제공한다.
- 요약이 없거나 구조가 일부만 있는 문서도 오류 경고, 데이터 손실, 자동 변환 없이 전체 원문을 읽을 수
  있다.
- 기존 기획서, 개발 작업, 개발 보고서를 새 구조로 소급 수정하지 않는다.
- 문서가 쓴 HTML을 허용하거나 저장된 HTML을 새 정본으로 만들지 않는다.

### R4. 읽기 순서와 접근성을 보장한다

- 넓은 창에서는 변화 흐름, 영향 범위, 위험, 결정 요청의 계층을 빠르게 훑을 수 있게 표시한다.
- 작은 창에서는 같은 정보가 한 열로 쌓이고, 시각 순서와 키보드·스크린 리더의 읽기 순서가 일치한다.
- 색상이나 아이콘을 제거해도 제목과 문장만으로 현재 상태, 위험, 변경 결과를 이해할 수 있다.
- 위험이 있는 경우는 결정 요청 가까이에서 보이되, 다른 정보를 가리거나 승인·수정 요청·폐기 조작을
  밀어내지 않는다.

### R5. 원문과 비용 경계를 유지한다

- 구조화 표시는 문서 본문만으로 결정적으로 만들어지며 네트워크 요청이나 LLM 호출을 하지 않는다.
- 표시를 위해 별도 HTML 문서, 요약 캐시, 이미지, 문서별 차트 데이터를 저장하지 않는다.
- 인쇄나 외부 공유용 내보내기는 현재 범위에 포함하지 않는다. 필요성이 확인되면 같은 원문을 일회성으로
  표현하는 별도 기획에서 다룬다.

## 확인 필요

첫 릴리스의 구조화 표시 대상은 기획서와 개발 작업으로 한정하는 것을 제안한다. 두 문서는 현재
결정권자가 실제로 읽고 승인 또는 QA 확인을 하는 화면이 있으며, 기존 원문 토글도 있다. 개발 보고서는
기존 요약 계약을 유지하지만 전용 읽기·결정 화면이 없으므로 이번 범위에 넣지 않는다.

사용자가 보고서까지 같은 형식과 표시 대상으로 포함해야 한다고 판단하면, 보고서를 여는 화면과 그
문서에 맞는 결정 시점을 함께 정의하도록 수정 요청을 남긴다. 이 기획서를 승인하면 위의 두 문서 종류와
고정 항목을 첫 계약으로 확정한다.

## 기대효과

- 검토자는 긴 본문을 읽기 전에 현재 문제, 제안, 결과, 영향, 위험과 요청된 판단을 같은 자리에서 비교한다.
- 문서마다 같은 위치에서 같은 의미를 찾아, 기획 승인과 개발 작업 QA의 읽기 부담을 줄인다.
- 기존 문서의 유효성과 단일 Markdown 정본을 보존해 도입 과정에서 문서 이력이나 호환성을 훼손하지 않는다.
- 자동 요약과 저장 변환물이 없어 외부 비용, 보안 경계 확대, 정본 불일치 위험을 만들지 않는다.

## 완료 조건

1. 필수 항목을 모두 갖춘 새 기획서를 열면 제안·현재·변경 후·사용자 결과·영향 범위·결정 요청이 정한
   순서로 보이고, 위험 값이 있을 때만 비용과 위험 영역이 함께 보인다.
2. 같은 구조를 갖춘 개발 작업을 QA 화면에서 열면 사용자가 확인할 결과와 QA 조작을 같은 화면에서
   확인할 수 있다.
3. 기존 평문 요약 문서와 필수 항목이 빠진 문서를 각각 열면 현재와 같은 Markdown 요약 또는 원문 표시가
   유지되고, 전용 보드는 임의의 값을 만들어 내지 않는다.
4. 구조화된 문서에서 원문 전문을 열면 요약을 포함한 전체 Markdown 본문이 손실이나 재배치 없이 보인다.
5. 넓은 창과 작은 창에서 정보 순서가 일관되고, 키보드만으로 원문 전문 토글과 기존 결정 조작에 도달할
   수 있으며, 색상·아이콘 없이도 각 정보의 뜻을 알 수 있다.
6. 구조화된 표시를 여는 동안 네트워크 요청이나 LLM 호출이 발생하지 않고, 추가 HTML 정본이나 문서별
   변환물이 저장되지 않는다.
7. 문서 구조 판정, 구조화 표시, 평문 폴백, 원문 토글, 기획서 승인 흐름과 개발 작업 QA 흐름의 관련
   자동 검사가 모두 통과한다.
