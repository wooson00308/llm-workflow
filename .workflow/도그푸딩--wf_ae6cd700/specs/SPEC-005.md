# 연동 잡 재설치 시 사용자 편집값 보존

## 기획 내용

실제로 일어난 사고에서 출발한다. 사용자가 관리 UI에서 개발자 잡의 `max_per`를 `8/24h`로 올려 두었는데, 이후 관리 블록이 기본값 `6/24h`로 다시 쓰이면서 편집값이 조용히 사라졌다. 화면에는 아무 경고도 남지 않았고, 사용자가 알아챈 것은 쿼터가 예상보다 일찍 소진되어 대기 중인 작업이 한동안 실행되지 않은 뒤였다. 값은 손으로 복구했다.

여기서 나쁜 것은 값이 하나 바뀐 것이 아니다. 앱이 사용자의 결정을 경고 없이 폐기했고, 그 사실이 어디에도 드러나지 않았다는 것이다. `~/.claude/HEARTBEAT.md`는 전역 파일이고 앱이 소유하는 블록은 그 안의 일부다. 그 블록에 대해 앱이 지금 보장하는 것은 "같은 입력을 두 번 주면 파일이 변하지 않는다"(SPEC-002 R2)뿐이다. 같은 입력이 들어온다는 보장은 어디에도 없다.

지금 편집값이 보존되는 이유를 확인해 보면 문제가 분명해진다. 보존은 저장 계약이 아니라 화면 시딩에서 일어난다. 카드가 파일에서 읽은 값을 입력 폼에 채우고, 저장 버튼은 그 폼을 그대로 요청으로 만든다. 백엔드는 받은 값을 그 연동의 desired state로 신뢰하고 블록을 다시 쓴다. 즉 파일의 값이 살아남는 경로는 "화면이 파일을 정확히 읽어서 폼에 넣었다"는 조건 하나에 전부 걸려 있다. 그 조건이 한 번이라도 어긋나면 기본값이 그대로 파일에 기록되고, 그때 화면에 뜨는 것은 성공 표시뿐이다.

그 조건이 실제로 어긋날 수 있는 지점이 코드에 남아 있다. 상태 조회는 `HEARTBEAT.md` 읽기에 실패하면 빈 문서로 접어서 진행한다. 그러면 "관리 블록에 잡이 하나도 없다"와 구별되지 않고, 화면은 첫 설치 상태로 판단해 역할 3종을 켠 채 기본값을 채운다. 같은 코드의 설치 경로에는 이미 반대 판단이 주석으로 적혀 있다. 못 읽은 문서를 빈 문서로 보면 잡을 지우는 병합이 만들어지므로 오류로 올린다는 것이다. 조회 경로는 그 판단을 따르지 않는다.

그래서 이 기획서는 값 하나를 고치지 않고 보장의 위치를 옮긴다. 편집 가능 값의 보존을 화면 시딩의 부수효과가 아니라 쓰기 계약으로 만든다. 규칙은 하나다. **앱은 파일에 적힌 편집 가능 값을 기준으로 쓰고, 사용자가 화면에서 실제로 지정한 것만 그 위에 덮는다.** 기본값은 그 잡이 블록에 없을 때의 초기값이지, 읽지 못했을 때의 대체값이 아니다.

여기에 두 가지를 덧붙인다. 첫째, 되돌리는 것이 정당한 경우도 있다. 사용자가 값을 망쳐 놓고 처음부터 다시 시작하고 싶을 때다. 그것은 별도의 명시적 액션이어야 하고, 실행 전에 무엇이 어떻게 바뀌는지 보여야 한다. 둘째, 쓰기 전 확인 화면이 지금은 "쓸 값"만 나열한다. 사고를 눈으로 잡으려면 나열이 아니라 차이가 보여야 한다.

앱의 역할은 달라지지 않는다. 앱은 여전히 아무것도 실행하지 않고, 파일 계약을 관리하고 상태를 보여줄 뿐이다. 이 기획서가 바꾸는 것은 그 계약 안에서 "누구의 값이 이긴다"는 규칙이다.

### 확인 사실

아래는 현재 코드와 실제 파일에서 확인한 사실이고, 이 기획서는 그 위에 서 있다.

- 잡의 편집 가능 값은 `interval`, `max_per`, `model` 세 개다. `slug`, `prompt`, `timeout`, `condition`, `notify`는 앱이 소유하며 설치할 때마다 앱 값으로 다시 만들어진다(`role_managed_jobs`).
- 설치 커맨드는 자기 연동 잡의 편집 가능 값을 요청에서 문자열로 그대로 받는다(`RoleJobRequest`, `DreamJobRequest`). 요청 값이 파일 값과 다른지 비교하는 지점은 없다.
- 다른 연동의 잡은 이미 파일 기준으로 보존된다(`preserved_role_jobs`, `preserved_dream_job`). 보존 대상의 값이 검증을 통과하지 못하면 조용히 기본값으로 되돌리지 않고 `PreservedJob` 오류로 실패하며 아무 파일도 쓰지 않는다. 즉 "파일 값을 기준으로 삼는다"는 규칙은 연동 사이에서는 이미 성립하고, 자기 연동 안에서만 성립하지 않는다.
- 화면은 관리 블록에서 읽은 값으로 폼을 채운다(`roleFormFrom`). 블록에 잡이 하나도 없으면 첫 설치로 보고 역할 3종을 켠 상태에서 기본값(`planner 30m·4/24h`, `architect 30m·4/24h`, `developer 20m·6/24h`, 모두 `opus`)으로 시작한다.
- 상태 조회는 `HEARTBEAT.md` 읽기 실패를 빈 문서로 접는다(`inspect`의 `unwrap_or_default()`). 읽기 실패는 `readFailures`로 카드에 표시되지만, 같은 조회 결과의 `managedJobs`는 빈 목록이 되어 화면상 "잡 없음"과 구별되지 않는다. 같은 파일의 설치 경로(`read_document`)는 반대로 동작한다. `NotFound`만 빈 문서로 보고 다른 읽기 실패는 오류로 올리며, 그 이유가 주석에 적혀 있다.
- 화면은 관리 블록이 바뀌면 입력 폼을 파일 값으로 되돌린다. 판정 기준은 `managedJobs`의 직렬화 값이고, 사용자가 편집 중이던 값은 알림 없이 대체된다.
- 저장 버튼 문구는 이미 상태에 따라 다르다. 설치 전은 "이 프로젝트에 역할 잡 설치", 설치 후는 "역할 잡 변경 사항 저장"이다. 그러나 두 문구가 부르는 동작은 같은 커맨드이고 같은 payload 형태다.
- 쓰기 전 확인 화면은 쓰게 될 값만 나열한다(`기록: wf-developer-... — 20m · 6/24h · opus`). 파일의 현재 값이나 그 차이는 표시하지 않는다.
- 값을 기본값으로 되돌리는 명시적 액션은 없다. 지금 그 결과를 얻는 유일한 경로는 잡을 껐다 켜는 것이고, 화면은 그 사실을 "끄면 편집한 값도 함께 사라지고, 다시 켜면 기본값으로 시작합니다"로 안내한다.
- 현재 `~/.claude/HEARTBEAT.md`의 관리 블록에는 역할 잡 3종이 있고 `max_per`는 각각 `8/24h`, `8/24h`, `16/24h`다. 세 값 모두 앱 기본값과 다르다. 즉 이 저장소의 실사용 구성은 편집값에 의존하고 있다.

### 포함 범위

- 연동 관리 UI에 존재하는 모든 잡(현재 역할 잡 3종과 dream 잡)의 편집 가능 값에 대한 저장 규칙
- 관리 블록을 읽지 못한 상태와 잡이 없는 상태의 구분, 그리고 그 상태에서의 쓰기 차단
- 화면이 읽은 뒤 파일이 바뀐 경우의 처리
- 쓰기 전 확인 화면의 변경 내용 표시
- 기본값으로 되돌리는 명시적 액션

### 제외 범위

- 앱 소유 필드(`slug`, `prompt`, `timeout`, `condition`, `notify`)를 사용자 편집값으로 보존하는 것. 이 필드들이 앱 소유라는 것은 SPEC-002 R2에서 정한 계약이고 이 기획서는 그 계약을 바꾸지 않는다. 다만 되돌아간다는 사실을 사용자에게 알리는 것은 R4가 다룬다.
- 백엔드 값 검증 규칙 변경. 형식 검증(`interval`·`max_per`·`model`)과 실패 동작은 현행 그대로다.
- 모델 목록과 직접 입력 규칙(SPEC-004 R2·R3). 이 기획서는 그 규칙 위에서 값이 보존되는지만 다룬다.
- 잡의 실행 이력·로그를 읽어 보여주는 관측 기능 확장. SPEC-002가 제외한 범위다.
- 한 관리 블록을 여러 프로젝트가 공유할 때 다른 프로젝트의 잡이 지워지는 문제. 연동 축이 아니라 프로젝트 축의 문제이고 REPORT-TASK-012-DEV가 후속으로 지목해 둔 별도 사안이다.
- 관리 블록 밖 사용자 잡에 대한 어떤 변경도 하지 않는다(현행 유지).
- 편집 이력·되돌리기(undo) 기능. 이 기획서는 폐기를 막는 것이지 폐기된 값을 복원하는 것이 아니다.
- `.workflow/rules/*.md` 역할 계약 본문 변경, 마이그레이션 스키마 변경.

## 요구사항 명세

### R1. 저장은 파일의 현재 값을 기준으로 한다

- 잡 설정 쓰기는 관리 블록에 적힌 편집 가능 값에서 출발하고, 사용자가 이번 편집에서 실제로 지정한 값만 그 위에 덮는다.
- 기본값은 그 잡이 관리 블록에 없을 때의 초기값이다. 이미 블록에 있는 잡의 값을 기본값으로 대체하는 경로는 R5의 명시적 액션 하나뿐이다.
- 이 보장은 화면이 아니라 쓰기 경로에 있어야 한다. 화면이 파일 값을 폼에 채우는 동작은 유지하되, 그것이 유일한 보존 수단이어서는 안 된다. 판정 기준: 화면이 값을 잘못 채운 상태에서 저장이 일어나도 사용자가 지정하지 않은 필드는 파일 값이 유지되어야 한다.
- 규칙은 잡 종류마다 따로 정의하지 않는다. 역할 잡과 dream 잡, 이후 추가될 잡에 같은 규칙이 적용된다.
- 다른 연동 잡에 대한 현행 보존 동작(`preserved_*`)과 `PreservedJob` 실패 동작은 그대로 유지한다. 이 기획서는 같은 규칙을 자기 연동 안으로 넓히는 것이지 기존 보존을 대체하는 것이 아니다.

### R2. 읽지 못한 상태와 잡이 없는 상태를 구분한다

- 관리 블록 읽기에 실패한 상태는 "관리 블록에 잡이 없다"와 다른 상태로 다룬다. 화면에서 두 상태가 같아 보여서는 안 된다.
- 읽기에 실패한 상태에서는 잡 설정 저장을 막고 사유를 표시한다. 앱은 자신이 모르는 값을 덮어쓰지 않는다.
- 읽기 실패 상태에서 폼을 기본값으로 채워 보여주지 않는다. 기본값이 화면에 보이면 사용자는 그것이 파일의 값이라고 읽는다.
- 이 구분은 읽기 실패가 이미 `readFailures`로 표시된다는 사실과 별개다. 경고가 떠 있어도 저장 버튼이 살아 있고 폼에 기본값이 차 있으면 사고는 그대로 일어난다.

### R3. 화면이 읽은 뒤 파일이 바뀌면 확인 없이 덮어쓰지 않는다

- 저장 시점에 관리 블록이 화면이 읽은 시점의 값과 다르면, 그대로 덮어쓰지 않는다. 사용자에게 달라졌다는 사실과 무엇이 다른지 보이고 어떻게 할지 정하게 한다.
- 자동 새로고침이 사용자가 편집 중인 입력값을 알림 없이 파일 값으로 대체해서는 안 된다. 앱이 화면과 파일 중 한쪽을 임의로 고르지 않는다는 점에서 앞 항목과 같은 규칙이다.
- 편집 중이 아닐 때(사용자가 아무 필드도 건드리지 않은 상태) 파일 값 변화가 화면에 반영되는 현행 동작은 유지한다. 이 요구는 사용자의 입력을 지키는 것이지 화면을 낡은 채로 두는 것이 아니다.

### R4. 확인 화면은 나열이 아니라 차이를 보여준다

- 쓰기 전 확인 화면은 잡별로 파일의 현재 값과 쓰게 될 값을 함께 보여주고, 달라지는 값을 구분해 표시한다.
- 아무 값도 달라지지 않으면 그 사실을 밝힌다. 파일이 바뀌지 않는다는 것을 사용자가 확인 화면에서 알 수 있어야 한다.
- 관리 블록 안의 앱 소유 필드가 사용자 편집 상태와 다르면, 그 필드가 앱 값으로 되돌아간다는 사실을 확인 화면에 함께 밝힌다. 값 자체는 R1의 보존 대상이 아니지만 되돌아간다는 사실은 알려야 한다.
- 잡이 제거되는 경우(토글을 끈 경우) 그 잡의 편집값이 함께 사라진다는 것을 확인 화면에서 밝힌다. 현재 필드 옆 안내 문구만으로는 확인 단계에서 다시 보이지 않는다.
- 확인 절차 자체(SPEC-002 R6의 전역 파일 쓰기 사전 확인)는 그대로 유지한다. 이 요구는 그 화면에 담기는 정보를 바꾼다.

### R5. 기본값으로 재설정을 명시적 액션으로 분리한다

- 값을 앱 기본값으로 되돌리는 별도 액션을 제공한다. 저장 액션과 문구·위치에서 구분되어야 하고, 저장의 부작용으로 일어나서는 안 된다.
- 실행 전에 현재 값과 기본값의 차이를 보여주고 확인을 받는다. 확인 절차는 R4와 같은 화면 규약을 따른다.
- 이 액션도 쓰기이므로 SPEC-002 R6의 전역 파일 쓰기 규약(명시적 사용자 액션, 원자적 저장)을 그대로 따른다.
- 이 액션은 편집 가능 값만 되돌린다. 잡의 존재 여부(활성·비활성)는 바꾸지 않는다.

### R6. 기존 쓰기 계약을 유지한다

- 같은 상태로 다시 저장하면 파일이 변하지 않는다(SPEC-002 R2의 멱등). 이 기획서의 규칙은 그 성질을 강화할 뿐 약화해서는 안 된다.
- 관리 블록 밖의 사용자 잡과 전역 설정은 계속 읽기만 하고 원문 그대로 보존한다.
- 실패 시 원본은 바이트 단위로 그대로 남는다. 마커 손상·블록 뒤 사용자 줄 흡수 등 기존 실패 조건과 동작은 유지한다.
- 앱 시작·프로젝트 열기·자동 새로고침·화면 진입은 전역 파일을 쓰지 않는다. 파일 값을 읽어 폼에 채우는 것도, R2의 상태 구분도 읽기일 뿐이며 쓰기를 유발해서는 안 된다.
- SPEC-004 R3의 목록 밖 `model` 값 보존과 충돌하지 않는다. 파일에 목록 밖 모델명이 적혀 있으면 이 기획서의 규칙 아래에서도 그대로 남아야 한다.

## 확인 필요

사용자 결정이 필요한 항목이다. 승인 시 아래 제안대로 진행한다.

1. **토글을 껐다 켰을 때 편집값 복원 여부.** 하트비트에는 비활성 상태 필드가 없어서 "꺼짐"은 곧 "관리 블록에 없음"이다(SPEC-002 R5). 그래서 잡을 끄면 편집값을 적어 둘 곳이 사라지고, 다시 켜면 기본값에서 시작한다. 이것도 넓게 보면 "사용자 편집값이 사라지는" 경로다.

   제안: 이번 범위에서 다루지 않고, 사라진다는 사실을 확인 화면에서 밝히는 것(R4)까지만 한다. 근거는 비용이다. 꺼진 잡의 값을 기억하려면 관리 블록 밖에 앱이 소유하는 새 저장소가 필요하고, 그것은 이 기획서가 다루는 "한 파일 안에서 누구의 값이 이기는가"와 다른 종류의 변경이다. 관측된 사고도 켜져 있는 잡의 값이 바뀐 경우였다.

2. **기본값 재설정의 단위.** 잡 하나씩 되돌릴지, 연동의 잡 전체를 한 번에 되돌릴지의 선택이다.

   제안: 잡 단위로 한다. 관측된 사고가 잡 하나의 값이었고, 연동 전체 재설정은 잡 단위 재설정을 반복하면 얻을 수 있다. 반대로 전체 단위만 제공하면 잡 하나를 되돌리려는 사용자가 나머지 잡의 값까지 잃는다. 되돌리기 액션이 값을 잃게 만드는 것은 이 기획서의 취지와 정반대다.

## 기대효과

- 사용자가 편집한 주기·쿼터·모델이 앱의 어떤 쓰기 경로에서도 조용히 기본값으로 돌아가지 않는다. 관측된 사고(쿼터 조기 소진으로 작업이 실행되지 않음)의 원인 경로가 닫힌다.
- 보존이 화면 시딩이 아니라 쓰기 계약에 있으므로, 이후 카드가 늘어나거나 저장 경로가 추가되어도 같은 보장이 자동으로 따라온다. 연동마다 같은 실수를 다시 하지 않는다.
- 앱이 값을 모르는 상태(읽기 실패)와 값이 없는 상태(미설치)가 구분되어, 앱이 모르는 것을 아는 척 덮어쓰지 않는다.
- 확인 화면이 차이를 보여주므로, 의도하지 않은 변경을 쓰기 전에 눈으로 잡을 수 있다. 지금은 성공 표시만 남고 무엇이 바뀌었는지 사후에도 알 수 없다.
- 되돌리기가 명시적 액션이 되어, "초기화하고 싶다"는 정당한 요구가 저장의 부작용이 아니라 사용자가 고르는 동작으로 표현된다.

## 완료 조건

1. 관리 블록에 편집값(예: 개발자 `max_per: 8/24h`)이 적힌 상태에서, 그 필드를 화면에서 건드리지 않고 다른 필드만 바꿔 저장하면 편집값이 그대로 남는다. 검증: 저장 전후 관리 블록에서 해당 줄을 대조한다.
2. 화면이 잘못된 값을 들고 있어도 사용자가 지정하지 않은 필드는 파일 값이 유지된다. 검증: 요청에 기본값이 실려 들어오는 경우를 자동화 테스트로 만들고, 파일의 편집값이 살아남는지 확인한다.
3. 역할 잡과 dream 잡에 같은 보존 규칙이 적용된다. 검증: 두 잡 각각에 대해 1번과 같은 시나리오의 테스트가 존재하고 통과한다.
4. 관리 블록을 읽지 못한 상태에서 잡 설정 저장이 차단되고 사유가 표시된다. 검증: 읽기 실패를 재현한 상태에서 화면을 확인하고, 그 상태에서 파일이 쓰이지 않음을 확인한다.
5. 읽기 실패 상태와 잡이 없는 상태가 화면에서 서로 다르게 표시된다. 검증: 두 상태를 각각 재현하고 화면을 대조한다.
6. 화면이 읽은 뒤 관리 블록이 바뀐 상태에서 저장을 시도하면 그대로 덮어쓰지 않고 차이를 알린다. 검증: 화면을 열어 둔 채 파일을 손으로 바꾸고 저장을 시도해 동작과 파일 내용을 확인한다.
7. 사용자가 필드를 편집하는 중에 자동 새로고침이 그 입력값을 알림 없이 대체하지 않는다. 검증: 입력 중 상태에서 새로고침 주기를 여러 번 넘긴 뒤 입력값이 유지되는지 확인한다.
8. 확인 화면에 잡별 현재 값과 쓰게 될 값의 차이가 표시되고, 달라지는 것이 없으면 그 사실이 표시된다. 검증: 값을 바꾼 경우와 바꾸지 않은 경우 각각의 화면을 확인한다.
9. 관리 블록 안의 앱 소유 필드를 손으로 고친 상태에서 저장하면, 그 필드가 앱 값으로 되돌아간다는 사실이 확인 화면에 표시된다. 검증: `timeout`을 손으로 바꾼 뒤 확인 화면을 확인한다.
10. 잡을 끄고 저장할 때 그 잡의 편집값이 함께 사라진다는 사실이 확인 화면에 표시된다. 검증: 편집값이 있는 잡을 끄고 확인 화면을 확인한다.
11. 기본값으로 재설정 액션이 저장 액션과 구분되어 존재하고, 실행 전에 현재 값과 기본값의 차이를 보여준다. 검증: 편집값이 있는 잡에서 액션을 실행해 확인 화면과 결과 파일을 확인한다.
12. 기본값 재설정은 편집 가능 값만 되돌리고 잡의 활성·비활성 상태를 바꾸지 않는다. 검증: 일부 역할이 꺼진 상태에서 실행한 뒤 관리 블록의 잡 목록이 그대로인지 확인한다.
13. 같은 상태로 다시 저장하면 파일이 변하지 않는다. 검증: 두 번째 저장 전후 파일 해시가 같다.
14. 파일에 목록 밖의 `model` 값이 적혀 있으면 이 기획서의 저장 규칙 아래에서도 그대로 남는다. 검증: 정식 모델명을 적어 둔 상태에서 다른 필드만 바꿔 저장하고 값을 대조한다.
15. 앱 시작·프로젝트 열기·자동 새로고침·연동 화면 진입만으로는 `~/.claude/HEARTBEAT.md`가 변경되지 않는다. 검증: 저장 액션 없이 화면을 여러 번 거친 뒤 파일 수정 시각과 해시가 그대로인지 확인한다.
16. SPEC-002·SPEC-003·SPEC-004의 완료 조건에 대응하는 기존 자동화 테스트가 모두 통과한다. 삭제되거나 비활성화된 테스트가 없다. 검증: 테스트 실행 결과와 테스트 목록 변경분을 확인한다.
17. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다.
