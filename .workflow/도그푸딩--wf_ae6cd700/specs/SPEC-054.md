# 누락된 런타임 계약을 보완하고 blocked 작업을 안전하게 재개한다

## 결정권자 요약

에이전트 런타임 개발 작업 두 건이 필요한 계약을 앞선 작업에서 받지 못해 멈춰 있다.
방해 요소를 해결해도 현재 워크플로에는 멈춘 작업을 다시 개발 준비로 돌리는 정식 경로가 없다.
SPEC-054는 실행 중 프로세스의 수명 계약, 설치·서비스·업데이트 조회 계약과 사용자 재개 절차를
함께 추가하자고 제안한다. 사용자가 결정할 것은 이 보완 범위와 재개 권한을 사용자에게만 두는 원칙이다.
승인하면 먼저 누락 계약을 별도 작업으로 검증하고, 사용자가 해결 근거를 확인한 뒤 원래 두 작업을
감사 기록과 함께 다시 진행할 수 있다. 기존 예약 구현은 재사용하고 자동 재개는 하지 않는다.
Claude와 Codex SDK, Dream, 원격 실행과 원래 두 작업의 제품 구현 범위는 달라지지 않는다.
승인하지 않으면 현재 두 작업은 막힘 상태로 남고 그 뒤의 에이전트 기능 개발도 계속 기다린다.

## 기획 내용

SPEC-051은 기존 Heartbeat를 앱이 관리하는 범용 에이전트 런타임으로 고도화하기로 결정했다. 아키텍트는
예약, 상태 저장, provider, dispatcher, 패키징, 앱 설치와 실행 UX를 순서대로 나눴다. 구현을 진행하면서
TASK-S051-04와 TASK-S051-06이 각각 앞선 작업이 제공하지 않은 계약을 요구한다는 사실이 드러났다.

TASK-S051-04는 프로젝트별 병렬 배정과 반복 실행, 프로세스 복구를 맡는다. provider 작업은 Claude와
Codex를 같은 진단·실행·이벤트·종료 결과로 정규화했지만, 호출이 프로세스 종료까지 기다리는 한 번의
함수다. dispatcher가 시작 직후 실행 식별자와 프로세스 신원을 저장하거나, 런타임 재시작 뒤 살아 있는
프로세스를 다시 감시할 계약이 없다. 완료 결과만으로는 중복 실행 방지와 이벤트 이어 읽기를 구현할 수
없다.

TASK-S051-06은 앱이 런타임 설치와 업데이트를 관리하는 기능을 맡는다. 패키징 작업은 세 운영체제용
독립 실행형 배포물, 무결성 검사, stable launcher와 서비스 재시작 정책을 만들었다. 그러나 앱이 읽을
수 있는 계약은 프로젝트 하나의 설정과 상태에 집중돼 있다. 설치된 버전과 실제 실행 중 버전, 서비스
등록·생존 상태, 복구 가능 여부, 업데이트가 끊을 전체 작업과 프로젝트를 한 번에 조회하는 기계 계약이
없다. 앱이 내부 상태 파일이나 운영체제 서비스 파일을 직접 읽으면 SPEC-051이 정한 저장소 경계를
깨뜨린다.

두 작업에는 현재 활성 lease가 없다. 그래도 Developer 계약은 `blocked` 상태를 의도적으로 선언한
작업으로 보고 대상에서 제외한다. 실제 방해 요소가 나중에 해소돼도 현재 상태 계약에는 `blocked`에서
`todo`로 돌아가는 전이와 이력 종류가 없고, 앱에도 사용자가 그 전이를 기록하는 조작이 없다. 파일을
직접 고치면 누가 왜 재개했는지 감사 기록이 사라지고, 에이전트가 사용자 권한을 대신 행사하게 된다.

이 기획서는 세 공백을 하나의 복구 흐름으로 묶는다. 먼저 원래 작업과 분리된 보완 작업이 런타임 계약을
추가한다. 그 자동 검증 결과가 나온 뒤 사용자가 막힌 사유와 해결 근거를 확인하고 원래 작업을 개발 준비로
돌린다. 원래 TASK-S051-04와 TASK-S051-06은 자신이 승인받은 범위와 완료 조건을 그대로 이어서 수행한다.

### 확인한 현재 상태

1. TASK-S051-04와 TASK-S051-06은 `blocked`이고 활성 lease가 없다. Developer 계약은 blocked 작업이
   lease와 무관하게 자격 대상이 아니라고 명시한다.
2. TASK-S051-01의 예약 도구는 대상, lease, 결과 식별자 접두어와 역할 인계문을 이미 반환하고 자동
   검사를 통과했다. 이 예약 알고리즘은 보완 대상이 아니다.
3. provider 공통 인터페이스는 진단과 동기식 `run`을 제공한다. 실행 결과에는 정규화 이벤트와 종료
   상태가 있지만 dispatcher가 시작 직후 저장할 실행 핸들이 없다.
4. 런타임의 agent JSON 계약은 설정 검증·저장·조회와 프로젝트별 상태 조회를 제공한다. 실행 계획과
   제어 명령은 아직 예약된 이름이고, 기기 전체 설치·서비스·업데이트 상태 조회는 없다.
5. 패키징 작업은 독립 실행형 배포물과 세 운영체제 서비스 복구 정책을 구현했다. 서비스 사실을 앱에
   구조화해 전달하는 조회 계약은 구현 범위에 없었다.
6. 작업 history의 허용 kind는 여섯 개이며 blocked 재개를 나타내는 값이 없다. 앱 소유 QA 결정은
   완료와 재작업을 기록하지만, 막힘 해소는 QA 확인이나 수정 요청과 다른 사건이다.
7. SPEC-053은 막힌 사유와 재개 조건을 우측 패널에 표시하는 기획으로 현재 사용자 검토 중이다.
   이 기획서의 재개 조작은 그 표시가 승인되면 같은 패널을 재사용하고, 승인되지 않으면 현재 작업 상세의
   상태 패널에서 최소 확인 흐름을 제공한다.

### 현재 두 작업과 보완 계약의 관계

| 원래 작업 | 지금 없는 계약 | 보완 결과 | 사용자가 확인할 재개 근거 |
| --- | --- | --- | --- |
| TASK-S051-04 | 실행 중 provider의 안정적인 신원·이벤트 위치·취소·복구 | provider 실행 수명 계약과 가짜 CLI 자동 검사 | 재시작·PID 재사용·취소 시나리오에서 중복 실행과 자식 프로세스가 없음 |
| TASK-S051-06 | 설치·실행 버전, 서비스 상태, 복구와 업데이트 영향 조회 | 기기 단위 조회·업데이트 계획·적용 결과 JSON 계약 | 세 운영체제 검사에서 조회가 실제 서비스와 일치하고 실패 시 기존 버전이 유지됨 |

### 포함 범위

- Claude와 Codex 공통 provider의 실행 시작·감시·종료·취소·복구 수명 계약.
- dispatcher가 영속 상태에 저장할 실행 식별자, 프로세스 신원과 이벤트 이어 읽기 기준.
- 설치 버전, 실행 중 버전, API 호환성, 서비스 등록·생존, 복구 가능 여부를 반환하는 기기 단위 조회.
- 업데이트 전 전체 실행 영향과 적용 뒤 서비스 전환·복구 결과의 구조화된 계약.
- macOS, Linux, Windows에서 같은 의미를 갖는 자동 검사와 계약 문서.
- 사용자가 blocked 작업을 해결 근거와 함께 todo로 돌리는 앱 소유 전이와 감사 기록.
- 재개 뒤 기존 자격 판정을 다시 적용하고 현재 TASK-S051-04·06에 처음 사용하는 흐름.

### 제외 범위

- TASK-S051-04가 소유한 실제 프로젝트별 큐·공정성·반복 실행 구현. 이 기획서는 그 작업이 사용할
  수명 계약까지만 제공한다.
- TASK-S051-06이 소유한 앱 설치기·업데이트 UX 구현. 이 기획서는 앱이 사용할 조회와 적용 결과
  계약까지만 제공한다.
- TASK-S051-01의 예약 알고리즘과 lease 규칙 변경.
- 에이전트나 Heartbeat가 blocked 작업을 자동 재개하는 기능.
- 모든 기존 blocked 작업을 일괄 변환하거나 소급해서 막힌 사유를 작성하는 마이그레이션.
- QA 확인·수정 요청을 막힘 재개 용도로 재사용하는 것.
- Claude Agent SDK, Codex SDK, Dream, 원격·클라우드 실행.

## 요구사항 명세

### R1. provider 시작과 종료 대기를 분리한다

- Claude와 Codex 공통 계약은 provider 프로세스를 시작해 실행 핸들을 반환하는 단계와, 그 실행의
  이벤트·종료를 감시하는 단계를 분리한다.
- 시작 성공은 프로세스가 생성됐다는 뜻까지만 말한다. 역할 작업 성공과 같은 결과로 취급하지 않는다.
- 진단 실패, 실행 파일 시작 실패, 시작 뒤 감시 실패를 서로 다른 단계로 구분한다.
- 기존 provider별 명령 구성, stdin prompt, 구조화 이벤트 정규화, 인증 진단과 과금 경로 경고의 의미는
  달라지지 않는다.
- 첫 실행을 실제 dispatcher에 연결하기 전에도 가짜 CLI로 이 계약을 독립 검증할 수 있다.

### R2. 실행 핸들이 재시작 뒤 같은 프로세스를 확인할 근거를 제공한다

- 실행 핸들은 런타임 실행 식별자, provider, 프로젝트, 역할, 대상, PID, 시작 시각과 PID 재사용을
  구분할 동등한 프로세스 신원을 제공한다.
- 실행별 이벤트 저장 위치와 마지막으로 영속화한 읽기 위치를 연결할 수 있다. 이벤트 위치는 다른
  프로젝트나 실행과 충돌하지 않는다.
- prompt 원문, 인증 토큰, API 키와 전체 환경은 실행 핸들·SQLite·일반 로그에 저장하지 않는다.
- 런타임 재시작 뒤 PID만 같고 신원이 다르면 실행 중으로 채택하지 않는다. 확정할 수 없으면
  `recovery_required`로 분류할 근거를 반환한다.
- 살아 있는 같은 프로세스로 확인되면 새 provider를 시작하지 않고 기존 이벤트 위치부터 감시를
  이어 갈 수 있다.

### R3. 취소와 종료가 프로세스 트리와 이벤트를 일관되게 닫는다

- 취소는 실행 핸들을 대상으로 하고 provider별 구현 세부 정보를 호출자에게 요구하지 않는다.
- 자식 프로세스까지 종료됐음을 확인한 뒤에만 취소 완료로 표시한다.
- 프로세스 종료, 이벤트 마감, lease 정리 중 일부만 성공하면 전체 성공으로 표시하지 않는다. 어느
  단계가 남았는지 구조화해 반환한다.
- 정상 종료, 일반 실패, 사용 제한, 시간 초과, 사용자 취소와 계약 밖 출력을 기존 공통 결과로 연결한다.
- 종료 결과는 실행 식별자와 예약의 대상·lease가 같은 작업을 가리키는지 검증할 수 있다.

### R4. 기존 예약 응답을 dispatcher가 소비할 계약으로 고정한다

- TASK-S051-01이 만든 예약 성공 응답의 대상, lease, 결과 식별자 접두어, 역할 인계문을 보완 계약이
  문서화하고 변경 없이 사용한다.
- 예약 실패·경합·마이그레이션 잠금에서는 provider 시작 함수를 호출하지 않는다.
- 예약 성공과 실행 핸들은 같은 실행 식별자 아래 영속화할 수 있어야 한다. 어느 하나만 남은 부분 실패는
  복구 단계가 구분된다.
- 이 요구사항은 후보 선택과 예약 알고리즘을 다시 구현하지 않는다. 실제 반복 배정은 TASK-S051-04에
  남는다.

### R5. 기기 단위 런타임과 서비스 상태를 읽기 전용으로 조회한다

- 버전화된 JSON 조회는 설치된 런타임 버전, 실제 실행 중 런타임 버전, 지원 API 주 버전과 앱 호환
  판정에 필요한 값을 반환한다.
- 서비스 등록 여부, 실행 여부, 운영체제가 아는 서비스 식별자, 마지막 확인 시각과 복구 가능 여부를
  반환한다.
- stale PID나 마지막 시작 기록을 살아 있는 서비스로 단정하지 않는다. 플랫폼 어댑터가 실제로 확인한
  사실과 확인하지 못한 값을 구분한다.
- 조회만으로 파일, 서비스, SQLite, 설정과 실행 상태를 변경하지 않는다.
- 등록 없음, 실행 파일 없음, 여러 등록물로 대상이 모호함, 권한 부족, 지원하지 않는 플랫폼·버전을
  서로 다른 결과로 구분한다.

### R6. 업데이트 계획이 영향 범위를 먼저 반환한다

- 업데이트 적용 전 읽기 전용 계획 요청이 현재 실행 중 작업 수와 영향받는 프로젝트 식별자를 반환한다.
- prompt, 도구 출력과 인증 정보는 영향 응답에 포함하지 않는다.
- 계획은 대상 버전, manifest 검증 상태, 서비스 재기동·재등록 필요 여부와 실패 시 복구 가능성을
  보여 준다.
- 사용자가 확인한 계획과 적용 시점의 상태가 달라졌으면 오래된 확인으로 적용하지 않는다. 새 영향
  범위를 다시 확인하게 한다.
- 실행 중 작업이 없더라도 계획과 적용은 분리한다. 무확인 자동 업데이트를 만들지 않는다.

### R7. 업데이트 적용과 복구 결과를 단계별로 반환한다

- 적용은 검증, 새 버전 설치, stable launcher 전환, 서비스 재기동 또는 재등록, 실행 버전 확인의
  결과를 단계별로 반환한다.
- 검증이나 설치가 실패하면 기존 launcher와 서비스가 바뀌지 않는다.
- launcher 전환 뒤 서비스 단계가 실패하면 현재 실행 가능한 버전과 사용자가 해야 할 복구 행동을
  명시한다. 부분 성공을 전체 성공으로 표시하지 않는다.
- 세 운영체제는 같은 의미의 상태·단계·오류를 반환하고 플랫폼 고유 이름은 진단 세부 정보로 제한한다.
- 앱은 이 계약만 사용하고 Heartbeat 내부 파일, SQLite, plist, systemd unit, Task Scheduler 출력을
  직접 파싱하지 않는다.

### R8. blocked 재개는 사용자만 실행한다

- 현재 상태가 blocked인 개발 작업 상세에 사용자가 실행하는 `개발 준비로 돌리기` 조작을 제공한다.
- 조작 전에 현재 막힌 사유, 재개 조건, 작업 갱신 시각과 사용자가 입력할 해결 근거를 보여 준다.
- SPEC-053이 승인·구현돼 있으면 그 우측 패널을 재사용한다. 그렇지 않으면 결정권자 요약을 폴백으로
  보여 주고, 둘 다 없으면 사유를 추측하지 않는다.
- 해결 근거는 비어 있을 수 없다. 자동 검사 결과나 관련 보완 작업을 적을 수 있지만 앱이 사실 여부를
  지어내지 않는다.
- 에이전트, Heartbeat와 일반 Markdown 편집은 사용자 재개를 기록할 수 없다.

### R9. 재개 전이가 상태·이력·감사 기록을 원자적으로 남긴다

- 재개는 task 상태를 blocked에서 todo로 바꾸고 `resumed` history 항목을 같은 편집에 추가한다.
- 앱은 task 식별자, 재개 시각, 사용자 입력 해결 근거와 재개 직전 문서 갱신 시각을 연결한 app-owned
  감사 기록을 남긴다.
- 감사 기록의 작성자는 사용자이며 에이전트가 같은 값을 쓸 수 없다. 기존 specification 결정과 QA
  결정의 의미를 재사용하거나 바꾸지 않는다.
- 기존 `## 막힌 사유` 절과 과거 개발 보고서는 보존한다. 현재 상태가 todo가 된 뒤에는 마지막 차단
  기록으로 읽힌다.
- history의 기존 여섯 kind와 기존 문서는 그대로 읽힌다. 새 resumed를 모르는 옛 앱은 문서를
  손상시키지 않고 안전하게 업그레이드 안내로 유도한다.

### R10. stale 화면과 동시 변경이 재개를 덮어쓰지 않는다

- 재개 기록 직전에 task가 여전히 blocked이고 사용자가 확인한 갱신 시각과 같은지 다시 확인한다.
- 문서가 바뀌었거나 이미 재개됐거나 migration lock이 있으면 아무 파일도 쓰지 않고 최신 상태를
  다시 보여 준다.
- 대상 작업에 유효한 lease가 있으면 재개하지 않는다. 다른 세션의 lease를 지우거나 수정하지 않는다.
- task 본문과 app-owned 감사 기록 중 하나만 쓰인 부분 성공을 정상 결과로 남기지 않는다. 원자적 저장
  또는 명시적 복구 결과가 필요하다.
- 같은 요청을 반복해도 history와 감사 기록이 중복되지 않는다.

### R11. 재개 뒤 기존 자격 판정을 다시 적용한다

- todo 전이는 작업을 즉시 실행한다는 뜻이 아니다. 선행 작업, source decision, migration lock, 활성
  lease와 scope 겹침을 기존 Developer 판정으로 다시 계산한다.
- 판정 결과가 아직 미충족이면 상태는 todo로 남되 화면은 현재 시작할 수 없는 이유를 보여 준다.
- 에이전트가 claim한 뒤에는 기존 규칙대로 in_progress history를 추가한다. resumed는 작업 시작을
  대신하지 않는다.
- 재개 이력과 활동 화면은 QA 수정 요청과 다른 이름으로 표시한다.

### R12. 현재 두 blocked 작업을 첫 적용 대상으로 검증한다

- provider 수명 계약의 보완 작업이 QA 대기 또는 완료이고 자동 검사가 통과한 뒤, 사용자가
  TASK-S051-04를 todo로 재개할 수 있다.
- 설치·서비스·업데이트 조회 계약의 보완 작업이 QA 대기 또는 완료이고 자동 검사가 통과한 뒤,
  사용자가 TASK-S051-06을 todo로 재개할 수 있다.
- 앱은 보완 작업 상태를 참고 정보로 보여 줄 수 있지만 자동으로 원래 작업 상태를 바꾸지 않는다.
- 재개된 원래 작업은 기존 문서의 범위·완료 조건을 그대로 따른다. 이번 보완 작업이 그 구현을 완료한
  것으로 표시하지 않는다.

## 확인 필요

없다. 사용자가 대화에서 다음 방향으로 진행하도록 요청했다.

- 선점이 없는 두 blocked 작업을 억지로 수정하지 않고 누락 계약을 먼저 보완한다.
- 현재 Developer 계약을 우회하지 않고 사용자 재개 전이를 정식으로 만든다.
- 기존 예약 구현을 재사용하고 provider 수명 계약과 기기 단위 런타임 조회 계약만 추가한다.
- 보완 검증 뒤 원래 작업을 다시 진행한다.

사용자가 승인하면 아키텍트는 provider 수명, 설치·서비스·업데이트 조회, blocked 재개 계약과 UI를 서로
검증 가능한 작업으로 나눈다. SPEC-053도 승인됐다면 우측 패널 파일 겹침과 작업 순서를 함께 조정한다.

## 기대효과

- 누락된 저수준 계약을 원래 대형 작업 안에서 임의로 설계하지 않고 독립 자동 검사로 먼저 고정한다.
- Heartbeat 재시작과 업데이트에서 중복 실행, 잘못된 서비스 판정, 기존 버전 손상 위험을 줄인다.
- 실제 방해 요소가 해결된 blocked 작업이 영구 정지하지 않고 사용자 감사 기록을 남기며 돌아온다.
- 에이전트 자동화가 사용자 재개 권한을 침범하지 않고 기존 approval·QA 의미도 유지한다.
- 현재 두 blocked 작업과 그 뒤의 SPEC-051 작업 체인이 다시 진행될 수 있다.

## 완료 조건

1. 가짜 Claude·Codex provider를 시작하면 종료 전에 실행 식별자, PID, 시작 시각·동등 신원과 이벤트
   위치를 가진 실행 핸들을 얻는다.
2. 런타임을 강제 종료한 뒤 같은 프로세스를 복구하면 새 provider가 시작되지 않고 마지막 영속 이벤트
   위치부터 감시가 이어진다.
3. PID가 같지만 시작 신원이 다른 경우 기존 실행으로 채택하지 않고 recovery_required가 된다.
4. 실행 핸들로 취소한 뒤 자식 프로세스가 남지 않고, 일부 정리 실패는 단계가 표시된 부분 실패로 남는다.
5. 실행 핸들·SQLite·일반 로그에서 prompt와 가짜 인증 비밀값을 검색해도 나오지 않는다.
6. 예약 실패, 경합, 마이그레이션 잠금 시나리오에서 provider 시작 호출이 0회다.
7. 기기 단위 조회가 설치 버전, 실행 버전, API 호환 정보, 서비스 등록·실행, 식별자, 확인 시각과 복구
   가능 여부를 한 JSON 응답으로 반환한다.
8. 등록 없음, stale PID, 여러 등록물, 실행 파일 없음, 권한 부족을 서로 다른 결과로 구분하고 조회 전후
   파일·서비스·SQLite가 바뀌지 않는다.
9. 업데이트 계획이 실행 중 전체 작업 수와 프로젝트 목록을 반환하고 prompt와 도구 출력은 포함하지 않는다.
10. 계획 확인 뒤 실행 상태가 바뀌면 적용이 중단되고 새 영향 확인을 요구한다.
11. manifest 검증 실패와 설치 실패에서 기존 launcher와 서비스가 유지되며, 서비스 단계 부분 실패는
    단계별 결과와 복구 행동을 반환한다.
12. macOS, Linux, Windows의 가짜 또는 격리 서비스 검사에서 같은 계약 필드와 의미를 반환한다.
13. blocked 작업을 사용자 해결 근거와 함께 재개하면 task가 todo가 되고 resumed history와 app-owned
    감사 기록이 한 번씩 남으며 막힌 사유 절은 보존된다.
14. 재개 시 문서 갱신 충돌, migration lock, 활성 lease, 이미 재개된 상태에서는 아무 기록도 추가되지 않는다.
15. 재개 뒤 선행 미충족 또는 scope 겹침이 있으면 Developer 자격은 계속 거절되고 화면에 해당 이유가 나온다.
16. 기존 task history, specification 결정, QA 결정과 활동 이력이 변경 전과 같은 의미로 읽힌다.
17. 보완 작업 검증 뒤 TASK-S051-04와 TASK-S051-06을 각각 재개하는 종단 시나리오가 통과한다.
18. 기존 Heartbeat 일반 잡, Dream, 기존 provider 종료 결과와 workflow-labs 역할 판정 회귀 검사가 통과한다.
