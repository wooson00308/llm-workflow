# 연동 잡 model 필드를 지원 모델 선택 UI로 전환

## 기획 내용

연동 관리 UI에서 잡의 `model`은 지금 자유 입력 텍스트 필드다. 검증은 프론트와 백엔드 양쪽에서 "공백 없는 한 줄 값"만 본다. 그래서 `opus`도 통과하고 `opuss`도, `claude-opus-4`도 통과한다. 사용자는 모델 별칭을 외워서 오타 없이 적어야 하고, 틀렸다는 사실은 저장 시점에 알 수 없다.

이 값이 틀렸을 때 실제로 무슨 일이 일어나는지 확인했다. 하트비트는 `model` 값을 `claude --model`에 그대로 넘긴다. 값이 잘못되면 클로드는 요청을 보내기 전에 종료하고, 하트비트는 그 잡을 `failure`로 기록한다. 여기서 두 가지가 나쁘다.

첫째, 실행 쿼터는 이미 차감된 뒤다. 하트비트는 클로드를 띄운 직후, 종료 코드를 보기 전에 쿼터를 깎는다. 오타 하나가 매 주기마다 쿼터를 태우면서 아무 일도 하지 않는다. 기획자 잡의 기본값이 `4/24h`이므로 하루치가 조용히 소진되고, 사용자는 "잡을 걸어 놨는데 아무것도 안 됐다"만 본다.

둘째, 앱 화면에 남는 것은 "실패" 배지 하나뿐이다. 사유는 표시되지 않는다. 앱은 하트비트 상태 파일만 읽고 그 파일에는 종료 코드 수준의 결과만 있다. 모델명이 틀렸다는 정보는 어디에도 도달하지 않는다.

사후에 사유를 보여주는 쪽으로 고치려면 앱이 하트비트 로그를 읽고 해석해야 하는데, 그건 SPEC-002가 제외 범위로 못 박은 관측 기능 확장이다. 애초에 틀린 값을 입력할 수 없게 만드는 쪽이 싸고 확실하다. 이 기획서는 그 예방을 다룬다.

그러면 "지원 모델 목록"이 어디서 오는가가 핵심 질문이 된다. 목록은 시간이 지나면 낡는다. 그리고 앱이 그 목록을 외부에서 조회하는 경로는 실질적으로 없다.

- 클로드 CLI에는 모델 목록을 기계가 읽을 형태로 내보내는 명령이 없다. `--model`은 잘못된 값을 받으면 대화형 선택기를 안내할 뿐이다.
- 앱이 CLI를 실행해서 알아내는 방식은 두 가지 이유로 막힌다. 지금까지 앱은 연동 정보를 전부 파일 읽기로만 얻었고 외부 명령을 실행한 적이 한 번도 없다. 그리고 GUI로 띄운 앱의 PATH에 그 실행 파일이 없을 수 있다는 문제는 SPEC-003 확인 필요 1번이 `dream-prep`에 대해 이미 겪은 것과 같은 문제다.

그래서 목록은 앱이 소유하는 값으로 두고, 갱신 압력 자체를 낮추는 쪽으로 설계한다. `claude --model`은 별칭(`opus`)과 정식 모델명(`claude-opus-5`)을 모두 받는다. 별칭은 "그 계열의 최신"을 가리키므로 모델 세대가 바뀌어도 유효하지만, 정식 모델명은 출시마다 낡는다. 목록을 별칭 중심으로 구성하면 앱이 목록을 자주 갱신하지 않아도 정확한 상태로 남는다.

그리고 목록만 남기지 않는다. 정식 모델명을 지정해야 하거나, 새 별칭이 나왔는데 앱이 아직 모르는 시점이 반드시 온다. 그때 사용자가 앱 릴리스를 기다려야 한다면 이 변경은 개선이 아니라 퇴행이다. 직접 입력 경로를 남긴다.

### 대상 도구 확인 사실

아래는 실제 설치본에서 확인한 사실이고, 이 기획서는 그 위에 서 있다.

- 하트비트(`claude-heartbeat` 0.5.1)는 잡의 `model` 값을 `claude --model <값>`으로 그대로 넘긴다. 값이 비어 있으면 `--model`을 붙이지 않고 CLI 기본 모델을 쓴다.
- 하트비트는 클로드 프로세스를 띄운 직후, 종료 코드를 확인하기 전에 쿼터를 차감한다. 소스 주석이 그 의도를 밝히고 있다: 실패해도 토큰은 이미 소비된 것으로 본다.
- `claude --model definitely-not-a-model -p "1"`은 종료 코드 1로 끝나고 `There's an issue with the selected model (...)`을 출력한다. 요청은 나가지 않는다.
- 하트비트는 종료 코드가 0이 아니면 상태 파일에 `failure`로 기록한다. 앱은 그 값을 "실패" 배지로 표시하며, 사유를 담는 경로는 없다.
- `claude --help`는 `--model`이 별칭 또는 정식 모델명을 받는다고 기술한다. 설치된 CLI 바이너리에서 확인되는 별칭은 `fable`, `haiku`, `opus`, `sonnet` 네 개다.
- CLI 하위 명령에 모델 목록 조회 명령은 없다.
- 현재 앱의 `model` 검증은 프론트 `/^\S+$/`, 백엔드 `is_model`(비어 있지 않고 공백 없음)이다. 두 규칙은 같은 값을 통과시킨다.
- 현재 `~/.claude/HEARTBEAT.md`의 관리 블록에 기록된 역할 잡 3종의 `model`은 모두 `opus`다.
- 관리 UI에 존재하는 잡은 현재 역할 잡 3종뿐이다. dream 잡 UI는 SPEC-003이 다루며 아직 구현되지 않았다.

### 포함 범위

- 연동 관리 UI의 `model` 편집을 선택 UI로 전환
- 앱이 소유하는 지원 모델 목록의 정의와 갱신 정책
- 목록에 없는 값을 위한 직접 입력 경로
- 파일에 이미 적혀 있는 목록 밖 값의 보존

### 제외 범위

- `interval`·`max_per` 필드의 UI 변경 — 아이디어는 `model`만 지목했고, 두 필드는 자유 형식 값이라 목록화 대상이 아니다
- 백엔드 `model` 검증 규칙 변경 — 선택 UI는 예방이고 백엔드 검증은 방어선이다. 방어선을 좁히면 손으로 편집한 파일을 앱이 저장하지 못하게 되는 회귀가 생긴다
- 빈 `model`(= CLI 기본 모델 사용) 지원 — 아래 "확인 필요" 2번 참조
- 앱이 모델 목록을 외부 명령이나 네트워크로 조회하는 기능
- 모델별 비용·속도·컨텍스트 한도 등 부가 정보 표시
- 잘못된 모델로 실패한 잡의 사유를 하트비트 로그에서 읽어 보여주는 기능 — SPEC-002가 제외한 관측 기능 확장이다
- `.workflow/rules/*.md` 역할 계약 본문 변경, 마이그레이션 스키마 변경

## 요구사항 명세

### R1. 모델 선택 UI

- 연동 관리 UI에 존재하는 모든 잡의 `model` 필드를 선택 UI로 전환한다. 현재 시점의 대상은 역할 잡 3종이고, dream 잡이 추가되면 같은 규칙이 적용된다(R5).
- 사용자는 목록에서 값을 고르는 것만으로 유효한 `model`을 지정할 수 있어야 한다. 기본 상태에서 타이핑이 필요해서는 안 된다.
- 목록 항목에는 값 자체(`opus`)가 보여야 한다. 파일에 기록되는 값과 화면에 보이는 값이 달라지면, 사용자가 `HEARTBEAT.md`를 직접 열었을 때 대조할 수 없다. 설명 문구를 덧붙이는 것은 무방하나 값 자체가 가려져서는 안 된다.
- 선택만으로는 파일이 바뀌지 않는다. 기존 편집 필드와 마찬가지로 저장 액션과 쓰기 전 확인 절차(SPEC-002 R6)를 그대로 거친다.
- 기존 필드 라벨 규약을 유지한다. 각 필드는 잡 이름과 필드 이름을 합친 접근성 라벨(예: "개발자 모델")로 식별 가능해야 한다. 이 라벨은 현재 테스트가 필드를 찾는 기준이기도 하다.

### R2. 지원 모델 목록의 출처와 갱신

- 목록은 앱이 소유하는 값이다. 앱은 목록을 얻기 위해 외부 명령을 실행하거나 네트워크를 호출하지 않는다.
- 목록은 앱 안 한 곳에만 정의한다. 같은 목록이 두 곳에 있으면 시간이 지나 갈라진다.
- 목록은 별칭 중심으로 구성한다. 근거는 갱신 주기다. 별칭은 모델 세대가 바뀌어도 유효하지만 정식 모델명은 출시마다 낡는다.
- 확인된 별칭 `opus`, `sonnet`, `haiku`, `fable`을 목록의 기본 구성으로 한다. 구현 시점에 `claude --help`의 `--model` 설명으로 이 집합을 다시 확인한다.
- 갱신은 앱 릴리스로 한다. 목록이 정의된 지점에 갱신 방법과 확인처(`claude --help`의 `--model` 항목)를 주석으로 남긴다.
- 목록이 낡아도 사용자가 막히지 않아야 한다는 조건은 R3가 담당한다. 즉 이 목록의 정확성은 편의의 문제이지 가용성의 문제가 아니어야 한다.

### R3. 목록 밖 값의 입력과 보존

- 목록에 없는 값을 지정할 수 있는 직접 입력 경로를 제공한다. 선택 UI 안에 그 경로가 있어야 하고, 고르면 값을 직접 적을 수 있어야 한다.
- 직접 입력 값의 검증 규칙은 현행과 같다: 비어 있지 않고 공백이 없는 한 줄. 규칙 위반 시 동작도 현행과 같다. 파일에 쓰지 않고 입력 위치에서 사유를 표시한다(SPEC-002 R5).
- 직접 입력 경로 옆에 위험을 밝힌다: 앱은 모델명이 실제로 존재하는지 확인하지 못하며, 값이 틀리면 잡은 매 주기 실패하면서 실행 쿼터만 소모한다.
- 파일에 이미 기록된 `model`이 목록에 없으면, 그 값을 잃지 않아야 한다. 이 경우 해당 필드는 직접 입력 상태로 열리고 파일의 값이 그대로 채워진다. 사용자가 저장하지 않는 한 파일의 값은 바뀌지 않는다.
- 이 규칙은 두 가지 실제 상황을 함께 처리한다. 사용자가 `HEARTBEAT.md`를 손으로 편집해 정식 모델명을 적어 둔 경우, 그리고 앱의 목록이 낡아 유효한 신규 별칭을 모르는 경우다. 어느 쪽이든 앱이 사용자의 값을 임의로 목록 안의 값으로 바꾸어서는 안 된다.

### R4. 기존 쓰기 계약 보존

- 이 변경은 UI 입력 방식만 바꾼다. `~/.claude/HEARTBEAT.md`에 기록되는 `- model:` 줄의 형식과 값은 달라지지 않는다.
- 같은 모델 값으로 저장하면 파일이 변하지 않는다(멱등). SPEC-002 R2·R6의 보장은 그대로 성립한다.
- 앱 시작·프로젝트 열기·자동 새로고침·설정 화면 진입은 여전히 전역 파일을 쓰지 않는다. 목록에 없는 값을 화면에 열어 보여주는 것도 읽기일 뿐이며, 그것이 파일 쓰기를 유발해서는 안 된다.
- 백엔드 검증은 그대로 둔다. 프론트에서 값을 고르게 하는 것과 무관하게, 백엔드는 잘못된 값을 계속 거부한다.

### R5. dream 잡 적용과 순서 의존성

- 아이디어의 대상에는 dream 잡의 `model` 필드도 포함된다. dream 잡 관리 UI는 SPEC-003의 산출물이며 이 기획서 작성 시점에 아직 구현되지 않았다.
- 두 기획서의 구현 순서와 무관하게 성립하도록, 이 기획서의 요구사항과 완료 조건은 "연동 관리 UI에 존재하는 모든 잡의 `model` 필드"를 대상으로 한다. 특정 잡 목록을 고정하지 않는다.
- SPEC-003이 먼저 구현되면 dream 잡도 이 규칙의 대상이다. 이 기획서가 먼저 구현되면 SPEC-003이 추가하는 dream 잡의 `model` 필드는 새로 만든 선택 UI를 쓴다.
- 어느 경우에도 모델 목록과 직접 입력 규칙은 잡마다 따로 정의되지 않는다. R2의 "한 곳에만 정의한다"가 여기에도 적용된다.

## 확인 필요

사용자 결정이 필요한 항목이다. 승인 시 아래 제안대로 진행한다.

1. **목록의 구성 범위.** 별칭만 넣을지, 정식 모델명(`claude-opus-5` 등)도 함께 넣을지의 선택이다. 정식 모델명을 넣으면 특정 세대를 고정하고 싶은 사용자가 고르기 편해지지만, 모델이 출시될 때마다 목록이 낡고 앱 릴리스로만 갱신되므로 "목록에 있는 값이 최신이 아닌" 상태가 상시화된다.

   제안: 별칭 네 개(`opus`, `sonnet`, `haiku`, `fable`)만 목록에 넣고, 정식 모델명은 직접 입력으로 지정한다. 세대 고정은 소수의 요구이고, 그 소수는 정확한 모델명을 이미 알고 있는 사용자다. 반면 목록이 낡는 비용은 모든 사용자가 지불한다.

2. **빈 `model`(CLI 기본 모델) 지원 여부.** 하트비트는 `model`이 비어 있으면 `--model`을 붙이지 않고 클로드 CLI의 기본 모델을 쓴다. 그런데 앱은 빈 값을 거부하므로, 지금 앱으로는 "CLI 기본 모델에 맡긴다"를 표현할 수 없다. 선택 UI를 만드는 김에 "CLI 기본값" 항목을 넣는 것이 자연스러워 보일 수 있다.

   제안: 이번 범위에서 다루지 않는다. 아이디어가 요청한 것은 오타 방지이고, 빈 값 지원은 그와 별개로 백엔드 검증 규칙과 저장 계약을 함께 바꿔야 하는 변경이다. 지금 끼워 넣으면 이 기획서의 완료 조건이 "입력 방식 전환"에서 "값의 의미 확장"으로 번진다. 필요하다면 별도 아이디어로 다룬다.

## 기대효과

- 모델명 오타로 잡이 매 주기 실패하면서 실행 쿼터만 태우는 실패 경로가 기본 사용 경로에서 사라진다. 사용자는 아무것도 외우지 않고 값을 고른다.
- 목록을 별칭 중심으로 두어, 모델이 새로 출시될 때마다 앱을 갱신해야 하는 부담이 생기지 않는다. 목록의 정확성이 기능의 가용성을 좌우하지 않는다.
- 직접 입력 경로가 남아 있어, 앱이 모르는 모델을 쓰려는 사용자가 앱 릴리스를 기다리지 않는다. 손으로 편집한 파일의 값도 앱을 열었다고 해서 바뀌지 않는다.
- 연동이 늘어나도 모델 선택 규칙은 한 곳에서 정의되므로, dream 잡을 비롯한 이후 잡이 같은 동작을 자동으로 얻는다.

## 완료 조건

1. 연동 관리 UI에 존재하는 모든 잡의 `model` 필드가 선택 UI로 표시되고, 목록에서 값을 고르는 것만으로 유효한 모델을 지정할 수 있다. 검증: 각 잡의 `model` 필드를 화면에서 확인하고, 타이핑 없이 값을 바꿔 저장까지 마친다.
2. 목록에 `opus`, `sonnet`, `haiku`, `fable`이 값 그대로 노출된다. 검증: 화면에서 네 항목을 확인하고, 각 값이 화면 표기와 동일하게 파일에 기록되는지 대조한다.
3. 목록은 앱 안 한 곳에만 정의되어 있고, 그 지점에 갱신 방법과 확인처가 주석으로 남아 있다. 검증: 코드에서 정의 지점이 하나임을 확인한다.
4. 목록에 없는 모델을 직접 입력으로 지정하고 저장할 수 있다. 검증: 정식 모델명 하나를 직접 입력으로 저장한 뒤 `HEARTBEAT.md`에 그 값이 그대로 기록되는지 확인한다.
5. 직접 입력 값이 검증 규칙(비어 있지 않고 공백 없음)을 위반하면 파일에 쓰이지 않고 입력 위치에 사유가 표시된다. 검증: 공백이 들어간 값과 빈 값 각각에 대한 테스트가 존재하고 통과한다.
6. 파일에 목록 밖의 `model` 값이 기록된 상태에서 설정 화면을 열면, 해당 필드가 직접 입력 상태로 그 값을 그대로 보여준다. 검증: `HEARTBEAT.md`의 관리 블록에서 `model`을 목록 밖 값으로 손수 바꾼 뒤 화면을 확인한다.
7. 6번 상황에서 아무것도 저장하지 않고 설정 화면을 열어 두었다가 나가면 `HEARTBEAT.md`가 변경되지 않는다. 검증: 화면 진입 전후 파일 해시를 비교하고, 자동 새로고침을 여러 번 거친 뒤에도 같은지 확인한다.
8. 직접 입력 경로 옆에 앱이 모델명을 검증하지 못한다는 점과 잘못된 값의 결과(매 주기 실패, 쿼터 소모)가 표시된다. 검증: 화면 문구를 확인한다.
9. 같은 모델 값으로 다시 저장하면 파일이 변하지 않는다. 검증: 두 번째 저장 전후 파일 해시가 같다.
10. SPEC-002 완료 조건 1~12에 대응하는 기존 자동화 테스트가 모두 통과한다. 삭제되거나 비활성화된 테스트가 없다. 검증: 테스트 실행 결과와 테스트 목록 변경분을 확인한다.
11. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다.
