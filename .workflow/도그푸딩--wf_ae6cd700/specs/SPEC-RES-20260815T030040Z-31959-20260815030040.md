# 격리 작업 사본 기반 개발 세션과 통합 절차

## 결정권자 요약

### 제안

개발 에이전트가 태스크별 격리 작업 사본에서 구현하고, 같은 개발자 역할이 공유 작업 공간에 안전하게 통합한 뒤에만 검증 완료로 기록하게 한다.

### 현재

사용자의 직접 작업과 자동 개발 세션이 한 작업 공간을 함께 써서 서로의 미완성 변경이 검사에 섞이며, 기존 선점과 파일 범위 선언은 직접 작업을 감지하지 못한다.

### 변경 후

직접 작업은 공유 작업 공간에서 계속되고 자동 개발은 별도 사본에서 병행되며, 충돌은 통합 시점에 드러나고 통합 결과를 다시 검사한 작업만 사용자 품질 확인으로 넘어간다.

### 비용과 위험

임시 사본과 빌드 자료에 저장 공간이 들고 공유 작업 공간이 정리될 때까지 통합이 기다릴 수 있다. 직접 작업과 기존 승인 경계는 건드리지 않으며, 통합 전 사본은 폐기할 수 있고 통합 뒤 변경은 일반 이력으로 되돌릴 수 있다.

## 기획 내용

사용자는 워크플로우를 거치지 않고 LLM과 직접 코드를 고칠 수 있어야 한다. 자동 개발 파이프라인도 그
동안 멈추지 않아야 한다. 현재 두 실행은 같은 Git 작업 공간을 사용한다. 직접 작업은 문서 lease와
`scope_files` 계약 밖에 있으므로 자동 세션이 그 존재나 범위를 판정할 수 없다. 이 상태에서는 파일이
겹치지 않아도 한쪽의 미완성 시그니처 변경이나 설정 변경이 다른 쪽 검사에 섞인다. 통과한 검사가 담당
태스크만의 결과라는 보장이 없다.

이 기획서는 개발 역할 세션의 코드 작업 공간을 태스크별 Git worktree와 전용 브랜치로 분리한다. 기획자와
아키텍트는 지금처럼 워크플로우 문서만 다룬다. 사용자 직접 작업도 현재 공유 작업 공간을 계속 사용한다.
개발 에이전트의 변경은 격리 사본에서 검사하고, 명시적인 통합 단계에서만 공유 작업 공간의 기준 브랜치에
반영한다.

격리 사본에서 검사를 통과했다는 사실과 사용자가 확인할 판에 반영됐다는 사실은 구분해 기록한다. 다만
태스크의 `verified` 의미는 바꾸지 않는다. `verified`는 격리 검사, 공유 기준 반영, 통합 결과 검사와
개발 보고서가 모두 끝났다는 뜻으로 유지한다. 격리 검사만 끝난 작업은 통합 대기 또는 통합 충돌 상태이며
`verified`가 아니다. 따라서 현재 그룹 QA 관문과 자동 완료 규칙은 더 약해지지 않는다.

### 선택한 운영 모델

1. 런타임은 개발 태스크 예약에 성공한 뒤 provider를 시작하기 전에 격리 사본을 준비한다. 세션이 임의로
   사본 경로와 브랜치 이름을 만들지 않는다.
2. 개발자 역할 세션은 격리 사본에서 제품 코드와 자동 검사를 다룬다. lease, 태스크 상태, 보고서 같은
   워크플로우 제어 문서는 공유 프로젝트의 정본에 기록해 앱과 다른 역할이 즉시 읽을 수 있게 한다.
3. 통합은 새 역할이나 아키텍트 역할이 아니라 개발자 역할의 마지막 책임이다. 최초 구현 세션이 이어서
   수행하거나, 저장된 격리 결과를 같은 태스크의 후속 개발자 세션이 인수할 수 있다.
4. 개발자는 격리 결과를 현재 공유 기준에 맞춘 뒤 통합하고 전체 영향 검사를 다시 수행한다. 통합과 재검사가
   성공해야 태스크를 `verified`로 전환한다.
5. 공유 작업 공간에 사용자의 미커밋 변경이 있으면 자동으로 stash, commit, reset, checkout 또는 삭제하지
   않는다. 통합은 기다리고 자동 개발은 다른 격리 사본에서 계속할 수 있다.

이 선택은 현재 세 역할의 권한 경계를 보존한다. 아키텍트는 계속 작업 정의와 범위만 책임지고 제품 코드를
병합하지 않는다. 별도 통합 역할과 새로운 승인 관문도 만들지 않는다. 통합 충돌은 구현의 연장선이므로
해당 태스크의 개발자 역할이 승인된 범위 안에서 해결한다.

### 개발 태스크의 수명 주기

1. 런타임이 기존 자격 판정과 예약 도구로 개발 태스크와 lease를 확보한다.
2. 런타임이 공유 기준의 최신 커밋에서 태스크 전용 사본과 브랜치를 준비하고, 제어 문서 정본과 코드 작업
   사본의 위치를 구분해 세션에 전달한다.
3. 세션은 lease 소유를 확인하고 공유 정본의 태스크를 `in_progress`로 전환한 뒤 격리 사본에서 구현한다.
4. 세션은 격리 사본에서 태스크 검증을 수행하고, 변경 커밋과 검사 결과를 재개 가능한 통합 후보로 기록한다.
5. 공유 작업 공간이 통합 가능한 상태이면 같은 세션이 통합을 시도한다. 그렇지 않으면 제품 변경을 건드리지
   않고 통합 대기로 남긴다.
6. 공유 기준이 달라졌으면 격리 브랜치를 최신 기준에 맞추고 태스크 범위 안의 충돌을 해결한 뒤 격리 검사를
   다시 수행한다.
7. 통합 뒤 공유 기준에서 태스크의 필수 검사와 그룹 영향 검사를 수행한다. 모두 통과하면 보고서를 완성하고
   태스크를 `verified`로 전환한다.
8. 성공한 사본은 정리한다. 통합 대기나 충돌은 변경 커밋과 진단 기록을 보존하되 물리 사본과 재생성 가능한
   빌드 산출물은 저장 공간 정책에 따라 회수할 수 있다.

### 포함 범위

- 개발 역할의 자동·수동 배정 모두에 적용되는 태스크별 Git worktree와 브랜치.
- 예약, 격리 사본 준비, provider 시작, lease 반납 사이의 실패 안전 계약.
- 공유 워크플로우 정본과 격리 코드 사본의 쓰기 경계.
- 격리 검사, 통합 대기, 통합 충돌, 통합 검사와 `verified` 전이의 의미.
- 개발자 역할의 통합 책임과 충돌 해결 범위.
- 직접 작업을 덮어쓰지 않는 통합 대기 정책.
- 기존 `scope_files`와 `depends_on` 판정의 유지와 목적 재정의.
- 그룹 QA와 자동 그룹 완료가 통합된 기준만 보도록 하는 관문.
- 사본, 브랜치와 빌드 산출물의 회수, 저장 공간 상한과 복구.
- 런타임 재시작과 세션 중단 뒤 같은 태스크 사본을 이어받는 기록.
- 앱에서 격리 작업, 통합 대기와 충돌 사유를 구분해 보여 주는 상태.

### 제외 범위

- 사용자 직접 작업에 우선권 lease나 `scope_files` 입력을 요구하는 기능.
- 직접 작업 때문에 새 개발 세션을 전부 멈추고 진행 중 태스크 하나만 끝내는 우선권 관문. 원본 아이디어가
  별도 아이디어로 미룬 범위다.
- 기획자와 아키텍트 세션의 작업 사본 격리.
- Git이 아닌 버전 관리 시스템과 Git 저장소가 아닌 프로젝트 지원.
- 사용자의 미커밋 변경을 자동 stash, commit, reset, 삭제하거나 다른 브랜치로 옮기는 기능.
- 충돌하는 사용자 의도와 승인 기획 중 어느 쪽이 맞는지 에이전트가 추측해 결정하는 기능.
- 원격 저장소 push, pull request 생성, 릴리스 브랜치 병합과 배포.
- 클라우드 또는 원격 실행 환경의 작업 사본 관리.
- 기존 완료 작업을 새 격리 이력으로 소급 변환하는 마이그레이션.

## 요구사항 명세

### R1. 워크플로우 제어면과 코드 작업면을 분리한다

- lease, 마이그레이션 잠금, 태스크 상태, 작업 그룹, 결정과 역할 보고서의 정본은 등록된 공유 프로젝트에
  남는다.
- 개발 세션의 제품 코드 편집, 빌드와 자동 검사는 태스크 전용 격리 사본에서만 수행한다.
- 격리 브랜치의 제품 변경 커밋에는 태스크 상태 전이, lease와 역할 보고서를 섞지 않는다. 워크플로우 문서가
  제품 변경과 함께 뒤늦게 통합돼 앱 화면을 덮어쓰지 않아야 한다.
- 세션은 두 위치를 명시적으로 전달받는다. 어느 위치가 정본인지 추측하거나 현재 디렉터리 하나를 두 용도로
  사용하지 않는다.
- 공유 정본 쓰기는 기존 역할 권한과 태스크 lease를 그대로 따른다. 격리 도입이 결정 파일과 앱 소유 상태의
  쓰기 권한을 넓히지 않는다.

### R2. 런타임이 예약 뒤, provider 시작 전에 사본을 준비한다

- 개발 태스크 예약 성공 뒤 런타임이 격리 사본과 태스크 브랜치를 준비한다. provider 세션은 준비가 완전히
  성공한 뒤에만 시작한다.
- 준비 결과는 태스크, lease, 공유 기준 커밋, 브랜치, 격리 사본, 제어 문서 정본과 실행 식별자를 한 실행에
  연결한다.
- 디렉터리 생성, 브랜치 생성 또는 기준 확인이 실패하면 provider를 시작하지 않는다. 만들어진 일부 자원을
  정리하고 자신의 lease를 반납하며 실패 단계를 기록한다.
- 자동 배정과 사용자가 대상을 고르는 수동 배정은 같은 준비 경로를 사용한다. 한 경로만 공유 작업 공간에서
  실행하는 우회는 허용하지 않는다.
- 런타임 재시작 뒤에도 준비 완료와 provider 미시작, provider 실행 중, 격리 검증 완료와 통합 대기를 서로
  구분할 수 있어야 한다.

### R3. 재현 가능한 기준에서 태스크 사본을 만든다

- 새 격리 사본은 예약 시점에 확인한 공유 기준 브랜치의 커밋에서 시작한다. 공유 작업 공간의 미커밋 파일은
  복사하거나 검사 입력으로 사용하지 않는다.
- 동일 태스크와 동일 실행의 사본·브랜치 이름은 충돌하지 않고 재시도에서 원래 기록을 찾을 수 있어야 한다.
- 다른 태스크가 같은 브랜치를 재사용하지 않는다. 하나의 태스크 재시도도 이전 실행을 덮어쓰지 않고 계보를
  잇는다.
- Git 저장소가 아니거나 기준 커밋을 확정할 수 없으면 개발 세션을 공유 작업 공간에서 대신 시작하지 않는다.
  실행 전 요구 조건을 사용자에게 보여 주고 lease를 안전하게 반납한다.
- 하위 모듈, 대용량 파일 저장소와 로컬 의존성이 필요한 프로젝트는 준비 결과에서 충족 여부를 확인한다.
  준비되지 않은 의존성을 무시한 채 검사를 시작하지 않는다.

### R4. 격리 검사는 통합 후보를 만들 뿐 완료를 선언하지 않는다

- 개발 세션은 태스크 완료 조건에 적힌 검사를 격리 사본에서 수행한다. 공유 작업 공간의 제품 변경과 빌드
  산출물이 검사 입력에 섞이지 않았음을 확인할 수 있어야 한다.
- 격리 검사가 통과하면 변경 커밋, 시작 기준, 검사 명령과 결과, 변경 파일 목록을 내구성 있는 통합 후보로
  기록한다.
- 격리 검사 통과만으로 태스크를 `verified`로 전환하거나 그룹 QA를 열지 않는다.
- 격리 검사 실패는 현재 개발 실패 절차를 따른다. 통합 단계로 넘어가거나 실패한 검사를 공유 기준에서 다시
  돌려 성공으로 대체하지 않는다.
- 격리 환경에서만 통과하고 통합 환경에서 실패한 검사는 서로 다른 결과로 보고한다. 어느 한쪽을 숨기지 않는다.

### R5. 통합은 개발자 역할이 수행하고 그 뒤에 완료를 기록한다

- 통합 주체는 해당 태스크를 맡은 개발자 역할이다. 아키텍트와 기획자에게 제품 코드 쓰기 권한을 추가하지
  않고 새 사용자 승인 관문도 만들지 않는다.
- 최초 구현 세션이 통합까지 수행할 수 있다. 세션이 끝났으면 같은 태스크를 선점한 후속 개발자 세션이 저장된
  통합 후보와 보고서를 먼저 읽고 이어받는다.
- 통합 직전에 공유 기준과 격리 후보의 시작 기준을 다시 비교한다. 기준이 달라졌으면 최신 커밋에 맞춘 뒤
  검사를 다시 수행한다.
- 통합 성공 뒤 공유 기준에서 태스크 필수 검사와 영향을 받는 통합 검사를 실행한다. 통합 커밋, 검사 결과,
  최종 변경 파일과 남은 위험을 보고서에 기록한 뒤에만 `verified`로 전환한다.
- 통합과 상태 전이 중 일부만 성공하면 전체 성공으로 표시하지 않는다. 다시 실행해 중복 통합하지 않도록
  어느 단계까지 끝났는지 기록한다.

### R6. 사용자의 직접 작업은 자동으로 변경하지 않는다

- 공유 작업 공간에 추적 파일의 미커밋 변경, stage된 변경 또는 기준 전환 중 상태가 있으면 자동 통합을
  시작하지 않는다.
- 런타임과 개발 세션은 직접 작업을 stash, commit, reset, checkout, 삭제하거나 소유권을 추측하지 않는다.
- 공유 작업 공간이 통합 가능해질 때까지 해당 태스크는 통합 대기로 남는다. 대기 중에도 다른 태스크의 격리
  구현과 검증은 기존 병렬 상한 안에서 계속할 수 있다.
- 공유 기준이 새 커밋으로 전진하면 개발자는 격리 후보를 그 기준에 맞춘다. 충돌이 태스크의 승인 범위와
  `scope_files` 안에서 기계적으로 해결 가능하면 해결하고 격리 검사를 다시 수행한다.
- 충돌 해결이 범위 밖 파일을 요구하거나 사용자 직접 작업의 의도를 선택해야 하면 자동으로 한쪽을 택하지
  않는다. 구체적인 충돌, 필요한 판단과 재개 조건을 막힌 사유와 보고서에 기록한다.
- 충돌 없는 통합도 사용자의 미커밋 파일과 인덱스 내용이 통합 전후 동일함을 보장해야 한다.

### R7. 통합 대기와 중단을 재개할 수 있게 기록한다

- 실행 기록은 최소한 공유 기준, 격리 변경 커밋, 브랜치와 사본 식별, 격리 검사 결과, 통합 단계, 마지막
  오류와 갱신 시각을 연결한다.
- 통합 대기는 일반 개발 후보와 구분한다. 공유 작업 공간이 여전히 통합 불가인 동안 동일 provider 세션을
  반복 기동하지 않는다.
- 런타임은 공유 작업 공간이 통합 가능해지거나 기준 커밋이 바뀐 사실을 감지하면 현재 자격과 lease를 다시
  확인한 뒤 통합 재개 후보로 올린다.
- 중단된 세션의 격리 사본과 변경 커밋은 곧바로 신뢰하지 않는다. 후속 세션은 변경분과 검사 결과를 읽고
  유지, 재작성과 폐기의 판단을 역할 보고서에 남긴다.
- 사본 디렉터리를 회수했더라도 변경 커밋과 메타데이터가 남아 있으면 같은 기준에서 사본을 재생성할 수 있어야
  한다. 재생성할 수 없는 부분 상태는 복구 필요로 표시한다.

### R8. 기존 범위와 선행 판정을 유지한다

- `scope_files` 겹침 판정은 개발 태스크 사이에서 계속 시작 전 안전 조건으로 사용한다. 격리 사본이 있다는
  이유로 겹치는 자동 태스크를 동시에 실행하지 않는다.
- `depends_on`은 구현과 통합 순서를 모두 제한한다. 선행 작업이 `verified`가 아니면 후속 작업을 오래된
  기준에서 시작하지 않는다.
- `scope_files`는 물리 작업 공간 보호뿐 아니라 통합 충돌과 의미 충돌을 줄이는 선언으로 설명을 갱신한다.
- 직접 작업에는 선언을 강제하지 않는다. 그 빈칸은 격리와 통합 충돌 감지가 담당하며, 직접 작업을 추측한
  범위로 기존 판정을 오염시키지 않는다.
- 누락되거나 잘못된 `scope_files`를 개발자가 자동 확장할 권한은 생기지 않는다. 현재 작업 정의 오류 복구
  경로를 사용한다.

### R9. 그룹 QA는 통합된 공유 기준만 확인한다

- 현재 그룹 revision의 모든 태스크가 격리 검사만 끝난 상태에서는 사용자 QA 또는 자동 그룹 완료를 열지
  않는다.
- 모든 태스크가 공유 기준에 통합되고 각 태스크가 `verified`일 때만 그룹 검증을 시작한다.
- 그룹 검증 직전에 QA 대상 기준 커밋과 포함된 태스크의 통합 커밋을 고정한다. 검증 중 기준이 바뀌면 이전
  결과로 완료하지 않고 다시 판정한다.
- 사용자 모드 QA 안내는 사용자가 실제로 열어 확인할 공유 기준을 가리킨다. 격리 사본 경로나 개발자 전용
  명령을 사용자에게 요구하지 않는다.
- 자동 모드 그룹도 통합 기준에서 전체 검증을 통과해야 완료된다. 개별 격리 검사 합계로 대체하지 않는다.

### R10. 임시 저장 공간을 기기 단위로 제한한다

- 동시에 물리적으로 존재할 수 있는 개발 사본 수는 기기와 프로젝트의 개발자 병렬 상한 중 더 작은 값보다
  많을 수 없다. 실행 슬롯이 없는 태스크를 미리 복제하지 않는다.
- 런타임이 관리하는 모든 격리 사본과 전용 빌드 자료의 기본 기기 상한은 20 GiB다. 새 실행으로 상한을
  넘길 가능성이 있거나 데이터 볼륨의 여유가 10 GiB 아래로 내려가면 provider 시작 전에 정리 또는 대기로
  전환한다.
- 정리는 재생성 가능한 빌드 산출물, 성공·취소된 사본, 오래된 실패 사본 순으로 수행한다. 통합되지 않은
  변경 커밋, 역할 보고서와 사용자 직접 작업은 삭제하지 않는다.
- 성공한 통합의 물리 사본은 보고서와 최종 상태가 저장된 뒤 회수한다. 통합 대기와 충돌 사본도 변경 커밋이
  보존되고 재생성 가능하면 물리 디렉터리를 회수할 수 있다.
- 공용 다운로드 캐시나 빌드 캐시를 사용하더라도 태스크별 검사 결과가 다른 사본의 미완성 산출물 때문에
  성공해서는 안 된다. 통합 기준 재검사가 최종 보증이다.
- 상한 도달과 정리 실패를 전체 자동화 성공으로 표시하지 않는다. 회수한 크기, 남은 사용량, 필요한 사용자
  조치를 민감한 경로 없이 보여 준다.

### R11. 앱이 구현, 통합과 대기를 구분해 보여 준다

- 실행 상태에서 사본 준비, 격리 구현, 격리 검증 완료, 통합 대기, 충돌 해결, 통합 검증과 복구 필요를
  구분한다.
- 통합 대기는 공유 작업 공간에 사용자 변경이 있다는 사실까지만 말한다. 파일 내용과 직접 작업 prompt를
  수집하거나 표시하지 않는다.
- 사용자는 어느 태스크가 어느 기준에서 검사됐고 왜 아직 `verified`가 아닌지 확인할 수 있어야 한다.
- 프로젝트 일시 정지는 새 사본 준비와 새 통합 시도를 멈추지만 실행 중 세션을 자동 종료하거나 사용자
  직접 작업을 변경하지 않는다.
- 취소는 격리 provider 프로세스, lease, 물리 사본과 보존할 변경 커밋을 단계별로 처리한다. 일부 실패를
  전체 성공으로 표시하지 않는다.

### R12. 비밀과 로컬 환경을 격리 기록에 복제하지 않는다

- provider prompt 원문, 인증 토큰, API 키와 전체 환경 변수는 브랜치 이름, 커밋 메시지, 사본 메타데이터,
  일반 로그와 역할 보고서에 저장하지 않는다.
- 격리 사본 준비는 프로젝트가 이미 허용한 로컬 의존성만 사용한다. 사용자 홈 전체, 다른 프로젝트의
  미추적 파일과 직접 작업 내용을 사본에 복제하지 않는다.
- 브랜치와 사본 이름은 태스크와 실행을 구분할 수 있지만 비밀 값과 prompt 내용을 포함하지 않는다.
- 사본 정리와 통합 명령은 정확한 관리 대상만 다룬다. 등록되지 않은 worktree, 사용자 브랜치와 직접 작업
  파일을 넓은 경로 삭제로 처리하지 않는다.

### R13. 도입 시점의 실행을 섞지 않는다

- 기능 활성화 전에 이미 공유 작업 공간에서 실행 중인 개발 세션은 중간에 사본으로 옮기지 않는다. 해당
  세션을 종료 또는 회수한 뒤 새 개발 예약부터 격리 계약을 적용한다.
- 활성화 뒤 개발 역할의 자동·수동 예약은 모두 격리 준비를 요구한다. 준비 실패 때 옛 공유 작업 방식으로
  후퇴하지 않는다.
- 기존 `verified` 태스크와 그룹 QA 기록은 그대로 유효하다. 새 격리 단계나 브랜치 정보를 소급해서 만들지
  않는다.
- 기획자·아키텍트 자격, 사용자 기획 승인, 그룹 QA 결정과 기존 lease 소유 의미는 달라지지 않는다.
- 새 상태를 모르는 이전 런타임은 격리 기능을 부분 실행하지 않고 호환성 오류와 업데이트 안내를 반환한다.

## 기대효과

- 사용자는 공유 작업 공간에서 LLM과 직접 작업하면서도 자동 개발 세션을 별도 사본에서 계속 돌릴 수 있다.
- 자동 검사는 다른 세션의 미완성 변경이 섞이지 않은 태스크 결과를 측정한다.
- 직접 작업과 자동 작업의 충돌이 조용한 검사 오염이 아니라 기준 비교와 통합 충돌로 드러난다.
- `verified`와 그룹 QA가 공유 기준 반영 및 재검사까지 포함하므로 기존 완료 의미가 약해지지 않는다.
- 아키텍트 권한과 세 역할 모델을 유지하면서 충돌 해결 책임이 해당 구현을 이해하는 개발자에게 남는다.
- `scope_files`는 격리 뒤에도 선행 계획과 의미 충돌 억제 수단으로 값을 유지한다.
- 임시 사본과 빌드 산출물에 기기 단위 상한과 자동 회수 순서가 생겨 빌드 캐시가 무한히 커지는 일을 막는다.
- 중단 뒤에도 변경 커밋과 단계 기록으로 이어서 작업할 수 있어 격리가 새로운 유실 지점이 되지 않는다.

## 완료 조건

1. 공유 작업 공간에 미커밋 직접 작업을 둔 상태에서 두 개발 태스크를 시작하면 각 세션이 서로 다른 격리
   사본에서 실행되고, 어느 검사에도 공유 공간의 미커밋 내용이 섞이지 않는다.
2. 개발 예약 성공 뒤 사본 준비가 실패하면 provider가 시작되지 않고, 부분 생성 자원과 해당 lease가
   안전하게 정리되며 실패 단계가 남는다.
3. 자동 배정과 수동 배정이 같은 격리 준비 경로를 사용하고 공유 작업 공간 실행으로 후퇴하지 않는다.
4. 세션이 쓰는 태스크 상태와 보고서는 공유 정본에서 즉시 보이지만 제품 변경 커밋에는 섞이지 않는다.
5. 격리 검사가 통과해도 태스크는 `verified`가 아니며, 통합과 공유 기준 재검사가 성공한 뒤에만 한 번
   `verified`로 전환된다.
6. 공유 작업 공간이 깨끗하고 기준이 바뀌지 않은 경우 개발자 역할이 격리 결과를 통합하고 필수 검사를
   통과해 작업을 완료한다.
7. 공유 기준이 전진했지만 충돌이 없는 경우 최신 기준에 맞춘 격리 검사와 통합 검사가 모두 수행된다.
8. 승인 범위 안에서 충돌이 발생하면 개발자 역할이 격리 사본에서 해결하고 검사를 다시 수행한다.
9. 충돌 해결이 범위 밖 변경이나 사용자 의도 선택을 요구하면 자동 통합하지 않고 구체적인 막힌 사유와
   재개 조건을 남긴다.
10. 공유 작업 공간에 미커밋 변경이 있으면 통합은 기다리며, 그 변경의 내용, stage 상태와 파일 해시는 통합
    시도 전후 동일하다.
11. 통합 대기 중인 태스크 때문에 다른 비겹침 개발 태스크의 격리 구현이 멈추지 않으며, 같은 대기 태스크를
    provider가 반복 실행하지 않는다.
12. 런타임을 사본 준비 뒤, 구현 중, 격리 검사 뒤와 통합 중에 각각 종료해도 중복 브랜치·중복 통합·중복
    상태 전이 없이 복구하거나 복구 필요 상태로 남는다.
13. `scope_files`가 겹치거나 `depends_on`이 충족되지 않은 자동 태스크는 격리 사본이 있어도 기존처럼
    동시에 시작되지 않는다.
14. 현재 revision의 모든 태스크가 통합된 기준에서 `verified`가 되기 전에는 사용자 QA와 자동 그룹 완료가
    열리지 않는다.
15. 그룹 QA가 고정한 기준 커밋이 검사 중 바뀌면 이전 결과로 그룹을 완료하지 않는다.
16. 관리 사본과 빌드 자료가 20 GiB 상한을 넘기 전에 정리 또는 대기로 전환되고, 데이터 볼륨 여유가
    10 GiB 아래인 상태에서 새 provider가 시작되지 않는다.
17. 저장 공간 정리가 통합되지 않은 변경 커밋, 보고서, 사용자 브랜치와 직접 작업 파일을 삭제하지 않는다.
18. 성공·취소·통합 대기 사본을 물리적으로 회수한 뒤에도 보존된 변경 커밋에서 필요한 사본을 재생성할 수
    있다.
19. Git 저장소가 아니거나 기준 커밋이 없는 프로젝트에서는 공유 작업 방식으로 후퇴하지 않고 요구 조건을
    안내한다.
20. prompt 원문, 인증 값과 전체 환경이 브랜치, 커밋 메시지, 사본 기록, 일반 로그와 보고서에 남지 않는다.
