# 실행 도구 사용 한도에 걸린 동안 배정을 멈추고 대기 상태를 보여준다

## 결정권자 요약

### 제안

실행 도구의 사용 한도에 걸려 끝난 실행이 확인되면 그 도구를 쓰는 역할의 자동 배정을 재개 시각까지
멈추고, 그동안 화면이 한도 대기 중이라는 사실과 다시 시작할 시각을 보여준다.

### 현재

한도에 걸려 세션이 시작하자마자 끝나도 배정은 그 사실을 모른다. 반복 실행 역할은 기본 5분 주기로,
예약 실행 역할은 20분에서 30분 주기로 다음 차례가 오면 또 새 세션을 시작하고, 그 세션도 같은 이유로
곧바로 끝난다. 남는 것은 실패 기록뿐이다. 실행 환경은 실패 메시지에서 한도 문구를 알아보고 한도
도달이라는 구분까지 만들어 두지만 그 구분은 실행 기록으로 나오지 않고 일반 실패에 묻힌다. 사용자가
앱에서 한도 상태를 본 적이 없는 것은 대응이 잘 되어서가 아니라 그 상태를 보여주는 자리가 없기
때문이다.

### 변경 후

한도 도달로 끝난 실행이 확인되면 그 실행 도구를 쓰는 역할의 자동 배정이 재개 시각까지 멈춘다. 해제
시각이 함께 오면 그 시각까지 쉬고, 오지 않으면 정해진 대기 시간만큼 쉰 뒤 한 번 다시 시도한다. 다른
실행 도구를 쓰는 역할은 평소대로 배정된다. 그동안 실행 화면은 어느 도구가 한도 대기 중이고 언제 다시
시작하는지를 사용자 언어로 보여준다. 사용자는 실패 기록이 쌓이는 것을 지켜보는 대신 지금 왜 멈춰
있고 언제 풀리는지를 바로 알게 되며, 한도가 풀리면 아무것도 하지 않아도 배정이 저절로 돌아온다.

### 비용과 위험

한도 도달을 가리는 구분값과 해제 예정 시각은 실행 환경이 만들어 실어 보내야 한다. 그래서 이 문서는
그 값이 왔을 때의 보류와 표시까지를 정하고, 값을 만들어 싣는 일과 클로드의 최신 한도 문구를 인식
대상에 넣는 일은 실행 환경 쪽 후속으로 넘긴다. 값이 오기 전까지 앱 동작은 지금과 같다. 보류 판정이
틀리면 멀쩡한 역할이 쉬게 되므로 보류는 한도 도달로 분류된 종료에서만 걸고, 사용자의 직접 배정은
막지 않는다. 이 변경은 자동 배정 설정값을 바꾸지 않고 이미 실행 중인 세션도 중단하지 않으며, 되돌리면
지금의 반복 배정 동작으로 그대로 돌아온다.

## 기획 내용

### 문제

역할마다 어떤 실행 도구를 쓸지 따로 고르고, 자동 배정은 역할별 주기로 돌아가며 빈 자리에 세션을
시작한다. 이 주기는 실행 도구가 지금 쓸 수 있는 상태인지를 시작 전에 확인하지만, 확인하는 것은 도구가
설치되어 있고 로그인되어 있는지까지다. 계정의 사용 한도가 소진되었는지는 확인 대상이 아니다.

그래서 한도에 걸린 뒤의 동작은 이렇게 된다. 배정이 세션을 시작하고, 실행 도구가 한도 메시지를 내며
즉시 끝나고, 실행 기록에 실패가 하나 남는다. 다음 주기가 오면 같은 일이 처음부터 반복된다. 반복 실행
모드의 기본 판정 간격은 5분이고 예약 실행 잡의 기본 주기는 개발자 20분, 기획자와 아키텍트 30분이므로,
한도가 몇 시간 이어지면 그 사이에 실패 기록만 수십 개가 쌓인다. 이 반복은 한도가 풀리는 시점을 앞당기지
못하고, 오히려 재시도 자체가 한도를 다시 건드리는 호출이 된다.

사용자 입장에서 더 나쁜 것은 이 상황이 화면에서 한도 문제로 보이지 않는다는 점이다. 자동 배정 상태는
역할마다 상태값과 다음 판정 시각을 이미 싣고 있지만, 화면이 문장으로 올리는 것은 주의 상태 하나뿐이고
그 문장은 종료 사유 문자열을 사람 말로 바꾼 것이다. 지금의 변환 규칙은 사유 문자열에 한도라는 낱말이
들어 있으면 동시 실행 자리가 모두 사용 중이라는 문장으로 바꾼다. 계정의 사용 한도와 동시 실행 자리
소진은 사용자가 해야 할 일이 전혀 다른 두 가지인데 같은 문장으로 표시된다.

SPEC-051 R11은 실행 한도 소진, 실행 도구 인증과 사용 제한, 워크플로 대상 없음을 서로 다른 대기 사유로
표시하라고 이미 요구했다. 대상 없음과 자리 소진은 그 요구대로 구분되어 있으나, 사용 한도는 아직 자기
문장을 갖지 못했다.

### 한도 사실이 어디에서 오는가

실행 환경에는 실행 도구의 실패 메시지에서 한도 문구를 알아보는 판정이 이미 있고, 코덱스 어댑터와 클로드
어댑터가 둘 다 그 판정을 쓴다. 판정에 걸리면 그 실행의 상태는 일반 실패와 구분되는 한도 도달로 정해진다.
문제는 그다음이다. 이 구분은 프로세스 감시 결과 안에만 남고, 앱이 읽는 실행 기록으로 나갈 때는 실패
하나로 합쳐진다. 그래서 앱에는 구분할 근거가 도착하지 않는다.

이 문서는 그 근거가 도착한다는 전제 위에서 앱이 할 일을 정한다. 앱이 실패 메시지의 문구를 직접 다시
읽어 한도인지 판정하지는 않는다. 같은 판정을 두 곳에서 하면 실행 도구가 문구를 바꿀 때마다 두 곳이
어긋나고, 문구를 알아보는 일은 이미 실행 환경이 하고 있다. 아이디어가 부수 확인으로 적어 둔 클로드의
최신 한도 문구 미인식도 같은 이유로 실행 환경 쪽 후속이다.

### 보류가 걸려야 하는 자리

세션을 자동으로 시작하는 경로는 지금 둘이다. 실행 환경의 반복 배정과, 앱이 사용자 기기에 설치하는 예약
잡이다. 두 경로 모두 세션을 시작하기 전에 앱이 설치한 조건 검사를 거치며, 그 검사가 대상이 없다고 답하면
어느 쪽도 세션을 시작하지 않는다. SPEC-065가 정한 단독 배정도 이 자리에서 다른 세션이 도는 동안 배정을
미루는 방식으로 동작한다. 즉 앱이 배정을 붙잡을 수 있는 공통 지점은 이미 있고, 이 문서가 더하는 것은
그 지점이 한도 대기라는 사실도 알게 하는 일이다.

보류의 단위는 실행 도구다. 사용 한도는 계정과 실행 도구에 걸리므로 같은 도구를 쓰는 다른 역할도 똑같이
실패하고, 다른 도구를 쓰는 역할은 아무 영향이 없다. 역할 단위로 걸면 같은 도구를 쓰는 옆 역할이 계속
실패를 쌓고, 프로젝트 전체를 멈추면 멀쩡한 도구를 쓰는 역할까지 세운다.

### 해제 시각을 모를 때

실행 도구가 언제 풀리는지 알려 주는 경우와 알려 주지 않는 경우가 모두 있다. 해제 예정 시각이 오면 그
시각까지 쉬는 것이 정확하다. 오지 않을 때 앱이 시각을 추정하면 틀린 시각을 사용자에게 확정된 사실처럼
보여주게 되므로, 추정하는 대신 정해진 대기 시간만큼 쉬고 한 번 다시 시도하는 방식으로 처리한다. 다시
시도한 실행이 또 한도로 끝나면 같은 대기가 한 번 더 걸린다. 이 방식은 해제 시각을 몰라도 스스로
교정되고, 최악의 경우에도 대기 시간마다 실행 하나씩만 소모한다.

## 요구사항 명세

### 한도 사실을 받는 자리

- R-01. 실행 기록의 종료 사유에 한도 도달이라는 구분이 실려 오면 앱은 그 구분을 다른 실패와 구분해
  보관하고, 어느 실행 도구의 한도인지 함께 보관한다.
- R-02. 해제 예정 시각이 함께 오면 그대로 보관한다. 오지 않으면 비워 두며, 앱이 시각을 추정해 채우지
  않는다.
- R-03. 앱은 실패 메시지 원문을 다시 읽어 한도 여부를 판정하지 않는다. 판정의 근거는 실행 환경이 실은
  구분값 하나다.
- R-04. 구분값을 싣지 않는 실행 환경에서는 지금과 똑같이 동작한다. 값이 없다는 이유로 실행이 실패하거나
  화면이 멈추지 않는다.

### 배정 보류

- R-05. 한도 도달로 분류된 종료가 확인되면 그 실행 도구를 쓰는 역할의 자동 배정을 재개 시각까지 보류한다.
- R-06. 재개 시각은 해제 예정 시각이 있으면 그 시각이고, 없으면 이 문서가 정한 대기 시간이 지난 시각이다.
- R-07. 보류는 실행 도구 단위로 건다. 다른 실행 도구를 쓰는 역할의 배정은 영향받지 않는다.
- R-08. 보류는 같은 기기에서 그 실행 도구를 쓰는 모든 프로젝트에 적용된다. 한도는 계정에 걸리므로 프로젝트를
  바꿔도 같은 결과가 나온다.
- R-09. 보류는 자동으로 세션을 시작하는 모든 경로에 적용된다. 한쪽 경로만 멈추고 다른 경로가 계속 시작하면
  이 요구는 충족되지 않는다.
- R-10. 재개 시각이 지나면 보류가 저절로 풀리고 배정이 평소대로 돌아온다. 사용자가 해제 조작을 하지 않아도
  된다.
- R-11. 보류가 풀린 뒤 처음 시작한 실행이 다시 한도로 끝나면 같은 규칙으로 보류를 다시 건다.
- R-12. 보류는 이미 실행 중인 세션을 중단하지 않는다. 시작하지 않는 것만이 보류의 동작이다.
- R-13. 보류는 자동 배정 켜짐 여부, 역할별 주기, 병렬 인원 같은 사용자 설정값을 바꾸지 않는다.
- R-14. 사용자의 직접 배정은 보류가 막지 않는다. 다만 시작 조건 확인 단계에서 지금 그 실행 도구가 한도
  대기 중이라는 사실을 알린다.

### 표시

- R-15. 한도 대기 중인 실행 도구가 있으면 실행 화면에서 그 사실을 알 수 있다. 상세를 열어야만 알 수 있는
  방식은 이 요구를 충족하지 않는다.
- R-16. 표시에는 어느 실행 도구가 대기 중인지와 언제 다시 시작하는지가 담긴다.
- R-17. 재개 시각을 모르면 시각을 지어내지 않고, 다시 시도할 때까지 남은 대기를 사용자가 알 수 있게
  표시한다.
- R-18. 한도 대기는 동시 실행 자리 소진, 배정할 대상 없음, 실행 도구 로그인 필요와 각각 다른 문장으로
  표시한다. 사유 문자열에 한도라는 낱말이 들어 있다는 이유로 자리 소진 문장이 나오지 않는다.
- R-19. 한도 도달로 끝난 실행의 상세에서 종료 사유가 사용 한도 도달로 표시된다.
- R-20. 표시 문구는 비개발자가 읽고 무엇을 기다리는지 알 수 있는 말로 쓴다. 내부 상태 이름이나 파일 경로를
  그대로 보여주지 않는다.

### 보호

- R-21. 이 기능은 기획서, 작업 그룹, 개발 작업, 결정, 보고서 문서를 쓰거나 상태를 바꾸지 않는다.
- R-22. 이 기능은 선점을 대신 반납하지 않고, 실행을 자동으로 취소하거나 다시 시작하지 않는다.
- R-23. 보류 상태를 읽지 못하면 보류를 걸지 않고 지금과 같이 배정한다. 확인 실패를 보류 사유로 삼지 않는다.

## 선택한 기본값

이 절의 값은 이 문서가 정한 기본값이다. 다른 값이 맞다고 판단하면 수정 요청으로 돌려보내면 된다.

- 해제 예정 시각을 모를 때의 대기 시간은 1시간으로 한다. 시간당 한도가 풀리는 가장 짧은 주기가 1시간이고,
  5분마다 실패를 쌓는 지금과 비교하면 한도 구간에서 소모하는 실행이 12분의 1로 줄어든다. 더 길게 잡으면
  이미 풀린 한도를 계속 기다리게 되고, 더 짧게 잡으면 지금의 반복 실패에 가까워진다.
- 보류 범위는 실행 도구 단위이며 같은 기기의 모든 프로젝트에 적용한다.
- 사용자의 직접 배정은 보류 중에도 막지 않고 경고만 보여준다. 한도 상태가 바뀌었는지 사용자가 직접
  확인할 방법을 남겨 두기 위해서다.

## 범위 밖

- 한도 도달 구분값과 해제 예정 시각을 실행 기록에 실어 보내는 일. 실행 환경이 해야 하며 별도 후속으로
  넘긴다.
- 클로드의 최신 한도 문구를 인식 대상에 넣는 일. 같은 이유로 실행 환경 쪽 후속이다.
- 사용량 잔여분을 조회하거나 한도 소진을 미리 예측하는 기능. 이 문서는 이미 발생한 한도 도달에만
  반응한다.
- 한도에 걸린 역할을 다른 실행 도구나 다른 모델로 자동으로 바꿔 실행하는 일.
- 한도 대기를 알림, 메일, 외부 전송으로 사용자에게 보내는 일.
- 한도로 실패한 실행을 자동으로 다시 실행해 결과를 되살리는 일.

## 인수 조건

1. 한도 도달 구분값이 실린 종료 실행 기록을 넣으면, 같은 실행 도구를 쓰는 역할의 자동 배정이 새 세션을
   시작하지 않는다.
2. 같은 상태에서 다른 실행 도구를 쓰는 역할은 평소와 같이 배정된다.
3. 해제 예정 시각이 실려 온 경우, 그 시각 전에는 배정이 시작되지 않고 그 시각이 지나면 시작된다.
4. 해제 예정 시각이 없는 경우, 정해진 대기 시간 전에는 배정이 시작되지 않고 대기 시간이 지나면 한 번
   시작된다. 그 실행이 다시 한도로 끝나면 같은 대기가 다시 걸린다.
5. 보류 중에 실행 화면을 열면 어느 실행 도구가 한도 대기 중인지와 다시 시작할 시각이 보이며, 그 문장이
   동시 실행 자리 소진이나 배정할 대상 없음 문장과 다르다.
6. 재개 시각을 모르는 상태에서 화면을 열면 시각이 지어내진 값 없이 남은 대기가 보인다.
7. 한도로 끝난 실행의 상세를 열면 종료 사유가 사용 한도 도달로 보인다.
8. 보류 중에 사용자가 직접 배정을 시도하면 한도 대기 중이라는 경고가 나오되 시작 자체는 막히지 않는다.
9. 보류가 걸렸다가 풀리는 동안 자동 배정 켜짐 여부와 역할별 설정값이 그대로다.
10. 보류가 걸린 시점에 실행 중이던 세션은 끝까지 진행된다.
11. 구분값을 싣지 않는 실행 기록만 있는 상태에서는 보류가 걸리지 않고 화면이 지금과 같이 동작한다.
12. 이 과정 전체에서 기획서, 작업 그룹, 개발 작업, 결정, 보고서 문서의 내용과 상태가 바뀌지 않는다.

## 기대효과

- 한도 구간에 쌓이던 실패 기록이 사라진다. 실행 기록이 실제로 확인해야 할 실패만 담게 되어, 실패 하나가
  다시 신호로 읽힌다.
- 한도를 다시 건드리는 재시도가 줄어든다. 5분마다 던지던 호출이 대기 시간마다 한 번으로 바뀐다.
- 사용자가 지금 멈춰 있는 이유와 언제 풀리는지를 화면에서 바로 알게 된다. 앱에서 한도 상태를 볼 수 없던
  상황이 해소된다.
- 실행 환경이 구분값을 싣기 시작하면 그 값을 받아 쓸 보류와 표시가 이미 준비되어 있어, 후속 작업이 값
  생산에만 집중할 수 있다.
