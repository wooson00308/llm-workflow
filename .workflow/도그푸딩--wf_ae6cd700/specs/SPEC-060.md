# 자동 확인 모드 작업 그룹의 기준 전진 갇힘 해소

## 결정권자 요약

### 제안

자동 확인 모드 작업 그룹이 코드 저장소에 새 커밋이 들어왔다는 이유만으로 완료되지 못하고 개발 중에 영구히 남는 문제를 없앤다.

### 현재

자동 확인 모드 그룹은 모든 작업이 검증 완료가 되는 순간 품질 확인이 볼 코드 상태를 한 번 고정한다. 그 뒤 새 커밋이 하나라도 들어오면 고정한 값과 현재 코드 상태가 다르다는 이유로 그룹을 완료 대신 개발 중으로 되돌린다. 고정 값을 다시 잡거나 지우는 경로가 어디에도 없어서, 한 번 어긋난 그룹은 개발이 진행될수록 영영 완료되지 않는다. 지금 이 저장소에도 여섯 작업이 전부 검증 완료인데 이 이유로 개발 중에 갇혀 있는 그룹이 하나 있다.

### 변경 후

코드 상태가 달라졌으면 그룹을 다시 판정해 현재 코드 상태를 기준으로 완료 여부를 정한다. 검증이 끝난 자동 확인 모드 그룹은 그 시점에 완료로 표시되고, 완료된 작업이 개발 중 목록에 계속 쌓여 실제 진행 상황을 가리는 일이 사라진다. 지금 갇혀 있는 그룹도 사용자가 아무 조작을 하지 않아도 화면을 다시 열 때 함께 회복된다.

### 비용과 위험

사람이 확인하는 시간 구간이 있는 사용자 확인 모드에서는 확인 도중 코드가 바뀌면 제출을 기록하지 않는 지금의 보호를 그대로 유지한다. 이 문서가 푸는 것은 사람이 확인하는 자리가 없는 자동 확인 모드의 완료 판정과, 거절 뒤 사용자가 다시 확인할 길이 막혀 있던 부분이다. 승인하지 않으면 작업 그룹 문서, 작업 상태, 결정 기록은 지금 그대로 남고, 갇힌 그룹도 갇힌 채로 남는다. 이 변경은 판정 규칙만 바꾸므로 되돌리면 지금 동작으로 그대로 복귀한다.

## 기획 내용

### 문제

자동 확인 모드 작업 그룹은 완료 판정을 사람이 아니라 앱이 내린다. 그룹에 속한 모든 작업이 검증 완료이고 그룹 구성이 유효하면 사용자 확인 없이 완료가 된다.

여기에 품질 확인 대상 코드 상태를 고정하는 장치가 함께 걸려 있다. 그룹이 품질 확인을 열 수 있는 상태가 되는 시점에 그때의 공유 기준 커밋을 고정 기록으로 남기고, 이후 판정에서 고정 값과 현재 커밋이 다르면 자동 확인 모드 그룹을 완료로 넘기지 않고 개발 중으로 되돌린다.

고정 기록은 그룹 식별자와 구성 버전을 열쇠로 저장되며, 한 번 기록되면 다시 쓰이지 않는다. 저장된 값을 갱신하거나 삭제하는 경로는 앱 어디에도 없다. 그 결과 다음 상태가 만들어진다.

- 그룹의 모든 작업이 검증 완료다.
- 그 뒤 저장소에 새 커밋이 들어왔다.
- 고정 값은 옛 커밋을 가리키고, 현재 커밋과 영원히 일치하지 않는다.
- 그룹은 개발 중 표시에 갇히고, 이를 벗어날 경로가 없다.

이 저장소에서 실제로 확인한 사례는 GROUP-RES-20260815T032125Z-60360-20260815032125이다. 이 그룹에 속한 여섯 작업은 모두 검증 완료 상태이고, 고정 기록은 2026-08-15에 잡힌 옛 커밋을 가리키며, 현재 공유 기준은 그보다 여러 커밋 앞서 있다. 그래서 이 그룹은 완료로 넘어가지 못한다.

### 원인 분석

고정 장치의 원래 목적은 SPEC-RES-20260815T030040Z-31959-20260815030040의 R9에 적혀 있다. 그 항목은 "그룹 검증 직전에 QA 대상 기준 커밋과 포함된 태스크의 통합 커밋을 고정한다. 검증 중 기준이 바뀌면 이전 결과로 완료하지 않고 다시 판정한다"고 규정한다. 즉 기준이 바뀌었을 때 요구된 동작은 다시 판정하는 것이었다.

현재 구현은 이 중 앞부분만 반영했다. 기준이 바뀌면 완료로 넘기지 않는 처리는 있지만, 다시 판정하는 처리가 없다. 완료를 막는 데서 끝나고 재판정으로 이어지지 않아 그룹이 갇힌다.

두 모드의 성격 차이가 여기서 갈린다.

- 사용자 확인 모드에는 확인 창이 있다. 사용자가 안내를 읽고 화면에서 동작을 확인한 뒤 결과를 제출하기까지 시간이 흐르고, 그 사이에 코드가 바뀌면 사용자가 확인한 대상과 기록되는 대상이 어긋난다. 고정 값은 이 구간을 지키는 근거로서 의미가 있다.
- 자동 확인 모드에는 확인 창이 없다. 판정은 프로젝트를 읽을 때마다 문서 상태에서 즉시 다시 계산되며, 시작과 끝이 나뉜 확인 절차가 존재하지 않는다. 지킬 구간이 없는 자리에 구간 보호 장치를 적용한 것이 이 문제의 원인이다.

### 해결 방향

자동 확인 모드에서는 고정 값을 완료를 막는 근거로 쓰지 않고, 판정 시점의 현재 공유 기준에서 완료 여부를 정한다. 판정에 사용한 기준 커밋은 그 시점 값으로 다시 기록한다. R9가 요구한 "다시 판정한다"를 그대로 구현하는 방향이며, 새로운 규칙을 세우는 것이 아니라 빠진 절반을 채우는 것이다.

이 방향에서 원래 취지가 약해지지 않는 근거는 다음과 같다. 자동 확인 모드의 완료 판정 조건은 그룹에 속한 모든 작업이 검증 완료이고 구성이 유효하다는 것이며, 이 조건은 그대로 유지된다. 지금도 앱은 새 커밋이 기존 검증 결과를 깨뜨렸는지 판단하지 않으며, 그룹을 개발 중에 붙잡아 두는 동작 역시 그 판단을 대신해 주지 않는다. 따라서 이 변경으로 잃는 검증 능력은 없고, 없어지는 것은 회복 경로가 없는 정지 상태뿐이다.

### 사용자 확인 모드의 같은 결함

같은 고정 기록이 사용자 확인 모드에도 걸려 있고, 여기에도 회복 경로가 없다. 확인 대상 코드가 바뀐 상태에서 제출하면 앱은 "확인 대상 코드가 그사이 변경되었습니다. 확인한 내용이 지금의 코드와 다르므로 제출하지 않았습니다. 품질 확인을 다시 진행해 주세요"라고 안내하며 거절한다. 그러나 고정 값을 다시 잡는 경로가 없으므로 사용자가 안내대로 다시 확인해도 같은 거절이 반복된다. 안내 문구가 약속하는 재확인이 실제로는 불가능하다.

이 결함은 자동 확인 모드 문제와 뿌리가 같고, 뿌리를 그대로 두면 사용자가 직접 다루는 모드에 똑같은 막다른 길이 남는다. 그래서 이 기획서는 사용자 확인 모드의 재확인 경로도 함께 다룬다. 다만 확인 창 보호는 유지하므로, 한 번의 확인 진행 도중에 코드가 바뀐 제출은 지금과 같이 거절한다. 이 범위 판단에 동의하지 않으면 자동 확인 모드로만 좁혀 달라는 수정 요청으로 되돌려 주면 된다.

### 다루지 않는 범위

- 새 커밋이 기존 검증 결과를 깨뜨렸는지 판단하는 기능. 자동 검사를 다시 실행하거나 재검증을 요구하는 절차는 이 문서의 대상이 아니다.
- 사용자 확인 모드의 품질 확인 흐름 자체의 재설계. 안내 항목 구성, 제출 화면, 결정 기록 절차는 그대로 둔다.
- 작업 그룹의 구성 버전 규칙, 작업 상태 전이 규칙, 결정 문서 형식의 변경.
- 워크플로우 규칙 문서의 개정. 이 문서가 요구하는 동작은 기존 규칙 및 SPEC-RES-20260815T030040Z-31959-20260815030040의 R9와 어긋나지 않으므로 규칙 개정은 필요하지 않다고 본다.
- 이미 기록된 고정 기록 파일을 사용자가 직접 지우게 하는 안내나 도구.

## 요구사항 명세

### R1. 자동 확인 모드 그룹은 현재 코드 상태에서 완료를 판정한다

- 자동 확인 모드 그룹의 완료 판정은 판정 시점의 현재 공유 기준에서 이루어진다. 이전에 기록된 고정 값이 현재 기준과 다르다는 사실만으로 완료를 막지 않는다.
- 완료로 판정한 그룹은 판정에 사용한 현재 기준 커밋을 확인 대상 기준으로 기록한다. 기준이 전진했으면 그 값으로 갱신한다.
- 완료 판정 조건 자체는 바뀌지 않는다. 그룹에 검증 완료가 아닌 작업이 있거나, 구성이 유효하지 않거나, 자동 확인 모드 그룹에 사용자 확인 항목이 들어 있으면 지금과 동일하게 완료로 넘어가지 않는다.
- Git 작업 트리가 아니어서 기준 커밋을 확정할 수 없는 프로젝트의 동작은 이 변경 전과 같아야 한다.

### R2. 이미 갇힌 그룹은 사용자 조작 없이 회복된다

- 변경이 반영된 뒤 프로젝트를 다시 읽으면, 기준 전진 때문에 개발 중에 남아 있던 자동 확인 모드 그룹이 완료로 표시된다.
- 회복에 사용자 조작, 별도 실행 명령, 고정 기록 파일의 수동 삭제, 데이터 이전 절차를 요구하지 않는다.
- 확인 대상은 GROUP-RES-20260815T032125Z-60360-20260815032125이다. 여섯 작업이 모두 검증 완료인 이 그룹이 완료로 표시되어야 한다.

### R3. 확인 창 보호는 사용자 확인 모드에서 유지된다

- 사용자 확인 모드에서 사용자가 확인을 진행한 뒤 제출하기까지 확인 대상 코드가 바뀌면, 그 제출은 지금과 같이 기록하지 않는다. 결정 문서와 작업 문서는 그대로 남는다.
- 이 거절은 문서 최신성 거절과 구분되는 결과로 계속 전달되어, 화면이 "그룹이 바뀌었다"와 "확인 대상 코드가 바뀌었다"를 구분해 안내할 수 있어야 한다.
- 자동 확인 모드에는 확인 창이 없으므로 고정 값을 완료를 막는 근거로 쓰지 않는다.

### R4. 사용자 확인 모드에 재확인 경로를 연다

- 확인 대상 코드 변경으로 제출이 거절된 뒤, 사용자는 현재 코드 상태에서 품질 확인을 다시 진행해 제출할 수 있어야 한다. 같은 거절이 무한히 반복되는 상태가 남지 않는다.
- 재확인이 열린 뒤에도 R3은 그대로 적용된다. 새로 시작한 확인 진행 도중에 코드가 다시 바뀌면 그 제출도 거절한다.
- 거절 안내 문구가 약속하는 행동과 실제로 가능한 행동이 일치해야 한다.

### R5. 문서와 기록은 이 변경으로 다시 쓰이지 않는다

- 이 변경은 판정 규칙과 기준 기록만 다룬다. 작업 그룹 문서, 작업 문서, 결정 문서의 내용과 상태는 이 변경 자체로 수정되지 않는다.
- 자동 완료의 의미, 사용자 품질 확인 결정 기록 절차, 그룹 구성 버전 규칙은 그대로 유지된다.

## 수용 기준

1. 모든 작업이 검증 완료인 자동 확인 모드 그룹에서 공유 기준 커밋이 전진한 뒤 프로젝트를 다시 읽으면, 그룹이 완료로 표시된다.
2. 그 그룹에 기록된 확인 대상 기준 커밋이 전진한 현재 커밋과 일치한다.
3. GROUP-RES-20260815T032125Z-60360-20260815032125가 사용자 조작 없이 완료로 표시된다.
4. 검증 완료가 아닌 작업이 하나라도 있는 자동 확인 모드 그룹은 기준 전진 여부와 무관하게 완료로 넘어가지 않는다.
5. 사용자 확인 모드 그룹에서 확인을 연 뒤 기준이 전진한 상태로 제출하면, 지금과 같이 확인 대상 코드 변경 거절이 돌아오고 결정 문서와 작업 문서가 그대로 남는다.
6. 5번 거절 이후 사용자가 현재 코드 상태에서 다시 확인을 진행하면 제출이 기록된다.
7. Git 작업 트리가 아닌 프로젝트에서 그룹 상태 계산과 제출 판정이 이 변경 전과 동일하게 동작한다.

## 기대효과

- 검증이 끝난 자동 확인 모드 작업 그룹이 실제로 완료로 마감되어, 개발 중 목록이 진행 중인 일만 담게 된다. 판 상태를 볼 때 남은 일과 끝난 일이 구분된다.
- 회복 경로가 없어 사람이 파일을 직접 손대야만 벗어날 수 있던 상태가 사라진다. 앱 소유 상태를 사람이 편집하는 상황을 만들지 않는다.
- 사용자 확인 모드에서 안내 문구가 약속하는 재확인이 실제로 가능해져, 거절 안내와 실제 동작이 일치한다.
- 확인 도중 코드가 바뀌면 완료로 기록하지 않는다는 원래 보호는 그 보호가 의미를 갖는 자리에만 남는다.
