# 프로젝트별 병렬 CLI 에이전트 런타임과 실행 UX

## 결정권자 요약

현재 앱의 Heartbeat 연동은 역할 잡을 설정하고 한 번 실행할 수 있지만, 앱이 직접 관리하는
프로젝트별 에이전트 실행 기능으로 보이지 않으며 역할별 병렬 배정도 지원하지 않는다.
SPEC-051은 기존 Heartbeat를 범용 에이전트 런타임으로 고도화하고 앱의 일급 기능으로 관리하는
방향을 제안한다. 사용자가 결정할 것은 이 방향과 첫 릴리스 범위다.
승인되면 앱이 종료된 뒤에도 프로젝트별로 Claude와 Codex CLI 작업이 계속되고, 역할별 최대
인원과 실제 배정 가능한 작업 수에 따라 한 번 또는 반복 실행된다.
Claude Agent SDK는 사용하지 않으며, Dream은 새 실행 기능과 첫 릴리스 범위에서 제외한다.
승인하지 않으면 지금처럼 Heartbeat 연동 카드와 역할별 단일 실행 방식을 유지하고, 앱은 병렬
에이전트 실행과 후속 작업 배정을 직접 책임지지 않는다.

## 기획 내용

LLM Workflow는 지금까지 에이전트를 실행하는 책임을 외부 Heartbeat에 두고, 앱은 잡 설정과 상태
표시를 담당했다. 이 경계는 초기 연동을 안전하게 도입하는 데 유효했지만, 사용자가 실제로 하고 싶은
일은 Heartbeat 설정 파일을 관리하는 것이 아니다. 프로젝트마다 기획자, 아키텍트, 개발자 역할에
Claude 또는 Codex를 배정하고, 할 수 있는 작업 수만큼 병렬로 실행하며, 앱을 닫아도 작업이 이어지는
것이다.

이 기획서는 새 실행기를 처음부터 만드는 대신 현재 claude-heartbeat를 provider 중립적인 에이전트
런타임으로 고도화하는 방향을 첫 릴리스의 기준으로 삼는다. workflow-labs는 그 런타임을 별도 도구처럼
사용자에게 떠넘기지 않고, 호환 버전의 설치·업데이트·상태 확인과 실행 UX를 직접 관리한다. Heartbeat라는
이름과 구현 방식은 진단 화면에 남을 수 있지만, 사용자가 만나는 주 기능의 이름과 개념은 프로젝트별
에이전트다.

### 현재 확인한 사실

1. Heartbeat는 macOS의 LaunchAgent, Linux의 systemd 사용자 서비스, Windows의 Task Scheduler를
   각각 다루는 서비스 어댑터를 이미 갖고 있다. GUI 앱이 종료된 뒤에도 실행하는 기반을 새로 만들
   필요는 없다. 다만 Windows 등록은 로그인 시 시작에 집중돼 있어 비정상 종료 후 자동 복구는
   보강해야 한다.
2. Heartbeat 0.8은 프로젝트별 잡 파일, 같은 프로젝트 안의 실행 그룹, 비동기 executor와 실행 중
   중복 방지를 갖고 있다. 프로젝트 분리와 병렬 실행의 기초는 있지만 역할별로 여러 작업 대상을 골라
   예약하는 기능은 없다.
3. 실제 provider 실행은 `claude -p` 한 명령으로 고정돼 있다
   (`/Users/catze/Git/claude-heartbeat/src/heartbeat/core.py`). 이 지점을 실행 도구별 계약으로
   분리하면 Claude CLI를 유지하면서 Codex CLI를 추가할 수 있다.
4. 앱은 프로젝트별 잡 파일로 역할 잡을 읽고 쓰며, 설치·업데이트·서비스 제어·지금 실행 UI까지 이미
   제공한다. SPEC-002, SPEC-020, SPEC-024, SPEC-036, SPEC-037의 개발 작업은 모두 완료됐다.
5. 현재 앱의 지금 실행은 `heartbeat once -j`를 데몬 밖에서 직접 부른다
   (`src-tauri/src/infrastructure/heartbeat_process.rs`). Heartbeat CLI도 데몬이 실행 중이면 중복될 수
   있다고 경고하므로, 병렬 실행 기능은 이 경로를 그대로 확장해서는 안 된다.
6. 현재 앱의 역할 자격 판정은 역할마다 첫 대상 하나와 대기 여부를 구한다
   (`src-tauri/src/infrastructure/role_eligibility.rs`). 역할별로 여러 대상을 정확히 배정하려면 같은
   규칙으로 후보 목록, 충돌, 예약 결과를 반환하는 headless 판정 계약이 필요하다.
7. Codex는 공식적으로 `codex exec --json` 비대화형 실행과 JSONL 이벤트 출력을 제공한다.
   Claude도 `claude -p` 비대화형 실행을 제공한다. 첫 릴리스에서 어느 쪽도 SDK가 필수는 아니다.

### 기존 승인분과의 관계

- SPEC-002의 "앱은 LLM을 실행하지 않는다"는 초기 안전 경계는 이 기획서가 승인되면 바뀐다. 앱이
  GUI 프로세스 안에서 LLM을 직접 실행한다는 뜻은 아니다. 앱이 관리하는 companion runtime에 실행을
  요청하고 그 상태와 정책을 제품 책임으로 받아들이는 것으로 바뀐다.
- SPEC-020의 지금 실행 UX는 유지하되 실행 통로를 데몬 큐로 바꾼다. 사용자에게는 한 번 실행으로
  보이지만 데몬과 별도 프로세스가 같은 잡을 동시에 시작할 가능성은 없어진다.
- SPEC-024의 프로젝트별 잡 파일은 마이그레이션 기반으로 유지한다. slug에서 경로를 추정하지 않고
  정확한 프로젝트 식별자와 작업 디렉터리를 계약에 추가한다.
- SPEC-023의 자격 판정과 건너뜀 사유는 유지한다. 단일 대상의 유무를 넘어 역할별 후보 목록과 예약
  결과까지 같은 판단 기준으로 확장한다.
- SPEC-036의 기기 전체 데몬 제어는 진단·관리 기능으로 남긴다. 프로젝트 하나의 반복 실행을 멈추는
  기능은 다른 프로젝트에 영향을 주지 않는 별도 제어로 추가한다.
- SPEC-037의 설치·업데이트 UX를 확장해 사용자가 Python 환경이나 별도 저장소 경로를 직접 관리하지
  않아도 되는 배포 방식으로 바꾼다.

### 제품 방향

첫 릴리스는 다음 관계를 제품 계약으로 삼는다.

- Heartbeat 런타임은 운영체제 서비스, 실행 일정, 프로젝트별 큐, 프로세스 시작·종료·타임아웃,
  동시 실행 제한, 실행 상태와 로그를 책임진다.
- LLM Workflow의 headless 판정 경로는 역할별 자격, 의존성, 활성 lease, 파일 범위 충돌, 대상 예약과
  역할 프롬프트를 책임진다.
- 앱은 프로젝트별 실행 정책을 편집하고, 런타임 설치·업데이트·호환성 확인, 자동·수동 배정, 실행
  상태와 제어를 한 UX에서 제공한다.
- Claude와 Codex는 각 CLI를 통해 실행한다. provider 인증 정보는 각 CLI가 소유하고 앱과 런타임은
  토큰이나 API 키를 저장하지 않는다.

런타임이 Python으로 남을지 단일 실행 파일로 패키징될지, 앱과 로컬 IPC를 사용할지 버전화된 JSON CLI를
사용할지는 아키텍트가 정한다. 사용자가 별도 Python 설치와 editable checkout을 관리하지 않고도 설치와
업데이트를 끝낼 수 있어야 한다는 제품 결과는 이 기획서가 고정한다.

### 사용자 흐름

1. 사용자가 프로젝트의 에이전트 화면을 연다. 화면은 런타임 설치·실행·호환 상태와 현재 프로젝트의
   역할별 설정, 실행 중·대기·최근 종료 작업을 보여준다.
2. 역할마다 Claude 또는 Codex, 모델, 한 번 실행 또는 반복 실행, 최대 병렬 인원을 정한다. 처음에는
   역할별 최대 인원이 1이어서 현재 동작과 같은 보수적인 상태로 시작한다.
3. 자동 배정을 선택하면 앱이 현재 배정 가능한 작업 수와 제한 요인을 미리 보여준다. 수동 배정을
   선택하면 사용자가 역할과 대상 문서를 실행 슬롯마다 지정한다.
4. 시작 확인 화면은 실행 도구, 역할별 최대 인원, 지금 시작할 대상, 반복 여부, 적용 범위를 보여준다.
   사용자가 확인한 뒤에만 유료 CLI 세션이 시작된다.
5. 한 번 실행은 확인 시점에 예약된 대상만 처리하고 종료한다. 반복 실행은 사용자가 일시 정지할 때까지
   빈 자리가 생길 때마다 새로 배정 가능한 대상을 채운다.
6. 사용자가 앱을 닫아도 런타임은 실행 중인 작업과 반복 배정을 계속한다. 앱을 다시 열면 같은 실행
   상태와 로그를 이어서 보여준다.
7. 사용자는 프로젝트 단위로 새 배정을 일시 정지하거나 재개할 수 있다. 실행 중 작업은 별도의 취소
   조작을 명시적으로 선택할 때만 종료한다.

### 포함 범위

- Claude와 Codex CLI provider 지원.
- 앱이 관리하는 Heartbeat companion runtime의 설치, 업데이트, 호환성 검사와 복구 안내.
- macOS, Linux, Windows에서 GUI 종료 후 계속 실행되는 사용자 서비스.
- 프로젝트별 실행 큐, 반복 정책, 상태, 로그와 제어의 분리.
- 기획자·아키텍트·개발자 역할별 provider, 모델, 실행 방식, 최대 병렬 인원 설정.
- 역할별 자동 배정과 사용자가 대상을 직접 고르는 수동 배정.
- 배정 가능한 여러 대상을 한 번에 계산하고 CLI 실행 전에 중복 없이 예약하는 headless 판단 경로.
- 한 번 실행, 반복 실행, 프로젝트 일시 정지·재개, 실행 중 작업 취소·재시도.
- 앱을 다시 열었을 때 실행 중·대기·완료·실패 상태와 로그 복원.
- 기존 Claude Heartbeat 설정과 실행 이력의 호환 또는 안내가 포함된 마이그레이션.

### 제외 범위

- Claude Agent SDK 사용. 사용자 요구에 따라 금지한다.
- 첫 릴리스에서 Codex SDK 또는 Codex App Server 사용. CLI로 충족하지 못하는 요구가 실증된 뒤 별도
  기획으로 검토한다.
- 원격 서버나 클라우드에서 실행하는 호스팅형 에이전트.
- 여러 사용자 사이의 작업 배정, 조직 계정, 중앙 서버 기반 동기화.
- 실행 중인 에이전트와 앱 안에서 자유 대화하는 채팅 UI.
- Dream을 새 에이전트 화면이나 범용 런타임 계약으로 이전하는 작업. 기존 Dream 연동을 제거할지는
  별도 결정으로 남기며, 이 기획서의 완료 조건에는 포함하지 않는다.
- 기존 역할 계약이 정한 승인·QA 권한을 에이전트에게 넓히는 것. 병렬 실행돼도 한 세션 한 역할과 한
  대상 원칙은 유지한다.
- 새 Rust 실행기를 병행 구현하는 것. Heartbeat 고도화가 배포·운영 요구를 충족하지 못한 실증이
  생기면 후속 대안으로 검토한다.

## 요구사항 명세

### R1. 에이전트 실행을 앱의 일급 기능으로 보여준다

- 프로젝트 화면에 에이전트 전용 진입점을 둔다. 사용자는 Heartbeat 파일이나 데몬 개념을 먼저 이해하지
  않아도 역할을 설정하고 실행할 수 있다.
- 화면은 현재 프로젝트의 설정과 실행을 기본으로 보여준다. 기기 전체 서비스와 버전 진단은 고급 관리
  정보로 구분한다.
- 각 역할 행은 provider, 모델, 한 번·반복 실행, 최대 병렬 인원, 현재 실행 수, 대기 수, 마지막 결과를
  함께 보여준다.
- 프로젝트가 바뀌면 설정과 실행 목록도 해당 프로젝트의 값으로 바뀐다. 다른 프로젝트의 작업이 섞여
  보이지 않는다.

### R2. Claude와 Codex를 CLI provider로 실행한다

- Claude는 비대화형 Claude CLI, Codex는 비대화형 Codex CLI를 사용한다.
- 런타임은 provider마다 명령 구성, 인증 확인, 구조화 출력 해석, 취소, 종료 결과 정규화를 분리한다.
- Claude Agent SDK는 어떤 경로에서도 사용하지 않는다.
- Codex SDK와 App Server가 설치돼 있지 않아도 첫 릴리스의 모든 완료 조건을 충족한다.
- CLI 미설치, 로그인 필요, 권한 부족, 지원하지 않는 버전을 서로 다른 상태로 보여주고 다음 행동을
  안내한다.
- 앱과 런타임은 provider 인증 토큰과 API 키를 저장하거나 로그에 남기지 않는다.
- Claude 실행 환경에 API 과금 경로를 바꿀 수 있는 키가 상속되는 경우 이를 사용자에게 알리고,
  사용자가 의도하지 않은 과금 경로로 조용히 실행하지 않는다.

### R3. 프로젝트별 실행을 서로 격리한다

- 각 실행 요청은 안정적인 프로젝트 식별자와 실제 작업 디렉터리를 가진다. slug를 역변환해 작업
  디렉터리를 추측하지 않는다.
- 프로젝트마다 실행 정책, 큐, 반복 상태, 쿼터, 실행 이력과 오류를 분리한다.
- 한 프로젝트의 잘못된 설정, 자격 판정 실패, provider 인증 실패가 다른 프로젝트의 큐를 멈추지 않는다.
- 프로젝트 일시 정지는 그 프로젝트의 새 배정만 막는다. 기기 전체 데몬이나 다른 프로젝트 작업을
  정지하지 않는다.
- 기기 전체 용량이 찼을 때 한 프로젝트가 빈 슬롯을 독점하지 않도록 대기 프로젝트 사이에 공정한
  순서를 적용한다.

### R4. 역할별 병렬 인원과 기기 전체 안전 상한을 적용한다

- 기획자·아키텍트·개발자마다 최대 병렬 인원을 따로 정한다. 기본값은 각 역할 1이다.
- 프로젝트 전체 기본 상한은 3이며, 사용자는 기기 전체 상한 안에서 조정할 수 있다.
- 기기 전체 기본 상한은 동시 실행 16이다. 사용자는 이 값을 낮출 수 있고, 높이는 변경은 첫 릴리스의
  일반 UX에서 제공하지 않는다.
- 한 역할의 실제 실행 수는 역할 상한, 프로젝트의 남은 슬롯, 기기의 남은 슬롯, provider가 실행
  가능한 상태, 현재 배정 가능한 대상 수 중 가장 작은 값이다.
- 쿼터와 반복 주기는 병렬 인원과 별도다. 최대 병렬 인원을 높였다고 실행 한도나 provider 사용 제한을
  우회하지 않는다.
- 설정을 낮춰 현재 실행 수보다 작아져도 실행 중 작업을 자동 종료하지 않는다. 새 배정을 멈추고 실행
  수가 낮아질 때까지 기다린다.

### R5. 자동 배정은 정확한 대상 예약 뒤에만 CLI를 시작한다

- headless 판정 경로는 역할별로 지금 배정 가능한 대상 목록과 제외 사유를 반환한다.
- 의존성, 최신 사용자 결정, 활성 lease, 파일 범위 충돌, 마이그레이션 잠금과 역할 계약의 순서를 현재
  워크플로 규칙과 동일하게 적용한다.
- 서로 다른 dispatcher가 같은 대상을 동시에 선택할 수 없도록 CLI 프로세스를 시작하기 전에 원자적인
  예약이 성립한다.
- 예약과 역할 세션의 정식 claim 사이에 소유권이 모순되지 않는다. 예약된 대상과 lease가 어긋나면 CLI를
  시작하지 않거나, 이미 시작한 프로세스에 새 유료 요청을 보내기 전에 종료한다.
- 현재 배정 가능한 대상이 0이면 provider CLI를 실행하지 않는다. 반복 모드는 다음 판정 시점까지
  대기하고, 한 번 실행은 대상 없음 결과로 끝난다.
- planner와 architect가 병렬로 결과 문서를 만들 때 식별자가 충돌하지 않도록 각 배정에 유일한 결과
  식별자 또는 동등한 예약 정보를 제공한다.
- 자동 배정의 대상 순서는 각 역할 계약이 정한 우선순위를 보존한다.

### R6. 수동 배정은 사용자가 역할과 대상을 명시한다

- 사용자는 역할별 실행 슬롯을 추가하고 각 슬롯에 대상 문서 또는 작업을 지정할 수 있다.
- 같은 대상을 두 슬롯에 넣으면 저장 전에 막고 이유를 보여준다.
- 사용자가 지정한 대상도 마이그레이션 잠금, 이미 활성인 lease, 완료·거절 상태처럼 실행할 수 없는
  조건을 통과해야 한다. 수동 배정은 워크플로 안전 규칙의 우회가 아니다.
- 자동 판정이 후보를 만들지 못한 상태에서는 오류 원인과 함께 수동 배정 진입점을 제공한다. 사용자가
  잘못된 대상 식별자를 입력하면 CLI를 시작하지 않는다.
- 한 번 실행의 수동 배정은 선택한 슬롯만 실행한다. 반복 실행의 수동 배정은 선택 목록을 다 처리한 뒤
  자동으로 새 대상을 추측하지 않고 대기한다.

### R7. 한 번 실행과 반복 실행의 의미를 구분한다

- 한 번 실행은 사용자가 확인한 시점의 예약 목록을 한 차례 처리하고 새 대상을 보충하지 않는다.
- 반복 실행은 빈 슬롯이 생길 때마다 자격 판정을 다시 수행해 역할 상한까지 새 대상을 보충한다.
- 반복 실행의 판정 간격과 실행 한도는 역할별로 편집할 수 있으며 현재 Heartbeat 설정의 유효값을
  마이그레이션한다.
- 반복 실행을 일시 정지하면 새 배정만 멈춘다. 실행 중 작업 종료는 별도 조작이다.
- 취소는 대상 작업과 프로세스 트리를 명확히 보여준 뒤 확인받고 수행한다. 취소 결과가 lease와 예약
  상태에 반영되지 않으면 성공으로 표시하지 않는다.
- 재시도는 같은 대상의 이전 실패를 연결해 보여주며, 새로운 중복 실행을 만들지 않는다.

### R8. GUI가 종료돼도 실행과 후속 배정이 계속된다

- 앱 창 종료와 앱 프로세스 종료가 실행 중 CLI 프로세스, 프로젝트 큐, 반복 배정을 멈추지 않는다.
- macOS, Linux, Windows에서 각 운영체제의 사용자 서비스로 런타임을 시작하고 감시한다.
- 운영체제 재시작이나 사용자 재로그인 뒤에는 저장된 반복 정책과 큐를 복원한다. 플랫폼의 사용자 서비스
  정책상 로그아웃 중 실행을 보장하지 못하는 경우 그 경계를 설치 화면에 명시한다.
- 런타임이 비정상 종료된 뒤 다시 시작되면 기존 PID와 프로세스 생존 여부, 예약과 lease를 먼저
  조정하고 나서 새 작업을 시작한다. 살아 있는 같은 작업을 중복 실행하지 않는다.
- 앱을 다시 열면 런타임이 보존한 상태를 기준으로 화면을 복원한다. 앱이 닫히기 전의 메모리 값으로
  실행 중이라고 추측하지 않는다.

### R9. 앱과 런타임은 버전화된 계약으로 통신한다

- 상태 조회, 작업 목록, 실행 요청, 일시 정지·재개, 취소, 로그, provider 진단에 기계가 읽을 수 있는
  버전화된 계약을 제공한다.
- 앱은 Heartbeat 내부 상태 파일의 우연한 필드나 운영체제별 서비스 파일을 직접 해석해 새 기능을
  만들지 않는다. 계약에 없는 값은 모름으로 표시한다.
- 앱의 지금 실행도 이 계약의 큐를 사용한다. 데몬 밖에서 별도 `once` 프로세스를 띄우지 않는다.
- 호환되지 않는 런타임 버전에서는 실행 버튼을 막고, 필요한 버전과 업데이트 방법을 보여준다.
- 부분 실패는 전체 성공이나 전체 실패로 뭉뚱그리지 않는다. 예약, provider 시작, 역할 세션, 정리 중
  어디에서 실패했는지 구분한다.

### R10. 설치와 업데이트를 앱이 관리한다

- 신규 사용자는 터미널에서 저장소를 복제하거나 editable package를 설치하지 않고 앱 안에서 런타임을
  설치할 수 있다.
- 앱은 자신이 지원하는 런타임 버전 범위를 알고 설치된 버전과 실행 중 버전을 구분한다.
- 업데이트는 실행 중 작업에 미치는 영향을 미리 보여주고 사용자의 확인을 받는다. 기존 SPEC-037의
  세션 중단 고지를 유지한다.
- 설치·업데이트·복구는 macOS, Linux, Windows에서 지원한다. 한 플랫폼이 수동 설치를 요구하는 상태로는
  첫 릴리스를 완료하지 않는다.
- 런타임 패키징 방식이 바뀌어도 기존 `heartbeat` CLI와 프로젝트별 잡을 사용하는 사용자가 마이그레이션
  안내 없이 갑자기 실행을 잃지 않는다.

### R11. 실행 상태와 비용 위험을 사용자가 이해할 수 있게 한다

- 작업 상태를 최소한 예약 중, 대기, 실행 중, 일시 정지, 성공, 실패, 취소됨, 복구 필요로 구분한다.
- 실행 중 항목은 프로젝트, 역할, provider, 대상 문서, 시작 시각, 경과 시간과 취소 조작을 보여준다.
- 최근 종료 항목은 결과, 소요 시간, 종료 원인과 로그 진입점을 보여준다.
- provider CLI가 제공하는 구조화 이벤트를 이용할 수 있으면 진행 상황을 갱신하되, 비밀값과 전체 프롬프트를
  진단 로그에 그대로 남기지 않는다.
- 사용자가 최대 병렬 인원이나 반복 실행을 켤 때 동시에 여러 유료 세션이 시작될 수 있음을 확인 화면에
  명시한다.
- 실행 한도 소진, provider 인증·사용 제한, 워크플로 대상 없음은 서로 다른 대기 사유로 표시한다.

### R12. Dream을 새 에이전트 기능과 분리한다

- 새 에이전트 화면의 역할, provider, 실행 큐와 상태 목록에 Dream을 포함하지 않는다.
- Heartbeat의 provider 중립화가 Dream 설치나 Dream 전용 prompt·quota를 전제로 하지 않는다.
- 기존 Dream 연동이 남아 있어도 새 기능의 설치·실행·업데이트를 막지 않는다.
- 기존 Dream 연동의 유지·숨김·제거는 별도 아이디어에서 결정한다.

## 확인 필요

없다. 이 기획서는 사용자가 대화에서 정한 다음 결정을 반영했다.

- 새 실행기를 먼저 만드는 대신 Heartbeat 고도화와 기존 연동 UX 개편을 첫 방향으로 삼는다.
- 앱 종료 후 실행, 프로젝트 분리와 역할별 병렬 배정을 첫 릴리스 조건으로 둔다.
- 자동 배정을 우선하고, 정확히 배정할 수 없는 경우 사용자가 직접 지정하는 UX를 제공한다.
- Claude Agent SDK를 사용하지 않는다.
- Dream을 새 기능의 범위에서 제외한다.

사용자가 승인하면 위 결정 전체를 기준으로 아키텍트가 두 저장소의 릴리스 경계와 개발 작업을 분해한다.
범위를 줄이고 싶다면 승인 전에 첫 릴리스에서 미룰 요구사항을 수정 요청으로 남긴다.

## 기대효과

- 사용자가 외부 Heartbeat 설정을 이해하지 않아도 앱에서 프로젝트별 에이전트 팀을 구성하고 운영한다.
- 앱을 닫아도 역할별 작업 배정이 이어져 장시간 워크플로가 GUI 수명에 묶이지 않는다.
- 배정할 일이 있을 때만 CLI를 시작하고 같은 대상을 중복 실행하지 않아 토큰과 시간을 절약한다.
- Claude와 Codex를 프로젝트와 역할에 맞게 섞어 쓰면서도 워크플로 규칙과 실행 상태는 하나의 UX로
  관리한다.
- 이미 구현된 Heartbeat의 크로스플랫폼 서비스와 앱 연동 자산을 재사용해 새 실행기 개발보다 빠르게
  첫 릴리스를 만들 수 있다.

## 완료 조건

1. macOS, Linux, Windows에서 앱 프로세스를 종료한 뒤에도 실행 중 작업이 계속되고 반복 실행이 새
   배정 가능한 대상을 시작한다.
2. 두 프로젝트에서 반복 실행을 동시에 켰을 때 각 프로젝트의 설정, 큐, 상태, 로그와 오류가 섞이지
   않고 한 프로젝트 일시 정지가 다른 프로젝트를 멈추지 않는다.
3. 기획자·아키텍트·개발자 역할마다 Claude 또는 Codex, 모델, 한 번·반복 실행과 최대 병렬 인원을
   저장할 수 있고 다시 열었을 때 같은 값이 보인다.
4. 역할 상한 3, 프로젝트 상한 5, 기기 남은 슬롯 4, 배정 가능 대상 2인 시나리오에서 실제 시작 수가
   2이고 어떤 대상을 선택했는지 실행 전에 확인할 수 있다.
5. 배정 가능 대상이 없거나 마이그레이션 잠금이 있을 때 Claude와 Codex CLI 프로세스가 시작되지 않는다.
6. 여러 자동 dispatcher가 같은 대상을 동시에 발견해도 예약 성공은 하나뿐이고 provider CLI도 하나만
   시작된다.
7. 병렬 planner·architect 실행이 서로 다른 결과 식별자를 사용하고 같은 문서를 덮어쓰지 않는다.
8. 수동 배정에서 같은 대상 중복, 활성 lease 대상, 완료·거절 대상을 선택하면 실행 전에 막고 사유를
   보여준다.
9. 한 번 실행은 최초 예약 목록을 처리한 뒤 종료하고, 반복 실행은 작업 종료 후 새 대상을 역할 상한까지
   보충한다.
10. 프로젝트 일시 정지는 새 배정만 멈추고 실행 중 프로세스를 종료하지 않는다. 명시적 취소는 대상
    프로세스 트리와 상태를 정리하고 결과를 화면에 남긴다.
11. 런타임 비정상 종료와 재시작을 재현했을 때 살아 있는 같은 작업이 중복 실행되지 않고, 정리할 수
    없는 상태는 복구 필요로 표시된다.
12. 현재 지금 실행 UX가 데몬 큐를 사용하며, 데몬이 실행 중인 상태에서도 같은 잡을 우회 실행하는 별도
    프로세스가 생기지 않는다.
13. Claude CLI만 설치된 환경, Codex CLI만 설치된 환경, 둘 다 설치된 환경에서 선택 가능한 provider와
    진단 결과가 실제 상태와 일치한다.
14. Claude Agent SDK와 Codex SDK가 설치되지 않은 환경에서 Claude·Codex 각각의 성공 실행과 구조화된
    종료 결과 표시가 동작한다.
15. CLI 미설치, 로그인 필요, 권한 부족, provider 사용 제한, 실행 시간 초과, 사용자 취소가 서로 다른
    결과와 다음 행동으로 표시된다.
16. 앱이나 런타임 로그에 provider 인증 토큰과 API 키가 남지 않고, 의도하지 않은 Claude API 키 상속을
    진단하거나 차단한다.
17. 신규 설치 사용자가 터미널 명령 없이 앱에서 런타임 설치와 서비스 시작을 완료하고, 호환되지 않는
    버전은 실행 전에 업데이트 안내를 받는다.
18. 기존 Claude Heartbeat 역할 잡과 실행 이력이 마이그레이션 뒤 유지되거나, 자동 이전할 수 없는 값은
