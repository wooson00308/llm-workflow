# 자동 세션의 역할이 화면 어디에서나 같게 보인다

## 결정권자 요약

### 제안

예약으로 시작한 세션이 자기 역할을 선점 기록에 함께 남기게 하고, 역할이 비어 있는 기록은 화면이 실행 정보로 채워 보여준다.

### 현재

앱이 예약해서 시작한 자동 세션은 예약하는 순간 역할이 이미 정해져 있는데도, 선점 기록에는 역할이 빠진 채 저장된다. 그래서 앱 밖 세션 목록에서 자동 세션이 전부 미기재로 표시되고, 역할별 개수 요약도 역할 미기재 한 덩어리로 뭉친다. 여기에 더해 같은 세션이 자리마다 다르게 보인다. 진행 중 목록은 실행 정보의 역할을 읽어 기획자나 개발자로 제대로 표시하는데, 그 실행이 활성 상태에서 벗어나면 아직 만료되지 않은 같은 세션의 선점 기록이 앱 밖 세션 목록으로 넘어오면서 미기재로 바뀐다. 사용자에게는 한 세션이 역할을 잃어버리는 것처럼 보인다.

### 변경 후

예약으로 시작한 세션은 선점 기록에 역할이 남으므로, 앱 밖 세션 목록과 역할별 개수 요약에서 기획자, 아키텍트, 개발자로 곧바로 구분된다. 역할이 없는 예전 기록과 사용자가 직접 연 세션은, 같은 대상을 잡고 있는 실행 정보에 역할이 있으면 그 값으로 채워서 보여준다. 두 경로가 합쳐지면서 한 세션의 역할 표시가 화면 어느 자리에서나 같아지고, 실행이 끝나는 순간 표시가 바뀌는 현상도 사라진다. 사용자는 지금 어느 역할이 몇 개 돌고 있는지를 화면에서 그대로 셀 수 있다.

### 비용과 위험

이미 저장된 선점 기록은 고쳐 쓰지 않고 그대로 둔다. 역할을 알려주는 근거가 없는 세션은 계속 미기재로 표시하며, 추정으로 채우지 않는다. 선점과 갱신과 해제 절차, 만료 판정, 마이그레이션 보호 동작은 하나도 바꾸지 않고, 역할 항목은 지금처럼 선택 항목으로 남기므로 역할 없이 기록된 선점도 계속 유효하다. 되돌릴 때는 기록에 역할을 적는 부분과 화면의 보완 표시만 걷어내면 원래 동작으로 돌아간다. 이 기획서가 승인되지 않으면 자동 세션은 계속 미기재로 표시되고, 같은 세션이 자리마다 다르게 보이는 현상도 그대로 남는다.

## 기획 내용

### 사용자가 보는 문제

사용자는 자동 세션을 화면에서 셀 수 없다. 앱 밖 세션 목록에 여러 줄이 떠 있어도 전부 미기재라서, 지금 기획이 도는지 개발이 도는지 알 수 없다. 여러 세션을 한꺼번에 돌릴 때 이 목록은 판이 어떻게 흘러가는지 확인하는 자리인데, 정작 그 자리에서 역할이 사라진다.

그리고 같은 세션의 표시가 시간에 따라 바뀐다. 진행 중일 때는 역할이 보이다가, 실행이 활성 상태에서 벗어나면 같은 세션이 앱 밖 세션 목록으로 옮겨 가면서 미기재가 된다. 화면이 스스로 말을 바꾸는 셈이라, 사용자는 표시를 믿기 어렵다.

### 왜 이렇게 되는가

원인은 쓰는 쪽과 읽는 쪽 두 군데에 있다.

쓰는 쪽부터 보면, 예약 헬퍼는 어느 역할로 예약하는지를 인자로 받아서 알고 있고, 그 값을 세션에 보내는 역할 프롬프트에도 적어 넣는다. 그런데 실제로 선점 기록을 만드는 선점 헬퍼는 필수 다섯 항목만 기록하고 역할은 기록하지 않는다. 공통 규칙이 역할 항목을 선택 항목으로 정해 두었으니 규칙을 어긴 것은 아니지만, 값을 이미 손에 쥐고 있는 자리에서 버리고 있다. 예약을 거쳐 시작하는 세션이 곧 자동 세션 전부이므로, 결과적으로 자동 세션 전부가 미기재가 된다.

읽는 쪽을 보면, 화면은 역할을 두 출처에서 가져온다. 진행 중 목록과 실행 상세와 실행 기록은 실행 정보의 역할을 읽고, 앱 밖 세션 목록과 역할별 개수 요약은 선점 기록의 역할을 읽는다. 앱이 돌린 실행이 잡은 대상은 앱 밖 세션 목록에서 빼는데, 그 제외 판정이 실행의 활성 상태를 기준으로 한다. 실행이 활성 상태에서 벗어나도 선점 기록은 만료 전까지 남아 있으므로, 그 사이 같은 세션이 앱 밖 세션 목록으로 넘어오고 표시가 미기재로 바뀐다. 널뛰기의 정체가 이것이다.

두 원인은 성격이 다르다. 앞의 것은 앞으로 만들 기록의 문제이고, 뒤의 것은 이미 남아 있는 기록과 앱 밖에서 시작한 세션의 문제다. 그래서 한쪽만 고치면 화면은 여전히 일관되지 않는다. 앞의 것만 고치면 지금 떠 있는 기록과 사용자가 터미널에서 직접 연 세션은 계속 미기재로 남고, 뒤의 것만 고치면 실행 정보가 없는 세션은 여전히 채울 근거가 없다.

### 무엇을 하지 않는가

- 선점과 갱신과 해제 절차, 만료를 판정하는 기준, 마이그레이션 보호 동작은 바꾸지 않는다.
- 이미 저장된 선점 기록을 뒤늦게 고쳐 쓰거나 일괄로 채워 넣지 않는다.
- 역할 항목을 필수 항목으로 승격하지 않는다. 역할 없이 기록된 선점은 계속 유효한 선점이다.
- 역할을 알려주는 근거가 없을 때 에이전트 이름이나 대상 문서 종류로 역할을 추측하지 않는다.
- 역할 이름의 표기와 색, 목록의 정렬과 접힘 규칙은 지금 그대로 둔다.

## 요구사항 명세

### REQ-01 예약으로 만든 선점 기록에는 역할이 남는다

예약을 거쳐 시작한 세션의 선점 기록에는 그 예약이 정한 역할이 함께 저장된다. 기획자, 아키텍트, 개발자 세 역할 모두 같다.

### REQ-02 기존 선점 호출은 그대로 동작한다

역할을 알려주지 않고 선점하는 호출은 지금과 똑같이 성공하고, 역할이 없는 선점 기록을 만든다. 역할 항목은 선택 항목으로 남는다.

### REQ-03 갱신과 해제는 역할을 훼손하지 않는다

이미 역할이 적힌 선점 기록을 갱신해도 역할은 그대로 유지된다. 해제 동작은 지금과 같다.

### REQ-04 화면은 실행 정보로 빈 역할을 채운다

선점 기록에 역할이 없을 때, 같은 대상을 잡고 있는 살아 있는 실행 정보에 역할이 있으면 화면은 그 역할로 표시한다. 이 보완은 앱 밖 세션 목록과 역할별 개수 요약 양쪽에 똑같이 적용된다.

### REQ-05 근거가 없으면 미기재를 유지한다

선점 기록에도 역할이 없고 채울 실행 정보도 없으면 미기재 표시를 그대로 둔다. 추정으로 채우지 않는다.

### REQ-06 두 값이 다르면 선점 기록을 따른다

선점 기록의 역할과 실행 정보의 역할이 서로 다르면 선점 기록의 값을 표시한다. 선점 기록은 세션 자신이 남긴 값이고 실행 정보는 앱이 배정할 때 정한 값이므로, 실제로 무엇을 하고 있는지에 더 가까운 쪽이 선점 기록이다. 이 우선순위는 기획자가 정한 기본값이며, 반대로 두는 편이 낫다고 보면 이 기획서를 되돌려 보내면 된다.

### REQ-07 표시는 자리마다 같다

한 세션의 역할은 진행 중 목록, 앱 밖 세션 목록, 역할별 개수 요약, 실행 상세에서 모두 같은 값으로 보인다. 실행이 활성 상태에서 벗어나 같은 세션이 다른 목록으로 옮겨 가도 역할 표시는 바뀌지 않는다.

## 인수 기준

1. 예약으로 기획자 세션을 하나 시작한 뒤 그 세션의 선점 기록을 열면 역할이 기획자로 적혀 있다. 아키텍트와 개발자도 같다.
2. 역할을 알려주지 않는 방식으로 선점하면 선점은 성공하고, 역할이 없는 선점 기록이 만들어진다.
3. 역할이 적힌 선점을 갱신한 뒤에도 역할이 그대로 남아 있다.
4. 예약으로 시작한 세션이 여럿 도는 동안 앱 밖 세션 목록의 각 줄과 역할별 개수 요약이 역할별로 구분되어 보이고, 미기재 덩어리가 나타나지 않는다.
5. 역할이 없는 선점 기록이 있고 같은 대상을 잡은 살아 있는 실행 정보가 있을 때, 화면은 그 실행 정보의 역할로 표시한다.
6. 역할이 없는 선점 기록만 있고 채울 실행 정보가 없을 때, 화면은 미기재로 표시한다.
7. 한 세션의 실행이 활성 상태에서 벗어나 앱 밖 세션 목록으로 옮겨 가는 동안, 그 세션의 역할 표시가 바뀌지 않는다.

## 기대효과

- 자동 세션을 여럿 돌리는 동안 사용자가 화면만 보고 어느 역할이 몇 개 도는지 셀 수 있다. 지금은 셀 수 없어서 판 상태를 사용자가 따로 추적해야 한다.
- 표시가 시간에 따라 바뀌지 않으므로, 화면에서 읽은 값을 그대로 믿고 판단할 수 있다.
- 역할별 개수 요약이 실제 값을 담게 되어, 특정 역할만 밀려 있거나 비어 있는 상황을 눈으로 잡을 수 있다.
- 사용자 눈에 버그로 보이던 미기재 표시가 사라진다.
