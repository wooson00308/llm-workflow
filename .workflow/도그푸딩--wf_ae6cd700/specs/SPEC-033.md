# 자격 판정이 데몬 한도 안에서 끝나고, 문서가 늘어도 그대로 끝난다

## 기획 내용

이미 고장 났다. 2026-08-04 저녁, 아키텍트 역할 잡이 네 번 연속으로 뜨지 못했다. 데몬이 조건 스크립트를 10초에 끊었고, 끊긴 조건은 안전을 위해 "불충족"으로 처리되므로 세션이 아예 기동하지 않았다(확인 사실 1·2). 그 시간 동안 분해를 기다리던 승인 결정이 있었는지 없었는지는 아무도 모른다 — 판정이 답을 내기 전에 죽었기 때문이다.

아이디어는 이것을 문서 수 문제로 읽었다. 문서가 사이클마다 4~6개씩 늘어 200건 언저리가 됐고 성장은 복리이니, 완료 문서를 스캔 경로에서 빼자는 것이다. 재현해 보니 진단의 앞부분은 맞고 처방의 전제는 틀렸다.

맞는 부분: 재현된다. 저장소 문서를 임시 디렉터리로 복사하고 조기 종료가 걸리지 않게 만든 뒤 재면 아키텍트 분기가 12.4~13.4초다. 한도가 10초이므로 이미 넘는다(확인 사실 3).

틀린 부분: 비용을 끄는 것은 문서 수가 아니다. 같은 픽스처에서 결정 문서를 122건에서 30건으로 줄이면 13.37초가 6.08초로 줄지만, 작업 문서를 97건에서 20건으로 줄이면 13.12초가 12.24초로 거의 그대로다(확인 사실 4). 문서 수가 곧 비용이라면 이 워크플로우에서 가장 큰 디렉터리인 `reports/` 144건이 가장 비쌌어야 하는데, 그 디렉터리는 판정 비용이 0이다 — 조건 스크립트가 읽지 않고 앱은 목록만 센다(확인 사실 8).

비용은 후보 하나마다 같은 디렉터리를 처음부터 다시 훑는 자리에서 나온다. 아키텍트 분기는 승인 결정 31건 각각에 대해 "이보다 늦은 결정이 있는가"를 판정하려고 매번 `decisions/` 122건을 다시 읽고, 안쪽 한 바퀴마다 프로세스를 네 개까지 띄운다. 판정 한 번에 프로세스가 수천 개 뜬다(확인 사실 5). 곱하기의 양변이 모두 결정 수다. 문서를 절반으로 줄이면 비용은 4분의 1이 되지만, 곱을 없애면 비용은 문서 수에 비례하는 선형이 된다. 후자가 같은 노력으로 훨씬 멀리 간다.

그래서 이 기획서는 아이디어의 제목("완료 문서를 스캔 경로에서 뺀다")을 이번 범위로 삼지 않는다. 그렇게 판단한 근거가 하나 더 있다. 아이디어 자신이 경고한 대로 문서를 옮기는 일은 참조 무결성 수술이고, 실제로 세어 보니 옮김이 깨뜨리는 판정이 다섯 개다(확인 사실 13). 그중 하나는 아이디어가 든 예보다 더 아프다 — 완료 작업을 `tasks/`에서 치우면 선행 판정이 그 문서를 못 찾아 미충족으로 떨어지고, 그 작업에 매달린 후행 작업이 전부 닫힌다. 측정이 "아카이브는 필요 없다"고 말하는데 비용이 그만큼 큰 수술을 지금 할 이유가 없다. 확인 필요 1번이 이 자리를 사용자에게 묻는다.

두 번째 아픈 지점인 화면 폴링은 성격이 다르다. 앱은 2.5초마다 프로젝트를 통째로 다시 읽고, 그 재읽기에서 결정·기획서·작업 세 디렉터리를 각각 두 번씩 훑는다 — 지금 문서량으로 폴링 한 번에 파일 본문 읽기 534회다(확인 사실 11·12). 두 번 훑는 이유는 코드가 각각 적어 두었고 둘 다 타당한 이유다. 다만 여기는 아직 고장 난 자리가 아니다. 사용자가 겪은 증상도, 측정된 실패도 없다. 그래서 이 기획서는 이 자리를 "고장을 예방하는 큰 개조"가 아니라 "이유가 사라진 중복만 걷어내기"로 다루고, 그 이상은 확인 필요 4번에서 사용자에게 맡긴다.

세 번째 아픈 지점인 역할 세션의 토큰은 이 기획서가 직접 다루지 않는다. 세션이 무엇을 읽을지는 계약과 세션의 판단이고, 판정 비용을 줄이는 일과 원인이 다르다.

마지막으로 한 가지 짚어 둔다. 조건 스크립트는 첫 대상을 찾으면 그 자리에서 답을 내고 끝난다. 그래서 10초 한도가 진짜로 위험한 이유는 "일감이 없을 때 오래 걸린다"가 아니라, 대상이 스캔 순서에서 늦게 나오면 그 대상이 데몬에게 보이지 않는다는 것이다(확인 사실 9). 지금 최악 경로가 12.4~13.4초이므로 그 여백은 이미 음수다. 오늘 네 번의 타임아웃이 잘못된 행동으로 이어지지 않은 것은 그때 마침 대상이 없었기 때문일 뿐, 판정이 옳아서가 아니다.

### 확인 사실

2026-08-04 기준으로 이 저장소 작업 트리, `~/Git/claude-heartbeat`, `~/.claude/heartbeat`의 실제 파일에서 직접 읽거나 직접 측정한 값이다. 추정으로 적은 항목은 없다. 저장소에 미커밋 변경이 있으므로 줄 번호는 작업 트리 기준이다.

1. **데몬은 조건 검사를 10초에 끊고, 그 한도는 하드코딩이다.** `~/Git/claude-heartbeat/src/heartbeat/core.py:247`이 `subprocess.run(condition, shell=True, capture_output=True, timeout=10)`이다. 잡 문법의 `timeout` 필드는 이 자리가 아니라 세션 실행에 쓰인다(`:355`·`:416`). 초과하면 `:251`이 `condition 타임아웃 (10s) → 안전을 위해 skip`을 남기고 `_check_condition`이 거짓을 돌려주므로, 잡은 실행되지 않는다(`:373`~`:374`). fail-closed다.

2. **그 타임아웃이 실제로 났다.** `~/.claude/heartbeat/heartbeat_20260804.log`에 `안전을 위해 skip` 줄이 4건 있고, 전부 `wf-architect-Users-catze-project-workflow-labs` 잡이다(로컬 시각 20:46:17·21:38:05·21:54:05·22:12:11). 같은 날 기획자·개발자 잡에는 한 건도 없고, 8월 2일·3일 로그에는 아예 없다.

3. **재현된다.** 저장소의 `.workflow`를 임시 디렉터리로 복사하고, 모든 아이디어를 참조하는 기획서 한 장과 모든 결정을 참조하는 작업 한 장을 넣어 조기 종료가 걸리지 않게 만든 뒤 세 역할을 쟀다. 설치본(`.workflow/rules/wf-eligible.sh`, `condition_script_version: 6`) 기준 planner 1.35s · architect 12.67s · developer 0.47s. 작업 트리 본문(`heartbeat_condition.rs:20`의 `CONDITION_SCRIPT_VERSION = 7`) 기준 1.47s · 12.41s · 0.48s. 아키텍트만 한도를 넘고, 두 버전 모두 넘는다. 측정 환경은 사용자의 macOS 개발 기기다.

4. **비용을 끄는 것은 문서 수가 아니라 결정 수의 곱이다.** 같은 픽스처에서 결정 파일만 30·60·90·122건으로 두고 아키텍트 분기를 재면 6.08s·8.73s·10.51s·13.37s다. 결정을 122건으로 둔 채 작업 파일을 97건에서 20건으로 줄이면 13.12s에서 12.24s로 거의 변하지 않는다.

5. **그 곱이 코드에 그대로 있다.** `.workflow/rules/wf-eligible.sh:144`~`:174`의 아키텍트 분기는 결정 파일 하나를 볼 때마다(`:144`) 같은 디렉터리 전체를 다시 훑어 "더 늦은 결정이 있는가"를 판정한다(`:159`~`:169`). 바깥 루프가 실제로 도는 횟수는 `outcome: approved`이면서 `created_by: user`인 결정 수이고 지금 31건이며, 안쪽은 `decisions/`의 122건 전부다. 안쪽 한 바퀴마다 `grep` 한 번과 `sed` 최대 세 번이 새 프로세스로 뜬다(`:162`·`:164`·`:166`·`:167`). QA 결정 89건은 첫 `grep`에서 걸러지므로 한 개씩만 뜨고, 나머지 33건은 네 개씩 뜬다. 판정 한 번에 프로세스가 6천 개를 넘는다.

6. **같은 모양이 기획자 분기에도 있다.** `wf-eligible.sh:124`~`:132`가 같은 "더 늦은 결정" 판정을 같은 방식으로 한다. 바깥 루프가 도는 것이 `outcome: revision_requested` 결정뿐이고 지금 2건이라 아직 싸다. 작업 트리의 v7 본문은 이 안쪽 루프에 `created_by` 읽기를 두 줄 더했다(설치본과의 차이가 그것뿐이다). 수정 요청이 쌓이면 같은 자리에서 같은 일이 난다.

7. **문서는 사이클마다 는다.** 이 워크플로우의 `created_at` 기준 하루 생성량은 8/1·8/2·8/3·8/4 순으로 아이디어 2·10·4·16, 기획서 2·7·9·15, 결정 2·19·40·61이다. 작업 문서는 `created_at`을 싣지 않아 같은 방식으로 셀 수 없다. 현재 총량은 아이디어 32·기획서 33·작업 96·결정 122·보고서 144다.

8. **가장 큰 디렉터리가 가장 싸다.** `reports/` 144건은 조건 스크립트가 한 번도 읽지 않고, 앱은 `count_markdown_files`(`fs_project_repository.rs:1719`)로 디렉터리 목록만 세어 개수를 낸다(`:1715`). 문서 수가 곧 비용이라는 가정이면 설명되지 않는 자리다.

9. **판정은 첫 대상에서 끝난다.** 세 분기 모두 대상을 찾는 즉시 `verdict eligible 0`으로 종료한다(`wf-eligible.sh:106`·`:137`·`:173`·`:194`). 그래서 답이 나오는 시각은 대상이 스캔 순서의 어디에 있는지에 달렸고, 10초를 넘겨서야 닿는 대상은 데몬에게 "일감 없음"과 구별되지 않는다. 지금 최악 경로가 12.4~13.4초이므로(확인 사실 3) 이 여백은 이미 음수다. 현재 상태에서는 세 잡 모두 조기 종료가 걸려 `eligible`을 낸다(`~/.claude/heartbeat/state.json`의 세 잡 항목).

10. **스킵 사유는 이미 화면까지 온다.** `core.py:373`~`:376`이 사유를 로그와 `last_condition_output`에 남기고, `heartbeat_status.rs:132`가 그 값을 읽으며, 같은 파일의 테스트가 `condition 타임아웃 (10s)` 원문을 다룬다(`:491`). 부족한 것은 표시가 아니라 타임아웃이 나지 않는 것이다.

11. **앱은 2.5초마다 프로젝트를 통째로 다시 읽는다.** `src/features/projects/application/useProjectWorkspace.ts:419`~`:422`가 `2_500`ms 간격으로 `inspect`와 `readIntegrations`를 부른다. `inspect`(`fs_project_repository.rs:100`)는 `summary_from_manifest`(`:697`)를 거쳐 `PreparedWorkflow::read`(`:764`)로 문서를 매번 새로 읽는다. 캐시는 없다.

12. **그 재읽기가 세 디렉터리를 두 번씩 훑는다.** 결정은 `read_spec_decisions`(`:1562`)와 `qa_decision_events`(`:1475`), 기획서는 `read_markdown_summaries`(`:982`)와 `spec_references`(`:1024`), 작업은 `read_markdown_summaries`(`:1002`)와 `task_dependency_graph`(`:1304`)다. 아이디어는 한 번이다. 지금 문서량이면 폴링 한 번에 파일 본문 읽기가 (33+96+122)×2 + 32 = 534회다. 두 번 훑는 이유는 코드가 적어 두었다 — 작업 쪽은 목록 요약이 선언을 담지 않기 때문이고(`:769`~`:770`), 결정 쪽은 두 함수가 모으는 형태가 달라 합치면 두 결과 타입을 동시에 들고 다녀야 하기 때문이다(`REPORT-TASK-023-DEV`의 "QA 스캔을 latest_spec_decisions와 합치지 않았다").

13. **완료 문서를 스캔 경로에서 빼면 다섯 개의 판정이 깨진다.** 전부 문서 사이의 참조를 세는 판정이다.
    - 기획자·아이디어 처리 여부: `wf-eligible.sh:104`가 `specs/*.md`에서 `source_idea_id`를 찾는다. 앱 쪽은 `spec_references`(`fs_project_repository.rs:1024`)다.
    - 기획자·수정 요청 응답 여부: `wf-eligible.sh:135`가 `specs/*.md`에서 `source_decision_id`를 찾는다.
    - 아키텍트·분해 여부: `wf-eligible.sh:171`이 `tasks/*.md`에서 `source_decision_id`를 찾는다. 완료 작업을 치우면 그 승인이 미분해로 보여 이중 분해가 난다. 아이디어가 지목한 사고다.
    - 개발자·선행 충족: `task_file`(`:67`~`:69`)이 `tasks/*.md`에서 선행 작업 문서를 찾고 `dep_satisfied`(`:72`~`:74`)가 그 문서의 `status`가 `qa_waiting`·`completed`인지 본다. 완료 작업을 치우면 문서를 찾지 못해 미충족이 되고(`:190`), 그 작업에 매달린 후행 작업이 전부 닫힌다. 아이디어가 든 예보다 이쪽이 더 직접적이다.
    - QA 이벤트 병합: `merge_qa_decision_events`(`fs_project_repository.rs:1519`)가 `decisions/`의 QA 결정을 작업 타임라인에 합친다. QA 결정을 치우면 완료된 작업의 이력이 화면에서 빈다.

14. **판정은 조회 시점 파생이고 어디에도 저장하지 않는다는 것이 계약이다.** `docs/file-contract.md:79`가 아이디어 상태를 "조회 시점 파생이며 앱은 아이디어 파일을 쓰지 않는다"고 적고, `:172`가 의존 충족을 "읽는 시점의 파생이며 어디에도 저장하지 않는다"고 적으며 "이 정의는 계약 문서·조건 스크립트·앱·에이전트 세션에서 모두 같다"고 못박는다.

15. **두 판정이 같은 답을 내야 하고 테스트가 그것을 고정한다.** `role_eligibility.rs:167`의 `assert_matches_condition_script`가 세 역할 각각에 대해 앱의 판정과 스크립트의 종료 코드를 대조한다. 앱 판정은 파일을 만지지 않고 값만 받는다(`:48`의 `pending_role_work`, `:128`의 `has_developer_work`).

16. **스크립트 본문은 플랫폼별 두 벌이고 버전이 함께 움직인다.** `heartbeat_condition.rs:20`의 `CONDITION_SCRIPT_VERSION = 7`, `:27`의 `CONDITION_SCRIPT_SH`, `:253`의 `CONDITION_SCRIPT_PS1`이고 두 본문 안에도 `# condition_script_version: 7` 줄이 있다. 그 셋의 일치를 테스트가 단언한다(`:836`~`:837`). 판정을 고치면 이 넷이 한 묶음으로 움직인다.

17. **지금 열린 작업과 겹치는 자리가 있다.** TASK-096이 `in_progress`(SPEC-029), TASK-099·TASK-100이 `todo`(SPEC-031)다. TASK-097·TASK-098은 `completed`가 됐다. 그리고 `status: user_review`인 SPEC-032가 손대겠다고 적은 자리는 `heartbeat_condition.rs`·`role_eligibility.rs`·`project_instructions.rs`인데, 이 기획서가 손대는 자리와 같다. 두 기획서가 모두 승인되면 같은 파일에서 만난다.

### 포함 범위

- 조건 스크립트 세 역할 분기가 데몬의 10초 한도 안에서, 여유를 두고 답을 낸다.
- 그 여유가 문서가 늘어도 유지된다. 판정 비용이 컬렉션 크기의 곱으로 늘지 않는다.
- 비용을 줄여도 세 역할의 판정 결과가 지금과 같다.
- 앱의 조회 재읽기에서 이유가 사라진 중복 훑기를 걷어낸다(범위는 확인 필요 4번에서 정한다).
- 판정 비용의 회귀를 사람이 다시 발견하지 않도록, 한도 대비 여유가 검증 가능한 형태로 남는다.

### 제외 범위

- 완료 문서를 다른 디렉터리로 옮기는 아카이브. 확인 필요 1번에서 사용자가 뒤집을 수 있다.
- `.workflow` 안에 파생 인덱스 파일을 두는 일. 확인 필요 2번에서 사용자가 뒤집을 수 있다.
- 데몬의 10초 한도 자체를 바꾸거나 설정 가능하게 만드는 일. claude-heartbeat 저장소 몫이고 2026-08-03 사용자 결정으로 그 저장소는 별도 백로그다. 한도를 늘리는 것은 이 기획서가 답하려는 문제를 미루기만 한다.
- 역할 세션이 읽는 문서 양과 토큰을 줄이는 일(아이디어의 아픈 지점 3). 원인이 다르고 계약·세션 판단의 자리다.
- 타임아웃 사유를 화면에 더 잘 보이게 하는 일. 확인 사실 10대로 이미 화면까지 온다.
- 문서 스키마 변경·마이그레이션. 앱 마이그레이션 흐름의 자리다.
- 판정 규칙 자체의 변경. 무엇이 자격인지는 그대로 두고 같은 답을 더 싸게 낸다. SPEC-032가 겹침 규칙을 더하려는 것과 이 기획서는 별개이며, 두 기획서가 규칙에 대해 서로 다른 말을 하지 않는다.
- 앱의 폴링 주기 자체를 바꾸는 일. 2.5초라는 값의 적정성은 이 기획서가 답하는 질문이 아니다.

## 요구사항 명세

### R1. 판정이 한도 안에서 여유를 두고 끝난다

- 조건 스크립트의 세 역할 분기가, 대상이 없어 조기 종료가 걸리지 않는 최악 경로에서도 목표 상한 안에 끝난다. 상한 값은 확인 필요 3번에서 정한다.
- 기준선은 확인 사실 3의 측정값이다. 같은 픽스처·같은 방법으로 잰 값을 전후로 비교한다.
- 아키텍트 분기가 이번 회차의 대상이다. 확인 사실 2가 실제로 끊긴 유일한 잡이고 확인 사실 3이 유일하게 한도를 넘는 분기다.

### R2. 여유가 문서가 늘어도 유지된다

- 판정 비용이 컬렉션 크기의 곱으로 늘지 않는다. 확인 사실 4·5가 지금의 곱이 어디서 나오는지 짚는다.
- 문서량을 지금의 여러 배로 부풀린 픽스처에서도 R1의 상한을 지킨다. 배수는 확인 필요 3번에서 상한과 함께 정한다.
- 확인 사실 6의 기획자 분기도 같은 모양을 갖고 있다. 아키텍트 분기만 고치고 같은 모양을 남겨 두면 수정 요청이 쌓이는 날 같은 사고가 난다.

### R3. 판정 결과가 달라지지 않는다

- 세 역할의 판정 답이 지금과 같다. 자격 규칙은 바뀌지 않는다.
- 특히 "오래된 미답변 수정 요청이 영영 보이지 않는다"는 종류의 누락이 생기지 않는다. 아이디어가 스캔 상한·조기 종료 방식에 붙인 조건이고, 어떤 방식을 택하든 이 요구가 남는다.
- 만료 lease를 선점으로 세지 않는 규칙, 읽을 수 없는 표기를 선점으로 세지 않는 규칙, 판정이 lease 파일을 읽기만 하는 규칙이 그대로다.
- 확인 사실 14의 계약 문장이 그대로 성립한다. 판정은 조회 시점 파생이고, 그 결과를 문서에 되쓰지 않는다.

### R4. 두 판정이 계속 같은 답을 낸다

- 조건 스크립트와 앱의 같은 판정이 같은 답을 낸다. 확인 사실 15의 대조 테스트가 통과한다.
- 스크립트를 고치면 두 플랫폼 본문을 모두 고치고, `CONDITION_SCRIPT_VERSION`과 두 본문의 버전 줄을 함께 올린다(확인 사실 16).
- 앱 판정은 지금처럼 파일을 만지지 않는다. 필요한 값은 읽는 쪽이 모아서 넘긴다.
- 두 구현의 알려진 차이 목록에 새 차이가 생기면 그 자리에 적는다. 적지 않은 차이를 남기지 않는다.

### R5. 참조 무결성이 그대로다

- 확인 사실 13의 다섯 판정이 전부 지금과 같은 답을 낸다.
- 문서를 스캔 경로에서 빼는 방식을 쓴다면, 그 다섯 판정 전부가 빠진 문서까지 보거나 판정 키가 함께 바뀌어야 한다. 하나라도 남으면 이중 분해나 후행 작업 동결이 난다.
- 확인 필요 1·2번을 제안대로 정하면 이 요구는 "아무것도 옮기지 않는다"로 자동 충족된다. 뒤집을 경우 이 요구가 그 작업의 완료 조건이 된다.

### R6. 파생물을 둔다면 파일이 진실이다

- 이 요구는 확인 필요 2번을 뒤집어 파생 인덱스를 둘 때만 적용된다.
- 인덱스가 없거나 깨졌거나 낡았을 때도 판정이 성립한다. 인덱스는 빠른 길일 뿐 유일한 길이 아니다.
- 어긋나면 재생성으로 복구된다. 사람이 손으로 고치는 자리가 생기지 않는다.
- 갱신 주체가 하나로 정해진다. 역할 세션은 앱을 거치지 않고 문서를 직접 편집하므로, 앱만 인덱스를 갱신하면 세션이 문서를 쓴 직후가 가장 어긋난 순간이 된다 — 그리고 그 순간이 바로 판정이 돌아야 하는 순간이다. 아이디어가 "핵심 확인 필요"로 짚은 자리다.
- 인덱스는 앱 소유 상태가 되고, 역할 세션은 그것을 쓰지 않는다.

### R7. 조회 재읽기에서 이유가 사라진 중복이 사라진다

- 범위는 확인 필요 4번에서 정한다.
- 확인 사실 12의 세 쌍 각각에 대해, 두 번 훑는 이유가 지금도 유효한지 확인하고 유효하지 않은 것만 하나로 합친다. 이유가 유효한 것은 그대로 둔다.
- 합쳐도 조회 결과가 지금과 같다. 화면에 보이는 값이 한 글자도 달라지지 않는다.
- 폴링 주기는 그대로다.

### R8. 회귀가 사람의 눈에 다시 의존하지 않는다

- 판정 비용이 다시 한도에 다가가는 것을 사람이 로그에서 발견하는 방식이 아닌 형태로 잡는다. 형태는 아키텍트가 정한다.
- 오늘의 실패는 사용자가 로그를 읽어서 발견됐다. 확인 사실 2의 네 건은 그 전에 아무 데서도 드러나지 않았다.
- 이 요구는 판정 규칙을 바꾸지 않는다.

### R9. 지금 되는 것이 그대로 된다

- 세 역할의 자격 판정, 선행 판정, 아이디어 상태 판정, QA 이벤트 병합이 지금과 같은 값을 낸다.
- 조건 스크립트가 여전히 사유 코드를 표준 출력 첫 줄이자 유일한 줄로 낸다. 데몬이 그 줄을 `last_condition_output`으로 옮기고 앱이 문장으로 옮기는 경로가 그대로다(확인 사실 10).
- 조건 스크립트가 여전히 `.workflow` 아래에 아무것도 쓰지 않는다.
- 기존 자동 테스트가 삭제되거나 비활성화되지 않는다.
- 확인 사실 17 때문에, 이 기획서의 작업은 열려 있는 TASK-096·TASK-099·TASK-100과 파일이 겹치지 않도록 분해되거나 순서가 지어진다. SPEC-032가 먼저 승인되면 그 작업들과 같은 파일에서 만나므로, 나중에 서는 쪽이 선행 선언으로 순서를 적는다.

## 확인 필요

사용자 결정이 필요한 항목이다. 승인 시 아래 제안대로 진행한다.

1. **아이디어의 본안인 아카이브(완료 문서를 스캔 경로에서 제외)를 이번 범위에 넣을지.**

   제안: 뺀다. 근거는 측정이다. 확인 사실 4에서 작업 문서를 97건에서 20건으로 줄여도 아키텍트 분기가 13.12초에서 12.24초로밖에 안 줄었고, 확인 사실 8에서 가장 큰 디렉터리인 `reports/` 144건은 판정 비용이 0이다. 즉 완료 문서를 치워도 오늘의 타임아웃은 사라지지 않는다. 반대로 비용은 크다 — 확인 사실 13대로 옮김이 깨뜨리는 판정이 다섯 개고, 그중 개발자 선행 판정은 완료 작업이 사라지는 순간 후행 작업 전체를 닫는다. 얻는 것이 확인되지 않은 수술이다.

   비용: 문서는 계속 는다(확인 사실 7). 곱을 없애도 선형 성장은 남으므로, 언젠가는 문서 총량 자체가 문제가 되는 날이 온다. 그날 이 논의를 다시 해야 한다. 지금 하지 않는 것은 "필요 없다"가 아니라 "지금은 근거가 없다"이다.

   대안: 지금 아카이브까지 함께 한다. 뒤집기로 하면 R5가 그 작업의 완료 조건이 되고, 다섯 판정 전부가 아카이브 디렉터리까지 보도록 조건 스크립트 두 본문·앱·계약이 같이 움직인다. 범위가 이 기획서의 두 배 이상이 되고, 참조를 하나라도 놓치면 이중 분해나 작업 동결로 드러난다.

2. **파생 인덱스를 둘지, 판정이 같은 디렉터리를 반복해서 훑지 않게 고칠지.**

   제안: 반복 훑기를 없애는 쪽으로 간다. 새 파일을 만들지 않는다. 근거는 셋이다. 첫째, 측정이 그 자리를 지목한다 — 확인 사실 5의 곱이 사라지면 확인 사실 3의 12.4초가 결정 수에 비례하는 선형 비용으로 내려간다. 둘째, 파생 인덱스는 갱신 주체 문제를 푸는 대가가 크다. 역할 세션은 앱을 거치지 않고 문서를 직접 쓰므로(공통 규칙 §5·§6), 앱만 갱신하는 인덱스는 세션이 문서를 쓴 직후 — 판정이 돌아야 하는 바로 그 순간 — 가장 어긋난다. 셋째, 확인 사실 14의 계약이 "판정은 조회 시점 파생이고 어디에도 저장하지 않는다"를 네 자리(계약·스크립트·앱·세션)에서 같다고 못박고 있어, 인덱스는 그 문장과의 관계를 새로 정의해야 한다.

   비용: 조건 스크립트는 POSIX sh와 PowerShell 두 벌이고 연관 배열이 없다. 반복 훑기를 없애려면 두 본문에서 한 번 훑고 결과를 들고 다니는 방식을 각각 짜야 하며, 그것이 지금 본문보다 읽기 어려울 수 있다. 확인 사실 16대로 두 본문과 버전이 한 묶음으로 움직이므로 변경 면도 작지 않다.

   대안: 파생 인덱스를 둔다. 뒤집기로 하면 R6이 살아나고, 갱신 주체·복구 경로·계약 문장과의 관계를 그 작업이 먼저 정해야 한다. 판정 비용은 더 크게 떨어질 수 있지만, 진실이 두 곳에 있는 상태를 이 저장소가 처음으로 갖게 된다.

   또 하나의 대안: 스캔에 상한을 두거나 조기 종료한다(예: 최근 N일분 결정만). 아이디어가 든 방향인데 제안에서 뺐다. R3이 요구하는 "오래된 미답변 수정 요청이 영영 안 보이지 않는다"는 근거를 대기 어렵고, 반복 훑기를 없애면 상한 없이도 답이 나오기 때문이다.

3. **목표 상한과 성장 여유를 얼마로 둘지.**

   제안: 최악 경로 3초, 그리고 지금 문서량의 3배 픽스처에서도 그 3초를 지킨다. 근거는 한도가 10초이고(확인 사실 1) 측정이 사용자의 개발 기기 한 대에서 나왔다는 것이다. 데몬이 도는 환경이 더 느릴 수 있고 다른 프로세스와 CPU를 나눠 쓰므로, 한도의 30%를 상한으로 두면 3배 이상 느린 환경에서도 살아남는다. 3배 문서량은 확인 사실 7의 성장 속도로 대략 사나흘 치다.

   비용: 3초는 지금 아키텍트 분기(12.4초)의 4분의 1이 아니라 4분의 1보다 낮은 값이다. 곱을 없애는 것만으로 닿지 못하면 추가 작업이 필요할 수 있고, 그때 확인 필요 2번의 대안이 다시 올라온다.

   대안: 상한을 더 느슨하게(예: 5초) 잡는다. 도달은 쉬워지고 여유는 줄어든다. 또는 상한을 두지 않고 "지금보다 빠르면 된다"로 둔다 — 그러면 R1이 검증할 수 없는 요구가 되고, 오늘과 같은 실패가 언제 다시 오는지 아무도 모른다.

4. **앱 조회 쪽(2.5초 폴링)을 어디까지 넣을지.**

   제안: 확인 사실 12의 세 쌍 중 "두 번 훑는 이유가 지금은 유효하지 않은 것"만 합치고, 캐시·증분 읽기·폴링 주기 변경은 넣지 않는다. 근거는 이 자리에 아직 측정된 실패가 없다는 것이다. `REPORT-TASK-023-DEV`의 경고는 문서 20건 시점의 것이고 성능 사고의 기록이 아니다. 고장 나지 않은 것을 고치지 않는다는 원칙과, 오늘 실제로 끊긴 자리에 노력을 집중한다는 판단이다.

   비용: 폴링 한 번에 534회 읽기(확인 사실 12)는 그대로 문서 수에 비례해 는다. 이 결정은 그 성장을 늦출 뿐 멈추지 않으므로, 화면이 느려지는 날 이 항목이 다시 올라온다.

   대안 1: 아예 넣지 않는다. 이 기획서를 조건 스크립트 한 자리로 좁힌다. 범위가 작아지고 검증이 단순해진다.

   대안 2: 캐시나 증분 읽기까지 넣는다. 뒤집기로 하면 무엇이 바뀌었는지 아는 문제(파일 감시·변경 시각 비교)가 새로 생기고, 확인 사실 14의 "조회 시점 파생" 계약과 다시 만난다. 확인 필요 2번의 대안과 사실상 같은 결정이므로 둘을 함께 정하는 편이 낫다.

## 기대효과

- 아키텍트 역할 잡이 다시 뜬다. 확인 사실 2의 네 번은 세션이 기동조차 못 한 시간이고, 그 시간에 분해를 기다리는 승인이 있었는지는 확인할 방법이 없다.
- 판정이 거짓말하지 않는다. 확인 사실 9대로 지금은 대상이 스캔 순서에서 늦게 나오면 "일감 없음"과 구별되지 않는다. 여유가 생기면 그 구별이 돌아온다.
- 문서가 느는 속도가 판정 수명을 정하지 않는다. 곱이 선형이 되면 확인 사실 7의 성장이 같은 사고를 다시 만드는 시점이 크게 밀린다.
- 데몬이 같은 프로젝트의 세션을 여럿 띄우게 되는 날에도 전제가 선다. 병렬은 스캔 빈도를 곱하므로, 지금 상태로 병렬을 켜면 타임아웃이 더 자주 난다. SPEC-032가 병렬의 안전장치를 만드는 것과 이 기획서가 병렬의 비용을 감당 가능하게 만드는 것이 같은 자리에서 만난다.
- 아카이브라는 큰 수술을 근거 없이 하지 않아도 된다. 확인 사실 13의 다섯 판정을 건드리지 않고 오늘의 실패를 닫는다.

## 완료 조건

1. 조건 스크립트 세 역할 분기가, 조기 종료가 걸리지 않는 최악 경로에서 확인 필요 3번의 상한 안에 끝난다. 검증: 확인 사실 3과 같은 방법(임시 디렉터리 픽스처, 모든 대상을 처리 완료로 만든 상태)으로 재고 전후 값을 보고서에 적는다. 기준선은 planner 1.47s · architect 12.41s · developer 0.48s다.
2. 문서량을 확인 필요 3번이 정한 배수로 부풀린 픽스처에서도 같은 상한을 지킨다. 검증: 같은 방법으로 재고 값을 보고서에 적는다.
3. 세 역할의 판정 결과가 이 저장소의 실제 문서에서 전후로 같다. 검증: 착수 전과 착지 후에 세 역할을 각각 실행해 사유 코드와 종료 코드를 대조하고 보고서에 적는다.
4. 확인 사실 15의 대조 테스트가 통과한다. 판정 규칙을 바꾸지 않았으므로 기존 시나리오가 수정 없이 통과해야 한다. 검증: `role_eligibility.rs`의 기존 테스트.
5. 조건 스크립트 두 플랫폼 본문이 같은 규칙을 담고, `CONDITION_SCRIPT_VERSION`과 두 본문의 버전 줄이 함께 올라간다. 검증: 확인 사실 16의 일치 단언 테스트가 새 값에서 통과한다.
6. 확인 사실 13의 다섯 판정이 전부 지금과 같은 답을 낸다. 검증: 각 판정을 덮는 기존 테스트가 수정 없이 통과하고, 문서를 옮기지 않았다는 사실을 보고서에 적는다.
7. 확인 사실 6의 기획자 분기에도 같은 모양이 남지 않는다. 검증: 수정 요청 결정을 여럿 만든 픽스처에서 기획자 분기가 상한 안에 끝난다.
8. 조건 스크립트가 `.workflow` 아래에 아무것도 쓰지 않는다. 검증: 실행 전후로 `.workflow` 아래 파일 목록과 내용이 같다는 확인을 보고서에 적는다.
9. 사유 코드가 여전히 표준 출력의 첫 줄이자 유일한 줄이다. 검증: 세 역할 실행의 표준 출력이 한 줄인지 확인한다.
10. 확인 필요 4번에서 정한 범위대로 조회 재읽기의 중복이 정리되고, 조회 결과가 지금과 같다. 검증: `fs_project_repository.rs`의 기존 테스트가 수정 없이 통과한다.
11. R8의 회귀 감지 장치가 선다. 검증: 그 장치가 지금 문서량에서 통과하고, 상한을 넘긴 픽스처에서 실패하는 것을 확인한다.
12. 기존 자동 테스트가 삭제되거나 비활성화되지 않는다. 검증: 테스트 목록 변경분을 확인한다.
13. 이 기획서의 작업이 TASK-096·TASK-099·TASK-100과 같은 파일에서 병행되지 않고, SPEC-032의 작업과 만나는 경우 나중에 서는 쪽이 선행 선언으로 순서를 적는다. 검증: 분해 결과의 선행 선언과 작업 범위를 보고서에 적는다. 확인 사실 17이 근거다.
