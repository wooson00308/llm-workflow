# 하트비트 설치 안내의 단계별 마법사화

## 기획 내용

지금 하트비트 카드의 미설치 안내는 명령 두 줄이다. `pip install claude-heartbeat`와 `heartbeat init`, 그리고 저장소 링크 한 줄(`HeartbeatCard.tsx:246-252`). 처음 설치하는 사용자는 이 두 줄을 따라간 뒤 자기가 어디쯤 왔는지 앱에서 확인할 방법이 없다. 아이디어가 지적한 문제가 이것이고, 이 기획서가 그것을 단계별 체크리스트로 바꾼다.

다만 조사해 보니 문제가 "진행 상황이 안 보인다" 하나가 아니었다. 지금 안내는 틀렸다기보다 **모자란다**. 실제 도구가 요구하는 단계는 넷인데(`heartbeat --help`: `init`, `install-service`, `install`) 안내는 그중 둘만 적는다. 빠진 것이 `heartbeat install-service` — OS 스케줄러(launchd / Task Scheduler / systemd)에 데몬을 등록하는 단계다. 이 단계를 건너뛴 사용자는 두 줄을 다 따라 했는데도 데몬이 뜨지 않고, 카드는 "설치됨 · 데몬 미실행"을 띄운 채 더 이상 아무것도 안내하지 않는다. 그 상태에서 안내 블록은 이미 사라진 뒤다. 미설치 분기에만 안내가 붙어 있기 때문이다.

그래서 이 기획서는 마법사를 "미설치일 때 더 친절하게 보여주는 화면"으로 잡지 않는다. **필수 단계 중 하나라도 안 끝났으면 남은 단계를 보여주는 화면**으로 잡는다. 그렇지 않으면 지금 실제로 사람이 막히는 지점(등록 안 한 채 설치됨으로 보이는 상태)이 마법사를 만들고도 그대로 남는다.

감지 쪽은 새로 발명할 것이 많지 않다. 앱은 이미 세 신호를 각각 읽고 있다 — `~/.claude/HEARTBEAT.md`, `~/.claude/heartbeat/`, `~/.claude/heartbeat/heartbeat.pid`. 문제는 읽은 뒤 셋을 OR로 접어 `installed` 한 값으로 만든다는 것이다(`heartbeat_status.rs`의 `installation_of`). 즉 앱은 어디까지 됐는지를 모르는 게 아니라, 알 수 있는 것을 버리고 있다. 마법사가 할 일의 큰 부분은 그 접기를 푸는 것이다.

접혀 있는 값을 푸는 것만으로는 안 되는 단계가 둘 있다.

하나는 **패키지 설치**다. `pip install`은 `~/.claude` 아래에 아무 흔적도 남기지 않는다. 남는 흔적은 PATH 어딘가의 실행 파일뿐인데, 이건 앱이 판정하면 안 된다. GUI로 띄운 앱의 PATH는 로그인 셸의 PATH와 다르다. 근거는 도구 자신이 제공한다 — `install-service`가 만드는 launchd plist는 `EnvironmentVariables`에 PATH를 통째로 박아 넣는다. 스케줄러가 물려주는 환경으로는 `heartbeat`를 못 찾는다는 것을 도구가 이미 알고 그렇게 대응하고 있다는 뜻이다. 앱이 PATH를 훑으면 설치해 둔 사용자에게 "미설치"라고 말하는 오탐이 나온다. 이건 지금 없는 문제를 새로 만드는 쪽이다. 그래서 이 단계는 독립 감지를 하지 않고, 뒤 단계가 끝났다는 사실에서 역으로 함의한다. `heartbeat init`이 돌았다면 패키지는 있는 것이다.

다른 하나는 **서비스 등록**이다. 이건 아티팩트가 `~/.claude` 밖에 있고 플랫폼마다 다르다. macOS는 확인됐다. `heartbeat install-service --print-only`가 `~/Library/LaunchAgents/com.claude-heartbeat.plist`를 Label `com.claude-heartbeat`로 만든다고 그대로 출력한다. Linux(systemd user unit)와 Windows(Task Scheduler)의 아티팩트 위치는 이 조사에서 확인하지 못했다. 특히 Windows는 등록물이 파일이 아니라 스케줄러의 항목이라, 파일 존재 판정이 아예 성립하지 않을 수 있다. 여기서 선택지가 갈리므로 확인 필요 2번으로 올린다.

그리고 이 문제는 방금 승인된 SPEC-015(DECISION-EEEEB81D)와 맞물린다. 그 기획서가 연동의 Windows 차단을 푼다. 차단이 풀리면 Windows 사용자가 이 마법사를 처음 만나는 사람이 되는데, 그때 마법사가 macOS 기준 명령과 경로를 보여주면 안 된다. 순서 의존이 생긴다.

마지막으로 아이디어가 제안한 "다시 확인" 버튼은 이미 있는 것과 겹친다. 통합 상태는 프로젝트가 열려 있는 동안 2.5초마다 자동으로 다시 읽힌다(`useProjectWorkspace.ts:329`). 사용자가 터미널에서 명령을 치고 앱으로 돌아오면 체크는 이미 채워져 있다. 버튼을 달면 "눌러야 갱신되는 것처럼 보이는" 잘못된 모델을 심는다. 그래서 이 기획서는 버튼 대신 **자동으로 확인 중이라는 사실을 화면에 밝히는 쪽**을 기본안으로 둔다(확인 필요 3번).

### 확인 사실

- 현재 미설치 안내는 `pip install claude-heartbeat` + `heartbeat init` 두 줄과 저장소 링크가 전부다(`HeartbeatCard.tsx:246-252`).
- 도구의 하위 명령은 `init`, `start`, `stop`, `status`, `once`, `jobs`, `skills`, `install`, `install-service`, `uninstall-service`다. 설치 경로에 필요한 것은 `init` → `install-service` → (선택) `install dream`이다.
- `heartbeat init`은 `~/.claude/HEARTBEAT.md`를 만든다. 앱은 이 파일을 이미 읽는다.
- `heartbeat install-service --print-only`는 등록 없이 등록물만 출력한다. macOS 결과는 `~/Library/LaunchAgents/com.claude-heartbeat.plist`, Label `com.claude-heartbeat`, 로드 명령 `launchctl load <plist 경로>`다.
- 설치 판정은 `HEARTBEAT.md` 존재 · `heartbeat/` 존재 · `heartbeat.pid` 존재의 OR다(`heartbeat_status.rs`의 `installation_of`). 셋 중 아무거나 하나면 "설치됨"이 된다.
- `daemonRunning`은 pid 파일 존재만 본다. 프로세스 생존도, 서비스 등록 여부도 확인하지 않는다(`types.ts:195-204`).
- dream 스킬 판정은 `~/.claude/skills/dream/SKILL.md` 존재이고 dream 카드가 이미 한다(`heartbeat_dream.rs`). 로컬 확인 결과 `heartbeat skills`는 `[✓] dream`을 보고한다.
- 통합 스냅샷은 2.5초 주기로 자동 재조회된다(`useProjectWorkspace.ts:329`).
- 클립보드 플러그인은 지금 의존성에 없다(`@tauri-apps/plugin-clipboard-manager` 없음). 복사 수단은 새로 정해야 한다.
- SPEC-015가 승인되어(DECISION-EEEEB81D) 연동의 Windows 차단 해제와 플랫폼별 실행 자산 설치가 예정돼 있다.
- SPEC-009 파생 TASK-028~031이 같은 카드의 **설치됨** 분기(쿼터 표시·소진 경고)를 작업 중이다. 이 기획서는 그 반대편 분기를 만진다.

### 포함 범위

- 하트비트 카드의 설치 안내를 4단계 체크리스트로 바꾼다: 패키지 설치 → `heartbeat init` → `heartbeat install-service` → (선택) dream 스킬.
- 단계별 완료 감지 기준을 정의하고, 접혀 있는 설치 판정을 단계별로 펼쳐 화면 payload에 싣는다.
- 감지할 수 없는 단계를 완료로도 미완료로도 단정하지 않는 표시 상태를 만든다.
- 각 단계에 실행할 명령 원문과 복사 수단을 붙인다.
- 마법사 표시 조건을 "미설치"에서 "필수 단계 중 미완료 있음"으로 넓힌다.
- 자동 재감지가 돌고 있다는 사실을 화면에 밝힌다.

### 제외 범위

- 앱이 `pip`·`heartbeat`·`launchctl` 등 외부 명령을 대행 실행하는 원버튼 설치. 아이디어가 원칙으로 못박았고 이 기획서도 그대로 유지한다.
- 상태 감지를 위해 외부 명령을 실행하는 것. `heartbeat status`나 `heartbeat skills`를 불러 판정하지 않는다. 판정은 전부 파일 존재의 읽기다.
- 서비스 등록 실패의 원인 진단. `launchd_stderr.log` 같은 로그를 읽어 해석하는 것은 별건이다.
- 데몬 프로세스의 생존 확인. pid 파일이 남는 한계는 이 기획서가 고치지 않는다.
- 역할 잡 설치 폼과 관리 블록 쓰기 동작. 마법사는 도구가 준비되는 데까지만 이끌고, 그 뒤는 기존 폼이 받는다.
- dream 카드 자체의 개편. 마법사의 dream 단계는 안내와 감지만 하고 설치 UI는 dream 카드가 계속 소유한다.
- 실행 한도·쿼터 표시. SPEC-009 파생 작업의 몫이다.

## 요구사항 명세

### R1. 설치 상태가 단계별로 드러난다

앱이 이미 읽는 신호를 OR로 접어 버리지 않는다. 화면이 단계마다 그 단계의 완료 여부를 따로 알 수 있어야 한다. 지금처럼 "설치됨" 한 값만 오면 마법사가 성립하지 않는다.

기존 `installation` 값의 의미는 바꾸지 않는다. 그 값에 의존하는 배지와 다른 분기가 이미 있다. 단계 정보는 더해서 싣는다.

### R2. 단계는 넷이고 순서가 고정이다

패키지 설치 → `heartbeat init` → `heartbeat install-service` → dream 스킬. 앞 단계를 건너뛰고 뒤 단계를 할 수 없으므로 화면도 그 순서로만 보여준다. 사용자가 임의 순서로 진행했다고 가정하지 않는다.

네 번째만 선택이고 1~3은 필수다.

### R3. 감지 기준은 파일 존재뿐이다

각 단계의 완료 판정 근거는 다음과 같다.

| 단계 | 판정 근거 |
| --- | --- |
| 1. 패키지 설치 | 독립 감지하지 않는다. R5로 함의한다 |
| 2. `heartbeat init` | `~/.claude/HEARTBEAT.md` 존재 |
| 3. `heartbeat install-service` | 플랫폼별 등록 아티팩트 존재. macOS는 `~/Library/LaunchAgents/com.claude-heartbeat.plist` |
| 4. dream 스킬 | `~/.claude/skills/dream/SKILL.md` 존재 |

외부 명령을 실행해 판정하지 않는다. 없는 파일은 오류가 아니라 "그 단계가 아직 안 끝났다"이고, 읽기 실패는 R4의 확인 불가로 간다.

### R4. 감지할 수 없는 단계를 단정하지 않는다

각 단계의 표시 상태는 셋이다: 완료 · 미완료 · 확인 불가. 확인 불가는 앱이 판정 근거를 갖지 못한 상태이며, 미완료와 다른 문구로 보여준다.

이 요구는 SPEC-014 R8과 같은 성질이다. 앱이 "모른다"를 "아니다"로 번역하면 사용자는 이미 끝낸 일을 다시 하거나, 안 끝난 일을 끝난 줄 안다.

확인 불가 단계는 사용자의 진행을 막지 않는다. 다음 단계 안내가 계속 보인다.

### R5. 1단계는 뒤 단계에서 함의한다

2단계가 완료면 1단계도 완료로 본다. `heartbeat init`이 만든 파일이 있다는 것은 그 명령이 실행됐다는 것이고, 실행됐다면 패키지가 있는 것이다.

2단계가 미완료면 1단계는 확인 불가다. 미완료가 아니다. 앱은 패키지가 없다고 말할 근거가 없다.

PATH를 훑어 실행 파일을 찾지 않는다. GUI 앱의 PATH가 사용자 셸의 PATH와 다르다는 것이 도구 자신의 launchd plist에서 확인된다.

### R6. 각 단계에 실행할 명령 원문과 복사 수단이 있다

명령은 사용자가 자기 터미널에 그대로 붙여 넣을 수 있는 형태여야 한다. 화면이 조각을 다시 조립하게 만들지 않는다.

복사는 한 번의 조작으로 끝나고, 복사됐다는 사실이 사용자에게 보인다. 복사에 실패하면 실패를 알리고, 명령 원문은 여전히 화면에서 선택할 수 있어야 한다.

### R7. 재감지는 자동이고 사용자가 그것을 안다

사용자가 터미널에서 명령을 치고 앱으로 돌아오면 별도 조작 없이 체크가 채워진다. 이미 도는 자동 재조회를 쓰고, 마법사를 위해 새 폴링을 추가하지 않는다.

화면은 자동으로 확인 중이라는 사실을 밝힌다. 사용자가 "왜 안 바뀌지, 눌러야 하나" 하고 기다리지 않게 하는 것이 이 요구의 목적이다.

### R8. 안내가 데몬이 도는 상태까지 이어진다

마법사는 필수 단계 중 하나라도 미완료·확인 불가면 보인다. `installation`이 `installed`인 것만으로 사라지지 않는다.

지금 실제로 막히는 자리가 여기다. `heartbeat init`까지만 한 사용자는 "설치됨 · 데몬 미실행" 배지를 받고 안내는 잃는다. 그 상태에서 다음에 뭘 해야 하는지가 화면 어디에도 없다.

필수 3단계가 모두 완료면 마법사는 접힌다. 그 뒤의 화면은 지금과 같다.

### R9. dream 단계는 선택이고 필수 단계를 막지 않는다

dream이 미설치여도 마법사는 완료된 것으로 접힌다. dream은 없어도 워크플로우가 돈다.

이 단계는 상태와 명령만 보여주고, 설치 UI를 여기서 다시 만들지 않는다. dream 카드가 그 소유자다. 두 화면이 같은 것을 각자 그리면 갈라진다.

### R10. 명령과 경로가 그 플랫폼 기준으로 나온다

마법사가 보여주는 명령·아티팩트 경로는 앱이 도는 플랫폼의 것이다. macOS 사용자에게 systemd 경로를 보여주지 않고, 그 반대도 아니다.

SPEC-015가 연동의 Windows 차단을 풀고 나면 Windows 사용자가 이 화면을 처음 만난다. 그때 화면이 macOS 기준이면 안내가 아니라 오답이 된다.

### R11. 앱이 대행하지 않는다는 사실이 화면에 남는다

체크리스트가 되면서 "앱이 알아서 해 줄 것 같은" 인상이 생긴다. 실행은 사용자 터미널의 몫이고 앱은 안내와 감지만 한다는 문구를 유지한다. 지금 안내가 첫 줄에 두고 있는 말이다.

각 단계의 조작은 명령 복사까지이며, 실행 버튼을 두지 않는다.

## 확인 필요

1. **1단계(패키지 설치)의 독립 감지를 포기하는 것.** PATH를 훑어 `heartbeat` 실행 파일을 찾는 방법은 있지만, GUI 앱의 PATH가 셸과 달라 설치해 둔 사용자에게 미설치라고 말할 위험이 있다. 그래서 R5처럼 2단계에서 함의하고, 2단계 미완료일 때는 확인 불가로 둔다. 대신 "패키지를 이미 설치했다면 이 단계는 넘어가도 된다"는 안내가 필요해진다. 이 절충에 동의하는지 확인이 필요하다.

2. **서비스 등록 감지의 플랫폼 범위.** macOS 아티팩트만 확인됐다(`~/Library/LaunchAgents/com.claude-heartbeat.plist`). 두 안이 있다.
   - (A) macOS만 감지하고 Linux·Windows는 확인 불가로 두되 명령은 안내한다. 범위가 작고 오판정이 없다.
   - (B) 세 플랫폼의 아티팩트 경로를 이 범위에서 조사·확정한다. Windows Task Scheduler는 등록물이 파일이 아닐 수 있어 조사 결과에 따라 (A)로 되돌아올 수 있다.

   기획자 의견은 (A)다. 이 화면의 목적은 "다음에 뭘 해야 하는지 알려 주는 것"이고, 그건 감지 없이도 명령 안내로 달성된다. 감지는 확인된 플랫폼부터 채워 넣으면 된다.

3. **"다시 확인" 버튼을 두지 않는 것.** 아이디어가 제안했지만 2.5초 자동 재조회가 이미 돈다. 버튼은 없는 인과를 심는다(눌러야 갱신된다는 오해). 대신 R7처럼 자동 확인 중임을 밝히는 쪽을 기본안으로 뒀다. 버튼이 주는 통제감이 더 중요하다고 보면 되돌릴 수 있다.

4. **마법사 표시 조건을 "미설치"에서 "필수 단계 미완료"로 넓히는 것(R8).** 아이디어의 문구는 미설치 상태의 안내를 말했지만, 서비스 등록 단계를 체크리스트에 넣으라는 요구를 만족시키려면 설치됨 상태에서도 마법사가 보여야 한다. 아이디어 의도를 넓히는 해석이라 확인이 필요하다. 넓히지 않으면 지금 사람이 실제로 막히는 자리가 그대로 남는다.

5. **복사 수단의 새 의존성.** 클립보드 플러그인이 지금 없다. Tauri 클립보드 플러그인을 새로 넣을지, 웹 표준 API로 처리할지는 아키텍트가 정할 문제지만, 전자면 의존성이 하나 는다. 의존성 추가 자체를 꺼리는지 확인이 필요하다.

6. **SPEC-015와의 순서.** R10이 플랫폼별 명령·경로를 요구하는데, 플랫폼 분기의 기준은 SPEC-015가 세운다. 마법사를 먼저 만들면 macOS 기준으로 만들었다가 Windows 해제 시점에 다시 손대게 된다. SPEC-015 파생 작업 뒤에 이 기획서의 작업을 거는 것이 자연스러워 보이나, 실행 순서는 아키텍트가 SPEC-013의 의존 선언으로 건다.

## 기대효과

- 처음 설치하는 사용자가 자기가 어디까지 왔는지 앱에서 본다. 명령 두 줄을 따라간 뒤 "이제 뭘 해야 하나"를 다른 문서에서 찾지 않아도 된다.
- 지금 안내에서 빠져 있던 서비스 등록이 안내에 들어온다. 두 줄만 따라 하고 데몬이 안 뜨는 상태에서 멈추는 경로가 없어진다.
- "설치됨 · 데몬 미실행"이라는 결과만 보여 주던 자리에 원인과 다음 행동이 붙는다.
- 앱이 이미 읽고 있으면서 버리던 신호가 화면에 쓰인다. 새 감지 수단을 늘리지 않고 정보량이 는다.
- 대행 실행 없이도 설치 경험을 개선할 수 있다는 것이 확인된다. "외부 명령 비실행" 원칙과 사용성이 맞바꿀 대상이 아니라는 선례가 된다.

## 완료 조건

- 하트비트 카드가 4단계 체크리스트를 보여주고, 각 단계가 완료·미완료·확인 불가 중 하나로 표시된다.
- 각 단계의 완료 판정이 R3 표의 파일 존재에서만 나온다. 판정을 위해 실행되는 외부 명령이 없다.
- `HEARTBEAT.md`만 있고 서비스 등록이 안 된 상태에서 마법사가 보이고, 3단계가 미완료로 표시된다.
- 필수 3단계가 모두 완료면 마법사가 접히고, dream 미설치는 그 접힘을 막지 않는다.
- 각 단계의 명령을 한 번의 조작으로 복사할 수 있고, 복사 결과가 사용자에게 보인다.
- 터미널에서 `heartbeat init`을 실행한 뒤 앱을 조작하지 않아도 2단계 체크가 채워진다.
- 앱이 설치를 대행하지 않는다는 문구가 화면에 남아 있고, 실행 버튼이 없다.
- 위 항목이 자동화 테스트로 고정된다. 확인 불가 상태가 미완료로 표시되지 않는 것을 포함한다.
