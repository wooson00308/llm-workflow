# 워크플로 상태를 명령 한 번으로 조회한다

## 결정권자 요약

### 제안

워크플로의 지금 상태를 한 번의 명령으로 요약해 주는 읽기 전용 조회 도구를 추가한다.

### 바뀌는 것

- 지금: 상태를 알려면 문서 수백 건을 대조해야 한다 → 앞으로: 명령 한 번이 집계, 도장 대기, 활성 선점, 최근 실패를 한 화면으로 답한다
- 같은 명령이 사람이 읽는 출력과 세션이 읽는 출력을 함께 낸다
- 상태 판정은 새로 만들지 않고, 앱과 자격 확인 도구가 이미 쓰는 판정을 그대로 가져다 쓴다

### 비용과 위험

- 기존 판정을 가져다 쓸 수 없는 항목은 추측해서 채우지 않고 출력에서 빼기로 했으므로, 첫 판에 빠지는 항목이 생길 수 있다.
- 아무것도 쓰지 않는 조회 전용 도구라 되돌리기 쉽고, 승인되지 않으면 지금처럼 문서를 직접 읽는 방식이 그대로 남는다.

## 기획 내용

### 배경

워크플로 상태를 팔로업하려면 지금은 문서를 하나하나 읽어야 한다. 세션도 사용자와의 대화형 작업도
같은 상태를 파악할 때마다 기획서와 작업 그룹과 작업 문서를 훑고, 그만큼 컨텍스트 토큰이 나간다.
앱 화면은 이 상태를 이미 다 계산해 보여주지만, 세션이 그 결과를 받아 볼 통로가 없다.

SPEC-049가 같은 문제의 앞 절반을 이미 처리했다. 자격 확인 도구가 "일감이 있다/없다"만 답하던 것을
대상 문서와 후보별 제외 사유까지 답하도록 넓혔다. 그 답은 "지금 이 역할이 무엇을 집어야 하는가"에
한정된다. 이번 기획은 남은 절반, 곧 "판 전체가 지금 어떤 상태인가"를 맡는다.

### 확인 사실

2026-08-19 기준으로 이 저장소에서 직접 확인한 값이다.

1. 활성 워크플로 한 곳의 문서는 아이디어 81건, 기획서 88건, 작업 그룹 75건, 개발 작업 220건,
   결정 279건, 보고서 415건으로 모두 1,158건이다.
2. 규격 준수 비용 측정 도구(`scripts/measure-compliance-cost.mjs`)를 지금 작업 트리에 돌린 값은
   기획자 약 103만 토큰, 아키텍트 약 154만 토큰, 개발자 약 149만 토큰이다. 대조 대상 문서를 전부
   읽었을 때의 상한이며, 어느 값도 한 세션의 컨텍스트에 들어가지 않는다.
3. 기획서 88건 중 86건이 `status: user_review`다. 그런데 결정 문서를 대조하면 실제로 사용자 도장을
   기다리는 기획서는 SPEC-083 한 건뿐이다. 앱은 기획서의 표시 상태를 최신 결정으로 덮어 계산하지만
   (`apply_latest_decision`), 문서의 `status` 필드 자체는 결정 이후에도 그대로 남기 때문이다.
4. 상태 판정 구현은 지금 세 벌이다. 앱의 Rust 판정(`role_eligibility.rs`,
   `fs_project_repository.rs`), 화면 쪽 파생 계산(`useProjectWorkspace.ts`), 자격 확인 스크립트
   (`.workflow/rules/wf-eligible.sh`)다.
5. 자격 확인 스크립트는 이미 `--json` 기계 출력을 갖고 있다. 담는 값은 역할, 대상 id, 대상 종류,
   후보별 제외 사유, 판정 코드다. 상태 집계나 도장 대기 목록은 이 출력에 없다.
6. 앱이 설치하고 버전을 붙이는 헬퍼 스크립트는 지금 셋이다(`wf-claim.sh`, `wf-eligible.sh`,
   `wf-reserve.sh`). 앞의 둘은 관리 자산 동기화 경로(`managed_project_assets.rs`)를 타고,
   예약 헬퍼는 프로젝트 저장소 경로(`fs_project_repository.rs`)를 탄다. 설치 경로가 하나가
   아니므로 새 헬퍼를 어느 쪽에 얹을지는 정해진 답이 없다.
7. 런타임 기록으로는 lease 6건(그중 미만료 5건)과 보고 없이 끝난 실행 기록 21건이 있다.
   21건은 모두 2026-08-19 하루치다.

### 설계 결정

확인 사실 3번이 이번 설계의 기준이다. 문서에 적힌 `status` 필드만 세어 요약을 만들면 도장 대기가
86건으로 나온다. 실제 값은 1건이므로 86건 중 85건이 틀린 값이 된다. 상태 판정을 새로 구현하지
않는다는 원 아이디어의 제약은 이 도구가 맞는 값을 내기 위한 조건이다.

그래서 출력의 모든 값을 두 갈래로 나눈다.

- 그대로 읽는 값: 문서에 이미 적혀 있어 판정이 필요 없는 값. 개발 작업의 상태, 작업 그룹의 상태와
  revision, lease의 대상과 만료 시각이 여기 든다.
- 판정이 필요한 값: 최신 결정으로 덮은 기획서의 실제 상태, lease의 만료 여부, 역할별 일감 유무가
  여기 든다. 이 값은 이미 있는 판정 구현에서 받아 온다.

두 번째 갈래를 받아 올 통로를 어떤 방식으로 만들지는 아키텍트가 정한다. 자격 확인 스크립트의 기계
출력을 넓히는 방법과, 앱이 판정 결과를 조회 가능한 형태로 내주는 방법이 모두 열려 있다. 이 기획이
고정하는 것은 방식이 아니라 불변식이다. 판정 규칙을 적은 네 번째 자리를 만들지 않는다.

설치 위치는 앱이 관리하는 규칙 디렉터리로 정한다. 세션은 이미 그 자리의 스크립트를 프로젝트
루트에서 부르는 절차를 역할 계약으로 갖고 있고, 설치와 버전 동기화 경로도 이미 있다. 실행 파일을
PATH에 얹는 방식은 세션이 도구를 찾지 못할 위험을 새로 만들므로 쓰지 않는다.

## 요구사항 명세

### R1. 조회 명령을 하나 설치한다

- 설치 위치는 `.workflow/rules/wf-status.sh`다. 기존 세 헬퍼와 같은 디렉터리에 두고, 앱이 설치와
  버전 표기를 맡는다. 두 설치 경로 중 어느 쪽에 얹을지는 아키텍트가 정한다.
- 호출은 프로젝트 루트에서 `sh .workflow/rules/wf-status.sh [--json]`이다.
- 종료 코드는 0 정상 출력, 1 읽기 실패, 2 사용법 오류다.
- 일감의 유무를 종료 코드에 싣지 않는다. 그것은 `wf-eligible.sh`의 계약이고, 이 명령은 상태를
  보여줄 뿐 무엇을 집으라고 답하지 않는다.
- 완료 조건: 앱의 설치 경로로 스크립트가 설치되고, 인자 없는 호출과 `--json` 호출이 모두 0으로
  끝나며, 알 수 없는 인자가 2로 끝나는 테스트가 통과한다.

### R2. 판정을 새로 만들지 않는다

- 출력의 모든 값은 (a) 문서나 런타임 기록에 그대로 적힌 필드이거나, (b) 이미 있는 판정 구현이 돌려준
  결과여야 한다.
- 판정이 필요한 값을 (b)로 받아 올 수 없으면 그 값을 출력에서 뺀다. 스크립트 본문에 판정 규칙을 새로
  적는 것으로 대신하지 않는다.
- 빠진 항목이 있으면 사람용 출력의 마지막 줄과 기계 출력의 전용 필드에 "제외된 항목"으로 이름을
  남긴다. 값이 조용히 사라지지 않게 한다.
- 완료 조건: 같은 픽스처를 놓고 이 명령의 출력과 앱의 판정 결과를 대조해, 두 쪽이 함께 표현하는 값이
  하나라도 어긋나면 실패하는 회귀 테스트가 있다. 확인 사실 3번의 상황(결정이 끝난 기획서가 도장
  대기로 세어지는 경우)을 그 테스트가 픽스처로 담는다.

### R3. 출력 범위는 다섯 묶음이다

1. 머리글: 프로젝트 이름, 워크플로 이름과 id, 판정 시각(UTC).
2. 진행 집계: 워크플로별 기획서, 작업 그룹, 개발 작업의 상태별 건수.
3. 사용자 대기: 도장을 기다리는 기획서 목록과 품질 확인을 기다리는 작업 그룹 목록.
4. 활성 선점: 만료되지 않은 lease의 대상 id, 역할, 만료 시각.
5. 최근 실패: 막힌 개발 작업 전부와, 보고 없이 끝난 실행 기록의 최근 20건.
- 다섯 묶음의 순서는 고정이다. 담을 것이 없는 묶음은 건수 0으로 남기고 묶음 자체를 없애지 않는다.
- 완료 조건: 다섯 묶음이 이 순서로 나오고, 빈 묶음도 자리를 지키는 테스트가 통과한다.

### R4. 사람용 출력은 한 화면에 들어간다

- 인자 없는 호출의 출력은 60줄 이하, 4KB 이하다.
- 한국어로 쓰고, 문서 id는 그대로 적는다.
- 목록이 상한을 넘으면 넘은 만큼을 "외 N건"으로 접는다.
- 완료 조건: 확인 사실 1번 규모의 픽스처에서 줄 수와 바이트가 상한 안에 드는 테스트가 통과한다.

### R5. 기계용 출력은 표준 출력의 JSON 한 문서다

- `--json` 호출은 표준 출력에 JSON 문서 하나만 낸다. `schemaVersion`을 담고, 사람용 출력과 같은
  값을 담는다.
- 진단이나 경고 문구는 표준 오류로 보낸다. 표준 출력을 그대로 파싱할 수 있어야 한다.
- 완료 조건: 표준 출력을 JSON 파서에 그대로 넣어 통과하고, 표준 오류에 문구가 있는 경우에도 표준
  출력의 파싱이 깨지지 않는 테스트가 있다.

### R6. 읽기 전용이다

- 파일을 만들지 않고, 고치지 않고, 지우지 않는다. lease를 잡지도 갱신하지도 않는다.
- 마이그레이션 락이 걸려 있어도 조회는 된다. 락이 걸린 사실을 머리글에 표시한다.
- 완료 조건: 명령 실행 전후로 프로젝트 디렉터리의 파일 목록과 내용 해시가 같음을 확인하는 테스트가
  통과한다.

### R7. 여러 워크플로를 함께 다룬다

- `project.yml`에 `status: active`로 등록된 워크플로 전부를 대상으로 한다.
- 묶음마다 어느 워크플로의 값인지 표시한다.
- 완료 조건: 활성 워크플로가 둘인 픽스처에서 두 워크플로의 값이 섞이지 않고 구분되어 나오는 테스트가
  통과한다.

## 범위 밖

- 쓰기 동작 전부. 선점, 상태 전이, 문서 생성은 이 명령이 하지 않는다.
- 무엇을 집을지 고르는 판단. 그 답은 `wf-eligible.sh`가 계속 맡는다.
- 문서 본문의 요약이나 검색. 이 명령은 상태만 답한다.
- 실패 기록의 확인 처리 상태에 따른 접기. 그 판단은 SPEC-083이 아직 사용자 결정을 기다리는
  상태이므로, 이번 출력은 기록을 있는 그대로 낸다.
- 계속 띄워 두는 감시 모드, 색 출력, 셸 자동완성.

## 기대효과

- 세션과 대화형 작업이 상태를 확인하는 비용이 문서 수와 무관해진다. 지금은 대조 대상이 늘수록 읽는
  양이 함께 늘지만, 조회 출력은 4KB 상한을 갖는다.
- 도장 대기와 활성 선점이 한자리에서 보이므로, 사용자가 지금 무엇을 처리해야 하는지 앱을 켜지 않고도
  확인할 수 있다.
- 판정 구현이 넷으로 늘지 않는다. 판정이 어긋날 자리를 새로 만들지 않은 채 조회 통로만 추가된다.
