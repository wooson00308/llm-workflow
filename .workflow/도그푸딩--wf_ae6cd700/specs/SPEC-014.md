# 연동의 Windows 지원 해제와 플랫폼별 조건 스크립트 설치

## 기획 내용

연동은 지금 Windows에서 통째로 막혀 있다. 막은 이유는 하나다. 앱이 설치하는 조건 스크립트가 POSIX `sh`라서, Windows에서는 하트비트가 조건 검사에 실패하고 잡을 조용히 건너뛴다. SPEC-002는 이 사실을 알면서 "Windows용 조건 스크립트는 수요가 확인되면 별도로 다룬다"로 보류했고, 그 제안이 DECISION-1265B3C7로 승인됐다. 이제 Windows 실사용자의 수요가 확인됐으므로 그 별도 건을 여는 것이 이 기획서다.

막힌 것이 앱 쪽 한 조각뿐이라는 점이 중요하다. 하트비트 자체는 Windows를 지원한다. 서비스 등록은 `sys.platform`으로 어댑터를 골라 win32에서 Task Scheduler를 쓰고, 조건 검사는 `shell=True`로 실행하므로 Windows에서는 `cmd.exe`가 명령을 받는다. 즉 데몬은 돌고 명령도 실행된다. 다만 그 명령이 `sh .workflow/rules/wf-eligible.sh planner`라서, `sh`가 없는 기본 Windows에서는 실행이 실패한다. 그러면 하트비트는 그 잡을 skip 처리한다.

그래서 이 기획서는 앱이 설치하는 조건 스크립트를 플랫폼별로 나눈다. Windows에는 PowerShell 구현을, 그 외에는 현행 `sh`를 설치하고, 관리 블록에 적히는 `condition` 명령도 그 플랫폼에 맞게 기록한다. 아이디어가 PowerShell을 고른 이유가 그대로 근거다. Windows PowerShell은 기본 탑재라 사용자가 아무것도 더 설치하지 않아도 된다. 이 원칙은 앱의 "외부 명령 비실행"과 같은 결이다. 앱은 여전히 아무것도 실행하지 않고 파일만 쓴다.

이 작업의 진짜 위험은 두 스크립트가 갈라지는 것이다. 판정 로직이 두 벌이 되는 순간, 한쪽만 고친 변경이 "Windows에서만 기획자 잡이 안 깨어남" 같은 형태로 나타난다. 그리고 이 실패는 화면에서 정상으로 보인다. 하트비트는 조건 불충족과 조건 실행 실패를 모두 `last_result: "skipped"`로 기록하고, 앱 카드는 그 값을 "건너뜀 · 처리할 대상 없음"으로 번역한다. 즉 스크립트가 아예 실행되지 못한 상태에서도 화면은 "처리할 대상이 없다"고 단정한다. 지금은 Windows에서 설치 자체가 막혀 있어서 이 오표시가 드러나지 않지만, 차단을 푸는 순간 이것이 Windows 사용자가 가장 먼저 만날 화면이 된다. 그래서 판정 일치를 자동화 테스트로 고정하는 것과 이 문구를 바로잡는 것이 차단 해제와 같은 무게로 이 범위에 들어간다.

나눠야 할 자산이 하나가 아니라는 점도 처음부터 안고 간다. 방금 승인된 SPEC-013(DECISION-73D4BC1B)이 선점 헬퍼를 조건 스크립트와 같은 방식의 앱 관리 자산으로 도입하면서, "이번에는 POSIX sh만, Windows 대응 시 헬퍼 포함 의무를 IDEA-54B29779 범위에 부채로 명시"로 확정했다. 즉 헬퍼의 플랫폼 대응을 이 기획서가 맡는 것은 사용자가 이미 내린 결정이다. 그래서 이 기획서는 플랫폼 분기를 "조건 스크립트를 어떻게 나눌지"가 아니라 "앱이 `.workflow/rules/`에 설치하는 실행 자산을 어떻게 나눌지"로 쓴다. 다만 헬퍼의 `sh` 구현은 아직 파일로 존재하지 않는다 — DECISION-73D4BC1B에서 파생된 개발 작업이 아직 하나도 없다. 그래서 무엇을 먼저 여는지가 결정 사항으로 남는다(확인 필요 5번).

판정 로직 자체는 바꾸지 않는다. 두 구현 모두 현행 `sh` 스크립트의 판정을 그대로 옮긴다. 조건 스크립트의 판정 기준을 손보자는 별도 아이디어(IDEA-C95EABD2, 수정요청·반려 회수 정책)가 인박스에 있지만, 그것과 이 기획서를 섞으면 "옮겼는데 결과가 달라졌다"와 "일부러 바꿨다"가 한 diff 안에서 구분되지 않는다. 옮기기와 고치기는 분리한다.

### 확인 사실

아래는 이 저장소 코드와 현재 설치된 하트비트 소스(`~/Git/claude-heartbeat`, 편집 가능 설치)에서 확인한 사실이고, 이 기획서는 그 위에 서 있다.

- Windows 차단의 원천은 상수 하나다. `PLATFORM_SUPPORTED = !cfg!(windows)`가 연동 스냅샷의 섹션 공통 값 `supported`로 나가고, 잡 설치 경로 두 개(역할 잡·dream 잡)가 진입 즉시 이 값을 보고 `UnsupportedPlatform`으로 거부한다.
- 화면에서 그 값을 쓰는 곳은 셋이다. 연동 뷰 상단의 미지원 경고 배너, 하트비트 카드의 설치 버튼과 역할별 기본값 재설정 버튼, dream 카드의 같은 자리. 모두 비활성 처리다.
- 플랫폼 지원 여부가 연동별이 아니라 섹션 공통 값이라는 것은 SPEC-003 확인 필요 2번의 승인된 결정이다. 지금 코드 주석에도 그 근거가 적혀 있다.
- 조건 스크립트 자산은 한 모듈이 소유한다. 설치 경로는 컨트롤 루트 아래 `rules/wf-eligible.sh`이고, 본문 안에 앱 관리 표기(`# managed_by: workflow-labs`)와 버전 표기(`# condition_script_version: 1`)가 있다.
- 설치 판정은 네 가지다. 파일이 없으면 설치, 관리 표기나 읽을 수 있는 버전이 없으면 덮어쓰지 않고 실패, 파일 버전이 앱이 아는 버전보다 높으면 다운그레이드 거부, 내용이 이미 같으면 파일을 쓰지 않는다. 쓰기는 같은 디렉터리의 임시 파일을 거쳐 원자적으로 옮긴다.
- 잡의 `condition` 문자열은 한 곳에서 만들어진다. 형식은 `sh .workflow/rules/wf-eligible.sh <role>`이고, 화면이 보여주는 조건 스크립트 경로도 같은 상대 경로다.
- 관리 블록 밖 중복 잡 감지는 조건 문자열에 파일명 `wf-eligible.sh`가 들어 있는지로 역할 잡을 식별한다. 역할 이름은 조건 문자열을 공백으로 쪼개 `planner`·`architect`·`developer` 토큰을 찾아 정한다. 확장자가 다른 파일명은 현재 규칙으로 걸리지 않는다.
- 하트비트는 조건을 `subprocess.run(condition, shell=True, capture_output=True, timeout=10, cwd=<slug 역변환 경로>)`으로 실행하고 종료 코드가 0일 때만 잡을 깨운다. Windows에서 `shell=True`는 `cmd.exe`를 거친다는 뜻이다.
- 조건 검사의 타임아웃(10초)과 예외는 fail-closed다. 실행이 실패하면 잡을 깨우지 않고 skip한다.
- 하트비트는 조건 불충족과 조건 실행 실패를 구분해 기록하지 않는다. 둘 다 `last_run`을 갱신하고 `last_result`를 `"skipped"`로 적는다. 로그 파일에만 사유가 남는다.
- 앱 카드는 `skipped`를 "건너뜀 · 처리할 대상 없음"으로 번역한다. 역할 잡 카드와 dream 카드가 같은 문구를 쓴다.
- 조건 실행의 cwd는 잡의 `slug`를 역변환한 경로다. 역변환은 `/`에서 시작해 존재하는 디렉터리를 최장 일치로 찾아 내려가는 추정이다.
- 앱의 slug 생성은 프로젝트 경로 문자열의 `/`를 `-`로 바꾸고 앞에 `-`를 붙이는 것이다. Windows 경로는 구분자가 `\`이고 드라이브 문자가 붙으므로, 이 규칙이 만든 값을 하트비트가 되돌릴 수 있는지는 확인되지 않았다. macOS에서 확인할 수 없는 항목이다.
- 홈 디렉터리 해석은 커맨드 계층이 Tauri 경로 API로 한다. `HOME` 환경 변수를 쓰지 않으므로 이 부분은 Windows에서도 성립한다.
- 조건 스크립트를 실제로 실행해 종료 코드를 확인하는 기존 테스트는 전부 `#[cfg(unix)]`로 묶여 있다. Windows 빌드에서는 이 테스트들이 아예 컴파일되지 않는다.
- 하트비트 서비스 등록 어댑터는 darwin·win32·linux 셋이고 win32는 Task Scheduler다. 데몬 자체는 Windows에서 돈다.
- dream 잡의 조건은 `dream-prep check-unprocessed --slug=<slug>`이고 앱 관리 스크립트를 거치지 않는다. `dream-prep`은 이 저장소 밖 별도 패키지의 콘솔 스크립트이며, 그 소스는 현재 이 머신에 없다. Windows 동작을 이 저장소에서 확인할 수단이 없다.
- 이 저장소에는 앱 설치본과 별개로 `scripts/wf-eligible.sh`가 있고, `docs/heartbeat.md`가 그 경로를 공식 인터페이스로 안내한다. 두 벌의 정리는 SPEC-002 확인 필요 1번에서 별도 아이디어로 미뤄 둔 상태다.
- 저장소의 `.workflow/` 디렉터리는 커밋된다. 따라서 한 저장소를 여러 플랫폼에서 열면 다른 플랫폼용 조건 스크립트가 작업 트리에 함께 존재할 수 있다.
- SPEC-013은 선점 헬퍼를 조건 스크립트와 같은 방식으로 `.workflow/rules/`에 설치하는 앱 관리 자산으로 도입한다. 그 기획서는 "조건 스크립트와 선점 헬퍼의 Windows 지원"을 자기 제외 범위에 두고 이 아이디어로 넘겼다.
- 그 기획서는 2026-08-03T04:18:48Z에 DECISION-73D4BC1B로 승인됐다(`created_by: user`). 결정문이 확인 필요 2번을 이렇게 확정했다: "이번에는 POSIX sh만, Windows 대응 시 헬퍼 포함 의무를 IDEA-54B29779 범위에 부채로 명시". 즉 선점 헬퍼의 플랫폼 대응을 이 기획서가 맡는 것은 사용자가 이미 내린 결정이다.
- 그 결정에서 파생된 개발 작업은 아직 없다. `source_decision_id: DECISION-73D4BC1B`를 참조하는 작업 문서가 하나도 없으므로, 선점 헬퍼는 계약상 존재가 확정됐을 뿐 아직 파일로 존재하지 않는다.
- 즉 앱이 `.workflow/rules/`에 설치하는 실행 자산은 지금 하나지만 둘이 되는 것이 확정돼 있다.

### 포함 범위

- 조건 스크립트를 플랫폼별 자산 둘로 나눈다. Windows는 PowerShell 구현, 그 외는 현행 `sh` 구현이다.
- 두 자산에 같은 설치·버전·덮어쓰기 거부 규약을 적용한다.
- 관리 블록에 기록되는 `condition` 명령을 실행 플랫폼에 맞게 만든다.
- 두 구현의 판정 일치를 자동화 테스트로 고정한다.
- Windows 미지원 안내와 설치 차단을 해제한다.
- 관리 블록 밖 중복 역할 잡 감지가 두 조건 형태를 모두 알아보게 한다.
- Windows에서 조건 검사가 프로젝트 루트를 cwd로 실행되는지 확인하고, slug 생성이 그 전제를 깨면 맞춘다.
- 조건 검사가 실행되지 못한 상태를 "처리할 대상 없음"으로 단정하지 않게 한다.
- dream 연동을 Windows에서 어떻게 취급할지 정하고 그 결정을 화면에 반영한다.
- 플랫폼 분기 규약을 "앱이 `.workflow/rules/`에 설치하는 실행 자산" 전체에 걸리는 규칙으로 쓰고, 그 대상에 SPEC-013의 선점 헬퍼를 포함한다. DECISION-73D4BC1B가 헬퍼의 Windows 대응을 이 범위의 부채로 못박았다.

### 제외 범위

- 조건 스크립트의 판정 로직 변경. 두 구현 모두 현행 `sh`의 판정을 그대로 옮긴다. 판정 기준을 손보자는 건은 IDEA-C95EABD2로 따로 있다.
- 하트비트 패키지 수정. 조건 실행 방식, slug 역변환, `skipped` 기록의 세분화는 모두 그 저장소의 일이다. 이 기획서는 앱이 보낼 값과 앱이 보여줄 화면만 다룬다.
- `dream-prep` 수정. 이 저장소 밖 패키지다.
- 앱이 PowerShell이나 `sh`를 대신 실행하는 것. 조건 스크립트가 실제로 도는지 앱이 직접 확인하지 않는다. "외부 명령 비실행"은 계약급 원칙이다.
- 저장소의 `scripts/wf-eligible.sh`를 플랫폼별로 늘리는 것과 `docs/heartbeat.md` 개정. 두 벌 정리 자체가 SPEC-002에서 별도 건으로 미뤄져 있고, 여기서 손대면 그 결정을 조용히 바꾸는 것이 된다.
- Windows용 설치 안내 강화. 설치 마법사는 IDEA-48EDAF2B로 따로 있다.
- 하트비트 데몬을 Windows에 등록하는 절차의 앱 내 안내. 데몬 등록은 지금도 앱이 하지 않는다.
- 잡 이름·slug의 표시 형식 개선. Windows 경로가 들어간 잡 이름이 길고 지저분해 보이는 문제는 이 기획서가 다루지 않는다.
- 실행 한도·주기 기본값의 플랫폼별 차등.
- 선점 헬퍼 자체의 판정·종료 코드·소유자 확인 규약. 그것은 SPEC-013이 이미 정했고 DECISION-73D4BC1B로 승인됐다. 이 기획서는 그 헬퍼를 플랫폼별로 나누는 일만 한다.
- SPEC-013의 POSIX `sh` 헬퍼 구현. 그 결정문이 "이번에는 POSIX sh만"으로 확정했으므로 sh 구현은 SPEC-013의 작업이다. 이 기획서의 헬퍼 관련 작업은 그 구현이 저장소에 들어온 뒤에야 딛고 설 것이 생긴다. 확인 필요 5번 참조.

## 요구사항 명세

### R1. 조건 스크립트 자산이 플랫폼별로 둘이다

- 앱이 설치하는 조건 스크립트는 실행 플랫폼에 따라 결정된다. Windows에서는 PowerShell 구현을, 그 외 플랫폼에서는 현행 `sh` 구현을 설치한다.
- Windows 구현은 Windows 기본 탑재 PowerShell로 실행 가능해야 한다. 사용자가 다른 런타임을 따로 설치해야 한다면 아이디어가 PowerShell을 고른 이유가 사라진다.
- 두 구현은 같은 인터페이스를 갖는다. 인자는 `planner` | `architect` | `developer`, 종료 코드는 `0`(대상 있음) / `1`(없음) / `2`(잘못된 사용법)이고, `.workflow/.runtime/migration.lock`이 있으면 역할과 무관하게 `1`이다.
- 파일 이름은 두 구현이 서로 구분되게 정한다. 아이디어는 `wf-eligible.ps1`을 제안했다. 최종 이름은 아키텍트가 정하되 R6의 감지 규칙과 같은 근거를 쓴다.

### R2. 설치 규약은 두 자산에 같다

- 두 자산 모두 본문에 앱 관리 표기와 버전 표기를 갖는다.
- 설치 판정은 현행과 같다. 파일이 없으면 설치, 관리 표기나 읽을 수 있는 버전이 없으면 덮어쓰지 않고 실패, 파일 버전이 앱이 아는 버전보다 높으면 거부, 내용이 같으면 쓰지 않는다.
- 쓰기는 현행과 같은 원자적 저장을 따른다. 실패해도 기존 파일이 반쯤 덮이지 않는다.
- 설치 액션은 현재 플랫폼의 자산 하나만 쓴다. 다른 플랫폼용 자산이 같은 디렉터리에 있어도 읽거나 지우거나 덮어쓰지 않는다.
- 버전 번호는 두 구현이 공유한다. 같은 판정을 담은 두 파일이 서로 다른 버전을 갖는 상태를 만들지 않는다.

### R3. 두 구현의 판정이 같다

- 같은 저장소 상태에 대해 두 구현의 종료 코드가 같아야 한다.
- 일치는 자동화 테스트로 고정한다. 사람이 눈으로 대조하는 것으로는 갈라짐을 막지 못한다.
- 테스트 시나리오는 역할별 자격 있음과 없음을 모두 덮는다. 최소한 다음을 포함한다.
  - 기획자: 참조 없는 아이디어가 있음 / 모든 아이디어가 참조됨 / 참조 없는 아이디어에 lease가 있음
  - 아키텍트: 후속 작업 없는 승인 결정이 있음 / 모든 승인 결정에 후속 작업이 있음 / 그 결정의 기획서에 lease가 있음
  - 개발자: `todo` 작업이 있음 / `todo` 작업이 없음 / `todo` 작업에 lease가 있음
  - 공통: 잘못된 인자로 `2`, `migration.lock`이 있으면 역할과 무관하게 `1`
- 판정 로직을 바꾸는 변경은 두 구현과 이 테스트를 함께 고쳐야 통과하도록 한다.

### R4. 잡의 condition이 플랫폼에 맞게 기록된다

- 관리 블록에 쓰이는 `condition`은 그 플랫폼에서 실제로 실행 가능한 명령이어야 한다.
- Windows의 `condition`은 사용자가 PowerShell 실행 정책을 바꾸지 않아도 동작해야 한다. 설치는 성공했는데 조건 검사만 조용히 실패하는 상태를 기본값으로 만들지 않는다.
- `condition`은 한 줄이어야 한다. 하트비트 파서가 줄 단위로 값을 읽는다.
- 조건 스크립트 경로는 프로젝트 루트 기준 상대 경로다. 하트비트가 조건을 프로젝트 cwd에서 실행하기 때문이다.
- 화면이 보여주는 조건 스크립트 경로는 실제로 기록되는 값과 같아야 한다. 설치 확인 화면에서 사용자가 읽는 경로와 파일에 적히는 경로가 어긋나지 않는다.

### R5. Windows 차단이 풀린다

- Windows에서 연동 뷰의 미지원 경고 배너가 보이지 않는다.
- Windows에서 역할 잡 설치·저장·기본값 재설정 버튼이 동작한다.
- 잡 설치 경로가 Windows라는 이유만으로 요청을 거부하지 않는다.
- 지원 여부 판정을 연동별로 쪼개지 않는다. SPEC-003이 정한 "플랫폼 지원 여부는 섹션 공통 정책"을 유지한다. dream 연동의 취급은 확인 필요 3번의 결정을 따른다.
- 지원 플랫폼이 늘어나도 화면 문구가 특정 OS 이름을 하드코딩한 채 남지 않는다.

### R6. 중복 잡 감지가 두 조건 형태를 모두 알아본다

- 관리 블록 밖에 같은 slug를 쓰면서 조건 스크립트를 참조하는 역할 잡이 있으면, 그 조건이 어느 플랫폼 형태든 중복으로 감지된다.
- 감지 규칙이 특정 확장자에만 걸리지 않는다. 지금 규칙은 파일명 `wf-eligible.sh` 포함 여부라서 PowerShell 조건은 통과해 버린다.
- 역할 이름 판정은 현행과 같다. 조건 문자열의 토큰에서 역할 인자를 찾는다.
- 감지는 감지만 한다. 앱은 사용자 잡을 고치거나 지우지 않는다.
- 감지 규칙이 다른 연동의 조건과 겹치지 않는다. dream 조건이 역할 잡 중복으로 잡히면 안 된다.

### R7. Windows에서 조건 검사가 프로젝트 루트에서 실행된다

- 하트비트가 잡의 `slug`를 역변환해 얻은 경로가 실제 프로젝트 루트여야 한다. 그래야 상대 경로 조건이 성립한다.
- Windows 경로에서 앱의 slug 생성 규칙이 이 전제를 깨는지 확인한다. 깨면 이 범위에서 맞춘다.
- slug 생성 규칙을 바꾸게 되면, 이미 설치된 잡의 이름이 바뀌어 하트비트의 실행 이력과 실행 한도 창이 초기화된다는 사실을 사용자가 알 수 있어야 한다. 잡 이름이 상태 키이기 때문이다.
- 이 확인은 실제 Windows 환경에서 이뤄져야 한다. macOS·Linux에서 추정으로 대신하지 않는다.

### R8. 조건 검사가 돌지 못한 상태를 "대상 없음"으로 단정하지 않는다

- 하트비트가 `skipped`로 기록하는 상태에는 두 가지가 섞여 있다. 조건 검사가 통과하지 못한 것과 조건 검사가 실행되지 못한 것이다. 화면 문구가 둘 중 하나로 단정하지 않는다.
- 문구는 앱이 아는 사실까지만 말한다. 앱은 하트비트가 그 잡을 건너뛰었다는 것만 알고, 그 이유가 대상 없음인지 실행 실패인지 모른다.
- 사용자가 실제 사유를 어디서 확인할 수 있는지 알 수 있어야 한다. 사유는 하트비트 로그 파일에만 남는다.
- 이 요구는 문구와 안내까지다. 앱이 사유를 알아내기 위해 새 파일을 읽거나 명령을 실행하지 않는다.
- 역할 잡 카드와 dream 카드가 같은 결론을 쓴다. 한쪽만 고쳐 두 카드의 문구가 어긋나지 않는다.

### R9. 플랫폼이 섞여도 자산이 서로를 망가뜨리지 않는다

- 한 저장소에 두 플랫폼의 조건 스크립트가 함께 있어도 각 플랫폼의 설치와 조건 검사가 정상 동작한다.
- 설치 액션이 현재 플랫폼의 자산만 건드린다는 사실(R2)이 이 상황에서도 유지된다.
- 두 자산이 함께 있는 상태가 오류나 경고로 보이지 않는다. `.workflow/`가 커밋되는 저장소에서는 정상적인 상태다.

### R10. 플랫폼 분기는 선점 헬퍼에도 걸린다

- R1·R2가 정하는 것은 "조건 스크립트를 어떻게 나눌지"가 아니라 "앱이 `.workflow/rules/`에 설치하는 실행 자산을 어떻게 나눌지"다. 그 대상은 조건 스크립트와 SPEC-013의 선점 헬퍼 둘이다.
- 선점 헬퍼도 Windows에서 PowerShell 구현으로 설치되고, 두 구현이 같은 인터페이스(인자·종료 코드·소유자 확인·`migration.lock` 존중)를 갖는다. 그 인터페이스의 내용은 SPEC-013이 정한 것을 그대로 쓴다. 이 기획서가 다시 정하지 않는다.
- 두 구현의 동작 일치를 조건 스크립트와 같은 방식으로 자동화 테스트에 고정한다. 헬퍼는 파일을 만들고 지우므로, 일치 검증은 종료 코드뿐 아니라 결과 lease 파일의 존재 여부와 소유자까지 대조한다.
- 설치·버전·덮어쓰기 거부 규약(R2)이 헬퍼에도 같게 적용된다. 버전 축은 SPEC-013이 조건 스크립트와 분리해 두기로 한 것을 따른다.
- 플랫폼 분기 규칙을 자산마다 새로 정하지 않는다. 세 번째 실행 자산이 생겨도 같은 규약이 적용되는 형태여야 한다.
- 이 요구는 헬퍼의 POSIX `sh` 구현을 이 범위에서 만들라는 뜻이 아니다. 그것은 SPEC-013의 작업이다.

### R11. dream 연동의 Windows 취급이 정직하다

- dream 잡의 조건은 앱 관리 스크립트가 아니라 외부 명령이다. 그 명령의 Windows 동작을 앱이 보증할 수 없다.
- 앱은 보증할 수 없는 것을 보증하는 것처럼 보여서는 안 된다. 확인 필요 3번의 결정에 따라, 열어 주되 한계를 밝히거나 열지 않되 사유를 밝힌다.
- 어느 쪽이든 dream 카드가 이 사실을 사용자에게 밝힌다. 판단은 사용자에게 남긴다.

## 확인 필요

사용자 결정이 필요한 항목이다. 승인 시 아래 제안대로 진행한다.

1. **Windows 조건 명령이 PowerShell 실행 정책을 어떻게 지나갈지.**

   제안: 앱이 기록하는 `condition`이 실행 정책의 영향을 받지 않는 호출 형태를 쓴다. Windows 클라이언트의 기본 실행 정책은 스크립트 파일 실행을 막고, 그 상태에서 조건 검사는 실패한 뒤 skip으로 끝난다. 사용자에게 보이는 증상은 "설치는 됐는데 아무 일도 안 일어남"이고, 이건 이 기획서가 없애려는 바로 그 실패다. 앱이 쓰는 명령 하나에만 적용되는 우회이므로 시스템 정책을 바꾸지 않는다는 점도 근거다.

   반대 근거: 실행 정책 우회를 앱이 기본값으로 파일에 박는 것은 보안 정책이 엄격한 환경에서 거슬릴 수 있고, 감사 대상이 될 수 있다. 대안은 정책 변경을 사용자에게 안내하고 앱은 정직한 호출만 쓰는 것인데, 그러면 Windows 사용자의 기본 경험이 "안 도는 상태"가 된다. 또 다른 대안은 스크립트 파일 대신 명령 자체를 조건 문자열에 담는 것인데, 판정 로직이 한 줄 문자열로 들어가면 R3의 일치 테스트가 대조할 대상이 사라진다.

2. **판정 일치 테스트를 어디서 돌릴지.**

   제안: 두 구현을 각자의 플랫폼에서 실행해 대조한다. 즉 Windows 러너가 필요하다. 배포 대상이 Windows 기본 탑재 PowerShell이므로, 실제로 그 런타임에서 돌려 봐야 일치를 보증할 수 있다. 지금 조건 스크립트 실행 테스트가 `#[cfg(unix)]`로 묶여 있는 것도 같은 이유의 뒤집힌 형태다.

   반대 근거: 러너 추가는 CI 시간과 비용을 늘리고, 이 저장소는 지금까지 단일 플랫폼 검증으로 굴러 왔다. 대안은 macOS·Linux에 크로스 플랫폼 PowerShell을 설치해 한 머신에서 두 구현을 대조하는 것이다. 러너를 늘리지 않고 갈라짐은 잡을 수 있지만, 검증하는 런타임이 실제 배포 대상과 다르다는 구멍이 남는다. 세 번째 선택지는 일치 테스트를 자동화하지 않고 시나리오 표를 문서로 두는 것인데, 그건 갈라짐을 막지 못하므로 이 기획서의 목적과 어긋난다.

3. **dream 연동을 Windows에서 열지.**

   제안: 함께 연다. 플랫폼 지원 여부가 섹션 공통 값이라는 것이 SPEC-003의 승인된 결정이고, dream만 계속 막으려면 그 결정을 뒤집어 연동별 지원 판정을 새로 만들어야 한다. 대신 dream 카드가 "이 잡의 조건은 앱 관리 스크립트가 아니라 외부 명령이고, 그 명령의 Windows 동작은 앱이 보증하지 않는다"는 사실을 밝힌다. 실제로 `dream-prep`은 Python 콘솔 스크립트라 Windows에 설치되면 실행 자체는 성립할 가능성이 높지만, 이 저장소에서 확인할 수 없으므로 보증하지 않는다.

   반대 근거: 확인되지 않은 것을 열어 주면 Windows 사용자가 "설치했는데 안 도는" 상태를 만날 수 있고, 그건 R8이 아무리 문구를 정직하게 써도 좋은 경험이 아니다. dream을 막아 두는 대안은 그 위험을 없애지만, 연동별 지원 판정이라는 구조를 하나 더 만들고 SPEC-003의 결정을 되돌린다. 세 번째 선택지는 dream을 열되 Windows에서 확인되지 않았다는 경고를 카드에 상시 표시하는 것인데, 확인이 끝난 뒤에도 경고가 남아 있으면 사용자가 경고를 무시하는 습관을 들인다.

4. **`skipped` 문구 수정을 이 범위에 둘지.**

   제안: 이 범위에 둔다. R8이 요구하는 것은 문구 한 줄과 안내 한 줄이고 새 원천도 새 판정도 없다. 그리고 이 오표시는 Windows를 여는 순간 Windows 사용자가 가장 먼저 만나는 화면이다. 차단만 풀고 문구를 그대로 두면, 조건 검사가 실행되지 못한 Windows 사용자에게 앱이 "처리할 대상 없음"이라고 잘못 말한다.

   반대 근거: 문구를 약하게 바꾸면 정상 상태의 가독성이 떨어진다. 지금 문구는 대부분의 경우 맞는 말이고, "건너뜀 · 처리할 대상 없음"은 사용자가 한눈에 이해한다. 대안은 이 항목을 제외 범위로 두고 별도 아이디어로 다루는 것인데, 그러면 Windows 차단 해제와 그 해제가 드러내는 오표시가 서로 다른 시점에 반영되어 그 사이 기간이 생긴다.

5. **조건 스크립트만으로 Windows를 먼저 열지, 선점 헬퍼까지 갖춘 뒤 한꺼번에 열지.**

   제안: 조건 스크립트가 준비되면 먼저 연다. 선점 헬퍼의 Windows 구현은 SPEC-013의 `sh` 헬퍼가 저장소에 들어온 뒤에 이어 붙인다. 근거는 두 가지다. 첫째, DECISION-73D4BC1B가 파생 작업을 아직 하나도 만들지 않았으므로 헬퍼는 계약상 확정됐을 뿐 파일로 존재하지 않는다. 헬퍼를 기다리면 Windows 차단 해제가 다른 기획서의 구현 일정에 통째로 묶인다. 둘째, 헬퍼가 없는 동안 세션은 지금처럼 lease를 직접 만든다. 그건 Windows에서도 macOS에서와 같은 정도로 동작하고, 지금 이 저장소가 매일 하는 일이다.

   반대 근거: 헬퍼 없이 Windows를 열면 Windows 세션은 "직접 생성" 경로로만 돌게 되고, DECISION-73D4BC1B의 확인 필요 1번이 정한 "헬퍼가 있으면 강제"가 플랫폼마다 다른 시점에 켜진다. 한동안 두 플랫폼의 선점 방식이 다른 상태가 되고, 그 기간에 병렬을 켜면 선점 안전성이 플랫폼에 따라 달라진다. 한꺼번에 여는 대안은 그 불일치 기간을 없애지만, Windows 사용자가 두 기획서의 구현을 모두 기다려야 한다.

   어느 쪽이든 사용자가 결정하면 실행 순서는 아키텍트가 SPEC-013이 도입한 `depends_on`으로 선언한다.

## 기대효과

- Windows 사용자가 연동을 쓸 수 있게 된다. 지금은 앱이 설치하는 스크립트 하나 때문에 하트비트 자체가 지원하는 플랫폼에서 연동만 막혀 있다.
- 조건 스크립트를 두 벌로 늘리면서 생기는 가장 큰 위험(판정이 갈라져 한 플랫폼에서만 조용히 안 도는 것)이 자동화 테스트로 고정된다.
- 조건 검사가 실행되지 못한 상태가 "처리할 대상 없음"으로 잘못 보이지 않게 되어, 플랫폼과 무관하게 오진의 원인이 하나 줄어든다.
- 플랫폼 지원 여부가 섹션 공통 정책이라는 기존 구조를 유지한 채 확장된다. 연동별 지원 판정이라는 새 축이 생기지 않는다.
- 조건 스크립트가 앱 관리 자산이라는 성질이 플랫폼이 늘어도 유지된다. 판정 기준이 바뀔 때 앱 업데이트만으로 모든 플랫폼에 전파된다.
- DECISION-73D4BC1B가 이 범위의 부채로 남긴 선점 헬퍼의 플랫폼 대응이 갚인다. 병렬 실행을 켤 때 선점 안전성이 플랫폼에 따라 달라지지 않는다.

## 완료 조건

1. Windows에서 역할 잡을 설치하면 PowerShell 조건 스크립트가 `.workflow/rules/` 아래에 설치된다. 검증: Windows에서 설치 액션을 실행하고 파일 존재와 본문의 관리·버전 표기를 확인한다.
2. Windows 외 플랫폼에서 역할 잡을 설치하면 현행 `sh` 조건 스크립트가 설치된다. 검증: 기존 조건 스크립트 설치 테스트가 그대로 통과한다.
3. 두 자산 모두 관리 표기가 없는 파일이나 더 높은 버전의 파일을 덮어쓰지 않고 실패하며, 그 파일이 변경되지 않는다. 검증: 두 자산 각각에 대한 자동화 테스트가 존재하고 통과한다.
4. 같은 설치를 두 번 실행해도 조건 스크립트 파일이 변하지 않는다. 검증: 두 번째 실행 전후의 내용과 수정 시각이 같은지 두 플랫폼에서 확인한다.
5. 설치 액션이 다른 플랫폼용 조건 스크립트를 만들거나 고치거나 지우지 않는다. 검증: 두 자산이 모두 있는 상태에서 설치한 뒤 현재 플랫폼 자산 외의 파일이 바이트 단위로 그대로인지 확인한다.
6. 두 구현이 같은 저장소 상태에 대해 같은 종료 코드를 낸다. 검증: R3이 열거한 시나리오 표를 자동화 테스트로 돌려 두 구현의 종료 코드를 대조한다.
7. 잘못된 인자에 두 구현 모두 `2`를 낸다. 검증: 6번과 같은 테스트에 포함한다.
8. `.workflow/.runtime/migration.lock`이 있으면 두 구현 모두 역할과 무관하게 `1`을 낸다. 검증: 6번과 같은 테스트에 포함한다.
9. Windows에서 설치된 잡의 `condition`이 그 플랫폼에서 실행 가능한 한 줄 명령이고, 실행하면 조건 스크립트의 종료 코드가 그대로 나온다. 검증: Windows에서 관리 블록에 기록된 `condition` 문자열을 그대로 실행해 종료 코드를 확인한다.
10. Windows 기본 실행 정책 상태에서 조건 검사가 성공한다. 검증: 실행 정책을 기본값으로 되돌린 Windows 환경에서 9번과 같은 실행을 반복한다.
11. Windows에서 연동 뷰에 미지원 경고 배너가 보이지 않고 설치·저장·재설정 버튼이 활성 상태다. 검증: Windows에서 화면을 확인하고, 지원 여부 값에 따른 화면 분기 테스트를 통과시킨다.
12. Windows에서 역할 잡 설치 요청이 플랫폼을 이유로 거부되지 않는다. 검증: 설치 경로의 플랫폼 거부 분기에 대한 테스트가 새 동작을 반영하고 통과한다.
13. 관리 블록 밖에 PowerShell 조건을 쓰는 같은 slug의 역할 잡이 있으면 중복으로 감지되고 역할 이름이 함께 나온다. 검증: 자동화 테스트로 확인한다.
14. 기존 `sh` 조건을 쓰는 중복 잡 감지 결과가 이 변경 전후로 같다. 검증: 기존 중복 감지 테스트가 그대로 통과한다.
15. dream 조건을 쓰는 잡이 역할 잡 중복으로 감지되지 않는다. 검증: 기존 연동별 중복 감지 테스트가 그대로 통과한다.
16. Windows에서 하트비트가 잡의 slug를 역변환한 cwd가 실제 프로젝트 루트이고, 그 cwd에서 상대 경로 조건이 종료 코드 `0`을 낸다. 검증: Windows에서 데몬이 잡을 실행하게 두고 로그와 상태 파일로 확인하거나, 같은 slug로 역변환 결과를 재현해 확인한다.
17. slug 생성 규칙을 바꾸게 된 경우, 잡 이름이 바뀌어 실행 이력과 실행 한도 창이 초기화된다는 사실이 사용자에게 표시된다. 검증: 규칙을 바꾸지 않았다면 이 조건은 해당 없음으로 기록하고, 바꿨다면 화면에서 해당 안내를 확인한다.
18. 역할 잡 카드와 dream 카드의 `skipped` 문구가 조건 검사 실행 실패 가능성을 배제하지 않는다. 검증: 두 카드의 문구를 확인하는 자동화 테스트가 존재하고 통과한다.
19. 사용자가 건너뜀의 실제 사유를 어디서 확인하는지 화면에서 알 수 있다. 검증: 렌더된 화면의 안내 문구를 확인한다.
20. 확인 필요 3번이 제안대로 결정되면, Windows에서 dream 카드가 열리고 그 조건이 외부 명령이라 앱이 동작을 보증하지 않는다는 사실이 카드에 표시된다. 검증: 자동화 테스트로 해당 문구를 확인한다.
21. 두 플랫폼용 조건 스크립트가 한 저장소에 함께 있어도 설치와 조건 검사가 정상 동작하고, 그 상태가 오류나 경고로 표시되지 않는다. 검증: 두 파일이 모두 있는 작업 트리에서 설치와 조건 실행을 확인한다.
22. 화면이 보여주는 조건 스크립트 경로가 관리 블록에 실제로 기록되는 경로와 같다. 검증: 설치 확인 화면의 문자열과 저장된 파일의 `condition` 값을 대조한다.
23. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다. 검증: 두 명령을 실행한다.
24. 판정 일치 테스트가 확인 필요 2번의 결정에 따른 실행 환경에서 실제로 돌고 결과가 기록된다. 검증: CI 설정과 실행 로그를 확인한다.
25. 플랫폼 분기 규약이 조건 스크립트 하나에만 맞춰진 형태로 굳지 않는다. 검증: 세 번째 실행 자산이 생겼을 때 규약을 다시 정하지 않아도 되는지 아키텍트 설계 문서에서 확인한다.
26. Windows에서 선점 헬퍼가 PowerShell 구현으로 설치되고, SPEC-013이 정한 인자와 종료 코드 계약을 그대로 지킨다. 검증: Windows에서 헬퍼를 각 종료 코드가 나오는 상황으로 호출해 대조한다.
27. 선점 헬퍼 두 구현이 같은 상황에서 같은 종료 코드를 내고 같은 lease 상태를 남긴다. 검증: 선점 성공·이미 선점됨·만료 인수·소유자 불일치 해제·`migration.lock` 존재를 시나리오로 두고 두 구현의 종료 코드와 결과 lease 파일(존재 여부와 `agent`·`lease_id`)을 대조한다.
28. 선점 헬퍼에도 관리 표기·버전 표기·다운그레이드 거부·멱등 설치가 조건 스크립트와 같게 적용된다. 검증: 조건 스크립트의 해당 테스트와 짝을 이루는 테스트가 헬퍼에도 존재하고 통과한다.
29. 확인 필요 5번의 결정이 실행 순서로 선언된다. 검증: 이 기획서에서 나온 작업 문서의 `depends_on`이 그 결정과 일치하는지 확인한다.
