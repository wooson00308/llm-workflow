# 아이디어 문서뷰가 사용자가 친 개행을 그대로 보여준다

## 기획 내용

아이디어 인박스의 문서뷰가 사용자가 친 개행을 삼킨다. 입력창에서 Enter를 한 번 눌러 줄을 나눠 적으면, 파일에는 그 개행이 그대로 저장되는데 화면에서는 줄이 전부 이어 붙어 한 덩어리 문장으로 보인다. 아이디어가 지목한 그대로다.

원인은 데이터가 아니라 표현 계층이다. 아이디어 전문은 기획서·개발 작업과 같은 Markdown 뷰어로 그려지는데(SPEC-008이 통일한 경로다), Markdown의 기본 규칙에서 개행 한 번은 문단을 나누지 않고 공백 한 칸이 된다. 문단을 나누려면 빈 줄이 필요하다. 저장·전달 경로는 아무것도 잃지 않는다. 아래 확인 사실 3~5에 그 경로를 적었다.

문제는 이 규칙이 아이디어 입력창의 성격과 어긋난다는 것이다. 아이디어를 적는 자리는 여러 줄을 전제한 textarea이고, 안내 문구는 "떠오른 아이디어를 편하게 적어주세요"다. 편하게 적으라고 해 놓고, 편하게 적은 결과를 화면에서 무너뜨린다. 사용자는 자기가 나눈 줄이 어디로 갔는지 알 수 없고, 문서뷰에 보이는 것이 자기가 적은 것과 다르다는 사실만 확인하게 된다. 이 저장소의 아이디어는 배경·원인·방향·제외를 줄로 나눠 적는 형식이 대부분이라, 그 구분이 사라지면 문서로서의 값이 실제로 줄어든다.

그래서 이 기획서는 아이디어 문서뷰가 사용자가 친 줄을 줄로 보여주게 만든다. 반대로, 아이디어에 이미 잘 동작하는 것은 건드리지 않는다. 불릿·제목·표·링크 같은 Markdown 표기는 지금처럼 해석되고, 빈 줄로 나눈 문단도 지금처럼 문단으로 남는다. 바뀌는 것은 문단 안의 개행 하나뿐이다.

한 가지가 이 기획서의 핵심 쟁점이다. 이 뷰어는 세 화면이 함께 쓴다(확인 사실 6). 아이디어에 맞는 처방이 개발 작업 상세에는 새 결함이 된다. 확인 사실 7이 그 숫자를 보여주고, 확인 필요 1번이 그 결정을 사용자에게 묻는다.

### 확인 사실

2026-08-04 09:06Z 기준 작업 트리에서 직접 읽거나 실제 의존성으로 실행해 확인한 값이다. 추정으로 적은 항목에는 그렇다고 적었다.

1. 아이디어 전문은 `MarkdownBody`가 그린다. 미리보기 패널이 본문을 읽어 오면 그 값을 그대로 넘긴다(`src/features/projects/components/IdeaInbox.tsx:236`).
2. `MarkdownBody`는 react-markdown에 remark-gfm 하나만 물려 쓴다. 다른 플러그인도, 렌더 옵션도 없다(`src/features/projects/components/MarkdownBody.tsx:1`~`:19`). 버전은 react-markdown 10.1.0, remark-gfm 4.0.1이다(`package.json:27`~`:28`).
3. 그 조합에서 개행 한 번은 문단을 나누지 않는다. 저장소의 실제 의존성(`node_modules`의 remark-parse·remark-gfm·remark-rehype)으로 `"첫 줄\n둘째 줄\n셋째 줄\n\n새 문단"`을 파싱해 확인했다. mdast는 문단 두 개이고, 앞 문단은 텍스트 노드 하나(`"첫 줄\n둘째 줄\n셋째 줄"`)를 갖는다. 즉 개행 한 번은 텍스트 안의 `\n` 문자로만 남고, 빈 줄만 문단을 나눈다.
4. 그 `\n`은 화면에서 공백 한 칸으로 무너진다. HTML 기본 표시 규칙이 그렇고, `.markdown-body`와 그 자손 규칙 어디에도 `white-space` 선언이 없다(`src/App.css:309`~`:329`). 그래서 세 줄이 한 줄로 흐른다.
5. 개행은 저장·전달 경로에서 사라지지 않는다. 아이디어를 만들 때 앱은 입력값을 `trim()`만 해서 frontmatter 아래에 그대로 쓰고(`src-tauri/src/infrastructure/fs_project_repository.rs:234`~`:236`), 읽을 때는 frontmatter만 걷어낸 본문을 `trim()`해서 넘긴다(`:1200`). 입력창도 값을 `trim()`만 한다(`src/features/projects/components/IdeaComposer.tsx:17`). 파일에는 사용자가 친 개행이 그대로 있다.
6. 이 뷰어는 세 화면이 함께 쓴다. 아이디어 미리보기(`IdeaInbox.tsx:236`), 기획서 리더(`src/features/projects/components/SpecWorkspace.tsx:144`), 개발 작업 상세(`src/features/projects/components/DevelopmentBoard.tsx:274`). 세 곳 모두 같은 컴포넌트를 옵션 없이 호출한다.
7. 문서 종류마다 개행 습관이 정반대다. 문단 안에 개행 한 번이 들어 있는 문서를 세면 개발 작업 61/73, 기획서 0/28, 아이디어 0/26, 보고서 1/103이다(2026-08-04 09:06Z, 도그푸딩 워크플로우). 개발 작업 문서는 본문을 고정폭으로 랩해 적는 관행이 있고(예: `tasks/TASK-013.md`의 문단과 불릿 이어쓰기), 기획서와 아이디어는 한 문단을 한 줄로 적는다. 보고서에는 앱 뷰어가 없다.
8. 입력 자리는 여러 줄을 전제한다. 아이디어 작성 입력은 textarea이고 제출은 버튼이다(`IdeaComposer.tsx:27`~`:34`, `:37`~`:43`). Enter는 제출이 아니라 줄바꿈으로 들어간다. 안내 문구는 "떠오른 아이디어를 편하게 적어주세요"와 "Markdown으로 안전하게 저장됩니다"다(`:32`, `:36`).
9. 사용자가 친 자유 입력이 화면에 다시 그려지는 자리는 아이디어 본문 하나뿐이다. 기획서 결정 코멘트와 작업 QA 코멘트도 textarea로 받지만(`SpecWorkspace.tsx:196`~`:203`, `DevelopmentBoard.tsx:296`~`:308`), 그 값을 되읽어 보여주는 화면이 지금 없다. `src` 아래에 저장된 코멘트를 렌더하는 코드가 없다.
10. 지금 저장소의 아이디어 26건 중 이 결함이 눈에 띄는 문서는 없다. 전부 한 줄짜리이거나, 빈 줄로 문단을 나눈 뒤 불릿을 쓴 형식이다. 문단 안에 개행 한 번을 넣은 아이디어가 하나도 없다(확인 사실 7의 0/26). 즉 재현은 저장된 문서가 아니라 사용자가 앞으로 치는 입력에서 나온다. 검증용 입력은 만들어야 한다.
11. 목록 행은 이번 대상이 아니다. 목록은 본문이 아니라 요약(`excerpt`)을 쓰고, 그 요약은 빈 줄과 제목 줄을 뺀 앞 세 줄을 공백으로 이어 160자로 자른 값이라(`fs_project_repository.rs:1458`) 애초에 한 줄이다. 요약은 CSS로 두 줄에서 말줄임된다.
12. 기존 테스트는 이 경우를 비켜 갔다. 아이디어 전문 테스트는 네 줄을 `"\n\n"`으로 이어 붙여 만든다(`src/features/projects/components/IdeaInbox.test.tsx:272`~`:291`). 개행 한 번짜리 입력을 쓰는 테스트가 아이디어에도, `MarkdownBody`에도 없다(`MarkdownBody.test.tsx:7`~`:25`의 본문도 전부 빈 줄로 나뉘어 있다).
13. 이번 결함은 지금 테스트 스택으로 자동 검증할 수 있다. 판정 대상이 상자 크기가 아니라 DOM 구조(줄바꿈 요소의 유무 또는 텍스트 분리)라서, 레이아웃을 계산하지 않는 jsdom에서도 확인된다. 스타일시트가 필요하지도 않다. SPEC-021이 부딪힌 제약이 여기에는 걸리지 않는다.
14. 개행을 줄바꿈으로 바꾸는 remark 플러그인은 지금 설치돼 있지 않다(`node_modules`에 `remark-breaks` 없음). 수단을 무엇으로 할지는 아키텍트가 정한다. 이 기획서는 화면에서 무엇이 보여야 하는지만 정한다.

### 포함 범위

- 아이디어 문서뷰에서 사용자가 친 개행 한 번이 줄바꿈으로 보이게 한다.
- 빈 줄로 나눈 문단이 지금처럼 문단으로 남게 한다. 줄바꿈과 문단이 화면에서 구분된다.
- 아이디어 본문의 나머지 Markdown 표기(불릿·제목·표·코드·인용·링크) 해석을 그대로 유지한다.
- 이 처방을 어느 문서뷰까지 적용할지 정한다(확인 필요 1번).
- 이 회귀를 다시 잡을 자동 검사를 남긴다.

### 제외 범위

- 요약(`excerpt`) 생성 규칙과 목록 행의 표시. 확인 사실 11대로 목록은 한 줄 요약을 쓰는 자리이고 이번 결함과 무관하다.
- 아이디어의 저장 규칙. 입력값을 `trim()`해서 원문 그대로 쓰는 동작(확인 사실 5)을 바꾸지 않는다. 화면 문제를 저장할 때 문자열을 손봐 우회하지 않는다.
- 아이디어 작성 입력창의 동작과 안내 문구. Enter의 의미, 글자 수 상한, "Markdown으로 안전하게 저장됩니다" 문구를 그대로 둔다. 개행이 보이는 대로 나오면 안내로 설명할 것이 없어진다.
- 기존 아이디어 문서의 본문 수정. 확인 사실 10대로 지금 저장된 26건은 이 결함이 드러나지 않는 형식이고, 문서를 고쳐 화면을 맞추는 방향이 아니다.
- 결정 코멘트·QA 코멘트를 화면에 보여주는 기능. 확인 사실 9대로 그 화면 자체가 없다. 만들면 같은 성격의 자유 입력이 하나 더 생기지만, 그것은 그 화면을 만드는 작업에서 다룬다.
- 개발 작업 문서의 고정폭 랩 관행 변경. 확인 사실 7의 61건을 다시 적는 일은 이 아이디어가 요청한 범위가 아니다.
- 구현 수단 선택. 플러그인을 들일지, 뷰어에서 처리할지, 아이디어 화면에서만 다르게 부를지는 아키텍트가 정한다.
- 문서뷰의 글꼴·여백·최대 폭 등 표현 조정. 이번에 바뀌는 것은 줄바꿈 하나다.

## 요구사항 명세

### R1. 친 대로 보인다

- 아이디어 본문에서 개행 한 번으로 나눈 두 줄이 화면에서도 두 줄로 보인다.
- 사용자가 입력창에 친 줄 구성과 문서뷰에 보이는 줄 구성이 같다. 줄이 합쳐지지 않는다.
- 줄 수와 무관하게 성립한다. 세 줄이든 열 줄이든 각각의 줄이 유지된다.

### R2. 문단과 줄바꿈이 구분된다

- 빈 줄로 나눈 두 덩어리는 지금처럼 서로 다른 문단으로 보인다. R1을 만족시키느라 문단 구분이 줄바꿈 하나로 납작해지면 안 된다.
- 문단 사이 간격과 줄 사이 간격이 화면에서 구별된다. 사용자가 빈 줄을 하나 넣었는지 아닌지가 보여야 한다.

### R3. 나머지 Markdown은 그대로다

- 불릿 목록, 번호 목록, 제목, 표, 코드 블록, 인용, 링크, 강조가 지금과 같이 해석된다. 목록이 목록으로 보이고, 표가 표로 보인다.
- 링크는 지금처럼 새 창으로 열린다.
- 아이디어 본문이 Markdown 문서로 해석되는 성질 자체가 사라지면 안 된다. 원문을 그대로 늘어놓는 방식으로 R1을 만족시키는 것은 이 요구사항 위반이다.
- frontmatter는 계속 화면에 보이지 않는다(SPEC-008 R1).

### R4. 읽기는 읽기다

- 이번 변경이 아이디어 파일을 쓰지 않는다. 본문도, 수정 시각도 달라지지 않는다(SPEC-008 R7 유지).
- 저장 경로의 문자열 처리가 달라지지 않는다. 확인 사실 5의 `trim()` 동작이 그대로다.

### R5. 목록과 문서 정보는 그대로다

- 목록 행의 두 줄 말줄임 요약이 지금과 같다.
- 미리보기의 제목·상태 배지·문서 ID·업데이트 시각·파일명이 지금과 같다.
- 불러오는 중과 실패 표시가 지금과 같다.

### R6. 적용 범위가 결정대로다

- 확인 필요 1번에서 아이디어 뷰만 고르면, 기획서 리더와 개발 작업 상세의 표시가 이번 변경으로 달라지지 않는다.
- 세 뷰 전부를 고르면, 확인 사실 7의 개발 작업 61건에서 문단이 랩 지점마다 끊겨 보이게 된다. 그 경우 그 61건의 본문을 다시 적는 일이 이 기획서의 범위에 함께 들어와야 한다. 화면만 바꾸고 문서를 그대로 두면 결함 하나를 고치고 다른 결함을 들이는 것이다.

### R7. 회귀를 자동으로 잡는다

- 개행 한 번으로 나눈 본문을 아이디어 문서뷰에 그렸을 때 두 줄로 렌더된다는 것을 자동 검사가 확인한다. 확인 사실 13대로 지금 스택에서 성립하는 검증이다.
- 빈 줄로 나눈 본문이 두 문단으로 렌더된다는 것도 같은 검사가 확인한다. R1만 검사하면 R2가 깨진 채로 통과한다.
- 확인 필요 1번에서 아이디어 뷰만 고른 경우, 개발 작업 상세가 개행 한 번을 줄바꿈으로 그리지 않는다는 것도 검사가 확인한다. 적용 범위를 나눈 결정이 코드에서 유지되는지가 그 검사의 대상이다.
- 검증 입력은 새로 만든다. 확인 사실 10대로 저장소에 재현 문서가 없다.

## 확인 필요

사용자 결정이 필요한 항목이다. 승인 시 아래 제안대로 진행한다.

1. **아이디어 뷰에만 적용할지, 세 문서뷰 전부에 적용할지.**

   제안: 아이디어 뷰에만 적용한다. 근거는 셋이다. 첫째, 숫자가 갈린다. 확인 사실 7대로 개발 작업 문서 73건 중 61건이 문단 안에 개행을 갖고 있고, 그 개행은 사람이 나눈 줄이 아니라 고정폭 랩의 부산물이다. 전부에 적용하면 그 61건이 랩 지점마다 끊긴 들쭉날쭉한 문단으로 보인다. 기획서(0/28)와 아이디어(0/26)는 영향이 없으므로, 이 결정은 사실상 개발 작업 상세 하나를 두고 하는 결정이다. 둘째, 입력의 성격이 다르다. 아이디어는 사람이 입력창에 치는 자유 입력이고, 기획서와 개발 작업은 에이전트가 Markdown 문서로 작성해 파일로 남긴 것이다. 셋째, 사람이 치는 자유 입력을 개행 그대로 보여주는 것은 널리 쓰이는 처리 방식이다(코멘트 입력은 개행을 줄바꿈으로 보여주고 저장소의 문서 파일은 그러지 않는 GitHub의 구분이 같은 갈래다 — 이 항목은 저장소에서 확인한 사실이 아니라 업계 관행 인용이다).

   반대 근거: 같은 뷰어가 문서 종류마다 다르게 그리게 된다. SPEC-008이 세 문서의 읽기 화면을 같은 모습으로 만든 것이 명시적 목표였고, 그 약속은 지금 테스트 이름에도 남아 있다("renders markdown formatting like the other document views", `IdeaInbox.test.tsx:354`). 같은 `.md` 파일인데 어느 화면에서 여느냐에 따라 줄이 달라 보이는 것은 설명이 필요한 상태다. 뒤집기로 하면 R6의 두 번째 항목이 발동해 개발 작업 문서 61건의 본문을 다시 적는 일이 범위에 들어오고, 아키텍트가 그 분해까지 맡는다. 그 경우 작업량이 이 결함의 크기를 크게 넘어선다.

2. **개행이 여러 개 연속일 때 그 수를 그대로 보여줄지.**

   제안: 그대로 보여주지 않는다. 빈 줄 하나든 셋이든 문단 구분 하나로 본다. 근거는 둘이다. 첫째, 지금 동작이 그렇고 이 아이디어가 문제 삼은 것은 "개행이 안 보인다"이지 "빈 줄 수가 안 맞는다"가 아니다. 둘째, 빈 줄 수를 그대로 보존하려면 Markdown 해석을 벗어나는 표현 방식으로 가야 해서 R3와 정면으로 부딪힌다.

   반대 근거: 사용자가 빈 줄 셋으로 크게 끊어 적었다면 그 의도도 입력의 일부다. 뒤집기로 하면 R2가 "빈 줄 수를 보존한다"로 바뀌고, R3와의 충돌을 아키텍트가 풀어야 한다.

## 기대효과

- 사용자가 적은 것과 앱이 보여주는 것이 같아진다. 지금은 문서뷰에 보이는 글이 자기가 친 글과 달라서, 앱에 남긴 아이디어를 다시 읽을 때 원문을 의심하게 된다.
- 아이디어를 편하게 적을 수 있게 된다. 지금은 줄을 나누려면 빈 줄을 넣어야 한다는 것을 사용자가 알고 있어야 하는데, 입력창은 그런 말을 한 적이 없다.
- 아이디어의 구조가 화면에 남는다. 배경·원인·방향·제외를 줄로 나눠 적는 이 저장소의 형식이 문서뷰에서 그대로 읽힌다.
- 기획자 세션이 참고하는 정보와 사용자가 화면에서 보는 정보가 같아진다. SPEC-008이 전문 읽기 경로로 좁힌 간극의 마지막 한 칸이다.
- 자유 입력을 화면에 되돌려 주는 규칙이 하나 정해진다. 확인 사실 9대로 지금은 아이디어 하나뿐이지만, 결정 코멘트나 QA 코멘트를 보여주는 화면이 생기면 그때 따를 선례가 된다.

## 완료 조건

1. 개행 한 번으로 나눈 두 줄이 아이디어 문서뷰에서 두 줄로 보인다. 검증: 개행 한 번짜리 본문을 그리는 자동화 테스트로 확인한다.
2. 세 줄 이상을 개행 한 번씩으로 나눈 본문도 각 줄이 유지된다. 검증: 같은 테스트에서 줄 수를 확인한다.
3. 빈 줄로 나눈 덩어리가 서로 다른 문단으로 보이고, 문단 간격과 줄 간격이 화면에서 구별된다. 검증: 문단 구조를 자동화 테스트로 확인하고, 간격 차이는 사용자 QA에서 눈으로 확인한다.
4. 불릿·번호 목록·제목·표·코드 블록·인용·강조가 지금과 같이 해석된다. 검증: 기존 `IdeaInbox.test.tsx`와 `MarkdownBody.test.tsx`가 수정 없이 통과한다.
5. 링크가 새 창으로 열리고 `rel` 속성이 그대로다. 검증: 기존 테스트로 확인한다.
6. frontmatter가 화면에 보이지 않는다. 검증: 기존 테스트로 확인한다.
7. 목록 행의 두 줄 말줄임 요약과 요약 생성 규칙이 그대로다. 검증: 기존 테스트로 확인하고, 변경분에 `markdown_excerpt`가 없는지 확인한다.
8. 미리보기의 제목·상태 배지·문서 ID·업데이트 시각·파일명, 불러오는 중·실패 표시가 그대로다. 검증: 기존 테스트로 확인한다.
9. 아이디어 파일이 쓰이지 않는다. 검증: 변경분에 `src-tauri/` 파일이 없는지 확인한다. 확인 필요 1번의 어느 선택지도 백엔드를 바꾸지 않는다.
10. 확인 필요 1번의 결정이 코드에 그대로 반영돼 있다. 아이디어 뷰만 고른 경우, 개발 작업 상세에서 개행 한 번이 줄바꿈으로 그려지지 않는다. 검증: 개발 작업 상세를 대상으로 하는 자동화 테스트로 확인한다.
11. 확인 필요 1번에서 세 뷰 전부를 골랐다면, 개발 작업 문서의 고정폭 랩이 정리돼 문단이 끊겨 보이지 않는다. 검증: 개발 작업 상세를 화면에서 확인하고 정리 대상 문서 수를 보고서에 남긴다. (아이디어 뷰만 고른 경우 이 조건은 해당 없음으로 기록한다.)
12. 기존 자동화 테스트가 삭제되거나 비활성화되지 않는다. 검증: 테스트 목록 변경분을 확인한다.
13. `npm run check`가 통과한다.
