# 사용자 확인 절차 판정이 자연스러운 한국어 관찰 서술을 통과하도록 고친다

## 결정권자 요약

### 제안

품질 확인 동선을 사용자 확인 절차로 인정하는 판정이 한국어 어미 변화 때문에 멀쩡한 문장을 놓치는
것을 고쳐서, 평범한 관찰 서술로 적힌 기능이 품질 확인으로 넘어가게 한다.

### 현재

확인 동선은 화면과 사용자 행동과 눈에 보이는 결과를 모두 말해야 사용자 확인 절차로 인정된다.
그런데 결과를 가리는 대조가 낱말의 특정 활용형만 알아서, "보인다", "적혀 있다", "바뀐다" 같은
평범한 서술이 하나도 인정되지 않는다. 2026-08-18에 개발이 모두 끝난 기능 하나가 이 이유로
"구성 확인 필요"로 표시되었고, 사용자는 그 기능의 품질 확인을 열 수 없다.

### 변경 후

같은 낱말은 어미가 달라져도 같은 낱말로 인식한다. 실측된 그 기능은 문서를 한 글자도 고치지 않고
판정을 통과해 품질 확인이 열리고, 앞으로 자연스러운 한국어로 쓴 확인 동선이 문장 표현 때문에
막히는 일이 없어진다.

### 비용과 위험

개발자용 절차나 터미널 명령이 확인 동선에 섞이는 것을 막는 지금의 차단은 그대로 둔다. 넓히는 것은
결과를 가리키는 낱말을 알아보는 범위 하나다. 판정이 넓어지는 만큼 확인 동선답지 않은 글이 통과할
여지가 생기지만, 그때 사용자는 확인 화면에서 수정 요청으로 되돌릴 수 있다. 지금의 잘못된 탈락은
사용자가 되돌릴 방법이 없다. 작업 그룹 문서와 개발 작업은 건드리지 않고 판정 부분만 바꾸므로
되돌리기도 쉽다.

## 기획 내용

### 실측한 문제

2026-08-18, 작업 그룹 GROUP-070은 소속 개발 작업 TASK-S070-01이 검증까지 끝났는데도 품질 확인이
열리지 않았다. 품질 확인 화면에서 이 그룹은 "준비 중인 기능" 목록에 "구성 확인 필요"라는 상태
이름만 달고 나오며, 확인을 시작하는 버튼이 없다. 무엇이 부족한지도, 누가 고쳐야 하는지도 화면에
적히지 않는다.

### 코드에서 확인한 사실

- 사용자 확인 모드 그룹은 확인 동선 하나하나가 사용자 확인 절차로 인정되어야 품질 확인 대기 상태가
  된다. 하나라도 인정되지 않으면 그룹 전체가 구성 오류 상태로 내려간다.
- 인정 판정은 확인 동선 본문에 세 가지가 각각 하나 이상 있는지를 본다. 화면을 가리키는 낱말,
  사용자 행동을 가리키는 낱말, 눈에 보이는 결과를 가리키는 낱말이다. 셋을 모두 만족해야 한다.
- 대조 방식은 미리 정해 둔 낱말 목록과의 글자열 포함 검사다. 목록에는 낱말마다 활용형 하나만 들어
  있다. 결과 쪽 목록의 "보이"는 "보이고"와 "보입니다"에는 걸리지만 "보인다"에는 걸리지 않는다.
  한글은 음절을 한 글자로 적기 때문에 "보인다"라는 글자열 안에는 "보이"라는 글자열이 없다.
- GROUP-070의 확인 동선은 화면 조건과 행동 조건을 만족한다. 화면 쪽은 "화면", "창", "버튼", "앱"이
  걸리고 행동 쪽은 "열", "확인"이 걸린다. 떨어지는 것은 결과 조건 하나다. 결과 목록의 낱말 32개
  가운데 본문에 나타나는 것이 하나도 없다(2026-08-18 대조).
- 그 문서가 쓴 기대 문장은 "보인다", "같아진다", "적혀 있다", "바뀐다", "나오는", "동작한다"처럼
  모두 평범한 관찰 서술이다. 문서가 규약을 어긴 것이 아니라 판정이 한국어를 좁게 읽었다.

### 판단

- 판정 자체는 남긴다. 확인 동선에 개발자용 절차가 섞여 사용자에게 나가는 것을 막는 장치는 필요하고,
  그 자리는 명령과 코드 블록을 걸러내는 별도 검사와 함께 동작한다. 이번에 고칠 것은 그 검사가 아니라
  결과 낱말 대조 방식이다.
- 대조는 어미가 바뀐 형태도 같은 낱말로 인식해야 한다. 어간을 기준으로 맞추든 인식할 형태를 넓히든
  구현 방식은 아키텍트가 정한다.
- 두 방향의 오판은 비용이 다르다. 멀쩡한 동선을 떨어뜨리면 기능 하나의 품질 확인이 통째로 막히고
  사용자가 할 수 있는 일이 없다. 반대로 덜 다듬어진 동선을 통과시키면 사용자가 확인 화면에서 수정
  요청으로 돌려보낼 수 있다. 회복 경로가 있는 쪽으로 기울이는 것이 맞다.

### 사유 표시를 이 문서에서 정하지 않는 이유

원천 아이디어는 판정 실패 사유를 화면에 보여 주는 방식도 후보로 적었다. 이 문서는 그 방식을 택하지
않는다. 같은 날 접수된 IDEA-FC871690이 "사용자가 할 일이 없는 문제 상태를 화면이 어떻게 설명하고
누구에게 넘길 것인가"를 정면으로 다루고 있어서, 두 문서가 같은 화면에 각자의 문구 요구를 적으면
나중에 상충한다. 이 문서는 오판을 없애는 데까지만 간다. 실측 사례인 GROUP-070은 이 변경만으로
품질 확인이 열리므로, 아이디어가 말한 막힘은 이 문서로 해소된다.

## 요구사항 명세

### REQ-01 어미가 달라져도 같은 낱말로 인식한다

- 화면, 행동, 결과 세 조건의 낱말 대조는 어미 변화로 글자 모양이 바뀐 형태도 같은 낱말로 인식한다.
- 기준이 되는 사례는 결과 쪽 "보이"다. "보인다", "보이고", "보입니다", "보였다"가 모두 같은 낱말로
  인식되어야 한다.
- 수용 기준: 이 네 형태를 각각 담은 확인 문장이 모두 결과 조건을 만족한다.

### REQ-02 실제 확인 동선이 쓰는 관찰 서술을 결과로 인정한다

- 다음 서술이 눈에 보이는 결과로 인정된다. 보인다, 나타난다, 표시된다, 적혀 있다, 열린다, 나온다,
  바뀐다, 같아진다, 남아 있다, 사라진다.
- 인식 범위를 어떻게 넓힐지는 정하지 않는다. 위 서술이 결과로 인정되는 것이 요구사항이다.
- 수용 기준: GROUP-070의 확인 동선 본문이 문서 수정 없이 결과 조건을 만족한다.

### REQ-03 지금 통과하던 문장은 계속 통과한다

- 이 변경 전에 사용자 확인 절차로 인정되던 문장은 변경 후에도 인정된다.
- 수용 기준: 이 판정을 다루는 기존 자동 시험이 모두 통과한다.

### REQ-04 개발자용 절차 차단은 약해지지 않는다

- 터미널 명령, 패키지 실행기 호출, 저장소 조작 지시, 내부 자동 시험 절차, 코드 블록이 들어간 확인
  동선은 지금과 같이 인정되지 않는다.
- 본문이 비어 있는 확인 동선도 지금과 같이 인정되지 않는다.
- 화면도 사용자 행동도 말하지 않는 문장은 결과 낱말이 있어도 인정되지 않는다. 세 조건을 모두
  만족해야 한다는 규칙은 그대로다.
- 수용 기준: 명령이 섞인 확인 동선과 "백엔드 로직이 올바르게 동작한다."처럼 화면도 행동도 말하지
  않는 문장이 변경 후에도 인정되지 않는다.

### REQ-05 문서를 고쳐서 해결하지 않는다

- 이 변경은 판정 쪽만 고친다. 이미 작성된 작업 그룹 문서의 문장을 낱말 목록에 맞추어 바꾸지 않는다.
- 수용 기준: GROUP-070 문서의 본문이 이 변경으로 수정되지 않은 상태에서, 그 그룹이 품질 확인 대기
  상태가 된다.

## 범위 밖

- 구성 오류의 사유를 화면에 사용자 언어로 표시하는 일과, 그 상태를 아키텍트에게 자동으로 넘기는 일.
  IDEA-FC871690이 다루는 자리다.
- GROUP-070의 문장을 판정에 맞추어 손보는 개별 조치. 원천 아이디어가 아키텍트 몫의 별도 조치로
  명시했다.
- 그룹 상태를 정하는 나머지 조건. 문서 구조 유효성, 작업의 그룹 revision 일치, 자동 확인 모드의
  규칙은 지금 그대로 둔다.
- 영어로 쓴 확인 동선의 판정. 지금 동작을 바꾸지 않는다.
- 확인 동선을 쓰는 방법에 대한 규약 변경. 아키텍트가 지키는 작성 규칙은 그대로다.

## 기대효과

- 개발이 끝난 기능이 문장 표현 하나 때문에 품질 확인에서 막히는 일이 없어진다. 실측 사례에서는
  검증까지 끝난 기능 하나가 이 이유로 멈춰 있었다.
- 아키텍트가 확인 동선을 쓸 때 판정이 아는 활용형을 맞추려 애쓰지 않고, 사용자가 읽기 좋은 한국어로
  쓸 수 있다.
- 품질 확인 목록에서 "구성 확인 필요"가 나오는 빈도가 실제 구성 오류에 가까워진다. 그 상태를 사용자
  언어로 설명하는 후속 작업도 잘못된 사례에 가려지지 않는다.

  정하라는 지시가 적혀 있다.
- GROUP-070: 2026-08-18 실측 사례. 확인 동선과 소속 작업 상태를 이 기획서의 사실 확인에 사용했다.
