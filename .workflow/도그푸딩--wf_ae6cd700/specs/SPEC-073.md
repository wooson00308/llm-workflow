# 사용자가 할 일이 없는 문제 상태를 사용자에게 과제로 보여주지 않는다

## 결정권자 요약

### 제안

사용자가 손댈 수 없는 기능 문제 상태를 상태 이름만으로 보여주지 않고 무엇이 문제이고 누가 처리하는지
함께 밝히며, 처리 주체가 정해져 있지 않던 구성 확인 필요 상태에 아키텍트 자동 처리 경로를 만든다.

### 현재

품질 확인을 기다리는 기능에는 확인 시작 입구가 뜬다. 그런데 한 기능이 구성 확인 필요로 뜨면 화면은 그
이름만 보여준다. 사용자는 자기더러 무엇을 확인하라는 것인지 알 수 없고, 실제로 사용자가 할 행동은
없다. 이 상태의 기능은 어느 역할도 자동으로 맡지 않아, 사람이 발견해 물어볼 때까지 그대로 남는다.

### 변경 후

사용자 행동이 없는 문제 상태는 상태 이름과 함께 문제, 처리 주체, 사용자가 할 일이 없다는 사실을 목록
자리에서 바로 보여준다. 구성 확인 필요 기능은 아키텍트가 자동으로 맡는 대상이 되어 사용자가 알리지
않아도 수정이 시작되고, 문서를 고쳐서는 풀 수 없는 경우에만 무엇을 판단해야 하는지와 함께 사용자에게
올라온다. 사용자는 목록에서 자기 차례가 아닌 항목을 넘겨보고 자기 차례만 처리한다.

### 비용과 위험

어떤 문서가 구성 오류인지 가리는 판정 기준은 이 문서에서 바꾸지 않는다. 판정 결과가 같은 상태로 나오는
것을 전제로 그 결과를 설명하는 방식과 그다음 처리 주체만 정한다. 자동 처리는 원인이 문서 밖에 있을 때
같은 기능을 반복해서 잡을 위험이 있으므로, 한 번 시도해 풀리지 않으면 자동 대상에서 빠지는 조건을 함께
요구한다. 상태 계산, 사용자 확인 흐름, 승인 도장, 기능별 구성 버전은 그대로다. 승인하지 않으면 지금의
상태 이름 표시와 지금의 자동 처리 범위가 그대로 유지된다.

## 기획 내용

### 문제

2026-08-18 실측이다. 평소 품질 확인을 기다리는 기능에는 확인 시작 입구가 뜨는데, 한 기능이 구성 확인
필요로 떠서 사용자가 자기더러 무엇을 하라는 것인지 알 수 없었다. 이 상태의 실제 뜻은 기능의 문서 구성이
판정 규칙과 맞지 않아 확인 화면을 열 수 없다는 것이고, 고칠 주체는 문서를 쓴 아키텍트이거나 판정 규칙
자체다. 사용자 몫의 행동은 없다. 그런데 화면은 사유도, 처리 주체도, 사용자가 할 일이 없다는 말도 없이
상태 이름만 보여준다.

이름 자체도 오해를 키운다. 확인이라는 낱말은 이 앱에서 사용자가 하는 품질 확인 동작과 같은 낱말이다.
사용자는 확인이 필요하다는 문장을 읽고 자기에게 확인을 요구한다고 읽는다.

### 상태 이름이 이미 하는 일과 하지 않는 일

기능 상태 중 사용자가 지금 할 행동이 있는 것은 사용자 QA 대기 하나뿐이다. 홈 화면의 내 선택 대기 목록도
기획서 승인과 이 상태만 담는다. 나머지 상태는 진행 상황이거나 문제 상황이며 사용자가 할 행동이 없다.

그중 아키텍트 구성 중과 아키텍트 재분류 대기는 이름 안에 처리 주체가 들어 있어, 사용자가 자기 차례가
아니라는 것을 이름만 보고도 읽을 수 있다. 반면 구성 확인 필요, 구성 중단 의심, 개발 막힘은 그 정보를
담고 있지 않다. 개발 보드의 기능 레인과 품질 확인 화면의 준비 중인 기능 목록에서 이 세 상태는 이름
하나로만 나타난다.

### 자동 처리 경로가 없는 상태는 하나다

세 상태의 처리 경로를 확인하면 다음과 같다.

- 구성 중단 의심은 아키텍트가 자동으로 맡는다. 준비 중인 기능에 유효한 선점이 없으면 아키텍트 대상
  판정이 그 기능을 대상으로 답한다.
- 개발 막힘은 개발자가 자동으로 맡는다. 막힌 작업은 사용자 요청 없이 개발자가 다시 집고, 작업 정의
  자체가 잘못된 경우에는 아키텍트가 집는다.
- 구성 확인 필요는 어느 역할의 대상 조건에도 들어가지 않는다. 기능 문서는 활성 상태이고 선점도 없으며
  진행 중인 작업도 없다. 아키텍트 대상 판정이 보는 조건은 사용자 확인 반려, 작업 정의 오류, 준비 중
  중단, 승인된 새 기획서 네 가지이고 이 상태는 그중 어느 것도 아니다.

즉 화면 설명이 없는 것은 세 상태 모두의 문제이고, 처리 주체 자체가 없는 것은 구성 확인 필요 하나의
문제다. 이 문서는 앞의 것을 세 상태 모두에 대해 고치고, 뒤의 것을 구성 확인 필요에 대해 고친다.

### 구성 오류로 판정되는 원인은 한 가지가 아니다

지금 판정은 다음 중 하나라도 해당하면 구성 확인 필요로 답한다.

- 기능 문서의 필수 값이 없거나 형식이 어긋난다. 식별자, 구성 버전, 출처 기획서, 출처 승인, 최종 변경
  시각, 확인 절차 번호 중복이 여기에 속한다.
- 이 구성 버전에 속한 작업이 하나도 없거나, 작업이 가리키는 기능과 구성 버전과 출처가 기능 문서와
  어긋난다.
- 사용자 확인 모드인데 확인 절차가 없거나, 적힌 절차가 사용자 행동으로 인정되지 않는다.
- 자동 확인 모드인데 확인 절차가 적혀 있다.
- 끝나지 않은 작업이 남아 있다.

앞의 네 가지는 아키텍트가 문서를 고쳐 해결할 수 있다. 다만 세 번째는 문서가 아니라 판정 규칙 쪽이
원인일 수 있다. GROUP-070이 그 사례이고, 그 원인은 IDEA-85EF9AD9에서 나온 별도 기획서가 다룬다. 자동
처리를 만들 때 이 경우를 반드시 상정해야 한다. 문서에 손댈 곳이 없는 기능을 아키텍트가 계속 다시 잡으면
같은 결과가 반복되고 실행 한도만 소모한다.

지금 화면은 이 다섯 가지를 한 이름으로 합쳐 보여준다. 어떤 원인인지 화면에서 구분할 방법이 없다.

### 사유는 상태를 계산하는 쪽이 함께 내려준다

화면이 기능 문서와 작업 문서를 다시 읽어 원인을 추측하면, 판정과 화면이 서로 다른 근거로 답하게 되고
판정 조건이 바뀔 때마다 두 곳이 어긋난다. 상태를 계산하는 쪽이 왜 그 상태로 답했는지를 함께 내려주고,
화면은 그 값을 사용자 언어 문장으로 옮기기만 한다.

## 요구사항 명세

### 사용자 행동이 없는 상태의 표시

- R-01. 기능 상태 중 사용자가 지금 할 행동이 있는 것은 사용자 QA 대기 하나로 유지한다. 이 문서는 사용자
  행동이 있는 상태를 늘리지 않는다.
- R-02. 구성 확인 필요, 구성 중단 의심, 개발 막힘 상태의 기능은 상태 이름과 함께 무엇이 문제인지, 누가
  처리하는지, 사용자가 지금 할 일은 없다는 사실을 사용자 언어로 보여준다.
- R-03. 그 설명은 상세 화면을 열지 않아도 목록 자리에서 보인다.
- R-04. 사용자 행동이 없는 상태의 표시는 확인 시작 입구와 구분되는 모습으로 보여준다. 눌러서 사유를 더
  보게 만드는 것은 허용하되, 그 자리가 사용자에게 처리를 요구하지 않는다.
- R-05. 문구에는 내부 상태 이름, 파일 경로, 코드 식별자를 그대로 쓰지 않는다.
- R-06. 이 표시는 기능 상태를 보여주는 모든 자리에 적용한다. 개발 보드의 기능 레인, 품질 확인 화면의
  준비 중인 기능 목록, 확인 도중 상태가 바뀌어 열 수 없게 된 기능 화면, 기획서 화면의 기능 상태가 그
  자리다.

### 구성 오류의 사유

- R-07. 구성 확인 필요로 판정된 기능은 어떤 조건이 맞지 않아 그렇게 판정됐는지 사용자 언어로 한 가지
  이상 함께 보여준다.
- R-08. 사유는 상태를 계산하는 쪽이 상태와 함께 내려준 값이다. 화면이 문서를 다시 읽어 원인을 추측하지
  않는다.
- R-09. 해당하는 조건이 여럿이면 여럿을 보여준다. 하나로 합쳐 뭉뚱그리지 않는다.
- R-10. 사유를 만들지 못하는 경우에는 사유 없이 상태와 처리 주체만 보여준다. 그 경우에도 화면이 멈추거나
  기능이 목록에서 사라지지 않는다.

### 구성 오류의 자동 처리

- R-11. 구성 확인 필요 기능은 아키텍트의 자동 대상이 된다. 사용자가 알리거나 승인하지 않아도 시작된다.
- R-12. 대상 선정은 다른 아키텍트 대상과 같은 선점 규칙을 따른다. 유효한 선점이 걸린 기능은 대상이 아니다.
- R-13. 아키텍트는 같은 기능 식별자를 유지한다. 새 기능 문서를 만들지 않는다.
- R-14. 구성 버전을 올리지 않는다. 구성 오류 수정은 사용자 반려에 답하는 재작업이 아니다.
- R-15. 자동 처리가 손대는 범위는 그 기능 문서와 그 기능에 속한 작업 문서다. 사용자 결정 문서, 승인
  기록, 판정 규칙 자체는 바꾸지 않는다.
- R-16. 아키텍트가 문서를 고쳐 판정 조건을 충족시키면 기능은 평소 흐름으로 돌아간다. 사용자 확인 모드
  기능이면 사용자 QA 대기가 되어 확인 입구가 열린다.
- R-17. 아키텍트가 문서 쪽에 고칠 곳이 없다고 판단하면 그 판단을 보고로 남기고 기능을 그대로 둔다. 같은
  구성 버전의 같은 기능은 그 뒤로 자동 대상이 되지 않는다.
- R-18. R-17이 성립한 기능은 화면에서 사람의 판단이 필요한 상태로 보여주고, 사용자가 무엇을 판단해야
  하는지 함께 보여준다. 이때 처음으로 이 기능이 사용자 차례가 된다.

### 보호

- R-19. 어떤 기능의 상태도 이 변경이 강제로 바꾸지 않는다. 상태는 지금과 같은 계산 결과로 나온다.
- R-20. 구성 오류 판정 조건 자체를 넓히거나 좁히지 않는다.
- R-21. 사용자 확인 흐름, 결정 도장, 기획서 승인 게이트는 그대로다.
- R-22. 구성 중단 의심과 개발 막힘의 기존 자동 처리 경로는 바꾸지 않는다. 이 두 상태에는 화면 설명만
  더한다.

## 선택한 기본값

이 절의 값은 이 문서가 정한 기본값이다. 다른 값이 맞다고 판단하면 수정 요청으로 돌려보내면 된다.

- 설명을 붙이는 대상은 구성 확인 필요, 구성 중단 의심, 개발 막힘 세 상태로 한다. 아키텍트 구성 중과
  개발 중은 이름만으로 진행 중이라는 사실이 읽히고, 아키텍트 재분류 대기는 이름에 처리 주체가 이미
  들어 있다.
- 사유는 목록에서 한 줄로 보여주고, 해당 조건이 여럿이면 상세 자리에서 전부 보여준다.
- 아키텍트 대상 순서는 사용자 확인 반려 다음, 작업 정의 오류 수정 앞에 둔다. 구성 확인 필요 기능은
  개발이 모두 끝난 뒤 마지막 단계에서 막힌 상태이고, 사용자는 그 기능의 확인을 기다리고 있다. 앞 단계의
  대상을 먼저 처리해도 이 기능은 계속 막혀 있다.
- 아키텍트가 한 번 시도해 풀지 못하면 그 구성 버전에서는 자동 대상에서 빼고 사용자 판단으로 넘긴다.
  원인이 문서 밖에 있으면 몇 번을 다시 시도해도 같은 결과가 나오기 때문이다.

## 범위 밖

- 어떤 문서가 구성 오류인지 가리는 판정 기준을 고치는 일. 자연스러운 한국어 관찰 서술이 사용자 확인
  절차로 인정되지 않는 문제를 포함하며, IDEA-85EF9AD9에서 나온 별도 기획서가 다룬다.
- GROUP-070의 확인 절차 문장을 지금 판정 규칙에 맞게 고치는 개별 조치. 아키텍트 몫의 별도 작업이다.
- 기능 상태 이름 체계를 전면 개편하는 일. 이 문서는 세 상태의 설명과 한 상태의 처리 경로만 더한다.
- 개발 작업 단위의 상태 표시를 바꾸는 일. 이 문서가 다루는 것은 기능 단위 상태다.
- 사용자 행동이 없는 상태를 알림이나 메일로 사용자에게 보내는 일.
- 구성 오류를 앱이 직접 고치는 일. 문서를 고치는 주체는 아키텍트 세션이다.

## 인수 조건

1. 구성 확인 필요로 판정되는 기능을 만들고 개발 보드를 열면, 상태 이름과 함께 무엇이 문제이고 누가
   처리하며 사용자가 지금 할 일은 없다는 문장이 상세를 열지 않아도 보인다.
2. 같은 기능을 품질 확인 화면에서 보면 준비 중인 기능 목록에서 같은 세 가지가 보인다.
3. 구성 중단 의심 기능과 개발 막힘 기능에서도 같은 세 가지가 보인다.
4. 사용자 QA 대기 기능은 지금과 같이 확인 시작 입구로 보이고, 사용자가 할 일이 없다는 설명이 붙지
   않는다.
5. 판정 조건 두 가지 이상에 해당하는 기능을 열면 사유가 두 가지 이상 보인다.
6. 사유를 만들지 못하는 기능에서도 목록이 그대로 보이고 상태와 처리 주체가 표시된다.
7. 구성 확인 필요 기능이 있고 그 기능에 유효한 선점이 없으면 아키텍트 대상 판정이 그 기능을 대상으로
   답한다.
8. 같은 기능에 유효한 선점이 있으면 대상으로 답하지 않는다.
9. 사용자 확인 반려 대상과 구성 확인 필요 기능이 동시에 있으면 반려 대상이 먼저 나오고, 작업 정의 오류
   대상과 동시에 있으면 구성 확인 필요 기능이 먼저 나온다.
10. 아키텍트가 문서를 고쳐 판정 조건을 충족시키면 그 기능이 사용자 QA 대기로 바뀌고 확인 입구가 열리며,
    기능 식별자와 구성 버전은 그대로다.
11. 아키텍트가 고치지 못하고 판단을 보고로 남긴 경우, 같은 기능이 같은 구성 버전에서 다시 자동 대상으로
    답하지 않고 화면에는 사람의 판단이 필요하다는 사실과 판단할 내용이 보인다.
12. 이 과정 전체에서 사용자 결정 문서와 승인 기록의 내용이 바뀌지 않는다.
13. 같은 문서 집합을 넣으면 이 변경 전후로 같은 기능 상태가 나온다.
14. 화면에 나오는 문구에 내부 상태 이름, 파일 경로, 코드 식별자가 그대로 나타나지 않는다.

## 기대효과

- 사용자가 목록을 훑을 때 자기 차례인 항목과 아닌 항목이 구분된다. 지금은 상태 이름을 하나하나 해석해야
  구분되고, 구성 확인 필요는 해석해도 구분되지 않는다.
- 구성 오류로 막힌 기능이 사람의 발견을 기다리지 않는다. 지금은 사용자가 화면에서 이상을 느끼고 물어볼
  때까지 아무 일도 일어나지 않는다.
- 구성 오류의 원인이 문서인지 판정 규칙인지가 기록으로 남는다. 아키텍트가 고쳐 풀리면 문서 문제였고,
  보고만 남고 사용자 판단으로 올라오면 판정 규칙 쪽을 볼 차례라는 것이 그 자체로 드러난다.
- 문서 밖이 원인인 경우에도 실행 한도를 반복 시도로 소모하지 않는다.
