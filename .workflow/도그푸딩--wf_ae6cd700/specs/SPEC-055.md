# 막힌 작업의 정의를 감사 가능하게 수정하고 재개한다

## 결정권자 요약

막힘이 반복되는 원인은 개발 실패보다 잘못된 작업 정의를 고칠 공식 절차가 없기 때문이다.
이 기획서는 사용자가 수정을 요청하면 Architect가 승인 범위 안에서 같은 작업을 보완하게 한다.
사용자가 결정할 것은 이 수정 권한과 작업 생성 전 영향 범위 검사를 필수로 둘지 여부다.
승인하면 범위·선행·완료 조건의 누락을 감사 기록과 함께 고치고, 확인 후 안전하게 재개할 수 있다.
TASK-S052-01과 TASK-143의 누락된 검사 범위를 첫 적용 대상으로 삼는다.
개발자의 임의 범위 확장, 자동 재개, 테스트 완화와 원래 기획을 넘어서는 변경은 허용하지 않는다.
승인하지 않으면 차단은 계속 안전하게 동작하지만 잘못 분해된 작업은 공식적으로 복구할 수 없다.

## 기획 내용

현재 개발 작업의 `blocked` 상태는 필요한 안전장치다. 작업 범위를 벗어난 파일을 개발자가 임의로
수정하거나 실패한 검사를 무시하는 대신, 실제 방해 요소를 기록하고 개발을 중단하게 한다. 최근 세
사례에서 이 장치는 의도대로 동작했다.

- TASK-S051-04는 dispatcher가 필요한 예약 응답과 provider 실행 수명 계약이 선행 작업에 없어
  중단됐다.
- TASK-S051-06은 앱이 필요한 기기 단위 서비스·실행 버전·업데이트 영향 조회 계약이 런타임에 없어
  중단됐다.
- TASK-S052-01은 규칙 버전을 올리면 함께 바뀌어야 하는 검사 모듈 두 개가 선언 범위에서 빠져
  중단됐다. 구현 상태의 전체 검사 592개 중 11개가 실패했고, 변경을 되돌리면 592개가 모두 통과했다.

직접 원인은 다르지만 공통된 복구 공백이 있다. Developer는 `blocked` 작업을 자격 대상으로 선택할 수
없다. Architect는 승인 결정에서 작업이 하나라도 만들어지고 나면 같은 결정을 다시 처리할 자격이 없다.
작업 본문의 범위와 완료 조건은 Architect 소유이므로 Developer가 고칠 수도 없다. 사용자가 상태만
`todo`로 바꾸더라도 잘못된 정의는 그대로 남아 같은 지점에서 다시 막힌다.

SPEC-054는 사용자만 `blocked` 작업을 `todo`로 재개하는 흐름을 제안하고 승인받았다. 이 흐름은 실제
방해 요소가 해소된 작업에는 적합하지만, 작업 정의가 잘못된 경우에는 충분하지 않다. 재개 전에
Architect가 누락된 범위·선행·완료 조건을 승인된 기획 안에서 고칠 수 있어야 한다.

이 기획서는 차단 안전장치를 완화하지 않는다. 대신 사용자가 작업 정의 수정 요청을 남기고, Architect가
그 요청만을 근거로 같은 작업 문서를 보완한 뒤, 사용자가 결과를 확인하고 SPEC-054의 조작으로 재개하는
복구 고리를 추가한다. 새 작업을 만들 때도 같은 누락을 줄이도록 읽기 전용 영향 범위 검사를 의무화한다.

### 현재 세 작업의 관계

| 작업 | 현재 직접 원인 | 필요한 복구 경로 |
| --- | --- | --- |
| TASK-S051-04 | provider 실행 수명 계약 누락 | SPEC-054의 선행 계약 보완 뒤 사용자 재개 |
| TASK-S051-06 | 서비스·버전·업데이트 영향 조회 누락 | SPEC-054의 선행 계약 보완 뒤 사용자 재개 |
| TASK-S052-01 | 검사 모듈 두 개가 작업 범위에서 누락 | 이번 기획의 Architect 수정 뒤 사용자 재개 |

TASK-143은 아직 `todo`지만 TASK-S052-01을 선행으로 기다리고 있다. 또한 같은 규칙 버전을 다시 올리면서
동일한 검사 모듈 두 개를 범위에서 제외했다. 실제 개발을 시작해 한 번 더 차단되게 하지 않고, 사용자
수정 요청으로 사전에 작업 정의를 보완할 첫 사례다.

### 복구 흐름

1. Developer가 실제 방해 요소를 만나면 현재 계약대로 작업을 `blocked`로 전환하고 사유를 기록한다.
   새 선택 분류로 작업 정의 오류인지, 선행 계약 누락인지, 구현·환경 장애인지 구분한다.
2. 사용자에게 작업 정의 오류가 보이면 작업 상세에서 `작업 정의 수정 요청`을 선택하고 이유를 남긴다.
   아직 시작하지 않은 `todo` 작업도 명백한 정의 오류가 확인됐고 활성 lease가 없으면 같은 요청을 만들
   수 있다.
3. 앱은 작업 id, 사용자가 확인한 문서 갱신 시각과 요청 이유를 앱 소유 감사 기록으로 남긴다. 작업의
   상태와 본문은 이 단계에서 바꾸지 않는다.
4. Architect는 미처리 수정 요청 하나를 선점한다. 같은 작업 id를 보존하고 승인된 기획서의
   범위 안에서 선언 범위, 선행 관계, 구현 범위, 완료 조건과 검증 절차를 보완한다.
5. Architect는 수정 근거와 전후 차이를 보고서에 남기고 작업에 처리한 수정 요청 id를 연결한다.
   `blocked` 작업은 여전히 `blocked`이고 `todo` 작업은 `todo`로 남는다.
6. `blocked` 작업은 사용자가 수정 결과와 해결 근거를 확인한 뒤 SPEC-054의 사용자 전용 조작으로
   `todo`에 복귀한다. `todo` 작업은 수정 요청이 처리되면 기존 Developer 자격 판정을 다시 적용한다.

### 차단 원인 분류

현재 `## 막힌 사유` 절의 네 필드는 SPEC-053의 승인된 표시 계약이므로 그대로 유지한다. 작업이 현재
`blocked`일 때만 의미를 갖는 선택 frontmatter 필드 `blocked_kind`를 추가해 분류를 저장한다.

| 값 | 뜻 | 기본 후속 행동 |
| --- | --- | --- |
| `task_definition_gap` | 범위, 선행, 완료 조건과 검증 절차가 서로 충돌하거나 빠짐 | Architect 수정 요청 |
| `missing_dependency_contract` | 승인 범위 안의 선행 계약이나 제공 값이 아직 없음 | 선행 보완 작업 확인 |
| `implementation_failure` | 정의는 충분하지만 구현·검사에서 해결할 수 없는 실패 발생 | 사유에 적힌 해결 뒤 재개 |
| `external_dependency` | 권한, 외부 서비스, 운영체제와 사용자 선택 등 저장소 밖 의존 | 외부 해결 뒤 재개 |

분류는 사유를 대신하지 않는다. 기존 `blocked` 문서에 값이 없으면 앱과 에이전트는 원인을 추측하지 않고
`분류되지 않음`으로 표시한다. 다시 차단될 때 현재 사실로 갱신하고, 차단을 해제한 뒤에도 마지막 분류는
감사 정보로 보존하되 현재 분류로 사용하지 않는다.

### 작업 정의 수정의 경계

Architect는 수정 요청을 근거로 기존 작업 id와 후행 의존 참조를 보존한다. 새 작업으로 복제하면 후행
작업이 이전 `blocked` 작업을 계속 기다리므로 같은 문서를 보완한다.

수정할 수 있는 내용은 다음으로 제한한다.

- `scope_files`와 `depends_on`
- 작업 본문의 현재 상태 설명, 변경 범위와 손대지 않는 범위
- 완료 조건, 검증 절차와 범위·선행 설명
- 변경된 사용자 결과를 정확히 반영하기 위한 결정권자 요약
- 처리한 Architect 수정 요청을 연결하는 새 선택 frontmatter 필드

다음 값은 바꾸지 않는다.

- 작업 id, `source_spec_id`와 `source_decision_id`
- 기존 상태와 추가 전용 이력
- 기존 막힌 사유 절과 과거 Developer 보고서
- 목표일과 알 수 없는 기존 메타데이터
- 승인된 기획서의 요구사항과 제품 범위

수정이 원래 기획의 제품 의도를 바꾸거나 새로운 사용자 결정을 요구하면 Architect 수정으로 처리하지
않는다. 새 idea와 specification review로 보낸다. 한 수정 요청으로 다른 task까지 함께 편집하지 않는다.

### 작업 생성 전 영향 범위 검사

Architect는 새 작업과 수정 작업을 `todo` 또는 기존 상태로 인계하기 전에 범위가 완료 조건을 실제로
충족할 수 있는지 읽기 전용으로 확인한다.

- 변경할 상수, 규칙 버전, 공개 계약과 파일 이름을 직접 참조하는 호출부·검사·fixture를 검색한다.
- 작업이 요구하는 모든 검증 명령을 읽고, 그 검사가 고정한 snapshot·버전 단언과 검사 도우미가 변경될
  가능성을 확인한다.
- 예상 변경 파일이 `scope_files` 안에 모두 있는지 대조한다. 검증에 필요하지만 수정하지 않을 파일은
  읽기 전용 근거로 구분한다.
- 기존 미완료 작업과 동일 경로가 겹치면 선행 관계 또는 별도 순서가 선언돼 있는지 확인한다.
- 전체 범위를 아직 알 수 없으면 좁은 범위를 확정한 척하지 않는다. 승인 범위 안의 탐색 작업을 먼저
  두거나 사용자에게 새 기획이 필요한 이유를 보고한다.

작업 본문에는 검색한 핵심 symbol·contract, 영향을 확인한 모듈과 검증 범위를 구현자가 다시 확인할 수
있는 짧은 `범위 사전 검사` 절로 남긴다. 이 절은 파일 목록만 늘어놓지 않고 왜 그 범위면
완료 조건을 충족할 수 있는지를 설명한다.

### Developer 착수 전 검사

Developer는 제품 파일을 바꾸기 전에 작업의 범위 사전 검사와 실제 저장소를 짧게 대조한다. 명백한
누락을 발견하면 구현과 되돌리기를 먼저 반복하지 않는다.

- 누락 경로, 그 파일이 필요한 직접 참조와 실패할 검증을 기록한다.
- 상태를 `blocked`로 전환하고 `blocked_kind: task_definition_gap`을 같은 편집에 기록한다.
- `## 막힌 사유`의 필요한 해결에 Architect 수정 요청이 필요함을 적는다.
- 범위 밖 파일을 고치거나 검사를 삭제·완화하지 않는다.

이 검사는 구현 가능성을 증명하는 별도 설계 단계가 아니다. 작업 정의와 저장소의 명백한 불일치를
초기에 찾는 안전 검사다. 실행 중에만 드러나는 실제 실패는 기존 절차대로 기록한다.

## 포함 범위

- 막힌 사유의 선택 원인 분류와 기존 문서 폴백.
- `blocked` 또는 lease 없는 `todo` 작업에 대한 사용자 전용 Architect 수정 요청.
- 작업 id와 승인 결정을 보존하는 Architect의 제한된 같은 문서 수정.
- 미처리 수정 요청을 Architect 자격과 선점 대상으로 추가하는 규칙.
- 작업 수정 전후, 요청 이유와 처리 근거를 연결하는 감사 기록.
- 신규·수정 작업의 범위 사전 검사와 Developer 착수 전 범위 대조.
- SPEC-054의 차단 재개와 연결하되 자동 재개는 하지 않는 흐름.
- TASK-S052-01과 TASK-143의 누락 범위를 첫 적용으로 검증하는 종단 시나리오.

## 제외 범위

- Developer가 `scope_files`, 선행 관계, 완료 조건과 검증 절차를 직접 고치는 기능.
- 앱이나 에이전트가 검색 결과만으로 범위를 자동 확장하는 기능.
- Architect 수정 완료만으로 `blocked` 작업을 `todo`로 자동 전환하는 기능.
- 실패한 검사 삭제·완화, 전체 저장소를 포괄하는 과도한 범위와 동시 작업 보호 해제.
- 승인된 기획서의 제품 의도와 사용자 결정 범위를 작업 수정으로 변경하는 것.
- `qa_waiting`·`completed` 작업의 정의를 이 경로로 수정하는 것. 이 상태는 기존 QA 또는 새 idea 흐름을 쓴다.
- 기존 `blocked` 작업 전체를 소급 분류하거나 자동 재개하는 migration.
- SPEC-054가 담당하는 provider 실행 수명, 기기 런타임 조회와 설치 계약 구현.

## 요구사항 명세

### R1. 차단 원인을 선택 값으로 분류한다

- Developer가 새로 `blocked`로 전환할 때 현재 사실에 맞는 `blocked_kind`를 막힌 사유 절, 상태, 이력과
  갱신 시각을 기록하는 같은 편집에 쓴다.
- 허용 값은 작업 정의 오류, 선행 계약 누락, 구현 실패와 외부 의존에 대응하는 네 값이다. 값이 없거나
  알 수 없는 기존 문서는 분류되지 않음으로 읽고 추측하지 않는다.
- 분류가 작업 정의 오류이면 필요한 해결과 재개 조건에 Architect 수정 요청이 필요한 구체적 근거를
  쓴다. 분류만으로 사유를 자동 생성하지 않는다.
- 차단 해제 뒤 마지막 분류는 보존하지만 상태가 `blocked`가 아니면 현재 방해 요소로 표시하지 않는다.

### R2. 사용자가 작업 정의 수정 요청을 기록한다

- 앱은 `blocked` 작업과 아직 lease가 없는 `todo` 작업에 `작업 정의 수정 요청` 조작을 제공한다.
- 요청 전에 작업 상태, 현재 범위, 선행 관계, 갱신 시각, 막힌 사유와 기존 수정 요청을 보여 준다.
  사용자의 요청 이유는 비어 있을 수 없다.
- 앱 소유 기록은 작업 id, 사용자가 확인한 기준 갱신 시각, 요청 이유와 생성 시각을 가진다.
  `created_by`는 `user`이고 에이전트가 같은 기록을 쓸 수 없다.
- `in_progress`, `qa_waiting`, `completed` 작업, 활성 lease가 있는 작업과 migration lock 중에는 요청을
  기록하지 않는다.

### R3. stale 화면과 중복 요청을 안전하게 거절한다

- 요청 저장 직전에 작업이 사용자가 확인한 갱신 시각과 같은지, 상태와 lease 조건이 여전히
  허용되는지 다시 확인한다.
- 작업이 바뀌었거나 같은 기준 문서의 미처리 수정 요청이 이미 있으면 새 기록을 만들지
  않고 최신 상태를 보여 준다.
- 요청 기록 일부만 남거나 작업을 함께 고치는 부분 성공을 만들지 않는다. 요청 단계는 작업을
  쓰지 않는다.
- 반복 클릭과 재시도는 같은 요청을 중복 기록하지 않는다.

### R4. Architect가 미처리 수정 요청을 별도 자격 대상으로 처리한다

- Architect 자격 판정은 승인된 기획서에서 아직 작업이 없는 기존 대상과, 앱 소유의 미처리 작업 정의
  수정 요청 두 종류를 구분한다.
- 중단된 개발을 풀기 위한 수정 요청을 새 기획서 분해보다 먼저 선택한다. 같은 종류 안에서는 요청
  생성 시각이 이른 것부터 선택한다.
- Architect는 작업이 아니라 수정 요청 id를 선점한다. 선점 뒤 최신 요청, 기준 갱신 시각, 작업 상태,
  승인 결정, lease와 migration lock을 다시 확인한다.
- 조건이 바뀌었거나 다른 수정이 이미 처리했으면 어떤 작업도 쓰지 않고 lease를 반납한다.

### R5. Architect 수정 권한을 기존 승인 범위 안으로 제한한다

- 한 수정 요청은 작업 하나만 수정한다. 작업 id, `source_spec_id`, `source_decision_id`, 상태와 기존
  이력을 보존한다.
- 선언 범위, 선행 관계, 작업 본문의 구현 범위, 제외 범위, 완료 조건과 검증 절차, 그리고 그 변화에
  맞는 결정권자 요약만 수정할 수 있다.
- 막힌 사유 절과 이전 Developer 보고서를 삭제하거나 재작성하지 않는다. 현재 방해 요소의 기록과 작업
  정의 보완 기록을 구분한다.
- 수정이 승인된 기획서의 요구사항을 추가·제거하거나 사용자 제품 결정을 바꾸어야 하면 처리하지 않고
  새 idea가 필요하다고 보고한다.

### R6. 같은 작업에 수정 요청과 처리 결과를 연결한다

- 수정된 작업은 처리한 수정 요청 id를 선택 frontmatter 필드로 연결하고 갱신 시각을 바꾼다. 알 수
  없는 기존 메타데이터는 보존한다.
- Architect 보고서는 요청 이유, 수정 전후 범위와 선행 관계, 바뀐 완료 조건·검증 절차, 범위 사전 검사
  근거와 남은 위험을 기록한다.
- 같은 요청 id가 작업에 이미 연결돼 있으면 Architect 자격 판정에서 처리 완료로 본다. 재시도가 작업과
  보고서를 중복 수정하지 않는다.
- 여러 차례 수정이 발생해도 앱 소유 요청 기록과 보고서는 추가 전용 감사 기록으로 남는다.

### R7. Architect가 범위 사전 검사를 수행한다

- 새 작업과 수정 작업을 인계하기 전에 변경할 상수·계약·버전을 직접 참조하는 호출부, 검사, fixture와
  snapshot을 읽기 전용 검색으로 확인한다.
- 모든 검증 명령이 수정할 수 있는 파일이 선언 범위에 포함됐는지 대조한다. 범위 밖에서 읽기만 하는
  파일과 실제 수정 가능성이 있는 파일을 구분한다.
- 누락 범위, 겹침 순서와 검증되지 않은 완료 조건이 남으면 작업을 준비됐다고 보고하지 않는다.
- 작업 본문의 `## 범위 사전 검사` 절에 검색 대상, 영향받는 모듈, 검증 범위와 남은 불확실성을 구현자가
  재현할 수 있게 기록한다.

### R8. Developer가 구현 전에 명백한 범위 누락을 확인한다

- Developer는 제품 파일을 바꾸기 전에 작업의 범위 사전 검사 절과 실제 참조를 짧게 대조한다.
- 범위 밖 파일 변경이 완료 조건이나 전체 검증에 명백히 필요하면 제품 코드를 변경하지 않고 작업 정의
  오류로 차단한다.
- 보고서에는 정확한 누락 경로, 직접 참조와 실패할 검증을 남긴다. 증거 없이 넓은 범위를 요구하지 않는다.
- 이 검사로 검사 삭제·비활성화와 광범위한 쓰기 권한을 정당화하지 않는다.

### R9. 수정 완료와 상태 재개를 분리한다

- `blocked` 작업을 Architect가 수정해도 상태는 `blocked`이고 기존 차단 이력은 그대로다.
- 앱은 수정 완료와 범위 사전 검사 근거를 차단 패널에 보여 주지만 자동으로 `todo`로 바꾸지 않는다.
- 사용자는 SPEC-054의 재개 조작에서 수정 보고서와 방해 요소 해결 근거를 확인한 뒤 `blocked`에서
  `todo`로 전환한다.
- `todo` 작업 수정은 `todo`를 유지한다. 처리 완료 뒤 선행 관계, 승인 결정, lease와 범위 겹침을 기존
  Developer 자격 판정으로 다시 계산한다.

### R10. 기존 승인과 QA 의미를 바꾸지 않는다

- 작업 정의 수정 요청은 기획서 수정 요청과 작업 QA 반려와 다른 기록과 이름을 사용한다.
- `qa_waiting`과 `completed` 작업은 수정 요청 대상이 아니다. QA 재작업과 새 idea 흐름을 우회하지 않는다.
- 수정은 기획서 결정, QA 결정, 작업 이력의 기존 의미와 앱 소유권을 변경하지 않는다.
- 이전 앱이 새 선택 필드와 기록 schema를 모르면 작업 문서를 손상시키지 않고 업데이트 안내로 유도한다.

### R11. 첫 두 작업을 실제로 보완한다

- TASK-S052-01 수정은 현재 두 범위 파일에 저장소 조회 검사 모듈과 관리 자산 검사 모듈을 추가한다.
  정확한 경로는 `src-tauri/src/infrastructure/fs_project_repository.rs`와
  `src-tauri/src/infrastructure/managed_project_assets.rs`다. Developer 보고서의 11개 실패와 직접 버전
  단언을 근거로 기록한다.
- TASK-143도 같은 검사 모듈 두 개를 범위에 추가하고 TASK-S052-01 선행 관계를 보존한다. 아직 `todo`인
  상태에서 수정해 불필요한 시작·차단 왕복을 만들지 않는다.
- 두 수정은 작업 id, 기획서와 승인 결정, 이력과 본문 의도를 보존한다.
- TASK-S052-01은 Architect 수정만으로 재개하지 않고 사용자 조작을 기다린다. TASK-143은 수정된 `todo`
  상태에서 일반 선행 판정을 따른다.

### R12. 차단 빈도와 복구 결과를 관찰한다

- 앱 활동 화면은 차단 분류, 수정 요청, Architect 수정과 사용자 재개를 서로 다른 이벤트 이름으로
  보여 준다.
- 동일 작업이 같은 차단 분류와 같은 누락 경로로 다시 `blocked`가 되면 이전 수정 기록과 함께 확인할
  수 있다.
- 이 정보는 감사 기록과 작업 사실에서 로컬로 파생하며 LLM 요약과 원격 분석을 필수로 하지 않는다.
- 첫 버전은 대시보드나 통계 목표를 만들지 않는다. 재발을 확인할 수 있는 이벤트 연결까지만 제공한다.

## 확인 필요

사용자는 아래 두 원칙만 확인하면 된다.

1. **Architect 수정은 사용자의 명시적 요청 뒤에만 허용한다.**

   제안: `blocked` 또는 lease 없는 `todo` 작업에서 사용자가 이유를 남겨 요청 기록을 만든 경우에만
   같은 작업 정의를 수정한다. 자동 범위 확장보다 감사 가능성과 사용자 통제를 우선한다.

2. **Architect 수정과 차단 재개는 두 단계로 유지한다.**

   제안: Architect가 작업 정의를 고쳐도 `blocked` 상태를 유지한다. 사용자가 수정 결과와 방해 요소
   해결을 확인한 뒤 SPEC-054 조작으로 재개한다. 클릭은 하나 늘지만 잘못된 수정이 즉시 개발을
   재개하는 위험을 막는다.

## 기대효과

- Developer가 범위 밖 파일을 고치거나 검사를 무시하지 않고도 잘못된 작업 정의를 공식적으로
  되돌려보낼 수 있다.
- Architect가 같은 작업 id를 보완하므로 후행 의존과 기존 감사 이력이 끊기지 않는다.
- 새 작업 생성 전에 범위 영향을 확인해 명백히 빠진 검사와 호출부를 일찍 발견한다.
- 차단 안전 의미를 유지하면서 `blocked` 작업이 영구적인 막다른 길이 되는 문제를 해결한다.
- TASK-S052-01과 TASK-143이 같은 범위 오류를 반복하지 않고, SPEC-054의 런타임 계약 작업과 서로 맞는
  복구 경로를 갖는다.

## 완료 조건

1. Developer가 작업을 `blocked`로 바꿀 때 허용된 차단 분류 네 가지 중 하나를 같은 편집에 기록하고,
   값이 없거나 알 수 없는 기존 문서는 앱이 추측하지 않는다.
2. 사용자가 `blocked` 또는 lease 없는 `todo` 작업에서 빈 값이 아닌 이유로 수정 요청을 기록하면 앱
   소유 기록에 작업 id, 기준 갱신 시각, 이유, `created_by: user`와 생성 시각이 남는다.
3. 오래된 문서, 활성 lease, migration lock, 허용되지 않는 상태와 중복 요청에서는 작업과 결정 기록
   어느 쪽도 바뀌지 않는다.
4. Architect 자격 판정이 미처리 사용자 수정 요청을 찾고 새 기획서 분해보다 먼저 선택하며, 요청 id를
   선점한 뒤 모든 조건을 재검증한다.
5. Architect 수정이 같은 작업 id, 기획서와 승인 결정, 상태, 이력, 막힌 사유와 알 수 없는 메타데이터를
   보존한다.
6. 수정은 선언 범위, 선행 관계와 승인된 기획 안의 작업 본문 절만 바꾸고, 제품 의도를 바꾸는 요구는
   새 idea로 돌린다.
7. 작업이 처리된 수정 요청 id를 연결하고 Architect 보고서가 요청, 수정 전후, 사전 검사 근거와 남은
   위험을 기록해 재시도에도 중복 수정이 생기지 않는다.
8. 새 작업과 수정 작업의 범위 사전 검사가 직접 참조, 검사, fixture, snapshot과 검증 범위를 확인하고
   작업 본문에 재현 가능한 근거를 남긴다.
9. Developer 사전 검사가 누락 범위 fixture를 제품 편집 전에 작업 정의 오류로 차단하며 정확한 경로,
   직접 참조와 실패할 검증을 보고한다.
10. Architect 수정 뒤 `blocked` 작업은 `blocked`로 남고 사용자 재개 전 Developer 자격에서 제외된다.
    `todo` 작업은 `todo`를 유지하고 기존 자격 판정을 다시 적용한다.
11. 기획서 결정, QA 반려, 작업 정의 수정 요청과 차단 재개가 앱과 활동 화면에서 서로 다른 이름과 감사
    기록으로 읽힌다.
12. TASK-S052-01 수정이 누락된 검사 모듈 두 개를 범위에 추가한 뒤 이전 11개 실패가 해결되고 검사를
    약화하지 않은 상태로 Rust 전체 검사가 통과한다.
13. TASK-143 수정이 같은 모듈 두 개를 범위에 추가한 뒤 시작되지 않은 `todo` 상태를 보존하고,
    TASK-S052-01 선행 관계가 충족될 때만 Developer 자격을 얻는다.
14. 동시 수정 요청, Architect 재시도와 사용자 재개 재시도에서 요청, 작업 갱신, 보고서와 재개 이력이
    각각 한 번만 남는다.
15. 차단 분류와 수정 메타데이터가 없는 기존 작업, 기존 기획서·QA 결정과 여섯 이력 종류가 migration
    없이 계속 읽힌다.
16. 자동 범위 확장, Developer의 작업 본문 편집, 자동 재개, 검사 삭제·완화와 광범위한 저장소 쓰기
    권한이 추가되지 않는다.
