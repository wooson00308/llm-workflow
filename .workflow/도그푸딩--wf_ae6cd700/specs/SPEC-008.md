# 아이디어 전문 읽기 경로 추가

## 기획 내용

지금 아이디어는 앱에서 전문을 볼 수 없다. 인박스 화면은 왼쪽 목록과 오른쪽 미리보기 패널로 나뉘는데, 두 곳 모두 문서 앞부분만 잘라 만든 요약(excerpt)을 쓴다. 요약은 본문에서 빈 줄과 제목 줄을 뺀 앞 세 줄을 붙여 160자에서 자르고 `…`을 붙인 문자열이다. 즉 네 번째 줄부터는 앱 어디에서도 볼 방법이 없다.

이건 잘림 표시를 손보면 되는 문제가 아니다. 기획서와 개발 작업은 목록에서 문서를 고르면 원문을 읽어 와 Markdown으로 그려 주는 경로가 있는데, 아이디어에는 그 경로 자체가 없다. 목록의 두 줄 말줄임은 목록이니까 정상이지만, 그 옆 패널까지 같은 요약을 되풀이하니 사용자는 고를 수는 있어도 읽을 수가 없다.

특히 이 저장소의 아이디어는 대부분 여러 항목의 불릿으로 되어 있다. 배경, 원인, 방향, 제외 사항이 줄마다 나뉘어 있는데 앞 세 줄만 남으면 "무엇을 하자"만 남고 "왜, 어디까지"가 사라진다. 기획자 세션이 아이디어를 기획서로 옮길 때 참고하는 정보가 정작 사용자 화면에서는 안 보이는 셈이다.

그래서 아이디어에도 전문 읽기 경로를 만든다. 미리보기 패널이 선택된 아이디어의 원문 전체를 보여주고, 표현은 기획서·개발 작업 상세가 쓰는 문서 뷰어를 그대로 재사용해 세 문서 종류의 읽기 화면이 같은 모습이 되게 한다. 목록 행의 두 줄 말줄임은 그대로 둔다. 상세에서 전문을 볼 수 있다면 목록이 요약을 보여주는 건 표준 패턴이다.

### 확인 사실

- 아이디어 목록 행과 미리보기 패널은 둘 다 `WorkflowItemSummary.excerpt`를 쓴다. 미리보기는 그 값을 문단 하나(`<p>`)로 그린다.
- `excerpt`는 문서 본문에서 빈 줄과 `#`으로 시작하는 줄을 뺀 뒤 앞 세 줄을 공백으로 이어 붙이고, 160자를 넘으면 잘라 `…`을 붙여 만든다. 목록 조회 결과에 함께 담겨 온다.
- 목록 행의 요약은 CSS로 두 줄에서 말줄임 처리된다(`-webkit-line-clamp: 2`). 목록 영역 자체는 높이 상한과 스크롤이 있다.
- 미리보기 패널에는 높이 상한도 스크롤도 없다. 지금 내용이 항상 짧아서 문제가 드러나지 않았을 뿐이다.
- 기획서와 개발 작업에는 문서 하나를 읽어 `{summary, body}`를 돌려주는 앱 경로가 있고, `body`는 frontmatter를 걷어낸 본문이다. 아이디어에는 이에 해당하는 경로가 없다.
- 두 문서의 읽기 화면은 같은 Markdown 뷰어 컴포넌트(GFM 확장 포함, 링크는 새 창)를 쓴다. 아이디어 미리보기만 서식 없는 평문으로 그린다.
- 기획서 화면은 문서를 불러오는 동안 읽기 패널에 "기획서를 불러오는 중…"을 보여주고, 화면 아래에도 같은 뜻의 표시가 뜬다. 조회에 실패하면 문서 상태는 그대로 두고 공용 오류 표시로 알린다.
- 아이디어 목록은 화면에 들어오면 첫 항목을 자동으로 고르고, 고른 항목이 목록에서 사라지면 다시 첫 항목으로 옮겨 간다.
- 문서 읽기 경로는 워크플로우 디렉터리 안의 파일만 열도록 파일명을 검증한다. 상위 경로를 가리키는 이름은 거부된다.
- 아이디어 상태 배지(`수집됨` / `기획서 채택`)와 하단 문서 정보(문서 ID, 업데이트, 파일명)는 목록 조회 결과만으로 그려진다.

### 포함 범위

- 아이디어 원문 전체를 읽어 오는 경로를 만든다.
- 아이디어를 선택하면 미리보기 패널이 요약 대신 원문 전문을 보여준다.
- 전문 표현을 기획서·개발 작업과 같은 문서 뷰어로 통일한다.
- 전문을 불러오는 중과 불러오지 못했을 때의 표시를 정한다.
- 전문이 길 때 미리보기 패널이 화면 구조를 무너뜨리지 않게 한다.

### 제외 범위

- 목록 행의 표시 변경. 두 줄 말줄임과 요약 사용은 그대로 둔다.
- `excerpt` 생성 규칙 변경. 목록이 계속 쓰므로 그대로 둔다.
- 아이디어 편집·삭제·상태 변경. 이 기획서는 읽기만 다룬다.
- 아이디어 상세를 별도 화면이나 모달로 여는 것. 아이디어에는 기획서의 결정 도구나 개발 작업의 QA 패널 같은 조작이 없어서, 지금의 목록·미리보기 2단 구조로 충분하다.
- 검색에서 아이디어를 골랐을 때의 동작 개선. 현재는 아이디어 화면으로 이동만 하고 그 아이디어를 선택해 주지는 않는다. 이 기획서와 맞닿아 있지만 검색 쪽 동작이라 따로 다룬다.
- 아이디어 본문 내 링크·이미지 처리 정책 변경. 재사용하는 문서 뷰어의 현행 동작을 그대로 따른다.
- 목록에서 아이디어를 고를 때의 자동 선택 규칙 변경.

## 요구사항 명세

### R1. 아이디어를 선택하면 전문이 보인다

- 목록에서 아이디어를 고르면 미리보기 패널이 그 문서의 본문 전체를 보여준다. 앞 몇 줄로 잘린 요약이 아니다.
- 화면에 처음 들어와 첫 항목이 자동으로 선택된 경우에도 같다. 사용자가 한 번 더 눌러야 전문이 나오는 상태여서는 안 된다.
- 다른 아이디어로 옮기면 그 아이디어의 전문으로 바뀐다. 이전 문서의 본문이 남아 있어서는 안 된다.
- 선택된 아이디어가 없으면 지금의 안내 화면을 그대로 보여준다.
- 본문의 frontmatter는 화면에 보이지 않는다. 기획서·개발 작업과 같은 기준이다.

### R2. 표현은 다른 문서와 같다

- 전문은 기획서·개발 작업 상세가 쓰는 문서 뷰어로 그린다. 불릿, 강조, 표, 링크 같은 Markdown 서식이 같은 방식으로 보인다.
- 세 문서 종류의 읽기 화면이 같은 서식 규칙을 따른다. 아이디어만 다른 글꼴이나 다른 링크 동작을 갖지 않는다.
- 이 저장소의 아이디어는 대부분 불릿 목록이다. 목록이 목록으로 보여야 한다.

### R3. 목록은 지금 그대로다

- 목록 행은 계속 요약을 두 줄로 말줄임해 보여준다. 행의 정보량과 높이가 지금과 같다.
- 요약을 만드는 규칙은 바뀌지 않는다.
- 목록에서 선택된 항목의 표시, 상태 아이콘, 날짜, `기획 반영` 표시는 그대로다.

### R4. 미리보기의 문서 정보는 유지된다

- 미리보기 상단의 제목과 상태 배지, 하단의 문서 ID·업데이트 시각·파일명은 지금과 같이 보인다. 전문이 들어오면서 이 정보가 사라져서는 안 된다.
- 이 정보는 목록 조회 결과로 이미 알고 있는 값이다. 전문을 아직 못 읽었거나 못 읽더라도 계속 보인다.

### R5. 불러오는 중과 실패를 사용자가 안다

- 전문을 불러오는 동안 사용자가 그 사실을 알 수 있다. 빈 화면이 이유 없이 머무는 상태여서는 안 된다.
- 전문을 불러오지 못하면 실패했다는 사실이 보인다. 요약으로 조용히 되돌아가 정상처럼 보이는 화면이어서는 안 된다.
- 실패해도 화면은 계속 동작한다. 다른 아이디어를 고를 수 있고, 앱이 멈추거나 화면이 사라지지 않는다.
- 표시 문구와 위치는 기획서 화면의 현행 방식에 맞춘다. 세부 표현은 아키텍트가 정한다.

### R6. 긴 문서가 화면을 무너뜨리지 않는다

- 본문이 아무리 길어도 미리보기 패널이 옆의 목록 패널과 나란한 2단 구조를 유지한다. 패널이 아래로 무한정 늘어나 목록이 화면 밖으로 밀려나서는 안 된다.
- 본문 끝까지 읽을 수 있어야 한다. 잘려서 접근할 수 없는 부분이 생기면 이 기획서의 목적이 무너진다.
- 짧은 아이디어에서 빈 공간이 어색하게 남지 않는다.
- 다른 아이디어로 옮기면 본문은 처음부터 보인다. 이전 문서에서 내려 둔 위치가 남아 있어서는 안 된다.

### R7. 읽기는 읽기다

- 전문을 조회하는 동작이 아이디어 파일이나 워크플로우 문서를 쓰지 않는다. 파일의 수정 시각도 바뀌지 않는다.
- 조회는 등록된 워크플로우 디렉터리 안의 아이디어 문서만 대상으로 한다. 상위 경로를 가리키는 파일명은 거부된다. 기획서·개발 작업 읽기와 같은 기준이다.

## 확인 필요

사용자 결정이 필요한 항목이다. 승인 시 아래 제안대로 진행한다.

1. **긴 본문의 스크롤 처리.** 미리보기 패널 안에서 본문만 스크롤할지, 화면 전체가 아래로 늘어나게 둘지의 선택이다.

   제안: 패널 안에서 본문만 스크롤한다. 근거는 지금 화면 구조다. 왼쪽 목록은 이미 높이 상한과 자체 스크롤을 갖고 있어서, 오른쪽만 늘어나면 두 패널의 아래 끝이 크게 어긋난다. 기획서 읽기 패널이 이미 같은 방식(본문 영역 상한 + 자체 스크롤)이라 화면 사이 일관성도 맞는다. 반대로 페이지 전체를 늘리면 스크롤 막대가 하나여서 단순하다는 장점이 있지만, 긴 아이디어를 읽는 동안 목록이 화면 밖으로 사라져 다음 항목으로 옮기려면 매번 위로 올라와야 한다.

2. **전문을 못 읽었을 때 표시.** 실패를 알릴지, 조용히 기존 요약을 대신 보여줄지의 선택이다.

   제안: 실패했다는 사실을 보여준다. 요약으로 조용히 대체하면 화면은 지금과 똑같아 보이는데, 사용자는 그게 전문인 줄 알고 뒷부분이 없는 채로 판단하게 된다. 문제를 감추지 않는다는 점에서 SPEC-006이 접힌 카드에도 경고를 남긴 것과 같은 규칙이다. 다만 제목·상태·문서 정보(R4)는 그대로 두어, 실패해도 어떤 문서를 보고 있었는지는 알 수 있게 한다.

## 기대효과

- 아이디어를 앱에서 끝까지 읽을 수 있다. 지금은 파일을 직접 열어야만 볼 수 있는 배경·제외 사항·판단 근거가 화면에 드러난다.
- 사용자가 기획서를 검토할 때 출처 아이디어의 전문을 같은 앱에서 대조할 수 있다. 승인·수정 요청 판단의 재료가 늘어난다.
- 아이디어·기획서·개발 작업의 읽기 화면이 같은 모습이 되어, 문서 종류마다 표현이 달라 생기는 위화감이 사라진다.
- 불릿으로 적은 아이디어가 목록으로 보인다. 지금은 세 줄이 한 문단으로 붙어 원래 구조를 알 수 없다.
- 긴 아이디어를 쓰는 데 부담이 없어진다. 지금은 길게 써도 앞 세 줄만 보이니 짧게 쓸 이유가 생긴다.

## 완료 조건

1. 아이디어를 선택하면 미리보기 패널에 문서 본문 전체가 보인다. 검증: 네 줄 이상인 아이디어를 골라 요약에 없던 뒷부분이 화면에 있는지 확인하고, 자동화 테스트로 뒷부분 문자열이 렌더되는지 확인한다.
2. 화면에 처음 들어와 자동 선택된 아이디어도 전문이 보인다. 검증: 아이디어 화면을 처음 여는 자동화 테스트로 확인한다.
3. 다른 아이디어로 옮기면 그 문서의 전문으로 바뀌고 이전 본문이 남지 않는다. 검증: 두 아이디어를 번갈아 선택하는 자동화 테스트로 확인한다.
4. 선택된 아이디어가 없을 때 기존 안내 화면이 그대로 나온다. 검증: 아이디어가 없는 워크플로우로 화면을 그려 확인한다.
5. frontmatter가 화면에 보이지 않는다. 검증: 렌더된 화면에 `schema:`, `id:` 같은 frontmatter 문자열이 없음을 확인한다.
6. 전문이 기획서·개발 작업과 같은 문서 뷰어로 그려진다. 검증: 불릿·강조·링크가 포함된 아이디어를 그려 서식이 적용되는지 확인하고, 링크 동작이 기존 문서 화면과 같은지 확인한다.
7. 목록 행이 지금과 같이 두 줄 말줄임 요약을 보여준다. 검증: 목록 행의 표시를 확인하고, 요약 생성 규칙이 바뀌지 않았음을 기존 테스트로 확인한다.
8. 미리보기의 제목·상태 배지·문서 ID·업데이트 시각·파일명이 그대로 보인다. 검증: 자동화 테스트로 각 항목을 확인한다.
9. 전문을 불러오는 동안 그 사실이 화면에 표시된다. 검증: 조회가 끝나지 않은 상태의 화면을 자동화 테스트로 확인한다.
10. 전문 조회에 실패하면 실패 사실이 보이고, 요약이 전문인 것처럼 대신 나오지 않는다. 검증: 조회 실패를 재현한 자동화 테스트로 확인한다.
11. 조회에 실패해도 다른 아이디어를 이어서 선택할 수 있다. 검증: 실패 후 다른 항목을 선택하는 자동화 테스트로 확인한다.
12. 긴 본문에서도 목록 패널과 미리보기 패널의 2단 구조가 유지되고 본문 끝까지 읽을 수 있다. 검증: 긴 아이디어를 넣고 화면에서 확인한다.
13. 다른 아이디어로 옮기면 본문이 처음부터 보인다. 검증: 긴 아이디어를 아래까지 내린 뒤 다른 항목을 선택해 확인한다.
14. 전문 조회가 파일을 쓰지 않는다. 검증: 조회 전후로 아이디어 파일 내용과 수정 시각이 같은지 확인한다.
15. 워크플로우 디렉터리 밖을 가리키는 파일명 조회가 거부된다. 검증: 상위 경로를 포함한 파일명으로 조회하는 테스트가 실패 결과를 반환하는지 확인한다.
16. 프론트엔드·백엔드 테스트와 타입 검사가 통과한다. 검증: 저장소의 테스트·타입 검사 명령을 실행한다.
