# 두 번째 연동 dream 추가와 연동 공통 구조 추상화

## 기획 내용

SPEC-002는 연동을 앱 내장 고정 목록으로 시작하고 플러그인 추상화를 미뤘다. 그때의 근거는 명확했다. 연동이 하나뿐인데 추상화를 만들면 쓰이지 않는 계층이 된다. 그 판단의 유효기간이 지금 끝난다. 두 번째 연동이 실제로 생기므로, 이번에 공통 구조를 뽑는다.

추가할 연동은 `dream`이다. 역할 세션(기획자·아키텍트·개발자)은 실행될 때마다 트랜스크립트를 남기지만, 그 기록은 다음 세션에 전달되지 않는다. 다음 세션은 문서만 읽고 시작하므로 "왜 이 방향이 반려됐는지", "사용자가 어떤 표현을 싫어했는지" 같은 과정의 맥락을 매번 잃는다. `dream`은 그 트랜스크립트를 메모리 topic 파일로 정제하는 도구다. 하트비트가 역할 세션을 깨우고, dream이 그 결과를 다음 세션이 읽을 형태로 남기면 학습 고리가 닫힌다. 두 연동은 같은 목적의 앞뒤 절반이다.

앱의 역할은 SPEC-002와 동일하다. 앱은 아무것도 실행하지 않는다. 파일 계약을 소유하고 상태를 보여줄 뿐이다. dream 잡 역시 앱이 잡 정의를 관리 블록에 써주는 것까지이며, 정제 실행은 하트비트 데몬과 클로드 세션의 몫이다.

추상화의 범위는 좁게 잡는다. 동적 로딩과 서드파티 등록은 여전히 하지 않는다. 이번에 뽑는 것은 두 연동이 실제로 공유하는 세 가지뿐이다. 연동 카드의 공통 골격, 설치 상태 판정의 공통 표현, 관리 블록 소유권 규약. 세 번째 연동이 왔을 때 공통 부분을 고치지 않아도 되는 상태가 목표이고, 그 이상은 아니다.

이 기획서는 SPEC-002의 산출물 위에 선다. SPEC-002는 승인(DECISION-1265B3C7)되었고 TASK-003~TASK-007이 모두 완료되어 하트비트 연동은 이미 동작한다. 따라서 이 작업의 상당 부분은 신규 기능이 아니라 기존 코드의 구조 변경이다. 구조 변경에서 가장 중요한 완료 조건은 "기존 동작이 그대로다"이며, 아래 완료 조건에 이를 명시한다.

### 대상 도구 확인 사실

`dream`의 다음 동작을 실제 설치본에서 확인했고, 이 기획서는 그 위에 서 있다.

- `dream`은 `claude-heartbeat` 저장소 안의 스킬이다. 설치본의 모듈 경로는 `<claude-heartbeat>/skills/dream/`이고, 같은 저장소에 `heartbeat-register` 스킬이 함께 있다.
- 설치 상태는 `heartbeat skills`가 `[✓] dream — dream skill` / `[ ] heartbeat-register — ...` 형태로 보여준다. 설치 명령은 `heartbeat install dream [--slug SLUG]`이다.
- 스킬 설치본은 `~/.claude/skills/dream/SKILL.md`에 놓인다.
- 전처리 CLI `dream-prep`의 하위 명령은 `prep`, `list`, `status`, `check-unprocessed`, `classify`, `mark`이다.
- `dream-prep check-unprocessed --slug SLUG`는 미처리 트랜스크립트가 있으면 `0`, 없으면 `1`로 종료한다. 도움말에 `for heartbeat condition`이라고 명시되어 있다. 즉 dream 잡의 조건 검사는 별도 스크립트를 만들 필요가 없다.
- `dream-prep status --slug SLUG`의 출력은 한 줄이다: `  전체: 15, 처리됨: 3, 미처리: 12`. JSON 출력 옵션은 없다.
- 그 출력의 `처리됨`은 "정제 완료 수"가 아니다. 구현상 `전체 − find_unprocessed_transcripts()`이고, 이 함수는 마킹(`processed` legacy / `processed_v2` `sealed`)뿐 아니라 활성 파일 게이트(mtime quiet 30분 미만이면 제외, 단 10MB 이상은 강제 처리)까지 적용한다. 실제로 이 저장소 slug에서 `status`는 `처리됨: 3`을 보고했지만, `classify`가 보여주는 그 3개는 마킹된 파일이 아니라 지금 열려 있는 활성 트랜스크립트였다. 이 값을 "정제 완료"로 표시하면 사실과 다르다.
- 정제 메타는 `~/.claude/projects/<slug>/memory/dream_meta.md`에 있다. `last_dream`, `last_lint` 타임스탬프와 `processed_v2:` 목록을 담는다. 아직 한 번도 정제하지 않은 프로젝트에는 이 파일이 없다.
- 메모리 topic 파일은 `~/.claude/projects/<slug>/memory/*.md`이며 `MEMORY.md`와 `dream_meta.md`는 topic이 아니다. `_dream_prep/`는 중간 산출물 디렉터리다.
- `slug` 규칙은 하트비트와 같다(경로의 `/` → `-`). 이 저장소는 `-Users-catze-project-workflow-labs`로 확인했다.
- 현재 `~/.claude/heartbeat/state.json`에는 `dream-catze`, `dream-unity` 잡 기록이 남아 있다. 사용자가 dream 잡을 손으로 구성해 온 이력이 실제로 있으므로, 중복 잡 위험은 가정이 아니라 관측된 사실이다.

### 포함 범위

- 연동 카드·설치 상태 판정·관리 블록 소유권의 공통 구조 분리
- 내장 연동 목록에 `dream` 추가와 dream 연동 카드
- dream 설치 상태 표시와 미설치 시 설치 안내
- dream 정제 상태의 읽기 전용 표시
- 관리 블록에 dream 잡 1종 설치·토글·편집
- 관리 블록 밖 중복 dream 잡 감지

### 제외 범위

- 동적 플러그인 로딩, 서드파티 연동 등록 구조 — SPEC-002의 제외 범위를 유지한다
- 앱이 `heartbeat install dream`을 대행하거나 dream을 실행하는 기능
- 앱이 메모리 topic 파일, `MEMORY.md`, `dream_meta.md`를 읽는 것 이상으로 쓰거나 편집하는 기능
- 메모리 내용 뷰어, 정제 이력 그래프 등 관측 기능 확장
- Windows에서의 연동 지원 — 아래 "확인 필요" 2번 참조
- `.workflow/rules/*.md` 역할 계약 본문 변경, 마이그레이션 스키마 변경
- 조건 스크립트 이중화 정리(`scripts/wf-eligible.sh` ↔ `.workflow/rules/wf-eligible.sh`) — SPEC-002 확인 필요 1번이 별도 아이디어로 미룬 항목이며 이 기획서가 조용히 가져오지 않는다

## 요구사항 명세

### R1. 연동 공통 구조 분리

- 연동 섹션은 특정 연동에 종속되지 않는다. 섹션이 내장 연동 목록을 순회해 카드를 그리고, 각 연동은 자기 카드의 내용만 책임진다.
- 연동 카드의 공통 골격을 정의한다: 이름, 한 줄 설명, 설치 상태 배지, 미설치 안내, 연동별 본문.
- 설치 상태를 연동 공통 표현으로 정의한다. 최소 구분은 미설치 / 설치됨이며, 연동별 부가 상태(하트비트의 데몬 실행 여부, dream의 선행 조건 충족 여부)는 그 위에 얹는다.
- 관리 블록 소유권 규약을 연동 공통 규칙으로 승격한다. SPEC-002 R2가 하트비트에 대해 정한 내용(단일 관리 블록, 파일 끝 배치, 블록 밖 원문 보존, 손상 시 쓰지 않고 실패, 멱등)이 연동 수와 무관하게 성립해야 한다.
- 판단 기준: 세 번째 연동을 추가할 때 공통 골격·상태 표현·블록 규약을 수정하지 않아도 된다. 이 기준을 코드 리뷰 시점에 설명할 수 있어야 한다.
- 동적 로딩은 도입하지 않는다. 연동 목록은 여전히 앱 내장 고정 목록이며 이번에는 항목이 둘이다.

### R2. dream 연동 카드와 설치 상태

- 내장 연동 목록에 `dream`을 추가한다. 카드 설명은 목적을 밝힌다: 역할 세션이 남긴 트랜스크립트를 메모리로 정제해 다음 세션이 과거 맥락을 아는 상태로 시작하게 한다.
- dream은 하트비트에 의존하므로 설치 상태를 세 가지로 구분해 표시한다: 하트비트 미설치 / 하트비트 설치됨·dream 스킬 미설치 / 둘 다 설치됨.
- dream 스킬 설치 여부는 파일 존재로 판정한다. 하트비트 판정과 같은 방식이며, 앱은 이를 위해 외부 명령을 실행하지 않는다.
- 미설치일 때는 설치 안내(`heartbeat install dream`과 공식 저장소 위치)만 보여준다. 앱이 설치를 대행하지 않는다.
- 둘 다 설치됨일 때만 dream 잡 설치·관리 UI를 노출한다.
- dream 잡의 조건 명령은 `dream-prep` 실행 파일에 의존한다. 앱은 하트비트 데몬의 PATH를 알 수 없으므로 이를 검증하지 못한다. 대신 설치될 조건 명령 원문을 화면에 그대로 보여주어, 사용자가 터미널에서 같은 명령을 실행해 확인할 수 있게 한다. 이유를 함께 밝힌다: 조건 검사가 실패하면 하트비트는 잡을 skip 처리하므로 증상이 "아무 일도 일어나지 않음"이 된다.

### R3. dream 정제 상태 표시

- 다음 네 가지를 읽기 전용으로 표시한다. 모두 현재 프로젝트의 slug 기준이다.
  - 전체 트랜스크립트 수: `~/.claude/projects/<slug>/*.jsonl` 개수
  - 정제 마킹된 트랜스크립트 수: `dream_meta.md`의 legacy `processed`와 `processed_v2`의 `sealed` 항목 기준
  - 미정제 트랜스크립트 수: 위 둘의 차
  - 마지막 정제 시점: `dream_meta.md`의 `last_dream`
  - 메모리 topic 파일 수: `memory/*.md` 중 `MEMORY.md`와 `dream_meta.md`를 제외한 개수
- `dream_meta.md`가 없거나 `last_dream`이 없으면 "정제 기록 없음"으로 표시한다. 오류로 취급하지 않는다. 이 경우 정제 마킹 수는 0이다.
- 프로젝트 디렉터리 자체가 없으면 "트랜스크립트 없음"으로 표시한다. 오류로 취급하지 않는다.
- 미정제 수 옆에 판정 기준을 밝힌다: 이 수는 마킹 기준이며, 실제 실행 시 dream은 열려 있는 활성 트랜스크립트를 다음 라운드로 미루므로 한 번에 처리되는 수는 이보다 적을 수 있다. "확인 필요" 1번 참조.
- 상태 표시는 앱의 기존 자동 새로고침 주기를 따른다. 이를 위해 별도 감시 장치를 새로 만들지 않는다.

### R4. dream 잡 설치와 관리 블록

- dream 잡은 SPEC-002가 만든 것과 같은 관리 마커 블록 하나에 기록한다. 연동마다 별도 마커 블록을 만들지 않는다. 블록을 늘리면 "파일 끝 배치"와 "블록 뒤 사용자 `- key: value` 줄 흡수" 위험이 블록 수만큼 늘어나고, 이미 승인된 SPEC-002의 파일 계약이 달라진다.
- 따라서 SPEC-002 R2·R6의 보장은 dream 잡이 블록에 들어간 뒤에도 그대로 성립해야 한다: 블록 밖 원문 바이트 보존, 전역 설정 `tick` 보존, 멱등, 마커 손상 시 원본 무변경 실패, 명시적 사용자 액션에서만 쓰기, 쓰기 전 대상 경로와 변경 요지 확인.
- 잡 이름은 역할 잡과 같은 규칙을 따른다. 프로젝트마다 달라야 하고, 재설치해도 안정적이어야 하며, `heartbeat jobs` 출력에서 어느 프로젝트의 어떤 잡인지 알아볼 수 있어야 한다.
- 잡 이름은 사용자가 손으로 만들어 온 dream 잡 이름(관측된 예: `dream-catze`, `dream-unity`)과 충돌하지 않아야 한다.
- 역할 잡 설치와 dream 잡 설치는 각각 독립적으로 켜고 끌 수 있다. dream만 설치하거나 역할 잡만 설치한 상태가 모두 유효해야 한다.

### R5. dream 잡 기본값

- 설치 시 dream 잡 1종을 아래 기본값으로 기록한다.

| 필드 | 값 |
| --- | --- |
| model | opus |
| interval | 2h |
| timeout | 30m |
| max_per | 6/24h |
| notify | all |
| condition | `dream-prep check-unprocessed --slug=<slug>` |

- `slug`는 현재 프로젝트 루트 경로에서 규칙대로 생성하고, 생성한 값을 UI에 그대로 보여준다.
- `prompt`는 앱이 소유하는 한 줄 고정 문구다. 다음을 포함한다: dream 정제를 수행할 것, 대상 프로젝트가 현재 프로젝트임, 처리할 트랜스크립트가 없으면 정제 없이 정지할 것.
- 기본 주기의 근거를 UI나 설명 문구에 남긴다: 관측된 dream 실행은 15분 규모이고, 정제할 트랜스크립트는 역할 세션이 끝난 뒤에야 생긴다. 역할 잡보다 촘촘하게 돌릴 이유가 없다.
- `interval`, `max_per`, `model`을 편집할 수 있고, 검증 규칙과 실패 시 동작은 SPEC-002 R5와 같다.
- 잡별 마지막 실행 시각·결과·소요 시간을 하트비트 상태 파일에서 읽어 표시하고, 기록이 없으면 "실행 기록 없음"으로 표시한다.

### R6. 중복 잡 감지 확장

- 관리 블록 밖에 같은 `slug`를 쓰면서 `dream-prep`을 조건으로 참조하는 잡이 이미 있으면 경고를 표시한다.
- 경고만 하고 자동으로 지우지 않는다. 사용자 잡은 앱 소유가 아니다.
- 경고 문구는 위험을 구체적으로 밝힌다: 같은 프로젝트에 dream 잡이 둘이면 두 세션이 같은 트랜스크립트를 동시에 정제해 같은 메모리 파일을 서로 덮어쓸 수 있고, 쿼터도 두 배로 소모된다.
- 중복 감지 규칙은 R1의 공통 구조 위에 얹는다. 역할 잡과 dream 잡이 각각 자기 판정 기준을 제공하고, 감지·경고 표시 자체는 공통이어야 한다.

### R7. 기존 동작 보존

- SPEC-002의 완료 조건 1~12가 이 변경 이후에도 그대로 성립한다.
- 이 변경으로 `~/.claude/HEARTBEAT.md`의 기존 관리 블록 내용이 달라지지 않는다. dream 잡을 설치하지 않은 사용자의 파일은 이 변경 전후로 동일해야 한다.
- 앱 시작·프로젝트 열기·자동 새로고침·설정 화면 진입은 전역 파일을 쓰지 않는다. dream 상태 조회도 읽기 전용이다.

## 확인 필요

사용자 결정이 필요한 항목이다. 승인 시 아래 제안대로 진행한다.

1. 미처리 트랜스크립트 수의 출처. 아이디어는 `dream-prep status` 출력 활용을 지시했다. 그런데 그 값을 그대로 쓰려면 앱이 외부 프로세스를 실행해야 하고, 여기에는 두 가지 실제 비용이 있다. 첫째, `dream-prep`은 파이썬 환경에 설치된 실행 파일이고(확인된 설치본은 pyenv 아래에 있다), GUI로 띄운 앱의 PATH에는 그 경로가 없을 수 있어 조회가 조용히 실패한다. 둘째, `status`의 출력은 JSON이 아닌 한국어 한 줄이고, 그 `처리됨` 값은 마킹된 수가 아니라 "지금 당장 처리 가능하지 않은 수"여서 그대로 옮기면 사실과 다른 화면이 된다. 지금까지 앱은 하트비트 상태를 포함해 모든 연동 정보를 파일 읽기로만 얻었고, 외부 명령 실행은 한 번도 하지 않았다.

   제안: R3대로 파일에서 직접 유도한다. 즉 트랜스크립트 파일 수와 `dream_meta.md`의 마킹 목록만으로 "미정제 수"를 계산하고, 그것이 마킹 기준임을 화면에 밝힌다. 이 값은 dream이 한 번에 처리할 수를 정확히 예측하지는 않지만 밀린 정도를 보여주는 데는 충분하고, 활성 파일 게이트 같은 dream 내부 판정 로직을 앱이 베껴 쓰지 않아도 된다. 활성 파일 게이트까지 반영한 정확한 수가 필요하다고 판단되면, 앱이 외부 명령을 실행하는 정책 자체를 별도로 결정한 뒤 다루는 것이 맞다.

2. Windows 지원 범위. SPEC-002는 조건 스크립트가 POSIX `sh`라는 이유로 Windows에서 연동 카드에 미지원 안내를 표시하고 설치 액션을 막았다. dream 잡의 조건은 `dream-prep check-unprocessed`이고 `sh`를 거치지 않으므로, 원리상 dream만 Windows에서 동작할 여지가 있다.

   제안: 이번 범위에서는 현행 유지한다. 연동 섹션 전체를 Windows에서 막는 지금 동작을 그대로 두고, 연동별 플랫폼 정책 분기를 만들지 않는다. 연동이 둘뿐인 시점에 플랫폼 × 연동 조합을 열면 검증할 상태 수만 늘어난다. Windows 수요가 확인되면 별도로 다룬다.

## 기대효과

- 역할 세션이 남긴 맥락이 메모리로 정제되어 다음 세션에 전달된다. 문서에 남지 않는 과정의 정보(반려 사유, 사용자 표현 선호, 실패한 접근)가 매번 소실되지 않는다.
- 연동이 둘이 되는 시점에 공통 구조를 뽑아, 세 번째 연동의 추가 비용이 카드 내용 작성으로 줄어든다. 쓰이지 않는 추상화를 미리 만들지도, 두 벌 복사가 굳어진 뒤에 뽑지도 않는다.
- dream 잡 구성에서 사람이 손으로 적던 값(slug, 조건 명령, 프롬프트, 주기, 쿼터)이 앱이 생성하는 값이 되어, 오타로 조용히 안 돌아가는 실패가 사라진다.
- 정제 상태가 앱 안에서 보이므로, 메모리가 갱신되고 있는지를 `~/.claude/projects/` 아래를 뒤지지 않고 확인한다.

## 완료 조건

1. 설정 화면의 연동 섹션에 `claude-heartbeat`와 `dream` 두 카드가 표시된다. 검증: 화면을 확인한다.
2. dream 카드가 하트비트 미설치 / 하트비트 설치됨·dream 미설치 / 둘 다 설치됨 세 상태를 서로 다르게 표시한다. 검증: 세 상태를 각각 재현하고 화면을 확인한다.
3. 연동 카드 골격·설치 상태 표현·중복 잡 경고 표시가 두 연동에서 공통 구조를 통해 렌더링된다. 검증: dream 카드가 하트비트 전용 타입·컴포넌트를 재사용하지 않음을 코드에서 확인하고, 세 번째 연동을 추가할 때 수정이 필요 없는 경계를 리뷰에서 설명한다.
4. dream 잡 설치 후 `~/.claude/HEARTBEAT.md`의 기존 관리 마커 블록 안에 dream 잡이 R5의 기본값으로 추가된다. 새 마커 블록이 생기지 않는다. 검증: 설치 전후 파일을 비교해 블록 밖 내용이 바이트 단위로 동일한지 확인하고, `heartbeat jobs`로 잡이 인식되는지 확인한다.
5. 같은 설치를 두 번 실행해도 파일이 변하지 않는다. 검증: 두 번째 실행 전후 파일 해시가 같다.
6. 역할 잡과 dream 잡을 독립적으로 켜고 끌 수 있고, 한쪽만 설치된 상태가 모두 유효하다. 검증: 네 가지 조합(둘 다 없음 / 역할만 / dream만 / 둘 다)을 만들고 각 상태에서 파일과 화면을 확인한다.
7. dream 잡 토글을 끄면 잡이 관리 블록에서 사라지고, 다시 켜면 같은 이름으로 복구된다. 검증: 토글 왕복 후 파일 내용이 최초 설치 결과와 같다.
8. 설치되는 dream 잡의 `condition` 명령을 그대로 셸에서 실행하면, 미처리 트랜스크립트가 있을 때 `0`, 없을 때 `1`로 종료한다. 검증: 두 경우를 각각 만들어 종료 코드를 확인한다.
9. 전체·미정제 트랜스크립트 수, 마지막 정제 시점, 메모리 topic 파일 수가 파일 내용과 일치하게 표시된다. 검증: `dream_meta.md`가 있는 slug와 없는 slug를 각각 확인하고, 없는 경우 "정제 기록 없음"과 미정제 수 = 전체 수로 표시되는지 확인한다.
10. 미정제 수 옆에 마킹 기준이라는 설명이 표시된다. 검증: 화면 문구를 확인한다.
11. 관리 블록 밖에 같은 slug의 중복 dream 잡이 있으면 경고가 표시되고, 그 잡은 앱에 의해 수정되거나 삭제되지 않는다. 검증: 중복 잡을 만든 뒤 화면 경고를 확인하고 해당 줄이 그대로인지 확인한다.
12. dream 잡을 설치하지 않은 상태에서 이 변경 전후의 `~/.claude/HEARTBEAT.md` 관리 블록 내용이 동일하다. 검증: 변경 전 파일을 보관하고 변경 후 역할 잡 설치 결과와 해시를 비교한다.
13. SPEC-002의 완료 조건 1~12에 대응하는 기존 자동화 테스트가 모두 통과한다. 검증: 테스트 실행 결과를 확인하고, 삭제되거나 비활성화된 테스트가 없음을 확인한다.
14. 앱 시작·프로젝트 열기·자동 새로고침·설정 화면 진입만으로는 `~/.claude/HEARTBEAT.md`가 변경되지 않고, `~/.claude/projects/` 아래에도 쓰지 않는다. 검증: 설치 액션 없이 앱을 켜고 프로젝트를 열어 새로고침을 여러 번 거친 뒤 두 경로의 수정 시각과 해시가 그대로인지 확인한다.
15. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다.
