# 하트비트 연동 가이드 문서 추가

## 기획 내용

LLM Workflow는 LLM을 실행하지 않는다. 그래서 "누가 언제 역할 세션을 깨우는가"는 전적으로 사용자 환경(스케줄러, 반복 실행 명령, CI 잡)의 몫이고, 현재 저장소에는 그 방법을 설명한 문서가 없다. 조건 검사 스크립트 `scripts/wf-eligible.sh`는 이미 존재하지만 사용법이 어디에도 적혀 있지 않아 저장소를 읽은 사람만 쓸 수 있다.

이 기획서는 외부 스케줄러가 주기적으로 역할 세션을 깨우는 "하트비트" 운용 방식을 문서 하나로 정리하는 것을 다룬다. 문서는 세 가지를 답한다.

1. 기획자·프로젝트 아키텍트·개발자 각각을 어떤 잡으로 돌리는가 (역할 잡 3종 예시)
2. 처리할 대상이 있는지 어떻게 판정하는가 (`scripts/wf-eligible.sh` 사용법)
3. 그 판정이 선점(claim-first) 프로토콜과 어떤 관계인가

특히 3번이 핵심이다. 조건 스크립트는 "지금 깨울 가치가 있는가"를 판단하는 사전 필터일 뿐, 선점 그 자체가 아니다. 스크립트 검사와 세션 시작 사이에는 시간 간격이 있어서, 스크립트를 통과하고도 다른 세션이 먼저 lease를 잡았으면 그 세션은 `NO_ELIGIBLE_WORK`로 끝나는 것이 정상이다. 이걸 문서에 못 박지 않으면 "스크립트가 0을 반환했는데 세션이 아무것도 안 했다"를 버그로 오해하게 된다.

문서는 앱 기능이 아니라 저장소 운용 가이드다. 앱에 하트비트 기능을 넣는 것이 아니라, 사용자가 자기 환경에서 구성할 수 있도록 설명하는 것이 목적이다.

### 포함 범위

- 하트비트 가이드 문서 1개 신규 작성
- 문서 발견성을 위한 `README.md` 문서 링크 1줄 추가
- 가이드가 참조하는 `scripts/wf-eligible.sh`가 저장소에 포함된 상태 보장

### 제외 범위

- 앱(Rust/React) 코드 변경 — 하트비트는 앱 밖의 운용 방식이다
- `scripts/wf-eligible.sh` 로직 변경 — 현재 동작을 그대로 기술한다
- 실제 스케줄러(cron, launchd, GitHub Actions 등) 설치·등록·운영
- 특정 LLM 제품 전용 설정을 유일한 정답으로 규정하는 것 — 공급자 중립 원칙 유지
- lease 만료 교체 구간의 원자성 개선 (2026-08-01 로그의 기존 후속 과제)
- `.workflow/rules/*` 규칙 파일 수정 — 앱 관리 자산이다

## 요구사항 명세

### R1. 문서 신설

- `docs/heartbeat.md`를 새로 만든다.
- 한국어로 작성하고, 기존 `docs/file-contract.md`·`docs/releasing.md`의 문체와 구조 수준을 따른다.
- 문서 첫머리에 하트비트가 무엇인지, 왜 앱이 아니라 사용자 환경의 책임인지 2~3문장으로 밝힌다.

### R2. 역할 잡 3종 예시

- 기획자·프로젝트 아키텍트·개발자 각각에 대해 독립된 잡 예시를 하나씩, 총 3개 제시한다.
- 각 예시는 다음 구조를 공통으로 갖는다: 조건 검사 → 대상이 있을 때만 역할 세션 실행 → 세션 종료 후 아무것도 하지 않음(다음 주기에 재검사).
- 각 역할이 무엇을 대상으로 깨어나는지 명시한다.
  - 기획자: 미처리 아이디어 또는 `revision_requested` 결정
  - 프로젝트 아키텍트: 최신 결정이 `approved`인 기획서
  - 개발자: `todo` 상태 작업
- 각 예시에 그 역할에 넘길 프롬프트의 요지를 포함한다: 역할 고정, 공통 규칙과 역할 계약 준수, 대상 없으면 `NO_ELIGIBLE_WORK` 보고 후 정지.
- 실행 주기 권장값과 그 근거(작업 시간 대비 지나치게 짧은 주기는 중복 기동만 늘린다)를 적는다.
- 특정 LLM CLI에 종속되지 않도록, 예시는 "조건 검사 명령 + 역할 세션 실행 명령"의 조합 형태로 제시하고 실행 명령 자리는 교체 가능한 것으로 설명한다.

### R3. 조건 스크립트 사용법

`scripts/wf-eligible.sh`의 현재 동작을 정확히 기술한다.

- 실행 위치: 프로젝트 루트
- 인자: `planner` | `architect` | `developer` 중 하나
- 종료 코드: `0` = 처리 가능한 대상 있음, `1` = 없음, `2` = 잘못된 사용법
- `.workflow/.runtime/migration.lock`이 있으면 역할과 무관하게 `1`을 반환한다는 점(마이그레이션 중 기동 억제)
- 각 역할의 판정 기준이 이미 lease가 있는 대상과 이미 후속 문서가 참조하는 대상을 제외한다는 점
- 문서에 적는 경로·인자·종료 코드는 실제 스크립트와 일치해야 한다.

### R4. 선점 프로토콜과의 관계

- 조건 스크립트는 사전 필터이며 선점이 아니라는 것을 명시한다.
- 실제 클레임은 세션이 `.workflow/.runtime/leases/<문서-id>.yml`을 배타적으로 생성해서 수행한다는 것을 다시 밝히고 `docs/file-contract.md`를 참조한다.
- 검사와 세션 시작 사이의 경합으로 인해 스크립트가 `0`을 반환해도 세션이 `NO_ELIGIBLE_WORK`로 끝날 수 있으며, 이것이 정상 동작임을 명시한다.
- 하트비트 잡이 절대 하면 안 되는 것을 적는다: 스크립트 결과를 근거로 lease를 대신 만들거나, 만료되지 않은 남의 lease를 지우거나 갱신하는 것.
- 여러 역할 잡을 동시에 돌려도 되는 조건(역할별 대상이 다르고 클레임이 파일시스템 원자성으로 보호된다)을 밝힌다.

### R5. 참조 무결성

- 가이드가 참조하는 `scripts/wf-eligible.sh`가 저장소에 커밋되어 있어야 한다. 현재 이 파일은 추적되지 않은 상태이므로, 추적되지 않았다면 이번 작업에서 함께 포함한다.
- `README.md`의 문서 링크 문단에 하트비트 가이드 링크 1줄을 추가한다. 그 외 `README.md` 내용은 건드리지 않는다.

## 확인 필요

사용자 결정이 필요한 항목이다. 승인 시 아래 제안대로 진행한다.

- 파일명: 아이디어 원문은 `HEARTBEAT.md`로 적었지만 `docs/` 아래 기존 문서는 모두 소문자(`file-contract.md`, `releasing.md`, `todo-list.md`)다. 관례를 따라 `docs/heartbeat.md`를 제안한다. 원문 표기를 유지하려면 수정 요청으로 알려주면 된다.

## 기대효과

- 저장소를 처음 받은 사람이 코드를 읽지 않고도 세 역할을 자동 기동하도록 구성할 수 있다.
- 조건 검사와 선점의 역할 분리가 문서로 고정되어, `NO_ELIGIBLE_WORK` 종료를 버그로 오해하거나 잡이 lease를 대신 조작하는 잘못된 구현을 예방한다.
- 이미 존재하지만 설명이 없던 `scripts/wf-eligible.sh`가 공식 인터페이스가 되어, 이후 스크립트 변경 시 문서가 계약 기준점 역할을 한다.

## 완료 조건

1. `docs/heartbeat.md`가 존재하고 역할 잡 3종·스크립트 사용법·선점 프로토콜 관계 세 주제를 모두 다룬다.
2. 문서에 기재된 인자 3종과 종료 코드 `0`/`1`/`2`의 의미가 실제 스크립트 동작과 일치한다. 검증: 프로젝트 루트에서 `sh scripts/wf-eligible.sh planner; echo $?`, `sh scripts/wf-eligible.sh bogus; echo $?`를 실행해 문서 기술과 대조한다.
3. 문서에 "스크립트가 `0`을 반환해도 세션이 `NO_ELIGIBLE_WORK`로 끝날 수 있다"는 문장이 명시적으로 존재한다.
4. `scripts/wf-eligible.sh`가 저장소에 추적된 상태다. 검증: `git ls-files scripts/wf-eligible.sh`가 경로를 출력한다.
5. `README.md`에서 하트비트 가이드로 가는 링크를 따라갈 수 있고, 그 외 `README.md` 변경은 없다. 검증: `git diff`에서 `README.md` 변경이 링크 1줄에 한정된다.
6. 앱 코드(`src/`, `src-tauri/`)와 `.workflow/rules/` 변경이 없다.
