# 품질 확인 대기열 카드가 기능 소개의 첫 문장만 두 줄까지 보여준다

## 결정권자 요약

### 제안

품질 확인 목록의 기능 카드가 기능 소개 전체 대신 소개의 첫 문장 하나만 보여주게 하고, 그
문장을 그리는 줄 수 상한을 세 줄에서 두 줄로 내린다.

### 현재

카드는 소개 문단을 세 줄까지 보여준다. 소개가 4문장 이상인 기능 15건에서는 그 세 줄이 문장
한가운데에서 말줄임으로 끊기고, 끊긴 자리까지 읽어도 대개 나오는 것은 기능이 무엇인지가 아니라
배경 설명이다. 카드 높이는 소개 길이에 따라 달라진다.

### 변경 후

카드에는 소개의 첫 문장 하나만 실리고, 그 문장은 마침표까지 온전히 보인다. 카드마다 제목 한
줄과 문장 하나라는 같은 모양이 되어 확인 대기 목록을 훑는 것만으로 어떤 기능이 확인을
기다리는지 알 수 있다. 첫 문장 뒤의 설명은 시작을 눌러 들어간 확인 화면과 완료 기록 화면에서
지금과 똑같이 전부 읽을 수 있다.

### 비용과 위험

카드만 보고는 기능의 배경을 알 수 없게 된다. 확인 화면 머리말과 완료 기록 화면의 기능 상세,
준비 중인 기능 목록, 확인 동선은 손대지 않고 기능 문서도 한 건도 고치지 않으므로, 되돌리려면
카드의 표시 규칙만 되돌리면 된다.

## 현재 코드 상태

앱이 화면에 내려 주는 기능 소개 값은 하나다. `src-tauri/src/infrastructure/fs_project_repository.rs`
3390행의 `parse_work_group_description`이 기능 문서 본문에서 소개를 뽑고, 3443행의
`join_paragraphs`가 한 문단 안에서 나뉜 줄은 공백 하나로 잇고 문단 사이는 빈 줄 하나로 남긴다.
이 값이 프론트 계약 `src/features/projects/domain/types.ts` 208행의 `description`으로 실려 온다.

이 값을 쓰는 화면 자리는 셋이다.

- `src/features/projects/components/qa/QaWorkbench.tsx` 84행. 지금 확인할 기능 목록의 카드
  안에서 `group.description`을 `qa-queue-goal` 클래스로 그린다. 값을 가공하지 않고 그대로 넣는다.
- 같은 파일 132행. 시작을 눌러 열린 확인 화면의 머리말에서 `feature.description`을
  `qa-feature-goal` 클래스로 그린다.
- `src/features/projects/components/WorkspaceShell.tsx` 854행. 완료 기록 화면의 기능 상세에서
  같은 값을 같은 클래스로 그린다.

줄 수 상한은 스타일 선언에 있다. `src/features/projects/components/qa/QaWorkbench.css` 16행의
`.qa-queue-goal`이 `-webkit-line-clamp: 3`으로 세 줄에서 끊고, 34행의 `.qa-feature-goal`은 줄 수
상한 없이 `white-space: pre-line`으로 문단 구분을 살린다.

이 두 선언을 지키는 시험이
`src/features/projects/components/qa/qaWorkbenchAlignment.test.ts` 41행에 있다. 43행부터 46행이
대기열 쪽의 세 줄 상한을 확인하고, 48행부터 50행이 열린 화면 쪽에 줄 수 상한이 없고 문단 구분이
살아 있음을 확인한다.

소개에서 첫 문장을 잘라 내는 규칙은 저장소 어디에도 없다. 프론트의 `src/features/projects/domain/`
에는 문서 절 분리(`documentSections.ts`), 실행 활동(`runActivity.ts`), 기획서 결정 이름표
(`specDecisionLabels.ts`)가 각각 모듈 하나와 시험 하나로 들어 있다.

## 변경 범위

- `src/features/projects/domain/featureIntro.ts`를 새로 만들고 소개 문자열에서 첫 문장을 잘라 내는
  함수 `featureIntroLead(description: string): string` 하나를 내보낸다. 판정 규칙은 아래 완료 조건
  C2가 정한 그대로다.
- `src/features/projects/components/qa/QaWorkbench.tsx` 84행이 `group.description` 대신 그 함수의
  결과를 그리게 한다. 결과가 빈 문자열이면 지금 빈 소개를 다루는 방식과 같이 카드에 아무것도
  그리지 않는다.
- `src/features/projects/components/qa/QaWorkbench.css` 16행의 `.qa-queue-goal`에서
  `-webkit-line-clamp` 값을 3에서 2로 내린다. 같은 선언의 나머지 속성은 그대로 둔다.
- `src/features/projects/components/qa/qaWorkbenchAlignment.test.ts` 41행 시험의 기대값과 시험
  이름을 두 줄 상한에 맞춘다. 48행부터 50행의 열린 화면 쪽 확인은 그대로 둔다.
- 새 모듈의 단위 시험 `src/features/projects/domain/featureIntro.test.ts`와, 카드가 첫 문장만
  그린다는 것을 확인하는 시험을 `src/features/projects/components/qa/QaWorkbench.test.tsx`에 더한다.

## 범위 밖

- 기능 소개를 뽑아 내려 주는 저장소 읽기 코드. `parse_work_group_description`과 `join_paragraphs`,
  그리고 프론트 계약의 `description` 필드는 지금 값을 그대로 유지한다. 확인 화면과 완료 기록
  화면이 같은 값을 계속 써야 하므로 값을 좁혀서 내려 주지 않는다.
- `src/features/projects/components/qa/QaWorkbench.tsx` 132행과
  `src/features/projects/components/WorkspaceShell.tsx` 854행의 표시 기준. 두 자리는 소개 전체를
  계속 보여준다.
- `.qa-feature-goal` 스타일 선언.
- 준비 중인 기능 목록의 구성. 이 목록은 지금도 소개를 보여주지 않는다.
- 기능 문서 파일. 문서를 고쳐야만 올바르게 보이는 방식은 이 작업의 해법이 아니다.
- 카드를 눌렀을 때의 동선과 카드 안의 상태 표시.

## 완료 조건

- C1. 지금 확인할 기능 목록의 카드는 소개의 첫 문장 하나만 그린다. 소개가 4문장 이상인 기능에서도
  카드에 들어가는 값에 둘째 문장의 첫 낱말이 포함되지 않는다. (기획서 R1, R3, 완료 판정 A1)
- C2. 첫 문장 판정이 다음 규칙 그대로다. (기획서 R1)
  - 소개의 처음부터 읽어, 마침표·물음표·느낌표 중 하나가 나오고 그 바로 다음 글자가 공백류
    (공백, 줄바꿈, 탭)이거나 소개의 끝이면 그 부호까지가 첫 문장이다.
  - 그런 자리가 하나도 없으면 소개 전체가 첫 문장이다.
  - 결과의 앞뒤 공백은 없앤다.
  - 소수점처럼 부호 뒤에 공백이 오지 않는 자리는 문장 끝으로 보지 않는다. "실측 3.5초가 나온다."는
    통째로 첫 문장이다.
  - 부호가 잇달아 붙은 자리는 공백이 따라오는 마지막 부호에서 끊는다. "정말인가!? 그렇다."의 첫
    문장은 물음표까지다.
  - 소개가 여러 문단이고 첫 문단이 한 문장이면, 문단 사이의 빈 줄 앞에서 끊긴 그 한 문장이 결과다.
- C3. 카드의 소개 자리는 최대 두 줄까지 그리고 넘치면 말줄임으로 끊는다. 대기열 스타일 선언의 줄
  수 상한이 2이고, 넘침을 감추는 선언과 여러 줄 상자 선언은 지금 값 그대로 남는다. (기획서 R2,
  완료 판정 A3)
- C4. 소개가 1문장인 기능의 카드 값은 이 변경 전후로 같다. (완료 판정 A2)
- C5. 소개가 비어 있는 기능의 카드는 제목만 그린다. 빈 줄이나 자리표시 문구가 들어가지 않는다.
  (기획서 R6, 완료 판정 A6)
- C6. 시작을 눌러 열린 확인 화면의 머리말과 완료 기록 화면의 기능 상세는 소개 전체를 그대로
  그린다. 두 자리에 줄 수 상한이 붙지 않고 문단 구분이 살아 있다. (기획서 R5, 완료 판정 A5)
- C7. 카드에는 소개를 펼치는 조작이 없고, 카드를 누르면 확인 화면이 열린다. 이 동선을 이 작업이
  바꾸지 않는다. (기획서 R4, 완료 판정 A4)
- C8. 이 작업의 변경은 선언한 여섯 파일 안에서 끝난다. 기능 문서, 저장소 읽기 코드, 프론트 계약
  타입, 완료 기록 화면 코드가 수정되지 않는다. (기획서 R7, 완료 판정 A7)
- C9. `npm run check`가 통과한다.

## 검증 절차

1. `src/features/projects/domain/featureIntro.test.ts`를 만들어 C2의 여섯 규칙을 각각 확인한다.
   4문장 소개, 문장 부호가 하나도 없는 소개, 소수점이 든 소개, 부호가 잇달아 붙은 소개, 문단이
   여럿인 소개, 빈 문자열과 공백만 있는 문자열을 넣고 기대값을 확인한다. 4문장 소개 사례는 저장소의
   긴 소개와 같은 형태로 만들고, 결과에 둘째 문장의 첫 낱말이 없음을 함께 확인해 C1을 덮는다.
2. `src/features/projects/components/qa/QaWorkbench.test.tsx`에 시험을 더한다. 소개가 여러 문장인
   기능 픽스처를 지금 확인할 기능 목록에 올리고, 대기열 카드 자리에 첫 문장만 있고 둘째 문장이
   없음을 확인한다(C1). 소개가 1문장인 픽스처로 카드 값이 소개와 같음을 확인한다(C4). 소개가 빈
   픽스처로 카드에 소개 자리 자체가 없음을 확인한다(C5). 같은 픽스처로 기능을 열어 확인 화면
   머리말에 소개 전체가 그대로 있음을 확인한다(C6). 픽스처를 만드는 방식은 같은 파일 17행의
   기존 픽스처 도우미를 따른다.
3. `src/features/projects/components/qa/qaWorkbenchAlignment.test.ts` 41행 시험을 두 줄 상한으로
   고쳐 통과시킨다. 대기열 쪽 줄 수 상한이 2, 여러 줄 상자와 넘침 감추기가 지금 값 그대로임을
   확인하고(C3), 48행부터 50행의 열린 화면 쪽 확인은 고치지 않은 채 통과시킨다(C6).
4. `npm run check`를 통과시킨다(C9). 기존 시험 가운데 이 작업이 고치도록 지시받지 않은 것은 하나도
   고치지 않는다.
5. `git status`와 변경 파일 목록으로 선언한 여섯 파일 밖의 수정이 없음을 확인한다(C8).
6. 앱을 띄워 품질 확인 화면을 연다. 소개가 긴 기능과 짧은 기능의 카드가 같은 높이로 서고 카드마다
   문장 하나가 마침표까지 온전히 보이는지, 카드에 펼치기 조작이 없는지 눈으로 확인한다(C3, C7).
   카드를 눌러 확인 화면 머리말에 소개 전체가 문단 구분과 함께 보이는지 확인한다(C6). 확인한 화면을
   보고서에 적는다.

## 범위 사전 검사

선언한 파일은 여섯이다. 새 판정 모듈과 그 시험, 대기열 카드를 그리는 화면 파일과 그 시험, 줄 수
상한을 든 스타일 파일과 그 스타일을 지키는 시험이다. 완료 조건이 요구하는 편집이 이 여섯 밖으로
나가지 않는다는 것을 아래 값 경로에서 하나씩 확인했다.

판정 규칙을 프론트에 두고 저장소 읽기 코드에 두지 않은 이유는 C6 때문이다. 확인 화면 머리말과 완료
기록 화면은 소개 전체를 계속 써야 하므로, 내려오는 값을 좁히면 그 두 자리가 함께 좁아진다. 값은
지금대로 전부 내려보내고 카드가 그릴 때만 좁히면 화면 셋의 요구를 모두 만족하면서 계약 타입과
저장소 읽기 코드를 건드리지 않아도 된다.

`src-tauri/src/infrastructure/fs_project_repository.rs`를 열어 보고 뺐다. 3390행의
`parse_work_group_description`이 소개 절을 뽑고 3443행의 `join_paragraphs`가 문단을 정리한 문자열을
낸다. 이 작업은 그 문자열을 입력으로 받을 뿐 다른 값을 요구하지 않으므로 고칠 자리가 없고, C8이
이 파일이 수정되지 않을 것을 요구한다.

`src/features/projects/domain/types.ts`도 열어 보고 뺐다. 208행의 `description`이 소개 전체를 담는
문자열이고 카드가 쓸 값은 그 문자열에서 계산된다. 새 필드를 만들지 않으므로 계약이 그대로다.

`src/features/projects/components/WorkspaceShell.tsx`도 열어 보고 뺐다. 854행이 완료 기록 화면에서
`selectedGroup.description`을 `qa-feature-goal`로 그린다. 이 작업은 그 값도 그 클래스도 바꾸지
않으므로 C6이 편집 없이 성립한다.

`src/features/projects/components/DevelopmentBoard.tsx`도 확인하고 뺐다. 341행과 451행의
`description`은 진행 현황 문구와 칸 설명이며 기능 소개와 다른 값이다. 이 화면은 기능 소개를 그리지
않는다.

지금 이 워크플로에 검증되지 않은 작업 문서가 하나도 없어, 선언한 여섯 파일과 겹치는 진행 중 작업이
없다. 이 그룹의 작업도 하나뿐이라 `depends_on`을 둘 상대가 없다. 기계 상태를 조건으로 삼는 측정이
없으므로 `solo_run`도 두지 않는다.

- 값 경로: C1과 C2의 카드에 실리는 첫 문장. 값을 만드는 자리는 새 모듈
  `src/features/projects/domain/featureIntro.ts`의 `featureIntroLead`이고 새로 쓴다. 입력은
  `src-tauri/src/infrastructure/fs_project_repository.rs` 3390행이 만들어 프론트 계약
  `src/features/projects/domain/types.ts` 208행의 `description`으로 실려 오는 문자열이며, 두 자리
  모두 값을 이미 그대로 실어 나르므로 편집하지 않는다. 소비 자리는
  `src/features/projects/components/qa/QaWorkbench.tsx` 84행으로, 지금 `group.description`을 직접
