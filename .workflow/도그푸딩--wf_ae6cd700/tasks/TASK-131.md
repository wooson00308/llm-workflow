# 한국어 파일 계약 문서에 확장 대응표와 전후 예문을 넣는다

## 결정권자 요약

QA 의견에 따라 한국어 문체 안내를 다시 작성했다. 기존의 계약서식 표현을 일반적인 기획·개발 문서
표현으로 바꾸고, 표 제목도 표현별 대안으로 수정했다.
표에는 공통 규칙의 세 가지 예시와 기존 문서에서 자주 발견된 네 가지 표현이 들어 있다. 각 항목은
문맥에 맞는 구체적인 대안을 제시한다. 필요하면 표에 없는 표현도 사용할 수 있다.
의미가 분명하다는 이유만으로 어색한 비유를 허용하던 설명은 삭제했다. 한국 기획·개발 문서에서 실제로
통용되는 표준 기술 용어이고 문장에서 정확한 의미로 사용된 경우에만 예외로 인정한다.
전후 예문 세 쌍은 내용이 적절하다는 QA 의견에 따라 유지했다. 프런트 테스트 705개와 타입 검사, 빌드가
모두 통과했다. 변경 범위는 파일 계약의 문체 안내와 워크플로 기록이며 앱 코드는 변경하지 않았다.

---

## 이 작업이 맡는 범위

SPEC-046의 R4 중 한국어 파일 계약 문서 쪽과 R7의 대조 조건이다. 기획서 완료 조건 5·6을 이 작업이
처리한다.

공통 규칙과 세 역할 계약, 버전 상수, 검사는 TASK-130이 맡는다. 이 작업은 그 결과를 읽어 대조한다.

## 아키텍트가 고정하는 값

### 1. 새 절은 `docs/file-contract.md`의 `## 안전 규칙` 바로 앞에 넣는다

문서의 절 제목은 이름이고 번호가 아니므로 삽입해도 다른 참조가 밀리지 않는다. 그래도 `## 안전 규칙`
앞을 고르는 이유는 둘이다. 문체는 특정 문서 종류의 계약이 아니라 네 종류 모두에 걸리는 내용이므로
`## 기획서`·`## 개발 작업` 같은 종류별 절 안에 넣을 곳이 없다. 그리고 `## 안전 규칙`은 문서를 닫는
목록이라 그 뒤에 본문 절을 더하면 문서의 끝이 두 번 온다.

절 제목은 `## 문서 문체`로 한다.

### 2. 절이 담는 세 가지

| 하위 내용 | 기획서 근거 |
| --- | --- |
| 공통 규칙 §9가 단일 정의라는 것과 그 절을 가리키는 한 줄 | R7 |
| 확장 대응표 — 최소 세 쌍에 사용량이 큰 낱말을 더한 표 | R4 |
| 전후 예문 — 고치기 전 문장과 고친 뒤 문장의 쌍 | R4 |

문서 전체가 공통 규칙을 한국어로 다시 적는 구조이고, 요약 절 규칙을 한국어로 다시 적은 전례가 이미
있다(기획서 확인 사실 8). 그 전례와 같은 밀도로 쓴다.

### 3. 확장 대응표에 들어가는 낱말

**최소 세 쌍은 공통 규칙과 글자 그대로 같은 대응이어야 한다.** TASK-130이 규칙 본문에 쓴 값을 읽어
그대로 옮긴다. 기획서가 정한 값은 아래와 같지만, 대조의 기준은 기획서가 아니라 실제로 설치된 규칙
본문이다.

| 바꿀 낱말 | 바꿔 쓸 말 |
| --- | --- |
| 착지 | 구현, 반영, 병합, 배포 |
| 닫다 | 해결, 충족, 완료 |
| 원천 | 데이터 출처, 원본 문서, 판단 기준 |

여기에 기획서 확인 사실 1에서 사용량이 큰 낱말을 더한다. 확인 사실 1이 센 값은 "자리" 1652회·281편,
"몫" 392회·192편, "닫" 387회·174편, "착지" 289회·85편, "어법" 253회·106편, "원천" 189회·74편,
"표면" 81회·26편이다. 최소 세 쌍에 들어 있지 않은 네 낱말("자리", "몫", "어법", "표면")을 확장
대응표에 더한다.

- 각 낱말의 바꿔 쓸 말은 개발자가 정한다. 기획서가 이 네 낱말의 대응을 정해 두지 않았다. 정할 때
  근거는 그 낱말이 실제로 쓰인 문맥이고, 고른 근거를 보고서에 적는다.
- 낱말을 더 넣어도 된다. 확인 사실 1의 일곱 낱말은 하한이지 상한이 아니다.

### 4. 전후 예문의 개수와 출처

- 최소 세 쌍을 넣는다. 세 쌍은 최소 대응 예시의 세 낱말을 각각 하나씩 보인다.
- 예문의 "전" 문장은 이 저장소의 기존 문서에서 실제로 쓰인 문장을 가져오되, 출처 문서를 인용하지
  않고 문장만 옮긴다. 기존 문서를 고치지 않는다는 것이 기획서 R8이다.
- 예문의 "후" 문장은 공통 규칙 §9의 문장 원칙을 지켜야 한다. 이 문장 자체가 기획서 완료 조건 6이
  확인하는 표본이다.

### 5. 대응표는 금지 목록이 아니라는 것을 문서가 밝힌다

뜻이 하나로 정해지는 문맥에서는 그 낱말을 쓸 수 있고, 그때는 대상을 함께 적는다. R4 네 번째 항목이
요구한 내용이고, 공통 규칙과 이 문서가 같은 말을 해야 한다.

## 완료 조건

1. `docs/file-contract.md`에 `## 문서 문체` 절이 `## 안전 규칙` 바로 앞에 있고, 고정값 2의 세 가지를
   담는다. 검증: 문서 확인. (R4 / 기획서 완료 조건 5)
2. 확장 대응표에 최소 세 쌍이 있고, 그 세 쌍이 설치된 공통 규칙 본문의 최소 대응 예시와 같은
   대응이다. 검증: 규칙 본문과 이 문서를 나란히 두고 대조한 결과를 보고서에 적는다. (R7 / 기획서
   완료 조건 5)
3. 확장 대응표에 "자리", "몫", "어법", "표면" 네 낱말이 더 들어 있고, 각각의 바꿔 쓸 말과 그것을
   고른 근거가 있다. 검증: 문서 확인과 보고서. (R4)
4. 전후 예문이 최소 세 쌍 있고, 각 쌍의 "후" 문장이 공통 규칙 §9의 문장 원칙을 지킨다. 검증: 세션이
   예문마다 원칙 세 항목을 대조하고 결과를 보고서에 적는다. (R4 / 기획서 완료 조건 6)
5. 대응표가 금지 목록이 아니라는 것과, 뜻이 하나로 정해지는 문맥에서는 대상을 함께 적고 쓸 수 있다는
   것이 문서에 있다. 공통 규칙과 다른 규칙으로 읽히지 않는다. 검증: 두 문서 대조. (R4·R7)
6. 이 작업이 만든 개발 작업 문서와 개발 보고서가 §9의 문장 원칙을 지킨다. 검증: 보고서를 쓴 뒤
   세션이 스스로 확인하고 그 결과를 보고서에 적는다. (기획서 완료 조건 11)
7. 변경 파일이 `docs/file-contract.md` 하나뿐이다. 앱 소스와 규칙 자산, `.workflow/` 아래 기존 문서가
   달라지지 않았다. 검증: `git diff --stat`. (R8 / 기획서 완료 조건 12)
8. `npm run check`가 통과한다.

## 검증 절차

1. 설치된 `.workflow/rules/workflow.md`의 §9를 열어 최소 대응 예시 세 쌍의 원문을 읽는다. 그 값과
   이 문서의 확장 대응표를 낱말 단위로 대조하고 결과를 보고서에 적는다. 완료 조건 2의 근거다.
2. 전후 예문의 "후" 문장마다 §9의 세 항목(주체·행동·결과가 구체적인가, 한 문장에 주장이 하나인가,
   비유를 구체어로 바꿨는가)을 대조하고 결과를 보고서에 적는다. 완료 조건 4의 근거다.
3. `git diff --stat`으로 변경 파일이 하나뿐임을 확인한다. 완료 조건 7의 근거다.
4. `npm run check`.
5. 보고서를 쓴 뒤 자기 문장이 §9의 원칙을 지키는지 확인한다. 완료 조건 6의 근거다.

## 범위 파일

- `docs/file-contract.md` — 새 `## 문서 문체` 절.

앱 소스와 규칙 자산은 이 작업이 만지지 않는다. TASK-130의 범위다.

## 선행

- `TASK-130`(SPEC-046) — 공통 규칙 §9와 최소 대응 예시 세 쌍을 만드는 작업이다.

두 작업은 서로 다른 파일을 고치므로 파일이 겹쳐서 순서를 두는 것이 아니다. 순서를 두는 이유는 기획서
R7과 완료 조건 5가 요구하는 대조의 기준 때문이다. 이 작업은 확장 대응표를 기획서의 서술이 아니라
실제로 설치된 규칙 본문과 맞춰야 한다. TASK-130이 문장을 다듬으면서 세 쌍의 표기가 기획서와 달라질
수 있고, 그때 이 작업이 먼저 끝나 있으면 어긋난 대응표가 확인 도장까지 통과한다.

## 확인 동선

화면 변경이 없는 문서 작업이다. 다음 내용을 확인하면 된다.

1. `docs/file-contract.md`를 열어 `## 안전 규칙` 바로 앞에 `## 문서 문체` 절이 있는지 본다.
2. `### 표현별 대안` 표의 첫 세 줄이 아래와 같은지 본다.
   - 착지 → 구현, 반영, 병합, 배포
   - 닫다 → 해결, 충족, 완료
   - 원천 → 데이터 출처, 원본 문서, 판단 기준
3. 같은 표에 자리, 몫, 어법, 표면의 대안도 있는지 본다.
4. 표 아래 설명이 어색한 비유를 허용하지 않고, 실제로 통용되는 표준 기술 용어만 예외로 인정하는지
   확인한다.
5. `### 수정 전과 수정 후`에 예문 세 쌍이 있는지 본다. 각 쌍의 "후" 문장에 착지·닫다·원천이 남아
   있지 않아야 한다.
6. 자동 검사 결과는 `npm run check`이고 프런트 테스트 705개 통과, 타입 검사와 빌드 성공이다.
7. 변경 파일은 `git diff --stat -- docs/`로 확인한다. `docs/file-contract.md` 한 줄만 나오면 정상이다.

위 내용이 모두 확인되면 정상이다.
