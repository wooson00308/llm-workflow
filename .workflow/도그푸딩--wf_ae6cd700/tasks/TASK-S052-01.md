# 새 기획서와 개발 작업이 구조화된 요약 계약을 따른다

## 결정권자 요약

규칙 버전을 올리면 다른 파일 두 개에 박혀 있는 이전 버전 문자열이 함께 깨진다.
그 두 파일이 작업 범위 밖이어서 범위 조건과 전체 검사 통과 조건을 같이 지킬 수 없었다.
이번에 두 파일을 범위에 넣고 완료 조건을 새 범위와 일치시켜 그 충돌을 없앴다.
두 파일에서는 버전 문자열만 고치고 기존 검사를 지우거나 약하게 만들지 않는다.
그사이 다른 작업이 규칙 버전을 16으로 올렸으므로 이 작업은 그 위에서 17로 올린다.
구현 대상인 구조화 요약 계약 자체는 승인된 범위 그대로이며 넓히거나 줄이지 않았다.
사용자가 재개한 뒤 네 파일을 모두 구현했고 자동 검사가 전부 통과해 지금은 사용자 확인을 기다린다.

## 막힌 사유

- 막힌 지점: 규칙 버전 상승이 범위 밖 두 파일의 이전 버전 문자열 단언을 함께 깨뜨려, 범위 파일 두 개만 바꾸라는 완료 조건과 전체 자동 검사 통과 조건을 동시에 지킬 수 없었다.
- 필요한 해결: 관리 자산 동기화 검사와 프로젝트 저장소 검사를 가진 두 파일을 범위 파일에 추가하고, 완료 조건 10을 네 파일 기준으로 다시 썼다.
- 재개 조건: 문서 수리가 끝났으므로 추가 선행 조건 없이 사용자가 앱에서 재개하면 된다. 규칙 버전 전제는 TASK-148이 올린 16을 기준으로 갱신했다.
- 관련 대상: TASK-148

## 확인 동선

이 작업에는 눈으로 볼 화면이 없다. 바뀐 것은 앱이 설치하는 규칙 문언과 사용자·개발자용 계약 문서라
자동 검사가 그 문언을 대조한다. 확인 도장은 아래 수치를 신뢰한다는 뜻이다.

- `cargo test --manifest-path src-tauri/Cargo.toml` → 610 passed, 0 failed
- `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets` 경고 없음, `cargo fmt` 적용

문언을 직접 읽고 싶다면 두 곳을 보면 된다.

1. 임시 폴더를 프로젝트로 열면 앱이 `.workflow/rules/workflow.md`를 새로 설치한다. 그 파일의
   frontmatter가 `rules_version: 17`이고, `## 8.` 절 안에 `### The structured summary`가 있다. 일곱
   하위 제목이 `### 제안`부터 `### 결정 요청`까지 이 순서로 한 번씩 정의되고, `### 영향 범위`가
   `- 변경:`과 `- 유지:` 두 표식을 요구하며, `### 비용과 위험`은 선택이라고 적혀 있다.
2. `.workflow/rules/roles/`의 세 계약은 각각 `rules_version: 11`(planner), `11`(architect),
   `12`(developer)이고, 자기 문서의 의무만 적은 뒤 공통 규칙 `§8`을 가리킨다. 제목 목록을 다시 적지
   않는다.

같은 내용이 `docs/file-contract.md`의 `#### 구조화된 요약` 절과 기획서·개발 작업 예시에 한국어로 적혀
있다. 개발 보고서 예시와 설명은 평문 요약과 열 줄 상한을 그대로 유지한다.

이미 있는 문서는 바뀌지 않는다. 기존 기획서·작업의 평문 요약이나 요약 없는 문서를 앱이 고치지 않고,
그 때문에 목록·활동 화면의 표시나 자격 판정이 달라지지도 않는다.

## 목적

앱이 설치하고 갱신하는 공통 규칙과 역할 계약에 구조화된 결정권자 요약 문법을 추가한다. 이후
planner가 새 기획서나 수정 요청 후속 기획서를 쓸 때와 architect가 새 개발 작업을 만들 때 같은
구조를 사용하게 한다. developer는 구조화된 작업의 상태를 바꿀 때 그 구조와 현재 사실을 함께
유지한다. 개발 보고서는 SPEC-052의 표시 범위가 아니므로 기존 평문 요약 계약을 계속 따른다.

설치된 `.workflow/rules/` 파일을 직접 고치지 않는다. 정본인 앱 내장 규칙과 파일 계약 설명을
갱신하고, 기존 동기화 경로가 프로젝트에 새 버전을 배포하게 한다.

## 구조화된 요약 계약

새 기획서와 새 개발 작업의 `## 결정권자 요약` 절에는 아래 하위 제목을 정확히 이 순서로 한 번씩
쓴다.

1. `### 제안`
2. `### 현재`
3. `### 변경 후`
4. `### 사용자 결과`
5. `### 영향 범위`
6. 선택 항목 `### 비용과 위험`
7. `### 결정 요청`

`영향 범위`에는 `- 변경:`과 `- 유지:` 표식을 이 순서로 각각 한 번 쓰고 두 값 모두 비우지 않는다.
나머지 필수 항목도 값을 비우지 않는다. 같은 제목의 반복, 순서 변경, 다른 깊이의 제목, 알 수 없는
하위 제목, 한쪽 영향 표식 누락은 구조화 형식이 아니다. 앱이나 작성 역할이 비슷한 제목을 추측하거나
빠진 값을 만들지 않는다.

기획서의 `결정 요청`은 승인 또는 수정 요청으로 판단할 범위를 말한다. 개발 작업의 `결정 요청`은
사용자가 QA에서 확인할 결과를 말한다. `비용과 위험`은 실제 값이 있을 때만 쓰며 값이 없으면 제목도
쓰지 않는다.

## 기존 요약 계약과의 관계

현재 공통 규칙의 빈 줄 제외 10줄 상한은 위 구조가 요구하는 최소 하위 제목과 값의 수보다 작다.
구조화된 기획서와 개발 작업에는 이 물리적 줄 수 상한을 적용하지 않고, 각 일반 항목을 짧은 한 문단,
영향 표식을 각각 한 항목으로 제한해 간결성을 보장한다. 평문 요약과 개발 보고서에는 기존 10줄 상한을
그대로 둔다. 백틱 토큰, 파일 경로, 코드 식별자 등 현재 요약 절 금지 조건은 구조화된 값에도 그대로
적용한다.

기존 평문 요약, 요약이 없는 문서와 불완전한 구조는 유효성을 잃지 않는다. 기존 문서를 소급 변환하지
않고, 읽기·표시·자격 판정은 지금과 같다. 새 구조는 본문 계약이며 프론트매터 필드나 스키마 버전을
추가하지 않는다.

## 역할별 의무

- planner 계약은 새 기획서와 수정 요청에 따라 다시 쓰는 기획서가 위 구조를 사용하고, 승인하지 않을
  때 유지되는 상태를 `영향 범위`의 유지 값과 결정 요청에 분명히 적도록 한다.
- architect 계약은 새 개발 작업이 위 구조를 사용하고, 코드 모양이 아니라 완료 뒤 사용자가 얻는
  결과와 QA 판단을 적도록 한다.
- developer 계약은 구조화된 작업을 `in_progress`나 `qa_waiting`으로 전이할 때 필수 항목과 순서를
  보존하면서 사실을 갱신하게 한다. 구조가 없는 기존 작업을 소급 변환하지 않는다.
- developer가 쓰는 구현 보고서는 기존 평문 요약을 유지하며 구조화 표시 대상이 아님을 명시한다.

## 완료 조건

1. 앱 내장 공통 규칙이 위 제목, 순서, 필수·선택 항목, 두 영향 표식과 구조 불인정 조건을 한 번씩
   정의한다. 기획서와 개발 작업만 새 구조의 작성 대상이고 보고서는 기존 계약을 유지한다. (R1·R2)
2. 현재 10줄 상한과 새 구조의 충돌을 해소한다. 구조화된 문서는 항목별 간결성 규칙을 따르고, 기존
   평문 요약과 보고서는 10줄 상한을 유지한다. (R1·R3)
3. planner·architect·developer 계약이 위 역할별 의무를 각각 적고 공통 정의를 참조한다. 정의를 세
   계약에 서로 다르게 복제하지 않는다. (R1·R2)
4. 기존 평문·무요약·불완전 문서가 유효하고 소급 수정하지 않는다는 호환성 규칙이 명시된다. 요약
   구조는 자격 판정과 문서 스키마에 영향을 주지 않는다. (R3)
5. 문서가 쓴 HTML을 허용하지 않고 별도 HTML 정본, 요약 캐시, 이미지, 차트 데이터, 네트워크 또는
   LLM 호출을 만들지 않는 경계가 계약과 설명 문서에서 읽힌다. (R3·R5)
6. `docs/file-contract.md`의 기획서·개발 작업·개발 보고서 예시와 역할 설명이 앱 내장 계약과 같은
   구조 및 호환성 규칙을 말한다.
7. 공통 규칙과 본문이 바뀐 세 역할 계약의 버전 상수·frontmatter 버전과 관련 단언이 함께 올라간다.
   착수 시점의 값은 공통 규칙 16, planner 10, architect 10, developer 11이므로 각각 17, 11, 11, 12가
   된다. 상수와 규칙 본문의 frontmatter 값은 항상 같은 수를 말한다. 스키마 버전은 바뀌지 않는다.
8. 앱 내장 규칙 동기화의 기존 설치·갱신·충돌 보존 검사가 삭제되거나 완화되지 않는다.
9. `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다.
10. 변경분은 범위 파일 네 개뿐이고 `.workflow/rules/`, 기존 기획서·작업·보고서, 결정 기록을 수정하지
    않는다.
11. 범위에 새로 들어온 `fs_project_repository.rs`와 `managed_project_assets.rs`에서는 이전 규칙 버전을
    직접 비교하는 문자열만 새 버전으로 바꾼다. 검사 함수의 판정 대상, 시나리오, 단언 개수는 그대로
    두고 어떤 검사도 삭제하거나 무력화하지 않는다.

## 검증 절차

1. `cargo test --manifest-path src-tauri/Cargo.toml`을 실행한다.
2. 앱 내장 공통 규칙과 세 역할 계약을 추출해 제목 순서, 필수·선택 항목, 영향 표식, 호환성 문언과
   버전 값을 테스트 단언과 대조한다.
3. `docs/file-contract.md`의 예시와 역할별 설명을 같은 항목표로 대조한다.
4. `git diff --stat`과 `git diff -- . ':!.workflow'`로 범위 파일 밖의 제품 변경이 없고 기존 자동
   검사가 삭제되지 않았음을 확인한다.
5. 새로 포함한 두 파일의 `git diff`를 읽어 바뀐 줄이 이전 규칙 버전 문자열뿐인지 확인한다. 검사
   이름, 시나리오 구성과 단언 줄 수는 변경 전과 같아야 한다.

## 범위 파일

  단언 검사.
- `docs/file-contract.md` — 사용자·개발자용 문서 계약과 예시.

- `src-tauri/src/infrastructure/managed_project_assets.rs` — 관리 자산 동기화 검사가 같은 방식으로
  이전 버전 문자열과 버전 상수를 비교한다.

## 선행

- `TASK-S051-01`은 완료됐다. 그 작업이 같은 앱 내장 규칙 파일에 남긴 예약 인계와 결과 접두어 문언을
  지우지 않고 보존한다.
- `TASK-148`이 공통 규칙을 버전 16으로 올리면서 막힌 작업 재개 계약과 일곱 번째 이력 값을 추가했고,
  `docs/file-contract.md`와 `fs_project_repository.rs`도 함께 바꿨다. 이 작업은 그 결과 위에서
  버전을 17로 올리므로 TASK-148 뒤에 선다. 재개 계약 문언과 이력 값 설명을 그대로 두고 구조화 요약
  계약만 더한다.
- 세 범위 파일이 TASK-148과 겹치므로 두 작업을 같은 시각에 진행하지 않는다.
