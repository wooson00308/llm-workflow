# 승인된 기획서에 후속 수정 요청을 기록하는 길이 쓰기 경로에 난다

## 결정권자 요약

이제 이미 승인한 기획서에도 수정 요청을 보낼 수 있다. 앱 안쪽의 기록 경로가 그것을 받아들이게
됐고, 누르는 자리는 다음 작업이 만든다.

열린 칸은 하나다. 승인된 기획서에 후속 수정 요청만 허용하고 재승인과 폐기는 그대로 막는다.
막힌 열한 조합을 전부 확인했고, 거절될 때 결정 기록이 늘지 않는 것까지 봤다.

승인 뒤에 수정 요청이 붙은 기획서에서 세 역할의 대기 물량 판정이 무엇을 답하는지도 처음으로
실물에서 확인했다. 그 수정 요청은 기획자 몫이 되고, 파생 작업이 없던 승인은 아키텍트 몫에서
빠지며, 이미 파생된 작업은 개발자 몫으로 그대로 남는다. 판정 규칙은 한 줄도 고치지 않았다.

볼 화면이 없는 작업이라 확인은 아래 숫자를 믿는 일이 된다.

## 확인 동선

**볼 화면이 없는 작업이다.** 바뀐 것은 앱 안쪽의 기록 경로 하나이고, 그 경로를 사용자가 누르는
자리는 TASK-128이 만든다. 지금 앱을 띄워도 승인된 기획서 화면은 어제와 같다 — 결정 도구는 여전히
사용자 선택 대기 상태에서만 그려진다. 그 순서는 기획서가 정한 것이다. 화면이 먼저 열리면 버튼을
누르고 오류를 보게 되기 때문에 쓰기 경로가 먼저 선다.

그래서 이 작업은 자동 검사로 닫았고, 확인 도장은 **아래 숫자를 믿는다**는 뜻이 된다.

### 1. 검사 두 개를 다시 돌린다

```sh
cargo test --manifest-path src-tauri/Cargo.toml
npm run check
```

**정상이면 앞엣것이 504 passed / 0 failed / 0 ignored, 뒤엣것이 22 files / 642 tests passed다.**
이 세션이 넘길 때의 값이고, 다른 세션이 그 사이에 검사를 더했으면 숫자는 늘 수 있다. 늘어도
`failed`가 0이면 정상이다.

### 2. 이 작업이 새로 만든 다섯 건만 돌려 본다

```sh
cargo test --manifest-path src-tauri/Cargo.toml -- \
  fs_project_repository::tests::a_follow_up \
  fs_project_repository::tests::records_a_follow_up \
  fs_project_repository::tests::refuses_every_spec
```

**정상이면 `5 passed; 0 failed`다.** 각각이 확인하는 것은 이렇다.

| 테스트 | 확인하는 것 |
| --- | --- |
| `records_a_follow_up_revision_request_on_an_approved_spec` | 승인된 기획서에 수정 요청이 기록되고 결정 문서가 하나 는다 |
| `a_follow_up_revision_request_writes_the_same_decision_frontmatter` | 그 결정 문서의 프론트매터가 지금과 같은 여섯 값뿐이다 |
| `refuses_every_spec_decision_the_table_blocks` | 표에서 막힌 열한 조합이 전부 거절되고 결정 문서가 늘지 않는다 |
| `a_follow_up_revision_request_moves_the_approval_out_of_architect_work` | 그 수정 요청이 기획자 몫이 되고 승인이 아키텍트 몫에서 빠진다 |
| `a_follow_up_revision_request_leaves_the_derived_task_to_the_developer` | 이미 파생된 작업이 그대로 개발자 몫으로 남는다 |

뒤의 둘은 앱의 판정과 조건 스크립트를 세 역할 모두에서 대조한다. 갈라지면 그 자리에서 실패한다.

### 3. 판정 본문을 건드리지 않았다는 것을 눈으로 본다

```sh
git status --short src-tauri/src/infrastructure/role_eligibility.rs \
  src-tauri/src/infrastructure/heartbeat_condition.rs .workflow/rules/ docs/file-contract.md
```

**정상이면 이 세션 때문에 새로 뜨는 줄이 없다.** 작업 트리에는 이 세션 전부터 다른 작업들의
미커밋 변경이 섞여 있어 위 명령이 줄을 낼 수는 있다. 이 세션이 만졌는지 아닌지는 아래로 가른다.

```sh
find . -newermt "2026-08-05 19:50" -type f \
  -not -path "./target/*" -not -path "./src-tauri/target/*" \
  -not -path "./node_modules/*" -not -path "./dist/*" -not -path "./.git/*"
```

**정상이면 목록에 이 작업의 범위 파일과 이 작업 문서, 그 lease, 보고서, 개발 로그, 빌드 산출물
하나만 있다.** 판정 본문 둘도 규칙 자산도 파일 계약 문서도 그 목록에 없다.

### 4. 알아 둘 것

- 이 변경으로 지금 당장 화면에서 달라지는 것은 없다. 사용자가 실제로 누르게 되는 것은 TASK-128
  뒤다.
- 잘못 보낸 후속 수정 요청을 취소하는 길은 여전히 없다. 수정 요청 상태에 결정을 또 얹는 칸은
  이번에도 막혀 있고, 그것이 기획서가 승인한 선택이다.

---

SPEC-042의 R1(기록)·R2(허용 조합 표)·R6(거절 문구)·R8(판정 불변)이다. 기획서 완료 조건
1·2·3·4·11·15·16이 여기서 닫힌다.

화면 쪽 R1과 R3·R4·R7은 TASK-128의 몫이고, R5는 TASK-129의 몫이다. 이 작업이 먼저 서는 이유는
기획서 완료 조건 5다 — 화면이 여는 조작과 쓰기 경로가 허용하는 조합이 같아야 하고, 그 대조의
기준이 되는 조합 테스트가 이 작업의 산출물이다. 순서가 뒤집히면 사용자는 버튼을 누르고 오류를
본다(확인 사실 2).

## 지금 이 자리가 어떻게 되어 있는가

`record_spec_decision`이 결정을 쓰기 전에 문을 하나 지난다. 문서를 읽고 상태를 정규화한 뒤
`apply_latest_decision`으로 최신 결정을 덮어씌우고, 그 결과가 `user_review`가 아니면
`ProjectError::SpecNotAwaitingDecision`을 낸다. 그 열거값의 문면이
`fs_project_repository.rs:61`의 "사용자 선택 대기 상태인 기획서만 승인·수정 요청·폐기할 수
있습니다."다.

즉 지금 판정은 상태 하나만 보고 보내려는 결정 종류를 보지 않는다. 이 작업이 바꾸는 것이 정확히
그 자리다 — 판정이 (상태, 보내려는 결정) 두 값을 받는다.

`validate_decision`은 손대지 않는다. 코멘트 필수와 길이 상한은 지금 그대로이고(R1), 수정 요청은
이미 코멘트가 필수인 쪽이다.

## 바꾸는 것

### 1. 허용 조합이 표대로 판정된다 (R1·R2)

행은 `apply_latest_decision`이 정한 지금 상태, 열은 보내려는 결정이다.

| 지금 상태 | 승인 | 수정 요청 | 폐기 |
| --- | --- | --- | --- |
| `draft` | 막는다 | 막는다 | 막는다 |
| `user_review` | 허용 | 허용 | 허용 |
| `approved` | 막는다 | **허용(이번 변경)** | 막는다 |
| `revision_requested` | 막는다 | 막는다 | 막는다 |
| `rejected` | 막는다 | 막는다 | 막는다 |

- 바뀌는 칸은 `approved` 행의 수정 요청 하나다. 나머지 열넷은 지금 동작 그대로다.
- 표에 없는 상태값은 막는 쪽이다. 지금도 그 값은 `user_review`가 아니므로 막힌다.
- 판정이 한 자리에 있어야 한다. 상태와 결정 종류를 함께 읽는 자리가 둘로 갈리면 화면과 대조할
  기준이 둘이 되고, 기획서 완료 조건 5의 대조가 무엇과 무엇을 맞추는지 말할 수 없게 된다.

허용된 뒤 쓰이는 결정 문서의 모양은 지금과 같다. 스키마·`id`·`spec_id`·`outcome`·
`created_by: user`·`created_at` 여섯이고 새 필드도 새 값도 만들지 않는다(R1·R8). 문서를 쓰는
코드는 이미 그렇게 되어 있으므로 이 작업에서 그 자리를 고칠 일이 없다 — 고쳐지지 않았다는 것을
완료 조건 2가 확인한다.

### 2. 거절 문구가 새 규칙과 어긋나지 않는다 (R6)

지금 문면은 "사용자 선택 대기 상태인 기획서만 승인·수정 요청·폐기할 수 있습니다."이고, 이 작업
뒤에는 사실이 아니다. 승인된 기획서도 수정 요청은 받는다.

- 새 문면은 무엇이 허용되고 무엇이 막혔는지를 말한다.
- **열거값 이름은 바꾸지 않는다.** `ProjectError::SpecNotAwaitingDecision`을 그대로 두어야
  기존 테스트가 수정 없이 통과한다(완료 조건 4). 바뀌는 것은 `#[error(...)]` 안의 문자열이다.
- 화면이 애초에 막힌 조합의 버튼을 그리지 않으므로 이 문장이 사용자에게 닿는 것은 화면과 쓰기
  경로가 어긋났을 때뿐이다. 그래도 사실과 어긋난 문장을 남기지 않는다.

### 3. 새 상태에서 세 판정이 무엇을 답하는지 실물로 확인한다 (R8)

승인 뒤에 수정 요청이 붙은 기획서는 지금 이 프로젝트에 0건이라(확인 사실 11) 그 상태에서 판정이
돌아본 적이 없다. 이 작업이 그 상태를 픽스처로 만들고 앱의 판정과 조건 스크립트가 같은 답을
내는지 대조한다.

- 대조 어법은 이미 이 파일 안에 있다. `a_closed_idea_is_not_planner_work_in_either_judgement`이
  조건 스크립트를 설치하고 세 역할의 종료 코드를 앱의 `pending_work`와 맞춘다. 그 어법을 새
  픽스처에 그대로 쓴다.
- 그 자리에서 대조하는 이유도 그 테스트의 주석에 이미 적혀 있다 — `role_eligibility.rs`의 대조
  헬퍼는 자기 테스트 모듈 안에 있어 다른 모듈에서 부를 수 없다.
- 확인할 답 셋은 기획서가 미리 정해 두었다(확인 사실 6·7·8). 그 수정 요청이 기획자 대기 물량이
  되고, 밀려난 승인이 아키텍트 대기 물량에서 빠지며, 그 승인에서 파생된 작업은 그대로 개발자
  후보로 남는다.
- **판정 본문은 한 줄도 고치지 않는다.** `role_eligibility.rs`와 조건 스크립트 두 본문은 이
  작업에서 읽기만 한다. 대조가 어긋나면 값을 맞추지 말고 그 사실을 보고서에 적는다.

## 손대지 않는 것

- **판정 규칙.** 최신 결정 하나가 기획서 상태를 정하는 규칙(확인 사실 3), 세 역할 자격 판정,
  조건 스크립트 두 본문, `CONDITION_SCRIPT_VERSION` 전부 그대로다(R8).
- **결정 문서의 스키마와 프론트매터.** 앱 소유 상태이고 마이그레이션은 앱의 몫이다.
- **파생 작업.** 후속 수정 요청을 받아도 앱이 그 기획서의 개발 작업을 되돌리거나 닫지 않는다.
  확인 사실 8이 근거이고, 이것이 부작용이 아니라 R3이 올린 약속이다. 그 약속이 지켜지는지를
  완료 조건에서 확인한다.
- **개발 작업 QA 기록.** `record_task_qa`는 이 작업의 범위 밖이다.
- **코멘트 검증.** 필수 여부와 길이 상한이 지금 그대로다.
- **역할 계약 문언과 파일 계약 문서.** 확인 사실 5·6이 이미 성립해 고칠 것이 없고, 그 파일들은
  TASK-118이 이미 닫았다(기획서 제외 범위·완료 조건 19).

## 완료 조건

1. 최신 결정이 `approved`인 기획서에 `revision_requested` 결정이 기록되고 결정 문서가 하나
   늘어난다. 승인 결정을 심은 픽스처의 테스트가 그것을 확인한다. (기획서 완료 조건 1, R1)
2. 기록된 결정 문서의 프론트매터가 지금과 같은 여섯 값만 갖고 새 필드가 없다. 같은 테스트가
   문서를 읽어 단언한다. (기획서 완료 조건 2, R1·R8)
3. 표에서 막힌 칸이 전부 거절된다. 최소한 승인된 기획서에 대한 승인과 폐기, 수정 요청 상태의
   기획서에 대한 세 결정, `draft`에 대한 세 결정을 조합별로 확인한다. 거절될 때 결정 문서가
   늘지 않는 것까지 확인한다. (기획서 완료 조건 3, R2)
4. `refuses_a_second_decision_on_a_spec_the_app_already_decided`가 수정 없이 통과한다. 그
   테스트가 확인하는 조합은 승인→승인이고 표가 그것을 계속 막는다. (기획서 완료 조건 4, R2·R9)
5. 거절 문구가 무엇이 허용되고 무엇이 막혔는지를 말하고, 승인된 기획서도 수정 요청은 받는다는
   사실과 어긋나지 않는다. 열거값 이름은 그대로다. (기획서 완료 조건 11, R6)
6. 세 역할 자격 판정과 조건 스크립트 두 본문이 이 변경분에서 달라지지 않는다. 기존 대조
   테스트가 수정 없이 통과한다. (기획서 완료 조건 15, R8)
7. 승인 뒤 수정 요청을 받은 기획서 픽스처에서 (가) 그 수정 요청이 기획자 대기 물량이 되고
   (나) 그 승인이 아키텍트 대기 물량에서 빠지며 (다) 그 승인에서 파생된 작업이 그대로 개발자
   후보로 남는다. 앱의 판정과 조건 스크립트가 세 역할 모두에서 같은 답을 낸다. (기획서 완료
   조건 16, R8)
8. `user_review` 기획서의 승인·수정 요청·폐기가 지금과 같다. 기존 테스트가 수정 없이 통과한다.
   (기획서 완료 조건 17, R9)
9. 기존 자동 테스트가 삭제되거나 비활성화되지 않는다. (기획서 완료 조건 18, R9)
10. 역할 계약 문언과 파일 계약 문서가 이 변경분에서 달라지지 않는다. (기획서 완료 조건 19)
11. `cargo test --manifest-path src-tauri/Cargo.toml`과 `npm run check`가 통과한다. (기획서
    완료 조건 21)

## 검증 절차

1. 표의 열다섯 칸 중 확인하기로 한 조합마다 픽스처를 만들고 결과를 단언한다. 허용된 칸은
   결정 문서가 하나 느는 것과 그 프론트매터를, 막힌 칸은 열거값과 결정 문서가 늘지 않는 것을
   본다.
