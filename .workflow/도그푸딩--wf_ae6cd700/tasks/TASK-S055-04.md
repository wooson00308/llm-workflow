# 작업 상세에서 정의 수정을 요청하고 처리 결과를 확인한다

## 결정권자 요약

### 제안

작업 상세에서 정의 수정을 요청하는 조작을 제공하고, 요청과 처리 결과를 같은 자리에서 읽게 한다.

### 현재

세 차례 범위 누락을 모두 대조한 정의로 구현과 자동 검증을 마쳤다. 요청 저장 조작과 처리 결과와
활동 기록이 실제 전달 경로를 따라 이어지며 사용자 품질 확인을 기다린다.

### 변경 후

막힌 작업과 아직 선점되지 않은 개발 준비 작업에 정의 수정 요청 조작이 생긴다. 요청 전에 현재 범위와
선행과 갱신 시각과 기존 요청을 함께 보여 주고, 이유를 적어 두 번 확인해야 요청이 남는다. 요청이 처리
되면 처리 결과와 사전 검사 근거가 같은 화면에서 읽힌다. 기존 목록 조회는 요청 기록과 작업에 연결된 처리 사실을
각각 활동 사건으로 함께 돌려주며, 수정만으로 작업 상태를 자동 전환하지 않는다. 현재 범위 선언은 정상 목록과 선언 없음과
형식 오류를 구분해 화면까지 전달한다.

### 사용자 결과

잘못 분해된 작업을 발견한 자리에서 바로 이유와 함께 되돌려 보낼 수 있고, 무엇이 고쳐졌는지 확인한 뒤에
재개 여부를 판단할 수 있다.

### 영향 범위

- 변경: 작업 상세의 정의 수정 요청과 처리 결과, 활동 화면의 요청과 수정 사건
- 유지: 사용자 품질 확인 도장과 일괄 확인, 막힌 사유 표시와 재개 조작, 상태 기계와 결정 기록의 뜻

### 비용과 위험

요청 조작이 재개 조작 옆에 함께 놓이므로 두 조작을 혼동할 여지가 있다. 두 조작의 이름과 결과를 화면에서
분명히 갈라야 한다.

### 결정 요청

테스트 프로젝트의 작업 상세에서 요청 전 정보, 두 단계 확인, 실패 뒤 재조회, 처리 결과와 활동 기록을
차례로 확인해야 한다.

## 막힌 사유

- 막힌 지점: 작업 문서는 최상위 조립 파일이 작업 공간 훅을 통째로 넘긴다고 적었지만,
  현재 `src/App.tsx`는 훅의 작업별 조작을 `WorkspaceShell`에 개별 속성으로 열거한다. 새 정의
  수정 요청 조작을 화면에 연결하려면 이 파일을 수정해야 하지만 선언 범위에 없다.
- 필요한 해결: 아키텍트가 `src/App.tsx`를 `scope_files`에 추가하고, 작업 공간 훅이 내보낸 정의
  수정 요청 조작을 최상위 조립에서 `WorkspaceShell`로 넘기는 필요경로를 범위 사전 검사와 완료
  조건에 반영해야 한다.
- 재개 조건: `src/App.tsx`가 선언 범위에 들어오고, 두 번째 확인이 작업 공간 훅의
  요청 함수를 거쳐 저장 명령을 한 번 호출하는 연결 조건이 작업 문서에 명시되면 다시 시작할 수 있다.
- 관련 대상: 없음

## 목적

SPEC-055의 R2 화면 부분과 R9와 R12를 구현한다. 사용자가 정의 수정을 요청하고 처리 결과를 확인하는

## 변경 범위

### 요청 조작

- 현재 상태가 막힘이거나, 개발 준비이면서 활성 선점이 없을 때만 요청 영역을 보여 준다.
- 작업 상세 응답은 현재 범위 선언을 정상 목록, 선언 없음, 형식 오류로 구분해 싣는다. 정상 목록이면 빈 목록을
  포함해 문서의 경로 문자열과 순서를 그대로 보여 준다. 선언이 없으면 선언이 없다고, 형식이 틀리면 목록으로 읽지 못했다고
  표시하며 빈 목록으로 바꾸어 표시하지 않는다.
- 요청 전에 작업의 현재 상태와 선언 범위와 선행 관계와 갱신 시각과 막힌 사유와 기존 요청 목록을 함께
  보여 준다.
- 이유 입력은 필수다. 빈 값은 호출 전에 막고 길이 제한과 현재 글자 수를 보여 준다.
- 첫 확인은 대상과 갱신 시각과 입력한 이유를 확인 상태로 고정하고, 두 번째 확인만 명령을 한 번 호출한다.
  진행 중에는 중복 클릭과 입력 변경을 막는다.
- 오래된 문서와 허용되지 않는 상태와 활성 선점과 마이그레이션 잠금과 중복 요청은 성공으로 표시하지
  않는다. 입력을 유지한 채 사유와 최신 문서를 다시 읽는 동작을 제공한다.

### 처리 결과 표시

- 작업에 연결된 요청은 처리 완료로, 연결되지 않은 요청은 미처리로 구분해 보여 준다. 화면이 처리 여부를
  다른 근거로 추측하지 않는다.
- 처리된 요청이 있으면 그 요청의 이유와 처리 시점을 함께 보여 준다. 수정 내용 자체는 작업 본문과 보고서
  에 있으므로 화면이 다시 요약하지 않는다.
- 작업 본문에 범위 사전 검사 절이 있으면 그 절을 읽을 수 있게 한다. 절이 없으면 없는 대로 두고 문장을
  지어내지 않는다.
- 수정이 처리돼도 상태는 그대로다. 막힌 작업은 막힌 채로 남고 재개 조작은 지금과 같은 자리에 있다.
  개발 준비 작업은 개발 준비로 남는다.

### 활동 화면

- 정의 수정 요청과 아키텍트 수정 처리를 각각 고유한 이름으로 보여 준다. 기획 수정 요청과 품질 확인 반려
  와 사용자 재개의 기존 이름은 바꾸지 않는다.
- 같은 작업이 같은 분류로 다시 막히면 이전 요청과 수정 기록을 함께 확인할 수 있게 한다.
- 목록 조회가 정의 수정 요청 기록과 작업에 연결된 처리 식별자를 사건으로 합친 뒤 기존 작업 사건 목록에 싣는다.
  새 요약 호출이나 원격 호출을 만들지 않는다.

## 손대지 않는 것

- 사용자 품질 확인 도장과 레인 일괄 확인 경로
- 막힌 사유 절의 표시 규칙과 재개 조작의 동작
- 상태 기계와 이력 값의 뜻
- 요청 기록의 저장 판정과 형식
- 아키텍트 자격 판정
- 전역 스타일 파일

## 완료 조건

1. 막힘 상태와, 선점이 없는 개발 준비 상태의 작업에서만 요청 영역이 보인다. 진행 중과 품질 확인 대기와
   완료 상태에서는 보이지 않는다.
2. 작업 상세 응답이 현재 범위 선언을 정상 목록, 선언 없음, 형식 오류로 서로 다르게 싣는다. 정상 목록은 빈
   목록을 포함해 문서에 적힌 경로 문자열과 순서를 그대로 보여 준다. 요청 영역은 이 값과 현재 상태와 선행 관계와 갱신 시각과
   기존 요청 목록을 함께 보여 주며, 선언 없음과 형식 오류를 빈 목록으로 표시하지 않는다.
3. 빈 이유와 길이 초과는 호출 전에 거절되고 첫 확인만으로는 명령 호출이 일어나지 않는다.
4. 두 번째 확인이 같은 대상과 갱신 시각과 이유로 작업 공간 callback을 거쳐 요청 저장 명령을 한 번만
   호출한다. 연타와 응답 지연에서도 호출은 한 번이다.
5. 오래된 문서와 활성 선점과 마이그레이션 잠금과 허용되지 않는 상태와 중복 요청 응답에서 성공 표시가
   없고 입력이 유지되며 최신 문서를 다시 읽을 수 있다.
6. 작업이 연결한 요청은 처리 완료로, 연결되지 않은 요청은 미처리로 표시된다. 화면이 다른 근거로 처리
   여부를 만들지 않는다.
7. 작업 본문에 범위 사전 검사 절이 있으면 읽을 수 있고, 없으면 대체 문장을 만들지 않는다.
8. 수정이 처리된 뒤에도 막힌 작업은 막힘으로, 개발 준비 작업은 개발 준비로 남는다. 화면이 상태를 자동
   으로 바꾸지 않는다.
9. 목록 조회가 앱 소유 정의 수정 요청을 `task_revision_requested` 사건으로 싣고, 작업이 연결한 요청을
   작업 갱신 시각의 `task_revision_applied` 사건으로 싣는다. 두 사건이 활동 화면에서 각각 `정의 수정 요청`,
   `아키텍트 수정`이라는 이름으로 한 번씩 보이고, 기획 수정 요청과 품질 확인 반려와 사용자 재개의 기존
   이름이 바뀌지 않는다.
10. 같은 작업이 같은 분류로 다시 막힌 픽스처에서 이전 요청과 수정 기록을 함께 확인할 수 있다.
11. 좁은 화면과 넓은 화면에서 요청 영역의 읽기 순서와 초점 순서가 같고 긴 이유와 식별자가 잘리지 않는다.
12. 키보드만으로 이유 입력과 첫 확인과 최종 확인과 오류 뒤 재조회에 순서대로 도달한다.
13. 기존 품질 확인 대기 표시와 일괄 확인과 재개 조작과 막힌 사유 표시 검사가 변경 전과 같이 통과한다.
14. 요청 기록이 없는 기존 프로젝트에서 작업 상세와 활동 화면이 변경 전과 같이 보인다.

## 검증 절차

1. `cargo test --manifest-path src-tauri/Cargo.toml scope_declaration`로 정상 비어 있지 않은 목록, 정상 빈 목록, 선언 없음,
   형식 오류 픽스처의 작업 상세 응답을 대조한다. 응답이 세 상태를 보존하고 정상 목록의 경로 문자열과 순서를 바꾸지 않는지
   확인한다. 이어 `npx vitest run src/features/projects/components/BlockedTaskPanel.test.tsx src/features/projects/components/DevelopmentBoard.test.tsx`를
   실행해 세 선언 상태의 화면 표시가 다르고 정상 빈 목록이 선언 없음으로 표시되지 않는지 확인한다.
2. 다섯 가지 상태와 선점 있음 픽스처로 요청 영역의 노출 여부를 표로 검사한다.
3. 빈 값과 길이 초과와 첫 확인에서 호출이 없는지, 연타와 응답 지연에서 한 번인지 확인한다.
4. 오래된 갱신 시각과 활성 선점과 마이그레이션 잠금과 중복 요청 응답을 주입해 입력 보존과 재조회 동작을
   확인한다.
5. 연결 필드가 있는 작업과 없는 작업으로 처리 완료와 미처리 표시를 대조한다.
6. 범위 사전 검사 절이 있는 작업과 없는 작업으로 표시와 폴백을 확인한다.
7. 수정 처리 응답 뒤 상태가 그대로인지, 재개 조작이 여전히 사용자 조작으로만 동작하는지 확인한다.
8. `cargo test --manifest-path src-tauri/Cargo.toml task_revision_events`로 요청 사건과 연결된 수정 사건이 목록 조회에
   한 번씩 실리는지 검사한다. `npx vitest run src/features/projects/components/ActivityView.test.tsx`로 새 두 이름과 기존 이름을 대조한다.
9. 좁은 화면과 넓은 화면과 키보드 전용 이동을 확인한다.
10. 저장소 루트에서 `npm run check`를 실행한다.

## 범위와 선행

TASK-149가 같은 사유 패널에 재개 조작을 먼저 만들고 이 작업이 그 옆에 요청 조작을 더하므로 그 작업이
선행한다. 요청을 저장하는 명령은 이 승인의 두 번째 작업이 제공하므로 그 작업도 선행한다.

Rust 도메인과 목록 조회 파일은 이 승인의 앞선 세 작업과 겹치지만 세 작업 모두 구현을 끝내고 품질 확인을
기다린다. 요청 저장 계약을 실제로 사용하는 TASK-S055-02만 기존 선행으로 보존한다. 규칙 문언과 자격
판정 결과는 이 화면 작업의 입력 계약이 아니므로 TASK-S055-01과 TASK-S055-03을 새 선행으로 더하지 않는다.

화면의 작업 공간 훅, 게이트웨이, 도메인 타입과 최상위 조립은 TASK-S051-09와 TASK-S051-10의 선언과
겹치지만 두 작업도 구현을 끝내고 품질 확인을 기다린다. 어느 구현 결과가 다른 구현 결과의 입력은 아니므로
선행을 새로 만들지 않는다. 이후 재작업 선점이 생기면 `scope_files` 교집합 판정이 동시 수정을 막는다.

## 확인 동선

일회용 테스트 프로젝트를 앱으로 열고 왼쪽 메뉴에서 `개발`을 선택한다. 활성 선점이 없는 `막힘` 작업이나
`준비` 작업의 카드를 눌러 상세 화면을 연다.

1. 오른쪽 패널의 `작업 정의 수정 요청`에서 대상 상태, 갱신 시각, 선행 관계, 범위 선언과 기존 요청을
   확인한다. 정상 빈 범위는 `변경 파일 없음 (빈 목록으로 선언됨)`으로 보이고, 선언 없음과 형식 오류는
   각각 다른 문장으로 보여야 한다.
2. `수정이 필요한 이유`를 입력하고 `정의 수정 요청 확인`을 한 번 누른다. 대상과 갱신 시각과 입력 이유가
   확인 상자에 고정되고 아직 저장 결과는 나타나지 않아야 한다.
3. `한 번 더 누르면 수정 요청`을 누른다. 성공하면 입력이 비워지고 기존 요청 목록에 미처리 요청이 나타난다.
   거절 상황에서는 입력이 남고 `최신 작업 다시 읽기`로 같은 상세를 다시 조회할 수 있어야 한다.
4. 왼쪽 메뉴의 `활동`을 열면 요청은 `정의 수정 요청`으로 보인다. 아키텍트가 그 요청을 작업에 연결해
   처리한 테스트 데이터에서는 `아키텍트 수정`이 별도 항목으로 보여야 한다. 기존 `반려`와 `사용자 재개`
   이름은 그대로여야 한다.
5. 실제 창 크기를 좁혔다 넓혀도 정보의 읽기 순서가 바뀌지 않고, 키보드 Tab 이동이 이유 입력, 첫 확인,
   최종 확인, 오류 뒤 재조회 순서를 따라야 한다. 활동 사건과 세 범위 상태의 데이터 조립은 자동 검사 결과를
   품질 확인 근거로 함께 사용한다.
