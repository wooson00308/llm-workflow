# 겹침 선언 필드를 만들고 두 자격 판정이 그것을 보게 한다

SPEC-032의 본체다. 개발 작업 문서에 기계가 읽는 겹침 선언을 도입하고, 조건 스크립트 두 본문과 앱의
`has_developer_work`가 그 선언으로 겹치는 작업을 자격에서 뺀다. R1·R2·R3·R6·R8·R9와 완료 조건
1~8·12·13·15를 닫는다. 계약 문언은 TASK-102, 화면은 TASK-103이다.

## 이 작업이 셋 중 가장 크고, 쪼개지지 않는 이유

R3이 "두 판정이 같은 답을 낸다"를 요구하고 확인 사실 8의 대조 테스트가 그것을 고정한다. 앱만 고치면
새 픽스처에서 스크립트와 갈리고, 스크립트만 고치면 반대로 갈린다. 파서도 마찬가지다 — 선언을 읽는
쪽이 sh·PowerShell·Rust 셋이라 셋이 같은 결론을 내야 한다. **한 커밋에서 함께 움직인다.** TASK-097이
같은 이유로 두 본문을 한 작업에 묶은 선례다.

## 승인된 확인 필요가 이 작업의 설계다

DECISION-0D79A7F0은 세 항목 모두 기획서 제안대로 승인했다. 뒤집지 않는다.

1. **선언은 범위 파일 목록이다.** 병행 금지 작업 id 목록 대안은 뒤집혔다. 근거는 R2 — 나중에 분해되는
   작업은 지목할 대상이 그 시점에 없다.
2. **선언이 없는 작업은 활성 lease가 하나라도 있으면 착수 대상에서 뺀다.** "모든 미완료 작업과
   겹친다"로 본다.
3. 동시 세션 수 옵트인은 이 기획서에 넣지 않는다. 이 작업에 설정 화면도 잡 파일 변경도 없다.

## 아키텍트가 고정하는 값

기획서가 "형태는 확인 필요 1번에서 정한다"까지만 적었고 이름과 표기는 정하지 않았다. **세 구현과
TASK-102의 계약 문언이 같은 이름을 써야 하므로 여기서 고정한다.** 임의로 바꾸지 않는다. 바꿔야 할
이유가 나오면 고쳐서 진행하지 말고 보고서에 적고 아키텍트 후속으로 넘긴다.

- 필드 이름은 **`scope_files`**로 한다. 아키텍트 계약이 이미 "the files and modules a task touches"를
  범위 절에 적으라고 요구하고 있어(확인 사실 2) 그 어휘를 그대로 쓴다.
- 표기는 `depends_on`과 같다. **열 0에서 시작하는 한 줄 흐름 시퀀스 하나**이고 값은
  `[a/b.rs, c/d.ts]` 꼴이다. 블록 표기를 허용하지 않는 이유는 R1 셋째 항목 그대로다 —
  `append_task_history`의 스캔(`fs_project_repository.rs:902`~)이 깨지고 sh가 읽을 수 없다.
- 경로는 **프로젝트 루트 기준 상대 경로**를 적힌 그대로 쓴다. 정규화·글롭·디렉터리 접두 일치·대소문자
  접기를 하지 않는다. 세 구현이 같은 결론을 내야 하고, 경로 정규화는 플랫폼마다 다르다.
- 토큰에 허용하는 문자는 **`A-Za-z0-9`·`_`·`-`·`.`·`/`** 다. `depends_on`의 집합에 `.`과 `/`를 더한
  것이다. 공백이 든 경로는 형식 오류다 — sh의 단어 분리가 그것을 나눠 버린다.
- 겹침 판정은 **두 목록의 문자열 완전 일치 교집합**이다.

## 작업 내용

### 판정 규칙 (R2·R6·R8)

`todo` 작업 `T`가 **겹침으로 막힌다**는 것은, 대상 id가 `T`가 아닌 미만료 lease `L`이 하나라도 있고
다음 중 하나가 성립하는 것이다.

1. `T`의 `scope_files`가 없거나 형식 오류다. (승인된 확인 필요 2번. `L`이 무엇을 잡았는지 보지
   않는다 — 기획서의 비용 문단이 "다른 문서를 잡은 lease가 살아 있는 동안"이라고 적어 작업이 아닌
   문서를 잡은 lease도 세는 쪽을 이미 계산에 넣었다.)
2. `L`의 대상 id가 작업 문서 `U`를 가리키고, `U`의 `scope_files`가 없거나 형식 오류다.
   ("겹친다"는 대칭 관계다. 1번의 같은 답을 반대편에서 읽은 것이고, R1 넷째 항목의 "판정 불가는
   안전한 쪽으로 기운다"와도 같다.)
3. `L`의 대상 id가 작업 문서 `U`를 가리키고, `T`와 `U`의 `scope_files`가 같은 경로를 하나라도
   함께 가리킨다.

그 밖에는 막지 않는다. 특히 **`L`의 대상이 작업 문서가 아니고 `T`에 선언이 있으면 비교할 상대가
없으므로 막지 않는다.**

- `T` 자신을 잡은 lease는 이 규칙이 다루지 않는다. 기존 조건(`lease_blocks "$tid"`)이 이미 뺀다.
  **그 조건을 이 규칙으로 대체하지 않는다.**
- **미만료 lease만 센다**(R8). 지금 `lease_blocks`·`Test-Leased`·`lease_ids`가 쓰는 만료 판정을
  그대로 쓴다. 새 만료 규칙을 만들지 않는다.
- **판정은 lease 파일을 읽기만 한다.** 만들거나 고치거나 지우지 않는다(완료 조건 8).
- `U`의 상태는 보지 않는다. `qa_waiting`인 작업에 lease가 남아 있어도 그 lease가 미만료면 센다 —
  만료가 유일한 해제 조건이라는 것이 R8이다.

### 선언 파서 (R1·완료 조건 1)

세 구현이 같은 결론을 낸다. 판정 순서는 `parse_dependency_declaration`(`:1265`)과 같다.

1. `^scope_files:`로 시작하는 줄이 없다 → **부재**.
2. 그런 줄이 둘 이상이다 → **형식 오류**. (YAML 중복 키이기도 하다.)
3. 값이 `[`로 시작해 `]`로 끝나지 않는다 → **형식 오류**. 블록 표기와 값 없는 키가 여기서 걸린다.
4. 안쪽이 비었거나 쉼표뿐이다 → **빈 목록**. 빈 목록은 "만지는 파일이 없다"이고 아무와도 겹치지
   않는다. 부재와 다르다.
5. 토큰에 허용 문자 밖의 문자가 있거나 빈 토큰이 있다 → **형식 오류**. 따옴표로 감싼 표기가 여기서
   걸린다.
6. 그 밖에는 **목록**이다.

**부재와 형식 오류는 판정에서 같은 답을 낸다**(위 규칙 1·2번). 그래도 파서는 둘을 구분한다 —
`DependencyDeclaration`이 그렇게 되어 있고, R7의 화면이 "선언을 안 썼다"와 "잘못 썼다"를 다르게 말할
여지를 남긴다.

### 조건 스크립트 두 본문 (R3·완료 조건 4)

- sh: `lease_blocks`(`:57`) 옆에 헬퍼를 더한다. 미만료 lease 파일 목록을 훑고, 각 대상 id로
  `task_file`(`:93`)을 찾아 그 문서의 `scope_files`를 읽는다. `deps_of`(`:69`)를 본떠 만들되 허용
  문자 집합이 다르다는 것만 다르다.
- PowerShell: `Get-Declaration`(`:333`)을 본뜬 함수 하나와 `Test-Leased`(`:320`) 옆의 목록 헬퍼
  하나. **비교는 전부 `-c` 접두 연산자다** — 본문 머리가 적은 대소문자 규칙이 이 필드에도 그대로
  적용된다. 경로는 대소문자를 구분한다.
- **`developer)`·`'developer'` 절만 고친다.** 기획자·아키텍트 절의 판정 규칙은 그대로다(R9 둘째
  항목).
- `CONDITION_SCRIPT_VERSION`과 두 본문의 버전 줄을 **착수 시점 값에서 정확히 +1**로 올린다.
  **고정값을 가정하지 않는다** — 분해 시점 상수는 7이고 설치본은 6이라 어긋나 있다. 착수 시점에 읽은
  값을 보고서에 적고 +1을 적용한다. 세 자리가 같은 값이어야 한다.
- **설치본 `.workflow/rules/wf-eligible.sh`를 손으로 고치지 않는다.** 앱이 설치 경로로 덮어쓰는
  산출물이다.

### 앱 판정 (R3)

- `role_eligibility.rs`는 **파일을 만지지 않는다**(모듈 머리 넷째 줄). 겹침 집합은
  `fs_project_repository.rs`가 계산해서 넘긴다. `unsatisfied_dependencies`가 이미 그 어법이다.
- `has_developer_work`에 조건 하나가 는다. 네 조건이 된다.
- **활성 lease가 하나도 없으면 판정이 지금과 같다**(R9 셋째 항목). 새 조건은 잡힌 lease가 있을 때만
  개입한다. 기존 검사가 그것을 확인한다.

### R7이 쓸 payload

TASK-103이 그릴 값을 여기서 만든다. 화면 코드는 이 작업에 없다.

```rust
/// 활성 lease 하나가 이 작업의 착수를 막는 근거(SPEC-032 R7).
pub struct TaskOverlapBlock {
    /// lease가 잡은 문서 id. 활동 뷰의 카드가 쓰는 값과 같다.
    pub lease_target_id: String,
    /// 두 선언이 함께 가리킨 경로. 선언에 적힌 문자열 그대로이고 오름차순·중복 없음이다.
    /// 선언 부재나 형식 오류로 막힌 경우 비어 있다.
    pub shared_files: Vec<String>,
}
```

- `TaskDocument`에 `overlap_blocks: Vec<TaskOverlapBlock>`을 더한다. **비어 있으면 막히지 않은
  것이다.** 별도의 불리언을 만들지 않는다.
- `read_task`가 미만료 lease를 읽어 채운다. `lease_ids`(`:672`)가 쓰는 읽기를 그대로 쓴다.
- 자기 자신을 잡은 lease는 담지 않는다. 그것은 "겹쳐서 막혔다"가 아니라 "내가 잡고 있다"이고, 화면이
  이미 다른 자리에서 말한다.
- 목록 payload(`WorkflowItemSummary`)는 **건드리지 않는다**. 카드를 눌렀을 때만 도는 경로에 두는 것이
  `dependencies`와 같은 판단이다(SPEC-013 R5).

### 검사

**Rust (`fs_project_repository.rs`의 `mod tests`)**

1. 파서: 정상 목록·부재·빈 목록·중복 키·블록 표기·따옴표 표기·공백 든 경로·허용 문자 밖 문자 각각의
   결과. (완료 조건 1)
2. 서로 다른 승인에서 나온 두 작업이 같은 경로를 선언하고 한쪽에 미만료 lease가 있으면 다른 쪽이
   겹침 집합에 든다. (완료 조건 2)
3. 겹치지 않는 두 작업은 한쪽에 미만료 lease가 있어도 다른 쪽이 집합에 들지 않는다. (완료 조건 3)
4. 선언이 없는 작업은 활성 lease가 있을 때 집합에 들고, 없을 때 들지 않는다. (완료 조건 6)
5. 만료된 lease는 아무것도 막지 않는다. (완료 조건 7)
6. 판정 전후로 lease 디렉터리의 파일 이름과 내용이 같다. `role_eligibility.rs:787`~`:799`의 기존
   검사와 같은 어법이다. (완료 조건 8)
7. 형식 오류 선언을 가진 작업이 활성 lease가 있을 때 집합에 들고, **그 작업을 잡은 lease가 다른
   작업까지 막는다**(판정 규칙 2번).
8. `read_task`가 `overlap_blocks`를 채우고 `shared_files`가 실제 교집합이다. 막히지 않았으면
   비어 있다.

**대조 (`role_eligibility.rs`의 `mod tests`)** — 검사 2·3·4·5의 상황마다 앱과 스크립트가 같은 답을
낸다. `assert_matches_condition_script`(`:167`)를 쓴다. **기존 단언은 하나도 줄지 않는다.**
(완료 조건 5)

**조건 스크립트 (`heartbeat_condition.rs`의 `SCENARIOS`)** — 같은 상황을 행으로 더한다. 사유 코드는
늘리지 않는다. `eligible`·`no-target`이 이미 어휘에 있다.

괄호 안은 SPEC-032의 완료 조건 번호다.

1. `scope_files`를 열 0의 한 줄로 읽고, 중복 키·형식 오류가 판정 불가로 읽힌다. 검증: 검사 1. (1)
2. 서로 다른 승인에서 나온 두 작업이 같은 파일을 선언하고 한쪽에 미만료 lease가 있을 때 다른 쪽이
   개발자 자격에서 빠진다. 검증: 그 픽스처에서 조건 스크립트가 1을, 앱 판정이 `false`를 낸다. (2)
3. 겹치지 않는 두 작업은 한쪽에 미만료 lease가 있어도 다른 쪽이 열린다. 검증: 뒤집은 짝. (3)
4. `CONDITION_SCRIPT_VERSION`과 sh·ps1 두 본문의 버전 줄이 같은 값이고 착수 시점 값 +1이다.
   **착수 시점 값을 보고서에 적는다.** (4)
5. 대조 테스트가 새 상황을 포함해 통과하고 기존 단언이 줄지 않았다. (5)
6. 선언이 없는 작업이 활성 lease가 있을 때 자격에서 빠지고, 없을 때 열린다. 두 판정의 답이 같다.
   검증: 검사 4와 같은 상황의 대조 시나리오. (6)
7. 만료된 lease는 겹치는 작업을 막지 않는다. 검증: 검사 5와 대조 시나리오. (7)
8. 판정이 lease 파일을 만들거나 고치거나 지우지 않는다. 검증: 검사 6. (8)
9. 활성 lease가 하나도 없을 때의 개발자 판정이 지금과 같고, `depends_on` 판정과 기획자·아키텍트
   판정이 달라지지 않는다. 검증: 기존 검사가 **수정 없이** 통과한다. 착수 시점 검사 개수를 세어
   보고서에 적는다. (12)
10. 기존 자동 테스트가 삭제되거나 비활성화되지 않았다(`#[ignore]` 신규 0건). (13)
11. PowerShell 본문이 ASCII만 쓴다. 검증: `the_powershell_implementation_is_ascii`가 수정 없이
    통과한다.
12. **실저장소에서 세 역할의 판정을 착수 전과 착지 후에 각각 적는다.** 이 저장소의 작업에는
    `scope_files`가 하나도 없으므로(소급 기입은 기획서 제외 범위) 활성 lease가 없는 동안에는 세 답이
    같아야 하고, **다르면 그것이 회귀다.** 검증: 두 시점의 종료 코드와 사유를 보고서에 적는다.
13. 변경분에 `project_instructions.rs`·`DevelopmentBoard.tsx`·`types.ts`가 없다. (14)
14. `cargo test --manifest-path src-tauri/Cargo.toml`과 `npm run check`가 통과한다. (15)

## 검증 문구 규칙

이 저장소는 여러 세션의 미커밋 변경이 한 작업 트리에 겹쳐 있다. **"`git diff`가 비어 있다"를 완료
조건으로 쓰면 성립하지 않는다.** 무변경은 파일·심볼 단위로 확인한다 — 어느 상수·본문·단언이 착수
시점과 같은 값인지 직접 읽어 보고서에 남긴다.

## 범위 밖

- **계약 문언과 `rules_version` 인상.** TASK-102가 한다. 이 작업에 `project_instructions.rs`
  변경분은 없다.
- **화면.** TASK-103이 한다. `types.ts`·`DevelopmentBoard.tsx`·`App.css`를 만지지 않는다.
- **기존 작업 94건에 `scope_files`를 소급 기입하는 일.** 기획서 제외 범위다. 이 작업이 만드는
  픽스처에만 선언이 있다.
- **lease 파일 계약의 확장.** `task_id`가 이미 있고 그 id로 작업 문서를 찾으면 선언에 닿는다.
- **겹침을 발견했을 때 `depends_on`을 자동으로 채우거나 순서를 재배치하는 일.**
- **겹치는 작업을 `blocked`로 옮기는 일.** 개발자 계약이 이미 금지한다.
- **동시 세션 수 옵트인 설정.** 승인된 확인 필요 3번이 잘랐다.
- **경로 정규화·글롭·디렉터리 접두 일치.** 문자열 완전 일치만 한다.
- **목록 payload(`WorkflowItemSummary`)에 선언을 싣는 일.** TASK-037이 정한 선이 그대로다.
- **`depends_on` 판정 규칙의 변경.** R9 첫째 항목이 불변을 요구한다.
- **실제 파일 잠금이나 편집 충돌 해소.** 이 기획서가 다루는 것은 착수 자격이다.
