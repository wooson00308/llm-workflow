# 품질 확인 화면이 기능 소개를 카드에서는 세 줄로, 상세에서는 문단째로 보여준다

## 결정권자 요약

### 제안

확인 대기 목록의 기능 카드는 소개를 최대 세 줄까지만 보여주고 넘치면 말줄임으로 끊는다. 시작을
눌러 들어간 확인 화면과 완료 기록 화면은 소개를 전부 보여주되 문단 구분을 살린다.

### 현재

카드에는 줄 수 상한이 없어서 소개가 긴 기능은 카드가 그만큼 길어진다. 카드 높이가 기능마다 달라
목록을 훑어도 몇 개가 올라와 있는지 한눈에 들어오지 않는다. 확인 화면과 완료 기록 화면에서는
문단이 여럿인 소개도 빈 줄이 사라진 채 한 덩어리로 이어져 보인다.

### 변경 후

카드 높이가 기능마다 같아진다. 소개가 짧은 기능이든 긴 기능이든 카드가 차지하는 자리가 같아서,
확인 대기 목록을 위에서 아래로 훑는 것만으로 어떤 기능이 올라와 있는지 셀 수 있다. 세 줄을
넘는 소개는 끝이 말줄임으로 끊겨 더 있다는 것이 보인다. 기능 하나를 열면 소개가 잘리지 않고
전부 보이고, 문단이 여럿이면 문단 사이가 벌어져 읽는 자리에서는 끊어 읽을 수 있다.

### 비용과 위험

세 줄을 넘는 소개는 목록에서 뒷부분이 보이지 않는다. 잘린 부분은 시작을 눌러 들어가면 전부
보이므로 읽을 방법이 사라지지는 않는다. 이 작업은 표시 규칙만 바꾸고 화면의 구조나 확인 동선은
건드리지 않으므로, 되돌리기는 표시 규칙을 되돌리는 것으로 끝난다. 세 줄이라는 상한이 짧다고
판단되면 품질 확인에서 수정 요청으로 돌려보내면 된다.

## 현재 코드 상태

세 자리가 같은 값을 읽고 두 가지 클래스로 그린다. 클래스 선언은 둘 다
`src/features/projects/components/qa/QaWorkbench.css`에 있다.

- 목록 카드: `src/features/projects/components/qa/QaWorkbench.tsx` 83행이
  `<span className="qa-queue-goal">`로 그린다. 선언은 같은 CSS 16행이며 `display: block`,
  `margin-top`, 색, 글자 크기, `line-height: 1.55`, `word-break: keep-all`만 있고 줄 수를 제한하는
  선언이 없다.
- 확인 화면 머리말: 같은 tsx 130행이 `<p className="qa-feature-goal">`로 그린다.
- 완료 기록 화면 기능 상세: `src/features/projects/components/WorkspaceShell.tsx` 854행이 같은
  클래스로 그린다.
- `.qa-feature-goal` 선언은 같은 CSS 31행이며 `margin`, `max-width: 62ch`, 색, 글자 크기,
  `line-height: 1.6`, `word-break: keep-all`이다. 줄바꿈 처리를 지정하는 선언이 없어 값 안의
  줄바꿈이 공백으로 접힌다.

세 자리 모두 값이 비었을 때 요소를 아예 그리지 않는 조건을 이미 달고 있다. 그래서 소개가 없는
기능은 지금도 제목만 보인다.

줄 수를 제한하는 방식은 이 저장소에 이미 쓰는 어법이 있다. `src/App.css` 412행과 640행이
`display: -webkit-box`, `-webkit-box-orient: vertical`, `-webkit-line-clamp`, `overflow: hidden`
조합을 쓴다. 640행 쪽이 `overflow: hidden`까지 갖춘 형태다.

스타일 선언을 확인하는 시험은
`src/features/projects/components/qa/qaWorkbenchAlignment.test.ts`에 있다. 이 시험은 CSS 원문을
읽어 선택자별 선언을 꺼내 값을 확인한다. 화면 시험은 스타일 시트를 적용하지 않으므로 이 변경을
확인할 수 있는 자리는 이 시험 하나다.

이 작업은 TASK-S066-01과 파일이 겹치지 않고, 그 작업을 기다리지도 않는다. 두 작업이 어떤 순서로
끝나도 화면이 지금보다 나빠지지 않는다. 이 작업만 끝난 상태에서는 카드가 지금 값 그대로 세 줄에서
끊기고, TASK-S066-01이 끝나면 그 세 줄에 소개만 담긴다.

## 완료 조건

- C1. 목록 카드의 소개는 최대 세 줄까지 보이고 넘치면 말줄임으로 끊긴다(R2). `.qa-queue-goal`에
  줄 수 상한과 넘침 처리를 더한다. 저장소에 이미 있는 어법을 쓴다. 즉 `display: -webkit-box`,
  `-webkit-box-orient: vertical`, `-webkit-line-clamp: 3`, `overflow: hidden`을 함께 선언한다.
- C2. 카드에서는 문단 구분을 살리지 않는다(R2). 값 안의 줄바꿈이 공백으로 접혀 한 줄기로 이어져야
  하므로, `.qa-queue-goal`에 줄바꿈을 보존하는 선언을 넣지 않는다.
- C3. 확인 화면 머리말과 완료 기록 화면 기능 상세는 줄 수를 제한하지 않고 소개를 전부 보여준다
  (R3). `.qa-feature-goal`에 줄 수 상한이나 높이 상한을 넣지 않는다.
- C4. 그 두 자리에서 문단이 여럿이면 문단 구분이 보인다(R3). `.qa-feature-goal`에
  `white-space: pre-line`을 선언한다. 이 값은 빈 줄을 살리면서 한 문단 안의 여러 공백은 접으므로,
  TASK-S066-01이 정리해 보내는 값의 모양과 맞물린다.
- C5. 두 클래스의 기존 선언 중 이번 목적과 무관한 것은 그대로 둔다. 색, 글자 크기, 줄 간격,
  `word-break: keep-all`, `max-width: 62ch`, 바깥 여백은 손대지 않는다.
- C6. 소개가 없는 기능은 소개 자리가 아예 그려지지 않는다(R5). 이 동작은 지금 코드가 이미 하고
  있으므로 이 작업은 그 조건을 건드리지 않는다. 빈 자리를 채우는 선언이나 자리표시 문구를 넣지
  않는다.
- C7. 확인 동선은 그대로다(R6). 목록 카드에 확인 플로우를 노출하는 선언이나 구조 변경을 넣지
  않는다.
- C8. `qaWorkbenchAlignment.test.ts`에 다음을 확인하는 시험을 넣는다.
  - `.qa-queue-goal`의 `-webkit-line-clamp`가 `3`이고, `display`가 `-webkit-box`이며,
    `overflow`가 `hidden`이다.
  - `.qa-feature-goal`의 `white-space`가 `pre-line`이고, 줄 수 상한 선언이 없다.
- C9. 기존 시험을 지우거나 느슨하게 고치지 않는다. 이 파일의 기존 세 항목은 그대로 통과해야 한다.
- C10. 이 작업은 화면 구성 파일과 Rust 코드를 한 줄도 고치지 않는다. 두 클래스 이름이 세 자리에
  이미 붙어 있으므로 구성 파일을 고칠 이유가 없다.

## 범위 밖

- 앱이 읽어 오는 기능 설명 값의 내용. TASK-S066-01이 맡는다.
- 사용자 확인 플로우의 표시 방식. 기획서가 건드리지 않는다.
- 기능 제목, 상태 표시, 준비 중인 기능 목록의 구성.
- 소개 안에 굵게 표시 같은 다른 마크다운 기호가 들어 있을 때 그것을 서식으로 그리는 일. 기획서는
  절 제목 기호가 글자 그대로 보이지 않을 것만 요구하며, 그 요구는 값에서 절을 빼는 TASK-S066-01이
  충족한다.
- 개발 화면과 기록 화면의 다른 카드들. 이번 두 클래스만 다룬다.

## 범위 사전 검사

이 작업이 바꾸는 값은 두 개의 스타일 선언이다. 값을 만드는 자리와 그 값을 쓰는 자리를 모두 열어
확인했다.

- 값 경로: 카드의 줄 수 상한과 넘침 처리(C1, C2). 원천은
  `src/features/projects/components/qa/QaWorkbench.css` 16행의 `.qa-queue-goal` 선언이다. hop은
  둘이다. (1) `src/features/projects/components/qa/QaWorkbench.tsx` 83행이 이 클래스 이름을 이미
  스팬에 붙이고 있다. 클래스 이름이 바뀌지 않으므로 이 hop은 값을 무변경으로 나르고 편집이 필요
  없다. (2) 같은 tsx 6행이 이 CSS 파일을 불러오므로 선언이 화면에 닿는다. 이 불러오기도 그대로다.
  저장소 전체에서 `qa-queue-goal`을 쓰는 자리는 이 두 곳뿐임을 확인했다.
- 값 경로: 상세 자리의 문단 구분(C3, C4). 원천은 같은 CSS 31행의 `.qa-feature-goal` 선언이다.
  hop은 셋이다. (1) `QaWorkbench.tsx` 130행이 확인 화면 머리말에 이 클래스를 이미 붙이고 있다.
  (2) `src/features/projects/components/WorkspaceShell.tsx` 854행이 완료 기록 화면 기능 상세에
  같은 클래스를 이미 붙이고 있다. 두 자리가 같은 클래스를 쓰므로 선언 한 곳을 고치면 두 화면이
  함께 달라지고, 두 파일은 편집이 필요 없다. (3) 이 CSS는 `QaWorkbench.tsx`가 불러오지만 스타일
  시트는 문서 전체에 적용되므로 다른 화면인 완료 기록 화면에도 닿는다. 지금 그 화면이 이 클래스의
  색과 크기를 그대로 받고 있다는 사실이 그 근거다. 저장소 전체에서 `qa-feature-goal`을 쓰는 자리는
  이 셋뿐임을 확인했다.
- 값 경로: 선언이 실제로 그 값인지 확인하는 시험(C8). 원천은 이 작업이 쓰는 선언이고, 소비자는
  `src/features/projects/components/qa/qaWorkbenchAlignment.test.ts`다. 이 시험은 CSS 파일을
  원문으로 읽어 선택자별 선언을 꺼내므로, 선언을 고치면 이 시험이 바로 그 값을 본다. 편집이
  필요하므로 선언에 넣었다.

선언에서 뺀 파일과 근거를 정리한다.

- `src/features/projects/components/qa/QaWorkbench.tsx`와
  `src/features/projects/components/WorkspaceShell.tsx`: 세 자리 모두 필요한 클래스 이름과 빈 값
  처리를 이미 갖추고 있다. 표시 규칙을 스타일 선언으로 처리하므로 구성이 달라지지 않는다.
- `src/features/projects/components/qa/QaWorkbench.test.tsx`와
  `WorkspaceShell.test.tsx`: 화면 시험은 스타일 시트를 적용하지 않아 줄 수 상한도 줄바꿈 처리도
  확인하지 못한다. 이 두 시험이 확인하는 것은 값이 화면에 실리는지이고, 그 동작은 이 작업이
  바꾸지 않는다.
- `src/App.css`: 줄 수 상한 어법의 선례가 있는 파일이지만, 이번에 고치는 두 클래스는 여기에 없다.
  선례는 읽기만 했다.
- Rust 쪽 파일 전부: 값의 내용은 TASK-S066-01이 다룬다. 이 작업은 값을 만들지 않고 그리기만 한다.
