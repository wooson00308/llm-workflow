# 그룹 문서에서 사용자용 소개 문단만 뽑는다

## 결정권자 요약

### 제안

앱이 기능 설명으로 읽어 오는 값을 기능 소개 문단 하나로 좁힌다. 소개 뒤에 이어지는 내부 절은
읽지 않는다.

### 현재

앱은 문서 제목 한 줄과 소개 절의 제목 줄만 걷어내고 나머지를 전부 기능 설명으로 읽는다. 그래서
작업을 어떻게 나눴는지, 품질 확인을 어떤 방식으로 하는지 적어 둔 대목까지 함께 딸려 온다. 절
제목에 쓰인 우물 정 기호도 글자 그대로 섞여 들어오고, 문단을 나누던 빈 줄은 사라져 전부 한
덩어리로 이어진다. 가장 긴 기능은 이 값 하나가 26줄, 1191자다.

### 변경 후

앱이 읽어 오는 기능 설명이 소개 문단 하나로 줄어든다. 같은 기능 기준으로 26줄이 4줄, 1191자가
200자가 된다. 소개가 여러 문단이면 문단 구분이 값 안에 남아서, 이 값을 쓰는 화면이 문단을 살려
그릴 수 있다. 이 작업만으로는 아직 화면의 줄 수 상한과 문단 그리기가 달라지지 않는다. 그 부분은
TASK-S066-02가 맡는다.

### 비용과 위험

기능 설명에서 사라지는 대목은 작업 분해 근거와 품질 확인 방식 설명이다. 이 내용은 기능 문서
파일에 그대로 남아 있어 필요하면 문서를 열어 읽을 수 있다. 기존 기능 문서 62건을 모두 확인한
결과 새 규칙에서 소개가 비는 문서는 없었다. 문서 파일은 한 건도 바뀌지 않고 값을 읽는 규칙만
바뀌므로, 되돌리기는 규칙을 되돌리는 것으로 끝난다.

## 현재 코드 상태

기능 설명 값을 만드는 자리는 `src-tauri/src/infrastructure/fs_project_repository.rs` 3226행의
`parse_work_group_body` 하나다. 이 함수는 본문을 줄 단위로 훑으면서 세 가지를 동시에 만든다.
사용자 확인 플로우 시나리오 목록, 시나리오 식별자 구조 유효성, 그리고 기능 설명 문자열이다.

기능 설명을 모으는 조건은 3260행 한 줄이다. 시나리오 절(`### QA-`)에 속하지 않고, 문서 제목
(`# `)도 아니고, `## 기능 설명`이라는 제목 줄도 아닌 줄을 전부 `description_lines`에 넣는다.
그래서 `## 품질 확인 방식`이나 `## 작업 구성` 같은 내부 절의 제목 줄과 본문이 함께 들어간다.
3278행에서 그 줄들을 `\n`으로 이어 붙이고 앞뒤 공백만 잘라 값으로 삼는다.

만들어진 값은 3114행에서 받아 3208행의 `WorkGroupSummary` 조립에 그대로 실린다. 필드는
`src-tauri/src/domain/project.rs` 307행의 `pub description: String`이고, 이 구조체는
`#[serde(rename_all = "camelCase")]`로 직렬화되어 화면 타입
`src/features/projects/domain/types.ts` 195행의 `description: string`이 된다.

저장소의 기능 문서 62건에 이번 규칙을 적용해 확인한 결과는 다음과 같다. 소개가 비는 문서는 0건,
소개 길이는 최소 33자, 최대 350자, 소개가 두 문단 이상인 문서는 3건이다. 소개 안에 목록이나
인용, 표를 쓴 문서는 0건이다.

지금 진행 중이거나 시작하지 않은 작업 중 이 파일을 함께 고치는 것이 셋 있다. TASK-S065-01,
TASK-S065-02, TASK-S063-01이다. 셋 다 이 작업보다 앞에 두었다. 셋이 이미 서로 순서가 매겨져
있으므로 마지막 하나만 적어도 결과는 같지만, 겹치는 상대를 문서에서 바로 읽을 수 있도록 셋을
모두 적었다.

## 완료 조건

- C1. 본문에 `## 기능 설명` 절이 있으면 그 절의 본문만 소개로 뽑는다(R1). 다음 절 제목을 만나면
  거기서 끝낸다. 절 제목은 우물 정 기호 두 개 이상으로 시작하는 줄이며, 시나리오 절 제목도 여기에
  해당한다.
- C2. 그런 절이 없으면 문서 제목 줄 다음부터 첫 번째 절 제목 앞까지를 소개로 뽑는다(R1). 문서
  제목 줄이 없는 문서는 본문 처음부터 센다.
- C3. 소개 뒤에 오는 절의 제목과 본문은 어떤 경우에도 값에 들어가지 않는다(R1). 특히 지금 값에
  섞여 들어오던 내부 절이 한 줄도 남지 않아야 한다.
- C4. 뽑은 소개를 다음 모양으로 정리한다(R3이 요구하는 문단 구분을 값이 실어 나르게 하기 위한
  것이다). 한 문단 안에서 줄이 나뉘어 있으면 공백 하나로 이어 붙인다. 문단과 문단 사이는 빈 줄
  하나로 남긴다. 값 전체의 앞뒤 공백은 잘라 낸다.
- C5. 소개를 뽑을 수 없으면 빈 문자열을 값으로 준다(R5). 공백만 있는 소개도 빈 문자열이 된다.
  자리표시 문구를 넣지 않는다.
- C6. 사용자 확인 플로우 시나리오를 뽑는 동작과 시나리오 식별자 구조 유효성 판정은 한 가지도
  달라지지 않는다(R6). 시나리오 본문, 시나리오 순번 검사, 중복 식별자 처리가 지금과 같은 답을
  낸다.
- C7. 값을 받는 쪽의 모양을 바꾸지 않는다. `WorkGroupSummary`의 필드 이름과 타입은 그대로 두고,
  이 작업은 그 필드에 담기는 문자열만 바꾼다.
- C8. 다음 시험을 새로 넣는다.
  - `## 기능 설명` 절을 쓰고 그 뒤에 내부 절을 둔 본문에서, 값에 소개만 들어오고 내부 절의 제목과
    본문이 들어오지 않는다.
  - `## 기능 설명` 절이 없고 문서 제목 다음에 곧바로 소개를 쓴 본문에서, 값에 소개가 들어온다.
  - 소개가 두 문단인 본문에서, 값이 문단 사이를 빈 줄 하나로 유지하고 문단 안의 줄은 공백 하나로
    이어진다.
  - 소개가 없는 본문에서 값이 빈 문자열이다.
  - 위 본문들에서 시나리오 목록이 지금과 같이 뽑힌다.
- C9. 이 작업은 `.workflow` 아래의 문서 파일을 한 건도 고치지 않는다(R7). 선언한 파일 밖의 파일도
  바뀌지 않는다.

## 범위 밖

- 화면의 줄 수 상한과 문단 그리기. TASK-S066-02가 맡는다.
- 사용자 확인 플로우의 내용과 표시 방식. 이번 기획서가 건드리지 않는다.
- 아키텍트가 기능 문서를 쓸 때 지키는 작성 지침. 기획서가 제외 범위로 적었다.
- 기존 기능 문서를 새 규칙에 맞게 고치는 일. R7이 금지한다.
- 개발 화면의 작업 상세에 있는 그룹 정보. 제목과 상태만 쓰므로 이 값과 무관하다.

## 범위 사전 검사

이 작업이 바꾸는 값은 하나다. 기능 문서 본문에서 뽑아 `WorkGroupSummary`에 싣는 기능 설명
문자열이다. 값을 만드는 자리와 값의 타입을 모두 열어 확인했다.

- 값 경로: 기능 설명 문자열(C1~C5). 원천은 기능 문서 본문이고, 만드는 자리는
  `src-tauri/src/infrastructure/fs_project_repository.rs` 3226행 `parse_work_group_body`다.
  hop은 넷이다. (1) 3114행의 호출부가 반환값 세 개를 나눠 받는다. 이 작업이 반환 타입을 바꾸지
  않으므로 호출부는 그대로다. (2) 3208행의 `WorkGroupSummary` 조립이 `description` 필드에 넣는다.
  필드 이름과 타입이 그대로이므로 편집이 필요 없다. (3) `src-tauri/src/domain/project.rs` 307행의
  `pub description: String`. `String`을 그대로 유지하므로 이 hop은 값을 무변경으로 나른다. 직렬화
  이름도 `camelCase` 규칙으로 이미 `description`이라 달라지지 않는다. (4) 화면 타입
  `src/features/projects/domain/types.ts` 195행의 `description: string`과 그 값을 읽는 세 자리
  (`src/features/projects/components/qa/QaWorkbench.tsx` 83행과 130행,
  `src/features/projects/components/WorkspaceShell.tsx` 854행). 세 자리 모두 값이 비었을 때를
  이미 걸러 내고 있어 C5의 빈 문자열을 지금 코드가 그대로 받아 준다. 문자열 하나를 받아 그리는
  모양도 달라지지 않으므로 편집이 필요 없다. 그래서 선언은 만드는 파일 하나로 닫힌다.
- 값 경로: 사용자 확인 플로우 시나리오 목록과 구조 유효성(C6). 원천과 만드는 자리가 위와 같은
  함수다. 이 작업은 그 두 반환값을 바꾸지 않으므로 값 경로도 바뀌지 않는다. 소비자는 3132행의
  `structurally_valid` 계산과 3170행 부근의 사용자 모드 시나리오 검사, 그리고 화면의 확인 플로우다.
  기능 설명을 모으는 조건과 시나리오를 모으는 조건이 지금은 같은 반복문의 분기로 붙어 있으므로,
  분리하든 그대로 두든 시나리오 쪽 동작이 달라지지 않는다는 것을 C6과 C8의 마지막 항목이 시험으로
  못 박는다.

선언에서 뺀 파일과 근거를 정리한다.

- `src-tauri/src/domain/project.rs`: `description` 필드의 이름과 타입을 유지한다. 담기는 문자열이
  달라져도 이 파일이 나르는 값의 모양은 같다.
- `src/features/projects/domain/types.ts`와 세 화면 파일: 같은 이유로 편집이 필요 없다. 화면이
  이 값을 어떻게 그릴지는 TASK-S066-02의 몫이고, 그 작업은 이 파일들이 아니라 스타일 선언을
  고친다.
- `src-tauri/src/infrastructure/role_eligibility.rs`와 `heartbeat_condition.rs`: 기능 문서를 읽지만
  상태와 확인 방식과 구성 버전만 본다. 두 파일을 확인한 결과 기능 설명 문자열을 읽는 자리는 없다.
- `src-tauri/src/infrastructure/project_instructions.rs`: 아키텍트가 기능 문서를 쓸 때 지키는
  작성 지침이 들어 있다. 기획서가 이 지침 수정을 제외 범위로 적었고, 이번 규칙은 지침을 고치지
  않고도 두 가지 문서 형태를 모두 받아 준다.
- 기능 문서 파일 자체: R7이 금지한다. 62건 전수 확인에서 소개가 비는 문서가 0건이었으므로 문서를
  고쳐야만 올바르게 보이는 경우가 없다.
