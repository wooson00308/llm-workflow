# 결정이 끝난 기획서 화면에서 후속 기획 요청을 보내고 도장 이력을 읽는다

## 결정권자 요약

승인이 끝난 기획서 화면에 후속 기획 요청을 보내는 자리가 섰다. 앞 작업이 안쪽에 낸 길을 이제
사용자가 실제로 밟는다.

누르기 전에 무엇이 일어나는지 읽힌다. 기존 승인은 지워지지 않고 그 승인에서 나온 개발 작업도
그대로 돈다. 대신 그 기획서의 화면 상태가 수정을 요청한 기획으로 바뀐다.

실수로 눌리지 않는다. 기획서를 열자마자 보이는 자리에 두지 않았고, 한 번 여는 조작과 코멘트를
지나야 기록된다.

그 기획서에 찍힌 도장들도 시간순으로 읽힌다. 도장이 하나뿐인 기획서에서도 한 줄로 나온다.

지금 필요한 것은 사용자 확인이다. 아래 확인 동선을 따라 승인된 기획서를 하나 열어 보면 된다.

## 확인 동선

**볼 화면이 있는 작업이다.** 앱을 띄우고 기획서 검토 탭에서 아래 넷을 밟으면 된다.

**기록까지 누를 필요는 없다.** 이 저장소의 기획서 결정은 사용자의 도장이고, 양식을 열어 두었다가
"취소"로 빠져나오면 아무것도 기록되지 않는다. 기록되는 것은 "후속 기획 요청 기록"을 누른 순간
하나뿐이다.

### 1. 승인된 기획서에서 조작이 열리는지

기획서 검토 탭 → 필터 "결정됨" → 상태 알약이 "승인됨"인 문서를 아무거나 연다.

**정상이면 오른쪽 사용자 결정 패널이 이렇다.**

- "승인된 기획입니다" 상자 아래에 "후속 기획 요청" 버튼이 **하나만** 있다.
- 승인 도장 버튼도 기획서 폐기 버튼도 **없다**. 이 둘이 보이면 화면이 앱 안쪽보다 넓게 연 것이고,
  눌렀을 때 오류가 난다.
- 그 아래 "결정 이력"이 열려 있고 도장이 시간순으로 한 줄씩 나온다.

### 2. 이력이 읽히는지

같은 자리에서 이력을 읽는다. **정상이면 항목마다 이름과 시각이 있고, 고치거나 지우는 버튼이
하나도 없다.**

- 대부분의 기획서는 도장이 하나라 **한 줄**로 나온다. 그것이 정상이다.
- **두 줄이 나오는 문서는 SPEC-022 하나다.** 승인 도장이 둘 찍혀 있고, 위가 8월 4일 08:52,
  아래가 09:38이어야 한다(기기 시간대에 따라 표기 시각은 달라진다). 이력이 시각순인지 보려면
  이 문서를 열면 된다.
- SPEC-041에는 결정 문서가 둘 있지만 이력은 한 줄이다. 하나가 위임 대리 결정이라 앱이 세지 않는
  것이고, 규칙이 정한 그대로다.

### 3. 실수로 눌리지 않는지

1번에서 연 승인된 기획서에서 "후속 기획 요청"을 누른다.

**정상이면 양식이 열리면서 아래가 순서대로 읽힌다.**

1. 사실 셋 — "기존 승인 결정은 지워지지 않습니다" / "이 기획서에서 나온 개발 작업은 그대로
   진행됩니다" / "대신 이 기획서가 수정을 요청한 기획으로 바뀝니다"
2. 확인 문구 — "이 기획서에 후속 기획 요청을 기록합니다. 결정 기록은 되돌릴 수 없습니다."
3. 코멘트 입력과 "후속 기획 요청 기록" 버튼. **코멘트가 비어 있는 동안 그 버튼은 잠겨 있다.**

여기서 "취소"를 누르고 나온다. 아무것도 기록되지 않는다.

### 4. 지금까지 되던 것이 그대로인지

- 상태 알약이 "내 선택 대기"인 기획서를 연다. **정상이면 승인 도장 찍기 · 수정 요청 · 기획서 폐기
  셋이 어제와 똑같이 있고, "후속 기획 요청"은 없다.**
- 상태 알약이 "수정 요청됨"이거나 "폐기됨"인 문서를 연다. **정상이면 결정 도구가 하나도 없고
  이력만 읽힌다.**

### 5. 자동 검사 두 개

```sh
npm run check
cargo test --manifest-path src-tauri/Cargo.toml
```

**정상이면 앞엣것이 23 files / 664 tests passed, 뒤엣것이 538 passed / 0 failed / 0 ignored다.**
이 세션이 넘길 때의 값이고, 다른 세션이 그 사이에 검사를 더했으면 숫자는 늘 수 있다. 늘어도
`failed`가 0이면 정상이다.

### 6. 알아 둘 것

- 배치와 여백은 자동 검사가 덮지 못한다. 눈으로 볼 때 그 자리를 함께 봐 주면 된다.
- 활동 뷰는 아직 같은 사건을 "수정 요청"이라고 부른다. 두 화면의 이름을 맞추는 것은 TASK-129의
  몫이라 이 작업에서는 갈려 있는 것이 정상이다.
- 잘못 보낸 후속 기획 요청을 취소하는 길은 없다. 수정 요청 상태에 결정을 또 얹는 칸이 막혀 있고,
  그것이 기획서가 승인한 선택이다.

## 지금 이 자리가 어떻게 되어 있는가

`SpecWorkspace.tsx:64`가 `awaitingDecision = activeStatus === "user_review"`이고, 승인·수정
요청·폐기 묶음이 그 조건 아래에만 그려진다(`:161`). 결정이 끝난 기획서에는 `:207`~`:212`의
결과 상자만 남는다 — "승인된 기획입니다"와 "결정 기록은 원문과 분리되어 보존됩니다" 두 줄이고,
조작할 것이 없다.

무장 확인(`useArmedConfirm`)은 지금 승인 버튼에만 걸려 있다(`:164`~`:172`). 수정 요청과 폐기는
코멘트 입력을 먼저 열고, 코멘트가 비면 기록 버튼이 잠긴다(`:193`~`:205`).

## 확인된 사실 셋

기획서가 "값은 이미 만들어져 화면까지 도착해 있다"고 적은 자리(R7)의 실물이다. 이 셋 위에서
새 조회도 새 필드도 만들지 않는다.

1. **결정 이력은 목록 payload에 이미 실려 있다.** `workflow_items`가 `spec_decision_events`가
   만든 이벤트를 기획서 항목의 `events`에 넣고 시각순으로 정렬한다. 그 필드는
   `WorkflowItemSummary`의 것이고 프론트 타입에도 `events?: TaskEvent[]`로 있다. 즉 이 화면이
   이미 받는 `workflow.items.specs` 안에 답이 있다.
2. **문서 전문 조회에는 그 값이 없다.** `read_spec`은 요약을 읽고 최신 결정만 덮어씌울 뿐
   이벤트를 채우지 않는다. 그러므로 이력은 `document.summary`가 아니라 목록 항목에서 찾아야
   한다 — 열린 문서와 같은 파일 이름을 가진 항목이다.
3. **결정 직후에도 값이 갱신된다.** `decideSpec`이 기록 결과로 받은 요약을 그대로
   `setProject`에 넣고, 그 요약을 만드는 경로가 워크플로우 문서를 다시 읽는다. 새로 찍힌 도장이
   같은 렌더에서 이력에 들어온다는 뜻이다. 2.5초 주기의 폴링을 기다리지 않는다.

## 바꾸는 것

### 1. 승인된 기획서에서 후속 기획 요청을 보낼 수 있다 (R1)

- 화면이 여는 조작이 TASK-127의 표와 같은 조합을 연다. 승인된 기획서에서는 후속 기획 요청
  하나만 열리고, 재승인과 폐기 버튼은 그리지 않는다. 수정 요청·폐기된 기획서와 작성 중 기획서에는
  아무 조작도 열리지 않는다.
- 화면이 표보다 넓게 열면 사용자가 버튼을 누르고 오류를 본다. 좁게 열면 앞 작업이 낸 길이 닿지
  않는다. 기획서 완료 조건 5가 요구하는 대조가 이것이다.
- 기록되는 값은 지금과 같은 수정 요청이다. 새 결정 종류를 만들지 않는다.
- 코멘트는 필수다. 후속 기획의 재료가 그 코멘트이고, 비면 기록되지 않는 지금 규칙 그대로다.

### 2. 이 조작을 "후속 기획 요청"이라고 부른다 (확인 필요 4번의 승인된 제안)

- 기록되는 값은 수정 요청 그대로지만 화면 이름이 갈린다. 아직 결정되지 않은 기획서의 수정
  요청은 그 문서를 다시 쓰라는 것이고, 승인된 기획서의 그것은 승인과 파생 작업을 그대로 두고
  후속 기획을 요청하는 것이다.
- **이름을 정하는 규칙은 한 자리에만 둔다.** 같은 규칙을 TASK-129의 활동 뷰가 쓰고, 이 화면의
  이력(R7)도 쓴다. 세 자리가 각자 판단하면 "같은 사실을 두 자리에서 다르게 말하지 않는다"(R5)가
  깨진다. 그래서 `src/features/projects/domain/specDecisionLabels.ts`를 새로 만들고 이 화면이
  첫 사용자가 된다.
- 그 모듈이 답하는 질문은 하나다 — 한 기획서의 시각순 결정 목록에서 어느 항목이 후속 기획
  요청이고 어느 항목이 수정 요청인가. 판별 근거는 그 항목 앞에 승인이 있었는가이고, 목록 자체가
  그 답을 갖고 있으므로 새 값을 앱에서 받아 올 필요가 없다.
- 함수 모양은 구현자가 정한다. 정해진 것은 자리(한 모듈)와 답(항목별 이름)과 근거(앞선 승인의
  유무)다.

### 3. 무엇이 일어나고 무엇이 일어나지 않는지가 누르기 전에 읽힌다 (R3)

누르기 전 자리에 다음 셋이 있다. 앱이 아는 것 이상은 말하지 않는다 — 무엇이 만들어질지, 다음에
무엇을 해야 할지는 예고하지 않는다.

- 기존 승인 결정이 지워지지 않는다.
- 그 승인에서 나온 개발 작업이 그대로 돈다. 이것은 부작용이 아니라 이 기획서가 하는 약속이다
  (확인 사실 8).
- 그 대신 이 기획서의 화면 상태가 "수정을 요청한 기획입니다"로 바뀐다(확인 사실 3).

아직 개발 작업으로 쪼개지지 않은 승인이었다면 그 승인이 아키텍트 대기 물량에서 빠진다(확인 사실
7). 이 사실을 화면에 적을지는 구현자가 정한다 — 적는다면 그 조건을 화면이 알아야 하는데, 지금
기획서 항목에 파생 작업 건수가 실리는지는 TASK-120의 산출물에 달려 있다. 알 수 없으면 적지
않는다. 앱이 아는 것 이상을 말하지 않는 쪽이 R3의 마지막 줄이다.

### 4. 실수로 눌리지 않는다 (R4)

- 기획서를 열자마자 눌리는 자리에 두지 않는다. 명시적으로 한 번 여는 조작을 지난 뒤에 나온다.
  `user_review`의 수정 요청이 코멘트 입력을 먼저 여는 것과 같은 어법이다.
- 코멘트가 비면 기록되지 않는다. 지금 그대로다.
- 확인 문구가 이 조작이 무엇을 하는지 말한다. 지금 기획서 쪽 수정 요청에는 그 문구가 없고 작업
  QA 쪽에는 있다(확인 사실 13). 결정이 누적되는 자리가 열리는 이상 그 비대칭을 남겨 두지
  않는다.
- 문서를 바꿔 열면 열어 둔 조작과 입력이 초기화된다. 지금 `useEffect`가 파일 이름 변화에서 하는
  일 그대로이고, 새로 여는 조작도 그 초기화에 들어가야 한다.

### 5. 도장 이력이 그 화면에서 시각순으로 읽힌다 (R7)

- 결정이 둘 이상인 기획서에서 "언제 승인됐고 언제 후속 요청이 왔나"가 이 화면에서 읽힌다.
- **결정이 하나뿐인 기획서에서도 같은 이력이 한 줄로 나온다.** 확인 필요 3번의 승인된 제안이다.
  갈래를 두면 어느 기획서에서 이력을 볼 수 있는지 사용자가 미리 알 수 없기 때문이다.
- 그 결과 지금 결과 상자가 하던 말의 일부를 이력이 대신하게 되어 상자의 문구가 달라진다.
  기획서가 확인 필요 3번의 비용으로 이미 적어 둔 값이다. 같은 사실을 두 자리에서 두 번 말하지
  않도록 정리한다.
- 항목마다 무엇이 언제였는지가 읽힌다. 이름은 위 2번의 규칙이 정한다.
- 이력은 읽기 전용이다. 결정을 고치거나 지우는 자리를 만들지 않는다.
- 시각을 읽을 수 없는 결정은 애초에 이벤트가 되지 않는다. 목록을 만드는 쪽이 이미 그런 항목을
  빼므로 화면이 따로 다룰 것이 없다.

## 손대지 않는 것

- **쓰기 경로.** 허용 판정과 거절 문구는 TASK-127이 이미 닫았다. 이 작업에서 다시 열지 않는다.
- **활동 뷰와 개발 작업 화면.** R5는 TASK-129의 몫이다. 새 이름 규칙 모듈을 만들되 이 작업에서
  쓰는 것은 기획서 화면뿐이다.
- **문서 화면의 두 양식과 파생 작업 배지.** TASK-120의 산출물이고 SPEC-039의 몫이다. 이 작업은
  그 위에 조작과 이력을 올린다.
- **판정 규칙과 결정 문서의 모양.** 그대로다.
- **개발 작업 QA 흐름.** 그대로다.

## 완료 조건

1. 승인된 기획서에서 후속 기획 요청을 보낼 수 있고, 화면이 여는 조작이 TASK-127의 표와 같은
   조합이다. 상태별 픽스처의 컴포넌트 테스트가 다섯 상태에서 무엇이 열리고 무엇이 열리지
   않는지를 단언하고, 그 결과가 조합 테스트와 어긋나지 않는다. (기획서 완료 조건 5, R1)
2. 후속 기획 요청이 기존 승인과 파생 작업을 건드리지 않는다는 것이 누르기 전에 읽힌다. (기획서
   완료 조건 6, R3)
3. 그 기획서의 화면 상태가 바뀐다는 사실도 누르기 전에 읽힌다. (기획서 완료 조건 7, R3)
4. 후속 기획 요청이 기획서를 열자마자 눌리지 않고, 여는 조작과 코멘트를 지나야 기록된다. 확인
   문구가 무엇이 일어나는지 말한다. 코멘트가 비면 기록되지 않는다. (기획서 완료 조건 8, R4)
5. 결정이 둘 이상인 기획서의 이력이 이 화면에서 시각순으로 읽히고, 승인과 후속 기획 요청이 각각
   언제였는지가 나온다. 결정 둘을 심은 픽스처의 컴포넌트 테스트가 확인한다. (기획서 완료 조건
   12, R7)
6. 결정이 하나뿐인 기획서에서도 같은 이력이 한 줄로 나온다. (기획서 완료 조건 13, R7)
7. 이력에서 결정을 고치거나 지우는 자리가 없다. (기획서 완료 조건 14, R7)
8. 화면 이름을 정하는 규칙이 한 모듈에 있고 그 모듈에 자기 테스트가 있다. 앞에 승인이 있는
   수정 요청과 없는 수정 요청이 다른 이름을 받는다. (R5의 단일 출처, 확인 필요 4번)
9. `user_review` 기획서의 승인·수정 요청·폐기 동선이 지금과 같다. 기존 테스트가 수정 없이
   통과한다. (기획서 완료 조건 17, R9)
10. 기존 자동 테스트가 삭제되거나 비활성화되지 않는다. (기획서 완료 조건 18, R9)
11. 역할 계약 문언과 파일 계약 문서가 이 변경분에서 달라지지 않는다. (기획서 완료 조건 19)
12. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다. (기획서
    완료 조건 21)

## 검증 절차

1. 다섯 상태(작성 중·선택 대기·승인·수정 요청·폐기)의 픽스처로 화면을 열어 각각 무엇이
   그려지는지 단언한다. TASK-127의 조합 테스트와 나란히 놓고 열린 칸이 같은지 읽는다.
2. 승인된 기획서 픽스처에서 여는 조작 → 설명과 확인 문구 → 코멘트 → 기록까지 밟고, 코멘트가 빈
   채로는 기록되지 않는 것을 확인한다.
3. 결정이 하나인 픽스처와 둘인 픽스처에서 이력이 각각 한 줄과 두 줄로 나오고 이름이 갈리는 것을
   확인한다.
4. 이름 규칙 모듈의 테스트를 따로 돌린다.
5. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`.
6. 앱을 띄워 실제 승인된 기획서 하나를 열고 조작이 보이는지, 이력이 읽히는지 눈으로 확인한다.
   **실제로 결정을 기록하지는 않는다.** 이 저장소의 기획서 결정은 사용자의 도장이다.
