# 문서 화면이 결정권자 양식을 기본으로 그리고 원문을 토글로 남긴다

## 결정권자 요약

이제 기획서와 개발 작업을 열면 먼저 보이는 것이 결정권자에게 쓴 요약이다. 지금까지는 작업자가
작업자에게 쓴 본문이 통째로 열렸고, 도장을 찍기 전에 문서를 처음부터 읽어야 했다.

원문은 사라지지 않는다. 토글을 한 번 누르면 전문이 그대로 펴지고, 문서를 닫았다 다시 열면 언제나
평문에서 시작한다.

요약이 없는 옛 문서는 지금과 똑같이 열린다. 원문이 그대로 나오고 어떤 문구도 붙지 않으며, 그
문서에는 토글도 서지 않는다. 앱은 문서 파일을 고치지 않으며 요약을 지어내지도 않는다.

기획서 화면에는 그 기획서에서 나온 개발 작업의 상태별 건수가 붙었고, 개발 작업 상세에서는 시작
가능 여부가 상태 배지 옆으로 옮겨 왔다. 지금 필요한 것은 사용자 QA다.

## 확인 동선

앱을 띄우고 도그푸딩 워크플로를 연다. 눈으로 볼 몫이 남아 있어서다 — 자동 검사는 마크업과 문자열
까지만 보장하고, 그래서 그렇게 보이는지는 이 동선이 판정한다.

1. **기획서 검토** → 목록에서 SPEC-042(또는 SPEC-040·SPEC-041)를 연다. 본문 자리에 `결정권자 요약`
   절만 나와야 한다. 문서 오른쪽 위의 `원문 전문 보기`를 한 번 누르면 전문이 펴지고, 그 안에 요약
   절도 그대로 있다. `요약만 보기`로 되돌아온다.
2. 같은 화면에서 옛 기획서(예: SPEC-001)를 연다. 원문이 그대로 나오고, **토글 버튼도 안내 문구도
   붙지 않는다.** 이것이 정상이다 — 이 저장소의 문서 167건 중 요약 절을 가진 것은 15건뿐이다.
3. 1의 문서에서 토글을 열어 둔 채 목록에서 다른 문서를 고른다. 새 문서는 다시 요약에서 시작해야
   한다(토글 상태를 저장하지 않는다).
4. **기획서 본문 위의 배지 줄** → SPEC-039를 열면 `준비 1 · 진행 중 0 · 막힘 0 · QA 대기 2 · 완료 0`
   과 그 오른쪽에 `이 기획서를 출처로 적은 개발 작업 전체를 셉니다`가 보인다. 개발 작업 화면에서
   `기획서별 묶기`를 켜고 SPEC-039 레인 헤더의 수치와 나란히 두면 같은 값이어야 한다. 파생 작업이
   없는 기획서(예: SPEC-001)에서는 `이 기획서에서 나온 개발 작업이 아직 없습니다.`가 대신 선다.
5. **개발 작업** → TASK-129를 연다. 본문이 요약 절에서 시작하고, 머리의 상태 배지 옆에
   `시작할 수 없음`이 붙는다. 아래 선행 작업 상자 헤더에는 그 낱말이 **없어야** 한다 — 자리를 옮긴
   것이지 복제한 것이 아니다.
6. 선행도 겹침도 선언하지 않은 작업(예: TASK-122)을 연다. 상태 배지 옆에 시작 가능 여부가 아예
   붙지 않는다.
7. `← 개발 작업으로`로 나갔다가 같은 작업을 다시 연다. 다시 요약에서 시작해야 한다.

어긋난 것으로 볼 신호: 요약 절이 있는 문서인데 열자마자 원문 전체가 나오면 절 찾기가 틀린 것이고,
요약이 없는 문서에 안내 문구나 눌러도 아무 일 없는 토글이 보이면 폴백이 틀린 것이다.

---

SPEC-039의 R1·R2·R5·R6이다. 기획서 완료 조건 1·2·3·4·10을 이 작업이 닫는다.

R1과 R2를 가르지 않은 이유는 가른 중간 상태가 뜻을 갖지 않기 때문이다. 기본 뷰가 그릴 것이
요약 절이고(R2), 요약 절 없이 세운 기본 뷰는 R6의 폴백만 남아 토글이 같은 것을 두 번 보여준다.
R5도 같은 이유로 여기 있다 — 배지가 서는 자리가 "기본 뷰"이고 그 자리는 이 작업의 산출물이다.
R8이 R5를 SPEC-038과 무관한 몫으로 묶었지만, 그것은 R5가 쓰는 **값**이 이미 앱 안에 있다는 뜻이고
배지가 설 **자리**까지 앞당기지는 못한다.

## 아키텍트가 고정하는 값

### 1. 절의 이름은 TASK-118이 계약에 박은 문자열 그대로다

- 요약 절: `## 결정권자 요약`
- 이 작업은 이 한 문자열만 찾는다. 후보를 추측하지 않고, 대소문자·공백 변형도 만들지 않는다(R2).
- 문자열이 TASK-118의 착지와 갈라지면 화면이 아무 문서에서도 요약을 찾지 못한다. 그래서 이 작업이
  TASK-118 뒤에 선다(아래 선행).

### 2. 절 찾기는 순수 모듈이고 화면 밖에 산다

`src/features/projects/domain/documentSections.ts`를 새로 만든다.

- 입력은 문서 본문 문자열과 찾을 절 제목 하나, 출력은 그 절의 본문과 나머지다.
- 두 화면(`SpecWorkspace`·`DevelopmentBoard`)이 함께 쓰고, TASK-121이 `## 확인 동선`을 찾을 때 같은
  함수를 쓴다. 쓰는 곳이 셋이므로 컴포넌트 안에 두지 않는다. TASK-119가 문장 조립을
  `DevelopmentBoard.tsx` 안에 둔 것과 반대 판단이고, 근거도 반대다 — 그쪽은 쓰는 곳이 하나였다.
- 절의 경계는 **같은 깊이의 다음 제목까지**다. `## 결정권자 요약` 다음의 `###`는 절 안이고 다음
  `##`는 절 밖이다. 문서 본문에 코드 블록이 있을 수 있으므로 코드 펜스 안의 `#`은 제목이 아니다.
- 판정은 원문 문자열 위에서 한다. Markdown을 파싱해 트리로 만들지 않는다. 지금 화면이
  `react-markdown`에 본문을 통째로 넘기는 구조를 바꾸지 않기 위해서다 — 자른 조각도 같은
  경로로 그린다.

### 3. 두 양식은 공용 컴포넌트 하나가 그린다

`src/features/projects/components/DocumentReader.tsx`를 새로 만든다.

- 기본 뷰(요약 절)와 원문 토글을 이 컴포넌트가 갖는다. 두 화면이 같은 것을 두 벌 만들면 기본값이
  갈릴 자리가 생긴다.
- `MarkdownBody`는 고치지 않는다. 그리는 방법이 아니라 무엇을 넘길지가 바뀌는 것이고,
  `MarkdownBody`는 아이디어 미리보기도 쓴다(제외 범위: 아이디어 화면).
- **토글 상태를 저장하지 않는다**(승인된 확인 필요 3번). 문서를 열 때마다 평문에서 시작한다. 새
  저장소 파일을 만들지 않는다 — `browserSpecLaneCollapseStore` 계열에 다섯 번째를 더하지 않는다.
- 토글은 한 번의 조작으로 전문에 닿는다. 단계를 겹치지 않는다(R1).
- 원문 전문에는 요약 절도 함께 있다. 기본 뷰에서 감춰졌던 절이 토글 뒤에서 전부 보여야 한다
  (기획서 완료 조건 2). 원문은 자르지 않은 본문 그대로다.

### 4. 폴백은 오류가 아니다 (R6)

- 요약 절이 없으면 기본 뷰가 원문 전문을 그린다. 지금 화면과 같은 결과다.
- **아무 문구도 붙이지 않는다**(승인된 확인 필요 2번). 읽기 실패 문구도, 안내 문구도 없다.
- 폴백일 때 토글이 어떻게 보이는지는 개발자가 정한다. 같은 것을 두 번 보여주는 토글을 남길지
  숨길지는 문언이 아니라 화면 판단이고, 어느 쪽이든 기획서 완료 조건 4를 깨지 않는다. 고른 쪽과
  근거를 보고서에 적는다.
- 문서 파일을 고치지 않는다. 소급 기입은 없다.

### 5. 기획서 화면의 파생 작업 배지 (R5, 승인된 확인 필요 4번)

- 대상은 그 기획서에서 나온 개발 작업의 **상태별 건수**다. 묶는 열쇠는 `sourceSpecId`이고, 보드의
  레인이 쓰는 것과 같은 값이다(확인 사실 11).
- 값은 `SpecWorkspace`가 이미 받는 `workflow.items.tasks`에서 센다. 새 payload도 새 조회도 없다.
- **무엇을 센 값인지 화면이 문장으로 밝힌다.** 레인이 `LANE_BASIS_NOTE`로 계산 집합을 한 줄
  밝히는 것과 같은 어법이다. 배지는 판정이 아니라 집계다.
- **규격 밖 상태를 조용히 빠뜨리지 않는다.** 레인의 `unknownCount`와 같은 이유다. 다섯 상태 밖의
  값이 있으면 그 건수가 보인다.
- 파생 작업이 0건인 기획서에서 무엇을 보일지도 정한다. 빈 배지 줄을 두는 것과 아무것도 두지 않는
  것 중 하나이고, 고른 쪽을 보고서에 적는다.
- 보드의 레인이 같은 값을 이미 말한다는 것이 이 항목의 비용이다(기획서 확인 필요 4번). 계산
  집합이 어긋나지 않도록 두 자리의 셈 대상을 보고서에서 대조한다.

### 6. 작업 상세의 시작 가능 여부 (R5)

- TASK-119가 `task-dependency-summary` 자리에 남겨 둔 "시작 가능"/"시작할 수 없음"을 기본 뷰의
  자리에서 읽히게 한다. 지금 상태(상태 배지)도 같은 자리에서 읽힌다.
- 같은 사실을 두 자리에서 말하지 않는다. 옮기는 것이지 복제하는 것이 아니다.

### 7. 넘지 않는 선

- 앱이 요약을 만들지 않는다. LLM 호출도, 본문 축약도, 앞 몇 줄 잘라 쓰기도 아니다. 절이 있으면
  그대로 잘라 오고 없으면 폴백이다.
- 문서 파일을 쓰지 않는다. 소급 기입 없다.
- 아이디어 화면을 건드리지 않는다(제외 범위).
- 일괄 QA 다이얼로그를 건드리지 않는다. 확인 동선은 TASK-121의 몫이고 그쪽도 단건만 다룬다.
- 선행·겹침 판정과 TASK-119가 세운 문장을 고치지 않는다. 자리를 옮기는 것은 고정값 6 하나뿐이다.
- Rust를 고치지 않는다. 문서 payload에 새 필드를 만들지 않는다.
- 목록 미리보기·검색·QA 기록·결정 기록의 동작을 바꾸지 않는다.
- 기존 자동 테스트를 지우거나 비활성화하지 않는다.

## 완료 조건

1. 기획서 검토와 개발 작업 상세가 기본 뷰와 원문 토글을 갖고, 문서를 열면 기본이 평문이다.
   검증: `SpecWorkspace.test.tsx`·`DevelopmentBoard.test.tsx`·`DocumentReader.test.tsx`. (R1 /
   기획서 완료 조건 1)
2. 토글을 열면 원문 전문이 나오고, 기본 뷰에서 감춰졌던 절이 전부 보인다. 검증: 같은 테스트.
   (R1 / 기획서 완료 조건 2)
3. 문서를 닫았다 다시 열면 다시 평문에서 시작한다. 토글 상태가 저장되지 않는다. 검증: 같은
   테스트. (승인된 확인 필요 3번)
4. 요약 절을 `## 결정권자 요약` 하나로 찾고 그 외의 후보를 추측하지 않는다. 검증: 그 절을 가진
   픽스처와 다른 이름의 절만 가진 픽스처 두 벌로 `documentSections.test.ts`와 컴포넌트 테스트.
   (R2 / 기획서 완료 조건 3)
5. 요약 절이 없는 문서는 기본 뷰에서 원문 전문이 나오고 어떤 문구도 붙지 않는다. 검증: 같은
   테스트. (R6 / 기획서 완료 조건 4)
6. 절의 경계가 같은 깊이의 다음 제목이고, 코드 펜스 안의 `#`을 제목으로 읽지 않는다. 검증:
   `documentSections.test.ts`. (고정값 2)
7. 기획서 화면이 파생 작업의 상태별 건수를 보여주고, 무엇을 센 값인지 화면이 문장으로 밝히며,
   규격 밖 상태가 조용히 빠지지 않는다. 검증: `SpecWorkspace.test.tsx`. (R5 / 기획서 완료 조건 10)
8. 개발 작업 상세가 지금 상태와 시작 가능 여부를 기본 뷰의 자리에서 보여주고, 같은 사실이 두
   자리에 남지 않는다. 검증: `DevelopmentBoard.test.tsx`와 변경분 확인. (R5)
9. 앱이 문서 파일을 쓰지 않는다. 검증: 변경분에 문서 쓰기 경로가 늘지 않았음을 확인. (R9 /
   기획서 완료 조건 13)
10. 아이디어 화면·목록 미리보기·검색·QA 기록·결정 기록이 달라지지 않는다. 검증: 기존 테스트가
    수정 없이 통과한다. (R9 / 기획서 완료 조건 15)
11. 기존 자동 테스트가 삭제되거나 비활성화되지 않는다. 검증: 테스트 목록 변경분 확인. (기획서
    완료 조건 16)
12. `npm run check`가 통과한다. Rust 변경이 없으므로 `cargo test`는 이 작업의 완료 조건이 아니다.
    (기획서 완료 조건 17)

## 검증 절차

1. `npm run check`.
2. `npx vitest run src/features/projects`.
3. `git diff --stat`으로 변경 파일이 범위 파일 아홉뿐임을 확인하고 결과를 보고서에 적는다. 완료
   조건 9·10의 근거가 그 확인이다.
4. 설치본 계약(`.workflow/rules/`)이 아니라 TASK-118이 고친 앱 내장 계약 본문에서 `## 결정권자 요약`
   문자열을 확인하고, 이 작업이 찾는 문자열과 문자 단위로 같은지 대조한 결과를 보고서에 적는다.
   완료 조건 4의 전제다.
5. 앱을 띄워 요약 절이 있는 문서와 없는 옛 문서를 각각 열어 기본 뷰·토글·폴백을 눈으로 확인한다.
   기획서 완료 조건 1·2·4의 눈 확인 몫이다. 이 저장소의 기존 문서 355건에는 요약 절이 거의 없으므로
   있는 쪽 확인에는 TASK-118 이후에 쓰인 문서나 손으로 만든 픽스처를 쓴다.
6. 기획서 배지의 셈 대상과 보드 레인의 셈 대상을 나란히 두고 어긋나지 않는지 대조한 결과를
   보고서에 적는다. 고정값 5의 비용 항목이다.
