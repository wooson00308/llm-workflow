# 상태 조회 명령을 앱이 설치하고 버전을 붙인다

## 결정권자 요약

### 제안

상태 조회 명령을 앱이 관리하는 네 번째 실행 자산으로 세워, 프로젝트를 열 때 함께 설치되게 한다.

### 바뀌는 것

- 지금: 상태를 물어볼 명령이 없다 → 앞으로: 프로젝트마다 조회 명령이 규칙 자리에 설치되고 설정 화면의 자산 목록에 설치 버전이 함께 뜬다
- 명령을 부르면 프로젝트 이름과 워크플로와 판정 시각이 먼저 나온다. 나머지 묶음은 다음 작업이 채운다.

### 비용과 위험

- 관리 자산이 여덟에서 아홉으로 는다. 관리 표기가 없는 파일이 같은 이름으로 있으면 동기화가 지금과 같은 방식으로 멈추고 사용자에게 그 파일을 치우라고 알린다.
- 사용자에게 보이는 화면은 설정 화면의 자산 한 줄뿐이고, 그 줄은 목록을 받은 대로 그리는 기존 코드가 만든다. 자동 검증이 설치와 목록 노출을 함께 확인한다.

## 현재 코드 상태

앱이 `.workflow/rules/`에 설치하는 실행 자산은 지금 셋이다. 그중 둘이 관리 자산 동기화 경로를 타고,
예약 헬퍼는 프로젝트 저장소 경로를 탄다. 이 작업은 앞의 경로에 하나를 더한다.

- `src-tauri/src/infrastructure/managed_script.rs`가 설치 규약을 혼자 갖는다. 자산은 확장자를 뺀
  이름, 표시 이름, 버전 접두사, 버전, 현재 플랫폼 구현을 넘기고(24행부터), 117행의 설치 계획이
  파일 없음, 관리 표기 없음, 버전 줄 없음, 설치본이 더 높음, 내용 같음을 판정한다.
- 그 계획이 돌려주는 값의 식별자는 121행에서 `claim_helper`로 박혀 있다. 조건 스크립트는
  `managed_project_assets.rs` 645행에서 그 값을 자기 식별자로 덮어 쓴다. 새 자산도 같은 자리에서
  덮어 써야 한다.
- `src-tauri/src/infrastructure/claim_helper.rs`가 자산 서술의 본보기다. 22행부터 이름과 접두사와
  버전 상수가 서고, 444행과 450행이 운영체제별 구현을 컴파일 시점에 고르고, 456행이 자산 상수를
  만든다. 두 구현 본문은 플랫폼과 무관하게 항상 컴파일된다.
- `src-tauri/src/infrastructure/managed_project_assets.rs` 617행의 사전 점검이 자산별 설치 계획을
  모은다. 632행이 선점 헬퍼, 643행이 조건 스크립트다. 866행부터의 잠금 경합 결과가 자산 목록을
  손으로 나열하고, 929행의 정렬 순서가 여덟 개의 식별자를 순서대로 들고 있다.
- `src-tauri/src/infrastructure/mod.rs`가 인프라 모듈을 나열한다. 새 모듈은 여기에 이름을 올려야
  컴파일에 들어간다.
- 설정 화면은 자산 목록을 받은 대로 훑어 그린다. `src/features/projects/components/SettingsView.tsx`
  227행이 자산 배열을 그대로 돌며 줄을 만들고, 표시 이름과 버전은 payload에 실려 온다.

## 변경 범위

새 모듈 `src-tauri/src/infrastructure/status_helper.rs`를 만들고 다음을 담는다.

- 확장자를 뺀 이름은 `wf-status`, 표시 이름은 `상태 조회 도구`, 버전 접두사는
  `# status_helper_version:`, 버전은 1이다.
- 셸 구현과 PowerShell 구현의 본문 상수를 둘 다 둔다. 현재 플랫폼 구현을 컴파일 시점에 고르는
  방식은 선점 헬퍼와 같다. PowerShell 본문은 바이트 순서 표시로 시작하고 셸 본문은 그렇지 않다.
- 자산 상수와, 컨트롤 루트를 받아 설치 경로를 돌려주는 함수를 둔다.

이 작업이 넣는 스크립트 본문은 호출 계약까지다.

- 호출은 프로젝트 루트에서 `sh .workflow/rules/wf-status.sh` 또는 `sh .workflow/rules/wf-status.sh
  --json`이다.
- 인자 없는 호출은 사람용 머리글을, `--json` 호출은 머리글만 담은 JSON 한 문서를 표준 출력에 낸다.
  머리글은 프로젝트 이름, 활성 워크플로의 이름과 id, 판정 시각(UTC), 마이그레이션 락이 걸려 있으면
  그 사실이다. 프로젝트 이름과 워크플로 목록은 `.workflow/project.yml`에서 읽는다.
- JSON 문서는 `schemaVersion`을 담고 값은 1이다.
- 종료 코드는 0 정상, 1 읽기 실패, 2 사용법 오류다. 알 수 없는 인자와 인자 둘 이상은 2다.
- 일감의 유무를 종료 코드에 싣지 않는다.
- 진단 문구는 표준 오류로 낸다.
- 파일을 만들거나 고치거나 지우지 않고, lease를 잡거나 갱신하지 않고, git을 부르지 않는다.

`mod.rs`에 새 모듈 이름을 올린다.

`managed_project_assets.rs`에 배선을 더한다.

- 617행의 사전 점검에 새 자산의 설치 계획을 더하고, 조건 스크립트와 같은 자리에서 식별자를
  `status_helper`로 덮어 쓴다.
- 계획 실패의 갈래는 조건 스크립트와 같은 함수를 그대로 쓴다.
- 866행부터의 잠금 경합 결과 목록에 새 자산을 더한다.
- 929행의 정렬 순서에 `status_helper`를 조건 스크립트 다음 자리로 더하고 배열 길이를 아홉으로 올린다.

## 범위 밖

출력의 다섯 묶음을 채우지 않는다. 진행 집계, 사용자 대기, 활성 선점, 최근 실패와 두 형식의 완성은
같은 그룹의 다음 작업이 맡는다.

조건 스크립트를 고치지 않는다. 상태 투영 출력은 같은 그룹의 다른 작업이 맡고, 이 작업의 머리글은
판정이 필요 없는 값만 담는다.

설치 규약을 고치지 않는다. `managed_script.rs`의 판정과 원자적 쓰기는 그대로 쓰고, 121행의 박힌
식별자도 그대로 둔다. 새 자산은 조건 스크립트와 같은 방식으로 경계에서 덮어 쓴다.

화면을 고치지 않는다. 설정 화면은 자산 배열을 받은 대로 그리므로 새 자산이 늘어도 코드가 바뀌지
않는다.

예약 헬퍼가 타는 프로젝트 저장소 설치 경로에는 손대지 않는다.

## 완료 조건

- C1. 프로젝트 컨트롤 루트에 자산이 설치되고, 파일 이름이 현재 플랫폼의 확장자를 따른다. 설치된
  본문의 머리에 관리 표기와 `# status_helper_version: 1` 줄이 있다.
- C2. 이미 같은 내용이 설치되어 있으면 파일을 다시 쓰지 않는다. 내용이 다르면 앱 본문으로 되돌린다.
- C3. 관리 표기가 없는 파일이 그 경로에 있으면 설치가 충돌로 끝나고 파일을 덮어쓰지 않는다.
  설치본 버전이 앱 상수보다 높으면 덮어쓰지 않는다.
- C4. 관리 자산 동기화 결과의 자산 목록에 `status_helper`가 표시 이름 `상태 조회 도구`와 함께
  들어 있고, 정렬 순서에서 조건 스크립트 다음에 온다.
- C5. 잠금 경합으로 동기화가 미뤄질 때의 자산 목록에도 같은 자산이 들어 있다.
- C6. 프로젝트 루트에서 인자 없이 부르면 종료 코드가 0이고, 표준 출력에 프로젝트 이름과 활성
  워크플로의 이름과 id와 판정 시각이 나온다.
- C7. `--json`으로 부르면 종료 코드가 0이고, 표준 출력 전체가 JSON 한 문서로 파싱되며
  `schemaVersion` 값이 1이다.
- C8. 알 수 없는 인자로 부르면 종료 코드가 2다. 인자를 둘 이상 붙여도 2다.
- C9. 마이그레이션 락이 있는 프로젝트에서도 두 호출이 0으로 끝나고, 머리글에 락이 걸린 사실이
  표시된다.
- C10. 명령 실행 전후로 프로젝트 디렉터리의 파일 목록과 각 파일 내용의 해시가 같다.
- C11. 두 구현의 버전 상수가 같고, PowerShell 본문이 바이트 순서 표시로 시작하며 셸 본문은 그렇지
  않음을 확인하는 시험이 있다.
- C12. 활성 워크플로가 둘인 픽스처에서 머리글이 두 워크플로를 모두, 서로 구분되게 낸다.

- C10은 실행 전후로 프로젝트 디렉터리를 훑어 경로 목록과 내용 해시를 모은 뒤 두 벌을 비교한다.

- `cd src-tauri && cargo clippy --all-targets -- -D warnings` 와 `cargo fmt --check` 를 돌린다.

## 범위 사전 검사

선언한 세 파일은 새 자산 모듈 하나, 모듈 나열 하나, 동기화 배선 하나다. 완료 조건을 채우는 데 이
밖의 편집이 필요한지 자산이 설치되고 목록에 실려 화면까지 가는 길을 따라가며 확인했다.

`src-tauri/src/infrastructure/managed_script.rs`를 열어 보고 뺐다. 117행의 설치 계획이 자산이
넘기는 이름과 접두사와 버전만으로 돌고, 새 자산에 필요한 판정이 이미 다 있다. 121행이 식별자를
`claim_helper`로 박아 두었지만 조건 스크립트가 645행에서 덮어 쓰는 길을 이미 냈으므로 같은 길을
쓴다. 여기를 고쳐 자산마다 식별자를 받게 만드는 편이 깨끗해 보이지만, 그러면 선점 헬퍼와 조건
스크립트의 배선까지 함께 흔들리고 이 기획이 요구하지 않은 변경이 된다.

`src-tauri/src/infrastructure/claim_helper.rs`를 열어 보고 뺐다. 자산 서술의 본보기로 읽었을 뿐이고,
새 자산은 자기 모듈에 선다. 선점 헬퍼의 본문과 버전은 이 작업과 무관하다.

`src-tauri/src/infrastructure/fs_project_repository.rs`를 열어 보고 뺐다. 1636행부터가 예약 헬퍼를
설치하고 검증하는 자리인데, 이 그룹은 관리 자산 동기화 경로를 골랐으므로 그 자리에 새 자산을 얹지
않는다. 동기화 자체는 369행이 이미 관리 자산 모듈에 넘기고 있어 배선이 필요 없다.

`src/features/projects/components/SettingsView.tsx`와 그 시험을 열어 보고 뺐다. 227행이 자산 배열을
받은 대로 돌며 줄을 만들고, 표시 이름과 설치·제공 버전은 payload에 실려 온다. 화면 시험이 자산
목록을 직접 만들어 넣는 방식이라 새 자산 때문에 깨지지 않는다. 검증 절차에서 그 사실을 실제로
확인한다.

`src/features/projects/domain/types.ts`를 열어 보고 뺐다. 자산 하나의 모양은 이미 식별자와 표시
이름과 두 버전과 사유를 담고 있고, 새 자산은 그 모양을 그대로 쓴다.

`src-tauri/src/infrastructure/heartbeat_condition.rs`를 열어 보고 뺐다. 이 작업은 조건 스크립트를
읽지도 부르지도 않는다. 같은 그룹의 다른 작업이 그 파일만 잡으므로 두 작업이 나란히 진행된다.

기계 상태를 조건으로 삼는 측정이 없으므로 이 작업은 조용한 기계를 요구하지 않는다. 같은 그룹의
마지막 작업이 새 자산 모듈을 이어서 채우므로 그쪽에 순서를 선언했고, 이 작업이 먼저다.

- 값 경로: C1과 C2와 C3의 설치 판정. 값을 만드는 자리는 새 모듈의 본문 상수와 버전 상수이고 선언
  안에 있다. 판정하는 자리는 `managed_script.rs` 117행이며 자산이 넘긴 값으로만 돌아 편집이 필요
  없다. 파일을 쓰는 자리는 같은 파일의 원자적 쓰기이고 역시 그대로다. 설치 경로를 조립하는 자리는
  자산 상수의 경로 함수이며 선언 안이다.
- 값 경로: C4와 C5의 자산 목록. 값을 만드는 자리는 `managed_project_assets.rs` 617행의 사전 점검이
  모으는 계획 목록이고 선언 안에 있다. 식별자를 자산별로 가르는 자리는 645행의 덮어쓰기와 같은
  모양으로 선언 안에 더한다. 목록을 정렬하는 자리는 929행이고 선언 안이다. 잠금 경합 결과를 따로
  세우는 자리는 866행부터이며 손으로 나열하는 목록이라 여기도 편집이 필요하고 선언 안이다. 그
  목록이 실려 나가는 자리는 `domain/project.rs`의 동기화 결과 구조체이고, 자산 하나의 모양이 이미
  식별자와 표시 이름과 두 버전을 담으므로 편집이 필요 없다. 화면이 받는 자리는 설정 화면 227행이며
  배열을 받은 대로 돌기 때문에 새 식별자가 늘어도 그대로 그린다.
- 값 경로: C6과 C7과 C12의 머리글. 값을 만드는 자리는 `.workflow/project.yml`의 프로젝트 이름과
  워크플로 등록 항목이고, 앱이 소유하는 파일이라 읽기만 한다. 읽는 자리와 형식을 만드는 자리는 새
  모듈의 스크립트 본문이며 선언 안에 있다. 판정 시각은 스크립트가 실행 시점에 만드는 값이라 다른
  홉이 없다. 활성 여부는 등록 항목에 그대로 적힌 값이므로 판정이 필요 없다.
- 값 경로: C9의 마이그레이션 락 표시. 값을 만드는 자리는 앱의 마이그레이션이고 락 파일이 그 자리에
  선다. 읽는 자리는 새 모듈의 스크립트 본문 한 곳뿐이며 선언 안에 있다. 조건 스크립트의 락 처리와
  달리 이 명령은 락을 만나도 계속 진행한다.
- 값 경로: C11의 버전과 바이트 순서 표시. 두 값 모두 새 모듈의 상수이고 시험도 같은 파일 안에 선다.
  선언 밖으로 나가는 홉이 없다.
