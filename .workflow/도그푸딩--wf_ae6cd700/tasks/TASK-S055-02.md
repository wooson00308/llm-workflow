# 사용자가 남긴 작업 정의 수정 요청을 앱 소유 기록으로 저장한다

## 결정권자 요약

### 제안

사용자가 잘못 분해된 작업을 지목해 이유와 함께 수정 요청을 남기면, 앱이 그 요청을 자기 소유 기록으로
한 번만 저장한다.

### 현재

잘못된 정의로 막힌 작업을 되살릴 공식 입구가 없다. 사용자가 상태만 되돌려도 같은 정의가 남아 같은
자리에서 다시 막히고, 무엇을 왜 고쳐 달라고 했는지는 어디에도 기록되지 않는다.

### 변경 후

막힌 작업과 아직 선점되지 않은 개발 준비 작업에 수정 요청을 남길 수 있다. 요청에는 작업 식별자와
사용자가 화면에서 본 갱신 시각과 요청 이유가 함께 남고, 저장 직전에 그 작업이 그대로인지 다시
확인한다. 요청을 저장하는 동안 작업 문서 자체는 바뀌지 않는다.

### 사용자 결과

수정이 필요하다고 판단한 순간에 이유를 남길 수 있고, 그 요청이 남았다는 사실과 시각을 나중에 그대로
확인할 수 있다.

### 영향 범위

- 변경: 수정 요청을 저장하는 앱 명령과 그 기록 형식, 작업 조회가 함께 돌려주는 요청 목록
- 유지: 작업 문서의 상태와 이력과 본문, 기획 승인과 품질 확인 기록의 뜻, 재개 조작과 그 감사 기록

### 비용과 위험

같은 작업에 미처리 요청이 이미 있으면 새 요청을 만들지 않는다. 사용자가 두 가지를 각각 요청하고 싶어도
앞 요청이 처리될 때까지 기다려야 한다.

### 결정 요청

품질 확인에서는 요청이 한 번만 남는지, 허용되지 않는 상태와 오래된 화면과 잠금에서 아무 파일도 바뀌지
않는지를 자동 검사 수치로 확인한다.

## 확인 동선

이 작업에는 눈으로 볼 화면이 없다. 요청을 남기는 화면 조작은 이 승인의 다른 작업이고, 여기서 만든 것은
저장 명령과 기록 형식과 조회 값이라 자동 검사가 그 판정을 대조한다. 확인 도장은 아래 수치를 신뢰한다는
뜻이다.

- `cargo test --manifest-path src-tauri/Cargo.toml` → 629 passed, 0 failed
- `npm run check` → 타입 검사 통과, 25개 파일 851 tests 통과, 배포 빌드 성공
- `cargo clippy --all-targets` 경고 없음, `cargo fmt` 적용

수치 대신 동작을 직접 보고 싶다면 임시 프로젝트에서 개발용 호출로 재현할 수 있다. 화면이 아직 없으므로
명령을 직접 부른다.

1. `.workflow/<워크플로우>/tasks/`에 `status: blocked`인 작업 문서를 두고, 그 문서의 `updated_at` 값과
   비어 있지 않은 이유, 임의의 요청 식별자로 `record_task_revision_request`를 호출한다.
2. `decisions/REVISION-XXXXXXXX.md`가 한 건 생기고 `task_id`, `request_id`, `previous_updated_at`,
   `created_by: user`, `created_at`이 들어 있으며 본문에 입력한 이유가 그대로 있다. 작업 문서는 한 글자도
   바뀌지 않는다.
3. 같은 요청 식별자로 다시 호출하면 성공을 다시 받지만 요청 문서는 한 건 그대로다. 다른 요청 식별자로
   호출하면 앞 요청이 아직 처리되지 않았으므로 새 문서를 만들지 않고 그 요청을 돌려준다.
4. 작업 상태를 `in_progress`나 `qa_waiting`이나 `completed`로 바꾸거나,
   `.workflow/.runtime/leases/TASK-XXX.yml`에 미만료 lease를 두거나,
   `.workflow/.runtime/migration.lock`을 만들거나, `updated_at`을 다른 값으로 보내면 거절되고 `tasks/`와
   `decisions/`의 파일 내용이 호출 전과 같다.
5. 작업 문서 프론트매터에 `revision_request_id: REVISION-XXXXXXXX`를 넣고 작업을 다시 조회하면 그 요청이
   처리 완료로 읽히고, 미처리 요청이 없어졌으므로 다음 요청을 다시 받을 수 있다.

## 목적

SPEC-055의 R2, R3, R10과 R6의 기록 측면을 구현한다. 사용자만 만들 수 있는 작업 정의 수정 요청을 앱
소유 기록으로 저장하고, 그 기록을 작업 조회 결과에 함께 실어 화면과 자격 판정이 읽을 수 있게 한다.
아키텍트가 그 요청을 처리하는 경로와 화면은 이 작업의 범위가 아니다.

## 범위 사전 검사

- 앱이 자기 소유 기록을 쓰는 기존 경로가 둘 있다. 품질 확인 결정과 막힌 작업 재개 감사 기록이며 둘 다
  `fs_project_repository.rs`에 있고 결정 디렉터리에 문서를 만든다. 새 기록도 같은 자리와 같은 방식을
  따르므로 새 저장소나 새 디렉터리를 만들지 않는다.
- 재개 감사 기록이 프로젝트 쓰기 잠금 아래에서 대상 문서를 다시 읽어 상태와 갱신 시각과 선점을 차례로
  판정하는 형태를 이미 갖고 있다. 이번 요청 저장도 같은 판정 순서를 쓰되 작업 문서는 쓰지 않는다.
- 작업 조회 결과 구조는 `domain/project.rs`에 있고 화면이 그 값을 그대로 읽는다. 요청 목록을 실으려면
  이 구조와 명령 계층과 실행기 등록이 함께 움직이므로 네 파일이 범위에 들어 있다.
- 사용자 문서에 기록 형식을 적어야 하므로 그 파일도 범위에 있다. 규칙 본문은 앞 작업이 정의하므로 이
  작업에서 고치지 않는다.
- 읽기만 하고 고치지 않는 파일이 하나 있다. 규칙 본문의 정본은 앞 작업이 확정하며 이 작업은 그 문언에
  맞춰 구현만 한다.
- 같은 네 파일을 범위로 가진 미완료 작업은 이 승인에서 파생된 앞 작업뿐이고 선행으로 선언돼 있다.

## 변경 범위

### 기록 형식

- 결정 디렉터리에 작업 정의 수정 요청 문서를 만든다. 문서는 고유 식별자와 대상 작업 식별자와 사용자가
  확인한 기준 갱신 시각과 생성 시각을 갖고, 작성자 값은 사용자다. 요청 이유는 본문에 그대로 남긴다.
- 기존 품질 확인 결정과 재개 감사 기록과 다른 스키마 이름을 쓴다. 세 기록이 서로의 뜻을 빌리지 않는다.
- 요청 문서는 추가 전용이다. 처리된 뒤에도 지우거나 다시 쓰지 않는다.

### 저장 판정

- 요청을 만들 수 있는 상태는 막힘과, 활성 선점이 없는 개발 준비 두 가지뿐이다. 진행 중과 품질 확인
  대기와 완료 상태는 거절한다.
- 저장 직전에 프로젝트 쓰기 잠금 아래에서 대상 문서를 다시 읽어 상태와 갱신 시각이 사용자가 확인한
  값과 같은지, 선점이 여전히 없는지 확인한다. 마이그레이션 잠금 중에는 아무것도 쓰지 않는다.
- 같은 대상에 아직 처리되지 않은 요청이 이미 있으면 새 문서를 만들지 않고 현재 상태를 돌려준다.
- 요청 이유가 비어 있으면 거절한다.
- 이 명령은 작업 문서를 쓰지 않는다. 요청 문서 한 건만 만들거나 아무것도 만들지 않는다.
- 같은 요청 식별자로 다시 호출하거나 응답을 잃고 재시도해도 문서는 한 건만 남는다.

### 조회

- 작업 조회 결과에 그 작업의 수정 요청 목록을 생성 시각 순서로 싣는다. 각 항목은 요청 식별자와 기준
  갱신 시각과 이유와 생성 시각을 갖는다.
- 작업 문서가 처리한 요청 식별자를 연결하고 있으면 그 요청은 처리 완료로 읽는다. 연결이 없으면
  미처리로 읽는다. 앱은 처리 여부를 다른 근거로 추측하지 않는다.
- 형식이 어긋난 요청 문서 하나가 조회 전체를 실패시키지 않는다. 그 문서만 건너뛴다.

### 사용자 문서

- 기록 형식과 저장 판정과 처리 완료 판정을 사용자 문서에 적는다. 기존 결정 기록 설명과 나란히 두어 셋이
  서로 다른 기록임을 읽을 수 있게 한다.

## 손대지 않는 것

- 작업 문서의 상태와 이력과 본문
- 아키텍트가 요청을 처리하는 경로와 자격 판정
- 막힌 작업 재개 조작과 그 감사 기록
- 기획 승인과 품질 확인 결정의 뜻과 앱 소유권
- 앱 화면
- 앱이 설치하는 규칙 문언과 규칙 버전

## 완료 조건

1. 막힘 상태와, 선점이 없는 개발 준비 상태의 작업에 비어 있지 않은 이유로 요청하면 대상 작업 식별자와
   기준 갱신 시각과 이유와 생성 시각과 사용자 작성자 값을 가진 앱 소유 기록이 한 건 남는다.
2. 진행 중과 품질 확인 대기와 완료 상태의 작업, 활성 선점이 있는 작업, 마이그레이션 잠금 중에는 요청이
   기록되지 않고 어떤 파일도 바뀌지 않는다.
3. 사용자가 확인한 갱신 시각이 현재 문서와 다르면 아무것도 쓰지 않고 최신 상태를 돌려준다.
4. 같은 대상에 미처리 요청이 이미 있으면 두 번째 요청 문서를 만들지 않는다.
5. 이유가 비어 있는 요청은 거절되고 파일이 만들어지지 않는다.
6. 요청 저장은 작업 문서를 바꾸지 않는다. 요청 문서만 남거나 아무것도 남지 않으며 둘 다 아닌 중간
   결과가 성공으로 보고되지 않는다.
7. 같은 요청을 직렬로 반복하거나 동시에 두 번 보내도 기록은 한 건이다.
8. 작업 조회가 그 작업의 요청 목록을 생성 순서로 돌려주고, 작업이 연결한 요청 식별자를 근거로 처리
   완료와 미처리를 구분한다.
9. 형식이 어긋난 요청 문서가 있어도 조회 전체가 실패하지 않고 그 문서만 건너뛴다.
10. 새 기록의 스키마 이름이 품질 확인 결정과 재개 감사 기록 어느 쪽과도 겹치지 않으며, 세 기록이 서로의
    판정에 섞이지 않는다.
11. 요청 기록과 연결 필드가 없는 기존 프로젝트가 마이그레이션 없이 그대로 읽힌다.
12. 기존 품질 확인 기록과 재개 기록과 기획 결정 판정 검사가 변경 전과 같이 통과한다.
13. 기존 자동 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. `cargo test --manifest-path src-tauri/Cargo.toml`을 실행한다.
2. 다섯 가지 상태와 선점 있음과 마이그레이션 잠금과 오래된 갱신 시각 픽스처로 저장 판정을 표로 검사하고,
   거절된 경우 작업과 결정 디렉터리의 원문이 그대로인지 확인한다.
3. 같은 요청을 직렬로 두 번, 그리고 동시에 두 번 보내 기록이 한 건인지 확인한다.
4. 미처리 요청이 있는 대상에 두 번째 요청을 보내 거절되는지 확인한다.
5. 연결 필드가 있는 작업과 없는 작업으로 처리 완료와 미처리 구분을 대조한다.
6. 형식이 어긋난 요청 문서를 섞어 조회가 그 문서만 건너뛰는지 확인한다.
7. 요청 기록이 없는 기존 프로젝트 픽스처로 조회와 기존 결정 판정이 변하지 않는지 확인한다.

## 범위와 선행

앞 작업이 규칙 문언에서 기록의 소유권과 연결 필드를 정의하므로 그 작업이 선행한다. 같은 두 파일이
겹치는 것도 그 작업과의 관계다.

이 작업은 요청을 만드는 쪽만 담당한다. 요청을 아키텍트 자격 대상으로 삼는 판정과 화면 조작은 이 승인의
다른 두 작업이 맡으며 둘 다 이 작업 뒤에 온다.

명령 등록 파일은 앱의 모든 백엔드 기능이 함께 쓰는 자리라 다른 승인의 미완료 작업 셋과도 겹친다. 이
겹침에는 어느 쪽이 먼저여야 할 이유가 없으므로 선행 관계를 선언하지 않는다. 선언 범위가 겹치는 두 작업을
같은 시각에 시작하지 않게 하는 것이 이 경우의 안전장치이며, 그 판정은 선점 시점에 이루어진다.
