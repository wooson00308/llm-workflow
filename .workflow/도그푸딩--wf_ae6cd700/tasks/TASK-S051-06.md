# 앱이 호환 런타임 설치와 업데이트를 안전하게 관리한다

## 결정권자 요약

신규 사용자는 터미널 명령 없이 앱에서 호환 런타임을 설치하고 서비스를 시작할 수 있다.
현재 런타임 계약에 설치 판단에 필요한 서비스와 실행 상태 정보가 없어 구현을 진행할 수 없다.
앱은 설치된 버전과 실행 중 버전을 구분하고 호환되지 않으면 실행을 막는다.
업데이트 전에 영향을 받을 실행을 보여주며 사용자가 확인한 뒤에만 전환한다.
검증이나 설치가 실패하면 현재 동작하는 버전과 서비스는 그대로 유지된다.
세 운영체제의 앱 배포물은 자기 플랫폼에 맞는 런타임을 함께 제공한다.

## 목적

TASK-S051-05의 target별 독립 실행형 배포물을 Tauri 앱이 소유하는 설치·업데이트·복구 흐름에 연결한다.
이 작업은 백엔드 명령과 배포 자산만 만들고 실제 화면은 후속 작업에서 구현한다.

## 설치 경계

- 앱 번들은 현재 target의 런타임 압축물과 manifest를 resource로 포함한다. 다른 target의 배포물을
  포함하지 않는다.
- 앱은 resource를 앱 데이터의 버전 디렉터리에 풀고 모든 해시와 API major를 검증한 뒤 stable
  launcher를 전환한다.
- 경로는 운영체제 표준 앱 데이터 디렉터리에서 Tauri가 해석한다. 환경 변수나 사용자 입력으로 설치
  루트를 조립하지 않는다.
- 설치·업데이트·복구 명령은 고정된 runtime CLI 인자와 JSON 표준 입력만 사용한다. 셸을 거치지 않고
  화면이 보낸 문자열을 명령줄로 이어 붙이지 않는다.

## 백엔드 계약

1. inspect: 번들 버전, 디스크 설치 버전, 실행 중 버전, API 호환성, 서비스 상태, 복구 가능 여부를
   구분해 반환한다.
2. plan_install: 생성·교체할 경로와 서비스 변경, 기존 설치 마이그레이션 미리보기, 실행 중 작업 수,
   중단 위험을 반환하며 아무것도 쓰지 않는다.
3. apply_install: 직전 plan의 식별자와 사용자 확인을 받아 설치한다. 상태가 달라진 오래된 plan은
   거절한다.
4. plan_update와 apply_update: 설치와 같은 두 단계 구조를 사용한다. 실행 중 작업이 있으면 자동으로
   종료하지 않고 영향과 선택지를 반환한다.
5. repair: manifest는 정상인데 launcher나 서비스 등록만 어긋난 경우에 한해 복구한다. 데이터베이스를
   지우거나 새로 만들지 않는다.
6. 모든 결과는 성공, 부분 성공, 실패 단계, 실제 적용 버전을 구조화해 반환한다.

## 호환성 규칙

- 앱은 지원하는 runtime API major와 최소·최대 버전을 상수 한 곳에서 가진다.
- 설치 버전과 실행 중 버전을 따로 조회한다. 디스크만 새 버전인 상태를 정상으로 표시하지 않는다.
- API major가 다르거나 지원 범위를 벗어나면 설정·실행 명령을 막고 필요한 앱 또는 런타임 버전과
  업데이트 방법을 반환한다.
- Dream의 설치 여부는 호환성 판단에 사용하지 않는다.
- 기존 `update_heartbeat`의 editable checkout 갱신은 레거시 고급 관리로 남길 수 있지만 새 에이전트
  설치·업데이트의 정상 경로로 호출하지 않는다.

## 손대지 않는 것

- 프로젝트 역할 설정과 실행 큐
- provider 진단과 실행
- 에이전트 화면
- Dream 설치·업데이트 UI와 기존 데이터
- 사용자 확인 없는 자동 서비스 재시작

## 완료 조건

1. macOS·Linux·Windows 앱 번들이 자기 target의 런타임 resource와 manifest를 포함한다.
2. Python과 checkout이 없는 환경에서 앱 백엔드만으로 런타임 설치와 서비스 시작을 완료한다.
3. install·update 계획 조회는 파일, launcher, 서비스, 데이터베이스를 변경하지 않는다.
4. 사용자 확인과 최신 plan 식별자 없이 적용 명령을 호출하면 아무것도 바뀌지 않는다.
5. 해시 불일치, target 불일치, API major 불일치, 지원 범위 밖 버전은 stable launcher 전환 전에
   실패한다.
6. 설치 중 실패해도 이전 launcher와 서비스가 계속 동작하고 임시 디렉터리가 정리된다.
7. 설치된 버전과 실행 중 버전이 다르면 호환으로 표시하지 않고 재시작 또는 복구 행동을 안내한다.
8. 실행 중 작업이 있는 업데이트는 그 수와 프로젝트를 계획에 포함하고 자동으로 종료하지 않는다.
9. repair는 launcher와 서비스만 복구하며 프로젝트 설정·큐·이력 데이터베이스를 지우지 않는다.
10. 호환되지 않는 런타임에서는 설정·시작 명령이 provider를 실행하기 전에 막힌다.
11. Dream 미설치 상태에서도 새 런타임 설치·업데이트가 성공한다.
12. 기존 설치·업데이트·서비스 제어 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. 임시 app data와 가짜 Tauri resource에서 설치 계획, 적용, 재조회, 업데이트, 되돌리기 경로를 검사한다.
2. 압축물 변조, manifest 변조, 다른 target, 호환 불가 API, 쓰기 권한 실패를 주입해 이전 버전 보존을
   확인한다.
3. 실행 중 작업이 있는 상태와 없는 상태의 update plan을 비교하고 적용 전 프로세스 수가 변하지
   않는지 확인한다.
4. launcher 손상과 서비스 등록 손상을 각각 복구하고 데이터베이스 해시가 바뀌지 않는지 확인한다.
5. release workflow의 세 target 산출물에 올바른 runtime resource가 한 개씩 포함되는지 확인한다.
6. `cargo test --manifest-path src-tauri/Cargo.toml`을 macOS·Linux·Windows에서 실행한다.
7. `npm run check`를 실행한다.

겹치므로 예약 도구 등록이 완료된 뒤 이 작업의 모듈을 추가한다.
