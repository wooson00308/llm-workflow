# 앱이 호환 런타임 설치와 업데이트를 안전하게 관리한다

## 결정권자 요약

설치 계획은 기존 서비스, 미등록, 확인 불가를 구분하고 적용할 처리 방법을 화면에 보여 준다.
사용자는 적용 전에 서비스 label·실행 경로·등록·실행 상태와 기존 등록 보존 여부를 확인한다.
다른 기존 서비스는 삭제·중지·덮어쓰기·중복 등록하지 않고 이전 미리보기를 안전한 다음 행동으로 안내한다.
확인 불가 상태도 등록 불필요로 접지 않으며 서비스 변경 없이 새 계획이 필요하다고 알린다.
계획 뒤 서비스 신원이 바뀌면 파일을 쓰기 전에 오래된 계획을 거절한다.
오류 설명이 stdout에만 있어도 빈 문구 대신 원문을 보여 준다.
전체 자동검사와 격리된 최신 앱의 실제 설치 계획 확인까지 통과해 사용자 QA를 기다린다.

## 막힌 사유

- 막힌 지점: QA-196CE251은 기존 서비스의 신원·처리 방법과 안전한 복구를 계획 화면에서 확인할 수 있어야 하지만, `AgentInstallPlan`과 `AgentRuntimeView`는 새 백엔드 값을 버리고 `serviceTransitionRequired` 한 값만 표시한다. 동시에 이 작업의 `손대지 않는 것`은 에이전트 화면을 금지하고 화면·타입·검사 파일은 `scope_files` 밖이다.
- 필요한 해결: `src/features/projects/domain/types.ts`, `src/features/projects/components/agents/AgentRuntimeView.tsx`, `src/features/projects/components/agents/AgentRuntimeView.test.tsx`를 최소 범위에 넣고, 설치 계획에서 서비스 상태·처분·기존 등록 보존·다음 안전 행동을 적용 전에 표시하도록 완료 조건과 손대지 않는 범위를 교정한다.
- 재개 조건: 아키텍트가 위 세 경로와 화면 경계를 작업 정의에 반영해 `todo`로 돌리면 개발자가 같은 백엔드 구현 위에서 화면과 회귀검사를 완성한다. 사용자 입력이나 수동 재개는 필요 없다.
- 관련 대상: QA-196CE251, TASK-S051-06, AgentInstallPlan, AgentRuntimeView

## 목적

TASK-S051-05의 target별 독립 실행형 배포물을 Tauri 앱이 소유하는 설치·업데이트·복구 흐름에 연결한다.
이 작업은 백엔드 명령과 배포 자산만 만들고 실제 화면은 후속 작업에서 구현한다.

## 런타임에서 받는 사실

앱은 아래 사실을 런타임의 버전화된 JSON 응답에서만 읽는다. TASK-147이 이 계약을 제공하며, 이 작업은
받은 값을 앱의 백엔드 명령으로 옮기기만 한다. 계약에 없는 값은 추측하지 않고 모름으로 표시한다.

### 기기 조회에서 받는 값

- 설치된 런타임 버전, 실제 실행 중 버전, API 주 버전, target.
- 서비스의 등록 여부, 실행 여부, 운영체제가 아는 식별자, 실제 실행 경로, 마지막 확인 시각, 복구 가능
  여부, 그 판정의 확인 출처.
- 확인한 값, 확인하지 못한 값, 권한 때문에 확인할 수 없는 값이 서로 구분돼 온다. 오래된 PID나 마지막
  시작 기록만으로 실행 중이라고 오지 않으므로 앱도 그렇게 해석하지 않는다.
- 등록 없음, 실행 파일 없음, 등록이 여러 개라 모호함, 권한 부족, 지원하지 않는 플랫폼·버전이 서로 다른
  코드와 단계로 구분돼 온다.

### 업데이트 계획에서 받는 값

- 대상 버전과 target, manifest 검증 결과, launcher 전환 필요 여부, 서비스 재시작·재등록 필요 여부,
  실패 시 복구 가능성.
- 현재 실행 중인 작업 수와 중복 없는 프로젝트 식별자 목록. 앱이 이 수를 따로 세지 않는다.
- 계획 식별자. 대상 manifest, 현재 설치·실행 버전, 서비스 신원, 영향 실행 스냅샷을 묶은 지문이며 앱은
  이 값을 그대로 보관했다가 적용 요청에 실어 보낸다.
- 계획 조회는 런타임 쪽에서도 아무것도 쓰지 않는다.

### 적용 결과에서 받는 값

- manifest 검증, 새 버전 설치, stable launcher 전환, 서비스 재시작 또는 재등록, 실행 버전 확인의
  단계별 결과. 앱은 이 단계 이름을 그대로 쓰고 새 이름을 만들지 않는다.
- 지문이 달라졌으면 어떤 단계도 수행하지 않고 새 계획이 필요하다는 결과가 온다.
- 부분 실패일 때 현재 실행 가능한 버전, 성공·실패 단계, 사용자가 수행할 복구 행동이 함께 온다.
- 세 운영체제가 같은 상태, 단계, 오류 코드를 쓴다. 플랫폼 고유 이름은 선택적 진단 세부 정보에만 있다.

### 앱이 스스로 가지는 것

- 앱 번들 resource의 압축물과 manifest, 그 해시 검증, 앱 데이터 버전 디렉터리로 푸는 절차.
- 앱이 지원하는 runtime API major와 최소·최대 버전 상수.
- 사용자 확인 절차와 plan 식별자의 보관·대조.

## 설치 경계

- 앱 번들은 현재 target의 런타임 압축물과 manifest를 resource로 포함한다. 다른 target의 배포물을
  포함하지 않는다.
- 앱은 resource를 앱 데이터의 버전 디렉터리에 풀고 모든 해시와 API major를 검증한 뒤 stable
  launcher를 전환한다.
- 경로는 운영체제 표준 앱 데이터 디렉터리에서 Tauri가 해석한다. 환경 변수나 사용자 입력으로 설치
  루트를 조립하지 않는다.
- 설치·업데이트·복구 명령은 고정된 runtime CLI 인자와 JSON 표준 입력만 사용한다. 셸을 거치지 않고
  화면이 보낸 문자열을 명령줄로 이어 붙이지 않는다.

## 백엔드 계약

1. inspect: 번들 버전, 디스크 설치 버전, 실행 중 버전, API 호환성, 서비스 상태, 복구 가능 여부를
   구분해 반환한다.
2. plan_install: 생성·교체할 경로, 서비스의 등록·실행·신원, `register`, `already_managed`,
   `migration_required`, `unknown` 처리 방법과 기존 설치 마이그레이션 미리보기를 반환하며 아무것도
   쓰지 않는다. 화면은 이 값을 적용 확인 전에 그대로 보여 준다.
3. apply_install: 직전 plan의 식별자와 사용자 확인을 받아 설치한다. 상태가 달라진 오래된 plan은
   거절한다.
4. plan_update와 apply_update: 설치와 같은 두 단계 구조를 사용한다. 실행 중 작업이 있으면 자동으로
   종료하지 않고 영향과 선택지를 반환한다.
5. repair: manifest는 정상인데 launcher나 서비스 등록만 어긋난 경우에 한해 복구한다. 데이터베이스를
   지우거나 새로 만들지 않는다.
6. 모든 결과는 성공, 부분 성공, 실패 단계, 실제 적용 버전을 구조화해 반환한다.

## 호환성 규칙

- 앱은 지원하는 runtime API major와 최소·최대 버전을 상수 한 곳에서 가진다.
- 설치 버전과 실행 중 버전을 따로 조회한다. 디스크만 새 버전인 상태를 정상으로 표시하지 않는다.
- API major가 다르거나 지원 범위를 벗어나면 설정·실행 명령을 막고 필요한 앱 또는 런타임 버전과
  업데이트 방법을 반환한다.
- Dream의 설치 여부는 호환성 판단에 사용하지 않는다.
- 기존 `update_heartbeat`의 editable checkout 갱신은 레거시 고급 관리로 남길 수 있지만 새 에이전트
  설치·업데이트의 정상 경로로 호출하지 않는다.

## 손대지 않는 것

- 프로젝트 역할 설정과 실행 큐
- provider 진단과 실행
- 역할 정책·실행 큐 등 설치 계획과 적용 결과 안내 밖의 에이전트 화면
- Dream 설치·업데이트 UI와 기존 데이터
- 사용자 확인 없는 자동 서비스 재시작

## 완료 조건

1. macOS·Linux·Windows 앱 번들이 자기 target의 런타임 resource와 manifest를 포함한다.
2. Python과 checkout이 없는 환경에서 앱 백엔드만으로 런타임 설치와 서비스 시작을 완료한다.
3. install·update 계획 조회는 파일, launcher, 서비스, 데이터베이스를 변경하지 않는다.
4. 사용자 확인과 최신 plan 식별자 없이 적용 명령을 호출하면 아무것도 바뀌지 않는다.
5. 해시 불일치, target 불일치, API major 불일치, 지원 범위 밖 버전은 stable launcher 전환 전에
   실패한다.
6. 설치 중 실패해도 이전 launcher와 서비스가 계속 동작하고 임시 디렉터리가 정리된다.
7. 설치된 버전과 실행 중 버전이 다르면 호환으로 표시하지 않고 재시작 또는 복구 행동을 안내한다.
8. 실행 중 작업이 있는 업데이트는 그 수와 프로젝트를 계획에 포함하고 자동으로 종료하지 않는다.
9. repair는 launcher와 서비스만 복구하며 프로젝트 설정·큐·이력 데이터베이스를 지우지 않는다.
10. 호환되지 않는 런타임에서는 설정·시작 명령이 provider를 실행하기 전에 막힌다.
11. Dream 미설치 상태에서도 새 런타임 설치·업데이트가 성공한다.
12. 기존 설치·업데이트·서비스 제어 검사를 삭제하거나 약화하지 않는다.
13. 앱은 설치 버전, 실행 중 버전, 서비스 등록·실행 상태, 복구 가능 여부를 런타임 조회 응답의 필드에서만
    읽는다. SQLite, launcher 파일, launchd plist, systemd unit, Task Scheduler 출력을 직접 파싱하는
    경로가 없다.
14. 업데이트 계획의 실행 중 작업 수와 프로젝트 목록은 런타임 계획 응답에서 온다. 앱이 같은 수를 따로
    세거나 다른 값으로 덮어쓰지 않는다.
15. 런타임이 확인 불가나 권한 부족을 반환하면 앱은 실행 중으로 추측하지 않고 그 구분을 그대로 유지해
    반환한다.
16. 런타임 응답의 API 주 버전이 앱의 지원 범위 밖이면 설치·업데이트 적용 명령이 파일을 바꾸기 전에
    막힌다.
17. 적용 결과의 단계 이름과 부분 실패 표현은 런타임 계약의 단계를 그대로 사용한다. 앱이 새 단계 이름을
    만들거나 여러 단계를 하나로 합치지 않는다.
18. 설치 계획은 등록 없음, 앱 관리 서비스, 다른 기존 서비스, 확인 불가를 서로 다른 처리 방법으로
    반환하고 서비스 label·실행 경로·등록·실행 상태와 함께 적용 확인 화면에 표시한다.
19. 적용은 계획에 표시한 처리만 실행한다. 다른 기존 서비스와 확인 불가 상태에서는 서비스 등록 명령을
    호출하지 않고 기존 등록을 삭제·중지·덮어쓰지 않으며, 화면에 보존 사실과 이전 미리보기 또는 새 계획
    같은 안전한 다음 행동을 안내한다.
20. 계획 뒤 서비스 신원이나 상태가 달라지면 버전 파일을 쓰기 전에 오래된 계획을 거절하고, 런타임 실패
    설명이 stderr 없이 stdout에만 있어도 화면에 빈 문자열 대신 원문을 남긴다.

## 검증 절차

1. 임시 app data와 가짜 Tauri resource에서 설치 계획, 적용, 재조회, 업데이트, 되돌리기 경로를 검사한다.
2. 압축물 변조, manifest 변조, 다른 target, 호환 불가 API, 쓰기 권한 실패를 주입해 이전 버전 보존을
   확인한다.
3. 실행 중 작업이 있는 상태와 없는 상태의 update plan을 비교하고 적용 전 프로세스 수가 변하지
   않는지 확인한다.
4. launcher 손상과 서비스 등록 손상을 각각 복구하고 데이터베이스 해시가 바뀌지 않는지 확인한다.
5. release workflow의 세 target 산출물에 올바른 runtime resource가 한 개씩 포함되는지 확인한다.
6. 런타임 조회와 계획 응답을 흉내 내는 가짜 실행 파일로 등록 없음, 정상 실행, 확인 불가, 권한 부족,
   중복 등록, 지원 범위 밖 API 주 버전을 각각 주입해 앱이 그 구분을 유지하는지 확인한다.
7. 앱 백엔드 코드를 검색해 launcher 파일, plist, unit 파일, Task Scheduler 출력, 런타임 데이터베이스를
   직접 읽는 경로가 없음을 확인한다.
8. `cargo test --manifest-path src-tauri/Cargo.toml`을 macOS·Linux·Windows에서 실행한다.
9. `npm run check`를 실행한다.
10. 설치 계획 화면 검사에 다른 기존 서비스와 확인 불가 픽스처를 넣어 서비스 신원·처리 방법·보존 안내가
    적용 전에 보이고, 등록 없음만 실제 등록 호출로 이어지는지 확인한다.

    외부·확인 불가 서비스에서는 `install-service`가 호출되지 않는지 확인한다.

## 범위와 선행

TASK-S051-05가 독립 실행형 배포물과 세 운영체제 서비스 기반을 먼저 제공한다. 그 위에서 TASK-147이
기기 단위 조회, 업데이트 계획과 단계별 적용 결과를 버전화된 JSON으로 제공하며, 이 작업은 그 응답을
앱 백엔드 명령으로 옮긴다. 따라서 두 작업이 모두 선행한다.

TASK-S051-01과 `infrastructure/mod.rs`가 겹치므로 예약 도구 등록이 완료된 뒤 이 작업의 모듈을 추가한다.
TASK-S051-05는 사용자 품질 확인에서 기계 판독용 조회 명령을 추가하라는 수정 요청을 받아 다시 개발 대기
상태다. 그 재작업이 만드는 조회와 TASK-147의 기기 계약이 서로 다른 두 명령으로 갈라지면 이 작업이
어느 쪽을 읽어야 할지 정할 수 없으므로, 앱은 TASK-147이 확정한 계약 하나만 사용한다.

## 범위 사전 검사

QA-196CE251의 설치 계획 값이 만들어지는 곳부터 사용자 확인 화면까지 현재 코드를 다시 추적했다.
`AgentRuntimeView`는 기존에 계획과 적용 결과, 이전 미리보기 진입점을 모두 렌더하므로 별도 상위 조립이나
gateway 수정은 필요 없다. CSS도 기존 계획 정의 목록과 안내 문단을 재사용할 수 있어 범위에서 제외했다.

- 값 경로: 완료 조건 18의 서비스 상태·처분은 `agent_runtime_install_service.rs`의 `InstallPlan`과
  `plan_install`에서 생성하도록 편집하고, Tauri invoke가 JSON을 그대로 운반하므로 gateway는 무편집,
  `types.ts`의 `AgentInstallPlan`을 편집해 받은 뒤 `AgentRuntimeView.tsx`에서 표시하며 두 테스트 파일의
  픽스처와 화면 단언을 편집한다.
- 값 경로: 완료 조건 19의 보존·다음 행동은 `apply_install`의 `service_transition` 세부 결과에서 생성해
  기존 workspace state와 `AgentRuntimeView` 결과 목록이 이미 `detail`을 그대로 운반·표시하므로 중간
  application 파일은 무편집이다. 계획 전 안내는 같은 view에서 `serviceAction`과 `service`로 만든다.
- 값 경로: 완료 조건 20의 오래된 계획 거절은 설치 서비스의 fingerprint와 적용 전 조회에서 끝나고,
  stdout 실패 원문은 `agent_runtime_process.rs`의 `RuntimeCallFailure::message`에서 기존 command 오류 문자열
  경로를 그대로 지나 화면에 도달한다. 새 payload나 상위 callback은 필요 없다.

## 확인 동선

이번 QA는 실제 서비스에 적용하지 않고, 같은 코드와 런타임을 별도 앱 식별자에 묶은 격리 번들에서
설치 계획까지만 확인한다. 정상 최신 앱은 현재 에이전트 화면에 열어 두었다.

1. `src-tauri/target/debug/bundle/macos/LLM Workflow QA.app`을 열고 최근 프로젝트
   `workflow-labs` → 좌측 `에이전트` → `설치 계획 보기`를 누른다.
2. 설치 계획에 아래 값이 모두 보이면 정상이다.
   - 서비스 전환: `필요함`
   - 처리 방법: `기존 서비스 이전 필요`
   - 서비스 신원: `com.catze.dream-heartbeat`와 실제 Python 실행 경로
   - 등록 / 실행: `예 / 아니요`
3. 같은 계획의 안내에 기존 서비스를 그대로 유지하고 런타임 파일과 launcher만 놓으며,
   `삭제·중지·덮어쓰기·중복 등록하지 않습니다`와 `기존 역할 잡 이전` 미리보기가 명시돼야 한다.
4. `이 계획을 적용`은 누르지 않는다. 외부·확인 불가 서비스에서 등록 명령을 호출하지 않는 경계와
   미등록만 한 번 등록하는 경계는 자동검사로 확인했다.
5. 자동검사 결과는 Rust 라이브러리 709건, 런타임 종단 17건, 프런트 28파일 906건이며 typecheck,
   production build, `cargo fmt --check`, Clippy 경고 0건도 통과했다.

격리 앱은 `com.workflowlabs.desktop.qa` 데이터 루트를 사용하므로 정상 앱의 설치본과 설정을 바꾸지 않는다.
실기기 확인에서도 설치 계획 생성만 수행했고 기존 서비스에는 변경 명령을 보내지 않았다.
