# 한도 도달로 끝난 실행을 구분해 받고 실행 도구 단위 보류 기록을 남긴다

## 결정권자 요약

### 제안

실행 도구의 계정 사용 한도에 걸려 끝난 실행이 실행 기록에 실려 오면, 그 사실과 다시 시작할 시각을
기기 단위 기록으로 남긴다.

### 현재

한도로 끝난 실행이 와도 앱은 그것을 일반 실패와 똑같이 다룬다. 어느 실행 도구가 지금 쓸 수 없는
상태인지, 언제 다시 쓸 수 있는지를 앱 안 어디에도 적어 두지 않는다. 그래서 배정을 멈출 근거도,
화면에 보여줄 근거도 없다.

### 변경 후

한도로 끝난 실행이 확인되면 어느 실행 도구의 한도인지와 언제 다시 시작하는지가 기록으로 남는다.
해제 예정 시각이 함께 오면 그 시각을 쓰고, 오지 않으면 1시간 뒤를 쓰되 두 경우를 기록에서 구별해
둔다. 그 기록은 사용자 홈 아래 기기 단위 자리에 있어, 같은 실행 도구를 쓰는 다른 프로젝트도 같은
기록을 읽는다. 배정을 멈추는 일과 화면에 보여주는 일이 모두 이 기록 위에서 이루어진다.

### 비용과 위험

구분값을 싣지 않는 실행 환경에서는 기록이 생기지 않고 앱 동작이 지금과 같다. 앱은 실패 메시지
원문을 다시 읽어 한도를 판정하지 않으므로, 문구가 바뀌어도 앱이 오판하지 않는다. 이미 재개 시각이
지난 옛 실행에서는 기록을 만들지 않아 과거 실행이 뒤늦게 배정을 멈추는 일이 없다. 이 작업만으로는
배정이 멈추지도 화면이 달라지지도 않으며, 되돌리면 기록을 만들지 않던 지금 동작으로 돌아간다.

## 현재 코드 상태

실행 행 하나의 모델은 `src-tauri/src/domain/agent_runtime.rs` 677행의 `RunSummary`다. 이 구조체는
`run_id`, `project_id`, `role`, `provider`, `state`, `target_id`, `started_at`, `finished_at`,
`failure_stage`, `reason`, `remaining`, `previous_run_id`, `result_prefix`를 담고, JSON에서는
camelCase로 오간다. 해제 예정 시각을 담을 항목은 아직 없다. `finished_at`과 `result_prefix`가
`#[serde(default)]`를 단 선택 항목으로 들어온 선례이고, 같은 파일 702행부터의 `run_summary_tests`가
구형 행에서 그 키가 없어도 읽히는지를 확인한다. 종료 상태 값은 661행의 `RunState` 여덟 개이고
`Succeeded`·`Failed`·`Cancelled`·`RecoveryRequired`가 끝난 상태다.

실행 목록을 만드는 자리는 `src-tauri/src/application/agent_runtime_status_service.rs` 122행의
`AgentRuntimeStatusService::inspect`다. 런타임 상태를 읽어 133행에서 `runs`를 만들고, 155행부터
`QueueSnapshot`을 조립한다. 이 함수는 지금 파일을 쓰지 않는다. 커맨드 쪽 진입점은
`src-tauri/src/commands/agent_runtime.rs` 425행의 `inspect_agent_runs`이고, 605행의 `locations`가
번들 자산 경로와 앱 데이터 경로를 준다. 사용자 홈은 585행의 `heartbeat_home`이 `app.path().home_dir()`로
해석하며, 같은 파일이 홈 해석을 커맨드 계층에서만 한다는 규칙을 주석으로 적어 두었다.

기기 단위로 파일을 남기는 자리는 아직 없다. 인프라 모듈 목록은
`src-tauri/src/infrastructure/mod.rs`이고 새 모듈은 여기에 한 줄을 더해 등록한다.

화면 폴링은 2.5초마다 `inspect_agent_runs`를 부른다
(`src/features/projects/application/useProjectWorkspace.ts` 2003행). 그래서 같은 실행 행을 수백 번
다시 보게 되고, 기록을 만드는 판정은 같은 행에서 두 번 만들지 않는 규칙을 스스로 가져야 한다.

## 완료 조건

- C1. 실행 행이 해제 예정 시각을 담을 수 있게 한다(R-02). `RunSummary`에 선택 항목
  `usage_limit_resets_at`을 더하고 JSON 이름은 `usageLimitResetsAt`으로 한다. `#[serde(default)]`를
  달아 이 키를 싣지 않는 실행 행에서도 지금과 똑같이 읽힌다. 앱은 이 값이 비어 있을 때 다른 값으로
  메우지 않는다.
- C2. 한도 도달을 가리는 구분값은 종료 사유 값 `usage_limit_reached` 하나다(R-01, R-03). 대조는
  전체 일치이며 대소문자를 구분한다. 실패 메시지 원문을 정규식이나 부분 문자열로 훑어 한도 여부를
  판정하는 코드를 만들지 않는다. 이 판정 함수는 `domain/agent_runtime.rs`에 두어, 뒤이어 화면과
  조건 검사가 같은 이름을 쓰게 한다.
- C3. 기기 단위 보류 기록을 읽고 쓰는 모듈 `src-tauri/src/infrastructure/provider_hold.rs`를 새로
  만들고 `infrastructure/mod.rs`에 등록한다. 기록의 자리는 보류 기록 루트 아래
  `provider-holds/<실행 도구 이름>.yml` 하나이며, 보류 기록 루트는 사용자 홈 아래 `.workflow-labs`다.
  홈 해석은 커맨드 계층이 하고 이 모듈은 루트 경로를 인자로 받는다.
- C4. 기록 본문은 다음 여섯 줄이고 값의 순서도 이대로다(R-01, R-02, R-06). 시각은 모두
  `YYYY-MM-DDTHH:MM:SSZ` 형식의 UTC이며 오프셋 표기와 소수 초를 쓰지 않는다. 조건 검사 스크립트가
  이 형식만 비교하기 때문이다.
  - `schema_version: 1`
  - `provider: <실행 도구 이름>`
  - `resume_at: <다시 시작할 시각>`
  - `resume_at_known: true|false`
  - `recorded_at: <이 기록을 남긴 시각>`
  - `run_id: <이 기록의 근거가 된 실행 식별자>`
- C5. 재개 시각을 정하는 규칙은 하나다(R-06). 실행 행에 해제 예정 시각이 있으면 그 시각이
  `resume_at`이고 `resume_at_known`은 `true`다. 없으면 그 실행의 종료 시각에서 1시간이 지난 시각이
  `resume_at`이고 `resume_at_known`은 `false`다. 앱이 시각을 추정해 `resume_at_known`을 참으로
  만드는 일은 없다.
- C6. 실행 도구 이름이 `A-Za-z0-9`, `_`, `-` 밖의 문자를 담고 있으면 기록 파일을 만들지 않는다.
  파일 이름이 그 디렉터리 밖을 가리키는 길을 막는다. 이 경우 조회는 오류가 아니라 보류 없음으로
  답한다.
- C7. `inspect`가 실행 목록에서 한도 도달 종료를 골라 기록을 남긴다(R-01, R-05). 고르는 조건은
  세 가지를 모두 만족하는 행이다 — 종료 사유가 C2의 구분값이고, 상태가 끝난 상태이며, 종료 시각이
  있다. 실행 도구마다 종료 시각이 가장 늦은 행 하나만 근거로 삼는다.
- C8. 같은 행에서 기록을 두 번 만들지 않는다. 이미 있는 기록의 `run_id`가 고른 행의 실행 식별자와
  같으면 파일을 다시 쓰지 않는다. 이 규칙이 없으면 2.5초 폴링이 같은 행으로 보류를 무한히 연장한다.
- C9. 계산한 `resume_at`이 이미 지난 시각이면 기록을 만들지 않는다(R-10을 거스르지 않기 위해서다).
  이 규칙 하나가 과거 실행이 뒤늦게 보류를 거는 일을 함께 막는다.
- C10. 보류는 실행 도구 단위다(R-07). 기록은 실행 도구 이름으로만 갈리며 역할 이름이나 프로젝트
  식별자로 갈리지 않는다. 한 실행 도구의 기록이 다른 실행 도구의 기록을 바꾸거나 지우지 않는다.
- C11. 보류 조회는 만료된 기록을 보류로 답하지 않는다(R-10). `resume_at`이 지금보다 뒤일 때만
  보류 중이다. 만료된 기록 파일을 지우거나 고치지 않고 그대로 둔다. 사용자가 해제 조작을 하지
  않아도 보류가 풀린다.
- C12. 기록을 읽지 못하면 보류 없음으로 답한다(R-23). 파일이 없는 경우, 형식이 깨진 경우,
  `resume_at`이 C4의 형식이 아닌 경우, 디렉터리를 읽지 못한 경우가 모두 여기에 든다. 확인 실패를
  보류로 바꾸지 않고 오류로도 올리지 않는다.
- C13. 실행 도구별 보류 상태가 실행 목록 응답에 함께 실린다(R-15, R-16, R-17을 화면이 만족할
  근거다). `QueueSnapshot`에 항목 `provider_holds`를 더하고 JSON 이름은 `providerHolds`로 한다.
  값은 지금 보류 중인 실행 도구마다 하나씩이고 실행 도구 이름, `resume_at`, `resume_at_known`을
  담는다. 보류가 없으면 빈 목록이다.
- C14. 기록을 쓰거나 읽지 못해도 실행 목록 조회는 지금과 같이 성공한다(R-04, R-23). 쓰기 실패가
  `QueueSnapshot`을 조회 불가로 만들지 않는다.
- C15. 커맨드 계층이 보류 기록 루트를 해석해 넘긴다. `inspect_agent_runs`가 `app.path().home_dir()`로
  홈을 얻어 `.workflow-labs`를 붙인 경로를 서비스에 넘긴다. 홈을 얻지 못하면 보류 기록 없이 지금과
  같이 조회한다. 서비스와 인프라 모듈은 환경 변수로 홈을 찾지 않는다.
- C16. 이 작업은 워크플로 문서를 하나도 쓰지 않는다(R-21). 기획서, 작업 그룹, 개발 작업, 결정,
  보고서 파일을 만들거나 고치거나 지우지 않고 작업 상태를 바꾸지 않는다. 선점 기록을 만들거나
  고치거나 지우지 않고, 실행을 취소하거나 다시 시작하지 않는다(R-22).
- C17. 자동 배정 설정값을 바꾸지 않는다(R-13). 역할별 주기, 병렬 인원, 자동 배정 켜짐 여부를 담은
  정책을 이 작업이 쓰지 않는다. 실행 중인 세션을 중단하는 코드도 만들지 않는다(R-12).
- C18. 다음 검사를 새로 넣는다. 파일을 다루는 검사는 임시 디렉터리에 실제 파일을 만들어 확인한다.
  - 한도 구분값이 실린 종료 행을 넣으면 그 실행 도구의 기록 파일이 생기고, `resume_at`이 실려 온
    해제 예정 시각과 같으며 `resume_at_known`이 참이다(인수 조건 1, 3).
  - 해제 예정 시각이 없는 같은 행에서는 `resume_at`이 종료 시각의 1시간 뒤이고 `resume_at_known`이
    거짓이다(인수 조건 4, 6).
  - 같은 행을 두 번 넣어도 파일 내용이 달라지지 않는다(C8).
  - `resume_at`이 이미 지난 값이 되는 행에서는 파일이 생기지 않는다(C9).
  - 구분값이 없는 실패 행, 취소 행, 종료 시각이 없는 행에서는 파일이 생기지 않는다(인수 조건 11).
  - 사유 문자열에 한도라는 낱말이 들어 있으나 구분값과 정확히 같지는 않은 행에서는 파일이 생기지
    않는다(R-03).
  - 실행 도구 A의 기록이 있어도 실행 도구 B의 조회는 보류 없음으로 답한다(인수 조건 2).
  - `resume_at`이 지난 기록은 보류 없음으로 답하고 파일은 그대로 남는다(인수 조건 9의 근거이자
    R-10).
  - 형식이 깨진 기록과 없는 기록 모두 보류 없음으로 답하고 오류를 올리지 않는다(C12).
  - 보류가 있는 상태에서 만든 `QueueSnapshot`의 `provider_holds`에 그 실행 도구가 들어 있고,
    보류가 없으면 빈 목록이다(C13).
- C19. 선언한 다섯 파일 밖의 파일이 바뀌지 않는다.

## 범위 밖

- 조건 검사 스크립트가 이 기록을 읽어 배정을 멈추는 일. TASK-S071-02가 맡는다.
- 역할과 실행 도구의 대응표를 프로젝트 안에 남기는 일. TASK-S071-02가 그 대응표를 읽는 쪽과 함께
  맡는다.
- 화면 문장과 표시. TASK-S071-03이 맡는다.
- 한도 도달 구분값과 해제 예정 시각을 실행 기록에 실어 보내는 일. 기획서가 실행 환경 쪽 후속으로
  넘겼다.
- 앱이 닫혀 있는 동안의 한도 감지. 작업 그룹이 범위 밖으로 적었다.
- 실행 목록 조회 주기, 실행 상태 값 목록, 실행 취소와 재시도 절차.
- 사용량 잔여분 조회와 한도 예측.

## 범위 사전 검사

이 작업이 만드는 값은 셋이다. 실행 행이 실어 오는 해제 예정 시각, 기기 단위 보류 기록 파일,
그리고 실행 목록 응답에 실리는 보류 목록이다. 셋을 각각 원천에서 소비자까지 따라가 확인했다.

- 값 경로: 해제 예정 시각(C1, C5, 인수 조건 3·4). 원천은 실행 환경이 실행 행에 싣는
  `usageLimitResetsAt`이다. hop은 셋이다. (1) `src-tauri/src/domain/agent_runtime.rs` 677행의
  `RunSummary`. 지금 이 항목이 없으므로 편집 대상이다. 같은 파일 702행부터의 `run_summary_tests`가

  이번 항목을 적는 일은 조건 스크립트를 고치는 TASK-S071-02가 함께 한다.
