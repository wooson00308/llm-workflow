# 앱이 실행 계획과 큐 상태와 제어 결과를 런타임에서 읽는다

## 결정권자 요약

앱은 실행 전에 지금 시작할 대상과 제한 요인과 유료 세션 위험을 정확히 보여줄 수 있다.
사용자가 확인한 계획만 시작하며 확인 뒤 조건이 달라지면 다시 확인을 요구한다.
실행 중과 대기와 최근 종료 상태는 런타임의 영속 기록에서 복원된다.
런타임을 읽지 못하면 상태를 모름으로 두고 마지막에 본 값을 실행 중이라고 말하지 않는다.
프로젝트 일시 정지와 재개와 취소와 재시도가 다른 프로젝트에 영향을 주지 않는다.
부분 실패는 예약과 실행과 정리 중 어디에서 실패했는지 구분해 전달된다.
실행은 언제나 런타임 큐를 거치며 앱이 직접 도구를 띄우는 경로를 만들지 않았다.
전용 자동 검사 18건을 더했고 앱 전체 검사를 통과했다.
사용자는 아래 확인 동선을 검토한 뒤 QA를 확정할 수 있다.

## 목적

TASK-S051-04의 project queue를 Tauri 백엔드 명령으로 노출한다. 앱 프로세스가 dispatcher 상태를
추측하거나 내부 데이터베이스를 읽지 않고 버전화된 JSON CLI를 통해 계획, 시작, 상태, 로그, 제어를
수행한다.

## 명령 계약

### 계획과 시작

- `plan_agent_run`: project ID, 역할별 자동·수동 슬롯, 한 번·반복 방식을 받아 후보, 제외 사유,
  실제 시작 수, 적용된 역할·프로젝트·기기 제한, provider 진단, API 과금 위험을 반환한다. 파일과
  provider 프로세스를 변경하지 않는다.
- 계획 결과에는 일회용 `planId`, runtime revision, 만료 시각을 둔다.
- `start_agent_run`: 같은 `planId`와 사용자 확인을 받아 시작한다. 후보, 설정, lease, runtime revision이
  달라졌거나 계획이 만료됐으면 아무 provider도 시작하지 않고 새 계획 필요 상태를 반환한다.
- 자동 계획은 런타임이 계산한 후보 순서를 사용한다. 수동 계획은 대상 식별자를 검증하고 중복을
  거절한다.

### 상태와 제어

- `inspect_agent_runs`: 현재 프로젝트의 정책, 반복 상태, 예약·대기·실행 중·일시 정지·최근 종료·복구
  필요 항목, provider 진단, 기기 슬롯 사용량을 반환한다.
- `pause_agent_project`와 `resume_agent_project`: 새 배정만 제어한다.
- `cancel_agent_run`: 대상·프로세스 트리·정리 영향을 미리 보여주는 plan과 확인 뒤 적용을 분리한다.
- `retry_agent_run`: 이전 실패 식별자를 필수로 받고 새 계획과 새 실행 식별자를 반환한다.
- `read_agent_run_log`: 실행 식별자와 cursor만 받으며 민감정보가 제거된 이벤트 묶음과 다음 cursor를
  반환한다. 파일 경로를 화면에서 받지 않는다.

## 안전 규칙

- 모든 명령은 project ID와 실제 작업 디렉터리의 대응을 검증한다.
- 앱의 기존 `run_heartbeat_job`처럼 데몬 밖에서 `heartbeat once`를 띄우는 경로를 새 화면에서 사용하지
  않는다. 실행은 항상 runtime queue를 거친다.
- 화면이 보낸 provider 실행 파일, 명령 인자, 로그 경로를 사용하지 않는다. 백엔드가 고정 명령과
  runtime 응답 식별자만 사용한다.
- runtime 응답의 API major, request ID, project ID가 기대값과 다르면 성공으로 처리하지 않는다.
- 조회 실패는 마지막 메모리 값을 실행 중이라고 추측하는 근거가 아니다. 상태를 모름으로 구분한다.

## 손대지 않는 것

- 런타임 dispatcher와 provider 구현
- 역할 설정 화면과 실행 대시보드 UI
- Dream 실행과 기존 Dream 카드
- 앱 프로세스가 직접 provider CLI를 시작하는 새 경로
- 실행 중 작업의 자동 취소

## 완료 조건

1. 자동 계획은 후보와 제외 사유, 실제 시작 수, 모든 제한 요인을 provider 시작 없이 반환한다.
2. 수동 계획은 같은 대상 중복, 활성 lease, 완료·거절 상태, 잘못된 식별자를 사유와 함께 거절한다.
3. 확인한 최신 plan만 시작할 수 있고 만료·revision 변경·후보 변경에서는 provider가 시작되지 않는다.
4. 한 번과 반복, 자동과 수동의 네 조합이 runtime 요청에 서로 다른 정확한 값으로 전달된다.
5. 상태 조회가 reserved, queued, running, paused, succeeded, failed, cancelled,
   recovery_required를 구분하고 프로젝트·역할·provider·대상·시각·경과 시간을 싣는다.
6. 앱을 다시 열어 첫 조회를 했을 때 런타임이 보존한 큐와 실행 상태가 그대로 나온다.
7. 프로젝트 일시 정지는 다른 프로젝트와 실행 중 작업을 멈추지 않는다.
8. 취소 계획은 대상 프로세스 트리와 lease 영향을 보여주고 확인 없는 적용은 아무것도 바꾸지 않는다.
9. 취소 결과에서 프로세스 종료와 lease 정리 중 하나가 실패하면 성공으로 표시하지 않는다.
10. 재시도는 이전 실행을 연결하고 새 실행 식별자를 사용한다.
11. 로그 조회는 cursor 기반이며 인증 토큰, API 키, 전체 prompt를 반환하지 않는다.
12. 호환되지 않는 runtime, project ID 불일치, 계약 밖 JSON은 provider 시작 전에 실패한다.
13. 새 실행 경로가 `heartbeat once`를 호출하지 않는다.
14. 기존 Tauri 명령과 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. 가짜 runtime CLI의 요청 기록으로 모든 Tauri 명령이 고정 인자와 표준 입력 JSON만 사용하는지
   확인한다.
2. plan 뒤 설정·후보·lease·runtime revision을 각각 바꿔 stale plan이 실행되지 않는지 검사한다.
3. 상태 아홉 종류와 부분 실패, 잘못된 계약 버전, project ID 불일치 응답을 직렬화 검사로 고정한다.
4. 프로젝트 둘을 두고 pause·resume·cancel·retry가 대상 프로젝트만 바꾸는지 확인한다.
5. 민감정보와 전체 prompt가 든 가짜 이벤트를 로그 조회해 제거된 결과만 전달되는지 확인한다.
6. 프로세스 실행 기록에서 `heartbeat once`, `claude`, `codex`를 앱이 직접 시작한 흔적이 없는지
   확인한다.
7. `cargo test --manifest-path src-tauri/Cargo.toml`을 실행한다.
8. `npm run check`를 실행한다.

     provider 시작 없이 온다.
   - `a_stale_plan_becomes_a_new_plan_request_not_a_success`: 조건이 달라진 계획은 성공으로 바뀌지
     않고 새 계획 필요로 전달된다.
   - `starting_sends_the_plan_and_the_confirmation`: 계획 식별자와 확인이 함께 간다.

4. 상태와 제어를 `src-tauri/src/application/agent_runtime_status_service.rs`에서 확인한다.
   - `every_contract_state_survives_the_round_trip`: 여덟 상태가 모두 구분돼 오고 역할·provider·
     대상·시작 시각이 함께 실린다.
   - `a_runtime_that_cannot_be_read_leaves_the_state_unknown`: 조회 실패는 모름이지 실행 중이 아니다.
   - `rows_from_another_project_make_the_whole_answer_untrusted`와

     처리하지 않는다.
   - `pausing_one_project_reports_only_that_project`: 일시 정지는 새 배정만 막고 돌던 실행은 목록에
     그대로 있다.
   - `the_log_page_travels_by_cursor_and_carries_no_path`: 로그 요청에 파일 경로가 실리지 않는다.
