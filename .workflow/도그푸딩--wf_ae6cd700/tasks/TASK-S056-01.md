# 품질 확인 대기 카드가 확인 동선 첫 문단을 미리보기로 보여준다

## 결정권자 요약

### 제안

품질 확인 대기 상태인 작업 카드의 미리보기를 그 문서의 확인 동선 첫 문단으로 바꾼다.

### 현재

카드의 미리보기는 어느 상태든 본문 앞 세 줄을 잘라 만든다. 그래서 카드에는 결정권자 요약의 앞부분이
실리고, 그 작업을 어떻게 확인해야 하는지는 실리지 않는다. 확인 방법은 카드를 열어 도장 옆까지 가야
읽히므로, 눈으로 봐야 하는 작업과 자동 검사 수치를 신뢰하면 되는 작업이 목록에서 구분되지 않는다.

### 변경 후

품질 확인 대기 카드에는 개발자가 쓴 확인 동선의 첫 문단이 그대로 실린다. 화면이 없는 작업은 그렇다고
말하는 문장이, 화면이 있는 작업은 어디에서 무엇을 보면 되는지가 카드에서 읽힌다. 확인 동선 절이 없는
작업은 지금과 같은 발췌를 그대로 보여준다.

### 사용자 결과

품질 확인 대기가 여러 건 쌓여도 목록을 훑는 것만으로 눈으로 확인할 작업을 먼저 고를 수 있다. 카드를
하나씩 열어 확인 방법을 찾는 왕복이 사라진다.

### 영향 범위

- 변경: 품질 확인 대기 상태 문서의 카드 미리보기 문구
- 유지: 다른 상태의 카드 표시, 사용자 확인 도장과 레인 일괄 확인, 단건 패널의 확인 동선 표시, 앱이 설치하는 규칙 문언과 역할 계약과 규칙 버전, 목록 조회가 읽는 파일 수

### 비용과 위험

카드 문구의 근거는 개발자가 쓴 문장 그 자체다. 확인 동선을 부실하게 적은 작업은 카드도 그만큼 부실하게
보이며 앱은 그 문장을 검사하지도 보완하지도 않는다.

### 결정 요청

품질 확인에서는 확인 동선이 있는 대기 카드와 없는 대기 카드와 대기가 아닌 카드 세 경우의 표시를 목록
화면에서 직접 확인한다.

## 확인 동선

개발 메뉴의 목록에서 품질 확인 대기 카드를 열지 않고 미리보기 문장만 읽으면 된다. 지금 읽고 있는 이
문단이 그대로 이 작업의 카드에 실린다.

1. 앱에서 이 프로젝트를 열고 왼쪽 메뉴의 `개발`을 고른다. 보드에서는 `QA 대기` 열, 리스트에서는 상태
   필터를 `QA 대기`로 두면 대상 카드가 모인다.
2. 이 작업(TASK-S056-01)의 카드를 본다. 카드 아래 미리보기가 결정권자 요약의 앞부분이 아니라 위
   문단이면 정상이다. 카드를 열 필요가 없다.
3. 확인 동선 절이 없는 품질 확인 대기 작업이 함께 있으면 그 카드는 변경 전과 같은 발췌를 보여준다.
   직접 만들어 보려면 임시로 작업 문서 하나에서 `## 확인 동선` 제목만 `## 확인동선`처럼 바꿔 저장한
   뒤 목록을 새로 고치면 된다. 그 카드만 예전 발췌로 돌아가고 다른 카드는 그대로다. 확인이 끝나면
   제목을 되돌린다.
4. `준비`·`진행 중`·`막힘`·`완료` 열의 카드와 아이디어·기획서 화면의 카드를 함께 본다. 미리보기 문구가
   변경 전과 같아야 한다.
5. 어떤 카드에도 새 딱지나 새 색 구분이 붙지 않고 정렬 순서도 그대로다. 앱은 확인 방식을 분류하지
   않는다.

문서에 적힌 문장을 그대로 싣기 때문에, 확인 동선을 부실하게 적은 작업은 카드도 그만큼 부실하게 보인다.
그것은 앱의 결함이 아니라 그 문서의 상태다.

화면 없이 수치만 보고 싶다면 자동 검사가 같은 사실을 대조한다.

- `cargo test --manifest-path src-tauri/Cargo.toml` → 617 passed, 0 failed
- `npm run check` → 타입 검사 통과, 25개 파일 851 tests 통과, 배포 빌드 성공

## 목적

SPEC-056의 R1부터 R8까지를 구현한다. 목록 조회가 이미 읽고 있는 본문에서 확인 동선 첫 문단을 뽑아 품질
확인 대기 문서의 미리보기 값으로 쓴다. 앱이 확인 방식을 분류하거나 문장을 지어내지 않는다.

## 범위 사전 검사

- 카드 미리보기는 앱 백엔드가 만든다. 목록 요약을 만드는 함수가 본문 앞 세 줄을 잘라 미리보기 값을
  채우고, 프런트엔드는 그 값을 받아 그대로 그린다. 그래서 이 변경은 백엔드 파일 하나로 끝난다.
- 그 요약 함수는 이미 문서 상태를 읽어 요약 구조에 담는다. 상태에 따라 미리보기를 다르게 만드는 데
  새 입력이 필요하지 않다.
- 요약 함수는 아이디어와 기획서와 작업 문서를 함께 처리한다. 품질 확인 대기라는 상태 값은 작업 문서에만
  나타나므로 상태 하나로 갈라도 다른 문서 종류의 표시는 바뀌지 않는다.
- 미리보기 값은 요약 구조의 기존 필드다. 그 필드를 그대로 쓰면 도메인 구조와 명령 계층과 프런트엔드
  타입이 바뀌지 않는다. 새 필드를 더하면 세 층이 함께 움직여야 하고, 그 파일들은 다른 승인의 미완료
  작업들이 함께 쓰고 있다. 새 필드를 만들지 않는 쪽을 택한 이유가 이것이다.
- 확인 동선 절의 제목은 앱이 설치하는 규칙과 개발자 계약이 고정한 문자열이다. 이 작업은 그 문자열을
  읽기만 하고 규칙 파일을 고치지 않는다. 규칙 문언과 규칙 버전은 이 작업의 범위 밖이다.
- 절을 정확한 제목으로만 찾는 판정은 프런트엔드에 이미 같은 규칙의 구현이 있다. 이번에는 백엔드에서
  판정하므로 그 구현을 옮겨 쓰지 않고 같은 규칙을 이 파일 안에서 구현한다. 프런트엔드 파일은 건드리지
  않는다.
- 같은 파일을 범위로 가진 미완료 작업이 넷 있다. 둘은 품질 확인 대기 상태이고 둘은 이 세션이 방금 만든
  다른 승인의 작업이다. 어느 쪽이 먼저여야 할 이유가 없어 선행 관계를 선언하지 않았다.

## 변경 범위

### 미리보기 선택

- 문서 상태가 품질 확인 대기이고 본문에 유효한 확인 동선 절이 있으면 그 절의 첫 문단을 미리보기 값으로
  쓴다.
- 그 밖의 모든 경우는 지금의 앞 세 줄 발췌를 그대로 쓴다. 상태가 품질 확인 대기가 아닌 경우와, 확인
  동선 절이 없거나 제목이 어긋나는 경우와, 절은 있으나 첫 문단이 비어 있는 경우가 여기에 해당한다.
- 절이 없다는 사실을 카드에서 따로 지적하지 않는다. 대체 문장을 만들지 않는다.

### 절과 문단 판정

- 확인 동선 절은 제목 문자열이 개발자 계약이 정한 문자열과 문자 단위로 같을 때만 성립한다. 앞뒤 공백이
  다르거나 제목 깊이가 다르거나 철자가 다른 제목은 보완하지 않는다.
- 코드 울타리 안의 같은 문자열은 제목으로 세지 않는다.
- 첫 문단은 제목 바로 아래에서 시작해 처음 만나는 빈 줄 앞까지다. 여러 줄이면 한 줄로 이어 붙인다.
- 값은 문서에 적힌 그대로 싣는다. 요약하거나 다시 쓰거나 번역하지 않는다.
- 카드에 담기지 않는 길이는 기존 발췌와 같은 방식으로 잘라 보여준다.

### 하지 않는 것

- 화면 확인형과 수치 신뢰형을 앱이 가르지 않는다. 분류 딱지도 색 구분도 정렬 우선순위도 만들지 않는다.
- 목록 조회가 문서 파일을 더 읽지 않는다. 이미 읽은 같은 본문에서 값을 하나 더 뽑는다.

## 손대지 않는 것

- 요약 구조의 필드 구성과 명령 계층과 프런트엔드 타입
- 프런트엔드의 카드 그리기와 단건 패널의 확인 동선 표시
- 사용자 확인 도장과 상태 기계와 결정 기록의 뜻
- 레인 단위 일괄 확인 경로
- 앱이 설치하는 규칙 문언과 세 역할 계약과 규칙 버전
- 기존 작업 문서의 본문

## 완료 조건

1. 확인 동선 절이 있는 품질 확인 대기 문서의 미리보기가 그 절의 첫 문단이 된다.
2. 화면이 없다고 적은 작업의 미리보기에서 그 문장이 읽히고, 화면이 있는 작업의 미리보기에서 어디에서
   무엇을 보는지가 읽힌다.
3. 확인 동선 절이 없는 품질 확인 대기 문서의 미리보기가 변경 전과 같은 발췌다.
4. 품질 확인 대기가 아닌 문서의 미리보기가 변경 전과 같다. 아이디어와 기획서의 미리보기도 같다.
5. 제목의 철자와 깊이와 공백이 다른 경우와 코드 울타리 안의 같은 문자열은 절로 인정되지 않고 기존 발췌로
   되돌아간다.
6. 첫 문단이 여러 줄이면 한 줄로 이어지고, 문서에 적힌 문장이 요약이나 재작성 없이 그대로 실린다.
7. 길이가 넘치면 기존 발췌와 같은 방식으로 잘린다.
8. 앱이 만든 분류 딱지나 색 구분이나 정렬 변경이 어떤 카드에도 생기지 않는다.
9. 목록 조회가 이 변경 때문에 문서 파일을 더 읽지 않는다.
10. 요약 구조의 필드 구성이 바뀌지 않아 명령 계층과 프런트엔드가 수정 없이 그대로 동작한다.
11. 앱이 설치하는 규칙 문언과 세 역할 계약의 내용과 네 규칙 버전이 변경 전과 같다.
12. 기존 단건 확인과 레인 일괄 확인과 단건 패널의 확인 동선 표시 검사가 변경 전과 같이 통과한다.
13. 기존 자동 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. `cargo test --manifest-path src-tauri/Cargo.toml`을 실행한다.
2. 확인 동선이 있는 대기 문서, 없는 대기 문서, 대기가 아닌 문서, 아이디어와 기획서를 한 픽스처에 함께
   두고 각 미리보기 값을 표로 대조한다.
3. 제목 철자 변경, 제목 깊이 변경, 앞뒤 공백 변경, 코드 울타리 안의 같은 제목을 각각 넣어 모두 기존
   발췌로 되돌아가는지 확인한다.
4. 첫 문단이 한 줄인 경우와 여러 줄인 경우와 절이 비어 있는 경우를 확인한다.
5. 길이가 넘치는 첫 문단으로 자르기 동작이 기존 발췌와 같은지 확인한다.
6. 변경 전후로 조회가 여는 파일 수가 같은지 확인한다.
7. 규칙 본문과 네 버전 상수가 변경 전과 같은지 확인한다.
8. 저장소 루트에서 `npm run check`를 실행해 프런트엔드가 수정 없이 통과하는지 확인한다.

## 범위와 선행

선행 작업은 없다. 이 작업은 표시 값을 만드는 한 파일 안에서 끝나고 다른 승인의 결과를 기다리지 않는다.

같은 파일을 범위로 가진 미완료 작업이 넷 있다. 둘은 규칙 계약을 다루다가 품질 확인 대기에 이른 작업이고,
둘은 작업 정의 수정 경로를 만드는 다른 승인의 작업이다. 이 겹침에는 어느 쪽이 먼저여야 할 이유가 없어
선행 관계를 선언하지 않았다. 선언 범위가 겹치는 두 작업을 같은 시각에 시작하지 않게 하는 것이 이 경우의
안전장치이며, 그 판정은 선점 시점에 이루어진다.
