# 연동 카드에서 데몬을 끄고 켠다

## 결정권자 요약

이제 커밋 컷을 시작할 때 터미널을 열지 않아도 된다. 연동 탭의 하트비트 카드에 끄기·켜기 버튼이
섰고, 끄기를 누르면 먼저 확인 화면이 열려 세 가지를 말한다 — 이 조작이 이 프로젝트가 아니라 이
기기의 모든 잡에 걸린다는 것, 지금 끊기는 세션이 몇 개인지, 재부팅하면 다시 켜진다는 것.

08-05 컷에서 정지 타이밍을 놓쳐 세션 여러 개가 밤새 돌았고 그중 TASK-104가 도중에 죽어 고아가
됐다. 그때 화면은 아무 말도 하지 않았다. 이제 그 자리에서 지금 도는 세션을 세어 보인다.

앱은 세션을 정리하지 않는다. 고지하고 사용자가 고른다. 꺼진 상태는 카드에 계속 남고, 앱이 대신
다시 켜지 않는다.

자동 검사는 전부 통과했다. 앱을 띄워 실제로 껐다 켜 보는 걸음만 사용자 몫으로 남았다.

## 확인 동선

### 1. 검사 두 개를 다시 돌린다

```sh
npm run check
cargo test --manifest-path src-tauri/Cargo.toml
```

**정상이면 앞엣것이 23 files / 705 tests passed / 0 failed이고, 뒤엣것이 538 passed / 0 failed다.**
이 세션이 넘길 때의 값이고, 다른 세션이 그 사이에 검사를 더했으면 숫자는 늘 수 있다. 늘어도
`failed`가 0이면 정상이다. 이 작업은 Rust를 한 줄도 바꾸지 않았으므로 538은 TASK-123이 넘길 때와
같은 값이다.

### 2. 앱에서 실제로 껐다 켠다 (사용자 확인)

**이 세션이 하지 못한 확인이다.** 화면을 누를 수단이 없고, 이 세션이 그 데몬이 띄운 프로세스라면
끄기가 성공하는 순간 죽어 다시 켤 걸음이 남지 않는다.

```sh
npm run tauri dev
```

이 프로젝트를 연 뒤 왼쪽 메뉴의 **연동 → claude-heartbeat 카드 펼치기**. 하트비트 업데이트 통로
바로 아래에 **데몬 끄기·켜기** 상자가 새로 서 있다.

1. **끄기를 누른다.** 바로 실행되지 않고 확인 화면이 먼저 열린다. 그 안에 넷이 있어야 한다 —
   실행 기록이 있는 잡 수와 이름(이 프로젝트 것과 그 밖의 것이 나뉜다), dream 잡도 함께 멈춘다는
   한 문장, 지금 끊기는 세션(이 세션의 lease가 살아 있으면 1개 이상으로 보인다), 재부팅하면 다시
   켜진다는 문장. **취소를 눌러도 아무 일도 일어나지 않는 것까지 한 번 확인한다.**
2. **확인하고 데몬 끄기.** 진행 표시가 뜨고 그동안 두 버튼이 눌리지 않는다.
3. **결과를 읽는다.** "데몬 끄기 명령이 끝났습니다"와 종료 코드, 그리고 조작한 대상 이름이 나온다.
   이 기기에서 그 이름은 `com.catze.dream-heartbeat`이고 앱이 내장한 `com.claude-heartbeat`이 아니다.
   결과가 "꺼졌습니다"로 끝나지 않는 것이 정답이다 — 명령이 끝난 것과 데몬이 내려간 것은 다른
   사실이라, 조회 주기(2.5초)가 따라오기 전에는 "상태 갱신을 기다리는 중"이라고 말한다.
4. **몇 초 뒤 카드를 본다.** 배지가 "설치됨 · 데몬 미실행"으로 바뀌고 카드 위쪽에 "하트비트 데몬이
   멈춰 있습니다" 경고가 선다. 카드를 접어도 머리의 "확인할 경고가 있습니다"가 남는다. **그 상태로
   주기를 여러 번 두고 봐도 앱이 스스로 다시 켜지 않는 것**이 확인 필요 4번의 승인안이다.
5. **켜기를 누른다.** 확인 화면 없이 바로 나가고, 세션 목록도 나오지 않는다. 잠시 뒤 배지가
   "설치됨 · 데몬 실행 중"으로 돌아온다.

**반드시 5번까지 하고 끝낸다** — 내린 채로 두면 다음 세션이 깨어나지 않는다.

터미널에서 직접 확인하려면 `launchctl list | grep dream-heartbeat`가 1번 뒤에 사라지고 5번 뒤에 다시
나타난다. 사이에 `~/.claude/heartbeat/heartbeat.pid`가 잠시 남아 있을 수 있는데 그것도 정상이다 —
앱의 실행 여부 판정이 그 파일 하나이고, 결과가 데몬 상태를 단정하지 않는 이유가 그 한계다(R7).

이미 실측된 값 하나가 화면에서도 그대로 나온다. 이미 올라가 있는 서비스에 켜기를 다시 누르면 종료
코드 5와 `Bootstrap failed: 5: Input/output error`가 나오고 데몬은 그대로 돈다. 앱은 이것을 실패로
접지 않고 숫자와 원문을 접힌 자리에 그대로 싣는다.

### 3. 화면으로 만들 수 없는 상태

대상 미확정 넷(등록물 없음·대상 모호·이름을 읽지 못함·macOS 아님)과 실행 수단 없음은 이 기기의
등록물로는 만들 수 없다. 그 다섯은 자동 검사로 닫았고, 그 자리의 확인 도장은 위 1번의 숫자를 믿는다는
뜻이 된다.

## 이 작업이 닫는 것

SPEC-036의 화면 전부다. R1·R2·R3·R5·R6·R7·R9의 표시 쪽과 확인 필요 2·4번의 승인안, 기획서
완료 조건 1·3·4·5·6·7·9·10·11·12·13·16·17을 닫는다.

TASK-123이 만든 커맨드를 화면까지 잇는다. 배선은 이 저장소가 이미 쓰는 통로 그대로다 —
`tauriProjectGateway.ts`에 호출을 더하고, `useProjectWorkspace.ts`가 진행·결과 상태를 들고
`IntegrationsState`에 얹어 내보내고, `WorkspaceShell`이 `IntegrationsView`에 넘기고, 뷰는 값을
보지 않고 카드에 그대로 넘긴다. `heartbeatRuns`가 같은 모양의 선례다.

## 자리

끄기·켜기는 역할별 조작이 아니라 데몬 전체의 일이다. 그래서 역할 잡 폼 안이 아니라 **하트비트
카드의 공통 자리**, TASK-116이 세운 업데이트 통로 옆에 선다. dream 카드에는 이 통로를 만들지
않는다 — 데몬은 하나이고 조작 자리도 하나다.

## R1 — 두 조작과 겹쳐 누르기

- 끄기와 켜기가 각각 버튼이다. 성공 경로에서 사용자가 터미널을 열지 않는다.
- 진행 중에는 버튼이 눌리지 않고 진행 표시가 보인다. `bootout`은 데몬이 내려갈 때까지 걸리므로
  표시가 없으면 사용자는 눌리지 않았다고 판단하고 다시 누른다. `runningNow`와 TASK-116의 업데이트
  진행 표시가 같은 이유로 있는 선례다.
- 끝나지 않은 상태에서 두 번 눌러도 호출이 한 번만 나간다.

## R3·R2 — 끄기 전 확인 화면

끄기 버튼은 누르는 즉시 실행하지 않는다. TASK-116이 만든 확인 화면과 같은 자리·같은 모양을 쓰되,
첫 줄에서 갈라 준다 — 업데이트는 저장소를 갱신하고 데몬을 재기동하는 것이고, 이쪽은 데몬을 내리고
그대로 둔다.

확인 화면에 실리는 것 넷:

1. **이 기기의 모든 잡이 멈춘다.** 화면은 프로젝트 하나의 연동 탭인데 사정거리는 기기 전체다.
   멈추는 잡의 수와 이름을 TASK-122가 스냅샷에 실은 값으로 말한다. 앱이 지어내지 않는다 —
   이름은 `state.json`에서 읽은 문자열 그대로이고, 앱이 더한 것은 "이 프로젝트의 것인가" 하나다.
   이 프로젝트 것과 그 밖의 것이 나뉘어 보인다.
2. **dream 잡도 함께 멈춘다.** 하트비트 카드와 dream 카드가 화면에서 갈려 있어도 데몬은 하나라는
   것이 읽혀야 한다(R2). 잡 목록에 dream 잡이 있으면 그 사실이 목록으로 드러나고, 목록과 별개로
   한 문장이 그것을 말한다.
3. **지금 끊기는 세션.** 원천은 `project.activeLeases`다. 활동 뷰가 이미 쓰는 값이고 TASK-116이
   카드까지 내려 둔 값이라 앱이 새로 계산하지 않는다. 세션이 0개일 때와 하나 이상일 때 문구가
   다르다 — 0개면 "지금 끊길 세션이 없습니다"이고, 하나 이상이면 개수와 목록(에이전트 이름·대상
   문서)이 선다.

   **그 수가 이 프로젝트의 것뿐이라는 사실을 함께 말한다.** R3이 고지의 원천을
   `project.activeLeases` 하나로 정했는데 그 값은 지금 열린 프로젝트의 `.workflow/.runtime/leases`만
   읽은 것이고, 데몬이 멈추면 다른 프로젝트에서 도는 세션도 함께 끊긴다. 앱은 그쪽 lease를 읽지
   않으므로 그 수를 알지 못한다. 0개를 "끊길 세션이 없습니다"로만 말하면 그것이 R4가 금한
   "앱이 모르는 것을 아는 척하는" 문장이 된다. 잡 목록(1번)이 다른 프로젝트의 잡을 이미 보이고
   있으므로 이 문장은 그 목록과 같은 사실을 말한다.
4. **재부팅·재로그인하면 다시 켜진다.** 확인 필요 2번의 승인안이다. 이 조작은 잠깐 내리는 것이고
   등록 해제가 아니다. "껐는데 다시 켜져 있다"를 사용자가 만나기 전에 말해 둔다. 영구 정지를
   원하면 설치 마법사 3단계의 등록 해제가 그 자리라는 것도 함께 말한다 — 이 토글이 그것을 하지
   않는다는 사실이 R8의 요구다.

취소하면 아무것도 실행되지 않는다. 확인을 누르면 화면이 닫히고 같은 조작이 두 번 실행되지 않는다.

**앱은 세션을 정리하지 않는다.** 드레이닝을 기다리지도, lease를 지우지도 않는다. 남의 lease에
손대는 것은 `.workflow/rules/workflow.md` §4가 금한다. 화면이 lease를 쓰는 경로가 없다.

**켜기에는 확인 화면이 붙지 않는다.** 끊을 세션이 없는 조작이고 되돌릴 수 없는 것도 아니다.
대신 버튼 옆 문장이 사정거리를 말한다 — 이 기기의 잡이 전부 다시 깨어난다.

## R5 — 조작할 수 없는 상태를 구분해 말한다

TASK-122·TASK-123이 낸 다섯 사유가 화면에서 서로 다른 문구가 된다. 하나의 실패 문구로 뭉뚱그리지
않는다. 사유마다 사용자가 할 다음 행동이 다르다.

- **등록된 서비스가 없다** — 데몬이 OS 스케줄러 밖에서 손으로 떠 있거나 아예 없다. 설치 마법사
  3단계가 그 자리라는 것을 잇는다.
- **등록물이 여럿이라 대상이 모호하다** — 앱이 고르지 않는다는 것과 찾은 plist 경로를 전부 보인다.
  사용자가 정리해야 한다는 것을 말한다. 엉뚱한 서비스를 내리면 데몬은 계속 도는데 화면은 껐다고
  말하게 되고, 앱은 그 어긋남을 확인할 수단이 없다(확인 필요 3번).
- **이름을 읽지 못했다** — plist는 하나인데 그 안의 이름을 읽지 못했다. 읽지 못한 파일 경로를 보인다.
- **macOS가 아니다** — 이 플랫폼에서 앱이 할 수 있는 것이 없다고 말한다. 확인하지 않은 명령을
  대신 싣지 않는다(R9). 이 상태에서는 버튼이 나가지 않는다.
- **실행 수단을 찾지 못했다** — 사유와 함께 사용자가 그대로 칠 명령 원문이 나오고 복사할 수 있다.
  원문에 빈칸이 없다(완료 조건 10). "지금 실행" 실패 표시와 TASK-116의 같은 자리가 쓰는 모양을
  그대로 쓴다.

앞 넷은 누르기 전에 이미 알 수 있는 상태다(스냅샷이 싣는 판정이다). 그 상태에서는 **버튼이 나가지
않거나 눌리지 않고**, 왜 그런지가 그 자리에서 읽힌다. 다섯째는 눌러 봐야 나오는 결과다.

이 실패들이 설치 마법사의 단계 상태를 바꾸지 않는다. SPEC-016 R5·SPEC-020 R6이 세운 선이고,
커맨드가 스냅샷을 돌려주지 않는 것이 그 구조적 근거다.

## R7 — 확인한 것까지만 말한다

결과 표시가 "꺼졌습니다"로 끝나지 않는다.

- **명령이 성공했다는 것과 데몬이 내려갔다는 것을 한 문장으로 뭉뚱그리지 않는다.** 앱의 실행 여부
  판정은 pid 파일 존재 하나이고(확인 사실 1), 그 판정은 조회 주기를 타고 늦게 따라온다.
- 종료 코드가 0이 아닌 경우 숫자와 stderr 원문을 그대로 보인다. 접힌 자리(`<details>`)를 쓴다 —
  TASK-116이 stderr에 같은 자리를 쓴다. 앱이 코드의 뜻을 지어내지 않는다.
- **모순된 두 상태를 동시에 말하지 않는다.** 명령이 끝났는데 `daemon_running`이 아직 참이면, 화면은
  "명령은 끝났고 상태 갱신을 기다리는 중"으로 말한다. "꺼짐"과 "실행 중"이 한 화면에 함께 서지
  않는다.
- `heartbeat status`의 출력을 파싱하지 않는다(완료 조건 14).

## R6 — 꺼 놓은 것을 잊게 두지 않는다

- 데몬이 꺼진 상태가 카드에서 계속 보인다. 사용자가 끄는 이유는 잠깐 멈추기 위해서이고, 끈 채로
  잊으면 루프 전체가 조용히 서는데 그 상태는 화면에서 "아무 일도 일어나지 않음"과 구별되지 않는다.
- 표시 통로는 **084가 세운 본문 경고 통로**를 그대로 쓴다(`IntegrationWarning`). 접힘·펼침의
  동작에 새 규칙을 만들지 않는다.
- 문구가 원인을 단정하지 않는다. `daemon_running`이 거짓인 것은 사용자가 껐을 때도, 설치가 아직
  안 됐을 때도, 데몬이 정리 없이 죽었을 때도 같은 모양이다. 앱은 셋을 구분하지 못하므로 구분하는
  척하지 않는다 — `noRunEvidenceNote`가 같은 어법을 이미 쓴다.
- **앱이 사용자를 대신해 다시 켜지 않는다.** 확인 필요 4번의 승인안이다. 자동 복구는 사용자가
  의도해서 꺼 둔 상태를 앱이 무르는 것이고, 커밋 컷 도중에 데몬이 되살아나면 아이디어가 적은 페인이
  그대로 재현된다. 조회 주기가 몇 번을 돌아도 켜기 호출이 나가지 않는다.
