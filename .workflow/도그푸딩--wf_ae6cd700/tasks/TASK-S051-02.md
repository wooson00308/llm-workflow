# 런타임 제어 계약과 프로젝트별 영속 상태를 만든다

## 결정권자 요약

앱과 런타임이 주고받는 요청과 응답을 버전화된 계약으로 구현했다.
프로젝트 설정은 런타임 저장소에 남고 프로젝트별 조회 결과는 서로 섞이지 않는다.
지원하지 않는 설정은 저장 전에 거절하며 비밀값은 저장 경로와 응답에 넣지 않는다.
기존 잡과 별개로 계약과 설정과 비어 있는 실행 상태를 조회할 수 있다.
자동 검사를 통과했으며 사용자는 아래 동선으로 명령 결과를 확인할 수 있다.

## 목적

provider 중립 런타임의 안정적인 제어 표면과 상태 저장 기반을 만든다. 앱은 운영체제별 내부 파일이나
`state.json`의 비계약 필드를 읽지 않고, `heartbeat agent`의 JSON 요청·응답만 사용한다. 이 작업은
provider 프로세스를 실행하거나 작업을 배정하지 않고 이후 작업이 사용할 계약과 저장소를 완성한다.

## 아키텍처 결정

- 앱과 런타임은 로컬 소켓 대신 버전화된 JSON CLI로 통신한다. 기존 앱이 고정 인자 프로세스를 안전하게
  실행하는 구조를 재사용할 수 있고, macOS·Linux·Windows에서 별도 IPC 권한과 수명 주기를 만들지
  않기 때문이다.
- 변경 요청은 JSON 한 건을 표준 입력으로 받고 응답은 JSON 한 건을 표준 출력으로 낸다. 진단 문구는
  표준 오류로 분리한다. 명령줄에 프로젝트 경로나 prompt를 노출하지 않는다.
- 프로젝트 설정, 큐, 실행, 이벤트, 재시도 연결은 Python 표준 라이브러리 SQLite 데이터베이스에
  저장한다. WAL과 짧은 트랜잭션으로 데몬과 제어 CLI의 동시 접근을 직렬화한다. 앱은 데이터베이스를
  직접 열지 않는다.
- 데이터베이스는 프로젝트의 안정적인 `projectId`를 기본 키로 삼고 실제 `workingDirectory`를 별도
  값으로 보관한다. slug 역변환은 새 계약에 없다.

## 계약 범위

계약 문서와 타입은 최소한 다음을 정의한다.

1. `apiVersion`과 `runtimeVersion`, 요청 식별자, 프로젝트 식별자, 명령 종류, 성공·부분 성공·실패
   envelope.
2. 프로젝트 정책: 실제 작업 디렉터리, 프로젝트 최대 병렬 인원 기본값 3, 일시 정지 여부, 반복 정책.
3. 역할 정책: planner·architect·developer, provider, model, 실행 방식, 최대 병렬 인원 기본값 1,
   판정 간격, 실행 한도.
4. 기기 정책: 동시 실행 기본 상한 16. 첫 릴리스에서는 16 이하로만 변경할 수 있다.
5. 실행 상태: reserved, queued, running, paused, succeeded, failed, cancelled, recovery_required와
   상태 변경 시각, 대상 문서, 역할, provider, 이전 실행 식별자.
6. 제어 명령: 계약 조회, 설정 읽기·검증·저장, 상태 조회, 실행 계획 조회, 시작, 일시 정지·재개,
   취소, 재시도, 로그 조회, provider 진단. 이 작업에서는 계약·설정·빈 상태 조회를 구현하고 실행
   동작은 후속 작업이 채운다.
7. 오류 단계: request_validation, reservation, provider_start, role_session, cleanup, recovery.
8. 모르는 필드의 처리와 하위호환 규칙. 같은 주 버전의 응답에서 모르는 선택 필드는 무시하고,
   지원하지 않는 주 버전은 실행 전에 거절한다.

## 저장소 규칙

- 프로젝트별 설정, 큐, 반복 상태, 실행 이력, 오류를 `projectId`로 분리한다.
- 쓰기 트랜잭션은 원자적이다. 잘못된 설정 하나가 다른 프로젝트의 읽기와 실행을 막지 않는다.
- prompt 원문, provider 인증 토큰, API 키, 전체 환경 변수는 저장하지 않는다.
- 로그 메타데이터와 실행 이벤트는 보존 기한을 갖고 정리할 수 있어야 한다. 기본 보존값은 계약 문서에
  적되 실행 결과를 검증하는 동안 필요한 최근 기록은 남긴다.
- 데이터베이스 스키마 버전은 런타임이 소유한다. 앱이 직접 마이그레이션하지 않는다.
- 기존 Heartbeat `state.json`과 jobs.d는 하위호환 입력일 뿐 새 에이전트 상태의 원천이 아니다.

## 손대지 않는 것

- Claude·Codex 프로세스 시작과 구조화 출력 해석
- 자동·수동 대상 배정과 lease 획득
- 운영체제 서비스 등록과 독립 실행형 패키징
- 앱 저장소와 화면
- Dream의 설정, prompt, quota, 실행 이력

## 완료 조건

1. `heartbeat agent contract`가 지원하는 계약 버전과 런타임 버전을 JSON으로 반환한다.
2. 설정 요청은 `projectId`와 실제 작업 디렉터리를 필수로 요구하며 slug만 있는 요청을 거절한다.
3. 역할별 provider, model, 실행 방식, 최대 병렬 인원과 프로젝트·기기 상한을 저장하고 다시 읽으면
   같은 값이 나온다.
4. 역할 상한 기본값은 1, 프로젝트 상한 기본값은 3, 기기 상한 기본값은 16이다.
5. 기기 상한을 16보다 크게 올리는 요청과 알 수 없는 역할·provider·실행 방식은 쓰기 전에 거절된다.
6. 두 프로젝트를 동시에 갱신해도 설정, 큐, 상태, 오류가 섞이지 않는다.
7. 같은 프로젝트를 데몬과 제어 CLI가 동시에 갱신해도 데이터베이스가 깨지거나 일부 행만 반영되지
   않는다.
8. 앱이 알아야 하는 상태는 모두 JSON 계약으로 조회할 수 있고 내부 테이블 이름이나 파일 형식에
   의존하지 않는다.
9. 응답이 성공·부분 성공·실패와 실패 단계를 구분한다.
10. 데이터베이스와 로그에 prompt 원문, 인증 토큰, API 키가 기록되지 않는다.
11. 기존 jobs.d 잡 파싱과 Heartbeat 명령이 변경 전과 같이 동작한다.
12. 기존 자동 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. 계약 문서의 모든 요청·응답 예시를 스키마 검증기에 통과시킨다.
2. 임시 홈에서 두 프로젝트와 세 역할 설정을 저장하고 프로세스를 다시 시작한 뒤 같은 값이 복원되는지
   확인한다.
3. 잘못된 버전, 중복 역할, 존재하지 않는 작업 디렉터리, 상한 초과, 잘못된 실행 방식 요청이 아무
   상태도 바꾸지 않는지 확인한다.
4. 프로세스 여러 개가 같은 프로젝트와 다른 프로젝트를 동시에 갱신하는 경합 검사를 반복 실행한다.
5. 데이터베이스와 JSON 응답을 검색해 주입한 가짜 prompt·토큰·키가 남지 않는지 확인한다.
6. `pytest tests/test_agent_contract.py tests/test_agent_store.py tests/test_agent_cli.py -v`를 실행한다.
7. `pytest tests/ -v`를 실행한다.

## 범위와 선행

선행 작업은 없다. TASK-S051-01과 파일이 겹치지 않아 병렬로 진행할 수 있다. provider와 dispatcher는
이 작업의 계약과 저장소가 완료된 뒤 구현한다.

## 확인 동선

화면이 없는 명령 계약 작업이다. 자동 검사와 다음 명령 결과로 확인한다.

1. 터미널 → `heartbeat agent contract` 실행 → 성공 결과에 지원 버전, 런타임 버전, 역할·provider 목록과 기본 상한이 표시된다.
2. 임시 저장소를 지정하고 유효한 세 역할 설정을 `heartbeat agent config write`에 JSON으로 전달 → 성공 결과가 저장한 설정을 그대로 반환한다.
3. 같은 프로젝트 식별자로 `heartbeat agent state` 실행 → 앞 설정과 빈 큐·실행·오류 목록이 JSON으로 표시된다.
4. `pytest tests/test_agent_contract.py tests/test_agent_store.py tests/test_agent_cli.py -v` 실행 → 27개 검사가 모두 통과한다.
