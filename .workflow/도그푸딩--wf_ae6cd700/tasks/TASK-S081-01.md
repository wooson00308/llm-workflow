# 선점 갱신과 실행 기록을 겹쳐 앱 밖 세션의 표시를 정하는 판정 단위를 만든다

## 결정권자 요약

### 제안

앱 밖 세션 하나를 정상 줄과 카드 중 어디에 둘지, 어떤 근거를 함께 보일지 정하는 판정을 화면과 분리된
단위 하나로 만든다.

### 바뀌는 것

- 지금: 신호가 10분 넘게 없으면 그 사실 하나로 경고 카드다 → 앞으로: 실행 기록이 생존을 말하면 정상 줄,
  앱이 생존 근거를 하나도 확인하지 못했을 때만 카드라는 판정이 선다

### 비용과 위험

- 새 판정이 자기 자리에 서고 화면은 아직 옛 판정을 쓰므로, 두 판정이 잠시 함께 남는다.
- 이 작업만으로는 화면이 달라지지 않고, 목록에 붙이는 일은 같은 기능의 다음 작업이 맡는다. 화면 코드와
  스타일을 하나도 건드리지 않으므로 되돌리려면 새로 만든 파일 둘을 지우면 된다.

## 현재 코드 상태

앱 밖 세션 목록의 판정은 지금 화면 파일 안에 함수 하나로만 있다.
`src/features/projects/components/agents/AgentRunDashboard.tsx` 715행의 `leaseIsStale`이
`heartbeatAt`을 파싱해 지금과의 차이가 `10 * 60_000`을 넘는지만 본다. 127행이 그 판정으로
`attentionLeases`(카드)와 `healthyLeases`(정상 줄)를 가르고, 200행이 카드에 `신호 지연` 문구를 붙인다.
근거는 선점 갱신 시각 하나뿐이고 실행 기록은 이 판정에 참여하지 않는다.

판정에 겹칠 두 번째 근거는 이미 앱 안에 있다.

- 실행 행: `state.queue.runs`가 프로젝트의 실행 전체를 싣는다. 형태는
  `src/features/projects/domain/types.ts` 1621행의 `AgentRunSummary`이고, 이 작업이 쓰는 값은
  `state`, `reason`, `targetId` 셋이다. 상태값 아홉 개는 같은 파일 1610행의 `AgentRunStatus`가 정한다.
- 마지막 활동 시각: `src/features/projects/domain/runActivity.ts` 132행의 `summarizeRunActivity`가
  이벤트 묶음에서 `lastActivityAt`을 계산한다. 이벤트에 절대 시각 필드가 없어 같은 파일 126행의
  `eventOccurredAt`이 실행 시작 시각과 경과 초를 더해 만든 값이다. 지금 이 값을 쓰는 자리는 실행 상세
  화면 하나뿐이다(`AgentRunDashboard.tsx` 403행).

선점과 실행을 잇는 열쇠는 문서 식별자다. 같은 파일 640행의 `runRoleByTarget`이 이미 그 방식으로 역할을
채우고 있으며, 선점 기록의 `taskId`와 실행 행의 `targetId`를 맞춘다. `AgentRunSummary`에는 선점 식별자
필드가 없으므로(`src-tauri/src/domain/agent_runtime.rs` 695행) 다른 열쇠는 없다.

기획서가 말하는 상태 이름과 코드의 상태값 대응은 다음과 같다. `src-tauri/src/domain/agent_runtime.rs`
661행의 `RunState`와 `AgentRunDashboard.tsx` 38행의 `stateLabels`를 대조해 확인했다.

- 앱이 진행 중으로 묶어 보여주는 넷(배정 중, 시작 대기, 진행 중, 일시 정지)은 `reserved`, `queued`,
  `running`, `paused`다. 같은 파일 47행의 `activeStates`가 이미 이 넷을 묶고 있다.
- 세션 자신의 결과로 끝난 상태는 `succeeded`(완료), `failed`(실패), `cancelled`(취소됨) 셋이다.
- 기획서가 종료에 함께 넣은 `시간 초과`는 실행 상태가 아니다. `RunState`에 그런 값이 없고, 시간 초과는
  실행 기록의 신호 종류로만 남는다(`runActivity.ts` 51행의 `RunSignalKind`, `AgentRunDashboard.tsx`
  55행의 `signalLabels`). 시간 초과로 끝난 실행은 상태값으로는 `failed`로 온다. 새 상태값을 만들지 않는다.
- `recovery_required`(복구 필요)와 `unrecognized`(상태 확인 필요)는 세션의 결과가 아니라 앱 쪽 사정이다.
  복구 필요는 앱이 실행을 취소하다가 프로세스 종료나 선점 반납에 실패했을 때 남는 상태이고
  (`docs/agent-runtime.md` 90행), 상태 확인 필요는 계약 밖 상태값이 왔을 때 앱이 붙이는 값이다
  (`RunState`의 `#[serde(other)]`).

기획서가 근거로 든 2026-08-18 사고의 실제 값도 확인했다. 그날 종료 처리된 실행 기록
21건이 모두 `reason: supervisor_identity_unverified`를 달고 있다
(`.workflow/.runtime/silent-runs/*.json`). 이 사유는 화면에서도 이미 앱 쪽 사정으로 옮겨지고 있으며,
`AgentRunDashboard.tsx` 825행이 `supervisor_identity_unverified`와 `handle_mismatch`를
`세션 정리를 안전하게 미뤘습니다. 선점이 만료되면 자동으로 다시 배정됩니다.`로 바꾼다. 상태값이
`failed`나 `cancelled`로 와도 이 사유가 붙어 있으면 세션이 스스로 끝난 것이 아니다.

## 변경 범위

새 파일 `src/features/projects/domain/externalSessionHealth.ts`를 만들고, 아래 완료 조건이 정한 판정을
그 안에 둔다. 화면 파일과 실행 기록 파일은 읽기만 하고 고치지 않는다. 새 파일의 시험은
`src/features/projects/domain/externalSessionHealth.test.ts`에 쓴다.

판정 함수는 화면 형태를 모르고 값만 받는다. 받는 값은 넷이다.

- 선점 갱신 시각(`heartbeatAt`) 원문 문자열
- 지금(밀리초)
- 그 선점의 대상 문서를 맡은 실행 행 하나 또는 없음. 실행 행에서 쓰는 값은 `state`와 `reason` 둘뿐이다.
- 그 실행의 활동 기록 조회 결과. 읽었으면 마지막 활동 시각(없을 수 있음), 읽지 못했으면 읽지 못했다는 사실

돌려주는 값은 표시에 필요한 사실만 담는다. 문구 문자열과 CSS 클래스 이름은 담지 않는다. 문구를 짓는
일은 화면의 몫이고, 이 단위는 어느 줄에 서는지와 어떤 근거를 말할지를 정한다.

## 범위 밖

- 화면 파일 `src/features/projects/components/agents/AgentRunDashboard.tsx`. 715행의 `leaseIsStale`을
  지우거나 새 판정으로 갈아 끼우는 일, `신호 지연` 문구를 바꾸는 일, 근거 줄을 그리는 일은 모두 같은
  기능의 다음 작업이 맡는다. 이 작업이 함께 고치면 두 작업의 파일이 겹친다.
- 스타일 파일 `src/App.css`. 이 작업은 화면 요소를 하나도 만들지 않는다.
- 활동 기록을 실제로 읽어 오는 경로. 조회는 다음 작업이 만들고, 이 작업은 조회 결과를 값으로 받는
  자리까지만 정한다.
- `src/features/projects/domain/runActivity.ts`. `summarizeRunActivity`와 `eventOccurredAt`을 그대로
  쓰며 고치지 않는다. 같은 파일 91행의 `IDLE_THRESHOLD_SECONDS`는 실행 상세 화면의 활동 없음 표시가
  쓰는 5분 기준이고, 기획서 제외 범위가 그 화면과 기준 시간을 바꾸지 않는다고 못 박았다. 이 작업의
  10분 기준으로 재사용하지 않는다.
- 선점 기록 파일. 읽지도 쓰지도 않는다. 이 판정은 앱이 이미 메모리에 들고 있는 값만 본다.
- 앱이 돌린 실행이 잡은 대상을 앱 밖 세션 목록에서 빼는 기준. SPEC-069가 정한 대로 두며, 그 판정은
  `AgentRunDashboard.tsx` 104행부터 107행에 그대로 남는다.
- 목록의 정렬, 접힘 규칙, 역할 칩, 역할별 개수 요약.

## 완료 조건

- C1. `externalSessionHealth.ts`가 판정 함수 하나와 그 결과 타입을 내보낸다. 함수는 위 변경 범위가
  적은 네 값을 받고, 화면 문구와 CSS 클래스 이름을 하나도 담지 않은 결과를 돌려준다.
  (기획서 R1)
- C2. 결과에는 최소한 이 셋이 들어 있다. 정상 줄과 카드 중 어디에 서는지, 기획서가 정한 세 값
  (생존, 종료, 확인 불가) 중 무엇인지, 카드일 때 어떤 종류의 근거를 말해야 하는지. 근거 종류는 셋이고
  각각 실행이 종료로 남음, 앱에 실행 기록 없음, 앱 쪽 운영 사유로 종료 처리됨이다. 마지막 활동 시각을
  함께 말해야 하는 근거에는 그 시각도 결과에 실린다. (기획서 R5, R6)
- C3. 선점 갱신이 10분 이내인 선점은 실행 기록을 보지 않고 정상 줄이며, 덧붙이는 보조 문구가 없다는
  결과가 나온다. 이 판정은 지금의 `leaseIsStale`과 같은 값을 낸다. 갱신 시각을 파싱하지 못한 선점은
  지금과 같이 뜸하지 않은 것으로 다룬다. (기획서 R10, 완료 판정 A6)
- C4. 갱신이 10분을 넘고 실행 행의 상태가 `reserved`, `queued`, `running`, `paused` 중 하나이면
  생존이고 정상 줄이다. 이때 마지막 활동 시각과 활동 공백 길이는 보지 않으며, 활동 기록을 읽지 못한
  경우에도 결과가 같다. (기획서 R2, R3, 완료 판정 A1)
- C5. 갱신이 10분을 넘고 실행 행의 상태가 `succeeded`, `failed`, `cancelled` 중 하나이며 그 실행이
  아래 C6의 운영 사유에 해당하지 않으면 종료이고 카드다. 근거 종류는 실행이 종료로 남음이고, 결과에
  그 실행의 상태값과 마지막 활동 시각이 실린다. 마지막 활동 시각을 읽지 못했거나 값이 없으면 그
  사실이 결과에 남고 판정 자체는 바뀌지 않는다. (기획서 R3, 완료 판정 A2)
- C6. 다음 중 하나에 해당하는 실행은 앱 쪽 운영 사유로 종료 처리된 것으로 본다. 상태가
  `recovery_required`이거나 `unrecognized`인 경우, 그리고 상태와 상관없이 `reason`이
  `supervisor_identity_unverified` 또는 `handle_mismatch`인 경우다. 이 판정은 상태값 판정보다 앞선다.
  (기획서 R4)
- C7. C6에 해당하는 실행은 마지막 활동으로 가른다. 활동 기록을 읽었고 마지막 활동이 10분 이내이면
  생존이고 정상 줄이다. 활동 기록을 읽었으나 마지막 활동이 10분보다 오래됐거나 활동 시각 자체가 없으면
  확인 불가이고 카드이며, 근거 종류는 앱 쪽 운영 사유로 종료 처리됨이다.
  (기획서 R4, 완료 판정 A4, A5)
- C8. C6에 해당하는 실행의 활동 기록을 읽지 못한 경우는 확인 불가이고 카드다. 활동이 없는 것으로 세지
  않는다는 뜻이며, 근거 종류는 C7의 카드와 같다. (기획서 R9)
- C9. 갱신이 10분을 넘고 그 선점의 대상을 맡은 실행 행이 없으면 확인 불가이고 카드이며, 근거 종류는
  앱에 실행 기록 없음이다. 생존 쪽으로 추정하지 않는다. (기획서 R7, 완료 판정 A3)
- C10. 갱신이 뜸하다고 보는 기준과 마지막 활동이 최근인지 보는 기준이 둘 다 10분이고, 파일 안에서 같은
  상수 하나를 쓴다. 실행 상세 화면의 5분 기준을 가져다 쓰지 않는다. (기획서 R8)
- C11. 이 작업의 변경이 선언한 두 파일 안에서 끝난다. 화면 파일, 스타일 파일, 실행 기록 파일, 백엔드
  코드가 수정되지 않는다. (완료 판정 A8)
- C12. `npm run check`가 통과한다.

## 검증 절차

1. `externalSessionHealth.test.ts`에 완료 판정 A1부터 A5까지를 각각 하나 이상의 시험으로 옮긴다.
   시험 이름에 어떤 완료 판정을 확인하는지 적는다.
   - A1: 상태가 `running`인 실행 행과 갱신이 20분 지난 선점 → 정상 줄, 생존. 같은 입력에서 활동 기록을
     읽지 못한 경우에도 결과가 같은지 함께 확인한다(C4).
   - A2: 상태가 `succeeded`인 실행 행과 마지막 활동이 12분 전 → 카드, 종료, 근거 종류는 실행이 종료로
     남음이며 결과에 상태값과 활동 시각이 실린다. `failed`로도 같은 확인을 한다(C5).
   - A3: 실행 행 없음, 갱신 12분 경과 → 카드, 확인 불가, 근거 종류는 앱에 실행 기록 없음(C9).
   - A4: `reason`이 `supervisor_identity_unverified`인 `failed` 실행 행과 마지막 활동 3분 전 →
     정상 줄, 생존(C6, C7). 상태가 `recovery_required`인 경우로도 같은 확인을 한다.
   - A5: 같은 실행 행에서 마지막 활동만 21분 전으로 바꾼다 → 카드, 확인 불가, 근거 종류는 앱 쪽 운영
     사유로 종료 처리됨(C7).
2. 경계와 예외를 확인하는 시험을 더한다. 갱신이 정확히 10분일 때와 10분을 막 넘겼을 때(C3, C10),
   갱신이 9분이면 실행 행이 무엇이든 정상 줄이고 보조 문구가 없다는 것(C3), 활동 기록을 읽었으나
   활동 시각이 없는 운영 사유 실행이 카드라는 것(C7), 활동 기록을 읽지 못한 운영 사유 실행이 카드라는
   것(C8), 갱신 시각을 파싱하지 못한 선점이 정상 줄이라는 것(C3).
3. `npm run test -- externalSessionHealth`로 위 시험이 전부 통과하는 것을 확인한다.
4. `npm run check`를 통과시킨다(C12).
5. `git status`로 선언한 두 파일 밖의 수정이 없음을 확인한다(C11).

## 범위 사전 검사

선언한 파일 둘은 모두 이 작업이 새로 만드는 것이다. 판정에 필요한 값이 전부 함수 인자로 들어오도록
설계했기 때문에, 완료 조건을 채우는 데 기존 파일의 편집이 하나도 필요하지 않다. 아래 값 경로로 그것을
하나씩 확인했다.

`src/features/projects/components/agents/AgentRunDashboard.tsx`를 열어 보고 뺐다. 715행의
