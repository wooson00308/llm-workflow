# 기획 승인과 작업 QA에서 결정 보드의 종단 계약을 검증한다

## 결정권자 요약

기획 승인과 개발 작업 QA의 실제 화면에서 결정 보드와 기존 조작이 함께 작동함을 검증했다.
새 구조, 기존 평문과 불완전한 문서의 폴백을 두 화면에서 고정하는 회귀 검사가 통과했다.
사용자는 키보드로 원문과 결정 도구에 도달하고 화면 종류에 맞는 판단 요청을 읽을 수 있다.
이 작업은 제품 동작을 더하지 않고 두 검토 흐름의 출시 기준을 자동 검사로 고정한다.

## 목적

TASK-S052-03의 보드가 실제 기획서 검토와 단건 개발 작업 QA 화면에서 승인된 요구사항을 충족하는지
두 기존 컴포넌트 테스트에 종단 픽스처를 추가한다. 이 작업은 화면 구현을 고치지 않는다. 실패가
`DocumentReader`나 보드 구현 결함을 드러내면 범위를 넓혀 우회하지 않고 TASK-S052-03의 수정 요청으로
돌려보낸다.

## 기획서 검토 시나리오

구조화된 새 기획서를 열었을 때 제안, 현재, 변경 후, 사용자 결과, 변경·유지 영향, 선택적 위험과
결정 요청이 보이고 기존 승인·수정 요청·폐기 조작도 같은 화면에 있어야 한다. 결정 요청은 기획서에서
무엇을 승인하거나 수정할지 말하며 승인 후 결과와 유지 영역을 함께 제공한다.

원문 토글을 키보드로 열면 요약을 포함한 전체 기획서가 보이고 결정 조작은 그대로 도달 가능해야 한다.
평문 요약, 필수 제목 하나가 빠진 구조와 요약 절이 없는 기존 기획서는 각각 기존 요약 또는 전체 원문
경로로 열리고, 앱이 빠진 값을 만들거나 오류 문구를 붙이지 않아야 한다.

## 개발 작업 QA 시나리오

구조화된 `qa_waiting` 작업을 열었을 때 결정 요청은 사용자가 QA에서 확인할 결과를 말하고, 변화 흐름과
영향 범위가 기존 확인 동선·메모·확인·반려 조작과 같은 화면에서 읽혀야 한다. 확인 동선 절은 현재처럼
QA 패널에 한 번만 나타나고 원문 토글을 열면 전체 Markdown 안에서도 확인할 수 있어야 한다.

평문 또는 불완전 구조의 작업은 기존 Markdown 요약으로 폴백하며 QA 조작과 기록 인자가 달라지지
않는다. `qa_waiting`이 아닌 작업의 비활성 QA 안내도 그대로다. 일괄 QA 화면은 SPEC-052의 변경 범위가
아니므로 기존 검사가 수정 없이 통과해야 한다.

## 완료 조건

1. 구조화된 기획서와 개발 작업 픽스처가 각 화면에서 전용 보드를 표시하고, 기획서는 승인 판단,
   작업은 QA 확인 판단을 `결정 요청`으로 보여 준다. (R1·R2)
2. 기획서의 승인·수정 요청·폐기와 작업의 확인·반려 조작이 보드와 함께 존재하고 기존 callback 인자와
   활성 조건을 유지한다. (R2·R4)
3. 키보드로 원문 토글과 기존 결정 조작에 도달하고, 시각 순서와 같은 DOM 순서에서 보드 제목과 값을
   읽을 수 있다. (R4)
4. 원문 토글은 두 화면에서 구조화 요약을 포함한 전체 Markdown을 표시하며 확인 동선 이동 계약도
   유지한다. (R3·R4)
5. 평문 요약, 불완전 구조와 무요약 문서 픽스처가 각각 기존 요약 또는 원문 폴백을 확인한다. 빈 카드,
   자동 보완과 오류 경고가 없다. (R3)
6. 위험 없는 픽스처에 위험 영역이 없고, 위험 있는 픽스처에서는 결정 조작과 함께 읽힌다. (R1·R4)
7. 기획서 결정, 단건 QA, 비활성 QA와 일괄 QA의 기존 자동 검사가 삭제·완화되지 않고 통과한다.
8. 렌더만으로 gateway, 파일 쓰기, 네트워크 또는 LLM 호출이 발생하지 않는다. 새 mock 요청이 필요하지
   않아야 한다. (R5)
9. `npx vitest run src/features/projects/components/SpecWorkspace.test.tsx
   src/features/projects/components/DevelopmentBoard.test.tsx`와 `npm run check`이 통과한다.
10. 변경분은 두 테스트 파일뿐이며 제품 소스나 기존 문서를 수정하지 않는다.

## 검증 절차

1. 두 화면에 완전한 구조, 위험 없는 구조, 필수 항목이 빠진 구조와 평문 요약 픽스처를 각각 연다.
2. `userEvent.tab()`과 키보드 활성화로 원문 토글 및 결정 조작의 도달성과 기존 callback을 확인한다.
3. 작업 화면에서 확인 동선이 기본 화면에 중복되지 않고 QA 패널 및 원문 전문에 남는지 확인한다.
4. 지정한 두 테스트 파일과 `npm run check`을 실행한다.
5. 변경분에서 기존 결정·QA·일괄 QA 테스트의 삭제나 완화가 없는지 확인한다.

## 확인 동선

기획서 검토 화면에서 구조화된 기획서를 열고 결정 보드, `원문 전문 보기`, 승인·수정 요청·폐기 조작을 확인한다. 개발 작업 화면에서 구조화된 `qa_waiting` 작업을 열고 결정 보드, 확인 동선, 원문, 확인·반려 조작을 키보드로 이동한다. 완전 구조는 전용 보드로 열리고, 위험이 없으면 위험 영역이 없어야 하며, 불완전·평문·무요약 문서는 기존 요약 또는 원문으로 열려야 한다.
