# 확인 동선의 낱말 대조가 어미가 바뀐 형태를 같은 낱말로 인식한다

## 결정권자 요약

### 제안

확인 동선을 사용자 확인 절차로 인정하는 낱말 대조를 고쳐서, 어미가 달라진 평범한 관찰 서술도 같은
낱말로 인식하게 한다.

### 현재

낱말 목록에는 낱말마다 활용형이 하나씩만 들어 있고, 그 글자열이 본문에 그대로 있는지만 본다. 그래서
보입니다는 인정되고 보인다는 인정되지 않는다. 개발이 끝난 기능 하나가 이 이유로 구성 확인 필요에
멈춰 있고, 사용자는 그 기능의 품질 확인을 열 방법이 없다.

### 변경 후

같은 낱말은 어미가 달라져도 같은 낱말로 읽힌다. 멈춰 있던 그 기능은 문서를 한 글자도 고치지 않고
판정을 통과해 지금 확인할 기능 목록으로 올라오고, 앞으로 자연스러운 한국어로 쓴 확인 동선이 문장
표현 때문에 막히는 일이 없어진다.

### 비용과 위험

넓히는 것은 낱말을 알아보는 범위 하나다. 개발자용 절차와 코드 블록을 걸러내는 차단, 화면과 행동과
결과 셋을 모두 말해야 한다는 규칙, 기능 상태를 정하는 나머지 조건은 그대로 둔다. 판정이 넓어진 만큼
덜 다듬어진 동선이 통과할 여지가 생기지만, 그때 사용자는 확인 화면에서 수정 요청으로 되돌릴 수
있다. 화면과 기능 문서는 건드리지 않고 판정 한 곳만 바꾸므로 되돌리기도 쉽다.

## 현재 코드 상태

판정은 `src-tauri/src/infrastructure/fs_project_repository.rs` 한 파일에 있다.

`scenario_describes_user_observable_flow`가 3399행이다. 본문을 `to_ascii_lowercase`로 한 번 낮춘 뒤
세 낱말 목록과 대조한다. 화면 목록이 3401행, 행동 목록이 3446행, 결과 목록이 3479행이고, 세 목록
모두 `lowered.contains(token)`으로만 맞춘다. 3515행이 세 결과를 그리고 곱한다.

`scenario_is_user_safe`가 3390행이다. 본문이 비었거나 코드 울타리를 담고 있으면 먼저 거절하고,
제목과 본문에 `contains_internal_qa_instruction`이 걸리지 않으면서 위 함수가 참을 낼 때만 참을
낸다. `contains_internal_qa_instruction`은 3518행이며 이 작업에서 고치지 않는다.

이 판정을 부르는 자리는 같은 파일에 둘이다. 3236행의 기능 표시 상태 계산이 하나다. 사용자 확인 모드
기능에서 확인 동선이 비었거나 하나라도 인정되지 않으면 구성 확인 필요로 내려가고, 그렇지 않으면
사용자 QA 대기가 된다. 1606행의 옛 계약 작업 확인 동선 이관이 다른 하나다.

결과 목록이 왜 떨어지는지는 한글 표기 때문이다. 목록의 "보이"는 "보이고"와 "보입니다"의 앞 두 글자와
글자열이 같아 걸리지만, "보인다"는 "인"이라는 한 글자 안에 종성이 들어가 있어서 "보이"라는 글자열을
포함하지 않는다.

GROUP-070이 실측 사례다. 그 확인 동선 본문은 화면 조건과 행동 조건을 만족하고 결과 조건 하나만
떨어진다. 본문이 쓰는 서술은 보인다, 같아진다, 적혀 있고, 남아 있지, 열리고, 바뀐다, 나오는이며,
결과 목록 32개 가운데 걸리는 것이 하나도 없다.

## 변경 범위

- 세 낱말 목록의 대조 방식을 바꾼다. 지금의 글자열 포함 검사를 먼저 그대로 해 보고, 걸리지 않을
  때만 어미 변화를 견디는 대조를 한 번 더 한다. 먼저 하는 검사를 그대로 두는 것이 지금 통과하던
  문장이 계속 통과한다는 보증이다.
- 어미 변화를 견디는 대조는 이렇게 판정한다. 낱말과 본문을 각각 초성·중성·종성으로 풀고, 낱말이
  본문의 어느 글자 경계에서 시작해 끝까지 이어지는지를 본다. 낱말이 끝나는 글자에 남는 것이 종성
  하나뿐이면 같은 낱말로 인정하고, 초성이나 중성이 남으면 인정하지 않는다. 이렇게 하면 "보이"가
  "보인다"와 "보입니다"에는 걸리고, "창"이 "차이"에는 걸리지 않는다.
- 한글이 아닌 글자는 이 대조에서 지금과 같이 글자 하나씩 그대로 맞춘다. 목록에 함께 들어 있는 영어
  낱말의 판정이 달라지지 않아야 한다.
- 결과 목록에 낱말을 더한다. 적혀, 열리, 나오, 바뀌, 같아지, 남아 여섯이다. 위 대조와 합쳐지면
  적혀 있다, 열린다, 나온다, 바뀐다, 같아진다, 남아 있다가 모두 결과로 인정된다. 나머지 넷은 지금
  목록의 보이, 보여, 나타, 표시, 사라로 이미 덮인다.
- 개발자용 절차 차단, 코드 울타리 거절, 빈 본문 거절, 세 조건을 모두 만족해야 한다는 규칙은 손대지
  않는다.

## 범위 밖

- 구성 오류의 사유를 화면에 사용자 언어로 보여주는 일과 그 상태를 아키텍트에게 자동으로 넘기는 일.
  SPEC-073에서 나온 GROUP-073이 맡는다.
- GROUP-070을 비롯한 기능 문서의 확인 동선 문장을 판정에 맞추어 고치는 일. 기획서 REQ-05가 문서를
  고쳐서 해결하지 않는다고 정했다.
- 기능 표시 상태를 정하는 나머지 조건. 문서 구조 유효성, 작업의 구성 버전 일치, 자동 확인 모드의
  규칙, 작업 상태 조건은 지금 그대로 둔다.
- 개발자용 절차를 걸러내는 검사의 낱말 목록과 판정 방식.
- 영어로 쓴 확인 동선의 판정 동작.
- 확인 동선을 쓰는 방법에 대한 규약 문서.

  확인 문장이 모두 결과 조건을 만족한다. (기획서 REQ-01)

  둘이 지금 방식으로 남아 있지 않다. (기획서 REQ-01)
- C3. 다음 열 가지 서술이 결과로 인정된다. 보인다, 나타난다, 표시된다, 적혀 있다, 열린다, 나온다,
  바뀐다, 같아진다, 남아 있다, 사라진다. (기획서 REQ-02)

  모두 만족하고, 그 본문을 담은 사용자 확인 모드 기능의 표시 상태가 사용자 QA 대기가 된다.
  (기획서 REQ-02 수용 기준, REQ-05 수용 기준)

  화면 문장들이 변경 후에도 인정된다. (기획서 REQ-03)
- C6. 터미널 명령, 패키지 실행기 호출, 저장소 조작 지시, 내부 자동 시험 절차가 섞인 확인 동선과 코드
  울타리를 담은 확인 동선이 변경 후에도 인정되지 않는다. 본문이 빈 확인 동선도 인정되지 않는다.

- C7. "백엔드 로직이 올바르게 동작한다."처럼 화면도 사용자 행동도 말하지 않는 문장은 결과 낱말이
  있어도 인정되지 않는다. (기획서 REQ-04)
- C8. 넓힌 대조가 글자 경계를 지킨다. "창"이 "차이"에, "앱"이 "애매"에 걸리지 않는다. 낱말이 끝나는
  글자에 초성이나 중성이 남는 경우는 같은 낱말로 인정하지 않는다.
- C9. 이 작업의 변경은 선언한 파일 하나 안에서 끝난다. 기능 문서, 화면 코드, 프론트 계약 타입이
  수정되지 않는다. (기획서 REQ-05)

## 검증 절차

1. 판정 함수가 있는 파일의 시험 모듈에 시험을 더한다. C1의 네 형태, C3의 열 가지 서술, C8의 글자
   경계 사례를 각각 확인 문장으로 만들어 결과 조건 판정에 넣고 기대값을 확인한다. 화면 낱말과 행동
   낱말도 어미가 바뀐 형태로 하나씩 넣어 C2를 확인한다.
2. C4를 확인하는 시험을 더한다. GROUP-070 문서의 확인 동선 본문을 그대로 옮겨 적은 문자열을 판정에
   넣어 참이 나오는지 보고, 그 본문을 확인 동선으로 담고 소속 작업이 모두 검증인 사용자 확인 모드
   기능 픽스처의 표시 상태가 사용자 QA 대기로 나오는지 확인한다. 픽스처를 만드는 방식은 같은 시험
   모듈의 기존 기능 픽스처 도우미를 따른다.
3. 11945행의 기존 시험 `nondeveloper_scenarios_accept_visible_ui_flows_and_reject_cli_instructions`를
   고치지 않고 통과시킨다. C5, C6, C7이 이 시험과 새로 더한 시험으로 덮인다.
4. `cargo fmt --check`와 `cargo clippy --all-targets -- -D warnings`를 통과시킨다.
5. `cargo test --manifest-path src-tauri/Cargo.toml`을 전체 통과시킨다.
6. `npm run check`를 통과시킨다. 이 작업은 화면을 고치지 않으므로 기존 시험이 그대로 통과해야 한다.
7. 앱을 띄워 품질 확인 화면을 열고, GROUP-070이 준비 중인 기능 목록의 구성 확인 필요 자리에서
   빠지고 지금 확인할 기능 목록에 확인 시작 입구와 함께 서는지 눈으로 확인한다. 확인한 화면을
   보고서에 적는다.

## 범위 사전 검사

선언한 파일은 `src-tauri/src/infrastructure/fs_project_repository.rs` 하나다. 고칠 함수와 그 함수를
부르는 두 자리와 시험 모듈이 모두 이 파일 안에 있어서, 완료 조건이 요구하는 편집이 밖으로 나가지
않는다. 3399행의 판정 함수와 3401행·3446행·3479행의 세 목록이 편집 대상이고, 어미 변화를 견디는
대조를 하는 도우미도 같은 파일에 둔다. 11636행부터의 시험 모듈이 시험을 더할 자리다.

`src-tauri/src/domain/project.rs`를 살펴보고 뺐다. 287행이 표시 상태 값을 정의하고 사용자 QA 대기
값이 이미 거기 있다. 이 작업은 값을 새로 만들지 않고 판정이 답하는 쪽을 바꿀 뿐이므로 고칠 자리가
없다.

`src/features/projects/domain/types.ts`와 `src/features/projects/components/qa/QaWorkbench.tsx`도
살펴보고 뺐다. 타입 167행에 사용자 QA 대기 값이 이미 있고, 화면 19행이 그 값을 지금 확인할 기능
목록으로, 23행이 나머지를 준비 중인 기능 목록으로 가른다. 두 자리 모두 이 작업이 바꾸는 값을 지금
그대로 실어 나르므로 편집이 필요 없다.

`src-tauri/src/infrastructure/heartbeat_condition.rs`도 살펴보고 뺐다. 이 파일의 조건 스크립트는
역할 대상 판정을 하며 확인 동선의 낱말 대조를 들고 있지 않다. 확인 동선 판정은 선언한 파일 하나에만
있다.

TASK-S073-01이 같은 파일을 선언하고 있고 지금 준비 중이다. 겹침 선언이 두 작업의 동시 시작을 막고,
어느 쪽이 먼저 반영되어도 다른 쪽의 완료 조건이 달라지지 않아 `depends_on`을 두지 않았다. 그 작업이
고치는 자리는 3236행의 표시 상태 계산이고 이 작업이 고치는 자리는 3399행의 낱말 대조여서, 두 편집이
같은 함수에서 만나지 않는다.

- 값 경로: C4의 표시 상태. 값을 만드는 자리는 3399행의 판정 함수가 내는 참·거짓이고, 3390행의
  `scenario_is_user_safe`가 그것을 그대로 받아 확인 동선 하나의 인정 여부로 낸다. 두 자리 모두
  선언한 파일 안이고 앞의 것이 편집 대상이다. 그다음 자리는 같은 파일 3236행의 표시 상태 계산으로,
  사용자 확인 모드 기능에서 확인 동선 하나라도 인정되지 않으면 구성 확인 필요를, 모두 인정되면
  사용자 QA 대기를 답한다. 이 분기는 지금 코드가 이미 두 답을 모두 갖고 있어 편집하지 않는다.
  이어지는 자리는 `src-tauri/src/domain/project.rs` 287행의 표시 상태 값으로, 사용자 QA 대기가 이미
  정의되어 있어 값이 그대로 실린다. 프론트 계약은 `src/features/projects/domain/types.ts` 167행이
  같은 값을 이미 갖고 있고, 소비 자리는 `src/features/projects/components/qa/QaWorkbench.tsx` 19행과
  23행이 그 값으로 두 목록을 가르는 조건이다. 선언 밖 세 자리는 모두 이 작업이 새 값을 만들지 않기
  때문에 지금 코드가 그대로 실어 나르며, 편집이 필요 없다.
- 값 경로: C1과 C3의 인정되는 서술. 값을 만드는 자리는 3479행의 결과 낱말 목록과 새 대조 도우미이고
  둘 다 편집 대상이다. 소비 자리는 3515행에서 세 조건을 곱하는 식으로, 같은 함수 안이며 곱하는 규칙
  자체는 바꾸지 않는다. 이 값은 함수 밖으로 목록 모양 그대로 나가지 않고 참·거짓 하나로만 나가므로
  위의 값 경로에 합류한다.
- 값 경로: C2의 세 목록 적용. 만드는 자리는 3401행·3446행·3479행 세 목록이고 소비 자리는 각 목록의
  대조식이다. 세 자리 모두 같은 함수 안이고 모두 편집 대상이다. 도우미를 한 곳에만 붙이면 C2가
  떨어지므로 세 대조식을 함께 고친다.
- 값 경로: C6과 C7의 거절. 만드는 자리는 3518행의 개발자용 절차 검사와 3390행의 빈 본문·코드 울타리
  검사이고, 둘 다 이 작업에서 읽기만 한다. 소비 자리는 3394행에서 두 검사와 판정 함수를 곱하는
  식이다. 세 자리 모두 선언한 파일 안이고, 곱하는 순서와 조건을 바꾸지 않으므로 값이 그대로 남는다.
- 값 경로: C5의 기존 시험. 소비 자리는 11945행의 기존 시험이 판정 함수에 넣는 문장들이다. 이 문장
  들은 지금 글자열 포함 검사로 통과하고 있고, 새 대조는 그 검사가 떨어졌을 때만 덧붙어 도는 두 번째
  단계여서 통과하던 문장의 답이 달라지지 않는다. 시험 파일은 선언한 파일 안이며 기존 시험은 고치지
  않는다.
- 값 경로: C9의 문서 불변. 이 작업이 읽는 GROUP-070 본문은 시험 문자열로만 옮겨 적고, 기능 문서
  자체는 열어 고치지 않는다. 표시 상태가 바뀌는 것은 판정이 달라진 결과이며 문서가 달라진 결과가
  아니다.
