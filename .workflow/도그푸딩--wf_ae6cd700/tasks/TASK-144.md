# 막힌 사유 절을 추측 없이 읽는 로컬 파서를 만든다

## 결정권자 요약

막힌 작업 문서에 네 필수 항목이 정확히 있을 때만 화면이 사용할 값으로 분리한다.
제목이나 항목이 빠지거나 반복되면 일부 정보만 섞지 않고 기존 문서용 폴백을 선택하게 한다.
관련 대상은 작성 순서를 보존하고, 대상 없음도 작성자의 명시적인 값으로 구분한다.
코드 예시 안의 비슷한 제목과 라벨은 현재 사유로 잘못 읽지 않는다.
판정은 이미 읽어 온 문서에서만 수행하므로 네트워크나 인공지능 호출과 추가 저장이 없다.
기존 결정권자 요약 파서와 원문 절 분리 동작은 그대로 유지한다.
구현과 검증이 완료됐으며 집중 검사 68개와 전체 검사 820개 및 배포 빌드가 통과했다.
사용자는 아래 확인 동선의 자동 검사 결과를 검토해 QA하면 된다.

## 목적

SPEC-053의 R1, R3부터 R5까지가 사용할 결정적 읽기 계약을 구현한다. 앱은 문장의 의미를 해석하거나
불완전한 절에서 일부 필드를 추정하면 안 된다. 이미 읽은 Markdown 본문 하나를 입력으로 받아 유효한
현재 사유 전체 또는 실패만 반환하는 순수 로컬 파서를 만든다.

## 현재 상태

- `src/features/projects/domain/documentSections.ts`의 `splitSection`은 정확한 제목 하나의 절을 코드
  펜스 밖에서 분리하고 원문을 보존한다.
- 같은 모듈의 결정권자 요약 파서는 구조 전체가 유효할 때만 값 모델을 반환한다. 불완전 구조를 일부
  값으로 돌려주지 않는 방식을 이번 파서도 따른다.
- 현재 절 분리 함수는 같은 제목이 여러 번 있으면 첫 번째를 반환한다. 막힌 사유 계약은 제목 중복도
  무효이므로 새 판정은 전체 본문에서 코드 펜스 밖의 정확한 제목 개수를 확인해야 한다.
- TASK-S052-02가 같은 모듈에서 구조화된 결정권자 요약 파서를 추가했다. 그 공개 동작과 검사를 보존한
  뒤 확장하도록 이 작업이 TASK-S052-02에 의존한다.

## 변경 범위

### 반환 모델

- 유효한 절을 막힌 지점, 필요한 해결, 재개 조건, 관련 대상 원문과 관련 대상 목록으로 분리하는 타입과
  함수를 `documentSections.ts`에서 공개한다.
- 함수는 문서 본문 전체를 입력으로 받는다. 유효하지 않거나 없는 경우 `null` 하나를 반환하고 부분
  결과나 오류 문구를 조립하지 않는다.
- 네 값은 라벨 뒤의 원문을 양끝 공백만 제거해 보존한다. 값 안의 콜론, Markdown 표기와 한국어 문장을
  요약하거나 번역하지 않는다.

### 유효성 판정

- 코드 펜스 밖에서 정확한 `## 막힌 사유` 제목이 한 번만 있어야 한다. 깊이, 띄어쓰기와 철자가 다른
  제목은 후보로 보정하지 않는다.
- 해당 절의 비어 있지 않은 본문은 아래 네 개의 최상위 Markdown 목록 항목으로만 구성돼야 한다.
  순서와 라벨을 정확히 지키고 각 값은 비어 있지 않아야 한다.

  ```markdown
  - 막힌 지점: 값
  - 필요한 해결: 값
  - 재개 조건: 값
  - 관련 대상: 값
  ```

- 제목, 라벨, 목록 항목의 누락·중복·순서 변경, 추가 평문·추가 목록, 빈 값 중 하나라도 있으면 절 전체를
  무효로 판정한다. 코드 펜스 안의 같은 문자열은 제목이나 라벨 개수에 포함하지 않는다.
- 관련 대상 값이 정확히 `없음`이면 대상 목록은 빈 배열이다. 그 밖에는 쉼표와 그 뒤 공백을 구분자로
  사용해 작성 순서대로 나누고 각 항목의 양끝 공백만 제거한다. 비어 있는 항목이 생기는 표기는 절 전체를
  무효로 판정한다.
- 파서는 관련 대상이 실제 작업인지 판정하지 않는다. 현재 워크플로 작업 목록과의 정확한 일치는 화면
  작업이 맡는다.

### 기존 동작 보존

- `splitSection`, 결정권자 요약 절과 구조화 요약 파서의 기존 공개 동작을 바꾸지 않는다.
- 파서는 네트워크, Tauri gateway, 저장소, LLM과 브라우저 저장소를 호출하지 않는다.
- 원문 본문을 수정하거나 정규화한 Markdown을 새로 만들지 않는다.

## 손대지 않는 것

- 작업 상세 화면, 관련 작업 링크와 반응형 스타일
- 작업 상태 전환, 이력, lease와 Markdown 파일 쓰기
- 구조화 절이 없는 기존 문서의 표시 문구
- 결정권자 요약의 현재 구조화 계약
- 기존 작업 문서의 일괄 변환

## 완료 조건

1. 정확한 제목과 네 목록 항목을 가진 본문이 네 값과 작성 순서의 관련 대상 목록으로 분리된다.
2. 관련 대상 값 `없음`은 빈 목록이 되며, 화면이 대체 문구나 링크를 만들 필요가 없도록 원문 값도
   보존된다.
3. 실제 작업 식별자, 존재하지 않는 작업 식별자와 외부 의존 문구를 파서가 임의로 구분하거나 버리지
   않는다.
4. 제목 없음·중복·철자 변경·깊이 변경, 라벨 누락·중복·순서 변경, 빈 값, 추가 항목과 빈 관련 대상
   조각이 각각 `null`이 된다.
5. 코드 펜스 안의 제목과 라벨 예시는 판정에 포함되지 않고 실제 절의 경계도 끊지 않는다.
6. 값 안의 콜론과 Markdown 표기가 요약·번역·문장 조립 없이 보존된다.
7. 기존 절 분리와 결정권자 요약 파서 검사가 수정 전과 같은 결과로 통과한다.
8. 판정 중 네트워크·LLM 호출, 파일·브라우저 저장과 본문 변경이 발생하지 않는다.
9. 기존 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. `npx vitest run src/features/projects/domain/documentSections.test.ts`를 실행한다.
2. 정상 절, `없음`, 실제·없는 작업 식별자와 외부 의존이 섞인 관련 대상 픽스처에서 반환 값과 순서를
   확인한다.
3. 제목과 네 라벨 각각의 누락·중복·변형·순서 변경, 빈 값과 추가 항목을 표 기반 검사로 넣고 모두
   `null`인지 확인한다.
4. backtick과 물결표 코드 펜스 안에 같은 제목·라벨을 넣은 픽스처로 오인하지 않는지 확인한다.
5. 기존 `splitSection`과 결정권자 요약 검사 전체가 그대로 통과하는지 확인한다.
6. 저장소 루트에서 `npm run check`를 실행해 타입 검사, 프런트엔드 전체 검사와 배포 빌드가 통과하는지
   확인한다.

## 확인 동선

`npx vitest run src/features/projects/domain/documentSections.test.ts`를 실행하면 68개 검사가 모두
통과해야 한다. 이어 `npm run check`를 실행하면 타입 검사, 24개 테스트 파일의 820개 검사와 배포
빌드가 모두 성공해야 한다. 사용자 확인 도장은 이 자동 검사 수치와 개발 보고서의 남은 위험을
검토하고 신뢰한다는 뜻이다.
