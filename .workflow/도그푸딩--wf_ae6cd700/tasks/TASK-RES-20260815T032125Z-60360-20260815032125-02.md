# 예약 헬퍼가 개발 태스크의 격리 작업 사본을 준비하고 위치를 예약 결과에 싣는다

## 결정권자 요약

### 제안

개발 작업 예약에 성공한 직후, 자동 세션이 쓸 별도의 작업 사본을 준비하고 그 위치를 예약 결과에 실어, 준비가 완전히 끝난 뒤에만 세션이 시작되게 한다.

### 현재

예약은 대상과 소유권만 잡고 끝난다. 그래서 자동 세션은 사용자가 지금 코드를 고치고 있는 바로 그 작업 공간에서 시작하고, 두 작업의 미완성 변경이 서로의 검사에 섞인다.

### 변경 후

개발 예약마다 그 작업만의 사본이 확정된 기준에서 준비되고, 준비가 실패하면 세션이 아예 시작되지 않으며 잡아 둔 소유권과 만들다 만 자원이 정리된다. 사용자는 자기 작업 공간이 자동 세션 때문에 바뀌지 않는다는 것과, 실패한 예약이 흔적을 남기지 않는다는 것을 얻는다.

### 비용과 위험

작업 사본마다 저장 공간이 들고, 예약 결과의 계약 판이 올라가므로 아직 새 계약을 모르는 실행 환경에서는 자동 배정이 시작되지 않고 갱신 안내로 이어진다. 이는 옛 방식으로 조용히 되돌아가지 않기 위한 의도된 동작이다. 사용자 승인 기록과 이미 완료된 작업은 건드리지 않으며, 헬퍼 본문과 판 번호를 이전 값으로 되돌리면 취소할 수 있다. 준비 성공과 실패를 각각 재현하는 자동 검사로 확인을 마쳤다. 실행 환경에 Git이 없으면 개발 예약이 계속 실패하고, 사본 회수는 아직 없어 사본이 쌓인다.

## 현재 상태

- 예약 헬퍼 본문은 `src-tauri/src/infrastructure/reservation_helper.rs`의 `RESERVATION_HELPER_SH`(17행)와 `RESERVATION_HELPER_PS1`(111행) 두 상수이며, 판 번호는 같은 파일의 `RESERVATION_HELPER_VERSION`(15행, 현재 3)과 각 본문 3행의 주석이 함께 들고 있다.
- 현재 흐름은 자격 판정 실행, 대상 추출, `wf-claim acquire`, `expires_at` 읽기, 결과 접두사 생성, JSON 한 줄 출력 순서다. POSIX 본문은 72~105행, PowerShell 본문은 151~193행이다.
- 현재 JSON은 `contractVersion`, `role`, `targetId`, `leaseId`, `resultPrefix`, `expiresAt`, `promptVersion`, `rolePrompt` 여덟 값을 싣고 `contractVersion`은 1이다.
- `expires_at`을 읽지 못하면 잡은 lease를 `wf-claim release`로 반납하고 종료하는 실패 경로가 이미 있다. POSIX 95~98행, PowerShell 173~180행이다.
- `.workflow/.runtime/`는 저장소의 `.gitignore` 33행이 통째로 무시하므로, 그 아래에 만든 디렉터리는 공유 작업 공간의 변경 목록에 나타나지 않는다.
- 세 역할이 같은 경로를 쓰며 역할별 분기는 `prompt_for`(POSIX 56행)와 `Get-RolePrompt`(PowerShell 132행)의 안내 문장 한 줄뿐이다.

## 변경 범위

`src-tauri/src/infrastructure/reservation_helper.rs` 한 파일에서 POSIX 본문과 PowerShell 본문에 같은 동작을 넣는다.

1. 역할이 `developer`일 때만, `wf-claim acquire` 성공과 `expires_at` 확인 뒤 JSON 출력 전에 격리 준비 단계를 수행한다. `planner`와 `architect`의 흐름은 지금과 같다.
2. 준비 첫 단계로 공유 기준을 확정한다. 프로젝트 루트가 Git 작업 트리인지 확인하고, 현재 체크아웃된 기준의 커밋 해시를 읽는다. Git 저장소가 아니거나 커밋 해시를 확정할 수 없으면 공유 작업 공간에서 세션을 대신 시작하지 않고, 잡은 lease를 반납한 뒤 실패로 종료한다.
3. 사본 경로와 브랜치 이름을 대상 식별자와 lease 식별자만으로 조립한다. 사본은 `.workflow/.runtime/worktrees/<대상 식별자>/<lease 식별자>`에 만들고 브랜치는 같은 두 값으로 이름을 만든다. 이름에 prompt 원문, 인증 값, 환경 변수 값을 넣지 않는다. 같은 태스크를 다시 예약해도 lease 식별자가 다르므로 이전 실행을 덮어쓰지 않는다.
4. 2번에서 읽은 커밋에서 전용 브랜치를 만들어 사본을 준비한다. 공유 작업 공간의 미커밋 파일은 사본으로 복사하지 않는다.
5. 준비 결과를 `.workflow/.runtime/isolation/<대상 식별자>.yml`에 기록한다. 기록은 최소한 대상 식별자, lease 식별자, 기준 커밋, 브랜치 이름, 사본 경로, 제어 문서 정본 경로, 준비 완료 시각, 준비 단계 이름을 담는다. 이 파일은 앱 소유 상태이므로 에이전트 세션이 직접 고치지 않는다는 사실을 파일 첫 줄 주석에 적는다.
6. 2~5번 중 어느 단계라도 실패하면 그 단계까지 만든 자원을 정리한다. 만든 브랜치와 사본 디렉터리를 제거하고, 기록 파일을 남겼으면 실패 단계를 담아 갱신한 뒤, 잡은 lease를 `wf-claim release`로 반납하고 0이 아닌 코드로 종료한다. 실패한 예약은 JSON을 출력하지 않으므로 세션이 시작되지 않는다.
7. JSON 출력에 `workspacePath`, `controlRoot`, `baseCommit`, `branch` 네 값을 추가한다. `workspacePath`는 준비한 사본의 경로, `controlRoot`는 워크플로우 제어 문서의 정본이 있는 프로젝트의 `.workflow` 경로다. `planner`와 `architect`의 출력에는 이 네 값을 넣지 않는다.
8. `contractVersion`을 2로 올린다. 새 계약을 모르는 실행 환경이 사본 경로를 무시한 채 공유 작업 공간에서 세션을 시작하는 부분 실행을 막기 위한 것이며, 값을 그대로 두고 필드만 늘리는 방식은 쓰지 않는다.
9. 역할 안내 문장에 코드 작업 사본 위치와 제어 문서 정본 위치를 세션이 함께 전달받는다는 사실을 넣는다. 안내 문장은 역할, 대상, lease, 결과 접두사, 읽어야 할 관리 규칙, 그리고 이 두 위치까지만 말하고 provider별 지시를 넣지 않는다.
10. `RESERVATION_HELPER_VERSION`을 4로 올리고 두 본문 3행의 판 번호 주석도 4로 맞춘다. 같은 파일 시험 모듈 466·476·486행의 리터럴 판 번호 검사를 새 값으로 맞춘다.

## 완료 조건

1. Git 작업 트리이고 기준 커밋을 읽을 수 있는 프로젝트에서 `developer` 역할로 예약하면, 선언한 경로에 사본과 전용 브랜치가 만들어지고 JSON이 `workspacePath`, `controlRoot`, `baseCommit`, `branch`를 담아 출력된다.
2. 같은 프로젝트에서 `planner` 또는 `architect` 역할로 예약하면 사본과 브랜치가 만들어지지 않고 JSON에 그 네 값이 없다.
3. Git 저장소가 아닌 프로젝트에서 `developer` 역할로 예약하면 JSON이 출력되지 않고 종료 코드가 0이 아니며, 잡았던 lease 파일이 남아 있지 않다.
4. 사본 준비가 실패하도록 만든 상태에서 `developer` 역할로 예약하면 만들다 만 사본 디렉터리와 브랜치가 남지 않고, lease가 반납되며, 기록 파일에 실패 단계가 남는다.
5. 준비에 성공하면 `.workflow/.runtime/isolation/<대상 식별자>.yml`이 변경 범위 5번의 여덟 값을 모두 담는다.
6. 사본 경로와 브랜치 이름 어디에도 prompt 원문, 인증 값, 환경 변수 값이 들어가지 않는다. 같은 태스크를 두 번 예약하면 서로 다른 사본 경로와 브랜치 이름이 만들어지고 앞선 기록이 덮어써지지 않는다.
7. 준비한 사본에는 공유 작업 공간의 미커밋 변경이 들어 있지 않다.
8. 예약 전후로 공유 작업 공간의 미커밋 변경과 stage 상태가 동일하다.
9. 출력 JSON의 `contractVersion`이 2다.
10. `RESERVATION_HELPER_VERSION`이 4이고 두 본문의 판 번호 주석도 4이며, 판 번호 리터럴 검사가 통과한다.
11. POSIX 본문과 PowerShell 본문이 완료 조건 1~9에 대해 같은 JSON 필드 구성과 같은 종료 코드를 낸다.

## 범위 사전 검사

`src-tauri/src/infrastructure/reservation_helper.rs` 한 파일만 선언했다. 헬퍼 본문 두 개, 판 번호 상수, 판 번호 리터럴 검사, 그리고 완료 조건 1~11을 재현할 시험 모듈이 모두 이 파일 안에 있으므로 완료 조건을 만족하는 데 다른 파일 편집이 필요하지 않다.

- 값 경로: 완료 조건 1·2·9(JSON 새 필드와 계약 판) — 원천은 `reservation_helper.rs`의 `RESERVATION_HELPER_SH` 101~103행 `printf` 형식 문자열과 `RESERVATION_HELPER_PS1` 182~191행 `[ordered]@{}` 리터럴이다. 두 자리가 값을 만드는 유일한 hop이고 둘 다 편집 대상이다. 이 값을 소비하는 것은 헬퍼를 호출해 JSON을 읽는 실행 환경이며, 그 소비자는 이 저장소 밖에 있다. 저장소 안에서 이 JSON을 구문 분석하는 코드는 없다는 것을 `contractVersion`·`resultPrefix`·`rolePrompt` 검색으로 확인했고, 나오는 자리는 이 파일의 본문과 시험 모듈뿐이다.
- 값 경로: 완료 조건 3·4(실패 시 정리와 반납) — 원천은 같은 두 본문의 실패 분기다. POSIX 95~98행과 PowerShell 173~180행에 이미 있는 `wf-claim release` 호출이 같은 패턴의 앞 hop이고, 새 준비 단계의 실패 분기가 그 자리 앞에 추가된다. 최종 소비자는 `.workflow/.runtime/leases/<대상>.yml` 파일의 존재 여부를 보는 자격 판정과 이 파일의 시험이다. `wf-claim` 본문은 `claim_helper.rs`에 있지만 이 태스크는 그 호출 방식을 바꾸지 않고 이미 있는 반납 호출을 재사용하므로 선언 밖에 둔다.
- 값 경로: 완료 조건 5(준비 기록) — 원천은 새 기록 파일을 쓰는 두 본문의 코드다. 기록은 `.workflow/.runtime/isolation/<대상 식별자>.yml`에 남고, 소비자는 TASK-RES-20260815T032125Z-60360-20260815032125-03의 자격 판정과 통합을 이어받는 개발자 세션이다. 이 태스크는 기록을 만드는 쪽만 담당하고 읽는 쪽은 선언 밖이다.
- 값 경로: 완료 조건 10(판 번호) — 원천은 `RESERVATION_HELPER_VERSION`(15행)과 두 본문 3행의 주석이다. 값은 `RESERVATION_HELPER` 서술(210행)을 지나 `fs_project_repository.rs`의 관리 자산 동기화(1601·1615행)로 가서 설정 화면의 관리 자산 판 번호로 나타난다. 편집 대상은 이 파일의 세 자리다.

`fs_project_repository.rs`를 열어 보고 선언에서 뺐다. 1601·1615행이 판 번호를 상수 이름으로만 참조하고, 시험 모듈 8416·8428행도 기대 문자열을 `format!("# reservation_helper_version: {RESERVATION_HELPER_VERSION}")`로 조립한다. 8431행의 미래 판 번호 검사도 리터럴 999를 쓰므로 판 번호가 3에서 4로 올라가도 이 파일은 고칠 필요가 없다.

`managed_script.rs`도 열어 보고 뺐다. `install`·`validate`·`plan_install`(98·112·119행)이 `ManagedScript`의 `version` 필드를 값으로 받아 비교할 뿐 예약 헬퍼의 판 번호를 리터럴로 갖지 않는다.

`heartbeat_condition.rs`는 예약 헬퍼가 호출하는 자격 판정 스크립트를 담지만, 이 태스크는 그 호출의 인자와 종료 코드 해석을 바꾸지 않는다. 기록을 읽어 판정을 바꾸는 일은 다음 태스크의 몫이므로 선언 밖에 둔다.
