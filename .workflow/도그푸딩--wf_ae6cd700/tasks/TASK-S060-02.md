# 사용자가 확인한 코드 상태를 제출에 실어 재확인 경로를 연다

## 결정권자 요약

### 제안

확인 대상 코드가 바뀌어 제출이 거절된 뒤에도 사용자가 다시 확인해서 제출할 수 있게 한다.

### 현재

사용자가 품질 확인을 진행하는 동안 코드가 바뀌면 앱은 제출을 거절하면서 품질 확인을 다시 진행해
달라고 안내한다. 그런데 확인 대상으로 잡아 둔 코드 상태를 다시 잡는 길이 없어서, 안내대로 다시
확인해도 같은 거절이 되돌아온다. 안내가 약속하는 행동이 실제로는 불가능하고, 그 그룹의 품질 확인은
끝낼 방법이 없다.

### 변경 후

제출에는 사용자가 확인할 때 화면이 보고 있던 코드 상태가 함께 실린다. 그 상태가 지금의 코드와 같으면
결과가 기록되고, 다르면 지금처럼 거절한다. 확인 도중 코드가 바뀌면 남겨 둔 임시 결정을 비우고 처음부터
다시 보게 하므로, 확인하지 않은 코드에 결과가 붙지 않는다. 거절 뒤 다시 확인하면 제출이 기록되어,
안내가 약속하는 재확인이 실제로 가능해진다.

### 비용과 위험

확인을 진행하는 도중에 코드가 바뀌면 그때까지 고른 결과와 메모가 지워지고 처음부터 다시 확인해야
한다. 이것은 확인한 대상과 기록되는 대상을 어긋나지 않게 하려고 남겨 두는 보호이며, 지금도 기능
내용이 바뀌면 같은 방식으로 임시 결정을 비운다. 자동 확인 그룹의 판정, 결정 기록 절차, 작업 문서와
결정 문서는 이 작업으로 바뀌지 않는다. 되돌리면 지금 동작으로 그대로 복귀한다.

## 완료 조건

- C1. 제출 요청에 사용자가 확인할 때 화면이 읽고 있던 확인 대상 기준 커밋을 담는 선택 필드를
  더한다. 백엔드 도메인 타입과 화면 타입 양쪽에 더하고, 값이 없을 수 있는 필드로 둔다. 값이 없는
  요청도 역직렬화에 실패하지 않아야 한다.
- C2. 제출 판정은 그룹 요약의 고정 값 대신 요청에 실린 값과 판정 시점의 현재 기준 커밋을 비교한다.
  두 값이 다르면 지금과 같은 `WorkGroupQaBaseChanged`로 거절하고, 결정 문서를 만들지 않으며 작업
  문서도 건드리지 않는다. 오류 종류와 메시지는 바꾸지 않는다.
- C3. 그룹에 확인 대상 기준이 있는데 요청이 값을 담지 않았으면 같은 거절로 처리한다. 그룹에 기준이
  없으면, 즉 Git 작업 트리가 아니어서 현재 기준 커밋을 확정할 수 없으면 이 판정을 건너뛴다. 그래야
  Git 작업 트리가 아닌 프로젝트의 제출 판정이 변경 전과 같다.
- C4. 사용자 확인 그룹의 확인 대상 기준 기록도 TASK-S060-01이 만든 갱신 동작을 쓴다. 저장된 값이
  현재 커밋과 다르면 현재 값으로 갱신하고, 그룹 요약에도 갱신한 값을 싣는다. 이 변경으로 한 번만
  고정하고 다시 쓰지 않는 예전 동작에 남는 사용처가 없어지면 그 동작을 남겨 두지 않는다.
- C5. 확인 화면은 사용자가 확인 결과를 고르는 시점의 요약에 실린 확인 대상 기준을 임시 결정과 함께
  저장하고, 제출에는 임시 결정에 저장된 그 값을 싣는다. 제출 시점의 최신 요약 값을 다시 읽어 싣지
  않는다. 거절 직후 화면이 프로젝트를 다시 읽어 요약이 갱신되므로, 최신 값을 실으면 사용자가 확인하지
  않은 코드에 결과가 붙는다.
- C6. 저장해 둔 임시 결정은 그룹 갱신 시각이 같고 확인 대상 기준도 같을 때만 물려받는다. 기준이
  달라졌거나 저장된 항목에 기준 값이 없으면 물려받지 않고, 지금의 임시 결정 비움 안내와 같은 경로로
  처음부터 다시 보게 한다. 확인 화면이 처음 상태로 돌아가는 자리도 이 값을 함께 보게 해서, 요약이
  갱신되면 고른 결과와 메모가 남지 않는다.
- C7. 거절 뒤 현재 코드 상태에서 다시 확인해 제출하면 결정이 기록된다. 같은 거절이 반복되기만 하는
  상태가 남지 않는다.
- C8. 다시 시작한 확인 도중에 코드가 또 바뀌면 그 제출도 거절된다. C5가 확인 시점 값을 싣기 때문에
  이 조건이 성립하며, 최신 값을 실어 우회하는 경로를 만들지 않는다.
- C9. 결정 문서 형식, 결정 기록 절차, 같은 요청 식별자 재전송 처리, 자동 확인 그룹의 판정은 바뀌지
  않는다. 재전송 처리(709~729행)는 지금처럼 기준 커밋 판정보다 앞에서 끝나 이미 남은 결정을 그대로
  돌려준다.
- C10. 이 작업으로 `.workflow` 아래의 문서 파일, 규칙 문언, 역할 계약, 규칙 버전은 하나도 바뀌지
  않는다.
- C11. 기존 백엔드 시험을 새 규칙에 맞춰 다시 쓴다. 어느 것도 지우지 않는다.
  - `work_group_qa_rejects_a_submission_after_the_base_commit_moves`(11762행): 확인 시점 기준을
    실은 요청으로 고쳐 쓴다. 이 시험이 지키는 보호는 그대로 유지되고, 요청이 그 값을 싣게 된 변경에
    맞춰 픽스처만 바뀐다.
  - `work_group_qa_records_on_the_pinned_base_and_replays_a_recorded_request`(11791행): 현재
    기준을 실은 요청이 기록되고, 같은 요청 식별자의 재전송은 기준이 움직인 뒤에도 이미 남은 결정을
    돌려준다는 기대를 유지한다.
  - `work_group_pins_its_qa_base_commit_when_qa_can_open_and_never_repins_it`(11709행): 사용자
    확인 그룹의 고정이 갱신되는 규칙으로 바뀌므로 기대값과 이름을 함께 고쳐 쓴다. 이 시험이 고정한
    "다시 쓰지 않는다"가 바로 이 작업이 바꾸는 규칙이다. 아직 확인을 열 수 없는 그룹은 고정하지
    않는다는 앞부분 기대는 그대로 둔다.
  - `each_work_group_revision_pins_its_own_base_commit`(11814행): 구성 버전마다 자기 기준을 갖고
    이전 버전의 기록을 지우지 않는다는 규칙은 유지된다. 통과를 확인하고, 갱신 규칙과 어긋나는 기대만
    고쳐 쓴다.
  - `work_group_qa_keeps_its_previous_behaviour_outside_a_git_work_tree`(11889행): 수정 없이
    통과해야 한다. 수정이 필요하면 C3을 넘은 것이다.
- C12. 백엔드 시험을 새로 더한다. 확인 시점 기준을 실은 제출이 기준 전진 뒤 거절되고, 이어서 현재
  기준을 실은 제출이 기록되는 흐름을 한 시험으로 확인한다(수용 기준 5·6). Git 작업 트리인데 요청이
  기준을 담지 않은 제출이 거절되는 시험도 더한다(C3).
- C13. 화면 시험을 새로 더한다. 제출 본문에 확인 시점 기준이 실리는 검사, 요약의 기준이 달라지면
  저장해 둔 임시 결정을 물려받지 않고 안내가 보이는 검사, 기준 값이 없는 저장 항목을 버리는 검사
  셋이다. 앞의 둘은 확인 화면 시험 파일에, 마지막은 임시 결정 저장소 시험 파일에 넣는다.

## 범위 사전 검사

선언한 여덟 파일은 확인 시점 기준 커밋이 만들어지는 자리에서 제출 판정까지의 경로 위에 있다. 각 hop을
실제 코드에서 열어 확인했고, 값이 무변경으로 통과하는 hop은 선언에서 뺐다.

- 값 경로: 확인 시점 기준 커밋이 화면까지 가는 경로(C1·C5). 원천은
  `fs_project_repository.rs`의 `current_base_commit`(3011~3022행)이고 `QaBasePin`(2864~2908행)이
  기록과 캐시를 맡는다. `parse_work_group` 3176~3181행이 그 값을 그룹 요약에 싣고,
  `src-tauri/src/domain/project.rs` 312행 `qa_base_commit`이 `qaBaseCommit`으로 직렬화된다. 이
  두 hop은 값이 이미 있어 편집이 필요 없다. 편집이 필요한 hop은 `types.ts` 183~197행이며, 여기에
  선택 필드를 선언해야 화면이 그 값을 읽을 수 있다. 다음 hop인 `QaWorkbench.tsx` 45~52행은 요약
  객체를 통째로 넘기므로 필드 추가만으로 값이 흐르지만, 53행 `key`는 C6이 요구하는 초기화 자리라
  편집한다. 그다음 `QaFlowReview.tsx` 44~55행이 임시 결정에 값을 저장하고,
  `browserQaReviewDraftStore.ts` 9~14행 항목 타입과 35~42행 검증이 그 값을 받는다. 셋 모두 편집
  대상이고 선언에 들어 있다.
- 값 경로: 제출 요청에 실린 기준 커밋이 판정까지 가는 경로(C1·C2·C3). 원천은
  `QaFlowReview.tsx` 82~93행의 제출 본문 조립이고, 실을 값은 위 경로가 임시 결정에 저장한 값이다.

  170~174행은 요청 객체를 그대로 넘기고, `commands/projects.rs` 236~243행은 요청을 통째로
  역직렬화해 넘기며, `application/project_service.rs` 110~115행도 그대로 전달한다. 세 hop 모두
  필드를 하나씩 열거하지 않으므로 값이 무변경으로 통과하고, 그래서 선언에서 뺐다. 편집이 필요한
  hop은 `domain/project.rs` 442~449행의 요청 타입과 `fs_project_repository.rs` 755~761행의 판정

  모든 hop이 값을 무변경으로 나르고, 이 경로의 파일은 선언에서 뺐다. 같은 지점이 거절 뒤 프로젝트를
  다시 읽으므로 C7의 재확인 경로가 별도 조작 없이 열린다.
- 값 경로: 사용자 확인 그룹의 기준 기록 갱신(C4). TASK-S060-01이 `QaBasePin`에 더하는 갱신 동작이
  원천이고, 소비자는 `parse_work_group` 3176~3181행의 고정 호출 하나다. 두 hop이 같은 파일 안이라

  `None`이고, 화면이 실을 값도 없다. 이때 판정을 건너뛰므로 제출은 지금처럼 기록된다. 이 불변은

  C11이 그 시험을 수정 없이 통과시킨다.

선언에서 뺀 파일과 그 근거를 다시 정리하면 다음과 같다.

- `src-tauri/src/commands/projects.rs`와 `src-tauri/src/application/project_service.rs`: 제출
  요청과 오류를 통째로 전달한다. 필드를 열거하지 않으므로 값이 무변경으로 통과한다.
- `src/features/projects/infrastructure/tauriProjectGateway.ts`: 제출 객체를 그대로 넘긴다.
- `src/features/projects/application/useProjectWorkspace.ts`: 오류 메시지를 그대로 올리고 프로젝트를
  다시 읽는 동작이 이미 있어 재확인 경로에 필요한 편집이 없다.
- 그룹 요약을 만드는 다른 화면 시험 파일들: C1이 선택 필드로 선언하므로 기존 픽스처가 그대로
  통과한다. 검증 절차 5번이 이것을 확인하며, 그 시험이 깨지면 필드를 필수로 선언한 신호다.
