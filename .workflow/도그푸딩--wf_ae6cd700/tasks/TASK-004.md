# HEARTBEAT.md 파서와 앱 관리 잡 블록 엔진 구현

SPEC-002의 R2·R3과 R6의 쓰기 안전 요구를 구현한다. 하트비트 설정 파일을 읽고, 앱 관리 마커 블록만 안전하게 만들고 갱신하고 지우는 Rust 모듈과 테스트를 만든다. UI와 Tauri 커맨드는 붙이지 않는다.

## 의존성

- 선행 작업 없음. TASK-003과 파일이 겹치지 않으므로 병렬로 진행해도 된다.
- 이 작업의 파서를 TASK-005가 중복 잡 감지에 재사용한다. TASK-006·TASK-007이 이 모듈을 호출한다.

## 범위

- 신규 파일 `src-tauri/src/infrastructure/heartbeat_jobs.rs` 1개.
- `src-tauri/src/infrastructure/mod.rs`에 모듈 선언 1줄 추가.
- 그 외 파일은 건드리지 않는다.

## 작업 내용

### 0. 테스트 가능성 제약 (먼저 읽을 것)

- 이 모듈은 **절대로 실제 `~/.claude/HEARTBEAT.md` 경로를 스스로 계산하지 않는다.** 모든 공개 함수는 대상 파일 경로 또는 파일 내용을 인자로 받는다. 홈 디렉터리 해석은 TASK-006이 커맨드 계층에서 한다.
- 테스트가 사용자의 실제 하트비트 설정을 건드리면 안 된다. 모든 테스트는 `tempfile::tempdir` 안에서 돈다.

### 1. 파서 (읽기)

하트비트 파서와 **같은 규칙으로** 읽는다. 아래는 실제 구현(`src/heartbeat/core.py`)을 확인한 사실이다.

- 줄 단위로 읽고 각 줄을 trim한다.
- `## `로 시작하는 줄이 새 잡의 시작이며 그 뒤 문자열이 잡 이름이다.
- 잡 헤더 이후의 `- `로 시작하는 줄에서 첫 `:`을 기준으로 key/value를 나눈다. key는 소문자로 정규화된다.
- 첫 `## ` 헤더보다 앞에 있는 `- ` 줄은 전역 설정이다(`tick`).
- 그 외 모든 줄은 무시된다. HTML 주석 마커 줄도 무시된다.

파서가 내보내는 값에는 최소한 잡 이름, 원문에서 그 잡이 차지하는 줄 범위, key/value 목록이 들어간다. 줄 범위는 TASK-005의 중복 감지와 이 모듈의 블록 교체에 모두 필요하다.

- 값을 하트비트처럼 초 단위로 파싱하지 않는다. 앱은 원문 문자열을 그대로 보존한다. 앱이 파싱해서 다시 쓰면 사용자가 적은 표기가 바뀐다.

### 2. 관리 블록 마커 (R2)

- 마커는 `AGENTS.md` 관리 블록과 같은 주석 패턴을 쓴다. 다음 두 줄을 그대로 쓴다.

```
<!-- workflow-labs:heartbeat-jobs:start -->
<!-- workflow-labs:heartbeat-jobs:end -->
```

- 신규 설치는 항상 파일 끝에 블록을 붙인다. 첫 `##` 헤더보다 앞에 삽입하지 않는다. 사용자의 `- tick:` 줄이 관리 잡의 필드로 흡수되어 전역 설정이 조용히 무력화되는 것을 막는 조건이다.
- 이미 블록이 있으면 그 자리에서 내용만 교체한다. 파일 끝으로 옮기지 않는다.
- 블록 밖의 모든 내용(사용자 잡, 전역 설정, 빈 줄, 주석)은 바이트 단위로 보존한다.
- 줄바꿈은 원본을 따른다. 파일에 `\r\n`이 있으면 `\r\n`으로 쓴다. `project_instructions.rs`의 `newline_for`와 같은 처리다.

### 3. 실패 조건 (R2, R6)

아래 경우에는 파일을 쓰지 않고 사유를 담은 오류를 반환한다. 실패 시 원본은 바이트 단위로 그대로 남아야 한다. 판정을 모두 끝낸 뒤에 쓰는 순서를 지킨다.

- 시작 마커와 종료 마커의 개수가 각각 1이 아닌 경우(하나만 있음, 여러 쌍 있음).
- 종료 마커가 시작 마커보다 앞에 오는 경우.
- 종료 마커 다음 줄부터 다음 `## ` 헤더가 나오기 전까지의 구간에 `- `로 시작하는 줄이 있는 경우. 그 줄은 하트비트 파서에서 관리 블록 마지막 잡의 필드로 흡수되므로, 마커만 검사해서는 잡을 수 없는 손상 형태다. 오류 문구에 흡수될 줄의 내용을 포함해 사용자가 어디를 고쳐야 하는지 알 수 있게 한다.
- 대상 경로가 일반 파일이 아닌 경우.

파일이 아예 없으면 실패가 아니다. 관리 블록만 담은 새 파일을 만든다.

### 4. 잡 이름 (R2)

- 잡 이름은 `wf-<역할>` 뒤에 slug를 이어 붙인 값이다. slug가 `-`로 시작하므로 결과는 `wf-planner-Users-catze-project-workflow-labs` 형태가 된다.
- 이 규칙을 고른 이유: 하트비트는 잡 이름을 `state.json`의 키로 쓴다. 프로젝트 경로가 다르면 slug가 다르므로 이름이 반드시 달라지고, 같은 프로젝트를 다시 설치해도 경로가 같으면 이름이 같다. `heartbeat jobs` 출력에서 어느 프로젝트인지 경로로 바로 읽힌다. 세 조건(고유·안정·식별 가능)을 새 의존성 없이 동시에 만족하는 가장 단순한 규칙이다.
- 알려진 결과: 프로젝트 디렉터리를 옮기면 잡 이름이 바뀌고 이전 이름의 실행 기록이 `state.json`에 남는다. 앱은 그 파일을 쓰지 않으므로 정리하지 않는다. 이 동작을 그대로 둔다.

### 5. slug 생성 (R3)

- 프로젝트 루트 절대 경로의 `/`를 전부 `-`로 바꾼다. 결과가 `-`로 시작하지 않으면 앞에 `-`를 붙인다.
- 절대 경로 `/Users/catze/project/workflow-labs`는 `-Users-catze-project-workflow-labs`가 된다. 이 값은 실제 설정 파일에 있는 값과 일치한다.
- 역변환은 구현하지 않는다. 하트비트의 slug → 경로 변환은 실제 디렉터리를 탐색하는 그리디 추정이라 앱이 따라 할 대상이 아니다.

### 6. 역할 잡 기본값 (R3)

세 역할의 잡을 아래 값으로 만든다.

| 필드 | 기획자 | 아키텍트 | 개발자 |
| --- | --- | --- | --- |
| model | opus | opus | opus |
| interval | 30m | 30m | 20m |
| timeout | 20m | 20m | 30m |
| max_per | 4/24h | 4/24h | 6/24h |
| notify | all | all | all |

- `slug`는 5번 규칙으로 만든다.
- `condition`은 `sh .workflow/rules/wf-eligible.sh <역할>`이다. 역할 인자는 `planner` | `architect` | `developer`. 프로젝트 루트 기준 상대 경로이며, 하트비트가 조건을 프로젝트 cwd에서 실행하므로 상대 경로로 충분하다. 이 경로는 TASK-003이 설치하는 파일을 가리킨다.
- `prompt`는 역할마다 아래 한 줄 고정 문구다. 앱이 소유하며 사용자가 편집하지 않는다. 세 문구 모두 역할 고정, 공통 규칙과 역할 계약 준수, 대상 없으면 `NO_ELIGIBLE_WORK`만 보고 후 정지를 담고 있다.

```
기획자 역할로 진행해줘. .workflow의 공통 규칙과 planner 역할 계약을 따르고, 처리할 대상이 없으면 NO_ELIGIBLE_WORK만 보고하고 멈춰.
프로젝트 아키텍트 역할로 진행해줘. .workflow의 공통 규칙과 architect 역할 계약을 따르고, 처리할 대상이 없으면 NO_ELIGIBLE_WORK만 보고하고 멈춰.
개발자 역할로 진행해줘. .workflow의 공통 규칙과 developer 역할 계약을 따르고, 처리할 대상이 없으면 NO_ELIGIBLE_WORK만 보고하고 멈춰.
```

- `prompt`는 반드시 한 줄이다. 줄바꿈이 들어가면 하트비트 파서가 뒷부분을 잃는다.
- 필드 출력 순서는 `slug`, `model`, `prompt`, `interval`, `timeout`, `condition`, `notify`, `max_per`로 고정한다. 순서가 흔들리면 멱등이 깨진다.

### 7. 설치·갱신·제거 (R2, R5의 파일 측면)

- 공개 함수는 "활성화할 역할 목록과 역할별 설정"을 입력으로 받아 파일 내용을 만든다. 역할이 하나도 활성이 아니면 마커를 포함한 블록 전체를 파일에서 제거한다. 하트비트에는 비활성 상태 필드가 없으므로 "꺼짐"은 "블록에 없음"이다.
- 같은 입력으로 다시 실행하면 파일이 변하지 않아야 한다. 내용이 이미 같으면 쓰기 자체를 하지 않는다.
- 쓰기는 `write_text_atomically`와 같은 방식(같은 디렉터리 임시 파일 → `sync_all` → `persist`)을 쓴다.

### 8. 편집 값 검증 (R5의 파일 측면)

`interval`·`max_per`·`model`을 인자로 받을 때 아래 형식을 검증하고, 어긋나면 파일을 쓰지 않고 오류를 반환한다.

- `interval`: 숫자 + `s` | `m` | `h` | `d`
- `max_per`: `<횟수>/<기간>` 형태이고 기간은 위와 같은 단위 표기
- `model`: 공백 없는 한 줄 값

- 이 검증은 잘못된 값이 파일에 닿지 않게 하는 방어선이다. 입력 위치에 사유를 표시하는 UI 검증은 TASK-007이 담당한다. 두 곳 모두 있어야 하며, 이 작업은 백엔드 쪽만 한다.
- `timeout`·`notify`·`prompt`·`condition`·`slug`는 사용자 편집 대상이 아니다. 앱이 정한 값을 쓴다.

### 9. 테스트

`#[cfg(test)] mod tests`에 `tempfile::tempdir`로 작성한다.

- 파일이 없는 상태에서 설치하면 마커 블록과 역할 잡 3종이 기본값으로 생긴다.
- 사용자 잡과 `- tick:` 전역 설정이 있는 파일에 설치해도 블록 밖 내용이 바이트 단위로 같고, 블록이 파일 끝에 붙는다.
- 같은 입력으로 두 번 설치하면 파일 내용이 완전히 같다.
- 역할 하나를 끄면 그 잡만 블록에서 사라지고 나머지 둘은 그대로다. 다시 켜면 최초 설치 결과와 파일이 같다.
- 마커가 하나만 있는 파일, 순서가 뒤집힌 파일에서 실패하고 파일이 변경되지 않는다.
- 종료 마커 뒤에 `- tick: 5m` 같은 줄이 이어지는 파일에서 실패하고 파일이 변경되지 않는다.
- `interval`·`max_per`·`model`의 잘못된 값에 대해 실패하고 파일이 변경되지 않는다.
- `\r\n` 파일에 설치하면 결과도 `\r\n`을 유지한다.
- 파서가 실제 형식의 문서에서 잡 이름과 필드를 읽어 낸다. 첫 헤더 앞의 `- tick:`을 잡 필드로 오인하지 않는다.

## 완료 조건

1. 설치 후 대상 파일에 관리 마커 블록이 하나 생기고 그 안에 역할 잡 3종이 R3 기본값으로 기록된다. (기획서 완료 조건 2)
2. 같은 설치를 두 번 실행해도 파일이 변하지 않는다. (기획서 완료 조건 3)
3. 전역 설정 `- tick:`이 있는 파일에 설치해도 그 줄이 그대로 남고 블록보다 앞에 있다. (기획서 완료 조건 4)
4. 마커 손상 파일과 종료 마커 뒤에 `- key: value`가 이어지는 파일에서 설치가 실패하고 파일이 변경되지 않는다. (기획서 완료 조건 5)
5. 역할 토글 왕복 후 파일 내용이 최초 설치 결과와 같다. (기획서 완료 조건 8의 파일 측면)
6. `interval`·`max_per`·`model`의 잘못된 값이 파일에 쓰이지 않는다. (기획서 완료 조건 9의 파일 측면)
7. 위 항목 전부에 자동화 테스트가 있고 `cargo test`가 통과한다.
8. 모듈이 실제 홈 디렉터리 경로를 계산하지 않는다. 경로는 전부 인자로 들어온다.
9. 프론트엔드(`src/`)와 `.workflow/`에 변경이 없다.

## 참고 사실

- `src-tauri/src/infrastructure/project_instructions.rs:365`의 `plan_managed_file`이 마커 블록 판정·교체·부재 시 추가의 기존 구현이다. 같은 파일 `409`의 `append_block`, `434`의 `newline_for`, `453`의 `write_text_atomically`를 그대로 참고한다.
