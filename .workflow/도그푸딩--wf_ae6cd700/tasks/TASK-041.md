# 규칙 자산과 파일 계약이 선행 선언과 선점 헬퍼를 기준으로 갱신된다

SPEC-013 R8 전부와 R3·R4·R6의 계약 문구 몫을 구현한다. 앱이 설치하는 공통 규칙과 역할 계약 세 개를
선점 헬퍼 사용 기준으로 다시 쓰고, 개발자·아키텍트 계약에 선행 선언 규칙을 적고,
`docs/file-contract.md`를 두 변경에 맞게 갱신한다. 코드 판정과 헬퍼 구현은 이 작업이 아니다 —
판정의 단일 정의는 TASK-037, `sh` 반영은 TASK-040, 헬퍼 구현은 TASK-039다.

이 문서는 SPEC-013을 분해한 아키텍트 세션이 시간 초과로 종료되며 남기지 못한 다섯 번째 작업을
사용자 지시로 복원한 것이다. TASK-037·039·040의 본문이 "규칙 문서 갱신은 TASK-041이다"라고
가리키는 그 문서다.

## 의존성

- 선행 작업 없음. TASK-039가 명시했다 — 규칙이 먼저 가도 "헬퍼가 없는 프로젝트"의 처리(확인 필요
  1번의 결정)가 같은 문서에 있어 세션이 막히지 않는다. 반대로 헬퍼가 먼저 가도 규칙 §4의 현행
  절차는 여전히 유효하다.
- **`project_instructions.rs`를 만지는 유일한 `todo` 작업이다.** 규칙 자산의 버전 상수를 올리는
  작업이 동시에 둘이면 한쪽이 상대의 인상을 밟는다. 이 파일을 만지는 다른 작업이 생기면 병행 금지다.
- TASK-037·TASK-038과 파일이 겹치지 않는다. TASK-037은 `docs/file-contract.md`를 명시적으로 제외했다.

## 범위

- `src-tauri/src/infrastructure/project_instructions.rs` — 내장 규칙 본문과 버전 상수.
- `docs/file-contract.md` — 개발 작업 절과 lease 문단.
- 그 외 파일은 건드리지 않는다. 특히 조건 스크립트(`heartbeat_condition.rs`)와 헬퍼, 화면,
  `domain/project.rs`는 이 작업에서 바뀌지 않는다.

## 작업 내용

### 0. 먼저 읽을 제약

- 규칙 본문은 앱 소스에 내장되어 있고 설치 파일과 같은 값이어야 한다(SPEC-013 R6). 내장 본문만
  고치고 설치를 잊으면 앱이 다음 승인·QA 기록 때 갱신하므로 상수 인상이 갱신을 운반한다.
- 버전 리터럴을 흩뿌리지 않는다. `WORKFLOW_RULES_VERSION`(현재 4)과 `ROLE_RULES_VERSION`(현재 3)
  상수 두 개가 원본이다(TASK-022가 만든 구조). 이번 인상은 각각 5와 4다.
- 설치본이 앱 상수보다 새 버전이면 덮어쓰지 않고 멈추는 현행 안전 규칙을 유지한다.

### 1. 공통 규칙 §4를 헬퍼 기준으로 다시 쓴다 (R8)

- "lease 파일을 배타적으로 생성한다"가 아니라 "`.workflow/rules/wf-claim.sh`로 선점하고 종료 코드로
  결과를 판정한다"가 된다. 하위 명령 세 가지(선점·갱신·해제)와 종료 코드의 의미를 적는다:
  `0` 성공, `1` 그 밖의 실패, `2` 사용법 오류, `3` 미만료 lease 존재(다른 대상을 고르거나
  `NO_ELIGIBLE_WORK`), `4` 만료 lease 인수 경합 패배(선점 실패로 취급), `5` 소유자 불일치(갱신·해제
  중단). 각 경우에 세션이 할 일을 함께 적는다.
- 세션은 lease 파일을 직접 만들거나 지우거나 고치지 않는다는 문장을 명시한다.
- 헬퍼가 설치되어 있지 않은 프로젝트에서는 현행 절차(직접 배타적 생성)를 그대로 쓴다는 예외를
  명시한다. 헬퍼가 있는데 실행이 실패하면 선점 실패로 보고 그 대상을 포기한다 — 실행 실패를 직접
  생성으로 우회하지 않는다(DECISION-73D4BC1B 확인 필요 1번의 결정).
- 선점 직후 문서에 작업 중 상태를 남기는 의무(기획서 `status: draft` 스켈레톤, 작업
  `status: in_progress`)와, 긴 작업 중 갱신하고 끝나면 해제하는 의무는 그대로 유지한다. 동작의
  주체가 헬퍼로 바뀔 뿐이다.

### 2. 개발자 계약에 선행 선언 판정을 적는다 (R3)

- 자격 조건의 "its dependencies must be satisfied"가 평가 가능한 조건이 된다. 충족의 정의를 적는다:
  `depends_on`의 모든 id가 `qa_waiting` 또는 `completed`면 충족, 하나라도 `todo`·`in_progress`·
  `blocked`이거나, 참조한 작업 문서가 없거나, 자기 참조·순환이거나, 목록으로 읽을 수 없는 형식이면
  미충족이다(SPEC-013 R2).
- 세션은 의존이 미충족인 작업을 착수 대상으로 고르지 않으며, 그런 작업만 남아 있으면
  `NO_ELIGIBLE_WORK`를 보고한다. 미충족 작업을 `blocked`로 바꿔 두지 않는다 — `blocked`는 착수한
  뒤 실제로 막힌 작업의 상태다.

### 3. 아키텍트 계약에 병렬 안전 분해 의무를 적는다 (R4)

- 한 승인에서 나온 작업들을 나눌 때 동시 진행 안전성을 판단하고, 코드 범위가 겹치는 작업은
  `depends_on`으로 순서를 준다. 산문의 "병행 금지"를 그대로 옮기지 않고 어느 쪽이 선행인지 정해
  한쪽에만 적는다.
- 작업이 건드리는 범위를 본문의 범위 절에 남긴다. 순환을 만들지 않고, 존재하지 않는 작업 id를 적지
  않고, 겹치지 않는 작업을 방어적으로 직렬화하지 않는다.

### 4. 세 역할 계약의 선점 서술을 §4와 맞춘다 (R8)

- 지금 각 계약은 "대상 id로 이름 붙인 lease로 선점한다"고 적는다. 헬퍼 호출 기준으로 바꾸되, 헬퍼
  미설치 프로젝트의 예외가 §4에 있으므로 계약에는 §4를 따른다는 참조로 충분하다. 계약마다 절차를
  중복 서술해 두 문서가 갈라질 자리를 만들지 않는다.

### 5. 파일 계약 문서를 갱신한다 (R6)

- `docs/file-contract.md`의 개발 작업 절에 `depends_on`의 형식(열 0에서 시작하는 선택 필드, 같은
  워크플로우 안 작업 id 목록)과 R2의 충족 정의를 적는다. "작업 범위가 겹치면 병렬 작업을 금지한다"
  문장을 선언 방법과 함께 정리한다.
- lease 문단을 헬퍼 기준으로 갱신한다. 앱은 계속 읽기만 하고, 세션의 선점·갱신·해제가 헬퍼를
  거친다는 사실과 미설치 시 폴백을 적는다.

### 6. 테스트

- 내장 본문과 설치 파일이 같은 값임을 고정하는 기존 테스트가 새 본문으로 통과한다.
- 버전 상수 인상을 하나만 놓치면 잡히는 TASK-022의 테스트 구조가 5·4로 갱신되어 통과한다.
- 설치본이 앱보다 새 버전이면 멈추는 안전 규칙 테스트가 그대로 통과한다.

## 완료 조건

1. 설치된 `workflow.md` §4가 헬퍼 호출·종료 코드 여섯 개의 의미와 각 경우의 행동·직접 조작 금지·
   미설치 폴백을 담고 `rules_version: 5`다. (SPEC-013 완료 조건 28)
2. 설치된 `developer.md`에 충족 정의와 미충족 작업 선택 금지가, `architect.md`에 병렬 안전 분해
   의무가 적혀 있고 둘 다 `rules_version: 4`다. (SPEC-013 완료 조건 11·12)
3. 세 역할 계약의 선점 서술이 공통 규칙 §4와 어긋나지 않는다.
4. `docs/file-contract.md`가 `depends_on` 계약과 헬퍼 기준 lease 서술을 담고, 계약·조건 스크립트·
   역할 계약과 어긋나는 서술이 없다. (SPEC-013 완료 조건 16)
5. 앱 내장 본문과 설치 파일이 같은 값이고, 기존 규칙 자산 테스트가 삭제·비활성화 없이 통과한다.
6. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다.
   (SPEC-013 완료 조건 29)
