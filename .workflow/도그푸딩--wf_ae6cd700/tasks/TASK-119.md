# 막힘의 구조 사실이 작업 상세에서 평문 문장이 된다

## 결정권자 요약

이 작업이 끝나면, 개발 작업 상세에서 막힌 작업을 열었을 때 왜 막혔는지가 문장으로 읽힌다.
지금은 선행 작업 번호 옆에 "대기 중" 같은 낱말 하나만 놓여 있어서, 그 문서를 쓴 사람이
아니면 무엇을 기다려야 하는지 알 수 없다.

바뀐 뒤에는 선행 작업을 제목으로 부르고, 기다리면 풀리는 것과 사람이 선언을 고쳐야 하는
것이 서로 다른 문장으로 갈린다. 다른 세션과 범위가 겹쳐 막힌 경우도 무엇 때문에 겹쳤는지가
문장에 담긴다.

앱이 새로 알아내는 사실은 없다. 이미 계산해 둔 값을 사람이 읽는 말로 옮기는 것뿐이고,
무엇이 막힘인지 판정하는 규칙은 그대로다.

---

SPEC-039의 R3과 R4다. 기획서 완료 조건 5·6·7·8·9를 이 작업이 닫는다.

SPEC-038과 무관하게 먼저 착지할 수 있는 몫이다(R8). 앱이 이미 계산해 화면까지 보낸 값만 쓰고,
요약 절의 이름을 한 번도 참조하지 않는다.

## 아키텍트가 고정하는 값

### 1. 선행 작업의 제목은 목록에서 찾는다

기획서 제외 범위가 "문서 payload에 새 필드를 만들지, 화면이 목록에서 찾을지"를 아키텍트에게
남겼다(확인 사실 6). **화면이 목록에서 찾는 쪽으로 고정한다.**

근거는 셋이다.

1. `DevelopmentBoard`가 `workflow.items.tasks` 전체를 이미 들고 있고, 그 항목이 `id`와 `title`을
   싣는다. 새 조회도 새 payload도 필요 없다.
2. payload 쪽으로 가면 `src/features/projects/domain/types.ts`와
   `src/features/projects/infrastructure/tauriProjectGateway.ts`, 그리고 Rust의 읽기 경로가 범위에
   들어온다. 그 파일 셋 중 앞의 둘은 TASK-116·TASK-117이 이미 잡고 있어(둘 다 `todo`) 직렬 구간이
   늘어난다. 얻는 것이 없다.
3. Rust를 한 줄도 고치지 않으면 기획서 완료 조건 9("기존 Rust 테스트가 수정 없이 통과")가 그대로
   성립하고, 기획서가 그은 파일 무리의 선("이쪽은 프론트엔드다")이 지켜진다.

`TaskDetail`은 지금 `workflow`를 받지 않는다. 제목을 찾을 값을 `DevelopmentBoard`에서 한 번
추려 넘긴다. 같은 파일 안의 prop 하나가 늘어나는 것이고 새 파일은 생기지 않는다.

`missing` 판정의 선행은 목록에도 없다. 제목을 찾지 못하는 것이 그 판정의 뜻 자체이므로 추정으로
채우지 않는다 — 문장이 id만으로 말한다.

### 2. 문장을 조립하는 자리는 이 파일 안이다

새 모듈을 만들지 않는다. 흡수 대상인 상수 셋(`PERMANENT_DEPENDENCY_NOTE`·`OVERLAP_NOTE`·
`OVERLAP_UNDECLARED_NOTE`)이 지금 `DevelopmentBoard.tsx` 머리에 모여 있고, 문장을 쓰는 자리도
같은 파일의 `TaskDependencies` 하나뿐이다. 쓰는 곳이 하나인 코드를 파일로 가르지 않는다.

TASK-120이 만들 절 추출 모듈과는 성격이 다르다. 그쪽은 두 화면이 함께 쓰므로 밖에 있어야 한다.

### 3. 일곱 갈래가 각각 문장을 갖는다

R3의 대상은 앱이 이미 계산한 구조 사실 전부다. 빠뜨리면 그 갈래만 낱말로 남는다.

| 갈래 | 성격 | 문장이 말해야 하는 것 |
| --- | --- | --- |
| 선행 `satisfied` | 열림 | 그 선행이 끝났다는 것 |
| 선행 `pending` | 기다리면 풀림 | 어느 작업을 기다리는지, 그 작업이 끝나면 열린다는 것 |
| 선행 `missing` | 사람이 고쳐야 함 | 선언이 가리키는 작업이 없다는 것 |
| 선행 `cyclic` | 사람이 고쳐야 함 | 선언이 돌아서 어느 쪽도 먼저일 수 없다는 것 |
| 선언 형식 오류 | 사람이 고쳐야 함 | 선행 선언을 목록으로 읽지 못했다는 것 |
| 겹침 (공유 경로 있음) | 기다리면 풀림 | 어느 문서를 잡은 세션과 어느 경로에서 겹쳤는지 |
| 겹침 (공유 경로 없음) | 기다리면 풀림 | 두 작업 중 한쪽의 범위 선언이 없거나 형식이 잘못됐다는 것 |

- **기다리면 풀리는 것과 사람이 고쳐야 하는 것이 문장으로 갈린다.** 지금은 경고 톤과 상수 문구로만
  갈려 있고(확인 사실 5), 톤은 문장이 하는 말을 대신하지 못한다. 겹침은 lease가 풀리면 열리므로
  기다리는 쪽이다 — 지금의 톤 구분(`permanentDependencyStates`)이 겹침을 뺀 것과 같은 판정이다.
- **겹침의 두 갈래도 문장으로 갈린다.** 공유 경로로 막힌 것은 그 경로가 열리기를 기다리는 일이고,
  선언 부재·형식 오류로 막힌 것은 선언을 고치면 다음부터 겹치지 않는다. 사용자가 할 일이 다르다.
- 선행 미충족과 겹침은 동시에 성립할 수 있고 그때 둘 다 보인다. 지금 주석이 적은 성질 그대로다.

### 4. 문장이 넘지 않는 선 (R4)

- **조립해도 되는 것**: 앱이 계산한 구조 사실의 서술. 선행 판정, 겹침, 상태별 건수가 그것이다.
- **조립하면 안 되는 것**: 원인 추정과 다음 행동 권고. "이 작업은 지금 시작할 수 없다"까지가 앱이
  아는 것이고, "그래서 무엇을 해야 하는가"는 아니다. 선언을 고쳐야 열린다는 것은 판정에서
  유도되는 사실이므로 말해도 되지만, 무엇으로 고치라는 것은 앱이 모른다.
- **규격 밖 값**: `TaskDependencyState`의 넷 밖 값이 오면 규격 밖이라고 말한다. 아는 척도, 조용한
  누락도 아니다. 지금 코드가 `dependencyLabels[entry.state] ?? entry.state`로 원문을 흘리는 자리다.
- 사용자가 실행할 명령 원문은 이 작업에 없다. SPEC-034 R3의 금지는 그대로다.

### 5. 흡수된 상수는 남지 않는다

`PERMANENT_DEPENDENCY_NOTE`·`OVERLAP_NOTE`·`OVERLAP_UNDECLARED_NOTE` 셋과 `dependencyLabels`의
낱말 넷이 문장에 흡수된다. 흡수된 뒤 그 상수가 파일에 남아 있으면 같은 사실이 두 자리에서 말해질
경로가 남는다. 지운다.

`statusLabels`는 흡수 대상이 아니다. 상태 배지가 쓰는 값이고 이 작업이 건드리지 않는다.

### 6. 시작 가능 여부는 지금 자리에 그대로 둔다

`task-dependency-summary`("시작 가능"/"시작할 수 없음")는 이 작업에서 옮기지 않는다. R5가 그것을
기본 뷰의 자리로 옮기라고 하는데, 기본 뷰는 TASK-120의 산출물이라 아직 없다. 여기서 옮기면 같은
자리를 두 번 만든다.

### 7. 넘지 않는 선

- 선행·겹침 판정 규칙을 바꾸지 않는다. `dependency_state`도 `overlap_blocks`도, 조건 스크립트도
  그대로다. 표시만 바꾼다.
- Rust를 고치지 않는다. 문서 payload에 새 필드를 만들지 않는다.
- `blocked` 상태의 사유를 구조에서 유도하지 않는다. 담는 필드가 없다(확인 사실 7).
- 기획서 화면과 아이디어 화면을 건드리지 않는다.
- 일괄 QA 다이얼로그를 건드리지 않는다.
- 기존 자동 테스트를 지우거나 비활성화하지 않는다.

9. 기존 자동 테스트가 삭제되거나 비활성화되지 않는다. 검증: 테스트 목록 변경분 확인. (기획서 완료
   조건 16)
10. `npm run check`가 통과한다. Rust 변경이 없으므로 `cargo test`는 이 작업의 완료 조건이 아니다.
    (기획서 완료 조건 17)
