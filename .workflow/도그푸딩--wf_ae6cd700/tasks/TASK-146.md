# provider 실행을 시작·감시·취소·복구할 수명 계약으로 분리한다

## 결정권자 요약

Claude와 Codex 실행은 시작 직후 안정적인 실행 신원과 이벤트 위치를 돌려준다.
런타임이 다시 시작돼도 같은 프로세스인지 확인한 뒤 기존 감시를 이어 갈 수 있다.
취소는 자식 프로세스와 이벤트 마감을 함께 확인하고 남은 정리 단계를 숨기지 않는다.
작업 지시와 인증 정보는 실행 핸들, 이벤트와 일반 로그에 저장하지 않는다.
기존 한 번 실행 방식은 호환 경로로 유지해 일반 Heartbeat 동작을 바꾸지 않는다.
사용자는 자동 검사에서 재시작, 식별자 재사용과 취소 시나리오를 확인하면 된다.

## 목적

SPEC-054의 R1부터 R4까지를 구현한다. 현재 provider 공통 인터페이스는 진단 뒤 프로세스를 시작하고
종료할 때까지 기다리는 `run` 한 경로만 제공한다. 이를 즉시 반환하는 시작, 이벤트 감시, 종료 대기,
취소와 복구 단계로 나누고 TASK-S051-04의 dispatcher가 별도 설계 없이 소비할 계약을 만든다.

## 현재 상태

- TASK-S051-03은 Claude와 Codex의 명령 구성, 인증 진단, 구조화 이벤트 정규화, 프로세스 트리 종료와
  민감정보 제거를 구현해 품질 확인 대기 상태다.
- 공통 `run`은 프로세스 생성부터 종료까지 한 호출에서 처리하므로 시작 직후 PID와 프로세스 신원을
  영속화할 수 없다.
- 이벤트는 메모리 목록으로만 모인다. 런타임이 종료되면 이어 읽을 파일 위치와 마지막 영속 위치가 없다.
- TASK-S051-04의 dispatcher와 상태 저장소는 이 작업 범위 밖이다. 이번 작업은 그 작업이 사용할
  실행 핸들과 수명 조작을 독립 검사 가능한 형태로 제공한다.

## 실행 수명 계약

### 실행 시작

- `AgentProvider`는 진단과 별개로 `start`를 제공한다. 성공하면 provider 종료를 기다리지 않고
  `ProviderRunHandle`을 반환한다.
- 핸들은 런타임 실행 식별자, provider, 프로젝트, 역할, 대상, 예약 대상과 lease 식별자, PID, 시작
  시각, PID 재사용을 판별할 프로세스 생성 신원, 이벤트 파일과 계약 버전을 가진다.
- 시작 성공은 프로세스가 생성되고 prompt 전달 채널이 닫힌 상태까지만 뜻한다. 역할 성공, 이벤트
  정규화 성공이나 정리 성공으로 확대하지 않는다.
- 진단 실패, 실행 파일 생성 실패, prompt 전달 실패를 구분하고 실패한 시작에서는 성공 핸들을 만들지
  않는다. 프로세스가 만들어진 뒤 prompt 전달이 실패하면 프로세스 트리를 정리한 결과까지 반환한다.
- 예약 실패·경합·마이그레이션 잠금 같은 호출자 실패는 provider를 호출하지 않는다. 예약 성공 응답의
  대상, lease, 결과 식별자 접두어와 역할 인계문은 변경하지 않고 요청과 핸들의 대응을 검증한다.

### 이벤트와 종료 감시

- 실행별 append-only JSONL 이벤트 파일을 다른 실행·프로젝트와 충돌하지 않는 런타임 소유 경로에
  만든다. 표준 출력과 표준 오류는 기존 provider 정규화를 거쳐 기록하고 prompt 원문은 기록하지 않는다.
- `watch`는 핸들과 byte offset을 받아 그 위치 이후의 완전한 이벤트만 돌려준다. 부분 줄은 다음 읽기까지
  보류하고 같은 offset 재요청은 같은 결과를 내야 한다.
- `wait`는 정상 종료, 일반 실패, 사용 제한, 시간 초과, 사용자 취소와 계약 밖 출력을 기존 공통 결과로
  연결한다. 시작 성공과 역할 성공을 같은 상태로 취급하지 않는다.
- 종료 결과에는 실행 식별자, 대상과 lease가 포함돼 예약한 작업과 같은지 검증할 수 있다. 이벤트 마감,
  프로세스 종료와 후속 lease 정리 필요 여부를 단계별로 돌려준다.

### 취소와 복구

- `cancel`은 핸들 하나를 받고 provider별 신호나 명령을 호출자에게 요구하지 않는다. 루트와 모든 자식
  프로세스가 종료됐음을 확인한 뒤에만 취소 완료를 반환한다.
- 프로세스 종료, 이벤트 마감과 후속 정리 중 일부가 실패하면 부분 성공 단계와 남은 행동을 반환하고
  전체 성공으로 표시하지 않는다.
- `recover`는 PID와 프로세스 생성 신원을 함께 대조한다. 같은 살아 있는 프로세스면 새 provider를
  시작하지 않고 기존 이벤트 위치를 이어 읽을 수 있는 결과를 돌려준다.
- PID가 같아도 생성 신원이 다르거나 확인 권한이 없으면 실행 중으로 추측하지 않고
  `recovery_required`와 확인하지 못한 근거를 돌려준다. 죽은 프로세스는 종료·정리 단계로 분류한다.

## 민감정보와 호환성

- 핸들, 이벤트 파일, 종료 결과와 일반 로그에는 prompt 원문, 인증 토큰, API 키와 전체 환경을 넣지 않는다.
- 이벤트 세부 정보는 기존 민감정보 제거를 거치고 계약 밖 원문도 일반 이벤트에 그대로 보존하지 않는다.
- 기존 `run` 공개 동작은 새 시작·감시·대기 조합을 감싸는 호환 경로로 유지한다. 기존 호출자의 결과
  상태와 Claude·Codex 이벤트 의미는 달라지지 않는다.
- provider SDK, dispatcher 큐, SQLite 실행 저장과 실제 lease 갱신·반납은 추가하지 않는다.

## 완료 조건

1. 가짜 Claude와 Codex를 시작하면 종료 전에 실행 식별자, PID, 시작 시각·동등 신원, 예약 대상·lease와
   이벤트 위치를 가진 핸들을 얻는다.
2. 시작 성공과 역할 성공이 다른 상태이며 진단 실패, 실행 파일 시작 실패와 시작 뒤 감시 실패가 서로
   다른 단계로 반환된다.
3. 런타임 감시자를 종료한 뒤 같은 프로세스와 핸들을 복구하면 새 provider 시작은 0회이고 마지막
   확인 offset부터 이벤트가 이어진다.
4. PID가 같지만 프로세스 생성 신원이 다르거나 신원을 확인할 수 없으면 기존 실행으로 채택하지 않고
   `recovery_required`가 된다.
5. 핸들로 취소한 뒤 자식 프로세스가 남지 않는다. 종료나 이벤트 마감 일부 실패는 남은 단계가 있는
   부분 실패로 반환된다.
6. 예약 대상·lease가 요청과 다르면 provider를 시작하지 않고, 예약 실패·경합·마이그레이션 잠금
   픽스처에서도 시작 호출은 0회다.
7. 이벤트 offset 재요청은 중복이나 누락 없이 결정적이며 불완전한 마지막 줄은 완료될 때까지 노출하지
   않는다.
8. 핸들, 이벤트, 종료 결과와 일반 로그를 검색해도 주입한 prompt와 가짜 비밀값이 나오지 않는다.
9. 기존 동기식 `run`, provider 진단, 명령 배열, 이벤트 정규화와 일반 Heartbeat 잡 검사가 변경 전과
   같은 결과로 통과한다.
10. 기존 자동 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. `pytest tests/test_agent_provider_lifecycle.py -v`를 실행한다.
2. 종료 전 핸들 반환, 정상 종료, 느린 이벤트, 부분 줄과 offset 재요청을 가짜 CLI로 검사한다.
3. 감시 프로세스를 종료했다가 같은 자식 프로세스에 다시 연결하고 시작 횟수와 이벤트 연속성을 검사한다.
4. PID 재사용과 프로세스 신원 조회 권한 실패를 주입해 `recovery_required` 근거를 대조한다.
5. 자식 프로세스를 둔 CLI의 취소와 정리 실패를 각각 재현해 프로세스 트리와 단계별 결과를 확인한다.
6. prompt와 가짜 토큰을 주입한 뒤 핸들, JSONL, 결과와 일반 로그 전체를 검색한다.
7. `pytest tests/test_agent_providers.py tests/test_agent_provider_lifecycle.py -v`를 실행한다.
8. `pytest tests/ -q -k 'not test_parse_heartbeat_md_max_per_field'`를 실행해 알려진 기존 격리 검사를
   제외한 전체 회귀를 확인한다.

## 범위와 선행

TASK-S051-03의 공통 provider 진단과 이벤트 정규화를 보존한 뒤 수명 단계를 분리하므로 그 작업이
선행한다. TASK-147과 파일이 겹치지 않아 두 작업은 병렬로 진행할 수 있다. TASK-S051-04의 dispatcher,
상태 저장소와 실제 반복 배정 파일은 수정하지 않는다.
