# 자동 배정이 대상 선점과 결과 식별자를 한 번에 예약한다

## 결정권자 요약

자동 배정은 유료 실행 전에 대상 문서와 결과 식별자를 한 번에 예약한다.
경합한 실행은 다음 후보를 다시 판단해 중복 실행을 시작하지 않는다.
예약 인계를 받은 세션은 같은 소유권을 갱신하고 새 선점을 하지 않는다.
기존 판정 호출은 그대로 두고 자동 검사가 새 계약과 자산 갱신 안전성을 확인했다.
사용자는 확인 동선의 자동 검사 결과를 신뢰해 확인을 남기면 된다.

## 목적

여러 dispatcher가 같은 역할 후보를 동시에 발견해도 provider CLI를 시작하기 전에 대상 하나의
소유권을 확정한다. 현재 자격 도구가 반환하는 후보와 제외 사유를 기계가 읽을 수 있는 형태로
제공하고, 정식 lease와 결과 문서 식별자를 함께 예약하는 관리 자산을 추가한다.

## 현재 상태

- `heartbeat_condition.rs`의 셸·PowerShell 본문과 `role_eligibility.rs`의 앱 판정은 역할별 대상과
  후보별 제외 사유를 계산한다. 조건 스크립트의 기존 표준 출력과 종료 코드는 Heartbeat가 사용한다.
- `claim_helper.rs`가 lease의 배타적 생성, 갱신, 반납을 담당한다. lease 파일을 직접 다루는 새 경로를
  만들면 안 된다.
- 역할 계약은 세션이 직접 `wf-claim`의 `acquire`를 호출하는 경우만 설명한다. 런타임이 먼저 획득한
  lease를 같은 세션에 안전하게 넘기는 계약은 없다.
- planner와 architect가 만드는 결과 문서 식별자는 세션이 정한다. 병렬 세션 두 개가 같은 다음 번호를
  고를 수 있다.

## 변경 범위

- `heartbeat_condition.rs`: 기존 호출의 출력과 종료 코드는 유지하면서, 명시적 기계 출력 모드에서
  역할, 대상, 후보, 제외 사유를 버전화된 JSON 한 건으로 반환한다. 셸과 PowerShell 본문은 같은 값을
  내야 하며 관리 자산 버전을 올린다.
- `reservation_helper.rs`: 셸과 PowerShell용 예약 도구 본문을 새로 둔다. 도구는 자격 결과의 첫 대상을
  `wf-claim`으로 선점하고 경합 시 판정을 다시 수행해 다음 후보를 찾는다.
- `fs_project_repository.rs`, `mod.rs`: 새 관리 자산을 프로젝트에 설치·동기화하고 기존 앱보다 미래
  버전인 설치본을 덮지 않는 안전 규칙과 검사를 연결한다.
- `project_instructions.rs`: 공통 규칙과 세 역할 계약에 런타임 선점 인계 절차와 결과 식별자 사용 규칙을
  추가하고 바뀐 규칙 버전만 올린다.

## 예약 계약

1. 예약 도구는 `acquire <role> <agent> <minutes>`만 공개한다. 성공 결과에는 계약 버전, 역할,
   `targetId`, `leaseId`, `resultPrefix`, 만료 시각, `promptVersion`, `rolePrompt`를 담는다.
2. 대상 선점은 반드시 기존 `wf-claim` 도구를 호출해 수행한다. lease 파일을 새 도구가 직접 만들거나
   수정하거나 지우지 않는다.
3. `wf-claim` 종료 코드 3·4는 경합으로 보고 최신 자격 결과를 다시 읽는다. 종료 코드 1·5,
   마이그레이션 잠금, 읽기 실패는 안전하게 실패한다. 무한 재시도하지 않는다.
4. `resultPrefix`는 획득한 lease마다 유일하다. planner는 그 접두어로 SPEC 식별자를 만들고,
   architect는 같은 접두어와 작업 순번으로 여러 TASK 식별자를 만든다. 파일이 이미 있으면 덮어쓰지
   않고 실행을 중단한다.
5. `rolePrompt`는 앱이 관리하는 역할 계약에서 만든다. 역할, 대상, lease, 결과 접두어와 읽어야 할
   규칙을 담고 provider 이름이나 모델별 문구는 담지 않는다. runtime은 이 prompt를 조립하거나
   수정하지 않고 provider 표준 입력으로 전달한다.
6. 런타임이 넘긴 예약을 받은 세션은 같은 `targetId`와 `leaseId`로 `renew`를 호출해 소유권을
   검증한 뒤 시작한다. 다시 `acquire`하지 않는다. 인계 값이 없는 수동 세션은 기존 절차대로 직접
   선점한다.
7. 세션 종료 시 역할 계약이 정한 보고를 쓴 뒤 같은 lease를 반납한다. 런타임은 프로세스가 종료된 뒤
   같은 lease가 남아 있을 때만 자기 예약을 정리할 수 있다.
8. 예약은 승인, QA, 역할 분리, 한 세션 한 대상 원칙을 바꾸지 않는다. decisions, schema version,
   migration lock은 계속 앱 소유다.

## 손대지 않는 것

- 제품 기능 화면과 provider 실행 코드
- 결정 문서와 기획서 상태
- 기존 자격 판정의 후보 순서와 제외 조건
- 기존 조건 스크립트 호출의 표준 출력, 종료 코드, Heartbeat 연동 방식

## 완료 조건

1. 기존 방식으로 조건 스크립트를 호출하면 표준 출력과 종료 코드가 변경 전과 같다.
2. 기계 출력 모드는 planner, architect, developer 각각의 대상과 모든 후보별 제외 사유를 버전화된
   JSON으로 반환한다.
3. 같은 후보를 두 예약 프로세스가 동시에 요청하면 lease 획득은 하나만 성공하고 다른 프로세스는
   다음 후보를 예약하거나 대상 없음으로 끝난다.
4. 대상이 0건이면 provider 실행에 사용할 성공 응답을 만들지 않는다.
5. 마이그레이션 잠금이 있으면 lease와 결과 예약 정보가 새로 생기지 않는다.
6. 예약 성공 결과의 `targetId`, `leaseId`, `resultPrefix`, `rolePrompt`가 서로 대응하며 두 성공 예약의
   `resultPrefix`가 같지 않다.
7. 예약을 받은 세션의 첫 `renew`가 성공하고, 같은 대상에 별도 `acquire`를 시도하지 않아도 역할
   계약을 충족한다.
8. planner와 architect가 예약 접두어로 결과 파일을 동시에 만들 때 같은 경로를 선택하지 않는다.
9. 셸과 PowerShell 구현이 같은 픽스처에서 같은 대상, 후보, 제외 사유, 종료 상태를 낸다.
10. 앱이 관리 자산을 동기화할 때 새 예약 도구가 설치되고 미래 버전 자산은 덮지 않는다.
11. 같은 예약은 Claude와 Codex에 동일한 `rolePrompt`를 제공하며 runtime이 역할 지시를 따로
    보유하지 않는다.
12. 기존 자동 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. 조건 스크립트의 기존 역할별 시나리오 표를 셸과 PowerShell에서 실행해 기존 출력·종료 코드가
   유지되는지 확인한다.
2. 같은 표를 기계 출력 모드로 실행해 JSON 스키마와 앱 내부 판정의 대상·후보·사유를 대조한다.
3. 임시 프로젝트에 후보 둘을 만들고 예약 프로세스 둘을 동시에 시작해 서로 다른 대상을 얻는지
   확인한다.
4. 후보 하나만 있는 같은 경합에서 성공 하나와 대상 없음 하나가 나오며 lease가 하나뿐인지 확인한다.
5. 마이그레이션 잠금, 다른 소유자의 lease, 만료 lease, 잘못된 자격 출력, 결과 경로 충돌을 각각
   재현해 안전하게 실패하는지 확인한다.
6. 런타임 인계 payload가 있는 역할 세션과 없는 수동 세션의 계약 문구를 검사해 두 시작 경로가
   모순되지 않는지 확인한다.
7. `cargo test --manifest-path src-tauri/Cargo.toml`을 실행한다.

기계 출력과 lease 인계 계약을 사용한다.
