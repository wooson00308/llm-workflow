# 자격 판정이 통합 대기 작업을 구분해 반복 기동하지 않는다

## 결정권자 요약

### 제안

격리 검사를 마쳤지만 사용자의 미커밋 작업 때문에 아직 반영하지 못한 작업을 별도 상태로 판정해, 상황이 그대로인 동안 같은 세션을 다시 시작하지 않게 한다.

### 현재

시작했다가 멈춘 작업은 소유권만 풀리면 곧바로 다시 후보가 된다. 그래서 사용자가 자기 변경을 정리하지 않은 동안에도 같은 작업이 반복해서 다시 시작되고, 매번 같은 이유로 진행하지 못한 채 유료 세션만 소모한다.

### 변경 후

반영을 기다리는 작업은 기다리는 이유가 사라질 때까지 후보에서 빠지고, 겹치지 않는 다른 작업은 그동안 정상적으로 진행된다. 사용자는 자기 작업을 정리하지 않았다는 이유로 같은 세션이 되풀이되는 일을 겪지 않는다.

### 비용과 위험

기다리는 조건을 지나치게 넓게 잡으면 진행할 수 있는 작업까지 멈출 수 있으므로, 판정은 반영을 기다린다는 기록이 실제로 남아 있는 작업에만 적용한다. 사용자 승인 관문, 완료된 작업, 다른 두 역할의 판정은 건드리지 않으며 판정 규칙을 이전 형태로 되돌리면 취소할 수 있다. 이 작업은 판정을 재현하는 자동 검사와 두 판정 구현의 결과가 같은지 대조하는 검사로 확인한다. 판정이 실제로 동작하는 것은 별도로 배포되는 실행 환경이 기록에 반영 대기 단계를 적기 시작한 뒤이며, 그전까지 이 변경은 지금과 같은 판정을 유지한다.

## 막힌 사유

- 막힌 지점: 선언된 두 파일만으로는 완료 조건 6과 8의 앱 판정을 만들 수 없다. `role_eligibility.rs`는 파일 시스템을 읽지 않고 프로젝트 경로 인자도 받지 않으며(모듈 주석 4행), 판정 재료는 전부 `WorkflowInput`으로 들어온다. 기존의 같은 모양 재료인 `unsatisfied_dependencies`와 `overlap_blocked`도 `fs_project_repository.rs`가 계산해 넣어 준다. 그 구조체를 만드는 자리는 `fs_project_repository.rs` 1826~1836행 하나뿐이고 열 개 필드를 모두 적는 구조체 리터럴이라(`..` 생략도 `Default` 구현도 없음), 통합 대기 집합을 새 필드로 더하면 선언 밖 파일에서 컴파일이 깨진다. 완료 조건 8을 확인하는 `assert_matches_condition_script`(503행)는 `FileSystemProjectRepository::inspect`를 통해 실제 배선을 지나므로 시험 안에서만 배선한 값으로는 통과할 수 없다.
- 필요한 해결: 아키텍트가 `scope_files`에 `src-tauri/src/infrastructure/fs_project_repository.rs`를 더하고, 준비 기록과 Git 상태를 읽어 통합 대기 집합을 만드는 자리가 그 파일의 `PreparedWorkflow`임을 변경 범위에 적어야 한다. 제외 사유 값은 `role_eligibility.rs`의 지역 상수로 충분하므로 `domain/project.rs`는 더할 필요가 없다.
- 재개 조건: 위 파일이 `scope_files`에 들어오고 완료 조건 6과 8이 그 파일의 편집을 전제로 다시 서술되면 개발을 다시 시작한다.
- 관련 대상: 없음

## 현재 상태

- 개발자 자격 판정은 두 곳에 같은 규칙으로 구현되어 있다. 프로젝트에 설치되는 판정 스크립트 본문은 `src-tauri/src/infrastructure/heartbeat_condition.rs`의 `CONDITION_SCRIPT_SH`(27행) `developer)` 분기(950행)와 `CONDITION_SCRIPT_PS1`(1162행) `'developer'` 분기(1842행)이고, 앱이 화면에 쓰는 같은 판정은 `src-tauri/src/infrastructure/role_eligibility.rs`의 `developer_verdict`(378행)다.
- 두 구현이 어긋나지 않는지는 `role_eligibility.rs` 시험 모듈의 `assert_matches_condition_script`(504행)가 같은 픽스처로 두 결과를 대조해 확인한다.
- 현재 후보 조건은 `todo`, `in_progress`, 그리고 `definition_error`가 아닌 `blocked`다. 제외 사유는 미만료 lease, 미충족 선행, 범위 겹침 세 가지이고 `developer_verdict`가 각각 `LEASED`, `DEPENDENCIES_UNSATISFIED`, `OVERLAP`으로 기록한다.
- 죽은 세션이 남긴 `in_progress` 작업은 그 작업을 덮는 미만료 lease가 없으므로 곧바로 다시 후보가 된다. 판정에는 그 작업이 왜 멈췄는지를 구분하는 수단이 없다.
- `role_eligibility.rs`는 파일 시스템을 읽지 않는다. 모듈 주석 4행이 그 사실을 규정하고 있고, `pending_role_work`(103행)와 `developer_verdict`(378행) 어느 쪽도 프로젝트 경로를 받지 않는다. `WorkflowInput`(35행)의 `directory`는 절대 경로가 아니라 디렉터리 이름이다.
- 그래서 파일을 읽어야 하는 제외 재료는 모두 `src-tauri/src/infrastructure/fs_project_repository.rs`가 만들어 넘긴다. 미만료 lease 집합은 `summary_from_manifest`(1801행)가 `lease_ids`(1809행)로 만들어 `pending_role_work`에 인자로 주고, `unsatisfied_dependencies`와 `overlap_blocked`는 `PreparedWorkflow`(1870행)가 계산해 `WorkflowInput` 구조체 리터럴(1826~1837행)에 싣는다. 그 리터럴은 열 개 필드를 모두 적으며 `..` 생략도 `Default` 구현도 없다.
- 제외 사유 값 중 `LEASED`, `DEPENDENCIES_UNSATISFIED`, `OVERLAP`은 `src-tauri/src/domain/project.rs`의 공개 상수(160·169·172행)이고, `role_eligibility.rs`가 29~30행에서 가져다 쓴다. 화면은 이 값을 이름으로 해석하지 않는다. `AgentRunDashboard.tsx`의 `eligibleQueue`(578행)가 `eligible`인 후보만 골라 대기열에 넣으므로, 새 사유 값은 화면 수정 없이 그대로 실려 나간다.
- 두 판정의 대조 검사 `assert_matches_condition_script`(504행)는 `FileSystemProjectRepository::inspect`를 호출해 실제 배선으로 앱 판정을 만든 뒤 스크립트 실행 결과와 비교한다. 시험 모듈 안에서만 조립한 값으로는 이 대조를 만족시킬 수 없다.
- 격리 준비 기록은 TASK-RES-20260815T032125Z-60360-20260815032125-02가 `.workflow/.runtime/isolation/<대상 식별자>.yml`에 남긴다. 담는 값은 `schema_version`, `target_id`, `lease_id`, `base_commit`, `branch`, `workspace_path`, `control_root`, `prepared_at`, `step`이고, 현재 `step`에 들어오는 값은 `preparing`, `ready`, `failed:worktree`, `failed:record` 넷이다. 반영 대기를 뜻하는 값은 아직 없다.
- 앱은 제품 코드에서 Git 명령을 실행한 적이 없다. Git을 부르는 자리는 시험 모듈뿐이고, `reservation_helper.rs` 시험의 `git_project` 보조 함수(437행)가 임시 프로젝트에 저장소와 첫 커밋을 만드는 방식을 이미 갖고 있다.
- 판정 스크립트의 판 번호는 `CONDITION_SCRIPT_VERSION`(20행, 현재 20)과 두 본문 3행의 주석이 함께 들고 있다.

## 변경 범위

같은 판정 규칙을 세 곳에 구현한다. 설치되는 판정 스크립트의 두 본문은 `src-tauri/src/infrastructure/heartbeat_condition.rs`에, 앱 판정은 `src-tauri/src/infrastructure/role_eligibility.rs`에 있으며, 앱 판정이 쓸 재료를 파일에서 읽어 만드는 자리는 `src-tauri/src/infrastructure/fs_project_repository.rs`다. 새 제외 사유 값 하나는 `src-tauri/src/domain/project.rs`에 둔다.

1. 통합 대기를 뜻하는 준비 기록의 단계 값을 `integration_waiting`으로 정한다. 이 값은 판정이 읽는 쪽에서 규정하고, 기록에 실제로 적는 주체는 별도로 배포되는 실행 환경이다. 그 실행 환경이 값을 적기 전까지 이 판정은 어떤 작업도 새로 제외하지 않는다.
2. 개발자 후보 판정에 통합 대기 제외를 추가한다. 어떤 작업의 `.workflow/.runtime/isolation/<대상 식별자>.yml` 기록의 `step`이 `integration_waiting`이면, 그 작업은 기다리는 이유가 그대로인 동안 후보에서 뺀다.
3. 기다리는 이유가 그대로인지는 두 가지를 함께 보아 판정한다. 공유 작업 공간에 추적 파일의 미커밋 변경 또는 stage된 변경이 남아 있고, 동시에 기록의 `base_commit`이 공유 기준의 현재 커밋과 같으면 그대로다. 둘 중 하나라도 달라지면, 즉 공유 작업 공간이 깨끗해졌거나 기준 커밋이 전진했으면 그 작업은 다시 후보가 된다. 미추적 파일은 보지 않는다.
4. Git 상태는 통합 대기 단계의 기록이 하나라도 있을 때만 조회한다. 그런 기록이 없으면 Git 명령을 실행하지 않고 판정이 변경 전과 완전히 같은 경로로 끝난다. 앱은 지금까지 제품 코드에서 Git을 실행하지 않았고 판정은 프로젝트를 읽을 때마다 도는 경로이므로, 조회 비용을 이 조건 뒤에 둔다.
5. 앱 판정의 재료는 `fs_project_repository.rs`가 만든다. 통합 대기로 제외할 작업 식별자 집합을 `summary_from_manifest`에서 계산해 `role_eligibility.rs`로 넘긴다. 기록 파일은 컨트롤 루트 하나 아래에 대상 식별자로 저장되고 Git 기준도 프로젝트 하나에 하나이므로, 워크플로우마다 다시 만들지 않고 `lease_ids`와 같은 자리에서 한 번 만들어 모든 워크플로우가 같은 집합을 본다. `role_eligibility.rs`는 그 집합을 받기만 하고 파일 시스템과 Git을 직접 만지지 않는다. 이 규정은 지키되, 집합을 `WorkflowInput`의 새 필드로 실을지 `pending_role_work`의 새 인자로 줄지는 구현자가 고른다.
6. `developer_verdict`에 통합 대기 제외 사유를 새 값 `integration-waiting`으로 기록한다. 상수는 `domain/project.rs`의 `LEASED`·`DEPENDENCIES_UNSATISFIED`·`OVERLAP` 옆에 공개 상수로 두어, 이 값이 구분되어야 하는 세 사유와 한자리에서 읽히게 한다. 화면은 고치지 않는다.
7. 제외 사유를 보는 차례는 기존 세 사유 뒤, 원천 결정과 작업 그룹 판정 앞에 둔다. lease·선행·겹침은 통합 대기와 무관하게 성립하는 조건이고, 통합 대기 작업은 이미 승인된 원천에서 나온 작업이므로 그 뒤의 두 판정까지 갈 이유가 없다. 스크립트 본문과 앱 판정이 같은 차례를 쓴다.
8. 통합 대기 제외는 그 작업 하나에만 적용한다. 같은 워크플로우의 다른 작업은 기존 조건 그대로 판정하며, 범위가 겹치지 않는 작업이 통합 대기 작업 때문에 후보에서 빠지지 않는다.
9. 기록 파일이 없거나, 읽을 수 없거나, `step`이 `integration_waiting`이 아닌 작업은 지금과 똑같이 판정한다. 기록이 없다는 사실만으로 후보에서 빼지 않는다.
10. 기록은 통합 대기인데 Git 조회가 실패하면, 즉 프로젝트가 Git 작업 트리가 아니거나 Git을 실행할 수 없거나 현재 커밋을 읽을 수 없으면 그 작업을 제외한 채로 둔다. 기다림이 끝났다는 근거를 얻지 못한 상태이므로 대기를 유지하는 쪽이 반복 기동을 막는 이 작업의 목적에 맞다. 세 구현이 모두 같게 처리한다.
11. `planner`와 `architect` 분기의 판정은 바꾸지 않는다.
12. `CONDITION_SCRIPT_VERSION`을 21로 올리고 두 본문 3행의 판 번호 주석도 21로 맞춘다. 같은 파일 2105·2119~2120행의 리터럴 판 번호 검사를 새 값으로 맞춘다.

- 공유 작업 공간이 정리된 사실을 감지해 통합을 다시 올리는 일. 이 작업은 판정만 바꾸고 감지와 재기동은 실행 환경의 몫이다.
