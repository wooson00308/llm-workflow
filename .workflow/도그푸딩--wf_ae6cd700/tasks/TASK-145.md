# 막힌 사유와 관련 대상을 작업 우측 패널에 표시한다

## 결정권자 요약

막힌 작업의 현재 사유, 필요한 해결, 재개 조건과 관련 대상을 오른쪽 패널에 표시했다.
실제 작업만 제목과 상태가 있는 열기 동작으로 만들고 나머지는 작성된 문구 그대로 보존했다.
새 형식이 없는 기존 문서는 결정권자 요약 또는 원문 확인 안내로 안전하게 처리했다.
품질 확인 대기 화면의 메모와 완료 조작, 다른 상태의 기존 안내는 그대로 유지했다.
자동 검사 831개와 배포 빌드가 통과해 구현은 사용자 품질 확인을 기다린다.
사용자는 넓은 화면과 작은 화면에서 표시 순서, 키보드 이동과 긴 문장 줄바꿈을 확인하면 된다.

## 목적

SPEC-053의 R3부터 R8까지를 구현한다. 현재 `TaskDetail`의 오른쪽 패널은 QA 대기일 때 확인 동선과 사용자
조작을 보여 주지만 `blocked`에서는 상태명과 공통 안내만 보여 준다. TASK-144의 결정적 파서를 사용해
작성된 현재 사유를 같은 정보 계층에 추가하고, 불완전한 기존 문서는 추측 없이 폴백한다.

## 현재 상태

- `DevelopmentBoard.tsx`의 `TaskDetail`은 본문, 현재 작업 요약, 계산된 선행 판정과 파일 겹침을 이미
  가지고 있다. 새 백엔드 payload 없이 표시할 수 있다.
- 작업 목록인 `workflow.items.tasks`에는 각 작업의 식별자, 제목, 상태와 파일명이 있다. 관련 대상과
  정확히 일치하는 실제 작업을 확인하고 기존 `onReadTask` 경로로 여는 데 충분하다.
- 구조 정보는 왼쪽 문서 영역의 `TaskDependencies`가 출처를 구분해 표시한다. 이번 작업은 그 영역을
  옮기거나 같은 문장으로 다시 만들지 않는다.
- 작업 상세 레이아웃은 넓은 화면에서 문서와 오른쪽 패널 두 열, 980픽셀 이하에서 한 열이 된다. QA
  패널 너비 조절 장치는 작은 화면에서 이미 숨겨진다.
- TASK-S052-03과 TASK-S052-04가 결정 보드와 개발 화면 회귀 검사를 준비 중이다. 새 막힘 영역을 독립
  구성 요소와 스타일로 두고 기존 전역 스타일 및 기존 대형 검사 파일을 수정하지 않아 파일 충돌을
  피한다.

## 변경 범위

### 상태별 오른쪽 패널

- 현재 상태가 `blocked`이면 QA 대기 분기보다 먼저 막힘 패널을 선택하고 제목을 `진행이 막혔습니다`로
  표시한다.
- 유효한 절이 있으면 `작성된 막힘 사유`라는 출처 영역에서 막힌 지점, 필요한 해결, 재개 조건, 관련
  대상을 이 순서로 표시한다. 각 값은 TASK-144가 반환한 뜻을 축약·번역·추론하지 않는다.
- 작업 문서의 `updatedAt`을 사유의 최신성으로 함께 표시한다. 값이 없거나 읽을 수 없으면 시각을
  지어내지 않고 확인할 수 없다고 표시한다.
- `qa_waiting`이면 현재 확인 동선, 메모, 완료와 개발 준비로 되돌리기 조작을 그대로 유지한다.
  `completed`와 그 밖의 상태도 기존 안내와 조작 부재를 유지한다.
- 막힘 패널에는 `todo` 전환, lease 정리, 재개, QA 결정과 자동 수정 조작을 넣지 않는다.

### 관련 대상

- TASK-144가 반환한 관련 대상 순서대로 각 항목을 그린다. 값이 `없음`이면 링크나 대체 대상을 만들지
  않고 관련 대상 없음으로 표시한다.
- 문자열이 현재 워크플로 작업 요약의 `id`와 문자 단위로 정확히 일치할 때만 실제 작업으로 본다.
  해당 항목은 식별자, 제목, 현재 상태와 키보드로 누를 수 있는 열기 동작을 제공한다.
- 실제 작업 항목을 열면 기존 `onReadTask`를 해당 파일명으로 한 번 호출하고 성공한 문서로 상세를
  교체한다. 읽기 실패에서는 현재 문서를 버리거나 가짜 문서를 만들지 않는다.
- 존재하지 않는 작업 식별자와 외부 저장소·사람·승인 설명은 링크, 제목과 상태를 만들지 않고 작성된
  텍스트 그대로 표시한다. 한 항목의 확인 실패가 뒤 항목을 숨기지 않는다.

### 기존 문서 폴백

- 현재 상태가 `blocked`인데 파서 결과가 `null`이면 정확한 `## 결정권자 요약` 절을 찾아 패널에
  Markdown 원문 그대로 표시한다. 구조화 요약 값으로 재조립하거나 자동 요약하지 않는다.
- 결정권자 요약도 없으면 `구조화된 막힘 사유가 없습니다`라고 표시하고 왼쪽 문서의 `원문 전문 보기`
  동작을 사용할 수 있음을 안내한다. 원인과 관련 대상을 추측하지 않는다.
- 불완전하거나 중복된 막힌 사유 절도 부분 값을 표시하지 않고 같은 폴백을 사용한다.
- 원문 보기의 기존 토글과 원문 내용은 변경하지 않는다. 사용자가 원문을 열었을 때 마지막 막힌 사유
  절이 그대로 보존돼 있어야 한다.

### 구성 요소와 접근성

- 막힘 전용 표시를 `BlockedTaskPanel.tsx`로 분리하고 스타일은 `BlockedTaskPanel.css`에 둔다.
  `DevelopmentBoard.tsx`는 파서 결과, 폴백 절, 작업 목록과 열기 콜백을 연결한다.
- DOM 순서는 제목, 최신성, 네 항목, 관련 대상 순서다. 실제 작업 열기와 기존 원문 보기 동작은
  키보드 포커스를 받고 알아볼 수 있는 접근성 이름을 가진다.
- 색상만으로 실제 작업, 외부 설명과 상태를 구분하지 않는다. 긴 한국어 문장과 공백 없는 식별자는
  패널 폭 안에서 줄바꿈된다.
- 작은 화면에서는 기존 상세 레이아웃의 한 열 전환을 유지하고 막힘 패널 내부도 한 열 순서를 유지한다.
  넓은 화면과 작은 화면에 별도 DOM을 만들지 않는다.
- 기존 선행·형식·겹침 영역과 시작 가능 판정을 그대로 둔다. 작성자 사유를 근거로 판정을 바꾸거나
  구조 정보를 막힘 문장으로 다시 만들지 않는다.

## 손대지 않는 것

- 작업 상태, 이력, 결정 기록, lease와 Markdown 파일 쓰기
- 선행 충족, 순환·누락, 파일 겹침과 시작 가능 판정
- QA 대기 조작과 일괄 QA 화면
- LLM, 네트워크 조회, 새 Tauri 명령과 브라우저 저장
- 기존 작업 문서와 보고서의 소급 변환
- 결정 보드, 문서 원문 렌더러와 전역 스타일 파일
- SPEC-054가 제안한 blocked 재개 조작

## 완료 조건

1. 네 필수 값이 있는 `blocked` 작업을 열면 오른쪽 패널에 제목, 작성 출처, 막힌 지점, 필요한 해결,
   재개 조건, 관련 대상과 문서 갱신 시각이 정한 순서로 보인다.
2. 실제 작업과 정확히 일치하는 관련 대상은 식별자, 제목, 상태와 열기 동작을 제공하고, 열기 성공 시
   같은 상세 화면에서 해당 작업으로 바뀐다.
3. 외부 의존과 존재하지 않는 작업은 링크·제목·상태를 지어내지 않고 작성된 텍스트만 보인다. 여러
   대상의 작성 순서가 유지되고 하나의 실패가 나머지를 가리지 않는다.
4. 관련 대상 `없음`은 링크와 대체 문구를 만들지 않고 대상이 없다는 작성 사실만 보여 준다.
5. 유효한 막힌 사유 절이 없는 `blocked` 작업은 결정권자 요약으로 폴백하고, 불완전한 절의 일부 값은
   섞어 표시하지 않는다.
6. 결정권자 요약도 없는 작업은 구조화된 사유가 없다는 안내와 원문 확인 경로를 보여 주며 원인을
   추측하지 않는다.
7. 마지막 막힌 사유 절이 남아 있어도 상태가 `blocked`가 아니면 현재 사유로 표시하지 않는다. QA
   대기와 완료·그 밖의 상태의 기존 패널 동작이 유지된다.
8. 기존 선행·형식·겹침 표시와 시작 가능 판정이 그대로 보이고, 그 문장을 작성자 사유 영역에서 다시
   반복하지 않는다.
9. 넓은 화면과 980픽셀 이하 화면에서 정보가 같은 DOM 순서로 한 열에 쌓이며 긴 문장과 식별자가
   가로로 잘리지 않는다.
10. 키보드만으로 실제 관련 작업과 기존 원문 보기 동작에 화면 읽기 순서대로 도달할 수 있고, 색상 없이도
    각 항목의 의미와 상태가 읽힌다.
11. 표시와 관련 작업 열기 외에 QA 콜백, 파일 쓰기, 결정·lease 변경, 네트워크·LLM 호출과 새 브라우저
    저장이 발생하지 않는다.
12. 기존 검사를 삭제하거나 약화하지 않고 프런트엔드 전체 검사가 통과한다.

## 검증 절차

1. `npx vitest run src/features/projects/components/BlockedTaskPanel.test.tsx`를 실행한다.
2. 유효한 절, `없음`, 실제·없는 작업 식별자와 외부 의존이 섞인 픽스처를 각각 열어 표시 순서, 제목,
   상태와 링크 유무를 확인한다.
3. 제목·라벨 누락과 중복, 빈 값과 절 없음 픽스처로 결정권자 요약 폴백과 무요약 안내가 각각
   선택되는지 확인한다.
4. 같은 막힌 사유 절을 `todo`, `in_progress`, `qa_waiting`, `completed` 상태 문서에 넣어 현재 막힘
   패널이 나오지 않고 기존 분기가 유지되는지 확인한다.
5. 관련 작업 버튼을 키보드로 실행해 `onReadTask`가 정확한 파일명으로 한 번 호출되고 성공 때만
   상세가 교체되는지 확인한다. 외부·없는 항목에는 버튼이 없는지 확인한다.
6. 기존 선행·겹침 픽스처와 막힌 사유를 함께 렌더해 구조 정보가 유지되고 공통 문장이 중복되지 않는지
   확인한다.
7. 새 스타일을 원문으로 읽는 회귀 검사에서 패널 항목의 한 열 흐름과 긴 문자열 줄바꿈 선언을 확인한다.
   jsdom은 실제 레이아웃을 계산하지 않으므로 980픽셀 이하의 실제 배치는 사용자 QA에서 함께 확인한다.
8. 저장소 루트에서 `npm run check`를 실행해 타입 검사, 프런트엔드 전체 검사와 배포 빌드가 통과하는지
   확인한다.

## 범위와 선행

TASK-144의 파서 결과를 사용하므로 그 작업이 `qa_waiting` 또는 `completed`가 된 뒤 시작한다.
TASK-143과는 파일이 겹치지 않아 병렬로 진행할 수 있다. 기존 진행 중인 TASK-S052-01과도 파일이
겹치지 않는다. 결정 보드 작업이 예정한 전역 스타일과 기존 대형 검사 파일을 수정하지 않고 독립 파일을
사용하므로 TASK-S052-03·04와의 불필요한 직렬화를 만들지 않는다.

## 확인 동선

1. 앱의 개발 작업 화면에서 `blocked` 상태이며 유효한 `## 막힌 사유` 절이 있는 작업을 연다.
2. 오른쪽의 `진행이 막혔습니다` 패널에서 문서 갱신 시각, 막힌 지점, 필요한 해결, 재개 조건과 관련
   대상이 작성 순서대로 보이는지 확인한다.
3. 실제 작업과 일치하는 관련 대상은 식별자, 제목과 현재 상태가 보이는 버튼인지 확인하고, 키보드로
   실행했을 때 같은 상세 화면에서 그 작업이 열리는지 확인한다.
4. 없는 작업이나 외부 의존은 버튼 없이 작성 문구만 보이고, 관련 대상이 `없음`이면 대체 링크가 생기지
   않는지 확인한다.
5. 구조화 사유가 없는 막힌 작업에서는 결정권자 요약 또는 원문 확인 안내가 나오며 원인을 추측하지
   않는지 확인한다.
6. 창 너비를 980픽셀 이하로 줄여 패널이 문서 아래 한 열로 쌓이고 긴 문장과 식별자가 가로로 잘리지
   않는지 확인한다. 다시 넓힌 뒤에도 정보 순서가 같은지 확인한다.
7. `qa_waiting` 작업을 열어 기존 확인 동선, 메모 입력, 완료와 개발 준비로 되돌리기 조작이 그대로인지
   확인한다. 이 확인 결과를 TASK-145 품질 확인 메모에 기록한다.
