# 실행 화면이 한도 대기와 한도로 끝난 실행을 다른 문장으로 보여준다

## 결정권자 요약

### 제안

실행 화면이 어느 실행 도구가 사용 한도 대기 중이고 언제 다시 시작하는지를 보여주고, 한도로 끝난
실행의 종료 사유를 사용 한도 도달로 표시한다.

### 현재

계정 사용 한도와 동시 실행 자리 소진이 화면에서 같은 문장으로 나온다. 지금 규칙은 종료 사유
문자열에 한도라는 낱말이 들어 있으면 자리가 모두 사용 중이라는 문장으로 바꾸는데, 두 상황은
사용자가 해야 할 일이 전혀 다르다. 한도 대기 자체를 알려주는 자리도 없어, 사용자는 왜 아무것도
시작되지 않는지 알 수 없다.

### 변경 후

한도 대기 중이면 실행 화면 위쪽에서 어느 실행 도구가 쉬고 있고 언제 다시 시작하는지가 바로 보인다.
다시 시작할 시각을 모를 때는 시각을 지어내지 않고 남은 대기만 보여준다. 한도로 끝난 실행을 열면
종료 사유가 사용 한도 도달로 적혀 있고, 자리 소진과 대상 없음과 로그인 필요는 각각 자기 문장을
갖는다. 보류 중에 직접 배정을 시도하면 한도 대기라는 사실을 알려주되 시작을 막지는 않는다.

### 비용과 위험

문구는 비개발자가 읽을 말로 쓰고 내부 상태 이름이나 파일 경로를 그대로 보여주지 않는다. 보류가
없을 때 화면은 지금과 똑같다. 이 작업은 배정을 멈추지도 설정을 바꾸지도 않으며 표시만 더한다.
되돌리면 지금 화면으로 그대로 돌아간다.

## 현재 코드 상태

실행 화면의 본체는 `src/features/projects/components/agents/AgentRunDashboard.tsx` 78행의
`AgentRunDashboard`이고, 124행부터 진행 중·배정 대기·최근 종료·앱 밖 세션 구역을 차례로 그린다.
실행 목록은 89행에서 `state.queue?.runs`로 읽는다.

종료 사유를 사람 말로 옮기는 자리는 세 함수다. 694행의 `exclusionLabel`은 시작 조건 확인이 돌려준
제외 사유 목록을 한 문장으로 바꾸고, `limit_reached`가 있으면 자리가 모두 사용 중이라고 답한다.
695행의 `reasonLabel`은 실행 행의 사유 문자열을 문장으로 바꾸는데, `/limit/` 정규식에 걸리면 실행
자리가 모두 사용 중이라고 답한다. 719행의 `humanRuntimeMessage`도 `limit_reached`에 같은 문장을
낸다. 계정 사용 한도가 이 세 자리 어디에서도 자기 문장을 갖지 못한 것이 지금 상태다.

실행 상세에서 종료 사유를 보여주는 자리는 같은 파일 395행이고, 값이 있으면 `reasonLabel`을 통과시켜
그린다. 그래서 사유 문장을 고치면 상세 표시도 함께 고쳐진다.

배정이 비는 이유를 문장 하나로 세우는 선례가 이미 있다. 99행에서 만든 단독 수행 안내를 228행이
배정 대기 구역 안에 그리고, 스타일은 `src/App.css` 73행의 `agent-queue-notice`다. 다만 그 구역은
226행의 조건에 따라 대기 후보나 안내가 있을 때만 나타난다.

직접 배정 창은 같은 파일 287행의 `DirectAssignDialog`다. 334행이 시작 조건 확인 결과를 문장으로 보여주는 자리이고,
335행의 단추가 실제 시작을 건다. 역할별 실행 도구는 화면이 이미 손에 쥐고 있다 —
`src/features/projects/domain/types.ts` 1449행의 `AgentProjectPolicy`가 역할 이름으로 찾는
`roles`를 담고, 1433행의 `AgentRolePolicy`에 실행 도구 이름이 있다. 대시보드는 303행과 633행에서
이미 같은 정책 값을 읽고 있다.

실행 목록 응답의 타입은 `src/features/projects/domain/types.ts` 1669행의 `AgentQueueSnapshot`이다.
TASK-S071-01이 이 응답에 실행 도구별 보류 목록을 더하지만 화면 타입에는 아직 그 항목이 없다.

## 완료 조건

- C1. 실행 목록 응답의 보류 목록을 화면 타입에 더한다. `AgentQueueSnapshot`에 항목 `providerHolds`를
  넣고, 값은 실행 도구 이름과 다시 시작할 시각과 그 시각을 아는지 여부를 담은 항목들의 배열이다.
  선택 항목으로 두어 이 값을 싣지 않는 응답에서도 화면이 지금과 같이 그려진다(R-04).
- C2. 한도 대기 중인 실행 도구가 있으면 실행 화면에서 상세를 열지 않고 알 수 있다(R-15). 안내는
  진행 중 구역보다 위, 화면 본문의 첫 자리에 선다. 배정 대기 구역 안에 넣지 않는다 — 그 구역은
  대기 후보가 없으면 통째로 사라지므로 요구를 충족하지 못한다.
- C3. 안내 문장에 어느 실행 도구가 대기 중인지와 언제 다시 시작하는지가 담긴다(R-16). 다시 시작할
  시각을 아는 경우에는 그 시각을 사용자가 읽는 시각 표기로 보여준다.
- C4. 다시 시작할 시각을 모르는 경우에는 시각을 보여주지 않고, 다시 시도할 때까지 남은 대기를
  보여준다(R-17). 남은 대기는 시간이 흐르면 저절로 낡는 값이므로 화면에 머무는 동안 다시 계산해
  갱신한다. 갱신 주기는 같은 파일이 이미 쓰는 30초 주기를 따른다.
- C5. 보류 중인 실행 도구가 둘 이상이면 모두 알 수 있다. 하나만 보여주고 나머지를 감추지 않는다.
- C6. 보류가 없으면 안내를 그리지 않는다. 보류가 없을 때의 화면은 지금과 한 픽셀도 다르지 않다.
- C7. 계정 사용 한도가 자기 문장을 갖는다(R-18). 종료 사유가 TASK-S071-01이 정한 한도 도달 구분값과
  정확히 같을 때만 사용 한도 도달 문장을 낸다. 사유 문자열에 한도라는 낱말이 들어 있다는 이유로
  이 문장이 나오지 않는다.
- C8. 동시 실행 자리 소진, 배정할 대상 없음, 실행 도구 로그인 필요는 각각 지금의 자기 문장을
  그대로 유지한다(R-18). 세 문장과 사용 한도 도달 문장이 서로 다르다. `reasonLabel`의 `/limit/`
  정규식이 계정 사용 한도를 먼저 삼키지 않도록 판정 차례를 바로잡는다.
- C9. 같은 구분을 `exclusionLabel`과 `humanRuntimeMessage`에도 넣는다. 시작 조건 확인이 계정 사용
  한도로 자리를 내주지 않았을 때와 런타임 메시지가 그 사유를 담고 왔을 때 모두 사용 한도 도달
  문장이 나온다. 세 함수가 같은 판정 함수를 쓰고 각자 정규식을 따로 갖지 않는다.
- C10. 한도로 끝난 실행의 상세에서 종료 사유가 사용 한도 도달로 보인다(R-19). 395행이 이미
  `reasonLabel`을 통과시키므로 C7이 서면 이 조건도 함께 선다. 상세를 열지 않아도 최근 종료 목록의
  같은 문장이 바뀌는 것까지 확인한다.
- C11. 직접 배정은 보류가 막지 않는다(R-14). 창의 시작 단추가 보류를 이유로 비활성이 되지 않고,
  시작 조건 확인과 시작 동작이 지금 그대로다.
- C12. 직접 배정 창의 시작 조건 확인 단계에서 지금 그 실행 도구가 한도 대기 중이라는 사실을
  알린다(R-14). 고른 역할의 실행 도구를 정책에서 찾아 보류 목록과 맞춰 보고, 대기 중이면 경고
  문장을 보여준다. 정책이나 보류 목록을 읽지 못하면 경고를 지어내지 않고 지금과 같이 그린다.
- C13. 모든 문구를 비개발자가 읽고 무엇을 기다리는지 알 수 있는 말로 쓴다(R-20). 내부 상태 이름,
  사유 코드, 파일 경로, 식별자를 화면 문장에 그대로 쓰지 않는다. 실행 도구 이름은 사용자가 설정
  화면에서 이미 만나는 이름이므로 그대로 쓴다.
- C14. 이 작업은 배정을 멈추거나 다시 열지 않고 설정값을 바꾸지 않는다(R-12, R-13). 실행을
  취소하거나 다시 시작하지 않는다(R-22). 워크플로 문서를 쓰지 않는다(R-21).
- C15. 다음 검사를 `AgentRuntimeView.test.tsx`에 넣는다. 보류 목록을 담은 실행 목록 응답을 주어
  화면을 그리고 확인한다.
  - 보류가 있는 응답으로 그리면 상세를 열지 않은 첫 화면에 그 실행 도구 이름과 다시 시작할 시각이
    보이고, 그 문장이 자리 소진 문장이나 대상 없음 문장과 다르다(인수 조건 5).
  - 다시 시작할 시각을 모르는 응답으로 그리면 시각이 보이지 않고 남은 대기가 보인다(인수 조건 6).
  - 보류 목록이 비었거나 항목 자체가 없는 응답에서는 안내가 그려지지 않는다(인수 조건 11).
  - 한도 구분값이 실린 종료 행의 상세를 열면 사유가 사용 한도 도달로 보인다(인수 조건 7).
  - 사유 문자열에 한도라는 낱말이 들어 있으나 구분값과 같지는 않은 종료 행에서는 지금의 자리 소진
    문장이 그대로 나온다(R-18).
  - 보류 중에 직접 배정 창을 열어 시작 조건을 확인하면 한도 대기 경고가 보이고, 시작 단추가
    비활성이 아니다(인수 조건 8).
- C16. 선언한 네 파일 밖의 파일이 바뀌지 않는다.

- 실행 도구 진단 구역의 문구와 상태 표시.
- 실행 목록 조회 주기.

## 범위 사전 검사

이 작업이 다루는 값은 둘이다. 실행 목록 응답이 실어 오는 실행 도구별 보류 목록과, 실행 행의 종료
사유 문자열이다. 둘 다 원천에서 화면까지 따라가 확인했다.

- 값 경로: 실행 도구별 보류 목록(C1~C6, C12, 인수 조건 5·6·8·11). 원천은 TASK-S071-01이
  `QueueSnapshot`에 더하는 `providerHolds`이고 소비자는 화면 안내와 직접 배정 창이다. hop은
  넷이다. (1) 백엔드의 응답 조립. 이전 작업이 맡으므로 이 작업의 편집 대상이 아니다. (2)
  `src/features/projects/infrastructure/tauriProjectGateway.ts` 349행의 `inspectAgentRuns`가
  `invoke<AgentQueueSnapshot>`으로 응답 전체를 그대로 받는다. 파일을 열어 확인했고 항목별로
  옮겨 담는 코드가 없어 항목을 더해도 이 파일은 바뀌지 않는다. 선언에서 뺐다. (3)
  `src/features/projects/application/useProjectWorkspace.ts` 339행의 `readAgentRuns`가 받은 값을
  상태의 `queue`에 통째로 넣는다. 345행부터를 열어 확인했고 항목을 골라 담지 않으므로 이 파일도
  바뀌지 않는다. 선언에서 뺐다. 지금 다른 작업들이 잡고 있는 파일이기도 하다. (4)
  `src/features/projects/domain/types.ts` 1669행의 `AgentQueueSnapshot`과
  `AgentRunDashboard.tsx`. 타입에 항목이 없고 화면에 그리는 코드가 없으므로 둘 다 편집 대상이다.
  직접 배정 창이 실행 도구를 찾는 데 쓰는 정책 값은 같은 타입 파일 1433행과 1449행에 이미 있고
  대시보드가 303행에서 이미 읽고 있으므로, 그 경로에는 편집이 필요 없다.
- 값 경로: 종료 사유 문장(C7~C10, 인수 조건 7). 원천은 실행 행의 사유 문자열이고 소비자는 최근
  종료 목록과 실행 상세와 직접 배정 창이다. hop은 셋이다. (1) `AgentRunDashboard.tsx` 694행의
  `exclusionLabel`, 695행의 `reasonLabel`, 719행의 `humanRuntimeMessage`. 세 자리 모두 계정 사용
  한도를 자리 소진으로 옮기고 있으므로 편집 대상이다. (2) 같은 파일 395행의 상세 사유 표시. 이미
  `reasonLabel`을 통과시키므로 값을 무변경으로 나르며, 이 줄 자체는 고칠 필요가 없다. 열어
  확인했다. (3) 판정 함수의 정본. 구분값 대조는 TASK-S071-01이
  `src-tauri/src/domain/agent_runtime.rs`에 두지만, 화면은 그 값을 백엔드에서 받아 오지 않고
  같은 문자열을 화면 쪽에서 대조한다. 그래서 화면 쪽 상수 하나를 이 파일에 두고 세 함수가 함께
  쓰게 한다. 문자열이 두 곳에 적히는 것은 사실이므로, 값이 갈라지면 어느 쪽이 정본인지 알 수
  있도록 상수 옆 주석에 백엔드 정본의 자리를 적는다.
- 안내가 서는 자리(C2). 지금 배정 대기 구역은 `AgentRunDashboard.tsx` 226행의 조건 때문에 대기
  후보나 단독 수행 안내가 있을 때만 나타난다. 그 안에 넣으면 대기 후보가 없는 순간 안내가 함께
  사라져 R-15를 충족하지 못한다. 그래서 124행의 화면 본문 첫 자리에 새 구역을 세운다. 스타일은
  `src/App.css` 73행의 `agent-queue-notice`가 있는 자리에 함께 둔다. 그 파일을 열어 확인했고
  선언에 넣었다.

선언에서 뺀 파일과 근거를 정리한다.

- `src/features/projects/infrastructure/tauriProjectGateway.ts`와
  `src/features/projects/application/useProjectWorkspace.ts`. 위에 적은 대로 응답을 통째로 나른다.
  349행과 339행부터를 열어 확인했고, 이번 완료 조건 가운데 두 파일을 고쳐야 풀리는 것이 없다.
- `src/features/projects/components/agents/AgentRuntimeView.tsx`. 자동 배정 켜기와 실행 환경 상태를
  그리는 자리이고 실행 목록을 그리지 않는다. 이번 안내는 실행 목록 화면의 자리이므로 이 파일을
  고치지 않는다. 지금 여러 작업이 잡고 있는 파일이기도 하다. 검사 파일 이름이
  `AgentRuntimeView.test.tsx`인 것은 이 파일이 대시보드를 품고 함께 렌더되기 때문이며, 대시보드의
  검사가 이미 그 파일에 있는 것을 확인했다.
- 백엔드 전체. 이 작업은 응답을 읽기만 한다. 응답에 값을 싣는 일과 배정을 멈추는 일은 앞선 두
  작업이 맡는다.
