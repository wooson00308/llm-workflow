# 세션의 규격 준수 비용을 다시 잴 수 있는 측정 방법을 정하고 기준값을 남긴다

## 결정권자 요약

세션이 규격을 지키는 데 쓰는 비용을 반복해서 잴 수 있는 측정 방법을 만들고 한 차례 실행했다.
기획자, 아키텍트, 개발자 각각에 대해 착수 문서와 대조 문서의 양을 나눠 재고, 계산에 쓴 문서 수와
환산 기준을 함께 낸다.
측정 시점을 인자로 받아 지정한 커밋의 상태를 읽으므로, 변경 전 기준값은 나중에도 다시 계산할 수 있다.
변경 전 기준값은 2026-08-06 시점 커밋에서 개발자 기준 약 76만 토큰이고, 나흘 전 같은 측정값의 약
20배다. 문서가 쌓일수록 비용이 늘어난다는 SPEC-049의 문제 제기가 숫자로 확인됐다.
실제 절감 폭 판단은 변경이 적용된 뒤 같은 명령으로 다시 재는 몫이며 이번 작업의 완료 조건이 아니다.
측정 도구는 통과와 실패를 가르는 검사가 아니라 관찰 도구이므로 기존 검사 명령에 넣지 않았다.
기존 검사 761개와 타입 검사, 배포 빌드가 그대로 통과했다.

## 목적

SPEC-049의 포함 범위 마지막 항목과 완료 조건 11번을 구현한다. 기획서가 인용한 세션당 3만에서 4만
토큰이라는 값은 세션 하나의 관찰에서 나온 추정이고, 기획서 스스로 재검증이 필요하다고 적었다.
같은 값을 언제든 다시 잴 수 있는 측정 방법을 만들고, 이번 변경 전의 기준값을 남긴다.

사용자 확인 결과 이번 기획은 구조를 완료 조건으로 삼고 실제 절감 폭 측정은 변경이 적용된 뒤 별도로
관찰하기로 정해졌다. 그래서 이 작업의 완료 조건은 측정 방법이 동작하고 기준값이 남는 것까지이며,
절감 폭 자체는 완료 조건이 아니다.

## 측정 대상

세션 하나가 실제 구현과 무관하게 반복해서 읽는 고정 비용을 잰다. 역할마다 읽는 문서가 다르므로
기획자, 아키텍트, 개발자 세 역할을 각각 낸다.

역할별로 다음 두 가지를 합산한다.

1. 착수 절차가 항상 읽게 하는 문서. 프로젝트 등록 문서, 공통 규칙, 배정된 역할 계약 하나, 활성
   워크플로의 워크플로 문서와 안내 문서다.
2. 대상을 찾기까지 대조해야 하는 문서. 지금은 자격 확인 도구가 대상을 알려주지 않으므로 세션이
   해당 역할의 판정에 필요한 문서군을 훑는다. 기획자는 아이디어와 기획서와 결정, 아키텍트는 결정과
   작업 문서, 개발자는 작업 문서와 선점 파일이다.

바이트 수를 토큰으로 환산하는 기준은 기획서 배경 절이 쓴 값을 그대로 쓴다. 한국어 문서 약 2바이트를
1토큰으로 센다. 이 환산은 근사값이므로 측정 결과에 환산 기준을 함께 적어, 나중에 기준이 바뀌어도
값을 다시 해석할 수 있게 한다.

## 변경 범위

- `scripts/measure-compliance-cost.mjs`: 측정을 실행하는 스크립트를 새로 만든다.
- `docs/compliance-cost-measurement.md`: 측정 방법과 이번에 얻은 기준값을 적는 문서를 새로 만든다.

## 설계 지침

- 스크립트는 측정 시점을 인자로 받는다. 인자를 주지 않으면 작업 트리의 현재 상태를 재고, 커밋
  식별자를 주면 그 시점의 파일 내용을 읽어 잰다. 이렇게 해야 이번 변경이 반영된 뒤에도 변경 전
  기준값을 다시 계산할 수 있고, 이 작업이 다른 작업의 완료 순서에 묶이지 않는다.
- 출력은 사람이 읽는 표와 기계가 읽는 형태를 함께 낸다. 나중 비교가 손으로 옮겨 적는 일이 되지
  않게 한다.
- 역할별 값과 합계, 그리고 계산에 쓴 문서 수를 함께 낸다. 비용이 문서 수에 비례해 늘어난다는 것이
  기획서의 문제 제기이므로, 문서 수가 결과에 보여야 값의 변화를 해석할 수 있다.
- 기존 검사 명령에 이 스크립트를 넣지 않는다. 측정은 관찰 도구이지 통과·실패를 가르는 검사가
  아니다. 실행 방법은 문서에 적는다.
- 저장소에 이미 있는 스크립트 두 개와 같은 방식으로 노드 스크립트로 만들고 같은 디렉터리에 둔다.

## 손대지 않는 것

- 자격 확인 도구와 앱 내부 판정
- 역할 계약과 공통 규칙의 본문
- 검사 명령 구성과 패키지 설정
- 이미 있는 문서와 개발 로그

## 완료 조건

1. 측정 스크립트가 기획자, 아키텍트, 개발자 세 역할 각각의 규격 준수 토큰 비용 추정값을 낸다.
2. 같은 스크립트가 계산에 쓴 문서 수와 환산 기준을 함께 낸다.
3. 인자 없이 실행하면 현재 상태를, 커밋 식별자를 주면 그 시점의 상태를 잰다.
4. 같은 입력으로 두 번 실행하면 같은 값이 나온다.
5. 측정 문서에 측정 대상, 환산 기준, 실행 방법, 결과 해석 방법이 적혀 있다.
6. 측정 문서에 이번 변경 전 기준값이 실행 시점의 커밋 식별자와 함께 적혀 있다.
7. 기존 자동 검사를 삭제하거나 비활성화하지 않고, 검사 명령 구성도 바꾸지 않는다.

## 검증 절차

1. 인자 없이 스크립트를 실행해 세 역할의 값과 문서 수, 환산 기준이 출력되는지 확인한다.
2. 같은 명령을 두 번 실행해 출력이 같은지 확인한다.
3. 과거 커밋 식별자를 인자로 주어 실행하고, 현재 상태의 값과 다른 값이 나오는지 확인한다. 문서가
   늘어난 만큼 값이 달라지는 것이 정상이다.
4. 없는 커밋 식별자를 주었을 때 스크립트가 알아볼 수 있는 오류로 끝나는지 확인한다.
5. 측정 문서에 적힌 실행 방법을 그대로 따라 해서 문서에 적힌 기준값이 재현되는지 확인한다.
6. `npm run check`를 실행해 기존 검사가 그대로 통과하는지 확인한다. 이 작업은 검사 대상 코드에
   손대지 않으므로 결과가 착수 전과 같아야 한다.

## 확인 동선

이 작업에는 볼 화면이 없다. 앱 화면은 바뀌지 않았고, 결과는 터미널에서 실행하는 측정 스크립트와
측정 문서로 확인한다.

1. 저장소 루트에서 인자 없이 실행한다.

   ```sh
   node scripts/measure-compliance-cost.mjs
   ```

   기획자·아키텍트·개발자 세 줄이 있는 표가 나오고, 각 줄에 착수 문서 수와 바이트, 대조 문서 수와
   바이트, 합계와 추정 토큰이 있다. 표 아래에 문서군별 문서 수와 바이트가 나오고, 머리말에 환산
   기준 `2바이트 = 1토큰`이 적혀 있다. `--- JSON ---` 줄 다음에 같은 값이 JSON으로 다시 나온다.

2. 같은 명령을 한 번 더 실행해 출력이 같은지 확인한다. 작업 트리를 그사이 바꾸지 않았다면 두 출력이
   완전히 같아야 한다.

3. 변경 전 기준값을 다시 계산한다.

   ```sh
   node scripts/measure-compliance-cost.mjs c1449d8398ebee47e3ca46663fd99bcc10b090e0
   ```

   `docs/compliance-cost-measurement.md`의 `이번 변경 전 기준값` 절에 적힌 표와 숫자가 그대로
   나와야 한다. 개발자 줄의 추정 토큰은 763847이다. 이 값은 커밋을 읽으므로 지금 작업 트리에 무엇이
   쌓여 있든 바뀌지 않는다.

4. 오래된 시점과 비교한다.

   ```sh
   node scripts/measure-compliance-cost.mjs c4ff7da
   ```

   개발자 줄의 추정 토큰이 37671로, 3번 값보다 크게 작다. 문서가 늘어난 만큼 값이 커지는 것이
   정상이다.

5. 없는 커밋 식별자를 준다.

   ```sh
   node scripts/measure-compliance-cost.mjs no-such-commit
   ```

   `커밋 식별자 no-such-commit을 확인할 수 없습니다`라는 오류로 끝나고 종료 코드가 1이다.

6. 측정 문서를 읽고 측정 대상, 환산 기준, 실행 방법, 결과 해석 방법, 기준값이 모두 적혀 있는지
   확인한다. 특히 값이 상한이라는 점과, 선점 파일이 커밋 측정에서 0으로 나오는 이유를 확인한다.

7. 자동 검사로 확인한 항목: `npm run check`가 착수 전과 같이 통과한다(검사 파일 24개, 검사 761개,
   타입 검사, 배포 빌드). 이 작업은 검사 대상 밖의 파일 두 개만 추가했으므로 검사 구성과 결과는
   바뀌지 않았다.

## 범위와 선행

선행 작업은 없다. TASK-139, TASK-140과 파일이 겹치지 않으므로 셋 중 어느 것과도 병렬로 진행할 수
있다.

측정 시점을 인자로 받게 만드는 이유가 여기에 있다. 이 작업이 TASK-140보다 늦게 끝나도 변경 전
기준값을 그 시점의 커밋에서 다시 계산할 수 있으므로, 순서를 강제하지 않아도 기준값이 오염되지
않는다.
