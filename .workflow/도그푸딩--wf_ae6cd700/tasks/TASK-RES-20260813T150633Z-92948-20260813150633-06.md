# 오늘 화면과 개발 화면의 품질 확인 입구를 전용 작업대 하나로 모은다

## 결정권자 요약

### 제안

오늘 화면의 내 선택 대기에 지금 시작할 수 있는 기능 품질 확인을 기획서 승인과 함께 보여 주고, 개발
화면의 품질 확인 조작이 모두 전용 작업대로 이어지게 한다.

### 현재

구현과 개발자 검증을 마쳐 사용자 QA를 기다린다. 오늘 화면의 내 선택 대기가 기획서 승인과 지금 확인할 수
있는 기능을 함께 보여 주고, 개발 화면의 품질 확인 조작은 모두 전용 작업대로 이어진다. 작업 상세와
기획서별 묶기에는 품질 결정을 입력하는 자리가 남아 있지 않다.

### 변경 후

앱을 열면 오늘 화면에 확인할 기능이 기획서 승인과 나란히 보이고, 누르면 개발 화면을 거치지 않고 그 기능의
품질 확인 작업대로 바로 간다. 개발 화면은 상태와 건수를 계속 보여 주되 결정 양식은 갖지 않는다.

### 사용자 결과

사용자는 앱을 연 순간 지금 결정할 것이 무엇인지 한 자리에서 본다. 같은 결정을 어느 화면에서 하느냐에 따라
다른 조작을 익힐 필요가 없어진다.

### 영향 범위

- 변경: 오늘 화면의 내 선택 대기 목록과 건수, 개발 화면의 품질 확인 조작이 향하는 곳, 작업 상세와 기획서별 일괄 화면의 결정 양식
- 유지: 개발 화면의 상태 표시와 카드와 기능 요약, 검색과 개발 상태 필터와 기획서별 묶기, 작업 상세의 읽기 기능, 작업별 품질 확인 결정 문서의 형식과 사용자 전용 결정 권한

### 비용과 위험

없앤 것은 화면 쪽 배선으로 한정했고 앱이 품질 확인을 기록하는 명령과 그 검사는 그대로 두었다. 앱 백엔드
검사 전 건이 통과해 기록 규칙이 변하지 않은 것을 확인했다. 남은 위험은 품질 확인을 시작하는 자리가
작업대 한 곳뿐이라는 점이며, 그 화면에서 막히면 확인을 이어갈 다른 입구가 없다.

### 결정 요청

QA에서는 오늘 화면에 확인할 기능이 기획서 승인과 함께 보이고 한 기능이 한 건으로 세어지는지, 눌렀을 때
개발 화면을 거치지 않고 작업대로 가는지, 개발 화면의 품질 확인 조작이 같은 작업대로 가는지, 그리고
기획서 승인과 개발 상태 표시가 이전과 같은지를 본다.

## 막힌 사유

- 막힌 지점: 완료 조건 7과 변경 범위 10이 요구하는 "개발 화면에 결정 통로를 내려주던 선언" 제거는 개발 화면 컴포넌트의 두 속성 선언을 지우는 일인데, 그 두 속성을 넘겨 개발 화면을 그리는 검사 파일이 선언된 범위 파일 밖에 하나 더 있어 타입 검사가 깨진다. 범위 안 파일만 고쳐서는 완료 조건 7과 검증 단계 6을 동시에 만족시킬 수 없다.
- 필요한 해결: 아키텍트가 `src/features/projects/components/BlockedTaskPanel.test.tsx`를 이 작업의 범위 파일 선언에 추가하고, 그 파일의 개발 화면 렌더링에서 두 속성을 지우는 일을 완료 조건이나 검증 단계가 포함하도록 작업 문서를 고쳐야 한다.
- 재개 조건: 범위 파일 선언에 위 검사 파일이 들어가고 작업 문서가 그 파일의 수정을 지시하면 개발을 다시 시작한다. 다른 선행 작업이나 외부 승인은 기다리지 않는다.
- 관련 대상: 없음

## 범위 사전 검사

이 작업이 다루는 값은 넷이다. 오늘 화면이 세는 결정 건수와 그 목록, 기능을 눌렀을 때 작업대로 넘기는 대상,
개발 화면에서 없어지는 결정 양식과 그 배선, 그리고 그 배선이 사라질 때 함께 깨지는 검사다. 현재 코드를 열어
각 값의 경로를 확인했다.

넷째 값은 2026-08-13 아키텍트 세션이 추가했다. 앞선 개발자 세션이 이 작업을 정의 오류로 막으면서, 없어질
속성을 넘겨 개발 화면을 그리는 검사 파일이 선언 밖에 하나 더 있다고 보고했기 때문이다. 이번 세션은 그
보고를 그대로 받지 않고 파일을 다시 열어 확인했고, 보고가 짚은 타입 결함 외에 실행 시점에도 깨지는 단언이
같은 파일에 하나 더 있는 것을 찾아 함께 담았다.

  백엔드 파일은 편집하지 않고 선언에도 넣지 않으며, 껍데기 화면 한 곳만 편집한다. 기능 묶음 하나가 한

## 현재 상태

오늘 화면의 내 선택 대기는 사용자 검토 상태의 기획서만 나열하고, 건수 배지도 그 수만 쓴다. 품질 확인
대기 작업은 이 목록에 나타나지 않는다.

개발 화면에는 품질 확인 입구가 셋 있다. 확인할 기능 묶음 카드에서 여는 기능 확인 화면, 기획서별 묶기에서
여는 레인 일괄 확인 양식, 그리고 작업 상세 오른쪽의 단건 결정 양식이다. 뒤의 둘은 확정 전에 같은 버튼을
시간 안에 다시 누르게 한다.

앞선 작업까지 마치면 품질 확인 작업대가 대기열과 세션과 제출을 모두 갖추지만, 그 작업대로 가는 길은 주요
메뉴 하나뿐이다.

## 변경 범위

1. 오늘 화면의 내 선택 대기가 사용자 검토 상태의 기획서와 지금 확인할 수 있는 기능 품질 확인을 함께
   보여 준다. 건수 배지는 두 종류를 합한 수를 쓴다.
2. 같은 기능에 품질 확인 대기 작업이 여러 건이어도 한 건으로 센다. 아직 확인할 수 없는 기능 묶음은 세지
   않고 목록에도 넣지 않는다.
3. 품질 확인 항목에는 기능 제목, 확인 항목 수, 그리고 품질 확인을 시작한다는 조작 문구를 둔다. 작업
   식별자 목록과 개발 상태 수치는 넣지 않는다.
4. 오늘 화면의 품질 확인 항목을 누르면 개발 화면이나 중간 상세를 거치지 않고 그 기능의 품질 확인 작업대로
   간다.
5. 품질 확인 작업대가 처음 열 기능을 밖에서 받을 수 있게 한다. 지정 없이 열면 지금처럼 대기열을 보여
   준다.
6. 기획서 승인도 품질 확인도 없을 때만 기다리는 선택이 없다고 표시한다.
7. 개발 화면의 확인할 기능 묶음 카드에서 품질 확인 조작을 누르면 같은 기능의 작업대로 이동한다. 카드가
   보여 주는 제목과 건수와 준비 중 예고는 그대로 둔다.
8. 기획서별 묶기의 레인 일괄 확인 양식을 없애고, 그 자리의 조작은 해당 기능의 작업대로 이동하게 한다.
9. 작업 상세 오른쪽의 품질 확인 결정 양식을 없애고, 그 자리에는 상태 표시와 작업대로 이동하는 조작만
   둔다. 작업 상세의 문서 읽기, 선행 작업 표시, 막힌 작업 안내와 정의 수정 요청은 그대로 둔다.
10. 위 변경으로 쓰이지 않게 된 화면 쪽 배선을 정리한다. 대상은 개발 화면에 결정 통로를 내려주던 선언과
    그 위쪽 전달 선언, 그리고 그 선언만을 위해 있던 훅 동작과 계약 선언과 명령 호출이다. 앱 백엔드의 기록
    명령과 그 검사는 지우지 않는다.
11. 검색, 개발 상태 필터, 기획서별 묶기, 보기 전환, 타임라인은 그대로 동작한다.
12. 막힌 작업 안내 검사 파일이 위 변경을 따라오도록 고친다. 이 파일은 개발 화면을 직접 그려서 막힘
    사유 표시와 정의 수정 요청 표시를 확인하는데, 두 곳이 변경에 걸린다. 첫째, 개발 화면을 그리는
    보조 함수가 없어지는 결정 통로 속성 두 개를 넘기고 있어 선언이 사라지면 타입 검사가 이 호출을
    거부한다. 둘째, QA 대기 상태를 확인하는 경우만 확인할 기능 카드의 품질 확인 조작과 개발 화면 안
    확인 단계 목록을 거쳐 작업 상세로 들어간 뒤 결정 입력 자리가 있다고 단언하는데, 그 경로와 그
    입력 자리가 이 작업에서 없어진다. 이 파일이 원래 확인하던 막힘 사유와 정의 수정 요청 관련 단언은
    그대로 두고, 위 두 곳만 고친다.

## 범위 밖

- 품질 확인 작업대 안의 대기열 구성과 항목 확인과 제출 동작의 변경
- 앱 백엔드와 명령 계층의 변경
- 기능 묶음 판정 기준의 변경
- 기획서 승인 화면과 그 결정 흐름의 변경
- 막힌 작업 복구와 작업 정의 수정 요청 흐름의 변경
- 개발 화면의 상태 표시와 카드 구성 자체의 재설계

## 완료 조건

1. 사용자 검토 상태의 기획서와 지금 확인할 수 있는 기능이 함께 있는 프로젝트에서 오늘 화면의 내 선택
   대기가 둘을 모두 보여 주고, 건수 배지가 두 종류를 합한 수를 말한다.
2. 같은 기능의 품질 확인 대기 작업이 여러 건이어도 목록에 한 항목으로 나오고 건수에도 한 건으로 세어진다.
   아직 확인할 수 없는 기능은 목록에도 건수에도 들어가지 않는다.
3. 오늘 화면의 품질 확인 항목을 선택하면 개발 화면을 거치지 않고 그 기능의 품질 확인 작업대가 열린다.
4. 개발 화면의 확인할 기능 카드에서 품질 확인을 열면 같은 기능의 작업대가 열린다.
5. 품질 확인 작업대에 처음 열 기능을 지정하지 않고 들어가면 대기열이 보인다.
6. 기획서별 묶기와 작업 상세에 품질 결정을 입력하는 양식이 남아 있지 않고, 두 자리 모두 작업대로 가는
   이동만 제공한다.
7. 그 양식만을 위해 있던 화면 쪽 배선이 남아 있지 않다. 앱 백엔드의 기록 명령과 그 검사는 그대로 있다.
8. 기획서 승인 흐름, 개발 작업 상태 표시, 작업별 품질 확인 결정 문서의 형식, 사용자만 품질 결정을 남기는
   권한이 변경 전과 같다.
9. 기획서 승인도 품질 확인도 없으면 기다리는 선택이 없다고 표시한다.
10. 검색, 개발 상태 필터, 기획서별 묶기, 보기 전환, 타임라인, 작업 상세의 읽기 기능이 변경 전과 같이
    동작한다.
11. 막힌 작업 안내 검사가 통과한다. 그 검사가 개발 화면을 그릴 때 없어진 결정 통로 속성 두 개를 넘기지
    않고, QA 대기 상태를 확인하는 경우는 변경 후에도 남아 있는 이동 경로로 작업 상세에 도달한다. 목록
    보기와 기획서별 묶기는 QA 대기 작업의 카드를 그대로 보여 주므로 둘 중 하나를 쓰면 된다. 그 검사가
    원래 확인하던 막힘 사유 표시와 정의 수정 요청 표시에 대한 단언은 변경 전과 같은 내용으로 남아
    있다.

## 검증 단계

1. 껍데기 화면 검사에 오늘 화면 검사를 추가하고 실행한다. 완료 조건 1·2·3·9를 각각 확인한다. 확인할 수
   있는 기능과 아직 확인할 수 없는 기능과 사용자 검토 기획서가 섞인 워크플로 요약을 넣어 목록과 배지 수를
   단언하고, 항목을 눌렀을 때 열리는 화면을 단언한다.
   명령: `npx vitest run src/features/projects/components/WorkspaceShell.test.tsx`
2. 개발 화면 검사를 고쳐 실행한다. 완료 조건 4·6·10을 확인한다. 기획서별 묶기와 작업 상세에 결정 입력
   자리가 없음을 단언하고, 검색과 필터와 보기 전환이 이전과 같이 동작함을 단언한다.
   명령: `npx vitest run src/features/projects/components/DevelopmentBoard.test.tsx`
3. 작업대 검사에 처음 열 기능 지정 검사를 추가하고 실행한다. 완료 조건 5를 확인한다.
   명령: `npx vitest run src/features/projects/components/qa/QaWorkbench.test.tsx`
4. 훅 검사를 실행해 남은 동작과 지운 동작이 의도대로인지 확인한다. 완료 조건 7의 화면 쪽 배선 정리를
   확인한다.
   명령: `npx vitest run src/features/projects/application/useProjectWorkspace.test.ts`
5. 앱 백엔드 검사를 실행해 기록 명령과 결정 문서 형식이 그대로인지 확인한다. 완료 조건 7의 뒷부분과 완료
   조건 8을 확인한다.
   명령: `cd src-tauri && cargo test`
6. 타입 검사와 저장소 전체 검사를 실행한다. 쓰이지 않는 선언이 남아 있으면 타입 검사가 알린다.
   명령: `npm run typecheck` 다음 `npm test`
7. 막힌 작업 안내 검사를 고쳐 실행한다. 완료 조건 11을 확인한다. 개발 화면을 그리는 보조 함수에서 결정
   통로 속성 두 개를 지우고, QA 대기 상태를 확인하는 경우가 변경 후에도 남아 있는 이동 경로로 작업
   상세에 도달하게 고친 뒤, 막힘 사유 표시와 정의 수정 요청 표시 단언이 그대로 통과하는지 본다. 이
   검사는 앞 단계의 타입 검사보다 먼저 고쳐 두는 편이 낫다. 고치지 않으면 앞 단계의 타입 검사가 이
   파일에서 먼저 실패한다.
   명령: `npx vitest run src/features/projects/components/BlockedTaskPanel.test.tsx`
8. 선언한 범위 파일을 모두 고친 뒤에도 범위 밖 파일에서 타입 오류나 검사 실패가 남으면, 그 파일을 임의로
   고치지 말고 막힘으로 되돌려 아키텍트에게 넘긴다. 범위 판단이 또 짧았다는 뜻이기 때문이다.

## 확인 동선

준비물: 사용자 검토 상태의 기획서 하나, 같은 기획서에서 나온 품질 확인 대기 작업이 둘 이상이고 그 기획서의
다른 작업이 모두 끝난 기능 하나, 그리고 아직 진행 중인 작업이 남아 있어 지금은 확인할 수 없는 기능 하나.

1. 앱을 열면 오늘 화면이 나온다. 내 선택 대기 구획을 본다. 기획서 승인 항목과 품질 확인 항목이 같은
   목록에 함께 있고, 오른쪽 위 건수 배지가 두 종류를 합한 수를 말하면 정상이다. 같은 기능의 대기 작업이
   여러 건이어도 목록에는 한 줄로만 나와야 한다.
2. 같은 구획에서 아직 확인할 수 없는 기능이 보이지 않는지 확인한다. 그 기능이 목록에 있거나 건수에
   포함되어 있으면 잘못된 것이다. 품질 확인 줄에 작업 식별자나 개발 상태 수치가 적혀 있어도 잘못된 것이다.
3. 품질 확인 줄을 누른다. 개발 화면이나 중간 상세를 거치지 않고 그 기능의 품질 확인 작업대가 바로 열리고,
   화면 위 이동 경로 끝이 품질 확인이면 정상이다. 제목이 그 기능의 이름이어야 한다.
4. 왼쪽 주요 메뉴에서 품질 확인을 누른다. 특정 기능이 아니라 대기열이 보이면 정상이다.
5. 왼쪽 주요 메뉴에서 개발을 누른다. 확인할 기능 구획의 카드에서 `QA 시작`을 누르면 같은 기능의 작업대가
   열려야 한다. 이 화면 안에서 확인 단계 목록이 열리면 잘못된 것이다.
6. 개발 화면으로 돌아와 `기획서별 묶기`를 켠다. QA 대기만 남은 레인의 헤더에 `이 그룹 N건 품질 확인 열기`가
   있다. 눌렀을 때 대상 선택 목록이나 확인 메모 입력이 뜨는 대화상자가 나오면 잘못된 것이고, 그 기능의
   작업대로 이동하면 정상이다.
7. 개발 화면에서 보기를 리스트로 바꾸고 QA 대기 작업 한 건을 연다. 오른쪽 패널에 상태 표시와
   `품질 확인 작업대 열기`만 있어야 한다. `테스트 플로우와 확인 메모` 입력창이나 `확인 완료`,
   `개발 준비로 되돌리기` 버튼이 남아 있으면 잘못된 것이다. 문서 본문 읽기와 확인 동선 표시는 그대로다.
8. 오늘 화면으로 돌아가 기획서 승인 줄을 누른다. 기획서 검토 화면이 이전과 같이 열리고 승인·수정 요청
   조작이 그대로면 정상이다.
9. 개발 화면에서 검색, 개발 상태 필터, 기획서별 묶기, 보기 전환, 타임라인이 이전과 같이 동작하는지 훑는다.
10. 사용자 검토 기획서도 확인할 수 있는 기능도 없는 워크플로를 고른다. 오늘 화면 내 선택 대기에
    `기다리는 선택이 없습니다`가 보이고 배지가 0이면 정상이다.
11. 품질 확인 작업대에서 기능 하나를 끝까지 확인해 제출한다. 완료와 재작업 요청이 이전과 같은 형식으로
    기록되고 개발 화면의 작업 상태가 그에 맞게 바뀌면 정상이다.
