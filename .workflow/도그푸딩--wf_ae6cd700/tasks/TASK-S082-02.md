# 아이디어 카드에 재반영중 표기를 더하고 중단 의심 안내를 고친다

## 결정권자 요약

### 제안

아이디어 목록 줄과 오른쪽 문서 카드가 재반영중을 새 상태로 보여주게 하고, 중단 의심 안내 문장을
사실에 맞게 고친다.

### 바뀌는 것

- 지금: 재작성 중인 아이디어가 첫 기획과 똑같이 반영중으로 보인다 → 앞으로: 재반영중이라는 별도 표기로 보인다
- 지금: 중단 의심 안내가 사용자에게 직접 확인하라고 말한다 → 앞으로: 남은 기획서 번호와 다음 기획자 세션이 이어받는다는 사실을 적는다

### 비용과 위험

- 아이디어 목록에 다섯 번째 색이 늘어나므로, 줄 오른쪽 배지가 지금보다 한 종류 더 많아진다.
- 표시 문구와 색만 바꾸므로 되돌리기 쉽고, 판정 쪽이 아직 새 값을 내려보내지 않아도 화면은 지금과 같이 그려진다.

## 현재 코드 상태

아이디어 화면은 `src/features/projects/components/IdeaInbox.tsx` 하나다. 16행의 `IdeaState`가 화면이
아는 상태를 `inbox`·`drafting`·`closed`·`adopted` 넷으로 못 박고, 19행의 `ideaState`가 백엔드가
실어 보낸 `status` 문자열을 그 넷 중 하나로 바꾼다. 아는 값이 아니면 `inbox`로 떨어뜨린다. 화면은
판정을 다시 하지 않는다는 것이 18행 주석에 적혀 있다(SPEC-012 R6).

그 넷에 붙는 표시가 세 표에 나뉘어 있다. 25행의 `stateLabels`가 사용자 문구를, 32행의 `stateIcons`가
아이콘 이름을, 39행의 `statePillClasses`가 미리보기 배지의 클래스를 정한다. 목록 줄은 162행에서
`idea-list-icon` 뒤에 상태 값을 그대로 붙이고, 174행에서 `idea-state-tag` 뒤에도 같은 값을 붙인다.
그래서 상태 값이 하나 늘면 스타일 클래스 이름도 그 값으로 함께 늘어난다.

중단 의심은 상태 축과 별개의 표시다. 46행의 `isStalled`가 `stalledSpecIds`가 비어 있지 않은지만
보고, 176행이 목록 줄에 배지를, 212행부터 220행이 미리보기에 안내를 그린다. 안내 문장은 216행과
217행이며, 지금 "자동 처리로 다시 잡히지 않으므로 직접 확인해야 합니다."로 끝난다. 221행부터
224행의 주석은 종결 안내가 중단 의심 안내와 같은 자리를 나눠 쓰는 이유를 적으면서 그 근거로
"`stalledSpecIds`는 반영중에서만 채워지므로"라고 적는다.

색은 `src/App.css`에 있다. 411행이 `.status-drafting`을, 428행이 `.idea-list-icon.drafting`을,
435행이 `.idea-state-tag.drafting`을 파랑(#3f6184 / #deeaf5)으로 잡는다. 429행과 436행이 채택을
초록으로, 430행과 437행이 종결을, 438행이 중단 의심을 붉은 갈색으로 잡고, 427행의 기본값이
수집됨의 갈색이다. 447행의 `.idea-stall-note`가 중단 의심과 종결 안내가 함께 쓰는 상자다.

화면 계약은 `src/features/projects/domain/types.ts`에 있다. 43행부터 46행의 주석이 아이디어 상태를
네 값으로 적고, 61행부터 63행의 주석이 중단 의심 근거를 "아이디어가 반영중인데"로 적는다. 두 필드
모두 타입은 `string`과 `string[]`이라 값이 늘어도 계약이 깨지지 않는다.

시험은 `IdeaInbox.test.tsx`에 있다. 101행이 미리보기 배지를 `/^(수집됨|반영중|채택)$/`로 집으므로
새 문구가 이 정규식에 들어가지 않으면 그 시험은 새 상태를 보지 못한다. 145행이 지울 문장
`/직접 확인해야 합니다/`를 단언하므로 문구를 고치면 이 줄이 함께 바뀌어야 한다. 254행의 시험은
알 수 없는 값으로 `retired`를 쓰므로 이 작업과 충돌하지 않는다.

## 변경 범위

- `IdeaInbox.tsx` 16행의 `IdeaState`에 `redrafting`을 더하고, 19행의 `ideaState`가 그 값을 그대로
  통과시킨다. 아는 값이 아니면 `inbox`로 떨어뜨리는 지금 동작은 그대로 둔다.
- 25행·32행·39행의 세 표에 `redrafting` 항목을 더한다. 문구는 재반영중, 아이콘은 반영중과 같은
  `refresh`, 미리보기 배지 클래스는 새로 만드는 `status-redrafting`이다.
- 212행부터 220행의 중단 의심 안내 문장을 완료 조건 C5가 요구하는 내용으로 바꾼다. 214행의 제목
  "중단 의심"은 그대로 둔다.
- 221행부터 224행 주석의 "반영중에서만 채워지므로"를 사실에 맞게 고친다. 종결과 중단 의심이 함께
  뜨지 않는다는 결론 자체는 그대로다.
- `src/App.css`에 `.status-redrafting`, `.idea-list-icon.redrafting`, `.idea-state-tag.redrafting`
  세 규칙을 더한다. 색은 글자 #54508f, 바탕 #e6e4f3이다. 기존 네 상태의 색은 건드리지 않는다.
- `types.ts` 43행과 61행의 주석을 다섯 값과 넓어진 선점에 맞춘다.
- `IdeaInbox.test.tsx`에 아래 검증 절차가 요구하는 시험을 더하고, 101행의 정규식과 145행의 문구
  단언을 새 문구에 맞게 고친다.

## 범위 밖

- 아이디어 상태를 계산하는 백엔드 판정. `src-tauri` 아래 파일은 같은 기능의 TASK-S082-01이 맡는다.
  이 작업은 `status`에 `redrafting`이 실려 오면 그것을 사용자 문구로 그리는 데까지만 한다.
- 중단 의심이라는 표기 이름. 목록 배지와 미리보기 안내 제목 모두 지금 이름을 그대로 쓴다.
  (기획서 R8)
- 종결 안내 문장과 그 색. 이 작업이 고치는 것은 중단 의심 안내 문장 하나다.
- 기획서 화면, 개발 보드, 품질 확인 화면의 구성 중단 의심 표기. 다른 축의 값이고 이 파일들과
  무관하다.
- 아이디어 카드에서 재작성 중인 기획서를 바로 열거나 세션을 조작하는 입구. 기획서가 제외 범위로
  못 박았다.
- 아이디어 목록 줄의 배치와 미리보기 레이아웃. 배지가 하나 더 생길 수 있는 자리는 172행의
  `idea-list-tags`이며 이미 두 배지를 나란히 놓는 가로 배치라 구조를 바꿀 필요가 없다.

## 완료 조건

- C1. 화면이 `status` 값 `redrafting`을 아는 상태로 받아들이고, 목록 줄과 미리보기 배지 모두에
  재반영중이라는 문구로 그린다. (기획서 R1, R13, 완료 판정 A1)
- C2. 같은 아이디어를 목록 줄에서 볼 때와 미리보기에서 볼 때 상태 문구가 같다. 한쪽만 다른 상태를
  보이지 않는다. (기획서 R12, 완료 판정 A7)
- C3. 재반영중 배지의 아이콘은 반영중과 같은 회전 화살표이고, 색은 글자 #54508f, 바탕 #e6e4f3이다.
  배지 모양은 다른 상태와 같은 알약 모양을 그대로 쓴다. (기획서 R13)
- C4. `stalledSpecIds`가 채워진 재반영중 아이디어는 목록 줄에 재반영중과 중단 의심 두 배지를 함께
  보이고, 미리보기에는 재반영중 배지와 중단 의심 안내를 함께 보인다. (완료 판정 A3)
- C5. 중단 의심 안내에 남아 있는 기획서 문서 식별자가 그대로 나오고, 다음 기획자 세션이 그 문서를
  이어받는다는 문장이 함께 있다. 사용자가 직접 확인해야 한다는 문장은 없다. 안내 제목은 중단
  의심 그대로다. (기획서 R7, R8, 완료 판정 A6)
- C6. 수집됨·반영중·채택·종결 네 상태의 문구·아이콘·색과 종결 안내 문장이 이 작업 전후로 같다.
  알 수 없는 값을 수집됨으로 읽는 동작도 그대로다. (완료 판정 A4, A10)
- C7. `status`에 `redrafting`이 한 번도 실려 오지 않아도 화면이 지금과 똑같이 그려진다. 이 작업만
  먼저 반영된 상태에서 사용자가 보는 화면에 달라지는 것은 중단 의심 안내 문장뿐이다.
- C8. 이 작업의 변경은 선언한 네 파일 안에서 끝난다. 백엔드 코드, 다른 화면, 다른 스타일 파일이
  수정되지 않는다.
- C9. `npm run check`가 통과한다.

## 검증 절차

1. `IdeaInbox.test.tsx`에 재반영중 픽스처를 더한다. `status: "redrafting"`이고 `stalledSpecIds`가
   빈 목록인 것 하나, `stalledSpecIds`에 기획서 식별자가 들어 있는 것 하나다.
2. C1과 C2의 시험을 더한다. 목록 줄에서 재반영중 배지를 집고, 같은 아이디어를 눌러 미리보기
   배지에서도 같은 문구가 나오는지 본다. 101행의 정규식에 재반영중을 더해 기존 배지 시험이 네
   상태를 모두 집게 한다.
3. C3의 시험을 더한다. 목록 줄의 아이콘 요소와 배지 요소가 `redrafting` 클래스를 달고 있는지,
   미리보기 배지가 `status-redrafting` 클래스를 달고 있는지 본다. 색 자체는 시험이 아니라 6번의
   눈 검수로 확인한다.
4. C4의 시험을 더한다. 1번의 두 번째 픽스처로 목록 줄에 배지가 둘 함께 나오는지, 미리보기에
   재반영중 배지와 중단 의심 안내가 함께 나오는지 본다.
5. C5의 시험을 고치고 더한다. 145행의 `/직접 확인해야 합니다/` 단언을 지우고, 그 문장이 화면
   어디에도 없다는 단언으로 바꾼다. 남은 기획서 식별자가 나온다는 기존 단언은 그대로 두고, 다음
   기획자 세션이 이어받는다는 문장을 집는 단언을 더한다.
6. C3과 C6을 눈으로 확인한다. `npm run dev`로 앱을 띄우고 아이디어 화면을 열어, 다섯 상태의
   배지가 나란히 있을 때 재반영중이 반영중과 구분되는지, 네 기존 상태의 색이 그대로인지 본다.
   확인한 화면을 캡처해 보고서에 적는다. 이 저장소의 화면은 웹킷에서 검수한다.
7. C6의 회귀를 시험으로 확인한다. 67행·90행·203행·237행·254행의 기존 시험을 하나도 고치지 않은
   채 통과시킨다. 기대값을 고쳐야 하는 시험이 나오면 기존 상태의 표시를 건드린 것이므로, 고치지
   말고 구현을 되돌아본다.
8. C7을 확인한다. `redrafting`이 없는 기존 픽스처만 쓰는 시험이 전부 통과하는지 본다.
9. `npm run check`를 통과시킨다(C9).
10. `git status`와 변경 파일 목록으로 선언한 네 파일 밖의 수정이 없음을 확인한다(C8).

## 범위 사전 검사

선언한 파일은 넷이다. 아이디어 화면 하나와 그 시험, 화면이 읽는 payload 계약, 그리고 상태 색이
사는 공용 스타일이다. 완료 조건이 요구하는 편집이 이 넷 밖으로 나가지 않는다는 것을 아래 값
경로에서 하나씩 확인했다.

`src-tauri` 아래 파일은 열어 보고 뺐다. `redrafting`이라는 값을 실제로 만들어 내려보내는 자리는
`src-tauri/src/infrastructure/fs_project_repository.rs` 4015행의 `derive_idea_states`이고, 그 편집은
TASK-S082-01의 완료 조건이다. 이 작업의 완료 조건은 값이 실려 왔을 때 화면이 무엇을 그리는가
하나뿐이고, 시험은 픽스처로 그 값을 직접 넣으므로 백엔드 편집 없이 닫힌다. `status`가 `string`
이라 계약을 넓히는 편집도 필요 없다.

`src/features/projects/components/WorkspaceShell.tsx`를 열어 보고 뺐다. 305행이
`workflow.items.ideas`를 훑지만 문서가 바뀐 시각만 보고 `status`를 읽지 않으므로, 값이 하나 늘어도
이 파일의 동작이 달라지지 않는다.

`src/features/projects/components/agents/AgentRunDashboard.tsx`도 열어 보고 뺐다. 586행이 같은
목록을 훑지만 식별자와 제목만 쓴다.

`src/features/projects/components/statusPillWrap.test.ts`를 확인하고 뺐다. 18행이 아이디어 상태
배지의 줄바꿈을 다루지만, 세 상태 문구를 시험 데이터의 제목 문자열 안에서 인용할 뿐 상태 표를
읽지 않는다. 배지 모양을 바꾸지 않으므로 이 시험의 기대값도 바뀌지 않는다.

`src/features/projects/components/BlockedTaskPanel.css`와 `qa/QaWorkbench.css`도 확인하고 뺐다.
아이디어 상태 클래스를 정의하지 않는다.

지금 이 워크플로에서 선언한 네 파일을 잡고 있는 진행 중 작업은 없다. 같은 기능의 TASK-S082-01은
`src-tauri` 아래 두 파일만 선언하므로 겹치는 파일이 하나도 없고, 그래서 두 작업 사이에 순서를 두지
않았다. 기계 상태를 조건으로 삼는 측정이 없으므로 이 작업은 조용한 기계를 요구하지 않는다.

- 값 경로: C1과 C2의 재반영중 문구. 값을 만드는 자리는 백엔드 판정이고 선언 밖이며,
  TASK-S082-01이 맡는다. 화면으로 들어오는 자리는 `src/features/projects/domain/types.ts` 46행의

  바꾸는 자리는 `IdeaInbox.tsx` 16행의 `IdeaState`와 19행의 `ideaState`이며 둘 다 편집 대상이다.
