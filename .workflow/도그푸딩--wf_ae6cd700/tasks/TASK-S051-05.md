# 런타임을 독립 실행형으로 배포하고 세 운영체제에서 복구한다

## 결정권자 요약

사용자는 Python이나 소스 저장소를 준비하지 않고도 앱이 제공하는 런타임을 설치할 수 있다.
각 운영체제용 배포물은 버전과 무결성을 확인할 수 있고 비정상 종료 뒤 서비스가 다시 시작한다.
기존 설정과 실행 기록은 유지되며 옮길 수 없는 값은 쓰기 전에 목록으로 보인다.
사용자가 요구한 조회는 기존 조회 명령을 넓혀 구현했고 두 번째 조회 명령은 만들지 않았다.
한 번 호출로 설치 버전, 실행 중 버전, 서비스 등록·실행 상태, 복구 가능 여부와 판단 근거를 받는다.
등록 없음, 실행 파일 없음, 등록물 중복, 권한 부족, 지원하지 않는 플랫폼과 버전이 서로 다른 결과다.
확인하지 못한 값과 권한 때문에 확인할 수 없는 값은 실행 중으로 올라가지 않는다.
세 운영체제 서비스 어댑터가 같은 필드를 같은 뜻으로 채우고, 조회는 아무것도 바꾸지 않는다.
전용 자동 검사 16건을 더했고 알려진 기존 실패 한 건을 제외한 전체 회귀 검사를 통과했다.
사용자는 아래 확인 동선을 검토한 뒤 QA를 확정할 수 있다.

## 목적

Python 3.11 이상과 editable checkout을 사용자가 관리해야 하는 현재 배포 경계를 없앤다. Heartbeat를
macOS, Linux, Windows용 독립 실행형 companion으로 빌드하고, 앱이 설치·업데이트할 수 있는 버전화된
배포물과 서비스 계약을 만든다.

## 품질 확인 재작업

사용자 품질 확인 기록 QA-7C6AA0E3이 이 작업을 되돌렸다. 요구는 하나다. 설치 버전, 실행 중 버전,
서비스 등록 상태, 복구 가능 여부를 한 번에 돌려주는 기계 판독용 JSON 조회 명령을 추가하는 것이며,
목적은 TASK-S051-06의 차단 사유를 푸는 것이다. 재작업은 이 요구와 아래 경계만 다루고 이미 확인받은
패키징·전환·마이그레이션 결과를 다시 설계하지 않는다.

### 기존 명령을 확장한다

- 현재 `runtime inspect`는 호출된 실행 파일 자신의 버전, API 주 버전, target, 실행 경로만 돌려준다.
  요구된 사실을 담도록 이 명령의 응답을 넓힌다.
- 새 이름의 두 번째 조회 명령을 만들지 않는다. TASK-147이 기기 상태와 업데이트 계약의 정본이며 같은
  명령을 확장해 계획과 적용 단계를 얹는다. 여기서 다른 모양을 만들면 TASK-147이 그것을 대체해야 하고
  앱은 두 응답 중 무엇을 읽을지 정할 수 없게 된다.
- 명령의 자리는 이미 이 작업의 범위 안에 있다. `cli.py`의 `runtime` 명령군과 서비스 어댑터, 그리고
  설치 자산을 읽는 `legacy_migration.py`가 모두 범위 파일이다. `agent_cli.py`와 `agent_contract.py`는
  범위 밖이므로 수정하지 않는다. API 주 버전 같은 상수가 필요하면 그 모듈을 고치지 않고 가져다 쓴다.

### 응답에 담는 사실

TASK-147이 확장할 기반이므로 필드의 뜻을 그 작업의 계약과 같게 맞춘다.

- 설치된 런타임 버전, 실제 실행 중인 버전, API 주 버전, target.
- 서비스의 등록 여부, 실행 여부, 운영체제가 아는 등록 식별자, 실제 실행 경로, 마지막 확인 시각,
  복구 가능 여부, 그 판정이 무엇을 보고 내려졌는지.
- 확인한 값, 확인하지 못한 값, 권한 때문에 확인할 수 없는 값을 구분한다. 오래된 PID나 마지막 시작
  기록만으로 실행 중이라고 답하지 않는다.
- 등록 없음, 실행 파일 없음, 등록물이 여러 개라 모호함, 권한 부족, 지원하지 않는 플랫폼이나 버전을
  서로 다른 결과로 구분한다.
- 조회는 읽기 전용이다. 호출 전후로 런타임 파일, launcher, 서비스 정의, 데이터베이스와 프로젝트 설정이
  바뀌지 않는다.

### 서비스 어댑터의 구조화 조회

위 서비스 사실은 `서비스 계약` 절이 이미 요구한 구조화된 조회에서 나온다. 현재 어댑터는 등록물을
문자열 하나로 돌려주는 탐지만 제공하므로, 세 어댑터가 같은 필드와 같은 뜻으로 조회 결과를 반환하도록
완성한다. 플랫폼 고유 이름과 명령 출력은 선택적인 진단 세부 정보에만 둔다.

## 패키징 결정

- PyInstaller의 one-folder 형식으로 target별 배포물을 만든다. one-file의 매 실행 압축 해제와 임시
  경로 수명 문제를 피하고, 서비스가 고정된 실제 실행 경로를 사용하게 하기 위해서다.
- 배포물에는 Python 런타임과 `portalocker`, `psutil`, Heartbeat 패키지를 포함한다. Claude Agent SDK와
  Codex SDK는 포함하지 않는다.
- 배포물은 target, runtime version, API major, 파일별 SHA-256을 담은 manifest와 함께 압축한다.
  앱 서명과 배포 서명은 앱 릴리스 절차가 검증할 수 있는 형태로 노출한다.
- 버전 디렉터리와 별도의 stable launcher 경로를 둔다. 업데이트는 새 버전을 완전히 설치·검증한 뒤
  launcher를 원자적으로 전환한다. 실행 중인 프로세스를 가리키는 파일을 제자리에서 덮어쓰지 않는다.

## 서비스 계약

- macOS LaunchAgent는 KeepAlive와 RunAtLoad를 사용하고 stable launcher의 `start`를 실행한다.
- Linux systemd user service는 Restart 정책과 재시작 간격을 사용한다. 로그아웃 뒤 실행을 보장하려면
  linger가 필요하다는 플랫폼 경계를 설치 결과에 명시한다.
- Windows Task Scheduler는 로그인 시 시작뿐 아니라 비정상 종료 뒤 재시작하도록 XML 설정의
  RestartOnFailure와 중복 인스턴스 금지 정책을 사용한다.
- 세 어댑터 모두 install, inspect, start, stop, restart, uninstall을 구조화된 결과로 제공한다.
  등록물의 실제 이름과 실행 경로를 응답에 포함한다.
- 재시작 전에 dispatcher의 영속 상태가 먼저 복구된다. 서비스 재시작이 새 작업 중복 실행으로
  이어지면 안 된다.

## 기존 설치 마이그레이션

1. 기존 wheel·editable 설치와 jobs.d, `state.json`, 서비스 등록물을 읽기 전용으로 탐지한다.
2. 기존 역할 잡의 interval, timeout, max_per, model과 실행 이력에서 옮길 수 있는 값을 미리보기로
   반환한다. Dream 잡은 새 에이전트 설정으로 옮기지 않는다.
3. 자동 이전할 수 없는 필드, 알 수 없는 provider, 등록물 중복은 목록으로 반환하고 사용자 확인 전에는
   쓰지 않는다.
4. 새 런타임 설치가 끝나기 전에는 기존 서비스와 실행 파일을 바꾸지 않는다.
5. 전환 뒤에도 기존 `heartbeat` CLI와 일반 jobs.d 잡은 계속 동작한다. 되돌리기 정보가 남아야 한다.

## 손대지 않는 것

- 앱의 설치 화면과 Tauri 명령
- 프로젝트별 설정을 새 런타임 계약으로 보내는 앱 로직
- provider 인증과 모델 선택 UX
- Dream 제거 또는 마이그레이션
- 원격 배포와 자동 무확인 업데이트

## 완료 조건

1. macOS universal, Linux x86_64, Windows x86_64 독립 실행형 배포물이 CI에서 만들어진다.
2. Python이 설치되지 않은 깨끗한 환경에서 각 배포물의 계약 조회와 빈 상태 조회가 성공한다.
3. 배포물 manifest의 target, runtime version, API major, 모든 파일 해시가 실제 내용과 일치한다.
4. stable launcher 전환이 원자적이고 실패한 설치가 현재 실행 가능한 버전을 훼손하지 않는다.
5. macOS·Linux·Windows에서 사용자 서비스가 앱 프로세스와 독립적으로 실행된다.
6. 런타임 프로세스를 강제 종료하면 세 플랫폼의 서비스 정책이 다시 시작하며 같은 작업을 중복
   실행하지 않는다.
7. 운영체제 재시작이나 재로그인 뒤 저장된 반복 정책과 큐가 복원된다. 로그아웃 중 실행을 보장하지
   못하는 플랫폼은 설치 결과에 그 경계를 명시한다.
8. Windows 서비스는 로그인 시 한 번만 시작하는 현재 설정을 넘어 비정상 종료 재시작을 지원한다.
9. 기존 역할 잡과 실행 이력의 마이그레이션 미리보기가 원본 값과 일치하고 Dream 값은 포함하지 않는다.
10. 옮길 수 없는 값이 있으면 사용자 확인 전 기존 설정·서비스·실행 파일을 쓰지 않는다.
11. 기존 일반 Heartbeat 명령, jobs.d 잡, Dream 동작이 변경 전과 같다.
12. Claude Agent SDK와 Codex SDK가 배포물에 포함되지 않는다.
13. 기존 자동 검사를 삭제하거나 약화하지 않는다.
14. 조회 명령 하나가 설치 버전, 실행 중 버전, API 주 버전, target, 서비스 등록·실행 상태, 등록 식별자,
    실행 경로, 마지막 확인 시각, 복구 가능 여부와 확인 근거를 한 JSON 응답으로 돌려준다.
15. 등록 없음, 실행 파일 없음, 등록물 중복, 권한 부족, 지원하지 않는 플랫폼·버전이 서로 다른 결과로
    구분되고, 확인하지 못한 값과 권한 때문에 확인할 수 없는 값이 실행 중으로 승격되지 않는다.
16. 조회 전후로 런타임 파일, launcher, 서비스 정의, 데이터베이스와 프로젝트 설정의 해시가 같다.
17. 같은 사실을 돌려주는 조회 명령은 하나뿐이다. 기존 명령을 확장했고 이름이 다른 두 번째 조회 명령을
    만들지 않았다.
18. 세 운영체제 서비스 어댑터가 같은 필드와 같은 뜻으로 구조화된 조회 결과를 반환한다. 플랫폼 고유
    이름과 명령 출력은 선택적 진단 세부 정보에만 있다.
19. `agent_cli.py`와 `agent_contract.py`를 수정하지 않고도 위 조건이 성립한다.

## 검증 절차

1. 세 운영체제 CI에서 독립 실행형 배포물을 빌드하고 압축 해제한 격리 환경에서 계약·버전·상태 명령을
   실행한다.
2. 시스템 Python과 저장소 checkout을 PATH에서 제거한 상태로 같은 smoke test를 반복한다.
3. manifest 파일 하나를 변조해 설치 검증이 실패하고 stable launcher가 바뀌지 않는지 확인한다.
4. 각 서비스 어댑터로 임시 등록물을 설치·시작·강제 종료·자동 재시작·중지·해제하는 통합 검사를
   실행한다.
5. 실행 중인 가짜 provider와 반복 큐를 둔 채 런타임을 강제 종료하고 서비스 재기동 뒤 중복 실행이
   없는지 확인한다.
6. 기존 editable·wheel 설치와 역할 잡·Dream 잡·실행 이력 픽스처로 미리보기, 확인 전 무쓰기,
   전환, 되돌리기를 검사한다.
7. 설치 없음, 정상 실행, 오래된 PID, 등록물 중복, 실행 파일 없음, 권한 부족 픽스처로 조회 응답을
   대조하고 각 경우가 서로 다른 결과가 되는지 확인한다.
8. 조회 전후에 설치 루트, launcher, 서비스 정의 픽스처, 데이터베이스와 설정의 해시가 같은지 확인한다.
9. 조회 명령의 응답 필드를 TASK-147 문서의 기기 조회 항목과 나란히 놓고 이름과 뜻이 어긋나지 않는지
   대조한다.
10. `pytest tests/ -v`를 macOS·Linux·Windows에서 실행한다.

## 범위와 선행

TASK-S051-04까지의 런타임과 복구 상태가 완성된 뒤 패키징한다. 배포물 안에 들어갈 코드가 바뀌는 동안
패키징 경계를 먼저 고정하면 다시 설계해야 하므로 순서를 둔다. TASK-S051-04는 현재 품질 확인 대기
상태이므로 이 선행 조건은 충족돼 있다.

이 재작업은 범위 파일을 늘리지 않는다. 요구된 조회 명령이 쓰는 세 가지 재료가 모두 이미 범위 안에
있기 때문이다. 명령 자리는 `cli.py`의 `runtime` 명령군, 서비스 사실은 세 서비스 어댑터, 설치 자산의
버전과 무결성은 `legacy_migration.py`에서 온다.

TASK-147은 이 작업의 조회를 기반으로 기기 상태·업데이트 계약을 완성하며 `agent_cli.py`,
`agent_contract.py`와 새 관리 모듈을 자기 범위로 가진다. 두 작업은 `cli.py`, 서비스 어댑터와
`legacy_migration.py`가 겹치지만 TASK-147이 이 작업을 선행으로 선언하고 있어 순서가 정해져 있다.

## 확인 동선

이번 재작업의 확인 대상은 조회 명령 하나다. 화면은 없고 자동 검사와 명령 출력으로 확인한다.
QA 확정은 아래 숫자와 출력을 직접 확인한 뒤 그 결과를 신뢰한다는 뜻이다.

1. `claude-heartbeat` 저장소에서 `pytest tests/test_service.py tests/test_agent_package.py -v`를 실행해
   26개 검사가 통과하는지 확인한다(플랫폼 전용 7건은 다른 운영체제에서 건너뛴다).
2. 조회 명령을 직접 실행한다. `heartbeat runtime inspect`(또는 저장소에서
   `python -c "from heartbeat.cli import runtime_status; import json; print(json.dumps(runtime_status(), indent=1))"`).
   응답 한 덩어리에 `installedVersion`, `runningVersion`, `apiMajor`, `target`, `recoverable`,
   `service.registered`, `service.running`, `service.label`, `service.executable`, `checkedAt`,
   `evidence`가 모두 들어 있는지 본다.
3. 실패 구분은 `tests/test_service.py`에서 확인한다.
   - `test_missing_registration_is_its_own_result`: 등록 없음.
   - `test_a_registration_without_its_executable_is_not_recoverable`: 실행 파일 없음.
   - `test_two_registrations_are_ambiguous_instead_of_one_guess`: 등록물 중복.
   - `test_unreadable_state_never_becomes_running`: 권한 부족과 도구 없음이 실행 중으로 승격되지 않는다.
   - `test_a_platform_without_an_adapter_answers_in_the_same_shape`: 지원하지 않는 플랫폼.
   - `test_every_adapter_returns_the_same_inspect_fields`: 세 어댑터의 필드와 뜻이 같다.
4. 설치 쪽 구분과 무쓰기는 `tests/test_agent_package.py`에서 확인한다.
   - `test_status_reports_installed_running_and_service_facts_in_one_response`: 한 응답에 모두 담긴다.
   - `test_installed_runtime_separates_the_ways_an_install_can_be_unreadable`: launcher 없음, 버전
     디렉터리 없음, manifest 못 읽음이 서로 다른 결과다.
   - `test_an_incompatible_api_major_is_its_own_result`: 지원하지 않는 버전.
   - `test_status_never_turns_an_unconfirmed_service_into_a_running_version`: 확인 못 한 서비스에서
     실행 중 버전을 만들어내지 않는다.
   - `test_status_changes_nothing_it_reports_on`: 조회 전후 해시가 같다.
   - `test_only_one_command_answers_the_device_status_question`: 두 번째 조회 명령이 생기지 않았다.
5. 응답 필드가 TASK-147 문서의 기기 조회 항목과 어긋나지 않는지 대조한다. 이름과 뜻은
   `docs/agent-runtime-contract.md`의 `기기 상태 조회` 절에 적어 두었다.

   1 deselected를 확인한다. 제외한 한 검사는 이번 범위 밖의 기존 jobs.d 격리 문제다.

## 이전 확인 동선 (패키징·전환, 한 차례 확인 완료)

1. GitHub Actions의 CI 실행 → `standalone runtime` 세 운영체제 작업 선택 → macOS universal, Linux x86_64, Windows x86_64 artifact가 모두 생성되고 manifest 검증과 `heartbeat agent contract`가 성공한다.
2. 내려받아 압축을 푼 artifact → `heartbeat runtime verify-manifest --root <압축해제경로>` 실행 → target·버전·API major·파일 해시가 포함된 성공 JSON이 표시된다.
3. 새 버전과 기존 버전이 있는 테스트 설치 경로 → 새 배포물의 파일 하나를 바꾼 뒤 `heartbeat runtime activate` 실행 → 검증 실패가 표시되고 기존 `bin/heartbeat` launcher 내용이 바뀌지 않는다.
4. Windows artifact의 Task Scheduler 정의 확인 → XML에서 `RestartOnFailure`와 `IgnoreNew` 확인 → 로그인 뒤 시작하고 비정상 종료 재시작 및 중복 실행 방지 설정이 함께 보인다.
