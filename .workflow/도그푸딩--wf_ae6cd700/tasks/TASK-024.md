# 캘린더를 전이 사실 타임라인으로 바꾸고 하루 칸을 집계로 표시한다

SPEC-007 R1·R6·R8을 구현한다. 배치 기준을 `due_at`에서 전이 이벤트 시각으로 바꾸고, 하루 칸을
종류별 집계로 그리고, 완료 작업 절단을 이 보기에서 걷어낸다.

날짜를 선택해 상세를 보는 것과 빈 달·이력 없는 작업 안내는 TASK-025다. 이 작업이 끝난 시점의 화면은
"무슨 종류의 일이 며칠에 몇 건 있었는가"까지 보여준다.

## 의존성

- **선행 필수: TASK-023.** 이벤트가 실제로 채워져야 화면을 확인할 수 있다. TASK-022만으로는
  이 저장소의 작업 21건에 이력이 없어 그리드가 비어 있다.
- TASK-025와 병행 금지. 같은 컴포넌트와 같은 CSS 블록을 만진다.

## 범위

- `src/features/projects/components/DevelopmentBoard.tsx` — `CalendarView`, 뷰 전환 라벨, 요약줄,
  타임라인용 작업 목록.
- `src/App.css` — 하루 칸 집계 칩 스타일.
- `src/features/projects/components/DevelopmentBoard.test.tsx` — 캘린더 테스트 교체와 추가.
- `docs/file-contract.md` — `due_at` 설명 중 캘린더 배치 문장 한 줄.
- 그 외 파일은 건드리지 않는다. 백엔드·타입·규칙 자산은 바뀌지 않는다.

## 작업 내용

### 0. 먼저 읽을 제약

- 보드·리스트는 그대로다. `due_at`은 계약에서 선택 필드로 남고 카드·표의 목표일 표시도 그대로다
  (기획서 제외 범위). `formatDueDate`와 `calendarDateKey` 헬퍼는 보드·리스트가 계속 쓰므로 지우지
  않는다.
- 이벤트의 `at`은 RFC3339 순간이다. 기존 `calendarDateKey`(`:520`)는 문자열 앞 10자를 정규식으로
  떼는 방식이라 `due_at`(날짜)에는 맞지만 순간에는 맞지 않는다. `2026-08-02T23:00:00Z`는 한국에서
  8월 3일이다. 이벤트용 날짜 키는 `new Date(at)`을 로컬 연·월·일로 푸는 새 헬퍼로 만든다.
  `localDateKey`(`:548`)가 `Date`를 로컬 키로 바꾸는 기존 헬퍼이므로 그 위에 얹는다.
- 파싱되지 않는 `at`은 그 이벤트만 버린다. 화면이 오류를 내지 않는다.

### 1. 보기 이름

이 보기는 목표일을 보여주지 않는다. "일정"이라는 말이 남으면 화면이 하는 일과 어긋난다(R1).
사용자에게 보이는 말을 "타임라인"으로 맞춘다.

- 뷰 전환 버튼 라벨 `캘린더` → `타임라인` (`:26`).
- 상단 안내 문구 "작업 흐름을 보드·리스트·일정으로 바꿔 보세요" → "일정"을 "타임라인"으로 (`:81`).
- 섹션 접근성 이름 `개발 작업 캘린더` → `개발 작업 타임라인` (`:399`).
- 헤더 오른쪽 `<code>due_at</code> 기준` → `상태 전이 기록 기준` (`:407`).

내부 식별자는 바꾸지 않는다. `ViewMode`의 `"calendar"` 값, `CalendarView` 컴포넌트 이름,
`.task-calendar`·`.calendar-grid` 등 CSS 클래스는 그대로 둔다. 사용자에게 보이지 않는 이름을 바꾸면
diff만 커지고 얻는 것이 없다.

### 2. 타임라인이 받는 작업 목록

`CalendarView`는 지금 `filteredTasks`를 받는데, 그 목록은 `tasksForDevelopment`(`:477`)가 완료 작업을
최근 3개로 자른 뒤의 것이다. 과거를 보여주는 화면에서 완료를 자르면 지난달이 거의 빈다(R8).

`DevelopmentBoard`에 메모 하나를 더한다.

```ts
const timelineTasks = useMemo(
  () => workflow.items.tasks.filter((item) => matchesFilters(item, query, statusFilter)),
  [query, statusFilter, workflow.items.tasks],
);
```

`CalendarView`에는 이 목록을 넘긴다. 보드·리스트는 `filteredTasks` 그대로다. 검색어·상태 필터는
타임라인에도 그대로 적용된다(R8).

### 3. 요약줄

지금 요약줄은 항상 `{filteredTasks.length}개 표시 · 완료는 최근 3개만 표시`다(`:128`). 타임라인
보기에서는 사실이 아니다(기획서 완료 조건 21).

- 보드·리스트: 지금 문구 그대로.
- 타임라인: `{timelineTasks.length}개 표시 · 완료 작업까지 전부 표시`.

### 4. 하루 칸

이벤트를 `(작업, 이벤트)` 쌍으로 펼쳐 로컬 날짜 키로 묶는다. 한 작업이 하루에 전이를 여러 번 남기면
쌍도 여러 개다.

하루 칸은 이벤트마다 칩을 두지 않고 종류별로 접는다(결정 1번). 칸 안에는 종류당 칩 하나가 최대 여섯
개다. 이벤트가 100건이든 칩 수는 여섯을 넘지 않으므로 칸 높이가 이벤트 수를 따라 늘지 않는다(R6).

종류 표시와 순서는 작업 수명 순으로 고정한다. 건수 순으로 흔들리면 날짜를 옮겨 다닐 때 읽기 어렵다.

| kind | 표시 | 기존 색 근거 |
| --- | --- | --- |
| `created` | 생성 | 중립(`.status-border-*` 기본값) |
| `in_progress` | 시작 | `status-border-in_progress` |
| `blocked` | 막힘 | `status-border-blocked` |
| `qa_waiting` | QA 대기 | `status-border-qa_waiting` |
| `completed` | 완료 | `status-border-completed` |
| `revision_requested` | 반려 | `status-border-blocked` 계열 |

칩은 `종류 이름 + 건수`를 글자로 담는다. 색은 거들 뿐이고 색 없이도 종류가 읽힌다(R6, 기획서 완료
조건 16). 여섯 값 밖의 `kind`가 들어오면 그 이벤트는 그리지 않는다. 백엔드가 이미 걸러 내지만 화면도
방어한다.

이벤트가 없는 날은 지금처럼 비어 있고, 오늘 표시(`.today`)와 이번 달 밖 흐림(`.outside`)은 그대로
둔다.

### 5. 일정 미지정 영역 제거

`.unscheduled-tasks` 섹션(`:432`~`:437`)을 통째로 걷어낸다. 배치 기준이 목표일이 아니게 되면 목표일이
없다는 사실은 이 화면에서 의미가 없다(R1, 기획서 완료 조건 2).

`App.css`의 `.unscheduled-tasks` 규칙(`:464`~`:474`)은 이 변경 때문에 쓰이지 않게 된 것이므로 함께
지운다. 그 자리는 TASK-025의 상세 패널이 쓴다. 무관한 CSS는 손대지 않는다.

이력이 없어 타임라인에 나타나지 않는 작업을 알리는 안내(R5)는 TASK-025에서 만든다. 이 작업에서는
자리를 비워 둔다.

### 6. 문서 한 줄

`docs/file-contract.md:140`의 "캘린더뷰는 이 값을 기준으로 작업을 배치하고, 필드가 없거나 형식이
잘못된 작업은 일정 미지정으로 표시한다"가 이 변경으로 거짓이 된다. `due_at`이 선택 필드이고 보드·
리스트 카드가 목표일로 표시한다는 사실만 남기고, 캘린더 배치 문장은 지운다. 그 이상 고치지 않는다.

### 7. 테스트

`DevelopmentBoard.test.tsx`:

- 기존 `places due tasks on the calendar and preserves unscheduled tasks`(`:64`)를 교체한다.
  `일정 미지정`과 목표일 배치를 검증하는 테스트라 새 기준에서는 성립하지 않는다.
- `due_at`이 없고 이벤트가 있는 작업이 그 날짜 칸에 나타난다. (기획서 완료 조건 1)
- 화면 어디에도 `일정 미지정`과 `due_at을 추가하면`이 없다. 헤더에 `상태 전이 기록 기준`이 있다.
  (기획서 완료 조건 2)
- 하루에 이벤트가 여러 종류·여러 건인 픽스처에서 칸이 종류별 건수를 보여준다. 이벤트 수만큼 요소가
  늘지 않는다(종류 수만큼이다). (기획서 완료 조건 15)
- 종류 이름이 글자로 나온다. 색 클래스만으로 구분되지 않는다. (기획서 완료 조건 16)
- 완료 작업 4건이 각각 완료 이벤트를 가지면 넷 다 타임라인에 잡히고, 같은 픽스처의 보드 보기에서는
  최근 3개만 나온다. (기획서 완료 조건 20)
- 요약줄이 보드에서는 "완료는 최근 3개만 표시", 타임라인에서는 그렇지 않다. (기획서 완료 조건 21)
- 검색어·상태 필터가 타임라인 이벤트를 좁힌다.
- 파싱되지 않는 `at`을 가진 이벤트가 섞여 있어도 화면이 그려진다.
- 로컬 날짜로 묶인다. UTC 날짜가 다른 시각(예: `T23:00:00Z`)이 한국 기준 날짜 칸에 들어가는지
  확인한다. (테스트 환경 타임존이 UTC일 수 있으므로, 단정은 실행 환경의 로컬 날짜를 계산해 만든다.
  `todayKey`(`:7`)가 이미 같은 방식이다.)

보드·리스트의 목표일 표시 테스트는 손대지 않는다. 수정 없이 통과해야 한다(기획서 완료 조건 3).

## 완료 조건

1. 타임라인이 `due_at`이 아니라 전이 이벤트 시각으로 작업을 배치한다. `due_at`이 없고 이벤트가 있는
   작업이 해당 날짜 칸에 나타난다. (기획서 완료 조건 1)
2. "일정 미지정" 목록과 `due_at` 추가 안내가 사라지고 헤더 기준 표기가 새 기준을 가리킨다.
   (기획서 완료 조건 2)
3. 보드·리스트 카드의 목표일 표시와 `due_at` 계약이 그대로다. 관련 기존 테스트가 수정 없이 통과한다.
   (기획서 완료 조건 3)
4. 하루 칸이 이벤트 종류와 건수를 보여주고, 이벤트가 몰려도 칸이 종류 수(최대 6) 이상으로 늘지 않는다.
   (기획서 완료 조건 15)
5. 이벤트 종류가 색 외의 글자로도 구분된다. (기획서 완료 조건 16)
6. 타임라인이 완료 작업을 최근 3개로 자르지 않는다. 보드는 지금처럼 자른다. (기획서 완료 조건 20)
7. 요약줄의 표시 범위 문구가 타임라인 보기에서 사실과 어긋나지 않는다. (기획서 완료 조건 21)
8. 검색어·상태 필터가 타임라인에도 적용된다.
9. `npm run check`가 통과한다. (기획서 완료 조건 23)

## 참고 사실

확인 시점 2026-08-02. 추정 없이 파일에서 읽은 값이다.

- `CalendarView`는 `DevelopmentBoard.tsx:373`이고 `item.dueAt`으로 날짜 키를 만든다(`:390`).
  키가 없으면 `unscheduled`로 보낸다.
- `tasksForDevelopment`(`:477`)가 완료 작업을 `updated_at` 내림차순 3개로 자른다. `scopedTasks`(`:46`)
  → `filteredTasks`(`:50`) 순서로 흐르고 세 보기가 모두 `filteredTasks`를 받는다.
- 요약줄은 `:124`~`:129`, 뷰 전환은 `:110`~`:121`, 뷰 분기는 `:133`~`:144`다.
- `localDateKey`(`:548`)는 `Date`를 로컬 `YYYY-MM-DD`로 바꾼다. `calendarDays`(`:540`)가 42칸을
  만든다.
- 캘린더 CSS는 `App.css:438`~`:474`다. 칸은 `.calendar-grid > div`(`:449`, `min-height: 102px`),
  칩은 `.calendar-task`(`:456`)이고 상태별 색이 `:457`~`:460`에 있다. `.unscheduled-tasks`는
  `:464`~`:474`다.
- 테스트 픽스처는 `DevelopmentBoard.test.tsx:12`~`:15`이고 `todayKey`(`:7`)가 로컬 오늘 키를 만든다.
- 완료 3개 절단 테스트는 `:74`, 필터 공유 테스트는 `:47`이다.
