# 조회 출력이 다섯 묶음을 두 형식으로 답한다

## 결정권자 요약

### 제안

조회 명령이 진행 집계, 사용자 대기, 활성 선점, 최근 실패를 머리글과 함께 한 화면으로 답하게 한다.

### 바뀌는 것

- 지금: 판 상태를 알려면 문서 수백 건을 대조해야 한다 → 앞으로: 명령 한 번이 네 묶음을 한 화면에 낸다
- 지금 도장을 기다리는 기획서와 확인을 기다리는 기능이 실제 건수로 나온다. 문서에 남은 옛 표기 때문에 부풀지 않는다.
- 같은 값이 기계용 문서로도 나와 세션이 그대로 읽는다.

### 비용과 위험

- 판정 통로가 없는 프로젝트에서는 판정이 필요한 묶음이 빠지고, 빠진 항목의 이름이 출력 마지막 줄에 남는다. 값이 조용히 사라지지는 않는다.
- 읽기만 하는 명령이라 되돌리기 쉽다. 앱 판정과 대조하는 자동 검사가 두 쪽이 어긋나면 실패한다.

## 현재 코드 상태

TASK-S084-02가 만든 `src-tauri/src/infrastructure/status_helper.rs`에 두 구현의 본문과 자산 서술이
이미 서 있고, 인자 처리와 종료 코드와 머리글까지 채워져 있다. 이 작업은 그 본문을 이어서 채운다.

TASK-S084-01이 조건 스크립트에 상태 투영 출력을 세워 둔다. 그 계약은 다음과 같다.

- 호출은 `sh .workflow/rules/wf-eligible.sh status`, 표준 출력은 탭으로 가른 레코드 한 줄씩이다.
- `spec` 탭 워크플로 디렉터리 이름 탭 기획서 id 탭 표시 상태.
- `group` 탭 워크플로 디렉터리 이름 탭 기능 id 탭 표시 상태 탭 구성 버전 탭 확인 방식.
- `lease` 탭 대상 id 탭 역할 탭 만료 표기. 미만료인 것만 나온다.
- 종료 코드는 0 정상, 1 읽기 실패, 2 사용법 오류다.

판정이 필요 없는 값은 이 명령이 직접 읽는다. 읽는 자리는 넷이다.

- `.workflow/project.yml`의 프로젝트 이름과, 상태가 활성인 워크플로의 id와 이름과 디렉터리.
- 워크플로의 `groups/`와 `tasks/` 문서 머리에 적힌 `status`.
- `.workflow/.runtime/silent-runs/` 아래의 JSON 기록. 한 파일이 실행 하나이고 대상 문서 id, 역할,
  시작·종료 시각, 끊긴 사유를 담는다.
- `.workflow/.runtime/migration.lock`의 존재.

바이트 상한이 줄 수보다 먼저 찬다. 한글 한 자가 UTF-8에서 3바이트이므로 4KB는 한글 1,300자
안팎이고, 60줄을 다 쓰려면 한 줄이 20자 남짓이어야 한다. 출력 설계는 이 사실을 전제로 한다.

## 변경 범위

사람용 출력의 다섯 묶음을 이 순서로 고정한다. 담을 것이 없는 묶음도 자리를 지키고 건수 0으로 적는다.

1. 머리글. 프로젝트 이름, 활성 워크플로의 이름과 id, 판정 시각(UTC). 마이그레이션 락이 걸려 있으면
   그 사실을 한 줄 더한다.
2. 진행 집계. 워크플로마다 기획서·기능·개발 작업 세 줄이다. 기획서는 표시 상태 다섯 가지의 건수,
   기능은 문서에 적힌 준비 중과 활성의 건수, 개발 작업은 문서에 적힌 네 상태의 건수다. 건수가 0인
   상태 이름은 줄에서 생략하고, 하나도 남지 않으면 0건으로 적는다.
3. 사용자 대기. 도장을 기다리는 기획서 목록과 품질 확인을 기다리는 기능 목록이다. 도장 대기는 표시
   상태가 검토 대기인 기획서, 확인 대기는 표시 상태가 확인 대기인 기능이다.
4. 활성 선점. 미만료 lease의 대상 id, 역할, 만료 시각이다.
5. 최근 실패. 막힌 개발 작업 전부와, 보고 없이 끝난 실행 기록의 최근 20건이다. 최근 판정은 종료
   시각의 내림차순이고, 같으면 기록 파일 이름의 내림차순이다.

목록은 묶음마다 다섯 줄까지 내고, 넘은 만큼을 그 묶음의 마지막에 "외 N건"으로 접는다. 최근 실패의
실행 기록은 최근 20건 중 다섯 줄까지 내고 나머지를 같은 방식으로 접는다.

묶음 2와 3과 5의 줄은 어느 워크플로의 값인지 앞에 밝힌다. 묶음 4의 lease와 묶음 5의 실행 기록은
프로젝트 단위 기록이라 대상 문서가 활성 워크플로 정확히 한 곳에만 있을 때 그 워크플로 이름을 밝히고,
찾지 못하거나 둘 이상에서 찾으면 그 자리를 비운다. 대상 문서를 찾는 일은 문서 파일이 있는지 보는
것이며 판정이 아니다.

`--json` 호출은 같은 값을 담은 JSON 문서 하나만 표준 출력에 낸다. 구조는 다음으로 고정한다.

- 최상위에 `schemaVersion`(값 1), `generatedAt`, `project`, `workflows`, `activeLeases`,
  `recentSilentRuns`, `excluded`를 둔다.
- `project`는 이름과 마이그레이션 락 여부를 담는다.
- `workflows`의 항목은 워크플로의 id와 디렉터리와 이름, 세 축의 상태별 건수, 도장 대기 기획서 id
  목록, 확인 대기 기능 id 목록, 막힌 작업 id 목록을 담는다.
- `activeLeases`의 항목은 대상 id, 역할, 만료 시각, 짚은 워크플로 id를 담는다.
- `recentSilentRuns`의 항목은 실행 id, 역할, 대상 id, 종료 시각, 끊긴 사유, 짚은 워크플로 id를
  담는다.
- `excluded`는 빠진 항목의 이름을 담는 배열이고, 뺀 것이 없으면 빈 배열이다.
- 사람용 출력의 접기는 화면을 위한 것이므로 JSON에는 적용하지 않는다. 다만 실행 기록은 두 형식 모두
  최근 20건까지다.
- 진단이나 경고 문구는 표준 오류로 보낸다.

판정 통로를 쓸 수 없을 때의 처리를 정한다. 상태 투영 호출이 0이 아닌 코드로 끝나거나 레코드를 하나도
내지 못하면, 판정에 기대는 값을 빼고 나머지를 그대로 낸다.

- 빠지는 것은 기획서의 상태별 건수, 도장 대기 기획서 목록, 확인 대기 기능 목록, 활성 선점 묶음이다.
- 빠진 항목의 이름을 사람용 출력의 마지막 줄에 "제외된 항목:"으로 적고, JSON의 `excluded`에 같은
  이름을 담는다. 뺄 것이 없으면 사람용 마지막 줄은 "제외된 항목: 없음"이다.
- 빠진 묶음도 자리를 지운 채 남기지 않는다. 묶음 제목은 그대로 두고 그 자리에 제외되었음을 적는다.
- 이때에도 종료 코드는 0이다. 판정 통로가 없다는 사실은 상태이지 조회의 실패가 아니다.

두 구현에 같은 내용을 넣는다. 출력 문구와 묶음 순서와 JSON 열쇠 이름은 셸 구현과 PowerShell 구현이
글자 그대로 같다.

## 범위 밖

판정을 새로 적지 않는다. 최신 결정을 덮은 기획서 상태, 기능의 표시 상태, lease의 만료 여부는 상태
투영에서 받은 값을 그대로 쓴다. 받아 오지 못하면 뺀다.

조건 스크립트를 고치지 않는다. 상태 투영의 계약이 부족하다고 판단되면 그것은 이 작업의 범위가 아니라
같은 그룹의 다른 작업이 이미 정한 계약이므로, 고치지 말고 막힌 사유로 남긴다.

동기화 배선과 설치 규약을 고치지 않는다. 자산 버전도 올리지 않는다. 아직 발행된 적 없는 1판이라
본문이 달라져도 설치가 내용 비교로 덮어쓴다.

감시 모드, 색 출력, 셸 자동완성, 실패 기록의 확인 처리 상태에 따른 접기는 기획서가 범위 밖으로 정했다.

## 완료 조건

- C1. 인자 없는 호출의 표준 출력에 다섯 묶음이 위 순서로 나온다. 담을 것이 없는 묶음도 제목과 건수 0을
  남긴다. 아이디어 81건, 기획서 88건, 기능 75건, 개발 작업 220건, 결정 279건, 보고서 415건 규모의
  픽스처에서 출력이 60줄 이하이고 4,096바이트 이하다.
- C2. 목록이 다섯 줄을 넘으면 넘은 만큼이 "외 N건"으로 접힌다.
- C3. `--json` 호출의 표준 출력 전체가 JSON 파서를 그대로 통과하고, 위에서 정한 최상위 열쇠를 모두
  담는다. 표준 오류에 진단 문구가 나가는 상황에서도 표준 출력의 파싱이 깨지지 않는다.
- C4. 사람용 출력과 기계용 출력이 같은 값을 답한다. 두 형식의 상태별 건수, 도장 대기 목록, 확인 대기
  목록, 활성 선점 목록, 막힌 작업 목록이 서로 어긋나면 실패한다.
- C5. 앱 판정과 대조하는 회귀 검사가 있다. 한 픽스처를 놓고 이 명령의 기계 출력과 앱의 판정 결과를
  받아, 두 쪽이 함께 표현하는 값이 하나라도 어긋나면 실패한다. 대조 대상은 기획서의 상태별 건수와
  도장 대기 목록, 확인 대기 기능 목록, 활성 선점 목록이다.
- C6. C5의 픽스처가 다음 상황을 담는다. 문서에 검토 대기로 적혀 있으나 승인 결정이 있는 기획서가
  도장 대기로 세어지지 않는다. 결정이 하나도 없는 기획서만 도장 대기로 세어진다.
- C7. 활성 워크플로가 둘인 픽스처에서 두 워크플로의 값이 섞이지 않고, 묶음 2와 3과 5의 줄마다 어느
  워크플로의 값인지 나온다.
- C8. 상태 투영을 모르는 옛 조건 스크립트가 설치된 프로젝트에서 종료 코드가 0이고, 판정에 기대는 네
  항목이 빠지며, 빠진 항목의 이름이 사람용 마지막 줄과 기계 출력의 배열에 함께 나온다. 문서에서
  직접 읽는 값은 그대로 나온다.
- C9. 뺀 것이 없는 정상 실행에서 사람용 마지막 줄이 "제외된 항목: 없음"이고 기계 출력의 배열이
  비어 있다.
- C10. 막힌 작업이 전부 집계되고, 보고 없이 끝난 실행 기록이 종료 시각 내림차순으로 최근 20건까지
  나온다.
- C11. 명령 실행 전후로 프로젝트 디렉터리의 파일 목록과 각 파일 내용의 해시가 같다. 마이그레이션
  락이 걸린 프로젝트에서도 두 호출이 0으로 끝난다.
- C12. 두 구현의 묶음 순서와 JSON 열쇠 이름이 같음을 확인하는 시험이 있다.

- C11은 실행 전후로 프로젝트 디렉터리를 훑어 경로 목록과 내용 해시를 모아 비교한다.

- `cd src-tauri && cargo clippy --all-targets -- -D warnings` 와 `cargo fmt --check` 를 돌린다.

  60줄과 4,096바이트 안에 드는지, 도장 대기 기획서 건수가 앱 화면과 같은지 눈으로 확인한다. 설치본이
  옛 판이면 먼저 앱으로 동기화한다.

## 범위 사전 검사

선언한 파일은 하나다. 스크립트 두 본문과 그 시험이 모두 그 파일 안에 있고, 완료 조건을 채우는 데 이
밖의 편집이 필요한지 값마다 근원부터 소비자까지 따라가며 확인했다.

`src-tauri/src/infrastructure/heartbeat_condition.rs`를 열어 보고 뺐다. 판정값은 그 파일이 세우는
상태 투영에서 받아 오지만, 이 작업은 설치된 스크립트를 부르는 쪽이라 그 파일을 편집하지 않는다.
계약이 부족하면 고치지 않고 막힌 사유로 남긴다.

`src-tauri/src/infrastructure/managed_project_assets.rs`와 `managed_script.rs`를 열어 보고 뺐다.
자산 배선과 설치 판정은 앞 작업이 이미 세웠고, 본문이 달라져도 설치 계획이 내용 비교로 덮어쓰므로
버전 상수도 배선도 손댈 이유가 없다.

`src-tauri/src/infrastructure/fs_project_repository.rs`와 `src-tauri/src/domain/project.rs`를 열어
보고 뺐다. 대조 시험이 둘을 읽지만 읽기만 한다. 필요한 값은 215행 구조체의 공개 조회 함수(218행)가
돌려주는 요약에 이미 다 있다. 212행의 항목 묶음이 기획서와 기능과 작업을, 746행의 lease 요약이 대상
id와 역할과 만료 표기를, 280행의 열거가 기능 표시 상태를 싣는다.

`src/features/projects/application/useProjectWorkspace.ts`를 열어 보고 뺐다. 화면 파생 계산은 세
번째 판정 자리이고, 이 명령은 그 계산을 부를 수도 없고 대조 기준으로 삼지도 않는다. 대조 기준은 앱
Rust 판정 하나로 충분하다.

`.workflow/rules/wf-eligible.sh`와 `.workflow/rules/wf-status.sh`를 열어 보고 뺐다. 둘 다 앱이 다시
쓰는 설치본이고 정본은 Rust 상수다.

기계 상태를 조건으로 삼는 측정이 없다. 줄 수와 바이트 상한은 출력 내용만으로 정해지고 다른 세션이
나란히 돌아도 값이 흔들리지 않으므로 조용한 기계를 요구하지 않는다. 선언한 파일이 TASK-S084-02와
겹치므로 그쪽을 선행으로 선언했고, 상태 투영을 소비하므로 TASK-S084-01도 선행이다.

- 값 경로: C5의 기획서 상태별 건수와 도장 대기 목록. 값을 만드는 자리는 결정 문서와 기획서 문서이고
  판정하는 자리는 조건 스크립트의 상태 투영이며, 두 홉 모두 앞 작업이 값을 그대로 답하도록 세우므로
  이 작업에서 편집하지 않는다. 값을 받는 자리와 세는 자리와 두 형식으로 내는 자리는 모두 선언한
  파일의 스크립트 본문이다. 대조 기준은 앱 조회 함수가 돌려주는 기획서 항목의 상태값이고 읽기만
  한다.
- 값 경로: C5의 확인 대기 기능 목록. 값을 만드는 자리는 기능 문서와 그 기능의 작업 문서와 확인
  결정이고, 판정하는 자리는 상태 투영의 기능 레코드다. 소비하는 자리는 선언한 파일이며, 확인 대기에
  해당하는 레코드만 거르는 것이 이 작업의 몫이다. 표시 상태 어휘는 앞 작업이 고정했으므로 새로
  만들지 않는다.
- 값 경로: C5의 활성 선점 목록. 값을 만드는 자리는 선점 헬퍼가 쓴 lease 파일이고, 만료 판정은 상태
  투영이 이미 마친 상태로 넘어온다. 선언한 파일은 받은 줄을 형식으로 옮기고, 대상 문서가 어느
  워크플로에 있는지 확인하려고 워크플로 문서 디렉터리에서 같은 id의 파일이 있는지만 본다. 이 확인은
  파일 존재 여부이므로 판정 자리를 늘리지 않는다.
- 값 경로: C10의 막힌 작업과 실행 기록. 막힌 작업은 작업 문서 머리의 상태 값이라 선언한 파일이 직접
  읽는다. 실행 기록은 앱이 쓰는 JSON 파일이고, 대상 문서 id와 역할과 종료 시각과 끊긴 사유가 그
  파일에 그대로 있다. 선언한 파일이 그 값을 읽어 정렬하고 형식으로 옮기며, 다른 홉이 없다.
- 값 경로: C8의 제외된 항목. 값을 만드는 자리는 상태 투영 호출의 종료 코드와 출력이며, 값을 판단해
  이름을 담는 자리와 두 형식에 싣는 자리가 모두 선언한 파일이다. 조건 스크립트 쪽에 이 사실을 알릴
  필요가 없으므로 바깥으로 나가는 홉이 없다.
- 값 경로: C1의 줄 수와 바이트. 값을 만드는 자리는 이 작업이 정한 출력 형식 자체이고, 재는 자리는
  같은 파일의 시험이다. 픽스처를 만드는 코드도 같은 파일 안에 서므로 선언 밖으로 나가지 않는다.
