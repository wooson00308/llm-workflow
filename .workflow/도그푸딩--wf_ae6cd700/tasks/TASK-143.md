# 막힌 사유 문서 계약을 관리 규칙에 반영한다

## 결정권자 요약

앞으로 개발 작업이 막히면 현재 사유와 필요한 해결, 재개 조건을 같은 문서에 반드시 남긴다.
관련 작업이나 외부 의존도 함께 기록하므로 사용자가 원문 전체를 뒤지지 않고 상황을 파악할 수 있다.
막힘이 풀려도 마지막 기록은 지우지 않고, 다시 막히면 현재 사유로 교체한다.
기존 작업은 일괄 수정하지 않아 과거 감사 기록과 사용자가 만든 문서를 보존한다.
이 작업은 작성 규칙과 문서 안내만 바꾸며 화면이나 작업 상태는 직접 변경하지 않는다.
완료 후 새로 막힘을 기록하는 개발 세션부터 같은 형식을 사용한다.

## 목적

SPEC-053의 R1, R2와 R8 중 작성자 계약을 구현한다. 현재 공통 규칙은 실제 impediment가 있을 때만
작업을 `blocked`로 바꾸고 같은 편집에서 상태 이력을 추가하라고 요구하지만, 현재 사유를 어디에 어떤
형식으로 남길지는 정하지 않는다. 개발자 계약과 파일 안내에 고정 절을 추가해 새 차단과 재차단이
앱에서 결정적으로 읽힐 수 있게 한다.

## 현재 상태

- 관리되는 공통 규칙과 세 역할 계약의 정본은
  `src-tauri/src/infrastructure/project_instructions.rs`의 내장 문자열이다. 프로젝트에 설치된
  `.workflow/rules/` 사본은 앱 동기화가 관리하므로 이 작업에서 직접 편집하지 않는다.
- 공통 규칙은 `blocked` 전이에 상태, `history`, `updated_at`을 같은 편집에서 맞추게 하지만 본문의
  사유 절은 요구하지 않는다.
- 개발자 계약은 `blocked`가 실제 방해 요소를 만난 세션의 의도적인 상태라고 정의한다. 막힐 때 보고서와
  작업 문서에 어떤 현재 사실을 남길지는 정의하지 않는다.
- `docs/file-contract.md`는 작업 상태와 여섯 이력 종류를 설명하지만 차단 사유 절의 형식과 보존 규칙은
  설명하지 않는다.
- TASK-S052-01이 같은 두 파일에서 결정권자 요약 계약을 갱신하고 있다. 그 결과를 보존한 뒤 현재
  변경을 적용하도록 이 작업이 TASK-S052-01에 의존한다.

## 변경 범위

### 관리되는 공통 규칙

- 개발 작업을 `blocked`로 전환할 때 상태, `blocked` 이력, `updated_at`과 아래 절을 같은 문서
  편집에서 기록하도록 명시한다.

  ```markdown
  ## 막힌 사유

  - 막힌 지점: 지금 진행할 수 없는 구체적인 이유
  - 필요한 해결: 누가 무엇을 제공하거나 바꿔야 하는지
  - 재개 조건: 어떤 사실이 충족되면 개발을 다시 시작하는지
  - 관련 대상: TASK-001, 외부 승인 대기
  ```

- 제목과 네 라벨은 정확히 한 번씩 사용하고 값은 비워 두지 않는다. 관련 대상이 없으면 `없음`을 쓰고,
  여러 값은 쉼표와 공백으로 작성 순서대로 나열한다.
- 차단 상태에서 현재 사유가 달라지면 네 값과 `updated_at`을 함께 갱신한다. 새 `blocked` 이력은 실제
  상태 전이가 일어날 때만 추가하고, 사유 문구만 고치는 편집에는 가짜 전이를 추가하지 않는다.
- 차단 상태에서 벗어나도 절을 삭제하지 않는다. 같은 작업이 다시 차단되면 절은 새 현재 사유로 교체하고,
  이전 상세는 기존 개발 보고서와 append-only 상태 이력에 보존한다.
- 기존 작업을 소급 변환하지 않고, 유효한 절이 없는 기존 문서도 계속 읽을 수 있음을 명시한다.

### 개발자 역할 계약

- 실제 방해 요소 때문에 작업을 `blocked`로 넘기는 개발자는 공통 규칙의 막힌 사유 절을 같은 편집에서
  작성해야 한다.
- 방해 요소를 추측하거나 단순한 질문·승인 대기를 가짜 `blocked`로 만들지 않는 현재 원칙을 유지한다.
- 개발자가 막힌 사유를 쓸 때 네 값은 현재 확인한 사실만 기록하고, 해결되지 않은 내용을 완료됐다고
  표시하지 않게 한다.
- 개발 보고서에는 검증한 사실과 남은 impediment를 기록하되, 현재 사유의 정본은 작업 문서의 고정
  절임을 명시한다.

### 파일 계약 안내와 버전

- `docs/file-contract.md`의 개발 작업 절에 형식, 전환과 보존 규칙, 기존 문서 호환성을 설명한다.
- 공통 규칙과 개발자 역할 계약의 현재 내장 버전 상수와 frontmatter 버전을 각각 한 단계 올린다.
  절대 버전 숫자를 과거 값으로 되돌리지 않고 TASK-S052-01이 남긴 최신 값에서 증가시킨다.
- 설치·업그레이드 검사는 새 버전과 고정 제목·네 라벨이 관리 자산에 포함되는지 확인한다.

## 손대지 않는 것

- 앱의 작업 상세 화면과 Markdown 파서
- `blocked`에서 다른 상태로 전환하는 새 조작과 새 이력 종류
- 선행 작업, 파일 겹침, lease와 Developer 자격 판정
- 기존 작업 문서, 개발 보고서와 상태 이력의 소급 수정
- 프로젝트에 설치된 `.workflow/rules/` 파일의 직접 편집
- 기획서, 결정 기록, workflow manifest와 schema version

## 완료 조건

1. 새로 설치한 공통 규칙이 `blocked` 전환과 같은 편집에서 상태, 이력, 갱신 시각과 막힌 사유 절을
   함께 기록하도록 요구한다.
2. 설치된 개발자 계약이 정확한 제목과 막힌 지점, 필요한 해결, 재개 조건, 관련 대상 네 라벨을
   요구한다.
3. 제목과 라벨의 중복·누락·빈 값을 허용하지 않고, 관련 대상 없음과 여러 값의 표기법이 문서에
   정의돼 있다.
4. 차단 중 사유 변경, 차단 해제 뒤 보존, 재차단 시 현재 값 교체와 과거 보고서·이력 보존 규칙이
   공통 규칙과 파일 안내에서 같은 의미로 읽힌다.
5. 사유만 갱신할 때 존재하지 않은 상태 전이를 추가하지 않고 append-only 이력을 수정하지 않는다는
   경계가 명시돼 있다.
6. 기존 작업을 일괄 수정하지 않으며 유효한 절이 없는 기존 문서도 계속 유효하다고 명시돼 있다.
7. 공통 규칙과 개발자 역할 계약의 내장 버전과 frontmatter 버전이 각각 일치하고 이전 최신 값보다
   한 단계 높다.
8. 관리 자산 설치·갱신 검사가 새 계약을 포함한 사본을 만들고 최신 설치본을 다시 덮어쓰지 않는 기존
   안전 절차를 유지한다.
9. TASK-S052-01이 추가한 결정권자 요약 계약과 관련 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. `src-tauri`에서 `cargo test project_instructions`를 실행해 설치본의 버전, 제목, 네 라벨과 기존
   역할 계약 검사가 통과하는지 확인한다.
2. 구버전 공통 규칙과 개발자 계약을 가진 임시 프로젝트에 관리 자산 동기화를 실행하고, 두 파일만
   새 계약으로 갱신되는지 확인한다.
3. 앱보다 높은 버전 또는 관리 형식이 아닌 파일을 둔 픽스처에서 기존 충돌·보존 검사가 그대로
   통과하는지 확인한다.
4. `src-tauri`에서 `cargo test`를 실행해 관리 자산 동기화와 프로젝트 조회 전체 회귀를 확인한다.
5. 저장소 루트에서 `npm run check`를 실행해 프런트엔드와 배포 빌드가 계약 변경으로 깨지지 않는지
   확인한다.
6. 변경한 내장 공통 규칙, 개발자 계약과 파일 안내를 나란히 읽어 제목, 네 라벨, 보존 규칙과 기존
   문서 호환성이 서로 어긋나지 않는지 확인한다.

## 범위와 선행

TASK-S052-01이 같은 두 파일에서 요약 계약과 버전을 갱신하므로 그 작업이 `qa_waiting` 또는
`completed`가 된 뒤 시작한다. TASK-144와는 파일이 겹치지 않아 병렬로 진행할 수 있다. 이 작업은
화면 구현의 선행이 아니다. 기존 차단 문서도 폴백으로 표시할 수 있고, 새 계약은 이후 전환부터 적용되기
때문이다.
