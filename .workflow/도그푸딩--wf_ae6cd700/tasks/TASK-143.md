# 막힌 사유 문서 계약을 관리 규칙에 반영한다

## 결정권자 요약

앞으로 개발 작업이 막히면 현재 사유와 필요한 해결, 재개 조건을 같은 문서에 반드시 남긴다.
관련 작업이나 외부 의존도 함께 기록하므로 사용자가 원문 전체를 뒤지지 않고 상황을 파악할 수 있다.
막힘이 풀려도 마지막 기록은 지우지 않고, 다시 막히면 현재 사유로 교체한다.
기존 작업은 일괄 수정하지 않아 과거 감사 기록과 사용자가 만든 문서를 보존한다.
이 작업은 작성 규칙과 문서 안내, 그리고 규칙 버전을 확인하는 검사만 바꾸며 화면이나 작업 상태는
직접 변경하지 않는다.
완료 후 새로 막힘을 기록하는 개발 세션부터 같은 형식을 사용한다.

## 확인 동선

이 작업에는 눈으로 볼 화면이 없다. 바뀐 것은 앱이 설치하는 규칙 문언과 사용자·개발자용 계약 문서라
자동 검사가 그 문언을 대조한다. 확인 도장은 아래 수치를 신뢰한다는 뜻이다.

- `cargo test --manifest-path src-tauri/Cargo.toml project_instructions` → 22 passed, 0 failed
- `cargo test --manifest-path src-tauri/Cargo.toml` → 611 passed, 0 failed
- `npm run check` → 타입 검사 통과, 25개 파일 851 tests 통과, 배포 빌드 성공
- `cargo clippy --all-targets` 경고 없음, `cargo fmt` 적용

문언을 직접 읽고 싶다면 이 저장소의 설치본이 이미 갱신돼 있다. 개발 중인 앱이 관리 자산을 동기화하면서
새 계약을 내려받았고, 그 결과가 그대로 남아 있다.

1. `.workflow/rules/workflow.md`의 frontmatter가 `rules_version: 18`이고, 5절 안에
   `### Recording why a task is blocked`가 있다. 그 아래에 `## 막힌 사유` 제목과 네 라벨(막힌 지점,
   필요한 해결, 재개 조건, 관련 대상)이 예시 블록으로 한 번씩 정의돼 있다.
2. 같은 절에서 네 규칙을 읽을 수 있다. 값을 비우거나 라벨을 빠뜨리면 계약이 요구하는 절이 아니라는 것,
   관련 대상이 없으면 `없음`을 쓰고 여럿이면 쉼표와 공백으로 나열한다는 것, 사유 문구만 고치는 편집은
   상태 전이가 아니라 이력을 늘리지 않는다는 것, 차단에서 벗어나도 절을 지우지 않고 재차단 시 현재
   사유로 교체한다는 것.
3. `.workflow/rules/roles/developer.md`는 `rules_version: 13`이고 `## Blocking a task` 절에서 자기
   의무만 적은 뒤 공통 규칙 `§5`를 가리킨다. 라벨 목록을 다시 적지 않는다.
4. `.workflow/rules/roles/planner.md`와 `architect.md`는 `rules_version: 11` 그대로다. 본문이 바뀌지
   않은 계약은 버전이 오르지 않는다.

같은 내용이 `docs/file-contract.md`의 `### 막힌 사유 절`에 한국어로 적혀 있다.

기존 문서는 바뀌지 않는다. 이 절이 없거나 형식이 불완전한 기존 작업 문서를 앱이 고치지 않고, 그 때문에
목록·상세 화면의 표시나 자격 판정이 달라지지도 않는다.

## 목적

SPEC-053의 R1, R2와 R8 중 작성자 계약을 구현한다. 현재 공통 규칙은 실제 impediment가 있을 때만
작업을 `blocked`로 바꾸고 같은 편집에서 상태 이력을 추가하라고 요구하지만, 현재 사유를 어디에 어떤
형식으로 남길지는 정하지 않는다. 개발자 계약과 파일 안내에 고정 절을 추가해 새 차단과 재차단이
앱에서 결정적으로 읽힐 수 있게 한다.

## 현재 상태

- 관리되는 공통 규칙과 세 역할 계약의 정본은
  `src-tauri/src/infrastructure/project_instructions.rs`의 내장 문자열이다. 프로젝트에 설치된
  `.workflow/rules/` 사본은 앱 동기화가 관리하므로 이 작업에서 직접 편집하지 않는다.
- 공통 규칙은 `blocked` 전이에 상태, `history`, `updated_at`을 같은 편집에서 맞추게 하지만 본문의
  사유 절은 요구하지 않는다.
- 개발자 계약은 `blocked`가 실제 방해 요소를 만난 세션의 의도적인 상태라고 정의한다. 막힐 때 보고서와
  작업 문서에 어떤 현재 사실을 남길지는 정의하지 않는다.
- `docs/file-contract.md`는 작업 상태와 여섯 이력 종류를 설명하지만 차단 사유 절의 형식과 보존 규칙은
  설명하지 않는다.
- TASK-S052-01이 같은 파일들에서 구조화된 결정권자 요약 계약을 추가하고 버전을 공통 규칙 17,
  planner 11, architect 11, developer 12로 올린 뒤 품질 확인 대기 상태다. 이 작업은 그 값 위에서
  증가시키고 그 계약 문언과 검사를 보존한다.
- `fs_project_repository.rs`와 `managed_project_assets.rs`의 검사는 규칙 버전을 문자열로 직접 비교한다.
  버전 상수만 올리고 이 문자열을 그대로 두면 두 파일의 검사가 실패한다. 그래서 두 파일이 이 작업의
  범위에 함께 들어간다.
- 두 파일에는 낮은 버전의 규칙을 설치한 뒤 동기화가 최신으로 덮어쓰는지 보는 픽스처가 여럿 있고,
  그중 일부는 위쪽 방향, 즉 앱보다 높은 버전을 설치해 덮어쓰지 않는지 보는 픽스처다. 방향을 뒤집으면
  검사 의도가 반대가 된다.
- TASK-S052-01 재작업은 그 픽스처 가운데 두 개가 이전 상태에서 실제로는 아무 문자열도 바꾸지 못하는
  상태였음을 발견해 되살렸다. `reads_task_detail_and_records_user_qa_outcomes`는 아키텍트 계약을 11에서
  10으로 낮춘 뒤 다시 11이 되는지 보고, `a_batch_confirms_every_task_it_was_given`은 개발자 계약을
  12에서 11로 낮춘 뒤 다시 12가 되는지 본다. 두 검사는 이번 회귀에서 처음으로 실제 판정을 수행한다.

## 변경 범위

### 관리되는 공통 규칙

- 개발 작업을 `blocked`로 전환할 때 상태, `blocked` 이력, `updated_at`과 아래 절을 같은 문서
  편집에서 기록하도록 명시한다.

  ```markdown
  ## 막힌 사유

  - 막힌 지점: 지금 진행할 수 없는 구체적인 이유
  - 필요한 해결: 누가 무엇을 제공하거나 바꿔야 하는지
  - 재개 조건: 어떤 사실이 충족되면 개발을 다시 시작하는지
  - 관련 대상: TASK-001, 외부 승인 대기
  ```

- 제목과 네 라벨은 정확히 한 번씩 사용하고 값은 비워 두지 않는다. 관련 대상이 없으면 `없음`을 쓰고,
  여러 값은 쉼표와 공백으로 작성 순서대로 나열한다.
- 차단 상태에서 현재 사유가 달라지면 네 값과 `updated_at`을 함께 갱신한다. 새 `blocked` 이력은 실제
  상태 전이가 일어날 때만 추가하고, 사유 문구만 고치는 편집에는 가짜 전이를 추가하지 않는다.
- 차단 상태에서 벗어나도 절을 삭제하지 않는다. 같은 작업이 다시 차단되면 절은 새 현재 사유로 교체하고,
  이전 상세는 기존 개발 보고서와 append-only 상태 이력에 보존한다.
- 기존 작업을 소급 변환하지 않고, 유효한 절이 없는 기존 문서도 계속 읽을 수 있음을 명시한다.

### 개발자 역할 계약

- 실제 방해 요소 때문에 작업을 `blocked`로 넘기는 개발자는 공통 규칙의 막힌 사유 절을 같은 편집에서
  작성해야 한다.
- 방해 요소를 추측하거나 단순한 질문·승인 대기를 가짜 `blocked`로 만들지 않는 현재 원칙을 유지한다.
- 개발자가 막힌 사유를 쓸 때 네 값은 현재 확인한 사실만 기록하고, 해결되지 않은 내용을 완료됐다고
  표시하지 않게 한다.
- 개발 보고서에는 검증한 사실과 남은 impediment를 기록하되, 현재 사유의 정본은 작업 문서의 고정
  절임을 명시한다.

### 파일 계약 안내와 버전

- `docs/file-contract.md`의 개발 작업 절에 형식, 전환과 보존 규칙, 기존 문서 호환성을 설명한다.
- 본문이 바뀌는 계약은 공통 규칙과 개발자 역할 계약 둘이다. 내장 버전 상수와 규칙 본문 frontmatter를
  공통 규칙은 17에서 18로, 개발자 계약은 12에서 13으로 함께 올린다. planner와 architect 계약은 본문이
  바뀌지 않으므로 11에 그대로 둔다.
- 설치·업그레이드 검사는 새 버전과 고정 제목·네 라벨이 관리 자산에 포함되는지 확인한다.

### 버전 문자열을 가진 검사 파일

`fs_project_repository.rs`와 `managed_project_assets.rs`에서는 이전 규칙 버전을 직접 비교하는 문자열만
새 값으로 바꾼다. 검사 함수의 판정 대상, 시나리오 구성과 단언 개수는 그대로 둔다. 바꿀 문자열은 아래
규칙으로 고른다.

- 어떤 계약의 문자열인지 보고 고른다. 숫자만 보고 일괄 치환하지 않는다. 개발자 계약은 12에서 13이
  되지만 planner와 architect 계약은 11에 머무르므로, 11을 쓰는 픽스처는 그대로 두어야 한다.
- 낮은 버전을 설치해 동기화가 최신으로 올리는지 보는 픽스처는 낮추는 방향을, 앱보다 높은 버전을 설치해
  덮어쓰지 않는지 보는 픽스처는 높이는 방향을 유지한다. 방향을 뒤집으면 검사가 반대 사실을 확인한다.
- 각 치환은 실제로 존재하는 문자열을 대상으로 삼아야 한다. 대상 문자열이 픽스처 원문에 없으면 그 픽스처는
  아무것도 바꾸지 못하고 검사는 통과하지만 아무 사실도 확인하지 못한다. TASK-S052-01 재작업이 되살린 두
  픽스처가 그 상태였으므로, 이번 변경으로 다시 그렇게 만들지 않는다.

## 손대지 않는 것

- 앱의 작업 상세 화면과 Markdown 파서
- `blocked`에서 다른 상태로 전환하는 새 조작과 새 이력 종류
- 선행 작업, 파일 겹침, lease와 Developer 자격 판정
- 기존 작업 문서, 개발 보고서와 상태 이력의 소급 수정
- 프로젝트에 설치된 `.workflow/rules/` 파일의 직접 편집
- 기획서, 결정 기록, workflow manifest와 schema version

## 완료 조건

1. 새로 설치한 공통 규칙이 `blocked` 전환과 같은 편집에서 상태, 이력, 갱신 시각과 막힌 사유 절을
   함께 기록하도록 요구한다.
2. 설치된 개발자 계약이 정확한 제목과 막힌 지점, 필요한 해결, 재개 조건, 관련 대상 네 라벨을
   요구한다.
3. 제목과 라벨의 중복·누락·빈 값을 허용하지 않고, 관련 대상 없음과 여러 값의 표기법이 문서에
   정의돼 있다.
4. 차단 중 사유 변경, 차단 해제 뒤 보존, 재차단 시 현재 값 교체와 과거 보고서·이력 보존 규칙이
   공통 규칙과 파일 안내에서 같은 의미로 읽힌다.
5. 사유만 갱신할 때 존재하지 않은 상태 전이를 추가하지 않고 append-only 이력을 수정하지 않는다는
   경계가 명시돼 있다.
6. 기존 작업을 일괄 수정하지 않으며 유효한 절이 없는 기존 문서도 계속 유효하다고 명시돼 있다.
7. 공통 규칙과 개발자 역할 계약의 내장 버전과 frontmatter 버전이 각각 일치하고 이전 최신 값보다
   한 단계 높다. 착수 시점 값이 17과 12이므로 결과는 18과 13이다. planner와 architect 계약의 버전은
   11에서 바뀌지 않는다.
8. 관리 자산 설치·갱신 검사가 새 계약을 포함한 사본을 만들고 최신 설치본을 다시 덮어쓰지 않는 기존
   안전 절차를 유지한다.
9. TASK-S052-01이 추가한 결정권자 요약 계약과 관련 검사를 삭제하거나 약화하지 않는다.
10. 변경분은 범위 파일 네 개뿐이고 `.workflow/rules/`, 기존 기획서·작업·보고서, 결정 기록을 수정하지
    않는다.
11. `fs_project_repository.rs`와 `managed_project_assets.rs`에서는 이전 규칙 버전 문자열만 바뀐다.
    검사 이름, 시나리오 구성과 단언 개수가 변경 전과 같다.
12. 두 파일의 모든 버전 치환이 실제로 존재하는 문자열을 대상으로 삼는다. 아무것도 바꾸지 못하는 치환이
    남아 있지 않으며, 특히 TASK-S052-01이 되살린 아키텍트 계약 픽스처와 개발자 계약 픽스처가 계속
    실제로 낮은 버전을 설치한다.
13. 앱보다 높은 버전을 설치해 덮어쓰지 않는지 보는 픽스처의 방향이 유지된다.

## 검증 절차

1. `src-tauri`에서 `cargo test project_instructions`를 실행해 설치본의 버전, 제목, 네 라벨과 기존
   역할 계약 검사가 통과하는지 확인한다.
2. 구버전 공통 규칙과 개발자 계약을 가진 임시 프로젝트에 관리 자산 동기화를 실행하고, 두 파일만
   새 계약으로 갱신되는지 확인한다.
3. 앱보다 높은 버전 또는 관리 형식이 아닌 파일을 둔 픽스처에서 기존 충돌·보존 검사가 그대로
   통과하는지 확인한다.
4. `src-tauri`에서 `cargo test`를 실행해 관리 자산 동기화와 프로젝트 조회 전체 회귀를 확인한다.
5. 저장소 루트에서 `npm run check`를 실행해 프런트엔드와 배포 빌드가 계약 변경으로 깨지지 않는지
   확인한다.
6. 변경한 내장 공통 규칙, 개발자 계약과 파일 안내를 나란히 읽어 제목, 네 라벨, 보존 규칙과 기존
   문서 호환성이 서로 어긋나지 않는지 확인한다.
7. 두 검사 파일의 `git diff`를 줄 단위로 읽어 바뀐 줄이 버전 숫자와 버전 문자열뿐인지 확인한다.
   검사 이름, 시나리오, 단언 줄 수는 변경 전과 같아야 한다.
8. 두 파일의 각 버전 치환에 대해 대상 문자열이 픽스처 원문에 실제로 존재하는지 확인한다. 치환 뒤 픽스처
   내용이 의도한 낮은 버전 또는 높은 버전이 되는지 직접 읽어 대조한다.
