# 잡 model 필드를 지원 모델 선택 UI로 전환 (직접 입력 경로 포함)

SPEC-004 R1~R5를 구현한다. 연동 관리 UI의 `model` 자유 입력을 선택 UI로 바꾸고, 목록 밖 값을 위한 직접
입력 경로를 남긴다. 프론트만 바뀐다. 백엔드 검증과 파일 쓰기 계약은 그대로 둔다.

이 기획서는 작업 하나로 분해했다. 선택 UI만 먼저 넣고 직접 입력을 나중에 넣으면, 그 사이에 목록 밖 값이
적힌 파일을 앱이 표현하지 못해 저장 시 사용자의 값을 목록 안 값으로 바꿔 버리는 중간 상태가 생긴다.
그 상태는 R3 위반이고 QA 대상으로도 성립하지 않는다.

## 의존성

- 선행 필수 작업은 없다. 이 작업만으로 화면이 바뀌고 사용자가 QA할 수 있다.
- **SPEC-003 작업(TASK-008~TASK-012)과 병행 금지.** `SettingsView.tsx`와 `SettingsView.test.tsx`를 함께
  만진다. TASK-010은 카드 골격을, TASK-012는 같은 화면의 쓰기 경로를 재구성한다.
- 권장 착수 시점은 TASK-012 완료 후다. 그 시점에는 관리 UI에 역할 잡 3종과 dream 잡이 모두 있으므로
  R5의 "UI에 존재하는 모든 잡"이 한 번에 전환된다.
- 그보다 먼저 착수한다면 대상은 역할 잡 3종뿐이다. 이 경우 TASK-012 구현자에게 여기서 만든 모델 필드
  컴포넌트를 쓰라고 알려야 한다. 알리지 않으면 dream 잡의 `model`만 자유 입력으로 남아 R5가 깨진다.
  TASK-012 문서는 이 작업의 범위가 아니므로 고치지 않는다.

## 범위

- `src/features/projects/components/` — 모델 필드 컴포넌트 신규 파일 1개. 지원 모델 목록과 선택·직접 입력
  UI를 이 파일 안에 함께 둔다.
- `src/features/projects/components/SettingsView.tsx` — `model` 필드의 렌더만 새 컴포넌트로 교체한다.
- `src/features/projects/components/SettingsView.test.tsx` 및 필요한 경우 새 컴포넌트 전용 테스트 파일.
- 그 외 파일은 건드리지 않는다. 특히 `src-tauri/` 아래는 한 줄도 바꾸지 않는다 (R4).

## 작업 내용

### 0. 먼저 읽을 제약

- 백엔드 검증 `is_model`(`src-tauri/src/infrastructure/heartbeat_jobs.rs:323`)은 그대로 둔다. 프론트에서
  목록으로 좁혔다고 백엔드까지 좁히면, 손으로 정식 모델명을 적어 둔 파일을 앱이 저장하지 못하는 회귀가
  생긴다. 기획서가 제외 범위로 못 박은 항목이다.
- `~/.claude/HEARTBEAT.md`에 기록되는 `- model: <값>` 줄의 형식과 값은 달라지지 않는다.
- 빈 `model`(CLI 기본 모델 위임)은 이번 범위가 아니다. 선택지에 "기본값"·"지정 안 함" 항목을 만들지 않는다.
  기획서 확인 필요 2번이 제외로 승인됐다.
- 설치 요청 payload의 모양이 바뀌면 안 된다. 역할 잡 요청은 `{ role, enabled, interval, maxPer, model }`
  다섯 키 그대로다. 기존 테스트가 `toHaveBeenCalledWith`로 이 모양을 정확히 단언한다
  (`SettingsView.test.tsx:244`). 직접 입력 모드 같은 화면 상태를 폼에 섞어 넣고 그대로 spread 하면 여기서
  깨진다.
- 저장 흐름과 쓰기 전 확인 절차(SPEC-002 R6)는 그대로다. 이 작업은 입력 방식만 바꾼다.

### 1. 지원 모델 목록 (R2)

- 목록은 별칭 네 개다: `opus`, `sonnet`, `haiku`, `fable`. 이 순서로 노출한다. 임의로 더하거나 빼지 않는다.
- 착수 시 `claude --help`의 `--model` 설명으로 이 집합을 다시 확인하고, 확인 결과를 보고서에 적는다.
  2026-08-02 확인 시점의 사실은 "참고 사실"에 적어 두었다.
- 목록은 앱 안 한 곳에만 정의한다. 같은 목록이 두 곳에 있으면 시간이 지나 갈라진다. 잡마다 따로 정의하지
  않는다 (R5).
- 정의 지점 주석에 갱신 방법(앱 릴리스로만 갱신)과 확인처(`claude --help`의 `--model` 항목)를 남긴다.
- 앱은 목록을 얻으려고 외부 명령을 실행하거나 네트워크를 호출하지 않는다. 새 파일에 `invoke`·`Command`·
  `fetch`가 없어야 한다.

### 2. model 필드를 선택 UI로 (R1)

- 값이 목록 안에 있으면 선택 컨트롤로 렌더한다. 기본 상태에서 타이핑이 필요해서는 안 된다.
- 선택지에는 값 자체(`opus`)가 그대로 보여야 한다. 설명 문구를 덧붙이는 것은 무방하나 값이 가려지면 안 된다.
  사용자가 `HEARTBEAT.md`를 직접 열었을 때 화면과 파일을 대조할 수 있어야 한다.
- 접근성 라벨 규약을 유지한다. 선택 컨트롤의 이름은 현행과 같은 `"<잡 이름> 모델"`(예: `개발자 모델`)이다.
  기존 테스트가 이 이름으로 필드를 찾는다(`SettingsView.test.tsx:148`).
- 고르기만 해서는 파일이 바뀌지 않는다. 기존 저장 버튼과 확인 화면을 그대로 거친다.
- `interval`·`maxPer`의 렌더와 검증은 손대지 않는다.

### 3. 직접 입력 경로 (R3)

- 선택지 안에 직접 입력 항목을 둔다. 고르면 값을 적을 수 있는 칸이 나타난다.
- 직접 입력 칸의 접근성 이름은 선택 컨트롤과 겹치지 않게 한다(예: `개발자 모델 직접 입력`).
  `getByLabelText("개발자 모델")`이 계속 선택 컨트롤 하나만 가리켜야 한다.
- 검증 규칙은 현행과 같다: 비어 있지 않고 공백 없는 한 줄(`/^\S+$/`). 위반 시 파일에 쓰지 않고 그 입력
  위치에 사유를 표시한다(`aria-invalid`, `aria-describedby`). 현행 메시지 문구를 바꾸지 않는다.
- 직접 입력 경로 옆에 위험을 밝힌다: 앱은 모델명이 실제로 존재하는지 확인하지 못한다. 값이 틀리면 클로드가
  요청을 보내기 전에 종료하고 하트비트는 그 잡을 매 주기 실패로 기록하는데, 실행 쿼터는 실패해도 이미
  차감된 뒤다.
- 직접 입력 여부는 값에서 유도하지 말고 별도 상태로 다룬다. 값에서 유도하면 사용자가 직접 입력으로
  `opusX`를 적는 도중 `opus`를 지나는 순간 입력 칸이 사라진다. 다만 그 상태가 설치 요청 payload에 섞이면
  안 된다(0번 제약).

### 4. 목록 밖 값의 보존 (R3)

- 파일에 기록된 `model`이 목록에 없으면, 해당 필드는 직접 입력 상태로 열리고 파일의 값이 그대로 채워진다.
- 앱이 그 값을 목록 안의 값으로 바꾸지 않는다. 사용자가 저장하지 않는 한 파일의 값은 그대로다.
- 화면 진입과 2.5초 자동 새로고침은 여전히 전역 파일을 쓰지 않는다. 목록 밖 값을 화면에 열어 보여주는 것도
  읽기일 뿐이다 (R4).
- 파일에 값이 없는(미설치) 잡은 기존 기본값으로 시작한다. `roleJobDefaults`의 값과 정의 위치는 그대로 둔다.

### 5. 테스트

- 선택지에 `opus`·`sonnet`·`haiku`·`fable`이 값 그대로 노출된다.
- 타이핑 없이 선택 값을 바꿔 저장하면 그 값이 설치 요청에 실린다.
- 직접 입력을 골라 정식 모델명(예: `claude-opus-5`)을 적어 저장하면 그 값이 그대로 설치 요청에 실린다.
- 직접 입력 값이 공백을 포함하거나 비어 있으면 그 입력 위치에 사유가 표시되고, 확인 화면이 열리지 않으며
  설치 함수가 호출되지 않는다.
- 파일 값이 목록 밖(`claude-opus-5`)이면 그 필드가 직접 입력 상태로 열리고 값이 그대로 보인다.
- 직접 입력 옆에 검증 불가·매 주기 실패·쿼터 소모 경고 문구가 있다.
- 연동 카드 안에 잡이 여럿이면 각 잡의 모델 필드가 서로 독립적으로 동작한다.
- **기존 검증 테스트의 처리.** `SettingsView.test.tsx:268`의 `it.each`에는 `["개발자 모델", "claude opus", ...]`
  행이 있다. 선택 컨트롤에는 목록 밖 문자열을 그대로 넣을 수 없으므로 이 행은 지금 형태로 유지되지 않는다.
  그 행이 덮던 것(잘못된 `model` 값 → 입력 위치에 사유 표시 + 아무것도 쓰지 않음)을 직접 입력 경로 테스트로
  옮기고, 어떤 케이스도 사라지지 않았음을 보고서에 테스트 목록 전후로 적는다. 기획서 완료 조건 10의
  "삭제되거나 비활성화된 테스트가 없다"를 사용자가 QA에서 판단할 수 있어야 한다. 테스트를 임의로 지우거나
  `skip` 처리하지 않는다.

## 완료 조건

1. 연동 관리 UI에 존재하는 모든 잡의 `model` 필드가 선택 UI로 표시되고, 목록에서 고르는 것만으로 유효한
   모델을 지정해 저장까지 마칠 수 있다. (기획서 완료 조건 1)
2. 선택지에 `opus`·`sonnet`·`haiku`·`fable`이 값 그대로 노출되고, 고른 값이 화면 표기 그대로 파일에 기록된다.
   (기획서 완료 조건 2)
3. 지원 모델 목록이 앱 안 한 곳에만 정의되어 있고, 그 지점에 갱신 방법과 확인처가 주석으로 남아 있다.
   (기획서 완료 조건 3)
4. 목록에 없는 모델을 직접 입력으로 저장할 수 있고, `HEARTBEAT.md`에 그 값이 그대로 기록된다.
   (기획서 완료 조건 4)
5. 직접 입력 값이 비어 있거나 공백을 포함하면 파일에 쓰이지 않고 입력 위치에 사유가 표시된다. 두 경우
   각각에 대한 테스트가 있고 통과한다. (기획서 완료 조건 5)
6. 파일에 목록 밖 `model` 값이 있는 상태에서 설정 화면을 열면 해당 필드가 직접 입력 상태로 그 값을 그대로
   보여준다. (기획서 완료 조건 6)
7. 6번 상황에서 아무것도 저장하지 않으면 자동 새로고침을 여러 번 거쳐도 `HEARTBEAT.md`가 변하지 않는다.
   (기획서 완료 조건 7)
8. 직접 입력 경로 옆에 앱이 모델명을 검증하지 못한다는 점과 잘못된 값의 결과(매 주기 실패, 쿼터 소모)가
   표시된다. (기획서 완료 조건 8)
9. 같은 모델 값으로 다시 저장하면 파일이 변하지 않는다. (기획서 완료 조건 9)
10. SPEC-002 완료 조건 1~12에 대응하는 기존 테스트가 모두 통과하고, 삭제되거나 비활성화된 케이스가 없다.
    바뀐 테스트는 보고서에 전후로 적는다. (기획서 완료 조건 10)
11. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다. (기획서 완료 조건 11)

## 범위 밖

- `interval`·`max_per` 필드의 UI 변경. 기획서 제외 범위다.
- 백엔드 `model` 검증 규칙 변경. 프론트는 예방이고 백엔드는 방어선이다.
- 빈 `model`(CLI 기본 모델) 지원. 기획서 확인 필요 2번이 제외로 승인됐다.
- 앱이 모델 목록을 외부 명령이나 네트워크로 조회하는 기능.
- 모델별 비용·속도·컨텍스트 한도 표시.
- 잘못된 모델로 실패한 잡의 사유를 하트비트 로그에서 읽어 표시하는 기능. SPEC-002가 제외한 관측 기능 확장이다.
- dream 카드와 dream 잡 설치 UI 자체. SPEC-003 TASK-011·TASK-012 담당이다. 이 작업은 그 시점에 화면에 있는
  잡의 `model` 필드만 다룬다.

## 참고 사실

확인 시점 2026-08-02. 추정 없이 실측한 값이다.

- 현재 `model` 입력은 `SettingsView.tsx:62`의 `editableFields` 루프가 `interval`·`maxPer`와 같은 `<input>`으로
  렌더한다(`SettingsView.tsx:376`). 이 루프에서 `model`만 갈라내는 것이 이 작업의 진입점이다.
- 프론트 검증은 `SettingsView.tsx:91`의 `fieldRules.model`(`/^\S+$/`), 백엔드는
  `heartbeat_jobs.rs:323`의 `is_model`(비어 있지 않고 공백 없음)이다. 두 규칙은 같은 값을 통과시킨다.
- `claude --help`의 `--model`은 "별칭(예: `fable`, `opus`, `sonnet`) 또는 정식 모델명(예: `claude-fable-5`)"을
  받는다고 기술한다. CLI 바이너리 문자열에는 `fable`·`haiku`·`opus`·`sonnet`이 모두 있다.
- 같은 바이너리에 `opusplan` 문자열도 있다. 기획서 R2가 목록을 별칭 네 개로 고정했으므로 이번 작업에서
  임의로 추가하지 않는다. 추가 여부는 별도 아이디어로 다룰 사항이다.
- 관리 블록에 현재 기록된 역할 잡 3종의 `model`은 모두 `opus`다. 목록 밖 값 상태는 손으로 만들어야 한다.
- 하트비트는 `model` 값을 `claude --model`에 그대로 넘기고, 프로세스를 띄운 직후 종료 코드를 확인하기 전에
  쿼터를 차감한다. 그래서 틀린 모델명은 매 주기 쿼터만 태우고 화면에는 "실패" 배지만 남는다.
- 설치 요청 타입은 프론트 `types.ts:126`의 `RoleJobRequest`와 백엔드
  `heartbeat_service.rs:53`의 `RoleJobRequest`가 짝을 이룬다. 필드가 늘면 양쪽이 함께 어긋난다.
