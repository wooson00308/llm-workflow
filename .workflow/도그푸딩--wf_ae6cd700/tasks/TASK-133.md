# 열기와 수동 새로 고침에서만 관리 규칙을 동기화한다

## 결정권자 요약

최근 프로젝트와 선택한 폴더를 열 때 관리 규칙을 한 번 동기화하도록 연결했다.
사용자가 상단 새로 고침을 눌러도 프로젝트 조회 뒤 같은 동기화를 수행한다.
2.5초 자동 조회는 계속 읽기만 하며 관리 파일을 쓰는 명령을 부르지 않는다.
동기화 실패는 프로젝트 조회 실패와 별도로 보존해 읽은 프로젝트와 최근 기록을 유지한다.
네 가지 결과와 자산별 버전, 실패 이유, 복구 위치가 화면 계층에 그대로 전달된다.
프런트엔드 검사 710개와 타입 검사, 배포 빌드가 모두 통과했다.
설정 화면 표시는 후속 작업에서 추가하며 이 작업은 사용자 확인을 기다린다.

## 목적

SPEC-047의 R1, R2, R4 프런트엔드 상태 부분과 완료 조건 1, 2, 4, 6, 7을 처리한다. TASK-132가 만든
별도 동기화 명령만 사용하며 프로젝트 조회 명령의 의미를 바꾸지 않는다.

## 호출 순서

### 프로젝트를 열 때

최근 프로젝트 선택과 폴더 선택은 다음 순서를 따른다.

1. 프로젝트를 읽는다.
2. 읽은 결과를 즉시 현재 프로젝트로 보존하고 최근 프로젝트 목록을 갱신한다.
3. 초기화된 현재 문서 규격이면 관리 규칙 동기화를 한 번 호출한다.
4. 동기화 결과를 관리 규칙 전용 상태에 기록한다.

프로젝트 조회가 실패하면 동기화를 호출하지 않는다. 동기화만 실패하면 2번의 프로젝트 상태를 지우지
않는다. 초기화되지 않은 프로젝트, 마이그레이션이 필요한 프로젝트, 앱보다 새로운 문서 규격에는
동기화를 호출하지 않는다.

### 사용자가 새로 고침을 누를 때

현재 프로젝트를 다시 읽은 뒤 위와 같은 조건으로 동기화한다. 호출이 끝날 때까지 기존 새로 고침 진행
표시를 유지한다. 동기화 결과는 성공과 실패 모두 마지막 결과로 남긴다.

### 2.5초 자동 조회

자동 조회는 기존 `inspect`와 연동 조회만 호출한다. 관리 규칙 동기화 메서드를 호출하지 않는다. 자동
조회 성공이나 실패가 마지막 동기화 결과와 오류를 지우지 않는다.

## 상태 계약

프로젝트 조회 상태와 별도로 다음 상태를 둔다.

- 동기화 진행 여부
- 마지막 구조화 결과
- 명령 호출 자체가 실패했을 때의 오류

백엔드가 돌려준 `current`, `updated`, `retry_required`, `conflict`를 다른 값으로 합치지 않는다. 자산별
설치 버전과 앱 제공 버전, 실패 자산과 이유를 그대로 보존한다. 화면 문구를 이 훅에서 만들지 않는다.

## 변경 범위

- `types.ts`: 관리 규칙 동기화 결과와 전용 화면 상태, 게이트웨이 메서드 계약.
- `tauriProjectGateway.ts`: TASK-132의 별도 명령 호출.
- `useProjectWorkspace.ts`: 명시적 열기·수동 새로 고침과 자동 조회의 호출 경로 분리, 전용 상태 수명.
- `useProjectWorkspace.test.ts`: 호출 횟수, 순서, 실패 격리, 자동 조회 무호출 회귀 검사.

## 손대지 않는 것

- 백엔드 자산 설치와 잠금 구현
- 설정 카드와 공통 오류 문구
- 기존 프로젝트 문서 조회 주기
- 사용자 정의 규칙 편집과 저장

## 완료 조건

1. 폴더 선택과 최근 프로젝트 열기에서 현재 문서 규격 프로젝트를 읽은 뒤 동기화를 각각 한 번 호출한다.
2. 프로젝트 조회가 실패하거나 프로젝트가 현재 문서 규격이 아니면 동기화를 호출하지 않는다.
3. 수동 새로 고침은 프로젝트를 다시 읽은 뒤 동기화를 한 번 호출하고, 두 동작이 끝날 때까지 진행
   상태를 유지한다.
4. 2.5초 자동 조회를 여러 번 실행해도 동기화 호출 수가 늘지 않는다.
5. 동기화 실패 후에도 읽기에 성공한 프로젝트와 최근 프로젝트 기록이 유지된다.
6. 동기화 오류와 마지막 결과는 일반 프로젝트 오류와 별도이며 자동 조회가 지우지 않는다.
7. 전체 결과 네 종류와 자산별 버전, 실패 이유를 손실 없이 화면 계층에 제공한다.
8. 기존 프로젝트 열기, 최근 프로젝트 저장, 문서 자동 조회, 연동 조회 동작이 유지된다.
9. 기존 자동 검사를 삭제하거나 약화하지 않고 프런트엔드 전체 검사가 통과한다.

## 검증 절차

1. 게이트웨이 호출 기록으로 폴더 선택, 최근 프로젝트, 수동 새로 고침의 조회 후 동기화 순서를
   확인한다.
2. 가짜 시간을 2.5초씩 여러 번 진행해 프로젝트 조회는 반복되지만 동기화 호출은 늘지 않는지
   확인한다.
3. 충돌, 재시도 필요, 명령 거절을 각각 반환해 프로젝트가 남고 전용 상태만 바뀌는지 확인한다.
4. 자동 조회를 진행한 뒤에도 마지막 동기화 결과와 오류가 유지되는지 확인한다.
5. `npm run check`를 실행한다.

## 범위와 선행

TASK-132가 먼저 완료돼야 한다. 이 작업은 그 명령과 결과 계약을 소비한다. TASK-134는 이 작업이
제공하는 상태를 설정 화면과 공통 오류 영역에 표시한다.

SPEC-048도 같은 게이트웨이와 프로젝트 상태 훅을 수정할 가능성이 높다. 그 기획서에서 파생되는 작업이
이 문서의 `scope_files`와 겹치면 TASK-133 완료 뒤에 시작한다.

## 확인 동선

1. 현재 문서 규격 프로젝트를 폴더 선택과 최근 프로젝트 목록에서 각각 열면 프로젝트가 먼저 표시되고
   관리 규칙 동기화가 한 번 실행된다.
2. 상단 새로 고침을 누르면 프로젝트 조회 뒤 동기화가 한 번 더 실행되며, 두 단계가 끝날 때까지 진행
   표시가 유지된다.
3. 충돌이나 잠금 재시도, 명령 오류가 발생해도 열린 프로젝트와 최근 프로젝트 기록이 사라지지 않는다.
4. 자동 검사에서 2.5초 조회를 세 번 진행해도 동기화 호출은 추가되지 않고 마지막 결과가 유지됐다.
5. 프런트엔드 전체 710개 검사와 타입 검사, 배포 빌드가 통과했다. 확인 도장은 이 호출 시점과 오류
   격리 계약을 승인한다는 뜻이다.
