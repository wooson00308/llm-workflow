# 에이전트 화면에서 실행 계획과 큐를 확인하고 제어한다

## 결정권자 요약

실행 계획과 큐의 안전 계약과 프로젝트별 상태 복원은 그대로 유지했다.
정상 큐는 자동 갱신만 사용하고 수동 조회는 오류 복구 행동으로 한정했다.
세 역할 입력은 역할 선택 뒤 한 폼만 보여주며 빈 실행 목록은 한 문장으로 합쳤다.
새 배정 제어는 접힌 프로젝트 보조 제어로 낮추고 계획 확인만 주 행동으로 남겼다.
실행 중에는 분 단위 진행 시간을, 종료 뒤에는 더 늘지 않는 고정 소요 시간을 보여준다.

## 목적

TASK-S051-08의 실행 plan·start·status·pause·cancel·retry·logs 계약을 에이전트 화면에 연결한다.
사용자가 유료 CLI 세션이 몇 개 시작되는지 확인한 뒤에만 실행하고, runtime의 영속 상태를 프로젝트별
운영 대시보드로 보여준다.

## 시작 흐름

1. 역할마다 자동 배정 또는 수동 배정을 고른다. 자동이 기본이다.
2. 수동 배정은 슬롯을 추가하고 역할과 대상 문서를 선택한다. 자유 입력만 제공하지 않고 runtime이
   반환한 후보와 제외 사유를 함께 보여준다. 잘못된 식별자는 실행 전에 막는다.
3. 자동 배정 결과가 0건이면 제외 사유를 보여주고 같은 역할의 수동 배정 진입점을 제공한다. 수동
   배정은 안전 규칙을 우회하지 않는다는 설명을 함께 둔다.
4. 한 번 실행과 반복 실행을 명확히 구분한다. 반복 수동 배정은 지정 목록 이후 자동으로 바뀌지 않는다는
   설명을 붙인다.
5. `계획 확인`을 누르면 provider, 역할별 최대 인원, 프로젝트·기기 제한, 실제 시작 수, 대상 목록,
   반복 여부, 적용 프로젝트, 동시에 여러 유료 세션이 시작될 수 있음을 보여준다.
6. Claude API 과금 경로 위험이 있으면 확인 항목을 별도로 요구한다. 토큰이나 키 값은 보여주지 않는다.
7. 최신 plan의 확인 버튼만 start를 호출한다. stale plan 응답은 실패로 끝내지 않고 최신 계획을 다시
   확인하도록 유도한다.

## 상태 대시보드

- 상단에는 프로젝트의 새 배정 활성·일시 정지, 실행 중 수, 대기 수, 최근 결과, 기기 슬롯 사용량을
  보여준다.
- 세 역할 행은 설정값과 함께 현재 실행 수, 대기 수, 마지막 결과를 보여준다. 설정 표와 상태 표가
  서로 다른 역할 순서나 provider를 표시하지 않는다.
- 목록은 예약 중, 대기, 실행 중, 일시 정지, 성공, 실패, 취소됨, 복구 필요를 구분한다.
- 실행 중 항목은 프로젝트, 역할, provider, 대상 문서, 시작 시각, 분 단위 진행 시간, 취소 행동을
  보여준다. 1분이 되기 전에는 초를 세지 않고 `1분 미만`으로 표시한다.
- 최근 종료 항목은 결과와 `finishedAt - startedAt`으로 고정한 소요 시간, 종료 원인, 이전 실행과의
  재시도 연결, 로그 진입점을 보여준다. 1분 미만으로 끝난 실행만 초 단위로 표시하고 종료 시각이 없는
  구형 기록은 현재 시각으로 대신 계산하지 않고 기록 없음으로 표시한다.
- 대기 사유는 대상 없음, 마이그레이션 잠금, 실행 한도 소진, 역할·프로젝트·기기 슬롯 부족,
  provider 인증·사용 제한, 프로젝트 일시 정지를 구분한다.
- 구조화 이벤트가 도착하면 cursor 기반으로 진행 상황을 갱신한다. 전체 prompt와 비밀값은 표시하지
  않는다.

## 제어 흐름

- 프로젝트 일시 정지는 새 배정만 멈춘다는 문구를 확인한 뒤 실행한다. 실행 중 항목은 그대로 남는다.
- 취소는 대상, 역할, provider, 프로세스 트리와 lease 정리 영향을 보여주는 plan을 먼저 연다. 사용자
  확인 뒤에만 적용한다.
- 취소 결과는 프로세스 종료와 상태 정리 결과를 따로 보여준다. 일부 실패를 성공 배지로 접지 않는다.
- 재시도는 이전 실패를 보여주고 새 plan 확인을 거친다. 같은 실행 식별자를 재사용하지 않는다.
- 다른 프로젝트의 실행은 현재 화면 목록과 제어 대상에 섞이지 않는다. 기기 전체 사용량은 별도 요약으로
  구분한다.

## 상태 소유와 갱신

- 실행 계획, 실행 요청 진행, 마지막 오류, 취소 plan, 로그 cursor는 `useProjectWorkspace`가 프로젝트
  식별자별로 소유한다.
- 상태 조회는 앱이 열려 있을 때 주기적으로 수행하고 프로젝트 전환 시 즉시 새 프로젝트를 조회한다.
  앱을 다시 열었을 때는 메모리 복원 없이 runtime 상태를 첫 원천으로 사용한다.
- 화면을 떠났다가 돌아와도 앱이 시작한 조작의 진행 상태가 사라지지 않는다.

## 손대지 않는 것

- 런타임 dispatcher와 provider 프로세스
- 역할 설정 저장과 runtime 설치
- Dream 큐와 Dream 실행 UI
- 자유 대화와 원격 실행
- 실행 중 작업의 무확인 자동 취소

## 완료 조건

1. 프로젝트 메뉴에서 에이전트 화면을 열 수 있고, 자동·수동 배정과 한 번·반복 실행의 네 조합을
   선택해 서로 다른 의미를 확인할 수 있다. 최상위 조립부는 작업 공간이 반환한 에이전트 상태와 조작을
   화면 껍데기에 전달한다.
2. 시작 확인 화면이 provider, 역할별 최대 인원, 실제 시작 수, 대상 목록, 반복 여부, 적용 프로젝트,
   유료 세션 위험을 보여준다.
3. 역할 상한 3, 프로젝트 상한 5, 기기 남은 슬롯 4, 대상 2의 plan에서 실제 시작 수 2와 대상 둘이
   보인다.
4. 대상 없음이나 마이그레이션 잠금에서는 확인 화면에 시작 수 0과 사유가 보이고 provider 시작 버튼이
   실행되지 않는다.
5. 자동 배정 대상이 0건이면 제외 사유와 수동 배정 진입점이 보이며, 수동 대상도 같은 안전 검증을
   통과해야 한다.
6. 같은 수동 대상 중복, 활성 lease, 완료·거절 대상, 잘못된 식별자는 실행 전에 막히고 사유가 보인다.
7. stale plan은 provider를 시작하지 않고 최신 계획 재확인을 요구한다.
8. 한 번 실행은 최초 목록 뒤 종료되고 반복 자동 실행은 빈 슬롯에 새 대상을 보충하는 상태 변화가
   화면에 반영된다.
9. 프로젝트 일시 정지는 새 배정만 멈추며 실행 중 항목과 다른 프로젝트 상태는 유지된다.
10. 각 역할 행이 provider, model, 실행 방식, 최대 인원, 현재 실행 수, 대기 수, 마지막 결과를 함께
    표시한다.
11. 실행 중 항목이 프로젝트, 역할, provider, 대상, 시작 시각, 취소 행동과 시작부터 현재까지의
    `진행 시간`을 표시한다. 진행 시간은 초 단위로 움직이지 않고 `1분 미만` 또는 온전한 분 수로만
    갱신한다.
12. 성공, 실패, 취소됨, 복구 필요 항목은 `finishedAt - startedAt`을 `소요 시간`으로 표시하고 시간이
    지나거나 화면이 다시 렌더되어도 값이 늘지 않는다. 1분 미만 종료만 초 단위이며 `finishedAt`이 없는
    구형 종료 기록은 `소요 시간 기록 없음`으로 고정한다. 실행 한도·인증·사용 제한·대상 없음 사유도
    서로 다른 문구다.
13. 취소는 확인 전 실행되지 않고 부분 정리 실패를 성공으로 표시하지 않는다.
14. 재시도는 이전 실패와 새 실행을 함께 보여주며 중복 실행을 만들지 않는다.
15. 앱을 닫았다 다시 열면 runtime의 실행 중·대기·최근 종료 상태와 로그 cursor에서 복원된다.
16. 구조화 이벤트를 표시해도 인증 토큰, API 키, 전체 prompt가 화면과 브라우저 로그에 나타나지 않는다.
17. Dream이 실행 모드와 provider와 큐 목록에 나타나지 않는다.
18. 기존 화면 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. 자동·수동, 한 번·반복, 상한 최솟값, 대상 0, 마이그레이션 잠금 plan fixture를 각각 렌더하고
   start 호출 여부를 검사한다.
2. 수동 중복·lease·완료·거절·잘못된 식별자와 stale plan을 사용자 이벤트로 재현한다.
3. 모든 상태와 대기 사유 payload를 표 기반 검사로 렌더해 문구와 행동이 섞이지 않는지 확인한다.
4. 프로젝트 둘을 전환하며 pause·resume·cancel·retry를 수행해 게이트웨이 요청의 project ID를
   대조한다.
5. 화면을 언마운트·재마운트하고 앱 초기 상태를 다시 만들어 runtime 조회 결과가 상태를 복원하는지
   확인한다.
6. 비밀 문자열과 전체 prompt가 든 가짜 이벤트를 주입해 DOM과 console 출력에서 검색되지 않는지
   확인한다.
7. `npx vitest run src/features/projects/components/agents/AgentRuntimeView.test.tsx src/features/projects/application/useProjectWorkspace.test.ts src/features/projects/components/WorkspaceShell.test.tsx`를 실행한다.
8. `rg -n 'agentRuntime=|agentRuntimeActions=' src/App.tsx`로 작업 공간의 에이전트 상태와 조작이
   `WorkspaceShell`에 모두 전달되는지 확인한다.
9. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`을 실행한다.
10. Rust `RunSummary`가 `finishedAt`이 있는 응답과 없는 구형 응답을 모두 역직렬화하고 다시 camelCase로
    전달하는지 검사한다.
11. 가짜 시각을 전진시키며 실행 중 기록은 분 경계에서만 `진행 시간`이 바뀌고, 종료 기록은
    `finishedAt` 기준 `소요 시간`이 그대로이며 1분 미만 종료만 초 단위인지 검사한다.
12. `finishedAt`이 없는 종료 fixture를 렌더해 현재 시각을 사용하지 않고 `소요 시간 기록 없음`을
    표시하는지 검사한다.

## 범위 사전 검사

- `src/App.tsx`를 열어 `useProjectWorkspace`의 반환값을 `WorkspaceShell`에 조립하는 경로를 확인했다.
  현재 작업 공간은 에이전트 상태와 조작을 모두 반환하지만 화면 껍데기 호출에는 두 값이 빠져 있다.
  이 파일을 범위에 추가하면 누락된 두 전달값을 같은 작업에서 연결할 수 있다.
- `src/features/projects/application/useProjectWorkspace.ts`는 에이전트 상태와 조작을 만들고 반환하며 이미
  선언 범위에 있다. 대시보드 상태 소유와 최상위 연결에 필요한 변경을 이 범위 안에서 처리할 수 있다.
- `src/features/projects/components/WorkspaceShell.tsx`도 확인했지만 범위에는 추가하지 않았다.
  TASK-S051-09가 두 값을 받는 계약과 메뉴·화면 노출 조건을 이미 구현했으므로 이번 작업은 그 파일을
  바꾸지 않고 완성할 수 있다. 같은 이유로 기존 진입점 검사를 재실행하되 검사 파일도 수정하지 않는다.
- 나머지 선언 파일은 실행 계획·상태·제어의 타입, 게이트웨이, 상태 소유, 화면, 스타일과 검사를 모두
  포함한다. 따라서 추가한 최상위 조립 파일과 함께 완료 조건 전체를 구현하고 검증하기에 충분하다.
- `src-tauri/src/domain/agent_runtime.rs`의 `RunSummary`를 열어 런타임 상태 행의 `startedAt`은 받지만
  선택 필드 `finishedAt`은 선언하지 않아 버리는 것을 확인했다. 이 파일을 범위에 추가해 nullable
  종료 시각과 camelCase 직렬화 검사를 같은 소유 타입에서 닫는다.
- `src-tauri/src/application/agent_runtime_status_service.rs`는 상태 응답의 각 행을 `RunSummary`로 generic
  serde 역직렬화하고, `src-tauri/src/commands/agent_runtime.rs`는 `QueueSnapshot`을 그대로 반환한다.
  두 파일은 `RunSummary`에 필드가 생기면 별도 조립 없이 전달하므로 확인만 했고 범위에 추가하지 않았다.
- `src-tauri/src/infrastructure/agent_runtime_process.rs`의 `read_state`는 런타임 data를 raw JSON으로
  반환한다. 필드를 선별하지 않으므로 변경하지 않는다. 런타임 v0.8.3이 새 실행과 기존 종료 기록 모두에
  `finishedAt`을 제공하는 것은 `REPORT-TASK-S051-10-DEV-2.md`의 실제 응답 검사로 확인했다.
- 값 경로: 완료 조건 11의 `startedAt`은 런타임 상태 → `agent_runtime_process::read_state`(무변경 raw JSON)
  → `AgentRuntimeStatusService::inspect`(무변경 generic serde) → `RunSummary.started_at`(기존) →
  `inspect_agent_runs`(무변경 직렬화) → `tauriProjectGateway.inspectAgentRuns`(무변경) →
  `useProjectWorkspace` 큐 상태(무변경) → `AgentRunSummary.startedAt`(기존) →
  `AgentRunDashboard`(편집)로 이어진다. 화면만 현재 시각과 비교해 `진행 시간`을 온전한 분으로 표시한다.
- 값 경로: 완료 조건 12의 `finishedAt`은 런타임 v0.8.3 상태 → `read_state`(무변경 raw JSON) →
  `AgentRuntimeStatusService::inspect`(무변경 generic serde) → `RunSummary.finished_at`(편집) →
  `inspect_agent_runs`(무변경 camelCase 직렬화) → `tauriProjectGateway.inspectAgentRuns`(무변경) →
  `useProjectWorkspace` 큐 상태(무변경) → `AgentRunSummary.finishedAt`(편집) →
  `AgentRunDashboard`(편집)로 이어진다. 화면은 시작·종료 시각 차이만 사용하고 종료 시각이 없으면 현재
  시각을 대입하지 않는다.

## 확인 동선

1. 런타임 v0.8.3을 묶은 최신 로컬 앱에서 프로젝트를 열고 `에이전트`의 `작업` 탭으로 이동한다.
2. 실행 중인 기록은 시작 시각 옆에 `진행 시간 1분 미만` 또는 온전한 분 수만 보이고 초 숫자가 계속 움직이지 않아야 한다.
3. `최근 종료`의 성공·실패·취소·복구 필요 기록은 시작 시각 옆에 `소요 시간`이 보인다. 1분 미만 종료만 초 단위이고, 1분 이상은 온전한 분 수로 보이면 정상이다.
4. 종료 기록을 본 채 기다리거나 다른 탭을 다녀온 뒤 돌아온다. 같은 기록의 소요 시간이 늘어나지 않아야 한다.
5. 종료 시각이 없는 구형 런타임 fixture에서는 현재 시각으로 추정한 큰 숫자 대신 `소요 시간 기록 없음`이 보여야 한다.
6. 대상 0, API 과금 위험, stale plan, 취소, 재시도, 구조화 로그의 기존 확인·비밀값 차단 계약이 그대로 동작하면 정상이다.

## 막힌 사유

- 막힌 지점: 런타임 v0.8.3 상태 응답은 종료 실행에 `finishedAt`을 싣지만 `src-tauri/src/domain/agent_runtime.rs`의 `RunSummary`가 해당 필드를 선언하지 않아 Tauri 역직렬화 단계에서 버린다. 프런트만 수정하면 `finishedAt - startedAt`을 계산할 수 없으며 이 Rust 파일은 현재 `scope_files`에 없다.
- 필요한 해결: 아키텍트가 `src-tauri/src/domain/agent_runtime.rs`를 `scope_files`에 추가하고 `RunSummary.finished_at: Option<String>`을 앱 타입과 화면까지 전달하는 값 경로 및 직렬화 회귀 검사를 완료 조건에 명시해야 한다.
- 재개 조건: Rust `RunSummary` 소유 파일이 선언 범위에 포함되어 런타임의 선택 필드가 `AgentRunSummary.finishedAt`까지 손실 없이 전달될 수 있으면 같은 수정 요청으로 개발을 재개한다.
