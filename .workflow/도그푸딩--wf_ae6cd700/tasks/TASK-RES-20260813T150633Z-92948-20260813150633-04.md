# 품질 확인 세션에서 항목을 하나씩 확인하고 중단해도 이어가게 만든다

## 결정권자 요약

### 제안

기능을 연 뒤 확인할 항목을 짧은 목록으로 두고, 오른쪽에는 지금 볼 항목 하나만 크게 보여 준다. 각 항목에
확인함 또는 문제 있음을 남기고, 남긴 내용은 화면을 떠나도 기기에 남아 이어서 확인할 수 있게 한다.

### 현재

기능을 열면 작업 제목과 짧은 발췌가 단계 목록으로 나열될 뿐이다. 자세히 보거나 문제를 적으려면 작업
상세로 이동해야 하고, 돌아오면 어디까지 읽었고 무엇을 적고 있었는지 표시가 없다. 자동 검사만 확인하면
되는 항목은 목록에서 아예 빠진다.

### 변경 후

기능의 품질 확인 대기 작업이 하나도 빠짐없이 항목으로 남는다. 항목마다 확인 전, 확인함, 문제 있음, 다시
확인 필요 중 하나가 평문으로 붙고, 진행률이 늘 보인다. 확인 도중 대상 작업이 바뀌면 그 항목만 다시 확인
필요로 바뀐다.

### 사용자 결과

사용자는 화면을 잃지 않고 항목을 순서대로 검사한다. 문제가 있으면 그 항목에 바로 사유를 남기고, 다른
화면으로 갔다가 돌아오거나 앱을 다시 열어도 남긴 내용과 위치에서 이어서 확인한다.

### 영향 범위

- 변경: 기능을 연 뒤의 확인 항목 목록과 현재 항목 본문, 항목별 결과 선택과 문제 메모, 기기에 남는 중간 검토
- 유지: 작업 문서와 결정 기록, 기능 묶음 판정 기준, 대기열 화면, 개발 화면과 오늘 화면의 진입점

### 비용과 위험

이 단계에서 남긴 결과는 아직 정식 결정이 아니다. 기기에만 남고 작업 문서와 결정 기록에는 닿지 않으며,
제출은 뒤따르는 작업이 붙인다. 사용자가 남긴 내용을 정식 결정으로 오해하지 않도록 화면이 그 사실을
말해야 한다.

### 결정 요청

QA에서는 그 기능의 품질 확인 대기 작업이 모두 항목으로 보이는지, 자동 근거 항목을 접어도 제목과 상태와
건수가 남는지, 확인함은 메모 없이 되고 문제 있음은 사유를 요구하는지, 다른 화면으로 갔다가 돌아와도
남긴 내용이 그대로인지를 본다.

## 범위 사전 검사

이 작업이 다루는 값은 넷이다. 확인 항목 목록, 현재 항목의 확인 동선 본문, 항목별 결과와 메모, 그리고
대상 작업이 검토 시작 뒤 바뀌었는지의 판정이다. 현재 코드를 열어 각 값의 경로를 확인했다.

- 값 경로: 완료 조건 1·2의 항목 목록은 앞선 작업이 만든 `src/features/projects/domain/qaReview.ts`가
  돌려주는 확인 항목 목록에서 온다. 그 목록은 이미 자동 근거 여부를 항목의 값으로 담고 목록에서 빼지
  않으므로 도메인 모듈은 편집하지 않는다. 소비하는 자리는 이 작업이 만드는
  `src/features/projects/components/qa/QaSessionView.tsx`이고, 그 화면을 붙이는 자리는 앞선 작업이 만든
  `src/features/projects/components/qa/QaWorkbench.tsx`의 기능 열림 분기다. 두 화면 파일이 편집 대상이다.
- 값 경로: 완료 조건 3의 확인 동선 본문은 발췌가 아니라 절 전체가 필요하다. 값을 만드는 자리는 개발자가
  쓴 작업 문서의 확인 동선 절이고, 읽어 오는 자리는 `WorkspaceShell.tsx`가 이미 아래로 내려주고 있는 작업
  문서 읽기 통로이며, 잘라 내는 자리는 `src/features/projects/domain/documentSections.ts`의 `splitSection`이다.
  이 함수는 본문과 제목 문자열을 받아 절을 그대로 돌려주므로 편집하지 않는다. 개발 화면이 같은 방식으로
  확인 동선 절을 잘라 쓰는 선례가 이미 있어 새 통로도 새 필드도 만들지 않는다. 작업 문서 읽기 통로는
  앞선 작업이 품질 확인 화면까지 내려놓았으므로 껍데기 화면 파일은 편집하지 않는다.
- 값 경로: 완료 조건 4·5·6의 항목별 결과와 메모는 이 화면에서 생겨 기기 저장소까지 간다. 값을 만드는
  자리는 `QaSessionView.tsx`의 결과 선택과 메모 입력이고, 담아 두는 자리는 앞선 작업이 만든
  `src/features/projects/infrastructure/browserQaReviewDraftStore.ts`다. 그 저장소는 기능별 항목 결과와
  메모와 항목별 갱신 시각을 이미 담을 수 있으므로 편집하지 않는다. 이 작업은 읽고 쓰는 쪽만 만든다.
- 값 경로: 완료 조건 7의 다시 확인 필요 판정은 두 값을 비교해 만든다. 한쪽은 저장소에 담아 둔 항목별
  갱신 시각이고, 다른 한쪽은 워크플로 요약이 지금 들고 있는 작업 항목의 갱신 시각이다. 뒤쪽 값은 앱
  백엔드가 작업 문서에서 읽어 이미 화면까지 와 있고 도메인 모듈이 확인 항목에 담아 주므로, 앱 백엔드도
  도메인 모듈도 편집하지 않는다. 비교하는 자리는 `QaSessionView.tsx` 한 곳이다.
- 검토했으나 제외한 것: `src/features/projects/components/DevelopmentBoard.tsx`는 열지 않는다. 이 작업의
  어떤 완료 조건도 개발 화면을 지나지 않고, 그 화면의 확인 동선 표시는 그대로 둔다.
- 검토했으나 제외한 것: 앱 백엔드 파일은 넣지 않는다. 이 단계의 결과는 기기에만 남고 어떤 앱 명령도 부르지
  않으며, 작업 문서와 결정 기록에 닿는 것은 제출 화면을 만드는 작업의 완료 조건이다.

## 현재 상태

앞선 작업까지 마치면 품질 확인 화면은 대기열을 그리고, 기능을 열면 기능 제목과 바뀐 점과 전체 항목 수를
담은 확인 범위 설명을 보여 준다. 항목을 하나씩 확인하는 본문은 아직 없다.

기존 개발 화면의 기능 확인 화면은 확인 동선 발췌만 단계 목록으로 보여 주고, 자세히 보려면 작업 상세로
이동한다. 항목별 결과를 남길 자리는 없고 기능 전체에 메모 하나만 달 수 있다.

## 변경 범위

1. 확인 범위 설명 아래에 세션 본문을 만든다. 본문은 왼쪽의 짧은 항목 목록과 오른쪽의 현재 항목 하나로
   구성한다. 넓이가 부족하면 항목 목록을 접을 수 있는 한 열 흐름으로 바꾼다.
2. 세션 상단에 기능 이름, 바뀐 점 한 문장, 전체 항목 수와 진행률을 고정해 보여 준다. 진행률은 전체 수,
   결과를 남긴 수, 남은 수를 함께 말한다.
3. 그 기능의 품질 확인 대기 작업을 하나도 빼지 않고 항목 목록에 담는다. 확인 동선 문구를 근거로 항목을
   목록에서 없애지 않는다.
4. 자동 근거 항목은 시각적 무게를 낮추고 접을 수 있게 하되, 접힌 상태에서도 제목과 상태와 건수는 보이게
   한다. 접어도 전체 항목 수에서 빠지지 않는다.
5. 항목 상태를 확인 전, 확인함, 문제 있음, 다시 확인 필요 넷 중 하나로 평문 표시한다. 색이나 아이콘이나
   위치 하나에만 기대지 않는다.
6. 현재 항목 본문은 확인할 것, 개발자가 남긴 확인 동선과 기대 결과, 보조 정보 순서로 보여 준다. 화면 조작이
   없는 항목은 화면이 없다는 설명과 검증 결과를 같은 자리에 보여 준다.
7. 작업 원문은 보조 상세로 연다. 닫으면 같은 항목과 작성 중인 내용으로 돌아온다.
8. 현재 항목에서 확인함 또는 문제 있음 중 하나를 고른다. 확인함은 메모를 요구하지 않는다. 문제 있음은
   사유를 적어야 결과로 확정되고, 비어 있으면 그 항목의 결과가 남지 않는다.
9. 항목은 순서와 무관하게 열 수 있고, 이전과 다음 항목으로 이동할 수 있다.
10. 항목에서 고른 결과와 메모를 기기 저장소에 담는다. 함께 담는 값은 항목별 결과, 항목별 메모, 검토를
    시작한 시각, 항목별로 읽은 작업 갱신 시각이다. 작업 문서와 결정 기록에는 쓰지 않는다.
11. 다른 화면으로 이동했다가 돌아오거나 앱을 다시 열면 담아 둔 내용을 읽어 같은 항목과 같은 입력에서
    이어간다. 대기열의 그 기능 행은 시작 대신 계속으로 표시한다.
12. 임시 검토를 버리는 조작을 둔다. 실행 전에 대상 기능 이름과 사라질 항목 수를 보여 준다.
13. 담아 둔 항목별 갱신 시각과 지금의 작업 갱신 시각이 다르면 그 항목을 다시 확인 필요로 바꾼다. 그 항목의
    결과와 메모는 지우지 않고 남긴다.
14. 기능 묶음이 지금 확인할 수 있는 조건을 잃으면 담아 둔 내용을 지우지 않은 채 준비 중으로 표시하고 그
    이유를 알린다.
15. 항목 이동, 결과 선택, 메모 입력, 작업 원문 열기와 닫기를 키보드만으로 할 수 있게 한다. 초점은 현재
    항목을 따라가고, 화면 읽기 도구가 진행률과 항목 상태를 읽을 수 있게 한다.
16. 화면마다 가장 강한 행동은 하나만 둔다. 이 화면에서는 현재 항목의 결과 선택이 그 행동이다. 장식용
    그래프와 점수와 축하 효과는 넣지 않는다.

## 범위 밖

- 제출 전 검토 화면과 최종 제출
- 앱 명령 호출과 결정 문서 기록
- 부분 실패 결과 화면
- 대기열 구획 구성의 변경
- 개발 화면과 오늘 화면의 진입점 변경
- 화면 캡처와 파일 첨부

## 완료 조건

1. 기능을 열면 그 기능의 품질 확인 대기 작업이 하나도 빠짐없이 항목 목록에 있고, 전체 항목 수가 그 작업
   수와 같다.
2. 자동 근거 항목이 접힌 상태에서도 제목과 상태가 보이고 전체 건수에 포함된다. 확인 동선 문구를 근거로
   목록에서 사라지는 항목이 없다.
3. 현재 항목에 개발자가 작업 문서에 쓴 확인 동선 절의 내용이 발췌가 아닌 전체로 보인다. 앱이 그 문장을
   새로 쓰지 않는다.
4. 확인함은 메모 없이 선택되어 결과로 남는다.
5. 문제 있음은 사유가 비어 있으면 결과로 확정되지 않고, 사유를 적으면 그 항목의 결과로 남는다.
6. 다른 화면으로 이동했다가 돌아오거나 화면을 다시 그려도 항목별 결과와 메모와 보고 있던 항목이 그대로
   남는다. 이때 작업 문서와 결정 기록에는 아무 변화가 없다.
7. 담아 둔 갱신 시각과 다른 갱신 시각을 가진 작업이 있으면 그 항목만 다시 확인 필요로 바뀌고, 그 항목의
   결과와 메모는 지워지지 않는다.
8. 항목 상태 네 가지가 색이나 아이콘 없이 글자로도 구분된다.
9. 임시 검토 버리기를 누르면 기능 이름과 사라질 항목 수를 먼저 보여 주고, 확인한 뒤에만 지운다.
10. 기능 묶음이 지금 확인할 수 있는 조건을 잃으면 담아 둔 내용이 남은 채 준비 중으로 표시되고 그 이유가
    보인다.
11. 항목 이동과 결과 선택과 메모 입력과 작업 원문 열고 닫기를 키보드만으로 할 수 있고, 초점이 현재
    항목을 따라간다.
12. 좁은 창에서 항목 목록과 현재 항목이 세로로 놓이고, 가로 스크롤 없이 주요 조작을 쓸 수 있다.
13. 전체 항목 수와 결과를 남긴 수와 남은 수가 화면에서 늘 보인다.

## 검증 단계

1. 세션 화면 검사를 새로 작성하고 실행한다. 완료 조건 1·2·3·4·5·8·13을 각각 확인한다. 자동 근거 항목이
   섞인 기능, 확인 동선 절이 없는 작업, 사유가 비어 있는 문제 있음을 각각 넣어 결과를 단언한다.
   명령: `npx vitest run src/features/projects/components/qa/QaSessionView.test.tsx`
2. 임시 검토 검사를 추가하고 실행한다. 완료 조건 6·7·9·10을 확인한다. 저장소에 담아 둔 값을 미리 넣은 뒤
   화면을 다시 그려 이어지는지 단언하고, 작업 갱신 시각을 바꾼 뒤 그 항목만 다시 확인 필요가 되는지
   단언한다. 이때 작업 문서를 쓰는 통로가 한 번도 불리지 않았음을 함께 단언한다.
   명령: `npx vitest run src/features/projects/components/qa/QaWorkbench.test.tsx`
3. 완료 조건 11은 키보드 이동과 실행을 흉내 내는 검사로 확인한다. 항목 사이 이동, 결과 선택, 원문 열고
   닫은 뒤 같은 항목으로 초점이 돌아오는지를 단언한다.
4. 완료 조건 12는 좁은 창 폭을 가정한 스타일 규칙을 화면 전용 스타일 파일에서 읽어 세로 배치와 가로
   스크롤 없음을 단언해 확인한다.
5. 타입 검사와 저장소 전체 검사를 실행한다. 명령: `npm run typecheck` 다음 `npm test`

## 확인 동선

1. 앱을 열고 왼쪽 주요 메뉴에서 품질 확인을 누른다. 지금 확인할 기능 구획에서 기능 행을 누른다.
2. 확인 범위 설명 아래에 항목 확인 본문이 새로 보인다. 왼쪽에 확인 항목 목록이, 오른쪽에 지금 볼 항목
   하나가 놓이면 정상이다.
3. 본문 맨 위 고정 줄에 기능 이름과 `전체 N개 · 결과를 남긴 M개 · 남은 K개`가 보인다. 이 줄은 아래로
   내려도 화면에 남아야 한다. N은 그 기능에서 품질 확인을 기다리는 작업 수와 같아야 한다.
4. 목록의 자동 근거 묶음을 펼치지 않은 상태에서도 그 항목들의 제목과 상태가 보이고, 자동 근거 개수도
   보인다. 이 항목들이 전체 N에서 빠지면 잘못된 것이다.
5. 오른쪽 현재 항목에서 개발자가 그 작업 문서에 쓴 확인 동선 절이 통째로 보인다. 목록 카드에 실리던
   한 문단 발췌가 아니라 그 절의 모든 줄이어야 하고, 앱이 지어낸 새 문장이 있으면 잘못된 것이다.
6. 화면 조작이 없는 자동 근거 항목을 연다. 직접 조작할 화면이 없다는 안내와 개발자가 남긴 검증 결과가
   같은 자리에 함께 보이면 정상이다.
7. 현재 항목에서 확인함을 누른다. 메모를 적지 않아도 그 항목 상태가 확인함으로 바뀌고 진행률의 남긴
   수가 하나 늘면 정상이다.
8. 다른 항목으로 옮겨 문제 있음을 누른다. 사유가 비어 있는 동안에는 사유를 적어야 결과로 남는다는
   안내가 보이고 그 항목은 확인 전에 머무른다. 메모에 사유를 적으면 그때 문제 있음으로 바뀐다.
9. 작업 원문 보기를 누르면 그 작업 문서 전체가 열리고, 작업 원문 닫기를 누르면 같은 항목과 적고 있던
   메모가 그대로 남는다.
10. 다른 화면으로 갔다가 품질 확인으로 돌아온다. 대기열의 그 기능 행이 시작 대신 계속으로 표시되고,
    열면 남긴 결과와 메모와 보던 항목에서 이어지면 정상이다. 앱을 껐다 켜도 결과와 메모는 남는다.
    이때 보던 자리는 결과가 없는 첫 항목으로 돌아간다.
11. 임시 검토 버리기를 누른다. 기능 이름과 사라질 항목 수를 먼저 보여 주고, 한 번 더 눌러야 지워지면
    정상이다. 첫 누름만으로 지워지면 잘못된 것이다.
12. 확인하는 도중 그 기능의 작업 하나가 개발로 되돌아가면 준비 중이라는 안내와 남은 작업 수가 보인다.
    이때 남긴 임시 검토가 지워지면 잘못된 것이다.
13. 개발자가 그 기능의 작업 문서 하나를 고쳐 갱신 시각이 바뀌면, 그 항목만 다시 확인 필요로 바뀌고
    그 항목의 결과와 메모는 남아 있어야 한다.
14. 키보드만으로 같은 길을 걷는다. 탭과 엔터로 항목을 옮기고 결과를 고르고 메모를 적고 작업 원문을
    열고 닫는다. 항목을 옮길 때 초점이 현재 항목 본문으로 따라오면 정상이다.
15. 창 너비를 좁힌다. 항목 목록과 현재 항목이 세로로 쌓이고 가로 스크롤 막대가 생기지 않으면 정상이다.
16. 개발 화면을 다시 연다. 그 화면의 확인 동선 표시와 QA 조작이 이전과 같이 동작하면 정상이다.

쓰이지 않으며, 제출 화면은 뒤따르는 작업이 붙인다. 화면 아래 안내가 같은 사실을 말한다.
