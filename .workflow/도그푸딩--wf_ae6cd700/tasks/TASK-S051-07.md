# 앱이 프로젝트별 역할 정책을 런타임 계약으로 저장한다

## 결정권자 요약

프로젝트마다 기획자와 아키텍트와 개발자의 실행 도구와 모델과 인원을 따로 저장한다.
프로젝트를 바꾸면 다른 프로젝트의 설정이 섞이지 않고 앱을 다시 열어도 같은 값이 보인다.
기존 Claude Heartbeat 역할 설정은 쓰기 전에 이전 내용을 보여준 뒤 새 설정으로 옮길 수 있다.
옮길 수 없는 값은 조용히 버리지 않고 사용자가 확인할 목록으로 남는다.
Dream 설정은 새 역할 정책으로 옮기거나 변경하지 않는다.

## 목적

프로젝트의 안정적인 식별자와 실제 작업 디렉터리를 TASK-S051-02의 런타임 설정 계약에 연결한다.
역할별 provider, model, 한 번·반복 방식, 최대 병렬 인원, 판정 간격, 실행 한도와 프로젝트 상한을
조회·검증·저장하는 앱 백엔드를 만든다.

## 프로젝트 식별

- `projectId`는 `.workflow/project.yml`에 등록된 값을 읽는다. 표시 이름이나 slug에서 만들지 않는다.
- `workingDirectory`는 사용자가 연 프로젝트의 실제 정규 경로를 전달한다. 런타임 응답의 경로가 다른
  경우 저장과 실행을 막는다.
- `.workflow/project.yml`이 없거나 활성 workflow가 없으면 설정을 만들지 않고 구성 필요 상태를
  반환한다.

## 설정 계약

1. 세 역할 각각에 enabled, provider, model, runMode, maxParallel, interval, maxPer를 둔다.
2. 역할 최대 병렬 인원의 기본값은 1이다. 프로젝트 최대 병렬 인원의 기본값은 3이며 기기 상한을
   넘을 수 없다.
3. provider는 첫 릴리스에서 claude와 codex만 허용한다. model은 빈 값일 때 각 CLI 기본값을 사용하고
   앱이 임의 모델명을 넣지 않는다.
4. 저장은 현재 설정의 revision을 baseline으로 받는다. 화면이 읽은 뒤 다른 프로세스가 바꿨으면
   아무 값도 덮어쓰지 않고 최신 설정을 반환한다.
5. provider 진단이 ready가 아니어도 설정 자체는 저장할 수 있으나 실행 가능 상태와 다음 행동을 함께
   반환한다. 호환되지 않는 runtime에서는 저장하지 않는다.

## 기존 설정 마이그레이션

- 기존 앱 관리 역할 잡이 있으면 각 역할을 enabled와 claude provider로 제안한다.
- interval, timeout에 대응하는 실행 제한, max_per, model 원문을 보존한다. 새 계약에 직접 대응하지
  않는 값은 미리보기의 unresolved 목록에 넣는다.
- 기존 잡이 없는 역할은 임의로 켜지 않는다. 최대 병렬 인원은 1로 제안한다.
- 마이그레이션 미리보기와 적용을 분리한다. 사용자가 확인한 revision과 미리보기 식별자가 없으면
  쓰지 않는다.
- 적용 뒤에도 일반 Heartbeat 잡과 실행 이력을 지우지 않는다. Dream 잡은 읽기·쓰기 대상에서 제외한다.

## 손대지 않는 것

- 대상 예약과 provider 프로세스 시작
- 상태·로그·취소 화면
- 런타임 설치 파일과 서비스 등록
- 기존 Dream 설정과 화면
- 앱 소유 workflow manifest와 decisions

## 완료 조건

1. 세 역할의 provider, model, 실행 방식, 최대 병렬 인원, 판정 간격, 실행 한도를 저장하고 재조회하면
   같은 값이 나온다.
2. 역할 상한 기본값 1과 프로젝트 상한 기본값 3이 새 프로젝트에 적용된다.
3. 프로젝트를 전환하면 설정 응답의 `projectId`, 작업 디렉터리, 역할 값이 해당 프로젝트만 따른다.
4. 앱을 종료하고 런타임을 다시 시작해도 저장된 설정이 복원된다.
5. 잘못된 역할·provider·상한·경로와 호환되지 않는 runtime은 쓰기 전에 거절된다.
6. 같은 baseline revision으로 경합한 저장 두 건 중 하나만 성공하고 다른 요청은 최신 값을 받는다.
7. 기존 역할 잡의 interval, timeout, max_per, model이 마이그레이션 미리보기에 손실 없이 나타난다.
8. 직접 대응하지 않는 기존 값은 unresolved 목록에 나타나며 확인 전에는 새 설정을 쓰지 않는다.
9. 마이그레이션 뒤 기존 일반 잡과 실행 이력이 남고 Dream 잡과 설정은 변경되지 않는다.
10. provider CLI 미설치·로그인 필요·권한 부족·지원하지 않는 버전 상태가 설정 응답에 구분되어 실린다.
11. 설정 저장은 provider 프로세스를 시작하지 않는다.
12. 기존 연동 조회와 역할 잡 편집 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. 임시 프로젝트 둘과 가짜 runtime CLI로 설정 저장, 재조회, 프로젝트 전환, 프로세스 재시작을
   검사한다.
2. baseline 경합, 잘못된 project ID, 다른 실제 경로, 호환 불가 버전을 주입해 무쓰기를 확인한다.
3. 세 역할이 모두 있는 기존 jobs.d, 일부만 있는 파일, 알 수 없는 값, Dream 혼재 파일로 마이그레이션
   미리보기와 적용을 검사한다.
4. 적용 전후 기존 jobs.d와 상태 파일의 바이트를 비교해 삭제·수정되지 않았는지 확인한다.
5. provider 진단 상태별 가짜 응답에서 설정은 보존되고 실행 가능 상태만 달라지는지 확인한다.
6. `cargo test --manifest-path src-tauri/Cargo.toml`을 실행한다.
7. `npm run check`를 실행한다.

## 범위와 선행

확장하므로 설치 백엔드와 동시에 작업하지 않는다.
