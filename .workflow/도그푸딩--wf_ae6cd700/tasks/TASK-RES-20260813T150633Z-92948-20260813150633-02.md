# 기능별 확인 대상 판정과 기기 내 임시 검토 저장을 화면 밖 모듈로 분리한다

## 결정권자 요약

### 제안

어떤 기능을 지금 확인할 수 있고 그 기능에 어떤 확인 항목이 들어가는지 정하는 판정을, 개발 화면 안이
아니라 여러 화면이 함께 읽는 한 자리로 옮긴다. 제출 전 검토 내용을 기기에 임시로 담아 두는 자리도 함께
만든다.

### 현재

기능 묶음 판정은 개발 화면 파일 안에 있고, 에이전트 화면이 그 일부만 가져다 쓴다. 오늘 화면과 새 품질
확인 화면이 같은 기준으로 세려면 화면 파일을 서로 참조해야 한다. 제출 전 검토 내용을 담아 둘 자리는
아직 없다.

### 변경 후

기능 묶음, 확인 항목 목록, 자동 근거 구분, 지금 시작할 수 있는지의 판정이 한 자리에 모인다. 화면들은 그
자리를 읽기만 한다. 임시 검토 저장은 기존 화면 상태 저장과 같은 방식으로 기기에만 남는다.

### 사용자 결과

이 작업만으로는 화면이 달라지지 않는다. 개발 화면의 확인할 기능 목록과 에이전트 화면의 대기 건수는
지금과 똑같이 나온다. 뒤따르는 화면 작업이 이 판정 위에서 대기열과 세션을 만든다.

### 영향 범위

- 변경: 기능 묶음과 확인 항목을 정하는 판정이 놓인 자리, 제출 전 검토를 기기에 담아 두는 자리
- 유지: 개발 화면의 확인할 기능 목록과 준비 중 예고, 에이전트 화면의 대기 건수, 기능 묶음을 판정하는 기준 자체, 작업 문서와 결정 기록

### 비용과 위험

판정을 옮기는 동안 기준이 조금이라도 달라지면 두 화면의 건수가 어긋난다. 그래서 이 작업은 기준을 바꾸지
않고 자리만 옮기며, 옮기기 전후로 기존 화면 검사가 그대로 통과하는 것을 성공 기준으로 삼는다.

### 결정 요청

QA에서는 개발 화면과 에이전트 화면의 확인 대기 표시가 이전과 똑같은지, 그리고 아래 검증 단계의 자동
검사가 옮긴 판정과 새 저장소의 동작을 확인했는지를 본다.

## 범위 사전 검사

이 작업이 다루는 값은 둘이다. 화면들이 함께 읽을 기능 묶음 판정과, 기기에만 남는 제출 전 검토다. 두 값이
어디서 생겨 어디까지 가는지 현재 코드를 열어 확인했다.

- 값 경로: 완료 조건 1·2·3의 기능 묶음 판정은 지금
  `src/features/projects/components/DevelopmentBoard.tsx` 안에 있다. 값을 만드는 자리는 같은 파일의
  `qaGroups`, `qaBatchReady`, `buildQaSessions`, `buildUpcomingQa`, `isEvidenceOnlyQa`,
  `compareQaTasks`, `actionableQaFileNames` 일곱 함수이고, 입력은 화면이 이미 들고 있는 작업 목록과
  기획서 목록이다. 소비하는 자리는 같은 파일의 `QaSessionHub`와 `QaSessionView`, 그리고
  `src/features/projects/components/agents/AgentRunDashboard.tsx`의 `userDecisions`다. 판정을
  `src/features/projects/domain/qaReview.ts`로 옮기고 두 화면 파일이 그 모듈을 읽게 바꾼다. 두 화면 파일은
  값을 그대로 나르지 않고 가져오는 자리를 바꿔야 하므로 둘 다 편집 대상이다.
- 값 경로: 완료 조건 4의 확인 항목 구분은 `isEvidenceOnlyQa`가 작업 목록 항목의 `excerpt`에서 특정 한국어
  문구를 찾아 정한다. 그 `excerpt`는 앱 백엔드가 만드는 값이고, 품질 확인 대기 작업에서는
  `src-tauri/src/infrastructure/fs_project_repository.rs`의 `walkthrough_preview`가 확인 동선 절의 첫
  문단을 잘라 넣는다. 이 작업은 그 값을 읽기만 하고 만드는 쪽은 건드리지 않으므로 앱 백엔드 파일은
  선언에 넣지 않는다. 다만 옮긴 모듈에서는 이 구분이 목록에서 항목을 빼는 판정이 아니라 접어 둘지만
  정하는 값이 되도록 이름과 반환값을 나눈다. 목록에서 빼는 쪽은 이 작업에서 없앤다.
- 값 경로: 완료 조건 5·6의 제출 전 검토는 지금 어디에도 없다. 값을 만드는 자리는 뒤따르는 화면 작업이고,
  이 작업은 담아 두는 자리만 만든다. 만드는 파일은
  `src/features/projects/infrastructure/browserQaReviewDraftStore.ts`이며, 같은 폴더의
  `browserSpecLaneCollapseStore.ts`가 쓰는 어법을 그대로 따른다. 읽기 실패와 형식이 깨진 값은 던지지 않고
  빈 값으로 답하고, 저장 실패는 삼킨다. 이 저장소를 읽는 화면은 이 작업에서 만들지 않는다.
- 검토했으나 제외한 것: `src/features/projects/components/WorkspaceShell.tsx`는 열지 않는다. 오늘 화면이
  이 판정을 읽는 것은 진입점 통합 작업의 완료 조건이고, 지금 그 파일을 함께 고치면 판정 이동과 화면 변경이
  한 검토 단위에 섞인다.
- 검토했으나 제외한 것: `src/features/projects/components/DevelopmentBoard.test.tsx`와
  `src/features/projects/components/agents/AgentRuntimeView.test.tsx`는 선언에 넣지 않는다. 두 검사 파일은
  옮기는 함수들을 직접 부르지 않고 화면을 그려 결과만 확인한다. 이 작업은 판정 기준을 바꾸지 않으므로 두
  파일은 편집 없이 그대로 통과해야 하고, 그 통과가 완료 조건 7이다.

## 현재 상태

기능 묶음 판정은 개발 화면 파일 안의 함수 일곱 개로 되어 있다. 같은 기획서에서 나온 작업을 묶고, 그
묶음의 모든 작업이 완료이거나 품질 확인 대기일 때만 지금 확인할 수 있다고 판정한다. 기획서 연결이 없는
작업은 단건 묶음으로만 남는다.

확인 항목 중 확인 동선 발췌에 특정 한국어 문구가 들어간 항목은 자동 근거로 분류되어 직접 확인 단계
목록에서 빠진다. 그 항목도 기록 대상에는 남지만 단계 수에는 세어지지 않는다.

에이전트 화면은 이 판정 중 하나만 가져다 지금 누를 수 있는 품질 확인 건수를 센다. 오늘 화면은 이 판정을
전혀 읽지 않는다.

## 변경 범위

1. 기능 묶음 판정을 `src/features/projects/domain/qaReview.ts`로 옮긴다. 옮기는 것은 묶음 만들기, 지금
   확인할 수 있는지의 판정, 확인 항목 정렬, 지금 시작할 수 있는 확인 대상 파일 이름 모으기, 준비 중 묶음
   만들기다. 판정 기준은 한 줄도 바꾸지 않는다.
2. 자동 근거 구분은 옮기되 뜻을 나눈다. 옮긴 모듈은 확인 항목 전체를 하나의 목록으로 돌려주고, 항목마다
   자동 근거인지를 나타내는 값을 함께 담는다. 자동 근거 항목을 목록에서 빼는 동작은 없앤다.
3. 확인 항목 하나가 갖는 값을 다음으로 고정한다. 작업 파일 이름, 작업 식별자, 작업 제목, 확인 동선 발췌,
   자동 근거 여부, 작업 문서의 갱신 시각이다. 갱신 시각을 함께 담는 것은 뒤따르는 작업이 검토 도중 바뀐
   항목을 가려내는 근거로 쓰기 위해서다.
4. 기능 묶음 하나가 갖는 값을 다음으로 고정한다. 묶음 키, 기능 제목, 기능 설명, 확인 항목 목록, 직접 확인
   항목 수, 자동 근거 항목 수, 지금 확인할 수 있는지, 아직 끝나지 않은 작업 수다.
5. 개발 화면과 에이전트 화면이 옮긴 모듈을 읽게 바꾼다. 두 화면이 지금 그리는 내용은 바꾸지 않는다.
   개발 화면의 직접 확인 단계 수와 자동 검증 건수는 옮긴 모듈이 돌려준 값에서 다시 계산해 이전과 같은
   수를 보여 준다.
6. 제출 전 검토 저장소를 만든다. 워크플로 디렉터리와 기능 묶음 키를 열쇠로 삼아 항목별 결과와 메모, 검토를
   시작한 시각, 항목별로 읽은 작업 갱신 시각을 담는다. 읽기, 저장, 지우기 세 동작을 갖는다.
7. 저장소는 값을 읽지 못해도 던지지 않는다. 값 없음, 형식 오류, 배열, 저장소 접근 실패를 모두 빈 값으로
   답한다. 저장 실패도 삼킨다. 한 기능의 값이 깨져도 다른 기능의 값은 버리지 않는다.

## 범위 밖

- 품질 확인 대기열, 세션, 제출 전 검토 화면
- 오늘 화면과 개발 화면의 진입점 변경
- 기능 묶음 판정 기준 자체의 변경
- 확인 동선 발췌를 만드는 앱 백엔드 동작의 변경
- 여러 기기 사이의 임시 검토 공유

## 완료 조건

1. 기능 묶음과 확인 대상 판정이 화면 파일이 아니라 도메인 모듈 한 곳에 있고, 개발 화면과 에이전트 화면이
   그 모듈에서 값을 가져온다.
2. 같은 기획서에서 나온 작업이 모두 완료이거나 품질 확인 대기일 때만 그 기능이 지금 확인할 수 있는
   묶음으로 나온다. 준비나 진행 중이나 막힘이나 규격 밖 작업이 하나라도 있으면 나오지 않는다.
3. 아직 확인할 수 없는 묶음은 품질 확인 대기 건수와 남은 작업 수를 담아 따로 돌아온다.
4. 확인 항목 목록에 그 기능의 품질 확인 대기 작업이 하나도 빠짐없이 들어간다. 자동 근거로 분류된 항목도
   목록과 전체 건수에 남고, 자동 근거인지는 항목의 값으로만 구분된다.
5. 제출 전 검토 저장소가 기능별로 항목 결과와 메모를 저장하고 다시 읽어 온다. 한 기능을 지워도 다른
   기능의 값은 남는다.
6. 저장된 값이 없거나 형식이 깨졌거나 저장소 접근이 실패해도 저장소는 오류를 던지지 않고 빈 값으로
   답한다.
7. 개발 화면과 에이전트 화면의 기존 검사가 편집 없이 그대로 통과하고, 확인할 기능 목록과 준비 중 예고와
   대기 건수가 변경 전과 같은 수를 보여 준다.

   확인할 수 있는 묶음, 자동 근거가 섞인 묶음, 기획서 연결이 없는 작업을 각각 넣어 판정을 단언한다.
   명령: `npx vitest run src/features/projects/domain/qaReview.test.ts`
2. 저장소 검사를 새로 작성하고 실행한다. 완료 조건 5·6을 확인한다. 저장소 접근이 실패하는 상황을 흉내 내
   빈 값으로 답하는지 단언한다.
   명령: `npx vitest run src/features/projects/infrastructure/browserQaReviewDraftStore.test.ts`
3. 개발 화면과 에이전트 화면의 기존 검사를 편집하지 않고 실행한다. 완료 조건 7을 확인한다.
   명령: `npx vitest run src/features/projects/components/DevelopmentBoard.test.tsx src/features/projects/components/agents/AgentRuntimeView.test.tsx`
4. 타입 검사를 실행해 옮긴 모듈과 두 화면의 선언이 어긋나지 않는지 확인한다.
   명령: `npm run typecheck`
5. 저장소 전체 검사를 실행해 기존 동작이 유지되는지 확인한다. 명령: `npm test`

## 확인 동선

이 작업은 화면을 바꾸지 않는 것이 성공 기준이다. 그래서 확인 동선도 "무엇이 새로 보이는가"가 아니라
"이전과 같은 것이 그대로 보이는가"를 본다.

1. 앱에서 개발 화면을 연다. 상단의 확인할 기능 묶음에서 카드 제목과 오른쪽 위 숫자, 각 카드의 직접
   확인 단계 수와 자동 검증 건수가 변경 전과 같으면 정상이다. 준비 중 예고 카드의 "QA n건 준비 중 ·
   남은 작업 m개" 문구도 같은 수여야 한다.
2. 같은 화면에서 카드의 QA 시작을 누른다. 직접 확인 단계 목록과 접어 둔 자동 확인 항목 수가 이전과
   같고, 확인 완료를 누르면 그 기능의 작업이 함께 기록되면 정상이다.
3. 에이전트 화면을 연다. 내 선택 대기 건수가 개발 화면에서 지금 누를 수 있는 확인 항목 수와 어긋나지
   않으면 정상이다.

제출 전 검토를 담아 두는 자리는 이 작업에서 만들기만 했고 읽는 화면이 아직 없다. 그 부분은 눌러 볼
화면이 없으므로 자동 검사가 대신 확인했고, 확인 완료 도장은 아래 수치를 믿는다는 뜻이다.

저장소 최상위에서 같은 수치를 직접 확인할 수 있다.

1. `npx vitest run src/features/projects/domain/qaReview.test.ts` → 11건 통과.
2. `npx vitest run src/features/projects/infrastructure/browserQaReviewDraftStore.test.ts` → 10건 통과.
3. `npx vitest run src/features/projects/components/DevelopmentBoard.test.tsx src/features/projects/components/agents/AgentRuntimeView.test.tsx`
   → 131건 통과. 두 검사 파일은 이 작업에서 한 줄도 고치지 않았다.
4. `npm run typecheck` → 오류 없음.
5. `npm test` → 27개 파일 528건 통과, 42건 건너뜀.
