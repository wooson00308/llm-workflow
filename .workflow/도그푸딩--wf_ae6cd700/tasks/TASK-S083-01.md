# 실행 하나를 확인 처리해 최근 종료에서 감추고 전체 기록에 확인함으로 남긴다

## 결정권자 요약

### 제안

원인 파악이 끝난 실패 실행을 상세 화면에서 확인함으로 표시하면 최근 종료 목록에서 빠지고, 전체 실행
기록에는 확인함 표시를 달고 그대로 남는다.

### 바뀌는 것

- 지금: 조치가 끝난 실패도 최근 종료에 빨간 점으로 계속 남는다 → 앞으로: 확인한 기록은 그 구역에서 아예 보이지 않고 다음 종료 기록이 자리를 채운다
- 지금: 전체 실행 기록에서는 이 실패를 봤는지 알 방법이 없다 → 앞으로: 확인한 줄만 회색 점과 확인함 표시를 단다
- 지금: 전체 실행 기록의 줄은 눌러도 아무 일이 없다 → 앞으로: 줄을 눌러 상세를 열고 거기서 확인을 되돌린다

### 비용과 위험

- 확인 표시는 이 기기의 앱 저장소에 남으므로 다른 기기나 저장소를 비운 뒤에는 다시 미확인으로 보인다.
- 실행 기록과 워크플로 문서에는 아무것도 쓰지 않으므로, 되돌리려면 표시를 지우면 그만이고 승인되지 않으면 목록은 지금 그대로다.

## 현재 코드 상태

최근 종료 목록과 전체 실행 기록은 모두
`src/features/projects/components/agents/AgentRunDashboard.tsx` 한 파일 안에 있다.

- 91행이 `state.queue?.runs`에서 실행 목록을 받고, 93행의 `recent`가 진행 중이 아닌 실행을 걸러
  앞의 세 건만 자른다. 정렬은 따로 하지 않고 실행 환경이 준 순서를 그대로 쓴다.
- 267행부터의 구역이 `recent.length > 0`일 때만 그려진다. 머리에 최근 종료 제목과 전체 기록 버튼이
  있고, 줄마다 `agent-state-dot state-<상태값>` 점과 제목·역할·사유·소요 시간이 선다. 줄 전체가
  버튼이고 누르면 87행의 `selectedRun`이 채워져 상세가 열린다.
- 283행의 조건이 세우는 조용한 한 줄은 주의가 필요한 구역이 모두 비었을 때만 그려지며 그 조건에 `recent.length`가
  이미 들어 있다.
- 301행이 전체 실행 기록 서랍을 그리고, 550행의 `HistoryDrawer`가 받은 목록을 561행 한 줄에서
  그린다. 이 줄들은 `div` 하나이고 누를 수 있는 요소가 아니다. 그래서 지금은 전체 실행 기록에서
  상세로 들어가는 통로가 없다.
- 370행의 `DetailDrawer`가 상세를 그린다. 451행의 버튼 줄에 취소·재시도·진단 자료 버튼이 있고,
  재시도는 `failed`·`cancelled`·`recovery_required` 세 상태에서만 그려진다.

실행 상태값은 `src/features/projects/domain/types.ts` 1610행의 `AgentRunStatus`가 정하고, 화면 문구는
같은 화면 파일 37행의 `stateLabels`에 있다. 이 작업이 대상으로 삼는 둘은 `failed`(실패)와
`recovery_required`(복구 필요)다. 48행의 `activeStates`가 진행 중으로 묶는 넷을 이미 정의한다.

실행 하나를 가리키는 열쇠는 `types.ts` 1621행 `AgentRunSummary`의 `runId`이고, 프로젝트를 가리키는
열쇠는 347행 `ProjectSummary`의 `projectId`다. `projectId`는 형식상 `null`일 수 있다. 이 화면은
`AgentRuntimeView.tsx` 240행에서 정책을 읽은 뒤에만 그려지고 정책은 `projectId`가 있어야 읽히므로
(`useProjectWorkspace.ts` 312행) 실제로는 값이 있지만, 형식이 허용하는 `null`을 코드가 처리해야 한다.

표시 상태를 브라우저 저장소에 두는 방식은 이미 여러 벌 있다.
`src/features/projects/infrastructure/browserSpecLaneCollapseStore.ts`가 가장 가까운 본보기다. 키
하나에 전체 상태를 JSON으로 담고, 읽기·쓰기 실패와 형식 오류를 모두 삼켜 빈 값으로 돌린다. 이 화면을
그리는 시험 환경의 `localStorage`는 메서드가 없는 빈 객체라(같은 폴더의 저장소 시험 첫머리 주석)
삼키지 않으면 시험이 예외로 죽는다.

실행 목록 조회의 성패는 `useProjectWorkspace.ts` 380행이 `queue`에, 382행이 `queueError`에 남긴다.
`queue`가 `null`이면 아직 읽지 못한 것이고, `queueError`에 값이 있으면 조회가 정상이 아니다.

## 변경 범위

새 저장소 파일 `src/features/projects/infrastructure/browserRunAcknowledgementStore.ts`를 만든다.
프로젝트 식별자별로 확인한 실행 식별자 묶음을 담고, 읽기·저장·정리 셋을 내보낸다. 위 본보기와 같은
방식으로 모든 실패를 삼킨다. 시험은 같은 폴더의 `browserRunAcknowledgementStore.test.ts`에 쓴다.

`AgentRunDashboard.tsx`에서 다음을 고친다.

- 확인한 실행 묶음을 이 컴포넌트의 상태로 들고, 저장소에서 게으르게 읽는다. 프로젝트 식별자가 바뀌면
  다시 읽는다. 이 어법은 `src/features/projects/components/DevelopmentBoard.tsx` 156행부터 165행에
  그대로 있다.
- 93행의 `recent`가 확인한 실행을 뺀 뒤 세 건을 자른다. 자르는 수 3과 정렬은 건드리지 않는다.
- 상세 화면 버튼 줄에 확인함으로 표시를 두고, 이미 확인한 실행에서는 같은 자리를 확인 해제로 바꾼다.
  대상 상태가 아닌 실행에는 이 버튼을 그리지 않는다.
- 전체 실행 기록의 줄을 누를 수 있게 바꾸고, 누르면 그 실행의 상세가 열리게 한다. 지금 줄에 붙어 있는
  `agent-history-row` 클래스는 그대로 둔다. 시험과 스타일이 그 클래스를 잡고 있다.
- 상세와 전체 실행 기록이 함께 열려 있을 때 상세가 위에 오도록 그리는 순서를 맞추고, 전체 실행
  기록의 Escape 처리가 상세가 열려 있는 동안에는 닫지 않게 한다. 상세가 결과 보고서를 두고 이미 같은
  방식을 쓴다(380행).
- 전체 실행 기록에서 확인한 줄은 상태 점의 상태 클래스를 붙이지 않아 기본 회색으로 두고, 보조 줄에
  확인함 표시를 붙인다. 상태 문구와 나머지 형식은 그대로 둔다.
- 실행 목록을 정상으로 읽어 온 순간에만 저장소를 정리한다.

`src/App.css`에 확인함 표시 한 종류와 전체 실행 기록 줄을 버튼으로 만들면서 필요한 최소한의 규칙을
더한다. 77행의 기본 점 색이 이미 회색이므로 점 색을 위한 새 규칙은 만들지 않는다.

## 범위 밖

- 일괄 확인. 최근 종료 구역 머리의 버튼과 건수 확인 창은 같은 그룹의 다음 작업이 맡는다. 이 작업이
  함께 만들면 두 작업의 파일이 겹치는 정도가 아니라 한 작업이 된다.
- 실행 기록 파일과 워크플로 문서와 결정 기록. 확인 표시는 이들에 쓰지 않는다. 백엔드 명령을 새로
  만들지 않고 `src-tauri/` 아래를 고치지 않는다.
- `src/features/projects/domain/types.ts`. 이 작업이 쓰는 `runId`와 `state`와 `projectId`가 이미 있고
  새 필드가 필요 없다.
- 최근 종료 구역의 이름, 전체 기록 버튼의 위치와 문구, 자르는 수 3, 실행 환경이 준 정렬.
- 조용한 한 줄의 문구와 조건. 283행의 조건에 `recent.length`가 이미 들어 있어 확인 처리로 목록이 비는
  경우가 저절로 들어간다.
- 확인 필요 구역, 진행 중, 배정 대기, 앱 밖 세션, 사용 한도 대기 구역.
- 상세 화면의 사유·도구 사용·마지막 활동·결과 보고서 표시와 취소·재시도·진단 자료 버튼.
- 완료·취소됨·상태 확인 필요 기록의 표시와 동작.
- 확인한 사람과 확인한 시각의 기록·표시, 알림·배지·요약 수치 연동.

## 완료 조건

- C1. 새 저장소가 프로젝트 식별자별로 확인한 실행 식별자를 담고, 저장한 값을 그대로 돌려준다. 한
  프로젝트의 값이 다른 프로젝트의 값에 섞이지 않는다. (기획서 R10)
- C2. 저장소의 읽기·저장이 어떤 경우에도 예외를 밖으로 내보내지 않는다. 값 없음, JSON 형식 오류,
  객체가 아닌 값, 배열, 저장소 접근 실패를 모두 빈 값으로 돌린다. 항목 하나가 깨져도 나머지
  프로젝트의 값은 남는다. (기획서 R10)
- C3. 저장소에 정리 동작이 있다. 지금 실행 기록에 있는 실행 식별자 묶음을 받아, 그 안에 없는 확인
  표시를 그 프로젝트에서 지운다. 다른 프로젝트의 값은 건드리지 않는다. (기획서 R13)
- C4. 화면은 실행 목록을 정상으로 읽어 온 순간에만 C3을 부른다. 아직 읽지 못했거나 조회 오류가 남아
  있는 순간에는 부르지 않는다. (기획서 R13)
- C5. 실행 상세 화면에서 상태가 `failed`이거나 `recovery_required`인 실행에만 확인함으로 표시가
  그려진다. 완료·취소됨·상태 확인 필요와 진행 중인 실행에는 그려지지 않는다.
  (기획서 R1, R2, 완료 판정 A8)
- C6. 확인함으로 표시를 누르면 그 실행이 확인한 것으로 바뀌고 저장소에 남는다. 이미 확인한 실행에서는
  같은 자리가 확인 해제로 바뀌고, 누르면 확인 표시가 지워진다. (기획서 R2)
- C7. 최근 종료 목록이 확인한 실행을 뺀 뒤 앞의 세 건을 그린다. 세 건이라는 수와 정렬은 지금 값을
  그대로 쓴다. 확인 처리한 실행의 자리는 다음 종료 기록이 채운다.
  (기획서 R5, 완료 판정 A1)
- C8. 최근 종료 구역에 확인한 기록이 어떤 형태로도 남지 않는다. 건수 줄, 접었다 펼치는 행, 자리를
  지키는 표시를 만들지 않는다. (기획서 R6, 완료 판정 A2)
- C9. 최근 종료 목록에 그릴 실행이 하나도 없으면 구역 자체가 그려지지 않고, 그 자리에 종료 기록이
  없다는 안내나 확인한 기록이 있다는 문구가 새로 서지 않는다. 화면 전체의 조용한 한 줄의 문구와
  조건은 지금과 같다. (기획서 R7, 완료 판정 A7)
- C10. 전체 실행 기록은 확인 여부와 무관하게 끝난 실행 전부를 그린다. 확인한 줄은 상태 점을 회색으로
  그리고 보조 줄에 확인함 표시를 붙이며, 상태 문구는 실패와 복구 필요 그대로다. 소요 시간, 역할 표기,
  보고서 없음 표시, 줄 구성은 지금과 같다. (기획서 R8, 완료 판정 A3, A10)
- C11. 전체 실행 기록의 줄을 누르면 그 실행의 상세가 열린다. 상세가 전체 실행 기록 위에 그려지고,
  상세를 닫으면 전체 실행 기록이 그대로 남는다. Escape 한 번이 두 화면을 함께 닫지 않는다.
  최근 종료 구역의 전체 기록 버튼은 위치와 문구가 그대로다. (기획서 R9, 완료 판정 A4)
- C12. 확인 해제하면 그 기록이 최근 종료 목록에 다시 올라오고 전체 실행 기록의 확인함 표시가
  없어진다. (기획서 R2, 완료 판정 A4)
- C13. 확인 처리와 확인 해제가 브라우저 저장소 밖으로 아무것도 쓰지 않는다. 백엔드 명령을 부르지
  않으므로 실행 기록 파일과 워크플로 문서와 결정 기록이 그대로다.
  (기획서 R11, 완료 판정 A11)
- C14. 확인 표시가 화면 표시에만 쓰인다. 재시도·복구·배정·자격 판정을 계산하는 자리는 이 값을 읽지
  않는다. 복구 필요 기록을 확인 처리해도 상세의 재시도 버튼과 남은 정리 안내가 그대로 동작한다.
  (기획서 R12, 완료 판정 A12)
- C15. 화면에 나오는 말이 확인함, 확인 해제 둘이다. 확인 필요 구역의 문구와 동작은 그대로다.
  (기획서 R14)
- C16. 확인 처리를 한 번도 하지 않은 프로젝트에서 최근 종료 목록과 전체 실행 기록에 그려지는 줄의
  구성, 상태 점 색, 소요 시간 표기, 역할 표기가 이 변경 전과 같다. 상세 화면에 새로 서는 확인함으로
  표시 버튼은 기획서 R2가 두라고 정한 조작 입구이므로 이 조건의 대상이 아니다.
  (기획서 R15, 완료 판정 A13)
- C17. 선언한 다섯 파일 밖이 수정되지 않는다.
- C18. `npm run check`가 통과한다.

## 검증 절차

1. `browserRunAcknowledgementStore.test.ts`에 저장소 시험을 쓴다. 같은 폴더의
   `browserSpecLaneCollapseStore.test.ts`가 쓰는 `localStorage` 대역을 그대로 세워 쓴다.
   - 저장한 값을 그대로 읽는다(C1).
   - 두 프로젝트의 값이 서로 섞이지 않는다(C1).
   - 값 없음·형식 오류·배열·접근 실패에서 빈 값이 나오고 예외가 나가지 않는다(C2).
   - 지금 실행 목록에 없는 식별자만 정리되고, 목록에 있는 값과 다른 프로젝트의 값은 남는다(C3).
2. `AgentRuntimeView.test.tsx`에 화면 시험을 더한다. 시험 이름에 어느 완료 판정을 확인하는지 적는다.
   - A1: 실패 실행 넷을 실은 상태에서 첫 줄의 상세를 열어 확인함으로 표시를 누르면, 최근 종료 목록의
     줄 수가 셋으로 남고 확인한 제목이 사라지며 넷째 실행의 제목이 올라온다(C6, C7).
   - A2: 같은 상태에서 최근 종료 구역 안에 확인한 기록의 제목도, 건수를 말하는 문구도 없다(C8).
   - A3, A10: 전체 기록을 열면 확인한 줄과 확인하지 않은 줄이 모두 있고, 확인한 줄에만 확인함 표시가
     붙으며 그 줄의 상태 점에 실패 상태 클래스가 없다. 상태 문구와 소요 시간은 확인 전과 같다(C10).
   - A4: 전체 기록의 확인한 줄을 눌러 상세를 열고 확인 해제를 누르면, 최근 종료 목록에 그 제목이 다시
     오고 전체 기록에서 확인함 표시가 사라진다. 이때 전체 기록이 닫히지 않는다(C11, C12).
   - A7: 실행이 확인한 실패뿐인 상태에서 최근 종료 구역이 화면에 없고, 확인한 기록이 있다는 문구도
     종료 기록이 없다는 안내도 없다. 다른 구역이 남아 있으면 조용한 한 줄이 나오지 않는다(C9).
   - A8: 완료와 취소됨 실행의 상세에 확인함으로 표시가 없다(C5).
   - A12: 복구 필요 실행을 확인 처리한 뒤에도 상세의 재시도 버튼이 그대로 있다(C14).
   - A13: 확인 표시가 하나도 없는 상태에서 최근 종료 목록의 줄 수와 상태 점 클래스가 이 변경 전
     기대값과 같다(C16).
3. 확인 표시가 앱을 다시 열어도 남는지는 저장소 시험과 화면 시험 둘로 나눠 확인한다. 저장한 값이
   다시 읽힌다는 것은 1번이 확인하고, 저장된 값을 들고 처음 그린 화면에서 그 실행이 최근 종료 목록에
   없다는 것은 2번에 시험을 하나 더해 확인한다(완료 판정 A9).
4. `npm run test -- AgentRuntimeView`와 `npm run test -- browserRunAcknowledgementStore`로 위 시험이
   모두 통과하는 것을 확인한다. 기존 시험이 함께 통과하는지도 본다. 특히 전체 기록 줄을 버튼으로 바꾼
   뒤에도 `.agent-history-row`를 잡는 기존 시험과 Escape로 서랍을 닫는 기존 시험이 통과해야 한다.
5. `npm run check`를 통과시킨다(C18).
6. `git status`로 선언한 다섯 파일 밖의 수정이 없음을 확인한다(C17). 확인 처리를 반복한 뒤 워크플로
   폴더에 변경이 없는 것도 같은 방법으로 본다(C13, 완료 판정 A11).

## 범위 사전 검사

선언한 다섯 파일은 새 저장소와 그 시험 둘, 화면 파일 하나, 화면 시험 하나, 스타일 하나다. 완료 조건을
채우는 데 이 밖의 편집이 필요한지 저장소부터 화면까지 값을 따라가며 확인했다.

`src/features/projects/domain/types.ts`를 열어 보고 뺐다. 1621행의 `AgentRunSummary`가 `runId`와
`state`를 이미 싣고 1724행의 `AgentQueueSnapshot`이 그 목록을 나르며, 347행의 `ProjectSummary`가
`projectId`를 싣는다. 확인 표시는 앱이 따로 드는 값이라 실행 계약에 필드를 더할 이유가 없다. 새
필드를 더하면 백엔드까지 함께 고쳐야 하는데 기획서 R11이 실행 기록을 고치지 말라고 정했다.

`src-tauri/` 아래를 열어 보고 뺐다. 실행 목록은 `src-tauri/src/commands/agent_runtime.rs` 445행의
`inspect_agent_runs`가 실행 환경에 물어 그대로 나르는 값이고, 이 작업은 그 값을 읽기만 한다. 확인
표시를 백엔드에 두면 명령과 저장 경로를 새로 만들어야 하며, 브라우저 저장소로 R10을 이미 충족한다.

`src/features/projects/application/useProjectWorkspace.ts`를 열어 보고 뺐다. 확인 표시는 실행 조회
주기와 수명이 다르고 화면 하나만 쓰는 값이라 공용 상태에 얹을 이유가 없다. 정리 시점을 정하는 데 필요한
`queue`와 `queueError`는 이 파일이 이미 채워 화면으로 내려보내므로 읽기만 하면 된다.

`src/features/projects/components/WorkspaceShell.tsx`를 열어 보고 뺐다. 693행이 이 화면을 그리면서
`key`를 주지 않아 프로젝트가 바뀌어도 마운트가 유지된다. 그래서 확인 표시를 다시 읽는 일이 필요한데,
그 처리는 화면 파일 안에서 하고 `DevelopmentBoard.tsx` 162행이 같은 상황을 같은 어법으로 이미 풀었다.
바깥에서 `key`를 주는 방식은 이 화면 전체를 다시 세워 실행 조회와 로그 구독까지 끊으므로 택하지 않는다.

`src/features/projects/infrastructure/browserSpecLaneCollapseStore.ts`를 열어 보고 뺐다. 새 저장소의
본보기로 읽었을 뿐이고, 그 파일이 담는 것은 기획서 레인 접힘이라 이 값을 얹으면 서로 다른 두 사실이
한 키에 섞인다. 저장소를 따로 만들고 키도 따로 잡는다.

기계 상태를 조건으로 삼는 측정이 없으므로 이 작업은 조용한 기계를 요구하지 않는다. 같은 그룹의 다음
작업이 화면 파일과 화면 시험과 스타일 셋을 함께 잡으므로 그쪽에 순서를 선언했고, 이 작업이 먼저다.
