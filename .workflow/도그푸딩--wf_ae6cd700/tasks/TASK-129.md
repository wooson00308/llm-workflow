# 기획서 도장과 개발 작업 도장이 누르는 자리에서 갈린다

## 결정권자 요약

기획서에 찍는 도장과 개발 작업에 찍는 도장이 화면에서 갈렸다. 오늘 사고가 난 그 자리다.

개발 작업 확인 자리의 반려 버튼이 더는 수정 요청이라고 부르지 않는다. 개발 준비로 되돌린다고
말한다. 기획서 쪽은 승인된 기획이면 후속 기획을 요청한다고 말하고, 두 이름이 겹치지 않는다.

활동 기록도 같은 규칙을 따른다. 승인 뒤에 온 기획서 수정 요청은 후속 기획 요청으로 불리고,
아직 결정되지 않은 기획서의 것은 그대로 수정 요청이다. 그 판별을 활동 기록이 따로 하지 않고
기획서 화면이 쓰는 자리에서 그대로 가져다 쓴다.

개발 작업 확인 자체의 동작은 달라지지 않았다. 달라진 것은 이름뿐이다.

지금 필요한 것은 사용자 확인이고, 아래 확인 동선이 그 자리다. 도장은 누르지 않아도 된다.

## 확인 동선

**볼 화면이 있는 작업이다.** 앱은 이미 떠 있다 — 이 세션이 고친 화면이 개발 서버를 타고 그 창에
이미 들어가 있어서 새로 빌드하거나 띄울 것이 없다. 창이 닫혀 있으면 `npm run tauri dev`로 띄운다.

**도장은 누르지 않는다.** 아래 1번에서 버튼을 한 번 누르는데 그것은 무장까지고, 3.5초 지나면
저절로 풀린다. 실제로 기록되는 것은 무장된 상태에서 한 번 더 누른 순간뿐이다. 메모 칸에 글자를
넣는 것도 아무것도 기록하지 않는다.

### 1. 개발 작업 반려 버튼이 기획서 쪽과 다른 말을 쓰는지

개발 화면 → "QA 대기" 열에서 작업 카드를 아무거나 연다 → 오른쪽 USER QA 패널.

**정상이면 이렇다.**

- 아래쪽 버튼 둘의 이름이 "개발 준비로 되돌리기"와 "확인 완료"다. "수정 요청"이라는 버튼이
  **없다**. 있으면 이 작업이 값을 내지 못한 것이다.
- "테스트 플로우와 확인 메모" 칸에 아무 글자나 넣으면 왼쪽 버튼이 눌리게 된다. 한 번 누르면
  이름이 "한 번 더 누르면 되돌리기"로 바뀌고, 그 위에 "작업을 개발 준비로 되돌리고 수정 요청을
  기록합니다."가 뜬다.
- **거기서 손을 뗀다.** 3.5초 뒤 이름이 "개발 준비로 되돌리기"로 돌아오면 아무것도 기록되지 않은
  것이다. 넣은 메모는 지워도 되고 그냥 화면을 나가도 된다.

### 2. 기획서 쪽 문면과 나란히 놓아 갈리는지

기획서 검토 탭 → 필터 "결정됨" → 상태가 "승인됨"인 문서를 아무거나 연다 → 오른쪽 사용자 결정
패널.

**정상이면** 거기 버튼 이름이 "후속 기획 요청"이다. 1번에서 본 "개발 준비로 되돌리기"와 나란히
놓았을 때, 무엇이 대상이고(기획서인가 작업인가) 무엇이 일어나는지(후속 기획을 요청하는가 개발
준비로 되돌리는가)가 이름만으로 갈리면 이 작업이 요구한 것이 선 것이다.

여기서도 누르지 않는다. 눌러도 양식이 열릴 뿐이고 "후속 기획 요청 기록"까지 눌러야 기록되지만,
확인에 필요한 것은 버튼 이름을 읽는 것까지다.

### 3. 활동 기록이 그대로인지

활동 탭 → "최근 활동".

**정상이면** 목록이 전과 똑같이 그려지고, 마크 이름이 "생성"·"시작"·"QA 대기"·"반려"·"승인" 등
전과 같다. 이 자리는 회귀만 본다.

**"후속 기획 요청"이라는 마크는 지금 이 프로젝트에서 볼 수 없다.** 그 이름이 뜨려면 승인된
기획서에 수정 요청 도장이 한 번 더 찍혀 있어야 하는데, 이 저장소의 결정 45건 중 그런 것이 아직
없다. 도장을 찍어 만들어 보는 것은 사용자의 결정이라 이 세션이 하지 않았다. 그 갈림은 자동
검사가 닫았고, 그 확인 도장은 아래 두 검사의 수치를 믿는다는 뜻이다.

- `npm run check` → 23개 파일 668개 검사 통과, 빌드 성공
- `cargo test --manifest-path src-tauri/Cargo.toml` → 538 passed / 0 failed

이름 갈림을 직접 눈으로 보고 싶으면 승인된 기획서에 후속 기획 요청을 한 번 찍으면 된다. 그것은
실제 결정 기록이 남는 조작이라 이 확인 동선이 요구하지 않는다.

SPEC-042의 R5다. 기획서 완료 조건 9·10이 여기서 닫힌다.

두 화면을 한 작업으로 묶은 이유는 R5가 요구하는 것이 "두 자리가 같은 사실을 다르게 말하지
않는다"이기 때문이다. 한쪽만 고친 중간 상태에서는 그 요구를 확인할 수 없다.

## 지금 이 자리가 어떻게 되어 있는가

- **개발 작업 쪽.** `DevelopmentBoard.tsx:391`의 확인 문구가 "작업을 개발 준비로 되돌리고 수정
  요청을 기록합니다."이고, 버튼 이름은 무장 전 "수정 요청", 무장 후 "한 번 더 누르면 수정
  요청"이다. 무엇이 대상인지(개발 작업)는 문구가 말하지만 버튼 이름만 보면 기획서 쪽과 같은
  말이다.
- **기획서 쪽.** 수정 요청 버튼에 확인 문구가 없다. 무장 확인은 승인 버튼에만 걸려 있다.
  TASK-128이 그 비대칭을 닫고 승인된 기획서의 조작을 "후속 기획 요청"으로 부른다.
- **활동 뷰.** `ActivityView.tsx:62`~`:66`의 `specEventLabels`가 기획서 결정을 승인·수정 요청·
  폐기로 부르고, 그 위 주석이 이미 "기획서에서는 사용자의 수정 요청이고 작업에서는 QA 반려다"를
  적어 두 값을 갈라 두었다. 갈려 있지 않은 것은 기획서 쪽 안에서의 두 뜻이다.

## 이름 규칙은 새로 만들지 않는다

TASK-128이 `src/features/projects/domain/specDecisionLabels.ts`를 만든다. 한 기획서의 시각순
결정 목록에서 어느 항목이 후속 기획 요청이고 어느 항목이 수정 요청인지를 그 모듈이 답한다.

활동 뷰는 그 모듈을 **쓴다**. 같은 판별을 다시 쓰지 않는다. 두 자리가 각자 판단하면 R5가 요구한
"같은 사실을 두 자리에서 다르게 말하지 않는다"가 바로 그 자리에서 깨진다.

쓸 수 있는 이유는 활동 뷰가 이미 기획서 항목 단위로 이벤트 목록을 훑기 때문이다.
`collectEntries(items.specs, "spec")`가 항목마다 그 항목의 `events`를 순서대로 돌므로, 어느
항목 앞에 승인이 있었는지는 그 자리에서 알 수 있다. 앱에서 새 값을 받아 올 필요가 없다.

## 바꾸는 것

### 1. 두 수정 요청이 서로 다른 문구를 쓴다 (R5)

버튼·제목·확인 문구에서 다음 둘이 읽힌다.

- **무엇이 대상인가** — 기획서인가 개발 작업인가.
- **무엇이 일어나는가** — 후속 기획을 요청하는가, 작업을 개발 준비로 되돌리는가.

개발 작업 쪽에서 바꾸는 것은 문구다. 지금 확인 문구는 이미 무엇이 일어나는지를 말하고 있으므로,
남은 것은 버튼 이름이 기획서 쪽과 같은 말을 쓰지 않게 하는 것이다. 무장 전후 두 문면이 함께
간다.

기획서 쪽 문면은 TASK-128이 정한다. 이 작업은 그 문면과 부딪히지 않게 맞추는 쪽이다. 두 문면을
나란히 놓고 읽었을 때 갈리지 않으면 이 작업은 값을 내지 못한 것이다.

### 2. 활동 기록의 이름이 그 결정과 어긋나지 않는다 (기획서 완료 조건 10)

- 기획서 이벤트 중 앞에 승인이 있는 수정 요청은 후속 기획 요청으로, 없는 것은 수정 요청으로
  불린다. 판별은 위 모듈이 한다.
- 개발 작업 이벤트의 이름은 지금 그대로다. 그쪽 `revision_requested`는 QA 반려이고 이번 변경의
  대상이 아니다.
- 항목의 표시 종류에 이름이 실려 있다면 그 자리도 함께 간다. 지금 마크는 이벤트 값으로 클래스를
  만들므로, 이름이 갈리면서 표시가 어긋나지 않는지 확인한다.

### 3. 같은 사실을 두 자리에서 다르게 말하지 않는다

기획서 화면의 이력(TASK-128)과 활동 뷰가 같은 결정을 같은 이름으로 부른다. 두 자리의 테스트가
같은 픽스처에서 같은 문자열을 기대하게 두면 이 성질이 다음 세션에도 남는다.

## 손대지 않는 것

- **개발 작업 QA의 동작.** `record_task_qa`도, 확인·반려가 작업 상태에 하는 일도 그대로다.
  기획서 제외 범위가 명시한다 — 이번에 손대는 것은 두 행위가 화면에서 갈리는지뿐이다.
- **쓰기 경로와 판정 규칙.** TASK-127이 닫았고 이 작업은 열지 않는다.
- **기획서 화면.** TASK-128의 몫이다. 이 작업에서 `SpecWorkspace.tsx`를 고치지 않는다. 문면이
  어긋나 고쳐야 하면 고치지 말고 보고서에 적어 후속으로 넘긴다.
- **결정 이름 규칙 모듈.** 이 작업은 그 모듈을 쓰기만 한다. 규칙을 바꿔야 할 이유가 보이면
  같은 방식으로 보고서에 적는다.
- **활동 피드의 정렬·상한·스크롤 복원.** 그대로다.
- **일괄 확인 화면.** SPEC-039가 이미 정한 범위이고 이번 변경의 대상이 아니다.

## 완료 조건

1. 기획서 결정의 수정 요청과 개발 작업 QA의 수정 요청이 서로 다른 문구를 쓰고, 각각 무엇이
   대상이고 무엇이 일어나는지를 말한다. 두 화면의 컴포넌트 테스트가 확인한다. (기획서 완료 조건
   9, R5)
2. 활동 뷰에서 앞에 승인이 있는 기획서 수정 요청이 후속 기획 요청으로 불리고, 없는 것은 수정
   요청으로 불린다. 결정 둘을 심은 픽스처의 테스트가 확인한다. (기획서 완료 조건 10, R5·R7)
3. 개발 작업 이벤트의 이름이 달라지지 않는다. (R5)
4. 이름 판별이 TASK-128의 모듈 하나에서만 나온다. 활동 뷰가 같은 판별을 다시 쓰지 않는다.
   (R5)
5. 기획서 화면의 이력과 활동 뷰가 같은 결정을 같은 이름으로 부른다. (R5·R7)
6. 개발 작업 QA 기록의 동작이 달라지지 않는다. 기존 테스트가 수정 없이 통과한다. (기획서 완료
   조건 17, R9, 제외 범위)
7. 활동 뷰의 나머지 동작 — 정렬, 상한과 잘림 알림, 문서로 이동 — 이 달라지지 않는다. 기존
   테스트가 수정 없이 통과한다. (기획서 완료 조건 17, R9)
8. 기존 자동 테스트가 삭제되거나 비활성화되지 않는다. (기획서 완료 조건 18, R9)
9. 역할 계약 문언과 파일 계약 문서가 이 변경분에서 달라지지 않는다. (기획서 완료 조건 19)
10. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다. (기획서
    완료 조건 21)

## 검증 절차

1. 개발 작업 QA 대기 픽스처에서 반려 버튼의 무장 전후 문면과 확인 문구를 읽고, TASK-128이 남긴
   기획서 쪽 문면과 나란히 놓아 갈리는지 확인한다. 두 문면을 보고서에 옮겨 적는다.
2. 기획서 결정이 승인 하나뿐인 픽스처와 승인 뒤 수정 요청이 붙은 픽스처로 활동 뷰를 그려, 두
   번째 것만 후속 기획 요청으로 불리는지 확인한다.
3. 같은 픽스처에서 기획서 화면의 이력과 활동 뷰가 같은 이름을 내는지 대조한다.
4. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`.
5. 앱을 띄워 활동 기록과 개발 작업 확인 자리를 눈으로 확인한다. **실제로 도장을 찍지 않는다.**
   확인과 반려는 사용자의 도장이다.
