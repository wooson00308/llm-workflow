# 패널 너비 계산 규칙과 브라우저 저장소를 만든다

## 결정권자 요약

### 제안

사이드바와 세 패널의 너비가 어디까지 움직이고 창이 좁을 때 어떻게 줄어들며 어디에 저장되는지를 한자리에
정하고, 그 규칙을 시험으로 고정한다.

### 바뀌는 것

- 지금: 너비를 조절할 수단이 없어 한계값도 저장 자리도 정해져 있지 않다 → 앞으로: 네 영역의 최소·최대·
  기본 너비와 저장 자리가 한 곳에 정해지고, 조절한 값이 앱을 껐다 켜도 남는다.
- 지금: 창을 좁혔을 때 본문이 어디까지 좁아지는지 정해진 값이 없다 → 앞으로: 어떤 조절에서도 본문이
  340px 아래로 내려가지 않고, 저장된 값은 그대로 남았다가 창을 넓히면 돌아온다.

### 비용과 위험

- 이 작업만으로는 화면이 달라지지 않는다. 사용자가 드래그와 접기를 만나는 것은 같은 기능의 뒤이은
  작업들이 끝난 뒤다.
- 규칙과 저장소만 새로 생기고 기존 화면 코드와 스타일은 한 줄도 바뀌지 않으므로, 되돌리려면 새로 만든
  파일 넷을 지우면 된다.

## 현재 코드 상태

너비를 다루는 값은 지금 전부 스타일 파일에만 있다. `src/App.css` 245행이
`.app-shell { grid-template-columns: 250px minmax(0, 1fr); }`로 사이드바 250px를 박아 두고, 1309행이
창 폭 980px 이하에서 같은 자리를 210px로 바꾼다. 466행이
`.spec-workspace-layout { grid-template-columns: minmax(190px, .72fr) minmax(340px, 1.45fr) minmax(190px, .68fr); }`
로 기획서 화면 세 칸의 비율과 하한을 정하고, 416행이
`.idea-inbox-layout { grid-template-columns: minmax(300px, .85fr) minmax(360px, 1.15fr); }`로 아이디어
화면 두 칸을 정한다. 기획서가 정한 최소값 190px·300px과 본문 하한 340px은 모두 이 세 규칙이 이미 쓰고
있는 값이다.

표시 상태를 브라우저 저장소에 담는 방식은 이미 자리가 잡혀 있다.
`src/features/projects/infrastructure/browserSpecLaneCollapseStore.ts`가 그 본보기이며, 29행이
`localStorage.getItem`을 `try` 안에서 부르고 값 없음·JSON 파싱 실패·객체가 아님·배열을 전부 빈 값으로
돌리며, 69행의 저장도 실패를 삼킨다. 같은 파일 43행이 항목 하나가 깨져도 나머지 항목은 살려 읽는다.
읽기 폭 상한 620px은 `src/App.css` 531행 `.markdown-body`에, 860px은 496행과 497행에 있다.

이 저장소는 워크플로 디렉터리를 첫 키로 쓰지만, 기획서 R6은 저장 단위를 이 컴퓨터의 앱 전체로 정했다.
그래서 이 작업이 만드는 저장소는 워크플로 키를 두지 않는다.

## 완료 조건

- C1. 네 영역의 한계값 표가 한 곳에 있고 아래 값과 같다. 사이드바는 최소 190px, 최대 380px, 기본
  250px이며 창 폭 980px 이하일 때의 기본은 210px이다. 기획서 화면 왼쪽 문서 목록 패널과 오른쪽 결정
  패널은 최소 190px, 최대 420px이다. 아이디어 화면 왼쪽 목록 패널은 최소 300px, 최대 520px이다. 사이드바
  밖의 세 패널에는 기본 px 너비를 두지 않는다. 그 셋의 기본은 스타일 파일의 비율 배치이며, 값을 새로
  만들면 R11이 요구한 "지금과 같은 배치"가 깨진다. (기획서 R1, R2, R3, R11)
- C2. 드래그 값 보정 함수가 한계 밖의 값을 받으면 그 영역의 최소값 또는 최대값으로 잘라 돌려준다.
  한계 안의 값은 그대로 돌려준다. (기획서 R2)
- C3. 방향키 한 걸음 함수가 지금 너비에서 16px 늘리거나 줄인 값을 C2와 같은 한계 안으로 잘라 돌려준다.
  최소값에서 더 줄이거나 최대값에서 더 늘리면 값이 움직이지 않는다. (기획서 R12, 완료 판정 A10)
- C4. 그리는 너비 계산 함수가 창 폭, 영역별 저장된 너비, 접힌 영역 집합을 받아 화면에 그릴 px 너비를
  돌려준다. 접힌 영역은 28px이다. 저장된 너비를 그대로 그리면 가운데 본문이 340px보다 좁아지는 경우,
  저장된 값은 바꾸지 않고 돌려주는 너비만 각 영역의 최소값까지 비례해서 줄인다. 최소값까지 줄여도
  340px을 지킬 수 없으면 각 영역의 최소값을 돌려준다. 창을 다시 넓히면 같은 저장된 값에서 원래 너비가
  다시 나온다. (기획서 R9, R10, 완료 판정 A9)
- C5. 저장된 너비가 없고 접히지도 않은 영역에 대해서는 C4의 함수가 px 값을 돌려주지 않는다. 그 영역은
  스타일 파일의 비율 배치로 그려져야 하며, 계산이 값을 만들어 내면 한 번도 조절하지 않은 화면이 지금과
  달라진다. (기획서 R11, 완료 판정 A12)
- C6. 되찾은 폭 계산 함수가 한 화면에 속한 영역들의 상태를 받아, 각 영역의 기준 너비에서 지금 그리는
  너비를 뺀 값을 더해 돌려준다. 접힌 영역의 그리는 너비는 28px이고, 기준 너비를 아직 모르는 영역은 0을
  보탠다. 기준 너비는 사용자가 그 영역을 처음 조작하기 직전에 비율 배치로 그려져 있던 너비다.
  (기획서 R8, 완료 판정 A6, A12)
- C7. 읽기 폭 상한 계산 함수가 되찾은 폭을 받아 `620 + 되찾은 폭`을 620px 이상 860px 이하로 잘라
  돌려준다. 되찾은 폭이 0 이하이면 620px을 돌려준다. (기획서 R8, 완료 판정 A6, A12)
- C8. 저장소가 영역별로 조절한 너비, 접힘 여부, 기준 너비를 브라우저 저장소 항목 하나에 담는다. 접힌
  영역을 다시 펼칠 때 쓰는 너비는 조절한 너비이며, 조절한 적이 없으면 기준 너비다. 키에 프로젝트
  식별자도 워크플로 디렉터리도 넣지 않는다. 저장 단위는 이 컴퓨터의 앱 전체다.
  (기획서 R4, R6, 완료 판정 A5, A7)
- C9. 저장소 읽기가 값 없음, JSON 파싱 실패, 객체가 아닌 값, 배열, 숫자가 아닌 너비, 참거짓이 아닌
  접힘값, 브라우저 저장소 접근 실패를 전부 빈 상태로 돌리고 예외를 던지지 않는다. 영역 하나의 값이
  깨져도 나머지 영역의 값은 살려 읽는다. (기획서 R7, 완료 판정 A8)
- C10. 저장소 쓰기가 브라우저 저장소 접근 실패를 삼키고 예외를 던지지 않는다. (기획서 R7, 완료 판정 A8)
- C11. 이 작업의 변경은 선언한 파일 넷 안에서 끝난다. 기존 파일이 하나도 수정되지 않는다.
- C12. `npm run check`가 통과한다.

## 검증 절차

1. `src/features/projects/domain/panelLayout.test.ts`에 C1부터 C7까지의 시험을 쓴다. C1은 표의 여덟 개
   값을 각각 확인한다. C2는 한계 아래·한계 위·한계 안 세 경우를 확인한다. C3은 늘리기·줄이기·최소값에서
   더 줄이기·최대값에서 더 늘리기 네 경우를 확인한다.
2. C4는 세 경우를 확인한다. 넉넉한 창에서 저장된 값이 그대로 나오는 것, 좁은 창에서 본문 340px이 지켜지고
   돌려주는 값만 줄어드는 것, 같은 저장된 값으로 창을 다시 넓히면 원래 너비가 나오는 것이다. 세 번째
   확인은 저장된 값이 계산 과정에서 바뀌지 않는다는 것을 함께 잡는다.
3. C5는 저장된 값도 접힘도 없는 영역에 대해 함수가 px 값을 돌려주지 않는 것을 확인한다.
4. C6은 세 경우를 확인한다. 기준 너비를 모르는 영역만 있을 때 0이 나오는 것, 조절해 좁힌 영역이
   좁힌 만큼을 보태는 것, 접힌 영역이 기준 너비에서 28px을 뺀 만큼을 보태는 것이다.
5. C7은 되찾은 폭이 0일 때 620px, 100px일 때 720px, 400px일 때 860px에서 멈추는 것과, 음수일 때
   620px이 나오는 것을 확인한다.
6. `src/features/projects/infrastructure/browserPanelLayoutStore.test.ts`에 C8부터 C10까지의 시험을 쓴다.
   대체 저장소는 `browserSpecLaneCollapseStore.test.ts` 27행부터의 방식을 따른다. C9는 값 없음, 깨진
   JSON, 배열, 숫자가 아닌 너비, 항목 하나만 깨진 경우를 각각 확인한다. C10은 쓰기가 예외를 던지는 대체
   저장소로 확인한다.
7. `npm run check`를 통과시킨다(C12).
8. `git status`로 선언한 파일 넷 밖의 수정이 없음을 확인한다(C11).

## 범위 사전 검사

선언한 파일은 새로 만드는 넷뿐이다. 이 작업의 완료 조건이 요구하는 것은 순수 계산과 브라우저 저장소
접근이고, 둘 다 기존 파일을 고치지 않고 새 파일 안에서 끝난다는 것을 아래에서 확인했다.

`src/App.css`를 열어 보고 뺐다. 245행·416행·466행·531행이 이 작업이 표로 옮겨 적을 값들의 출처이지만,
이 작업은 그 값을 읽어 표를 만들 뿐 스타일을 고치지 않는다. 스타일 쪽을 변수로 바꾸는 편집은
TASK-S080-03과 TASK-S080-04의 몫이고, 그 두 작업이 이 파일을 선언한다. 지금 고치면 규칙만 있고 붙일
화면이 없는 상태에서 화면이 먼저 달라진다.

`src/features/projects/infrastructure/browserSpecLaneCollapseStore.ts`도 열어 보고 뺐다. 실패를 삼키는
방식과 항목 하나가 깨져도 나머지를 살리는 방식을 그대로 따르지만, 저장 키가 다르고 저장 단위도 다르다.
기존 파일에 새 영역을 얹으면 기획서 레인 접힘 상태와 패널 너비가 한 항목을 나눠 쓰게 되어, 한쪽이
깨지면 다른 쪽도 함께 날아간다.

`src/features/projects/domain/types.ts`도 확인하고 뺐다. 워크플로 문서의 자료형이 모인 자리이고 화면
표시 상태의 자리가 아니다. 새 자료형은 이 작업이 만드는 도메인 파일 안에 둔다.

기계 상태를 조건으로 삼는 측정이 이 작업에 없으므로 조용한 기계를 요구하지 않는다. 같은 기능의 다른
세 작업과 선언한 파일이 하나도 겹치지 않지만, 세 작업이 모두 이 작업의 결과를 가져다 쓰므로 순서는
의존 선언으로 정했다.

- 값 경로: C1의 한계값 표. 값을 만드는 자리는 이 작업이 새로 만드는
  `src/features/projects/domain/panelLayout.ts`의 영역 표이며 편집 대상이다. 이 값을 실어 나르는 자리와
  소비하는 자리는 아직 없다. 표를 읽어 화면에 그리는 자리는 TASK-S080-03과 TASK-S080-04가 만들고, 두
  작업의 완료 조건이 스타일 파일의 기본값과 이 표의 값이 서로 같은지를 시험으로 잡는다. 이 작업의 소비
  자리는 같은 파일의 보정·한 걸음·그리는 너비 계산 함수와 새 시험 파일뿐이고 모두 선언 안에 있다.
- 값 경로: C2·C3·C4·C5의 계산 결과. 값을 만드는 자리는 같은 도메인 파일의 함수들이고, 판정하는 자리는
  `src/features/projects/domain/panelLayout.test.ts`다. 두 자리 모두 선언 안에 있다. 화면까지 가는 다음
  홉은 이 작업 범위 밖이며, 그 홉을 만드는 작업이 자기 선언에 화면 파일을 넣는다.
- 값 경로: C6·C7의 되찾은 폭과 읽기 폭 상한. 값을 만드는 자리는 같은 도메인 파일의 두 계산 함수다.
  둘 다 px 숫자만 받고 화면 요소를 재지 않으므로, 화면 없는 시험에서 그대로 확인된다. 기준 너비를 실제로
  재는 홉과 계산 결과를 스타일에 싣는 홉은 TASK-S080-03과 TASK-S080-04가 각각 선언한다. 이 값이 최종적으로
