# 공통 규칙에 한국어 문체 절을 넣고 세 역할 계약과 버전 상수를 함께 올린다

## 결정권자 요약

공통 규칙에 한국어 문서 작성 기준을 추가했다. 앞으로 에이전트가 작성하는 아이디어와 기획서, 개발
작업, 개발 보고서는 일반적인 한국 기획·개발 문체를 사용해야 한다. 표준적인 한자어와 기술 용어는
그대로 사용할 수 있으며, 쉬워 보이게 만들기 위해 어색한 고유어로 바꾸지 않는다.
여러 의미를 대신하는 비유는 실제 행위나 결과를 나타내는 표현으로 바꾼다. 영문식 긴 대시로 문장을
습관적으로 나누지 않는 기준도 포함했다. 기존 문서의 사실은 참고하되 문체까지 따라 쓰지 않는다.
기존의 문체를 정확성이라고 인정하던 문장은 삭제했다. 세 역할은 문서를 제출하기 전에 새 기준을
확인한다. 자동 검사는 추가하지 않았고, 기존 문서와 앱 화면도 변경하지 않았다.
Rust 테스트 539개와 프런트 테스트 705개가 통과했고 타입 검사와 빌드도 성공했다. 사용자 확인 후
앱이 프로젝트 규칙을 다시 설치하면 공통 규칙 버전이 13으로 표시된다.

## 이 작업이 맡는 범위

SPEC-046의 R1·R2·R3·R4(공통 규칙 쪽)·R5·R6·R7(버전과 테스트)·R8이다. 기획서 완료 조건 1·2·3·4·7·
8·9·10·11·12를 이 작업이 처리한다.

기획서 완료 조건 5·6은 한국어 파일 계약 문서에 확장 대응표와 전후 예문을 넣는 조건이므로
TASK-131이 맡는다. 두 작업은 서로 다른 파일을 고치고, TASK-131이 이 작업을 `depends_on`으로 기다린다.

규칙 자산의 본문은 앱 실행 파일 안의 문자열 상수다. 그래서 이 작업이 고치는 파일은
`src-tauri/src/infrastructure/project_instructions.rs` 하나이고, `.workflow/rules/` 아래 설치본은
손으로 고치지 않는다. 앱이 다시 설치한다.

## 아키텍트가 고정하는 값

기획서가 "무엇을"까지 적고 남긴 값이다. 규칙 본문과 세 역할 계약과 테스트가 같은 답을 내야 하므로
여기서 정한다.

### 1. 새 절은 §9이고 공통 규칙 맨 뒤에 덧붙인다

중간에 끼워 넣지 않는다. 근거는 상호참조 개수다. `project_instructions.rs` 안에 `§4` 11건·`§5` 2건·
`§6` 3건·`§8` 7건이 있고, `docs/file-contract.md`에 `§4` 2건·`§8` 1건이 있다. 새 절을 중간에 넣으면
이 23건이 전부 다른 절을 가리키게 된다. 맨 뒤에 덧붙이면 기존 번호가 하나도 움직이지 않는다.
TASK-118이 §8을 맨 뒤에 덧붙인 것과 같은 판단이다.

R1이 요구한 "독립된 상위 절"은 이 배치로 충족된다. 요약 절 규칙(§8) 안에 넣지 않는다.

### 2. §9가 담는 다섯 가지

한 절 안에 하위 절로 나눠 적는다. 기획서의 다섯 요구사항이 모두 "에이전트가 쓰는 한국어 문장을
어떻게 쓰는가"에 대한 것이므로 한 절에 모은다.

| 하위 내용 | 기획서 근거 |
| --- | --- |
| 문장 원칙 — 주체·행동·결과를 구체적으로, 한 문장에 주장 하나, 비유는 구체어로 | R1 |
| 적용 대상 — 아이디어·기획서·개발 작업·개발 보고서 네 종류. 사용자가 직접 쓴 문서는 제외 | R1 |
| 기존 문서는 사실의 출처이지 문체의 본보기가 아니다 | R3 |
| 바꿔 쓸 낱말의 핵심 원칙과 최소 대응 예시 세 쌍 | R4 |
| 인용은 근거를 보태는 데만 쓴다 | R5 |

### 3. 최소 대응 예시는 이 세 쌍이다

기획서 R4가 정한 그대로다. 낱말을 더하거나 빼지 않는다.

| 바꿀 낱말 | 바꿔 쓸 말 |
| --- | --- |
| 착지 | 구현, 반영, 병합, 배포 |
| 닫다 | 해결, 충족, 완료 |
| 원천 | 데이터 출처, 원본 문서, 판단 기준 |

- 대응표는 금지 목록이 아니다. 뜻이 하나로 정해지는 문맥에서는 그 낱말을 쓰되 대상을 함께 적는다는
  것을 규칙 본문이 밝힌다.
- 확장 대응표와 전후 예문은 여기 넣지 않는다. TASK-131이 한국어 파일 계약 문서에 넣는다.

### 4. 규칙 본문은 영어로 쓰고 낱말만 한국어로 인용한다

공통 규칙과 세 역할 계약의 본문은 전부 영어다(기획서 확인 사실 7). 이 작업도 영어로 쓴다. 다만
대응 예시의 낱말은 한국어를 그대로 인용한다. 번역하면 규칙이 가리키는 낱말이 사라진다. 절 제목
리터럴 두 개를 한국어로 둔 전례와 같은 처리다.

### 5. §8에서 지우는 문장과 대신 넣는 문장

지금 §8 마지막에 두 문장이 이어져 있다.

> These conditions reach the summary section and nothing else. The rest of the body keeps the
> language it has now: between workers that density is precision, not a defect.

- **두 번째 문장을 지운다.** 요약 절 밖을 규칙 대상에서 빼고 현재 문체를 인정하는 문장이 이것이다.
  R2가 없애라고 한 문장이다.
- **첫 번째 문장은 남긴다.** 이 문장은 요약 절의 금지 조건이 어디까지 걸리는지만 정한다. 지우면
  금지 조건의 적용 범위가 사라지고, R2 세 번째 항목("요약 절의 기존 금지 조건은 그대로 둔다")이
  깨진다.
- **대신 넣는 문장.** 작업자용 본문도 기술적으로 상세할 수 있지만 사람이 읽을 수 있어야 하고, 그
  기준은 §9에 있다는 내용이다. R2 두 번째 항목이 요구한 대체다.

기획서 확인 사실 4가 두 문장을 함께 인용하면서 "마지막 문장"이라고 적었기 때문에 어디까지가
대상인지 한 가지로 읽히지 않는다. 위 구분은 R2의 세 항목을 모두 만족시키는 유일한 읽기다. 구현
중에 이 읽기가 틀렸다고 판단되면 고쳐 쓰지 말고 보고서에 인계 사항으로 적는다.

### 6. 세 역할 계약에 붙는 두 가지

각 계약의 `## Completion` 절에 자기 점검 한 줄을 붙이고, 문서 종류별 초점을 함께 적는다.

| 계약 | 자기 점검을 하는 시점 | 그 역할이 쓰는 문서의 초점 |
| --- | --- | --- |
| `planner.md` | 기획서를 `user_review`로 넘기기 전 | 문제, 결정, 요구사항 |
| `architect.md` | 작업을 `todo`로 남기고 멈추기 전 | 범위, 완료 조건, 검증 |
| `developer.md` | 보고서를 쓰고 작업을 `qa_waiting`으로 넘기기 전 | 변경, 검증, 위험, 사용자 확인 |

- 자기 점검의 내용은 "자기 문장이 §9를 지키는지 확인한다"이다. 점검 결과는 어떤 자격 판정에도
  들어가지 않는다는 것을 계약이 함께 적는다(R6 네 번째 항목).
- 이 초점은 에이전트가 쓰는 문서의 구성 기준이다. 세 계약 문서끼리의 중복을 줄이라는 뜻이 아니다.
  DECISION-0A67218F이 이 해석을 확정했고 R6 세 번째 항목이 같은 말을 적는다.
- 각 계약은 §9의 정의를 자기 안에 다시 쓰지 않고 §9를 가리킨다. 요약 절 의무를 §8로 가리키는 지금
  구조와 같다.

### 7. 버전은 이렇게 움직인다

| 대상 | 지금 | 뒤 |
| --- | --- | --- |
| `WORKFLOW_RULES` 본문의 `rules_version`과 `WORKFLOW_RULES_VERSION` | 12 | 13 |
| `planner.md` 본문의 `rules_version` | 7 | 8 |
| `developer.md` 본문의 `rules_version` | 7 | 8 |
| `architect.md` 본문의 `rules_version` | 6 | 7 |
| `ROLE_RULES_VERSION` | 7 | 8 |

- 세 계약의 본문이 모두 바뀌므로 셋 다 하나씩 올린다. `ROLE_RULES_VERSION`은 세 값의 최댓값이라는
  규약대로 8이다.
- **아키텍트 계약을 8이 아니라 7로 두는 것이 이 표에서 놓치면 안 되는 값이다.**
  `a_role_contract_below_the_version_constant_is_not_rewritten_every_time`이 "아키텍트 계약의 버전이
  상수보다 낮다"를 전제로 세워져 있고, 전제가 깨지면 그 검사가 아무것도 확인하지 않는다. 7 < 8이
  그 전제를 유지한다. TASK-118이 6 < 7로 둔 관계를 한 칸씩 옮기는 것이다.
- 버전 문자열을 단언하는 기존 검사는 지우지 않고 새 값으로 고친다. 지금 `rules_version: 12`가 6건,
  `rules_version: 7`이 여러 건, `rules_version: 6`이 3건 있다.

### 8. 새 문언을 단언하는 검사를 하나 더한다

기존 검사 목록에 `records_the_*_in_the_installed_rules` 형태의 검사가 여러 개 있다. 같은 형태로
하나를 더해 §9의 문언과 세 역할 계약의 자기 점검 한 줄을 단언한다. 단언 대상은 설치된 규칙 파일의
문자열이고, 문서 본문을 읽는 코드는 만들지 않는다.

## 완료 조건

1. 공통 규칙에 §9가 **맨 뒤에 덧붙어** 있고 §1~§8의 번호가 하나도 움직이지 않았다. 그 절이 고정값
   2의 다섯 가지를 모두 담는다. 적용 대상에 아이디어와 기획서, 개발 작업, 개발 보고서 네 종류가
   적혀 있다. 검증: 새 검사와 `§` 참조 개수 전후 비교. (R1·R3·R5 / 기획서 완료 조건 1)
2. 고정값 5의 두 번째 문장이 규칙 본문에서 사라졌고, 첫 번째 문장은 남아 있으며, 작업자용 본문도
   사람이 읽을 수 있어야 한다는 문장이 대신 있다. 검증: 새 검사와 본문 확인. (R2 / 기획서 완료
   조건 2)
3. 기존 문서를 문체의 본보기로 삼지 않는다는 문장이 §9에 있다. 검증: 새 검사. (R3 / 기획서 완료
   조건 3)
4. §9에 바꿔 쓸 낱말의 핵심 원칙이 있고, 고정값 3의 세 쌍이 모두 들어 있다. 대응표가 금지 목록이

5. 인용을 지워도 그 문서만으로 핵심 내용이 읽혀야 한다는 기준이 §9에 있다. 검증: 새 검사. (R5 /
   기획서 완료 조건 7)
6. 세 역할 계약의 완료 절에 자기 점검 한 줄이 있고, 고정값 6의 표대로 문서 종류별 초점이 적혀
   있다. 어느 계약도 §9의 정의를 자기 안에 다시 쓰지 않는다. 검증: 새 검사. (R6 / 기획서 완료

7. `WORKFLOW_RULES_VERSION`이 13이고 `ROLE_RULES_VERSION`이 8이며, 본문의 `rules_version`이 공통
   규칙 13·기획자 8·개발자 8·아키텍트 7이다. 검증: `cargo test`. (R7 / 기획서 완료 조건 9)
8. `a_role_contract_below_the_version_constant_is_not_rewritten_every_time`이 새 값에서 통과하고,
   아키텍트 계약의 버전이 상수보다 낮다는 전제가 유지된다. 검증: 같은 검사.

10. 이 작업이 만든 개발 작업 문서와 개발 보고서가 §9의 문장 원칙을 지킨다. 검증: 보고서를 쓴 뒤
    세션이 스스로 확인하고 그 결과를 보고서에 적는다. (기획서 완료 조건 11)
11. 조건 스크립트(`heartbeat_condition.rs`, `.workflow/rules/wf-eligible.sh`)와 앱 판정 모듈

    고쳐지지 않았다. 앱 화면 코드가 달라지지 않았다. 문서 본문을 읽거나 검사하는 코드가 추가되지
    않았다. 본문의 권장 분량이 규칙에 들어가지 않았다. 검증: `git diff --stat`으로 변경 파일이
    범위 파일 하나뿐임을 확인하고 결과를 보고서에 적는다. (R8 / 기획서 완료 조건 12)
12. 요약 절(§8)의 금지 조건과 열 줄 상한, 확인 동선 절의 기존 규칙이 달라지지 않았다. 프론트매터
    계약과 스키마 버전도 그대로다. 검증: 기존 대조 검사가 수정 없이 통과한다. (R8)
13. `cargo test --manifest-path src-tauri/Cargo.toml`과 `npm run check`가 통과한다.

## 검증 절차

1. `cargo test --manifest-path src-tauri/Cargo.toml` — 규칙 본문 단언, 버전 문자열, 설치·갱신 계획
   검사.
2. `npm run check`.
3. `git diff --stat`으로 변경 파일이 `src-tauri/src/infrastructure/project_instructions.rs`
   하나뿐임을 확인하고 결과를 보고서에 적는다. 완료 조건 11의 근거가 이 확인이다.
4. `grep -o "§[0-9]" src-tauri/src/infrastructure/project_instructions.rs | sort | uniq -c`를 변경
   전후로 비교해 §4·§5·§6·§8의 참조 개수가 그대로임을 확인한다. 완료 조건 1의 뒷부분이다.
