# 사용자 정의 규칙 파일과 적용 규칙 미리보기를 백엔드에 추가한다

## 결정권자 요약

프로젝트마다 사용자 정의 규칙 문서 하나를 안전하게 읽고 저장하는 백엔드 기능을 추가한다.
저장 전에는 실제로 기록될 파일과 역할별로 에이전트가 읽을 규칙을 정확히 보여준다.
다른 프로그램이 파일을 먼저 바꾸면 저장하지 않으며, 마이그레이션 중에도 기존 파일을 보존한다.
앱의 공통 규칙과 역할 계약은 사용자 규칙보다 항상 우선한다.
형식이 잘못된 사용자 파일은 해당 규칙만 끄고 프로젝트의 나머지 기능은 유지한다.
이 작업은 설정 화면을 만들지 않으며, 다음 프런트엔드 작업이 사용할 계약까지 제공한다.

## 목적

SPEC-048의 R1, R3, R4, R5와 R6의 백엔드 부분을 구현한다. TASK-132가 만든 관리 자산 동기화와 공용
쓰기 잠금을 사용하되, 사용자 파일은 관리 자산 목록에 포함하지 않는다. 앱 업데이트와 관리 규칙
동기화는 사용자 본문, 사용 여부, 역할 범위, 수정 시각을 바꾸지 않아야 한다.

## 파일 계약

사용자 정의 규칙은 `.workflow/rules/custom.md` 한 파일에만 저장한다. 첫 버전의 정규 형식은 다음과 같다.

```yaml
---
schema: workflow-labs/custom-rules@1
enabled: true
applies_to: [planner, architect, developer]
updated_at: 2026-08-06T10:00:00Z
---

# 프로젝트 사용자 정의 규칙

개발 보고서에는 성능 측정값과 측정 환경을 함께 적는다.
```

- 필드 순서는 위 순서를 사용하고 역할은 기획자, 아키텍트, 개발자 순으로 정규화한다.
- 줄바꿈은 LF로 정규화하며 파일 끝에는 줄바꿈 하나를 둔다.
- 본문은 UTF-8 기준 64 KiB 이하여야 한다. 탭과 줄바꿈을 제외한 C0 제어문자와 DEL은 거부한다.
- `enabled: true`일 때는 적용 역할이 하나 이상이어야 한다. 꺼진 파일은 역할 목록이 비어 있어도 된다.
- 알 수 없는 필드, 중복 역할, 잘못된 역할, 잘못된 시각, 지원하지 않는 스키마는 추측해 고치지 않는다.
- 대상이 심볼릭 링크나 일반 파일이 아닌 항목이면 따라가지 않는다. 파일을 읽거나 덮어쓰지 않고 안전
  오류로 반환한다.

파일이 없으면 `absent`, 정상 형식이면 `valid`, 현재 스키마를 해석할 수 없으면 `invalid`, 앱보다 새로운
스키마면 `future_schema`, 일반 파일이 아니면 `unsafe_file` 상태다. 정상 상태가 아니면 사용자 규칙은
적용되지 않는다. 읽을 수 있는 잘못된 파일은 원문과 구체적인 오류를 함께 반환한다. 심볼릭 링크의
대상 내용은 반환하지 않는다.

## 조회, 미리보기, 저장 계약

백엔드는 조회, 미리보기 준비, 저장을 별도 명령으로 제공한다.

### 조회

조회 결과에는 파일 상태, 파싱된 값, 정확한 파일 원문, 마지막 수정 시각, 내용 식별값이 들어간다. 내용
식별값은 파일 전체 바이트의 SHA-256을 `sha256:` 접두어가 붙은 소문자 16진수로 반환한다. 파일이 없으면
식별값은 없다. 이 값은 보안 자격 증명이 아니라 동시 수정 여부를 판정하는 값이다.

### 미리보기 준비

구조화된 초안인 사용 여부, 역할 목록, 본문을 받아 한 번 검증하고 다음 결과를 반환한다.

- 저장될 파일 전체의 정확한 문자열
- 그 문자열에 고정된 `updated_at`
- 저장 파일 전체의 SHA-256 미리보기 식별값
- 기획자, 아키텍트, 개발자별 최종 규칙 출처 목록

역할별 목록은 설치된 공통 규칙, 설치된 해당 역할 계약, 사용자 정의 규칙 순서로 구성한다. 각 항목은
출처 이름, 정확한 원문, 읽는 순서, 적용 여부와 제외 이유를 가진다. 사용자 초안이 꺼져 있거나 해당
역할을 선택하지 않았어도 세 번째 출처를 생략하지 않고 적용되지 않는 이유를 표시한다. 화면이 문자열을
이어 붙이거나 우선순위를 추정하지 않게 한다.

읽는 순서와 우선순위는 다른 개념이다. 사용자 규칙을 마지막에 읽더라도 앱의 공통 규칙과 역할 계약이
항상 우선한다. 미리보기 결과에 이 원칙을 명시한다. 설치된 공통 규칙이나 역할 계약을 일반 파일로 읽을
수 없으면 최종 규칙 미리보기는 실패하지만 사용자 파일 조회와 프로젝트 문서 조회는 계속 가능하다.

### 저장

저장 요청은 마지막 조회의 내용 식별값, 구조화된 초안, 미리보기에 고정된 시각과 미리보기 식별값을 함께
보낸다. 백엔드는 같은 정규 직렬화를 다시 실행하고 미리보기 식별값이 일치하는지 확인한다. 따라서 실제
저장 바이트는 사용자가 본 저장 파일 미리보기와 같아야 한다.

파일이 없던 조회는 내용 식별값 없음까지 비교한다. 현재 파일 전체의 식별값이 마지막 조회와 다르면
`conflict`를 반환하고 어떤 내용도 쓰지 않는다. 앱 밖 변경을 자동 병합하거나 일부 필드만 고치지 않는다.
형식 오류나 더 새로운 스키마를 읽은 뒤 사용자가 명시적으로 덮어쓰는 화면도 현재 원문의 식별값을
사용해야 하므로, 그 사이에 다시 바뀐 파일은 똑같이 보호된다.

저장은 TASK-132의 공용 마이그레이션 잠금을 계획부터 원자적 교체가 끝날 때까지 획득한다. 잠금을 얻지
못하면 `retry_required`를 반환한다. 같은 디렉터리에 새 일반 임시 파일을 배타적으로 만든 뒤 교체하고,
검증이나 쓰기 실패 시 기존 파일을 보존한다. 예상된 `saved`, `conflict`, `retry_required`는 구조화된
결과로 반환하고 예기치 않은 입출력 오류와 구분한다.

## 관리 규칙과 진입 안내

TASK-132가 파일별 버전을 분리한 뒤 다음 제공 버전으로 올린다.

- 공통 규칙 14
- 기획자 역할 계약 9
- 아키텍트 역할 계약 8
- 개발자 역할 계약 9

공통 규칙에는 앱 기본 규칙, 역할 계약, 사용자 정의 규칙, 작업 문서의 우선순위를 적는다. 세 역할
계약에는 현재 역할이 적용 대상이고 파일이 활성화된 경우에만 사용자 본문을 읽는 절차를 적는다. 사용자
규칙은 앱 소유 상태, 사용자 결정, 선점, 역할 분리, 한 세션 한 대상, 승인 전 구현 금지를 완화하지
못한다.

AGENTS와 CLAUDE의 관리 진입 안내는 같은 `.workflow/rules/custom.md`를 가리킨다. Claude 안내가 AGENTS를
불러오는 기존 구조는 유지할 수 있지만, 두 진입점에서 서로 다른 사용자 본문이나 경로를 만들면 안 된다.
사용자 파일은 관리 자산 설치 계획과 버전 비교 대상에서 제외한다.

## 변경 범위

- `custom_rules.rs`: 파일 검증, 정규 직렬화, 내용 식별값, 역할별 적용 규칙 미리보기, 원자적 저장.
- 프로젝트 도메인, 서비스, 명령, 등록 계층: 조회, 미리보기 준비, 저장 요청과 구조화된 결과.
- `project_instructions.rs`: 기본 규칙 우선순위, 역할별 읽기 조건, 공통 진입 경로, 파일별 버전 증가.
- 저장소 계층: 현재 문서 규격 확인, 공용 잠금 사용, 사용자 파일과 관리 자산의 소유 경계 유지.
- Rust 의존성 파일: 파일 전체 SHA-256 계산에 필요한 검증된 라이브러리 추가와 잠금 파일 갱신.

## 손대지 않는 것

- 설정 화면과 프런트엔드 상태
- 여러 사용자 규칙 문서, 폴더, 이름, 정렬
- 개인, 앱 전체, 조직 전체 규칙
- 조건식, 템플릿, 마켓, 가져오기와 내보내기
- 자연어 의미 분석과 충돌 자동 판정
- 실행 중인 에이전트 세션의 규칙 재주입
- Codex 승인 정책과 Claude 권한 설정

## 완료 조건

1. 파일이 없는 프로젝트는 사용자 규칙이 꺼진 상태로 조회되고 기존 프로젝트 기능이 유지된다.
2. 정규 형식 파일은 사용 여부, 적용 역할, 본문, 수정 시각, 원문, 내용 식별값을 손실 없이 반환한다.
3. 저장 파일 미리보기와 실제 저장 파일의 바이트가 같고, 역할별 미리보기가 세 출처의 순서와 적용
   여부를 정확히 구분한다.
4. 사용하지 않거나 적용 대상이 아닌 역할의 사용자 본문은 최종 적용 규칙에서 비활성으로 표시된다.
5. 앱 기본 규칙과 역할 계약의 우선순위가 공통 규칙과 세 역할 계약에 들어가며 두 진입 안내는 같은
   사용자 파일을 가리킨다.
6. 앱 기본 규칙 동기화 전후에 사용자 파일의 내용과 수정 시각이 바뀌지 않는다.
7. 마지막 조회 뒤 파일이 생성, 수정, 삭제, 교체되면 저장이 거부되고 외부 내용을 보존한다.
8. 마이그레이션 잠금을 얻지 못하면 재시도 결과를 반환하고 기존 파일을 바꾸지 않는다.
9. 저장은 일반 임시 파일과 원자적 교체를 사용하며 검증, 생성, 쓰기, 교체 실패에서 기존 파일을
   보존한다.
10. 심볼릭 링크, 잘못된 스키마와 역할, 길이 초과, 금지된 제어문자를 자동 수정하거나 따라가지 않는다.
11. 잘못된 사용자 파일이 있어도 관리 규칙 동기화와 프로젝트 문서 조회는 정상 동작한다.
12. 공통 규칙 14와 역할별 9, 8, 9를 파일별로 판단해 더 새로운 설치본을 덮어쓰지 않는다.
13. 기존 자동 검사를 삭제하거나 약화하지 않고 Rust 전체 검사가 통과한다.

## 검증 절차

1. 없음, 정상, 꺼짐, 역할별 적용, 형식 오류, 미래 스키마, 심볼릭 링크 상태를 표 기반 검사로 확인한다.
2. 정규 직렬화 결과와 미리보기 문자열, 실제 저장 바이트를 그대로 비교한다.
3. 각 역할에서 공통 규칙, 해당 역할 계약, 사용자 규칙의 원문과 적용 여부를 확인한다.
4. 조회 뒤 외부 생성, 수정, 삭제, 다른 내용으로 교체, 심볼릭 링크 교체를 수행해 내용 식별값 충돌과
   전체 무쓰기를 확인한다.
5. 공용 잠금을 먼저 획득한 상태와 저장 도중 입출력 실패를 넣어 기존 파일 보존을 확인한다.
6. 관리 규칙 동기화 전후 사용자 파일의 내용과 수정 시각을 비교한다.
7. 공통 규칙과 세 역할 계약의 설치, 낮은 버전 갱신, 더 새로운 버전 보호 검사를 실행한다.
8. `cargo test --manifest-path src-tauri/Cargo.toml`을 실행한다.

## 범위와 선행

TASK-132가 먼저 완료돼야 한다. 이 작업은 TASK-132가 만든 관리 자산 계획, 파일별 버전, 공용 쓰기
잠금과 저장소 경계를 사용하고 같은 백엔드 파일을 수정한다.

TASK-133은 이 작업과 파일 범위가 겹치지 않으므로 TASK-132 뒤에 병렬로 진행할 수 있다. 프런트엔드
사용자 규칙 상태를 연결하는 TASK-136은 TASK-133과 이 작업이 모두 끝난 뒤 시작한다.

## 확인 동선

이 작업은 화면 변경이 없는 백엔드 계약 작업이다. 설정 화면과 실제 편집 흐름은 TASK-136과 TASK-137이
연결한다.

1. 자동 검사에서 저장 파일 미리보기와 실제 저장 바이트가 같고 세 역할의 규칙 출처 순서가 같은지
   확인한다.
2. 외부 생성, 수정, 삭제, 심볼릭 링크 교체와 공용 잠금 경합에서 기존 파일을 보존하는지 확인한다.
