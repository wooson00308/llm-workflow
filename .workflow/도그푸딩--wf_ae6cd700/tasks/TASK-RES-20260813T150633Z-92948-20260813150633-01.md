# 작업마다 확인 완료와 재작업 요청을 나눠 담는 한 번의 품질 확인 제출 통로를 만든다

## 결정권자 요약

### 제안

여러 작업의 품질 확인 결과를 한 번에 보내되, 작업마다 확인 완료인지 재작업 요청인지와 그에 붙는 메모를
따로 실어 기록하는 통로를 만든다.

### 현재

지금의 일괄 기록은 확인 완료만 보낼 수 있고 메모도 전 건이 하나를 공유한다. 문제가 섞인 기능은 작업을
하나씩 열어 따로 결정해야 하고, 검토를 시작한 뒤 작업이 바뀌었는지는 아무도 확인하지 않는다.

### 변경 후

제출 한 번이 작업별 결과와 메모를 함께 나른다. 기록 직전에 각 작업이 사용자가 검토를 시작할 때와 같은
상태인지 확인하고, 그사이 달라진 작업은 기록하지 않고 달라졌다는 사실을 건별로 돌려준다.

### 사용자 결과

이 작업만으로는 화면이 달라지지 않는다. 사용자가 한 번의 제출로 완료와 재작업 요청을 함께 남기는 화면은
뒤따르는 작업이 이 통로 위에 만든다.

### 영향 범위

- 변경: 품질 확인 결과를 앱에 보내는 통로, 그 응답이 돌려주는 건별 성공과 실패 사유
- 유지: 작업별 품질 확인 기록 문서의 형식, 작업 상태 전이와 이력, 기존 단건 기록과 일괄 확인 통로, 사용자만 품질 결정을 남기는 권한

### 비용과 위험

기존 일괄 확인 통로를 지우지 않고 새 통로를 더한다. 두 통로가 같은 기록 규칙을 쓰는 자리를 계속 하나로
두지 않으면 같은 결정이 통로에 따라 다르게 기록될 수 있다.

### 결정 요청

이 작업에는 눌러 볼 화면이 없다. QA에서는 아래 검증 단계의 자동 검사가 섞인 결과의 기록, 검토 시작 뒤
달라진 작업의 거절, 일부 실패 때 성공한 건의 보존을 확인했는지를 본다.

## 범위 사전 검사

이 작업이 만드는 값은 셋이다. 작업별 결과와 메모를 담은 요청, 검토 시작 시점의 갱신 시각, 그리고 건별
성공과 실패 사유를 구분해 담은 응답이다. 저장소의 현재 코드를 열어 각 값이 어디서 생겨 어디까지 가는지
확인했다.

- 값 경로: 완료 조건 1·2의 작업별 결과와 메모는 지금 어디에도 없다. 값이 생기는 자리는
  `src-tauri/src/domain/project.rs`에 더할 요청 타입이고, 나르는 자리는 `src-tauri/src/commands/projects.rs`의
  새 명령과 `src-tauri/src/application/project_service.rs`의 위임 메서드이며, 등록하는 자리는
  `src-tauri/src/lib.rs`의 `invoke_handler` 목록이다. 실제로 기록하는 마지막 자리는
  `src-tauri/src/infrastructure/fs_project_repository.rs`의 `record_one_task_qa`인데, 이 함수는 이미
  `outcome`과 `comment`를 인자로 받고 두 값에 따라 결정 문서와 상태 전이를 나눠 쓰므로 편집하지 않는다.
  같은 파일에 목록을 도는 새 함수만 더해 그 함수를 건별로 부른다. 다섯 파일 중 기록 함수를 담은 파일까지
  넷이 편집 대상이다.
- 값 경로: 완료 조건 3의 갱신 시각 대조는 작업 문서 frontmatter의 `updated_at`에서 시작한다. 화면이 읽는
  자리는 `src-tauri/src/domain/project.rs`의 `WorkflowItemSummary`가 이미 내보내는 `updated_at`이고, 이
  필드는 그대로 쓰므로 편집하지 않는다. 요청에 실리는 자리는 새 요청 타입의 항목이고, 대조하는 자리는
  같은 파일의 새 목록 함수다. 대조는 `record_one_task_qa` 안이 아니라 그 앞에서 한다. 안에서 하면 단건
  기록 통로의 판정까지 함께 바뀌어 이 작업이 유지하겠다고 적은 것을 어긴다. 대조 방식은 같은 파일의
  `resume_one_task`가 이미 쓰는 문자 단위 비교와 같은 어법을 쓴다.
- 값 경로: 완료 조건 4·5의 건별 결과는 기존 `TaskQaBatchEntry`로는 부족하다. 그 타입은 성공 여부와 사유
  문자열만 갖고 있어, 화면이 "기록에 실패했다"와 "그사이 작업이 바뀌어 다시 확인해야 한다"를 구분할 수
  없다. 그래서 `src-tauri/src/domain/project.rs`에 실패 종류를 함께 담는 결과 항목 타입을 더한다. 기존
  타입과 기존 일괄 통로는 그대로 둔다.
- 값 경로: 완료 조건 6의 앱 화면까지 이어지는 통로는 세 자리를 지난다. 계약을 선언하는 자리는
  `src/features/projects/domain/types.ts`의 `ProjectGateway`이고, 명령을 부르는 자리는
  `src/features/projects/infrastructure/tauriProjectGateway.ts`이며, 화면이 쓰는 동작으로 감싸는 자리는
  `src/features/projects/application/useProjectWorkspace.ts`다. 세 자리 모두 값을 그대로 나르지 않고 이
  통로를 위한 선언과 호출을 새로 더해야 하므로 셋 다 편집 대상이다. 훅이 내보내는 동작은 이 작업에서는
  아직 아무 화면도 부르지 않는다. 부르는 화면은 뒤따르는 작업이 만들며, 통로를 화면과 같은 작업에 넣으면
  Rust 계층과 화면이 한 검토 단위에 섞여 되돌리기 어려워진다.
- 검토했으나 제외한 것: `src/App.tsx`는 이 작업에서 열지 않는다. 이 작업의 어떤 완료 조건도 화면을 지나지
  않고, 훅이 내보낸 동작을 화면에 연결하는 것은 대기열 화면을 만드는 작업의 완료 조건이다.
- 검토했으나 제외한 것: `src/features/projects/components/DevelopmentBoard.tsx`는 넣지 않는다. 기존 일괄
  확인 통로를 그대로 두므로 그 화면의 동작은 이 작업의 변경으로 달라지지 않는다.

## 현재 상태

앱은 품질 확인을 두 통로로 기록한다. 단건 통로는 작업 하나에 확인 완료 또는 수정 요청을 남기고, 일괄
통로는 파일 이름 목록과 메모 하나를 받아 전 건을 확인 완료로만 기록한다. 두 통로 모두 결정 문서 작성과
작업 문서의 상태 전이를 `record_one_task_qa` 하나에서 처리한다.

일괄 통로에는 작업별 결과를 나눠 담을 자리가 없고, 작업별 메모를 담을 자리도 없다. 요청을 받은 시점의
작업 상태만 확인할 뿐 사용자가 검토를 시작한 시점과 비교하지 않는다.

## 변경 범위

1. 요청 타입을 더한다. 요청은 워크플로 디렉터리 하나와 항목 목록을 갖고, 항목은 파일 이름, 결과, 메모,
   검토를 시작할 때 읽은 갱신 시각 넷을 갖는다. 결과는 기존 확인 완료와 수정 요청 두 값만 쓴다.
2. 결과 항목 타입을 더한다. 항목은 파일 이름, 작업 식별자, 기록 성공 여부, 실패 종류, 실패 사유를 갖는다.
   실패 종류는 다음 셋으로 고정한다.
   - 검토 시작 뒤 작업이 바뀌었다
   - 작업이 더 이상 품질 확인 대기 상태가 아니다
   - 그 밖의 기록 실패
3. 저장소에 목록을 도는 새 함수를 더한다. 항목마다 다음 순서로 처리한다.
   - 작업 문서를 읽어 갱신 시각을 요청에 실린 값과 문자 단위로 비교한다. 다르면 기록하지 않고 첫 번째
     실패 종류로 결과를 남긴다.
   - 같으면 기존 기록 함수를 그대로 부른다. 그 함수가 품질 확인 대기가 아니라는 이유로 실패하면 두 번째
     실패 종류로, 다른 이유로 실패하면 세 번째 실패 종류로 결과를 남긴다.
   - 한 항목이 실패해도 다음 항목으로 계속 진행한다. 프로젝트 전체를 읽지 못하는 경우에만 요청 전체가
     실패한다.
4. 메모 검사는 항목마다 따로 한다. 수정 요청인데 메모가 비어 있으면 그 항목만 실패로 남기고 다른 항목은
   그대로 기록한다. 메모 길이 상한은 기존 단건 통로와 같은 2000자를 쓴다.
5. 응답은 프로젝트 요약과 요청 순서 그대로의 결과 목록을 함께 돌려준다.
6. 명령을 등록하고, 앱 화면 계층의 계약 선언과 호출과 훅 동작을 차례로 더한다. 훅 동작은 호출 자체가
   실패하면 값이 없음을 돌려주고, 건별 실패는 결과 목록에 담아 그대로 돌려준다. 건별 실패를 화면 전체
   오류 문구로 올리지 않는다. 기존 일괄 확인 동작이 쓰는 어법과 같다.
7. 기존 단건 통로와 일괄 확인 통로는 이름도 동작도 바꾸지 않는다.

## 범위 밖

- 품질 확인 화면, 대기열, 세션과 제출 전 검토 화면
- 기기 내 임시 검토 저장
- 결정 문서의 스키마와 필드 구성 변경
- 작업 상태 값의 추가나 의미 변경
- 기존 일괄 확인 통로의 제거나 동작 변경
- 개발 화면과 오늘 화면의 진입점 변경

## 완료 조건

1. 확인 완료와 수정 요청이 섞인 목록을 한 번 보내면 작업마다 그 결과에 맞는 품질 확인 결정 문서가 하나씩
   생기고, 확인 완료 작업은 완료로, 수정 요청 작업은 준비로 상태가 바뀌며 각 작업의 이력에 그 전이가
   하나씩 남는다.
2. 작업마다 서로 다른 메모를 실어 보내면 각 결정 문서에 그 작업의 메모가 담긴다. 다른 작업의 메모가
   섞이지 않는다.
3. 요청에 실린 갱신 시각이 작업 문서의 현재 값과 다르면 그 작업에는 결정 문서가 생기지 않고 상태도 바뀌지
   않으며, 결과 항목의 실패 종류가 검토 시작 뒤 작업이 바뀌었음을 가리킨다.
4. 목록의 일부만 실패해도 나머지는 기록된다. 결과 목록은 요청과 같은 순서이고, 성공한 항목은 성공으로,
   실패한 항목은 실패 종류와 사유를 함께 담아 돌아온다.
5. 이미 완료된 작업이 목록에 섞여 있으면 그 항목만 품질 확인 대기가 아니라는 실패 종류로 돌아오고, 같은
   요청의 다른 항목은 정상 기록된다.
6. 수정 요청 항목의 메모가 비어 있으면 그 항목만 실패하고 같은 요청의 확인 완료 항목은 기록된다.
7. 앱 화면 계층의 훅이 새 동작 하나를 내보내며, 호출이 실패하면 값 없음을, 성공하면 건별 결과 목록을
   돌려준다. 건별 실패가 화면 전체 오류 문구를 채우지 않는다.
8. 기존 단건 기록과 기존 일괄 확인의 동작과 검사가 이 변경 뒤에도 그대로 통과한다.
9. 품질 확인 결정 문서의 스키마 값, 결정을 사용자가 남긴 것으로 적는 방식, 작업 상태 값 목록이 변경 전과
   같다.

## 검증 단계

1. 저장소 계층 검사를 추가하고 실행한다. 완료 조건 1부터 6까지를 각각 확인한다.
   명령: `cd src-tauri && cargo test`
2. 앱 화면 계층의 훅 검사를 추가하고 실행한다. 완료 조건 7을 확인한다.
   명령: `npx vitest run src/features/projects/application/useProjectWorkspace.test.ts`
3. 타입 검사를 실행해 계약 선언과 호출과 훅이 어긋나지 않는지 확인한다.
   명령: `npm run typecheck`
4. 저장소 전체 검사를 실행해 기존 동작이 유지되는지 확인한다. 완료 조건 8을 확인한다.
   명령: `npm test`
5. 완료 조건 9는 결정 문서를 만드는 형식 문자열과 상태 값 목록을 변경 전후로 비교해 확인한다. 검사
   코드에서 생성된 결정 문서의 스키마 줄과 작성자 줄을 문자열로 단언한다.

## 확인 동선

이 작업에는 눌러 볼 화면이 없다. 통로만 만들었고 이 통로를 부르는 화면은 뒤따르는 작업이 만들기
때문에, 앱을 열어도 달라진 자리가 없다. 확인은 자동 검사가 대신했고, 확인 완료 도장은 아래 수치를
믿는다는 뜻이다.

같은 수치를 직접 확인하려면 저장소 최상위에서 다음을 실행한다.

1. `cd src-tauri && cargo test` → 751건 통과. 이 작업이 더한 네 건은
   `cargo test submission`으로만 골라 실행할 수 있고 4건 모두 통과한다. 각각 섞인 결과의 기록과
   메모 분리, 검토 시작 뒤 바뀐 작업의 거절, 대기 상태가 아닌 항목만의 실패, 재작업 요청 메모
   누락 항목만의 실패를 확인한다.
2. `npx vitest run src/features/projects/application/useProjectWorkspace.test.ts` → 통과. 이 작업이
