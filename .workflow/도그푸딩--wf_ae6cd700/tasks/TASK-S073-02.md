# 아키텍트 역할 계약이 구성 오류 기능을 맡는 절차를 적는다

## 결정권자 요약

### 제안

아키텍트가 구성 확인 필요 기능을 맡았을 때 무엇을 고칠 수 있고 무엇을 그대로 두어야 하는지, 문서로는
못 고칠 때 무엇을 남기는지를 역할 계약과 공통 규칙에 적는다.

### 현재

아키텍트 계약이 다루는 대상은 사용자 확인 반려, 작업 정의 오류, 중단된 구성, 새 승인 넷이다. 구성
확인 필요 기능은 그 어디에도 없다. 계약이 말하지 않는 대상을 세션이 받으면 무엇을 고쳐도 되는지
스스로 정하게 되고, 구성 버전을 올리거나 새 기능 문서를 만드는 식으로 사용자의 판단 기록을 흔들 수
있다.

### 변경 후

세션은 이 대상을 받았을 때 할 일을 계약에서 읽는다. 같은 기능 식별자와 같은 구성 버전을 유지한 채
기능 문서와 그 기능의 작업 문서만 고치고, 사용자 결정 문서와 승인 기록과 판정 규칙에는 손대지
않는다. 문서 쪽에 고칠 곳이 없으면 그 판단을 기능 문서에 남기고 보고서를 쓴 뒤 손을 뗀다. 그 표시가
있는 기능은 같은 구성 버전에서 다시 자동으로 잡히지 않으므로, 원인이 문서 밖에 있는 기능이 같은
시도를 반복하며 실행 한도를 소모하지 않는다.

### 비용과 위험

이 작업은 규칙 문서의 본문만 바꾼다. 앱 화면, 상태 계산, 대상 판정은 건드리지 않는다. 규칙 판
번호가 올라가면 앱이 프로젝트에 설치된 규칙 파일을 최신 판으로 갱신하는데, 그 갱신 경로는 이미
있고 사용자가 직접 쓴 문서는 대상이 아니다. 되돌리면 지금의 계약 본문으로 돌아간다.

## 현재 코드 상태

설치되는 규칙 본문의 정본은 `src-tauri/src/infrastructure/project_instructions.rs` 하나다. 공통 규칙
본문은 46행의 `WORKFLOW_RULES`, 아키텍트 계약 본문은 577행의 `ARCHITECT_RULES`이며, 두 본문이 쓰는
판 번호는 21행의 `WORKFLOW_RULES_VERSION`(지금 31)과 23행의 `ARCHITECT_RULES_VERSION`(지금 20)이다.
판 번호는 각 본문의 프론트매터 `rules_version` 줄에도 같은 수로 적혀 있다.

아키텍트 계약에서 대상을 정하는 절은 `## Eligibility`와 `## Choose in this order` 둘이다. 지금
적힌 대상은 현재 구성 버전의 사용자 확인 반려, 처리되지 않은 과거 작업 정의 수정 요청, 정의 오류로
막힌 작업, 선점이 끊긴 준비 중 기능, 파생 기능이 없는 최신 승인 다섯이다. `## Claim first` 절이
대상 종류마다 어떤 식별자를 선점하는지 적는다.

공통 규칙에서 기능 문서를 다루는 절은 `### Work groups and group QA`이고, 파일 계약은 `## 6. Preserve
the file contract` 절이 담는다. 기능 문서의 필수 값과 두 상태 값, 두 확인 모드 값이 그 절에 적혀
있고, 선택 필드는 지금 `source_qa_decision_id` 하나만 언급된다.

같은 파일의 시험이 설치된 본문을 다시 읽어 문장이 들어 있는지 본다. 1512행부터 2406행까지가 계약
주제마다 하나씩 있고, 2408행의 시험이 역할별 판 번호가 서로 독립적으로 오르는지 본다. 1770행부터
1773행까지가 네 판 번호를 수로 직접 대조한다.

TASK-S073-01이 정한 두 이름을 이 계약이 그대로 쓴다. 기능 문서 프론트매터의 선택 필드
`configuration_unresolved_revision`과 본문 절 `## 사람의 판단이 필요한 이유`다.

## 변경 범위

- 아키텍트 계약의 대상 목록에 구성 확인 필요 기능을 더한다. 선점이 걸리지 않은 것만 대상이며, 선점
  판정은 다른 대상과 같다.
- 대상 순서 절에 이 대상의 자리를 적는다. 사용자 확인 반려 다음이고 작업 정의 수정보다 앞이다.
- 선점 절에 이 대상은 기능 식별자로 선점한다고 적는다.
- 이 대상을 다루는 절을 새로 쓴다. 다음을 담는다.
  - 같은 기능 식별자를 유지하고 새 기능 문서를 만들지 않는다.
  - 구성 버전을 올리지 않는다. 이것은 사용자 반려에 답하는 재작업이 아니다.
  - 고칠 수 있는 범위는 그 기능 문서와 그 기능에 속한 작업 문서다. 사용자 결정 문서, 승인 기록,
    판정 규칙 자체는 바꾸지 않는다.
  - 문서를 고쳐 판정 조건을 충족시키면 기능은 평소 흐름으로 돌아간다.
  - 문서 쪽에 고칠 곳이 없다고 판단하면 기능 문서 프론트매터에
    `configuration_unresolved_revision`을 그 기능의 현재 구성 버전과 같은 수로 적고, 본문에
    `## 사람의 판단이 필요한 이유` 절을 그 글자 그대로 두어 사용자가 무엇을 판단해야 하는지를 적고,
    같은 판단을 보고서에 남긴 뒤 기능을 그대로 둔다. 그 표시가 있는 동안 같은 구성 버전의 같은
    기능은 다시 자동 대상이 되지 않는다.
  - 한 세션은 한 번만 시도한다. 같은 대상을 다시 잡아 반복하지 않는다.
- 공통 규칙의 기능 문서 절과 파일 계약 절에 선택 필드 `configuration_unresolved_revision`과 본문 절
  `## 사람의 판단이 필요한 이유`를 적는다. 필드가 없는 기존 문서는 그대로 유효하다는 것도 함께
  적는다.
- 두 판 번호를 하나씩 올리고 본문 프론트매터의 같은 값도 함께 올린다.

## 범위 밖

- 앱의 대상 판정과 조건 스크립트를 고치는 일. TASK-S073-03이 맡는다.
- 상태 계산이 그 필드와 절을 읽는 일. TASK-S073-01이 맡는다.
- 기획자와 개발자 계약을 고치는 일. 이 기획서에는 두 역할의 변경분이 없다.
- 이미 설치된 프로젝트의 규칙 파일을 이 작업이 직접 고치는 일. 갱신은 앱의 관리 자산 동기화가 한다.

## 완료 조건

- C1. 설치된 아키텍트 계약에 구성 확인 필요 기능이 대상 조건으로 적혀 있고, 선점이 걸린 기능은
  대상이 아니라는 문장이 함께 있다. (기획서 R-11, R-12)
- C2. 설치된 아키텍트 계약의 대상 순서가 사용자 확인 반려, 구성 확인 필요 기능, 작업 정의 수정
  순서로 적혀 있다. (기획서 선택한 기본값, 인수 조건 9)
- C3. 설치된 아키텍트 계약에 같은 기능 식별자를 유지하고 새 기능 문서를 만들지 않는다는 문장이
  있다. (기획서 R-13)
- C4. 설치된 아키텍트 계약에 구성 버전을 올리지 않는다는 문장이 있다. (기획서 R-14)
- C5. 설치된 아키텍트 계약에 고칠 수 있는 범위가 그 기능 문서와 그 기능의 작업 문서이고, 사용자 결정
  문서와 승인 기록과 판정 규칙은 바꾸지 않는다는 문장이 있다. (기획서 R-15, 인수 조건 12)
- C6. 설치된 아키텍트 계약에 문서를 고쳐 판정 조건을 충족시키면 기능이 평소 흐름으로 돌아간다는
  문장이 있다. (기획서 R-16, 인수 조건 10)
- C7. 설치된 아키텍트 계약에 고칠 곳이 없을 때 남기는 세 가지가 적혀 있다. 프론트매터 필드
  `configuration_unresolved_revision`, 본문 절 `## 사람의 판단이 필요한 이유`, 보고서다. 그리고 한 번
  시도해 풀리지 않으면 같은 구성 버전에서 다시 자동 대상이 되지 않는다는 문장이 함께 있다.
  (기획서 R-17, R-18, 인수 조건 11)
- C8. 설치된 공통 규칙에 그 선택 필드와 본문 절이 적혀 있고, 필드가 없는 기존 기능 문서가 그대로
  유효하다는 문장이 함께 있다.
- C9. 공통 규칙과 아키텍트 계약의 판 번호가 각각 하나씩 올랐고, 본문 프론트매터의 값과 상수 값이
  같다. 기획자와 개발자 계약의 판 번호와 본문은 바뀌지 않았다.
- C10. 규칙 갱신 경로가 지금과 같이 동작한다. 앞 판이 설치된 프로젝트를 열면 새 판으로 갱신되고,
  더 높은 판이 설치돼 있으면 내려쓰지 않는다.

## 검증 절차

1. `cargo test --manifest-path src-tauri/Cargo.toml project_instructions`로 규칙 설치 시험을 돌린다.
   C1부터 C8까지를 덮는 시험을 설치된 본문을 읽어 문장을 대조하는 기존 방식으로 새로 넣고 통과시킨다.
2. 판 번호를 수로 대조하는 기존 시험을 새 값으로 맞추고, 역할별 판 번호가 독립적으로 오르는지 보는
   시험과 앞 판 갱신·내려쓰기 거부 시험이 통과하는지 확인한다. C9와 C10이 여기서 확인된다.
3. `cargo test --manifest-path src-tauri/Cargo.toml`로 백엔드 전체를 돌려 회귀가 없는지 본다.
4. `cargo fmt --manifest-path src-tauri/Cargo.toml --check`와
   `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings`를 통과시킨다.

## 범위 사전 검사

선언한 파일은 하나다. 규칙 본문과 판 번호와 그 본문을 읽는 시험이 모두 이 파일 안에 있어서, 완료
조건이 요구하는 편집이 밖으로 나가지 않는다.

`src-tauri/src/infrastructure/managed_project_assets.rs`를 살펴보고 뺐다. 이 파일은
`project_instructions.rs`가 낸 자산 계획을 받아 설치와 되돌리기를 수행하며, 본문이나 판 번호를 직접
들고 있지 않다. 판 번호는 계획에 실려 오므로 값이 올라도 이 파일은 그대로 동작한다.
`docs/file-contract.md`도 살펴보고 뺐다. 이 문서에는 작업 그룹 프론트매터를 적은 절이 없어서, 새 선택
필드를 더할 자리가 없다. 문서에 절을 새로 만드는 일은 이 기획서가 요구하지 않았다.
`.workflow/rules/` 아래 설치본도 대상이 아니다. 그 파일들은 앱이 관리하는 자산이고 세션이 직접 쓰는
자리가 아니다.

- 값 경로: C1부터 C7까지의 계약 문장. 만드는 자리는 `project_instructions.rs` 577행의
  `ARCHITECT_RULES` 본문이고 편집 대상이다. 전달은 같은 파일의 자산 계획이 본문 문자열을 그대로
  담아 나가므로 값이 바뀌지 않고 지나간다. 소비 자리는 설치된 `.workflow/rules/roles/architect.md`를
  읽는 아키텍트 세션이고, 같은 파일의 시험이 설치 결과를 읽어 문장을 대조한다. 시험도 이 파일 안에
  있어 함께 편집한다.
- 값 경로: C8의 공통 규칙 문장. 만드는 자리는 같은 파일 46행의 `WORKFLOW_RULES` 본문이고 편집
  대상이다. 나머지 경로는 위와 같다.
- 값 경로: C9의 판 번호. 만드는 자리는 21행과 23행의 두 상수이고 편집 대상이다. 같은 값이 두 본문의
  프론트매터 줄에도 글자로 적혀 있어 함께 고친다. 소비 자리는 설치 판정과 1770행부터 1773행까지의
  수 대조 시험이며, 시험도 이 파일 안에 있다. 기획자와 개발자 상수는 건드리지 않는다.
- 값 경로: C10의 갱신 경로. 2443행과 2470행의 앞 판 갱신 시험, 2513행의 내려쓰기 거부 시험이 판
  번호를 값으로 받아 판정하므로 편집할 자리가 없다. 값이 오른 뒤에도 통과하는지만 확인한다.
