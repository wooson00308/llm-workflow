# 세 화면이 사용자 차례가 아닌 기능에 문제와 처리 주체를 함께 보여준다

## 결정권자 요약

### 제안

기능 목록에서 사용자가 지금 할 일이 없는 상태의 기능마다 무엇이 문제이고 누가 처리하며 사용자가 할
일은 없다는 사실을 상태 이름과 함께 보여준다.

### 현재

목록은 상태 이름 하나만 보여준다. 구성 확인 필요라는 이름을 읽은 사용자는 자기더러 무엇을 확인하라는
것인지 알 수 없다. 확인이라는 낱말이 사용자가 하는 품질 확인과 같은 낱말이어서, 자기 차례라고
읽히기까지 한다. 구성 중단 의심과 개발 막힘도 처리 주체를 이름에 담고 있지 않다.

### 변경 후

목록을 훑는 것만으로 자기 차례인 항목과 아닌 항목이 갈린다. 자기 차례가 아닌 항목에는 문제와 처리
주체와 지금 할 일이 없다는 사실이 한자리에 있고, 구성 확인 필요 기능에는 어떤 조건이 맞지 않았는지가
함께 붙는다. 아키텍트가 문서로는 못 고친다고 남긴 기능에서는 사용자가 무엇을 판단해야 하는지가
보인다. 확인 시작 입구는 지금처럼 사용자 QA 대기 기능에만 붙는다.

### 비용과 위험

새로 붙는 자리는 읽는 자리이고 누르는 자리가 아니다. 목록의 기존 동작과 확인 시작 입구는 그대로
두므로 사용자가 지금 하던 조작이 달라지지 않는다. 사유를 만들지 못한 기능에서도 목록이 그대로 보이고
그 기능이 목록에서 사라지지 않는다. 되돌리면 지금의 이름 하나짜리 표시로 돌아간다.

## 현재 화면 상태

기능 상태를 보여주는 자리는 넷이고 파일은 셋이다.

`src/features/projects/components/DevelopmentBoard.tsx`의 기능 레인이 첫째다. 438행이 상태 이름을
알약 모양으로 그리고, 431행이 사용자 QA 대기일 때만 확인 시작 입구를 대신 그린다. 274행에도 작업
상세 안에 같은 알약이 있다. 상태 이름 표는 508행, 정렬 우선순위는 505행이다.

`src/features/projects/components/qa/QaWorkbench.tsx`가 둘째와 셋째다. 준비 중인 기능 목록은 23행이
고른 기능들을 그리며, 항목마다 상태 이름 하나만 보여준다. 확인 도중 상태가 바뀌어 열 수 없게 된
기능 화면은 137행의 `QaFeatureHeld`이고, 상태 이름을 넣은 문장 하나를 보여준다. 상태 이름 표는
154행이다.

`src/features/projects/components/SpecWorkspace.tsx`가 넷째다. 348행이 기능 상태 이름과 작업 수를 한
줄로 보여주고, 상태 이름 표는 375행이다.

모양은 `src/App.css` 689행부터 702행까지가 상태별 알약 색을 정한다. 품질 확인 화면의 목록 모양은
`src/features/projects/components/qa/QaWorkbench.css` 17행과 20행이다.

이 프로젝트의 화면 관례에서 알약은 입구 표시로 쓰이고 있다. 그래서 사용자에게 처리를 요구하지 않는
설명은 알약이나 버튼이 아닌 형태로 세운다.

TASK-S073-01이 화면에 값을 내려준다. 사유 목록, 사람 판단 필요 상태, 사람 판단 거리 셋이다. 이
작업은 그 값을 사용자 문장으로 옮기는 일만 하며 문서를 다시 읽지 않는다.

## 변경 범위

- 사용자 행동이 없는 상태의 설명을 한 벌 만들어 세 화면이 함께 쓴다. 대상 상태는 구성 확인 필요,
  구성 중단 의심, 개발 막힘, 사람 판단 필요 넷이다. 설명은 무엇이 문제인지, 누가 처리하는지, 지금
  사용자가 할 일은 없다는 사실 셋을 담는다.
- 처리 주체는 상태마다 정한다. 구성 확인 필요와 구성 중단 의심은 아키텍트가, 개발 막힘은 개발자가
  맡는다고 사용자 언어로 적는다. 사람 판단 필요는 사용자가 판단할 차례라고 적고, 그 아래에 판단할
  내용을 함께 보여준다.
- 구성 확인 필요와 사람 판단 필요 기능에는 사유 목록을 사용자 문장으로 옮겨 함께 보여준다. 목록에서는
  한 줄로 보여주고, 해당하는 조건이 여럿이면 전부 보여준다. 목록이 비어 있으면 사유 없이 상태와 처리
  주체만 보여준다.
- 네 자리 모두에 적용한다. 개발 보드의 기능 레인, 품질 확인 화면의 준비 중인 기능 목록, 확인 도중
  열 수 없게 된 기능 화면, 기획서 화면의 기능 상태다.
- 설명 자리의 모양을 확인 시작 입구와 구분되게 한다. 누르는 자리로 보이지 않게 하고, 알약이나 버튼이
  아닌 형태로 세운다. 사유를 더 보게 하는 펼침은 두어도 되지만 그 자리가 처리를 요구하지 않는다.
- 문구에는 내부 상태 이름, 파일 경로, 코드 이름을 그대로 쓰지 않는다.

## 범위 밖

- 사유를 만드는 일과 상태를 계산하는 일. TASK-S073-01이 맡는다.
- 사람 판단 필요 기능을 홈 화면의 내 선택 대기 목록에 넣거나 앱 안에 새 입구를 만드는 일. 기획서
  R-01이 사용자 행동이 있는 상태를 늘리지 않는다고 정했다.
- 사용자 QA 대기 기능의 확인 시작 입구와 확인 절차 화면을 바꾸는 일.
- 개발 작업 단위의 상태 표시를 바꾸는 일. 이 작업이 다루는 것은 기능 단위 상태다.
- 아키텍트 구성 중, 개발 중, 아키텍트 재분류 대기, 완료 상태에 설명을 붙이는 일. 기획서가 대상을 세
  상태로 한정했고 사람 판단 필요가 이번에 더해진 넷째다.

## 완료 조건

- C1. 구성 확인 필요 기능을 개발 보드에서 보면 상태 이름과 함께 무엇이 문제이고 누가 처리하며
  사용자가 지금 할 일은 없다는 문장이 상세를 열지 않아도 보인다. (기획서 R-02, R-03, 인수 조건 1)
- C2. 같은 기능을 품질 확인 화면의 준비 중인 기능 목록에서 보면 같은 세 가지가 보인다.
  (인수 조건 2)
- C3. 구성 중단 의심 기능과 개발 막힘 기능에서도 같은 세 가지가 보이고, 처리 주체가 상태에 맞게
  나온다. (인수 조건 3)
- C4. 사용자 QA 대기 기능은 지금과 같이 확인 시작 입구로 보이고, 사용자가 할 일이 없다는 설명이
  붙지 않는다. (인수 조건 4)
- C5. 사유가 둘 이상인 기능에서 사유가 둘 이상 보이고, 하나로 합쳐지지 않는다. (기획서 R-09,
  인수 조건 5)
- C6. 사유 목록이 빈 기능에서도 목록이 그대로 보이고 상태와 처리 주체가 표시된다. 화면이 멈추거나 그
  기능이 목록에서 사라지지 않는다. (기획서 R-10, 인수 조건 6)
- C7. 사람 판단 필요 기능에서 사람의 판단이 필요하다는 사실과 판단할 내용이 함께 보인다. 판단할
  내용이 비어 있으면 그 사실만 보이고 화면이 멈추지 않는다. (기획서 R-18, 인수 조건 11)
- C8. 확인 도중 상태가 바뀌어 열 수 없게 된 기능 화면에서도 같은 설명이 보인다. (기획서 R-06)
- C9. 기획서 화면의 기능 상태 자리에서도 같은 설명이 보인다. (기획서 R-06)
- C10. 설명 자리는 확인 시작 입구와 구분되는 모습이고, 누르면 확인이 시작되는 자리가 아니다.
  (기획서 R-04)
- C11. 화면에 나오는 문구에 내부 상태 이름, 파일 경로, 코드 이름이 그대로 나타나지 않는다.
  (기획서 R-05, 인수 조건 14)
- C12. 사람 판단 필요 기능이 홈 화면의 내 선택 대기 목록에 들어가지 않는다. 그 목록은 지금과 같이
  기획서 승인과 사용자 QA 대기만 담는다. (기획서 R-01)

## 검증 절차

1. `npm run test`로 화면 시험을 돌린다. C1부터 C12까지를 덮는 시험을 세 화면의 기존 시험 파일에
   넣고 통과시킨다. C12는 홈 화면 시험 파일에서 확인한다.
2. `npm run check`로 타입 검사와 화면 시험과 생산 빌드를 함께 통과시킨다.
3. 앱을 띄워 개발 보드, 품질 확인 화면, 기획서 화면을 눈으로 확인한다. 설명 자리가 확인 시작 입구와
   구분되는지, 목록이 좁아졌을 때 문장이 잘리지 않는지, 웹킷에서 같은 모습인지를 본다. 확인한 화면을
   보고서에 적는다.

## 범위 사전 검사

선언한 아홉 파일은 상태를 그리는 화면 셋과 그 시험 셋, 홈 화면 시험 하나, 모양을 정하는 스타일
파일 둘이다. 네 자리 모두가 이 셋 안에 있고, 완료 조건이 요구하는 편집이 밖으로 나가지 않는다.

그룹 밖 순서가 한 자리에 붙는다. 공용 스타일 파일을 지금 TASK-S068-01과 TASK-S071-03이 함께
선언하고 있어, 두 작업 뒤로 두었다. 두 작업 모두 이미 진행 중인 화면 사슬에 속하고 이 작업은 그
사슬과 다른 화면을 고치므로, 먼저 가던 쪽을 보내고 그 뒤에 붙는다.

`src/features/projects/components/WorkspaceShell.tsx`를 살펴보고 본문은 뺐다. 114행이 사용자 QA 대기
기능만 골라 내 선택 대기 목록을 만들고, 791행과 817행은 완료 계열만 고른다. C12가 요구하는 것은 새
상태가 그 목록에 들어가지 않는 것인데, 지금 조건이 이미 그 답을 내므로 본문에 고칠 자리가 없다.
시험 파일만 선언해 그 사실을 붙든다.
`src/features/projects/components/agents/AgentRunDashboard.tsx`도 살펴보고 뺐다. 635행이 사용자 QA
대기만 고르며 상태 이름 표를 들고 있지 않다.
`src/features/projects/domain/types.ts`도 살펴보고 뺐다. 화면이 읽는 세 값은 TASK-S073-01이 이미 그
파일에 적어 두므로 이 작업에서 계약을 고칠 것이 없다.
`src/features/projects/components/qa/QaFlowReview.tsx`도 살펴보고 뺐다. 이 파일은 열린 기능의 확인
절차를 그리며 상태 이름을 보여주지 않는다. 확인 절차 화면은 이 작업의 대상이 아니다.

- 값 경로: C1부터 C3까지, C5, C6의 문제와 처리 주체와 사유. 값을 만드는 자리는 TASK-S073-01의 상태
  계산이고, 화면 계약인 `types.ts`의 기능 요약이 사유 목록을 그대로 실어 온다. 두 자리 모두 이
  작업에서는 읽기만 한다. 옮기는 자리는 세 화면의 상태 이름 표 옆에 두는 설명 한 벌이며, 세 파일
  모두 편집 대상이다. 소비 자리는 개발 보드 438행의 기능 레인, 품질 확인 화면의 준비 중인 기능 목록,
  기획서 화면 348행이고 셋 다 편집 대상이다.
- 값 경로: C7의 사람 판단 거리. 만드는 자리는 TASK-S073-01의 본문 절 판독이고 화면 계약이 문자열
  하나로 실어 온다. 이 작업은 그 값이 비었을 때와 있을 때를 갈라 그리는 자리를 세 화면에 만들며,
  세 파일 모두 편집 대상이다.
- 값 경로: C4와 C10의 입구 구분. 개발 보드 431행이 사용자 QA 대기일 때만 확인 시작 입구를 그리는
  분기를 이미 갖고 있어 그 조건은 바꾸지 않는다. 설명은 그 분기의 반대편에만 붙이므로 편집은 같은
  파일 안에서 끝난다. 모양은 `src/App.css` 689행 아래의 알약 규칙과 나란히 설명용 규칙을 두고, 품질
  확인 화면의 목록 모양은 그 화면의 스타일 파일에 둔다. 두 스타일 파일 모두 편집 대상이다.
- 값 경로: C8의 열 수 없게 된 기능 화면. `QaWorkbench.tsx` 137행의 화면이 상태 이름만 쓰고 있으므로
  같은 설명 한 벌을 여기서도 부르도록 편집한다. 같은 파일 안이다.
- 값 경로: C11의 문구. 화면이 내려받는 값은 상태 값과 사유 값이라는 기계 이름이고, 사용자에게 보이는
  문장은 이 작업이 만드는 설명 한 벌에서만 나온다. 기계 이름이 그대로 그려지는 자리가 없는지를 세
  화면의 시험에서 확인한다.
- 값 경로: C12의 내 선택 대기 목록. 만드는 자리는 `WorkspaceShell.tsx` 114행이고 사용자 QA 대기만
  고르므로 편집하지 않는다. 확인은 그 화면의 시험 파일에서 하며, 그 파일만 선언했다.
