# 기획서와 아이디어 화면의 패널에 리사이즈와 접기를 붙이고 읽기 폭을 넓힌다

## 결정권자 요약

### 제안

기획서 화면의 문서 목록 패널과 결정 패널, 아이디어 화면의 목록 패널에 리사이즈 핸들과 접기 버튼을 붙이고,
그렇게 되찾은 만큼 문서 본문의 읽기 폭도 함께 넓어지게 한다.

### 바뀌는 것

- 지금: 기획서를 읽는 동안에도 문서 목록과 결정 패널이 화면 좌우를 계속 차지한다 → 앞으로: 두 패널을
  드래그로 줄이거나 접어 본문에 자리를 넘길 수 있다.
- 지금: 본문 읽기 폭이 620px에 묶여 있어 패널을 치워도 빈 자리만 늘어난다 → 앞으로: 패널에서 되찾은
  만큼 읽기 폭도 함께 올라가고 860px에서 멈춘다.
- 아이디어 화면의 목록 패널도 같은 방식으로 줄이고 접을 수 있다.

### 비용과 위험

- 패널을 최소 너비까지 줄인 상태는 지금까지 아무도 본 적이 없는 배치이므로, 그 폭에서만 드러나는
  줄바꿈이나 잘림이 새로 보일 수 있다.
- 한 번도 조절하지 않은 화면은 지금과 완전히 같게 그려지고 읽기 폭도 620px 그대로이므로, 승인 전 상태와
  비교하기 쉽다.

## 현재 코드 상태

기획서 화면의 격자는 `src/App.css` 466행
`.spec-workspace-layout { display: grid; min-height: 540px; grid-template-columns: minmax(190px, .72fr) minmax(340px, 1.45fr) minmax(190px, .68fr); gap: 10px; margin-top: 12px; align-items: stretch; }`
이고, 1314행이 창 폭 980px 이하에서 `190px minmax(340px, 1fr)` 두 칸으로 바꾸며 1315행이
`.decision-panel { grid-column: 1 / -1; }`으로 결정 패널을 아래 전체 폭에 내린다. 아이디어 화면의 격자는
416행 `.idea-inbox-layout { ... grid-template-columns: minmax(300px, .85fr) minmax(360px, 1.15fr); ... }`이고
1313행이 같은 폭에서 `1fr` 한 칸으로 바꾼다. 기획서가 정한 최소값 190px·300px과 본문 하한 340px이 모두
이 규칙들이 이미 쓰고 있는 값이다.

읽기 폭은 531행 `.markdown-body { max-width: 620px; margin: 0 auto; }`가 정하고, 493행
`.document-reader-bar`가 같은 620px으로 토글을 본문 폭에 맞춘다. 860px은 496행과 497행이 이미 쓰는 값이다.

같은 `.markdown-body`를 쓰는 다른 자리들은 각자 최대 폭을 다시 정해 두고 있다. 501행이
`.decision-summary-board .markdown-body { max-width: none; ... }`, 618행이
`.task-detail-brief .markdown-body { max-width: 640px; ... }`,
`src/features/projects/components/qa/QaWorkbench.css` 41행이 `.qa-flow-section .markdown-body { max-width: 640px; ... }`다.
`src/features/projects/components/BlockedTaskPanel.css` 54행과 114행은 최대 폭을 정하지 않아 531행을 그대로
받는다. 그래서 531행의 값을 그냥 올리면 개발 화면의 막힌 작업 상자까지 함께 넓어지고, 기획서 완료 판정
A12가 요구한 "쓰지 않은 화면은 변경 전후로 같다"가 깨진다. 되돌림 값이 620px인 변수로 바꾸고 그 변수를
문서 본문 두 자리에만 실어 주면, 나머지 자리는 값이 그대로 남는다.

`src/features/projects/components/decisionSummaryBoardLayout.test.ts` 50행부터 56행이 531행의 최대 폭을
읽어 `.decision-summary-risk`의 620px과 같은지 확인한다. 531행을 변수로 바꾸면 이 확인이 문자열 비교에서
어긋나므로, 되돌림 값과 비교하도록 고친다. SPEC-076이 이 시험으로 지키려 한 것은 비용과 위험 상자의 한 줄
길이가 본문과 같다는 사실이고, 그 사실은 되돌림 값 비교로 그대로 유지된다.

그리는 자리는 `SpecWorkspace.tsx` 133행의 `<div className="spec-workspace-layout">`, 134행의
`<aside className="spec-list-panel">`과 그 135행 헤더, 193행의 `<aside className="decision-panel">`,
175행의 `<article className="spec-paper embedded">`이고, `IdeaInbox.tsx` 117행의
`<section className="idea-list-panel">`과 118행 헤더, 234행의 `<div className="idea-preview-body">`다.
결정 패널에는 헤더 요소가 없고 194행의 안내 문구로 시작한다.

- `SpecWorkspace.test.tsx`와 `IdeaInbox.test.tsx`에 화면 시험을 더하고,
  `documentPanelLayout.test.ts`를 새로 만들어 스타일 값과 도메인 표를 맞대어 확인한다.

## 범위 사전 검사

선언한 파일은 일곱이다. 두 화면의 격자와 읽기 폭이 모두 `src/App.css` 한 파일에 있고, 세 패널을 그리는
코드가 두 컴포넌트에 있으며, 나머지 넷은 그것들을 지키는 시험이다. 완료 조건이 요구하는 편집이 이 일곱
밖으로 나가지 않는다는 것을 아래 값 경로에서 확인했다.

`src/features/projects/components/DocumentReader.tsx`를 열어 보고 뺐다. 30행이 요약 절이 없는 문서를
`.document-reader` 감싸개 없이 본문만 그리고, 33행이 있는 문서를 감싸개 안에 그린다. 두 경우 모두 부모가
`.spec-paper`이고, CSS 사용자 정의 속성은 자식으로 상속되므로 `.spec-paper`에 값을 실으면 두 경우가 함께
따라온다. 이 파일을 고칠 이유가 없다.

`src/features/projects/components/MarkdownBody.tsx`도 열어 보고 뺐다. 10행이 `.markdown-body` 감싸개를
그릴 뿐 폭을 정하지 않는다. 폭은 전부 스타일 파일에 있다.

`src/features/projects/components/BlockedTaskPanel.css`를 열어 보고 뺐다. 54행과 114행이 최대 폭을 정하지
않아 `src/App.css` 531행을 그대로 받는다. 531행을 되돌림 값 620px인 변수로 바꾸고 이 화면에 변수를 싣지
않으므로, 값이 지금과 같게 남는다. 이 파일을 고치면 오히려 개발 화면이 달라진다.

`src/features/projects/components/qa/QaWorkbench.css`도 열어 보고 뺐다. 41행이 자기 최대 폭 640px을 이미
정하고 있어 변수에 닿지 않는다. C15의 확인은 이 파일을 읽어 값을 비교하는 것이지 고치는 것이 아니다.

`src/features/projects/components/WorkspaceShell.tsx`를 열어 보고 뺐다. 사이드바의 상태는 TASK-S080-03이
그 안에 두었고, 이 작업은 사이드바의 기준 너비와 그리는 너비를 읽기 폭 계산에 넣기만 한다. 두 화면
컴포넌트가 그 값을 알아야 하므로 값이 내려오는 통로가 필요하지만, 그 통로는 TASK-S080-03이 사이드바
상태를 둘 때 함께 만들도록 그 작업의 변경 범위에 적혀 있다. 이 작업에서 그 파일을 고쳐야 한다면
TASK-S080-03의 완료 조건이 모자란 것이므로, 그때는 고치지 말고 막힌 사유에 적어 보고한다.

`src/features/projects/components/PanelLayoutControls.tsx`와 `src/features/projects/domain/panelLayout.ts`와
`browserPanelLayoutStore.ts`도 열어 보고 뺐다. 셋 다 가져다 쓰기만 한다.
