# 아키텍트 자격 판정이 미처리 수정 요청을 먼저 고른다

## 결정권자 요약

### 제안

아키텍트가 할 일을 고를 때 사용자가 남긴 미처리 수정 요청을 새 기획서 분해보다 먼저 집도록 한다.

### 현재

아키텍트 자격 판정은 아직 작업이 만들어지지 않은 승인만 대상으로 삼는다. 사용자가 수정 요청을 남겨도
자동 실행이 그것을 집지 못하므로, 막힌 작업은 사람이 직접 세션을 붙여야만 풀린다.

### 변경 후

판정이 두 종류의 대상을 구분해 돌려준다. 미처리 수정 요청이 있으면 그것을 먼저 고르고, 같은 종류
안에서는 먼저 만들어진 요청부터 고른다. 앱 안의 판정과 자동 실행이 읽는 판정 도구가 같은 답을 낸다.

### 사용자 결과

수정 요청을 남겨 두면 다음 아키텍트 실행이 그 요청부터 처리하므로, 막힌 작업이 새 기획 분해에 밀려
계속 남아 있지 않는다.

### 영향 범위

- 변경: 아키텍트 자격 판정의 대상 종류와 우선순위, 앱이 설치하는 판정 도구의 기계 출력
- 유지: 기획자와 개발자 자격 판정, 선점 방식과 선점 도구, 기존 판정 호출의 표준 출력과 종료 코드

### 비용과 위험

판정 도구는 앱이 관리하는 자산이라 버전이 올라가고 프로젝트 설치본이 다음 동기화에서 교체된다. 자동
실행이 수정 요청을 집으면 유료 세션이 시작되므로, 요청을 남기는 일이 곧 실행을 부르는 일이 된다.

### 결정 요청

품질 확인에서는 두 종류가 섞였을 때의 선택 순서와, 요청이 처리된 뒤 다시 후보가 되지 않는지를 자동 검사
수치로 확인한다.

## 막힌 사유

- 막힌 지점: 완료 조건 8과 9는 앱 안의 판정도 고른 대상의 종류를 함께 알리고, 그 종류가 조건 스크립트의
  값과 같은지 대조하기를 요구한다. 그 값을 담을 자리는 앱 판정 결과 구조인 `RoleWorkVerdict`인데 그
  구조는 `src-tauri/src/domain/project.rs`에 있고 이 작업의 `scope_files`에 없다. 기존 두 필드
  (`target`, `candidates`)로는 종류를 표현할 수 없다. `WorkCandidate.verdict`는 "대상이면 eligible,
  아니면 제외 사유 코드"로 뜻이 정해져 있고 조건 스크립트와 어휘를 맞추는 값이라, 거기에 종류를 실으면
  같은 완료 조건 9가 요구하는 대조가 깨진다.
- 필요한 해결: `src-tauri/src/domain/project.rs`를 이 작업의 선언 범위에 더한다. 판정 결과에 대상 종류를
  담는 값 하나가 필요하다. 대안으로 `pending_role_work`의 반환 형태를 바꾸는 길도 있으나 그 경우 호출자인
  `src-tauri/src/infrastructure/fs_project_repository.rs`가 함께 움직여야 하므로 그 파일을 대신 더해야
  한다. 어느 쪽이든 선언 범위를 넓히는 판단은 아키텍트 몫이다.
- 재개 조건: 위 두 파일 가운데 하나가 `scope_files`에 들어오고, 종류를 어느 층에 담을지가 작업 문서에
  적히면 곧바로 구현할 수 있다. 나머지 완료 조건과 검증 절차는 지금 선언만으로 충족할 수 있으므로 다른
  선행은 필요하지 않다.
- 관련 대상: TASK-S055-02

## 목적

SPEC-055의 R4와 R6의 판정 측면을 구현한다. 아키텍트 자격 판정이 승인된 기획서와 미처리 수정 요청 두
종류를 구분하고 정해진 우선순위로 하나를 고르게 한다. 요청을 실제로 처리하는 것은 아키텍트 세션의
일이며 이 작업은 무엇을 고를지까지만 정한다.

## 범위 사전 검사

- 자격 판정은 두 곳에 있다. 앱 안의 판정과, 앱이 프로젝트에 설치하는 판정 도구의 본문이다. 두 곳이 같은
  답을 내야 하며 기존 검사가 그 일치를 확인한다. 그래서 두 파일이 함께 범위에 있다.
- 앱 안의 아키텍트 분기는 승인 결정 가운데 파생 작업이 없고 선점되지 않은 것을 후보로 삼는다. 새 종류를
  더하려면 이 분기와 도구 본문의 같은 절을 함께 고쳐야 한다.
- 판정 도구는 관리 자산이라 버전 상수를 갖는다. 착수 시점 값은 13이며 본문이 바뀌면 14가 된다. 그 값을
  검사하는 곳이 관리 자산 동기화 검사이므로 그 파일이 범위에 있다.
- 선점 도구와 예약 도구는 대상 식별자를 인자로 받을 뿐 대상의 종류를 해석하지 않는다. 요청 식별자를
  그대로 선점할 수 있으므로 두 자산은 바꾸지 않는다.
- 요청 문서의 형식과 처리 완료 판정 근거는 앞 작업이 확정한다. 이 작업은 그 형식을 읽기만 한다.
- 판정은 읽기만 한다. 이 작업에서 요청 문서나 작업 문서를 쓰는 경로를 만들지 않는다.

## 변경 범위

### 판정 대상

- 아키텍트 후보를 두 종류로 나눈다. 하나는 지금처럼 아직 작업이 만들어지지 않은 승인이고, 다른 하나는
  아직 처리되지 않은 작업 정의 수정 요청이다.
- 요청이 미처리인지는 대상 작업이 그 요청 식별자를 연결하고 있는지로만 판정한다. 다른 근거로 추측하지
  않는다.
- 대상 작업이 요청을 받을 수 없는 상태가 됐으면 그 요청은 후보가 아니다. 요청 생성 뒤 작업이 품질 확인
  대기나 완료로 옮겨 간 경우가 여기에 해당한다.
- 대상 작업이나 요청 식별자에 만료되지 않은 선점이 있으면 후보가 아니다.
- 마이그레이션 잠금 중에는 어느 종류도 후보가 되지 않는다.

### 우선순위

- 미처리 요청이 하나라도 있으면 승인 분해보다 먼저 고른다.
- 같은 종류 안에서는 먼저 만들어진 것부터 고른다. 요청은 생성 시각이 이른 것부터다.
- 판정 결과는 고른 대상의 식별자와 종류를 함께 알린다. 세션이 무엇을 선점하고 무엇을 해야 하는지 그
  값만으로 구분할 수 있어야 한다.

### 두 판정의 일치

- 앱 안의 판정과 설치되는 판정 도구가 같은 픽스처에서 같은 대상과 같은 종류와 같은 제외 사유를 낸다.
- 기존 판정 호출의 표준 출력과 종료 코드는 바뀌지 않는다. 기계 출력 모드에만 새 종류가 나타난다.
- 판정 도구의 자산 버전을 올린다.

## 손대지 않는 것

- 기획자와 개발자 자격 판정의 대상과 순서
- 선점 도구와 예약 도구의 본문
- 요청 문서를 만드는 앱 명령과 요청 형식
- 아키텍트가 요청을 처리하는 실제 수정 동작
- 앱 화면
- 규칙 문언과 역할 계약의 문장

## 완료 조건

1. 미처리 요청과 분해되지 않은 승인이 함께 있는 픽스처에서 판정이 요청을 고른다.
2. 미처리 요청이 여럿이면 생성 시각이 가장 이른 것을 고른다.
3. 요청이 없고 분해되지 않은 승인만 있으면 지금과 같은 대상을 고른다.
4. 대상 작업이 요청 식별자를 연결하고 있으면 그 요청은 후보가 아니다.
5. 대상 작업이 품질 확인 대기나 완료로 옮겨 간 요청은 후보가 아니다.
6. 대상 작업이나 요청 식별자에 만료되지 않은 선점이 있으면 후보가 아니고, 만료된 선점은 후보를 막지
   않는다.
7. 마이그레이션 잠금 중에는 어느 종류의 후보도 나오지 않는다.
8. 판정 결과가 고른 대상의 식별자와 종류를 함께 알린다.
9. 앱 안의 판정과 설치되는 판정 도구가 같은 픽스처에서 같은 대상과 종류와 제외 사유를 낸다.
10. 기존 방식으로 판정 도구를 호출하면 표준 출력과 종료 코드가 변경 전과 같다.
11. 판정 도구의 자산 버전이 한 단계 올라가고 동기화가 새 본문을 설치하며 앱보다 높은 버전은 덮어쓰지
    않는다.
12. 판정 과정에서 요청 문서와 작업 문서와 선점 파일이 하나도 바뀌지 않는다.
13. 요청 기록이 없는 기존 프로젝트에서 판정 결과가 변경 전과 같다.
14. 기존 자동 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. `cargo test --manifest-path src-tauri/Cargo.toml`을 실행한다.
2. 요청만 있는 경우, 승인만 있는 경우, 둘 다 있는 경우, 요청이 여럿인 경우를 표로 만들어 선택 결과를
   대조한다.
3. 연결된 요청, 허용되지 않는 상태로 옮겨 간 요청, 선점된 요청과 대상, 만료된 선점, 마이그레이션 잠금을
   각각 주입해 후보에서 빠지는지 확인한다.
4. 같은 픽스처를 앱 판정과 설치된 판정 도구에 각각 넣어 결과가 같은지 대조한다.
5. 기존 판정 호출의 출력과 종료 코드를 변경 전 값과 대조한다.
6. 판정 전후로 요청 문서와 작업 문서와 선점 디렉터리의 해시가 같은지 확인한다.
7. 구버전 판정 도구를 가진 임시 프로젝트에 동기화를 실행해 새 본문이 설치되는지, 높은 버전은 보존되는지
   확인한다.

## 범위와 선행

요청 문서의 형식과 처리 완료 판정 근거를 앞의 두 작업이 확정하므로 둘 다 선행한다. 규칙 문언에서 연결
필드를 정의하는 작업과, 요청 기록을 실제로 만드는 작업이다.

관리 자산 동기화 검사 파일이 규칙 문언 작업과 겹치므로 그 작업 뒤에 온다. 이 승인의 화면 작업과는 파일이
겹치지 않는다.
