# 하트비트 설치·데몬·실행 기록 읽기와 중복 잡 감지 구현

SPEC-002의 R1 상태 판정, R5의 상태 표시 데이터, R7의 중복 감지를 구현한다. 전부 읽기 전용이다. 이 작업에서 만드는 코드는 어떤 파일도 쓰지 않는다.

## 의존성

- TASK-004 선행 필수. 중복 잡 감지가 TASK-004의 파서를 재사용한다.
- TASK-003과는 무관하다.

## 범위

- 신규 파일 `src-tauri/src/infrastructure/heartbeat_status.rs` 1개.
- `src-tauri/src/infrastructure/mod.rs`에 모듈 선언 1줄 추가.
- 그 외 파일은 건드리지 않는다.

## 작업 내용

### 0. 읽기 전용 제약 (먼저 읽을 것)

- 이 모듈은 파일을 쓰지 않는다. 디렉터리도 만들지 않는다. 기획서 R6이 앱은 `~/.claude/heartbeat/` 아래에 쓰지 않는다고 명시한다.
- TASK-004와 마찬가지로 실제 홈 디렉터리 경로를 스스로 계산하지 않는다. 하트비트 홈(`~/.claude`)에 해당하는 디렉터리를 인자로 받는다. 홈 해석은 TASK-006이 한다.
- 대상 파일이 없거나 깨져 있어도 오류로 올리지 않고 "정보 없음" 상태로 내려보낸다. 상태 표시는 자동 새로고침 주기마다 호출되므로, 없는 파일 때문에 화면이 에러로 덮이면 안 된다. 단, 읽기 자체가 권한 문제 등으로 실패한 경우는 구분해서 알 수 있게 한다.

### 1. 설치 상태 판정 (R1)

세 상태를 아래 기준으로 구분한다. 판정 근거가 되는 세 경로는 모두 기획서가 실측으로 확인한 것이다.

- `미설치`: `<하트비트 홈>/HEARTBEAT.md`와 `<하트비트 홈>/heartbeat/` 디렉터리가 **둘 다** 없다.
- `설치됨·데몬 실행 중`: `<하트비트 홈>/heartbeat/heartbeat.pid`가 있다.
- `설치됨·데몬 미실행`: 위 둘 중 하나 이상이 있고 pid 파일은 없다.

판정 기준을 이렇게 정한 이유와 한계를 코드 주석과 UI 문구 양쪽에 남긴다.

- 하트비트는 데몬 기동 시 pid 파일을 쓰고 정상 종료 시 지운다. 또 상태 조회 시 pid의 프로세스 생존을 확인해서 죽어 있으면 pid 파일을 지운다. 따라서 pid 파일 존재는 대부분의 경우 실행 중과 일치한다.
- 한계: 데몬이 정리 없이 죽으면 pid 파일이 남아 "실행 중"으로 보인다. 앱은 프로세스 생존을 직접 확인하지 않는다. 확인하려면 플랫폼별 시스템 호출이나 새 의존성이 필요하고, 기획서가 요구한 것은 세 상태의 구분까지다.
- 이 한계 때문에 UI 문구는 "데몬이 살아 있음"이 아니라 판정 근거가 드러나는 표현을 쓴다. 문구 확정은 TASK-006이 한다.

### 2. 잡 실행 기록 읽기 (R5)

- 출처는 `<하트비트 홈>/heartbeat/state.json` 하나다. 최상위가 잡 이름을 키로 하는 객체이고, 값에 `last_run`, `last_result`, `last_duration`이 들어 있다.
- 앱은 요청한 잡 이름에 대해서만 값을 꺼낸다. 파일에 있는 다른 프로젝트의 잡과 `recent_runs` 같은 추가 필드는 읽지 않고 무시한다. 쓰지 않으므로 보존 문제는 없다.
- `last_run`은 타임존이 없는 로컬 시각 ISO 문자열이다(예: `2026-08-02T00:21:10.560104`). UTC로 해석하거나 타임존을 붙이지 않는다. 문자열을 그대로 올려보내고 표시 형식은 TASK-006이 정한다.
- `last_result`가 가질 수 있는 값은 `success`, `failure`, `skipped`, `quota_skipped`, `timeout`이다. 이 목록에 없는 값이 들어와도 오류로 만들지 말고 원문을 그대로 전달한다.
- `last_duration`은 초 단위 숫자다. 정수일 수도 소수일 수도 있다.
- 파일이 없거나, JSON이 깨졌거나, 해당 잡 키가 없으면 "실행 기록 없음"을 뜻하는 값을 반환한다. 세 경우를 구분하지 않아도 된다. 기획서는 이 상태를 오류로 취급하지 말라고 명시한다.

### 3. 중복 잡 감지 (R7)

- 대상은 `<하트비트 홈>/HEARTBEAT.md`다.
- TASK-004의 파서로 문서 전체의 잡을 읽고, 앱 관리 블록 **밖**에 있으면서 아래 두 조건을 모두 만족하는 잡을 찾는다.
  - `slug`가 현재 프로젝트의 slug와 같다.
  - `condition` 값에 조건 스크립트 경로(`wf-eligible.sh`)가 들어 있다.
- 찾은 잡의 이름과 어떤 역할을 가리키는지(조건 인자로 판별)를 결과에 담는다. 역할을 판별할 수 없으면 이름만 담는다.
- 감지만 한다. 수정도 삭제도 하지 않는다. 사용자 잡은 앱 소유가 아니다.
- 관리 블록이 아직 없는 상태에서도 동작해야 한다. 그때는 문서의 모든 잡이 블록 밖이다.

### 4. 결과 타입

- 위 세 가지를 하나의 읽기 결과 구조체로 묶는다. 프론트로 나갈 것이므로 `serde::Serialize`와 `#[serde(rename_all = "camelCase")]`를 붙인다. `domain/project.rs`의 기존 요약 타입들과 같은 방식이다.
- 타입 정의 위치는 `domain/` 아래가 기존 구조와 맞다. 판정 로직은 `infrastructure/`에 둔다. 기존 코드가 도메인 타입과 파일시스템 구현을 나눠 놓은 방식을 따른다.

### 5. 테스트

`#[cfg(test)] mod tests`에 `tempfile::tempdir`로 가짜 하트비트 홈을 만들어 작성한다.

- 빈 디렉터리에서 `미설치`가 나온다.
- `HEARTBEAT.md`만 있으면 `설치됨·데몬 미실행`이 나온다.
- `heartbeat/heartbeat.pid`가 있으면 `설치됨·데몬 실행 중`이 나온다.
- `state.json`에 기록이 있는 잡에서 시각·결과·소요 시간이 그대로 나온다.
- `state.json`이 없을 때, 깨진 JSON일 때, 해당 잡 키가 없을 때 각각 "실행 기록 없음"이 나오고 오류가 되지 않는다.
- 관리 블록 밖에 같은 slug와 조건 스크립트를 쓰는 잡이 있으면 감지되고, 블록 안의 잡은 감지되지 않는다.
- slug가 다른 잡, 조건이 다른 잡은 감지되지 않는다.
- 함수를 호출해도 대상 디렉터리에 새 파일이 생기지 않고 기존 파일의 수정 시각이 바뀌지 않는다.

## 완료 조건

1. 미설치 / 설치됨·데몬 미실행 / 설치됨·데몬 실행 중 세 상태를 서로 다르게 판정하는 함수가 있다. (기획서 완료 조건 1의 백엔드 측면)
2. 잡별 마지막 실행 시각·결과·소요 시간이 `state.json` 내용과 일치하게 나오고, 기록이 없으면 "실행 기록 없음"으로 나온다. (기획서 완료 조건 10)
3. 관리 블록 밖의 같은 slug 중복 역할 잡이 감지되고, 그 잡이 수정되거나 삭제되지 않는다. (기획서 완료 조건 12의 감지 측면)
4. 위 항목 전부에 자동화 테스트가 있고 `cargo test`가 통과한다.
5. 모듈이 어떤 파일도 쓰지 않고 실제 홈 디렉터리 경로를 계산하지 않는다.
6. 프론트엔드(`src/`)와 `.workflow/`에 변경이 없다.

## 참고 사실

- 실제 `state.json`에는 `recent_runs`라는 배열 필드도 있다. 쿼터 계산용이며 앱이 읽을 필요는 없다.
- 하트비트는 조건 검사가 실패(exit 0이 아님)해도 `last_run`을 갱신하고 `last_result`를 `skipped`로 기록한다. 그래서 정상 동작 중인 프로젝트도 대부분의 기록이 `skipped`다. UI 문구를 정할 때 `skipped`를 실패로 읽히게 만들면 안 된다.
- `quota_skipped`는 `max_per` 한도에 걸려 건너뛴 경우다. `skipped`와 원인이 다르다.
- 도그푸딩 환경의 실제 `state.json`에는 이 프로젝트와 무관한 잡(`dream-catze` 등)도 들어 있다. 잡 이름으로만 조회하는 이유다.
