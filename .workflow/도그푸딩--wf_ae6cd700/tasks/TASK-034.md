# 최근 활동 피드가 작업 전이와 기획서 결정을 한 타임라인으로 보여준다

SPEC-011의 R5·R6·R7을 구현한다. 활동 뷰 아래쪽에 "최근 활동" 섹션을 만들고, 선택된 워크플로우의 개발
작업 전이와 기획서 결정을 시간 역순 한 줄짜리 항목으로 보여준다. 항목에서 그 문서로 이동할 수 있고,
잘린 것과 없는 것을 구분해 알린다.

새 기록은 만들지 않는다. 두 원천 모두 이미 파일에 있고 TASK-032가 화면까지 날라 두었다.

## 의존성

- **선행: TASK-032.** 기획서 결정의 종류와 시각이 그 작업에서 기획서 항목의 `events`로 내려온다.
- **선행: TASK-033.** 이 작업이 섹션을 더할 `ActivityView.tsx`와 이동 콜백이 그 작업에서 만들어진다.
- **TASK-033과 병행 금지.** 같은 파일(`ActivityView.tsx`, `App.css`)을 만진다.
- **SPEC-009 계열 TASK-030(아직 `todo`)과 병행 금지.** `App.css`가 겹친다. 순서는 어느 쪽이 먼저여도
  된다.

## 범위

- `src/features/projects/components/ActivityView.tsx` — "최근 활동" 섹션.
- `src/features/projects/components/ActivityView.test.tsx` — 피드 테스트 추가.
- `src/features/projects/components/DevelopmentBoard.tsx` — `eventKinds` 상수에 `export` 키워드 하나만
  더한다. 그 밖의 변경은 하지 않는다.
- `src/App.css` — 피드 스타일.
- 그 외 파일은 건드리지 않는다. 백엔드·`types.ts`·`WorkspaceShell.tsx`는 이 작업에서 바뀌지 않는다.

## 작업 내용

### 0. 먼저 읽을 제약

- **이미 파일에 있는 사실만으로 만든다**(R5). 원천은 둘뿐이다: 개발 작업의 `events`(QA 결정이 백엔드에서
  이미 병합된 결과)와 기획서의 `events`(결정 문서). 보고서·아이디어·연동 상태를 넣지 않는다.
- **어느 원천도 화면이 쓰지 않는다**(R8). 이 섹션은 읽기만 한다.
- **같은 사실을 두 화면이 다른 말로 부르지 않는다**(R5, 기획서 완료 조건 18). 개발 작업 전이의 여섯
  이름은 개발 화면 타임라인과 같아야 한다. 라벨을 이 파일에 다시 적지 말고 한 정의를 공유한다.
- **`revision_requested`는 원천에 따라 다른 사건이다.** 개발 작업에서는 QA 반려("반려"), 기획서에서는
  사용자의 수정 요청("수정 요청")이다. 항목의 원천을 잃어버리고 `kind` 문자열만으로 라벨을 고르면 두
  사실이 한 이름으로 뭉개진다.
- **사실이 조용히 빠지지 않는다**(R7). 잘렸으면 잘렸다고 적는다.
- 새 타이머를 만들지 않는다(R8). TASK-033이 세운 제약이 이 섹션에도 그대로 적용된다.

### 1. 피드 항목 만들기 (R5)

선택된 워크플로우(`workflow` prop) 하나만 대상이다. 프로젝트 전역인 위 섹션과 범위가 다른 것은 기획서
확인 필요 4번이 승인한 설계다. `workflow`가 없으면 빈 상태를 그린다.

```tsx
type ActivityEntry = {
  at: string;
  instant: number;
  kind: string;
  source: "spec" | "task";
  item: WorkflowItemSummary;
};
```

- 개발 작업: `workflow.items.tasks`의 각 항목에서 `events`를 펼친다.
- 기획서: `workflow.items.specs`의 각 항목에서 `events`를 펼친다.
- `at`이 `Date.parse`로 읽히지 않는 항목은 그 항목만 버린다. 하나가 잘못되어 피드 전체가 비지 않는다
  (R5, 기획서 완료 조건 20).
- 알 수 없는 `kind`도 그 항목만 버린다. 라벨을 만들 수 없는 값을 원문 그대로 흘리지 않는다.
- 정렬은 시간 **역순**이다. 같은 순간이면 문서 식별자로 안정 정렬해 조회마다 순서가 흔들리지 않게 한다.
- 계산은 `useMemo`로 감싸고 의존은 `workflow.items`다. 2.5초마다 프로젝트를 다시 읽으므로 항목 목록이
  매 렌더 새 배열이 되지 않게 한다(R6의 "피드가 다시 계산되는 것이 드러나지 않는다").

라벨:

- 개발 작업 전이 여섯은 `DevelopmentBoard.tsx`의 `eventKinds`(`:29`)를 `export`해서 그대로 쓴다.
  "생성"·"시작"·"막힘"·"QA 대기"·"완료"·"반려"다. 이 파일에 값을 다시 적지 않는다.
- 기획서 결정 셋은 이 파일에 정의한다: `approved` → "승인", `revision_requested` → "수정 요청",
  `rejected` → "폐기". `SpecWorkspace.tsx:33`~`:35`가 쓰는 말과 같다.

항목 한 줄이 보여줄 것(기획서 완료 조건 17): 문서 식별자, 제목, 사건 종류, 시각. 사건 종류는 색만이
아니라 문구로 구분되어야 한다(R9, 기획서 완료 조건 30). 시각은 `time` 요소로 그리고 `dateTime`에
원문을 담는다.

### 2. 이동 (R6)

- 각 항목은 누를 수 있고, 누르면 TASK-033이 만든 `onOpenDocument`를 부른다. `kind`는 원천에 따라
  `"specs"` 또는 `"tasks"`이고 `workflow`는 선택된 워크플로우다. 워커 카드와 같은 규칙이다.
- 스크롤 자리 보존: 피드 목록에 자체 스크롤 영역을 주고(`max-height` + `overflow-y: auto`), 마지막
  스크롤 오프셋을 `ActivityView.tsx` 모듈 스코프 변수에 기억했다가 다시 마운트할 때 복원한다. 문서로
  이동하면 활동 뷰는 언마운트되므로, 이 보존이 없으면 돌아왔을 때 맨 위로 튄다.
  - 저장은 스크롤 이벤트에서, 복원은 `useLayoutEffect`에서 한다.
  - 파일이나 브라우저 저장소를 쓰지 않는다. 세션 안에서만 기억하면 되고, 기획서는 새 상태 저장소를
    금지한다(R8).

### 3. 잘린 것과 없는 것 (R7)

- 표시 한도는 **최근 30건**이다(기획서 확인 필요 3의 승인된 제안). 전체 항목 수가 30을 넘으면 앞의
  30건만 그리고, 잘렸다는 사실과 전체를 볼 곳(개발 화면 타임라인)을 함께 적는다.
- 항목이 하나도 없으면 "아직 기록이 없습니다"에 해당하는 빈 상태를 그린다. 잘려서 일부만 보이는 것과
  원래 없는 것이 다른 문구여야 한다(기획서 완료 조건 24).
- 전이 이력이 없어 피드에 한 번도 나타나지 않는 문서가 몇 건인지는 **알리지 않는다**. 개발 화면
  타임라인이 이미 그 안내를 한다(`DevelopmentBoard.tsx:498`).

### 4. 테스트

`ActivityView.test.tsx`에 더한다.

- 작업 전이와 기획서 결정이 섞인 스냅샷에서 항목이 시간 역순으로 늘어선다. (기획서 완료 조건 16)
- 항목 하나에 문서 식별자·제목·사건 종류·시각이 모두 나타난다. (기획서 완료 조건 17)
- 개발 작업 전이 여섯이 "생성"·"시작"·"막힘"·"QA 대기"·"완료"·"반려"로 불린다. 라벨 정의를
  `DevelopmentBoard`와 공유한다는 것을 import로 고정한다. (기획서 완료 조건 18)
- 기획서 결정만 있는 워크플로우에서 승인·수정 요청·폐기가 피드에 나타난다. (기획서 완료 조건 19)
- 같은 `revision_requested`가 작업에서는 "반려", 기획서에서는 "수정 요청"으로 나온다.
- `at`이 시각이 아닌 항목과 알 수 없는 `kind`가 섞여 있어도 나머지 항목이 정상으로 그려진다.
  (기획서 완료 조건 20)
- `workflow` prop을 다른 워크플로우로 바꾸면 피드 내용이 바뀐다. (기획서 완료 조건 21)
- 항목을 누르면 `onOpenDocument`가 그 문서와 원천에 맞는 종류로 호출된다. (기획서 완료 조건 22)
- 항목이 31건 이상이면 30건만 그려지고 잘림 고지가 보인다. (기획서 완료 조건 23)
- 항목이 0건이면 빈 상태 문구가 보이고 잘림 고지는 없다. 두 문구가 다르다.
  (기획서 완료 조건 24)
- 스크롤 오프셋을 준 뒤 언마운트하고 다시 마운트하면 그 오프셋이 복원된다. jsdom은 레이아웃이 없어
  `scrollTop`이 그대로 유지되지 않을 수 있으므로, 컨테이너의 `scrollTop`을 `Object.defineProperty`로
  기록 가능하게 만든 뒤 복원 값을 확인한다. (R6)
- 렌더 후 `vi.getTimerCount()`가 `0`이다. (기획서 완료 조건 27의 화면 몫)

`DevelopmentBoard.test.tsx`는 고치지 않는다. `export` 하나를 더하는 변경이라 동작이 바뀌지 않는다.

## 완료 조건

2. 각 항목이 문서 식별자·제목·사건 종류·시각을 보여준다. (기획서 완료 조건 17)
3. 작업 전이 종류의 이름이 개발 화면 타임라인의 여섯 이름과 같고, 정의를 공유한다.
   (기획서 완료 조건 18)
4. 기획서 결정 승인·수정 요청·폐기가 피드에 나타난다. (기획서 완료 조건 19)
5. 시각을 읽을 수 없는 기록이 있어도 피드가 정상으로 그려진다. (기획서 완료 조건 20의 화면 몫)
6. 피드가 선택된 워크플로우의 사실만 담고, 워크플로우를 바꾸면 내용이 바뀐다. (기획서 완료 조건 21)
7. 항목에서 해당 문서로 이동하고, 이동 규칙이 워커 카드와 같다. (기획서 완료 조건 22)
8. 이동했다 돌아와도 피드에서 보던 자리를 잃지 않는다. (R6)
9. 표시 한도를 넘으면 잘렸다는 사실과 전체를 볼 곳이 표시된다. (기획서 완료 조건 23)
10. 기록이 없어 빈 경우와 잘려서 일부만 보이는 경우가 다른 문구로 구분된다. (기획서 완료 조건 24)
11. 사건 종류가 색 외의 단서로도 구분된다. (기획서 완료 조건 30)
12. 피드가 파일을 쓰지 않고 새 타이머나 새 저장소를 만들지 않는다.
    (기획서 완료 조건 25·26·27의 화면 몫)
13. 피드 목록 구조가 보조 기술에 드러나고 항목을 키보드로 조작할 수 있다.
    (기획서 완료 조건 29의 이 작업 몫)
14. `npm run check`가 통과하고 기존 프론트엔드 테스트가 수정 없이 통과한다. (기획서 완료 조건 32)

## 참고 사실

확인 시점 2026-08-03. 추정 없이 파일에서 읽은 값이다.

- `DevelopmentBoard.tsx`의 `eventKinds`(`:29`~`:36`)가 여섯 종류를 "생성"·"시작"·"막힘"·"QA 대기"·
  "완료"·"반려"로 부른다. 지금은 export되지 않아 다른 파일에서 쓸 수 없다.
- `DevelopmentBoard.tsx:618`이 그 배열로 `eventKindLabels` 맵을 만들고, `timelineEvents`(`:621`)가
  맵에 없는 `kind`를 건너뛴다. 이 작업의 필터 규칙도 같다.
- 타임라인은 기록이 없어 표시되지 않는 작업 수를 이미 알린다(`:498`~`:500`). R7이 같은 안내를
  반복하지 말라고 한 대상이다.
- `SpecWorkspace.tsx:33`~`:35`의 결정 라벨은 "승인"·"수정 요청"·"폐기"다. `WorkspaceShell.tsx:465`의
  기록 화면은 승인·폐기 둘만 쓴다.
- `WorkflowItemSummary.events`는 선택 필드다(`types.ts:43`). 기존 픽스처가 이 키 없이 만들어져 있으므로
  `item.events ?? []`로 읽는다.
- 작업 이벤트에는 QA 결정이 백엔드에서 이미 병합돼 있다(`fs_project_repository.rs:1093`). 화면이 QA
  결정 문서를 따로 읽을 필요가 없다.
- `.workspace-content`(`App.css:144`)가 화면 전체의 스크롤 컨테이너다. 활동 뷰가 언마운트되면 이
  컨테이너의 스크롤 위치도 초기화되므로, 피드 자체 스크롤 영역이 "보던 자리"의 단위가 된다.
- 이 워크플로우의 현재 규모: 개발 작업 34건(이 작업 포함), 결정 문서 24건(기획서 결정 11건, QA 13건).
