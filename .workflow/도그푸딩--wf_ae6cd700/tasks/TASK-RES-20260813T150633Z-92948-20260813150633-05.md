# 제출 전 검토 화면에서 완료와 재작업 요청을 한 번에 기록하고 실패를 건별로 설명한다

## 결정권자 요약

### 제안

모든 항목에 결과가 생기면 제출 전 검토 화면을 연다. 완료 대상과 재작업 요청 대상을 나눠 보여 주고, 최종
버튼 한 번으로 각 작업에 그 결과를 기록한다.

### 현재

구현과 개발자 검증을 마쳐 사용자 QA를 기다린다. 항목별 결과를 정식 기록으로 만드는 길이 새 화면에
생겼고, 완료와 재작업 요청이 섞인 기능도 한 번의 제출로 처리된다. 기존 일괄 확인은 진입점 통합 작업이
없앨 때까지 개발 화면에 그대로 남는다.

### 변경 후

검토 화면이 완료 대상과 재작업 요청 대상을 건수와 함께 나눠 보여 준다. 각 항목을 그 자리에서 고칠 수
있고, 최종 버튼은 기록할 건수를 문구에 담는다. 일부만 실패하면 무엇이 성공하고 무엇이 실패했는지 항목마다
말하고 실패한 것만 다시 보낼 수 있다.

### 사용자 결과

사용자는 기능 하나를 한 번 제출해 문제없는 작업은 완료로, 문제 있는 작업은 재작업 요청으로 남긴다. 같은
버튼을 시간 안에 두 번 누르는 조작 없이 검토 화면 자체가 오클릭을 막는다.

### 영향 범위

- 변경: 제출 전 검토 화면, 최종 제출 버튼의 문구와 동작, 부분 실패와 검토 도중 변경에 대한 안내
- 유지: 작업별 품질 확인 결정 문서의 형식과 상태 전이, 사용자만 품질 결정을 남기는 권한, 대기열과 세션 화면의 구성, 개발 화면과 오늘 화면의 진입점

### 비용과 위험

한 번의 제출이 여러 작업의 기록을 만들기 때문에 일부만 성공하는 경우가 실제로 생긴다. 성공한 것을 다시
보내면 같은 작업에 결정이 두 번 남으므로, 재시도 대상에서 성공한 항목을 빼는 것이 이 화면의 핵심 조건이다.

### 결정 요청

QA에서는 완료와 재작업 요청 대상이 건수와 함께 나뉘어 보이는지, 최종 버튼이 기록할 건수를 말하는지,
항목을 고쳐도 다른 입력이 남는지, 일부 실패가 항목마다 설명되고 재시도에서 성공 건이 중복 기록되지 않는지,
그리고 대기열 진입부터 제출까지 키보드만으로 되는지를 본다.

## 범위 사전 검사

이 작업이 다루는 값은 셋이다. 검토 화면이 나누는 두 구획과 그 건수, 제출 요청에 실리는 항목별 결과와
메모와 갱신 시각, 그리고 응답이 돌려주는 건별 성공과 실패다. 현재 코드와 앞선 작업이 만든 통로를 열어
각 값의 경로를 확인했다.

- 값 경로: 완료 조건 1·2·3의 두 구획과 건수는 앞선 작업이 기기 저장소에 담아 둔 항목별 결과에서 온다.
  값을 읽는 자리는 `src/features/projects/components/qa/QaWorkbench.tsx`이고, 나누어 그리는 자리는 이
  작업이 만드는 `src/features/projects/components/qa/QaReviewSubmit.tsx`다. 항목을 그 자리에서 고치면 같은
  저장소에 다시 쓰므로 저장소 파일은 편집하지 않는다. 세션 화면
  `src/features/projects/components/qa/QaSessionView.tsx`는 항목을 고친 뒤 검토 화면으로 돌아오는 이동을
  받아야 하므로 편집 대상이다.
- 값 경로: 완료 조건 4·5의 제출 요청은 앞선 작업이 만든 앱 통로로 간다. 값을 만드는 자리는 검토 화면이고,
  화면까지 동작을 내려보내는 자리는 `src/App.tsx`와
  `src/features/projects/components/WorkspaceShell.tsx` 두 곳이다. 훅이 내보내는 동작은 이미 있지만 지금은
  어떤 화면도 받지 않으므로, 두 파일에 전달 선언을 더해야 값이 화면까지 닿는다. 그래서 두 파일 모두 편집
  대상이다. 명령을 부르는 계층과 앱 백엔드는 앞선 작업이 이미 만들었고 이 작업에서 값을 그대로 나르므로
  편집하지 않고 선언에도 넣지 않는다.
- 값 경로: 완료 조건 6·7의 건별 결과는 앞선 작업이 정한 결과 항목에서 온다. 그 항목은 파일 이름과 작업
  식별자와 성공 여부와 실패 종류와 사유를 담고, 실패 종류로 검토 시작 뒤 작업이 바뀐 경우와 그 밖의
  기록 실패를 구분한다. 읽는 자리는 검토 화면이고, 그 값으로 재시도 대상을 다시 계산하는 자리도 같은
  화면이다. 성공한 항목을 기기 저장소에서 지우고 실패한 항목만 남기는 것도 이 화면이 한다.
- 값 경로: 완료 조건 8의 제출 차단은 두 값을 비교해 정한다. 앞선 작업이 저장소에 담아 둔 항목별 갱신
  시각과 워크플로 요약이 지금 들고 있는 작업 갱신 시각이다. 그 비교와 다시 확인 필요 표시는 앞선 작업이
  이미 세션 화면에 만들었으므로, 이 작업은 그 상태를 읽어 제출을 막는 판정만 검토 화면에 더한다.
- 검토했으나 제외한 것: `src/features/projects/components/DevelopmentBoard.tsx`는 열지 않는다. 기존 일괄
  확인과 단건 확인 양식을 없애는 것은 진입점 통합 작업의 완료 조건이고, 이 작업이 끝나기 전에 없애면
  사용자가 품질 결정을 남길 길이 한동안 사라진다.
- 검토했으나 제외한 것: `src/features/projects/domain/qaReview.ts`와
  `src/features/projects/infrastructure/browserQaReviewDraftStore.ts`는 넣지 않는다. 이 작업의 완료 조건은
  모두 이미 있는 판정과 저장 동작을 읽고 쓰는 것으로 충족되며, 판정 기준이나 저장 값의 모양을 바꾸지
  않는다.

## 현재 상태

앞선 작업까지 마치면 사용자는 기능을 열어 항목마다 확인함 또는 문제 있음을 남길 수 있고, 그 내용은 기기에
남아 이어서 확인할 수 있다. 그러나 남긴 결과를 정식 기록으로 만드는 길이 새 화면에는 없다.

앱에는 작업별 결과와 메모를 담아 한 번에 기록하는 통로가 이미 있고, 검토 시작 뒤 바뀐 작업을 건별로
거절해 돌려준다. 화면 계층의 훅도 그 동작을 내보내고 있지만 아직 어떤 화면도 부르지 않는다.

기존 개발 화면의 일괄 확인은 전 건을 완료로만 기록하고, 확정 전에 같은 버튼을 시간 안에 다시 누르게 한다.

## 변경 범위

1. 모든 항목에 결과가 생기면 검토로 넘어가는 조작을 세션 화면에 둔다. 결과가 없는 항목이 남아 있으면 그
   조작을 쓸 수 없고, 몇 개가 남았는지 알린다.
2. 검토 화면을 만든다. 화면은 확인 완료 대상과 재작업 요청 대상을 구획으로 나누고 각 구획의 건수를
   보여 준다.
3. 각 항목 옆에서 결과와 메모를 다시 고칠 수 있다. 고치러 세션으로 돌아갔다가 검토 화면으로 다시 오면
   다른 항목의 입력이 그대로 남아 있어야 한다.
4. 최종 버튼 문구에 기록할 건수를 담는다. 문제가 없으면 완료 건수를, 문제가 섞이면 완료 건수와 재작업
   요청 건수를 함께 쓴다. 검토 화면 자체가 오클릭을 막는 단계이므로 같은 버튼을 시간 안에 다시 누르게 하는
   방식은 쓰지 않는다.
5. 최종 버튼은 앱 통로를 한 번 부른다. 요청에는 항목마다 파일 이름, 결과, 메모, 그 항목에 대해 담아 둔
   작업 갱신 시각을 싣는다.
6. 전 건이 기록되면 담아 둔 임시 검토를 지우고 대기열로 돌아간다.
7. 하나라도 실패하면 화면을 닫지 않는다. 성공한 완료 건, 성공한 재작업 요청 건, 실패한 항목의 제목과
   사유를 구분해 보여 준다. 실패 사유가 검토 시작 뒤 작업이 바뀐 것이면 그 뜻을 평문으로 말하고 다시
   확인하도록 안내한다.
8. 성공한 항목은 임시 검토에서 지우고 실패한 항목의 결과와 메모는 남긴다. 다시 제출하면 실패한 항목만
   대상이 되고 성공한 항목은 포함되지 않는다.
9. 항목 중 하나라도 다시 확인 필요 상태이면 최종 제출을 막고 그 항목을 가리킨다.
10. 재작업 요청 사유가 비어 있거나 입력이 너무 길면 제출 전에 그 항목에서 바로 고칠 수 있게 한다.
11. 대기열 행 진입부터 항목 결과 선택과 검토 화면 이동과 최종 제출까지 키보드만으로 할 수 있게 한다.
    오류가 생기면 초점이 그 자리로 간다.
12. 검토 화면에서 가장 강한 행동은 최종 제출 하나만 둔다. 완료 항목은 시각적으로 물러나게 하고, 행동이
    필요한 항목이 먼저 보이게 한다. 장식용 그래프와 점수와 축하 효과는 넣지 않는다.

## 범위 밖

- 앱 백엔드와 명령 계층의 변경
- 기능 묶음 판정 기준과 임시 검토 저장 값 모양의 변경
- 개발 화면과 오늘 화면의 진입점 변경
- 기존 일괄 확인과 단건 확인 양식의 제거
- 화면 캡처와 파일 첨부

## 완료 조건

1. 모든 항목에 결과가 생겨야 검토 화면으로 넘어갈 수 있고, 남은 항목이 있으면 그 수가 보인다.
2. 검토 화면이 확인 완료 대상과 재작업 요청 대상을 나눠 보여 주고 각 건수를 표시한다.
3. 한 항목의 결과나 메모를 고친 뒤 검토 화면으로 돌아오면 다른 항목의 결과와 메모가 그대로 남아 있다.
4. 최종 버튼 문구에 기록할 건수가 들어 있다. 문제가 없으면 완료 건수를, 섞이면 완료 건수와 재작업 요청
   건수를 함께 말한다.
5. 문제가 없는 기능은 최종 버튼 한 번으로 대상 전 건에 확인 완료가 기록되고, 시간 안에 같은 버튼을 다시
   누르라고 요구하지 않는다.
6. 확인함과 문제 있음이 섞인 기능을 한 번 제출하면 확인함 작업에는 완료가, 문제 있음 작업에는 재작업
   요청이 각각 기록되고 각 작업의 상태와 이력이 그 결과에 맞게 바뀐다.
7. 일부 작업만 실패하는 상황에서 성공한 건과 실패한 건이 항목별로 구분되어 보이고, 실패한 항목의 결과와
   메모가 남으며, 다시 제출할 때 성공한 항목이 대상에 포함되지 않는다.
8. 담아 둔 갱신 시각과 다른 작업이 하나라도 있으면 최종 제출이 막히고 그 항목이 가리켜진다.
9. 재작업 요청 사유가 비어 있으면 제출되지 않고 그 항목에서 바로 고칠 수 있다.
10. 전 건이 기록되면 그 기능의 임시 검토가 지워지고 대기열로 돌아간다. 대기열의 그 기능 행은 더 이상
    계속으로 표시되지 않는다.
11. 대기열 진입부터 최종 제출까지 키보드만으로 완료할 수 있고, 오류가 생기면 초점이 그 자리로 간다.
12. 좁은 창에서 검토 화면이 가로 스크롤 없이 읽히고 최종 제출을 쓸 수 있다.

## 검증 단계

1. 검토 화면 검사를 새로 작성하고 실행한다. 완료 조건 1·2·3·4·9·12를 각각 확인한다. 확인함만 있는 기능,
   확인함과 문제 있음이 섞인 기능, 사유가 비어 있는 항목을 각각 넣어 문구와 조작 가능 여부를 단언한다.
   명령: `npx vitest run src/features/projects/components/qa/QaReviewSubmit.test.tsx`
2. 제출 동작 검사를 추가하고 실행한다. 완료 조건 5·6·7·8·10을 확인한다. 앱 통로를 흉내 낸 값으로 전 건
   성공, 일부 실패, 검토 시작 뒤 변경을 각각 돌려주고 화면의 결과와 남은 임시 검토를 단언한다. 재시도에서
   보낸 대상 목록에 성공한 항목이 없음을 단언한다. 통로가 한 번만 불렸음도 함께 단언한다.
   명령: `npx vitest run src/features/projects/components/qa/QaWorkbench.test.tsx`
3. 껍데기 화면 검사에 전달 선언 검사를 추가하고 실행한다. 품질 확인 화면이 제출 동작을 실제로 받는지
   확인한다.
   명령: `npx vitest run src/features/projects/components/WorkspaceShell.test.tsx`
4. 완료 조건 11은 대기열 행에서 시작해 항목 결과 선택과 검토 이동과 최종 제출까지 키보드 조작만으로
   이어지는 검사로 확인한다. 사유가 빈 항목을 만들어 초점이 그 자리로 가는지도 단언한다.
5. 타입 검사와 저장소 전체 검사를 실행한다. 명령: `npm run typecheck` 다음 `npm test`

## 확인 동선

준비물: 같은 기획서에서 나온 품질 확인 대기 작업이 둘 이상인 기능 하나. 없으면 개발 화면에서 그런
기능을 먼저 만들어 둔다.

1. 앱을 열고 왼쪽 주요 메뉴에서 품질 확인을 누른다. 지금 확인할 기능 구획에서 기능 행을 누른다.
2. 항목 확인 본문 아래쪽에 `제출 전 검토로 넘어가기`가 보인다. 결과를 고르지 않은 항목이 남아 있는
   동안에는 이 조작을 쓸 수 없고, 그 아래에 `결과를 고르지 않은 항목이 N개 남았습니다.`가 보인다.
   N은 아직 확인함도 문제 있음도 고르지 않은 항목 수와 같아야 한다.
3. 모든 항목에 결과를 남긴다. 하나는 확인함으로, 하나는 문제 있음으로 하고 문제 있음에는 사유를 적는다.
   마지막 항목에 결과를 남기는 순간 남은 수 안내가 사라지고 조작이 열리면 정상이다.
4. `제출 전 검토로 넘어가기`를 누른다. 재작업 요청으로 기록할 항목 구획이 위에, 확인 완료로 기록할
   항목 구획이 아래에 오고 각 제목에 `재작업 요청 N건`과 `확인 완료 N건`이 붙으면 정상이다. 확인 완료
   구획이 위에 오거나 건수가 없으면 잘못된 것이다.
5. 최종 버튼 문구를 읽는다. 확인함만 있으면 `확인 완료 N건 기록하기`, 섞여 있으면
   `확인 완료 N건과 재작업 요청 M건 기록하기`여야 한다. 건수가 문구에 없으면 잘못된 것이다.
6. 검토 화면에서 한 항목의 메모를 고치고 다른 항목의 결과 단추를 눌러 구획을 옮긴다. 옮긴 뒤에도
   나머지 항목의 결과와 메모가 그대로 남아 있어야 한다.
7. 한 항목에서 `이 항목 다시 보기`를 누른다. 항목 확인 화면이 바로 그 항목에서 열리고 초점이 그 본문에
   있으면 정상이다. 다시 `제출 전 검토로 넘어가기`를 눌러 돌아오면 다른 항목의 결과와 메모가 그대로다.
8. 재작업 요청 항목의 메모를 모두 지운 뒤 최종 버튼을 누른다. 제출되지 않고 사유가 필요하다는 안내가
   뜨며 초점이 그 항목의 메모 입력으로 가야 한다. 사유를 다시 적으면 제출이 열린다.
9. 문제가 없는 기능으로 최종 버튼을 한 번 누른다. 같은 버튼을 시간 안에 다시 누르라고 요구하지 않고
   한 번에 기록되면 정상이다. 기록 뒤에는 대기열로 돌아가고, 그 기능 행이 `계속` 대신 `시작`으로
   바뀌거나 목록에서 사라져야 한다.
10. 확인함과 문제 있음이 섞인 기능을 제출한다. 개발 화면에서 확인함 작업은 완료로, 문제 있음 작업은
    재작업 요청으로 상태와 이력이 바뀌었는지 확인한다.
11. 검토 화면을 연 채로 그 기능의 작업 문서 하나를 편집기에서 고쳐 저장한다. 화면을 새로 고치면 그
    항목에 `다시 확인 필요`가 붙고 최종 제출이 막히며 초점이 그 항목의 `이 항목 다시 보기`로 가야 한다.
12. 일부 실패는 앱을 끄지 않고는 만들기 어렵다. 재현 조건이 갖춰지면 화면이 닫히지 않고 항목마다
    기록됨과 실패 사유가 갈려 보이며, 실패한 항목만 아래 구획에 남고 최종 버튼 건수도 그만큼 줄어야
    한다. 이 상태에서 다시 제출하면 이미 기록된 작업에 결정이 두 번 남지 않아야 한다. 이 갈래는
    `QaWorkbench.test.tsx`의 일부 실패 검사 두 건이 앱 통로를 흉내 내어 자동으로 확인한다.
13. 창 너비를 980픽셀 아래로 줄인다. 검토 화면이 가로 스크롤 없이 읽히고 최종 제출을 그대로 쓸 수
    있어야 한다.
14. 대기열 행부터 최종 제출까지 키보드만으로 같은 길을 걷는다. 탭과 엔터로 기능을 열고 항목 결과를
    고르고 검토로 넘어가고 최종 제출까지 간다. 검토 화면으로 넘어간 직후 초점이 그 화면에 있어야 하고,
    제출이 막히면 초점이 막힌 자리로 가야 한다.
