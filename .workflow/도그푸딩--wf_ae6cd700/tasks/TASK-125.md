# 개발자 분기가 단일 훑기 어법으로 접혀 같은 상한 안에 들어온다

## 결정권자 요약

개발 세션을 띄울지 판정하는 검사가 문서 세 배 규모에서 22.4초 걸리던 것이 1.5초로 내려왔다. 데몬은
10초에서 판정을 끊고 끊긴 판정을 "일감 없음"으로 처리하므로, 그대로 두면 개발 잡이 조용히 뜨지 않는
날이 온다. 그 자리가 닫혔다.

판정 규칙은 한 줄도 바뀌지 않았다. 같은 저장소에서 세 역할의 답이 바뀌기 전과 후에 같고, 손으로 만든
열다섯 가지 경계 상황에서도 두 판정이 전부 같은 답을 냈다. 기획자와 아키텍트 부분은 글자 하나
건드리지 않았다.

감시 장치의 기준값을 내리는 일은 이 작업이 하지 않는다. 그 값은 이 착지 위에 세워야 하므로
TASK-126이 받는다.

## 확인 동선

**볼 화면이 없는 작업이다.** 바뀐 것은 하트비트 데몬이 부르는 조건 스크립트의 내부 어법이고, 그
결과는 화면에 뜨는 무엇이 아니라 판정에 걸리는 시간이다. 그래서 이 작업은 자동 검사와 아래 측정으로
닫았고, 확인 도장은 **그 숫자들을 믿는다**는 뜻이 된다. 직접 다시 재고 싶다면 아래를 그대로 밟으면
된다.

### 1. 판정이 그대로인지 (제일 중요한 자리)

프로젝트 루트에서 세 역할을 각각 돌린다. 앱이 설치해 둔 본문(바뀌기 전, v10)이다.

```sh
for r in planner architect developer; do sh .workflow/rules/wf-eligible.sh $r; echo "exit=$?"; done
```

바뀐 본문(v11)은 `src-tauri/src/infrastructure/heartbeat_condition.rs`의 `CONDITION_SCRIPT_SH` 상수
안에 있다. 꺼내서 같은 것을 물으면 된다.

```sh
awk '/^const CONDITION_SCRIPT_SH: &str = r#"/{f=1;sub(/^const CONDITION_SCRIPT_SH: &str = r#"/,"");print;next} f&&/^"#;$/{exit} f' \
  src-tauri/src/infrastructure/heartbeat_condition.rs > /tmp/v11.sh
for r in planner architect developer; do sh /tmp/v11.sh $r; echo "exit=$?"; done
```

**정상이면 여섯 줄이 짝지어 같다.** 이 세션이 잰 값은 planner `no-target`/1, architect
`no-target`/1, developer `eligible`/0이고, 두 본문이 같았다. 저장소 상태가 달라졌으면 값 자체는
달라질 수 있지만 **두 본문의 답은 여전히 같아야 한다.** 하나라도 갈리면 그것이 회귀다.

### 2. 빨라졌는지

```sh
time sh .workflow/rules/wf-eligible.sh developer   # 바뀌기 전
time sh /tmp/v11.sh developer                       # 바뀐 뒤
```

**정상이면 뒤엣것이 눈에 띄게 빠르다.** 이 저장소 규모(작업 126건)를 3배로 부풀린 픽스처에서
22.41초 → 1.47초였고, 목표는 3초 안이다.

### 3. 자동 검사

```sh
cargo test --manifest-path src-tauri/Cargo.toml
```

**정상이면 499건 전부 통과한다.** 이 안에 두 가지가 들어 있다 — 스크립트와 앱 판정이 같은 답을
내는지 대조하는 검사, 그리고 조건 스크립트가 띄우는 외부 프로세스 수를 세는 계량 검사다.

### 4. 알아 둘 것

- **데몬은 아직 옛 본문을 쓴다.** 앱이 설치하는 `.workflow/rules/wf-eligible.sh`는 여전히 v10이고,
  앱을 다시 빌드해 설치본이 갱신돼야 이 개선이 실제로 걸린다. 이 작업은 설치본을 손대지 않는다.
- **프런트엔드 검사(`npm run check`)도 핸드오프 시점에 통과한다**(642건). 다만 이 세션 중간의 두
  실행은 실패했는데, 그것은 같은 작업 트리에서 TASK-120 세션이 `DevelopmentBoard.tsx`를 편집하던
  중이었기 때문이다. 이 작업은 `src/` 아래를 하나도 건드리지 않았다. 자세한 경위는 보고서의
  "게이트" 절에 있다.

## 왜 지금 비싼가

원인은 컬렉션 크기의 곱이 아니라 **작업 문서 하나당 상수 개의 외부 프로세스**다. 그래서 비용이
작업 수에 선형이고, 비율 단언(3배 픽스처가 1배의 3.5배 이하)은 이미 통과하는데 절대 상한만
넘는다. 3배 픽스처에서 프로세스 2,743개이고 명령별로 `sed` 866 · `grep` 865 · `head` 722 ·
`date` 145 · `tr` 145다(SPEC-041 확인 사실 3).

프로세스가 뜨는 자리는 `heartbeat_condition.rs`의 sh 본문 `developer)` 절과 그 절이 부르는
헬퍼들이다. 후보 하나마다 상태 검사(`grep`), 문서 id 읽기(`sed`·`head`), `lease_blocks`,
`deps_of`가 돌고, 선행마다 `task_file`(`grep -ls`)·`dep_satisfied`(`grep`)·`reaches`(같은 헬퍼
재귀)가 돌며, 마지막에 `overlap_blocks`가 lease마다 `scope_of`를 부른다.

기획자·아키텍트 분기는 이미 상수다(각각 3개·2개). 그 둘을 그렇게 만든 어법이 이 파일 안에 이미
넷 있다 — `scan_ideas`·`scan_refs`·`scan_decisions`·`scan_nondraft_refs`. 새 어법을 발명하지
않는다.

## 접는 방법

### 원칙

- **디렉터리마다 훑기 한 번.** `tasks/*.md` 한 번, `.workflow/.runtime/leases/*.yml` 한 번,
  현재 시각 한 번. 그 뒤로는 외부 명령을 부르지 않는다.
- **후보별 조회는 프로세스를 띄우지 않는 수단으로만.** `case`와 파라미터 확장이다. 조회마다
  `grep`이나 `sed`를 부르면 비용이 프로세스에서 자리만 옮긴다.
- **모은 값은 셸 변수에 담는다.** 임시 파일을 쓰지 않는다. 조건 스크립트는 `.workflow` 아래에
  아무것도 쓰지 않는다(R3, 완료 조건 11).

### 훑기가 내야 하는 값

작업 문서 하나마다 아래 여섯이 필요하다. 지금 여섯 자리에서 따로 읽는 것을 한 번에 읽는 것뿐이고,
읽는 규칙은 지금 본문의 어법을 그대로 옮긴다.

1. 첫 `^id:` 줄의 값 — 후보 id.
2. 그 파일이 담은 **모든** `^id: *<값>$` 줄의 값 — 선행 해석용. 아래 "판정이 달라지면 안 되는
   자리" 4번이 이유다.
3. 후보 상태 여부 — `^status: (todo|in_progress)`가 파일 **아무 줄에나** 있는가.
4. 선행 충족 여부 — `^status: qa_waiting` 또는 `^status: completed`가 아무 줄에나 있는가.
5. 선행 선언 — `^depends_on:`으로 시작하는 줄의 **개수**와 첫 줄의 값.
6. 겹침 선언 — `^scope_files:`으로 시작하는 줄의 **개수**와 첫 줄의 값.

lease 디렉터리는 파일마다 (파일 이름에서 뽑은 대상 id, 첫 `^expires_at:` 줄의 값)이면 된다.
따옴표 제거는 지금 `tr -d`가 하는 것과 같은 범위여야 한다.

선언 문자열의 파싱(대괄호 여부, 토큰 분리, 허용 문자 검사)은 지금 `deps_of`·`scope_of`가 하는
그대로 두되 **셸 내장으로만** 한다. 지금 토큰마다 `sed`를 하나씩 띄우는 자리가 그 안에 있다.

### 순환 선언 검출

`reaches`가 지금 선행을 따라가며 `task_file`·`deps_of`를 다시 부른다. 훑기 결과가 있으면 그
탐색이 문자열 조회만으로 끝난다. 방문 집합으로 종료를 보장하는 지금 성질은 그대로 둔다.

### 현재 시각

`lease_blocks`가 호출마다 `date -u`를 부른다. 훑기 앞에서 한 번 부르고 그 값을 쓴다. 판정 순간이
하나로 모이는 것은 앱 이식본(`role_eligibility.rs`)이 이미 그렇게 하고 있는 방식이고, 계약이
요구하는 "만료 판정은 판정 시점 기준"과 어긋나지 않는다.

### 조기 종료

첫 자격 후보에서 `verdict eligible 0`으로 끝나는 성질은 그대로다. 후보를 보는 순서도 지금과 같은
글롭 순서다. 훑기 비용을 앞에서 한 번 치르는 것은 기획자·아키텍트 분기가 이미 그런 모양이다.

### 윈도우 본문

같은 규칙을 같은 모양으로 담는다. 그쪽은 `$lineCache`가 있어 프로세스가 파일마다 뜨지 않으므로
비용 문제가 다르지만, 두 본문이 갈라지면 `SCENARIOS` 표가 두 답을 내기 시작한다. 이 작업의
윈도우 쪽 의무는 **판정 동일성**이고, 상한 검증은 sh 본문으로만 한다(SPEC-041 확인 필요 2번의
승인된 제안). 로컬에 `pwsh`가 없어 실행하지 못했다면 그 사실을 보고서에 적는다.

### 버전 줄

`CONDITION_SCRIPT_VERSION`과 두 본문의 버전 줄을 함께 올린다(10 → 11). 셋 중 하나만 올리면 버전
일치 단언이 먼저 깨진다. 설치본(`.workflow/rules/wf-eligible.sh`)은 **손대지 않는다** — 앱이
설치하는 자산이고, 앱이 다시 설치하기 전까지 데몬이 옛 본문을 쓰는 것은 알려진 구조다.

## 판정이 달라지면 안 되는 자리

여기 적힌 것은 전부 지금 본문이 실제로 하는 일이고, 훑기로 접을 때 소리 없이 달라지기 쉬운
자리다. R3·완료 조건 7·8이 이것들을 묶어서 요구한다.

1. **상태 검사는 앞자리 일치다.** `grep -qsE "^status: (todo|in_progress)"`는 값 전체를 보지
   않는다. `status: todoish`도 후보이고, `dep_satisfied`의 `^status: qa_waiting`도 마찬가지다.
   값 전체 비교로 바꾸면 그 문서에서 답이 뒤집힌다.
2. **상태 줄은 프론트매터에 한정되지 않는다.** 지금 `grep`이 파일 아무 곳이나 보므로 본문에 적힌
   예시 줄도 잡힌다. 첫 `status:` 줄만 보는 어법으로 바꾸면 답이 갈린다. 문서 id는 반대로 **첫**
   `^id:` 줄이다(`sed ... | head -1`).
3. **선언 줄 개수가 판정에 든다.** `depends_on:`이 두 줄 이상이면 미충족이고, `scope_files:`는
   정확히 한 줄이 아니면 판정 불가(= 막힘)다. 키가 없는 경우도 둘이 갈린다 — 선행은 "선언 없음 =
   충족", 겹침은 "선언 없음 = 막힘"이다.
4. **선행 해석은 후보 id 읽기와 다른 규칙을 쓴다.** `task_file`은 `grep -ls "^id: *<dep>$"`로
   파일 **아무 줄이나** 보고 글롭 순서로 **첫 파일**을 고른다. 후보 id는 첫 `^id:` 줄 하나다.
   두 규칙이 갈리는 문서(첫 id 줄 뒤에 다른 id 줄이 또 있는 문서)에서 지금과 같은 답이 나와야
   한다.
5. **겹침 판정의 게으른 자기 선언 읽기.** `overlap_blocks`는 막을 lease를 처음 만났을 때에만 자기
   선언을 읽는다. 활성 lease가 하나도 없으면 자기 선언이 형식 오류여도 막히지 않는다. 훑기가
   선언을 미리 읽더라도 이 성질이 유지돼야 한다.
6. **겹침 비교는 문자열 완전 일치다.** 경로 정규화도, 글롭도, 디렉터리 접두 일치도, 대소문자
   접기도 없다. 자기 lease는 건너뛴다. 잡힌 lease의 대상이 작업 문서가 아니면 막지 않는다.
7. **만료 표기 판정.** `????-??-??T??:??:??Z` 자리수 모양만 유효하고, 그 밖의 표기는 선점으로
   세지 않는다. 비교는 사전순 문자열 비교다. lease 파일을 읽기만 하고 지우거나 고치지 않는다.
8. **읽을 수 없는 파일은 목록에서 뺀다.** 지금 `grep -s`와 스캔 헬퍼가 그렇게 한다.
9. **사유 코드는 표준 출력의 첫 줄이자 유일한 줄이다.** 새 코드를 만들지 않는다. 훑기의 목록
   출력이 표준 출력으로 새면 그 줄이 사유를 밀어낸다 — 지금 헬퍼들이 출력을 반드시 명령 치환으로
   받는 이유가 그것이다.

## 완료 조건

1. 개발자 분기가 3배 픽스처에서 3초 안에 끝난다. 1배 픽스처에서도 상한 안이다. (기획서 완료
   조건 1·2, R1)
2. 기획자·아키텍트 분기의 값이 나빠지지 않는다. (기획서 완료 조건 2, R1)
3. 개발자 분기의 프로세스 계량이 착수 전(1배 919 · 3배 2,743)보다 내려가고, 비율 단언이 그대로
   통과한다. 기존 상한 상수는 이 작업에서 **손대지 않는다** — 내리는 것은 TASK-126이다.
   (기획서 완료 조건 3, R2)
4. "판정이 달라지면 안 되는 자리" 아홉이 전부 지금과 같은 답을 낸다. (기획서 완료 조건 7, R3)
5. 이 저장소의 실제 문서에서 세 역할의 사유 코드와 종료 코드가 착수 전과 착지 후에 같다. 값이
   달라졌다면 그 차이가 이 변경의 것이 아님을 근거와 함께 적는다. (기획서 완료 조건 7, R3)
6. 앱과 스크립트를 대조하는 기존 시나리오가 **기대값 수정 없이** 통과한다. 기대값이 뒤집힌 검사가
   하나도 없다. (기획서 완료 조건 8, R3·R4)
7. 두 플랫폼 본문이 같은 규칙을 담고, `CONDITION_SCRIPT_VERSION`과 두 본문의 버전 줄이 함께
