# dream 카드가 같은 통로로 실행 한도 사용량과 미정제 대기 경고를 보여준다

SPEC-009 R1·R2·R5의 dream 몫과 R3·R4의 dream 몫을 구현한다. dream 잡도 역할 잡과 같은 규칙으로
사용량과 소진을 보여주고, 소진 상태에서 미정제 트랜스크립트가 남아 있으면 경고한다. TASK-030이
연 골격 통로를 그대로 쓴다.

## 의존성

- **선행 필수: TASK-030.** 타입(`JobQuota`)과 골격의 `bodyWarning` 통로가 먼저 있어야 한다.
- TASK-030과 병행 금지. 어법과 표시 규칙을 그 작업이 정한다.
- TASK-028·TASK-029는 TASK-030의 선행이므로 자연히 먼저 끝나 있다.

## 범위

- `src/features/projects/components/integrations/DreamCard.tsx` — 사용량·소진·경고 표시.
- `src/features/projects/components/integrations/DreamCard.test.tsx` — 픽스처와 새 테스트.
- 그 외 파일은 건드리지 않는다. 골격·타입·뷰·CSS는 TASK-030이 이미 마쳤고, 이 작업은 그것을
  쓰기만 한다.

## 작업 내용

### 0. 먼저 읽을 제약

- **잡 종류별로 다른 규칙을 만들지 않는다**(R1 마지막 줄). 사용량 표시·소진 판정·회복 시각은 역할
  잡과 같은 규칙이고, 다른 것은 "무엇이 대기 중인가"의 근거뿐이다.
- dream의 대기 물량은 **미정제 트랜스크립트 수**다(R3). 역할 잡의 판정 경로
  (`pendingWork`)를 억지로 공유하지 않는다. 값은 이미 payload에 있다
  (`dream.refinement.unrefinedTranscripts`).
- 마이그레이션 락은 dream 경고에 영향을 주지 않는다. 락이 막는 것은 역할 세션이고 dream은 역할
  잡이 아니다. 기획서 완료 조건 9도 "역할 잡의 한도 경고"로 한정한다.
- 소진만으로는 경고가 아니다(R3). 미정제가 0건이면 사실 표시에 그친다.
- 관리 블록에 dream 잡이 없으면(`managedJob === null`) 아무것도 그리지 않는다. 지금 실행 기록을
  `installed &&`로 감싸는 것과 같은 조건이다(`DreamCard.tsx:558`).
- 관리 블록을 읽지 못한 상태에서는 잡 블록이 `UnreadableManagedBlock`으로 대체되므로 사용량도
  그려지지 않는다(`:159`~`:168`). 새 분기를 만들지 않고 그대로 성립한다는 것만 테스트로 못 박는다.

### 1. 사용량 표시

잡 행의 실행 기록 블록(`:558`~`:566`) 뒤에, 같은 `installed &&` 조건 아래 사용량 줄을 더한다.
실행 기록 블록은 고치지 않는다.

값은 `snapshot.dream.quota`다. 표시 규칙은 TASK-030이 하트비트 카드에 적용한 것과 같다.

- `counted`: `{used}/{limit} · {window} 기준`. `exhausted`이면 소진 표시와, `recoversAt`이 있으면
  로컬 시각으로 바꾼 회복 예상 시각을 함께 보여준다. "예상"임을 문구에 남긴다.
- `noRuns`: `실행 기록 없음 · 한도 {limit}회/{window}`. `0/`으로 적지 않는다.
- `unlimited`: `한도 없음`과 그 이유. 소진 표시도 경고도 없다.
- `unknown`: 아무것도 그리지 않는다.

문구와 클래스 이름은 TASK-030이 하트비트 카드에서 쓴 것과 **같은 낱말**을 쓴다. 두 카드가 같은
사실을 다른 말로 부르면 사용자가 두 규칙이 있다고 읽는다. 다만 표시 컴포넌트를 공유 파일로 빼지
않는다 — 두 카드가 각자 자기 잡을 그리는 지금 구조를 유지한다(`runResultLabels`가 두 파일에 따로
있는 것과 같은 선택이다).

### 2. 미정제 대기 경고 (R3)

조건은 `quota.kind === "counted" && quota.exhausted && refinement.unrefinedTranscripts > 0`이다.
`IntegrationWarning`으로 잡 행 안에 그린다.

문구에는 넷이 들어간다.

1. 무엇이 대기 중인지 — 미정제 트랜스크립트 수. 값이 이미 개수이므로 그대로 쓴다.
2. 왜 실행되지 않는지 — 실행 한도가 차서 하트비트가 조건 검사 전에 건너뛴다는 사실.
3. 언제 풀리는지 — 회복 예상 시각(있을 때).
4. 한도를 올리려면 어디를 보면 되는지 — 같은 잡 행의 실행 한도 입력 칸과 저장 버튼.

이미 카드에 있는 안내("미정제 수는 마킹 기준이고 한 번에 처리되는 수는 이보다 적을 수 있다",
`:644`~`:646`)와 어긋나지 않게 쓴다. 경고는 "정제할 것이 남아 있는데 잡이 안 돈다"는 사실까지다.

### 3. 골격에 경고를 알린다 (R4)

`DreamCard`(`:118`)가 `IntegrationCard`에 `bodyWarning={...}`을 넘긴다. 값은 2번의 조건과 같다.
`snapshot`이나 `dream`이 `null`이면 `false`다.

TASK-030이 만든 통로를 그대로 쓴다. 골격도 뷰도 이 작업에서 바뀌지 않는다. 이것이 "세 번째 연동이
같은 통로를 그대로 쓴다"가 성립한다는 증거다(기획서 완료 조건 11).

### 4. 테스트 (`DreamCard.test.tsx`)

`dream`(`:40` 부근) 픽스처에 `quota` 기본값을 더한다. 기본값은 여유 있는 `counted`로 둔다.
`{ kind: "unknown" }`을 기본으로 두면 새 표시가 대부분의 기존 테스트에서 안 그려져 회귀를 놓친다.

새 테스트:

- 관리 블록에 dream 잡이 있으면 사용량 표시가 보이고 마지막 실행 기록 표시도 함께 남는다.
  (기획서 완료 조건 1의 dream 몫)
- 한도 값이 관리 블록의 값과 같다. 앱 기본값(`6/24h`)이 아닌 값을 픽스처로 준다.
  (기획서 완료 조건 3)
- 소진 상태에서 소진 표시와 회복 예상 시각이 함께 보이고 문구에 "예상"이 들어 있다.
  (기획서 완료 조건 4)
- 소진 + 미정제 1건 이상에서 경고가 보이고, 소진 + 미정제 0건에서는 사실 표시만 있다.
  (기획서 완료 조건 5, 8)
- `lastResult: quota_skipped`이고 미정제 0건이면 경고가 없다. (기획서 완료 조건 7)
- 접힌 카드에 `확인할 경고가 있습니다`가 보인다. 소진이지만 미정제 0건이면 보이지 않는다.
  (기획서 완료 조건 10, 11)
- `noRuns`에서 `실행 기록 없음`이 보이고 `0/`로 시작하는 사용량 표시가 없다.
  (기획서 완료 조건 12)
- 관리 블록 읽기 실패 상태에서 사용량 표시가 없다. (기획서 완료 조건 13)
- `unlimited`에서 `한도 없음`이 보이고 소진 표시와 경고가 없다. (기획서 완료 조건 14)
- `used`가 `limit`보다 커도 오류 없이 소진으로 그려진다. (기획서 완료 조건 15)
- 관리 블록에 dream 잡이 없으면 사용량 표시가 없다.

`DreamCardHost`(`:81`)가 이미 접기·펼치기를 대신하므로 접힘 요약 테스트는 그 껍데기로 접어서
확인한다(`dream 카드 접기` describe, `:673`의 선례).

## 완료 조건

1. 관리 블록에 설치된 dream 잡의 사용 횟수·한도 횟수·창 길이가 보이고, 기존 마지막 실행 기록
   표시가 그대로 남는다. (기획서 완료 조건 1)
2. 한도 값이 관리 블록의 값이다. (기획서 완료 조건 3)
3. 소진 상태에 소진 표시와 로컬 시각의 회복 예상 시각이 함께 보인다. (기획서 완료 조건 4)
4. 소진이면서 미정제 트랜스크립트가 1건 이상일 때만 경고가 보인다. (기획서 완료 조건 5, 8)
5. `lastResult: quota_skipped`만 있고 미정제가 없으면 경고가 없다. (기획서 완료 조건 7)
6. 경고가 있으면 카드가 접혀 있어도 경고가 있다는 표시가 보인다. (기획서 완료 조건 10)
7. 두 연동이 같은 통로(`bodyWarning`)로 요약 경고를 띄운다. 이 작업은 골격을 고치지 않는다.
   (기획서 완료 조건 11)
8. 실행 기록이 없으면 `0`이 아니라 "실행 기록 없음"으로 보인다. (기획서 완료 조건 12)
9. 관리 블록을 읽지 못한 상태에서 사용량 표시가 없다. (기획서 완료 조건 13)
10. `max_per` 형식이 깨진 잡이 "한도 없음"으로 보이고 소진 표시·경고가 없다. (기획서 완료 조건 14)
11. 사용 횟수가 한도보다 커도 오류 없이 소진으로 보인다. (기획서 완료 조건 15)
12. 두 카드의 사용량 문구가 같은 낱말을 쓴다.
13. SPEC-003·SPEC-005·SPEC-006 계열의 기존 dream 테스트가 통과한다. 삭제·비활성화된 테스트가 없다.
    (기획서 완료 조건 18)
14. `npm run check`가 통과한다. (기획서 완료 조건 19)

## 검증 절차

```sh
npm run check
```

앱에서 확인한다.

- 연동 화면에서 dream 카드를 펼쳐 사용량이 보이는지 본다. 관리 블록에 dream 잡이 없으면 먼저
  설치한 뒤 확인한다.
- dream 잡의 실행 한도를 일시적으로 낮춰(예: `1/24h`) 저장한 뒤 소진 표시가 나오는지, 미정제
  트랜스크립트가 남아 있으면 경고까지 뜨는지 본다. 확인 후 값을 되돌린다.
- 카드를 접어 요약에 경고 표시가 남는지 본다. 같은 시각에 하트비트 카드도 함께 보아 두 카드가 같은
  방식으로 표시되는지 확인한다.

## 참고 사실

확인 시점 2026-08-03. 추정 없이 파일에서 읽은 값이다.

- dream 잡의 실행 기록은 `DreamCard.tsx:558`~`:566`이고 `installed &&`로 감싸여 있다. 기록이 없으면
  `실행 기록 없음` 한 줄이다(`:565`).
- `runResultLabels`(`:32`)는 하트비트 카드(`HeartbeatCard.tsx:29`)와 같은 표를 각자 갖고 있다.
  두 카드가 어법은 맞추되 코드를 공유하지 않는 선례다.
- 미정제 수는 `dream.refinement.unrefinedTranscripts`이고 카드가 이미 보여준다(`:640`).
  그 값이 마킹 기준이라는 단서도 함께 적혀 있다(`:644`~`:646`).
- dream 잡의 앱 기본값은 `dream.defaults`이고 `2h`·`6/24h`·`opus`다
  (`heartbeat_dream.rs:66`의 `default_settings`).
- 관리 블록의 dream 잡은 `dream.managedJob`이고 없으면 `null`이다. 카드는 그것을 `installed`로
  판정한다(`:274`).
- `DreamCardHost`(`:81`)는 펼침 상태를 대신 들고 있는 테스트 껍데기다. 시작이 펼침이므로 접힘
  테스트는 토글을 한 번 누른다.
- dream 카드 테스트의 스냅샷 픽스처는 `heartbeat` payload를 최소 형태로 채운다(`:63`~`:71`).
  `roles`가 빈 배열이라 역할 잡 사용량은 이 파일에서 그려지지 않는다.
- 이 저장소에 eslint·biome 설정이 없다. `npm run check`는 `tsc -b` + `vitest run` + `vite build`다.
