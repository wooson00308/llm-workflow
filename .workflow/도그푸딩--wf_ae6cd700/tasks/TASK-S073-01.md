# 기능 상태 계산이 구성 오류 사유와 사람 판단 필요 상태를 함께 내려준다

## 결정권자 요약

### 제안

기능 상태를 계산하는 쪽이 구성 확인 필요로 답할 때 어떤 조건이 맞지 않았는지를 함께 내려주고,
아키텍트가 문서로는 못 고친다고 남긴 기능을 사람 판단 필요 상태로 답하게 한다.

### 현재

기능 상태는 이름 하나만 나온다. 구성 확인 필요는 다섯 갈래의 서로 다른 원인을 한 이름으로 합쳐
보여주고, 화면은 그 원인을 알 방법이 없다. 아키텍트가 문서 쪽에 고칠 곳이 없다고 판단해도 그 사실을
기능에 남길 자리가 없어서, 같은 기능이 계속 같은 이름으로만 남는다.

### 변경 후

화면이 상태와 함께 사유 목록을 받는다. 필수 값 문제, 작업 없음, 작업 연결 어긋남, 사용자 확인 절차
문제, 자동 모드에 절차가 적힌 문제, 끝나지 않은 작업이 각각 다른 값으로 오므로 화면이 문서를 다시
읽지 않고도 사용자에게 원인을 말해 줄 수 있다. 아키텍트가 판단을 남긴 기능은 사람 판단 필요라는
별도 상태로 오고, 사용자가 무엇을 판단해야 하는지도 함께 온다.

### 비용과 위험

상태 계산 규칙 자체는 넓히거나 좁히지 않는다. 지금까지와 같은 문서 집합을 넣으면 같은 상태가
나오고, 새로 생긴 값은 상태 옆에 붙는 설명이다. 사람 판단 필요는 아키텍트가 기능 문서에 판단을
남긴 기능에서만 나오므로 지금 있는 어떤 기능의 상태도 이 작업으로 바뀌지 않는다. 품질 확인 제출과
승인 도장이 열리는 조건은 그대로다. 되돌리면 지금의 이름 하나짜리 표시로 돌아간다.

## 현재 코드 상태

기능 표시 상태의 정본은 `src-tauri/src/domain/project.rs` 280행의 `WorkGroupDisplayStatus`다. 지금
값은 아홉이고 `configuration_error`가 그중 하나다. 이 값을 담아 화면으로 나가는 요약은 같은 파일
303행의 `WorkGroupSummary`이며, 사유를 담을 자리는 아직 없다.

상태를 계산하는 곳은 `src-tauri/src/infrastructure/fs_project_repository.rs` 3098행의
`read_work_groups`가 부르는 그룹 하나짜리 판독이고, 판정 사슬은 같은 파일 3202행부터 3246행까지다.
사슬은 위에서부터 완료, 재분류 대기, 준비 중과 중단 의심, 개발 막힘, 개발 중을 거른 뒤 남은 것에
대해 다음 다섯 가지 가운데 하나라도 참이면 `ConfigurationError`로 답한다.

- `structurally_valid`가 거짓이다. 3185행부터 3197행이 식별자, 구성 버전, 출처 기획서, 출처 승인,
  최종 변경 시각, 상태 값, 확인 모드 값, 확인 절차 번호 중복을 함께 본다.
- `task_revisions_valid`가 거짓이다. 3179행이 이 구성 버전에 속한 작업이 하나도 없는 경우와 3276행의
  `task_is_valid_for_group`이 거짓인 경우를 함께 담는다.
- 사용자 확인 모드인데 확인 절차가 없거나 3390행의 `scenario_is_user_safe`가 거짓이다.
- 자동 확인 모드인데 확인 절차가 적혀 있다.
- 남은 작업 가운데 `verified`가 아닌 것이 있다. 앞 분기에서 `blocked`·`todo`·`in_progress`를 이미
  걸렀으므로 여기에는 그 셋이 아닌 낯선 상태 문자열만 남는다.

기능 문서 본문은 3288행의 `parse_work_group_body`가 확인 절차로, 3346행의
`parse_work_group_description`이 기능 설명으로 가른다. 설명은 `## 기능 설명` 절이며 다음 `##` 제목에서
끝난다. 그래서 `##` 제목으로 시작하는 절을 새로 두어도 설명 판독은 달라지지 않는다.

화면 쪽 계약은 `src/features/projects/domain/types.ts` 160행의 `WorkGroupDisplayStatus` 합집합과
182행의 `WorkGroupSummary`다. 백엔드 요약이 그대로 이 형태로 실려 오고 중간에서 값을 다시 만들지
않는다.

상태 이름 표는 세 화면에 각각 있다. `src/features/projects/components/DevelopmentBoard.tsx` 508행,
`src/features/projects/components/qa/QaWorkbench.tsx` 154행,
`src/features/projects/components/SpecWorkspace.tsx` 375행이다. 세 표 모두 상태 값을 빠짐없이 적은
객체를 색인하는 형태라, 상태 값이 하나 늘면 세 자리가 모두 타입 검사에서 걸린다. 개발 보드에는
505행에 상태 정렬 우선순위 배열도 있고, 여기에 없는 값은 정렬에서 맨 앞으로 밀린다.

품질 확인 제출은 같은 저장소 파일 835행에서 상태가 사용자 QA 대기일 때만 통과한다.

## 변경 범위

- 표시 상태에 사람 판단 필요를 더한다. 기능 문서 프론트매터의 선택 필드
  `configuration_unresolved_revision`을 읽어, 그 값이 그 기능의 현재 구성 버전과 같은 수이고 판정이
  구성 확인 필요로 답할 자리일 때만 이 상태로 답한다. 그 밖의 모든 자리에서는 지금과 같은 값을
  답한다.
- 구성 확인 필요와 사람 판단 필요로 답할 때 사유 목록을 함께 만든다. 값은 여섯이고, 위에 적은 다섯
  갈래 가운데 두 번째를 작업 없음과 작업 연결 어긋남으로 나눈 것이다. 해당하는 조건이 여럿이면
  여럿을 담는다.
- 기능 문서 본문에서 `## 사람의 판단이 필요한 이유` 절을 읽어 요약에 싣는다. 절이 없거나 비어 있으면
  빈 값으로 싣는다.
- 두 값을 프론트 계약 타입에 옮기고, 세 화면의 상태 이름 표에 새 상태의 이름을 더하고, 개발 보드의
  정렬 우선순위 배열에도 새 상태를 넣는다. 이 작업에서 세 화면이 하는 일은 여기까지이며, 사유를
  문장으로 풀어 보여주는 일은 TASK-S073-04가 맡는다.

## 범위 밖

- 구성 오류로 판정하는 조건 자체를 넓히거나 좁히는 일. 사용자 확인 절차가 사용자 행동으로 인정되는
  기준도 그대로 둔다.
- 사유를 사용자 문장으로 풀어 화면에 그리는 일. TASK-S073-04가 맡는다.
- 아키텍트 대상 판정에 이 상태를 넣는 일. TASK-S073-03이 맡는다.
- 아키텍트가 판단을 남기는 절차를 역할 계약에 적는 일. TASK-S073-02가 맡는다.

## 완료 조건

- C1. 기능 문서에 `configuration_unresolved_revision`이 없거나 그 값이 현재 구성 버전과 다르면, 모든
  기능의 표시 상태가 이 작업 전과 같다. 시험이 구성 확인 필요, 사용자 QA 대기, 개발 중, 개발 막힘,
  구성 중단 의심, 완료를 각각 확인한다. (기획서 R-19, 인수 조건 13)
- C2. 그 필드의 값이 현재 구성 버전과 같은 수이고 판정이 구성 확인 필요로 답할 자리이면 사람 판단
  필요로 답한다. 같은 필드가 있어도 판정이 다른 상태로 답할 자리이면 그 상태를 그대로 답한다.
  (기획서 R-18)
- C3. 구성 확인 필요로 답할 때 사유 목록에 해당하는 값이 모두 담긴다. 여섯 값은 필수 값 문제, 작업
  없음, 작업 연결 어긋남, 사용자 확인 절차 없음 또는 인정 불가, 자동 모드에 확인 절차 있음, 끝나지
  않은 작업 남음이다. (기획서 R-07)
- C4. 두 조건 이상에 해당하는 기능에서 사유 목록의 길이가 둘 이상이고, 두 조건이 각각 다른 값으로
  담긴다. 하나로 합친 값을 만들지 않는다. (기획서 R-09, 인수 조건 5)
- C5. 사유를 하나도 만들지 못하는 경우 사유 목록은 빈 목록이고, 상태와 요약의 나머지 값은 그대로
  나온다. 판독이 중간에 끊기거나 그 기능이 목록에서 빠지지 않는다. (기획서 R-10, 인수 조건 6)
- C6. 구성 확인 필요와 사람 판단 필요가 아닌 상태에서는 사유 목록이 빈 목록이다.
- C7. 기능 문서 본문에 `## 사람의 판단이 필요한 이유` 절이 있으면 그 절의 본문이 요약에 실리고, 절이
  없으면 빈 값이 실린다. 이 절이 있어도 기능 설명과 확인 절차 판독 결과는 달라지지 않는다.
- C8. 구성 오류로 판정하는 다섯 갈래의 조건식이 이 작업 전과 같다. 조건을 더하거나 빼지 않았음을
  시험이 확인한다. (기획서 R-20)
- C9. 품질 확인 제출은 사용자 QA 대기에서만 통과하고, 사람 판단 필요 상태의 기능에 제출하면 지금과
  같은 거절로 끝난다. (기획서 R-21, 인수 조건 12)
- C10. 확인 절차를 사용자 행동으로 인정받게 고쳐 판정 조건을 충족시키면, 같은 기능 식별자와 같은
  구성 버전을 유지한 채 상태가 사용자 QA 대기로 바뀐다. (인수 조건 10의 상태 부분)
- C11. 프론트 계약 타입에 새 상태와 사유 목록, 판단 거리 값이 있고, 세 화면의 상태 이름 표와 개발
  보드 정렬 우선순위에 새 상태가 들어가 타입 검사와 화면 시험이 통과한다. 새 상태의 이름은
  사람 판단 필요다.

## 범위 사전 검사

선언한 여섯 파일은 값을 만드는 자리 둘, 계약을 적는 자리 하나, 값이 늘어나면 타입 검사가 깨지는
자리 셋이다. 완료 조건이 요구하는 편집이 이 여섯 밖으로 나가지 않는지를 아래에서 값마다 따라갔다.

그룹 밖 순서가 한 자리에 붙는다. 화면 계약 파일을 지금 TASK-S071-03이 함께 선언하고 있고, 그 작업이
먼저 끝난 뒤에 이 작업이 같은 파일을 고치도록 뒤로 두었다. GROUP-071의 사슬이 이미 진행 중이고 이
그룹은 이제 시작하므로, 진행 중인 쪽을 먼저 보낸다.

`src-tauri/src/commands/projects.rs`를 살펴보고 뺐다. 93행의 `inspect_project`가 저장소가 만든
`ProjectSummary`를 그대로 돌려주고 그룹 요약의 필드를 하나씩 옮겨 담는 자리가 없다. 요약 구조체에
필드를 더하면 직렬화가 그대로 실어 보내므로 이 파일은 고칠 것이 없다.
`src/features/projects/infrastructure/tauriProjectGateway.ts`도 같은 이유로 뺐다. 이 파일에는
`workGroups`를 다시 만드는 자리가 없고 응답을 계약 타입으로 받기만 한다.
`docs/file-contract.md`도 살펴보고 뺐다. 이 문서에는 작업 그룹 프론트매터를 적은 절이 없어서, 새
선택 필드를 적을 자리가 지금 없다. 아키텍트가 그 필드와 절을 언제 쓰는지는 역할 계약에 적히고 그
편집은 TASK-S073-02의 몫이다.
`src/features/projects/components/WorkspaceShell.tsx`도 살펴보고 뺐다. 114행은 사용자 QA 대기만,
791행과 817행은 완료 계열만 고르므로 상태 값이 하나 늘어도 판정이 달라지지 않고, 상태 이름 표를
들고 있지도 않다.
`src/features/projects/components/agents/AgentRunDashboard.tsx`도 같은 이유로 뺐다. 635행이 사용자 QA
대기만 고른다.

- 값 경로: C2의 사람 판단 필요 상태. 만드는 자리는
  `fs_project_repository.rs`의 그룹 판독(3202행부터 3246행의 판정 사슬)이고, 프론트매터
  `configuration_unresolved_revision`을 읽는 줄을 3159행 근처의 프론트매터 판독에 더해야 하므로 편집
  대상이다. 값의 형태는 `domain/project.rs` 280행의 `WorkGroupDisplayStatus`이며 열거 값이 하나
  늘어나므로 편집 대상이다. 전달은 같은 파일 303행의 `WorkGroupSummary`가 그대로 담고 직렬화 이름만
  바뀌므로 필드 추가 없이 지나간다. 화면 계약은 `types.ts` 160행의 합집합이라 편집 대상이고,
  소비 자리인 세 상태 이름 표(개발 보드 508행, 품질 확인 154행, 기획서 화면 375행)는 값이 늘면
  타입 검사가 깨지므로 모두 편집 대상이다. 개발 보드 505행의 정렬 우선순위 배열은 타입 검사에
  걸리지 않지만 값이 없으면 정렬이 어긋나므로 함께 고친다.
- 값 경로: C3부터 C6까지의 사유 목록. 만드는 자리는 같은 판정 사슬이고, 지금은 다섯 조건을 하나의
  참·거짓으로 합쳐 쓰므로 조건마다 값을 남기도록 편집한다. 값의 형태는 `domain/project.rs`에 새
  열거를 두고 `WorkGroupSummary`에 목록 필드를 더하므로 편집 대상이다. 전달은 위와 같은 이유로
