# 쌓인 미확인 실패를 최근 종료 머리에서 한 번에 확인 처리한다

## 결정권자 요약

### 제안

최근 종료 구역 머리에 일괄 확인을 두어, 남아 있는 미확인 실패 기록을 한 번에 확인 처리한다.

### 바뀌는 것

- 지금: 쌓인 실패를 하나씩 열어 확인해야 한다 → 앞으로: 머리의 버튼 한 번으로 남은 미확인 실패가 모두 목록에서 빠진다
- 목록에 보이는 세 건이 아니라 전체 실행 기록에 남아 있는 미확인 실패 전부가 대상이라, 다음에 오래된 실패가 다시 올라오지 않는다
- 누르기 전에 몇 건을 처리하는지 문장으로 밝히는 창이 한 번 뜬다

### 비용과 위험

- 되돌리기는 개별 확인 해제뿐이라, 한 번에 처리한 기록을 되살리려면 전체 실행 기록에서 하나씩 풀어야 한다.
- 버튼과 창만 더하므로 되돌리기 쉽고, 승인되지 않으면 개별 확인만 남는다.

## 현재 코드 상태

이 작업이 손대는 자리는 모두
`src/features/projects/components/agents/AgentRunDashboard.tsx` 안에 있다.

- 267행의 최근 종료 구역은 `recent.length > 0`일 때만 그려지고, 268행의 머리에 제목 하나와 전체 기록
  버튼 하나가 선다. 스타일은 `src/App.css` 63행이 정하며, 제목과 나머지를 양 끝으로 미는 배치라
  지금은 오른쪽 자리에 요소가 하나만 있다는 전제로 되어 있다.
- 91행의 `runs`가 프로젝트의 실행 전부이고, 진행 중이 아닌 실행을 거르는 식은 93행과 301행에 이미
  있다. 일괄 확인의 대상은 목록에 보이는 세 건이 아니라 이 전체에서 골라야 한다.
- 확인 창의 본보기는 같은 파일 안에 둘 있다. 567행의 취소 확인과 573행의 재시도 확인이며, 둘 다
  `agent-overlay` 위에 `agent-dialog`를 얹고 머리와 설명 한 줄과 바닥의 버튼 둘로 되어 있다. 두 창은
  백엔드가 만든 미리보기 값을 열쇠로 열리지만, 일괄 확인은 앱 바깥에 물어볼 것이 없어 화면이 스스로
  여닫는 값으로 연다.

앞선 작업 TASK-S083-01이 확인 표시 저장소와 확인한 실행 묶음을 이 화면 안에 이미 세워 둔다. 이
작업은 그 값과 그 저장 경로를 그대로 쓰고 새로 만들지 않는다.

## 변경 범위

`AgentRunDashboard.tsx`에서 다음을 더한다.

- 그 시점 실행 전체에서 진행 중이 아니고 상태가 `failed`이거나 `recovery_required`이며 아직 확인하지
  않은 실행을 골라 일괄 확인의 대상으로 삼는다.
- 최근 종료 구역 머리에 일괄 확인 버튼을 둔다. 대상이 하나도 없으면 그리지 않는다. 전체 기록 버튼은
  위치와 문구를 그대로 두고 나란히 세운다.
- 버튼을 누르면 대상 건수를 문장으로 밝히는 확인 창이 뜬다. 창에서 실행을 누른 순간에만 확인 표시가
  적용되고, 취소하면 아무것도 바뀌지 않는다. 창의 짜임은 취소·재시도 확인 창과 같은 방식으로 한다.
- 적용은 앞선 작업이 만든 저장소를 한 번 불러 끝낸다.

`src/App.css`에는 머리 오른쪽에 버튼 둘이 나란히 설 수 있게 하는 최소한의 규칙만 더한다. 63행의
배치 규칙 자체는 고치지 않는다.

## 범위 밖

- 확인 표시 저장소와 개별 확인·확인 해제. 앞선 작업 TASK-S083-01이 만들고 이 작업은 쓰기만 한다.
  저장소 파일과 그 시험은 이 작업의 선언에 들어 있지 않다.
- 전체 실행 기록의 회색 점과 확인함 표시, 그 목록에서 상세를 여는 통로. 모두 앞선 작업의 몫이다.
- 일괄 확인의 되돌리기. 기획서가 되돌리기는 개별 확인 해제뿐이라고 정했다. 되돌리기 버튼이나 방금
  처리한 건수를 알리는 표시를 만들지 않는다.
- 완료·취소됨·상태 확인 필요 기록. 일괄 확인의 대상이 아니며 이들에는 확인하는 방법 자체가 없다.
- 최근 종료 구역의 이름, 자르는 수 3, 정렬, 전체 기록 버튼의 위치와 문구.
- 조용한 한 줄의 문구와 조건.
- 백엔드 명령과 실행 기록 파일과 워크플로 문서와 결정 기록.

## 완료 조건

- C1. 일괄 확인의 대상이 그 시점 실행 전체에서 진행 중이 아니고 상태가 `failed`이거나
  `recovery_required`이며 아직 확인하지 않은 실행 전부다. 최근 종료 목록에 보이는 세 건으로 한정하지
  않는다. (기획서 R3, 완료 판정 A5)
- C2. 대상이 하나도 없으면 최근 종료 구역 머리에 일괄 확인이 그려지지 않는다.
  (기획서 R4, 완료 판정 A6)
- C3. 일괄 확인을 누르면 확인 창이 먼저 뜨고, 창에 몇 건을 확인 처리하는지 문장으로 적힌다. 그 수는
  C1의 대상 수와 같다. (기획서 R4, 완료 판정 A5)
- C4. 창에서 실행을 누른 뒤에만 확인 표시가 적용된다. 창을 취소하거나 닫으면 확인 표시가 하나도
  바뀌지 않는다. (기획서 R4)
- C5. 실행 뒤 대상이던 기록이 모두 최근 종료 목록에서 빠지고, 남은 종료 기록이 그 자리를 채운다.
  남은 기록이 하나도 없으면 구역 자체가 그려지지 않으며 그 자리에 새 문구가 서지 않는다.
  (기획서 R5, R6, R7, 완료 판정 A5, A7)
- C6. 적용된 확인 표시가 개별 확인과 같은 자리에 저장되어, 개별 확인 해제로 하나씩 되돌릴 수 있다.
  (기획서 R2, R10)
- C7. 일괄 확인이 브라우저 저장소 밖으로 아무것도 쓰지 않는다. 백엔드 명령을 부르지 않으므로 실행
  기록 파일과 워크플로 문서와 결정 기록이 그대로다. (기획서 R11, 완료 판정 A11)
- C8. 화면에 나오는 말이 일괄 확인이다. 확인 필요 구역의 문구와 동작은 그대로다. (기획서 R14)
- C9. 전체 기록 버튼의 위치와 문구, 최근 종료 구역의 이름, 목록의 줄 구성이 이 작업 전후로 같다.
  (기획서 R9, R15)
- C10. 선언한 세 파일 밖이 수정되지 않는다.
- C11. `npm run check`가 통과한다.

## 검증 절차

1. `AgentRuntimeView.test.tsx`에 시험을 더한다. 시험 이름에 어느 완료 판정을 확인하는지 적는다.
   - A5: 미확인 실패 다섯 건을 실어 최근 종료 목록에 두 건만 보이는 상태를 만든다. 일괄 확인을 누르면
     창에 다섯이라는 수가 적히고, 실행 뒤 다섯 건 모두가 최근 종료 목록에서 빠진다(C1, C3, C5).
   - A6: 실행이 완료와 취소됨뿐인 상태에서 최근 종료 구역에 일괄 확인이 없다. 개별 확인으로 미확인
     실패를 모두 처리한 뒤에도 없다(C2).
   - A7: 실행이 확인한 실패뿐이 되면 최근 종료 구역이 화면에서 사라지고, 확인한 기록이 있다는 문구도
     종료 기록이 없다는 안내도 없다(C5).
   - 창을 취소하면 최근 종료 목록의 줄이 그대로 남는다(C4).
   - 일괄 확인 뒤 전체 기록에서 한 건을 확인 해제하면 그 기록이 최근 종료 목록에 다시 온다(C6).
   - 전체 기록 버튼의 이름과 최근 종료 제목이 그대로다(C9).
2. `npm run test -- AgentRuntimeView`로 위 시험과 기존 시험이 모두 통과하는 것을 확인한다. 앞선
   작업이 더한 시험도 함께 통과해야 한다.
3. `npm run check`를 통과시킨다(C11).
4. `git status`로 선언한 세 파일 밖의 수정이 없음을 확인한다(C10). 일괄 확인을 실행한 뒤 워크플로
   폴더에 변경이 없는 것도 같은 방법으로 본다(C7, 완료 판정 A11).

## 범위 사전 검사

선언한 세 파일은 화면 파일과 그 시험과 스타일이다. 이 작업이 더하는 것은 대상 계산 하나, 버튼 하나,
창 하나, 적용 호출 하나이고 넷 다 화면 파일 안에서 끝난다. 아래 값 경로로 확인했다.

`src/features/projects/infrastructure/browserRunAcknowledgementStore.ts`를 열어 보고 뺐다. 앞선 작업
TASK-S083-01이 만드는 파일이고, 이 작업은 그 저장소의 저장 동작을 여러 실행 식별자에 대해 부르기만
한다. 한 번에 여러 건을 담는 일은 앞선 작업이 정한 저장 단위로 이미 되고, 새 함수를 더할 이유가 없다.
만약 구현 중에 저장소 쪽 편집이 필요하다는 사실이 드러나면 그 순간 이 작업의 선언이 짧은 것이므로,
작업을 막고 정의 오류로 되돌려야 한다.

`src/features/projects/domain/types.ts`를 열어 보고 뺐다. 대상 판정에 쓰는 상태값과 실행 식별자가
1610행과 1621행에 이미 있고 새 필드가 필요 없다.

`src/features/projects/application/useProjectWorkspace.ts`를 열어 보고 뺐다. 취소·재시도 확인 창은
백엔드 미리보기 값을 열쇠로 열려 이 공용 상태를 쓰지만, 일괄 확인은 앱 바깥에 물어볼 것이 없어 화면
안의 값으로 연다. 공용 상태에 열쇠를 더하면 실행 조회 주기와 수명이 다른 값이 그 객체에 섞인다.

`src-tauri/` 아래를 열어 보고 뺐다. 이 작업은 백엔드에 아무것도 묻지 않는다.

기계 상태를 조건으로 삼는 측정이 없으므로 이 작업은 조용한 기계를 요구하지 않는다. 선언한 세 파일이
모두 앞선 작업 TASK-S083-01의 선언과 겹치므로 순서를 선언했고, 앞선 작업이 `verified`가 된 뒤에
시작한다.

- 값 경로: C1의 대상 목록. 값을 만드는 자리는 실행 환경이고 앱에는 `types.ts` 1621행의
  `AgentRunSummary`로 실려 `AgentRunDashboard.tsx` 91행의 `runs`에 닿는다. 그 홉들은 값을 그대로
  나르므로 편집이 필요 없다. 확인한 실행 묶음은 앞선 작업이 같은 컴포넌트 안에 세워 둔 값이라 같은
  자리에서 읽는다. 둘을 겹쳐 대상을 고르는 자리는 화면 파일 안이고 선언 안에 있다.
- 값 경로: C3의 건수. 값을 만드는 자리는 C1의 대상 목록 길이이고 화면 파일 안이다. 값을 나르는 자리는
  확인 창을 여는 화면 안의 값 하나이고, 값을 소비하는 자리는 창의 문장이다. 세 홉 모두 화면 파일
  안이라 선언 안에 있다.
- 값 경로: C4와 C6의 적용. 값을 만드는 자리는 확인 창의 실행 버튼이고 화면 파일 안이다. 값을 담는
  자리는 앞선 작업이 만든 저장소이고, 화면이 드는 확인한 실행 묶음도 앞선 작업이 세운 자리다. 저장소
  파일은 선언 밖이지만 이 작업이 그 파일을 고치지 않고 이미 있는 저장 동작을 부르기만 하므로 조건이
  남지 않는다. 적용된 값을 읽어 목록을 거르는 자리는 93행이고 선언 안에 있다.
- 값 경로: C2의 버튼 표시 여부. 값을 만드는 자리는 C1의 대상 목록이 비었는지이고, 값을 소비하는
  자리는 268행의 머리다. 둘 다 선언 안에 있다. 머리에 요소가 둘이 되면서 필요한 배치 규칙의 소비
  자리는 `src/App.css`이고 선언 안에 있다.
- 값 경로: C5의 구역 사라짐. 값을 만드는 자리는 93행의 `recent`이고 소비하는 자리는 267행의 조건이다.
  둘 다 앞선 작업이 이미 확인한 실행을 빼도록 고쳐 둔 자리라 이 작업이 새로 고칠 것이 없고, 일괄
  확인의 적용이 그 값을 바꾸면 구역이 저절로 빠진다. 조용한 한 줄의 조건인 283행도 같은 값을 읽으므로
  손대지 않는다.
