# 품질 확인 전용 화면에 기능 대기열과 확인 범위 설명을 만든다

## 결정권자 요약

### 제안

주요 메뉴에 품질 확인 화면을 더한다. 이 화면은 지금 확인할 수 있는 기능을 먼저 보여 주고, 기능을 열면
무엇이 바뀌었고 무엇을 몇 개 확인해야 하는지를 먼저 읽게 한다.

### 현재

사용자가 품질 확인을 하려면 개발 화면으로 들어가 확인할 기능 묶음을 찾아야 한다. 그 묶음은 개발 상태
표시와 필터와 보기 전환에 둘러싸여 있고, 무엇을 확인해야 하는지는 기능을 연 뒤에야 조각으로 보인다.

### 변경 후

메뉴에서 바로 열리는 전용 화면이 지금 확인할 기능과 준비 중인 기능을 두 구획으로 나눠 보여 준다. 준비된
기능은 행 전체를 눌러 열고, 열면 기능 제목과 바뀐 점과 확인할 항목 수를 먼저 읽는다.

### 사용자 결과

사용자는 개발 화면을 거치지 않고 지금 확인할 기능을 찾는다. 기능을 열면 항목을 하나씩 누르기 전에 이
기능이 무엇을 바꿨고 몇 개를 확인해야 하는지 알 수 있다.

### 영향 범위

- 변경: 주요 메뉴 항목, 품질 확인 대기열 화면, 기능을 열었을 때 먼저 보이는 확인 범위 설명
- 유지: 개발 화면의 확인할 기능 묶음과 결정 조작, 오늘 화면, 기능 묶음을 판정하는 기준, 작업 문서와 결정 기록

### 비용과 위험

이 작업이 끝난 시점에는 새 화면에서 항목을 확인하거나 결과를 제출할 수 없다. 사용자가 결정을 남기는 길은
아직 개발 화면 하나뿐이며, 뒤따르는 두 작업이 새 화면에 확인과 제출을 붙인다.

### 결정 요청

QA에서는 메뉴에서 품질 확인 화면이 열리는지, 지금 확인할 기능과 준비 중인 기능이 구분되어 보이는지,
준비 중인 기능에 시작 조작이 없는지, 기능을 열었을 때 확인 범위 설명과 항목 수가 먼저 보이는지를 본다.

## 범위 사전 검사

이 작업이 만드는 값은 셋이다. 새 화면으로 가는 메뉴 상태, 대기열이 그리는 두 구획, 기능을 열었을 때 먼저
보이는 확인 범위 설명이다. 현재 코드를 열어 각 값이 어디서 생겨 어디까지 가는지 확인했다.

- 값 경로: 완료 조건 1의 메뉴 진입은 `src/features/projects/components/WorkspaceShell.tsx` 안에서 끝난다.
  값을 만드는 자리는 같은 파일의 `view` 상태와 그 상태의 값 목록이고, 이름을 붙이는 자리는 같은 파일의
  `viewLabels`이며, 누르는 자리는 같은 파일의 주요 메뉴 버튼 묶음이고, 그리는 자리는 같은 파일의 화면
  분기다. 네 자리가 모두 한 파일 안에 있어 이 파일만 편집하면 값이 끝까지 이어진다.
- 값 경로: 완료 조건 2·3·4의 두 구획은 앞선 작업이 만든 `src/features/projects/domain/qaReview.ts`가
  돌려주는 값에서 온다. 그 모듈은 지금 확인할 수 있는 묶음과 아직 확인할 수 없는 묶음을 나눠 돌려주고,
  묶음마다 제목과 설명과 확인 항목 수와 남은 작업 수를 담는다. 입력이 되는 작업 목록과 기획서 목록은
  `WorkspaceShell.tsx`가 이미 들고 있는 워크플로 요약 안에 있으므로 새 조회를 만들지 않는다. 소비하는
  자리는 이 작업이 만드는 `src/features/projects/components/qa/QaWorkbench.tsx`다. 도메인 모듈은 값을 그대로
  돌려주면 되므로 편집하지 않고, 선언에도 넣지 않는다.
- 값 경로: 완료 조건 5·6의 확인 범위 설명은 두 곳에서 온다. 기능 제목과 설명은 도메인 모듈이 기획서
  요약에서 담아 준 값이고, 그 기획서 요약의 `excerpt`는 앱 백엔드가 문서 앞부분에서 잘라 만든다. 확인
  항목 수는 같은 모듈이 센 값이다. 두 값 모두 이미 만들어져 화면까지 와 있으므로 앱 백엔드와 도메인
  모듈은 편집하지 않는다. 이 작업은 그 값을 읽어 그리는 자리만 만든다. 앱이 새 문장을 지어내지 않는다는
  완료 조건 6은 이 경로를 그대로 지키는 것으로 충족된다.
- 값 경로: 완료 조건 7의 화면 모양은 `src/features/projects/components/qa/QaWorkbench.css`에서 끝난다.
  기존 `src/App.css`에 넣지 않는 것은 그 파일이 스타일 회귀 검사의 판독 대상이고 여러 작업이 함께
  고치는 자리이기 때문이다. 같은 저장소의 `src/features/projects/components/BlockedTaskPanel.css`가 이미
  화면별 스타일 파일을 따로 두는 선례이므로 같은 방식을 쓴다.
- 검토했으나 제외한 것: `src/App.tsx`는 열지 않는다. 이 화면이 그리는 데 필요한 워크플로 요약과 작업 문서
  읽기 통로는 `WorkspaceShell.tsx`가 이미 받고 있으므로 새로 내려보낼 값이 없다. 제출 동작을 내려보내는
  것은 제출 화면을 만드는 작업의 완료 조건이다.
- 검토했으나 제외한 것: `src/features/projects/components/DevelopmentBoard.tsx`는 열지 않는다. 개발 화면의
  확인할 기능 묶음과 결정 조작은 이 작업에서 그대로 두며, 두 입구를 하나로 잇는 것은 진입점 통합 작업의
  완료 조건이다. 그때까지 두 입구가 함께 있는 것은 의도한 중간 상태다.

## 현재 상태

주요 메뉴에는 오늘, 아이디어, 기획서, 개발, 기록, 활동이 있고 품질 확인 항목은 없다. 사용자 품질 확인은
개발 화면 안의 확인할 기능 묶음, 기획서별 레인의 일괄 확인, 작업 상세의 단건 확인 세 입구로만 들어간다.

확인할 기능 묶음은 기능 제목과 짧은 설명, 직접 확인 단계 수, 자동 검증 건수를 카드로 보여 주고 시작
버튼을 따로 둔다. 아직 확인할 수 없는 묶음은 흐린 카드로 남은 작업 수만 보여 준다.

## 변경 범위

1. 주요 메뉴에 품질 확인 항목을 더하고, 화면 이름 목록과 화면 상태 값 목록에 같은 이름을 더한다. 메뉴
   위치는 개발 다음, 기록 앞이다.
2. 품질 확인 화면 컴포넌트를 만든다. 이 화면은 워크플로 요약과 작업 문서 읽기 통로를 받고, 도메인 모듈이
   돌려준 묶음 목록을 그린다.
3. 대기열은 지금 확인할 기능 구획을 먼저, 준비 중인 기능 구획을 그다음에 그린다. 두 구획 모두 카드 격자가
   아니라 한 열 목록으로 그린다.
4. 준비된 기능 행에는 기능 제목, 확인 목표 한 문장, 직접 확인 항목 수, 자동 근거 항목 수, 그리고 시작
   또는 계속 중 하나의 상태만 둔다. 작업 식별자 목록, 파일 범위, 상태별 개발 수치, 긴 원문은 넣지 않는다.
5. 준비된 기능은 행 전체가 진입점이다. 행 안에 따로 시작 버튼을 두지 않고, 상태 표시는 버튼처럼 보이지
   않게 그린다.
6. 준비 중인 기능 행에는 기능 제목, 품질 확인 대기 건수, 남은 작업 수만 둔다. 누를 수 없고 진입점도 아니다.
7. 확인할 기능도 준비 중인 기능도 없으면 그 사실을 한 문장으로 알린다.
8. 기능을 열면 확인 범위 설명 화면을 그린다. 이 화면은 기능 제목, 바뀐 점 한 문장, 사용자가 확인할 결과,
   전체 항목 수를 담고, 대기열로 돌아가는 조작을 갖는다. 항목을 하나씩 확인하는 본문은 뒤따르는 작업이
   붙이므로 이 작업에서는 만들지 않는다.
9. 설명에 쓰는 문장은 기획서 요약과 작업 문서에서 온 값을 그대로 옮긴다. 앱이 문장을 새로 지어내지
   않는다. 작업 식별자, 파일 범위, 자동 검사 명령은 이 화면에 넣지 않는다.
10. 화면 스타일은 이 화면 전용 스타일 파일에 둔다. 제품의 낮은 채도 종이 배경과 딥그린 주요 행동과 절제된
    모션을 유지하고, 참조 서비스의 색상과 표 외형을 가져오지 않는다. 본문과 조작 글자는 제품의 최소
    11픽셀 정책을 지킨다.
11. 대기열 행 진입과 대기열 복귀를 키보드만으로 수행할 수 있게 하고, 현재 초점이 어디인지 보이게 한다.
    좁은 창에서는 가로 스크롤 없이 같은 행 목록을 볼 수 있게 한다.

## 범위 밖

- 항목별 확인, 결과 선택, 문제 메모 입력
- 제출 전 검토 화면과 최종 제출
- 기기 내 임시 검토의 저장과 복원
- 오늘 화면과 개발 화면의 진입점 변경
- 기능 묶음 판정 기준의 변경
- 검색, 정렬, 개발 상태 필터를 품질 확인 화면에 더하는 일

## 완료 조건

1. 주요 메뉴에 품질 확인 항목이 있고, 누르면 품질 확인 화면이 열린다. 화면 위치 표시에도 그 이름이
   나온다.
2. 대기열이 지금 확인할 기능을 먼저, 준비 중인 기능을 그다음에 보여 준다. 두 구획의 제목이 서로 다르고
   어느 쪽이 지금 할 수 있는 일인지 평문으로 읽힌다.
3. 준비된 기능 행에 기능 제목, 확인 목표 한 문장, 직접 확인 항목 수, 자동 근거 항목 수, 시작 또는 계속
   상태만 있다. 작업 식별자 목록과 파일 범위와 상태별 개발 수치는 행에 없다.
4. 준비 중인 기능 행은 품질 확인 대기 건수와 남은 작업 수를 보여 주고, 눌러도 아무 화면으로도 이동하지
   않으며 시작 조작이 없다.
5. 준비된 기능 행 전체를 누르면 그 기능의 확인 범위 설명 화면이 열리고, 기능 제목과 바뀐 점과 확인할
   결과와 전체 항목 수가 보인다. 전체 항목 수는 그 기능의 품질 확인 대기 작업 수와 같다.
6. 확인 범위 설명에 쓰인 문장이 기획서 요약과 작업 문서에 있는 문장에서 온 것이고, 앱이 만들어 낸 새
   사실이 아니다.
7. 화면 스타일이 이 화면 전용 스타일 파일에 있고, 기존 공용 스타일 파일에 이 화면의 규칙이 추가되지
   않았다.
8. 키보드만으로 대기열 행에 초점을 옮기고 기능을 열고 대기열로 돌아올 수 있으며, 초점 위치가 보인다.
9. 좁은 창에서 대기열과 확인 범위 설명이 가로 스크롤 없이 읽히고 주요 조작을 쓸 수 있다.
10. 개발 화면의 확인할 기능 묶음과 결정 조작, 오늘 화면의 내 선택 대기가 변경 전과 같이 동작한다.

## 검증 단계

1. 품질 확인 화면 검사를 새로 작성하고 실행한다. 완료 조건 2·3·4·5·6을 각각 확인한다. 확인할 수 있는
   기능과 준비 중인 기능이 함께 있는 워크플로 요약, 둘 다 없는 요약을 각각 넣어 그려지는 내용을 단언한다.
   준비 중인 기능 행에 진입 조작이 없음을 단언한다.
   명령: `npx vitest run src/features/projects/components/qa/QaWorkbench.test.tsx`
2. 껍데기 화면 검사에 메뉴 진입 검사를 추가하고 실행한다. 완료 조건 1과 10을 확인한다.
   명령: `npx vitest run src/features/projects/components/WorkspaceShell.test.tsx`
3. 완료 조건 7은 새 스타일 파일을 문자열로 읽어 이 화면의 선택자가 그 파일에 있음을 단언하고, 공용 스타일
   파일에는 없음을 단언해 확인한다. 같은 저장소의 막힌 작업 패널 검사가 쓰는 어법을 따른다.
4. 완료 조건 8은 키보드 이동과 실행을 흉내 내는 검사로 확인한다. 행에 초점을 준 뒤 실행 키로 기능이
   열리는지, 돌아가기 조작에 초점이 닿는지를 단언한다.
5. 완료 조건 9는 좁은 창 폭을 가정한 스타일 규칙을 새 스타일 파일에서 읽어 세로 배치와 가로 스크롤 없음을
   단언해 확인한다.
6. 타입 검사와 저장소 전체 검사를 실행한다. 명령: `npm run typecheck` 다음 `npm test`

## 확인 동선

1. 앱을 열고 왼쪽 주요 메뉴에서 개발 아래에 있는 품질 확인을 누른다. 화면 위쪽 위치 표시가
   품질 확인으로 바뀌고 품질 확인 화면이 열리면 정상이다.
2. 화면에 지금 확인할 기능과 준비 중인 기능 두 구획이 위아래로 보인다. 지금 확인할 기능 구획에는
   기능 제목, 확인 목표 한 문장, 직접 확인 개수, 자동 근거 개수, 그리고 오른쪽에 시작이라는 글자가
   있다. 작업 번호나 파일 이름이 행에 보이면 잘못된 것이다.
3. 준비 중인 기능 구획의 행에는 품질 확인 대기 건수와 남은 작업 수만 있다. 그 행을 눌러도 아무 화면도
   열리지 않고 시작 버튼도 없으면 정상이다.
4. 지금 확인할 기능 구획에서 행의 아무 곳이나 누른다. 기능 제목이 큰 제목으로 뜨고, 바뀐 점과
   사용자가 확인할 결과가 각각 구획으로 보이며, 오른쪽 위에 전체 항목 수가 보이면 정상이다. 이 수는
   그 기능에서 품질 확인을 기다리는 작업 수와 같아야 한다.
5. 바뀐 점의 문장은 그 기능의 기획서 첫머리에 적힌 문장과 같고, 사용자가 확인할 결과의 문장들은 각
   작업 문서의 확인 동선 첫 문단과 같다. 앱이 지어낸 새 문장이 있으면 잘못된 것이다.
6. 왼쪽 위 대기열로 돌아가기를 누르면 다시 대기열이 보인다.
7. 키보드만 써서 같은 길을 걷는다. 탭 키로 지금 확인할 기능의 행에 초점을 옮기면 초점 테두리가
   보이고, 엔터를 누르면 기능이 열리며, 그때 초점이 대기열로 돌아가기에 있어 엔터를 한 번 더 누르면
   대기열로 돌아오면 정상이다.
8. 창 너비를 좁힌다. 대기열 행과 확인 범위 설명이 세로로 쌓이고 가로 스크롤 막대가 생기지 않으면
   정상이다.
9. 개발 화면과 오늘 화면을 다시 연다. 개발 화면의 확인할 기능 묶음과 QA 시작, 오늘 화면의 내 선택
   대기가 이전과 같이 동작하면 정상이다.

이 작업에서 새 화면은 확인 범위까지만 만든다. 항목을 하나씩 확인하거나 결과를 제출하는 조작은 아직
없으며, 결정을 남기는 길은 개발 화면 하나뿐이다.
