# 실행 상세를 이벤트 나열에서 요약 카드와 이상 신호로 바꾼다

## 결정권자 요약

### 제안

실행 상세를 이벤트 종류 나열에서 사람이 읽는 요약 카드 하나와 몇 개의 신호로 바꾼다.

### 현재

실행 하나를 열면 같은 종류의 줄이 서른 개씩 늘어섰다. 무엇을 했고 어떻게 끝났는지 읽어 낼 수 없었다.
구현이 끝나 이제 사용자 확인을 기다린다.

### 변경 후

대상 문서와 역할, 시작과 경과, 상태와 사유, 도구 사용 횟수와 유형별 집계, 마지막 활동 시각이 한 카드에 모인다.
줄로 남는 것은 시작과 종료, 실패 상세, 오랫동안 활동이 없다는 신호뿐이다.

### 사용자 결과

실행이 지금 무엇을 하고 있고 어떻게 끝났는지 한눈에 읽는다. 오래 조용한 실행은 신호로 먼저 알아챈다.

### 영향 범위

- 변경: 실행 상세 화면의 구성, 이벤트 줄에 남기는 항목, 도구 사용의 표시 방식
- 유지: 실행 배정과 취소와 재시도, 실행 목록과 최근 종료 목록, 문서 승인과 품질 확인 관문

### 비용과 위험

집계가 원본과 어긋나면 사용자가 잘못된 사실을 읽는다. 유형별 횟수의 합과 총 횟수가 원본의 도구 이벤트 수와
같다는 것을 자동 검사로 확인했다.

### 결정 요청

QA에서는 도구를 여러 번 쓴 실행을 열어, 개별 도구 줄이 사라지고 요약 카드의 총 횟수와 유형별 횟수가 실제 사용과
같은지, 활동이 멈춘 실행에서 신호가 나타났다가 새 활동에 사라지는지 확인한다.

## 확인 동선

에이전트 화면에서 실행 하나를 눌러 오른쪽 상세 서랍을 연다. 서랍 맨 위에 요약 카드 하나가 있고, 그 아래에
줄이 몇 개만 남는다.

1. 도구를 여러 번 쓴 실행을 연다. 개별 도구 줄과 진행 줄이 하나도 보이지 않고, 카드의 `도구 사용` 칸에
   `총 N회`와 `파일 읽기 3` 같은 유형별 칩이 보인다. N이 그 실행이 실제로 쓴 도구 횟수와 같은지 본다.
   유형별 칩의 숫자를 모두 더하면 N이 된다.
2. 같은 카드에서 `대상`·`역할`·`시작`·`경과`(끝난 실행은 `소요`)·`상태`·`사유`·`마지막 활동`이 그 실행의
   현재 사실과 맞는지 본다. 진행 중, 완료, 실패, 취소, 복구 필요 실행을 각각 하나씩 열어 확인한다.
3. 활동 없음 신호: 진행 중인 실행을 열어 둔 채 5분 이상 새 이벤트가 오지 않으면 줄 목록에
   `활동 없음 · N분째 조용함`이 나타난다. 그 실행이 다시 움직이면 이 줄이 사라지고 `마지막 활동` 시각이
   갱신된다. 이때 `상태`는 계속 `진행 중`이며 실패나 취소로 바뀌지 않는다. 상세를 닫으면 이어 읽기가 멈춘다.
4. 실패한 실행을 연다. `실패` 줄 아래에 런타임이 준 문장이 그대로 보이고 성공 요약이나 짧은 안내 문구로
   바뀌지 않는다. 문장 안에 토큰이나 비밀번호 형태의 값이 있으면 그 자리만 `[민감정보 제거됨]`으로 보인다.
5. 실행 기록을 읽지 못하는 상황에서는 `도구 사용`과 `마지막 활동`이 `모름`으로 보이고, 직전에 열었던 다른
   실행의 숫자가 그대로 남지 않는다.
6. 알지 못하는 도구 이름은 `기타`로, 도구 이름이 없는 옛 기록은 `이름 없음`으로 묶여 보이고, 도구 이름
   원문은 화면 어디에도 나타나지 않는다.

집계 계산과 시각 계산, 신호 판정, 이어 읽기의 시작과 정지는 자동 검사로 닫았다. 위 1~6은 화면에서 눈으로
확인할 수 있는 부분이고, 확인 도장은 그 화면과 아래 보고서의 검사 수치를 함께 믿는다는 뜻이다.

## 범위 사전 검사

이 작업이 다루는 값은 셋이다. 도구 사용 횟수, 마지막 활동 시각, 활동 없음 신호다. 셋 모두 이벤트에서 나오므로
이벤트가 화면까지 오는 경로와 각 값이 계산되는 자리를 확인했다.

- 값 경로: 완료 조건 3·4의 도구 사용 횟수와 유형별 집계는 이벤트의 종류 값과 도구 이름 값에서 나온다. 두 값은
  런타임이 만들고 앞선 작업이 도구 이름을 더한다. 앱 쪽 `src-tauri/src/domain/agent_runtime.rs`의 `RunLogPage`는
  이벤트를 해석하지 않는 JSON 값 배열이고 `src-tauri/src/application/agent_runtime_status_service.rs`의 `read_log`도
  실행 식별자만 대조한 뒤 그대로 넘기므로, 두 자리 모두 값을 변경 없이 나른다. 편집하지 않는다.
  화면 쪽에서는 `src/features/projects/domain/types.ts`의 `AgentRunLogPage`가 이벤트를 형식 없는 배열로 들고 있어
  집계에 쓸 형태가 없으므로 이 파일을 편집한다. 집계 계산 자체는 화면 구성 요소 안에서 검사하기 어려우므로
  `src/features/projects/domain/runActivity.ts`를 새로 만들어 그 자리에 둔다.
- 값 경로: 완료 조건 5의 마지막 활동 시각은 이벤트가 담은 실행 시작 시각과 경과 초에서 계산한다. 저장된 이벤트에는
  절대 시각 필드가 없고 `../../Git/claude-heartbeat`의 `agent_dispatch.py`에 있는 `_drain_events`가 시작 시각과 경과
  초를 함께 싣는다는 것을 확인했다. 두 값을 더하면 그 이벤트가 일어난 시각이 되므로 런타임을 고치지 않고 계산할 수 있다.
  계산은 새 도메인 모듈이 맡는다.
- 값 경로: 완료 조건 6의 활동 없음 신호는 마지막 활동 시각과 현재 시각의 차이로 판정한다. 판정은 새 도메인 모듈이
  하고, 표시는 `src/features/projects/components/agents/AgentRunDashboard.tsx`의 실행 상세 서랍이 한다. 신호가 시간이
  지나면 나타나고 새 이벤트에 사라지려면 이벤트가 주기적으로 갱신되어야 하는데, 현재 실행 로그는 사용자가 단추를
  눌러야 읽힌다. 그래서 `src/features/projects/application/useProjectWorkspace.ts`를 편집해 실행 상세가 열려 있는 동안
  로그를 이어 읽게 한다. 같은 파일에는 이미 활성 실행이 있을 때 2.5초 주기로 실행 목록을 다시 읽는 자리가 있어,
  주기의 근거를 새로 만들지 않고 그 자리에 맞춰 넣는다.
- 값 경로: 완료 조건 1·2의 카드 항목 가운데 대상 문서와 역할과 provider와 상태와 사유와 시작 시각은 이미 실행 요약이
  담고 있고 실행 상세 서랍이 이미 받고 있다. 이 값들은 편집 없이 그대로 쓰며, 카드로 배치하는 일만 화면 구성 요소에서 한다.
- 검토했으나 제외한 것: `src/features/projects/infrastructure/tauriProjectGateway.ts`는 실행 로그 읽기 호출을 이미
  가지고 있고 이 작업은 새 백엔드 호출을 더하지 않는다. 편집이 필요 없으므로 선언에서 뺀다.
- 검토했으나 제외한 것: 실행 목록과 최근 종료 목록의 행 모양은 바꾸지 않는다. 기획서가 바꾸라고 한 것은 실행 상세이며,
  목록의 정렬과 표시를 함께 건드리면 승인 범위를 넘는다.

## 현재 상태

실행 상세 서랍은 역할과 대상과 실행 식별자와 provider를 목록으로 보여 주고, 사유 문장을 한 줄 덧붙인다. 로그 보기
단추를 누르면 그때 읽은 이벤트를 순서 목록으로 늘어놓는다. 각 줄은 이벤트의 종류와 단계와 상태와 메시지와 상세
문자열을 골라 중간점으로 이어 붙인 것이라, 도구 이벤트가 스물두 개면 같은 모양의 줄이 스물두 개 생긴다.

## 변경 범위

1. 실행 상세를 요약 카드 하나로 다시 만든다. 카드는 대상 문서와 그 제목, 역할과 provider, 시작 시각과 경과 또는 소요
   시간, 현재 상태나 종료 결과, 사유 문장, 총 도구 사용 횟수와 유형별 집계, 마지막 활동 시각을 담는다.
2. 진행 이벤트와 도구 이벤트는 집계에만 반영하고 개별 줄로 남기지 않는다. 줄로 남는 것은 시작, 성공과 실패와 취소를
   포함한 종료, 민감정보를 제거한 실패 상세, 활동 없음 신호뿐이다.
3. 실패 상세는 런타임이 준 문장을 그대로 보여 준다. 성공 요약이나 짧은 문구로 바꾸지 않는다.
4. 도구 이름을 안정적인 사용자 유형으로 묶는 규칙을 새 도메인 모듈에 둔다. 파일 읽기, 파일 편집, 명령 실행, 검색을
   유형으로 두고, 알지 못하는 이름은 기타로, 이름이 없는 기존 이벤트는 이름 없음으로 집계한다. 총 횟수는 이름 유무와
   상관없이 모든 도구 이벤트를 센다.
5. 알지 못하는 도구 이름의 원문을 화면에 노출하지 않는다.
6. 마지막 이벤트가 담은 실행 시작 시각과 경과 초로 그 이벤트의 시각을 계산하고, 그 값을 마지막 활동 시각으로 쓴다.
7. 활성 실행에서 마지막 활동으로부터 5분이 지나면 활동 없음 신호를 보여 준다. 새 이벤트가 오면 신호를 없애고 마지막
   활동 시각을 갱신한다. 이 신호는 실행 상태를 실패나 취소로 바꾸지 않는다.
8. 실행 상세가 열려 있는 동안 이벤트를 이어 읽는다. 상세를 닫으면 읽기를 멈춘다.
9. 로그나 상태를 읽지 못하면 그 항목을 모름으로 표시하고, 직전에 본 값을 현재 사실로 보여 주지 않는다.
10. 요약 카드와 신호에 필요한 화면 규칙을 `src/App.css`에 더한다.

## 범위 밖

- 결과 보고서 바로가기와 보고서 열람. 뒤따르는 작업이 맡는다.
- 진단 번들 저장과 복사. 뒤따르는 작업이 맡는다.
- 활동 없음 신호를 실패로 자동 전환하거나 자동으로 취소하는 동작
- 활동 없음 기준을 사용자가 설정하게 하는 기능
- 실행 목록, 최근 종료 목록, 전체 기록 서랍의 표시 변경
- 런타임 저장 내용의 변경

## 완료 조건

1. 시작 1건, 진행 8건, 도구 22건인 이벤트로 실행 상세를 열면 개별 진행 줄과 도구 줄이 하나도 보이지 않고, 요약 카드에
   도구 22회와 마지막 활동 시각이 보인다.
2. 실행 중, 성공, 실패, 취소, 복구 필요 상태 각각에서 대상과 시간과 결과와 사유가 그 실행의 현재 사실과 일치한다.
3. 파일 편집과 명령 실행과 검색 도구가 섞인 이벤트에서 유형별 횟수의 합과 총 횟수가 원본 이벤트의 도구 이벤트 수와 같다.
4. 이름이 없는 도구 이벤트는 총 횟수에 포함되고 이름 없음으로 분리된다. 알지 못하는 이름은 기타로 집계되고 그 원문이
   화면에 나타나지 않으며 화면이 깨지지 않는다.
5. 마지막 활동 시각이 마지막 이벤트의 시작 시각과 경과 초를 더한 값과 일치한다.
6. 활성 실행에서 마지막 이벤트로부터 5분이 지나면 활동 없음 신호가 나타나고, 새 이벤트를 받으면 사라지며, 실행 상태는
   자동으로 실패가 되지 않는다.
7. 실패 이벤트의 상세가 런타임이 준 전문 그대로 보이고 성공 요약으로 바뀌지 않는다.
8. 로그를 읽지 못한 상태에서 요약 카드가 해당 항목을 모름으로 표시하고 지난 값을 현재 사실로 보여 주지 않는다.
9. 도구 이름이 없는 구형 이벤트만으로도 요약 카드와 시작과 종료 표시가 동작한다.
10. 기존 실행 배정, 취소, 재시도, 목록 표시 검사가 변경 전과 같은 결과로 통과한다.

## 검증 단계
