# 프로젝트별 큐가 병렬 배정과 반복 실행을 안전하게 이어간다

## 결정권자 요약

현재 TASK-S051-04는 선행 예약과 실행 복구 계약이 비어 있어 구현을 계속할 수 없다.
기존 선행 모듈 검사는 통과했지만 이 작업의 전용 검사가 없어 완료 조건을 검증할 수 없다.
예약 소유권과 실행 식별자를 제공한 뒤 다시 개발을 시작해야 한다.

## 목적

프로젝트별 자동·수동 배정, 한 번·반복 실행, 병렬 상한, 공정성, 복구를 provider 중립 dispatcher에
구현한다. 자동 배정은 TASK-S051-01의 예약 도구로 lease를 획득한 뒤에만 provider를 시작한다.

## 배정 규칙

1. 실제 역할 실행 수는 역할 상한, 프로젝트 남은 슬롯, 기기 남은 슬롯, provider ready 상태,
   예약 가능한 대상 수의 최솟값이다.
2. 역할 기본 상한은 1, 프로젝트 기본 상한은 3, 기기 기본 상한은 16이다. 상한을 낮춰 현재 실행
   수보다 작아져도 프로세스를 종료하지 않고 새 배정만 막는다.
3. 기기 슬롯은 실행 가능한 프로젝트 사이를 라운드 로빈으로 배정한다. 한 프로젝트가 반복 실행을
   켠 채 빈 슬롯을 연속 독점하지 않는다.
4. 자동 배정은 역할 계약의 후보 순서를 그대로 사용한다. 예약 성공 응답이 없으면 provider를 시작하지
   않는다.
5. 수동 배정은 역할과 대상 식별자를 슬롯마다 받는다. 같은 요청 안의 중복 대상, 잘못된 식별자,
   완료·거절 상태, 활성 lease, 마이그레이션 잠금은 provider 시작 전에 거절한다.
6. 한 번 실행은 시작 확인 시점에 예약한 목록만 처리하고 빈 슬롯을 보충하지 않는다.
7. 반복 자동 실행은 빈 슬롯마다 자격을 다시 판정한다. 반복 수동 실행은 사용자가 지정한 목록을 다
   처리한 뒤 새 대상을 추측하지 않고 대기한다.
8. 프로젝트 일시 정지는 그 프로젝트의 새 예약만 막는다. 다른 프로젝트와 기기 전체 데몬은 계속
   동작한다.
9. provider에 보낼 prompt는 예약 성공 응답의 `rolePrompt`를 그대로 사용한다. runtime에 planner,
   architect, developer용 지시 사본을 두거나 provider별로 다른 역할 지시를 만들지 않는다.

## lease와 프로세스 수명

- dispatcher는 provider 프로세스를 만들기 전에 예약 도구의 성공 결과를 트랜잭션에 기록한다.
- 예약된 `leaseId`와 대상이 저장 내용과 다르면 provider를 시작하지 않는다.
- provider가 도는 동안 dispatcher는 같은 lease를 짧게 갱신한다. 역할 세션도 인계받은 lease를
  검증하고 역할 계약에 따라 갱신·반납한다.
- 정상 종료 뒤 같은 lease가 남아 있으면 dispatcher가 소유자 일치를 확인한 뒤 정리한다. 다른
  lease는 건드리지 않는다.
- 취소는 프로세스 트리 종료를 확인한 뒤 lease와 예약을 정리한다. 어느 단계가 실패하면
  `recovery_required`로 남긴다.

## 복구와 로그

- provider stdout은 실행별 append-only 이벤트 파일로 직접 연결한다. 데몬이 죽어도 자식 프로세스의
  출력이 끊기지 않고 재시작한 런타임이 마지막 offset부터 다시 읽을 수 있어야 한다.
- 시작 시 SQLite의 running·reserved 항목, PID와 프로세스 생존, lease 소유권을 대조한다.
- PID가 살아 있으면 같은 작업을 다시 시작하지 않고 감시를 복원한다. 죽었는데 상태가 남으면 실패
  단계와 정리 결과를 기록한다.
- PID 재사용을 막기 위해 시작 시각 또는 실행 토큰을 함께 검증한다. 확정할 수 없으면 실행 중으로
  추측하지 않고 `recovery_required`로 둔다.
- 재시도는 이전 실행 식별자를 보존하고 새 예약을 획득한다. 기존 실패 행을 덮어쓰지 않는다.

## 손대지 않는 것

- 앱 화면과 앱 설치 경로
- provider별 명령 구성과 인증 판정
- 워크플로 규칙의 승인·QA 권한
- Dream 실행과 기존 일반 Heartbeat 잡 스케줄
- 원격·클라우드 실행

## 완료 조건

1. 역할 상한 3, 프로젝트 상한 5, 기기 남은 슬롯 4, 예약 가능 대상 2에서 두 실행만 시작된다.
2. 예약 가능 대상 0건이나 마이그레이션 잠금에서는 Claude와 Codex 프로세스가 하나도 시작되지 않는다.
3. dispatcher 여러 개가 같은 대상을 발견해도 성공 lease와 provider 프로세스는 하나뿐이다.
4. 한 번 실행은 최초 예약 목록을 처리한 뒤 새 대상을 보충하지 않는다.
5. 반복 자동 실행은 종료로 빈 슬롯이 생길 때 역할 상한까지 새 대상을 보충한다.
6. 반복 수동 실행은 지정 목록을 다 처리한 뒤 자동 후보를 선택하지 않는다.
7. 중복 대상, 활성 lease, 완료·거절 대상, 잘못된 식별자의 수동 배정은 실행 전에 사유와 함께 막힌다.
8. 프로젝트 일시 정지는 새 배정만 멈추고 실행 중 프로세스와 다른 프로젝트를 멈추지 않는다.
9. 두 프로젝트가 계속 대기하는 부하 검사에서 둘 다 유한 시간 안에 기기 슬롯을 받는다.
10. 명시적 취소는 프로세스 트리, 예약, lease를 정리하고 cancelled 결과를 남긴다. 일부 정리는
    성공했지만 일부가 실패한 경우 전체 성공으로 표시하지 않는다.
11. 런타임 비정상 종료 뒤 살아 있는 프로세스를 중복 실행하지 않고 이벤트 읽기를 복원한다.
12. 죽은 프로세스, PID 재사용 의심, lease 불일치는 recovery_required와 구체적 정리 단계로 남는다.
13. 재시도가 이전 실패를 연결하고 같은 대상의 중복 실행을 만들지 않는다.
14. 한 프로젝트의 설정·provider 실패가 다른 프로젝트의 배정 루프를 멈추지 않는다.
15. 예약 응답의 prompt가 provider 표준 입력으로 전달되고 runtime의 상태·일반 로그에는 저장되지 않는다.
16. 기존 일반 Heartbeat 잡의 주기 실행과 Dream 동작이 변경 전과 같다.

## 검증 절차

1. 가짜 자격·예약 도구와 provider를 사용해 상한 최솟값, 한 번·반복, 자동·수동 조합을 표 기반
   검사로 고정한다.
2. dispatcher 프로세스 여러 개를 동시에 실행해 같은 대상 예약 경합과 서로 다른 대상 병렬 예약을
   반복한다.
3. 두 프로젝트에 지속적으로 후보를 공급해 라운드 로빈 공정성과 프로젝트 격리를 확인한다.
4. provider가 자식 프로세스를 둔 상태에서 데몬을 강제 종료하고 다시 시작해 PID·event offset·lease
   복구와 중복 방지를 확인한다.
5. 취소 중 프로세스 종료 실패와 lease 반납 실패를 각각 주입해 부분 실패가 recovery_required로
   남는지 확인한다.
