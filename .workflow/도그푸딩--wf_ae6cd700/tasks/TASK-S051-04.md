# 프로젝트별 큐가 병렬 배정과 반복 실행을 안전하게 이어간다

## 결정권자 요약

프로젝트마다 역할별로 여러 CLI 세션이 동시에 배정되고 반복 실행이 빈 자리를 채우도록 구현했다.
같은 대상을 두 세션이 함께 잡는 일은 예약이 성공한 뒤에만 실행을 시작해서 막는다.
앱을 닫거나 런타임이 비정상 종료돼도 살아 있는 세션을 다시 실행하지 않고, 이벤트를 마지막 위치부터
이어 읽는다.
실행 중 lease 소유권이 역할 세션으로 넘어가도 프로세스를 끊지 않으며, 취소는 정리 단계가 하나라도
남으면 성공으로 보고하지 않는다.
앱이 쓰는 실행 명령 여덟 개를 구현했고 계약 조회와 계약 문서가 같은 목록을 알린다.
전용 자동 검사 41건과 알려진 기존 실패 한 건을 제외한 전체 회귀 검사를 통과했다.
사용자는 아래 확인 동선의 자동 검사 결과를 검토한 뒤 QA를 확정할 수 있다.

## 막힌 사유

- 막힌 지점: 작업 문서에 예약 도구의 호출·응답 계약과 provider 실행 핸들 계약이 없어 개발 세션이 착수 기준을 세울 수 없었다.
- 필요한 해결: 두 계약을 이 문서에 확정했다. 실행 복구는 TASK-146이 제공하는 복구 호출과 예약 식별자 결합을 사용한다.
- 재개 조건: TASK-146이 qa_waiting 또는 completed가 되고, 대상 프로젝트에 앱의 관리 규칙 동기화로 예약 도구가 설치된 뒤 사용자가 앱에서 재개한다.
- 관련 대상: TASK-146, TASK-S051-03

## 목적

프로젝트별 자동·수동 배정, 한 번·반복 실행, 병렬 상한, 공정성, 복구를 provider 중립 dispatcher에
구현한다. 자동 배정은 TASK-S051-01이 설치한 예약 도구로 lease를 획득한 뒤에만 provider를 시작한다.
TASK-S051-02가 이름만 예약해 둔 실행 명령 여덟 개를 이 작업이 구현으로 채운다.

## 현재 상태

착수 전에 확인된 사실이다. 아래 계약은 모두 선행 작업이 이미 배달했으므로 이 작업에서 새로 설계하지
않는다.

- 예약 도구 `wf-reserve`는 앱이 관리하는 자산이며 자산 버전은 1이다. 판정 도구 `wf-eligible`의 기계
  출력에서 대상을 고르고 기존 선점 도구 `wf-claim`으로 lease를 만든다. 도구 자체는 lease 파일을
  만들거나 지우지 않는다.
- 예약 도구는 프로젝트의 `.workflow/rules/`에 설치돼 있을 때만 호출할 수 있다. 설치는 앱의 관리 규칙
  동기화가 수행하며, 동기화 전인 프로젝트에는 파일이 없다.
- `agent_contract.py`는 실행 상태 이름 여덟 개(`reserved`, `queued`, `running`, `paused`,
  `succeeded`, `failed`, `cancelled`, `recovery_required`)와 실패 단계 이름 여섯 개
  (`request_validation`, `reservation`, `provider_start`, `role_session`, `cleanup`, `recovery`)를
  이미 고정했다. 새 이름을 만들지 않는다.
- `agent_contract.py`의 계약 조회는 구현된 명령 다섯 개와 예약된 명령 여덟 개
  (`plan.read`, `run.start`, `project.pause`, `project.resume`, `run.cancel`, `run.retry`,
  `logs.read`, `provider.diagnose`)를 구분해 반환한다. 예약된 여덟 개가 이 작업의 구현 대상이다.
- `agent_store.py`에는 `agent_configurations`, `agent_queue`, `agent_runs`, `agent_events`,
  `agent_errors` 다섯 테이블이 있고 현재는 설정 저장과 조회만 구현돼 있다. 큐·실행·이벤트·오류의
  쓰기 경로는 비어 있으므로 이 작업이 채운다.
- TASK-S051-03의 재작업이 `start`, `watch`, `wait`, `cancel`과 `ProviderRunHandle`을 배달했다. 기존
  `run`은 이 네 단계를 감싸는 호환 경로로 남아 있다.
- TASK-146이 provider 수명 모듈에 복구 호출과 핸들의 예약 식별자 결합을 추가한다. 이 작업은 그
  결과를 소비하며 provider 파일을 직접 수정하지 않는다.

## 예약 도구 호출 계약

### 호출

- POSIX: `sh .workflow/rules/wf-reserve.sh acquire <role> <agent> <minutes>`
- Windows: `powershell -NoProfile -ExecutionPolicy Bypass -File .workflow/rules/wf-reserve.ps1 acquire <role> <agent> <minutes>`
- 셸을 거치지 않고 인자 배열로 실행한다. 작업 디렉터리는 프로젝트 설정의 실제 `workingDirectory`여야
  한다. 도구가 판정 도구, 선점 도구, lease 경로를 프로젝트 루트 기준 상대 경로로 찾기 때문이다.
- `role`은 `planner`, `architect`, `developer` 중 하나다. `agent`는 `A-Za-z0-9_.@-`만 쓸 수 있고,
  `minutes`는 1 이상의 정수다. 이 조건을 어기면 도구가 실행 전에 사용법 오류로 끝난다.
- 공개된 하위 명령은 `acquire` 하나뿐이다. 갱신과 반납은 예약 도구가 아니라 선점 도구를 직접 호출한다.

### 응답

종료 코드로만 판단한다. 표준 출력 문구로 성공을 판정하지 않는다.

- `0`: 표준 출력에 JSON 한 줄이 나온다. 필드는 `contractVersion`(현재 1), `role`, `targetId`,
  `leaseId`, `resultPrefix`, `expiresAt`, `promptVersion`(현재 1), `rolePrompt`다. `expiresAt`은
  `YYYY-MM-DDTHH:MM:SSZ` 한 가지 모양이다.
- `1`: 예약이 성립하지 않았다. 배정 가능한 대상 없음, 경합이 32회 재시도 안에 끝나지 않음, 마이그레이션
  잠금, 판정 도구나 선점 도구 파일 없음, 읽기 실패가 모두 이 코드로 온다. 표준 출력은 비어 있고 lease는
  생기지 않는다. provider를 시작하지 않으며 실패 단계는 `reservation`이다.
- `2`: 인자가 잘못됐다. 같은 인자로 다시 부르면 같은 결과가 나오므로 재시도하지 않고 실패 단계
  `request_validation`으로 남긴다.
- 예약 도구 파일 자체가 없으면 호출을 시도하지 않고 실패 단계 `reservation`으로 남긴다. 런타임이 판정
  결과를 스스로 해석하거나 lease 파일을 직접 만드는 대체 경로를 만들지 않는다. 설치는 앱의 관리 규칙
  동기화가 담당한다.

### 응답 값의 사용

- `targetId`, `leaseId`, `resultPrefix`, `expiresAt`은 실행 행에 저장한다.
- `rolePrompt`는 provider 표준 입력으로만 전달한다. 상태 데이터베이스, 이벤트 파일, 일반 로그, 명령줄
  어디에도 남기지 않는다.
- `rolePrompt`를 조립하거나 수정하지 않는다. 런타임은 planner·architect·developer용 지시 사본을 두지
  않고 provider별로 다른 문구를 만들지도 않는다. 같은 예약은 Claude와 Codex에 같은 문구를 전달한다.
- 한 번의 `acquire`는 대상 하나를 예약한다. 슬롯이 여러 개면 슬롯마다 따로 호출한다.

## provider 실행 계약

TASK-S051-03이 배달한 계약이며 계약 버전은 1이다.

- `start(request)`는 종료를 기다리지 않고 `ProviderRunHandle` 또는 `ProviderStartFailure`를 반환한다.
  요청에는 `project_id`, `role`, `target_id`, `project_root`, `prompt`, `model`, `timeout_seconds`,
  `billing_route_acknowledged`, `event_root`를 담는다. `prompt`에 예약 응답의 `rolePrompt`를 그대로
  넣는다.
- 핸들은 `run_id`, `provider`, `project_id`, `role`, `target_id`, `pid`, `started_at`, `event_path`,
  `process_identity`, `contract_version`을 가진다. `process_identity`는 나중에 같은 PID를 재사용한
  다른 프로세스와 구분하는 값이다.
- 시작 실패는 `diagnostic`, `spawn`, `prompt_delivery` 세 단계로 구분된다. 실패한 시작은 핸들을 만들지
  않으므로 실행 행을 `running`으로 올리지 않는다.
- `watch(handle, offset)`는 그 바이트 위치 뒤의 완결된 이벤트만 돌려주고 다음 `next_offset`을 함께
  준다. 마지막 부분 줄은 보류하므로 같은 offset 재요청은 항상 같은 결과를 낸다.
- `wait(handle)`는 정규화된 종료 결과를 준다. 상태는 `success`, `failed`, `usage_limited`,
  `cancelled`, `timed_out`, `off_contract` 여섯 가지다.
- `cancel(handle)`은 `cancelled`, `process_stopped`, `events_closed` 단계를 따로 돌려준다. 이 provider
  객체가 시작하지 않은 실행은 성공으로 보고하지 않는다.
- 시작한 실행은 `wait`가 반환할 때 provider의 활성 목록에서 빠진다. 종료 처리를 건너뛰면 항목이 쌓이므로
  dispatcher는 모든 실행에 대해 반드시 `wait`를 거친다. 이벤트 파일은 그 뒤에도 남으므로 `watch`로 계속
  읽을 수 있다.
- `event_root`를 런타임이 지정해 실행별 이벤트 파일이 프로젝트 사이에 섞이지 않게 한다.
- 복구 호출과 핸들의 예약 대상·lease 결합은 TASK-146이 추가한다. 이 작업은 그 반환 값을 사용하고
  provider 파일과 전용 검사를 수정하지 않는다.

## 배정 규칙

1. 실제 역할 실행 수는 역할 상한, 프로젝트 남은 슬롯, 기기 남은 슬롯, provider ready 상태,
   예약 가능한 대상 수의 최솟값이다.
2. 역할 기본 상한은 1, 프로젝트 기본 상한은 3, 기기 기본 상한은 16이다. 상한을 낮춰 현재 실행
   수보다 작아져도 프로세스를 종료하지 않고 새 배정만 막는다.
3. 기기 슬롯은 실행 가능한 프로젝트 사이를 라운드 로빈으로 배정한다. 한 프로젝트가 반복 실행을
   켠 채 빈 슬롯을 연속 독점하지 않는다.
4. 자동 배정은 역할 계약의 후보 순서를 그대로 사용한다. 예약 도구가 종료 코드 0을 내지 않으면
   provider를 시작하지 않는다.
5. 수동 배정은 역할과 대상 식별자를 슬롯마다 받는다. 같은 요청 안의 중복 대상, 잘못된 식별자,
   완료·거절 상태, 활성 lease, 마이그레이션 잠금은 provider 시작 전에 거절한다.
6. 한 번 실행은 시작 확인 시점에 예약한 목록만 처리하고 빈 슬롯을 보충하지 않는다.
7. 반복 자동 실행은 빈 슬롯마다 자격을 다시 판정한다. 반복 수동 실행은 사용자가 지정한 목록을 다
   처리한 뒤 새 대상을 추측하지 않고 대기한다.
8. 프로젝트 일시 정지는 그 프로젝트의 새 예약만 막는다. 다른 프로젝트와 기기 전체 데몬은 계속
   동작한다.
9. provider에 보낼 prompt는 예약 성공 응답의 `rolePrompt`를 그대로 사용한다.

## 제어 명령 표면

계약이 이미 이름을 예약한 여덟 명령을 구현하고, 계약 조회의 구현된 명령 목록과 계약 문서를 같은 값으로
갱신한다. 각 명령의 요청과 응답은 TASK-S051-08이 앱에서 소비하는 값을 만족해야 한다.

- `plan.read`: 역할별 자동·수동 슬롯과 실행 방식을 받아 후보, 제외 사유, 실제 시작 수, 적용된 역할·
  프로젝트·기기 상한, provider 진단, 과금 경로 위험을 반환한다. 파일과 프로세스를 바꾸지 않는다.
  일회용 계획 식별자, 런타임 개정 값, 만료 시각을 함께 반환한다.
- `run.start`: 같은 계획 식별자와 사용자 확인을 받아 시작한다. 후보, 설정, lease, 런타임 개정 값이
  달라졌거나 계획이 만료됐으면 provider를 하나도 시작하지 않고 새 계획이 필요하다는 결과를 반환한다.
- `project.pause`, `project.resume`: 그 프로젝트의 새 배정만 제어한다.
- `run.cancel`: 대상, 프로세스 트리, 정리 영향을 먼저 보여주는 단계와 확인 뒤 적용하는 단계를 나눈다.
- `run.retry`: 이전 실패 실행 식별자를 필수로 받고 새 예약과 새 실행 식별자를 반환한다.
- `logs.read`: 실행 식별자와 cursor만 받고 민감정보가 제거된 이벤트 묶음과 다음 cursor를 반환한다.
  화면에서 받은 파일 경로를 쓰지 않는다.
- `provider.diagnose`: provider별 진단 상태를 반환한다.
- 모든 응답은 성공·부분 성공·실패를 구분하고, 실패에는 계약이 고정한 여섯 실패 단계 이름 하나를 담는다.

## lease와 프로세스 수명

- dispatcher는 provider 프로세스를 만들기 전에 예약 성공 결과를 한 트랜잭션으로 기록한다. 실행 행은
  `reserved`에서 시작해 시작에 성공한 뒤에만 `running`이 된다.
- 예약된 `leaseId`와 대상이 저장 내용과 다르면 provider를 시작하지 않는다.
- provider가 도는 동안 dispatcher는 `sh .workflow/rules/wf-claim.sh renew <targetId> <leaseId> <minutes>`
  로 같은 lease를 짧게 갱신한다. 종료 코드 0은 성공, 5는 소유자가 아니라는 뜻이고, lease 파일이 이미
  사라진 경우도 5로 온다.
- 역할 세션은 보고를 쓴 뒤 같은 lease를 반납한다. 그래서 프로세스가 아직 살아 있는 동안에도 갱신이 5를
  낼 수 있다. 이 경우는 예약이 정상적으로 역할 세션에 넘어간 것으로 보고 갱신을 멈추고 사실만 기록한다.
  실행 중 프로세스를 종료하지 않으며 `recovery_required`로 올리지도 않는다. 프로세스 종료는 사용자의
  명시적 취소만 수행한다.
- 정상 종료 뒤에는 `sh .workflow/rules/wf-claim.sh release <targetId> <leaseId>`를 호출한다. 종료 코드
  0은 우리가 정리한 것이고, 5는 이미 반납된 것이므로 둘 다 정리 성공으로 본다. 1은 정리 실패로 남긴다.
  다른 lease는 건드리지 않는다.
- 런타임은 어떤 경우에도 lease 파일을 직접 만들거나 고치거나 지우지 않는다.
- 취소는 프로세스 트리 종료를 확인한 뒤 lease와 예약을 정리한다. 어느 단계가 실패하면 실패한 단계와 남은
  행동을 담아 `recovery_required`로 남긴다.

## 복구와 로그

- provider stdout은 실행별 append-only 이벤트 파일로 직접 연결한다. 데몬이 죽어도 자식 프로세스의
  출력이 끊기지 않고 재시작한 런타임이 마지막 offset부터 다시 읽을 수 있어야 한다.
- 실행 행에는 최소한 실행 식별자, 프로젝트, 역할, provider, 예약 대상, `leaseId`, `resultPrefix`,
  예약 만료 시각, PID, 시작 시각, 프로세스 생성 신원, 이벤트 파일 경로, 마지막으로 읽은 offset,
  이전 실행 식별자, 상태 변경 시각을 남긴다. prompt 원문과 인증 값은 남기지 않는다.
- 시작 시 저장된 `running`과 `reserved` 항목, PID와 프로세스 생존, lease 소유권을 대조한다.
- 같은 프로세스가 살아 있으면 같은 작업을 다시 시작하지 않고 감시를 복원한다. 죽었는데 상태가 남으면
  실패 단계와 정리 결과를 기록한다.
- PID 재사용 판별은 TASK-146의 복구 호출이 반환하는 결과를 사용한다. 같은 PID라도 프로세스 생성 신원이
  다르거나 확인할 수 없으면 실행 중으로 추측하지 않고 `recovery_required`로 둔다.
- 재시도는 이전 실행 식별자를 보존하고 새 예약을 획득한다. 기존 실패 행을 덮어쓰지 않는다.
