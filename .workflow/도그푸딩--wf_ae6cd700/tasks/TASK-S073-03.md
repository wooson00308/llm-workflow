# 아키텍트 대상 판정이 구성 확인 필요 기능을 자동으로 집는다

## 결정권자 요약

### 제안

구성 확인 필요로 판정된 기능을 아키텍트가 자동으로 맡는 대상 목록에 넣고, 그 자리를 사용자 확인 반려
다음이자 작업 정의 오류 수정 앞에 둔다.

### 현재

구성 확인 필요 기능은 어느 역할의 대상 조건에도 들어가지 않는다. 기능 문서는 활성이고 선점도 없으며
진행 중인 작업도 없어서, 아무도 집지 않은 채 남는다. 사용자가 화면에서 이상을 느끼고 물어볼 때까지
아무 일도 일어나지 않는다.

### 변경 후

이 상태의 기능이 생기면 다음 배정 차례에 아키텍트 세션이 그 기능을 받는다. 사용자가 알리거나 승인할
필요가 없다. 이미 잡혀 있는 기능은 선점 규칙에 걸려 두 세션이 같은 기능을 잡지 않는다. 사용자 확인
반려가 함께 있으면 반려가 먼저 나가고, 작업 정의 오류 수정과 함께 있으면 이 기능이 먼저 나간다.
아키텍트가 이미 문서로는 못 고친다고 남긴 기능은 다시 나가지 않는다.

### 비용과 위험

판정이 넓어지면 배정이 헛돌고 실행 한도를 소모하므로, 판정 조건은 화면이 쓰는 상태 계산과 정확히
같은 결과를 낸다. 앱과 조건 검사 스크립트 두 자리가 같은 답을 내야 하고, 두 자리가 갈라지면 화면이
보여주는 상태와 실제로 배정되는 대상이 어긋난다. 그래서 두 자리를 한 작업에서 함께 고치고 기존
대조 시험으로 붙든다. 기능 상태 자체와 사용자 확인 흐름, 승인 도장은 바뀌지 않는다. 되돌리면 지금의
다섯 갈래 대상 목록으로 돌아간다.

## 현재 코드 상태

아키텍트 대상 판정은 두 자리에 있고 둘이 같은 답을 내야 한다.

앱 쪽은 `src-tauri/src/infrastructure/role_eligibility.rs` 353행의 `architect_workflows_verdict`다.
이 함수가 다섯 단계를 차례로 밟는다. 그룹 사용자 확인 반려, 과거 작업 정의 수정 요청, 정의 오류로
막힌 작업, 선점이 끊긴 준비 중 기능, 파생 기능이 없는 최신 승인 순서다. 앞 단계가 대상을 정하면 뒤
단계는 후보 줄만 더한다. 대상 종류 이름은 100행부터 104행까지의 다섯 상수다. 선점 판정은
`lease_ids` 집합에 식별자가 들어 있는지 보는 것이고, 준비 중 기능 단계는 기능 식별자와 출처 승인
식별자와 출처 확인 결정 식별자 셋을 모두 본다.

이 함수가 보는 재료는 `WorkflowInput`이다. 이 구조체의 `items.work_groups`에 이미
`WorkGroupSummary`가 들어 있고, 그 안에 표시 상태가 실려 있다. TASK-S073-01이 끝나면 그 표시 상태에
구성 확인 필요와 사람 판단 필요가 구분되어 실려 오므로, 앱 쪽은 새 재료를 만들 필요 없이 이미 있는
값을 읽으면 된다.

스크립트 쪽은 `src-tauri/src/infrastructure/heartbeat_condition.rs`다. 셸 본문의 `architect)` 절이
1199행부터, PowerShell 본문의 `'architect'` 절이 2216행부터이며 둘 다 위와 같은 다섯 단계를 같은
차례로 밟는다. 대상을 적는 함수는 셸 본문 133행의 `note_target`이고 두 번째 인자가 대상 종류다.
기능 문서를 훑는 함수는 셸 본문 564행의 `scan_work_groups`와 PowerShell 본문 1885행의
`Get-WorkGroups`이며, 지금은 식별자, 문서 상태, 구성 버전, 출처 승인, 출처 기획서, 출처 확인 결정
여섯 값만 낸다. 확인 모드, 최종 변경 시각, 확인 절차 본문, 그 기능에 속한 작업의 상태와 연결은 지금
훑지 않는다. 20행의 `CONDITION_SCRIPT_VERSION`이 두 본문이 공유하는 판 번호이며 지금 값은 23이고,
두 본문의 판 번호 주석 줄에도 같은 수가 적혀 있다.

두 자리가 같은 답을 내는지는 이미 시험이 붙든다. `role_eligibility.rs` 654행의
`assert_matches_condition_script`가 임시 저장소에 문서를 놓고 앱 판정과 스크립트를 함께 돌려
대조한다. `heartbeat_condition.rs` 2722행의 `REASON_CODES`와 2732행의 시험이 두 본문의 사유 코드
목록이 같은지 보고, 3760행의 `SCENARIOS` 표가 시나리오마다 두 본문을 함께 돌려 종료 코드와 사유
코드를 대조한다.

구성 확인 필요로 판정하는 조건식의 정본은 `src-tauri/src/infrastructure/fs_project_repository.rs`
3202행부터 3246행까지의 판정 사슬이다. 조건은 여섯 갈래이고 TASK-S073-01의 문서에 갈래마다 적혀
있다. 확인 절차가 사용자 행동으로 인정되는지 보는 판정은 같은 파일 3390행의 `scenario_is_user_safe`와
그 아래 두 함수이며, 세 낱말 목록과 코드 블록 검사로 이루어져 있다.

## 변경 범위

- 앱 판정에 단계를 하나 더한다. 표시 상태가 구성 확인 필요인 기능을 대상으로 삼고, 그룹 사용자 확인
  반려 단계 다음이자 과거 작업 정의 수정 요청 단계 앞에 둔다. 선점은 기능 식별자, 출처 승인 식별자,
  출처 확인 결정 식별자 셋을 모두 보아 준비 중 기능 단계와 같은 규칙을 쓴다. 대상 종류 이름 상수를
  하나 더한다.
- 표시 상태가 사람 판단 필요인 기능은 이 단계의 후보가 아니다. TASK-S073-01이 그 상태를 별도 값으로
  내려주므로 이 단계는 구성 확인 필요만 고른다.
- 조건 검사 스크립트의 두 본문에 같은 단계를 같은 자리에 넣는다. 그러려면 기능 문서 훑기가 확인
  모드와 최종 변경 시각과 확인 절차 본문과 새 선택 필드를 함께 내야 하고, 그 기능에 속한 작업의
  상태와 연결을 대조하는 자리가 필요하며, 확인 절차가 사용자 행동으로 인정되는지 보는 판정을 같은
  규칙으로 옮겨야 한다. 앱의 판정 사슬과 같은 결과를 내는 것이 기준이다.
- 스크립트 판 번호를 하나 올리고 두 본문의 주석 줄도 함께 올린다.

## 범위 밖

- 구성 오류로 판정하는 조건 자체를 넓히거나 좁히는 일. 이 작업은 같은 판정을 스크립트에서도 낼 수
  있게 옮기는 것이며, 조건을 바꾸지 않는다.
- 상태 계산과 화면. TASK-S073-01과 TASK-S073-04가 맡는다.
- 아키텍트 세션이 그 대상을 받아 무엇을 하는지. TASK-S073-02가 계약에 적는다.
- 구성 중단 의심과 개발 막힘의 기존 자동 처리 경로. 그대로 둔다. (기획서 R-22)
- 개발자와 기획자 판정. 그대로 둔다.

## 완료 조건

- C1. 구성 확인 필요로 판정되는 기능이 있고 그 기능에 유효한 선점이 없으면, 앱 판정과 스크립트 두
  본문이 모두 그 기능 식별자를 아키텍트 대상으로 답한다. (기획서 R-11, 인수 조건 7)
- C2. 같은 기능에 유효한 선점이 있으면 대상으로 답하지 않고 선점된 후보로만 적는다. 기능 식별자,
  출처 승인 식별자, 출처 확인 결정 식별자 가운데 어느 것으로 걸려도 같다. 만료된 선점은 막지 않는다.
  (기획서 R-12, 인수 조건 8)
- C3. 사용자 확인 반려 대상과 구성 확인 필요 기능이 함께 있으면 반려 대상이 먼저 나온다.
  (인수 조건 9)
- C4. 과거 작업 정의 수정 요청 대상 또는 정의 오류로 막힌 작업과 구성 확인 필요 기능이 함께 있으면
  구성 확인 필요 기능이 먼저 나온다. (인수 조건 9)
- C5. 선점이 끊긴 준비 중 기능 또는 파생 기능이 없는 최신 승인과 함께 있으면 구성 확인 필요 기능이
  먼저 나온다. 두 단계의 기존 차례는 그대로다.
- C6. 표시 상태가 사람 판단 필요인 기능은 앱 판정과 스크립트 두 본문 모두에서 대상으로 답하지 않는다.
  같은 기능의 선택 필드를 지우면 다시 대상으로 답한다. (기획서 R-17, 인수 조건 11)
- C7. 여섯 갈래 조건 각각에 대해, 그 갈래 하나로만 구성 확인 필요가 되는 기능을 놓았을 때 앱 판정과
  스크립트 두 본문이 같은 답을 낸다. 확인 절차가 사용자 행동으로 인정되지 않아 생기는 갈래도 포함한다.
- C8. 구성 확인 필요가 아닌 기능은 이 단계의 대상이 되지 않는다. 완료, 재분류 대기, 준비 중, 개발
  막힘, 개발 중, 사용자 QA 대기 기능을 각각 확인한다.
- C9. 앱 판정과 스크립트를 함께 돌려 대조하는 기존 시험이 이 작업이 더한 상황에서도 통과한다. 두
  본문의 사유 코드 목록이 같고, 시나리오 표의 종료 코드와 사유 코드가 두 본문에서 같다.
- C10. 개발자와 기획자 대상 판정의 답이 이 작업 전과 같다. 아키텍트 판정에서도 구성 확인 필요 기능이
  하나도 없는 저장소에서는 답이 이 작업 전과 같다. (기획서 R-19, R-22)
- C11. 스크립트 판 번호가 하나 올랐고 두 본문의 주석 값과 상수 값이 같다.

## 검증 절차

1. `cargo test --manifest-path src-tauri/Cargo.toml role_eligibility`로 앱 판정 시험을 돌린다.
   C1부터 C8까지와 C10을 덮는 시험을 넣고, 대상 판정 시험은 기존 방식대로
   `assert_matches_condition_script`를 거쳐 스크립트와 함께 대조한다.
2. `cargo test --manifest-path src-tauri/Cargo.toml heartbeat_condition`으로 두 본문 대조 시험과
   시나리오 표를 돌린다. C9와 C11이 여기서 확인된다. PowerShell 본문 시나리오가 이 기기에서 건너뛰게
   되면 그 사실을 보고서에 적는다.
3. `cargo test --manifest-path src-tauri/Cargo.toml`로 백엔드 전체를 돌려 회귀가 없는지 본다.
4. `cargo fmt --manifest-path src-tauri/Cargo.toml --check`와
   `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings`를 통과시킨다.
5. `npm run check`로 화면 쪽 회귀가 없는지 확인한다.

## 범위 사전 검사

선언한 두 파일은 대상 판정의 두 정본이다. 두 자리가 같은 답을 내야 한다는 것이 이 작업의 핵심이라
한 작업에서 함께 고친다. 대조 시험도 두 파일 안에 있어서 완료 조건이 요구하는 편집이 밖으로 나가지
않는다.

이 작업은 이 그룹에서 가장 큰 작업이다. 스크립트 두 본문에 구성 오류 판정을 옮기는 일이 낱말 목록
셋과 문서 대조 여럿을 포함하기 때문이다. 그래도 나누지 않은 이유는, 앱과 스크립트 가운데 한쪽만
고친 상태에서는 두 자리를 대조하는 기존 시험이 반드시 실패하기 때문이다. 나누면 어느 쪽을 먼저
반영해도 시험이 통과하지 않는 중간 상태가 생긴다.

`src-tauri/src/infrastructure/fs_project_repository.rs`를 살펴보고 뺐다. 앱 판정이 읽는 표시 상태는
`WorkflowInput`의 `items.work_groups`에 이미 실려 오고, 1911행 근처의 `WorkflowInput` 조립 자리에
새 값을 더할 필요가 없다. 조건식의 정본이 이 파일이지만, 이 작업은 그 조건을 바꾸지 않고 스크립트로
같은 판정을 옮기는 것이므로 편집 대상이 아니다. 다만 스크립트가 옮겨 담을 규칙을 여기서 읽는다.
`src-tauri/src/infrastructure/reservation_helper.rs`도 살펴보고 뺐다. 이 헬퍼는 조건 검사의 기계
출력에서 대상 값을 문자열로 받고 대상 종류로 분기하지 않으며, 아키텍트 역할에는 격리 사본을 준비하지
않는다. 대상 종류가 하나 늘어도 이 파일은 그대로 동작한다.
`src/features/projects/domain/types.ts`도 살펴보고 뺐다. 대상 종류는 화면 계약에서 자유 문자열이라
값이 늘어도 타입이 깨지지 않는다.

- 값 경로: C1부터 C5까지의 대상과 차례. 만드는 자리는 `role_eligibility.rs` 353행의
  `architect_workflows_verdict`이며 단계를 하나 더하므로 편집 대상이다. 대상 종류 이름은 같은 파일
  100행부터 104행까지의 상수 옆에 하나 더하므로 편집 대상이다. 판정이 읽는 표시 상태는
  `WorkflowInput`의 `items.work_groups`가 이미 그대로 실어 오므로 그 경유 자리는 편집하지 않는다.
  같은 판정의 스크립트 쪽 자리는 `heartbeat_condition.rs` 1199행과 2216행의 두 절이며 편집 대상이다.
  소비 자리는 두 곳이다. 하나는 화면의 대기 물량 표시이고, 앱 판정의 답이 지금 경로를 그대로 타고
  나가므로 편집할 자리가 없다. 다른 하나는 예약 헬퍼가 읽는 스크립트의 기계 출력이고, 133행의
  `note_target`이 이미 대상과 종류를 함께 실어 내므로 이 역시 편집할 자리가 없다.
- 값 경로: C6의 사람 판단 필요 제외. 만드는 자리는 TASK-S073-01의 상태 계산이고 이 작업은 그 값을
  읽기만 한다. 앱 쪽은 표시 상태가 구성 확인 필요인 것만 고르므로 따로 제외 조건을 쓰지 않는다.
  스크립트 쪽은 기능 문서의 선택 필드를 직접 읽어 구성 버전과 대조해야 하므로, 564행의
  `scan_work_groups`와 1885행의 `Get-WorkGroups`가 그 필드를 함께 내도록 편집한다.
- 값 경로: C7의 여섯 갈래 판정. 앱 쪽은 이미 표시 상태 하나로 도착해 있어 편집할 자리가 없다.
  스크립트 쪽은 기능 문서 훑기가 확인 모드와 최종 변경 시각과 확인 절차 본문을 함께 내야 하고, 그
  기능에 속한 작업의 상태와 세 연결 값을 대조하는 자리와 확인 절차 인정 판정이 새로 필요하므로 두
  본문 모두 편집 대상이다. 옮겨 담을 규칙의 원본은 `fs_project_repository.rs`의 판정 사슬과 3390행
  아래 세 함수이며, 그 파일은 읽기만 한다.
- 값 경로: C9와 C11의 대조. 만드는 자리는 두 파일 안의 시험과 20행의 판 번호 상수이며 편집 대상이다.
  소비 자리는 관리 자산 설치 판정이고, 판 번호를 값으로 받으므로 편집할 자리가 없다.
