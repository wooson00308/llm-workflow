# 자격 확인 도구가 상태 판정 결과를 밖으로 내보낸다

## 결정권자 요약

### 제안

상태 조회가 쓸 판정값을 자격 확인 도구가 그대로 내보내는 출력 모드를 더한다.

### 바뀌는 것

- 지금: 기획서와 기능의 실제 상태, 선점의 만료 여부는 앱을 켜야 알 수 있다 → 앞으로: 같은 판정을 명령이 받아 갈 수 있다
- 판정 규칙은 새로 적지 않는다. 도구가 이미 계산해 놓고 버리던 값을 내보내기만 한다.

### 비용과 위험

- 자격 확인 도구의 버전이 올라간다. 버전이 낮은 채로 남은 프로젝트에서는 다음 작업의 조회가 판정값을 빼고 답한다.
- 역할 판정의 답과 종료 코드는 그대로다. 이 작업만으로 사용자에게 보이는 화면은 하나도 바뀌지 않으며, 자동 검증이 그 사실을 확인한다.

## 현재 코드 상태

이 작업이 손대는 자리는 모두 `src-tauri/src/infrastructure/heartbeat_condition.rs` 안에 있다. 이
파일은 조건 스크립트의 두 구현 본문을 Rust 상수로 들고 있고, 앱이 그 본문을
`.workflow/rules/wf-eligible.sh`(윈도우에서는 `.ps1`)로 설치한다. 저장소의 설치본은 앱이 다시 쓰는
사본이므로 손으로 고치지 않는다.

- 20행이 조건 스크립트 버전 24다. 두 본문의 머리에 같은 숫자가 주석으로 박혀 있고(29행, 1868행),
  설치 판정이 그 줄을 읽는다.
- 27행부터 셸 본문, 1864행부터 PowerShell 본문이다. 두 본문은 같은 판정을 각각 이식한 쌍이고, 셸
  판정의 함수 하나에 PowerShell 함수 하나가 대응한다.
- 셸 본문 78행의 기계 출력과 107행의 판정 종료 함수가 표준 출력을 쓰는 유일한 자리다. 나머지 진단은
  모두 표준 오류로 나간다.
- 셸 본문 203행이 마이그레이션 락을 보고 곧바로 종료한다. 이 줄은 역할 인자를 가리지 않으므로, 새
  출력 모드를 그대로 두면 락이 걸린 프로젝트에서 조회가 답하지 못한다. 기획서 R6은 락이 걸려 있어도
  조회는 된다고 정했다.
- 셸 본문 509행의 결정 훑기가 기획서별 최신 사용자 결정을 이미 고르고 있다. 지금은 찾는 결과와 같은
  결정만 출력한다.
- 셸 본문 620행의 구성 확인 훑기가 기능 하나의 표시 상태 사슬을 앱과 같은 순서로 이미 계산한다.
  최종 판정 자리(1083행 부근)에서 확정, 반려, 준비 중, 막힘, 진행 중에 해당하는 기능을 `continue`로
  버리고 구성 확인 필요만 출력한다. 버리는 가지마다 판정 결과는 이미 손에 있다.
- 셸 본문 564행의 기능 훑기가 기능의 구성 버전과 확인 방식을 읽고, 1270행의 선점 판정과 164행의
  만료 판정이 lease의 미만료 여부를 답한다.
- 셸 본문 1845행의 사용법 갈래가 알 수 없는 첫 인자를 사용법 오류 2로 끝낸다.
- 3331행의 시험 도우미가 임시 프로젝트를 만들어 설치본을 실제로 실행하고 표준 출력과 종료
  코드를 받아 온다. 이 파일의 시험은 모두 그 도우미를 쓴다.

앱 쪽 판정의 정본은 `src-tauri/src/infrastructure/fs_project_repository.rs`에 있다. 기획서 표시
상태는 4062행의 정규화와 5042행의 최신 결정 덮어쓰기가 정하고, 기능 표시 상태는 3238행부터의
사슬이 정한다. 이 작업은 그 두 자리를 읽어 대조하되 고치지 않는다.

## 변경 범위

조건 스크립트의 두 본문에 상태 투영 출력 모드를 더한다. 호출 계약은 다음과 같이 고정한다.

- 호출은 프로젝트 루트에서 `sh .workflow/rules/wf-eligible.sh status`다. 두 번째 인자는 받지 않으며,
  붙으면 지금의 사용법 오류와 같은 자리에서 2로 끝낸다.
- 표준 출력은 레코드 한 줄씩이고 필드 구분자는 탭 하나다. 레코드 종류는 셋이다.
  - `spec` 탭 워크플로 디렉터리 이름 탭 기획서 id 탭 표시 상태
  - `group` 탭 워크플로 디렉터리 이름 탭 기능 id 탭 표시 상태 탭 구성 버전 탭 확인 방식
  - `lease` 탭 대상 id 탭 역할 탭 만료 표기
- 워크플로 디렉터리 이름은 `.workflow/` 바로 아래 이름 그대로 쓴다. 앞뒤에 경로 구분자를 붙이지
  않는다.
- 기획서 표시 상태 어휘는 `draft`, `user_review`, `approved`, `revision_requested`, `rejected`
  다섯이다. 값은 앱의 정규화와 최신 결정 덮어쓰기를 그대로 따른다.
- 기능 표시 상태 어휘는 `completed`, `rework`, `preparing`, `preparing_stalled`, `blocked`,
  `developing`, `qa_ready`, `automatic_completed`, `configuration_error`,
  `human_judgment_required` 열이다. 앱 열거의 이름을 소문자와 밑줄로 옮긴 값이며 다른 이름을 새로
  만들지 않는다.
- `lease` 레코드는 판정 시각 기준 미만료인 lease만 낸다. 역할이 적혀 있지 않은 lease는 그 자리를
  빈 필드로 둔다.
- 종료 코드는 0 정상, 1 읽기 실패, 2 사용법 오류다. 레코드가 하나도 없어도 0이다. 이 모드는 판정
  사유 한 줄을 표준 출력에 내지 않는다.
- 진단 문구는 표준 오류로만 낸다.

이 계약을 채우기 위해 다음을 고친다.

- 203행의 마이그레이션 락 종료를 상태 모드에서 건너뛴다. 세 역할의 판정에서는 지금과 똑같이 걸린다.
- 509행의 결정 훑기가 기획서별 최신 사용자 결정의 결과값을 함께 낼 수 있게 넓힌다. 최신 결정을 고르는
  식은 지금 것을 그대로 쓴다.
- 620행의 구성 확인 훑기가 기능마다 최종 표시 상태를 낼 수 있게 넓힌다. 지금 `continue`로 버리는
  가지에서 그 가지의 이름을 내보내면 되고, 판정 순서를 바꾸지 않는다. 준비 중과 준비 중단의 구분은
  1270행의 선점 판정을 그대로 쓴다.
- 1845행 부근의 갈래에 상태 모드를 더한다. 이 모드는 후보 훑기와 대상 선택을 하지 않고, 셋 중 어느
  역할의 판정도 부르지 않는다.
- 20행과 두 본문 머리의 버전 주석을 25로 올린다.
- PowerShell 본문에 같은 계약의 구현을 더한다. 출력 줄의 필드 구분자와 어휘와 종료 코드는 셸 본문과
  글자 그대로 같다.

## 범위 밖

역할 판정을 고치지 않는다. 세 역할의 대상 선택, 후보 제외 사유, 종료 코드, 기계 출력 JSON의 모양은
이 작업 전후로 같다.

앱 Rust 판정과 화면 파생 계산을 고치지 않는다. 이 작업은 그 판정을 대조 기준으로 읽기만 한다.

조회 명령 자체는 만들지 않는다. 자산 설치와 출력 형식은 같은 그룹의 다른 두 작업이 맡는다.

하트비트 잡 설정과 조건 문자열을 고치지 않는다. 상태 모드는 데몬이 부르는 자리가 아니다.

## 완료 조건

- C1. `status` 인자로 부르면 표준 출력이 위 세 레코드 형식만 담고, 종료 코드가 0이다. 워크플로가
  비어 있어도 0으로 끝난다.
- C2. 기획서 레코드의 표시 상태가 앱 판정과 같다. 파일에 `user_review`로 적혀 있고 승인 결정이
  있는 기획서는 `approved`로 나온다. 결정이 없는 기획서만 `user_review`로 나온다.
- C3. 기능 레코드의 표시 상태가 앱 판정과 같다. 확정, 반려, 준비 중, 준비 중단, 막힘, 진행 중,
  확인 대기, 자동 완료, 구성 확인 필요, 사람 판단 필요 열 가지가 모두 픽스처로 한 번씩 나온다.
- C4. `lease` 레코드에 미만료 lease만 나온다. 만료된 lease와 만료 표기를 읽을 수 없는 lease는 나오지
  않는다.
- C5. 마이그레이션 락이 있는 프로젝트에서도 `status` 호출이 0으로 끝나고 레코드를 낸다. 같은
  프로젝트에서 세 역할 호출은 지금과 같이 판정 사유 `migration-lock`과 종료 코드 1로 끝난다.
- C6. 두 번째 인자를 붙이면 종료 코드 2로 끝나고 표준 출력에 레코드가 나오지 않는다.
- C7. 세 역할 호출의 종료 코드와 표준 출력과 기계 출력 JSON이 이 작업 전과 같다. 이 파일의 기존
  시험이 하나도 고쳐지지 않은 채 통과한다.
- C8. 두 본문의 버전 주석이 25로 같고, 설치 판정이 두 본문을 같은 버전으로 읽는다.
- C9. PowerShell 본문에 같은 계약의 구현이 있고, 두 본문의 상태 모드 출력 어휘가 글자 그대로 같음을
  확인하는 시험이 있다.
- C10. 상태 모드는 파일을 만들거나 고치거나 지우지 않고 git을 부르지 않는다.

  두 쪽이 함께 표현하는 기획서 id와 기능 id에 대해 상태값이 하나라도 다르면 실패한다.
- C3의 픽스처는 기능 표시 상태 열 가지가 모두 한 번씩 나오도록 만든다. 준비 중과 준비 중단의 구분은

- `cd src-tauri && cargo test` 로 크레이트 전체 시험을 돌려 다른 모듈의 회귀가 없음을 확인한다.
- `cd src-tauri && cargo clippy --all-targets -- -D warnings` 와 `cargo fmt --check` 를 돌린다.

## 범위 사전 검사

선언한 파일은 하나다. 조건 스크립트의 두 본문과 그 시험이 모두 그 파일 안에 있고, 완료 조건을 채우는
데 이 밖의 편집이 필요한지 값을 따라가며 확인했다.

`.workflow/rules/wf-eligible.sh`를 열어 보고 뺐다. 이 파일은 앱이 관리 자산 동기화에서 다시 쓰는
설치본이며, 정본은 선언한 파일의 상수다. 설치본을 손으로 고치면 다음 동기화가 되돌린다.

`src-tauri/src/infrastructure/managed_script.rs`를 열어 보고 뺐다. 117행의 설치 판정이 본문의 버전
주석 줄을 읽어 설치 여부를 정하는데, 읽는 접두사는 자산이 넘기는 값이고 조건 스크립트의 접두사는
이미 선언한 파일 19행에 있다. 버전 숫자만 올리면 되고 공용 규약은 그대로다.

`src-tauri/src/infrastructure/managed_project_assets.rs`를 열어 보고 뺐다. 643행이 조건 스크립트의
설치 계획을 세우고 891행 부근이 자산 버전을 결과에 싣는데, 두 자리 모두 자산 상수의 버전 필드를
읽으므로 숫자가 올라가도 배선이 그대로다.

`src-tauri/src/infrastructure/fs_project_repository.rs`와 `src-tauri/src/domain/project.rs`를 열어
보고 뺐다. 대조 시험이 이 둘을 읽지만 읽기만 한다. `inspect`는 215행의 구조체에 이미 공개 함수로
있고(218행), 대조에 필요한 값은 212행의 항목 묶음과 746행의 lease 요약과 280행의 기능 표시 상태
열거에 이미 실려 있다. 새 필드를 더할 이유가 없다.

`src/features/projects/application/useProjectWorkspace.ts`를 열어 보고 뺐다. 화면 파생 계산은 세
번째 판정 자리이지만 이 작업은 화면에 값을 내보내지 않는다.

기계 상태를 조건으로 삼는 측정이 없으므로 이 작업은 조용한 기계를 요구하지 않는다. 같은 그룹의 다른
두 작업과 파일이 겹치지 않아 순서를 선언하지 않았다.

- 값 경로: C2의 기획서 표시 상태. 값을 만드는 자리는 결정 문서의 결과값과 작성 시각이고 워크플로의
  `decisions/` 아래에 있다. 스크립트가 읽는 자리는 선언한 파일 509행의 결정 훑기이며 기획서별 최신
  결정을 이미 고르고 있고 선언 안에 있다. 파일에 적힌 상태를 읽는 자리는 기획서 문서의 머리이며
  같은 훑기에서 함께 읽는다. 내보내는 자리는 새 상태 갈래의 출력 줄이고 선언 안에 있다. 대조 기준은
  `fs_project_repository.rs` 4062행의 정규화와 5042행의 덮어쓰기이며, 두 자리 모두 값을 이미
  그대로 답하므로 편집이 필요 없다. 소비자는 이 작업의 대조 시험과 TASK-S084-03의 조회 명령이다.
- 값 경로: C3의 기능 표시 상태. 값을 만드는 자리는 기능 문서와 그 기능에 속한 작업 문서와 확인
  결정이고, 스크립트가 셋을 한 번에 읽는 자리가 선언한 파일 620행의 훑기다. 그 훑기의 최종 판정
