# 프로젝트 에이전트 화면에서 설치와 역할 정책을 관리한다

## 결정권자 요약

프로젝트 화면에 에이전트 전용 진입점이 생기고 Heartbeat를 몰라도 역할을 설정할 수 있다.
기획자와 아키텍트와 개발자마다 실행 도구와 모델과 방식과 최대 인원을 한 행에서 편집한다.
런타임 설치와 호환 상태와 복구 행동은 같은 화면에서 안내되고 터미널 명령을 요구하지 않는다.
기존 역할 설정을 옮길 때 바뀌는 값과 옮기지 못하는 값을 먼저 확인한다.
Dream은 새 화면에 나타나지 않고 기존 연동 화면에서 독립적으로 유지된다.

## 확인 동선

이 화면은 아직 앱 메뉴에 나타나지 않는다. 화면과 그 배선은 모두 만들었지만, 작업 공간의 값을 화면
껍데기로 넘기는 최상위 조립 파일이 이 작업의 선언 범위에 없어 그 두 줄을 넣지 않았다. 배선이 없는 동안
메뉴에 빈 진입점이 생기지 않도록 진입점 자체를 통로가 있을 때만 세우게 했다. 그래서 이번 확인은 자동
검사 수치로 한다.

- `npx vitest run src/features/projects/components/agents/AgentRuntimeView.test.tsx` → 30 passed, 0 failed
- `npm run check` → 타입 검사 통과, 26개 파일 884 tests 통과, 배포 빌드 성공
- `cargo test --manifest-path src-tauri/Cargo.toml` → 688 passed, 0 failed

검사가 무엇을 못박았는지는 이렇게 읽을 수 있다.

1. 준비 상태 여섯 가지(미설치, 실행 버전 불일치, 계약 불일치, 범위 밖 버전, 판정 불가, 런타임 호출
   실패)가 각각 다른 제목과 다른 버튼을 갖는다.
2. 실행 도구 진단 여섯 값(`ready`, `executable_missing`, `login_required`, `permission_denied`,
   `unsupported_version`, `billing_route_acknowledgement_required`)이 각각 다른 문장과 다음 행동을
   갖고, 모르는 값은 숨기지 않고 그대로 보여준다. 로그인 안내 자리에 토큰 입력칸은 없다.
3. 계획을 보기 전에는 적용 버튼이 없고, 실행 중 작업이 있는 업데이트 계획은 건수와 영향받는 프로젝트와
   세션이 끊길 수 있다는 사실을 먼저 보여준다.
4. 화면에 들어오는 것과 다시 읽기는 조회만 부른다. 설치·업데이트·저장·이전은 사용자가 누른 자리에서만
   시작한다.
5. 역할 표는 기획자·아키텍트·개발자 고정 순서이고 최대 인원 초기값은 1, 프로젝트 상한은 3, 기기 상한은
   16이며 16보다 높이려 해도 16으로 되돌아온다.
6. 역할 사용 여부는 사실만 보여주고 조작을 열지 않는다. 런타임 설정 계약에 끄기 필드가 없어 저장이
   거절되므로, 화면이 끄기를 성공처럼 보여주지 않는다.
7. 저장은 첫 확인에서 요약만 보여주고 두 번째 확인에서 한 번 호출된다. 요약에는 역할별 도구·모델·실행
   방식·최대 인원과 프로젝트 상한과 적용 프로젝트가 들어 있다.
8. 마이그레이션은 미리보기를 본 뒤에만 적용되고, 옮기지 못한 값과 손대지 않은 역할을 함께 보여준다.
9. 새 화면 어디에도 Dream 문자열이 없고, 연동 화면의 Dream 카드는 그대로 남아 있다. 연동 화면의 역할
   잡 자리는 "역할 설정은 이제 에이전트 화면에서 합니다"로 새 화면을 가리킨다.
10. 스냅샷이 바뀌면 편집 중이던 값이 새 프로젝트 값으로 바뀐다. 두 프로젝트의 폼이 섞이지 않는다.

화면을 눈으로 보려면 최상위 조립 파일에 두 줄(작업 공간의 에이전트 상태와 조작을 껍데기로 넘기는 값)을
더하면 된다. 그 한 줄짜리 후속은 개발 보고서에 인계로 적었다.

## 목적

Heartbeat 파일과 데몬을 주 개념으로 보여주는 기존 연동 UX에서 벗어나, 현재 프로젝트의 역할 정책과
런타임 준비 상태를 앱의 일급 `에이전트` 화면으로 제공한다. 실행 큐와 제어는 후속 작업에서 붙이고 이
작업은 설치·업데이트·복구·마이그레이션·설정 저장까지 완성한다.

## 화면 구조

1. `WorkspaceShell`의 프로젝트 메뉴에 `에이전트` 진입점을 추가한다. 현재 프로젝트가 바뀌면 화면의
   설정과 상태도 같은 프로젝트로 바뀐다.
2. 상단 준비 영역은 runtime 미설치, 설치 가능, 호환, 업데이트 필요, 실행 버전 불일치, 복구 필요를
   구분한다. 정상 상태에서는 내부 Heartbeat 이름을 주 제목으로 쓰지 않는다.
3. 역할 설정 표는 planner, architect, developer 고정 순서로 provider, model, enabled, one-shot 또는
   repeat, max parallel, interval, max per를 보여준다.
4. 프로젝트 상한은 역할 표와 함께 편집한다. 기기 상한은 고급 설정에서 1부터 16까지 낮출 수 있고,
   16보다 높이는 조작은 첫 릴리스에서 제공하지 않는다.
5. 기존 역할 잡이 있으면 마이그레이션 미리보기를 먼저 보여준다. 옮길 값, 기본값으로 채울 값, 옮길 수
   없는 값, Dream 제외 사실을 확인한 뒤에만 적용한다.
6. 저장 확인은 provider, 모델, 실행 방식, 역할별 최대 인원, 프로젝트 상한, 적용 프로젝트를 요약한다.

## 설치와 업데이트 UX

- 설치·업데이트·복구는 TASK-S051-06의 plan과 apply를 구분해 호출한다. plan 결과가 표시되기 전에는
  확인 버튼을 활성화하지 않는다.
- 실행 중 작업이 있는 업데이트 계획은 프로젝트·역할·대상 수와 세션 중단 가능성을 보여준다. 사용자가
  확인해도 백엔드가 stale plan으로 거절하면 최신 계획을 다시 보여준다.
- CLI 미설치, 로그인 필요, 권한 부족, 지원하지 않는 버전, Claude API 과금 경로 확인 필요를 서로
  다른 상태와 다음 행동으로 표시한다. 인증 토큰 입력칸은 만들지 않는다.
- 호환되지 않는 runtime에서는 저장과 실행 진입을 막고 필요한 버전과 앱 내 업데이트 행동을 보여준다.

## Heartbeat와 Dream 경계

- 새 에이전트 화면에 Dream 역할, provider, 큐, 상태를 넣지 않는다.
- 기존 연동 화면의 Dream 카드는 그대로 유지한다.
- 기존 Heartbeat 카드는 서비스·버전·레거시 잡을 확인하는 고급 관리로 남기되 역할 설정과 `지금 실행`
  주 동선을 새 화면과 중복 제공하지 않는다.
- Dream 미설치나 Dream 설정 오류가 새 에이전트 화면의 설치·저장 버튼을 막지 않는다.

## 상태 소유

- 설치 plan, 적용 진행, 설정 저장 오류, 마이그레이션 미리보기는 `useProjectWorkspace`가 소유한다.
  화면 전환으로 컴포넌트가 다시 마운트돼도 실행 중 표시가 사라지지 않는다.
- 자동 조회는 읽기 명령만 호출한다. 설치·업데이트·마이그레이션·저장은 사용자 조작에서만 시작한다.
- baseline revision 경합 실패는 폼을 조용히 덮지 않고 최신 값과 다시 확인할 내용을 보여준다.

## 손대지 않는 것

- 실행 계획, 자동·수동 대상 선택, 큐와 로그 목록
- 취소·재시도 UI
- Dream 설정과 설치 동작
- 채팅 UI와 원격 실행
- 런타임 데이터베이스 직접 읽기

## 완료 조건

1. 프로젝트 메뉴에서 에이전트 화면을 열 수 있고 Heartbeat 파일이나 데몬을 먼저 이해하지 않아도 역할
   설정을 찾을 수 있다.
2. 세 역할 행이 provider, model, 한 번·반복, 최대 병렬 인원, 판정 간격, 실행 한도를 표시·편집한다.
3. 역할 최대 병렬 인원의 초기값은 1, 프로젝트 상한의 초기값은 3이다.
4. 기기 상한의 초기값은 16이며 사용자는 1부터 16 사이로 낮출 수 있지만 16보다 높일 수 없다.
5. 프로젝트를 바꾸면 설정 폼과 저장 대상이 새 프로젝트 값으로 바뀌고 이전 프로젝트 값이 섞이지 않는다.
6. 저장 뒤 앱을 다시 열면 같은 설정이 보인다.
7. 설치·업데이트·복구는 앱 안의 plan과 확인 흐름으로 완료되며 터미널 명령 입력을 요구하지 않는다.
8. 설치 버전과 실행 중 버전 불일치, 호환 불가, CLI 미설치, 로그인 필요, 권한 부족, API 과금 경로
   위험이 각각 다른 문구와 행동을 갖는다.
9. 실행 중 작업이 있는 업데이트는 영향을 보여주고 사용자 확인 전에는 적용되지 않는다.
10. 기존 역할 잡 마이그레이션은 옮길 값과 unresolved 값을 보여주며 확인 전에는 쓰지 않는다.
11. Dream은 새 에이전트 화면과 provider 선택에 나타나지 않고 기존 Dream 카드는 유지된다.
12. Heartbeat 고급 관리 화면에서 역할 설정과 데몬 밖 `지금 실행` 주 동선이 제거되거나 새 화면으로
    안내되어 두 설정 원천이 생기지 않는다.
13. Dream 미설치 상태가 runtime 설치·업데이트·설정 저장을 막지 않는다.
14. 화면 진입과 자동 새로고침이 설치·업데이트·저장 명령을 호출하지 않는다.
15. 접근 가능한 이름, 키보드 조작, 오류 연결이 모든 입력과 확인 대화상자에 제공된다.
16. 기존 화면 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. runtime 준비 상태와 provider 진단 상태별 payload로 에이전트 화면의 문구와 버튼 상태를 검사한다.
2. 두 프로젝트를 전환하고 역할 값을 편집·저장·재조회해 폼과 baseline이 서로 섞이지 않는지 확인한다.
3. 설치, 업데이트, 복구의 plan·취소·적용·stale plan 경로를 사용자 이벤트로 검사한다.
4. 기존 역할 잡의 완전 이전, 일부 unresolved, Dream 혼재 상태를 렌더하고 확인 전 게이트를 검사한다.
5. 새 화면에서 Dream 문자열과 선택지가 없고 연동 화면의 Dream 카드가 남아 있는지 확인한다.
6. 게이트웨이 호출 기록으로 화면 진입과 자동 조회 중 쓰기 명령이 불리지 않는지 확인한다.
7. `npx vitest run src/features/projects/components/agents/AgentRuntimeView.test.tsx src/features/projects/components/WorkspaceShell.test.tsx src/features/projects/components/integrations/IntegrationsView.test.tsx`를 실행한다.
8. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`을 실행한다.
