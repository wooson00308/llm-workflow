# 격리를 모르는 실행 환경에서 개발 실행을 부분 실행하지 않는다

## 결정권자 요약

### 제안

별도 작업 사본을 다루지 못하는 실행 환경에서는 개발 실행을 시작하지 않고 갱신 안내를 돌려주도록, 개발 실행에만 적용되는 최소 실행 환경 판을 둔다.

### 현재

실행 환경이 새 예약 결과의 작업 사본 위치를 모르면 그 값을 무시한 채 공유 작업 공간에서 세션을 시작한다. 격리가 켜졌다고 생각한 사용자가 실제로는 예전과 같은 위험을 그대로 안게 된다.

### 변경 후

개발 실행은 격리를 지원하는 실행 환경에서만 시작되고, 그렇지 않으면 시작 대신 갱신 안내가 나온다. 기획과 아키텍처 실행, 설치와 진단은 지금처럼 동작한다. 사용자는 격리가 실제로 적용되는지를 화면에서 확실히 알 수 있다.

### 비용과 위험

현재 함께 배포되는 실행 환경은 아직 격리를 지원하지 않으므로, 이 변경이 반영되면 지원 판이 나올 때까지 자동 개발 실행이 시작되지 않고 갱신 안내만 나온다. 이는 조용히 예전 방식으로 되돌아가지 않기 위한 의도된 정지다. 설치와 갱신 경로, 다른 두 역할의 실행, 이미 완료된 작업은 건드리지 않으며 판 값을 이전으로 되돌리면 취소할 수 있다. 이 작업은 지원 판과 미지원 판을 각각 재현하는 자동 검사로 확인한다.

## 현재 상태

- 실행 환경 호환 판정은 `src-tauri/src/domain/agent_runtime.rs`의 `judge`(121행)가 수행하고, 결과는 `Compatibility`(86행)다. `allows_execution`(112행)이 참일 때만 실행이 열린다.
- 앱이 다루는 실행 환경 판의 범위는 같은 파일의 `MINIMUM_RUNTIME_VERSION`(24행, 현재 "0.9.0")과 `MAXIMUM_RUNTIME_VERSION`(25행, 현재 "1.99.99")이고, 계약 주 버전은 `SUPPORTED_API_MAJOR`(21행, 현재 1)이다.
- 실행을 여는 자리는 `src-tauri/src/application/agent_runtime_run_service.rs`의 `plan`(97행)과 `start`(118행)이며, 둘 다 첫 줄에서 `guard`(213행)를 호출해 호환하지 않으면 `RunFailure::Incompatible`로 막는다.
- `guard`는 역할을 보지 않는다. 실행 요청은 `RoleSlotRequest`(23행)에 `role` 값을 싣고 오지만 호환 판정에는 그 값이 쓰이지 않는다.
- 릴리스 검사 `scripts/verify-agent-runtime-contract.mjs`는 55~56행에서 `MINIMUM_RUNTIME_VERSION`과 `MAXIMUM_RUNTIME_VERSION` 두 이름을 정규식으로 읽어 함께 배포되는 실행 환경의 manifest 판과 대조한다. 저장소에 담긴 실행 환경 manifest의 판은 0.9 계열이다.
- `docs/agent-runtime.md`의 버전 표(9~11행)가 앱 판과 지원 실행 환경 판을 함께 적는다.

## 변경 범위

1. `src-tauri/src/domain/agent_runtime.rs`에 격리 지원의 최소 실행 환경 판을 새 상수로 둔다. 값은 "0.10.0"으로 정한다. 예약 결과의 계약 판이 2로 올라간 것은 계약 주 버전 안에서 일어난 호환되지 않는 변화이므로, 현재 0.9 계열의 다음 소수 판을 경계로 삼는다. 이 기본값에 이견이 있으면 새 아이디어로 되돌릴 수 있게 근거를 상수 주석에 적는다.
2. 새 상수의 이름에 `MINIMUM_RUNTIME_VERSION`이라는 문자열이 그대로 들어가지 않게 한다. 릴리스 검사가 그 이름을 정규식으로 찾으므로, 부분 문자열이 겹치면 함께 배포되는 실행 환경의 판정이 바뀐다.
3. 같은 파일에 어떤 실행 환경 판이 격리를 지원하는지 판정하는 함수를 둔다. 판정은 이미 있는 판 비교 도구를 그대로 쓰고, 판을 확인하지 못한 경우를 지원으로 접지 않는다.
4. `src-tauri/src/application/agent_runtime_run_service.rs`의 `plan`과 `start`에 역할을 보는 두 번째 관문을 더한다. 요청에 개발 역할 슬롯이 하나라도 있고 설치된 실행 환경 판이 격리를 지원하지 않으면, 계획을 만들지 않고 실행을 시작하지 않으며 갱신이 필요하다는 뜻이 담긴 실패로 돌려준다.
5. 개발 역할이 없는 요청은 지금과 같이 처리한다. 기존 `guard`는 그대로 두고 그 뒤에 새 관문을 둔다.
6. 새 실패는 기존 `RunFailure::Incompatible`과 구분되는 값으로 만들어, 화면이 "실행 환경 자체가 호환되지 않음"과 "격리를 지원하는 판으로 갱신이 필요함"을 다르게 안내할 수 있게 한다.
7. `MINIMUM_RUNTIME_VERSION`, `MAXIMUM_RUNTIME_VERSION`, `SUPPORTED_API_MAJOR`는 바꾸지 않는다. 설치, 갱신, 진단, 동의, 취소 경로도 바꾸지 않는다.
8. `docs/agent-runtime.md`에 격리 지원의 최소 실행 환경 판과 그 판 아래에서는 개발 실행이 시작되지 않는다는 사실을 적는다. 함께 배포되는 실행 환경이 아직 그 판에 이르지 않았다는 사실과, 지원 판이 나오기 전까지 자동 개발 실행이 대기 상태로 남는다는 사실도 함께 적는다.

## 범위 밖

- 함께 배포되는 실행 환경 자체의 갱신. 실행 환경은 별도 저장소에서 배포되며 이 저장소에서 만들 수 없다.
- `MINIMUM_RUNTIME_VERSION`과 계약 주 버전의 변경. 이를 올리면 함께 배포되는 실행 환경의 설치 자체가 막히고 릴리스 검사가 실패한다.
- 실행 상태 화면에 격리 단계를 표시하는 일. 표시할 상태 어휘는 실행 환경이 제공한 뒤에 다룬다.
- 예약 헬퍼의 계약 판. TASK-RES-20260815T032125Z-60360-20260815032125-02가 담당한다.

## 완료 조건

1. 격리 지원 최소 판이 "0.10.0"인 상수가 있고, 그 이름에 `MINIMUM_RUNTIME_VERSION` 문자열이 부분 문자열로 들어 있지 않다.
2. 설치된 실행 환경 판이 "0.10.0" 이상이면 개발 역할 슬롯이 있는 계획과 시작이 지금과 같이 진행된다.
3. 설치된 실행 환경 판이 "0.9.5"처럼 그보다 낮으면 개발 역할 슬롯이 있는 계획과 시작이 모두 막히고, 기존 호환 실패와 구분되는 실패가 돌아온다.
4. 같은 낮은 판에서도 개발 역할 슬롯이 없는 요청은 지금과 같이 계획과 시작이 진행된다.
5. 실행 환경 판을 확인하지 못한 경우에는 개발 역할 슬롯이 있는 요청이 진행되지 않는다.
6. `MINIMUM_RUNTIME_VERSION`, `MAXIMUM_RUNTIME_VERSION`, `SUPPORTED_API_MAJOR` 세 값이 변경 전과 같다.
7. 설치, 갱신, 진단, 동의, 취소 경로의 동작이 변경 전과 같다.
8. `docs/agent-runtime.md`가 변경 범위 8번의 세 가지 사실을 담고 있다.
9. 릴리스 검사가 변경 전과 같은 결과를 낸다.

## 검증 절차

1. `cargo test --manifest-path src-tauri/Cargo.toml agent_runtime`을 실행하고 전부 통과하는지 확인한다. 완료 조건 1~5를 재현하는 검사를 `domain/agent_runtime.rs`와 `application/agent_runtime_run_service.rs`의 시험 모듈에 추가한다. 기존 시험이 `RuntimeStatus` 값을 손으로 조립하는 방식을 그대로 쓴다.
2. 완료 조건 3과 4는 같은 낮은 판 상태에 대해 개발 역할 슬롯이 있는 요청과 없는 요청을 각각 넣어 결과를 비교해 확인한다.
3. 완료 조건 6은 세 상수 값을 직접 확인하는 검사로 고정한다.
4. 완료 조건 7은 `cargo test --manifest-path src-tauri/Cargo.toml agent_runtime_install_service`와 `cargo test --manifest-path src-tauri/Cargo.toml agent_runtime_status`를 실행해 기존 검사가 그대로 통과하는지로 확인한다.
5. 완료 조건 9는 `npm run agent-runtime:verify -- --self-test`를 실행해 확인하고, 결과를 보고서에 적는다.
6. `cargo fmt --manifest-path src-tauri/Cargo.toml --check`와 `cargo check --manifest-path src-tauri/Cargo.toml`을 실행한다.

## 범위 사전 검사

`domain/agent_runtime.rs`, `application/agent_runtime_run_service.rs`, `docs/agent-runtime.md` 세 파일을 선언했다. 판 값과 판정 함수는 첫 파일에, 실행을 여는 두 자리와 실패 값은 둘째 파일에, 사용자와 다음 세션이 읽을 설명은 셋째 파일에 있다. 완료 조건 1~9를 만족하는 편집이 이 세 파일 안에서 끝난다.

- 값 경로: 완료 조건 1·2·3·5(격리 지원 판정) — 원천은 `domain/agent_runtime.rs`에 새로 두는 최소 판 상수다. 첫 hop은 같은 파일의 새 판정 함수로, 이미 있는 `numeric_parts`(169행)와 `within_supported_range`(156행)가 쓰는 것과 같은 숫자 비교를 재사용한다. 두 자리 모두 편집 대상이다. 두 번째 hop은 `application/agent_runtime_run_service.rs`의 `plan`(97행)과 `start`(118행)이며, `guard`(213행) 호출 바로 뒤에 새 관문을 넣는다. 편집 대상이다. 세 번째 hop은 설치된 판을 담고 있는 `RuntimeStatus`의 `installed_version` 필드(`domain/agent_runtime.rs` 안)로, 이미 그 값을 들고 있으므로 새 필드를 만들지 않는다. 최종 소비자는 실패 값을 문자열로 받아 보여 주는 실행 화면이다.
- 값 경로: 완료 조건 4(역할 구분) — 원천은 `application/agent_runtime_run_service.rs`의 `RoleSlotRequest`(23행)가 이미 싣고 있는 `role` 값이다. 이 값은 지금 `roles_payload`(222행)로만 흘러가고 호환 판정에는 쓰이지 않는다. 새 관문이 같은 파일에서 그 값을 읽으므로 hop이 늘지 않고, 구조체에 필드를 더할 필요도 없다. 편집 대상은 관문 코드 한 자리다.
- 값 경로: 완료 조건 6(기존 판 보존) — 원천은 `MINIMUM_RUNTIME_VERSION`(24행)과 `MAXIMUM_RUNTIME_VERSION`(25행), `SUPPORTED_API_MAJOR`(21행)다. 세 값은 `judge`(121행), `infrastructure/agent_runtime_package.rs`(115행), `application/agent_runtime_install_service.rs`(398행), `infrastructure/agent_runtime_release.rs`(121행)로 흘러간다. 이 태스크는 세 값을 바꾸지 않으므로 그 네 자리 모두 값을 그대로 나르고 편집이 필요 없다.
- 값 경로: 완료 조건 9(릴리스 검사) — 원천은 같은 두 판 상수의 이름이다. `scripts/verify-agent-runtime-contract.mjs` 53~56행이 `domain/agent_runtime.rs`를 문자열로 읽어 정규식으로 두 이름을 찾고, 그 값을 함께 배포되는 실행 환경 manifest의 판과 대조한다. 정규식은 `MINIMUM_RUNTIME_VERSION:` 문자열을 그대로 요구하고 첫 일치만 쓰므로, 새 상수 이름이 그 문자열을 부분 문자열로 포함하면 판정이 바뀐다. 완료 조건 2가 그 이름 규칙을 요구하고 검증 절차 5가 결과를 확인하므로, 이 스크립트 자체는 편집하지 않고 선언 밖에 둔다.

`infrastructure/agent_runtime_package.rs`와 `application/agent_runtime_install_service.rs`를 열어 보고 선언에서 뺐다. 두 파일은 계약 주 버전과 기존 판 범위만 보고 새 격리 판을 참조하지 않는다. 설치 경로를 바꾸지 않는 것이 완료 조건 7이고, 이는 함께 배포되는 실행 환경이 아직 격리를 지원하지 않는 동안에도 앱의 설치와 갱신이 계속 동작해야 하기 때문이다.

`infrastructure/agent_runtime_release.rs`도 확인하고 뺐다. 121행이 게시된 판이 앱의 지원 범위 안인지 계산하지만, 그 범위는 이 태스크가 바꾸지 않는 두 상수에서 나온다.

화면 쪽 파일은 선언 밖에 두었다. 새 실패 값은 기존 실패와 같은 통로로 문자열이 되어 나가므로, 격리 갱신 안내를 별도 화면 요소로 만드는 일은 이 태스크의 완료 조건에 없다.
