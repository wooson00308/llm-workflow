# 격리를 모르는 실행 환경에서 개발 실행을 부분 실행하지 않는다

## 결정권자 요약

### 제안

별도 작업 사본을 다루지 못하는 실행 환경에서는 개발 실행 요청을 받아들이지 않고 갱신 안내를 돌려주도록, 개발 역할 요청에만 적용되는 최소 실행 환경 판을 둔다.

### 현재

개발 역할 실행 요청은 격리를 지원하는 실행 환경에서만 받아들여진다. 이 작업 전에는 실행 환경이 새 예약 결과의 작업 사본 위치를 모르면 그 값을 무시한 채 공유 작업 공간에서 세션을 시작했고, 격리가 켜졌다고 생각한 사용자가 실제로는 예전과 같은 위험을 그대로 안았다.

### 변경 후

개발 역할이 들어간 실행 요청은 격리를 지원하는 실행 환경에서만 받아들여지고, 그렇지 않으면 실행 후보를 만드는 단계에서 갱신 안내가 나온다. 기획과 아키텍처 실행, 설치와 진단은 지금처럼 동작한다. 사용자는 격리가 실제로 적용되는지를 화면에서 확실히 알 수 있다.

### 비용과 위험

현재 함께 배포되는 실행 환경은 아직 격리를 지원하지 않으므로, 이 변경이 반영된 지금부터 지원 판이 나올 때까지 앱 화면에서 개발 실행을 시작할 수 없고 갱신 안내만 나온다. 이는 조용히 예전 방식으로 되돌아가지 않기 위한 의도된 정지다. 설치와 갱신 경로, 다른 두 역할의 실행, 이미 완료된 작업은 건드리지 않으며 판 값을 이전으로 되돌리면 취소할 수 있다. 이 작업은 지원 판과 미지원 판을 각각 재현하는 자동 검사로 확인한다.

## 막힌 사유

- 막힌 지점: 완료 조건 3과 4가 요구하는 판정을 선언된 세 파일 안에서 만들 수 없다. 새 관문에 필요한
  입력은 설치된 실행 환경 판과 요청에 개발 역할 슬롯이 있는지 두 가지인데, 둘 다
  `application/agent_runtime_run_service.rs`의 `plan`과 `start`에 도달하지 않는다. 두 함수는 판정
  결과인 `Compatibility`만 받고, 그 값에는 판 문자열이 없다. `judge`(`domain/agent_runtime.rs` 121행)가
  `RuntimeStatus`의 `installed_version`을 읽은 뒤 판정 결과만 남기고 판 문자열을 버리며, 호출 자리인
  `commands/agent_runtime.rs`의 `compatibility_of`(523행)도 `RuntimeInspection`에서 `.compatibility`
  하나만 꺼내 넘긴다. 또한 `start`(118행)는 계획 식별자만 받아 역할을 알 수 없다. 계획을 만든 뒤
  역할을 다시 읽을 경로가 없고, 서비스는 값을 들고 있지 않은 단위 구조체다.
- 필요한 해결: 아키텍트가 `scope_files`에 `src-tauri/src/commands/agent_runtime.rs`를 추가하고, 설치된
  판과 개발 역할 슬롯 여부를 `plan`과 `start`까지 전달하는 방법을 작업 문서에 확정해야 한다. 두 값을
  넣으려면 두 함수의 인자를 바꿔야 하고, 그러면 365행과 382행의 호출 자리가 함께 바뀐다.
- 재개 조건: 위 파일이 선언에 들어가고 두 입력의 전달 방법이 확정된 작업 문서가 `todo`로 돌아오면
  개발을 다시 시작한다.
- 관련 대상: 없음

## 현재 상태

- 실행 환경 호환 판정은 `src-tauri/src/domain/agent_runtime.rs`의 `judge`(121행)가 수행하고, 결과는 `Compatibility`(86행)다. `allows_execution`(112행)이 참일 때만 실행이 열린다.
- `judge`는 `RuntimeStatus`의 `installed_version`을 읽어 범위를 판정한 뒤 판정 결과만 남긴다. `Compatible` 변형은 판 문자열을 담지 않는다(86~105행).
- 앱이 다루는 실행 환경 판의 범위는 같은 파일의 `MINIMUM_RUNTIME_VERSION`(24행, 현재 "0.9.0")과 `MAXIMUM_RUNTIME_VERSION`(25행, 현재 "1.99.99")이고, 계약 주 버전은 `SUPPORTED_API_MAJOR`(21행, 현재 1)이다.
- 실행을 여는 자리는 `src-tauri/src/application/agent_runtime_run_service.rs`의 `plan`(98행)과 `start`(119행)이며, 둘 다 첫 줄에서 `guard`(213행)를 호출해 호환하지 않으면 `RunFailure::Incompatible`로 막는다.
- 두 함수가 받는 판정 값은 `&Compatibility` 하나다. 설치된 판 문자열은 여기에 도달하지 않는다.
- 판정을 만들어 넘기는 자리는 `src-tauri/src/commands/agent_runtime.rs`의 `compatibility_of`(523행)이며, `AgentRuntimeInstallService::inspect`가 돌려준 `RuntimeInspection`에서 `.compatibility` 하나만 꺼내고 같은 구조체의 `status`는 버린다. `RuntimeInspection`은 `status: Option<RuntimeStatus>`를 이미 들고 있다.
- `plan`은 `&[RoleSlotRequest]`(23행)를 받으므로 요청에 어떤 역할이 들어 있는지 안다. `start`는 계획 식별자만 받으므로 역할을 알 수 없다. 화면도 `plan`이 돌려준 계획의 식별자만 되돌려 보낸다(`src/features/projects/application/useProjectWorkspace.ts` 396~405행).
- 실행 계획은 일회용이고 revision과 만료 시각이 유효 조건이다. 실행 환경 판이 바뀌면 계획이 무효가 되고, `start`(130~135행)는 그 답을 `RunFailure::PlanRejected`로 돌려준다. 설치본과 도는 판이 갈라진 동안에는 `judge`가 `RestartRequired`를 내고 `guard`가 모든 실행 명령을 막는다.
- `RunFailure::message`(71행)가 실패를 한 줄 문자열로 바꾸고, `run_blocking`(533행)이 그 문자열을 그대로 화면에 돌려준다. 새 실패를 화면에 보여 주기 위해 화면 쪽 파일을 고칠 필요는 없다.
- 릴리스 검사 `scripts/verify-agent-runtime-contract.mjs`는 55~56행에서 `MINIMUM_RUNTIME_VERSION`과 `MAXIMUM_RUNTIME_VERSION` 두 이름을 정규식으로 읽어 함께 배포되는 실행 환경의 manifest 판과 대조한다. 저장소에 담긴 실행 환경 manifest의 판은 0.9 계열이다.
- `docs/agent-runtime.md`의 버전 표(9~11행)가 앱 판과 지원 실행 환경 판을 함께 적는다.
- `src-tauri/src/commands/agent_runtime.rs`에는 시험 모듈이 없다. 이 파일의 변경은 컴파일 검사로만 확인한다.

## 변경 범위

1. `src-tauri/src/domain/agent_runtime.rs`에 격리 지원의 최소 실행 환경 판을 새 상수로 둔다. 값은 "0.10.0"으로 정한다. 예약 결과의 계약 판이 2로 올라간 것은 계약 주 버전 안에서 일어난 호환되지 않는 변화이므로, 현재 0.9 계열의 다음 소수 판을 경계로 삼는다. 이 기본값에 이견이 있으면 새 아이디어로 되돌릴 수 있게 근거를 상수 주석에 적는다.
2. 새 상수의 이름에 `MINIMUM_RUNTIME_VERSION`이라는 문자열이 그대로 들어가지 않게 한다. 릴리스 검사가 그 이름을 정규식으로 찾고 첫 일치만 쓰므로, 부분 문자열이 겹치면 함께 배포되는 실행 환경의 판정이 바뀐다.
3. 같은 파일에 격리 지원 여부를 판정하는 함수를 둔다. 입력은 조회 결과의 설치된 판이고, 결과는 지원·미지원·모름 세 가지를 구분하는 값이다. 판 비교는 이미 있는 `numeric_parts`(169행)를 그대로 쓴다. 설치된 판이 없거나 숫자 판 모양이 아니면 지원으로 접지 않고 모름으로 둔다. 미지원과 모름 값은 화면 문구를 만들 수 있도록 확인된 판과 필요한 판을 함께 싣는다.
4. `src-tauri/src/commands/agent_runtime.rs`가 실행 환경 조회 결과에서 호환 판정과 격리 지원 판정 두 값을 함께 꺼내 실행 계획 명령에 넘기도록 고친다. 지금 `compatibility_of`가 버리는 `status`가 그 입력이다. 명령 한 번이 실행 환경을 조회하는 횟수는 지금과 같이 한 번이어야 한다. 두 값을 함께 돌려주도록 기존 함수를 고치든 실행 명령 전용 함수를 새로 두든 상관없으나, 조회를 두 번 하는 구현은 받아들이지 않는다.
5. `src-tauri/src/application/agent_runtime_run_service.rs`의 `plan`이 격리 지원 판정을 인자로 더 받고, 기존 `guard` 호출 바로 뒤에 역할을 보는 두 번째 관문을 둔다. 요청한 역할 슬롯 중 개발 역할이 하나라도 있고 격리 지원 판정이 지원이 아니면, 실행 환경에 요청을 보내지 않고 갱신이 필요하다는 뜻이 담긴 실패로 돌려준다. 요청에 개발 역할이 섞여 있으면 요청 전체를 받아들이지 않는다. 사용자는 개발 역할을 뺀 요청으로 다시 시도할 수 있다.
6. 개발 역할이 없는 요청은 지금과 같이 처리한다. 기존 `guard`와 그 실패 값은 그대로 둔다.
7. 새 실패는 기존 `RunFailure::Incompatible`과 구분되는 값으로 만들고 `message`에 고유한 문구를 둔다. 화면이 "실행 환경 자체가 호환되지 않음"과 "격리를 지원하는 판으로 갱신이 필요함"을 다르게 안내할 수 있어야 한다.
8. `start`, `cancel`, `retry`에는 이 관문을 두지 않는다. 세 함수의 인자와 동작은 바꾸지 않는다. 근거는 아래 `## 범위 사전 검사`의 시작 단계 항목에 적는다.
9. `MINIMUM_RUNTIME_VERSION`, `MAXIMUM_RUNTIME_VERSION`, `SUPPORTED_API_MAJOR`는 바꾸지 않는다. 설치, 갱신, 진단, 동의, 취소 경로도 바꾸지 않는다.
10. `docs/agent-runtime.md`에 격리 지원의 최소 실행 환경 판과 그 판 아래에서는 개발 역할 실행 요청이 받아들여지지 않는다는 사실을 적는다. 함께 배포되는 실행 환경이 아직 그 판에 이르지 않았다는 사실과, 지원 판이 나오기 전까지 앱 화면에서 개발 실행을 시작할 수 없다는 사실도 함께 적는다.

## 범위 밖

- 함께 배포되는 실행 환경 자체의 갱신. 실행 환경은 별도 저장소에서 배포되며 이 저장소에서 만들 수 없다.
- 실행 환경이 스스로 수행하는 자동 배정. 그 경로는 앱의 실행 계획 명령을 지나지 않으므로 이 관문이 닿지 않는다. 자동 배정 쪽 정지는 실행 환경 저장소가 담당한다.
- `MINIMUM_RUNTIME_VERSION`과 계약 주 버전의 변경. 이를 올리면 함께 배포되는 실행 환경의 설치 자체가 막히고 릴리스 검사가 실패한다.
- 화면(`src/`)의 어떤 파일도 고치지 않는다. 새 실패는 기존 실패와 같은 통로로 문자열이 되어 나간다.
- 실행 상태 화면에 격리 단계를 표시하는 일. 표시할 상태 어휘는 실행 환경이 제공한 뒤에 다룬다.
- 예약 헬퍼의 계약 판. TASK-RES-20260815T032125Z-60360-20260815032125-02가 담당한다.

## 완료 조건

1. 격리 지원 최소 판이 "0.10.0"인 상수가 있고, 그 이름에 `MINIMUM_RUNTIME_VERSION` 문자열이 부분 문자열로 들어 있지 않다.
2. 격리 지원 판정 함수가 설치된 판 "0.10.0"과 "0.11.0"과 "1.0.0"에 대해 지원을, "0.9.5"와 "0.9.0"에 대해 미지원을 돌려준다.
3. 같은 함수가 설치된 판이 없는 조회 결과와 숫자 판 모양이 아닌 값에 대해 지원이 아닌 모름을 돌려준다.
4. 설치된 실행 환경 판이 "0.10.0" 이상이면 개발 역할 슬롯이 있는 실행 계획 요청이 지금과 같이 진행된다.
5. 설치된 실행 환경 판이 "0.9.5"처럼 그보다 낮으면 개발 역할 슬롯이 하나라도 있는 실행 계획 요청이 막히고, 기존 호환 실패와 구분되는 실패가 돌아오며, 실행 환경에 아무 요청도 나가지 않는다.
6. 같은 낮은 판에서도 개발 역할 슬롯이 없는 요청은 지금과 같이 실행 계획이 만들어진다.
7. 격리 지원 판정이 모름이면 개발 역할 슬롯이 있는 실행 계획 요청이 진행되지 않는다.
8. `start`, `cancel`, `retry`의 기존 시험이 인자 변경 없이 그대로 통과한다.
9. `MINIMUM_RUNTIME_VERSION`, `MAXIMUM_RUNTIME_VERSION`, `SUPPORTED_API_MAJOR` 세 값이 변경 전과 같다.
10. 설치, 갱신, 진단, 동의, 취소 경로의 동작이 변경 전과 같다.
11. `docs/agent-runtime.md`가 변경 범위 10번의 세 가지 사실을 담고 있다.
12. 릴리스 검사가 변경 전과 같은 결과를 낸다.
13. `src/` 아래 파일이 하나도 바뀌지 않는다.

## 검증 절차

1. `cargo test --manifest-path src-tauri/Cargo.toml agent_runtime`을 실행하고 전부 통과하는지 확인한다. 완료 조건 1~3을 재현하는 검사를 `domain/agent_runtime.rs`의 시험 모듈에 추가한다. 기존 시험이 `RuntimeStatus` 값을 손으로 조립하는 방식을 그대로 쓴다.
2. 완료 조건 4~7을 재현하는 검사를 `application/agent_runtime_run_service.rs`의 시험 모듈에 추가한다. 기존 시험 `an_incompatible_runtime_is_never_asked_to_plan_or_start`가 쓰는 `FakeCaller`와 `caller.calls`가 비어 있는지 보는 방식을 그대로 쓴다. 완료 조건 5와 6은 같은 낮은 판 값에 대해 개발 역할 슬롯이 있는 요청과 없는 요청을 각각 넣어 결과를 비교해 확인한다.
3. 완료 조건 8은 기존 시험을 고치지 않고 그대로 통과하는지로 확인한다. 기존 시험을 고쳐야 통과한다면 `start`, `cancel`, `retry`의 계약을 건드린 것이므로 되돌린다.
4. 완료 조건 9는 세 상수 값을 직접 확인하는 검사로 고정한다.
5. 완료 조건 10은 `cargo test --manifest-path src-tauri/Cargo.toml agent_runtime_install_service`와 `cargo test --manifest-path src-tauri/Cargo.toml agent_runtime_status`를 실행해 기존 검사가 그대로 통과하는지로 확인한다.
6. 완료 조건 12는 `npm run agent-runtime:verify -- --self-test`를 실행해 확인하고, 결과를 보고서에 적는다.
7. `cargo fmt --manifest-path src-tauri/Cargo.toml --check`와 `cargo check --manifest-path src-tauri/Cargo.toml`을 실행한다. `commands/agent_runtime.rs`에는 시험 모듈이 없으므로 이 파일의 변경은 `cargo check`가 유일한 자동 확인이다.
8. 완료 조건 13은 `git status`로 `src/` 아래 변경이 없음을 확인하고 보고서에 적는다.

## 범위 사전 검사

`domain/agent_runtime.rs`, `application/agent_runtime_run_service.rs`, `commands/agent_runtime.rs`, `docs/agent-runtime.md` 네 파일을 선언했다. 앞선 개정은 세 파일만 선언했고, 그 선언으로는 완료 조건을 만족할 수 없다는 사실이 개발 세션에서 확인됐다. 설치된 판이 실행 서비스에 이미 도달한다고 적은 앞선 개정의 값 경로 설명은 사실과 달랐다. 판을 버리는 자리가 `commands/agent_runtime.rs`의 `compatibility_of`(523행)이므로, 그 파일을 선언에 넣는 것이 이번 정정의 핵심이다.

- 값 경로: 완료 조건 1·2·3(격리 지원 판정) — 원천은 `domain/agent_runtime.rs`에 새로 두는 최소 판 상수다. 첫 hop은 같은 파일의 새 판정 함수이고, 판 비교는 이미 있는 `numeric_parts`(169행)를 재사용한다. 두 자리 모두 편집 대상이다. 이 조건은 도메인 파일 안에서 끝난다.
- 값 경로: 완료 조건 4·5·7(설치된 판이 관문까지 도달) — 원천은 실행 환경이 답한 조회 결과의 `RuntimeStatus.installed_version`이다. 첫 hop은 `application/agent_runtime_install_service.rs`의 `inspect`(136행)로, 이미 `RuntimeInspection.status`에 그 값을 담아 돌려주므로 편집이 필요 없다. 둘째 hop은 `commands/agent_runtime.rs`의 `compatibility_of`(523행)이며, 지금 `.compatibility`만 꺼내고 `status`를 버리므로 편집 대상이다. 셋째 hop은 같은 파일의 `plan_agent_run`(356행)이 서비스에 넘기는 인자이며 편집 대상이다. 넷째 hop은 `application/agent_runtime_run_service.rs`의 `plan`(98행) 서명과 그 안의 새 관문이며 편집 대상이다. 최종 소비자는 `RunFailure::message`(71행)가 만든 문자열을 `run_blocking`(533행)이 그대로 돌려주는 화면이다. 두 자리 모두 기존 실패와 같은 통로를 쓰므로 편집이 필요 없고, 그래서 `src/` 아래 파일은 선언 밖이다.
- 값 경로: 완료 조건 6(역할 구분) — 원천은 `application/agent_runtime_run_service.rs`의 `RoleSlotRequest`(23행)가 이미 싣고 있는 `role` 값이다. 이 값은 지금 `roles_payload`(222행)로만 흘러간다. 새 관문이 같은 함수 안에서 같은 슬라이스를 읽으므로 hop이 늘지 않고 구조체에 필드를 더할 필요도 없다. 역할 이름은 `POLICY_ROLES`(`domain/agent_runtime.rs` 359행)가 정한 "developer"다. 편집 대상은 관문 코드 한 자리다.
- 값 경로: 완료 조건 8(시작 단계를 건드리지 않는 근거) — `start`(119행)는 계획 식별자만 받고, 화면도 `plan`이 돌려준 계획의 식별자만 되돌려 보낸다(`src/features/projects/application/useProjectWorkspace.ts` 396~405행). 이 저장소에서 계획을 만드는 자리는 `plan` 하나뿐이므로, 격리를 지원하지 않는 실행 환경에서는 개발 역할 슬롯이 든 계획 자체가 만들어지지 않고 따라서 시작할 계획도 없다. 계획을 만든 뒤 실행 환경 판이 바뀌는 경우도 이미 막혀 있다. 설치본과 도는 판이 갈라진 동안에는 `judge`(121행)가 `RestartRequired`를 내고 `guard`(213행)가 모든 실행 명령을 막으며, 서비스가 재시작되면 계획의 revision 조건이 어긋나 `start`(130~135행)가 `RunFailure::PlanRejected`를 돌려준다. `start`에 역할을 전달하려면 Tauri 명령 인자와 화면 게이트웨이·훅과 그 시험을 함께 고쳐야 하고, 그러면 역할 판정의 근거가 화면이 보낸 값이 된다. 승인된 기획서가 요구하지 않은 확장이므로 하지 않는다.
- 값 경로: 완료 조건 9·12(기존 판과 릴리스 검사 보존) — 원천은 `MINIMUM_RUNTIME_VERSION`(24행), `MAXIMUM_RUNTIME_VERSION`(25행), `SUPPORTED_API_MAJOR`(21행)다. 세 값은 `judge`(121행), `infrastructure/agent_runtime_package.rs`(115행), `application/agent_runtime_install_service.rs`(398행), `infrastructure/agent_runtime_release.rs`(121행)로 흘러가며, 이 태스크가 세 값을 바꾸지 않으므로 그 네 자리 모두 값을 그대로 나르고 편집이 필요 없다. `scripts/verify-agent-runtime-contract.mjs` 53~56행은 `domain/agent_runtime.rs`를 문자열로 읽어 두 이름을 정규식으로 찾는다. 정규식은 `MINIMUM_RUNTIME_VERSION:` 문자열을 그대로 요구하고 첫 일치만 쓰므로, 새 상수 이름이 그 문자열을 부분 문자열로 포함하면 판정이 바뀐다. 완료 조건 1이 그 이름 규칙을 요구하고 검증 절차 6이 결과를 확인하므로 이 스크립트 자체는 편집하지 않고 선언 밖에 둔다.
- 값 경로: 완료 조건 11(문서) — 원천은 이번에 정한 격리 지원 최소 판이고, 소비자는 `docs/agent-runtime.md`를 읽는 사용자와 다음 세션이다. 중간 hop이 없다. 편집 대상이다.

`infrastructure/agent_runtime_package.rs`와 `application/agent_runtime_install_service.rs`를 열어 보고 선언에서 뺐다. 두 파일은 계약 주 버전과 기존 판 범위만 보고 새 격리 판을 참조하지 않으며, `inspect`는 이미 `RuntimeInspection.status`에 설치된 판을 담아 돌려준다. 설치 경로를 바꾸지 않는 것이 완료 조건 10이고, 이는 함께 배포되는 실행 환경이 아직 격리를 지원하지 않는 동안에도 앱의 설치와 갱신이 계속 동작해야 하기 때문이다.

`infrastructure/agent_runtime_release.rs`도 확인하고 뺐다. 121행이 게시된 판이 앱의 지원 범위 안인지 계산하지만, 그 범위는 이 태스크가 바꾸지 않는 두 상수에서 나온다.

`application/agent_runtime_status_service.rs`와 `application/agent_runtime_config_service.rs`도 확인하고 뺐다. 두 파일의 시험 모듈이 `Compatibility::Compatible`을 손으로 조립하는 자리를 많이 들고 있는데, 이번 설계는 `Compatibility`의 모양을 바꾸지 않고 격리 판정을 별도 값으로 두므로 그 자리들이 그대로 컴파일된다.

화면 쪽 파일은 선언 밖에 두었고 완료 조건 13이 그것을 고정한다. 새 실패 값은 기존 실패와 같은 통로로 문자열이 되어 나가므로, 격리 갱신 안내를 별도 화면 요소로 만드는 일은 이 태스크의 완료 조건에 없다.
