# 워크플로별 아이디어 초안을 기억하는 브라우저 저장소를 만든다

SPEC-025 R4가 저장 수단을 아키텍트에게 맡겼다. 이 작업은 그 결정을 코드로 고정한다.

## 저장 구조는 승인된 확인 필요 1·2번이 정한다

DECISION-5B7E9F14의 아키텍트 유의 사항 1번이 짚은 대로, 두 결론이 키 구조를 직접 결정한다.

- **확인 필요 1번(두 입력창의 초안은 하나)** → 입력창 자리를 키에 넣지 않는다. `quick-idea`와
  `idea-inbox-input`이 같은 초안을 본다. 두 입력창이 동시에 보이는 일이 없으므로(확인 사실 3) 합쳐도
  화면이 모순되지 않는다.
- **확인 필요 2번(초안은 워크플로 단위)** → 워크플로가 키다. 초안이 담길 곳이 쓰는 시점에 이미
  정해져 있고(확인 사실 7), 나누지 않으면 A에 쓰던 글이 B를 고른 상태에서 제출된다.

그래서 저장 형태는 **워크플로 디렉터리를 키로 하는 문자열 맵 하나**다. 초안 하나가 최대 1만 자이고
(확인 사실 10) 워크플로 수만큼 늘어난다는 한계는 승인 시 인지됐다.

키에 프로젝트 식별자를 넣지 않는다. 워크플로 디렉터리는 `<이름>--<워크플로 id>` 형태라 그 안의
`wf_` 식별자가 프로젝트를 넘어 유일하다. R3의 "프로젝트를 바꾼 경우에도 같다"는 이것으로 성립한다.
**구현이 같은 디렉터리 문자열을 두 프로젝트가 만들 수 있다는 근거를 찾으면 프로젝트 축을 더하고 그
근거를 보고서에 적는다.**

## 실패 규칙은 선례를 그대로 쓴다

유의 사항 2번이 지정한 대로 SPEC-019 선례(`browserSetupGuideCollapseStore.ts:19`~`:42`)의 실패 삼킴
규칙을 재사용한다. 읽기는 값 없음·JSON 파싱 실패·타입 불일치·저장소 접근 실패를 전부 기본값으로
돌리고 던지지 않는다. 쓰기는 실패를 삼킨다.

다만 **모양은 맵 저장소 쪽이 더 가깝다.** `jobValueMemoryStore.ts`가 이미
`Record<string, RememberedJobValues>`를 같은 실패 규칙으로 다루고 있고(`:20`~`:25`에 값 없음·파싱
실패·객체 아님·배열을 전부 빈 맵으로 돌리는 판정이 있다), 이 작업이 필요한 것이 정확히 그 형태다.
읽기 판정을 짤 때 이 파일을 본보기로 삼는다.

## 선례와 다른 점 하나 (기록으로 남긴다)

기획서가 짚은 대로 이번 것은 앞의 셋과 결이 다르다. 접힘 여부는 앱이 만든 표시 상태이고 잃어도 다시
누르면 그만이지만, 초안은 사용자가 직접 쓴 글이고 잃으면 되돌릴 방법이 없다. 확인 필요 3번은 그럼에도
"알리지 않는다"를 승인했고, 승인 문서가 그 한계를 인지한다고 적었다. **선례 파일들의 주석에 있는
"표시 상태라 읽지 못해도 알릴 가치가 없다"는 근거를 이 파일에 그대로 복사하지 않는다.** 그 문장은
여기서 참이 아니다. 실패를 삼키는 이유를 이 자산에 맞게 새로 적는다 — 실패해도 그 순간 화면의 글은
멀쩡하고 제출도 되며, 글자를 칠 때마다 저장하는 자리라 오류 표시가 입력 중 반복해서 뜨는 쪽이 더
나쁘다는 것이 승인된 근거다.

## 작업 내용

- 모듈 안의 함수들을 객체 하나로 내보낸다. 기존 넷과 같은 모양이다.
- **새 추상화를 만들지 않는다.** 저장소가 다섯이 되었다고 공통 계층을 세우지 않는다. TASK-061이 같은
  상황에서 같은 판단을 했다.
- 저장 키는 새로 둔다. 기존 키를 넓히지 않는다. 버전 접미사(`.v1`)를 붙이는 기존 규칙을 따른다.
- 필요한 동작은 셋이다. 이름과 시그니처는 구현이 정한다.
  - 워크플로 하나의 초안을 읽는다. 없으면 빈 문자열이다.
  - 워크플로 하나의 초안을 저장한다.
  - 워크플로 하나의 초안을 지운다. 제출 성공과 사용자가 입력창을 비운 경우에 쓰인다(R2).
- **빈 문자열을 저장하는 것과 항목을 지우는 것이 같은 결과로 읽히게 한다.** 읽기가 없는 키와 빈
  문자열을 모두 빈 초안으로 돌리면 저절로 성립한다. 맵에 빈 문자열이 쌓이지 않도록 저장 쪽에서 빈
  값을 지움으로 다루는 편을 권한다.
- 한 워크플로의 초안을 다루는 동작이 다른 워크플로의 항목을 건드리지 않는다.
- 읽기·쓰기 어느 쪽도 던지지 않는다. 저장소 접근 자체가 실패하는 환경(`localStorage` 접근이 예외를
  던지는 경우)에서도 마찬가지다.
- 테스트는 기존 저장소 테스트의 구성을 따른다. `browserSetupGuideCollapseStore.test.ts`와
  `jobValueMemoryStore`의 테스트가 본보기다.

## 완료 조건

1. 저장한 초안을 그대로 읽는다.
2. 저장된 값이 없으면 빈 초안이다. (SPEC-025 완료 조건 9의 절반)
3. JSON이 깨졌거나, 객체가 아니거나, 배열이거나, 값이 문자열이 아니면 빈 초안이다. 오류를 던지지
   않는다. (완료 조건 9)
4. 읽기가 던지는 저장소에서도 빈 초안을 돌려주고 던지지 않는다. (R4)
5. 쓰기가 던지는 저장소에서도 던지지 않는다. (R4, 완료 조건 10의 저장소 쪽 절반)
6. 초안을 지우면 그 워크플로의 초안이 빈 초안이 된다. (R2)
7. 한 워크플로의 저장·삭제가 다른 워크플로의 초안을 바꾸지 않는다. (R3, 완료 조건 8의 저장소 쪽 절반)
8. 빈 문자열을 저장한 뒤 읽으면 빈 초안이다. (R2 세 번째 항목)
9. 기존 저장소 넷의 키와 값이 이 저장소의 동작으로 바뀌지 않는다. 검증: 다른 키를 쓰는 테스트.
10. 삭제되거나 비활성화된 테스트가 없다. (완료 조건 16)
11. `npm run check`가 통과한다. (완료 조건 17)
