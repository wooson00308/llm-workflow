# 두 저장소의 런타임 릴리스 계약을 종단 검증으로 고정한다

## 결정권자 요약

앱과 런타임의 릴리스 계약, 종단 검사, 운영 문서 구현은 그대로 보존되어 있다.
검사 격리 누락과 표준 형식 불일치를 교정된 범위 안에서 수리했다.
제품 동작과 승인된 첫 릴리스 범위는 바꾸지 않는다.
두 저장소의 전체 자동 검사와 릴리스 계약 검증을 통과해 품질 확인을 기다린다.
사용자는 막힘을 직접 재개하지 않고 아래 확인 동선의 최종 품질 확인만 수행한다.

## 막힌 사유

- 막힌 지점: claude-heartbeat의 `tests/test_quota.py::test_parse_heartbeat_md_max_per_field`가 기대한 `(5, 86400)` 대신 `None`을 받고, workflow-labs의 `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check`가 에이전트 런타임 Rust 소스 8개 경로의 포맷 차이로 실패한다. 원인 경로는 모두 이 작업의 `scope_files`에 없다.
- 필요한 해결: 아키텍트가 quota 검사의 jobs.d 격리 경로와 Rust 포맷 실패 경로를 작업 범위에 포함하고, 선행 제품 코드를 고치지 말라는 본문 제약을 현재 완료 조건과 모순되지 않게 바꿔야 한다.
- 재개 조건: 아키텍트가 검증된 누락 범위를 정정해 작업을 `todo`로 돌리면, 개발자가 두 실패를 수리하고 전체 검사와 보존한 릴리스 계약 검사를 다시 통과한다.
- 관련 대상: TASK-S051-11, TASK-S051-05, TASK-S051-10

## 목적

앞선 열 작업이 만든 runtime 저장소와 workflow-labs 저장소의 경계를 버전화된 종단 검사와 릴리스
게이트로 고정한다. 이 작업은 새 제품 기능을 추가하지 않고, 승인 기획서의 완료 조건 20개를 반복
가능한 검사와 운영 문서로 만든다.

## 릴리스 경계

- runtime 저장소가 target별 독립 실행형 배포물, manifest, API 계약 fixture를 먼저 만든다.
- workflow-labs 릴리스는 지원 runtime 버전과 API major를 선언하고 정확한 target 배포물을 resource로
  포함한다.
- 계약 검증 스크립트는 앱의 지원 범위, runtime manifest, 실제 `heartbeat agent contract` 응답이
  일치하는지 확인한다.
- runtime 산출물이 없거나 해시·버전·API major가 다르면 Tauri bundle 단계 전에 실패한다.
- 앱과 runtime 릴리스 workflow는 계약 검사와 세 운영체제 smoke test를 통과한 산출물만 게시한다.

## 종단 시나리오

자동 검사는 실제 유료 요청을 만들지 않는 가짜 `claude`·`codex` 실행 파일과 실제 runtime daemon을
사용한다. provider SDK 모듈은 설치하지 않는다.

1. 앱에서 runtime을 설치하고 서비스를 시작한 뒤 앱 프로세스를 종료한다. 실행 중 가짜 provider와
   반복 배정이 계속되고 새 후보를 시작한다.
2. 프로젝트 둘의 반복 실행을 함께 켠다. 설정·큐·상태·로그·오류가 분리되고 한 프로젝트 pause가 다른
   프로젝트를 멈추지 않는다.
3. 역할별 provider·model·한 번·반복·최대 병렬 인원을 저장하고 앱·runtime 재시작 뒤 복원한다.
4. 역할 상한 3, 프로젝트 상한 5, 기기 남은 슬롯 4, 후보 2에서 두 대상만 예약·시작한다.
5. 대상 0과 migration lock에서 provider 프로세스가 생기지 않는다.
6. dispatcher 경합에서 lease와 provider가 하나만 생긴다.
7. planner·architect 병렬 예약이 서로 다른 결과 식별자 접두어를 받는다.
8. 수동 중복, 활성 lease, 완료·거절 대상을 실행 전에 거절한다.
9. one-shot은 최초 목록 뒤 끝나고 repeat는 새 후보를 보충한다.
10. project pause는 새 배정만 멈추고 cancel은 프로세스 트리와 상태를 정리한다.
11. runtime을 강제 종료·재시작해 살아 있는 같은 작업이 중복 실행되지 않고 불확실한 상태는 복구
    필요로 남는다.
12. 앱 실행 요청이 daemon queue를 사용하며 별도 `heartbeat once` 프로세스를 만들지 않는다.
13. Claude만 설치, Codex만 설치, 둘 다 설치한 세 환경에서 선택 가능한 provider와 진단이 일치한다.
14. SDK 없는 환경에서 두 provider의 성공 이벤트와 종료 결과가 표시된다.
15. 실행 파일 없음, 로그인 필요, 권한 부족, 사용 제한, 시간 초과, 취소를 서로 다르게 표시한다.
16. 앱·runtime 상태와 로그에 가짜 인증 토큰, API 키, 전체 prompt가 남지 않는다.
17. Python과 checkout 없는 환경에서 앱 설치·서비스 시작·호환 불가 업데이트 안내가 동작한다.
18. 기존 Claude Heartbeat 역할 잡과 실행 이력이 보존되거나 unresolved 목록으로 확인된다.
19. 새 화면과 provider 목록에 Dream이 없고 Dream 미설치가 설치·실행을 막지 않는다.
20. 양 저장소의 단위·통합 검사와 세 운영체제 서비스 smoke test가 통과한다.

## 운영 문서

`docs/agent-runtime.md`에는 다음을 적는다.

- 앱과 runtime의 버전 호환 표와 업데이트 순서
- 앱 종료, 로그아웃, 운영체제 재시작 때 플랫폼별 보장 경계
- project pause와 process cancel과 기기 서비스 stop의 차이
- provider 인증은 각 CLI가 소유하고 앱이 토큰을 저장하지 않는다는 경계
- Claude API 과금 경로 경고와 여러 유료 세션 동시 시작 위험
- recovery required 상태의 진단·복구 순서
- 기존 Heartbeat 잡과 Dream의 유지 범위

## 손대지 않는 것

- runtime dispatcher와 provider 제품 로직의 기능 변경
- 앱 백엔드와 화면의 제품 동작 변경. 전체 포맷 게이트를 복구하기 위한 Rust 표준 형식 반영만 허용한다.
- 실제 provider 계정으로 유료 요청을 보내는 CI
- Dream 제거
- 원격·클라우드 실행

## 완료 조건

1. 위 종단 시나리오 1번부터 20번까지 자동 검사 또는 명시된 사용자 QA 절차에 각각 대응한다.
2. 자동 시나리오는 macOS·Linux·Windows에서 같은 계약 fixture와 기대 상태를 사용한다.
3. 서비스 smoke test는 실제 플랫폼 서비스 등록·기동·강제 종료·재시작·해제를 수행하고 남은 등록물을
   정리한다. 플랫폼 기능이 없으면 성공으로 건너뛰지 않고 검사 환경 오류로 실패한다.
4. provider 성공 검사는 가짜 CLI를 사용하고 SDK 모듈과 실제 API 키 없이 통과한다.
5. 앱 릴리스가 runtime manifest와 실제 contract 응답을 검증하지 못하면 bundle 전에 실패한다.
6. runtime 릴리스가 target별 배포물과 manifest, 서비스 smoke test를 갖추지 못하면 게시되지 않는다.
7. 운영 문서가 설치, 호환, 실행 수명, 비용, 인증, 복구, 레거시, Dream 경계를 모두 설명한다.
8. 실제 Claude·Codex 로그인 환경의 사용자 QA 동선은 CLI별 성공 실행, 로그 표시, 취소를 짧게 확인하고
   토큰이나 전체 prompt를 수집하지 않는다.
9. 기존 자동 검사를 삭제·비활성화·완화하지 않는다.
10. quota 파서 회귀 검사는 임시 HEARTBEAT 파일과 임시 jobs.d를 함께 사용해 로컬 사용자 설정과
    격리되고, 기대한 `(5, 86400)` 값을 확인한다. 제품 파서 로직은 바꾸지 않는다.
11. 전체 Rust 포맷 검사가 통과하며, 이 작업이 추가한 8개 Rust 경로의 변경은 표준 형식 반영으로만
    제한한다.

## 범위와 선행

TASK-S051-05의 배포·서비스 파일과 TASK-S051-10의 최종 화면 검사를 확장하므로 두 작업 뒤에 진행한다.
앞선 작업의 제품 동작은 이 작업에서 바꾸지 않는다. 검증된 검사 격리 누락과 Rust 표준 형식만 이
작업에서 바로잡고, 다른 제품 결함이 드러나면 해당 작업으로 되돌려 수정한 뒤 이 게이트를 다시 통과시킨다.

## 확인 동선

1. macOS·Linux·Windows 릴리스 행렬에서 runtime 배포물의 서비스 등록, 기동, 강제 종료, 새 PID 재시작, 해제와 앱 bundle 결합이 모두 통과했는지 확인한다. 로컬 자동 검사는 배포물이 없어 이 항목 한 건만 건너뛰었고, 기능이 없는 runner는 성공으로 처리하지 않는다.
2. Claude와 Codex CLI에 로그인한 환경에서 앱의 프로젝트 메뉴 → 에이전트 화면으로 이동한다. provider별로 가장 작은 한 번 실행 계획을 하나씩 확인하고 시작한 뒤 구조화 로그와 성공 상태를 연다.
3. provider별로 짧은 실행을 하나 더 시작해 취소한다. 실행 중 프로세스와 대상이 명시되고, 취소 뒤 프로세스 트리와 lease 정리 결과가 성공·부분 실패로 구분되어야 한다.
4. 상태와 로그에 인증 토큰, API 키, 전체 prompt가 보이지 않아야 한다. 실제 CLI 호출은 비용이 발생할 수 있으므로 최소 실행으로 확인한다.
5. 자동 확인 근거는 런타임 전체 284건, 프런트엔드 902건, Rust 본체 701건과 종단 17건, 포맷·정적 검사·계약 fixture 전부 통과다.
