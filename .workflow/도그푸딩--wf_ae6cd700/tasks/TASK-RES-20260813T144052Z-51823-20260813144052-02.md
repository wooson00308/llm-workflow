# 실행 환경의 모든 새 실행 경로에서 프로젝트 동의를 확인한다

## 결정권자 요약

### 제안

실행 환경이 새 세션을 시작하기 직전에 그 프로젝트의 유효한 동의를 확인하고, 동의가 없으면 자동 배정과
직접 배정과 재시도 중 어느 경로로도 시작하지 않게 한다.

### 현재

실행 환경은 자동 배정 여부와 일시 정지만 확인하고 세션을 시작한다. 앱을 닫아 두어도 배정이 이어지므로
화면에서만 막는 방법으로는 동의 없는 실행을 멈출 수 없다.

### 변경 후

자동 배정과 직접 배정과 재시도가 모두 같은 동의 확인 하나를 지난다. 동의가 없거나 철회됐거나 고지
버전이 낮으면 대상 예약과 실행 도구 시작과 실행 한도 차감 없이 동의 필요 상태로 남고, 그 사유는 일반
실행 실패와 구분되는 이름으로 돌아온다.

### 사용자 결과

동의를 남기지 않은 프로젝트에서는 앱을 닫아 두어도 새 세션이 시작되지 않는다. 동의를 남기면 배정과
실행이 평소대로 이어진다.

### 영향 범위

- 변경: 자동 배정과 직접 배정과 재시도가 시작 직전에 거치는 확인, 시작하지 못한 이유로 돌려주는 값
- 유지: 이미 실행 중인 세션과 그 회복 절차, 일시 정지와 실행 취소의 뜻, 사용자 승인과 품질 확인 관문

### 비용과 위험

동의를 남기지 않은 프로젝트에서 자동 배정이 멈출 때 실행 환경은 아무 기록도 남기지 않는다. 사용자가 앱을
열어 보기 전에는 배정이 멈춘 이유를 알 방법이 없다. 승인된 범위 밖이라 이번에 다루지 않았다.

### 결정 요청

동의를 남기지 않은 프로젝트에서 자동 배정과 직접 배정과 재시도가 모두 시작되지 않고 동의 필요로
표시되는지, 동의를 남긴 뒤 같은 요청이 평소대로 실행되는지 확인한다.

## 확인 동선

이 작업에는 눈으로 볼 화면이 없다. 바뀐 것은 실행 환경이 세션을 시작하기 직전에 거치는 판정이고, 그
판정을 사람이 직접 실행해 볼 수 있는 화면이나 셸 명령은 이 저장소에 아직 없다. 동의를 남기고 지우는
명령은 표준 입력 JSON 계약으로만 구현돼 있어 셸에서 부를 수 없다. 따라서 이 작업은 자동 검사로 닫았고,
확인 도장은 아래 숫자를 신뢰한다는 뜻이다.

`../../Git/claude-heartbeat`에서 아래 네 명령을 실행하면 같은 숫자가 나와야 한다.

- `python -m pytest tests/test_agent_dispatch.py` → 39 passed. 동의 없음, 철회, 고지 버전 낮음, 유효한
  동의 네 경우의 자동 배정 결과와, 실행 중 세션이 유지되는지, 동의 없는 프로젝트가 다른 프로젝트의
  배정을 멈추지 않는지를 확인한다.
- `python -m pytest tests/test_agent_cli.py` → 30 passed. 직접 배정 시작과 재시도가 동의 부족을 일반
  실행 실패와 다른 사유로 알리는지 확인한다.
- `python -m pytest tests/test_agent_end_to_end.py` → 4 passed, 1 skipped. 건너뛴 하나는 환경 변수가
  없으면 실행하지 않는 실제 서비스 검사이며, 이번 변경과 무관하다.
- `python -m pytest` → 363 passed, 8 skipped, 실패 0건.

마지막 명령이 이 작업의 핵심이다. 직전 세션에서는 같은 명령이 3 failed, 360 passed였고, 실패하던 검사
세 개가 이번에 준비 코드만 고쳐 통과했다. 검사를 지우거나 건너뛰게 하거나 단언을 약하게 만든 곳은 없다.
`git diff tests/test_agent_end_to_end.py`로 확인할 수 있으며, 추가된 줄은 동의를 남기는 세 줄과 가져오기
한 줄뿐이다.

- 관련 대상: 없음

## 범위 사전 검사

이 작업이 다루는 값은 둘이다. 동의 유효 여부라는 판정 하나와, 시작하지 못한 이유로 돌려주는
`execution_consent_required`라는 사유 값이다. 실행 환경의 시작 경로를 실제 코드에서 따라가 값이 지나는
자리를 모두 확인했다.

- 값 경로: 완료 조건 1·3·4·7의 동의 판정은 앞 작업이 만든 저장 계층의 조회에서 온다. 이 작업은
  `../../Git/claude-heartbeat/src/heartbeat/agent_dispatch.py`에 판정 함수 하나를 만들어 그 조회를
  그대로 쓰고, 유효 판정 규칙을 다시 쓰지 않는다. 규칙이 두 곳에 있으면 명령이 답하는 유효와 실행이
  판정하는 유효가 갈라진다.
- 값 경로: 완료 조건 3·7의 직접 배정 경로는 같은 파일의 `_preflight_target`을 지난다. 이 함수는
  `start_one_run`, `queue_one_run`, `_start_run_row` 세 곳에서 불리고, 예약 도구 호출과 실행 도구 시작은
  모두 그 뒤에 있다. 따라서 이 함수의 맨 앞에 판정을 두면 예약과 시작과 한도 차감이 모두 일어나지
  않는다. 세 호출 지점은 이미 저장소를 갖고 있으므로 판정에 필요한 저장소를 이 함수에 함께 넘긴다.
- 값 경로: 완료 조건 3의 응답은 `_preflight_target`이 돌려주는 행이
  `../../Git/claude-heartbeat/src/heartbeat/agent_cli.py`의 `_start_from_plan`까지 가서 만들어진다. 그
  함수는 상태가 `idle`인 행을 대기 목록에 넣고 사유를 그대로 싣는다. 따라서 동의 부족은 수동 대상 지정
  여부와 관계없이 `idle` 상태로 돌려주어야 대기로 읽힌다. 이 자리는 편집 없이 값을 나르므로 사유만
  정확히 채운다.
- 값 경로: 완료 조건 4의 재시도 응답은 같은 파일의 `_execution_command`가 만든다. 지금은 시작하지 못한
  행을 무조건 실패로 옮기고, 사유를 응답 데이터의 최상위에서 찾기 때문에 동의 부족이
  `execution_failed`라는 일반 실패로 바뀐다. 그래서 이 자리는 편집한다. 동의 부족일 때 사유와 단계를
  응답 데이터에 함께 실어 봉투의 사유 코드가 `execution_consent_required`가 되게 한다.
- 값 경로: 완료 조건 1·2의 자동 배정 경로는 같은 파일의 `tick_project`을 지난다. 이 함수는 먼저
  `reconcile_project_runs`로 실행 중 세션을 회복하고, 그다음 일시 정지와 자동 배정 여부를 보고 조기
  반환한다. 동의 판정은 그 조기 반환 자리에 함께 둔다. 회복보다 앞에 두면 실행 중 세션의 감시가 끊기고,
  뒤의 배정 루프에 두면 의도의 시작 수가 먼저 올라간다.
- 값 경로: 완료 조건 8·11이 요구하는 저장소 전체 검사는 출시 관문 시나리오
  `../../Git/claude-heartbeat/tests/test_agent_end_to_end.py`를 함께 실행한다. 이 파일의 세 검사
  `test_limits_choose_two_targets_and_fake_clis_leave_no_prompt_in_state`,
  `test_migration_lock_and_no_target_start_no_provider`,
  `test_competing_dispatchers_start_one_provider_for_one_target`는 `start_one_run`을 직접 부르고, 그
  호출은 `_preflight_target` 맨 앞의 `project_may_execute`를 지난다. 그 판정은 `AgentStore.get_consent`가
  읽는 저장소 기록에서만 오는데, 세 검사 모두 동의 기록을 남기지 않으므로 새 확인에 걸려 실패한다.
  따라서 이 파일은 편집하며 `scope_files`에 포함한다. 준비 코드에 `store.save_consent`를 요구 고지
  버전으로 부르는 한 줄을 더하는 것이 필요한 변경이고, 세 검사가 지금 확인하는 사실은 그대로 둔다.
- 값 경로: 위 파일이 범위 밖 파일의 수정으로는 닿지 않는다는 것을 두 파일을 열어 확인했다. 이 파일은
  자체 `configuration` 헬퍼로 설정을 만들고 `tests/test_agent_dispatch.py`의 공용 준비 함수 `configure`를
  전혀 부르지 않는다. 세 검사 중 둘은 `store.save_configuration`도 부르지 않고 설정 객체를
  `start_one_run`에 직접 넘기므로, 설정 저장 경로를 고치는 방법으로도 닿지 않는다.
- 검토했으나 제외한 것: 같은 파일의 나머지 두 검사는 편집하지 않는다.
  `test_contract_and_persisted_projects_are_provider_neutral_and_dream_free`는 실행을 시작하지 않고 계약과
  저장 결과만 읽으므로 동의 판정을 지나지 않고,
  `test_platform_service_registration_restart_and_cleanup`은 환경 변수가 없으면 건너뛰는 실제 서비스
  smoke라 이 변경과 무관하다.
- 겹침 판정: `../../Git/claude-heartbeat/tests/test_agent_end_to_end.py`는 `TASK-S051-11`도 선언한 경로다.
  그 작업은 `qa_waiting`이고 지금 이 파일을 잡은 리스가 없으므로 이 작업의 착수를 막지 않는다. 선언을
  더해 두는 이유는 그 작업이 QA에서 되돌아와 다시 잡힐 때 두 세션이 같은 파일을 동시에 건드리지 않게
  하기 위해서다. 두 작업은 서로 다른 승인에서 나뉘어 `depends_on`으로 순서를 줄 수 없고, 선언이 그
  경우를 막는 유일한 장치다.
- 검토했으나 제외한 것: 같은 파일의 `build_plan`은 편집하지 않는다. 계획 조회는 예약도 시작도 하지
  않으므로 시작 직전 확인이라는 요구에 해당하지 않고, 동의 전 계획을 막는 것은 앱 화면의 관문이 맡는다.
- 검토했으나 제외한 것: `../../Git/claude-heartbeat/src/heartbeat/agent_store.py`는 열지 않는다. 동의
  기록의 조회 메서드는 앞 작업이 이미 만들며, 이 작업은 그것을 부르기만 한다.
- 검토했으나 제외한 것: 취소와 회복 경로는 손대지 않는다. 완료 조건 2가 요구하는 것은 그 경로가
  그대로 도는 것이고, 편집하지 않는 것이 그 조건을 지키는 방법이다.

## 현재 상태

자동 배정은 감시 서비스가 프로젝트마다 주기적으로 돌면서 자동 배정 여부와 일시 정지를 확인한 뒤 역할별
빈 자리를 채운다. 직접 배정과 재시도는 앱의 명령으로 들어와 같은 시작 함수를 지난다. 세 경로 모두 시작
직전에 예약 도구로 대상을 선점하고 실행 도구를 띄운다. 어느 경로에도 사용자가 실행 권한을 이해했는지
확인하는 자리는 없다.

## 변경 범위

1. 동의 판정 함수 하나를 만든다. 입력은 저장소와 프로젝트 식별자이고, 출력은 유효 여부다. 앞 작업이
   만든 조회와 요구 고지 버전을 그대로 쓴다.
2. 시작 전 확인 함수의 맨 앞에서 판정한다. 유효하지 않으면 자격 조회와 예약과 실행 도구 시작 없이
   상태가 `idle`이고 사유가 `execution_consent_required`인 행을 돌려준다. 수동 대상이 지정된 경우에도
   같은 상태로 돌려준다.
3. 자동 배정의 프로젝트별 처리에서 회복 절차 뒤, 배정 루프 앞에 같은 판정을 둔다. 유효하지 않으면 그
   프로젝트의 배정을 하지 않고 반환한다. 실행 행, 대상 예약, 역할별 시작 수 증가가 없어야 한다.
4. 재시도 응답이 동의 부족을 일반 실패와 다른 사유 코드로 알리게 한다. 응답의 사유 코드는
   `execution_consent_required`이고 단계는 예약 단계다. 새 실행 행과 오류 기록을 남기지 않는다.
5. 큐에 남아 있다가 나중에 시작되는 실행도 같은 확인을 지난다. 이 경로는 시작 전 확인 함수를 이미
   지나므로 별도 자리를 만들지 않고, 검사로 그 사실을 고정한다.
6. 계약 문서에 경로별 확인 지점과 사유 이름, 동의 부족이 실행 실패가 아니라 대기라는 사실을 적는다.
7. 출시 관문 시나리오 검사 파일의 준비 코드에 동의 기록을 더한다. 실행을 시작하는 세 검사가 유효한
   동의를 갖춘 상태에서 돌게 하는 것이 목적이며, 각 검사가 지금 확인하는 사실과 단언은 그대로 둔다.

## 범위 밖

- 동의 기록의 저장 구조와 확인·동의·철회 명령 자체
- 앱 화면과 앱 백엔드
- 계획 조회의 판정 변경
- 실행 중 세션의 강제 종료, 일시 정지와 취소의 의미 변경
- 역할별 자격 판정, 예약 도구, 실행 한도 규칙의 변경

## 완료 조건

1. 동의 기록이 없는 프로젝트에서 자동 배정 처리를 한 번 돌려도 실행 행, 대상 예약, 실행 도구 시작,
   역할별 시작 수 증가가 하나도 생기지 않는다.
2. 같은 상황에서 이미 실행 중이던 세션은 상태가 바뀌지 않고, 회복 절차는 평소처럼 수행된다.
3. 동의 기록이 없는 프로젝트에서 확인된 계획으로 직접 배정 시작을 요청하면 실행이 시작되지 않고, 응답의
   대기 목록에 역할과 `execution_consent_required` 사유가 실린다. 시작 목록은 비어 있고 실패 목록에는
   아무것도 들어가지 않으며, 실행 행과 오류 기록이 남지 않는다.
4. 같은 상황에서 재시도를 요청하면 응답의 사유 코드가 `execution_consent_required`가 된다. 실행 도구
   설치 실패, 로그인 필요, 권한 부족, 대상 없음과 서로 다른 값이며, 새 실행 행과 오류 기록이 남지 않는다.
5. 동의를 철회한 프로젝트와, 요구 고지 버전이 올라 기존 동의가 유효하지 않게 된 프로젝트도 완료 조건
   1·3·4와 같게 동작한다.
6. 유효한 동의를 기록한 뒤 같은 요청을 다시 보내면 예약과 실행 도구 시작이 평소대로 진행된다.
7. 큐에 들어 있던 실행이 동의 없이 시작되지 않는다. 그 실행은 예약을 잡지 않고 대기 사유를 남긴다.
8. 동의 판정이 유효할 때의 자동 배정 결과가 이 변경 전과 같다. 기존 자동 배정 검사가 그대로 통과한다.
9. 같은 기기에 동의가 없는 프로젝트와 동의가 유효한 프로젝트가 함께 있을 때, 앞의 프로젝트 때문에 뒤의
   프로젝트 배정이 멈추지 않는다.
10. 계약 문서에 경로별 확인 지점과 사유 이름과 대기라는 성격이 적혀 있다.
11. 저장소 전체 검사가 실패 없이 통과한다. 출시 관문 시나리오의 세 검사는 준비 코드에서 유효한 동의를
    남긴 뒤 이전과 같은 사실을 확인한다. 검사를 지우거나 건너뛰게 하거나 단언을 약하게 만들어 통과시키지
    않는다.
