# 격리 작업 사본과 통합 절차를 워크플로우·개발자 계약에 규정

## 결정권자 요약

### 제안

자동 개발 세션이 격리된 작업 사본에서 구현하고 공유 작업 공간에는 통합 단계에서만 반영하도록, 프로젝트에 설치되는 워크플로우 규칙과 개발자 역할 계약에 그 절차를 규정한다.

### 현재

규칙 문서에는 자동 개발 세션이 어느 작업 공간에서 코드를 고치는지에 대한 규정이 없다. 그래서 세션은 사용자가 직접 작업하는 공간을 그대로 쓰고, 서로의 미완성 변경이 상대의 검사 결과에 섞인다.

### 변경 후

규칙 문서가 격리 사본에서의 구현, 통합, 통합 뒤 재검사를 하나의 순서로 규정하고, 사용자의 미커밋 변경을 자동으로 치우지 못하게 금지한다. 사용자는 자동 세션이 자기 작업을 건드리지 않는다는 사실과 완료의 의미가 약해지지 않았다는 사실을 규칙 문서에서 직접 확인할 수 있다.

### 비용과 위험

규칙 문서의 판 번호가 올라가므로 각 프로젝트가 관리 자산 동기화를 한 번 더 받아야 한다. 사용자 승인 관문, 기존 결정 기록과 이미 완료된 작업의 상태는 건드리지 않으며, 판 번호와 본문을 이전 값으로 되돌리면 취소할 수 있다. 이 작업은 규칙 본문과 판 번호가 어긋나지 않는지 확인하는 자동 검사로 확인한다.

## 현재 상태

- 공통 규칙 본문과 세 역할 계약 본문은 앱의 Rust 상수로 보관되고, 프로젝트마다 `.workflow/rules/workflow.md`와 `.workflow/rules/roles/*.md`로 설치된다. 상수는 `src-tauri/src/infrastructure/project_instructions.rs`의 `WORKFLOW_RULES`(46행), `PLANNER_RULES`(445행), `ARCHITECT_RULES`(533행), `DEVELOPER_RULES`(667행)이다.
- 각 문서의 판 번호는 같은 파일의 `WORKFLOW_RULES_VERSION`(21행, 현재 26), `PLANNER_RULES_VERSION`(22행, 현재 11), `ARCHITECT_RULES_VERSION`(23행, 현재 18), `DEVELOPER_RULES_VERSION`(24행, 현재 18)이 들고 있으며, 각 상수 본문의 frontmatter `rules_version` 값과 같아야 한다.
- 현재 공통 규칙 §4의 "Runtime reservation handoff"는 예약이 역할, 대상, lease, 결과 접두사, 역할 프롬프트를 전달한다고만 적는다. 코드 작업 위치를 전달한다는 규정은 없다.
- 현재 개발자 역할 계약은 완료 조건 검사를 수행한 뒤 태스크를 `verified`로 옮기라고 적을 뿐, 그 검사를 어느 작업 공간에서 수행하는지와 공유 기준에 반영하는 단계가 있는지를 말하지 않는다.
- 공통 규칙 §6은 `scope_files`를 "동시에 시작하면 안 되는 작업을 가르는 선언"으로만 설명한다.

## 변경 범위

`src-tauri/src/infrastructure/project_instructions.rs` 한 파일에서 다음을 수행한다.

1. `WORKFLOW_RULES` 본문에 제어 문서 정본과 코드 작업 사본의 쓰기 경계를 규정하는 내용을 넣는다. lease, 마이그레이션 잠금, 태스크 상태, 작업 그룹, 결정, 역할 보고서의 정본은 등록된 공유 프로젝트에 남고, 개발 세션의 제품 코드 편집·빌드·자동 검사는 태스크 전용 격리 사본에서만 수행한다는 것, 격리 브랜치의 제품 변경 커밋에 태스크 상태 전이·lease·역할 보고서를 섞지 않는다는 것, 세션은 두 위치를 명시적으로 전달받고 어느 쪽이 정본인지 추측하지 않는다는 것, 격리 도입이 앱 소유 상태의 쓰기 권한을 넓히지 않는다는 것을 규정한다.
2. `WORKFLOW_RULES` §4의 예약 인계 절에 준비된 코드 작업 사본 위치와 제어 문서 정본 위치가 예약 결과에 함께 실린다는 사실을 추가한다.
3. `WORKFLOW_RULES` §6의 `scope_files` 설명에 그 선언이 물리적 동시 편집 보호뿐 아니라 통합 충돌과 의미 충돌을 줄이는 선언이라는 목적을 추가한다. `depends_on`이 구현 순서와 통합 순서를 함께 제한한다는 것, 선행 작업이 `verified`가 아니면 후속 작업을 오래된 기준에서 시작하지 않는다는 것도 함께 적는다. 사용자 직접 작업에는 선언을 요구하지 않는다는 것과, 누락되거나 잘못된 `scope_files`를 개발자가 임의로 넓힐 권한이 생기지 않고 기존 작업 정의 오류 복구 경로를 쓴다는 것도 명시한다.
4. `DEVELOPER_RULES` 본문에 격리 구현과 통합의 순서를 규정한다. 개발 세션은 완료 조건에 적힌 검사를 격리 사본에서 수행하고, 통과하면 변경 커밋·시작 기준·검사 명령과 결과·변경 파일 목록을 통합 후보로 기록한다. 격리 검사 통과만으로는 `verified`로 전환하지 않는다. 통합은 그 태스크를 맡은 개발자 역할의 책임이며 새 역할이나 새 사용자 승인 관문을 만들지 않는다. 최초 구현 세션이 통합까지 수행하거나, 저장된 통합 후보를 같은 태스크의 후속 개발자 세션이 읽고 이어받는다. 통합 직전에 공유 기준과 후보의 시작 기준을 다시 비교하고, 달라졌으면 최신 커밋에 맞춘 뒤 격리 검사를 다시 수행한다. 통합 성공 뒤 공유 기준에서 태스크 필수 검사와 영향받는 검사를 실행하고, 보고서를 완성한 뒤에만 `verified`로 전환한다.
5. `DEVELOPER_RULES` 본문에 사용자 직접 작업 보호를 규정한다. 공유 작업 공간에 추적 파일의 미커밋 변경, stage된 변경 또는 기준 전환 중 상태가 있으면 자동 통합을 시작하지 않는다. 개발 세션은 그 변경을 stash, commit, reset, checkout, 삭제하거나 소유권을 추측하지 않는다. 해당 태스크는 통합 대기로 남고, 대기 중에도 다른 태스크의 격리 구현은 계속할 수 있다. 충돌이 태스크의 승인 범위와 `scope_files` 안에서 해결 가능하면 해결하고 격리 검사를 다시 수행하며, 범위 밖 변경이나 사용자 의도 선택이 필요하면 자동으로 한쪽을 택하지 않고 공통 규칙 §5가 정한 `## 막힌 사유` 네 항목에 구체적인 충돌과 재개 조건을 기록한다.
6. `DEVELOPER_RULES` 본문에 격리 검사와 통합 검사의 보고 규칙을 규정한다. 격리 환경에서만 통과하고 통합 환경에서 실패한 검사는 서로 다른 결과로 보고하며 어느 한쪽을 숨기지 않는다. 통합과 상태 전이 중 일부만 성공하면 전체 성공으로 표시하지 않고 어느 단계까지 끝났는지 기록한다.
7. `WORKFLOW_RULES` 상수 본문의 `rules_version`을 27로, `WORKFLOW_RULES_VERSION`을 27로 함께 올린다. `DEVELOPER_RULES` 상수 본문의 `rules_version`을 19로, `DEVELOPER_RULES_VERSION`을 19로 함께 올린다.
8. 같은 파일 1646~1649행의 판 번호 고정 검사를 새 값으로 맞춘다.

## 범위 사전 검사

`src-tauri/src/infrastructure/project_instructions.rs` 한 파일만 선언했다. 이 파일이 관리 규칙 본문과 판 번호를 함께 들고 있고, 판 번호를 검사하는 고정 검사도 같은 파일의 시험 모듈에 있으므로, 완료 조건 1~9를 만족하는 데 필요한 편집이 모두 이 파일 안에서 끝난다.

- 값 경로: 완료 조건 1~6(규칙 본문의 새 규정) — 원천은 `project_instructions.rs`의 `WORKFLOW_RULES`(46행)와 `DEVELOPER_RULES`(667행) 문자열 상수다. 두 상수는 같은 파일의 `install_project_instructions` 계열 함수(889·939·975행)가 `control_root.join("rules")` 아래 파일로 그대로 쓰고, `ROLE_RULES` 표(831행)가 역할 문서의 파일 이름·라벨·본문·판 번호를 묶는다. 최종 소비자는 프로젝트의 `.workflow/rules/workflow.md`와 `.workflow/rules/roles/developer.md`를 읽는 각 역할 세션이다. 편집이 필요한 hop은 두 상수뿐이고, 설치 함수와 `ROLE_RULES` 표는 상수를 이름으로만 참조하므로 값을 바꾸지 않고 그대로 나른다.
- 값 경로: 완료 조건 7(판 번호 상향) — 원천은 `WORKFLOW_RULES_VERSION`(21행)과 `DEVELOPER_RULES_VERSION`(24행)이다. 두 값은 `ROLE_RULES` 표와 설치 함수를 지나 `managed_project_assets.rs`의 자산 상태 조립(865·883행)으로 가고, 거기서 `fs_project_repository.rs`의 관리 자산 동기화(1601·1615행)를 거쳐 설정 화면의 관리 자산 목록에 판 번호로 나타난다. 두 상수만 편집 대상이다.
- 값 경로: 완료 조건 8(고정 검사) — 원천은 같은 파일 1646~1649행의 리터럴 비교다. 소비자가 그 자리에서 끝나는 값이므로 hop이 하나뿐이고 편집 대상이다.

`managed_project_assets.rs`를 열어 보고 선언에서 뺐다. 865·883행과 시험 모듈 1059~1107·1263~1271행 모두 판 번호를 리터럴이 아니라 `project_instructions`의 상수 이름으로 참조하고, 기대값도 같은 상수에서 조립한다. 그래서 판 번호가 올라가도 이 파일의 편집 없이 검사가 성립한다.

`fs_project_repository.rs`도 열어 보고 뺐다. 4835~4836·4951~4952·7567~7568행이 기대 문자열을 `format!("rules_version: {WORKFLOW_RULES_VERSION}")`로 조립하고 이전 판은 `WORKFLOW_RULES_VERSION - 1`로 만들므로, 상수 상향만으로 검사가 그대로 성립한다. 12047~12051·12275~12278행의 다운그레이드 경로도 접두사 `"rules_version:"`만 보고 숫자를 리터럴로 갖지 않는다.

`heartbeat_condition.rs`와 `reservation_helper.rs`는 각각 자기 스크립트의 판 번호만 들고 있고 규칙 문서 판 번호를 참조하지 않는다. 두 파일은 이 태스크의 완료 조건 어느 것도 건드리지 않으므로 선언 밖에 둔다.
