# 그룹 품질 확인이 고정한 기준 커밋을 제출 시점에 다시 확인한다

## 결정권자 요약

### 제안

작업 그룹이 품질 확인을 열 때 확인 대상이 되는 코드 상태를 고정하고, 사용자가 결과를 제출하는 시점에 그 상태가 그대로인지 다시 확인한다.

### 현재

품질 확인은 그룹의 구성 버전과 갱신 시각이 바뀌었는지만 본다. 확인하는 동안 코드가 바뀌어도 제출은 그대로 기록되므로, 사용자가 실제로 본 화면과 완료로 남는 상태가 서로 다른 코드일 수 있다.

### 변경 후

품질 확인을 여는 시점의 코드 상태가 고정되고, 그 사이 코드가 바뀌면 제출이 기록되지 않고 다시 확인하라는 안내가 나온다. 사용자는 자기가 실제로 확인한 상태에 대해서만 완료 도장이 남는다는 것을 보장받는다.

### 비용과 위험

확인 도중 코드가 바뀌면 사용자가 확인을 다시 해야 하므로 한 번 더 손이 간다. 이미 기록된 결정, 완료된 작업과 다른 그룹의 상태는 건드리지 않으며, 같은 요청 식별자로 이미 기록된 제출은 지금처럼 그대로 유지된다. 판정을 이전 형태로 되돌리면 취소할 수 있다. 확인 도중 코드가 바뀐 상황을 재현하는 자동 검사로 확인을 마쳤다. 다만 고정 값은 같은 구성 버전에서 다시 만들어지지 않으므로, 기준이 한 번 움직인 그룹은 사용자가 다시 확인해도 제출이 계속 거절된다. 그 상태를 푸는 경로는 이 작업의 완료 조건 밖이며 별도 판단이 필요하다.

## 현재 상태

- 작업 그룹의 화면 상태는 `src-tauri/src/infrastructure/fs_project_repository.rs`의 `parse_work_group`(2865행 이하)이 계산해 `WorkGroupSummary`(`src-tauri/src/domain/project.rs` 290행)로 만든다. 모든 소속 작업이 `verified`이고 구조가 유효할 때만 사용자 모드는 `QaReady`, 자동 모드는 `AutomaticCompleted`가 된다.
- 품질 확인 제출은 같은 파일의 `submit_work_group_qa`(681행)가 처리한다. 프로젝트 쓰기 잠금을 잡고, 같은 요청 식별자로 이미 기록된 제출이 있으면 그대로 돌려주고, 없으면 그룹 문서를 다시 읽어 판정한다.
- 현재 최신성 검사는 738행 한 곳이다. 그룹의 `revision`과 `updated_at`이 제출에 실린 기대값과 다르면 `ProjectError::WorkGroupQaStale`(121행)로 거절한다.
- 이 검사는 워크플로우 문서의 변화만 본다. 확인 대상 코드가 바뀌었는지는 어디에서도 보지 않는다.
- `WorkGroupQaSubmission`(`domain/project.rs` 434행)은 화면에서 오는 값이며 `workflow_directory`, `file_name`, `expected_revision`, `expected_updated_at`, `request_id`, `entries` 여섯 값을 싣는다.

## 변경 범위

`src-tauri/src/domain/project.rs`와 `src-tauri/src/infrastructure/fs_project_repository.rs` 두 파일에서 다음을 수행한다.

1. 작업 그룹이 품질 확인을 열 수 있는 상태가 되는 시점에 확인 대상 기준 커밋을 고정한다. 고정 값은 프로젝트가 Git 작업 트리일 때 공유 기준의 현재 커밋 해시이며, 앱이 소유하는 상태로 `.workflow/.runtime/qa-base/<그룹 식별자>-<구성 버전>.yml`에 저장한다. 이미 고정 값이 있으면 다시 쓰지 않는다.
2. 고정 값을 `WorkGroupSummary`에 선택 필드로 실어, 화면 상태를 만드는 경로와 제출을 판정하는 경로가 같은 값을 쓰게 한다. 프로젝트가 Git 작업 트리가 아니면 값이 없는 상태로 두고, 값이 없다는 이유로 기존 판정이 달라지지 않게 한다.
3. `submit_work_group_qa`의 최신성 검사에 기준 커밋 비교를 더한다. 고정 값이 있고 제출 시점의 공유 기준 커밋이 그 값과 다르면 제출을 기록하지 않고 거절한다. 거절은 기존 최신성 거절과 구분되는 새 오류 값으로 하며, 사용자에게는 확인 대상 코드가 바뀌었으니 다시 확인해야 한다는 뜻이 전달되게 한다.
4. 거절한 제출은 결정 문서를 만들지 않고 작업 문서도 바꾸지 않는다. 기존 최신성 거절과 같은 자리에서 같은 방식으로 빠져나간다.
5. 같은 요청 식별자로 이미 기록된 제출을 다시 보내는 경우의 동작은 바꾸지 않는다. 기준 커밋 비교보다 먼저 판정하는 현재 순서를 유지해, 이미 남은 결정이 뒤늦게 거절로 바뀌지 않게 한다.
6. 그룹이 새 구성 버전으로 넘어가면 그 버전의 고정 값을 새로 만든다. 이전 버전의 고정 값은 지우지 않고 남긴다.
7. 자동 모드 그룹도 같은 고정 값을 사용한다. 고정 값이 있고 현재 기준 커밋이 다르면 자동 완료 상태로 넘기지 않는다.

## 완료 조건

1. 모든 소속 작업이 `verified`가 되어 사용자 모드 그룹이 품질 확인을 열 수 있는 상태가 되면 그 시점의 기준 커밋이 고정되어 저장된다.
2. 고정 값이 이미 있는 그룹과 구성 버전에 대해 상태를 다시 계산해도 고정 값이 바뀌지 않는다.
3. 기준 커밋이 그대로인 상태에서 품질 확인 결과를 제출하면 지금과 같이 결정 문서가 기록된다.
4. 제출 직전에 공유 기준 커밋이 바뀐 상태에서 제출하면 결정 문서가 만들어지지 않고 작업 문서도 바뀌지 않으며, 기존 최신성 거절과 구분되는 오류가 돌아온다.
5. 같은 요청 식별자로 이미 기록된 제출을 다시 보내면 기준 커밋이 바뀌었더라도 지금과 같이 기존 결정을 그대로 돌려준다.
6. 그룹이 새 구성 버전으로 넘어가면 그 버전의 고정 값이 새로 만들어지고 이전 버전의 고정 값이 남아 있다.
7. 자동 모드 그룹은 고정 값과 현재 기준 커밋이 다르면 자동 완료 상태가 되지 않는다.
8. Git 작업 트리가 아닌 프로젝트에서는 고정 값이 없는 상태가 되고, 그룹 상태 계산과 제출 판정이 변경 전과 같이 동작한다.
9. 그룹 상태 계산과 제출 판정의 다른 모든 조건이 변경 전과 같은 결과를 낸다.

## 범위 사전 검사

`domain/project.rs`와 `fs_project_repository.rs` 두 파일을 선언했다. 그룹 요약 구조는 앞 파일에 있고, 그 구조를 채우는 계산과 제출 판정과 오류 값은 모두 뒤 파일에 있다. 완료 조건 1~9를 만족하는 편집이 이 두 파일 안에서 끝난다.

- 값 경로: 완료 조건 1·2·6(기준 커밋 고정) — 원천은 프로젝트의 공유 기준 커밋 해시다. 첫 hop은 `fs_project_repository.rs`의 `parse_work_group`(2865행)으로, 그룹이 품질 확인을 열 수 있는 상태가 될 때 값을 읽어 `.workflow/.runtime/qa-base/` 아래에 저장한다. 편집 대상이다. 두 번째 hop은 `domain/project.rs`의 `WorkGroupSummary`(290행)로, 값을 선택 필드로 실어 나른다. 편집 대상이다. 세 번째 hop은 같은 파일 203행의 프로젝트 요약이 `work_groups`로 이 구조를 그대로 담아 명령 계층으로 내보내는 자리이며, 구조를 값으로 담기만 하므로 편집이 필요 없다.
- 값 경로: 완료 조건 3·4·5(제출 판정) — 원천은 위에서 저장한 고정 값이다. 첫 hop은 `fs_project_repository.rs`의 `submit_work_group_qa`(681행) 안, 현재 `revision`과 `updated_at`을 비교해 `ProjectError::WorkGroupQaStale`을 내는 738행이다. 그 자리에 기준 커밋 비교를 더한다. 편집 대상이다. 두 번째 hop은 같은 파일 121행의 `ProjectError` 열거형으로, 새 오류 값이 여기에 들어간다. 편집 대상이다. 최종 소비자는 오류를 문자열로 받아 보여 주는 품질 확인 화면이다.
- 값 경로: 완료 조건 7(자동 모드) — 원천은 같은 고정 값이고, 소비자는 `parse_work_group`이 `display_status`를 `AutomaticCompleted`로 정하는 분기다. 그 분기가 이미 이 파일 안에 있으므로 hop이 늘지 않는다.

`src/features/projects/domain/types.ts`를 열어 보고 선언에서 뺐다. 183행의 `WorkGroupSummary` 선언은 화면이 읽는 필드만 나열하며, Rust 쪽에 선택 필드를 더해도 화면이 그 필드를 읽지 않는 한 타입 검사와 실행이 그대로 성립한다. 이 태스크는 고정 값을 화면에 표시하지 않고 판정에만 쓰므로 화면 타입을 고칠 이유가 없다. 검증 절차 7이 그 사실을 확인한다.

`domain/project.rs`의 `WorkGroupQaSubmission`(434행)도 확인하고 고치지 않기로 했다. 기준 커밋은 화면이 보내는 값이 아니라 앱이 저장해 둔 값에서 읽어야 한다. 화면이 보낸 값을 믿으면 확인 도중 바뀐 코드를 화면이 그대로 다시 보내 검사를 통과시킬 수 있기 때문이다. 그래서 제출 구조에 필드를 더하지 않고 저장된 고정 값과 현재 커밋을 앱이 직접 비교한다.

`role_eligibility.rs`와 `heartbeat_condition.rs`는 후보 판정만 다루고 그룹의 품질 확인 개시나 제출을 판정하지 않는다. 그룹 상태는 이 두 파일이 아니라 `parse_work_group`이 정하므로 선언 밖에 둔다.
