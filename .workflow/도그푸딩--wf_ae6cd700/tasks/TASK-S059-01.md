# 개발 작업 화면의 모든 보기와 수치가 끝난 작업 그룹을 함께 제외한다

## 결정권자 요약

### 제안

개발 작업 화면의 목록과 수치가 모두 같은 기준으로 끝난 작업 그룹의 작업을 빼도록 맞춘다.

### 현재

작업 그룹별 보기 한 곳만 끝난 그룹을 빼고 그린다. 평면 보기와 리스트는 끝난 그룹의 작업까지 모두
그리고, 화면 머리의 진행 중 수치와 요약 띠의 진행 중·막힘·완료 수치, 표시 건수도 그 작업을 함께
센다. 그래서 보기를 바꾸면 방금 사라졌던 작업이 다시 나타나고, 완료 칸은 그동안 쌓인 총계가 되어
지금 흐름의 진행도를 읽을 수 없다.

### 변경 후

어떤 보기를 열어도 목록에 남는 작업이 같아지고, 화면 위 수치도 그 범위만 센다. 사용자는 개발 작업
화면에서 지금 판단해야 할 일만 보게 되며, 완료 칸을 이번 흐름에서 끝낸 양으로 읽을 수 있다. 감춘
그룹이 있으면 그 개수와 기록 화면에서 볼 수 있다는 안내가 목록 아래에 함께 나온다.

### 비용과 위험

타임라인 보기, 작업 상세 화면, 기록 화면은 손대지 않고 문서 파일도 하나도 바뀌지 않는다. 위험은
최근에 끝낸 작업을 개발 작업 화면에서 찾다가 못 찾는 경우이며, 감춘 개수와 기록 화면을 알려 주는
안내 한 줄로 대응한다. 되돌릴 때는 이 표시 규칙 하나만 되돌리면 된다.

## 현재 코드 상태

개발 작업 화면은 `src/features/projects/components/DevelopmentBoard.tsx` 한 컴포넌트가 그린다.

- `tasksForDevelopment`는 지금 인자를 그대로 돌려주는 항등 함수이고, `scopedTasks`가 그 결과다.
  `filteredTasks`는 `scopedTasks`에 검색어와 상태 필터를 적용한 결과이며, 평면 보드, 리스트,
  작업 그룹별 보기의 `visibleTasks`가 모두 이 값을 쓴다.
- `WorkGroupLaneBoard`만 자체적으로 `displayStatus`가 `completed`·`automatic_completed`인 그룹을
  `activeGroups`에서 빼고, 그 차이를 `completedCount`로 세어 `완료된 작업 그룹 N개는 기록 화면에
  있습니다.` 안내를 레인 목록 아래에 한 줄 붙인다. 이 처리는 레인 보기 안에만 있다.
- 화면 머리의 진행 중 수치 한 곳과 요약 띠의 진행 중·막힘·완료 수치 세 곳은 `count`에
  `workflow.items.tasks`를 그대로 넘긴다. 표시 건수는 보드·리스트에서 `filteredTasks` 기준,
  타임라인에서 `timelineTasks` 기준으로 나온다.
- `timelineTasks`는 `workflow.items.tasks`에서 바로 파생되며 좁혀진 집합을 쓰지 않는다.
- `matchingWorkGroup`은 작업의 소속 그룹을 확정하는 판정을 이미 갖고 있다. 같은 `id`의 그룹이 있고,
  `workGroupRevision`이 1 이상이며 그룹의 `revision` 이하이고, 작업의 `sourceSpecId`와
  `sourceDecisionId`가 그룹의 값과 같을 때만 그룹을 돌려준다. 지금은 `TaskDetail`만 이 함수를 쓴다.

## 완료 조건

- C1. 보드와 리스트가 그리는 작업 집합을 "끝난 작업 그룹에 속하지 않는 작업"으로 좁힌다. 이 판단은
  `tasksForDevelopment`가 맡고, `scopedTasks`와 `filteredTasks`는 지금의 파생 관계를 그대로 유지한다.
  검색과 상태 필터가 좁혀진 범위 안에서만 동작하는 것은 이 파생 관계로 만족된다.
- C2. 끝난 작업 그룹은 `displayStatus`가 `completed`이거나 `automatic_completed`인 그룹 두 가지다.
  `qa_ready`, `rework`, `configuration_error`, `developing`, `preparing`, `preparing_stalled`,
  `blocked` 그룹의 작업은 모든 보기에 그대로 보인다. 값을 판정하는 규칙을 새로 만들지 않고 백엔드가
  이미 넘겨 주는 `displayStatus`를 그대로 읽는다.
- C3. 소속 그룹을 확정할 수 없는 작업은 감추지 않는다. 확정 판정은 `matchingWorkGroup`이 이미 쓰는
  조건을 그대로 쓴다. 그 판정이 그룹을 돌려주지 못하는 작업은 모든 보기에 남는다. `TaskDetail`의
  기존 호출과 소속 그룹 확인 필요 안내는 지금 동작 그대로 둔다.
- C4. 화면 머리의 진행 중 수치와 요약 띠의 진행 중·막힘·완료 수치가 좁혀진 작업 집합을 센다. 지금
  `workflow.items.tasks`를 넘기는 네 자리를 모두 좁혀진 집합으로 바꾼다.
- C5. 보드와 리스트의 표시 건수는 좁혀진 집합에서 나온 수를 쓴다. 타임라인 보기의
  `N개 표시 · 전체 이력 표시` 문구와 그 수는 변경 전 값을 유지한다.
- C6. `WorkGroupLaneBoard`에 넘기는 `allTasks`도 좁혀진 집합으로 바꿔 레인 수치가 화면의 다른 부분과
  같은 기준을 쓰게 한다.
- C7. 타임라인 보기는 바뀌지 않는다. `timelineTasks`는 계속 `workflow.items.tasks`에서 파생되고,
  타임라인의 날짜별 집계, 이벤트 상세, 기록 없는 작업 안내는 변경 전과 같이 나온다.
- C8. 감춘 그룹이 하나라도 있으면 보드의 작업 그룹별 보기, 보드의 평면 보기, 리스트 셋 모두에서 목록
  아래에 `완료된 작업 그룹 N개는 기록 화면에 있습니다.` 안내가 정확히 한 번 나온다. N은 끝난 작업
  그룹의 개수이며 지금 `completedCount`가 세는 값과 같은 정의를 쓴다. 감춘 그룹이 없으면 안내는
  나오지 않는다. 문구와 `task-lane-note task-lane-completed-note` 클래스는 지금 것을 그대로 쓰므로
  스타일 파일은 건드리지 않는다. 타임라인 보기에는 이 안내를 붙이지 않는다.
- C9. 작업 상세 화면과 기록 화면은 바뀌지 않는다. `WorkspaceShell`의 기록 화면 필터와 완료 기능
  수치는 손대지 않는다.
- C10. 이 작업으로 `.workflow` 아래의 문서 파일, 앱이 설치하는 규칙 문언, 역할 계약, 규칙 버전은
  하나도 바뀌지 않는다.

## 범위 밖

- 감춤을 켜고 끄는 사용자 설정.
- 감춘 그룹을 개발 작업 화면 안에서 다시 펼쳐 보는 별도 영역.
- 안내 문구를 눌러 기록 화면으로 이동하게 만드는 입구화. 지금처럼 문장 한 줄로 둔다.
- 타임라인 보기의 표시 범위 변경.
- 기록 화면의 구성과 정렬 변경.
- 작업 그룹의 `displayStatus` 판정 규칙 변경. 백엔드가 지금 내리는 판정을 그대로 쓴다.

## 범위 사전 검사

선언한 두 파일은 `src/features/projects/components/DevelopmentBoard.tsx`와 그 검사 파일이다. 이
화면의 목록·수치·안내가 모두 이 한 컴포넌트 안에서 만들어지고 소비되므로, 완료 조건이 요구하는 편집
지점이 전부 이 파일 안에 있다. 아래 네 값의 경로를 실제 코드에서 따라가 확인했다.

- 값 경로: 끝난 작업 그룹 판정(C2). `src-tauri/src/infrastructure/fs_project_repository.rs`의
  `display_status` 파생(3127~3197행)이 원천이고, `src/features/projects/domain/types.ts`의
  `WorkGroupDisplayStatus`(160~169행)와 `WorkGroupSummary.displayStatus`(188행)가 그 값을 그대로
  나른다. `WorkflowSummary.items.workGroups`(29행)로 묶여 `WorkspaceShell.tsx` 525행이
  `DevelopmentBoard`에 넘기고, `WorkGroupLaneBoard`의 `activeGroups`(404~407행)가 이미 이 값으로
  `completed`와 `automatic_completed`를 거른다. 두 값이 이미 타입에 있고 이미 소비되고 있으므로
  백엔드·타입·상위 조립 어느 hop도 편집이 필요 없다. 편집이 필요한 hop은 판정을 화면 전체로
  넓히는 `DevelopmentBoard.tsx` 한 곳뿐이다.
- 값 경로: 작업의 소속 그룹 확정 여부(C3). 원천은 작업 문서에서 읽어 온
  `WorkflowItemSummary`의 `workGroupId`·`workGroupRevision`·`sourceSpecId`·`sourceDecisionId`이며,
  `types.ts` 51~57행에 이미 선언돼 있다. 이 네 값을 합쳐 소속을 확정하는 판정은
  `DevelopmentBoard.tsx`의 `matchingWorkGroup`(336~342행)에 이미 있고 지금은 `TaskDetail`(127행)만
  쓴다. 새 값을 만들지 않고 이 함수를 감춤 판정의 조건으로 함께 쓰므로, 편집 지점은 같은 파일
  하나다. 타입 정의는 필드 추가가 없어 선언 밖에 둔다.
- 값 경로: 화면이 그리는 작업 집합(C1·C4·C5·C6·C7). `tasksForDevelopment`(694행)가 만들고
  `scopedTasks`(92~95행) → `filteredTasks`(96~99행)를 거쳐 `BoardView`의 `items`(217행),
  `ListView`의 `items`(224행), `WorkGroupLaneBoard`의 `visibleTasks`(213행)로 들어간다. 수치 쪽
  소비자는 화면 머리 `count` 호출(141행)과 요약 띠 세 곳(184~186행), 표시 건수 계산(105행과
  187~191행)이다. 레인 수치는 `allTasks`(205행)를 통해 `buildWorkGroupLanes`(486행)가 센다.
  타임라인은 `timelineTasks`(100~103행)라는 별도 파생을 쓰므로 이 집합을 좁혀도 영향을 받지 않고,
  그래서 R7이 요구하는 불변이 코드 구조로 보장된다. 모든 hop이 한 파일 안이라 선언은 그 파일과
  검사 파일로 닫힌다.
- 값 경로: 감춘 작업 그룹 수와 안내(C8). 지금은 `WorkGroupLaneBoard` 안의
  `completedCount`(408행)가 만들고 같은 컴포넌트의 안내 문단(463~465행)이 소비한다. 안내를 평면
  보기와 리스트에서도 쓰려면 이 값을 `DevelopmentBoard` 본체로 올려야 하고, 그 편집도 같은 파일
  안이다. 표시 쪽 최종 소비자인 스타일은 `src/App.css` 649행의 `.task-lane-note` 하나이며
  `.task-lane-completed-note`에는 규칙이 없다. 안내를 다른 위치에서 같은 클래스로 렌더링하므로
  스타일 파일은 값을 바꾸지 않고 그대로 나른다. 그래서 `src/App.css`는 선언에서 뺐다.

선언에서 뺀 파일과 그 근거는 다음과 같다.

- `src-tauri/src/infrastructure/fs_project_repository.rs`: 완료·자동 완료 두 표시 상태를 이미
  만들어 넘긴다. 새로 필요한 필드가 없어 값이 무변경으로 통과한다.
- `src/features/projects/domain/types.ts`: 감춤 판정이 읽는 필드가 모두 이미 선언돼 있다. 타입
  모양이 바뀌지 않는다.
- `src/App.css`: 위 값 경로에서 확인한 대로 재사용하는 클래스에 규칙 변경이 없다.
- `src/features/projects/components/WorkspaceShell.tsx`와 그 검사 파일: 기록 화면은 자기 필터로
  완료 그룹을 따로 고르고(684~686행) 완료 기능 수치도 따로 센다(658~660행). C9가 요구하는 불변이
  이 분리로 성립한다. 검사 파일 663행은 같은 안내 문구와 같은 개수를 기본 보기에서 찾으므로, C8이
  문구와 개수 정의를 유지하는 한 수정 없이 통과한다. 이 검사가 깨지는 것은 C8 위반의 신호이며
  검증 절차 2번이 그것을 확인한다.
