# 차단 분류와 작업 정의 수정 계약을 관리 규칙에 반영한다

## 결정권자 요약

### 제안

막힘의 원인이 어느 종류인지 적게 하고, 작업 정의가 잘못됐을 때 누가 어떤 범위에서 고치는지를 앱이
설치하는 규칙 문언에 넣는다.

### 현재

규칙은 막힐 때 사유 네 항목을 적게 하지만 그 막힘이 정의 오류인지 선행 누락인지 구현 실패인지 구분하지
않는다. 정의가 잘못돼 막힌 작업을 누가 고칠 수 있는지도 규칙에 없어서, 개발자는 고칠 권한이 없고
아키텍트는 이미 분해한 승인을 다시 다룰 자격이 없는 상태로 남는다.

### 변경 후

막힘을 기록할 때 네 분류 중 하나를 같은 편집에 함께 적는다. 아키텍트는 사용자의 수정 요청을 근거로만
같은 작업 문서의 범위와 선행과 완료 조건을 고칠 수 있고, 새 작업을 만들기 전에 영향 범위를 먼저 읽고
그 근거를 작업 문서에 남긴다. 개발자는 구현을 시작하기 전에 그 근거와 저장소를 짧게 대조한다.

### 사용자 결과

막힌 작업을 열면 그 막힘이 정의 문제인지 다른 문제인지 구분해 읽을 수 있고, 정의 문제일 때 무엇을
요청하면 되는지가 문서에 적혀 있다.

### 영향 범위

- 변경: 앱이 설치하는 공통 규칙과 아키텍트·개발자 역할 계약, 사용자 문서의 작업 문서 설명
- 유지: 기존 막힌 사유 네 항목의 형식, 상태 기계와 이력 값의 뜻, 기획 승인과 품질 확인 권한, 기획자 계약

### 비용과 위험

규칙 버전이 올라가므로 모든 프로젝트의 설치본이 다음 쓰기 명령에서 새 문언으로 교체된다. 규칙 버전을
직접 비교하는 검사 두 곳이 같은 변경에서 함께 움직여야 한다.

### 결정 요청

품질 확인에서는 설치된 규칙 본문에 네 분류와 수정 권한 경계와 사전 검사 의무가 각각 한 번씩 적혀
있는지, 그리고 기존 문서가 그대로 읽히는지를 자동 검사 수치로 확인한다.

## 확인 동선

이 작업에는 눈으로 볼 화면이 없다. 바뀐 것은 앱이 설치하는 규칙 문언과 사용자 문서라 자동 검사가 그
문언을 대조하며, 확인 도장은 아래 수치를 신뢰한다는 뜻이다.

- `cargo test --manifest-path src-tauri/Cargo.toml` → 618 passed, 0 failed
- `npm run check` → 타입 검사 통과, 25개 파일 851 tests 통과, 배포 빌드 성공
- `cargo clippy --all-targets` 경고 없음, `cargo fmt` 적용

문언을 직접 읽고 싶다면 임시 폴더를 프로젝트로 열어 앱이 새로 설치한 규칙에서 네 가지를 확인한다.

1. `.workflow/rules/workflow.md`가 `rules_version: 19`이고, 5절에 `### Naming what kind of block it is`
   절이 있다. 선택 필드 `blocked_kind`와 네 값(`definition_error`, `missing_prerequisite`,
   `implementation_failure`, `external_dependency`)이 각각 한 번씩 정의돼 있고, 값이 없거나 모르는 값인
   문서는 분류되지 않은 것으로 읽으며 원인을 추측하지 않는다고 적혀 있다. 막힘에서 벗어나도 값을
   지우지 않되 현재 방해 요소로는 읽지 않는다는 문장도 같은 절에 있다.
2. 같은 5절의 `### When the task definition itself is wrong`에서, 작업 정의 수정 요청이 앱이
   `decisions/`에 남기는 앱 소유 기록이고 에이전트는 만들 수 없으며, 처리한 요청을 잇는 선택 필드가
   `revision_request_id`라는 것을 읽을 수 있다.
3. `.workflow/rules/roles/architect.md`가 `rules_version: 12`이고 두 절이 새로 있다.
   `## Check the scope before you hand a task over`는 고정 제목 `## 범위 사전 검사`와 그 절이 파일
   목록이 아니라 근거를 담아야 한다는 것을, `## Correcting a task whose definition is wrong`은 고칠 수
   있는 것과 보존할 것과 돌려보낼 조건을 적는다.
4. `.workflow/rules/roles/developer.md`가 `rules_version: 14`이고, 제품 파일을 바꾸기 전에 범위 사전
   검사 절과 저장소를 대조한다는 문장과 `### When the scope declaration is what is wrong` 절이 있다.
   범위 밖 파일이 필요하면 제품 코드를 고치지 않고 `blocked_kind: definition_error`로 막고 보고서에
   누락 경로와 직접 참조와 실패할 검증을 남기며, 이 대조가 검사 삭제나 완화의 근거가 아니라는 문장이
   함께 있다.
5. `.workflow/rules/roles/planner.md`는 `rules_version: 11` 그대로다. 본문이 바뀌지 않은 계약은 버전이
   오르지 않는다.

같은 내용이 `docs/file-contract.md`의 `### 차단 분류`, `### 작업 정의 수정 요청`, `### 범위 사전 검사 절`
세 절에 한국어로 적혀 있다.

기존 문서는 바뀌지 않는다. `blocked_kind`나 `revision_request_id`나 범위 사전 검사 절이 없는 기존 작업
문서를 앱이 고치지 않고, 그 때문에 목록·상세 화면의 표시나 자격 판정이 달라지지도 않는다.

## 목적

SPEC-055의 R1, R5, R7, R8 가운데 작성자 계약에 해당하는 부분을 구현한다. 앱이 설치하는 공통 규칙과 두
역할 계약, 그리고 사용자 문서에 차단 분류와 작업 정의 수정 절차와 범위 사전 검사 의무를 적는다. 앱
명령과 화면은 이 작업의 범위가 아니다.

## 범위 사전 검사

- 규칙 문언의 정본은 `project_instructions.rs`의 내장 문자열이다. 프로젝트에 설치된 `.workflow/rules/`
  사본은 동기화가 관리하므로 직접 편집하지 않는다.
- 착수 시점 버전은 공통 규칙 18, planner 11, architect 11, developer 13이다. 본문이 바뀌는 계약은 공통
  규칙과 아키텍트 계약과 개발자 계약 셋이므로 각각 19, 12, 14가 된다. planner는 11에 머무른다.
- 규칙 버전을 직접 비교하는 검사가 두 파일에 있다. `fs_project_repository.rs`의 설치·갱신 검사와
  `managed_project_assets.rs`의 동기화 검사이며, 두 파일이 범위에 들어 있는 이유가 이것이다.
- 두 파일에는 낮은 버전을 설치해 동기화가 올리는지 보는 픽스처와, 앱보다 높은 버전을 설치해 덮어쓰지
  않는지 보는 픽스처가 함께 있다. 방향이 서로 반대다.
- TASK-S052-01과 TASK-143이 앞서 같은 네 파일에서 버전을 올렸고 그 과정에서 실제로는 아무 문자열도
  바꾸지 못하던 픽스처 두 개를 되살렸다. 아키텍트 계약을 낮추는 픽스처와 개발자 계약을 낮추는 픽스처가
  그것이며, 이번 변경은 두 계약의 버전을 모두 올리므로 두 픽스처의 문자열이 함께 움직여야 한다.
- 검증에 필요하지만 수정하지 않는 파일은 없다. 네 파일 밖의 제품 변경이 필요하지 않다.

## 변경 범위

### 공통 규칙

- 개발 작업을 막힘 상태로 전환할 때 상태와 이력과 갱신 시각과 막힌 사유 절을 기록하는 같은 편집에서
  차단 분류 값 하나를 함께 적도록 정한다. 값은 선택 frontmatter 필드이며 현재 상태가 막힘일 때만 뜻을
  가진다.
- 허용 값은 작업 정의 오류, 선행 계약 누락, 구현 실패, 외부 의존 네 가지다. 값이 없거나 아는 값이
  아니면 분류되지 않음으로 읽고 원인을 추측하지 않는다고 적는다.
- 막힘을 벗어난 뒤에도 마지막 분류는 지우지 않지만 현재 방해 요소로 읽지 않는다고 적는다.
- 사용자가 남긴 작업 정의 수정 요청이 앱 소유 기록이며 에이전트가 그 기록을 만들 수 없다고 적는다.
- 처리한 수정 요청을 작업에 연결하는 선택 frontmatter 필드를 정의한다.

### 아키텍트 역할 계약

- 사용자의 수정 요청 하나를 근거로 작업 하나만 고칠 수 있고, 작업 식별자와 출처 기획서와 승인 결정과
  상태와 기존 이력을 보존한다고 적는다.
- 고칠 수 있는 것은 선언 범위, 선행 관계, 본문의 현재 상태와 변경 범위와 손대지 않는 범위, 완료 조건과
  검증 절차, 그리고 그 변화에 맞춘 결정권자 요약뿐이라고 적는다.
- 막힌 사유 절과 과거 개발 보고서를 지우거나 다시 쓰지 않는다고 적는다.
- 수정이 승인된 기획서의 요구를 더하거나 빼야 하거나 새 사용자 결정을 요구하면 처리하지 않고 새
  아이디어가 필요하다고 보고한다고 적는다.
- 새 작업과 수정 작업을 넘기기 전에 범위 사전 검사를 수행하고 그 근거를 작업 본문의 고정 제목 절에
  남긴다고 적는다. 절의 제목은 `## 범위 사전 검사`이며 파일 목록만 늘어놓지 않고 왜 그 범위면 완료
  조건을 충족할 수 있는지를 적는다.

### 개발자 역할 계약

- 제품 파일을 바꾸기 전에 작업의 범위 사전 검사 절과 실제 저장소를 짧게 대조한다고 적는다.
- 범위 밖 파일 변경이 완료 조건이나 전체 검증에 명백히 필요하면 제품 코드를 바꾸지 않고 작업 정의
  오류로 막고, 누락 경로와 그 파일을 필요로 하는 직접 참조와 실패할 검증을 보고서에 남긴다고 적는다.
- 이 대조가 검사 삭제나 완화나 넓은 쓰기 권한의 근거가 되지 않는다고 적는다.

### 사용자 문서

- 작업 문서 설명에 차단 분류 값과 뜻, 수정 요청 연결 필드, 범위 사전 검사 절을 같은 내용으로 적는다.
- 기존 문서가 이 값들을 갖지 않아도 계속 유효하며 일괄 변환하지 않는다고 적는다.

### 버전 문자열을 가진 검사 파일

두 검사 파일에서는 이전 규칙 버전을 직접 비교하는 문자열만 새 값으로 바꾼다. 검사 함수의 판정 대상과
시나리오 구성과 단언 개수는 그대로 둔다. 바꿀 문자열은 계약별로 고른다. 이번에는 공통 규칙과 아키텍트
계약과 개발자 계약이 올라가고 기획자 계약은 그대로이므로, 기획자 계약을 쓰는 픽스처의 숫자는 건드리지
않는다. 낮추는 픽스처와 높이는 픽스처의 방향은 각각 유지한다. 각 치환은 픽스처 원문에 실제로 있는
문자열을 대상으로 삼아야 하며, 아무것도 바꾸지 못하는 치환을 남기지 않는다.

## 손대지 않는 것

- 앱의 작업 상세 화면과 활동 화면
- 수정 요청 기록을 만드는 앱 명령과 자격 판정
- 기존 막힌 사유 네 항목의 제목과 라벨
- 기획자 역할 계약과 그 버전
- 프로젝트에 설치된 규칙 파일의 직접 편집
- 기획서와 결정 기록과 스키마 버전

## 완료 조건

1. 설치된 공통 규칙이 차단 분류 네 값과 그 뜻, 값이 없는 문서를 추측하지 않는다는 규칙, 막힘 해제 뒤
   보존 규칙을 각각 한 번씩 정의한다.
2. 설치된 공통 규칙이 작업 정의 수정 요청을 앱 소유 기록으로 정의하고 에이전트가 그 기록을 만들 수
   없다고 적으며, 처리한 요청을 작업에 연결하는 선택 필드를 정의한다.
3. 설치된 아키텍트 계약이 수정 권한의 대상과 보존 대상과 처리하지 않고 돌려보낼 조건을 적는다.
4. 설치된 아키텍트 계약이 범위 사전 검사 의무와 작업 본문에 남길 절의 고정 제목을 적는다.
5. 설치된 개발자 계약이 구현 전 대조와 정의 오류 차단 절차를 적고, 그 대조가 검사 삭제나 완화의 근거가
   아니라고 적는다.
6. 사용자 문서가 위 네 가지를 규칙 본문과 같은 뜻으로 설명한다.
7. 공통 규칙과 아키텍트 계약과 개발자 계약의 버전 상수와 본문 frontmatter 값이 각각 일치하고 착수 시점
   값보다 한 단계 높다. 결과는 19와 12와 14다. 기획자 계약은 11에서 바뀌지 않는다.
8. 분류 값과 수정 연결 필드가 없는 기존 작업 문서가 계속 읽히고 일괄 변환되지 않는다.
9. 관리 자산 동기화가 새 문언을 설치하고 앱보다 높은 버전의 설치본은 덮어쓰지 않는 기존 안전 절차를
   유지한다.
10. 변경분은 범위 파일 네 개뿐이고 프로젝트에 설치된 규칙 파일과 기존 기획서·작업·보고서와 결정 기록을
    수정하지 않는다.
11. 두 검사 파일에서는 이전 규칙 버전 문자열만 바뀐다. 검사 이름과 시나리오 구성과 단언 개수가 변경
    전과 같다.
12. 두 파일의 모든 버전 치환이 실제로 존재하는 문자열을 대상으로 삼는다. 아무것도 바꾸지 못하는 치환이
    남아 있지 않으며, 앞선 작업이 되살린 아키텍트 계약 픽스처와 개발자 계약 픽스처가 계속 실제로 낮은
    버전을 설치한다.
13. 앱보다 높은 버전을 설치해 덮어쓰지 않는지 보는 픽스처의 방향이 유지된다.
14. 기존 자동 검사를 삭제하거나 약화하지 않는다.

## 검증 절차

1. `cargo test --manifest-path src-tauri/Cargo.toml`을 실행한다.
2. 설치된 공통 규칙과 두 역할 계약을 추출해 네 분류, 수정 권한 경계, 사전 검사 제목, 개발자 대조 문언과
   네 버전 값을 단언과 대조한다.
3. 사용자 문서와 규칙 본문을 같은 항목표로 나란히 읽어 뜻이 어긋나지 않는지 확인한다.
4. 구버전 규칙을 가진 임시 프로젝트에 동기화를 실행해 네 파일 중 바뀐 셋만 새 문언으로 갱신되는지
   확인한다.
5. 앱보다 높은 버전과 관리 형식이 아닌 파일을 둔 픽스처에서 기존 충돌·보존 검사가 그대로 통과하는지
   확인한다.
6. 두 검사 파일의 변경 내역을 줄 단위로 읽어 바뀐 줄이 버전 숫자와 버전 문자열뿐인지 확인한다.
7. 두 파일의 각 버전 치환에 대해 대상 문자열이 픽스처 원문에 실제로 있는지 확인하고 치환 뒤 내용을 직접
   대조한다.
8. 저장소 루트에서 `npm run check`를 실행한다.

사용자가 어느 한쪽에 수정을 요청하면 이 작업의 착수 시점 값 전제도 다시 확인해야 한다.

문언을 근거로 삼으므로 이 작업이 먼저 온다.
