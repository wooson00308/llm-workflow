# 조건 스크립트 기획자 분기가 created_by를 두 자리에서 읽게 하고 버전을 올린다

SPEC-030의 R1·R2·R3·R5(조건 스크립트 축)를 닫는다. 기획자 분기가 결정 문서를 고를 때도, 더 늦은
결정을 찾을 때도 `created_by`를 보지 않아서 앱과 하트비트가 양방향으로 갈린다(확인 사실 4·5). 원인이
한 자리라 두 방향을 같은 변경으로 닫는다.

**승인된 확인 필요 1번이 이 작업의 범위를 정한다.** 사용자는 "반대 방향까지 이번에 닫는다"를 승인했다.
그래서 후보 선택과 비교 루프 두 자리 모두에 필터가 들어간다. 아이디어 문언(비교 루프만)보다 한 자리
넓지만, 같은 파일·같은 두 구현이라 추가 비용이 사실상 없다는 것이 기획서의 판단이다.

## 어법은 이미 이 저장소 안에 있다

새 판정을 설계하지 않는다. **아키텍트 분기가 쓰는 두 줄을 기획자 분기로 옮기는 것이 전부다**(확인
사실 2). TASK-086이 착지시킨 자리이고, 주석까지 같은 지적을 이미 적어 두었다.

- 후보 선택: `cb=$(sed -n 's/^created_by: *//p' "$d" | head -1)` 뒤에 `[ "$cb" = "user" ] || continue`.
  **값 전체를 비교한다** — 접두 일치로 두면 `user-delegate`가 통과한다. 아키텍트 분기 주석이 같은
  문장을 적고 있다.
- 비교 루프: 같은 기준으로 거른다. 앱이 세지 않는 결정을 여기서만 더 늦은 것으로 세면 두 판정이
  갈라진다.

PowerShell 쪽도 같다 — `switch -CaseSensitive`의 `'architect'` 절이 쓰는 `-cne 'user'` 비교를 같은 두
자리에 넣는다. 세 역할이 서로 다른 방식으로 같은 판정을 하지 않는 것이 R1 세 번째 항목이다.

## 앱은 고치지 않는다

`role_eligibility.rs`의 기획자 판정과 `fs_project_repository.rs`의 `read_spec_decisions`는 **이미
옳다**(확인 사실 3). 이 작업은 스크립트를 앱에 맞추는 방향이고, 앱 쪽에서 손대는 것은 모듈 머리
주석 하나와 대조 테스트뿐이다. 판정 함수 본문에 변경분이 있으면 방향을 잘못 잡은 것이다.

## 의존성

선행 선언 없음. 이 작업이 SPEC-030 파생 작업 중 먼저 온다.

TASK-098이 이 작업 뒤에 온다 — 계약 문언이 구현을 앞지르지 않아야 하기 때문이고, 파일은 겹치지
않는다. 순서의 근거는 그쪽 문서에 적었다.

## 병행 안전 확인 결과

- `heartbeat_condition.rs`를 범위에 올린 미완료 작업은 여덟이고 **전부 `qa_waiting`이다**(TASK-043·
  044·045·047·075·076·086·088). `role_eligibility.rs`도 같다(TASK-043·044·058·075·076·086·088).
  `todo`·`in_progress`인 것은 하나도 없어 지금 착수하면 겹치지 않는다.
- **다만 QA가 그중 하나를 `todo`로 되돌리면 같은 파일에 두 세션이 붙는다**(확인 사실 11). 착수 직전에
  두 파일을 범위로 삼는 `todo`·`in_progress` 작업이 생겼는지 다시 확인하고, 있으면 `blocked`으로
  두고 상신한다. 임의로 병행하지 않는다.
- 저장소 사본 `scripts/wf-eligible.sh`는 TASK-075가 이미 지웠다. `sh` 판정의 원본은
  `CONDITION_SCRIPT_SH` 하나다.
- **설치본 `.workflow/rules/wf-eligible.sh`를 손으로 고치지 않는다.** 그 파일은 앱이 설치 경로로
  덮어쓰는 산출물이고, 지금 상수(6)와 설치본(4)이 어긋나 있는 것도 앱이 다음 설치에서 따라 올리는
  종류의 차이다(확인 사실 8).

## 작업 내용

### 두 자리의 필터 (R1)

- 후보 선택에서 `created_by`가 정확히 `user`가 아닌 수정 요청 결정을 건너뛴다.
- 비교 루프에서 `created_by`가 정확히 `user`가 아닌 결정을 더 늦은 결정으로 세지 않는다.
- 두 구현을 **같은 커밋에서 함께 고친다.** 한쪽만 고치면 플랫폼마다 답이 달라진다(R2 셋째 항목).
- 아키텍트·개발자 분기는 건드리지 않는다. R5 넷째 항목이 두 역할의 판정 불변을 요구한다.

### 시나리오 표 (R2·완료 조건 3·4)

최소한 다음 두 행이 들어간다. 기획서가 실행값으로 확인한 두 픽스처다.

- **가림 방향(확인 사실 4).** `SPEC-X`에 `revision_requested`·`created_by: user`·08-01 결정 하나와
  `approved`·`created_by: user-delegate`·08-02 결정 하나. 기대: `planner` → `eligible` / 종료 코드 0.
  지금 본문은 여기서 1을 내고, 앱은 그 수정 요청을 계속 최신으로 센다.
- **헛기동 방향(확인 사실 5).** `SPEC-Y`에 `revision_requested`·`created_by: user-delegate` 결정
  하나뿐. 기대: `planner` → `no-target` / 종료 코드 1. 지금 본문은 여기서 0을 낸다.

두 번째 행이 **값 전체 비교를 고정한다**(완료 조건 3) — 접두 일치로 구현하면 `user-delegate`가
통과해 이 행이 깨진다.

**기존 픽스처 헬퍼로는 두 행을 못 세운다.** `write_decision_document`는 `outcome: approved`를 본문에
박아 두었고 `write_later_revision_request`는 `created_by: user`와 `created_at`을 박아 두었다.
`created_by`를 부르는 쪽이 정하는 수정 요청 결정 헬퍼가 하나 필요하다. **기존 헬퍼의 시그니처를
바꾸는 대신 하나를 더한다** — 기존 행들이 그대로 통과해야 한다(완료 조건 12).

사유 코드는 늘리지 않는다. `eligible`·`no-target`은 이미 어휘에 있고,
`the_scenario_table_only_expects_known_reason_codes`가 그것을 지킨다(기획서 제외 범위).

### 앱과의 대조 (R3)

`role_eligibility.rs`의 대조 단언에 같은 두 상황을 넣는다. 앱은 이 변경으로 동작이 달라지지 않으므로,
**여기서 갈리면 스크립트 쪽이 틀린 것이다.** 기존 단언은 하나도 줄지 않는다.

### 버전 축 (R5)

- `CONDITION_SCRIPT_VERSION`과 두 본문의 버전 줄을 **착수 시점 값에서 정확히 +1**로 올린다.
- **고정값을 가정하지 않는다.** 분해 시점 값은 6이지만 이 저장소는 상수(6)와 설치본(4)이 어긋나 있고
  미착지 작업이 여럿 `qa_waiting`으로 대기 중이라 착수 시점 값이 또 다를 수 있다(확인 사실 8).
  TASK-088이 같은 자리에서 세운 선례다. **착수 시점에 읽은 값을 보고서에 적고 +1을 적용한다.**
- 세 자리(상수·sh 본문·ps1 본문)가 같은 값이어야 한다. 버전 표기 테스트가 그것을 본다.

### 모듈 머리 주석 (R3 셋째 항목)

`role_eligibility.rs`의 "알려진 차이 5"는 지금 "남는 차이는 기획자 분기의 `created_by`와 두 분기가
보지 않는 `outcome` 값 목록이다"라고 적는다. 앞의 하나가 이 작업으로 없어지므로 **남은 하나만 적도록
고친다.** 이미 닫힌 차이를 계속 적어 두면 다음 사람이 같은 자리를 두 번 조사한다. 목록의 번호 매김과
머리글("아래 다섯은 남는다")이 항목 수와 어긋난 채로 남지 않게 한다.

## 검증 문구 규칙

이 저장소는 여러 세션의 미커밋 변경이 한 작업 트리에 겹쳐 있다. 그래서 **"`git diff`가 비어 있다"를
완료 조건으로 쓰면 성립하지 않는다.** 남의 세션 변경이 같은 파일에 얹혀 있어 판정이 늘 실패하거나,
반대로 자기 변경을 남의 것으로 오인해 통과시킨다. 개발자 라인에서 두 번 지적된 항목이다.

무변경은 파일·심볼 단위로 확인한다 — 어느 상수·본문·단언이 착수 시점과 같은 값인지 직접 읽어
보고서에 남긴다.

## 완료 조건

1. 기획자 분기가 `created_by`가 `user`가 아닌 결정을 후보로 고르지 않는다. 검증: 확인 사실 5의 행이
   두 구현에서 `no-target`/종료 코드 1. (SPEC-030 완료 조건 1)
2. 기획자 분기의 비교 루프가 `created_by`가 `user`가 아닌 결정을 더 늦은 결정으로 세지 않는다.
   검증: 확인 사실 4의 행이 두 구현에서 `eligible`/종료 코드 0. (완료 조건 2)
3. 값 비교가 전체 일치다. 검증: `created_by: user-delegate`가 통과하지 않는 것이 시나리오 표의 행으로
   고정되어 있다. (완료 조건 3)
4. 확인 사실 4·5의 두 상황이 표에 행으로 있고 `the_installed_script_matches_the_scenario_table`이
   통과한다. (완료 조건 4)
5. sh와 ps1이 같은 답을 낸다. 검증: 표가 CI 세 플랫폼에서 통과한다. **로컬에서 한 플랫폼만 도는
   경우 그 사실과 돌린 플랫폼을 보고서에 적는다.** (완료 조건 5, R2)
6. PowerShell 본문이 ASCII만 쓴다. 검증: `the_powershell_implementation_is_ascii`가 수정 없이
   통과한다.
7. `CONDITION_SCRIPT_VERSION`과 sh·ps1 본문의 `# condition_script_version:` 줄이 같은 값이고 착수
   시점 값 +1이다. 검증: **착수 시점 값을 보고서에 적고** 세 자리를 대조한다. (완료 조건 6)
8. `role_eligibility.rs`의 "알려진 차이 5"가 남은 차이만 적는다. 검증: 주석 본문 인용. (완료 조건 9)
9. 앱과 스크립트가 새 두 상황에서 같은 답을 낸다. 검증: `role_eligibility.rs`의 대조 단언이 줄지 않고
   새 상황에서도 통과한다. (R3 첫·둘째 항목)
10. 조건 스크립트의 설치·검증 경로가 새 버전 값으로 동작한다. 검증: `heartbeat_condition` 테스트가
    통과한다. (완료 조건 10의 조건 스크립트 절반)
11. **실저장소에서 세 역할의 판정이 변경 전후로 같다.** 검증: 착수 전과 착지 후에 `planner`·
    `architect`·`developer` 세 역할로 스크립트를 돌려 종료 코드와 사유를 보고서에 적는다. 확인 사실
    10대로 이 워크플로우의 결정은 전부 `created_by: user`라 전부 같아야 하고, **다르면 그것이
    회귀다.** (완료 조건 11)
12. 기존 시나리오 표의 모든 행이 그대로 통과하고 행이 삭제되지 않았다. 검증: 행 수 전후 비교.
    (완료 조건 12)
13. 아키텍트·개발자 분기의 판정 규칙을 고치지 않았다. 검증: 두 절의 본문이 착수 시점과 같은지 읽어
    보고서에 적는다. (R5 넷째 항목)
14. 기존 자동 테스트가 삭제되거나 비활성화되지 않았다(`#[ignore]` 신규 0건). (완료 조건 13)
15. `heartbeat_condition.rs`를 범위에 올린 작업이 이번 분해에서 이 하나뿐이다. 검증: SPEC-030 파생
    작업 둘의 범위 목록을 보고서에 적는다. (완료 조건 14)
16. `cargo test --manifest-path src-tauri/Cargo.toml`과 `npm run check`가 통과한다. **확인 사실 13의
    타 세션 위반(`heartbeat_status.rs` fmt 1건, `heartbeat_process.rs:216` clippy 1건)이 남아 있으면
    그것과 이 작업이 만든 결과를 구분해 적는다.** (완료 조건 15)

## 범위 밖

- **계약 문언의 임시 불릿 삭제와 `WORKFLOW_RULES_VERSION` 인상.** TASK-098이 한다. 이 작업에
  `project_instructions.rs` 변경분은 없다.
- 두 분기가 `outcome` 값 목록을 보지 않는 차이. 기획서 제외 범위이고, "알려진 차이 5"에 남겨 둘
  항목이 바로 그것이다. 후속 아이디어로 올린다.
- 개발자 분기. 결정 문서를 읽지 않으므로 대상이 아니다.
- 아키텍트 분기의 판정 규칙 변경. 확인 사실 2대로 이미 닫혀 있고 TASK-086이 착지시킨 자리다.
- 앱 판정(`role_eligibility.rs`의 판정 함수·`fs_project_repository.rs`)의 동작 변경. 확인 사실 3대로
  앱은 이미 옳게 거른다. 이 작업이 그 파일에서 만지는 것은 모듈 머리 주석과 테스트뿐이다.
- 이미 기록된 결정 문서의 소급 정리. 확인 사실 10대로 대상이 0건이다.
- 대리 결정의 형식 요건·재가 절차 자체. SPEC-028/TASK-088에서 착지했다.
- 조건 스크립트의 사유 출력 규약(SPEC-023). 기존 코드를 쓸 뿐 목록을 늘리지 않는다.
- 설치본 `.workflow/rules/wf-eligible.sh`의 직접 수정. 앱 설치 경로의 산출물이다.
- `created_at` 표기 규약 변경.
