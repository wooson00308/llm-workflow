# 아이디어 문서뷰에만 개행 표시를 켜고 적용 범위를 양쪽 검사로 고정한다

TASK-090이 만든 옵트인 프롭을 아이디어 문서뷰 한 곳에서만 켠다. 제품 코드 변경은 호출부 한 줄이고,
나머지는 그 결정이 코드에 남았는지를 고정하는 검사다. SPEC-027의 R1·R2·R6·R7과 완료 조건 1~13을
닫는다.

## 승인된 확인 필요 2건

DECISION-6F1B8C53은 두 항목 모두 기획서 제안대로 승인했다.

1. **아이디어 뷰에만 적용한다.** 근거는 결정 문서에 적힌 대로다 — 개발 작업 문서 73건 중 61건의 문단
   내 개행이 고정폭 랩의 부산물이라 전체 적용 시 들쭉날쭉해진다는 실측, 그리고 사람이 치는 자유
   입력과 에이전트가 쓴 Markdown 문서의 입력 성격 구분이다. **그래서 기획서 리더와 개발 작업 상세는
   이번 변경으로 달라지지 않는다.**
2. **연속 빈 줄은 문단 구분 하나로 본다.** 빈 줄 수를 보존하지 않는다. `remark-breaks`는 그 동작을
   바꾸지 않으므로 이 작업이 따로 할 일이 없다. 검사가 이 사실을 건드리지 않게만 주의한다.

## SPEC-008의 "세 뷰 동일 렌더"와의 관계 (결정 문서의 아키텍트 유의 사항)

DECISION-6F1B8C53이 이 관계를 기존 테스트 이름 처리와 함께 명시할 것을 요구했다. 판단은 셋이다.

1. **어긋나는 범위는 문단 안의 개행 하나뿐이다.** SPEC-008이 통일한 것은 전문 읽기 경로다 —
   frontmatter를 감추고, 같은 컴포넌트로 그리고, 같은 종이 모양을 쓴다. 이번 변경 뒤에도 세 화면은
   같은 컴포넌트를 부르고 같은 CSS를 쓴다. 달라지는 것은 그 컴포넌트에 넘기는 프롭 하나이고, 그
   프롭이 바꾸는 것은 소프트 개행의 렌더뿐이다. 제목·목록·표·코드·인용·링크·강조는 세 화면에서 같다.
2. **기존 테스트 이름을 고치지 않는다.** `renders markdown formatting like the other document views`
   (`IdeaInbox.test.tsx:354`)가 실제로 확인하는 것은 불릿 두 개, 링크의 `href`, 강조다. 셋 다 이번
   변경 뒤에도 세 화면에서 같으므로 그 이름이 거짓이 되지 않는다. SPEC-027 완료 조건 4가 이 파일의
   기존 테스트를 "수정 없이" 통과시킬 것을 요구하기도 하므로, 이름을 손보는 것은 그 요구와 부딪힌다.
3. **대신 예외를 새 검사의 이름으로 남긴다.** 아이디어 쪽 검사 이름이 "이 화면은 사용자가 친 줄을
   지킨다"를, 개발 작업 상세 쪽 검사 이름이 "저 화면은 지키지 않는다"를 말하게 쓴다. 나란히 놓인 두
   이름이 이 예외의 문서다. 권하는 이름은 아래 작업 내용에 적었다.

## 작업 내용

### 호출부

- `IdeaInbox.tsx`의 `<MarkdownBody body={body.body} />`에 `preserveLineBreaks`를 더한다. **이 한 줄이
  이 작업의 제품 코드 변경 전부다.**
- `SpecWorkspace.tsx:144`와 `DevelopmentBoard.tsx:274`는 건드리지 않는다. 승인된 확인 필요 1번이
  그렇게 정했고, R6 첫째 항목이 두 화면의 무변경을 요구한다.

### 아이디어 쪽 검사 (`IdeaInbox.test.tsx`)

- 본문 상수를 새로 만든다. 기획서 확인 사실 10대로 저장소의 아이디어 26건에는 재현 형태가 없다.
  이 저장소 아이디어의 실제 형식을 따라 배경·원인·방향을 개행 한 번씩으로 나눈 세 줄 + 빈 줄 +
  한 문단으로 쓴다. 한 상수로 R1과 R2를 함께 본다.
- `documentFor(firstIdea, body)`와 `onReadIdea` 목을 쓰는 기존 어법(`:272`~`:291`)을 그대로 따른다.
- 단언 둘을 한 검사에 담는다.
  - 미리보기 본문의 `<p>`가 둘이고, 앞 문단에 `<br>`가 둘이다. 세 줄 텍스트가 모두 그 문단 안에
    있다. (R1 / 완료 조건 1·2)
  - 뒤 문단이 별개의 `<p>`로 남는다. (R2 / 완료 조건 3의 자동 검증 몫)
- **단언 방법 주의.** `<br>`가 들어가면 `getByText("첫 줄")`이 맞지 않는다. `textContent`가 이어 붙기
  때문이다. `container.querySelectorAll(".markdown-body p")`·`querySelectorAll("br")`로 구조를 세고
  텍스트는 `toHaveTextContent`로 확인한다.
- 권하는 이름: `keeps the line breaks the user typed in the idea body`.

### 개발 작업 상세 쪽 검사 (`DevelopmentBoard.test.tsx`)

- 같은 성격의 본문(개행 한 번으로 나눈 두 줄)을 작업 상세에서 열고, `<br>`가 하나도 없으며 그 두 줄이
  `<p>` 하나 안에 있는 것을 확인한다. (R7 셋째 항목 / 완료 조건 10)
- 본문을 넘기는 방법은 `dependencyReader`(`:61`~`:69`)의 어법을 따라
  `vi.fn().mockResolvedValue({ summary, body })` 목을 그 검사 안에 둔다. `taskReader`(`:55`~`:60`)는
  본문을 제목·요약에서 조립하므로 이 검사에 맞지 않는다. **기존 헬퍼 둘을 고치지 않는다.**
- **이 검사는 TASK-090 이전 트리에서도 통과한다.** 지금은 아무도 켜지 않았기 때문이다. 그래도 남기는
  이유는 이 검사가 막는 것이 지금의 결함이 아니라 "적용 범위 결정이 나중에 조용히 넓어지는 일"이기
  때문이다. **그 사실을 검사 위 주석 한 줄로 적는다.** 승인된 확인 필요 1번을 근거로 인용한다.
- **빨간불이 되는지 확인한다.** `DevelopmentBoard.tsx`의 `MarkdownBody` 호출에 `preserveLineBreaks`를
  임시로 넣어 이 검사가 실패하는 것을 본 뒤 되돌린다. 절차와 실패 메시지를 보고서에 적는다.
  TASK-089가 CSS 검사에 쓴 것과 같은 절차다.
- 권하는 이름: `leaves a soft line break unbroken in the task detail`.
