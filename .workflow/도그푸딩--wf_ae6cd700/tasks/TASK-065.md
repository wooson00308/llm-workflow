# 저장 확인 화면 세 문장이 다른 프로젝트의 잡 보장을 밝힌다

SPEC-022 R3을 닫는다. 확인 사실 9가 짚은 대로 지금 문구는 블록 밖만 약속하거나(설치 화면) 사실과
다른 약속을 하고 있다(재설정 화면). 사고는 그 문장을 믿고 저장한 결과였다. TASK-064가 동작을
고친 뒤에도 무엇이 보장되는지 화면에서 읽을 수 없으면 같은 사용자가 같은 자리에서 다시 망설인다.

## 확인 필요 3번의 승인된 결론

DECISION-7A3E5B90이 "확인 사실 9의 세 문장에 다른 프로젝트 잡 보장을 명시한다"를 승인했다. 근거는
동작만 고치고 문구를 두면 그 보장이 어디서 오는지 화면에 남지 않는다는 것이다. 파일 소개 문구
("이 컴퓨터의 모든 프로젝트가 함께 씁니다")는 그대로 둔다.

## 의존성

- **선행 필수: TASK-064.** 이 작업이 넣는 문장은 "다른 프로젝트의 잡도 그대로 둡니다"라는 보장이다.
  보존 구현보다 먼저 들어가면 화면이 지금보다 더 강한 거짓을 말한다. 이 기획서의 출발점이 화면의
  거짓 약속을 믿고 데이터를 잃은 사고였으므로, 문구가 동작을 앞지르는 창을 만들지 않는다.
- **선행 필수: TASK-062.** 파일이 겹친다. TASK-062(SPEC-019)가 같은 `HeartbeatCard.tsx`의
  `HeartbeatSetupWizard` 접힘 상태를 고치는 중이다(작성 시점 `in_progress`). 고치는 구간은 서로
  멀지만(그쪽은 마법사 `open` 초기화, 이쪽은 확인 화면 문구) 한 파일이므로 순서를 정한다. 이
  작업이 TASK-064를 기다리는 동안 TASK-062는 끝나 있을 가능성이 높아 실질 비용은 거의 없다.

## 범위

- `src/features/projects/components/integrations/HeartbeatCard.tsx` — 문장 둘.
  - `:1037` 역할 잡 기본값 재설정 확인 화면.
  - `:1110` 역할 잡 설치 확인 화면.
- `src/features/projects/components/integrations/DreamCard.tsx` — 문장 하나.
  - `:835` dream 잡 설치 확인 화면.
- 위 문장을 검사하는 기존 테스트의 단언 문자열.
  - `src/features/projects/components/integrations/IntegrationsView.test.tsx:840`
  - `src/features/projects/components/integrations/DreamCard.test.tsx:318`
- 그 외 파일은 건드리지 않는다. Rust 쪽은 무변경이다.

**줄 번호는 작업 트리 기준이다.** SPEC-022 본문의 `HeartbeatCard.tsx:1021`·`:1094`는 기획서 작성
시점 값이고, 지금 같은 문장은 `:1037`·`:1110`에 있다. TASK-062가 이 파일을 고치면 다시 밀린다.
줄 번호가 아니라 문장 원문으로 찾는다.

## 작업 내용

- 세 문장에 다른 프로젝트의 잡도 그대로 남는다는 보장을 더한다. 지금 문장을 지우지 말고 보장을
  넓히는 방향으로 고친다. 세 화면의 지금 문장은 이렇다.
  - 역할 재설정(`HeartbeatCard.tsx:1037`): "이 잡의 편집 가능 값만 앱 기본값으로 되돌립니다. 잡의
    활성·비활성 상태와 같은 블록의 다른 잡은 그대로 둡니다."
  - 역할 설치(`HeartbeatCard.tsx:1110`): "앱 관리 블록만 다시 씁니다. 블록 밖의 잡과 전역 설정은
    읽기만 하고 그대로 둡니다."
  - dream 설치(`DreamCard.tsx:835`): "앱 관리 블록만 다시 씁니다. 블록 밖의 잡과 전역 설정은
    읽기만 하고 그대로 둡니다. 같은 블록의 역할 잡도 값 그대로 남습니다."
- 보장의 내용은 TASK-064가 실제로 구현한 것과 같은 말이어야 한다. 즉 "다른 프로젝트의 잡은 블록
  안에 있어도 값 그대로 남는다"까지다. 앱이 남의 잡을 보여주거나 관리한다는 인상을 주지 않는다.
- 파일 소개 문구는 손대지 않는다: `HeartbeatCard.tsx:1034`·`:1107`, `DreamCard.tsx:763`·`:833`의
  "전역 파일입니다. 이 컴퓨터의 모든 프로젝트가 함께 씁니다."
- 기존 테스트의 단언 문자열을 새 문구에 맞춘다. 단언을 지우지 말고 문자열만 고친다. 테스트 이름과
  나머지 본문은 그대로 둔다.
- 마크업 구조를 바꾸지 않는다. `aria-label`, `role="group"`, `<JobChanges>`의 자리와
  `removed`/`written` 인자를 건드리지 않는다.

## 완료 조건 6의 검증 (보고서 항목)

SPEC-022 완료 조건 6은 코드 변경이 아니라 대조와 기록이다. 이 작업의 보고서에서 닫는다.

- 확인 화면의 "지워짐" 목록은 `removedJobs`이고, 그 근거 값은 스냅샷의 `heartbeat.managedJobs`다
  (`HeartbeatCard.tsx:668`~`:676`). 그 값은 자기 slug의 잡만 담는다(확인 사실 3·8).
- TASK-064가 든 뒤에는 남의 잡이 저장으로 지워지지 않으므로, "목록에 없는데 지워지는 잡"이
  사라진다. TASK-064의 완료 조건 1~3 테스트 결과와 이 목록의 근거 값이 같은 범위를 가리키는지
  확인하고 `reports/REPORT-TASK-065-DEV.md`에 적는다.
- 대조 결과가 어긋나면(예: 여전히 목록 밖에서 지워지는 잡이 있으면) 문구를 고치지 말고 `blocked`로
  두고 보고한다. 화면이 지키지 못할 약속을 새로 적는 일이기 때문이다.

## 완료 조건

1. 위 세 문장이 다른 프로젝트의 잡도 그대로 남는다는 보장을 밝힌다. (SPEC-022 완료 조건 7, R3)
2. 세 문장이 TASK-064가 구현한 보장과 같은 말을 한다. 더 넓은 약속을 하지 않는다.
3. 파일 소개 문구 네 곳이 그대로다.
4. 완료 조건 6의 대조 결과가 보고서에 있다. (완료 조건 6)
5. 문구를 검사하는 기존 테스트 둘이 새 문자열로 통과한다. 테스트 이름과 나머지 본문은 그대로다.
6. 삭제되거나 비활성화된 테스트가 없다. (완료 조건 11)
7. `npm run check`가 통과한다. (완료 조건 13)
8. Rust 쪽에 변경분이 없다. `git diff -- src-tauri/`로 확인해 보고서에 적는다.

## 범위 밖

- 동작 변경. 보존은 TASK-064가 끝냈다. 이 작업은 화면 문장만 고친다.
- **dream 잡 기본값 재설정 확인 화면(`DreamCard.tsx:765`)의 문장.** 확인 사실 9가 이름을 올린 것은
  세 문장이고 결정도 "세 문장"을 승인했다. 다만 이 네 번째 화면의 "잡의 활성·비활성 상태와 같은
  블록의 역할 잡은 그대로 둡니다"는 같은 모양의 약속이라, 세 문장만 고치면 네 화면의 말이 서로
  어긋난다. **결정 범위를 넘겨 짚지 말고 보고서에 후속 항목으로 올린다.** 이 문장을 검사하는
  테스트는 `DreamCard.test.tsx:521`이다.
- `removedJobs`의 계산 범위를 남의 잡까지 넓히는 일. 앱은 남의 잡을 조회에서부터 걸러 내고
  (확인 사실 10), 보여주는 것은 이번 기획서의 제외 범위다.
- 설치 마법사·접힘·단계 판정(SPEC-016·SPEC-019의 몫).
- 문구의 다국어 처리나 문안 전반의 재작성.
