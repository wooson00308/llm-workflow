# 잡 단위 기본값 재설정을 저장과 분리된 명시적 액션으로 제공

SPEC-005 R5를 구현한다. 편집 가능 값을 앱 기본값으로 되돌리는 액션을 저장과 분리해 제공한다.

되돌리는 것이 정당한 경우가 있다. 사용자가 값을 망쳐 놓고 처음부터 다시 시작하고 싶을 때다. 그것을
저장의 부작용으로 두면 정당한 요구와 사고를 구별할 수 없다. 명시적 액션으로 두면 둘 다 표현할 수 있다.

지금 그 결과를 얻는 유일한 경로는 잡을 껐다 켜는 것이고, 그 경로는 잡을 블록에서 뺐다가 다시 넣는다.

## 의존성

- **선행 필수: TASK-014.** 재설정은 그 잡의 세 필드만 명시값으로 보내고 나머지 잡은 미지정으로 두는
  쓰기다. TASK-014의 요청 계약이 없으면 나머지 잡의 값을 화면이 다시 실어 보내야 하고, 그것이 이
  기획서가 없애려는 패턴이다.
- **선행 필수: TASK-016.** 실행 전 확인 화면은 R4와 같은 화면 규약을 따른다. 차이 표시 요소를
  재사용한다.
- **선행 필수: TASK-017.** 재설정도 쓰기이므로 기준값을 함께 보낸다. 화면이 읽은 뒤 파일이 바뀌었다면
  재설정도 그대로 덮어쓰면 안 된다.
- 선행 권장: TASK-015. 관리 블록을 못 읽은 상태에서는 되돌릴 현재 값이 없다.
- SPEC-005의 마지막 작업이다. 이 작업이 끝나면 기획서 완료 조건 17개가 모두 덮인다.

## 범위

- `src-tauri/src/application/heartbeat_service.rs` — 잡별 앱 기본값을 스냅샷에 담는다.
- `src/features/projects/domain/types.ts` — 위 값의 프론트 짝.
- `src/features/projects/components/integrations/HeartbeatCard.tsx`,
  `src/features/projects/components/integrations/DreamCard.tsx` — 재설정 액션과 확인 화면.
- `src/features/projects/components/SettingsView.test.tsx`,
  `src/features/projects/components/integrations/DreamCard.test.tsx`.
- 스타일이 필요하면 기존 확인 화면·버튼 클래스가 있는 스타일시트에만 더한다.
- 그 외 파일은 건드리지 않는다. 특히 새 Tauri 커맨드를 만들지 않는다.

## 작업 내용

### 0. 먼저 읽을 제약

- 재설정은 편집 가능 값(`interval`·`maxPer`·`model`)만 되돌린다. 잡의 활성·비활성 상태를 바꾸지
  않는다(R5).
- 앱 소유 필드는 어차피 매 쓰기마다 앱 값으로 다시 만들어진다. 재설정이 그 동작을 바꾸지 않는다.
- 이 액션도 쓰기다. SPEC-002 R6의 전역 파일 쓰기 규약을 그대로 따른다. 명시적 사용자 액션에서만
  호출하고, 확인 화면을 거치고, 저장은 원자적이다.
- 저장 액션의 문구와 위치를 바꾸지 않는다. 기존 테스트가 그 버튼 문구로 저장을 찾는다.
- 새 커맨드를 만들지 않는다. TASK-014의 요청 계약이 이 액션을 그대로 표현한다.

### 1. 기본값의 출처를 하나로 만든다 (R5)

- 지금 앱 기본값은 백엔드(`heartbeat_roles.rs:42`의 `default_settings`,
  `heartbeat_dream::default_settings`)와 프론트(`HeartbeatCard.tsx:46`의 `roleJobDefaults`,
  `DreamCard.tsx:44`의 `jobDefaults`) 양쪽에 상수로 있다. 주석이 "백엔드 기본값과 같다"고 말할 뿐이고
  구조가 보장하지 않는다.
- 재설정은 그 값을 사용자에게 보여주고 파일에 쓴다. 두 정의가 갈라지면 "기본값으로 되돌렸는데 미설치
  상태에서 시작하는 값과 다르다"가 된다. 그래서 백엔드 기본값을 스냅샷에 담아 내려보내고, 프론트의 두
  상수를 그 값으로 대체한다.
- 역할별로 값이 다르므로 역할 잡은 역할마다 필요하다. 스냅샷에 이미 역할별 목록
  (`heartbeat.roles`)이 있으므로 그 항목에 얹는다. dream은 연동 payload에 하나 얹는다.
- 첫 설치 시딩(`roleFormFrom`, `formFrom`)도 같은 값을 쓰게 된다. 시딩 값과 재설정 값이 구조적으로
  같아야 한다.

### 2. 재설정 액션 (R5)

- 잡마다 하나씩 둔다. 기획서 확인 필요 2번이 잡 단위로 승인됐다. 연동 전체를 한 번에 되돌리는 액션은
  만들지 않는다.
- 저장 액션과 문구·위치에서 구분되어야 한다. 저장의 부작용으로 일어나서는 안 된다.
- 잡 칸 안에서는 실행 기록 아래, 칸의 맨 마지막에 둔다. 편집 필드와 실행 기록을 먼저 읽고 나서
  닿는 위치이고, 되돌리기는 편집 흐름의 주 경로가 아니다. 역할 잡 카드와 dream 카드가 같은 배치와
  같은 크기를 쓴다.
- 관리 블록에 없는 잡에는 재설정 액션을 보여주지 않는다. 되돌릴 파일 값이 없고, 그 잡의 폼은 이미
  기본값에서 시작한다.
- 누르면 확인 화면이 열린다. 그 잡의 현재 파일 값과 기본값의 차이를 TASK-016의 표시 요소로 보여준다.
  달라지는 것이 없으면 그 사실을 밝힌다.
- 확인하면 요청을 보낸다. 대상 잡의 세 필드는 기본값을 명시값으로 싣고, 같은 요청의 다른 잡은 세
  필드를 모두 미지정으로 둔다. 그래야 다른 잡의 편집값이 그대로 남는다.
- `enabled`는 파일 기준으로 보낸다. 폼의 토글 상태가 아니다. 사용자가 토글을 바꿔 둔 상태에서
  재설정을 눌러도 잡의 존재 여부가 바뀌면 안 된다(완료 조건 12).
- 기준값(TASK-017)은 저장과 같은 값을 함께 보낸다.
- 성공하면 스냅샷이 갱신되고 폼이 재시딩된다. 재설정 후에는 사용자 편집이 없는 상태이므로 조용히
  재시딩되는 현행 경로가 그대로 맞다.

### 3. 테스트

- 편집값이 있는 잡에 재설정 액션이 보이고, 관리 블록에 없는 잡에는 보이지 않는다.
- 재설정 액션은 확인 화면을 거치기 전에 설치 함수를 부르지 않는다.
- 확인 화면에 현재 파일 값과 기본값의 차이가 보인다.
- 확인하면 대상 잡의 세 필드가 기본값 명시값으로, 다른 잡의 세 필드가 미지정으로 실린다.
- 일부 역할이 꺼져 있는 상태에서 재설정해도 요청의 `enabled`가 파일 기준 그대로다. 폼에서 토글을
  바꿔 둔 상태에서도 마찬가지다.
- 이미 기본값인 잡에서 재설정을 열면 달라지는 것이 없다는 사실이 표시된다.
- 저장 액션의 문구·동작이 그대로다(회귀).
- dream 잡에 대해 위와 같은 테스트를 만든다.
- 백엔드: 스냅샷의 역할별·dream 기본값이 `default_settings`와 같다.

## 완료 조건

1. 기본값으로 재설정 액션이 저장 액션과 구분되어 존재하고, 실행 전에 현재 값과 기본값의 차이를
   보여준다. (기획서 완료 조건 11)
2. 재설정은 편집 가능 값만 되돌리고 잡의 활성·비활성 상태를 바꾸지 않는다. 일부 역할이 꺼진 상태에서
   실행해도 관리 블록의 잡 목록이 그대로다. (기획서 완료 조건 12)
3. 재설정이 대상 잡 하나에만 적용되고, 같은 블록의 다른 잡 편집값이 그대로 남는다. (R5)
4. 앱 기본값이 앱 안 한 곳에서 나오고, 화면이 보여주는 기본값과 파일에 쓰이는 기본값이 같다. (R5)
5. 재설정도 확인 화면을 거치고, 확인 전에는 아무 파일도 쓰이지 않는다. (SPEC-002 R6)
6. 재설정 시점에 관리 블록이 화면이 읽은 값과 다르면 그대로 덮어쓰지 않는다. (R3과 같은 규칙)
7. 하트비트 카드와 dream 카드에 같은 규칙으로 존재한다. 두 카드 각각에 대한 테스트가 있고 통과한다.
8. 같은 상태로 다시 저장하면 파일이 변하지 않는다. (기획서 완료 조건 13)
9. 앱 시작·프로젝트 열기·자동 새로고침·연동 화면 진입만으로는 `~/.claude/HEARTBEAT.md`가 변경되지
   않는다. (기획서 완료 조건 15)
10. SPEC-002·SPEC-003·SPEC-004의 완료 조건에 대응하는 기존 자동화 테스트가 모두 통과하고, 삭제되거나
    비활성화된 케이스가 없다. (기획서 완료 조건 16)
11. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다.
    (기획서 완료 조건 17)

## 범위 밖

- 연동 전체를 한 번에 되돌리는 액션. 기획서 확인 필요 2번이 잡 단위로 승인됐다. 전체 재설정은 잡 단위
  재설정을 반복하면 얻을 수 있고, 전체 단위만 제공하면 잡 하나를 되돌리려는 사용자가 나머지 잡의
  값까지 잃는다.
- 꺼진 잡의 편집값을 기억했다가 다시 켤 때 복원하는 것. 기획서 확인 필요 1번이 제외로 승인됐다.
- 재설정 이력 저장이나 되돌리기(undo). 기획서 제외 범위다.
- 앱 소유 필드를 사용자 값으로 되돌리는 것. 앱 소유 필드에는 사용자 값이라는 개념이 없다.
- 잡을 관리 블록에서 제거하는 것. 그것은 토글이 하는 일이고 재설정과 다른 액션이다.
- 기본값 자체를 사용자가 바꾸는 기능. 요구되지 않았다.

## 참고 사실

확인 시점 2026-08-02. 추정 없이 실측한 값이다.

- 백엔드 기본값: 역할은 `heartbeat_roles.rs:42`의 `default_settings`이고 개발자만
  `20m`·`6/24h`·`opus`, 나머지는 `30m`·`4/24h`·`opus`다. dream은 `heartbeat_dream::default_settings`
  (`2h`·`6/24h`·`opus`)다.
- 프론트 기본값: `HeartbeatCard.tsx:46`의 `roleJobDefaults`와 `DreamCard.tsx:44`의 `jobDefaults`.
  현재 값은 백엔드와 같다.
- 스냅샷의 역할별 목록은 `heartbeat.roles`이고, 백엔드 타입은 `HeartbeatRoleStatus`
  (`role`, `jobName`, `lastRun`)다. dream payload는 `heartbeat_service.rs:50`의 `DreamIntegration`이다.
- 지금 기본값으로 돌아가는 유일한 경로는 토글을 껐다 켜는 것이고, 화면이 그 사실을 안내한다:
  "끄면 편집한 값도 함께 사라지고, 다시 켜면 기본값으로 시작합니다"(`HeartbeatCard.tsx:326`).
  그 경로는 잡을 블록에서 뺐다가 다시 넣으므로 잡의 존재 여부를 바꾼다. 재설정과 다르다.
- 저장 버튼 문구는 상태에 따라 갈린다: "이 프로젝트에 역할 잡 설치" / "역할 잡 변경 사항 저장"
  (`HeartbeatCard.tsx:351`), dream도 같은 형태다(`DreamCard.tsx:341`). 기존 테스트가 이 문구로
  저장 버튼을 찾는다.
- 실제 `~/.claude/HEARTBEAT.md`의 역할 잡 `max_per`는 `8/24h`·`8/24h`·`16/24h`로 세 값 모두 앱
  기본값과 다르다. 이 검증 절차는 그 값을 실제로 지웠다가 되돌리므로 원복을 빠뜨리면 이 저장소의
  하트비트 구성이 망가진다.
