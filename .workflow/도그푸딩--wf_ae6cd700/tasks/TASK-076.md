# 조건 스크립트가 판정 사유를 ASCII 코드로 표준 출력 첫 줄에 낸다

SPEC-023 R4와 R6을 닫는다. 지금 조건 스크립트는 판정 결과를 종료 코드로만 전달하고 표준 출력에
사유를 내지 않는다(확인 사실 15). 하트비트 데몬이 condition의 stdout 첫 줄(최대 200자)을
`state.json`의 `last_condition_output`으로 옮겨 주는 통로를 열어 두었으므로(확인 사실 16), 이 통로에
사유를 실어 보내는 것이 이 저장소의 몫이다.

TASK-077이 그 값을 화면에 옮긴다. 이 작업은 값을 만드는 쪽이다.

## 승인된 확인 필요 3번

DECISION-9E5D2C71이 "스크립트는 기계가 읽을 수 있는 ASCII 사유 코드를 내고, 앱이 그것을 사용자용
한국어 문장으로 옮긴다. 모르는 코드가 오면 받은 문자열을 그대로 보여준다"를 승인했다.

근거 둘이 이 작업의 제약이다. 첫째, PowerShell 본문은 ASCII만 쓸 수 있다. 설치가 BOM 없는 UTF-8로
쓰는데 Windows PowerShell 5.1이 그런 `.ps1`을 시스템 코드페이지로 읽기 때문이고, 그것을 고정한
테스트가 `the_powershell_implementation_is_ascii`(`heartbeat_condition.rs:768`)다(확인 사실 22).
한국어 문장을 본문에 넣을 수 없다. 둘째, 문장이 앱에 있으면 두 스크립트 본문이 같은 문장을 각각
관리하지 않아도 된다.

`state.json`을 직접 읽는 다른 도구에게는 문장이 아니라 코드가 보인다는 비용은 승인 시 인지됐다.

## 의존성

- **선행 필수: TASK-075.** 이유가 둘이다. 첫째, 같은 파일(`heartbeat_condition.rs`)을 고친다.
  둘째, TASK-075가 저장소 사본과 그 대조 테스트를 없앤 뒤라야 이 작업이 본문 하나만 고치면 된다.
  순서가 뒤집히면 `the_repository_copy_matches_the_managed_script`(`:593`) 때문에
  `scripts/wf-eligible.sh`까지 같은 사유 출력으로 고쳐야 하고, TASK-075가 그 파일을 곧바로 지운다.

## 범위

- `src-tauri/src/infrastructure/heartbeat_condition.rs`
  - `CONDITION_SCRIPT_SH`(`:26`) — `sh` 본문에 사유 출력 추가.
  - `CONDITION_SCRIPT_PS1`(`:209`) — PowerShell 본문에 같은 코드 출력 추가. ASCII만.
  - `CONDITION_SCRIPT_VERSION`(`:20`) — 4에서 5로 올린다(확인 사실 25).
  - `mod tests`(`:531`) — 시나리오 표와 일치 테스트 갱신. 아래 순서를 지킨다.
- `src-tauri/src/infrastructure/role_eligibility.rs` — **판정 규칙은 고치지 않는다.**
  `mod tests`(`:127`)의 대조 헬퍼가 종료 코드만 보므로 원칙적으로 무변경이다. 헬퍼 시그니처가
  바뀌어야 하면 그 이유를 보고서에 적는다.
- 그 외 파일은 건드리지 않는다. 화면·도메인·타입은 TASK-077이다.

## 시나리오 표와 일치 테스트 갱신 순서

DECISION-9E5D2C71의 아키텍트 유의 사항 2번이 명시를 요구한 항목이다. TASK-043이 고정한 자산 둘이
본문 변경과 함께 갱신돼야 한다: SPEC-015 R3 시나리오 표(`heartbeat_condition.rs:1253`~)와
`the_installed_script_matches_the_scenario_table`(`:1440`), 그리고 두 본문의 인터페이스 테스트
`both_implementations_carry_the_same_interface`(`:774`).

**순서는 아래 다섯 단계다. 본문을 먼저 고치지 않는다.**

1. **실행 헬퍼가 표준 출력을 함께 돌려주게 한다.** 지금 `run_condition`은 종료 코드(`i32`) 하나만
   준다(`:1447` 사용부). 종료 코드와 첫 줄을 함께 주는 형태로 넓힌다. 플랫폼 분기
   (`:511`~`:516`, 윈도우는 PowerShell, 그 외는 `sh`)는 그대로 쓴다.
2. **시나리오 표에 기대 사유 열을 더한다.** `Scenario` 구조체(`:1261`~`:1266`)에 필드를 하나 늘리고
   기존 행 전부를 채운다. **`expected`(종료 코드) 열의 값은 한 행도 바꾸지 않는다** — 사유 출력이
   판정을 바꾸지 않는다는 것이 R4이자 완료 조건 7이고, 이 열이 그 증거다.
3. **두 본문에 사유 출력을 넣는다.** `sh`와 PowerShell을 같은 커밋 안에서 함께 고친다. 한쪽만 고치면
   같은 표가 플랫폼마다 다른 답을 낸다.
4. **`CONDITION_SCRIPT_VERSION`을 5로 올린다.** 본문이 바뀌었으므로 이 값을 올려야 설치본이
   갱신된다(확인 사실 25). 버전 표기를 검사하는 기존 테스트(`:753`~`:754`)가 두 본문 모두에서
   통과해야 한다.
5. **사유 코드가 두 본문에서 갈라지는 것을 잡는 장치를 만든다.** 지금
   `both_implementations_carry_the_same_interface`(`:774`)는 세 역할 이름·`migration.lock`·
   `usage: wf-eligible`이 본문에 들어 있는지만 보는 문자열 포함 검사다(확인 사실 23). 사유 코드
   목록이 두 본문에서 같은지를 이 수준으로는 보장하지 못한다. R6이 "필요하면 함께 만든다"라고 한
   장치가 이것이다. 1~2단계에서 표가 사유까지 대조하게 되면 CI의 세 플랫폼 매트릭스
   (`.github/workflows/ci.yml:31`)가 실행 결과로 일치를 검사하므로, 그 위에 무엇을 더 둘지는
   구현이 판단해 보고서에 적는다.

## 작업 내용

- 사유는 **표준 출력 첫 줄 한 줄**이고 200자를 넘지 않는다(확인 사실 16의 계약).
- 사유는 ASCII 코드다. 사람이 읽는 문장으로 만들지 않는다. 코드 어휘는 이 작업이 정하고, TASK-077이
  그 목록을 받아 한국어 문장으로 옮긴다. **정한 코드 목록을 보고서에 그대로 나열한다** — TASK-077의
  입력이다.
- 최소한 다음 셋이 구분돼야 한다(R4).
  - 처리할 대상이 없음
  - `migration.lock`으로 판정 자체를 중단함(`scripts/wf-eligible.sh:9`에 있던 그 분기. TASK-075
    이후에는 설치본과 내장 본문에서 같은 자리를 본다)
  - 사용법 오류
  대상이 있어 깨우는 경우에도 사유를 낼지는 구현 판단이다. 낸다면 그 코드도 목록에 넣는다.
- **종료 코드 계약을 바꾸지 않는다**(R4, 완료 조건 7). 사유는 덧붙는 정보이고 판정이 아니다.
- **기존 표준 출력 사용과 충돌하지 않게 한다.** `deps_of`의 의존성 목록이 표준 출력으로 나가고
  호출자가 명령 치환으로 받아 간다(확인 사실 15, `scripts/wf-eligible.sh:49` 기준). 사유를 아무
  자리에나 찍으면 그 값이 오염된다. 사유가 첫 줄이어야 한다는 계약과 이 내부 사용이 어떻게
  공존하는지를 구현이 정하고 근거를 보고서에 적는다.
- 사용법 오류는 지금 표준 오류로 나간다(`:164` 기준). 이 경로도 사유를 내야 하므로 표준 출력에
  코드를 함께 낼지, 기존 표준 오류 문구를 옮길지 정한다. 사용자에게 보이던 사용법 문구를 없애지
  않는다.
- PowerShell 본문은 ASCII만 쓴다. 코드 어휘를 정할 때 이 제약을 먼저 만족시킨다.

## 완료 조건

1. 설치되는 조건 스크립트가 판정 결과와 함께 사유 한 줄을 표준 출력에 낸다. 검증: 세 역할과 잘못된
   인자로 실행해 첫 줄과 종료 코드를 함께 확인하는 Rust 테스트. (SPEC-023 완료 조건 6)
2. 사유 출력이 종료 코드를 바꾸지 않는다. 검증: 시나리오 표의 `expected` 열이 한 행도 바뀌지 않았음을
   `git diff`로 보이고, `the_installed_script_matches_the_scenario_table`이 통과한다. (완료 조건 7)
3. 사유가 한 줄이고 200자를 넘지 않는다. 검증: 완료 조건 1의 테스트에서 함께 단언한다. (완료 조건 8)
4. PowerShell 본문이 ASCII만 쓴다. 검증: `the_powershell_implementation_is_ascii`(`:768`)가 수정
   없이 통과한다. (완료 조건 10)
5. `CONDITION_SCRIPT_VERSION`이 5다. 검증: 변경분 확인. 버전 표기 테스트(`:753`~`:754`)가 두 본문
   모두에서 통과한다. (완료 조건 15)
6. 앱의 판정 결과와 설치 스크립트 종료 코드를 대조하는 테스트가 유지된다.
   `assert_matches_condition_script` 사용 단언이 36곳에서 줄지 않는다. (완료 조건 13)
7. 자격 판정 결과가 이전과 같다. 검증: 변경 전후로 세 역할의 종료 코드를 비교해 보고서에 적는다.
   (완료 조건 14, R7)
8. `pending_work` 표시가 달라지지 않는다. 검증: `role_eligibility.rs`의 대조 테스트가 통과한다. (R7)
9. 설치 동작이 달라지지 않는다. 관리 표기 없는 파일을 덮어쓰지 않고 상위 버전을 낮추지 않는다.
   검증: 기존 설치 테스트가 수정 없이 통과한다. (R7, 확인 사실 25)
10. 사유 코드 목록이 보고서에 나열돼 있다. TASK-077의 입력이다.
11. 시나리오 표가 사유까지 대조하고, 두 본문의 사유 일치를 무엇이 보장하는지가 보고서에 적혀 있다.
    (R6)
12. 기존 자동 테스트가 삭제되거나 비활성화되지 않았다. (완료 조건 16)
13. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다. (완료 조건 17)

## 범위 밖

- 화면의 사유 표시와 코드→문장 변환. TASK-077이 한다. 이 작업에 프런트엔드 변경분은 없다.
- 저장소 사본 정리와 문서 수정. TASK-075가 끝냈다.
- 자격 판정 규칙의 변경. 어떤 역할이 언제 깨어나는지는 달라지지 않는다(R7). 사유는 이미 내려진
  판정을 설명할 뿐이다.
- 확인 사실 10이 열거한 이식본과 스크립트 사이의 의도된 차이 다섯의 해소.
- `role_eligibility.rs`가 사유를 만들게 하는 일. 이식본은 앱이 화면을 그릴 때 쓰는 판정이고, 사유
  통로는 데몬이 스크립트를 돌린 결과다. 서로 다른 경로다.
- dream 잡의 사유 생성. 그 조건은 `dream-prep check-unprocessed`이고 도구 소스가 이 저장소 밖이다
  (확인 사실 24).
- 하트비트 데몬 쪽 변경. 확인 사실 20의 `quota_skipped` 낡은 사유 문제는 데몬 결함이고 TL이 데몬
  백로그에 등록했다. 이 저장소는 TASK-077의 R3 우회로 대응한다.
- 잡의 `condition` 문자열 형태 변경(확인 사실 26).
