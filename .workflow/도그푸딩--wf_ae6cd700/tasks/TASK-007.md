# 역할 잡 설치·토글·편집 액션과 전역 파일 쓰기 확인 절차 구현

SPEC-002의 R2 설치 액션, R5 관리 UI, R6 쓰기 안전을 구현한다. TASK-003·TASK-004가 만든 쓰기 엔진을 사용자 액션에 연결하는 마지막 작업이다.

## 의존성

- TASK-003, TASK-004, TASK-006 모두 선행 필수.
  - TASK-003: 조건 스크립트 설치 모듈
  - TASK-004: 관리 블록 쓰기 엔진
  - TASK-006: 커맨드 계층·게이트웨이·연동 카드 구조
- TASK-005는 TASK-006을 통해 간접적으로 필요하다.
- TASK-006과 같은 파일을 여럿 수정하므로 **병렬로 진행하지 않는다.**

## 범위

- `src-tauri/src/commands/heartbeat.rs`, `src-tauri/src/application/heartbeat_service.rs`에 쓰기 경로 추가.
- `src-tauri/src/lib.rs`에 쓰기 커맨드 등록.
- 프론트엔드: `types.ts`, `tauriProjectGateway.ts`, `useProjectWorkspace.ts`, `SettingsView.tsx`, `WorkspaceShell.tsx`(props 전달), `SettingsView.test.tsx`, `App.css`.

## 작업 내용

### 1. 쓰기 커맨드 (R2, R4, R6)

- 커맨드는 하나로 둔다. "역할별 활성 여부와 설정"을 받아 아래를 순서대로 수행한다.
  1. 플랫폼 검사. Windows이면 아무것도 하지 않고 거부한다.
  2. 입력값 검증. `interval`·`max_per`·`model` 형식이 어긋나면 아무것도 쓰지 않고 거부한다(TASK-004의 검증).
  3. 조건 스크립트를 `.workflow/rules/wf-eligible.sh`에 설치한다(TASK-003).
  4. `~/.claude/HEARTBEAT.md`의 관리 블록을 갱신한다(TASK-004).
  5. 갱신된 상태를 조회해서 반환한다. 프론트가 두 번 호출하지 않아도 되게 한다.
- **순서를 지킨다.** 조건 스크립트가 먼저다. 잡을 먼저 쓰면 존재하지 않는 스크립트를 가리키는 잡이 잠깐이라도 활성화되고, 하트비트는 조건 검사 실패를 skip으로 처리하므로 사용자에게는 "아무 일도 안 일어남"으로만 보인다.
- 3단계에서 실패하면 4단계를 하지 않는다. 4단계에서 실패하면 3단계 결과(설치된 스크립트)는 그대로 둔다. 잡 없이 스크립트만 있는 상태는 무해하고, 되돌리기를 넣으면 실패 경로가 두 배로 복잡해진다.
- 역할이 하나도 활성이 아니면 관리 블록을 제거한다. 조건 스크립트는 지우지 않는다. 앱 관리 자산이며 다른 실행 경로에서도 쓰인다.
- 실패 시 사용자에게 보이는 문구는 한국어로, 어느 파일의 어떤 상태 때문인지 드러나야 한다. 특히 마커 손상과 종료 마커 뒤 `- key: value` 흡수 위험은 사용자가 직접 고쳐야 하므로 무엇을 고쳐야 하는지 알 수 있어야 한다.

### 2. 설치 액션 UI (R2, R6)

- 액션 이름은 목적이 드러나게 짓는다. 예: "이 프로젝트에 역할 잡 설치".
- 쓰기 전에 확인 단계를 둔다. 확인 화면에 반드시 아래를 보여준다(R6).
  - 대상 경로 두 개: `~/.claude/HEARTBEAT.md`(전역)와 `.workflow/rules/wf-eligible.sh`(프로젝트 로컬). 전역 파일이라는 사실이 드러나야 한다.
  - 변경 내용의 요지: 어떤 역할 잡이 어떤 이름으로 들어가는지, 관리 블록 밖은 건드리지 않는다는 것.
- 확인 단계는 실수 클릭 방지용 2단계 무장(`useArmedConfirm`)만으로 대체하지 않는다. 기획서는 "대상 경로와 변경 내용의 요지를 보여주고 확인을 받는다"를 요구한다. 경로와 요지가 화면에 실제로 보여야 한다.
- 미지원 플랫폼(Windows)에서는 설치 액션을 노출하지 않거나 비활성화하고 미지원 안내를 보여준다. 프론트에서 막는 것과 별개로 백엔드도 거부한다.
- 하트비트 미설치 상태에서는 역할 잡 설치 액션을 노출하지 않는다(R1).

### 3. 역할 토글 (R5)

- 역할별 활성 토글 3개를 제공한다. 끄면 그 잡을 관리 블록에서 제거한다. 하트비트에는 비활성 상태 필드가 없으므로 "꺼짐"은 "블록에 없음"이다.
- 토글 변경도 전역 파일 쓰기다. 2번의 확인 절차를 거친다.
- 토글을 껐다 켜면 같은 이름으로 복구되어야 한다. 잡 이름은 slug에서 결정되므로 자동으로 성립하지만, 편집한 `interval`·`max_per`·`model`은 끄는 순간 파일에서 사라진다. 다시 켜면 기본값으로 돌아간다는 것을 UI에서 알 수 있게 한다. 값 보존을 위해 앱이 별도 저장소를 만들지 않는다. 기획서 범위 밖이고 새 상태 파일은 새 소유권 문제를 만든다.

### 4. 편집과 검증 (R5)

- `interval`, `max_per`, `model`을 역할별로 편집할 수 있게 한다. `prompt`·`condition`·`slug`·`timeout`·`notify`는 앱이 소유하며 편집 대상이 아니다.
- 저장 전에 프론트에서 형식을 검증하고, 잘못된 값은 **해당 입력 위치에서** 사유를 표시한다. 전역 에러 배너로 대체하지 않는다.
  - `interval`: 숫자 + `s` | `m` | `h` | `d`
  - `max_per`: `<횟수>/<기간>` 형태이고 기간은 위와 같은 단위 표기
  - `model`: 공백 없는 한 줄 값
- 검증에 걸리면 커맨드를 호출하지 않는다. 백엔드 검증(TASK-004)은 방어선으로 남겨 둔다. 두 곳 모두 있어야 한다.
- 기본 주기의 근거를 화면 문구로 남긴다(R3): 한 세션이 수 분에서 수십 분 걸리므로 주기를 그보다 짧게 잡으면 조건 검사만 반복되고 중복 기동 위험만 늘어난다.

### 5. 테스트

- 프론트(`SettingsView.test.tsx` 확장):
  - 확인 단계를 거치지 않으면 게이트웨이 호출이 일어나지 않는다.
  - 확인 화면에 두 대상 경로와 변경 요지가 표시된다.
  - `interval`·`max_per`·`model` 각각의 잘못된 입력에 대해 입력 위치에 사유가 표시되고 게이트웨이가 호출되지 않는다.
  - 미지원 플랫폼에서 설치 액션이 비활성이거나 없다.
  - 하트비트 미설치 상태에서 설치 액션이 노출되지 않는다.
- 백엔드(`heartbeat.rs` 또는 서비스 계층):
  - 잘못된 형식 입력에서 두 대상 파일 중 어느 것도 쓰이지 않는다.
  - 조건 스크립트 설치 실패 시 `HEARTBEAT.md`가 쓰이지 않는다.
  - 두 번 연속 같은 입력으로 실행해도 두 파일이 모두 변하지 않는다.
  - 테스트는 임시 디렉터리에서 돈다. 실제 `~/.claude`를 건드리면 안 된다. 커맨드 함수가 홈 경로를 직접 계산한다면, 경로를 받는 내부 함수를 분리해 그 함수를 테스트한다.

## 완료 조건

1. 역할 잡 설치 후 `~/.claude/HEARTBEAT.md`에 관리 마커 블록이 하나 생기고 역할 잡 3종이 R3 기본값으로 기록되며, 블록 밖 내용이 바이트 단위로 동일하다. (기획서 완료 조건 2)
2. 같은 설치를 두 번 실행해도 파일 해시가 같다. (기획서 완료 조건 3)
3. `- tick:`이 있는 파일에 설치해도 그 값이 유지된다. (기획서 완료 조건 4)
4. 마커 손상 파일과 종료 마커 뒤 `- key: value`가 이어지는 파일에서 설치가 실패하고 원본 해시가 유지된다. (기획서 완료 조건 5)
5. `.workflow/rules/`에 조건 스크립트가 설치되고 인자 3종과 종료 코드가 `scripts/wf-eligible.sh`와 같다. (기획서 완료 조건 6)
6. 역할 토글을 끄면 해당 잡이 블록에서 사라지고, 다시 켜면 최초 설치 결과와 파일이 같다. (기획서 완료 조건 8)
7. `interval`·`max_per`·`model`에 잘못된 형식을 입력하면 파일에 쓰이지 않고 입력 위치에 사유가 표시된다. (기획서 완료 조건 9)
8. 관리 블록 밖의 중복 잡이 앱에 의해 수정되거나 삭제되지 않는다. (기획서 완료 조건 12)
9. 전역 파일 쓰기가 명시적 사용자 액션에서만 일어나고, 쓰기 전에 대상 경로와 변경 요지가 화면에 표시된다. (기획서 R6)
10. `npm run check`와 `cargo test --manifest-path src-tauri/Cargo.toml`이 통과한다. (기획서 완료 조건 13)

```sh
npm run check
```

수동 확인. **시작 전에 반드시 백업한다.**

```sh
cp ~/.claude/HEARTBEAT.md /tmp/HEARTBEAT.md.bak
md5 ~/.claude/HEARTBEAT.md
```

```sh
npm run tauri dev
```

1. 설정 → 연동 → 역할 잡 설치. 확인 화면에 두 경로와 변경 요지가 보이는지 확인한다.
2. 확인 후 `~/.claude/HEARTBEAT.md`를 열어 관리 블록이 파일 끝에 붙었고 기존 잡과 전역 설정이 그대로인지 확인한다.

```sh
diff <(sed -n '1,/workflow-labs:heartbeat-jobs:start/p' ~/.claude/HEARTBEAT.md | sed '$d') /tmp/HEARTBEAT.md.bak
heartbeat jobs
```

- `diff`에 차이가 없어야 한다(블록 앞부분이 원본과 동일).
- `heartbeat jobs`에서 새 잡 3종이 인식되고 기존 잡과 `tick`이 그대로인지 확인한다.

3. 같은 설치를 한 번 더 실행한 뒤 `md5 ~/.claude/HEARTBEAT.md`가 직전 값과 같은지 확인한다.
4. 역할 하나를 껐다 켠 뒤 해시가 최초 설치 직후 값과 같은지 확인한다.
5. `interval`에 `30분`, `max_per`에 `4회`, `model`에 공백이 든 값을 넣고 각각 입력 위치에 사유가 뜨는지, 파일 해시가 변하지 않는지 확인한다.
6. 손상 재현: 백업본을 복사해 종료 마커 뒤에 `- tick: 5m`을 넣은 파일을 만들고 설치를 시도해 실패와 해시 유지를 확인한다.

```sh
sh .workflow/rules/wf-eligible.sh planner; echo $?
sh .workflow/rules/wf-eligible.sh bogus; echo $?
```

- 설치된 조건 스크립트가 동작하는지 확인한다. `bogus`는 `2`여야 한다.

확인이 끝나면 원상 복구한다.

```sh
cp /tmp/HEARTBEAT.md.bak ~/.claude/HEARTBEAT.md
md5 ~/.claude/HEARTBEAT.md
```

- 백업 시점 해시와 같은지 확인한다.

## 범위 밖

- 데몬 시작·중지, 잡 즉시 실행, `~/.claude/heartbeat/` 아래 쓰기. 기획서 R6이 금지한다.
- 중복 잡 자동 정리. 경고만 한다(R7). 도그푸딩 환경의 손으로 적은 `wf-planner`·`wf-architect`·`wf-developer` 정리는 사용자 몫이다.
- 토글로 꺼진 역할의 편집값 보존.
- 동적 플러그인 로딩, 서드파티 연동 등록.
- Windows용 조건 스크립트.
- 이 저장소의 `scripts/wf-eligible.sh` 제거와 `docs/heartbeat.md` 문구 수정. 기획서 `확인 필요` 1번의 승인 내용대로 별도 아이디어로 다룬다.

## 참고 사실

- `src/shared/ui/useArmedConfirm.ts`가 기존 2단계 확인 훅이다. 확인 화면과 함께 쓸 수는 있지만 그것만으로는 R6을 만족하지 못한다.
- `src-tauri/src/infrastructure/fs_project_repository.rs:28`의 `ProjectError`가 사용자용 한국어 오류 문구의 기존 형태다.
- 설치 확인 화면의 요지는 프론트가 알고 있는 값(역할 목록, 잡 이름 규칙, 대상 경로)으로 만든다. 백엔드 dry-run 커맨드를 따로 두지 않는다. 실패 경로에서 원본이 바뀌지 않는 것이 엔진 수준에서 보장되므로, 확인 단계는 "전역 파일을 건드린다"는 사실을 알리는 것으로 충분하다.
- 이 작업이 끝나면 도그푸딩 환경에는 같은 역할의 잡이 두 벌(수동 3개 + 관리 블록 3개) 존재하게 된다. R7 경고가 뜨는 것이 정상이며, 사용자가 수동 잡을 지우기 전까지 역할당 두 세션이 깨어난다. QA 시 이 상태를 예상 동작으로 본다.
