# 릴리스 가이드

## 브랜치 흐름

1. 기능 브랜치는 `dev`에서 분기하고 `dev`로 PR을 보낸다.
2. 릴리스 후보가 안정화되면 `dev`를 `main`으로 PR한다.
3. `package.json`, `src-tauri/Cargo.toml`, `src-tauri/tauri.conf.json`의 버전을 함께 변경한다.
4. 아래 "병합 조건"을 모두 충족한 것을 확인한 뒤에 그 PR을 `main`으로 병합한다.
5. `main` 병합 후 같은 버전의 태그를 만든다.

```bash
git tag v0.1.3
git push origin v0.1.3
```

### 병합 조건

이 절은 릴리스 컷의 병합 조건에 대한 정본이다. 세션 진입 문서 `AGENTS.md`의 릴리스 컷 절은 이 문서를
가리키는 포인터이며, 규범의 본문은 이 절에만 둔다.

병합 조건을 규범으로 두는 이유는 두 가지다. 첫째, 태그 워크플로 `.github/workflows/release.yml`은 버전
대조와 3-OS 번들 생성만 수행하고 테스트, 서식, 정적 검사 명령이 없다. 따라서 PR 검사가 산출물 앞의
마지막 검사이며, 그 자리를 건너뛰면 그 뒤에 남는 검사가 없다. 둘째, 지금까지 릴리스 두 번이 검사가
실패한 상태에서 병합됐고, 그중 v0.1.8은 그 병합 커밋에 태그가 붙어 설치 파일이 게시됐다.

1. **검사 네 갈래 통과 확인.** 병합은 그 PR의 검사 네 갈래가 모두 끝나고 통과한 것을 확인한 뒤에 한다.
   네 갈래는 `.github/workflows/ci.yml`이 정의하는 `Frontend` 1개와 `Rust (ubuntu-22.04)`,
   `Rust (windows-latest)`, `Rust (macos-latest)` 3개다. "검사가 돌고 있다"는 통과 확인이 아니다.
   한 갈래라도 실패하면 병합하지 않는다. 그 실패가 릴리스에 어떤 영향을 주는지에 대한 판단은 병합한
   뒤가 아니라 병합하기 전에 한다.
2. **로컬 게이트의 위상.** `cargo test`, `cargo fmt --check`,
   `cargo clippy --all-targets -- -D warnings`, `npm run check`의 로컬 실행은 원격에 보내기 전에
   문제를 빨리 찾기 위한 사전 신호이고, 병합의 근거가 아니다. 대부분의 문제가 이 단계에서 걸리므로
   이 게이트를 없애거나 명령을 줄이지 않는다.
3. **로컬에서 원리상 잡히지 않는 세 계열.** 아래 세 가지는 로컬 실행 횟수를 늘려도 재현되지 않으므로,
   게이트를 더 성실히 돌리는 것으로는 대체할 수 없다.
   - 운영체제 조건부 컴파일. `#[cfg(unix)]`로 갈린 코드는 맥에서 윈도우 타깃이 컴파일되지 않아
     `-D warnings` 위반이 원격에서만 드러난다. 맥에서 같은 명령을 다시 실행해도 윈도우 타깃 컴파일이
     일어나지 않으므로 재현되지 않는다.
   - 런타임 버전 차이. 로컬 node 25와 원격 node 22는 테스트 환경의 브라우저 저장소 동작이 달라서,
     테스트 격리 누락이 로컬에서는 드러나지 않고 원격에서만 실패로 나타난다. 로컬 런타임을 바꾸지
     않는 한 반복 실행으로는 같은 조건이 만들어지지 않는다.
   - 플랫폼별 설치 자산. 대조 헬퍼에 셸 이름과 스크립트 이름을 고정해 두면 맥에서는 통과하고
     윈도우에서는 스크립트가 실행되지 않는다. 맥에 그 셸이 있는 한 로컬 결과는 계속 통과다.
4. **확인 대상 커밋.** 통과 확인은 실제로 병합하는 커밋에서 나온 실행 결과여야 한다. 새 커밋을 올리면
   이전 통과는 병합의 근거가 아니며 다시 확인한다. 검사 워크플로의 동시성 그룹이
   `cancel-in-progress: true`이므로 같은 참조에 새 커밋을 올리면 이전 실행이 취소되기도 한다.
5. **재실행 기준.** 재실행은 검사 대상 코드와 무관한 실패에만 허용한다. 러너가 죽은 경우, 네트워크나
   의존성 내려받기가 실패한 경우, 실행이 취소된 경우다. 재실행했다면 그 사유를 병합 전에 한 줄
   남긴다. 그 밖의 실패는 재실행하지 않고 원인을 고치며, 같은 커밋을 다시 실행해 얻은 통과는 병합의
   근거가 되지 않는다.
6. **정본 표시.** 병합 조건은 이 문서와 세션 진입 문서 `AGENTS.md` 두 곳에 걸쳐 있다. 이 절이 정본이고
   `AGENTS.md`의 절은 이 문서를 가리키는 포인터다. 두 문서가 어긋나면 이 절을 따른다.
7. **컷 기록 요구.** 컷 세션은 그날의 개발 로그 `docs/development-logs/YYYY-MM-DD.md`에 통과를 확인한
   검사 실행과 병합 시각을 남긴다. 어느 실행을 근거로 병합했는지를 나중에 되짚기 위한 기록이다.

## GitHub 설정

업데이트 서명 키는 로컬에서 생성하고 개인 키를 저장소에 커밋하지 않는다.

```bash
npm run tauri signer generate -- -w /안전한/외부/경로/llm-workflow.key
```

GitHub Actions secret:

- `TAURI_SIGNING_PRIVATE_KEY`
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`
- `TAURI_UPDATER_PUBLIC_KEY`

제품 배포 전에는 다음 OS 서명 값도 설정한다.

- macOS Developer ID 인증서와 notarization 자격 증명
- Windows code-signing 인증서 또는 서명 서비스 자격 증명

Tauri updater 서명은 업데이트 산출물의 무결성을 확인하지만 macOS/Windows의 개발자 신뢰 서명을 대체하지 않는다.

현재 첫 공개 배포의 macOS 번들은 Developer ID 인증서 없이 생성한다. 따라서 신규 설치 시 macOS Gatekeeper 경고가 나타날 수 있다. 유효한 인증서가 준비되면 Apple 서명·notarization 환경 변수를 릴리스 워크플로에 다시 연결하고 검증한다.

## 배포 방식

`v*` 태그는 GitHub Actions에서 Linux, Windows, macOS universal 빌드와 `latest.json`을 생성한다. 릴리스는 드래프트로 만들어지며 설치 확인 후 사람이 게시한다. 앱 내부 updater는 공개 저장소에 게시된 최신 릴리스만 확인한다.

앱 업데이트는 프로젝트 Markdown을 자동으로 마이그레이션하지 않는다. 문서 마이그레이션은 프로젝트를 열 때 별도의 백업·lease 확인 절차로 실행한다.
