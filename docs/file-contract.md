# LLM Workflow 파일 계약

LLM Workflow와 외부 LLM은 프로세스나 API가 아니라 프로젝트의 Markdown/YAML 파일로 협업한다. 앱은 LLM을 실행하지 않으며, LLM은 앱의 내부 상태를 직접 조작하지 않는다.

`workflow-labs/*` 스키마 식별자는 기존 프로젝트와 앱 업데이트 호환성을 위해 이름 변경 후에도 유지한다.

## 디렉터리

```text
.                           # 선택한 프로젝트 루트
├── AGENTS.md               # Codex 및 공통 에이전트 진입점
├── CLAUDE.md               # Claude Code가 AGENTS.md를 import
└── .workflow/
    ├── project.yml
    ├── rules/
    │   ├── workflow.md       # 공급자 중립적인 공통 작업 규칙
    │   └── roles/
    │       ├── planner.md
    │       ├── architect.md
    │       └── developer.md
    ├── .runtime/             # Git 제외
    │   ├── leases/
    │   └── migrations/
    └── <slug>--<workflow-id>/
        ├── workflow.yml
        ├── ideas/
        ├── specs/
        ├── decisions/        # 앱이 기록하는 사용자 결정
        ├── tasks/
        ├── reports/
        └── state/
```

워크플로우를 처음 생성할 때 앱은 상세 규칙과 두 진입점을 함께 설치한다.

- 기존 `AGENTS.md`와 `CLAUDE.md`는 보존하고 앱 관리 마커 블록만 추가하거나 갱신한다.
- 기존 `CLAUDE.md`가 이미 `@AGENTS.md`를 import하면 중복 블록을 추가하지 않는다.
- 관리 마커가 손상됐거나 `.workflow/rules/workflow.md`가 앱 규격 파일이 아니면 덮어쓰지 않고 생성을 중단한다.
- 공통 규칙은 `schema: workflow-labs/agent-rules@1`, 역할 계약은 `schema: workflow-labs/agent-role@1`로 식별한다.
- 규칙 파일은 앱 관리 자산이며 기획서 결정 시 최신 역할 계약으로 안전하게 갱신한다.
- Codex의 `.codex/rules/*.rules`는 명령 승인 정책이므로 워크플로우 행동 규칙 저장소로 사용하지 않는다.

## 기획서

외부 LLM은 검토 가능한 기획서를 `specs/*.md`에 작성한다.

```markdown
---
schema: workflow-labs/spec@1
id: SPEC-001
title: 사용자 선택 대기 허브
status: user_review
source_idea_id: IDEA-A1B2C3D4
created_at: 2026-07-30T10:00:00Z
updated_at: 2026-07-30T10:10:00Z
---

# 사용자 선택 대기 허브

## 결정권자 요약

...

## 기획 내용

...

## 요구사항 명세

...

## 기대효과

...
```

기획서 상태는 `draft` 또는 `user_review`를 사용한다. 승인·수정 요청·폐기는 기획서 원문에 쓰지 않는다.

### 결정권자 요약 절

에이전트가 쓰는 기획서·개발 작업·개발 보고서는 본문 맨 앞에 도장을 찍을 사람을 위한 절 하나를 둔다. 제목은 세 문서 종류에서 같은 문자열 `## 결정권자 요약`이고, 자리는 H1 제목 바로 다음이며 다른 어떤 절보다 앞이다. 앱이 목록 미리보기와 검색 결과를 본문 앞 세 줄에서 만들기 때문에(`markdown_excerpt`) 요약이 맨 앞에 서면 표시 코드를 고치지 않아도 카드가 그날부터 요약을 보여준다. 아이디어 문서는 사용자도 직접 쓰는 자리라 이 의무의 대상이 아니다.

- 요약은 본문의 축약이 아니라 독자가 다른 층이라는 전제로 다시 쓴 문단이고, 본문에 없는 사실을 새로 만들지 않는다. 문서 종류별로 무엇을 말하는지는 그 문서를 만드는 역할 계약이 적는다.
- 분량 상한은 빈 줄을 제외하고 열 줄이다.
- 요약 절 안에는 백틱으로 감싼 토큰, 파일 경로, `snake_case`·`camelCase` 식별자, `파일:줄번호` 표기, 함수·타입·필드 이름이 없다. 예외는 문서 id 하나다 — `SPEC-`·`TASK-`·`IDEA-`·`DECISION-`으로 시작하는 값은 사용자가 앱 화면에서 마주치는 이름이라 허용하되 백틱 없이 평문으로 쓴다. 이 조건은 요약 절에만 걸리고 본문의 나머지 절은 지금 어법 그대로다.
- 문서의 상태를 전이하는 세션이 같은 편집에서 요약도 현재 사실에 맞춘다. `history` 항목을 같은 편집에서 덧붙이는 것과 같은 구조다. 이 의무는 에이전트 세션에만 걸린다 — 앱이 기록하는 `completed`·`revision_requested` 두 전이는 본문을 건드리지 않는다. 수정 요청으로 다시 쓰는 기획서는 새 문서이므로 요약도 새로 쓰고, 앞 문서의 요약을 복사해 오지 않는다.
- 요약 절이 없는 기존 문서는 그대로 유효하다. 그대로 읽히고 표시되고 판정되며, 요약의 유무는 어떤 자격 판정에도 들어가지 않고 문서 읽기가 요약 때문에 실패하지도 않는다. 소급 기입은 하지 않으므로 이 계약은 앞으로 쓰는 문서에 걸린다.

단일 정의는 공통 규칙 `.workflow/rules/workflow.md` §8이고, 세 역할 계약은 자기 문서의 의무만 적으며 그 절을 참조한다.

아이디어에서 출발한 기획서는 `source_idea_id`로 출처 아이디어를 참조한다. 수정 요청 재작업 기획서는 이전 기획서를 `source_spec_id`로, 그 수정을 요청한 결정을 `source_decision_id`로 참조하며 두 필드를 모두 적는다.

수정 요청 결정에 후속 기획서가 있는지는 `source_decision_id`로 판정한다. 그 결정 id를 `source_decision_id`로 적은 기획서가 `specs/` 아래 있으면 답이 나온 것이고, 없으면 기획자의 처리 대상이다. 판정 키가 `source_spec_id`가 아닌 이유는 한 기획서가 여러 번 수정 요청을 받을 수 있기 때문이다 — 그때 후속은 결정마다 하나씩 생기므로 기획서 id로는 구분되지 않는다. `source_spec_id`는 사람이 계보를 읽기 위한 값이고 판정에 쓰지 않는다. 같은 이름의 필드가 개발 작업에도 있지만 그쪽은 기획서를 승인한 결정을 가리키며, 이 판정은 `specs/`를 작업 판정은 `tasks/`를 보므로 섞이지 않는다.

앱은 이 참조와 lease를 읽어 아이디어를 `수집됨`·`반영중`·`종결`·`채택` 네 상태로 표시한다. 참조 기획서도 선점도 없으면 `수집됨`이고, `task_id`가 그 아이디어를 가리키는 미만료 lease가 있거나 참조 기획서 중 `draft`가 있으면 `반영중`이며, 참조 기획서가 모두 최신 결정 `rejected`로 끝났고 선점도 없으면 `종결`이고, 그 밖에 참조 기획서가 모두 `draft`를 벗어났고 선점도 없으면 `채택`이다. 이 판정은 조회 시점 파생이며 앱은 아이디어 파일을 쓰지 않는다 — 아이디어 문서의 `status`는 파일에서 `inbox`로 남는다.

조건 스크립트의 미처리 아이디어 판정은 화면의 `수집됨`보다 넓다. 참조 기획서가 있어도 그것이 **모두 `draft`**이고 미만료 lease가 없으면 스크립트는 그 아이디어를 대상으로 센다. 죽은 기획 세션이 남긴 `draft` 하나가 아이디어를 영원히 소비하지 않게 하는 회수 판정이고, 참조 기획서가 아예 없는 경우는 그 조건의 평범한 사례다. "하나라도 `draft`"가 아니라 "모두 `draft`"인 것이 기준이다 — 사용자에게 도달한 기획서와 죽은 재작업 `draft`를 함께 가진 아이디어는 회수 대상이 아니며, 그때 멈춘 것은 재작업이고 그 원천인 수정 요청 결정이 대상이 된다. 미만료 lease가 물고 있는 아이디어는 양쪽 모두에서 대상이 아니다. 화면의 네 파생 상태 판정은 이 변경으로 바뀌지 않는다 — 회수 대상인 아이디어도 참조 `draft`가 있으므로 화면에는 그대로 `반영중`으로 보이고, SPEC-012의 "중단 의심" 표시가 그 자리에서 같은 상태를 가리킨다. 다만 기획자 자격은 아이디어만으로 정해지지 않는다 — 후속 기획서가 없는 수정 요청 결정도 같은 크기의 대상이고, 화면의 아이디어 표시는 그쪽을 보여주지 않는다.

## 사용자 결정

앱은 승인·수정 요청·폐기 시 `decisions/*.md`에 추가 전용 기록을 만든다.

```markdown
---
schema: workflow-labs/decision@1
id: DECISION-001
spec_id: SPEC-001
outcome: revision_requested
created_by: user
created_at: 2026-07-30T10:20:00Z
---

성공 조건을 더 구체적으로 작성해 주세요.
```

- `outcome`: `approved`, `revision_requested`, `rejected`
- 수정 요청과 폐기에는 코멘트가 필수다.
- `revision_requested`는 기획자 역할이 새 ID의 개선된 기획서를 만들 수 있는 재작업 요청이다. 그 기획서의 최신 결정이면서 후속 기획서가 아직 없거나 있어도 모두 `draft`면 기획자의 처리 대상으로 남고, 후속 여부의 판정 키는 기획서 절에 적힌 `source_decision_id`다.
- `rejected`는 종료 상태다. 사용자가 새 아이디어로 다시 요청하지 않는 한 외부 LLM이 되살리지 않는다.
- 동일 기획서에 결정이 여러 개 있으면 가장 최근 앱 기록을 사용한다.
- 앱은 `schema: workflow-labs/decision@1`, `created_by: user`인 기록만 사용자 결정으로 신뢰한다.
- 외부 LLM은 decision 파일을 수정하지 않고 후속 기획서에 결과를 반영한다.

## 에이전트 역할 계약

- 기획자는 처리 대상인 아이디어 또는 `revision_requested` 결정 하나를 기획서로 가공하고 `user_review`에서 멈춘다. 대상인 아이디어는 그것을 `source_idea_id`로 참조하는 기획서가 모두 `draft`이고(참조가 아예 없는 경우를 포함한다) 유효한 lease도 없는 것이고, 대상인 수정 요청은 그 기획서의 최신 결정이면서 그 결정 id를 `source_decision_id`로 적은 기획서가 모두 `draft`이고 유효한 lease도 없는 것이다. 죽은 세션이 남긴 `draft` 기획서는 이 조건 때문에 원천을 다시 열고, 인수한 기획자는 그 문서를 새 ID로 복제하지 않고 같은 문서에서 이어 쓴다 — ID와 원천 참조를 보존하고 `created_at`은 그대로 두며 `updated_at`만 갱신한다. 선점 대상은 그대로 아이디어 id와 결정 id이고, 기획서 문서는 선점 대상이 되지 않는다.
- 기획자는 인수 대상을 아직 손대지 않은 원천보다 먼저 고르고, 그다음 축으로 수정 요청을 새 아이디어보다 먼저 고른다. 두 축이 충돌하면 인수가 먼저다 — 멈춘 일에는 비용이 이미 들어가 있다. 수정 요청이 아이디어보다 앞서는 이유는 사용자가 기획서를 끝까지 읽고 남긴 피드백이라 사람의 검토 비용이 이미 들어가 있고 사용자가 답을 기다리는 대기이기 때문이다. 같은 종류가 여럿이면 원천 문서의 `created_at`이 이른 것부터 고르고, 선점에 실패하면 다음 순번으로 넘어가며, 모든 대상이 선점되어 있으면 `NO_ELIGIBLE_WORK`를 보고한다. 조건 스크립트와 앱의 대기 물량 판정은 "있다/없다"만 답하므로 화면 표시나 종료 코드를 순서로 읽지 않는다.
- 프로젝트 아키텍트는 최신 결정이 `approved`인 기획서 하나를 `todo` 작업으로 분해하고 구현하지 않는다.
- 개발자는 의존성이 충족된 담당 `todo` 작업, 또는 미만료 lease가 덮지 않는 `in_progress` 작업 하나를 구현·검증하고 `qa_waiting`에서 멈춘다. 두 번째가 죽은 세션이 남긴 작업의 인수이며, 나머지 자격 조건은 `todo`와 완전히 같다. `blocked`은 세션이 의도적으로 선언한 상태이므로 어느 쪽으로도 대상이 아니다. 대상이 여럿이면 인수를 `todo`보다 먼저 고른다 — 멈춘 작업은 그것을 `depends_on`으로 기다리는 작업까지 함께 막는다.
- 기획자의 기획서 요약은 셋 중 가장 엄격하다. 승인 게이트의 재료이므로 넷을 모두 말한다 — 무엇을 왜 바꾸는지, 사용자가 이 문서에서 결정할 것이 무엇인지, 승인하면 무엇이 달라지는지, 승인하지 않으면 무엇이 그대로 남는지.
- 아키텍트의 개발 작업 요약은 이 작업이 끝나면 사용자에게 무엇이 달라지는지를 말한다. 코드 구조가 아니라 사용자가 겪을 변화다.
- 개발자의 개발 보고서 요약은 무엇을 했고 무엇이 확인됐는지, 사용자가 지금 무엇을 해야 하는지를 말한다. 더해서 담당 작업 문서의 `## 확인 동선` 절을 `qa_waiting` 전이를 기록하는 같은 편집에서 쓴다.
- 세 역할 모두 한 세션에서 다음 역할로 넘어가지 않으며, 처리 대상이 없으면 파일을 바꾸지 않는다.
- 세 역할 모두 착수 전에 대상 문서를 먼저 선점한다: 선점 헬퍼로 대상 문서 id의 lease를 얻은 뒤, 기획자는 `status: draft` 스켈레톤을, 개발자는 `status: in_progress`를 즉시 기록하고 나서 실제 작업을 시작한다. 선점에 실패하면 다른 대상을 고르거나 `NO_ELIGIBLE_WORK`를 보고한다. 절차의 단일 정의는 공통 규칙 `.workflow/rules/workflow.md` §4이고, 역할 계약은 그 절을 참조만 한다.

## 개발 작업

```markdown
---
schema: workflow-labs/task@1
id: TASK-001
title: 기획서 상태 파서 구현
status: in_progress
source_spec_id: SPEC-001
source_decision_id: DECISION-001
depends_on: [TASK-000]
updated_at: 2026-07-30T10:30:00Z
due_at: 2026-08-07
history:
  - { at: 2026-07-30T09:00:00Z, kind: created }
  - { at: 2026-07-30T10:30:00Z, kind: in_progress }
---

# 기획서 상태 파서 구현

## 결정권자 요약

...

## 확인 동선

...
```

본문에는 `결정권자 요약` 절을 맨 앞에 두고, 이어서 작업 범위와 완료 조건을 작성한다. `qa_waiting`으로 넘어가는 작업은 `확인 동선` 절도 갖는다. 두 절의 저자가 다르다 — 요약은 작업 문서를 만드는 아키텍트가 쓰고, 확인 동선은 개발자가 `qa_waiting` 전이를 기록하는 편집에서 덧붙인다.

지원 상태:

- `todo`: 시작 전
- `in_progress`: 작업 중
- `blocked`: 진행 불가
- `qa_waiting`: 작업 완료 후 사용자 QA 대기
- `completed`: QA까지 완료

`blocked`에서 나오는 경로는 사용자 재개 하나뿐이다. 아래 "막힌 작업 재개" 절이 그 계약이다.

파생 작업은 근거를 참조한다. `source_spec_id`는 이 작업이 나온 기획서를, `source_decision_id`는 그 기획서를 승인한 사용자 결정을 가리킨다. 앱은 이 결정 참조를 읽어 "승인됐지만 아직 작업으로 분해되지 않은 결정"을 판정하므로, 작업을 분해한 세션은 두 키를 함께 적는다.

개발 작업 카드를 선택하면 앱이 Markdown 본문을 상세 화면으로 보여준다. `qa_waiting` 작업에서는 사용자가 테스트 플로우와 확인 메모를 입력하고 다음 결정을 내린다.

사용자가 그 자리에서 읽을 확인 동선은 작업 문서 본문의 `## 확인 동선` 절에 있다. 앱이 확인 도장 옆에 작업 본문을 이미 펼쳐 두므로 사용자는 화면을 옮기지 않고 읽는다. 최소 형태는 "어느 화면 → 어느 조작 → 무엇이 보이면 정상"이고, 재현 조건이 있는 결함 수정은 그 조건을 함께 적는다. 눈으로 볼 화면이 없는 작업 — 계약 문언 변경이나 스크립트 판정 — 은 그 사실을 평문으로 말한다: 자동 검사로 닫혔고 확인 도장은 그 검사 수치를 신뢰한다는 뜻이라는 것. 빈 절을 두거나 화면이 있는 척하지 않는다. 요약 절의 금지 조건은 이 절에 걸리지 않는다 — 재현에는 경로나 명령이 필요할 수 있다.

개발 보고서의 `## 사용자 QA 제안` 관례는 계약 대상이 아닌 자유 기술이다. 앱은 보고서를 열지 않으므로 정본은 작업 문서 쪽이다.

- `confirmed`: 작업 상태를 `completed`로 변경한다. 확인 메모는 선택이다.
- `revision_requested`: 코멘트를 필수로 기록하고 작업 상태를 `todo`로 되돌린다.

QA 결정은 `decisions/*.md`에 `schema: workflow-labs/qa-decision@1`, `created_by: user`인 추가 전용 감사 로그로 남긴다. 개발자는 `todo` 작업에 최신 QA 수정 요청이 있으면 해당 테스트 플로우를 읽고 재작업한다.

### 막힌 작업 재개

사용자는 `blocked` 작업에 해결 근거를 적고 `todo`로 되돌릴 수 있다. 앱은 한 요청에서 작업 상태를 `todo`로 바꾸고 `history`에 `resumed` 항목 하나를 덧붙이며, 같은 시각의 감사 기록을 `decisions/*.md`에 남긴다.

```markdown
---
schema: workflow-labs/task-resume@1
id: RESUME-3F9A21C4
task_id: TASK-001
outcome: resumed
request_id: 7d1c0f2a-4b83-4c31-9c0e-6f2f5f0a1b22
previous_updated_at: 2026-07-30T10:30:00Z
created_by: user
created_at: 2026-07-31T09:12:44Z
---

원인이던 외부 API 스펙이 확정돼 남은 구현을 진행할 수 있다.
```

- 본문은 사용자가 입력한 해결 근거 원문만 담는다. 앱이 문장을 대신 지어내지 않는다.
- `previous_updated_at`은 사용자가 화면에서 확인한 작업 문서의 `updated_at`이다. 앱은 이 값이 현재 값과 문자 단위로 같을 때만 재개하며, 다르면 아무것도 쓰지 않고 사용자에게 다시 확인하라고 답한다.
- `request_id`는 같은 재개를 한 번만 기록하기 위한 요청 식별자다. 같은 값으로 다시 요청하면 앱은 새 기록을 만들지 않고 기존 성공 결과를 돌려준다.
- 대상 작업을 덮은 미만료 lease가 하나라도 있으면 소유자와 무관하게 거절한다. 앱은 lease 파일을 읽기만 하고 지우거나 갱신하지 않는다.
- 상태 전이와 감사 기록은 함께 남는다. 둘 중 하나만 저장되면 앱은 성공을 돌려주지 않고 이미 만든 기록을 되돌리며, 되돌리기까지 실패하면 남은 파일 경로와 필요한 복구 행동을 함께 돌려준다.
- 이 기록은 앱 소유이며 사용자 조작에서만 만들어진다. 외부 LLM은 이 파일을 만들지 않고 `resumed` 이력을 손으로 적지도 않는다.
- 재개 기록은 기획서 결정과 QA 결정 판정에 참여하지 않는다. 앱은 재개 뒤 개발자 자격 판정을 다시 계산하며, 선행이 미충족이거나 파일 범위가 겹치면 작업은 `todo`로 남고 자격은 계속 없음이다.

`due_at`은 선택 필드이며 `YYYY-MM-DD` 형식의 작업 목표일이다. 보드·리스트가 이 값을 작업의 목표일로 표시한다.

`history`는 선택 필드이며 개발 작업의 상태 전이 사실을 남기는 블록 시퀀스다. 항목 하나가 전이 하나이고, `at`은 RFC3339 시각, `kind`는 아래 일곱 값 중 하나다.

- `created`: 작업 문서 생성
- `in_progress`: 작업 시작
- `blocked`: 막힘
- `qa_waiting`: QA 대기 진입
- `completed`: QA 확인으로 완료
- `revision_requested`: QA 반려로 `todo` 복귀
- `resumed`: 사용자가 막힌 작업을 다시 열어 `todo` 복귀

기록은 추가 전용이다. 상태를 바꾼 세션이 같은 편집에서 항목 하나를 맨 뒤에 덧붙이고, 이미 있는 항목은 고치지 않는다. 죽은 세션이 남긴 `in_progress` 작업을 인수한 세션도 항목 하나를 덧붙인다 — 문서의 `status`는 이미 `in_progress`라 바뀌지 않지만 `kind: in_progress` 항목을 남기며, 인수 전용 `kind`를 새로 만들지 않는다. 반려 후 재작업이나 인수처럼 같은 `kind`가 여러 번 나오는 것은 정상이다. `completed`와 `revision_requested`는 앱이 QA 결정을 기록할 때, `resumed`는 앱이 사용자 재개를 기록할 때 남기므로 에이전트가 쓰지 않는다. `resumed`는 사용자가 작업을 다시 열었다는 사실이고 `in_progress`를 대신하지 않는다 — 되돌아온 `todo` 작업을 선점한 개발자는 기존과 같이 `in_progress` 항목을 따로 덧붙인다. 앱은 재개 감사 기록도 같은 작업 이벤트로 읽으며, 작업 이력과 감사 기록에 같은 `kind`와 시각이 함께 있으면 활동 화면에는 한 번만 나타난다. 항목은 위 예시처럼 한 줄 흐름 표기로 쓰고, 남길 항목이 없으면 `history` 키 자체를 쓰지 않는다.

`updated_at`은 마지막 변경 시각일 뿐이므로 전이 시각의 대체로 쓰지 않는다. 앱은 `history`를 관대하게 읽는다. 필드가 없거나, 시퀀스가 아니거나, 항목의 `at`·`kind`가 계약과 어긋나면 그 항목만 버리고 문서 읽기는 성공한다. 이력이 없는 기존 작업 문서도 그대로 유효하다.

`depends_on`은 선택 필드이며 이 작업보다 먼저 끝나야 하는 선행 작업 id의 목록이다. 값은 같은 워크플로우 안 개발 작업만 가리키고 기획서·결정·아이디어나 다른 워크플로우의 문서는 참조하지 않는다. 키는 다른 프론트매터 키와 같이 열 0에서 시작한다 — 들여쓴 자리에 두면 앱이 QA 전이를 기록할 때 `history` 블록으로 오인한다. 키가 없거나 목록이 비어 있으면 선행 작업이 없다는 뜻이고, 이 필드가 없는 기존 작업 문서도 그대로 유효하다.

의존 충족은 읽는 시점의 파생이며 어디에도 저장하지 않는다. 선언된 id가 모두 `qa_waiting` 또는 `completed`인 작업을 가리키면 충족이고, 하나라도 `todo`·`in_progress`·`blocked`이거나, 참조한 작업 문서가 없거나, 자기 자신을 참조하거나 순환을 이루거나, 목록으로 읽을 수 없는 형식이면 미충족이다. 저장하지 않으므로 QA 반려로 선행 작업이 `todo`로 돌아가면 후행 작업은 다시 미충족이 된다. 이 정의는 계약 문서·조건 스크립트·앱·에이전트 세션에서 모두 같다.

작업 범위가 겹치면 병렬로 진행하지 않는다. 겹침 판단은 아키텍트가 분해 시점에 하고, 결론은 산문의 "병행 금지"가 아니라 뒤에 오는 작업의 `depends_on`으로 남긴다. 개발자는 의존이 미충족인 작업을 착수 대상으로 고르지 않으며, 아직 차례가 아니라는 이유로 그 작업을 `blocked`로 바꾸지도 않는다.

lease 파일은 선점한 문서 id를 파일명으로 사용해 `.workflow/.runtime/leases/<문서-id>.yml`에 만든다. 세션은 이 파일을 직접 만들거나 고치거나 지우지 않고 앱 관리 자산인 선점 헬퍼 `.workflow/rules/wf-claim.sh`의 `acquire`·`renew`·`release`를 부르며, 결과를 출력 문자열이 아니라 종료 코드로 판정한다: `0` 성공, `1` 그 밖의 실패(입출력 오류, 마이그레이션 락), `2` 사용법 오류, `3` 대상이 이미 미만료 lease로 선점됨, `4` 만료 lease 인수 경합 패배, `5` 소유자 불일치. 헬퍼가 설치되지 않은 프로젝트에서는 세션이 현행 절차대로 배타적 생성으로 만들고, 헬퍼가 있는데 실행이 실패하면 선점 실패로 보고 그 대상을 포기한다. 이미 파일이 있고 만료 전이면 그 대상은 다른 세션이 작업 중인 것이다. lease에는 만료 시간이 있으며 활성 lease는 앱 마이그레이션도 막는다. `heartbeat_at`과 `expires_at`은 UTC `YYYY-MM-DDTHH:MM:SSZ` 표기로 쓴다. RFC3339가 허용하는 오프셋 표기나 소수 초는 이 계약의 읽는 쪽이 받지 않는다 — 조건 스크립트는 이 표기만 비교하고 선점 헬퍼도 이 표기만 쓴다. 자격 판정은 만료된 lease를 선점으로 세지 않으며, `expires_at`이 없거나 위 표기를 벗어나 시각으로 읽히지 않는 lease도 마찬가지다. 그러지 않으면 해제 없이 죽은 세션이 그 대상을 영원히 막는다. 판정은 lease 파일을 지우거나 고치지 않으므로 만료된 파일은 다음 선점이 인수할 때까지 그 자리에 남는다. 만료 lease를 인수해 남의 진행분 위에서 시작한 세션은 그 잔여물 — 문서의 진행분과 작업 트리의 코드 변경 둘 다 — 을 그대로 신뢰하지 않고 살릴 것·걷어낼 것·새로 쓸 것으로 갈라 판단하고, 무엇을 인수했고 무엇을 걷어냈으며 왜 그렇게 갈랐는지를 보고서 하나만 읽고 드러나게 적는다. 걷어낸 것이 검사라면 그 사실과 근거를 밝힌다 — 죽은 세션이 더한 잘못된 검사를 걷어내는 것과 통과시키려고 검사를 지우는 것은 다른 일이고, 보고서가 그 둘을 구분해 보인다. 이 의무는 인수할 수 있는 모든 역할에 같고, 단일 정의는 공통 규칙 `.workflow/rules/workflow.md` §4에 있다. 앱은 lease를 읽기만 하고 만들거나 지우거나 갱신하지 않는다. lease에는 선점 세션의 역할을 적는 선택 필드 `role`이 있고 값은 `planner`·`architect`·`developer` 중 하나다. 값이 없는 lease도 유효하며 헬퍼는 이 필드를 쓰지 않는다. 앱은 없는 역할을 추정으로 채우지 않는다.

## 문서 문체

에이전트가 작성하는 아이디어, 기획서, 개발 작업, 개발 보고서는 공통 규칙 `.workflow/rules/workflow.md`의 9번 문체 기준을 따른다. 이 섹션은 해당 기준을 한국어로 설명하고, 표현별 대안과 수정 예시를 제공한다. 두 문서의 내용이 다르면 공통 규칙을 기준으로 한다. 사용자가 직접 작성한 문서에는 적용하지 않는다.

문장에는 주체, 행동, 결과를 구체적으로 적고 주요 주장은 하나만 담는다. 한국의 기획·개발 문서에서 일반적으로 사용하는 한자어와 기술 용어는 그대로 사용한다. 쉬워 보이게 만들기 위해 표준 용어를 어색한 고유어로 바꾸지 않는다. 여러 작업을 하나의 비유로 표현하지 말고 실제 행위나 결과를 정확히 적는다. 영문식 긴 대시는 마침표나 접속 표현 대신 습관적으로 사용하지 않는다.

### 표현별 대안

| 피할 표현 | 문맥에 맞는 대안 | 사용 기준 |
| --- | --- | --- |
| 착지 | 구현, 반영, 병합, 배포 | 변경이 코드베이스에 적용된 과정을 정확히 구분한다. |
| 닫다 | 해결, 충족, 완료 | 요구사항이나 완료 조건을 처리했다고 말할 때 |
| 원천 | 데이터 출처, 원본 문서, 판단 기준 | 값을 읽어 오는 곳과 판단의 근거를 함께 부를 때 |
| 자리 | 화면 위치, 문서 섹션, 코드 위치, 즉시 | 실제 위치인지 처리 시점인지 구분한다. |
| 몫 | 담당 범위, 담당 작업, 책임 | 어떤 작업이나 역할이 담당하는 내용을 명시한다. |
| 어법 | 코드 관례, 구현 방식, 표기 방식, 문체 | 기존 코드의 작성 관례를 따르라고 할 때, 그리고 문서의 문체를 가리킬 때 |
| 표면 | 인터페이스, 공개 API, 노출 필드, 연동 지점 | 다른 구성 요소가 사용하는 접점의 종류를 명시한다. |

앞의 세 표현과 대안은 공통 규칙의 예시와 같다. 뒤의 네 표현은 이 저장소의 기존 문서에서 자주 발견돼 추가했다. 문맥에 따라 다른 표현이 더 적합할 수 있으며, 필요한 경우 이 표에 없는 대안도 사용할 수 있다.

이 표는 금지어 목록이 아니다. 다만 의미가 분명하다는 이유만으로 한국어에서 일반적으로 쓰이지 않는 비유를 허용하지 않는다. 해당 표현이 한국의 기획·개발 문서에서 통용되는 표준 기술 용어이고, 문장에서 정확한 의미로 사용된 경우에만 유지할 수 있다. 예를 들어 "데몬이 노출하는 표면"은 "데몬 인터페이스"나 "데몬이 노출하는 API"로 고친다.

### 수정 전과 수정 후

다음 예시는 기존 문서의 문장을 위 기준에 맞게 수정한 결과다. 예시를 위해 문장만 가져왔으며 기존 문서는 변경하지 않는다.

착지:

- 전: 여러 세션이 한 작업 트리를 쓰므로 그 사이 다른 작업이 착지했으면 숫자는 늘 수 있다.
- 후: 여러 세션이 한 작업 트리를 함께 쓴다. 검사를 돌리는 사이에 다른 작업이 병합되면 검사 개수는 늘어날 수 있다.

닫다:

- 전: 단위 검사까지다. SPEC-029의 완료 조건 8·9를 닫는다.
- 후: 이 작업의 범위는 단위 검사까지다. 이 작업이 SPEC-029의 완료 조건 8번과 9번을 충족한다.

원천:

- 전: 작업 이벤트는 두 원천(작업 문서 이력 + QA 결정)을 합치느라 dedup이 필요했지만, 기획서 결정은 원천이 결정 문서 하나뿐이다.
- 후: 작업 이벤트는 작업 문서 이력과 QA 결정 두 곳에서 데이터를 모은다. 그래서 작업 이벤트에는 중복 제거가 필요했다. 기획서 결정은 데이터 출처가 결정 문서 하나뿐이다.

## 안전 규칙

- `.workflow/.runtime/migration.lock`이 존재하면 모든 외부 쓰기를 멈춘다.
- 앱은 활성 lease가 있으면 문서 마이그레이션을 실행하지 않는다.
- 앱 업데이트와 프로젝트 문서 마이그레이션은 별도 작업이다.
- 알 수 없는 메타데이터는 보존한다.
- 사용자 결정과 LLM 원문을 같은 파일에서 동시에 수정하지 않는다.
- 외부 LLM은 작업 시작 시 `.workflow/rules/workflow.md`를 읽고, 실제 작업 전에 대상 문서를 lease로 선점한 뒤 작업 중 상태(`draft`/`in_progress`)부터 기록한다.
- 기획서 `user_review`는 사용자 선택 대기 상태이며, 외부 LLM이 승인·수정 요청·폐기를 대신 기록하지 않는다.
