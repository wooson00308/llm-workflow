# 규격 준수 비용 측정

역할 세션 하나가 실제 구현과 무관하게 반복해서 읽는 문서의 양을 재는 방법과, SPEC-049의 변경이
반영되기 전에 측정한 기준값을 적는다. 같은 명령을 나중에 다시 실행하면 변경 뒤의 값과 같은 기준으로
비교할 수 있다.

## 측정 대상

역할마다 읽는 문서가 다르므로 기획자, 아키텍트, 개발자를 각각 잰다. 역할별로 다음 두 묶음의 바이트
수를 합산한다.

### 착수 문서

착수 절차가 언제나 읽게 하는 문서다. 세 역할이 같은 구성이고 역할 계약 하나만 다르다.

- `.workflow/project.yml`
- `.workflow/rules/workflow.md`
- `.workflow/rules/roles/<역할>.md`
- 활성 워크플로의 `workflow.yml`
- 활성 워크플로의 `README.md`

문서 수가 늘어도 이 묶음은 늘지 않는다. 계약 본문이 길어질 때만 늘어난다.

### 대조 문서

자격 확인 도구가 대상 문서를 알려주지 않기 때문에, 세션이 대상을 찾기까지 스스로 대조해야 하는
문서군이다. 역할별로 다음과 같다.

| 역할 | 대조하는 문서군 |
| --- | --- |
| 기획자 | `ideas/`, `specs/`, `decisions/` |
| 아키텍트 | `decisions/`, `tasks/` |
| 개발자 | `tasks/`, `.workflow/.runtime/leases/` |

각 디렉터리의 바로 아래 문서만 센다. 기획서·작업 문서·결정 문서는 `.md`, 선점 파일은 `.yml`이다.
보고서는 어느 역할의 대조 대상도 아니지만, 문서가 어디에서 늘어나는지 함께 보려고 문서군 표에만
출력한다. 역할별 합계에는 들어가지 않는다.

## 환산 기준

바이트 수를 2바이트당 1토큰으로 환산한다. SPEC-049의 배경 절이 한국어 문서를 약 2바이트당 1토큰으로
환산한 값을 인용했고, 그 값과 비교할 수 있도록 같은 기준을 쓴다.

이 환산은 근사값이다. 그래서 스크립트는 환산 기준을 결과에 함께 출력한다(사람이 읽는 표의 머리말과
기계가 읽는 출력의 `bytesPerToken`). 나중에 기준이 바뀌어도 바이트 수를 다시 환산해 값을 해석할 수
있다.

## 실행 방법

```sh
# 작업 트리의 현재 상태를 잰다
node scripts/measure-compliance-cost.mjs

# 특정 커밋 시점의 상태를 잰다
node scripts/measure-compliance-cost.mjs c1449d8398ebee47e3ca46663fd99bcc10b090e0
node scripts/measure-compliance-cost.mjs HEAD
```

출력은 두 부분이다. 앞부분은 사람이 읽는 표이고, `--- JSON ---` 줄 다음부터는 기계가 읽는 JSON이다.
나중 비교를 손으로 옮겨 적지 않도록 두 형태를 함께 낸다. JSON만 저장하려면 그 줄 이후만 잘라내면
된다.

```sh
node scripts/measure-compliance-cost.mjs HEAD | sed -n '/^--- JSON ---$/,$p' | tail -n +2 > cost.json
```

이 스크립트는 `npm run check` 같은 검사 명령에 넣지 않는다. 통과와 실패를 가르는 검사가 아니라 값을
관찰하는 도구이며, 검사 명령 구성도 이번 작업에서 바꾸지 않았다.

없는 커밋 식별자를 주면 어떤 값을 확인하지 못했는지 적힌 오류로 끝난다. 커밋에 `.workflow`가 아직
없던 시점을 지정한 경우에도 등록 문서를 찾지 못했다는 오류로 끝난다. 이 저장소에서는 `c4ff7da`부터
`.workflow`가 커밋에 들어 있다.

## 결과 해석 방법

- 값은 상한이다. 대조 문서를 전부 끝까지 읽는다고 가정하고 바이트를 합산한다. 실제 세션은 후보를
  추릴 때 문서의 앞부분만 읽기도 하므로, 실제 소비량은 이 값보다 작을 수 있다. 변경 전후를 같은
  가정으로 비교하는 것이 이 측정의 목적이다.
- 착수 비용과 대조 비용을 나눠 본다. 착수 비용은 문서 수와 무관한 고정 비용이고, 대조 비용은 문서
  수에 비례해 늘어난다. SPEC-049가 자격 확인 도구를 넓히려는 이유가 두 번째 항목이므로, 변경 뒤에는
  대조 비용 쪽이 줄어드는지 본다.
- 문서 수를 함께 본다. 바이트가 늘었을 때 문서가 늘어서인지 문서 하나가 길어져서인지 문서군 표로
  구분할 수 있다.
- 작업 트리 측정과 커밋 측정은 대상이 다르다. 작업 트리 측정은 아직 커밋되지 않은 문서까지 세고,
  커밋 측정은 그 커밋에 들어 있는 파일만 센다.
- 선점 파일이 있는 `.workflow/.runtime/`은 저장소에서 제외된 런타임 상태라, 커밋 측정에서는 언제나
  0으로 나온다. 개발자 역할의 선점 파일 비용은 작업 트리 측정에서만 보인다. 이 저장소에서 선점 파일
  세 개의 크기는 501바이트로, 다른 항목에 비하면 무시할 수 있는 크기다.
- 같은 입력으로 두 번 실행하면 같은 값이 나온다. 커밋 식별자를 준 실행은 언제 실행해도 같은 값이고,
  인자 없는 실행은 작업 트리가 그대로일 때 같은 값이다.

## 변경 뒤에 다시 잴 때

1. SPEC-049의 변경이 병합된 커밋 식별자를 확인한다.
2. 그 식별자로 같은 명령을 실행한다.
3. 위 기준값과 비교할 때는 역할별 합계만 보지 말고 착수와 대조를 나눠 본다. 이번 기획이 줄이려는
   것은 대조 비용이고, 역할 계약에 문장이 추가되면 착수 비용은 오히려 조금 늘어난다.
4. 문서 수가 그사이에도 계속 늘어나므로, 절감 여부는 같은 문서 수 조건이 아니라 문서 하나당 대조
   비용의 변화로 읽는 편이 정확하다.
