- 대상 선정: `.workflow` 공통 규칙대로 `project.yml` → `workflow.md` → `roles/developer.md`
  순으로 읽고 `todo`인 TASK-007 하나를 lease(`.runtime/leases/TASK-007.yml`)로 선점한 뒤
  `in_progress`로 옮기고 착수했다. 선행 TASK-003·004·005·006은 모두 `completed`.

### 핵심 결정

- 쓰기 커맨드는 `install_heartbeat_jobs` 하나. 설치·토글·편집이 모두 "역할 3종 상태를 통째로 다시
  쓴다"는 같은 연산이라 나누지 않았다. 부분 갱신 커맨드는 최종 파일 형태가 호출 순서에 의존한다.
- 실행 순서는 검증 → 조건 스크립트 설치 → 관리 블록 갱신. 스크립트가 먼저인 이유는 조건 검사 실패가
  하트비트에서 skip이라, 없는 스크립트를 가리키는 잡은 "아무 일도 안 일어남"으로만 보이기 때문.
- 순서를 지키려면 쓰기 없는 검증 진입점이 필요해 `heartbeat_jobs.rs`에 `validate_role_jobs`를
  추가했다(기존 `validate_settings` 재사용, 판정 로직 변경 없음). 작업 문서 범위 밖 파일이라
  보고서에 사유를 남겼다.
- `HeartbeatState`에 `writeError`를 분리했다. 기존 `error`(조회 실패)에 담으면 2.5초 폴링이
  덮어써서 사용자가 읽기 전에 사라진다.
- 확인 절차는 `useArmedConfirm`(2단계 무장)이 아니라 별도 확인 화면. R6이 요구하는 것은 실수 클릭
  방지가 아니라 대상 경로와 변경 요지의 실제 표시다.
- 관리 블록이 비어 있으면 역할 3종을 켠 상태로 시작한다. R3의 "설치 시 3종을 기본값으로 기록"이
  그것이고, 하나라도 설치된 뒤부터는 "블록에 없음"이 곧 "꺼짐"이다.
