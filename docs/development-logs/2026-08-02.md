### 핵심 결정

- 쓰기 커맨드는 `install_heartbeat_jobs` 하나. 설치·토글·편집이 모두 "역할 3종 상태를 통째로 다시
  쓴다"는 같은 연산이라 나누지 않았다. 부분 갱신 커맨드는 최종 파일 형태가 호출 순서에 의존한다.
- 실행 순서는 검증 → 조건 스크립트 설치 → 관리 블록 갱신. 스크립트가 먼저인 이유는 조건 검사 실패가
  하트비트에서 skip이라, 없는 스크립트를 가리키는 잡은 "아무 일도 안 일어남"으로만 보이기 때문.
- 순서를 지키려면 쓰기 없는 검증 진입점이 필요해 `heartbeat_jobs.rs`에 `validate_role_jobs`를
  추가했다(기존 `validate_settings` 재사용, 판정 로직 변경 없음). 작업 문서 범위 밖 파일이라
  보고서에 사유를 남겼다.
- `HeartbeatState`에 `writeError`를 분리했다. 기존 `error`(조회 실패)에 담으면 2.5초 폴링이
  덮어써서 사용자가 읽기 전에 사라진다.
- 확인 절차는 `useArmedConfirm`(2단계 무장)이 아니라 별도 확인 화면. R6이 요구하는 것은 실수 클릭
  방지가 아니라 대상 경로와 변경 요지의 실제 표시다.
- 관리 블록이 비어 있으면 역할 3종을 켠 상태로 시작한다. R3의 "설치 시 3종을 기본값으로 기록"이
  그것이고, 하나라도 설치된 뒤부터는 "블록에 없음"이 곧 "꺼짐"이다.

### 핵심 결정과 근거

- 설치 커맨드는 자기 연동의 desired state만 받고, 관리 블록 전체는 서비스가 만든다. 카드가 남의 연동 값을
  payload에 실으면, 화면이 아직 읽지 못한 값을 저장 시점에 되돌려 쓰는 사고가 난다.
- 다른 연동의 잡은 블록에서 읽은 편집 가능 값(`interval`·`max_per`·`model`)으로 다시 만든다. 앱 소유 필드는
  항상 앱이 다시 만든다. 블록에 없는 잡은 되살리지 않는다. 그래서 네 조합이 모두 유효하다.
- 보존 대상 잡의 값이 검증을 통과하지 못하면 `PreservedJob { job, source }`로 실패하고 아무 파일도 쓰지 않는다.
  조용히 기본값으로 되돌리면 사용자가 손으로 적은 값이 저장 한 번에 사라진다.
- 잡 순서를 연동 목록 순서(역할 3종 → dream)로 고정했다. 요청 순서에 맡기면 같은 상태가 설치 이력에 따라
  다른 바이트가 되고, 멱등 판정이 매번 파일을 다시 쓰게 된다.
- dream 설치 경로는 조건 스크립트를 쓰지 않는다. 조건이 `dream-prep`이라 앱 관리 스크립트가 필요 없고,
  "dream만 설치" 상태에서 프로젝트 로컬에 파일이 생기면 안 된다.
- `IntegrationsState.writeError`를 `{ integration, message }`로 바꿨다. 단일 문자열이면 dream 쓰기 실패가
  하트비트 카드에 "역할 잡을 쓰지 못했습니다"로 표시된다. 필터는 섹션이 하고 카드 계약은 그대로 뒀다.
- dream 카드는 검증 규칙·라벨·기본값을 자기 안에 둔다. 완료 조건 3이 하트비트 전용 코드 재사용 금지를
  확인 대상으로 삼는다. 공유하는 것은 연동 골격과 앱 공용 `ModelField`뿐이다.
