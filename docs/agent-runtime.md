# 에이전트 런타임 운영

앱의 에이전트 화면은 별도로 배포되는 Claude Heartbeat 런타임을 사용한다. 앱은 런타임의 내부 파일이나
데이터베이스를 직접 해석하지 않고 버전화된 JSON 계약만 호출한다. 런타임은 Claude와 Codex CLI를
실행하지만 provider SDK나 실제 인증 비밀을 포함하지 않는다.

## 버전 호환과 업데이트 순서

| 앱 버전 | 지원 런타임 | API 주 버전 | 배포 target |
| --- | --- | --- | --- |
| 0.1.11 | 0.9.0 이상 1.99.99 이하 | 1 | macOS universal, Linux x86_64, Windows x86_64 |

런타임 릴리스가 먼저 target별 압축 파일과 manifest를 게시하고 앱 릴리스가 그중 현재 운영체제용 파일
하나를 내려받는다. 앱 릴리스는 manifest의 target, 버전, API 주 버전, 전체 파일 크기와 SHA-256을
검증한 다음 배포물의 실제 `agent contract` 응답을 앱의 지원 범위와 대조한다. 이 검사가 실패하면
Tauri bundle과 게시 단계는 시작되지 않는다.

업데이트는 새 런타임을 별도 버전 디렉터리에 설치하고 검증한 뒤 stable launcher를 전환한다. 실행 중
작업이 있으면 먼저 영향 범위를 확인한다. 디스크의 설치 버전과 실제 실행 중 버전이 다르면 서비스를
재시작해야 하며, 앱은 그 전까지 새 실행을 호환 상태로 표시하지 않는다.

새 런타임이 설치본에 도달하는 길은 둘이다. 첫째, 앱 릴리스에 실려 온 번들 런타임이 설치본보다 새
버전이면 자동으로 장착된다. 둘째, 고급 설정의 실행 환경에서 게시된 최신 런타임을 조회해 앱 릴리스
없이도 내려받아 설치할 수 있다. 내려받은 배포물은 릴리스 워크플로의 staging과 같은 규약으로 풀리고
(한 겹 걷기, manifest 자리 확인, launcher 실행 비트 복원), 그 뒤로는 번들 설치와 같은 검증·설치·
전환 경로를 지난다. 앱 지원 범위 밖의 게시본은 내려받기를 열지 않고 앱 업데이트로 안내한다.

## 격리 작업 사본과 개발 역할 실행

개발 역할 세션은 태스크마다 준비된 별도의 작업 사본에서 구현한다. 그 사본을 준비하는 것은 런타임이고,
앱은 런타임이 그 기능을 갖췄는지를 버전으로 확인한다. 격리 작업 사본을 다룰 수 있는 런타임의 아래
끝은 0.10.0이며, 이 값의 정본은 `src-tauri/src/domain/agent_runtime.rs`의
`ISOLATION_CAPABLE_RUNTIME_VERSION`이다.

설치된 런타임이 그 버전보다 낮거나 버전을 읽지 못하면, 개발 역할 슬롯이 하나라도 들어 있는 실행 계획
요청은 받아들여지지 않고 런타임 갱신 안내가 돌아간다. 요청에 개발 역할이 섞여 있으면 요청 전체를
받아들이지 않으며, 개발 역할을 뺀 요청은 그대로 처리된다. 기획과 아키텍처 실행, 설치·갱신·진단
경로는 이 판정의 영향을 받지 않는다.

앱과 함께 배포되는 런타임은 0.9 계열이라 아직 이 버전에 이르지 않았다. 따라서 0.10.0 이상의 런타임이
게시되어 설치되기 전까지는 앱 화면에서 개발 역할 실행을 시작할 수 없고 갱신 안내만 나온다. 격리가
적용된다고 생각한 사용자가 실제로는 공유 작업 공간을 그대로 쓰게 되는 상태를 막기 위한 의도된
정지다.

## 실행 수명과 플랫폼 경계

- 앱 창이나 앱 프로세스를 종료해도 등록된 사용자 서비스와 이미 시작한 CLI 프로세스는 계속 실행된다.
- macOS LaunchAgent는 로그인한 사용자의 세션에서 RunAtLoad와 KeepAlive로 복구한다. 로그아웃 중 실행은
  보장하지 않으며 다시 로그인한 뒤 서비스를 복원한다.
- Linux systemd user service는 Restart 정책으로 복구한다. 로그아웃 뒤에도 실행하려면 해당 계정에
  linger가 켜져 있어야 한다.
- Windows Task Scheduler는 로그인 트리거, RestartOnFailure, 중복 인스턴스 금지 정책으로 복구한다.
- 운영체제 재시작이나 사용자 재로그인 뒤 런타임은 SQLite의 큐와 반복 정책을 먼저 읽는다. 저장된 PID와
  프로세스 생성 신원이 모두 일치할 때만 기존 실행을 다시 감시한다.

## 자동 배정과 즉시 감지

- 프로젝트의 `automationEnabled`가 참일 때만 dispatcher가 해당 프로젝트의 `.workflow`를 감시한다.
- 파일 변경은 500ms 동안 한 번으로 묶어 다시 판정한다. 감시가 실패해도 자동 배정 자체는 실패로
  기록하지 않고, 역할별 `pollIntervalSeconds`(기본 5분)를 안전 확인 주기로 사용한다.
- 자격 후보 목록은 읽기 전용이다. 실제 실행 직전에만 프로젝트 예약 도구가 자격을 다시 확인하고 lease를
  원자적으로 잡는다. 대상이 없으면 실행·오류·quota 기록을 만들지 않고 정상 대기한다.
- 프로젝트 사이는 마지막 배정이 오래된 순서, 한 프로젝트 안에서는 마지막 배정이 오래된 역할 순서로
  빈 자리를 나눈다. 역할 내부 작업 순서는 프로젝트의 워크플로 계약이 계속 소유한다.
- 사용자 승인과 QA 관문은 자동 배정 대상이 아니다. 앱은 이를 `내 선택 대기`로 따로 보여준다.

릴리스 CI는 세 운영체제에서 같은 계약 fixture로 manifest, 호환 판정, 상태의 세 값 논리를 검사한다.
실제 서비스 등록·강제 종료·자동 재시작·해제는 각 플랫폼 릴리스 환경의 smoke test에서 수행하며,
서비스 관리 기능이 없는 환경은 성공으로 건너뛰지 않고 환경 오류로 다룬다. 해제 단계는 성공·실패와
관계없이 실행해 테스트 등록물을 남기지 않는다.

## 실행 권한 동의

동의는 앱과 런타임이 나눠 맡는다. 앱은 고지 화면과 상태 표시, 동의와 철회 조작을 담당하고, 런타임은
프로젝트별 기록을 보관하며 새 실행을 시작하기 직전에 유효한 동의를 확인한다. 앱을 닫아도 자동 배정이
이어지므로 기록의 정본은 런타임에 둔다. 앱은 자기 사본을 만들지 않는다.

앱은 프로젝트 설정을 읽을 때 동의 상태를 함께 받는다. 상태는 `granted`, `required`, `unsupported`,
`unreadable` 넷 중 하나이며, 동의한 고지 버전과 동의 시각, 런타임이 요구하는 고지 버전이 함께 온다.
동의를 남기고 지우는 두 명령은 프로젝트 식별자를 싣고, 동의는 사용자가 읽은 고지 버전을 함께 싣는다.
동의 시각은 런타임이 스스로 읽으므로 앱이 보내지 않는다.

**동의 상태를 읽지 못한 것은 동의로 추정하지 않는다.** 런타임이 이 명령을 모르면 `unsupported`,
그 밖의 이유로 확인하지 못하면 사유를 실은 `unreadable`이 되며, 어떤 실패도 `granted`가 되지 않는다.
동의 확인이 실패해도 설정과 provider 진단과 실행 가능 여부는 평소대로 조회된다. 동의를 다루는 두
명령은 설정 저장과 같은 규칙을 따라, 호환되지 않는 런타임에는 요청을 보내지 않는다.

## 멈춤과 취소의 차이

- 프로젝트 일시 정지는 그 프로젝트의 새 배정만 멈춘다. 이미 실행 중인 프로세스와 다른 프로젝트는
  계속 동작한다.
- 개별 실행 취소는 사용자가 확인한 실행의 프로세스 트리를 종료하고 lease를 반납한다. 두 단계 중 하나라도
  실패하면 성공으로 표시하지 않고 복구 필요 상태로 남긴다.
- 기기 서비스 정지는 dispatcher 전체를 멈춘다. 새 배정은 모든 프로젝트에서 중단되지만 이미 분리된
  provider 프로세스는 개별 취소 절차 없이 종료됐다고 가정하지 않는다.

## 인증과 비용

Claude와 Codex 인증은 각 CLI가 소유한다. 앱과 런타임은 로그인 토큰, API 키, 전체 환경 변수나 전체
prompt를 저장하지 않는다. 사용자는 각 CLI에서 직접 로그인하고 에이전트 화면의 provider 진단으로
설치, 로그인, 권한, 버전, 사용 제한 상태를 확인한다.

Claude CLI에 API 과금 경로를 바꿀 수 있는 환경 변수가 있으면 시작 확인 화면에서 별도 동의를 요구한다.
역할별 최대 병렬 인원이나 반복 실행을 높이면 여러 유료 세션이 동시에 시작될 수 있다. 실행 상한은 비용
한도가 아니며 provider의 quota를 우회하지 않는다.

## 복구 필요 상태

1. 에이전트 화면에서 실패 단계와 남은 정리 단계, 설치 버전과 실행 중 버전을 확인한다.
2. 실행 PID와 생성 신원이 일치하는지 확인한다. 불확실한 PID는 종료하거나 이어받지 않는다.
3. 프로세스 종료가 남았으면 해당 실행의 취소를 다시 확인한다. lease 반납만 남았으면 workflow lease
   소유권과 만료 시각을 확인한다.
4. 설치 버전과 실행 중 버전이 다르면 실행 중 작업의 영향을 확인한 뒤 런타임 서비스를 재시작한다.
5. manifest나 API 주 버전이 다르면 현재 앱이 지원하는 런타임으로 다시 설치한다.
6. 복구 뒤 상태를 새로 읽어 같은 run ID가 중복 시작되지 않았고 새 PID만 감시되는지 확인한다.

## 기존 Heartbeat와 Dream

기존 `jobs.d`, 일반 Heartbeat 잡, 실행 이력은 그대로 유지한다. 옮길 수 없는 역할 설정은 마이그레이션
미리보기의 unresolved 목록에서 사용자가 확인한 뒤에만 새 설정으로 저장한다. 앱의 전용 연동 화면과
Dream 설치 API는 제거했다. 외부 Dream 스킬·잡·파일은 삭제하거나 수정하지 않으며 새 에이전트 역할,
provider 목록, 큐로도 옮기지 않는다. Dream 설치 여부는 새 런타임의 설치와 실행을 막지 않는다.

## 사용자 확인

실제 계정 확인은 자동 CI와 분리한다. Claude CLI와 Codex CLI에서 각각 작은 작업 하나를 실행해 성공
상태와 구조화 로그가 화면에 나타나는지 확인한 뒤 실행 중 작업 하나를 취소한다. 이 과정에서 토큰, API
키, 전체 prompt를 복사하거나 첨부하지 않는다. CLI 미설치, 로그인 필요, 권한 부족, 사용 제한, 시간
초과, 취소가 서로 다른 안내로 표시되는지도 확인한다.
